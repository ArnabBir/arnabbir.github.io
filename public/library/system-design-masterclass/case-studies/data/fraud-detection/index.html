    Real-Time Fraud Detection¶

    1. Interview roadmap¶

    Design a payment risk platform that returns ALLOW, CHALLENGE, or BLOCK before authorization, then detects slower fraud patterns and feeds confirmed outcomes back into models. We will define decision accountability, estimate load and latency, design online features and rules/models, then cover event time, case management, replay, consistency, degradation, and privacy.

    2. Product framing¶

    Fraud detection minimizes expected loss while controlling false declines and customer friction. It does not move money; the payment orchestrator owns authorization. The platform supplies a versioned decision and evidence. Some facts, such as chargebacks, arrive weeks later, so low-latency decisions and retrospective learning have different clocks.

    Assume card and wallet payments across regions. Regulatory screening is adjacent but separate. Manual investigators review selected cases. A block policy must be explainable and reversible; a model score alone is not the audit record.

    3. Requirements¶

    Functional¶

    • Score payment attempts using transaction, account, device, merchant, and graph signals.
    • Execute deterministic rules and versioned models.
    • Return reason codes and required challenge.
    • Update velocity features within seconds.
    • Ingest chargebacks, authentication outcomes, and investigator labels.
    • Create cases, replay decisions, and support shadow policies.

    Non-functional¶

    • 100,000 decisions/second peak; p99 under 80 ms with 99.99% availability.
    • No duplicate attempt may inflate velocity counters.
    • High-risk emergency rules propagate globally in under 30 seconds.
    • Decisions and evidence remain auditable for the required retention period.
    • Graceful degradation must be explicit by product and risk tier.

    4. Correctness invariants¶

    1. A caller-scoped payment_attempt_id pins one policy version and one effective decision; retries cannot select a newer policy.
    2. Feature values used, rule/model versions, threshold, decision, and reasons are durably recorded.
    3. Duplicate or reordered events do not double-increment velocity features.
    4. Features respect event time and never use information learned after the decision in replay evaluation.
    5. A request never mixes policy artifacts: it pins one immutable bundle even while a fleet canary runs multiple versions.
    6. Fail-open or fail-closed behavior is configured and audited per instrument, amount, and regulation.

    5. Capacity estimates¶

    At 100,000 peak decisions/second and 4 KB request plus evidence, ingress is 400 MB/s. Sustaining that peak for 30 days produces 1.037 PB before compression, replication, and indexing; actual retention uses measured average rate, not peak. Keep a narrow query index and archive full evidence in object storage. Ten velocity reads per request require one million reads/s; three writes add 300,000 writes/s, before retries and stream maintenance.

    With an 80 ms p99, reserve about 10 ms gateway, 25 ms parallel feature fetch, 10 ms rules, 15 ms model, 10 ms persistence/network, and 10 ms margin. Cross-region calls do not fit. Models and hot features must be local. Expensive graph computation is precomputed; the request path fetches compact signals.

    These are stage deadline allocations, not additive p99 measurements: component p99s do not generally sum to end-to-end p99. Measure correlated feature stalls, audit latency, and queued requests together under the full workload. A feature group's deadline includes pool wait and retries, not just service execution.

    6. Entities and data model¶

    RiskRequest(attempt_id, account_id, merchant_id, device_id, amount_minor,
            currency, event_time, channel, context)

         feature_snapshot_ref, decided_at, degraded_flags)

    Amounts use integer minor units with currency. Raw risk events and decisions are immutable. Feature stores, graph indexes, and case search are projections. Investigators append state transitions and notes rather than rewriting prior evidence.

    7. Interfaces¶

    POST /v1/risk/decisions
Idempotency-Key: payment-attempt-123
{ "attemptId":"...", "amount":{"minor":250000,"currency":"INR"}, ... }

200 { "outcome":"CHALLENGE", "decisionId":"...", "policyVersion":81,
      "reasons":["DEVICE_NEW","VELOCITY_HIGH"] }

POST /v1/risk/events
POST /v1/cases/{id}/transitions

    The decision API is synchronous. First conditionally create a caller-scoped attempt record containing the canonical request hash, pinned policy version, and PENDING state. A retry reads this record before looking up the currently active policy; changed payloads conflict. Workers compute under the stored version and conditionally finalize one decision. A losing worker returns the committed winner, not its own computation; an unfinished attempt returns an explicit retryable pending outcome. Event APIs are durable asynchronous ingestion with stable IDs. Case transitions require expected version to prevent investigators overwriting concurrent work.

    The API fetches independent feature groups in parallel, evaluates one pinned policy bundle, persists the decision, and returns. Streaming updates near-real-time velocities. Batch jobs create graph and long-horizon features, training sets, and reconciliation reports.

    9. Decision execution¶

    Authenticate the caller, validate amount and event time, and first check the idempotency store. For a new attempt, pin the active policy bundle in its durable claim; for a retry, load the bundle already stored in that claim. Fetch account, device, merchant, and network features with deadlines. Rules can immediately block impossible states or require strong authentication; the model estimates risk for remaining traffic. A deterministic combiner maps evidence to outcome.

    sequenceDiagram
    autonumber
  participant P as Payment service
  participant R as Risk API
  participant F as Feature store
  participant E as Rules/model
  participant D as Decision store
  P->>R: score(attempt_id)
  R->>D: lookup or claim scoped attempt, hash, pinned policy
  alt terminal decision exists
    D-->>R: prior decision
  else new claim or resumable PENDING attempt
    R->>F: parallel feature batch
    F-->>R: values + ages
    R->>E: pinned bundle + features
    E-->>R: outcome + reasons
    R->>D: conditional finalize under attempt version
    D-->>R: committed winner or pending outcome
  end
  R-->>P: decision

    Persist evidence before returning a decision, as required by invariant 2. A replicated append log can replace the decision store only if attempt claims and finalization are serialized by one fenced partition owner with replayable deduplication; an offset plus a read-through cache alone cannot prevent concurrent conflicting decisions. Never recompute a retry under a newer policy without an explicit new attempt. On recovery, retain the pinned bundle or escalate the pending attempt rather than silently switching versions.

    10. Deep dive: velocity features and event time¶

    Examples include payments per card in 10 minutes, distinct accounts per device in 24 hours, and failed authentication amount per merchant in one hour. Stream processors deduplicate event IDs and update fixed event-time buckets. Querying a window sums current buckets. Expiration subtracts old buckets; exact distinct values use bounded sets for small windows and sketches when approximation is acceptable.

    A payment may be scored before its accepted event updates the stream. To avoid a burst slipping through, the decision path performs an atomic reservation/increment for critical short-window counters keyed by attempt ID. The stream later observes the reservation and does not increment twice. Less critical features tolerate seconds of lag.

    Late events revise historical features for training and investigation, but do not time-travel a completed decision. Replay asks what was known at decision time, using bitemporal records: event time and knowledge/receipt time. Watermarks close operational windows while retaining revisions for a configured horizon.

    11. Deep dive: rules, models, and policy rollout¶

    A policy bundle contains rule bytecode, model artifact, feature schema/defaults, thresholds, and degradation matrix. It is signed, immutable, validated offline, loaded into memory, and atomically activated. Rules return named evidence, not just booleans. Model explanations can provide bounded feature contributions but must not expose exploitable detail to customers.

    New bundles run on shadow traffic. Compare block/challenge rates, latency, missing features, decision flips, and later fraud labels. Canary by stable account hash, then expand. An emergency deny rule uses the same signed publication path with expedited approval and expiry; ad hoc database flags are too difficult to audit. Its independently monotonic emergency generation also gates new payment authorization, including reuse of an older ALLOW decision. Preserve the historical decision unchanged and record any current emergency veto separately. A freshness lease within the 30-second propagation bound makes disconnected authorities stop affected authorization; rollback of an ordinary bundle cannot roll back emergency blocks.

    12. Deep dive: delayed labels and reconciliation¶

    Authorization success is not a fraud label. Chargebacks arrive days later and may be disputed. Labels store source, observation time, event-effective time, and confidence. Training applies a maturity window and handles censored transactions. Investigator decisions supplement but do not overwrite network outcomes.

    Daily reconciliation joins payment attempts, risk decisions, actual authorization actions, challenges, and outcomes. It detects payments with no risk decision, callers that ignored BLOCK, duplicate decisions, missing audit payloads, and policy mismatches. Exceptions create cases. This reconciliation validates integration correctness independently of model quality.

    13. Partitioning and scaling¶

    Decision workers are stateless and scale by request rate. Feature keys partition by a hashed entity prefix. Hot merchants or devices use salted write buckets and read fan-in, but critical atomic account counters remain unsalted with strict rate controls. Co-locate regional replicas with scoring fleets.

    Event logs partition by primary entity while carrying all related keys; separate jobs update card, device, account, and merchant projections. This duplicates stream work but avoids one impossible ordering key. Graph features compute from immutable edges in batch and publish versioned snapshots.

    14. Consistency and idempotency¶

    Decision identity and policy activation need strong consistency. Most features are eventually consistent with recorded age. Critical reservations use linearizable conditional writes. Events are delivered at least once; ID retention exceeds retry and chargeback ingestion windows. Sink writes compare revisions. No claim of end-to-end exactly once is needed.

    Multi-region decision commands route a caller-scoped attempt to one fenced authority, normally the account's home region. Local replicas serve global merchant and device signals with bounded lag. During partition, a non-owner cannot durably finalize a competing decision; return an explicit unavailable/pending outcome or execute a separately identified, audited caller fallback. Quarantining conflicting decisions after both were returned would not preserve the one-decision invariant. Ownership transfer requires fencing and recovery of committed attempt claims before new decisions; local scoring latency therefore depends on keeping the caller near its authority.

    15. Reliability and overload¶

    • Feature group timeout applies its declared default and records degraded flags.
    • Model server failure falls back to deterministic rules, usually increasing challenges.
    • Policy load failure retains the last verified bundle.
    • Event lag freezes stale-sensitive features or tightens thresholds.
    • Audit append failure returns unavailable/pending rather than an unaudited finalized decision. High-value callers stop authorization; any lower-tier challenge fallback must be separately identified and durably audited by its owning caller.
    • A hot-key attack is rate-limited before it exhausts the feature store.

    Bulkheads separate merchants and feature groups. Requests have one bounded retry only when no decision is known. Load shedding prioritizes payment decisions over case search and shadow evaluation. Region evacuation uses tested policy and feature snapshots; recovery reconciles all attempts accepted during isolation.

    16. Security and privacy¶

    Use mTLS workload identity, tenant authorization, encryption, key rotation, field tokenization, and strict investigator roles. Separate decision evidence from raw personal data with reference-based access. Display access is audited. Retention differs for financial evidence and behavioral features. Subject deletion removes eligible behavioral data while legally retained decision records remain restricted.

    Protect model and rule endpoints from extraction; rate-limit scoring and reveal customer-safe reason families only. Policy publication requires code review, signed artifacts, dual approval for broad blocks, and a tamper-evident audit log.

    17. Observability and testing¶

    Measure end-to-end and per-stage latency, decision mix, score distribution, feature age/null/default rates, reservation conflicts, event and watermark lag, policy version coverage, caller compliance, fraud loss, false-positive proxies, challenge completion, and reconciliation exceptions. Slice by region, merchant, instrument, and policy while enforcing privacy thresholds.

    Tests include idempotent retry races, rule determinism, feature event-time boundaries, point-in-time leakage, malformed payload fuzzing, stale feature chaos, model timeouts, policy rollback, hot keys, and regional partitions. Replay historical manifests against old and candidate bundles. Red-team both adversarial input manipulation and investigator access.

    18. Tradeoffs¶

    • Synchronous fresh counters improve burst detection but add a latency and availability dependency; reserve only critical velocities and stream the rest.
    • Fail-open protects conversion but increases loss; fail-closed protects money but harms users. A risk-tier degradation matrix is better than one global answer.
    • A single opaque model is flexible but hard to audit; deterministic rules plus a model and reasoned combiner provide control.
    • Global strong feature consistency is too slow; local scoring with explicit staleness and reconciliation fits the latency budget.
    • Exact unique counts are costly; sketches are valid for model features, not deterministic regulatory thresholds unless error is accounted for.

    20. Interview questions¶

    1. Which features must be synchronously updated?
    2. How do you score when the feature store is unavailable?
    3. How do event time and knowledge time differ in model replay?
    4. How do you prove a caller enforced a block?
    5. How do you deploy an emergency rule safely?
    6. What partition key handles a device shared by many accounts?
    7. How do delayed chargebacks affect evaluation?

    21. L5 and L6 expectations¶

    An L5 candidate should produce a latency-budgeted online path, feature store, rules/model split, idempotent decisions, streaming velocities, failure fallback, and audit storage. An L6 candidate should define bitemporal replay, policy atomicity, critical reservations, caller reconciliation, label maturity, multi-region degradation, and governance around blocking decisions.

    22. Five-minute summary¶

    Place stateless regional risk workers in the payment path. A durable caller-scoped attempt claim pins a signed policy bundle, then workers fetch local features in parallel, evaluate explainable rules and a versioned model, combine them into allow/challenge/block, and durably finalize one winner with evidence. Retries resolve the attempt before consulting active policy. Critical burst counters reserve synchronously; other velocity and graph features update from an immutable event log with event-time buckets and idempotent revisions.

    Policies deploy through shadow, canary, atomic activation, and rollback. Missing dependencies follow an explicit risk-tier degradation matrix. Chargebacks and reviews are delayed, versioned labels, not immediate truth. Daily reconciliation verifies every payment had one decision and that the caller enforced it. Partition features by entity, salt hot aggregate keys, and keep scoring local rather than paying global coordination latency. The design's core is accountable decisions under uncertainty, not merely a high-AUC model.
