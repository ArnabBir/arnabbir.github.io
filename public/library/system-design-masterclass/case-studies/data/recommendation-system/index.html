    Recommendation System¶

    1. Interview roadmap¶

    Design a home-feed recommender for 100 million daily users. We will clarify objectives and safety constraints, estimate online and training load, separate candidate generation from ranking, then examine feature freshness, event-time training, experimentation, failures, privacy, and multi-region serving.

    2. Product framing¶

    For a user and context, return 50 eligible items likely to create long-term value. The system combines follows, collaborative similarity, content understanding, and popularity. It is not a single machine-learning model: it is a data and serving system whose output must remain useful when models or features fail.

    Out of scope are item creation, media delivery, and moderation internals. Moderation and inventory systems supply eligibility. The objective balances meaningful engagement, retention, creator diversity, and negative feedback rather than optimizing clicks alone.

    3. Requirements¶

    Functional¶

    • Record impressions, clicks, dwell, likes, follows, hides, and reports.
    • Generate candidates from several independent sources.
    • Rank, filter, diversify, and paginate recommendations.
    • Incorporate fresh activity within minutes and train models daily or hourly.
    • Support experiments, explanations, deletion, and model rollback.

    Non-functional¶

    • 1 million recommendation requests/second at peak, p99 under 200 ms.
    • 5 million engagement events/second, at-least-once delivery.
    • 99.99% availability; safe fallback if dependencies fail.
    • No blocked item served after a 10-second propagation SLO.
    • Reproducible training sets without future-data leakage.

    4. Invariants¶

    1. Every response contains only items eligible for that user, region, age policy, and request time.
    2. Pagination does not repeat an item within a feed session.
    3. Training features use information available at the example's event time, never future state.
    4. Model, feature schema, candidate-source, and policy versions are recorded for each impression.
    5. At-least-once events produce idempotent feature effects.
    6. User deletion removes personal online state and future training eligibility within policy deadlines.

    Recommendations are projections, not canonical state. Availability may use stale features, but safety cannot.

    5. Estimates¶

    At one million requests/second and 50 results, ranking 50 million final items/second is plausible; scoring the entire catalog is not. If each of five candidate sources returns 500 IDs, the ranker evaluates up to 2,500 candidates/request, or 2.5 billion scores/second, requiring lightweight models, batching, and regional fleets. A 5 KB response produces 5 GB/s before compression.

    Five million 200-byte events/second are 86.4 TB/day raw if sustained. Retain compressed immutable events in object storage and compact online features. For 500 million users with 10 KB online state, feature storage is 5 TB logical, or 15 TB at three replicas before overhead. Embeddings at 256 float16 dimensions consume 512 bytes each: one billion items require roughly 512 GB plus ANN indexes.

    6. Data model¶

    Interaction(event_id, user_id, item_id, type, event_time, received_time,
            request_id, position, model_version, consent_scope)

    Immutable interactions are canonical evidence. Online features, vector indexes, and session state are rebuildable projections. Offline tables use event-date partitions plus point-in-time snapshots. Personally identifying attributes are excluded or tokenized.

    7. Interfaces¶

    POST /v1/recommendations
{ "userId":"u1", "surface":"home", "sessionId":"s1", "cursor":"...", "limit":50 }

POST /v1/interactions
Idempotency-Key: e1
{ "requestId":"r1", "itemId":"i9", "type":"CLICK", "eventTime":"..." }

    The response includes requestId, opaque cursor, model version, and items with coarse explanation codes. Cursor state references a feed session and signed generation; clients cannot alter offsets. Interaction ingestion acknowledges after durable append. Batch APIs return per-record errors.

    The online path fans out candidate requests under strict deadlines, deduplicates IDs, fetches batched features, scores, applies policy and diversity, and stores session results. The offline path builds point-in-time datasets, trains and evaluates artifacts, then deploys through a registry.

    9. Candidate generation¶

    Independent sources improve coverage: recent items from followed creators, item-to-item ANN neighbors, user-embedding ANN retrieval, regional trends, editorial inventory, and exploration. Each receives a quota and 20-40 ms deadline. Partial results are acceptable. Candidate records include source and retrieval score for ranking features and diagnostics.

    ANN indexes are partitioned by language or broad market, replicated, and refreshed incrementally. New items enter a fresh-item index immediately and the main index after compaction. Cold users receive contextual popularity plus declared interests; cold items use content embeddings and exploration budget.

    Choosing and operating HNSW versus IVF/PQ¶

    HNSW keeps a navigable multi-layer proximity graph. It is a strong default for tens of millions of vectors per shard when high recall, low single-query latency, incremental insertion, and sufficient RAM matter. Build-time controls M set graph degree and memory, efConstruction trades build CPU for graph quality, and query efSearch trades latency for recall. Inserts are online, but deletes become tombstones and repeated embedding updates create graph churn, so replicas periodically rebuild from a pinned snapshot and swap generations.

    IVF partitions vectors into trained coarse centroids; a query probes nprobe nearby lists. Product quantization stores compact residual codes and computes approximate distances, often reducing vector memory by an order of magnitude. IVF/PQ fits hundreds of millions or billions of mostly stable vectors where memory cost and scan throughput dominate, but centroid/codebook training, batch-oriented rebuilds, and weaker fresh-item behavior add complexity. A small exact or HNSW delta index absorbs new and updated items; queries merge its results with the immutable IVF/PQ base, and compaction folds the delta into the next generation.

    Choose from measurements on production-shaped vectors, filters, and hardware, not catalog size alone. Establish exact top-K neighbors for a stratified query sample, then sweep HNSW efSearch or IVF nprobe and PQ code size. Record recall@K, p50/p99 latency, queries/core, resident bytes/vector, build time, update visibility, filtered-query recall, and merge overhead. Recommendation evaluation then checks whether retrieval loss changes downstream outcomes; ANN recall is diagnostic, not the product objective.

    Worked ANN benchmark. For 100 million 256-dimensional vectors, raw float16 embeddings alone use 51.2 GB. Assume a hypothetical HNSW profile using 78 GB with recall@100 0.96 and p99 18 ms. A hypothetical 32-byte IVF/PQ profile uses 3.2 GB plus 0.8 GB of lists/centroids, with recall 0.90 and p99 11 ms at nprobe=16, or recall 0.95 and p99 31 ms at nprobe=64.     10. Ranking and serving¶

    A cheap pre-ranker reduces 2,500 candidates to 300; a richer ranker scores those; a deterministic post-ranker enforces safety, author caps, diversity, freshness, and already-seen suppression. A feed session stores a bounded ordered oversupply, perhaps 200 IDs, allowing cheap pagination and stable experiments. When exhausted, the next cursor generates more while carrying an exact bounded seen set. Atomically advance session generation, its seen set, and page publication so concurrent cursors cannot publish overlapping pages. Return the winning stored page on a retry. Set an explicit session length/expiry bound; a Bloom filter may suppress unseen items and an evicting set permits old repeats, so neither supports an unlimited exact no-repeat promise.

    Deadline budgets prevent retry storms. If ANN times out, use follows and trends. If online features fail, use cached user state and item priors. Every page, cached cohort and retry rechecks current eligibility, with backfill advancing past scanned positions. Enforce a policy-freshness lease within the 10-second removal bound and fail closed when it expires; push invalidation alone cannot guarantee that deadline. This gate also applies to non-sensitive blocked inventory and survives model rollback. Cache anonymous cohort lists, but personalized lists have short TTLs and must respect deletion.

    Feature and inference batching capacity¶

    The orchestrator deduplicates item IDs before feature access and sends one multi-get per storage shard, not one RPC per candidate. If 2,500 retrieved candidates collapse to 1,800 unique items spread over 16 shards, the request issues at most 16 parallel shard RPCs. At 1 million requests/s this logical workload is 1.8 billion item lookups/s, but microbatching 32 requests for up to 2 ms lets a feature worker deduplicate shared hot items across roughly 57,600 keys and amortize transport. Batch size is capped by bytes and deadline; batchers flush immediately for near-expiry requests.

    Inference follows the ranking cascade. Suppose pre-ranking 2,500 candidates costs 4 microseconds/candidate on one CPU core: that is 10 ms CPU/request or 10,000 CPU-seconds/s at 1 million requests/s. At 65% utilization, it needs about 15,385 cores before redundancy. The full ranker scores 300 candidates/request in batches of 64 requests, or 19,200 rows/batch. If an accelerator sustains 1.2 million rows/s at that shape, demand is 300 million rows/s, requiring 250 accelerators; 30% failure/rollout headroom raises this to 325. Measure queueing and padding because theoretical FLOPS do not establish serving capacity.

    Worked deadline budget. From a 200 ms deadline, reserve 20 ms for edge/network, 10 ms for serialization, and 20 ms fallback margin. Candidate fanout receives 40 ms, feature multi-get 35 ms, pre-rank 20 ms, full inference 45 ms, and policy/session work 10 ms. Fanout closes when its 40 ms stage allowance ends, not at a conflicting 35 ms cutoff; late sources are omitted without retry. These allocations sum to 200 ms but require end-to-end measurement to establish p99. Dynamic batchers use absolute request deadlines.

    Deterministic diversification¶

    Diversification is a constrained re-ranking stage after safety filtering. First enforce hard constraints such as eligibility, block lists, and maximum one item from a sensitive category. Then greedily select the item maximizing lambda * relevance - (1-lambda) * max_similarity_to_selected - author_penalty - exposure_penalty, subject to per-author, topic, format, and freshness quotas. Maximum marginal relevance is explainable and bounded for hundreds of candidates; a learned slate model can improve interactions but is harder to debug and must still pass the hard constraint layer.

    With pinned candidates, features, exposure state and policy, stable score quantization and item-ID tie-breaks make the algorithm deterministic. The committed session page supplies retry identity when those inputs change. Relaxation is explicit: if fewer than 50 items remain, relax soft topic targets, then format targets, but never safety or block constraints. Track unique authors/topics, concentration indexes, pairwise embedding similarity, freshness, relevance loss against the un-diversified list, and guardrail outcomes by cohort.

    Worked diversification example. The top five scores are three near-identical posts from author A at 0.94, 0.93, and 0.92, a different-topic post from B at 0.89, and a fresh post from C at 0.84. With an author cap of two and similarity penalty 0.20, an illustrative slate is A1, B1, C1, A2 if the actual pairwise similarities and remaining penalties make that greedy order win; scores and one penalty constant alone do not determine the order. In that slate, A3 is rejected by the cap. The slate gives up 0.03-0.08 pointwise score for broader coverage, and the impression records both raw rank and final selection reason.

    11. Deep dive: streaming and event-time features¶

    Stream processors deduplicate event_id and maintain features such as 10-minute topic clicks, 7-day creator affinity, and recent seen items. Fixed event-time buckets allow expiration by subtracting old buckets. Watermarks handle delayed clients; revisions carry (user, feature, event_time, revision) so stale writes cannot overwrite newer state.

    Late data may update durable offline features but should not unexpectedly reorder an active session. New requests use the latest valid feature snapshot; an existing page remains immutable. High-volume celebrity-item counters use salted partial aggregation. User keys distribute naturally but bot users receive quotas to protect state.

    The online and offline feature definitions share declarative transformations. Materialization differs, semantics do not. Monitoring compares sampled online values with point-in-time offline recomputation to detect training-serving skew.

    12. Deep dive: leakage-free training¶

    Training examples join an impression with outcomes in a defined label window. Each feature is looked up "as of" impression time. A daily snapshot joined by current value is wrong because it leaks later popularity or user behavior. Immutable manifests pin input partitions, feature definitions, label horizon, consent state, and code.

    Constrain knowledge time as well as event time: a correction backdated to yesterday but first available tomorrow was not available to yesterday's ranker. Feast's point-in-time join documentation distinguishes these conditions and documents created-timestamp filtering where supported. Retain an availability timestamp reflecting the online path and validate the chosen offline store's behavior, rather than assuming an event-time join prevents all leakage (accessed 2026-09-08).

    Negative examples come from impressed-but-not-engaged items, not arbitrary catalog items. Position and prior model influence are logged to reduce selection bias. Exploration traffic supplies less biased evidence. Delayed outcomes require waiting for label maturity or marking censored examples.

    13. Deep dive: experimentation and feedback loops¶

    Assignment is deterministic by user and experiment salt, with mutually exclusive layers for conflicting tests. Log assignment even when serving falls back. Guardrails include hides, reports, latency, creator concentration, and retention, not only CTR. Promotion requires statistical and operational review.

    Recommendations influence future data. Over-exploitation narrows inventory and starves challengers. Reserve controlled exploration slots, cap repeated exposure, and monitor exposure distribution. Models are rolled out shadow, then 1%, 10%, and broader. The registry can atomically return a surface to the last known-good artifact.

    14. Partitioning and consistency¶

    User features and sessions partition by user ID; item features and embeddings by item ID; ANN indexes by market and vector centroid. Replicate read-heavy item state. Cache feature batches close to rankers. Heavy users are bounded by feature TTL and event-rate quotas.

    Interactions and feature projections are eventually consistent. Session page creation uses conditional write so request retries return the same generation. Eligibility uses a strongly controlled source and push invalidation. Model registry promotion is strongly consistent; workers pin an artifact per request, preventing mixed-model scoring.

    15. Failures and multi-region strategy¶

    • Candidate timeout yields partial ranking with source quotas redistributed.
    • Feature-store outage uses bounded stale cache and baseline ranker.
    • Model load failure leaves the previous artifact active.
    • Event lag harms freshness but not request availability; surface lag explicitly.
    • Session-store outage can return a non-personalized cached feed with a new degraded session.
    • Bad features trigger circuit breakers based on null and distribution drift.

    Users have a home region for mutable features; events accepted elsewhere replicate there asynchronously. Regional serving uses local replicas and tolerates bounded staleness. Eligibility tombstones and model rollback distribute globally on priority channels. Raw logs replicate to the training region; a region failure does not retrain from partial data.

    Dual-index and model migration¶

    An embedding-model change alters the vector space, so new query vectors cannot safely search an old item index. Build index B from a complete item snapshot using model B, then continuously apply ordered embedding changes after the snapshot watermark. Keep model/index bundles explicit: (query_model_A, item_index_A) and (query_model_B, item_index_B). Workers never mix those halves. Readiness requires checksum and cardinality reconciliation, update lag within SLO, benchmark gates, and successful load on every serving shard.

    Shadow a sampled set of live queries against bundle B, logging latency, recall against an exact sample, candidate overlap, source yield, downstream score distributions, eligibility loss, and business guardrails. Canary traffic pins the whole request to one bundle and feed sessions retain that assignment. Ramp 1%, 10%, 50%, 100%; retain A until active sessions expire and rollback time passes. Rollback atomically changes the registry pointer, while dual-write continues long enough to avoid rebuilding under incident pressure.

  IA --> BA
  MB[Query model B] --> BB[Bundle B]

    Worked migration. Index B is built from snapshot offset 900 and catches up through offset 1,240 while live is at 1,250, so its lag is 10 events. Reconciliation finds 99,998,700 of 100,000,000 eligible items; the missing 1,300 exceed the 100-item gate, so shadowing may continue but canary serving cannot start. After repair reaches the gate, 1% canary traffic uses model and index B together. A latency regression rolls the bundle pointer back to A; no request sends model-B vectors to index A.

    Runaway-source overload containment¶

    A candidate source can become runaway by returning too many IDs, expanding fanout recursively, retrying, or consuming shared feature/inference capacity after its usefulness falls. Enforce source-specific concurrency, QPS, response-byte, candidate-count, and CPU budgets at both caller and callee. The orchestrator accepts only the first bounded, schema-valid response before the source deadline, truncates excess deterministically, and never retries within the same recommendation request. Bulkheads give core follows/trends and active ranking separate queues from experimental sources.

    Admission uses per-source token buckets plus a global cost budget measured in candidates entering each downstream stage. Circuit breakers trip on timeout, malformed-size, marginal-yield, and resource-saturation signals. Under pressure, shed shadow traffic, exploration sources, expensive ANN probes, and extra candidates in that order; preserve eligibility and the safe fallback. Autoscaling may follow sustained demand but is not the first response to positive feedback, because scaling every downstream service amplifies cost and recovery time.

    Use the Applied AI Systems track to extend this design into model pipelines, serving, vector retrieval, evaluation, adaptation, reliability, and governed data flywheels.

    Worked overload example. An experimental graph source normally returns 300 candidates for 10% of requests, or 30 million candidates/s. A bug returns 30,000 and retries twice, attempting 9 billion candidates/s. A 500-ID response cap, 50,000-request/s source token bucket, and no-retry rule limit admission to 25 million candidates/s; its isolated queue fills and the breaker opens. Other sources retain their reserved inference lanes, and affected requests redistribute quota to trends rather than exhausting the shared feature store.

    16. Security, privacy, and abuse¶

    Authenticate event producers, authorize internal feature access by purpose, encrypt stores, and audit model/data access. Consent is evaluated both at collection and dataset construction. Deletion writes a tombstone to online stores, embedding indexes, caches, and future training filters; immutable audit data is access-restricted and aged out according to policy.

    Adversaries may poison interactions or scrape recommendations. Apply device/account rate limits, trust-weight events, detect coordinated behavior, sign cursors, and avoid exposing raw scores. Safety policy cannot be overridden by model output.

    17. Observability and testing¶

    Track request latency by stage, candidate count/source/timeout, feature age and null rate, model score drift, eligibility-filter count, diversity, cache hit rate, session duplicates, event-time lag, online-offline feature parity, and business guardrails. Join sampled impressions to eventual outcomes by request_id.

    Tests include feature transformation parity, point-in-time leakage checks, deterministic session pagination, model contract tests, ANN recall benchmarks, chaos timeouts, stale eligibility tests, skewed event loads, and deletion end-to-end audits. Replay a fixed event manifest and assert feature hashes. Load-test fallback paths, since they receive the most traffic during incidents.

    18. Tradeoffs¶

    • Precomputing full feeds makes reads cheap but becomes stale and expensive for inactive users; online composition balances freshness and cost.
    • One large ranker may improve relevance but threatens latency; cascaded ranking spends computation selectively.
    • Fresh mutable features improve response but amplify instability; immutable sessions provide user-visible continuity.
    • Central global features simplify semantics but add WAN latency; home-region writes with local replicas fit bounded staleness.
    • Rich personal history can improve accuracy but increases privacy and deletion cost; use minimum necessary, TTL-bound features.

    21. L5 and L6 expectations¶

    An L5 candidate should separate retrieval, ranking, post-filtering, event collection, training, and online features; estimate fanout; explain caching, fallback, partitioning, and model rollout. An L6 candidate should reason about leakage, feedback loops, experimentation validity, feature parity, safety priority, privacy lifecycle, multi-region ownership, and degradation budgets.

    22. Five-minute summary¶

    Use several bounded candidate sources so no model must search the full catalog. Merge and deduplicate candidates, pre-rank cheaply, score a smaller set with versioned online features, then apply non-negotiable eligibility and deterministic diversity. Store immutable session pages for stable, duplicate-free pagination. Under dependency failure, return safe trends or cached cohorts rather than fail the request.

    Interactions enter an immutable log. Idempotent event-time processors update TTL-bound online features; the same definitions produce point-in-time offline histories. Training manifests pin data, labels, consent, schema, and code, preventing future leakage and enabling replay. Model artifacts move through offline checks, shadowing, canaries, and experiments with guardrails. Partition mutable state by user, item state by item, and ANN by market/centroid. The L6 insight is that recommendation quality depends as much on data semantics, safety, experimentation, and failure behavior as on model choice.
