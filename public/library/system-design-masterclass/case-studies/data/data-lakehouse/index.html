    Design a Data Lakehouse¶

    Interview Roadmap¶

    Clarify batch versus streaming ingestion, analytical workloads, freshness, governance, and compatibility. State snapshot and schema invariants before naming formats or engines. Begin with immutable columnar files plus a transactional table log and catalog. Then evolve for concurrent writers, compaction, partition evolution, metadata scale, isolated compute, multi-region recovery, and safe migrations.

    Product Framing¶

    A lakehouse provides warehouse-like tables and transactions over low-cost object storage while allowing multiple compute engines. Producers ingest files, database changes, and event streams. Analysts and applications run SQL against stable snapshots. Data owners publish schemas, quality expectations, retention, and access policy through a catalog.

    The object store is not the table: a table is a versioned set of data and delete files described by metadata. The catalog resolves names, ownership, and current metadata pointers. Compute is replaceable. Dashboarding, model training algorithms, and source-database capture are adjacent but outside the core design.

    Requirements¶

    • Ingest batch files and streams with replay, quarantine, and lineage.
    • Create, append, update, merge, and delete table data atomically by snapshot.
    • Support snapshot-isolated reads, time travel, schema and partition evolution.
    • Serve interactive SQL, scheduled ETL, and large scans on independent compute pools.
    • Compact small files, expire snapshots, collect orphans, and control cost.
    • Enforce row, column, tenant, residency, retention, and audit policy.
    • Scale to exabytes, millions of tables, and thousands of concurrent commits.

    Correctness Invariants¶

    1. A published table snapshot references only immutable, checksummed files that are durably readable.
    2. A commit atomically changes one table from expected metadata version to one new version; conflicting writers retry or fail.
    3. Readers pin a snapshot for the query and never observe a partial file set.
    4. A source record identity has at most one effective table mutation under its ingestion contract, despite replay.
    5. Schema field identity is stable and independent of display name or ordinal; incompatible reuse is rejected.
    6. Snapshot expiration never deletes files reachable from a retained snapshot, branch, tag, or active query lease.
    7. Catalog authorization gates new plans and credentials; already issued object capabilities expire or are revoked at the data-serving boundary within a declared deadline.

    Capacity Estimates¶

    Assume 5 PB/day raw ingestion, 50 million new data files/day before compaction, 100,000 tables, 100,000 peak queries, and 10,000 table commits/s. At 1 GB target files, 5 PB/day is five million files even after healthy packing. Listing object-store prefixes cannot be a planning primitive; manifests and statistics must prune work.

    A 10 PB fact table with 256 MB scan tasks has 40 million tasks if read completely, so query planning must prune partitions/files and aggregate manifests hierarchically. Metadata can dominate latency for small-file tables. Separate budgets for ingest bytes, commit rate, catalog QPS, planning CPU, object GETs, shuffle, and egress.

    Core Entities and Data Model¶

    Namespace(namespace_id, owner, properties, policy_version)
Table(table_id, name, format_version, current_metadata_ref, state)
Schema(schema_id, fields[(field_id,name,type,required)], compatibility)
PartitionSpec(spec_id, transforms[(field_id,transform)])
Snapshot(snapshot_id, parent_id, sequence, schema_id, spec_id,
         manifest_list_ref, summary, committed_at)
Manifest(manifest_id, entries[(file_ref,status,partition,stats,sequence)])
DataFile(file_id, uri, format, size, rows, bounds, checksum, encryption_key)
DeleteFile(file_id, type, target_scope, sequence, stats)
IngestionCommit(source_id, source_position_range, snapshot_id, request_hash)
QueryLease(query_id, snapshot_ids, expires_at)

    Files and snapshot metadata are immutable. The catalog's current pointer and table lifecycle are canonical mutable state. Caches, materialized views, file indexes, query results, and usage statistics are projections.

    APIs and Interfaces¶

    POST /v1/tables                                  {namespace, schema, partition_spec}
GET  /v1/tables/{id}/metadata?snapshot=...
POST /v1/tables/{id}/commits                     Idempotency-Key: <uuid>
     {expected_metadata_version, new_files, delete_files, source_positions}
POST /v1/tables/{id}/snapshots/{id}:tag
POST /v1/tables/{id}:expire-snapshots
POST /v1/queries                                 {sql, catalog, warehouse, idempotency_key}
GET  /v1/queries/{id}/results?cursor=...

    Engines usually use a table-format protocol rather than REST for every file. Commit requests include operation semantics, base snapshot, file checksums, and conflict scope. Result cursors bind query ID, result generation, and row offset; results expire explicitly. Object credentials are short-lived and restricted to files authorized by the planned snapshot.

    Catalog revocation alone cannot revoke a bearer URL already issued by object storage. For an immediate-stop requirement, route reads through a policy-enforcing gateway or use a tested storage-policy/credential revocation path; otherwise the exposure bound includes credential lifetime and in-flight reads. Amazon S3 presigned URL documentation explicitly permits repeated use until expiry and downloads that continue past expiry if started earlier (accessed 2026-09-08). Snapshot isolation is a table-format mechanism, not an authorization revocation mechanism.

    High-Level Architecture¶

    flowchart LR
    Sources[Files, streams, databases] --> Ingest[Ingestion plane]
    Ingest --> Stage[(Staging object storage)]
    Ingest --> Commit[Table commit service]
    Commit --> Catalog[(Catalog and metadata pointers)]
    Commit --> Lake[(Immutable data, delete, manifest files)]
    Users --> Gateway[SQL and API gateway]
    Gateway --> Planner[Query planner]
    Planner --> Catalog
    Planner --> Compute[Elastic compute pools]
    Compute --> Lake
    Catalog --> Maint[Compaction, expiry, quality]
    Maint --> Lake

    The control plane owns names, metadata pointers, policy, and workload admission. Data planes ingest and compute against immutable artifacts. This separation lets engines fail or scale without changing table truth.

    Core Requirement Flows¶

    Batch and Stream Ingestion¶

    Batch ingestion lands checksummed files in staging, validates schema and quality, writes target-sized columnar files, then commits them. Streaming workers checkpoint source positions only as part of or after successful table commit. A stable (source, partition, position range) deduplicates retries. Bad records enter a bounded quarantine with reason, schema version, and source identity; poison data does not block unrelated partitions.

    Query¶

    The planner resolves names and policy, pins table snapshots, reads manifest lists, prunes files using partition transforms and column bounds, and creates scan tasks. Workers read columnar ranges directly from object storage, push down predicates, shuffle only required columns, and write immutable result pages. A query lease protects its snapshots from expiration until completion or bounded timeout.

    Mutation¶

    Updates and deletes produce copy-on-write replacement files or merge-on-read delete files. The commit validates conflicts against snapshots after the writer's base. Equality deletes suit key-based changes; position deletes are precise but couple to file layout. Readers merge applicable deletes by sequence. Maintenance later rewrites clean files without changing logical rows.

    Deep Dive 1: Transactional Table Format¶

    sequenceDiagram
    autonumber
    participant W as Writer
    participant O as Object store
    participant C as Catalog/commit service
    W->>C: load table metadata version V
    W->>O: write immutable data and manifests
    W->>C: commit expected V, operation, new metadata
    C->>C: validate files, policy, conflicts
    C->>C: CAS current pointer V to V+1
    alt success
        C-->>W: snapshot S committed
    else concurrent conflict
        C-->>W: retry with latest metadata
    end

    Publishing one metadata pointer is the linearization point. Files written before a failed CAS are invisible and later reclaimed. Append writers can often rebase if added files do not conflict. Overwrite, merge, and compaction inspect changed partitions/files or row-level conflict keys. Blind last-write-wins can lose rows and is rejected.

    Iceberg's reliability documentation describes optimistic pointer replacement and revalidation of operation assumptions after a conflict; it does not make arbitrary rebasing safe (accessed 2026-09-08).

    Snapshot metadata forms a parent chain with monotonically increasing sequence. Manifests summarize partitions and column bounds so planners avoid reading every file entry. Checkpoints or compact metadata files bound chain traversal. Branches support isolated maintenance or audit, while tags retain known snapshots.

    Deep Dive 2: Schema and Partition Evolution¶

    Assign immutable field IDs. Renaming changes a label, not identity; dropping reserves the ID; adding a nullable field is generally compatible. Type widening follows an explicit matrix. Required-field additions need defaults/backfill or a new contract. Writers declare schema ID and map by field identity, preventing ordinal changes from silently swapping data.

    Partitioning is metadata, not user-visible directory meaning. Transforms such as day(timestamp), bucket(tenant, 64), or truncate(country) receive spec IDs. New files may use a new partition spec while old files retain the old one; planners evaluate predicates across both. This hidden partitioning avoids rewriting an exabyte table merely to evolve layout.

    Schema registry approval, producer compatibility checks, and table constraints are control-plane governance. Data quality rules run before publication for critical tables or asynchronously with a quarantine/quality state for lower tiers. A contract change canary writes to a branch and compares row counts, nulls, bounds, and representative queries.

    Deep Dive 3: Compaction, Deletes, and Garbage Collection¶

    Small files inflate commits, planning, GET requests, and worker startup. Compaction selects a bounded partition/file group, reads at snapshot S, writes 256 MB-1 GB sorted files, and commits a rewrite only if inputs remain valid. It uses separate quotas so maintenance cannot starve ingestion. Sorting by common filters improves skipping but costs shuffle and can create skew.

    Merge-on-read writes quickly but charges readers to apply delete files; copy-on-write makes writes expensive but reads simple. Use merge-on-read for high update rates, then compact based on delete ratio, file count, query heat, and cost. Position deletes must be rewritten when target files change.

    flowchart TD
    Roots[Snapshots, tags, branches, query and writer pins] --> Mark[Traverse metadata and manifests]
    Mark --> Reachable[Reachable data/delete/metadata files]
    Inventory[Object inventory] --> Sweep{Older than grace and unreachable?}
    Reachable --> Sweep
    Sweep -->|no| Keep[Retain]
    Sweep -->|yes| Fence[Recheck pins and fence publication]
    Fence --> Delete[Delete with audit manifest]

    Expiration first removes snapshot references under retention. GC uses object inventory plus mark-and-sweep, never a possibly stale refcount. Grace exceeds the declared bounded commit, retry, and inventory windows. Writers register durable staging pins before publication, including reused old files that a prior mark did not reach; commit and GC coordinate through a generation or conditional deletion protocol. Query lease acquisition/renewal is serialized with snapshot retirement: a query cannot acquire a new pin after its snapshot is retired, and a worker that loses its lease stops reading before the protected interval ends. Grace alone cannot protect an indefinitely paused writer or an old file newly referenced after the mark. Legal holds and tags are roots. Dry-run manifests, deletion rate limits, and sampled restore protect against catastrophic policy errors.

    Deep Dive 4: Catalog, Planning, and Compute Isolation¶

    The catalog maps names to stable table IDs and metadata pointers, tracks ownership/policy, and emits change events. Cache immutable metadata aggressively, but validate the current pointer and authorization epoch. Namespace rename changes catalog mapping, not every file. Catalog unavailability can allow already-pinned read-only queries while rejecting commits and new authorization decisions.

    Planner metadata work is bounded through manifest summaries, partition/file-stat pruning, cached snapshots, and planning timeouts. Cost/cardinality estimates are advisory, but min/max bounds used to skip files are correctness-critical: false bounds can omit matching rows. Validate their encoding and schema association; missing or untrusted pruning bounds must cause a scan, not exclusion. Query admission estimates scan bytes, CPU, memory, shuffle, and concurrency. Separate interactive, ETL, ingestion, and maintenance warehouses with tenant quotas.

    Workers are disposable and read snapshots directly. Stage shuffles on encrypted local/remote storage and checkpoint long stages where useful. Straggler mitigation duplicates only deterministic tasks. Under overload, queue batch work, reject unbounded scans, spill within quota, and preserve catalog/commit capacity. Chargeback reports tie bytes and CPU to owner, query, and table.

    Partitioning and Scaling¶

    Shard catalog and commit ownership by stable table ID; place extreme commit-rate tables on dedicated shards. Metadata files partition naturally by snapshot and manifest. Data files partition by table-defined transforms and target size, not object-store directory listing. Hash source partitions across ingestion workers while preserving position order per source partition.

    Hot tables stress catalog, metadata planning, and object storage. Cache immutable manifests, fan out manifest evaluation, coalesce commits, and use hierarchical manifests. Coalescing adds latency and must preserve source-position identities. Skewed joins use heavy-key detection, salting, broadcast of genuinely small sides, and adaptive repartitioning. Fair admission prevents one tenant's Cartesian product from exhausting a warehouse.

    Consistency and Idempotency¶

    Catalog pointer CAS and policy updates require strong consistency per table/namespace. Readers get snapshot isolation, not necessarily multi-table atomicity. A workflow needing a consistent set records explicit snapshot IDs or publishes a versioned dataset manifest after all table commits. Object-store reads must satisfy the durability/read-after-write assumptions required before publication.

    Ingestion commits retain source ranges and request hashes. Stream delivery and catalog events are at least once; sinks compare versions. Exact range identity alone is insufficient if a restart changes batch boundaries: ranges [1,100] and [51,150] overlap without sharing an ID. Atomically advance a per-source-partition committed position with publication, reject gaps, and trim already committed prefixes, or deduplicate stable row-event IDs. Do not claim exactly-once transport. Materialized views record input snapshots and output snapshot for reproducibility.

    Reliability and Failure Modes¶

    A worker crash before commit leaves reclaimable files; after commit it discovers the ingestion identity and advances its source checkpoint. Object-store slowdown triggers bounded retries, task backoff, and query cancellation rather than unbounded memory. Catalog failure freezes commits; pinned reads may continue. Metadata corruption first recovers an exact verified replica. Serving a parent snapshot is an explicit stale read; write promotion must recover the acknowledged commit prefix or reconcile lost commits and ingestion positions before accepting new mutations.

    Compaction conflict discards output after grace. Lost catalog events are repaired by version scans. A bad schema rollout is stopped through compatibility checks and branch canary, then readers pin the prior snapshot while correction appends a new one. Restore verifies checksums, metadata reachability, row counts, and representative queries. Reconciliation finds source-position gaps, duplicate identities, orphan growth, manifest inconsistencies, and policy drift.

    Multi-Region Strategy¶

    Assign each table a metadata home region with synchronous zonal catalog replication. Replicate immutable objects according to residency and disaster tier. Remote engines read local replicas only when a snapshot replication manifest is complete; otherwise they route to home or fail explicitly. Cross-region egress is visible in planning cost.

    Disaster failover promotes a fenced catalog epoch after object completeness is proven. Active-active independent table writes are possible with a consensus catalog but often add latency without product value. Dataset sharing publishes immutable snapshot references and policy rather than copying ad hoc directories. Migration copies objects, verifies manifests, catches up metadata versions, then atomically switches location descriptors.

    Security and Abuse Prevention¶

    Use workload identity, short-lived object credentials, encryption with table/tenant keys, private networking, column masking, row filters, purpose-based roles, and immutable access/change audit. Policy is evaluated during planning and embedded in a signed plan; workers cannot request arbitrary paths. Recheck epochs for long queries where revocation requirements demand it.

    Protect against malicious files, decompression bombs, parser exploits, SQL resource attacks, unauthorized exports, path injection, and poisoned statistics. Sandbox format readers and UDFs. Scan sensitive columns, tokenize where possible, enforce residency and retention, and make break-glass access time-bound and reviewed. Query results inherit source classification and expiration.

    Observability and Testing¶

    Measure ingest bytes/records, source lag, commit conflicts, commit and catalog latency, files per snapshot, file-size distribution, delete ratio, metadata planning time, prune ratio, scanned versus returned bytes, shuffle/spill, queue time, query failures, orphan age, snapshot retention, policy denials, and cost by owner. Track freshness as source position to published snapshot, not merely job success.

    Property-test snapshot reachability, schema-ID mapping, partition transforms, conflict detection, and GC roots. Differential-test multiple engines against the same snapshots. Replay duplicate and reordered source batches. Chaos-test commit acknowledgements, object/catalog outages, worker loss, and region fencing. Scale-test million-file manifests, tiny files, skewed joins, and concurrent compaction. Regularly restore retained snapshots and execute golden queries.

    Important Tradeoffs¶

    Object storage lowers cost and decouples compute but makes metadata publication and small files critical. Copy-on-write favors reads; merge-on-read favors mutations. Strong multi-table transactions are convenient but impose coordination rarely justified for analytics; explicit dataset manifests are simpler. More statistics improve pruning but increase write and privacy cost. Global catalogs simplify names but can violate latency/residency goals; federated ownership with stable IDs adds discovery complexity. Open formats reduce lock-in but require rigorous compatibility testing.

    Final Architecture¶

    flowchart TB
    Producers --> Ingestion[Batch and streaming ingestion cells]
    Ingestion --> Lake[(Immutable columnar data/delete/metadata)]
    Ingestion --> Commit[Per-table commit owners]
    Commit --> Catalog[(Catalog, pointer CAS, schema, policy)]
    Clients --> Gateway[Governed query gateway]
    Gateway --> Planner[Snapshot-pinning planner]
    Planner --> Catalog
    Planner --> Warehouses[Isolated elastic compute warehouses]
    Warehouses --> Lake
    Catalog --> Maintenance[Compaction, quality, expiry, GC]
    Maintenance --> Lake
    Lake --> Replica[Verified regional replicas/archive]

    Interview Deep-Dive Questions¶

    1. What is the linearization point of a table commit?
    2. How can two append writers commit without losing files?
    3. Why do field IDs matter during rename and reorder?
    4. How can partitioning evolve without rewriting old data?
    5. When should a table use merge-on-read versus copy-on-write?
    6. How do you prove a file is safe to garbage-collect?
    7. How do compute and control planes degrade independently?

    L5 and L6 Expectations¶

    An L5 answer should define immutable files, transactional snapshots, a catalog, schema evolution, ingestion checkpoints, query pruning, compaction, and retries. An L6 answer should formalize conflict scopes, field identity, partition evolution, query leases and GC proof, metadata scaling, workload isolation, source reconciliation, regional object completeness, migrations, governance, engine compatibility, and cost attribution.

    Five-Minute Summary¶

    A lakehouse is a transactional metadata layer over immutable object-store files. Writers stage checksummed columnar data and manifests, then CAS one table metadata pointer from an expected version to a new snapshot. Readers pin that snapshot, prune hierarchical manifests with partition transforms and statistics, and run on isolated elastic compute. Record stable field IDs and versioned partition specs so schema and layout evolve without corrupting old files. Deduplicate ingestion by source-position range and commit checkpoints against published snapshots; delivery remains at least once. Use merge-on-read deletes for fast mutation or copy-on-write for fast reads, then compact under separate quotas. Expire snapshots before mark-and-sweep GC, preserving tags, branches, legal holds, and active query leases. Keep catalog/policy in a strongly consistent home region, verify immutable replica completeness before failover, and measure source-to-snapshot freshness, metadata scale, scan efficiency, and cost.
