    Distributed Cache¶

    1. Interview roadmap¶

    We will design a multi-tenant distributed key-value cache used by services to reduce database latency and load. We first define cache semantics because a cache is not canonical storage, estimate memory and network needs, expose get/set/delete and bulk APIs, and build a partitioned in-memory data plane. Deep dives cover placement, eviction, stampede prevention, invalidation, and failure recovery before adding optional cross-region warming.

    2. Product framing¶

    The platform stores derived or reproducible values with TTLs. Callers choose cache-aside, read-through, or write-through integration, but the default is cache-aside: miss, read the source of truth, then populate. The service optimizes availability and latency; it does not promise durable retention. A missing key may mean absent, expired, evicted, or temporarily unavailable, so business correctness must remain in the backing system.

    3. Requirements¶

    Functional requirements:

    • Get, multi-get, set with TTL, add-if-absent, compare-and-set, increment, and delete.
    • Namespaces with quotas, maximum object size, eviction policy, and authorization.
    • Optional negative caching and request coalescing.
    • Online node addition/removal with bounded disruption.
    • Usage, hot-key, and hit-rate diagnostics.

    Non-functional requirements:

    • 10 million reads/s and 2 million writes/s globally; 95% expected hit ratio.
    • p99 under 2 ms in-zone and 99.99% service availability.
    • Objects up to 1 MB, median 1 KB; TTL from one second to seven days.
    • No noisy tenant may exhaust shared memory or network.

    Durable databases, arbitrary queries, and cross-key transactions are out of scope.

    4. Correctness invariants¶

    1. The cache never fabricates a value: returned bytes correspond to a mutation applied by the authoritative owner for that key and namespace; the writer may have lost its response.
    2. Ordinary reads do not serve an entry after logical expiration, allowing the documented bounded clock error. Explicit stale-if-error reads use a separate maximum stale deadline and return a stale marker.
    3. Compare-and-set succeeds only against the observed version on the authoritative shard.
    4. Namespace isolation applies to storage, bandwidth, and authorization.
    5. Rebalancing never creates two accepted writers for one shard epoch.
    6. Add-if-absent has one linearization point on the primary: among concurrent callers, at most one creates the live key.
    7. Increment atomically applies to the current integer value on one key and returns the resulting value; it never silently converts arbitrary bytes.

    Read-after-write and delete visibility are configurable. The default is eventual across replicas, while primary reads provide session-level freshness. Cache loss must not violate application correctness.

    5. Capacity estimates¶

    At 10 million reads/s with 1 KB values on hits and 95% hit ratio, payload egress is 9.5 GB/s before protocol overhead; 10 GB/s is a conservative all-hit bound. Two million client writes/s plus one replica write per mutation bring aggregate node work to 14 million operations/s, requiring at least 140 node equivalents at a measured 100,000 operations/s each, before failure and skew reserve. At 8 Gbit/s usable egress per node, client-read bytes alone require ten nodes; include replication traffic separately. Suppose 2 billion entries average 1 KB value plus 150 bytes metadata: 2.3 TB logical. Replication factor two with 30% of RAM kept free requires 2.3 * 2 / 0.70 = 6.57 TB, or 103 nodes with 64 GB allocatable RAM each. A 95% hit rate still sends 500,000 reads/s to backing stores. For three balanced zones, preserving the 140-node work floor after one zone fails requires at least 210 nodes, before hot-shard and maintenance reserve; validate the operation mix rather than treating a reads-only benchmark as universal.

    6. Entities and data model¶

    Namespace(namespace_id, owner, memory_quota, qps_quota,
          max_value_bytes, default_ttl, eviction_policy, version)
Entry(namespace_id, key_bytes, value_bytes, value_version,
      created_at, expires_at, flags, size_bytes)
ShardMap(map_version, shard_id, primary, replicas[], epoch, state)

    Namespace configuration is canonical in a transactional metadata store. Entry state resides only in RAM, optionally with a local append log to speed restart but not to claim durability. Shard maps are versioned control-plane projections distributed to clients and proxies.

    7. Interfaces¶

    GET /v1/namespaces/{ns}/keys/{base64Key}
PUT /v1/namespaces/{ns}/keys/{base64Key}?ttl=300
DELETE /v1/namespaces/{ns}/keys/{base64Key}
POST /v1/namespaces/{ns}:multiGet
POST /v1/namespaces/{ns}/keys/{key}:add?ttl=300
POST /v1/namespaces/{ns}/keys/{key}:increment
POST /v1/namespaces/{ns}/keys/{key}:compareAndSet

    Responses include value_version, remaining TTL, shard-map version, and hit/miss. Binary clients use multiplexed RPC, deadlines, and bounded batches. Writes accept an idempotency token for safe retries. A lease-based getOrLoad(key, loader_id) interface returns either a value or temporary fill ownership; arbitrary loader code never executes inside cache nodes.

    add treats an expired entry as absent after expiration is checked under the same key lock or owner-thread turn as insertion. It returns STORED or EXISTS plus the observed version. increment(delta, initial, ttl) accepts signed 64-bit integer values only, checks overflow, creates initial when absent if requested, and preserves the existing TTL unless the create path supplies one. Both operations are linearizable on the current primary. Their result may still be lost after a primary-only acknowledgement and failover, so they are coordination conveniences for disposable state, not durable uniqueness or billing counters. An idempotency token is required to retry increment after an unknown response; otherwise a retry can apply the delta twice.

    8. High-level architecture¶

    flowchart LR
  App --> Client[Smart client]
  Client --> P[Primary shard]
  Client --> R[Replica shard]
  P --> R
  Admin --> Control[Cache control plane]
  Control --> Meta[(Metadata DB)]
  Control --> Maps[Signed shard maps]
  Maps --> Client
  P --> Metrics[Metrics and access samples]

    The control plane owns namespaces, placement, node health, and migrations. The data plane consists of smart clients and cache nodes. Smart clients avoid proxy hops; a thin proxy option supports untrusted or simple clients. Each client keeps a persistent, multiplexed connection pool per selected node, with bounded pending requests, idle and maximum connection ages, health probes, TLS session reuse, and a global connection budget. Map changes drain obsolete pools rather than reconnecting every request; retries choose only the owner for the required epoch and consume a retry budget. Nodes keep serving under the last shard map during a metadata outage. Start with primary-plus-replica partitions; add persistence or regional replication only for measured warm-up pain.

    9. Read and write paths¶

    A client hashes namespace and key to a virtual shard, checks its local map, and sends a deadline-bound request. Default reads go to the primary for predictable freshness; relaxed reads may choose a healthy replica. On a miss, the application loads canonical storage and sets a TTL with jitter. Writes mutate the primary, receive a monotonically increasing per-entry version, and replicate asynchronously. A stricter namespace can require one replica acknowledgment.

    sequenceDiagram
    autonumber
  participant A as Application
  participant C as Cache client
  participant P as Primary
  participant D as Database
  A->>C: get(key)
  C->>P: GET key, mapVersion
  P-->>C: MISS + fill token
  C-->>A: miss + fill ownership
  A->>D: read canonical row
  D-->>A: value, sourceVersion
  A->>C: set(key,value,ttl,fillToken)
  C->>P: conditional SET
  P-->>C: stored version

    Writes from cache-aside applications should usually update the database first and then delete the cache. Updating cache before database commit can expose uncommitted values. Delete-after-write narrows stale time, and CDC invalidation provides a second defense.

    From one node to a distributed cache¶

    First make one node correct. Hash (namespace, key) to a bucket array whose entries reference immutable key bytes and value metadata. Resolve collisions with open addressing or bucket chains; resizing is incremental so one request does not pause the process. Values come from slab or size-class allocators, while entry headers track version, expiry, size, and recency pointers. This avoids per-object allocator overhead and makes fragmentation measurable, but wastes space when values sit just above a class boundary.

    Requests run on sharded owner loops or fine-grained bucket locks. Under that serialization point, set, add, increment, CAS, and delete update the hash index, byte accounting, expiration structure, and recency/admission metadata as one mutation. Reads check expiration before returning bytes. Expired entries are unlinked lazily on access and proactively through timing-wheel buckets; delayed cleanup may consume memory but must never make expired data visible. Exact LRU rewrites shared recency state on every hit, so production nodes sample accesses into per-thread buffers and periodically update segmented recency lists. TinyLFU-style frequency sketches decide admission; recency structures choose a victim.

    Distribution adds placement above this node-local engine rather than changing key semantics. A virtual shard owns an independent hash-table slice, memory budget, expiration wheel, replication stream, and epoch. This gives migration and failover a bounded unit while the node-level allocator still shares physical pages under namespace quotas.

    10. Placement and rebalancing¶

    Use thousands of virtual shards, far more than nodes. Rendezvous hashing maps each shard to failure-domain-aware nodes and moves only affected shards when membership changes. The control plane publishes map epoch E+1 with a migrating state. The old primary snapshots entries to the new node while forwarding recent mutations; after catch-up, the controller grants a higher fencing epoch and switches clients. Old nodes redirect requests carrying new map versions and reject writes after fencing.

    Placement choices differ operationally:

    Method Lookup Membership change Operational fit
    hash(key) mod N O(1) Most keys move when N changes Fixed, uniform fleets or a teaching baseline
    Consistent-hash ring with virtual nodes O(log V) Roughly the added or removed capacity moves Familiar, but token balancing and failure-domain replicas need care
    Rendezvous hashing over candidate nodes O(N), or less with hierarchy Only keys preferring changed nodes move Simple deterministic ranking, weighting, and replica selection

    Direct modulo hashing is unacceptable for an elastic fleet because changing N remaps nearly every key. Rings and rendezvous both limit movement. This design hashes keys to a fixed virtual-shard ID first, then uses rendezvous hashing for shard-to-node assignment. Clients perform constant-time key-to-shard lookup and consume a precomputed map, so they do not score every node on every request.

    Cold movement is often preferable because entries are disposable: assign the new owner and accept misses. Warm copy is justified for expensive backing stores or very large working sets. Rate-limit migration so it does not consume latency headroom.

    flowchart LR
  subgraph Old[Old owner memory]
    OH[Shard hash index]
    OS[Size-class slabs]
    OT[Expiry wheel]
    OR[Recency and frequency]
    OH --> OS
    OH --> OT
    OH --> OR
  end
  subgraph New[New owner memory]

  Fence -->|reject later writes| Old

    The copy excludes already expired entries and transfers absolute expiry, not a fresh TTL. It preserves value and source versions but need not preserve exact recency: the destination can start copied entries in a probation segment to avoid declaring the entire moved set hot. Migration reserves destination memory before copying, accounts copy buffers outside tenant capacity, validates key counts and byte checksums, then closes old-owner writes, captures their final watermark, and switches only after the target has applied that complete prefix. A small nonzero lag is a preparation gate, not proof of safe writer transfer. Cold movement can discard values but must still fence the former owner. If headroom is insufficient, choose cold movement instead of risking fleet-wide eviction.

    11. Eviction and memory management¶

    TTL expiration uses a coarse timing wheel plus lazy checks on access; scanning all keys is too expensive. When memory crosses a watermark, evict within each namespace quota. Exact global LRU requires lock-heavy updates. Sampled LRU or segmented LRU approximates recency cheaply; TinyLFU admission plus a small recency window protects frequent values from one-hit scans. Objects larger than the namespace threshold are rejected because a few large entries can create allocator fragmentation and bandwidth spikes.

    Reserve memory for metadata and replication buffers. Slab or size-class allocation reduces fragmentation. Eviction is observable by cause: TTL, quota, pressure, manual delete, or rebalance.

    12. Stampedes, hot keys, and invalidation¶

    For a cold popular key, millions of misses can overload the database. A short fill lease allows one caller to load while others wait briefly, receive stale-if-allowed data, or fail fast. Lease holders publish only if their token and source version remain current. TTL jitter avoids synchronized expiry. Probabilistic early refresh lets a caller refresh before expiry with probability increasing as expiration approaches.

    A single hot key can saturate one shard. Replicate detected immutable hot values to read replicas or host-local near caches, with short TTL and versioned invalidations. This is safe only when bounded staleness is acceptable, values carry versions, invalidation loss expires naturally, and authorization is identical at every copy. Never near-cache secrets with immediate revocation requirements, one-time tokens, lock ownership, or values whose stale reuse can spend money. A mutable hot key remains single-owner for CAS, add, and increment; replicas can serve only explicitly stale reads. Split counters into independently owned stripes only when the caller accepts an approximate aggregate, never to preserve a linearizable counter contract. Negative results use short TTLs and distinguish not found from backend failure.

    flowchart TD
  Miss[Cache miss] --> Lease{Fill lease acquired?}
  Lease -->|yes| Load[Load source of truth]
  Load --> Publish[Conditional publish]
  Lease -->|no| Stale{Stale allowed?}
  Stale -->|yes| Return[Return stale + refresh pending]
  Stale -->|no| Wait[Bounded wait with jitter]
  Wait --> Retry[Retry cache once]

    CDC invalidations carry namespace, key, and source version. Nodes ignore older invalidations and keep bounded version high-watermarks or invalidate outstanding fill tokens even when the value is absent. Otherwise delete followed by a slow old loader can resurrect stale data. Define the retention window against maximum loader and CDC delay; beyond it revalidate with the source. Whole-namespace purges are asynchronous jobs with progress, not an unbounded request.

    13. Partitioning and scaling¶

    Partition by hash of (namespace_id, key) for even spread. Large tenants have namespace quotas but share shards until isolation is needed. Dedicated pools support regulated or extremely hot tenants. Multi-get groups keys by shard and executes in parallel with a concurrency bound; output preserves input order and marks per-key errors. Admission control limits operations, bytes, and CPU because QPS alone misses large-value abuse.

    Autoscaling watches sustained CPU, network, allocator pressure, and eviction rate. Adding empty RAM does not instantly improve hit rate; warm-up and movement are explicit rollout states.

    14. Consistency and idempotency¶

    Primary operations are ordered per key. Asynchronous replicas may lag, so relaxed reads can return older values. Quorum replication improves failover freshness but raises write latency; it still does not make the cache a database. CAS compares opaque versions containing the shard epoch and an entry generation that is not reused after eviction or delete/recreate; resetting a per-entry counter would allow an ABA match. Add-if-absent and increment share the same primary serialization point as CAS. Failover can lose any operation acknowledged before replication, and a client with an unknown increment response must retry with the same idempotency token or read and reconcile at the application layer.

    Set retries with the same idempotency token return the original result for a bounded window. Delete retries carry the original mutation token or expected generation: an unconditional delayed retry could otherwise erase a newly populated entry. Fill tokens prevent a slow loader from overwriting a newer fill. Source versions, when supplied, reject regression from delayed CDC or loaders.

    15. Failures and recovery¶

    • Node crash: clients refresh maps and retry once on the promoted replica; misses refill naturally.
    • Network partition: only the fenced primary epoch accepts writes. Isolated replicas may serve explicitly stale reads.
    • Control-plane outage: existing maps continue; topology changes pause.
    • Memory pressure: enforce tenant quotas, reject writes before reads, and evict by policy.
    • Backend slowdown: coalescing, stale-if-error, circuit breakers, and miss-rate admission protect it.
    • Bad client retry storm: deadlines, exponential jitter, retry budgets, and server load shedding.
    • Corrupt local snapshot: discard it and start cold; canonical data is elsewhere.

    Recovery promotes the most up-to-date replica when practical, increments epoch, and rebuilds redundancy in the background. Never block fleet recovery on restoring every disposable entry.

    Failure alerts should expose customer and dependency impact, not just dead nodes. Track unavailable and stale-read rates by namespace class, failover duration, promoted-replica lag in operations and bytes, estimated acknowledged writes lost, epoch mismatch rejects, redirect loops, retry amplification, connection-pool saturation, migration copy/catch-up lag, memory reservation failures, refill QPS, and backend error/latency after misses. Page when error budget burns or backing-store protection approaches its limit; ticket isolated replica rebuild lag before it removes failover margin.

    16. Multi-region strategy¶

    Deploy independent regional caches close to applications. Canonical database replication determines application freshness; cache invalidations follow CDC into each region. Cross-region synchronous cache writes add latency without creating durable correctness. For disaster recovery, the destination starts cold, optionally prewarmed from access-frequency sketches or a safe snapshot. Limit prewarming so it does not overload databases or links.

    If clients move between regions, they may observe older cached data. Applications requiring monotonic reads include a minimum source version; the cache returns miss when its value is older. Namespace metadata replicates globally, while one home control plane coordinates writes and promotes through a new epoch.

    17. Security and abuse prevention¶

    Use mTLS workload identity, namespace ACLs, encryption in transit, and optional value encryption for sensitive tenants. Cache keys and sampled values must not leak into ordinary logs. Operators get metadata-only diagnostics unless break-glass access is audited. Quotas cover memory, requests, ingress, egress, key length, and object size. Validate compression ratios to prevent decompression bombs and isolate parsers from the data process.

    18. Observability and testing¶

    Measure hit ratio by namespace and status, but pair it with saved backend work; a high hit ratio on cheap keys may be useless. Track p50/p99 latency, evictions and rejected admissions by cause, expirations pending cleanup, fill waits, replication lag, hot-key share, memory fragmentation by size class, slab utilization, timing-wheel backlog, recency-buffer drops, bytes, redirects, pool queue time, and backend load after misses. Trace sampled cache-aside flows without value contents.

    Unit tests cover TTL boundaries, add races, increment overflow and retry deduplication, CAS, allocator class boundaries, and eviction accounting. Property tests model map epochs and ensure fenced writers cannot commit. Deterministic node tests race access with expiry cleanup and assert that hash, slab, timing-wheel, quota, and recency accounting converge. Load tests use Zipfian popularity, varied sizes, synchronized expiries, slow client pools, and node churn. Fault tests kill primaries during replication, interrupt warm migration at every phase, and disconnect control plane. Replay tests compare eviction policies on production access samples. Capacity drills rehearse a full regional cold start without collapsing databases.

    19. Important tradeoffs¶

    Smart clients remove a hop but require library rollout; proxies centralize behavior but add cost and a bottleneck. Replication improves availability and read scale but consumes RAM. Primary reads give freshness; replica reads lower latency. Exact LRU costs more than its benefit at scale, so approximate admission wins. Warm rebalancing preserves hit rate but consumes network; cold movement is simpler. Persistence accelerates restart but risks callers treating cache as durable.

    20. Final design, questions, and expectations¶

    The final design uses versioned virtual shards, zone-aware primary and replicas, smart clients, in-memory entries, timing-wheel expiration, TinyLFU-style admission, per-namespace quotas, fill leases, and CDC invalidation. The transactional control plane publishes fenced shard maps; data nodes survive its outage. Regions remain independent and recover by refill.

    Interview questions: How do you stop a stampede? What happens to acknowledged writes on primary failure? How is a hot key detected and mitigated? Why does adding nodes cause misses? How do delete and database commit order interact? How would minimum-version reads work?

    An L5 answer should estimate RAM/QPS, define cache-aside paths, hash partitions, choose eviction, and handle node loss and hot keys. An L6 answer should distinguish saved work from hit ratio, fence rebalancing, isolate tenants by bytes, protect backing stores during cold start, define freshness contracts, and justify operational complexity with measured requirements.

    21. Five-minute summary¶

    This is a disposable, multi-tenant in-memory cache, not a database. Canonical namespace metadata lives in a control plane that publishes versioned, fenced shard maps. Smart clients hash namespace and key to zone-replicated primaries; optional replica reads trade freshness for latency. Entries expire through lazy checks and timing wheels, while sampled admission and eviction avoid exact-LRU overhead. Fill leases, TTL jitter, early refresh, and stale-if-error protect databases from stampedes. Virtual shards and rendezvous placement limit movement; hot keys gain read replicas or near-cache copies. Per-tenant memory, byte, and QPS quotas prevent noisy neighbors. Regional caches operate independently and consume versioned CDC invalidations. Failures produce misses or explicitly stale reads, never invented durability. The design is validated with skewed traffic, churn, synchronized expiry, and cold-region recovery tests.
