    Distributed Rate Limiter¶

    1. Interview roadmap¶

    We will design a shared rate-limiting platform for APIs running across many hosts and regions. Start with policy semantics and the safety invariant, estimate the request and key cardinality, define the check interface, and then separate policy management from enforcement. We will evolve a single Redis counter into local admission plus distributed quota accounting, examine hot keys and failure policy, and close with regional operation and rollout.

    2. Product framing¶

    A rate limiter protects dependencies, enforces customer plans, and allocates scarce capacity fairly. It answers whether an operation may proceed, usually in less than a millisecond inside a gateway or service. Limits may apply by tenant, user, API, IP, or combinations, with burst and sustained rates. Billing-grade metering is separate: this system makes fast admission decisions and emits auditable usage, but should not become a synchronous billing ledger.

    3. Requirements¶

    Functional requirements:

    • Create, version, stage, and disable policies such as 100 requests/second with burst 200.
    • Evaluate hierarchical limits: global, tenant, route, and user. Denial by any applicable policy denies the request.
    • Return allow/deny, retry delay, remaining approximation, and policy version.
    • Support shadow evaluation and emergency overrides.
    • Produce usage and decision events for debugging and capacity planning.

    Non-functional requirements:

    • 5 million checks/second globally, p99 enforcement overhead below 2 ms.
    • 99.99% limiter availability; bounded over-admission during failures.
    • Policy changes visible within 10 seconds, emergency revocation within 2 seconds.
    • Fair behavior under skew and explicit fail-open or fail-closed per route.

    Out of scope are bot detection, authentication, and exact monthly invoicing.

    4. Correctness invariants¶

    1. A decision evaluates one complete policy version, never a mixture of fields from two versions.
    2. Within the declared error budget, accepted cost for a quota does not exceed limit + burst + distributed_slack per window.
    3. Retries of a lease reservation with the same reservation token do not allocate twice within its retention horizon. Local checks are charged per invocation unless the SDK explicitly retains a bounded decision-token result.
    4. A policy scoped to tenant A cannot affect tenant B.
    5. Denial is conservative when any fail-closed dependency is unavailable; fail-open behavior is explicit policy, not an accidental timeout.

    Rate limits are not naturally exactly consistent at global scale. Exact global admission is possible through a shared serialization authority, at the cost of coordination latency and unavailability when that authority cannot be reached. This local fast-path design instead exposes bounded slack.

    5. Capacity estimates¶

    Assume 5 million checks/s peak, 25 million active keys in a minute, average key plus state 120 bytes, and three replicas. Active state is roughly 9 GB, including the three replicas once; allocator overhead, expiry indexes, and headroom motivate an illustrative 40 GB fleet for that key population. State explicitly whether each region holds the full population or a partition before multiplying this budget. At 250-byte decision events and 10% sampling, telemetry is 125 MB/s; all denials and policy changes are retained. A gateway making an 800 microsecond network call would consume 4,000 concurrent requests at peak, motivating in-process checks. Ten regions receiving cached policy snapshots need little control-plane bandwidth: 100,000 policies at 1 KB is 100 MB per full snapshot, while normal deltas are small.

    6. Entities and data model¶

    Policy(policy_id, scope_pattern, algorithm, rate, period_ms, burst,
       failure_mode, priority, version, status, effective_at)
PolicyBundle(bundle_version, checksum, generated_at, policies[])
Lease(lease_id, policy_id, bucket_id, owner, tokens, consumed,
      expires_at, fencing_token)
DecisionEvent(request_id, policy_id, version, key_hash, cost,
              outcome, reason, region, timestamp)

    Policy definitions are canonical in a transactional database. Signed bundles in object storage and local agent memory are projections. Issued-grant identities, amounts, and expiry are durable until no grant can be spent; losing this accounting cannot justify recreating a full bucket. Local consumption can be volatile only if restart discards the old grant without recrediting it. Events are append-only. Sensitive raw identities are converted to keyed hashes before telemetry.

    7. Interfaces¶

    Management API:

    PUT /v1/policies/{id}  If-Match: 41
POST /v1/policies/{id}:stage
POST /v1/policies/{id}:activate
GET /v1/bundles/latest?region=eu-west

    Hot-path library interface:

    check(DecisionRequest {
  request_id, subject_attributes, route, cost, deadline
}) -> Decision { allowed, retry_after_ms, reason, policy_version }

    The request ID is stable across safe retries. Batch checks are allowed only when all items share a deadline; partial outcomes are explicit.

    8. High-level architecture¶

    flowchart LR
  Admin --> API[Policy API]
  API --> DB[(Policy DB)]
  DB --> Compiler[Bundle compiler]
  Compiler --> Blob[(Signed bundles)]
  Blob --> Agent[Host agent]
  Agent --> SDK[In-process limiter]
  Client --> Gateway
  Gateway --> SDK
  SDK --> LeaseSvc[Regional lease service]
  LeaseSvc --> Store[(Sharded token store)]
  SDK --> Events[Decision event stream]

    The control plane validates and distributes immutable policy bundles. The data plane is the SDK, host agent, and regional lease service. A control-plane outage does not stop checks because agents retain the last valid bundle. The simplest deployment starts with direct atomic counters in a regional store; leases are introduced only when call volume or latency requires them.

    9. Policy lifecycle¶

    The API checks scope syntax, conflicting priorities, positive rates, and maximum burst. A compiler resolves inheritance into a deterministic ordered decision graph, signs it, and publishes a monotonically versioned bundle. Agents poll and subscribe to invalidations, verify signature and checksum, then atomically swap an immutable in-memory pointer. Activation records desired and observed rollout percentages. Canary hosts shadow the new bundle before enforcement; rollback means republishing the prior known-good content under a new monotonic version.

    Emergency deny rules use a small high-priority channel with short TTL and stronger propagation SLO. Temporary traffic overrides may expire back to the normal bundle. Security revocations have a separate durable generation and freshness rule: a stale agent fails closed for affected operations, and neither rollback nor TTL expiry silently restores revoked access.

    10. Admission algorithms¶

    A token bucket models sustained rate plus burst. For elapsed time dt, refill min(capacity, tokens + rate * dt) and allow cost c only when at least c tokens remain. A single owner updates timestamp and balance atomically. A sliding-window log is exact but stores every request; a fixed window is cheap but allows twice the nominal rate at boundaries. A sliding-window counter interpolates adjacent windows and is useful where approximate smoothing suffices.

    Use token buckets for traffic shaping, concurrency semaphores for simultaneous expensive work, and daily counters for coarse plan quotas. Policies name their semantics so operators do not mistake one for another. For hierarchical checks, this baseline may conservatively charge an earlier bucket when a later bucket denies; document that loss of utilization. Exact all-or-nothing charging needs co-located atomic reservation or a durable multi-bucket protocol, not an unsafe ad hoc refund.

    11. Distributed leases and bounded overshoot¶

    Every host asking a central store per request creates latency and hot-key pressure. Instead, the regional owner reserves chunks from a canonical bucket and leases them to hosts. For a fixed-window escrow quota, grants debit the authoritative allowance before issue and cannot create overspend merely because a host crashes; a crash strands capacity. For a continuously refilled bucket of capacity B and rate r, delayed consumption of previously issued grants can shift up to H * L admissions into an interval of duration dt, giving accepted_cost <= r * dt + B + H * L, assuming at most H holders each have at most L total outstanding tokens, grants cannot be duplicated, and clients enforce expiry. Add emergency budgets separately. Repeated unbounded fail-open replenishment or lost grant accounting invalidates this bound. Choose small grants near exhaustion; short expiry bounds stale consumption, but a new allocator epoch alone cannot revoke tokens already held by an isolated SDK.

    RFC 2697 section 3 specifies token refill and consumption for a single-rate traffic marker (accessed 2026-09-08). It supports the local token model, not this proposed distributed lease bound; the latter follows from the explicitly bounded outstanding grants.

    The SDK replenishes asynchronously below a threshold without exceeding its total outstanding-token cap. If its lease empties, it may synchronously request a small lease until the deadline. Strict policies deny on timeout; availability-oriented policies use a bounded, nonrenewable emergency budget and mark the event degraded. Unreported tokens are treated as consumed, not returned on expiry. Only verified unspent capacity may be reclaimed after the old holder is fenced from consumption; otherwise normal rate refill or the next quota window restores capacity.

    12. Hot keys, partitioning, and scaling¶

    Hash (policy_id, normalized_subject) to virtual shards. Replicate each shard across zones, with one writer at a time. Ordinary tenants distribute naturally; a global policy is a hot key. Split global capacity into per-shard or per-region sub-budgets and periodically rebalance based on demand. Heavy tenants receive dedicated shards, and admission queues cap work before the storage fleet.

    Consistent hashing minimizes movement, but rebalancing uses epochs: the old owner stops granting leases, the coordinator advances a fencing token, and the new owner starts from durable bucket state. Do not let both allocators mint grants from the same restored balance. Existing bounded grants may remain spendable within declared slack, but new grant ownership transfers only after fencing the old allocator and carrying its final bucket and issued-grant prefix.

    13. Consistency and idempotency¶

    Policy state is strongly consistent at publication and eventually propagated. A request uses the bundle version captured at check start. Regional token mutation is linearizable per bucket through a leader or atomic script. Cross-region totals are intentionally escrowed: each region owns a budget and cannot spend another region's allocation without transfer.

    Lease reservation deduplicates request_id for a short horizon. Keeping every request ID is too expensive, so direct per-request deduplication is limited to synchronous reservations; local lease consumption relies on the caller invoking check once. Downstream services must still be idempotent because an allow decision does not guarantee one execution.

    14. Failures and recovery¶

    • Policy database unavailable: reads and checks continue from bundles; writes stop.
    • Corrupt bundle: signature/checksum validation rejects it and retains last-known-good.
    • Agent unavailable: SDK uses its embedded bundle until max staleness, then follows route failure mode.
    • Token shard leader loss: quorum elects a leader; no grants occur without fencing.
    • Lease service overload: shed shadow checks first, shrink expensive cardinality, and deny or consume emergency budget.
    • Clock skew: token timestamps come from shard owners; monotonic process clocks measure local lease expiry.
    • Event pipeline outage: decisions continue through a bounded buffer; audit-required policies can switch to fail-closed.

    Recovery reconciles granted lease records and advances shard epochs. Operators can freeze policy rollout, drain a bad shard, or lower local lease sizes to tighten overshoot.

    15. Multi-region strategy¶

    Serve checks locally. For a global quota Q, an allocator escrows regional budgets summing to at most Q; regions spend independently. Every few seconds they report utilization, and the allocator moves unspent future capacity. A partition preserves safety but may reduce utilization. If product preference is availability, permit a documented regional emergency allowance and include it in global slack.

    Policies replicate globally through signed bundles. The home region accepts writes; failover requires a database promotion and a new publisher epoch. Active-active policy editing is unnecessary complexity unless administrators require it.

  Allocator[Global budget allocator]
  Allocator -->|escrow 45%| R1[Region A token shards]
  Allocator -->|escrow 45%| R2[Region B token shards]
  Allocator -->|reserve 10%| R3[Failover reserve]

  R2 -. utilization .-> Allocator

    16. Security and abuse prevention¶

    Management APIs require SSO, RBAC, tenant-scoped authorization, approval for global policies, and immutable audit records. Bundles are signed and agents use mTLS. Keys are normalized with explicit schema to prevent attackers bypassing limits through Unicode, path variants, or header casing. Hash secrets rotate with overlap. Cardinality guards reject unbounded user-controlled dimensions, while separate IP and credential limits resist distributed and account-based abuse.

    17. Observability and testing¶

    Measure decision latency, allow/deny counts, degraded decisions, bundle age, lease utilization, overshoot estimate, hot shards, and replenishment errors. Avoid high-cardinality raw keys; provide sampled hashed exemplars and a privileged explain endpoint. Alert on policy propagation lag and unexpected denial-rate changes, not merely CPU.

    Unit tests cover boundary refill and precedence. Property tests assert tokens never become negative and accepted cost stays within modeled slack. Deterministic simulations vary clocks, retries, host crashes, and shard reassignment. Load tests use Zipfian subjects, not uniform keys. Canary and shadow comparisons quantify changed decisions before activation. Regional game days isolate the allocator and kill shard leaders.

    18. Important tradeoffs¶

    Direct central checks maximize per-key precision but add latency and create hot keys. Local-only buckets maximize availability but cannot enforce shared quotas. Leases trade bounded over-admission for low latency and scale. Fixed windows are operationally simple but have boundary bursts; token buckets express burst explicitly. Global synchronous consensus gives tighter quotas but makes every request depend on inter-region latency. Escrowed regional budgets preserve safety and locality at the cost of temporary unused capacity.

    19. Final design¶

    Use a transactional policy control plane that compiles signed immutable bundles. Agents distribute bundles to in-process SDKs. SDKs evaluate hierarchy locally and consume adaptive token leases reserved atomically from zone-replicated regional shards. Hash normal keys, isolate heavy tenants, and split global hot limits into escrow budgets. Events flow asynchronously to audit and analytics. Policy-specific failure modes, fencing, last-known-good bundles, bounded queues, and emergency budgets make degradation intentional.

    20. Interview questions and L5/L6 expectations¶

    Questions: How is maximum overshoot calculated? What happens when 1,000 hosts hit one tenant? How do policy rollback and stale agents interact? Why not use a sliding log? How would you support request cost greater than one? Can a global quota remain available through a partition without exceeding its bound?

    An L5 candidate should clarify algorithms, estimate QPS and state, define atomic updates, shard keys, handle retries and store failure, and discuss hot tenants. An L6 candidate should make slack a product contract, separate planes, derive lease sizing, design escrow and fencing, stage policy migrations, set overload priorities, and connect precision choices to dependency capacity and revenue risk.

    21. Five-minute summary¶

    The limiter performs millions of checks on the local request path. Canonical policies live in a strongly consistent database and compile into signed versioned bundles, so a control-plane failure does not stop enforcement. Gateways evaluate applicable policies in process. For shared quotas, they consume short adaptive leases atomically reserved from sharded regional token buckets. Lease size controls the explicit overshoot bound. Hot global limits are split into regional escrow budgets rather than requiring cross-region consensus. Immutable bundle swaps prevent mixed versions; request IDs deduplicate reservations; fencing protects shard movement. Failure behavior is per policy, with strict routes denying and availability-oriented routes using bounded emergency capacity. Telemetry, shadow rollout, Zipfian load tests, and game days verify decisions and propagation. The key tradeoff is precision versus latency and availability, stated quantitatively rather than hidden.
