    Design a Secrets Management Service¶

    1. Interview roadmap¶

    Design a service that stores, issues, rotates, and revokes credentials for workloads and humans. Clarify secret types, identity authority, read availability, revocation speed, audit, and disaster recovery. Start with encrypted versioned secrets behind authenticated APIs, then add workload identity, envelope encryption, dynamic credentials, leases, rotation workflows, edge agents, policy compilation, and break-glass recovery. Security invariants dominate convenience: a highly available service that discloses the wrong secret has failed.

    2. Product framing¶

    Tenants store API keys, certificates, database passwords, and encryption material, or request short-lived credentials generated for downstream systems. Workloads retrieve by logical path and version; operators define policy and rotation. The service is not a general configuration store, KMS replacement, or place to put large blobs. KMS protects root keys; secrets management applies identity, policy, lifecycle, and delivery.

    Targets: 99.99% control writes, 99.999% cached workload reads for eligible secrets, under 50 ms p99 regional retrieval, routine revocation propagation within 60 seconds, complete durable audit, and zero plaintext in logs/backups. Availability modes differ: payment signing keys may fail closed, while a replicated read-only database password may use bounded stale cache.

    3. Functional and non-functional requirements¶

    Support create/read/version/delete, CAS, metadata listing, access policy, workload and human login, dynamic database/cloud credentials, leases, renew/revoke, rotation, certificate issuance, audit, notifications, import/export, and recovery. Non-functional requirements include least privilege, tenant isolation, key separation, tamper evidence, bounded blast radius, secure deletion, and operability during identity/KMS/downstream outages. We exclude arbitrary secret sharing links and direct storage of root HSM keys.

    4. Correctness and security invariants¶

    • Every disclosure is authorized against authenticated identity, resource, action, context, and a known policy generation.
    • Plaintext exists only in bounded trusted memory and is never persisted outside encrypted envelopes.
    • A secret version is immutable; rotation creates a new version and explicit activation state.
    • Lease/revocation generation fences stale renewals and issuers.
    • Dynamic credential issuance has one durable request identity and a reconciled downstream effect.
    • Audit records are append-only, ordered per tenant, and independently tamper-evident.
    • Deletion respects retention/legal hold and eventually removes all ciphertext/data-key references and backups per policy.
    • No control-plane outage silently broadens access.

    5. Capacity estimates¶

    Assume 100 million secret objects, 20 versions average, 5 million workload reads/s at fleet start, 20,000 writes/s, and 100,000 dynamic leases/s. At 2 KB ciphertext plus metadata per version, stored data is about 4 TB before replication and audit. Reads are bursty: deployment or node restart can multiply normal QPS by 100. KMS cannot unwrap per request at this rate; regional key caches, agents, and envelope encryption are required. Audit volume may exceed secret storage and must have independent capacity.

    6. Core entities and data model¶

    Secret(path, tenant, type, metadata, current_version, policy_ref, state)
SecretVersion(secret_id, version, ciphertext, wrapped_DEK, checksum, state, created_at)
Policy(policy_id, statements[], generation, compiled_hash)
Identity(subject, issuer, claims, session_generation)
Lease(lease_id, secret/version, subject, expiry, renewable, generation, state)
Rotation(job_id, secret, old_version, new_version, phase, deadline)
AuditEvent(event_id, tenant_sequence, actor, action, resource_hash, decision, chain_hash)

    Canonical metadata is separate from encrypted payloads. Paths are normalized and bounded. Listing returns metadata only through opaque, policy-bound cursors; it never decrypts values. Deletion writes a tombstone and queues cryptographic and physical erasure.

    7. API and delivery interfaces¶

    POST /v1/secrets/{path}/versions  Idempotency-Key, If-Match
GET  /v1/secrets/{path}?version=
DELETE /v1/secrets/{path}/versions/{v}
POST /v1/engines/{name}/credentials {role, ttl, request_id}
POST /v1/leases/{id}:renew
POST /v1/leases/{id}:revoke
POST /v1/secrets/{path}:rotate

    Responses include version, lease ID, expiry, renewable flag, policy generation, and a non-secret request ID. Workloads preferably use a node-local agent over a protected Unix socket. The agent authenticates workload identity and either serves an in-memory API or atomically replaces a tightly permissioned file on a memory-backed mount with swap and core dumps disabled. Do not write plaintext to an ordinary persistent volume, include that mount in backups, or assume atomic rename supplies confidentiality. Consumers must reopen the file on rotation; already copied plaintext cannot be recalled by changing the mount.

    8. High-level architecture¶

    flowchart LR
 W[Workloads and operators] --> I[Identity gateway]
 I --> A[Regional secret API]
 A --> P[Policy decision]
 A --> M[(Consensus metadata)]
 A --> O[(Encrypted object store)]
 A --> K[KMS/HSM]
 A --> E[Dynamic secret engines]
 E --> D[Databases/cloud/PKI]
 A --> U[Node-local agents]
 A --> L[Immutable audit pipeline]
 C[Global control plane] --> P

    The control plane manages tenants, policies, engines, key hierarchy, and replication. The data plane authenticates, authorizes, decrypts/leases, and delivers from regional cells. Agents may cache specifically permitted values, but policy and ciphertext remain canonical centrally.

    9. Static secret write and read paths¶

    On write, the API authenticates the caller, evaluates write policy, validates CAS/version limits, generates a random data-encryption key (DEK), encrypts plaintext with AEAD using tenant/path/version as associated data, wraps the DEK under a tenant-region key in KMS, and zeroizes plaintext buffers. One metadata transaction commits immutable ciphertext reference, checksum, current version, and operation ID. A lost response can be retried safely.

    On read, authenticate fresh workload credentials, evaluate compiled policy, fetch ciphertext, unwrap or retrieve a short-lived cached DEK, verify associated data/tag, emit audit, and return over mTLS. To meet the stated complete-audit target, durably append the disclosure decision before releasing plaintext and fail closed if the tamper-evident spool cannot accept it. A best-effort audit tier is a separately named weaker contract. The event proves authorized release was attempted, not that the client received the bytes.

    10. Identity and authorization¶

    Bootstrap is the hardest dependency. Workload identity should derive from an attested orchestrator identity, hardware identity, or short-lived signed service account token, not a baked-in shared secret. The gateway validates issuer, audience, nonce, expiry, workload generation, and channel binding. Human access uses SSO, MFA, reason/ticket, and stronger approval for production or break-glass operations.

    Policies are deny-by-default statements over tenant, path, action, identity attributes, environment, and optional network/device context. Compile and distribute signed policy bundles. A data cell may continue using a bounded-age bundle; emergency deny/revocation uses a high-priority channel. Avoid fetching group membership synchronously on each read.

    11. Deep dive: envelope encryption and key hierarchy¶

    An HSM-backed root protects regional/tenant key-encryption keys (KEKs); KEKs wrap per-version DEKs; DEKs encrypt data. This limits HSM throughput and blast radius. Associated data prevents moving ciphertext between tenants or paths. Cache unwrapped KEKs/DEKs only in locked memory for short periods, with process isolation and explicit zeroization; cache misses are rate-limited so a KMS outage does not become a storm.

    KEK rotation rewraps DEKs without exposing or rewriting plaintext. Root rotation rewraps KEKs under dual control. Compromise response identifies all descendants, disables issuance, rotates affected material, and preserves forensic audit. Cryptographic deletion destroys wrapping keys only when no unrelated secret shares them; otherwise delete the per-version wrapped DEK and ciphertext through retention workflows.

    12. Deep dive: dynamic credentials and leases¶

    For a database role, the engine reserves a durable issuance record keyed by request ID, creates a unique username/password with constrained grants and expiry, records downstream identity, then marks the lease active. A timeout after database creation is ambiguous; reconciliation queries by deterministic username/request tag rather than creating duplicates. If creation cannot be proven, reconcile or revoke candidates under the same issuance identity. Do not issue a fresh identity until a late old create cannot leave an active orphan; require downstream request fencing, an authoritative terminal result, or continued quarantine with native expiry.

    Renewal verifies subject, lease generation, maximum lifetime, and downstream state. Serialize renewal and revocation in the canonical lease workflow and ensure downstream ordering or reconciliation prevents a delayed renew from restoring revoked access. Revocation is idempotent and retries until the downstream confirms removal. Expiry uses a timing wheel to schedule work, but a durable lease state drives correctness. Downstream outage means leases may outlive control metadata; short native database TTLs and reconciler scans limit exposure.

    Native expiry often blocks only new authentication, not sessions already established with the credential. Verify each backend's session semantics; strict revocation may require terminating sessions or an authorization proxy checking a current lease. Do not certify a sixty-second access-revocation bound solely from a password expiry or a queued revoke job.

    13. Deep dive: rotation without downtime¶

    Rotation is a state machine, not UPDATE password. Generate a candidate, install it downstream, verify it independently, publish version N+1, wait for consumers to acknowledge/reload, then revoke N after a bounded overlap. For systems supporting two active credentials this is safe. For single-password accounts, create a replacement principal or coordinate a maintenance window.

    Agents write secret.tmp, fsync, rename atomically, and signal/reload the process. Consumers report version, but absence of acknowledgement is not proof of absence. Rollback before old revocation restores routing to N; after revocation it requires generating another credential. Rotation jobs are resumable and each phase is idempotent.

    14. Partitioning, scaling, and overload¶

    Partition metadata by tenant/path hash while colocating one secret's versions and leases where practical. Large tenants receive dedicated cells. Reads scale through stateless APIs, encrypted object storage, policy caches, DEK caches, and node agents. Dynamic engines shard by backend/role to enforce downstream quotas. Audit partitions by tenant sequence and fans out asynchronously.

    Overload priority is revoke/emergency deny, established lease renewal, ordinary reads, writes, then bulk list/rotation. Bound authentication, KMS unwrap, engine creation, and audit queues separately. Use singleflight for identical cache misses, jitter agent renewal, issue server retry windows, and apply per-tenant fairness. Never fail open authorization because policy/KMS is slow. Eligible agents may serve a bounded cached secret, clearly exposing version/age.

    15. Consistency and idempotency¶

    Secret metadata/version activation and lease generations are linearizable per secret/lease. Policy and agent caches are bounded eventual; revocation SLO includes their maximum age. Read-after-write through the API can pin minimum version, while an agent may lag. Mutation tokens map retries to one version/job. Dynamic issuance uses durable request records and reconciliation, not exactly-once claims. Audit transport is at least once with stable event IDs and sequence-gap detection.

    16. Reliability, failure modes, and recovery¶

    Metadata consensus spans zones; loss of quorum stops writes and sensitive uncached reads. Encrypted object replicas are checksummed. KMS outage allows only explicitly cached decryptions until key-cache expiry. Identity outage permits existing short-lived sessions only within policy. Engine outage blocks issuance but not static reads; revocation queues persist and alert.

    Backups contain ciphertext, metadata, policy, and audit checkpoints, encrypted under separate recovery keys held with dual control. Restore into an isolated cell, validate audit/key references, reconcile dynamic credentials, and rotate high-risk secrets before serving. A compromised region is fenced by control epoch and identities, not merely removed from DNS.

    17. Multi-region strategy¶

    Each secret has a home region for writes and asynchronous encrypted replicas elsewhere. Reads may occur in approved regions only, respecting residency policy. Promotion uses a fenced ownership epoch and documented RPO; concurrent active writers are avoided. Globally needed secrets can use synchronous metadata across regions at WAN latency, but plaintext never replicates, only envelopes. Regional KEKs isolate wrapping authority, but a region authorized to decrypt a replicated secret can disclose that same plaintext. Key separation alone does not isolate the secret value shared across regions.

    18. Security and abuse prevention¶

    Apply least privilege, separation of duties, two-person recovery/root operations, mTLS, HSM keys, memory hardening, no swap/core dumps, restricted debug endpoints, signed binaries/bundles, dependency provenance, and immutable external audit copies. Defend against confused deputy paths, token replay, SSRF through engines, policy wildcard mistakes, secret enumeration, response caching, log leakage, clipboard/UI exposure, malicious plugins, and administrator misuse. Honey secrets can detect unexpected access but never replace controls.

    Deletion first denies reads, tombstones versions, revokes dynamic effects, removes agent caches, then expires ciphertext and backups. Legal hold prevents physical erasure and is itself audited. Rate and anomaly controls can require step-up approval, but automated workload retrieval must not depend on brittle behavior models.

    19. Observability and testing¶

    Measure auth/policy decisions, read/write/issue/revoke latency, denial reasons, secret/policy version age, cache/stale use, KMS calls/errors, audit spool lag/gaps, lease expiry/revocation lag, rotation phase/age, engine reconciliation, plaintext response bytes by class, and unusual subject/path access. Never put secret paths, values, tokens, or decrypted data in broad metric labels/traces; use keyed hashes and restricted correlation maps.

    Property-test policy precedence, lease fencing, CAS, rotation transitions, and deletion retention. Fuzz parsers and engine responses. Use known-answer crypto and ciphertext-swapping tests. Load-test fleet bootstrap, KMS cold cache, mass rotation, and audit backpressure. Chaos-test identity/KMS/database outage, clock skew, lost responses, stuck revocation, region compromise, corrupt backup, and agent restart. Red teams test exfiltration, privilege escalation, and operator pathways.

    20. Important tradeoffs¶

    Central fetch gives fresher revocation but makes every startup dependent on the service; bounded agents improve availability with exposure windows. Static credentials are operationally simple but long-lived; dynamic credentials reduce blast radius while adding downstream reconciliation. Global active-active writes improve convenience but complicate ownership and revocation; home-region authority wins. Durable audit-before-read improves assurance but can reduce availability, so expose it as a tenant policy.

    21. Final architecture¶

    The final design combines attested identity, immutable secret versions, envelope encryption, linearizable activation/leases, compiled deny-by-default policy, reconciled dynamic engines, resumable rotation, bounded agents, and independent audit.

    22. Interview deep-dive questions¶

    How does a workload obtain its first credential? What if DB creation succeeds but the response is lost? When may an agent serve stale? How do you rotate a one-password system? What does KMS outage do? How are revocations prioritized? How is a restored region prevented from issuing old leases?

    23. L5 and L6 expectations¶

    An L5 candidate covers identity, policy, envelope encryption, versions, leases, rotation, availability, audit, and threat modeling. An L6 candidate finds bootstrap and revocation invariants, separates planes and failure modes, designs downstream reconciliation and disaster fencing, quantifies stale exposure, and addresses governance, migration, residency, and human operations.

    24. Five-minute summary¶

    Five-minute summary: authenticate with attested short-lived identity; authorize locally against signed versioned policy; store only immutable AEAD ciphertext with per-version DEKs wrapped by HSM-backed keys; make activation and leases linearizable. Generate dynamic credentials through durable request records and reconciliation, rotate through overlap and acknowledgement, prioritize revoke under overload, and permit only explicitly bounded agent caching. Keep audit tamper-evident, test recovery and compromise, and fail closed whenever uncertainty could disclose to the wrong principal.
