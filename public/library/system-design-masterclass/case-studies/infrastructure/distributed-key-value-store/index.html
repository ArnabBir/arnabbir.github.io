    Design a Distributed Key-Value Store¶

    1. Interview roadmap¶

    Design a multi-tenant store for Get, Put, conditional update, delete, and range scan. Clarify value size, consistency, latency, transactions, durability, and regions. Start with range-sharded replicated state machines using a write-ahead log and LSM storage. Then add MVCC, snapshots, rebalancing, split/merge, overload control, repair, and explicit geo modes. The challenge is maintaining observable semantics through leader, disk, and network failure.

    2. Product framing¶

    Applications store opaque values under ordered keys. The store is canonical, unlike a cache. We support linearizable single-key operations and snapshot-consistent scans in-region; optional transactions span a bounded number of ranges. Cross-region replicas are asynchronous by default. Targets: 99.99% writes, 99.999% reads where stale reads are allowed, 10 ms p99 small operations in-region, and no acknowledged-write loss under the configured failure model.

    3. Requirements¶

    Support get/put/delete, compare-and-swap, batch, scans with continuation, TTL, watches, backups, quotas, encryption, and idempotent mutations. Values are at most 1 MB, typical 1 KB. Preserve ordered scans. Avoid claiming unlimited transactions, exactly-once delivery, or availability during loss of quorum.

    4. Correctness invariants¶

    • Each range has one current epoch and one quorum-approved leader/lease holder.
    • An acknowledged write is committed to a quorum and survives any allowed minority failure.
    • Reads at timestamp T return the newest committed version at or before T.
    • Split/merge and replica movement never create two writable owners for one key/epoch.
    • CAS evaluates and writes atomically at one serialization point.
    • Version and tombstone reclamation preserves every supported replica, live snapshot, transaction, incremental backup chain, and restore policy.
    • Retry deduplication never maps one token to two effects.

    5. Capacity estimates¶

    Assume 10 PB logical retained data, 10 billion keys, 5 million reads/s, 1 million writes/s, and 3x replication. Those storage and key counts imply 1 MB retained per key, not 1 KB. Separately assume incoming values average 1 KB plus 100 bytes metadata: logical ingest is 1.1 GB/s before replication and compaction. Reconcile this difference through a measured size distribution, retained MVCC versions, and retention period; if instead each key has only one 1.1 KB version, the logical dataset is 11 TB. Three durable copies require 3.3 GB/s aggregate replica writes; leader-to-follower replication alone is about 2.2 GB/s, excluding ingress. Hot keys invalidate uniform assumptions. At 10 PB, 10-50 GB ranges yield 200,000-1,000,000 ranges; target 50% disk and 60% CPU utilization to preserve repair and failover headroom.

    6. Core entities and data model¶

    Range(start_key, end_key, range_id, epoch, replicas[], leader, state)
Version(key, commit_ts, value_or_tombstone, expiry, checksum)
LogEntry(index, term, command, client_id, sequence)
Transaction(txn_id, read_ts, priority, writes, status)
Snapshot(range_id, index, files[], checksum)

    The metadata directory maps ordered key spans to range descriptors. Data uses an LSM: mutable memtable, immutable memtables, sorted-string tables, Bloom filters, sparse indexes, and a WAL. MVCC keys encode (user_key, descending_timestamp).

    This LSM is not a relational heap plus B+ tree: it trades background compaction and read amplification for buffered sequential writes. Database Indexing explains B+ tree and heap access paths, while Relational Databases explains PostgreSQL-style WAL, checkpoints, transactions, and replicas.

    7. Interface¶

    Get(key, consistency, read_timestamp?) -> value, version
Put(key, value, idempotency_token, precondition?) -> version
Delete(key, token, precondition?) -> version
Scan(start, end, limit, cursor, read_timestamp?) -> rows, cursor
Txn(reads, conditions, writes, token) -> committed|aborted
Watch(prefix, after_revision) -> changes|compacted

    Opaque scan cursors bind range end, last key, read timestamp, directory epoch, and expiry. Clients retry NOT_LEADER and stale-epoch responses after refreshing descriptors, under one deadline.

    8. High-level architecture¶

    flowchart LR
 C[Clients] --> G[Smart client/gateway]
 G --> M[Metadata directory]
 G --> R[Range leaders]
 R --> F[Range followers]
 R --> W[WAL and LSM]
 M --> P[Placement control plane]
 P --> R
 R --> B[Backup/change stream]
 X[Compaction and repair] --> W

    The control plane places ranges and coordinates epochs. The data plane replicates each range through consensus and serves reads/writes. Placement outages stop movement but not operations on healthy ranges.

    9. Write and read paths¶

    A gateway locates the range and sends a mutation to its leader with client sequence. The leader validates epoch/precondition, appends to its WAL, replicates the log, waits for majority durable acknowledgement, applies in order to memtable/MVCC, and responds. Followers reject stale leader terms. Group commit batches fsync without weakening quorum durability.

    sequenceDiagram
    autonumber

    Linearizable reads go through the leader after confirming its lease/quorum or a read-index round. Snapshot reads at a sufficiently old closed timestamp can use followers. Bloom filters skip SSTables for absent point keys; reads merge memtable and SSTable versions. Read repair is not a substitute for consensus.

    10. LSM storage and compaction¶

    WAL provides recovery; memtables batch random writes into sorted sequential SSTables. Leveled compaction bounds read amplification, while size-tiered compaction favors write throughput but uses more space. Per-level checksums detect corruption. Block cache and Bloom filters accelerate reads, but canonical bytes remain WAL/SSTables.

    Compaction is correctness-sensitive: it can drop an overwritten version only below the global safe timestamp, and a tombstone only when no older value can reappear from covered storage levels or supported replica recovery. A self-contained old backup does not pin live tombstones forever: backup retention and restore-time deletion replay enforce its separate lifecycle. Incremental backup chains must retain their required bases and changes. Scheduler budgets disk and CPU so foreground latency wins. Emergency disk fullness rejects writes before WAL safety is endangered and prioritizes flush/space reclamation.

    11. Deep dive: consensus, leases, and clocks¶

    Raft-like consensus orders writes per range. Election terms fence old leaders. A lease avoids quorum reads only when clock uncertainty and maximum pause are bounded; otherwise use read index. Lease expiration is conservative under clock jumps. Committed log entries survive leader change, while uncommitted suffixes may be truncated and must never have been acknowledged.

    Thousands of ranges share processes, so elections use jitter and capped concurrency. A node outage must not trigger every range election simultaneously. Leaders are spread by load/failure domain, not simply count.

    12. Deep dive: range split, merge, and movement¶

    When size/QPS crosses thresholds, choose a sampled key boundary. The parent commits a SPLITTING record at index, creates child descriptors with higher epochs, snapshots shared files, then atomically updates directory ownership. Requests with old epochs receive both child hints. Shared immutable SSTables avoid immediate copying.

    Replica movement first adds a learner, streams a snapshot plus log tail, catches up, promotes it through consensus, then removes the old replica. Never reduce quorum during transfer. Merge requires adjacent ranges, compatible replicas, low load, and one committed transition. Reconciliation repairs stuck transitions.

    stateDiagram-v2
 [*] --> ACTIVE
 ACTIVE --> SPLITTING: size or QPS
 SPLITTING --> ACTIVE: abort safely
 SPLITTING --> RETIRED: children installed
 ACTIVE --> MOVING: add learner
 MOVING --> ACTIVE: promote then remove
 ACTIVE --> MERGING: adjacent cold range
 MERGING --> RETIRED: merged range installed

    13. Deep dive: transactions¶

    Single-range transactions execute in one replicated command. For cross-range transactions, MVCC plus two-phase commit writes intents at participants and a transaction record at a coordinator range. Reads encountering intents resolve committed/aborted status. Wound-wait priorities or wait queues handle conflicts; deadlock is bounded by transaction deadlines.

    The coordinator's commit decision is durable before participants finalize, so a crash leaves resolvable intents. Background recovery aborts expired pending transactions only after proving no commit. Transactions have limits on keys, bytes, ranges, and duration because old read timestamps block garbage collection.

    14. Partitioning, hot keys, and overload¶

    Ordered range partitioning enables scans but a sequential key pattern hotspots the final range. Encourage hash prefixes for non-scan workloads, pre-split known tenants, and split by QPS as well as bytes. One key cannot be split while retaining linearizability; mitigate with application sharding, commutative counters, batching, caching reads, or a dedicated range.

    Admission controls exist per node, tenant, and range. Separate read/write/maintenance queues; bound them by deadline and weighted fairness. Backpressure starts before memtable/WAL/disk saturation. Reject optional stale reads last if cheap, preserve replication and heartbeats, and stop accepting writes when quorum durability or disk reserve is threatened.

    15. Consistency and idempotency¶

    Linearizable operations serialize through the range leader. Snapshot isolation prevents inconsistent scans but permits write skew unless serializable conflict checks are enabled. Cross-range serializability uses timestamp ordering and read/write conflict tracking at added latency. Watches are at least once; resume from revision or receive compaction reset.

    Dedup records (client_id,sequence)->result replicate with the write and expire after a documented retry window. After expiry, clients need application idempotency. TTL is a logical tombstone based on server/HLC time; physical deletion is asynchronous.

    16. Reliability and recovery¶

    Leader loss elects a follower; minority partitions stop writes, avoiding split brain. Corrupt blocks retry another replica, quarantine the file, and repair from checksummed snapshots. Anti-entropy compares range/index and file hashes, but consensus determines authoritative history. Node replacement uses throttled learners. Backups combine periodic snapshots with ordered logs and are restored into an isolated cluster before promotion.

    The control plane continuously reconciles descriptor ownership, replica count/diversity, learner age, disk skew, and unavailable ranges. Disaster drills prove restore point and restore time rather than merely checking backup job success.

    17. Multi-region strategy¶

    For strong global data, place quorum replicas across regions, accepting WAN write latency and correlated network partitions. More commonly, each keyspace has a home region with synchronous multi-zone replicas and asynchronous remote logs. Promotion requires an explicit fenced epoch and known recovery point; acknowledged writes not replicated remotely may be lost under region destruction according to stated RPO.

    Active-active is offered only with constrained semantics such as LWW, CRDT counters/sets, or application conflict resolution. Calling conflicting opaque values "eventually consistent" does not solve them. Tenant policy selects latency, RPO, and conflict model.

    18. Security and abuse prevention¶

    Use mTLS workload identity, tenant/key-prefix ACLs, envelope encryption, HSM-backed keys, audit logs, signed backups, network isolation, and redacted diagnostics. Defend against oversized values, scan amplification, hot-key denial, transaction/intents exhaustion, watch fanout, and noisy neighbors with quotas. Key rotation rewrites wrapped data keys without blocking reads; deletion uses tombstones, retention, compaction, and backup lifecycle.

    19. Observability and testing¶

    Measure latency by operation/consistency, QPS/bytes, proposal-to-commit time, leader changes, quorum health, WAL fsync, compaction debt, read/write/space amplification, cache/Bloom efficacy, range skew, hot keys, split/move duration, transaction conflicts/intents, safe timestamp, replication lag, disk errors, and rejected work.

    Model-check election, reconfiguration, split, and transaction races. Property-test MVCC visibility, CAS, cursors, dedup, and tombstone GC. Fuzz WAL/SSTable corruption. Load-test sequential keys, one hot key, scans during compaction, node replacement, and retry storms. Chaos-test partitions, pauses, clock changes, disk-full, torn writes, and restore.

    20. Important tradeoffs¶

    Hash shards balance writes but lose range scans; ordered ranges win the required interface. Replication is simpler than erasure coding for small mutable values. Leaderless quorum can improve availability but conflict/read-repair semantics complicate conditional writes; consensus ranges win. Transactions add coordination and GC pressure, so bound them. Follower reads lower latency but expose staleness.

    flowchart TD
 D[Range directory with epochs] --> C[Smart routing]
 C --> L[Consensus range leader]
 L --> Q[Zonal quorum]
 Q --> S[WAL plus MVCC LSM]
 P[Placement and split controller] --> L
 S --> A[Snapshots, logs, repair]
 A --> R[Async disaster-recovery region]

    21. Final architecture¶

    The final design uses epoch-fenced ordered ranges, per-range consensus, quorum-durable WAL commits, MVCC LSM storage, controlled split/move workflows, and asynchronous disaster-recovery replication.

    22. Interview deep-dive questions¶

    When is a write acknowledged? Can a follower serve linearizable reads? How does a split avoid dual ownership? When may tombstones disappear? What happens to 2PC after coordinator failure? How is one hot key handled? What RPO follows asynchronous geo replication?

    23. L5 and L6 expectations¶

    An L5 candidate covers sharding, consensus, LSM, read/write paths, hot keys, recovery, and consistency. An L6 candidate states durability proofs, handles reconfiguration and GC invariants, quantifies overload/repair headroom, separates placement from serving, and offers explicit geo products rather than one vague consistency mode.

    24. Five-minute summary¶

    Five-minute summary: partition ordered keys into epoch-fenced ranges; replicate each through consensus; acknowledge after quorum-durable WAL commit; store MVCC versions in an LSM; route linearizable reads through a valid leader and safe snapshot reads to followers. Split and move through logged transitions, retain tombstones until safe, bound transactions and queues, reserve repair capacity, and expose region failure as a deliberate latency/RPO choice.
