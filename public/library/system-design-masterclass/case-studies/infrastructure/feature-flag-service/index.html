    Feature Flag Service¶

    1. Interview roadmap¶

    We will design a feature-management service that lets teams change behavior without redeploying code. We begin with evaluation semantics and blast-radius invariants, estimate policy distribution and evaluation volume, define flag models and APIs, then separate a strongly governed control plane from an in-process data plane. Deep dives cover deterministic targeting, snapshots and streaming, dependencies, stale state, experimentation, and multi-region recovery.

    2. Product framing¶

    A flag maps an evaluation context to a typed variation. Teams use flags for release ramps, kill switches, entitlements, configuration, and experiments. Most evaluations must happen in-process to avoid adding a remote dependency to every request. The platform distributes signed, versioned configuration to SDKs and records exposure events asynchronously. It is not an authorization system: security decisions require a dedicated policy engine and server-side trusted attributes.

    3. Requirements¶

    Functional requirements:

    • Create boolean, string, number, and JSON flags with environments and owners.
    • Target by attributes, segments, prerequisites, percentage rollout, and schedules.
    • Stage, approve, activate, rollback, archive, and audit changes.
    • Evaluate through server/client SDKs and a remote API for thin clients.
    • Emit exposure events and support experiment assignment without metric analysis itself.

    Non-functional requirements:

    • One million flags across tenants, 20 million evaluations/s, and 10 million connected SDK instances.
    • In-process p99 below 100 microseconds; remote p99 below 20 ms.
    • Normal changes propagate in 10 seconds; kill switches in 2 seconds.
    • Evaluations continue during control-plane and network outages.

    4. Correctness invariants¶

    1. One evaluation uses one immutable environment snapshot and returns a variation valid for that snapshot.
    2. Percentage assignment is deterministic for the same flag salt, subject key, and rollout definition.
    3. Tenant and environment boundaries are enforced before configuration reaches an SDK.
    4. A stale SDK follows the declared fallback policy; staleness never silently becomes authorization.
    5. Audit history is append-only and links every activation to actor, prior version, and review state.
    6. Exposure events do not alter evaluation and are deduplicable; analytics loss cannot block requests.

    5. Capacity estimates¶

    Twenty million evaluations/s cannot afford network calls, confirming local SDK evaluation. Suppose one million flag definitions average 2 KB: 2 GB total, but each environment subscribes only to relevant projects, perhaps 5 MB per server snapshot. Ten million clients receiving 5 MB full snapshots would imply 50 TB per fleet refresh, not 50 PB; repeated refreshes and reconnect storms still justify deltas and CDN distribution. Mobile/web clients receive only public, client-enabled flags; server agents use deltas. If 1% of evaluations emit 300-byte sampled exposures, telemetry is 60 MB/s. A kill-switch update to one million subscribed instances in two seconds needs hierarchical fan-out rather than one control server holding every connection.

    6. Entities and data model¶

    Flag(flag_id, project_id, key, type, owner, purpose, archived)
FlagVersion(flag_id, version, variations[], rules[], prerequisites[],
            fallthrough, off_variation, salt, created_by, checksum)
Environment(env_id, tenant_id, name, active_bundle_version, policy)
Segment(segment_id, version, included_keys, excluded_keys, rules[])
Bundle(bundle_version, env_id, flags[], segments[], checksum, signature)
Change(change_id, env_id, base_version, patch, state, approvals[], audit)
Exposure(event_id, flag_id, flag_version, subject_hash, variation, reason)

    The transactional control database is canonical. Immutable bundles in object storage/CDN and SDK memory are projections. Audit events are durable and separate from best-effort exposure telemetry.

    7. Interfaces¶

    POST /v1/projects/{p}/flags
PUT  /v1/flags/{key}/versions/{v}       If-Match: etag
POST /v1/changes/{id}:approve
POST /v1/changes/{id}:activate
POST /v1/environments/{id}:rollback
GET  /v1/sdk/bundles/latest             If-None-Match: checksum
GET  /v1/sdk/stream                     Last-Event-ID: bundle-version
POST /v1/evaluate

    SDK call:

    evaluate(flagKey, expectedType, subjectContext, callerDefault)
  -> Detail{value, variationId, reason, flagVersion, bundleVersion, stale}

    Unknown flags, type mismatches, missing attributes, cycles, and stale snapshots return typed reasons plus the caller-supplied default.

    8. High-level architecture¶

    flowchart LR
  Admin --> API[Flag management API]
  API --> DB[(Control DB)]
  DB --> Compiler[Validator/compiler]
  Compiler --> Blob[(Signed bundles)]
  Compiler --> Fanout[Regional stream fan-out]
  Blob --> CDN
  Fanout --> Relay[Host relay/agent]
  Relay --> SDK[In-process SDK]
  CDN --> ClientSDK[Client SDK]
  App --> SDK
  SDK --> Events[Exposure pipeline]

    The control plane owns authoring, review, compilation, and publication. The data plane is bundle distribution and deterministic SDK evaluation. Host relays multiplex connections for server processes. SDKs retain a validated last-known-good bundle, so control-plane unavailability does not enter application hot paths.

    9. Authoring and publication¶

    An edit creates a change against a base environment version. Validation checks types, missing variations, segment references, prerequisite cycles, unreachable rules, client-visible sensitive attributes, and maximum evaluation complexity. A simulator runs saved contexts and reports changed decisions. High-risk environments require a second approver and scheduled activation window.

    The compiler resolves references, produces deterministic ordering, signs a complete immutable bundle, stores it, then atomically advances the environment's active pointer. Distribution begins only after durable publication. Rollback activates a prior bundle's content as a new monotonic version, preserving audit chronology. Flag changes and code deploys should not be coupled transactionally; teams use defaults and staged rollout.

    10. Deterministic evaluation algorithm¶

    Given a captured snapshot: locate flag; verify type and on/off status; recursively evaluate prerequisites with a depth and visited-set bound; evaluate rules in order; then use fallthrough. A rule checks clauses against trusted context and segment membership. First matching rule wins. A percentage rollout hashes a canonical, length-prefixed encoding of (flag_salt, stable_subject_key, optional_group_key) into a fixed bucket, then selects the cumulative weight range. Specify UTF-8 normalization and field presence so concatenation cannot confuse distinct tuples.

    Never use language-native hash functions because versions may differ. Specify an algorithm such as SHA-256 first 64 bits modulo 100,000 and publish cross-language golden vectors. Changing variation weights preserves assignments in unchanged bucket ranges; changing salt intentionally reshuffles. Mutually exclusive experiments first hash into a shared allocation group with disjoint enrollment ranges, then select a variation inside the assigned experiment. Sharing a salt alone does not prevent two experiments from enrolling the same subject.

    flowchart TD
  Start[Capture bundle pointer] --> Exists{Flag exists and type matches?}
  Exists -->|no| Default[Caller default + reason]
  Exists -->|yes| Enabled{Flag enabled?}
  Enabled -->|no| Off[Off/fallback variation]
  Enabled -->|yes| Pre[Evaluate prerequisites]
  Pre -->|failed| Off[Off/fallback variation]
  Pre -->|passed| Rules[Rules in order]
  Rules --> Match{Rule matched?}
  Match -->|yes| Split[Variation or deterministic bucket]
  Match -->|no| Fall[Fallthrough]
  Split --> Detail[Value + version + reason]
  Fall --> Detail
  Off --> Detail
  Default --> Detail

    11. Distribution and propagation¶

    Regional fan-out nodes consume active-pointer events and notify relays through long-lived streams. Notifications can carry compact deltas, but each delta names base and target checksum. If a relay missed a version or checksum fails, it downloads the full signed bundle from object storage/CDN. SDKs parse and validate off-thread, then atomically swap one immutable pointer. Existing evaluations finish against the old snapshot.

    Connections use jittered reconnect and exponential backoff. Hierarchical relays reduce connection count and absorb bursts. Polling remains a repair path even when streaming works. The service measures publication-to-observation latency using relay acknowledgments and SDK heartbeat samples, not merely server publish time.

    sequenceDiagram
    autonumber
  participant U as Operator
  participant C as Compiler
  participant O as Bundle store
  participant R as Regional relay
  participant S as SDK
  U->>C: activate approved change
  C->>O: store signed bundle V42
  C->>C: CAS active pointer to V42
  C-->>R: version notification
  R-->>S: delta V41 to V42
  S->>S: verify, compile, atomic swap
  S-->>R: observed V42

    12. Segments, prerequisites, and complexity¶

    Small static segments can compile into sorted hashed-key sets or Bloom filter plus exact set. Very large dynamic segments may be delivered as versioned snapshots to server SDKs; remote lookup on every evaluation violates availability and latency. If freshness demands remote membership, expose that weaker mode explicitly and cache with fail behavior. Sensitive segment membership never ships to untrusted browser SDKs.

    Prerequisites form a directed acyclic graph checked at publish time. Evaluation memoizes flag results within one call and caps depth, clauses, regex complexity, and segment size. Cyclic or excessive bundles are rejected, not handled recursively in production.

    13. Partitioning, scaling, and hot paths¶

    Control data partitions by tenant/project; bundle compilation queues isolate tenants. The distribution plane partitions subscriptions by environment and relay. A global kill switch is a fan-out hot key, addressed by CDN caching, relay trees, and reserved emergency bandwidth. Client SDK snapshots use cache-control plus versioned URLs; never personalize a CDN bundle with server-only rules.

    Evaluation allocates no objects on the common path where practical. Precompile clause accessors and regexes, canonicalize rules, and keep snapshots immutable. Exposure emission uses a bounded nonblocking buffer. If full, sample or drop according to purpose and increment a local loss metric; evaluation never waits.

    14. Consistency and idempotency¶

    Management writes are strongly consistent and use optimistic concurrency. Activation is linearizable at the environment pointer, while SDK visibility is eventual. Every evaluation reports its bundle and flag versions, making mixed fleet state diagnosable. There is no global instant at which all processes switch.

    Activation requests carry idempotency keys. Bundle content is content-addressed, so repeat compilation is harmless. Stream events are at least once and SDK application is monotonic within a publisher epoch; resync validates the current authorized epoch/version and cannot silently accept a stale signed bundle as current. Exposure IDs derive from request/decision identity where available; analytics deduplicates but tolerates loss. Experiment assignment is deterministic rather than stored per request.

    15. Failure modes and recovery¶

    • Control database outage: evaluation and distribution of existing bundles continue; edits pause.
    • Compiler bug or corrupt bundle: signature/schema checks retain last-known-good; canary relays block broad rollout.
    • Stream outage: SDKs poll CDN with jitter and continue stale.
    • CDN outage: relays serve cached bundles; new instances use packaged bootstrap defaults if no cache exists.
    • SDK memory pressure: reject oversized bundle before swap and report health.
    • Exposure pipeline outage: bounded buffers drop analytics, never application traffic.
    • Operator misconfiguration: approvals, simulations, percentage ramps, automated guardrails, and one-click rollback limit blast radius.

    Kill switches need a safe compiled default and regular drills. A stale-age policy may force a safety-critical flag to its off variation after a deadline, while ordinary release flags stay last-known-good.

    16. Multi-region strategy¶

    Run active regional distribution and remote evaluation, backed by globally replicated immutable bundles. Keep one home writer for each environment to avoid conflicting activation order; failover acquires a higher publisher epoch before accepting writes. Regions can distribute cached bundles throughout a control outage. CDN snapshots cover mobile clients globally.

    Data residency applies to contexts and exposure events. Local SDK evaluation keeps attributes in-process. Exposure events hash stable keys with tenant-specific salts and remain regional unless approved. A region disconnected during activation keeps its prior bundle and reports stale; it does not synthesize a version.

    flowchart TB
  Writer[Home control writer, epoch 8] --> Global[(Replicated bundle store)]
  Global --> RA[Region A relays]
  Global --> RB[Region B relays]
  RA --> SA[SDK fleet A]
  RB --> SB[SDK fleet B]
  Witness[Failover coordinator] -->|grant epoch 9| Standby[Standby writer]
  Standby --> Global

    17. Security and abuse prevention¶

    Management uses SSO, RBAC, environment-scoped roles, mandatory approval for production, and immutable audits. SDK credentials are project/environment scoped and rotated. Server secrets and rules never enter client-visible bundles. Bundle signatures prevent tampering; TLS protects transport. Context values are minimized and redacted from diagnostics. Attribute names are schema-governed to prevent teams targeting protected characteristics without review. Rate limits and bundle-size limits stop accidental fan-out abuse.

    18. Observability and testing¶

    Track evaluation count and reason, default/error rate, SDK latency, snapshot age, version distribution, propagation percentiles, stream reconnects, full-resync rate, bundle size, compiler failures, exposure loss, and per-flag variation ratios. Avoid raw subject labels. An explain tool evaluates a supplied context against a specified historical bundle and returns clause decisions without changing state.

    Golden vectors run in every SDK language for hashing, type coercion, semver, dates, and regex behavior. Property tests guarantee bucket stability and total variation weights. Differential tests compare SDKs against a reference interpreter. Publication tests crash between object upload and pointer activation. Scale tests fan out emergency changes and reconnect all clients with jitter. Game days block control plane and CDN, rotate signing keys, and rehearse kill switches.

    19. Important tradeoffs¶

    Remote evaluation centralizes logic and fresh data but adds latency and a hard dependency. Local evaluation wins for availability but accepts propagation delay and SDK complexity. Deltas save bandwidth but need full-snapshot repair. Ordered first-match rules are understandable but make reordering behavioral. Large static segments consume memory; remote segments weaken availability. Last-known-good favors continuity, while stale-to-off favors safety; choose per flag purpose.

    20. Final design, questions, and expectations¶

    The final design stores governed, versioned flags in a transactional control plane, compiles signed immutable environment bundles, distributes them through regional relay trees and CDN, and evaluates against atomic in-memory snapshots. Deterministic hashing provides stable rollout. Polling repairs streams, defaults handle bootstrap, and exposure telemetry remains asynchronous.

    Interview questions: How do ten million SDKs receive a kill switch? How is percentage stability tested across languages? What happens if a prerequisite changes mid-evaluation? Why are flags not authorization? How does rollback interact with monotonic versions? How do large segments work?

    An L5 candidate should define rules, local evaluation, versioned distribution, deterministic rollout, fallbacks, and auditing. An L6 candidate should separate planes, quantify propagation, design governance and blast-radius controls, specify stale semantics by purpose, handle cross-language compatibility, residency, migrations, and fleet-wide emergency operations.

    21. Five-minute summary¶

    The system keeps feature evaluation off the network hot path. A strongly consistent control plane validates changes, checks dependency cycles and complexity, requires approvals, compiles signed immutable bundles, and atomically advances an environment pointer. Regional relay trees stream checksum-based deltas; polling and CDN full snapshots repair gaps. SDKs validate off-thread and atomically swap one bundle pointer, so an evaluation never mixes versions. Ordered rules and a specified hash produce deterministic targeting and percentage rollout across languages. Last-known-good bundles preserve availability, while safety flags may expire to off. Exposure telemetry uses bounded asynchronous buffers and cannot block requests. Home-region publication establishes total order; regional distribution continues from cached bundles. Golden vectors, simulations, canaries, propagation metrics, and kill-switch drills control the operational risk.
