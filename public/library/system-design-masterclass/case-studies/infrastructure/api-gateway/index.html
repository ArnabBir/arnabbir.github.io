    API Gateway¶

    This case study owns the gateway design. Use Proxies and Load Balancing and Deadlines, Retries, and Pools for data-path and overload mechanics.

    1. Interview roadmap¶

    We will design an edge gateway that terminates client connections, authenticates requests, routes to services, and enforces cross-cutting policy. We clarify which features belong on the synchronous path, estimate connections and bandwidth, define route and policy models, and separate configuration management from stateless regional proxies. Deep dives cover routing, retries, overload, streaming, policy rollout, and regional failover.

    2. Product framing¶

    The gateway is the public front door for HTTP, gRPC, and WebSocket APIs. It centralizes TLS, identity verification, routing, quotas, request limits, and telemetry. It should not contain business workflows or become the canonical source of user authorization; services still enforce resource-level authorization. Because every request passes through it, simplicity, bounded work, and safe degradation matter more than feature count.

    3. Requirements¶

    Functional requirements:

    • Terminate TLS and support HTTP/1.1, HTTP/2, gRPC, and selected WebSocket routes.
    • Match host, method, path, headers, and API version to weighted upstream clusters.
    • Authenticate tokens/API keys, enforce coarse authorization, quotas, CORS, and size limits.
    • Apply deadlines, circuit breakers, safe retries, transformations, and canary traffic splits.
    • Publish access logs, metrics, traces, and per-request diagnostic IDs.
    • Manage certificates, routes, policies, and staged rollouts.

    Non-functional requirements:

    • 5 million requests/s globally, 2 Tb/s peak, and 10 million concurrent connections.
    • Added p99 latency below 5 ms excluding TLS handshake and upstream time.
    • 99.999% availability for healthy routes; no control-plane dependency on requests.
    • Configuration propagation below 30 seconds, emergency revocation below 5 seconds.

    Business composition, payload persistence, and fine-grained resource authorization are out of scope.

    4. Correctness invariants¶

    1. A request is evaluated against one immutable configuration snapshot.
    2. A route can forward only to endpoints authorized for its tenant, protocol, and trust zone.
    3. Authentication failure never degrades to anonymous access unless the route explicitly permits anonymous clients.
    4. The gateway retries only operations declared replay-safe and only within one end-to-end deadline and retry budget.
    5. Request and response bodies never exceed configured limits, including after decompression.
    6. Configuration activation and certificate changes are auditable and rollbackable.

    The gateway guarantees at-most-one downstream attempt only when retries are disabled. With retries, downstream effects require idempotency.

    5. Capacity estimates¶

    Five million requests/s at 50 KB average response is 250 GB/s, or 2 Tb/s, making bandwidth the primary fleet dimension. At 20 Gbit/s safe egress per proxy, at least 100 proxies are needed before regional distribution, maintenance, and headroom. If average request duration is two seconds, Little's Law gives ten million in-flight requests, not ten million transport connections: HTTP/2 and HTTP/3 multiplex streams while idle keep-alive sockets carry none. Independently assuming ten million open connections and a tested 50,000-connection limit per proxy gives a 200-proxy connection floor. Also qualify concurrent-stream limits, per-stream buffers and TLS/packet CPU before selecting the larger fleet requirement. Access logs at 300 bytes/request produce 1.5 GB/s, so logs must be asynchronous and sampled for successful high-volume routes while retaining errors according to policy. A 100 MB global configuration distributed to 500 proxies is 50 GB per full rollout; deltas and regional relays reduce fan-out.

    6. Entities and configuration model¶

    Listener(listener_id, address, port, protocols, certificate_refs)
Route(route_id, tenant_id, match, priority, cluster_id, policies[], version)
Cluster(cluster_id, protocol, discovery_ref, locality_policy,
        health_policy, circuit_breaker)
Endpoint(endpoint_id, cluster_id, address, zone, weight, health, epoch)
Policy(policy_id, type, parameters, failure_mode, version)
Snapshot(snapshot_version, listeners[], routes[], clusters[], policies[], checksum)

    Canonical configuration lives in a transactional control database. The compiler emits validated, signed, immutable regional snapshots. Endpoint health and load are rapidly changing data-plane state delivered separately from slower route configuration.

    7. Interfaces¶

    Management:

    PUT  /v1/routes/{id}                 If-Match: version
POST /v1/configs/{id}:validate
POST /v1/configs/{id}:stage
POST /v1/configs/{id}:activate
POST /v1/configs/{id}:rollback
GET  /v1/proxies/{id}/status

    Discovery and proxy streams carry version, nonce, resource type, delta, and checksum; proxies ACK or NACK with error details. Client-facing interfaces preserve protocol semantics. Gateway-generated errors use a stable envelope containing status, code, request ID, and retryability without leaking internal addresses.

    8. High-level architecture¶

    flowchart LR
  Client --> DNS[Anycast/DNS and DDoS edge]
  DNS --> Proxy[Regional gateway proxies]
  Proxy --> Service[Upstream services]
  Discovery[Endpoint discovery] --> Proxy
  Admin --> API[Gateway control API]
  API --> DB[(Config DB)]
  DB --> Compiler[Snapshot compiler]
  Compiler --> Relay[Regional config relays]
  Relay --> Proxy
  Proxy --> Telemetry[Async telemetry pipeline]

    The control plane authorizes edits, validates references, compiles snapshots, and monitors rollout. The data plane consists of edge protection, proxies, endpoint discovery, and local policy engines. Proxies keep last-known-good snapshots and endpoint caches. A control outage prevents new configuration but must not interrupt established traffic.

    9. Request hot path¶

    On accept, the proxy negotiates TLS using an in-memory certificate map, parses with strict bounds, captures one snapshot pointer, and assigns a request ID. It normalizes host/path safely, matches a precompiled route trie, authenticates, checks policy, chooses a healthy endpoint, and forwards with propagated deadline and trace context. Response streaming uses bounded buffers and backpressure rather than reading complete bodies.

    sequenceDiagram
    autonumber
  participant C as Client
  participant G as Gateway
  participant I as Identity cache/provider
  participant U as Upstream
  C->>G: request + credentials
  G->>G: parse, normalize, capture snapshot
  G->>I: verify key/JWKS cache on miss
  I-->>G: verified claims
  G->>G: authorize route, quota, choose endpoint
  G->>U: request + deadline + identity context
  U-->>G: streaming response
  G-->>C: response
  G-->>G: enqueue telemetry without blocking

    Avoid remote calls where possible: JWT verification uses cached signed keys; API key lookups use bounded caches with revocation feeds; rate limiting uses local/distributed leases. Introspection-only tokens have an explicit fail policy.

    10. Routing and service discovery¶

    Compile exact hosts, wildcard hosts, path prefixes, methods, and headers into deterministic precedence; ambiguous routes are rejected before publication. Weighted routing hashes a stable key for sticky canaries when supplied, otherwise uses random weighted choice. Endpoint selection first chooses locality and priority, then power-of-two choices weighted by observed load. Passive health combines connection failures and latency; active probes verify idle endpoints.

    Discovery updates have epochs and endpoint TTLs. A disappearing endpoint drains existing streams for a bounded period but receives no new requests. Outlier ejection has maximum-ejection limits so correlated upstream failure does not remove every endpoint. Panic mode may broaden locality or fail fast according to route policy.

    11. Authentication and policy chain¶

    Policy order is explicit: connection and request bounds, authentication, coarse authorization, rate limit, transformations, routing, retry, and response filters. Authentication establishes a typed principal. The gateway signs or mTLS-protects forwarded identity headers and strips client-supplied copies. Services validate gateway identity and still authorize the object being accessed.

    JWT verification refreshes cached keys according to bounded freshness rules and validates issuer, audience, allowed algorithm, and token time claims. Planned key rotation may retain old keys through token lifetime; compromised or explicitly revoked keys must be rejected sooner through the revocation policy. Revocation-sensitive routes use short tokens or introspection. CORS is browser policy, not authentication. Transformations are declarative and bounded; arbitrary user code is not run on gateway workers.

    12. Deadlines, retries, and circuit breaking¶

    The client deadline is capped by route maximum. Each attempt gets only remaining time. Retry only connect failures, resets before response headers, and selected statuses for idempotent methods or requests carrying a downstream-supported idempotency key. Use exponential jitter and a global retry budget, for example retries below 10% of successful traffic. Hedging is reserved for idempotent latency-sensitive reads and consumes the same budget.

    Circuit breakers bound concurrent requests and pending connection queues per endpoint/cluster. When full, fail fast with retry guidance. Adaptive concurrency uses latency gradients but retains hard safety caps. Retries must not jump across data-residency boundaries.

    flowchart TD
  Req[Matched request] --> Deadline{Deadline remains?}
  Deadline -->|no| Fail[Fail timeout]
  Deadline -->|yes| Endpoint[Choose healthy endpoint]
  Endpoint --> Attempt[Send one attempt]
  Attempt --> Result{Success or potentially retryable outcome?}
  Result -->|success| Return[Stream response]
  Result -->|nonretryable| Error[Return original error]
  Result -->|retryable| Budget{Replay safe and budget available?}
  Budget -->|yes| Deadline
  Budget -->|no| Error

    13. Partitioning, overload, and hot routes¶

    Traffic partitions geographically through anycast or latency DNS, then by connection across proxies. Proxies are stateless except caches, so scale horizontally. Long-lived connections skew load; load balancers consider active connections and bytes, not only request count. A hot route or tenant gets explicit concurrency, QPS, and bandwidth limits plus dedicated pools when isolation matters.

    Overload defense is layered: DDoS filtering, connection caps, header/body limits, per-client quotas, route admission, bounded upstream queues, and load shedding. Preserve health, control, and critical APIs before bulk endpoints. Reject early before authentication work where safe. Backpressure streamed responses and cap slow-client connection time.

    14. Configuration consistency and rollout¶

    The compiler validates references, route ambiguity, trust-zone constraints, policy types, secret availability, and resource limits. Regional relays distribute snapshots. Proxies build indexes off-thread, validate checksum/signature, then atomically swap pointers. Requests in flight finish on their captured version. A delta names its base; mismatch triggers full snapshot repair.

    Rollout proceeds through test, one proxy, one zone, then percentages, with automated rollback on NACK, 5xx, latency, or authentication anomalies. Emergency deny/certificate revocation uses a small reserved channel. Rollback republishes known-good content under a new monotonic version while preserving current mandatory deny rules and revoked credentials. Revocation freshness has its own enforcement gate so an in-flight old route snapshot cannot bypass it. Endpoint discovery changes independently and faster than route snapshots.

    15. Failures and recovery¶

    • Proxy crash: connection-level load balancer removes it; clients retry according to protocol.
    • Control plane unavailable: existing snapshots and certificates continue; edits stop.
    • Bad config: preflight, NACK, canary, and automatic rollback contain it.
    • Identity provider unavailable: cached verification continues; routes requiring live introspection fail closed when identity cannot be established. A route may explicitly allow anonymous access, but provider failure does not turn an unverified token into an authenticated principal.
    • Discovery stale: endpoint TTL expires; fail fast rather than route indefinitely to removed hosts.
    • Upstream overload: breakers, queues, retry budgets, and local shedding prevent amplification.
    • Telemetry outage: bounded buffers sample/drop normal logs; security audit policy may reject sensitive operations.
    • Zone loss: locality routing shifts gradually within regional capacity and global traffic manager drains the region if needed.

    16. Multi-region strategy¶

    Every region has independent proxies, relays, discovery, identity caches, and rate-limit budgets. Anycast/DNS steers clients; health considers synthetic end-to-end requests, not process liveness. Stateless requests can fail over automatically. WebSockets and streams reconnect and resume at application level. Global rate limits use escrowed regional budgets rather than WAN checks.

    Configuration bundles replicate globally from a home writer. Promotion requires a higher publisher epoch. Certificates and trust bundles are prepositioned. Residency policy is compiled into allowed region-to-cluster edges, so failover cannot accidentally export data. Capacity reserves determine whether a full-region evacuation is credible.

    17. Security and abuse prevention¶

    Use hardware-backed private keys where justified, automated certificate rotation, modern TLS, mTLS upstream, least-privilege workload identity, and signed configuration. Normalize paths once to defeat traversal and route-confusion attacks. Defend against request smuggling by consistent parser rules and never forwarding ambiguous framing. Cap decompression, regex, headers, streams, and connection duration. Strip hop-by-hop and identity headers. Audit configuration and privileged diagnostics; redact credentials from logs and traces.

    18. Observability and testing¶

    Measure request/connection/byte rates, handshake failures, route match failures, auth reasons, limiter decisions, upstream latency, retries, ejections, queue time, resets, snapshot age/version distribution, NACKs, and telemetry drops. Bound metric cardinality through route IDs rather than paths. Distributed traces distinguish gateway queue, connect, TLS, and upstream phases. Synthetic probes traverse public DNS and real identity.

    Golden tests verify route matching and normalization. Differential tests compare compiler and proxy policy behavior. Fuzz parsers for smuggling and malformed protocols. Load tests include slow clients, large streams, WebSockets, hot tenants, and retry storms. Fault tests expire discovery, rotate certificates, partition control plane, and remove zones. Canary replay compares new snapshots against sampled sanitized requests.

    19. Important tradeoffs¶

    Central gateways simplify policy but enlarge blast radius and add latency. Sidecars reduce central network concentration but multiply operations. Local JWT verification is available but revocation is delayed. More retries hide transient faults but amplify overload. Rich transformations speed teams initially but turn infrastructure into business code. Atomic snapshots consume memory during rollout but avoid mixed configuration. Anycast fails over quickly but may move connections unexpectedly; DNS is slower but controllable.

    20. Final design, questions, and expectations¶

    Use stateless regional proxies behind DDoS protection and locality-aware balancing. Proxies evaluate one signed immutable snapshot, verify identity locally, enforce bounded policy, and route to discovered endpoints with deadlines, retry budgets, and breakers. A transactional control plane compiles and canaries snapshots; endpoint discovery remains a separate fast stream. Last-known-good operation, regional independence, and layered shedding protect availability.

    Questions: When is retry safe? How does config rollback affect in-flight requests? How are long-lived connections balanced? What happens when JWKS refresh fails? How do you prevent request smuggling? How does region failover preserve residency?

    An L5 candidate should design routing, authentication, rate limiting, discovery, retries, and scaling. An L6 candidate should bound amplification, separate planes and update cadences, stage policy/certificate changes, reason about protocols, overload priority, trust boundaries, regional capacity, and organizational ownership.

    21. Five-minute summary¶

    The gateway is a minimal synchronous policy and routing layer, not a business workflow engine. Regional stateless proxies terminate TLS, strictly parse and normalize requests, capture one immutable signed configuration snapshot, verify identity from local key caches, enforce quotas and bounds, and select healthy locality-aware endpoints. Deadlines and retry budgets prevent amplification; only replay-safe operations retry. Breakers and bounded queues fail fast under upstream overload. A transactional control plane validates and canaries route snapshots, while endpoint discovery updates independently. Proxies survive control outages on last-known-good state. Regions have independent capacity and escrow quotas; failover obeys compiled residency constraints. Protocol fuzzing, request replay, synthetic probes, staged rollouts, and version-distribution metrics control the gateway's unusually large blast radius.

    Primary source boundary¶

    JWT Best Current Practices, RFC 8725 sections 3.1 and 3.8-3.10 supports explicit algorithm, issuer/key, audience, and untrusted-claim validation (accessed 2026-09-19). Cache freshness, revocation propagation, and rollback gates here are proposed deployment contracts, not guarantees supplied by a JWT signature.
