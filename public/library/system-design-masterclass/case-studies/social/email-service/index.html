    Design an Email Service¶

    Interview roadmap¶

    Design a multi-tenant service that accepts transactional and bulk email, renders templates, enforces consent, sends through public mail infrastructure, and tracks delivery. Start with durable acceptance and one outbound provider, then add scheduling, reputation isolation, retries, inbound feedback, and regional operation. The hard part is not SMTP; it is preserving intent while handling ambiguous delivery, hostile input, changing policy, and mailbox-provider throttling.

    Product framing and requirements¶

    Clients submit single messages or campaigns, select an immutable template, schedule delivery, cancel unsent work, and query status. Recipients can unsubscribe by category. Operators manage domains, DKIM keys, IP pools, provider routes, quotas, and suppression lists. We support attachments by reference, webhooks, bounces, complaints, and opens only where privacy policy permits.

    Transactional mail should be accepted in 200 ms p99 and normally handed to a remote server within 10 seconds. Campaigns may complete over hours. Availability is 99.99% for acceptance and 99.9% for status. A successful API response means durable acceptance, never inbox placement. Search, analytics, and open tracking are projections and may lag.

    Correctness invariants¶

    • (tenant_id, idempotency_key) identifies one immutable logical message and request hash.
    • A message references one immutable template version and one normalized recipient set.
    • Current suppression and legal policy win over queued promotional work.
    • Each SMTP/provider submission has a stable attempt ID; retries create auditable attempts.
    • Status is monotonic within a defined lattice; late bounces may refine DELIVERED to BOUNCED but cannot resurrect cancelled work.
    • Transactional capacity is reserved and cannot be consumed by campaigns.
    • A sending domain uses only authorized identities and current signing keys.
    • We promise at-least-once processing, not exactly-once arrival.

    Capacity estimates¶

    Assume 5 billion single-recipient messages/day, 58,000/s average, 500,000/s peak, with 2 KB metadata and 12 KB rendered body on average. Metadata is 10 TB/day; bodies add 60 TB/day before compression and replication. Attachments live in object storage and are referenced, avoiding queue inflation. Reusing each SMTP connection for 20 sequential deliveries reduces connection establishments to about 25,000/s, not recipient deliveries: 500,000 recipient outcomes/s still require tracking. Concurrent sockets equal delivery rate times mean transaction duration for non-pipelined workers; connection reuse alone does not divide that concurrency by 20. Multi-recipient SMTP transactions are a separate optimization limited to compatible bodies and destination routing. Domain-specific throttles, not global bandwidth, set effective capacity. Retain detailed attempts for 30 days, aggregate metrics for 13 months, and suppression hashes until policy allows deletion.

    Core flows and domain algorithms¶

    Acceptance, rendering, and delivery¶

    Validate sender ownership, template variables, size, recipient limits, and tenant budget before acceptance. Store encrypted addresses and a keyed hash for suppression lookup. Rendering consumes the immutable template and bounded variables, writes the body to object storage, and emits a recipient task. Workers fetch bodies just in time, preventing large payloads in the broker.

    sequenceDiagram
    autonumber
 participant C as Client
 participant A as API
 participant D as Database
 participant O as Orchestrator
 participant W as Sender
 participant X as Remote MX
 C->>A: message plus idempotency key
 A->>D: commit message and outbox
 D-->>C: accepted(message_id)
 D->>O: committed intent
 O->>O: consent, render, route
 O->>W: recipient task and deadline
 W->>X: SMTP transaction with attempt ID
 X-->>W: 2xx, 4xx, 5xx, or timeout
 W->>D: conditional attempt transition

    The scheduling algorithm uses weighted deficit round robin across tenants inside separate transactional and bulk lanes. Each remote domain has an adaptive token bucket. Success slowly increases concurrency; 421/450 responses decrease it multiplicatively and add jitter. A tenant cannot borrow reserved transactional capacity. Expired password-reset mail is discarded rather than delivered late.

    Suppression and consent¶

    At send time, join category policy, tenant opt-out, global hard-bounce/complaint suppression, and jurisdiction. Promotional messages fail closed when the policy store is unavailable. Transactional mail may proceed from a recent signed policy snapshot only for explicitly approved categories. One-click unsubscribe tokens bind recipient hash, tenant, category, and expiry. Changes emit versioned events. The authoritative send claim atomically checks current policy/cancellation generation and changes QUEUED to SUBMITTING; stale cache comparison alone is insufficient. Define cancellation as preventing claims ordered after its commit. An already claimed or in-flight SMTP transaction may still complete and must be reported as too late or uncertain, since a database check cannot atomically revoke bytes at an external MX.

    Attempt state machine and retry¶

    The diagram shows the logical recipient lifecycle; each network submission also retains a separate immutable attempt identity and outcome history.

 DELIVERED --> BOUNCED: later authoritative failure evidence

    Cancellable groups the four pre-submission states. It is a visual grouping, not an additional persisted status. Cancellation must win the dispatch ownership check before a worker submits to the provider.

    SMTP 4xx is transient and 5xx is normally permanent; provider-specific classifiers are versioned. Backoff is exponential with full jitter and bounded by message expiry. A timeout after DATA is ambiguous: the remote server may have accepted the message. Reusing a message identifier helps deduplication but does not guarantee it. Query provider status when possible; otherwise retry according to product duplicate tolerance and record UNKNOWN evidence. Never retry malformed addresses or policy rejection.

    RFC 5321, sections 2.1 and 4.5.3.2.6, defines responsibility transfer at the final successful DATA reply and warns that losing that reply can cause duplicates. An internal attempt ID is not a standard SMTP deduplication facility. Distinguish remote acceptance from evidence of final delivery (accessed 2026-09-08).

    Reputation and routing¶

    Reputation is partitioned by customer class, sender domain, IP pool, destination domain, and traffic type. New identities warm gradually. Routing scores eligible pools by health, reputation, cost, residency, and quota, while hard policy filters precede scoring. Complaints immediately reduce or pause promotional traffic for that identity. Dedicated pools isolate large trusted tenants; shared pools are cheaper but impose admission controls so one abuser cannot poison everyone.

    Campaign expansion¶

    A campaign stores an immutable audience snapshot URI, template version, cancellation generation, and budget. Expanders lease deterministic audience ranges and derive recipient IDs from (campaign_id, audience_row_id). Duplicate leases collapse at a uniqueness constraint. Checkpoints permit restart without rescanning. Cancellation increments a generation checked by expanders, scheduler, and sender; already accepted remote messages remain irreversible.

    Partitioning, scaling, and regions¶

    Shard message metadata by tenant and time, placing very large tenants on dedicated shards. Partition send queues by priority and destination-domain hash so one worker owns local domain concurrency, then split hot domains into virtual shards coordinated by a shared quota lease. Suppression is hash-partitioned and heavily cached with versioned invalidation. Object storage serves bodies through short-lived credentials.

    Each tenant has a home region for residency. Acceptance uses zonal quorum and asynchronously copies encrypted canonical records to a paired region. Outbox offsets and campaign checkpoints replicate. A recovering region must restore the acknowledged message, idempotency, suppression and attempt prefix or expose the measured data-loss window and hold uncertain work for reconciliation. An asynchronous copy alone cannot guarantee all acknowledged mail survives regional destruction. Failover increments a region epoch; workers reject leases from older epochs. Duplicate enqueues are expected and absorbed by recipient/attempt uniqueness, but a failover during SMTP remains ambiguous. DNS, DKIM key metadata, and policy form a strongly governed control plane; message delivery is the elastic data plane.

    Backpressure propagates from mailbox domains to domain queues, campaign expansion, and API tenant budgets. Shed analytics first, pause low-reputation campaigns next, and reject new bulk work with 429 and retry guidance before affecting transactional acceptance. Queue byte limits prevent attachment references or poison tasks from exhausting brokers.

    Reliability and failure modes¶

    Database/broker dual writes use an outbox. Queue redelivery is ordinary. If rendering fails deterministically, quarantine the message; if object storage fails, retry without advancing attempt count. Provider or MX outage opens a per-route circuit, not a global breaker. Lost feedback is recovered by provider reconciliation and age scans. A suppression outage pauses marketing. Clock skew is handled with database time and tolerant lease expiry. Corrupt templates are checksum rejected.

    Dead letters retain reason, classifier version, and replay eligibility. Replay requires tenant, time, category, and maximum-count scope plus dry-run approval. A reconciliation job compares accepted recipients, terminal outcomes, outbox publication, provider billing, and old ambiguous attempts. It writes normal events so webhooks and projections converge. Disaster exercises restore DB, keys, bodies, and offsets into an isolated environment before traffic switching.

    Security, abuse, observability, and testing¶

    Authenticate tenants, authorize sender identities, verify DNS ownership, rotate DKIM keys, encrypt addresses and bodies, isolate credentials, malware-scan attachments, verify feedback signatures, and redact logs. Defend against phishing, list bombing, spoofing, header injection, tracking abuse, and enumeration with reputation onboarding, per-recipient frequency caps, complaint thresholds, CAPTCHA on public forms, and emergency kill switches. Retention and deletion workflows cover queues, object versions, analytics, and backups.

    Measure API durability latency, outbox lag, render failures, queue age by lane/domain, SMTP response classes, connection reuse, adaptive limits, retry amplification, unknown outcomes, bounce/complaint rate, suppression freshness, campaign completion, inbox proxy signals, cost, and tenant fairness. Trace IDs connect intent to attempts without exposing addresses.

    Property-test state transitions, idempotency, generation cancellation, and suppression precedence. Contract-test SMTP/provider adapters and webhook signatures. Fuzz MIME and headers. Load-test campaign cliffs plus password-reset bursts and hot-domain throttling. Chaos-test DB leader loss, broker duplication, stale policy caches, object-store latency, credential rotation, and regional fencing. Canary new classifiers and routes against controlled mailboxes before gradual tenant rollout.

    Tradeoffs and final architecture¶

    Direct SMTP provides control and lower marginal cost but demands reputation operations; external providers accelerate launch but add cost and opaque throttling. Rendering at request time gives immediate validation but increases latency and stores PII longer; asynchronous rendering keeps acceptance fast. Per-domain queues improve throttling but risk hot partitions; virtual shards plus a domain quota coordinator preserve control. Strong global suppression reads are safer but slower; versioned regional replicas with fail-closed promotional behavior are practical.

    flowchart TD
 I[Idempotent durable intent] --> T[Immutable template rendering]
 T --> P[Current consent and policy]
 P --> F[Fair priority scheduler]
 F --> Q[Destination-domain quota]
 Q --> R[Reputation-aware route]
 R --> X[SMTP or provider attempt]
 X --> N[(Canonical attempt state)]
 Y[Signed feedback and reconciliation] --> N
 Z[Metrics, replay, audit] --> N

    The final design keeps canonical intent and attempts in a transactional store, bodies in object storage, and analytics in replaceable projections. An outbox feeds policy/rendering and fair scheduling. Domain-partitioned workers enforce adaptive quotas and reputation-aware routes. Signed feedback and reconciliation close asynchronous gaps. The control plane governs identity, policy, keys, and routing; the data plane can scale and fail independently.

    Interview deep-dive questions¶

    1. What does a timeout after SMTP DATA mean, and when should we retry?
    2. How does a billion-recipient campaign avoid delaying password resets?
    3. How are opt-outs enforced for already queued work?
    4. How would destination-domain throttling survive repartitioning?
    5. Which state is canonical when callbacks and synchronous responses disagree?
    6. How do you warm a new IP pool without damaging shared reputation?
    7. What is restored and fenced during regional failover?

    L5 and L6 expectations¶

    An L5 candidate should clarify transactional versus bulk semantics, estimate storage and peak send rate, model message/recipient/attempt state, use outbox and idempotency, explain suppression, domain throttles, retries, queues, and major outages. They should not claim inbox delivery or exactly once.

    An L6 candidate should define the ambiguity policy, legal and reputation invariants, adaptive overload behavior, tenant isolation, control/data-plane separation, regional epochs, replay safety, cost routing, classifier migration, and abuse governance. They should connect dedicated pools and retention choices to economics and policy, and propose measurable rollout and reconciliation plans.

    Five-minute summary¶

    Durably accept an idempotent message and outbox record, referencing an immutable template and object-stored body. Before sending, enforce current suppression and category policy. Expand campaigns deterministically, reserve transactional capacity, schedule tenants fairly, and throttle adaptively per destination domain. Record explicit attempts and classify SMTP outcomes; treat post-submission timeout as ambiguous rather than promising exactly once. Route by eligibility, reputation, health, residency, and cost. Normalize signed bounces and complaints into monotonic canonical state and reconcile missing feedback. Partition by tenant/time and destination domain, split hot domains with coordinated quotas, and fence regional failover using epochs. Operate queue age, retry amplification, unknown outcomes, complaint rate, suppression freshness, fairness, and cost. Pause campaigns before degrading critical mail.
