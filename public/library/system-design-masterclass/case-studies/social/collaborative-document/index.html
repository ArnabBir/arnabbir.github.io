    Design a Collaborative Document Editor¶

    Interview roadmap¶

    Scope rich-text or plain-text documents, concurrent editing, presence, comments, offline work, history, and sharing. First define convergence and authorization, then compare operational transformation (OT) with conflict-free replicated data types (CRDTs). This design chooses server-ordered OT for bounded online documents, while showing when a CRDT is better.

    Requirements, invariants, and estimates¶

    Multiple users edit a document and see remote changes within 200 ms normally. Clients reconnect and catch up without losing acknowledged edits. Owners share/revoke access, history supports recovery, and periodic snapshots bound replay. Presence and cursors are ephemeral. Assume 10 million daily editors, one million concurrent connections, 20 operations per concurrently connected editor per minute, or roughly 330,000 ops/s while that one-million-editor concurrency holds. At 200 bytes/op, ingress is 66 MB/s; retained operation logs and snapshots reach petabytes over years. One viral document creates a hot key independent of global averages.

    • Every acknowledged operation is durable and belongs to one document revision.
    • Authorized replicas converge to identical content after receiving the same accepted operations.
    • Revision numbers increase monotonically per document; gaps may occur after failover.
    • Operation IDs make retries idempotent.
    • Revocation blocks future operations and sync; it cannot erase content already downloaded.
    • Snapshots correspond to a known log revision and are checksum-verifiable.
    • Presence loss never affects document correctness.

    The WebSocket connection plane is independent of document ordering. Global edge routing chooses a healthy regional gateway, which authenticates the handshake, owns socket backpressure and heartbeats, and forwards edit frames to the document plane. Gateways never become revision authority. A session registry stores a short lease from session_id to gateway_id, document, user, and monotonically increasing connection epoch. A gateway registry advertises READY, DRAINING, or UNHEALTHY, current sockets, and capacity. A compact fanout directory maps doc_id to the set of gateways with local subscribers, so each committed operation crosses the bus once per interested gateway rather than once per socket.

    With one million concurrent sockets and a tested limit of 10,000 sockets per gateway, the floor is 100 gateways. Provisioning 40 percent failover and drain headroom gives 140. At roughly 32 KB of socket buffers and protocol state, the fleet holds about 32 GB before process overhead. A 200-byte leased route per connection is about 200 MB raw and can be regionally sharded; it is reconstructible from gateway heartbeats, so it is not part of document durability.

    On planned drain, the gateway changes its registry state before rejecting new sockets, sends clients a RECONNECT(target_region,resume_token,last_ack_revision,connection_epoch) control frame, and keeps existing connections for a bounded grace period. The edge excludes draining gateways. The reconnect presents the signed resume token; the registry compare-and-swaps to a higher connection epoch, making late frames from the old socket stale. Every edit carries both session_id and that connection_epoch. The receiving gateway checks that it owns the current route, and the document leader checks the current session epoch again immediately before append; therefore a frame already forwarded by the old socket cannot commit after the document authority has durably advanced its session fence. The registry CAS alone is not that linearization point. The new gateway subscribes, requests replay after last_ack_revision, then enables sends. On an abrupt gateway loss there is no redirect frame: lease expiry and missed heartbeats remove it, clients reconnect with jitter, resend unacknowledged operation IDs under the new epoch, and rebuild lossy presence.

    OT versus CRDT¶

    OT transforms concurrent operations relative to a server-defined order. For text, insert and delete pairs need complete, tested transform functions satisfying convergence properties. It uses compact positions and gives the server a natural revision, ACL, undo, and audit boundary. Its weaknesses are central sequencing, difficult transform correctness, and complicated offline branches when base history is compacted.

    A sequence CRDT gives each element a stable identifier and defines commutative merge rules. Replicas can edit offline and exchange operations without one total-order leader; duplicates are harmless when operation IDs are unique. Costs include identifier/tombstone metadata, garbage collection requiring causal knowledge, less intuitive undo, schema evolution, and potentially unbounded document overhead. Rich-text tree CRDT semantics remain product-specific rather than automatic.

    Concern OT CRDT
    Online client/server editing Natural fit Good fit
    Long offline, peer-to-peer Complex rebasing Strong fit
    Metadata size Usually compact Larger IDs/tombstones
    Central authority/audit Natural Must be layered on
    Algorithm risk Transform matrix Merge/GC/schema rules
    Undo Server revision based Intent-preserving undo is harder

    Choose OT here because sessions are server-mediated, ACL changes require authority, documents have bounded size, and low metadata overhead matters. Choose a CRDT if local-first multi-day offline editing or peer-to-peer operation is a primary requirement. Do not combine both without a precise semantic boundary.

    Deep dives¶

    Transform correctness and rich text¶

    Text OT defines deterministic tie-breaking for insert/insert at one position, overlap rules for delete/delete, and position shifts for insert/delete. Property tests check convergence for every operation pair and permutations of concurrent edits. Rich text should use typed tree operations such as insert node, delete range, and set mark; manipulating serialized HTML creates invalid structures. Unsupported schema versions are rejected or translated at a version gateway.

    Offline sync and compaction¶

    Clients persist a base revision, local operation IDs, and pending operations. If the base remains in the log, the server transforms them through intervening history. If compacted, the client loads a snapshot and may reapply intent; for complex stale edits, present an explicit conflict copy instead of silently dropping content. Snapshot creation reads through revision R, writes checksum and format, then conditionally publishes the pointer. Logs before the oldest supported client/session revision can be archived.

    Hot documents and backpressure¶

    One leader establishes order, so a viral document has a finite write ceiling. Batch keystrokes over 20-50 ms, coalesce presence, and cap collaborators/edit rate. Separate read-only viewers into broadcast relays. If overloaded, drop cursor updates first, reduce rendering frequency, then switch excess users to read-only rather than accepting edits that cannot meet durability. Splitting one document by sections works only if cross-section operations and global undo semantics are constrained.

    Active-document memory residency¶

    A document leader is a durable ordering role; its materialized document is a bounded cache. On the first editor, the owner acquires or confirms its epoch, enters LOADING, reads the latest checksum-valid snapshot, and replays the tail to the current head before admitting edits. ACTIVE state is pinned while sockets, pending commands, snapshot work, or replay consumers reference it. After the final session leaves, an idle timer allows quick reconnects. Eviction first stops admission for that local instance, flushes committed outbox progress and optional snapshot work, records the head revision, and only then releases memory; durability never depends on the heap image.

    stateDiagram-v2
    [*] --> ABSENT
    ABSENT --> LOADING: first session or command
    LOADING --> ACTIVE: snapshot and tail verified
    LOADING --> FAILED: corrupt state or lost epoch
    ACTIVE --> IDLE: no sessions or pending work
    IDLE --> ACTIVE: reconnect before timeout
    IDLE --> EVICTING: idle timeout or memory pressure
    EVICTING --> ABSENT: pins zero and checkpoint recorded
    EVICTING --> ACTIVE: new session cancels eviction
    ACTIVE --> DRAINING: leader move or shutdown
    DRAINING --> ABSENT: successor ready and old epoch fenced
    FAILED --> ABSENT: release ownership

    Use a weighted LRU within a hard per-cell memory budget, charging tree bytes, transform tail, undo metadata, and subscriber indexes to the document and tenant. If an average resident document consumes 120 KB, 10,000 active documents require about 1.2 GB; reserve additional headroom for a few large documents and reject or relocate before the process swaps. Oversized documents can retain only a bounded transform window in memory and page cold tree sections if product operations permit it. Memory pressure evicts idle documents first, then rejects new opens; it does not discard acknowledged operations or silently move active leaders.

    Comments, anchors, and undo¶

    Anchors are logical ranges transformed alongside text operations; deleted ranges collapse according to product rules. Comments have canonical lifecycle records and versioned anchors. Undo should invert the user's intent relative to subsequent operations, not simply restore an old snapshot. The server retains enough authored-operation metadata to transform inverse operations.

    Partitioning, regions, consistency, and failure¶

    Partition documents by ID into cells; operation storage further ranges by revision. Huge tenants can receive dedicated cells. Snapshots use immutable object keys. Assign each open document a leased leader in its home region. Gateways are global but forward edits to that leader. Synchronous zonal replication precedes acknowledgement; async disaster-recovery replication follows. Thus acknowledged-edit durability covers the synchronous failure domains only; a regional-loss no-loss promise requires surviving synchronous acknowledgement or recovery of the complete acknowledged prefix before promotion. Failover uses epochs so the old leader cannot append. Clients resend unacknowledged operation IDs after reconnect.

    Document operations are strongly ordered per document. Presence, search, notifications, comments counters, and cross-region replicas are eventual. ACL updates are strongly checked before every accepted operation; gateways receive invalidations but socket membership is not authority. Operation uniqueness prevents duplicate append. An outbox guarantees committed broadcasts can replay.

    Leader loss causes reconnect, fencing, and resend. Gateway loss loses only presence and unacknowledged transport. Registry loss prevents optimized routing but gateways can retain existing sockets and the edge can use health-based placement; leases rebuild from heartbeats. Bus loss delays broadcasts; clients catch up from the log. Snapshot corruption falls back to the prior checksum-verified snapshot and replay. A poison operation is rejected before append. Cell overload has per-document and tenant admission limits. Backups plus immutable logs enable point-in-time recovery and audit.

    Security, privacy, observability, and testing¶

    Authenticate sessions and authorize open, edit, comment, share, export, and history independently. Encrypt transport/storage, isolate tenant keys where required, audit shares and administrative access, sanitize pasted rich content, scan attachments, and rate-limit share spam. Revocation terminates sessions promptly. Data deletion includes snapshots, operation logs, search, comments, exports, and backups under published retention. Client-side E2EE would prevent server transforms/search and requires a different trust architecture.

    Measure operation acceptance and broadcast latency, transform depth, pending-client queue, duplicate retries, leader moves, hot-document rates, snapshot duration/failure, replay length, reconnects, ACL-denied operations, presence drops, and convergence mismatches from sampled client hashes. Trace by doc/op IDs without content.

    Test OT algebra with property-based concurrent operation permutations, fuzz rich-text trees, replay duplicates/reorder, race ACL revocation with edits, crash leaders after commit before ack, corrupt snapshots, and reconnect from every compaction boundary. Drain gateways while edits are in flight, kill them without notice, expire registry leases, duplicate resume tokens, and assert that connection epochs plus operation IDs prevent split sessions and duplicate commits. Repeatedly hydrate and evict documents at snapshot boundaries, inject memory pressure and lost leader epochs, and verify that no leader admits edits before replay reaches the recorded head. Load-test one viral document, one million mostly idle sockets, reconnect storms with jitter, and many normal documents. Run cross-version client compatibility, schema migration, chaos, and restore drills. CRDT implementations additionally test arbitrary merge order, causal GC, and tombstone resurrection.

    Document-format migration uses an explicit reader/writer compatibility window. New servers first read both formats, snapshot workers produce shadow snapshots, and validators render both to normalized trees for comparison. Only then do leaders emit new operations. Old clients receive a capability error or a translated safe subset rather than corrupting unknown node types. Rollback remains possible until the old log and snapshots pass the retention boundary.

    Sampled replica hashes provide an additional convergence alarm, but mismatches trigger evidence capture and repair from canonical revisions rather than automatic client overwrite.

    L6 mechanisms: transforms, protocol, and compaction¶

    A worked OT transform matrix¶

    Use half-open text positions over Unicode code points in one normalized text leaf. Let I(p,s,id) insert string s before position p, and D(p,n) delete [p,p+n). T(a,b) rewrites operation a so it preserves its intent after concurrent operation b. Inserts at the same position are ordered by (actor_id,op_id); the lower key appears first. Deletes never delete concurrently inserted text, and overlapping deletes remove each original character once.

    a transformed against b I(q,t) D(q,m)
    I(p,s) Shift to p+len(t) when q<p, or when q=p and b wins the tie; otherwise keep p Keep p when p<=q; shift to p-m when p>=q+m; clamp to q when insertion falls inside the deleted range
    D(p,n) Keep when q>=p+n; shift start by len(t) when q<=p; when p<q<p+n, split into D(p,q-p) and D(q+len(t),p+n-q) so inserted text survives Map both endpoints through x -> x for x<=q, q for q<x<q+m, and x-m for x>=q+m; the new delete is the mapped half-open interval and may become a no-op

    Worked insert/insert: replicas start with cat. A sends I(1,"X",A7) and B sends I(1,"Y",B2). If A7 < B2, the server accepts A as revision 11 (cXat), transforms B to I(2,"Y",B2), and reaches cXYat. A first processes its ordered acknowledgement of A at r11, then applies canonical B at r12 without shifting B through A again. B first processes canonical A at r11 and rebases its pending B, then retires B on its r12 acknowledgement. Both render cXYat.

    Worked delete/insert: start with abcdef; A sends D(1,4) to remove bcde, while B sends I(3,"X",B9) after c. If A is first, B's position is clamped to 1 and the result is aXf. If B is first, A becomes a compound deletion of transformed intervals [1,3) and [4,6), applied right-to-left: it removes bc and de, but not concurrent X, again producing aXf. A production implementation represents a compound result as one retain/delete component list and normalizes adjacent components before append.

    The matrix is necessary but not sufficient. Tests enumerate every pair around boundaries 0, document length, equal positions, full overlap, containment, and empty output. Property tests assert apply(apply(S,a),T(b,a)) == apply(apply(S,b),T(a,b)); three-way tests assert transformation-path independence for all permutations. All implementations explicitly convert positions to the same Unicode code-point coordinate system; normalization alone does not reconcile UTF-16 code units with code points. Normalize inserted strings by the agreed rule before assigning positions, and do not renormalize an entire document after every operation without an explicit position-remapping operation.

    Wire payload, acknowledgement, and resync¶

    An edit frame is {doc_id, session_id, connection_epoch, leader_epoch, op_id, actor_id, base_revision, client_seq, schema_version, components, base_hash}. connection_epoch fences an older socket for the same session; leader_epoch fences an old document owner. Both must match current authority before append. client_seq detects a missing local send but does not determine document order. The acknowledgement is {op_id, accepted_revision, transformed_components, head_revision, session_id, connection_epoch, leader_epoch, result_hash}. Returning canonical transformed components lets the sender replace its optimistic form rather than infer what the server committed. An OP broadcast carries revision, original ID, canonical components, author, and resulting hash. NACK is typed: ACL_STALE, SCHEMA_UNSUPPORTED, BASE_COMPACTED, CONNECTION_EPOCH_STALE, LEADER_EPOCH_STALE, or INVALID_OPERATION; clients must not retry all failures blindly.

    The client keeps shadow at last_ack_revision, one in-flight batch, and a buffered local batch. A remote operation applies to shadow, then transforms through in-flight and buffered operations before applying to the visible document. ACK retires exactly the matching IDs and advances the shadow using the server's canonical operation. A revision gap, connection- or leader-epoch change, or hash mismatch pauses edits and sends RESYNC(session_id,connection_epoch,last_ack_revision,last_hash,pending_ids).

The server deduplicates pending IDs already committed and transforms only the remainder. The client verifies the server hash against canonical shadow, then atomically replaces it, reapplies valid pending intent, and only then unfreezes transmission. The visible tree with unacknowledged local edits is not expected to equal the server hash.

    Throughput, snapshots, undo, and offline bounds¶

    At the stated 330,000 ops/s, 200-byte logical operations become about 66 MB/s raw and roughly 5.7 TB/day. With three synchronous copies plus index/outbox overhead of 2x, provision roughly 66 MB/s * 3 * 2 = 396 MB/s sustained writes and about 34 TB/day before compression and expiry. Across one million active documents this is easy to shard; a single document remains serialized. Batching 20 keystrokes/s from 1,000 editors into 50 ms frames yields at most 20,000 primitive edits/s but about 20 leader batches/s per editor, so transform CPU is controlled by limiting both accepted batches/s and maximum components/batch. A 10,000-component pending window triggers read-only overload before quadratic transform work grows without bound.

    Snapshot on whichever comes first: 10,000 accepted components, 5 MB of log tail, or five minutes for active documents. A worker reads immutable revision R, materializes the typed tree, writes {format_version,R,root_hash} to object storage, then compare-and-swaps the document pointer only if it advances the prior snapshot. Keep a 24-hour hot tail and 30-day compressed archive as an example product policy. Compaction watermark is min(oldest supported session base, undo horizon, migration hold, replication checkpoint), not simply the latest snapshot.

    Undo records an intent group {actor_id, authored_op_ids, before_context, after_context}. To undo, fetch each canonical authored operation, invert it in reverse order, and transform the inverse through every later operation. Deleted content needed by the inverse lives in encrypted undo metadata until the undo horizon. Undo never rewinds another user's changes: undoing A's insertion deletes the surviving descendants of A's inserted span, while concurrently inserted B text remains. If later structure makes the inverse invalid, disable that undo entry instead of restoring a historical snapshot.

    Offline clients compact adjacent local inserts/deletes only while preserving stable operation IDs through a supersedes list. Fold only operations known never to have been submitted; resolve possibly committed IDs first, since partially accepting a composite would duplicate or erase intent. For example, typing hello, deleting lo, and adding p in one untouched leaf can upload I(p,"help") with the original IDs; crossing a remote anchor, comment boundary, or tree node forbids that fold. Once the server's history no longer covers the base, plain positional operations cannot be safely rebased from the snapshot alone. The client performs a three-way intent merge using its saved base, current snapshot, and local result, or creates a conflict document. This is the explicit offline bound that avoids pretending OT is a CRDT.

    Rich-text tree operations¶

    The canonical document is a schema-versioned tree with stable node IDs: block nodes contain inline leaves, and marks are normalized attributes rather than overlapping HTML tags. Operations include insert_node(parent_id,index,node), delete_node(node_id), move_node(node_id,new_parent,index), splice_text(leaf_id,pos,delete_count,text), and set_mark(leaf_id,start,end,key,value). The leader rejects cycles, unknown parents, invalid child types, and edits against deleted node IDs.

    Transforms use identity before position. Concurrent text splices in one leaf use the text matrix. Sibling inserts shift indexes with the same deterministic tie-break. A node edit against deletion becomes a no-op with an audit reason; concurrent moves of one node use last ordered move while preserving a single parent. Marks are interval operations transformed with text, split around deletions, and coalesced when adjacent values match. Structural normalization, such as merging adjacent equivalent text leaves, runs deterministically after each canonical operation and emits an ID-remap table in the ACK so cursors, comments, and pending edits retain anchors.

    Tradeoffs and final architecture¶

    Server OT provides compact operations, authoritative revisions, and straightforward enterprise policy, but limits one document's write throughput and offline independence. CRDTs improve decentralized convergence but spend metadata and add causal cleanup complexity. Snapshotting bounds startup but creates compaction compatibility obligations. A separate connection plane allows independent socket scaling and graceful gateway drains, at the cost of leased registries, reconnect protocol, and one more routing hop. Bounded document residency protects cells from memory exhaustion but makes hydration latency and eviction correctness explicit. Section sharding scales only when the product accepts weaker cross-section semantics. Durable operations must never share a fate with lossy presence.

    Questions, levels, and five-minute summary¶

    1. Which transform properties guarantee convergence?
    2. When does a CRDT beat OT for this product?
    3. How can logs be compacted while offline clients exist?
    4. What happens after commit but before sender acknowledgement?
    5. Can a viral document be partitioned without changing semantics?
    6. How does revocation interact with already downloaded content?

    L5 candidates should define operations, per-document ordering, retry IDs, snapshots, realtime reconnect, ACL checks, and OT/CRDT tradeoffs. L6 candidates should make convergence testable, negotiate offline and undo semantics, design fencing/compaction/migrations, quantify hot-document ceilings, isolate presence, and connect residency, audit, and deletion to product guarantees.

    In five minutes: route each document to a fenced home-region leader. Clients send idempotent operations based on a revision; the leader checks current ACL and schema, transforms through intervening OT operations, durably appends the next revision and outbox, then broadcasts. Clients transform incoming operations against pending local edits and reconnect by cursor; snapshots plus subsequent logs bound recovery. Keep presence lossy and separate. OT fits server-mediated, compact, auditable editing; choose a CRDT when long offline or peer-to-peer editing justifies stable element IDs, tombstones, and causal GC. Partition by document, protect viral documents with batching/read-only relays, and continuously property-test convergence, failover, compaction, and revocation races.
