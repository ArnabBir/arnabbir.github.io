    Design Twitter¶

    Interview roadmap¶

    Clarify whether the interview covers posting, following, home timelines, search, trends, and direct messages. This design serves tweets and home timelines; search, ads, and DMs are extensions. Start with chronological feeds, then add ranking. The decisive issue is asymmetric fanout: most authors are small, while a celebrity can have hundreds of millions of followers.

    Product framing and requirements¶

    Users create, delete, and read tweets; follow or unfollow accounts; and page through a home timeline. Tweets may contain text and references to uploaded media. Replies, reposts, and likes are modeled as typed edges or tweets, but notification delivery is outside the critical posting path.

    The system should sustain bursty global traffic, return a first timeline page in under 300 ms at p99, make ordinary tweets visible to most online followers within five seconds, and remain readable during partial failures. Deleted or access-revoked content must disappear quickly. A user must never receive a protected tweet without authorization. Ordering may be approximate across authors, but each tweet has a stable identity and an author's own sequence cannot reverse.

    Out of scope are full-text search, ad auctions, trend computation, and media transcoding internals.

    Correctness invariants¶

    • A successful create maps an idempotency key to exactly one tweet ID.
    • Canonical tweet state lives in the tweet store; timeline entries are disposable projections.
    • Authorization is checked at read time even when fanout happened earlier.
    • A delete tombstone dominates delayed fanout and cache entries.
    • Pagination never depends on mutable page numbers; cursors describe a stable boundary.
    • Follow state changes affect future eligibility, while policy defines whether historical tweets appear.
    • Queue delivery is at least once; consumers make effects idempotent.

    Capacity estimates¶

    Assume 500 million daily users, 200 million tweets/day, and 50 billion timeline item reads/day. At 50 delivered items/page, this is one billion page requests/day, about 11,574/s average and 116,000/s at 10x peak; the page-read/tweet-write API ratio is 5:1. A 20:1 ratio would instead require four billion pages/day averaging 12.5 delivered items/page. Do not equate item reads with page requests. Average tweet metadata is 1 KB, or about 200 GB/day before replication and indexes. At three replicas and one year online, tweet metadata approaches 220 TB. If an average author has 300 followers, naive fanout creates 60 billion entries/day; at 32 bytes each that is 1.9 TB/day before replication. Tweet-write peak at 10x average is about 23,150/s. Media bytes dominate storage and egress, so clients upload directly to object storage through signed URLs and consume via a CDN.

    These estimates justify separate canonical and derived stores, asynchronous fanout, and special treatment for high-fanout authors.

    Entities and data model¶

    User(user_id, handle, visibility, status, profile_version)
Tweet(tweet_id, author_id, author_seq, body, media_ids[], created_at, state)
Follow(follower_id, followee_id, state, updated_at)
TimelineEntry(owner_id, rank_time, tweet_id, author_id, source)
Idempotency(principal_id, key, request_hash, tweet_id, expires_at)
Tombstone(tweet_id, deleted_at, reason, policy_version)

    Tweet IDs can be time-sortable 128-bit IDs allocated regionally. Tweet partitions by tweet_id; an author-time index supports profiles. Follow edges need both directions: followees by follower for reads and followers by followee for fanout. Timeline entries partition by owner and bucket by month or sequence range to avoid unbounded partitions.

    APIs¶

    POST /v1/tweets                 Idempotency-Key: <uuid>
GET  /v1/tweets/{tweet_id}
DELETE /v1/tweets/{tweet_id}
PUT  /v1/users/{id}/following/{followee_id}
DELETE /v1/users/{id}/following/{followee_id}
GET  /v1/users/{id}/timeline?cursor=<opaque>&limit=50
POST /v1/media/uploads

    Creation returns 201 with the stable ID, or the original response on retry. A timeline cursor contains the last rank key, snapshot/ranking version, and a signed expiry; it is not a raw offset. Responses include content and policy versions so caches cannot resurrect older visibility.

    The write service commits tweet and outbox record atomically. Event-log consumers update profile indexes, notifications, counters, and timeline projections independently. Reads fetch candidate IDs, remove tombstones and unauthorized items, hydrate canonical tweets in batches, rank, and cache only short-lived pages.

    Core flows¶

    Create and fan out¶

    sequenceDiagram
    autonumber
    participant C as Client
    participant W as Tweet service
    participant D as Tweet DB
    participant K as Event log
    participant F as Fanout workers
    participant T as Timeline store
    C->>W: POST tweet + idempotency key
    W->>D: transaction: key, tweet, outbox
    D-->>W: committed tweet ID
    W-->>C: 201 Created
    W->>K: relay outbox event
    K->>F: tweet-created (at least once)
    F->>T: conditional insert(owner, tweet)

    For ordinary authors, workers enumerate follower shards and push an entry to each home timeline. Fanout is parallel but bounded; lag is measured by event age. For celebrities, the event records a pull candidate instead of writing millions of entries. The home read merges precomputed inbox entries with recent tweets from followed celebrity accounts, then ranks the combined set. Thresholds should use measured fanout cost and posting rate, not a permanent celebrity flag.

    Read a timeline¶

    sequenceDiagram
    autonumber
    participant C as Client
    participant T as Timeline service
    participant I as Timeline index
    participant H as Hot-author index
    participant S as Tweet store
    participant P as Policy
    C->>T: GET timeline(cursor)
    T->>I: scan pushed candidates
    T->>H: fetch pull candidates before boundary
    T->>S: batch hydrate IDs
    T->>P: batch authorize(viewer, authors, tweets)
    P-->>T: allowed set
    T-->>C: ranked page + next cursor

    The service overfetches because deletion, blocking, and moderation remove candidates. It applies a strict work budget; if filtering empties a page, it may return fewer items rather than scan without bound. Ranking can start with reverse chronology, then incorporate relationship affinity and quality. The cursor freezes the ranking model version for a short session to reduce duplicates and jumps.

    Domain deep dives¶

    Fanout, hot keys, and backpressure¶

    Follower lists are range-sharded, and each fanout task addresses one shard. A scheduler uses weighted queues so a viral account cannot starve ordinary authors. When lag exceeds the SLO, it degrades large accounts from push to pull, coalesces fanout tasks by author while retaining every distinct tweet reference, and postpones noncritical counters. Per-user timeline writes can also be hot when a user follows many prolific accounts; append buckets and write combining spread load.

    Deletes, edits, and privacy¶

    Deletion first marks canonical state and commits a tombstone event. Reads always honor canonical state or a compact tombstone cache, so physical removal from every timeline can lag. Sweepers remove projections and CDN objects. Protected-account changes and blocks increment policy versions; timeline cache keys include viewer and policy version. Cache hits still validate current policy freshness and deny state; a stored version number or delayed invalidation cannot alone prove the removal bound. If edits are allowed, immutable revisions preserve moderation evidence while only the latest authorized revision is served.

    Pagination and ranking stability¶

    Offset pagination fails under concurrent insertion. The cursor records (score, created_at, tweet_id) and the oldest candidate window already considered. Ranked scores change, so sessions either freeze candidates and the computed ordered scores briefly or accept clearly documented at-least-once appearance. Clients deduplicate by tweet ID. Refill logic limits scans and exposes an is_partial signal during dependency degradation.

    Partitioning and multi-region¶

    Tweets partition by hash of tweet ID with an author index; graphs partition by followee for fanout and maintain an asynchronously built reverse view. Timeline partitions use owner ID plus time bucket. Virtual shards permit rebalancing, and heavy owners can receive dedicated shards.

    Route writes to a user's fenced home authority to preserve author sequence. Replicate tweets, author-sequence high-watermarks, idempotency and graph changes; timeline projections are rebuildable. Failover fences the old writer and restores that authority before accepting new posts. A new random/time-sortable ID range alone cannot restore acknowledged author order or lost idempotency state; asynchronous disaster recovery must expose its RPO and cannot silently reorder prior acknowledgements by ID. Privacy and delete events use a priority lane and read-time deny lists.

    Consistency, idempotency, and failures¶

    Tweet creation is strongly consistent within its shard. Timelines, counts, and notifications are eventually consistent. Follow creation uses a compare-and-set state machine so retries cannot duplicate edges. Consumers store event IDs or use naturally unique keys such as (owner_id, tweet_id). Outbox relay retries forever; poison events enter quarantine with alarms and replay tooling.

    If the graph store is unavailable, posting still succeeds and fanout waits. If the timeline store fails, reads can fall back to pull from a bounded set of followees, returning a partial marker. If ranking fails, reverse chronology is valid. Cache failures cause load shedding, not unbounded database traffic. Every queue has retention sized for recovery, age-based alerts, and admission control. Rebuilding a timeline scans recent posts from current followees, while canonical tweets remain untouched.

    Abuse, security, and privacy¶

    Authenticate at the edge; authorize every mutation against the principal. Rate-limit by account, device, IP reputation, and action. Separate spam scoring from durable acceptance so false positives can be appealed, but block known malicious media before distribution. Encrypt transport and storage, isolate media upload credentials, audit employee access, and minimize viewer-specific cache sharing. Blocking, muted words, legal holds, geographic restrictions, and account deletion are policy inputs, not client filters.

    Observability and testing¶

    Track API p50/p99, create success, event age, fanout amplification, per-shard saturation, timeline empty/partial rate, hydration misses, policy-deny rate, cache hit rate, and delete propagation latency. Trace from tweet ID through outbox and fanout tasks. Synthetic accounts continuously post, follow, block, delete, and verify visibility across regions.

    Test model invariants with property tests; retry every mutation under injected timeouts; replay duplicate and reordered events; load-test Zipfian follower distributions; chaos-test broker, cache, and region loss; and verify authorization with a generated relationship matrix. Shadow ranking models and compare candidate loss before rollout.

    Important tradeoffs and final architecture¶

    Pure push gives cheap reads but catastrophic celebrity writes and stale privacy projections. Pure pull avoids amplification but makes every read proportional to followee count. Hybrid fanout bounds both. Storing full tweets in timelines improves locality but multiplies edits and deletions; storing IDs preserves one canonical copy at the cost of hydration. Global synchronous writes simplify semantics but damage availability and latency; home-region writes plus explicit eventual projections fit the product.

    flowchart TD
    A[Regional edge] --> B[Home-region write path]
    B --> C[(Canonical tweets + outbox)]
    C --> D[Global durable event log]
    D --> E[Priority policy/delete consumers]
    D --> F[Adaptive fanout scheduler]
    F --> G[(Regional pushed timelines)]
    D --> H[(Hot-author recent-post index)]
    I[Timeline read] --> G
    I --> H
    I --> J[Hydration + authorization]
    J --> K[Ranker or chronological fallback]

    Interview deep-dive questions¶

    1. How do you choose and dynamically change the push/pull threshold?
    2. What happens when a user blocks an author while fanout is delayed?
    3. How does cursor pagination behave when ranking scores change?
    4. How would you rebuild one corrupted timeline without replaying all history?
    5. Which workloads create hot partitions despite hashing?
    6. How do you prove deletion propagation meets policy?

    L5 and L6 expectations¶

    An L5 candidate should estimate amplification, separate canonical tweets from timelines, propose hybrid fanout, define cursor pagination, and explain retries, deletion, and cache fallback. An L6 candidate should make policy propagation an invariant, design adaptive overload behavior, articulate regional write ownership and recovery, quantify skew, provide migration and replay mechanisms, and connect ranking, moderation, privacy, and cost to operational ownership.

    Five-minute summary¶

    Store tweets once as canonical records and publish committed outbox events. Push ordinary authors' tweet IDs into follower timelines, but pull recent posts for accounts whose fanout cost is excessive. Timeline reads merge both candidate sources, batch-hydrate canonical tweets, enforce current policy, rank, and paginate with an opaque boundary cursor. Hash and bucket timeline data, shard follower enumeration, isolate viral fanout with fair queues, and degrade ranking to chronology. Use idempotency keys for writes and unique projection keys for at-least-once consumers. Treat deletes and access revocations as priority tombstones checked at read time. Keep each region's projections rebuildable from canonical state and the event log, and operate the design through lag, skew, partial-result, privacy, and recovery metrics.
