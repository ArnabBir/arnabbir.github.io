    Design the Facebook News Feed¶

    Interview roadmap¶

    Scope the feed rather than all of Facebook. Clarify sources, ranking, privacy, freshness, and interaction writes. Build a candidate-generation pipeline over posts and social edges, then add hybrid fanout, ranking, and policy filtering. The central distinction from a chronological timeline is that ranking combines many source types while privacy can change after materialization.

    Product framing and requirements¶

    Users publish posts, create friendship or follow edges, join groups, and consume a personalized feed containing eligible posts from friends, followed pages, and groups. They react, comment, hide, or report. This chapter owns post metadata, candidate generation, ranking, pagination, and visibility enforcement; media processing, recommendations beyond connected sources, ads, and comment internals are excluded.

    Feed reads should complete under 400 ms p99, post creation under 300 ms p99, and ordinary posts should become candidates within ten seconds. Availability favors reads, but never at the expense of showing content the viewer cannot currently access. Ranking may be eventually consistent. Deletes, blocks, group removal, and audience changes must take effect within a bounded policy SLO.

    Correctness invariants¶

    • A post has one canonical audience policy and lifecycle state.
    • Candidate presence never implies authorization; reads re-evaluate policy.
    • An idempotency key identifies one mutation and request body.
    • A reaction from one user has one current state per post.
    • Deleted content cannot be resurrected by delayed events or stale caches.
    • Feed cursors use stable boundaries, not offsets.
    • Model failure has a deterministic eligible chronological fallback.

    Capacity estimates¶

    Assume 1 billion daily users, 300 million posts/day, 20 feed sessions/user/day, and 20 items/page. That is 20 billion feed requests/day, around 230,000/s average and 1.5 million/s peak. At 2 KB metadata per post, new canonical metadata is 600 GB/day before replication. If each post were pushed to 500 recipients, 150 billion candidate entries/day would result. A 24-byte candidate reference is 3.6 TB/day. Groups and pages create extreme skew, so fanout must be selective. Media dominates bytes and uses object storage and CDN.

    The read path should fetch perhaps 500 candidates to return 20 after filtering and ranking. At peak this is too expensive without precomputed candidate inboxes, caches, and bounded retrieval.

    Entities and data model¶

    Post(post_id, author_id, body_ref, audience_id, created_at, state, version)
Audience(audience_id, type, owner_id, rule, version)
Edge(src_id, dst_id, edge_type, state, affinity, updated_at)
Candidate(owner_id, bucket, post_id, source_id, reason, created_at)
Interaction(post_id, user_id, type, state, updated_at)
FeedSession(session_id, user_id, model_version, boundary, expires_at)

    Posts partition by ID, with author-time indexes. Edges maintain viewer-to-sources and source-to-viewers projections. Candidate stores partition by viewer and time bucket. Interaction keys make updates naturally idempotent. Audience rules are versioned because retroactive access decisions need an auditable input.

    APIs¶

    POST /v1/posts                       Idempotency-Key: <uuid>
PATCH /v1/posts/{id}/audience
DELETE /v1/posts/{id}
GET /v1/feed?cursor=<opaque>&limit=20
PUT /v1/posts/{id}/reactions/me      {"type":"LIKE"}
DELETE /v1/posts/{id}/reactions/me
POST /v1/feed/{post_id}/feedback     {"action":"HIDE"}

    The feed response explains source reason at a product-safe level and returns a signed cursor containing session, rank boundary, and expiry. Mutation retries with the same key and different payload receive 409.

    Core flows¶

    Publishing and candidate generation¶

    Small friend audiences are pushed. Large pages and groups publish into source-specific recent-post indexes and are pulled during reads. Medium sources may push only to recently active, high-affinity followers. Candidate generation stores reason and source, not a copied post or permanent authorization decision.

    Feed read and ranking¶

    sequenceDiagram
    autonumber

    Candidate generation optimizes recall; ranking optimizes ordering. Retrieval imposes quotas per source class so one active group cannot monopolize the page. The ranker consumes precomputed features with point-in-time definitions; request-time features have strict latency budgets. Filtering occurs before and after ranking to handle races.

    Domain deep dives¶

    Candidate generation and diversity¶

    Sources include friend posts, pages, and groups. Each generator emits a common envelope with post ID, reason, event time, and source score. A mixer applies per-source caps, author deduplication, and freshness windows. This prevents a prolific source from occupying all retrieval slots before the expensive ranker. Missing one generator yields a partial but valid feed; the service records which source classes contributed.

    Ranking lifecycle¶

    Offline pipelines train models from impression and interaction logs while guarding against leakage and feedback loops. A feature registry defines ownership, freshness, defaults, and privacy classification. Online inference is versioned and shadowed before serving. If feature fetches or inference exceed budget, use cached features or a lightweight model, then chronology. Feed sessions pin a model version briefly, but do not promise immutable pages because new blocks and deletes override rank stability.

    Privacy-aware materialization¶

    Audience choices include public, friends, custom lists, and group membership. Expanding every custom audience into candidates is optional optimization, never the source of truth. Visibility evaluates current edge state, audience version, blocks in both directions, geographic policy, age restrictions, and moderation state. A deny cache receives priority invalidations. Positive authorization caches are short-lived and keyed by all relevant versions. Their freshness lease and the final response gate must fit the declared removal bound; knowing a cached version number alone does not prove it is current. Public content still requires fresh deletion, block and moderation state.

    Interactions and feedback¶

    Reaction updates are upserts on (post_id,user_id) and emit change events. Counters are eventually consistent sharded aggregates, so the displayed count can lag while the user's own reaction reads from canonical interaction state. Hide/report feedback immediately affects that viewer's feed through a viewer suppression store; asynchronous safety systems investigate broader action.

    Partitioning, scaling, and regions¶

    Hash posts by ID and retain author indexes separately. Partition candidate inboxes by viewer plus time bucket; split unusually active viewers into sub-buckets merged at read. Partition social reverse edges by source and range so large pages enumerate in parallel. Cache post bodies by immutable version, but never cache a cross-user assembled feed without viewer and policy identity.

    Use a user's home region for interaction and post writes, with regional ID allocation. Replicate canonical state and events. Build candidate inboxes locally because they are disposable. Membership and block changes travel on a priority stream; if their freshness cannot be proven, fail closed for restricted content. Region evacuation restores reads from replicated posts and rebuilds recent candidates, accepting lower personalization before full recovery.

    Consistency, idempotency, and failure recovery¶

    Post and audience updates are linearizable per post shard. Feed candidates, counters, and features are eventual. Outbox publication closes the database/broker dual-write gap. Consumers use event IDs and unique candidate keys. Event versions reject stale updates; tombstones dominate creates with lower versions.

    Broker lag delays freshness but not posting. Candidate-store loss triggers bounded pull from connected sources and asynchronous rebuild. Ranker failure falls back. Visibility failure fails closed for nonpublic content and can serve only already-proven public posts. Feature-store overload sheds expensive feature families. Circuit breakers and per-stage deadlines prevent retries from multiplying load. Recovery tools can replay by source, viewer shard, event range, and model version.

    Security, abuse, and privacy¶

    Authenticate sessions, authorize post mutations, encrypt data, and audit policy or employee access. Rate-limit publishing, interactions, group invitations, and scraping using account and device reputation. Safety classifiers can quarantine distribution while preserving canonical evidence. Explanations must not reveal private edge information. Data export and deletion traverse posts, interactions, indexes, training datasets, and caches with lineage-based completion records. Logs avoid post bodies and protected audience membership.

    Observability and testing¶

    Measure feed latency by stage, candidate count and age by source, eligibility rejection, model and feature fallback, diversity, empty-page rate, duplicate impressions, post-to-feed delay, deletion/block propagation, fanout cost, queue age, shard skew, and CDN egress. Business metrics need guardrails for reports, hides, and demographic quality, not only engagement.

    Contract-test each candidate generator. Property-test audience matrices and cursor boundaries. Replay duplicated, delayed, and reordered events. Load-test graph and page-size distributions rather than uniform traffic. Chaos-test loss of ranker, visibility cache, broker, and a region. Use offline evaluation, shadow traffic, canaries, and holdbacks for ranking changes. Synthetic private groups continuously verify no unauthorized exposure.

    L6 mechanisms: bounded retrieval, ranking, and stable delivery¶

    Candidate quotas and quantitative fanout choice¶

    For a request that needs 20 results, retrieve at most 600 candidates: 240 friend posts, 120 groups, 80 followed pages, 60 connected-source recency, and 100 reserve slots redistributed to generators that meet deadlines. Within a class, cap one author at 20 retrieval candidates and one group at 30. Deduplicate by post ID before visibility checks. Quotas are configuration by cohort and are logged with the request; they constrain infrastructure and concentration, not final page counts. An underfilled class lends unused quota rather than forcing low-quality items.

    Choose push versus pull from measured cost, not a label such as celebrity. For source s, let F_s be eligible followers, a_s the fraction active during the candidate TTL, P_s posts/day, e=24 bytes per inbox reference, and r_s expected reads/day. Push storage bytes are P_s * F_s * a_s * e. Compare monetary or normalized resource cost by applying write/storage prices, then compare with bounded source-index reads and ranking cost under expected read rate r_s; raw bytes cannot be compared directly with a per-lookup cost. A pull reads only the bounded recent candidate slice, not necessarily every daily post. With a 24-hour inbox, a_s=0.2, and a per-post fanout budget of 10 MB, push only while F_s * 0.2 * 24 <= 10 MB, or about 2.08 million followers. Operationally use a lower 1 million threshold to reserve retry/index headroom. Also switch to pull whenever predicted fanout completion exceeds the ten-second freshness SLO. Recompute the class from trailing seven-day active-follower and post-rate estimates; use hysteresis, for example enter pull above 1 million and return to push below 700,000, to prevent flapping.

    Ranking, diversity, and fallback ladder¶

    Stage one uses cheap freshness, affinity, source quality, and negative-feedback features to reduce 600 eligible candidates to 200. Stage two scores at most 80 with the full model. Selection then greedily maximizes model_score - lambda_author * author_count - lambda_source * source_count - lambda_topic * recent_topic_count, subject to an author cap of at most two items per page, a soft target of at most five from one source class, relaxed when fewer than four eligible classes exist, no exact duplicate media, and at least two source classes when inventory permits. Fairness and integrity constraints are evaluated as launch guardrails by geography and cohort; they are not inferred from engagement score.

    Fallback is deterministic and preserves eligibility: full model with fresh features, full model with registered defaults, lightweight model, then reverse chronological order over the already authorized mixed set. A timeout never bypasses visibility or block checks. If fewer than 20 safe candidates survive, return fewer than 20. The response records the fallback level so experiments do not treat degraded traffic as normal model output.

    Latency and feature budgets¶

    The 400 ms endpoint deadline allocates 25 ms for edge/auth, 70 ms for parallel candidate reads, 55 ms for visibility, 45 ms for lightweight feature fetch and pre-rank, 65 ms for heavy features plus inference, 45 ms for diversity selection and hydration, 25 ms for serialization/network, and 70 ms contingency. These sum to 400 ms; they are deadline allocations, not a proof obtained by summing measured component p99s. Deadlines are absolute from request start, so a late stage cannot consume another stage's reserve. Candidate generators have a 60 ms soft deadline and 70 ms hard deadline; late classes are omitted and recorded.

    Feature payload is capped at 80 candidates times 128 dense values, about 40 KB using 32-bit values before protocol overhead. At most 16 request-time features may perform remote reads, all through two batch calls with a combined 30 ms deadline. The rest come from a point-in-time online vector keyed by (viewer_id,post_id,feature_version) or viewer/source vectors. Missing-feature bitsets accompany defaults so the model can distinguish zero from unavailable. Shed semantic embeddings first, then cross features, while retaining block, audience, moderation, and age controls outside the feature system.

    Impression provenance and mutation-safe pagination¶

    Persist one deduplicated record per rendered card, not merely per response:

    Impression(impression_id, request_id, feed_session_id, viewer_id,
           post_id, post_version, author_id, source_type, source_id,
           candidate_reason, candidate_event_time, generator_version,
           retrieval_quota, pre_rank_score, final_score, rank_position,
           model_version, feature_snapshot_id, policy_version,
           mixer_version, fallback_level, experiment_ids, rendered_at)

    The client emits VISIBLE(impression_id) after a defined viewport/time threshold; server-return and client-visible events remain separate. Interaction training joins through impression_id, preserving which generator, policy, features, and model caused exposure. Logs are access-controlled and retention-limited because source and experiment provenance can reveal graph information.

    The signed cursor contains {session_id, viewer_id, issued_at, expires_at, model_version, mixer_version, as_of_time, last_score_bucket, last_event_time, last_post_id, seen_digest}. First-page as_of_time freezes the upper creation-time boundary: newer posts appear only after refresh, preventing inserts from shifting later pages. Seek with the total key (score_bucket DESC,event_time DESC,post_id DESC), never offset. Scores are quantized and the model/mixer version is pinned for the short session. Deletes and lost authorization are filtered immediately, so pages may shrink; the service over-fetches but never backfills with an item above the cursor boundary. Server page publication atomically advances the session generation and exact seen set; concurrent requests return the winning stored page or retry from the current cursor. Client and server retain exact seen IDs for the short session; the digest detects cursor tampering or state loss.

    If mutable features reorder an unseen post below the boundary, it may appear later; if they move it above, it waits for refresh. This yields no unauthorized or duplicate item within retained session state, but not a globally immutable ranking. Expired sessions start a new snapshot. A deterministic retry key (session_id,page_boundary) returns the same impression IDs where cached, preventing retries from double-counting exposure.

    Tradeoffs and final architecture¶

    Push-only candidate generation minimizes read work but amplifies writes and bakes in stale eligibility. Pull-only keeps graph changes simple but cannot meet feed latency for users with thousands of sources. Hybrid materialization plus read-time policy checks separates performance from correctness. A single end-to-end model is potentially optimal but hard to debug and expensive; retrieval, mixing, and ranking stages provide budgets and graceful degradation. Session snapshots improve pagination but consume state; short-lived signed cursors and client deduplication are usually enough.

    Interview deep-dive questions¶

    1. Which eligibility checks happen at fanout and which must happen at read?
    2. How do you stop a large group from dominating candidate retrieval?
    3. What cursor semantics are offered when model scores change?
    4. How do you roll back a model without invalidating every session?
    5. What is served when visibility or feature systems are unavailable?
    6. How do deletion guarantees extend into training data?

    L5 and L6 expectations¶

    L5 candidates should separate posts from candidates, estimate fanout, design hybrid push/pull, explain ranking fallback, and cover retries and privacy filtering. L6 candidates should define stage budgets and overload policy, version authorization inputs, handle regional evacuation, reason about model governance and feedback loops, build replay/migration paths, and balance relevance against safety, fairness, latency, and infrastructure cost.

    Five-minute summary¶

    Keep posts, relationships, and interactions canonical; treat feed candidates, counters, and features as rebuildable projections. Commit posts with an outbox, push candidates for bounded audiences, pull from recent indexes for large pages and groups, and mix source classes under explicit quotas. On every read, batch-check current visibility, rank a bounded eligible set, hydrate immutable post versions, and issue a signed boundary cursor. Partition inboxes by viewer and time and reverse edges by source ranges. Make every consumer idempotent and every lifecycle update versioned. Prioritize block and deletion propagation, degrade inference to simpler models and chronology, and fail closed when restricted-content authorization is uncertain. Operate stage latency, fanout skew, candidate quality, policy propagation, and recovery independently.
