    Design an Autocomplete System¶

    Interview roadmap¶

    Design query suggestions returned while a user types. Clarify sources, personalization, freshness, languages, safety, and latency. Build the smallest system from offline query counts and an in-memory prefix index, then add streaming updates, ranking, context, typo tolerance, hot-prefix protection, regional serving, and governance. The central tension is serving a safe ranked list in tens of milliseconds while popularity changes continuously.

    Product framing and requirements¶

    For a normalized prefix and context, return up to ten suggestions with display text and optional entity metadata. Sources include historical queries, catalog entities, editorial entries, and current trends. Results may vary by locale, market, device, and authenticated user. Administrators can block, pin, or expire phrases. We exclude full search and document retrieval; selection logs feed ranking asynchronously.

    Target 50 ms p99 from edge, 99.99% availability, hourly baseline freshness, trend visibility within one minute, and policy removal within one minute globally. Empty-prefix discovery is a different product and is not served by this endpoint. Results can be eventually consistent across users, but policy filtering must meet its bounded staleness contract.

    Correctness invariants¶

    • Every returned suggestion begins with the normalized prefix unless explicitly labeled typo correction.
    • Policy-denied text is never intentionally published; emergency blocks override every score and cache.
    • A response contains unique canonical suggestion IDs and a deterministic order for the same captured index, model, policy, trend watermark, and request context. Index version alone does not freeze personalized or streaming inputs.
    • Offline snapshots are immutable, checksummed, and atomically activated.
    • Streaming deltas are monotonic by (partition, offset) and deduplicated by event ID.
    • User history is never exposed across identities or used outside consent and retention policy.
    • Ranking degradation may reduce relevance, not bypass safety.

    Capacity estimates¶

    Assume 500 million daily search users, 20 searches/user/day, and six autocomplete requests/search: 60 billion requests/day, 700,000/s average and 5 million/s peak. A response around 1 KB yields 5 GB/s peak egress before protocol overhead. There are 500 million candidate strings across locales. Storing normalized text, ID, features, and top-prefix postings at 100 bytes is 50 GB raw, but replicated tries and postings may require hundreds of GB. Logs at 200 bytes/request produce 12 TB/day, so sample impressions while retaining selections and policy events fully.

    Core algorithms and flows¶

    Normalization and candidate retrieval¶

    Normalization applies locale-aware Unicode normalization, whitespace collapse, case handling, and script detection. Store the canonical form beside display variants; do not blindly strip accents because meaning changes in some languages. The prefix index maps each trie node to a bounded top-K candidate list. Lookup is O(length(prefix) + K), independent of corpus size. A compressed radix trie reduces pointers; a finite-state transducer compresses shared suffix/output structure further but complicates incremental changes.

    Each node stores perhaps 100 candidates, larger than the returned ten, to leave room for filtering and reranking. For long-tail prefixes absent from the precomputed index, descend into a term dictionary and merge bounded postings. Single-character prefixes are extremely hot and broad, so they use dedicated replicated objects and aggressive edge caching.

    Ranking¶

    Candidate score combines smoothed popularity, selection-through rate, recency, edit cost, locale match, entity quality, user affinity, and policy/editorial adjustment:

    score = w1*log1p(decayed_frequency)
      + w2*bayesian_selection_rate
      + w3*freshness + w4*context_match + w5*personal_affinity
      - w6*edit_cost - policy_penalty

    Use exponential decay weight = exp(-lambda * age) so old popularity fades. Bayesian smoothing prevents a phrase with one impression and one click outranking established results. The model reranks only a bounded candidate set and has a deterministic lexical/ID tie-break. If features or model are unavailable, fall back to snapshot base score and still run local policy filters.

    Build and publish¶

    sequenceDiagram
    autonumber
 participant L as Event log
 participant A as Aggregator
 participant B as Index builder
 participant V as Validator
 participant C as Control plane
 participant S as Serving fleet
 L->>A: queries and selections
 A->>B: privacy-thresholded counts
 B->>B: normalize, score, top-K per prefix
 B->>V: immutable snapshot and manifest
 V->>V: safety, quality, checksum tests
 V->>C: approved version
 C->>S: staged activation
 S->>S: mmap then atomic pointer swap

    Builders aggregate distinct-user counts and apply minimum support, bot filtering, privacy thresholds, and differential privacy where required. They generate immutable locale/market shards, manifests, checksums, model version, and source watermark. Servers download in the background, validate, warm key prefixes, then atomically switch pointers. Old snapshots remain for rollback and are deleted by retention policy.

    Trending deltas¶

    A streaming job computes event-time windows and compares observed frequency with a seasonality baseline. A trend requires enough distinct trusted users, geographic dispersion, and selection evidence. Use burst score such as (observed - expected) / sqrt(expected + c), capped to prevent tiny baselines from exploding. Deltas have TTLs and merge with snapshot candidates at read time. The snapshot records the aggregate cutoff/watermark; an overlay adds only contributions not already represented, or supplies an explicitly defined replacement trend feature. On snapshot swap, reset/rebase the overlay atomically so the same events do not inflate both base and delta scores. Late events revise only open windows; replay deduplicates by event ID and partition offset.

    Personalization, typo tolerance, and diversity¶

    Personal history is a separate keyed store queried only for authenticated, consented users. Merge a few matching recent selections, never the raw history of another user. Cache personalized responses privately or not at all. Contextual models may consider country, app surface, and broad time bucket; sensitive attributes are prohibited.

    For prefixes longer than two characters, retrieve bounded edit-distance-one candidates from a deletion index or trie traversal. Label corrections and demand a score margin before replacing literal-prefix results. Transliteration is locale-specific. Diversity constraints limit near-duplicates and ensure, where product requires, a mix of query and entity types. These post-ranking rules are versioned and tested against relevance sets.

    Partitioning, scaling, and hot keys¶

    Shard snapshots by locale/market and first normalized bytes, but replicate tiny hot-prefix tables everywhere. Serving nodes hold common shards in memory and memory-map colder shards. Consistent hashing assigns long-tail requests; replicas permit hedging only when the first request exceeds a percentile threshold, avoiding doubled normal load. Edge caches key by normalized prefix, locale, coarse context, policy generation, and index version. Personalized fragments do not enter shared caches.

    The fanout from typing means client behavior matters: debounce 50-100 ms, cancel superseded requests, and reuse a request sequence so late responses are ignored. Under overload, shed typo correction and personalization, shorten candidate pools, serve stale verified snapshots, and return no result rather than unfiltered text. Token buckets protect tenants and abusive IPs. Backpressure pauses analytics sampling before affecting selection events or policy distribution.

    Multi-region serving is active-active with complete local snapshots. Trend deltas replicate asynchronously and may differ briefly. The governance plane publishes signed policy generations through a high-priority channel; emergency deny rules are also pushed to edge processes. Snapshot activation is regionally staged, with a global minimum-safe policy version independent of content index version.

    Consistency, failures, and recovery¶

    Index and model versions are eventually consistent, but each response is internally consistent because one request pins a snapshot pointer. Policy is bounded-staleness and fail-safe: servers refuse versions older than the emergency deadline. Selection ingestion is at least once; deterministic event IDs and aggregate upserts make effects idempotent. We do not promise exact counts.

    Builder failure leaves the old snapshot active. Partial downloads never activate because manifests and checksums fail. A bad ranking release rolls back by pointer. Stream lag ages out deltas rather than making them permanent. Cache outage increases origin load, so admission control and local hot-prefix tables protect servers. Feature-store timeout uses defaults. A poison locale shard is quarantined while others publish. Region loss reroutes to another region with higher latency but no canonical write conflict.

    Deletion removes user signals by subject key and ages raw logs; derived anonymous aggregates remain only if policy permits. A policy incident triggers rule publication, cache-key generation change, snapshot scan, and auditable proof of propagation. Rebuilds are reproducible from source watermarks and code/model artifacts.

    Security, abuse, observability, and testing¶

    Authenticate internal publishers, sign snapshots and rules, encrypt user history, isolate operator roles, and audit pins/blocks. Defend against suggestion poisoning, bots, offensive phrase amplification, celebrity harassment, election manipulation, Unicode confusables, scraping, and query leakage. Require distinct-user and reputation thresholds, rate-limit clients, cap editorial influence, and provide rapid kill switches. Never log raw sensitive prefixes indiscriminately.

    Measure end-to-end and server latency, cache hit rate, candidates retrieved/filtered, empty rate, model fallback, index age, trend lag, policy generation lag, snapshot load failures, request cancellation, QPS by prefix entropy, hot-shard saturation, and selection metrics with guardrails for unsafe or low-diversity results. Track freshness and relevance by locale, not only globally.

    Property-test normalization idempotence, prefix validity, uniqueness, deterministic ordering, and denied-term absence. Golden sets measure recall, mean reciprocal rank, and locale quality. Replay historical traffic against candidate/model changes. Fuzz Unicode and malformed context. Load-test one-character hot keys and synchronized trends. Chaos-test cache loss, stale policy, corrupt snapshots, stream duplication, and region evacuation. Canary versions by region and user bucket with automatic safety rollback.

    Important tradeoffs and final architecture¶

    A database query per keystroke is simple but cannot meet latency and hot-key scale. Precomputed top-K prefix lists trade storage for predictable reads. Tries are straightforward; FSTs compress better but are harder to update, so immutable batch FST plus a small delta store works well. Fully online ranking is freshest but fragile; bounded reranking over a verified snapshot gives a safe fallback. Global strong consistency for trends wastes latency, while strong emergency policy propagation is justified.

    flowchart TD

 Gate -->|valid| Response[Cached response]
 Gate -->|stale| Empty[Refuse stale policy response]

    The final architecture keeps immutable, validated prefix snapshots as the reliable base; a TTL streaming overlay supplies freshness. Regional in-memory servers merge bounded candidates, apply hard policy, then rerank and diversify. Edge and local caches absorb hot prefixes, while private overlays personalize safely. Batch and stream paths are replayable, versioned, independently degradable, and observable.

    Interview deep-dive questions¶

    1. How do you serve five million requests/s for one-character prefixes?
    2. How can trends become fresh without poisoning suggestions?
    3. What consistency does an emergency block require?
    4. How is a snapshot deployed and rolled back without mixed reads?
    5. How do typo suggestions preserve the prefix contract?
    6. Which signals can be sampled, and which must remain complete?
    7. How would you evaluate a ranking change before launch?

    L5 and L6 expectations¶

    An L5 candidate should estimate keystroke amplification, define normalization and top-K prefix lookup, separate offline build from serving, use caching and sharding, explain ranking, freshness, retries, and safe fallback. They should identify hot prefixes and eventual consistency.

    An L6 candidate should define privacy and policy invariants, design snapshot migration and stream replay, quantify degradation stages, address multilingual ambiguity and poisoning, separate governance from serving, and connect model quality, logging cost, regional policy, and product constraints. They should propose measurable guardrails and incident recovery.

    Five-minute summary¶

    Build privacy-thresholded, immutable locale snapshots mapping normalized prefixes to generous top-K candidate lists. Validate and atomically activate them on regional in-memory servers. Stream trusted burst deltas with TTL for minute-level trends and merge a small consented user overlay. Apply emergency and normal policy before a bounded deterministic reranker; relevance fallback may simplify but never bypass safety. Cache versioned hot prefixes at edge, replicate tiny one-character tables, debounce clients, and ignore superseded responses. Shard colder data by locale and prefix, shed personalization and typo work under load, and serve an older verified snapshot during build failure. Observe index and policy age, hot-key saturation, candidate filtering, latency, empties, relevance, and abuse. Rebuild and rollback from signed manifests and source watermarks.
