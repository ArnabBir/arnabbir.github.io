    Design a ChatGPT-Like Assistant¶

    Interview roadmap¶

    Design a conversational AI product that accepts multimodal prompts, maintains conversation context, streams model output, uses tools and retrieval, enforces safety, and controls expensive GPU capacity. Clarify model scope, latency, privacy, tenant isolation, and whether training is included. Begin with one model and stateless inference, then add durable conversations, batching, routing, tool execution, retrieval, quotas, evaluation, and regional governance.

    Product framing and requirements¶

    Users create conversations, send messages, receive streamed answers, stop or regenerate, upload files, and optionally invoke approved tools. Organizations configure retention, model access, data residency, and tool policy. Operators deploy model versions and safety rules. Training the foundation model is out of scope; model serving, feedback, and safe rollout are in scope.

    Target API acceptance below 300 ms p99, time to first token below 2 seconds p95 for the standard tier, steady generation above 20 tokens/s, 99.9% successful request completion excluding client cancellation, and explicit overload responses rather than unbounded queues. Conversations are durable; token streams are resumable only from persisted checkpoints and may be regenerated. Safety and authorization cannot be bypassed when optional ranking or retrieval fails.

    Correctness invariants¶

    • A client idempotency key creates one user message and at most one active generation lineage.
    • Conversation branches are immutable parent-linked messages; regenerate creates a sibling, not an overwrite.
    • Tokens are exposed only after input policy and authorization pass, and tool results are treated as untrusted input.
    • A tool with side effects requires explicit policy, stable invocation ID, and idempotent or confirmed execution.
    • Billing is derived from metered accepted input and generated output with auditable model/tokenizer versions.
    • Tenant data, caches, retrieval indexes, and encryption keys never cross authorization boundaries.
    • Model output is probabilistic; infrastructure guarantees concern lifecycle and provenance, not factual correctness.

    Capacity estimates¶

    Assume 100 million daily users and 20 million prompts/hour at peak, or 5,556 prompt starts/s. Average input is 2,000 tokens and output 500 tokens: approximately 11.11 million input tokens/s and 2.78 million output tokens/s. Their sum is 13.89 million tokens/s, but prefill and autoregressive decode have different costs and cannot be sized as interchangeable output tokens. If one model replica sustains 1,000 output tokens/s under the measured context-length, batching, and latency constraints, decode alone needs about 2,778 replica equivalents before headroom. Prefill compute and KV-cache memory impose additional constraints; tensor parallelism may make one replica span several GPUs. At 4 KB/message metadata, one billion messages/day add 4 TB/day before attachments; 40 messages/conversation imply 25 million conversations/day. KV-cache sizing must specify layers, KV heads, head dimension, precision, and retained tokens rather than relying on a universal bytes-per-sequence constant.

    Core flows and algorithms¶

    Message acceptance and context construction¶

    The API authenticates tenant/user, checks model entitlement and coarse quota, validates bounded content references, then transactionally inserts the immutable user message, generation row, and outbox. Repeated keys with the same request hash return the existing generation; a different hash conflicts. The orchestrator runs input policy and builds context from the selected parent chain.

    Context has a strict token budget. Reserve space for system policy and output, include recent turns, then select older turns or summaries by relevance and recency. Summaries are derived data with source message IDs and summarizer version; they never replace canonical messages. Retrieval chunks include tenant, document ACL, source, version, and relevance score. Recheck ACL at query time and before including content. Prompt assembly is reproducible only with a recorded builder version plus the exact retrieved chunks, authorization decisions, summaries, tokenizer and ordering inputs; the builder version alone cannot recreate mutable retrieval results.

    Inference scheduling and continuous batching¶

    Prefill processes all input tokens and is compute-heavy; decode produces one token per sequence and is memory-bandwidth-heavy. Separate pools or scheduling classes when workload warrants. The scheduler groups requests by compatible model, adapter, precision, and maximum sequence shape. Continuous batching admits new sequences between decode iterations, improving GPU utilization without waiting for an entire batch to finish.

    Use weighted fair queuing across tenants and service tiers, with token-cost estimates rather than request counts. Admission checks available KV-cache blocks, queued token-seconds, deadline, and regional reserve. Reserve capacity for short interactive requests; long contexts cannot monopolize every batch. Under overload, reject low-tier requests with retry hints, cap output, route to a smaller model when policy permits, or degrade retrieval. Never queue beyond the point where the latency SLO is already impossible.

    KV cache uses paged blocks to reduce fragmentation. Prefix caching can reuse common system prompts only when model, tokenizer, exact tokens, policy version, and tenant-sharing classification match. Tenant-private prompt prefixes never enter a global cache. Eviction favors cancelled, over-deadline, and low-priority sequences. Preemption saves block mappings where feasible; recomputation trades compute for memory.

    Workers emit sequence-numbered chunks into a bounded stream buffer. The gateway acknowledges consumption internally and persists periodic chunks or the completed answer depending on product guarantees. A disconnected client reconnects after sequence N if chunks remain; otherwise it receives the durable partial/final text or an explicit non-resumable result. Slow clients cannot block GPU decode: buffer to a limit, then detach the stream while generation continues or cancel according to request policy.

    Cancellation is a versioned flag delivered to scheduler and worker; races may produce a few extra tokens that are metered according to documented policy but not streamed after terminal cancellation. Worker death before a checkpoint can restart the generation, which may produce different text. Expose restarted provenance and a new attempt/stream epoch with explicit replacement or branch semantics. Clients must never concatenate newly sampled text onto an old partial answer or treat reused sequence numbers as the same chunk. The output gateway fences the old attempt before accepting the new epoch.

    Tool execution¶

    The model proposes a typed tool call; the orchestrator validates schema, tenant allowlist, user authorization, argument policy, and budget. Read-only tools execute in network-isolated sandboxes with egress allowlists and time/output limits. Side-effecting tools require confirmation unless preauthorized, receive stable invocation IDs, and should expose idempotency. Persist the invocation ID, canonical argument hash, authorized scope and durable dispatch intent before making the external call; store the result and provenance afterward. An after-the-call audit record cannot recover an ambiguous effect safely. Tool output is escaped and labeled as untrusted to resist prompt injection.

    flowchart TD
 M[Model proposes tool call] --> V[Schema and policy validation]
 V --> A{Side effect?}
 A -->|yes| C[User confirmation or prior grant]
 A -->|no| X[Sandbox execution]
 C --> X
 X --> R[Result size and content filter]

    Loops are bounded by invocation count, wall time, and spend. A tool timeout is not assumed failed if an external side effect may have occurred; reconcile by invocation ID or ask the user before retry. Tool credentials are scoped, short-lived, and unavailable to the model text.

    Retrieval and files¶

    Uploads are malware-scanned, parsed asynchronously, chunked with document/version/ACL metadata, embedded, and written to a tenant-scoped vector index. Hybrid lexical/vector retrieval improves identifiers and names. Retrieve a broad bounded set, enforce ACL, rerank, and include citations. Index freshness is eventual and visible. Deletion tombstones content immediately in ACL filtering, then removes chunks, embeddings, caches, and source objects asynchronously with completion audit.

    Partitioning, scaling, and regions¶

    Partition conversation metadata by tenant and conversation ID in its home region. Object storage holds large content. Stream gateways shard by generation ID and are stateless beyond bounded buffers. GPU pools partition by model/version, hardware, region, and trust class. The scheduler has hierarchical queues: global model capacity, tenant fairness, then request priority. Very large tenants receive reserved pools or quotas to limit noisy-neighbor effects.

    Keep inference near users where model availability and residency allow, but fetch canonical conversation context from the home region or replicate encrypted read views. Enterprise residency may prohibit cross-region routing even during shortage; consumer traffic may opt into fallback. Control-plane model artifacts are signed, staged, and immutable. Rollout uses shadow evaluation, one-region canary, small traffic cohorts, then promotion. Old versions drain existing generations; conversation turns may explicitly cross model versions.

    Regional failure reroutes only eligible tenants. Durable message/outbox state replicates to a paired region with a recovery point objective. A failover epoch fences orchestrators, output gateways and tool dispatch. Generation uniqueness prevents two active lineages only if acknowledged lineage, invocation and idempotency state survived; otherwise pause side effects and reconcile the missing prefix before restart. GPU work in the failed region is lost and may restart non-deterministically; billing reconciliation removes duplicated metering.

    Consistency, idempotency, failures, and recovery¶

    Messages, generation lineage, tool confirmation, and terminal usage records need transactional consistency. Search indexes, summaries, analytics, and feedback are eventual projections. Outbox solves DB/event publication. Consumers deduplicate event IDs. Token streaming is at least once by sequence, so clients replace/ignore duplicate sequence numbers. Side effects depend on tool idempotency, never a platform claim of exactly once.

    Model-worker OOM quarantines the batch, reduces sequence limits, and retries individually only within deadline. GPU loss restarts or fails based on persisted progress. Scheduler partition prevents new admission and leases expire by epoch. Safety-service failure fails closed for disallowed risk classes and may use an approved local classifier for ordinary traffic. Retrieval failure returns an answer labeled without retrieval if product policy permits. Usage pipeline lag does not block bounded prepaid quotas because online reservations reconcile later.

    Reconciliation scans nonterminal generations past lease expiry, completed text without terminal usage, usage without generation, orphaned tool invocations, and deletion tombstones. Replay is scoped by tenant/model/time and cannot silently re-execute side-effecting tools. Disaster recovery tests include artifact registry, tokenizer/config parity, keys, conversation DB, and billing offsets.

    L6 GPU capacity model¶

    Capacity starts from a concrete model profile rather than a generic GPU replica. For P parameters at b bytes per weight, raw weights consume P*b; add quantization scales, runtime workspaces, graph buffers, and 10% to 20% allocator reserve. Tensor parallelism shards tensor operations within layers across GPUs; pipeline parallelism assigns different layer ranges to stages, and data parallelism replicates the serving unit for throughput. The smallest valid serving unit must fit weights plus peak KV cache plus workspace on every rank; losing one rank loses that unit.

    For example, a 70B-parameter model at BF16 needs about 140 GB of weights. On 80 GB GPUs, two-way tensor parallelism nominally leaves 10 GB per GPU after 70 GB of weights, which is too tight for KV and workspace; four-way tensor parallelism leaves about 45 GB per GPU before reserve and is plausible. At INT8 the weights are about 70 GB, so two-way tensor parallelism leaves roughly 45 GB per GPU, but quality and kernel throughput must pass evaluation. Using the 2.78 million output tokens/s demand above and an alternative measured 800 output tokens/s per four-GPU replica, decode needs ceil((20M / 3,600) * 500 / 800) = 3,473 replicas, or 13,892 GPUs before reserve. A 70% utilization target and an additional 10% capacity margin require ceil(3,473 / 0.70 * 1.10) = 5,458 replicas, or 21,832 GPUs. This 10% additive margin is not the same as surviving loss of 10% of installed capacity. Prefill is sized separately: disaggregated pools add their GPU requirements, while a shared pool must pass a joint prefill/decode workload test, not merely take the maximum of two isolated benchmarks.

    KV sizing comes from architecture, not a fixed per-request guess. Without grouped-query attention, bytes per sequence are approximately 2 * layers * hidden_size * bytes_per_element * cached_tokens; with grouped-query attention replace hidden size by KV-head width. A 32-layer model with KV width 1,024 and BF16 uses 2 * 32 * 1,024 * 2 = 128 KiB per cached token. An 8,000-token sequence therefore consumes about 1 GiB; 32 such sequences need 32 GiB before fragmentation. With 16-token, 2 MiB pages and a 40 GiB KV budget, only 20,480 blocks fit, and admission reserves blocks for the promised output rather than hoping decode memory appears later.

    FLOPs bound prefill and decode feasibility. A useful lower-bound estimate is roughly 2 * parameters * tokens per forward pass, excluding attention and communication. A 70B model generating 800 tokens/s requires at least 112 TFLOP/s of useful model work per replica for decode; measured kernels, memory bandwidth, all-reduce, attention growth, and batching determine the real sustainable rate. Capacity tests therefore publish a versioned profile by model, precision, GPU SKU, tensor/pipeline degree, input bucket, output bucket, and latency target. Planning uses p10 measured throughput, not vendor peak FLOPs, and reserves whole serving units because fractional stranded ranks cannot serve the model.

    Token-second admission and KV block scheduling¶

    Each request declares input tokens, maximum output, deadline, tier, model, and residency. The profiler predicts prefill milliseconds and decode tokens/s for its buckets. Use consistent work units: replica_seconds = prefill_replica_seconds + expected_output_tokens / profiled_replica_output_tokens_per_second; multiply each stage by its GPUs/replica when converting to GPU-seconds. This is compute-time accounting, not KV token-seconds, which integrate retained tokens over residence time. Reserve expected work for queueing and quota, but reserve KV blocks for input plus the allowed output cap. Request counts are insufficient because one 100,000-token prompt can cost more than hundreds of short turns.

    Suppose a pool has 100 replicas, each delivering 800 output tokens/s at target latency: raw decode capacity is 80,000 tokens/s. At a 70% utilization target, admit 56,000 tokens/s. If accepted traffic already reserves 48,000 tokens/s, the next scheduling horizon has 8,000 tokens/s left. A request expected to emit 400 tokens over 20 seconds reserves 20 tokens/s of decode rate plus its profiled prefill burst; 400 such requests fill the decode remainder. A queue holding 1.2 million predicted output tokens contains about 1,500 replica-seconds of decode work at 800 tokens/s. With only ten replica-equivalents of spare capacity, it takes about 150 seconds to drain, so a request with a 30-second start deadline is rejected immediately instead of aging in queue.

    The scheduler maintains hierarchical deficit counters for tier, tenant, then request and reconciles measured replica-seconds or GPU-seconds against its work estimates, separately tracking KV token-seconds. Prefill is chunked so a long prompt cannot block decode iterations. A KV allocator reserves logical pages, maps physical blocks only as tokens materialize, applies copy-on-write for shared prefixes, and records (model_version, tenant_scope, block_table_epoch). Decode selects sequences whose next-token step fits compute and available blocks; cancelled and deadline-expired sequences release pages first. Preemption order is over-deadline, best-effort, then largest recomputation-to-progress tradeoff. Interactive capacity and an emergency KV reserve are not borrowable by batch jobs.

  S->>K: materialize input blocks
  S->>G: chunked prefill
  loop Each decode iteration
    S->>K: allocate next-token pages
    S->>G: continuous batch step
    G-->>S: tokens and actual cost
  end
  S->>K: release or retain prefix pages
  S-->>A: reconcile reservation and usage

    Failure operations are explicit. A block leak detector compares scheduler ownership with allocator epochs and fences a suspect worker before reclaim. Fragmentation above a threshold triggers draining, not risky live compaction. Repeated OOM for one shape quarantines that profile and lowers admission while preserving small-request capacity. Alert on predicted-versus-actual token cost, reserved/used KV, block allocation latency, preemption loss, per-tier deficit, deadline rejection, prefilling starvation, decode batch occupancy, and stranded tensor-parallel ranks.

    Serving cells and model rollout guardrails¶

    A serving cell is the blast-radius unit: zonal ingress, admission shard, fair queues, stream gateways, model-serving units, KV managers, local safety classifiers, artifact cache, and telemetry collector. A regional router selects only cells matching model, residency, trust class, and adapter, using signed capacity advertisements with epoch and expiry. Cells do not share live KV state; failover restarts from durable conversation/generation state and is marked non-deterministic. The regional control plane distributes signed artifacts and policy, but a control-plane outage does not mutate an already loaded cell. Separate cells for premium interactive, standard, and batch traffic prevent batch saturation or one tenant adapter from exhausting all regional KV.

    flowchart TD
  R[Regional router] --> C1[Serving cell A]
  R --> C2[Serving cell B]
  CP[Regional control plane] -. signed artifacts and policy .-> C1
  CP -. signed artifacts and policy .-> C2
  C1 --> A1[Admission and fair queues]
  A1 --> G1[GPU serving units and KV blocks]
  G1 --> S1[Safety and stream gateways]
  C2 --> A2[Admission and fair queues]
  A2 --> G2[GPU serving units and KV blocks]
  G2 --> S2[Safety and stream gateways]
  D[(Durable conversation state)] --> C1
  D --> C2

    If a region needs 10,000 serving replicas across five cells, place 2,000 per cell and keep one cell-equivalent of regional failover headroom distributed across zones. Losing a cell then raises surviving utilization from 67% to about 84% when normal load used 6,700 replicas, leaving a narrow but viable degraded mode. Router advertisements expire in seconds; withdrawal stops new sessions, while existing streams drain unless worker safety requires termination. Cell evacuation caps concurrent context rebuilds and prefill traffic so failover does not create a GPU and network retry storm.

    Model rollout promotes an immutable bundle containing weights, tokenizer, chat template, kernels, quantization, safety model, tool schema compatibility, and capacity profile. Stages are offline golden/adversarial evaluation, shadow traffic with outputs discarded, one-cell canary, small sticky user cohort, regional ramp, then global default. Hard gates include artifact signature and checksum, tokenizer parity, deterministic smoke prompts, output schema/tool-call validity, memory headroom, and rollback compatibility. Statistical guardrails compare task quality and safety severity by locale plus p95 first-token latency, inter-token gaps, OOM, tokens/GPU-second, refusal rate, tool errors, user stops, and cost. A severe safety regression, cross-tenant leak signal, or artifact mismatch stops immediately; noisy quality metrics require minimum sample sizes and confidence intervals.

    Rollback changes routing to the previous complete bundle and drains the candidate; it never overwrites loaded weights in place. Conversations record model bundle per generation, so rollback does not rewrite history. New tokenizer or context semantics require compatibility handling at context construction, not mixed ranks in one serving unit. Operators retain enough old capacity until candidate traffic and long generations drain, and rehearse rollback under full load. If the new model needs 25% more KV per token, rollout capacity includes that tax before any traffic shift rather than discovering it through canary OOMs.

    Streaming safety mechanics¶

    Input policy runs before GPU admission. During generation, output is accumulated into small sentence- or token-window buffers and checked by a low-latency local classifier; high-risk domains use a larger holdback window or non-streamed completion. Only approved spans receive monotonically sequenced stream events. The client treats final, blocked, cancelled, and replaced as terminal and discards any later event. A final whole-answer classifier can replace or truncate previously buffered but not yet released text; already emitted text cannot be recalled, so holdback length is a product risk decision rather than a perfect guarantee.

    For example, at 25 tokens/s a 20-token holdback adds about 800 ms before the first releasable span but gives the classifier more context. Standard benign traffic might use a 5-token rolling buffer after initial clearance, while self-harm, sexual, financial, or tool-action contexts use sentence-level buffering or wait for a complete safe response. Classifier timeout fails closed for high-risk traffic; ordinary traffic may fall back to a versioned in-cell model only if policy explicitly permits. If unsafe continuation is detected, stop decode, release KV, emit a terminal blocked event with safe replacement text generated through a separately approved path, persist the hidden unsafe span in restricted audit storage only when retention policy allows, and do not send it through analytics logs.

    Safety versions are pinned for a generation so a mid-stream policy deployment cannot produce contradictory decisions. Emergency deny rules may terminate active generations through a higher policy epoch, with the terminal event recording both versions. Slow safety service backpressure reduces admission before unreviewed buffers grow without bound. Operations monitor classifier latency/timeouts, held-token depth, blocked-after-partial rate, unsafe-token exposure estimate, fallback usage, appeals, locale skew, and policy-version divergence. Chaos tests kill the streaming classifier, reorder token events, disconnect clients before a block, and roll policy epochs during generation; release tests verify that no chunk follows a terminal safety event.

    Security, safety, observability, and testing¶

    Encrypt data, isolate tenant keys and indexes, use short-lived service identities, verify model artifacts, sandbox parsers/tools, prevent SSRF, redact logs, and audit privileged access. Defend against prompt injection, data exfiltration, account abuse, automated scraping, denial through huge contexts, unsafe file formats, tool escalation, and feedback poisoning. Layer input/output classifiers, model alignment, tool policy, rate limits, user reporting, and human escalation. Safety decisions are versioned and appealable where policy requires.

    Observe acceptance, time to first token, inter-token latency, completion latency, tokens/s, prefill/decode utilization, batch occupancy, KV-cache use/fragmentation, queue token-seconds, admission rejection, cancellation waste, stream reconnects, model errors, safety outcomes, retrieval latency/groundedness, tool success/ambiguity, token accounting drift, cost per completion, and fairness by tier. Do not place prompt content in ordinary traces.

    Property-test lineage, idempotency, stream sequencing, ACL precedence, quota reservations, and cancellation races. Golden and adversarial sets evaluate usefulness, safety, hallucination, citation support, bias, and regression by locale. Load-test mixed context lengths and slow clients. Chaos-test GPU death, scheduler failover, artifact corruption, retrieval lag, tool timeout, region loss, and metering duplication. Red-team prompt/tool boundaries. Canary model and policy versions with automated operational and quality guardrails.

    Tradeoffs and final architecture¶

    One large model simplifies quality but wastes cost and capacity; policy-aware routing across models improves economics at consistency cost. Larger batches improve throughput but hurt first-token latency. Persisting every token improves resume but adds write amplification; periodic checkpoints plus final text are usually sufficient. Longer context seems accurate but increases latency/cost and can dilute relevance; retrieval and source-aware summaries win. Global prompt caches save GPU work but create privacy risk; cache only explicitly shareable exact prefixes.

    flowchart TD
 I[Idempotent user message] --> P[Authorization and input policy]
 P --> C[Versioned context and retrieval]
 C --> A[Token-cost admission and fair queue]
 A --> B[Continuous-batched model pool]
 B --> O[Output policy and sequenced stream]
 B --> T[Governed tool loop]
 T --> C
 O --> D[(Immutable conversation lineage)]
 D --> U[Metering, evaluation, audit]

    The final design separates durable conversation lifecycle from expensive, replaceable inference. A policy/context orchestrator prepares authorized prompts; a cost-aware scheduler admits them to versioned GPU pools using continuous batching and paged KV cache. Sequenced gateways stream bounded output. Retrieval and tools are governed subsystems with provenance, ACL, and side-effect controls. Usage, safety, and model changes remain auditable.

    L5 and L6 expectations¶

    An L5 candidate should model immutable conversations and generations, estimate token/GPU load, explain context limits, streaming, batching, quotas, tool isolation, retrieval, failures, and idempotency. They should distinguish probabilistic model quality from infrastructure guarantees.

    An L6 candidate should define safety and side-effect invariants, token-economic admission, model/control-plane rollout, residency, fairness, deletion proof, metering reconciliation, non-deterministic recovery, and degradation policy. They should connect GPU utilization, latency tiers, privacy, evaluation, and organizational governance.

    Five-minute summary¶

    Transactionally accept an idempotent user message into immutable conversation lineage, then authorize, moderate, and assemble a versioned token-bounded context from recent turns, summaries, files, and ACL-checked retrieval. Admit by estimated token-seconds and KV capacity through tenant-fair queues; continuously batch compatible requests on signed model pools. Stream sequence-numbered chunks through bounded gateways and explicitly handle disconnect, cancellation, checkpoint loss, and non-deterministic restart. Validate model-proposed tools, confirm side effects, pass stable invocation IDs, sandbox execution, and treat results as untrusted. Partition conversations by tenant/home region and GPUs by model/trust class. Degrade or reject before queues violate SLOs. Reconcile generations, usage, and tools; measure first-token latency, token rate, queue cost, KV use, safety, groundedness, fairness, and spend. Never promise factual truth or exactly-once external effects.
