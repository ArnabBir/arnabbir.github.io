    Interviewer Packet¶

    Practice home · Prompt · Rubric

    Keep this file hidden from the candidate during a blind-first session.

    Session setup¶

    Choose one mode:

    Mode Candidate design Deep dive/close Feedback after timer
    20-minute screen 16 min 4 min 2 min
    45-minute standard 35 min 10 min 3 min
    60-minute senior 45 min 15 min 5 min
    90-minute loop 45 min 45 min 15 min

    Give the candidate only prompt.md and a blank copy of workbook.md. Do not volunteer scale implications or solution nouns.

    Canonical assumptions¶

    Provide these only when asked:

    • Four channels: push, email, SMS, and in-app.
    • Transactional messages target seconds; campaigns may complete over hours.
    • A recipient can opt out by category and channel; legal suppression overrides promotional traffic.
    • Quiet hours use recipient-local policy where known; security bypass requires explicit classification.
    • Provider callbacks can be duplicate, late, missing, or out of order.
    • Providers have different quotas by route, sender, country, account, and channel.
    • A timeout may occur after provider acceptance.
    • Multi-region residency matters, but a complete consensus design is not required unless chosen as a deep dive.
    • Status must be explainable to tenants without claiming that a human read a message.

    What not to assume for the candidate¶

    • Do not grant exactly-once delivery.
    • Do not imply Kafka, a particular database, or a cloud scheduler is required.
    • Do not accept "use priority queue" as evidence of tenant fairness.
    • Do not equate synchronous provider acceptance with delivery.
    • Do not require the candidate to reproduce the reference architecture.

    Opening script¶

    Design a multi-tenant notification platform using the prompt. Start by clarifying scope and the promises you want the API to make. You own the discussion. I will answer policy questions and may ask you to go deeper on one branch.

    Branching guide¶

    flowchart TD
    A[Candidate frames semantics] -->|Clear| B[Probe scheduling and fairness]
    A -->|Vague| C[Ask what accepted and delivered mean]
    C --> B
    B -->|Mechanism given| D[Inject campaign plus OTP burst]
    B -->|Only priority queue| E[Ask how tenant B progresses]
    E --> D
    D --> F[Provider timeout after submit]
    F -->|Acknowledges ambiguity| G[Probe evidence and reconciliation]
    F -->|Blind retry| H[Reveal late acceptance callback]
    H --> G
    G --> I[Choose policy, incident, or migration branch]

    Core probes and follow-ups¶

    Branch A: Requirements and semantics¶

    Probe: What exactly does the create response guarantee?

    • If candidate says "sent": ask what happens if the process crashes after provider acceptance.
    • If candidate says "accepted": ask where durable acceptance ends and how status evolves.
    • Strong evidence: controlled guarantees, status vocabulary, cancellation boundary, honest uncertainty.

    Branch B: Identity and dedupe¶

    Probe: The producer retries the same request after a timeout, then the queue redelivers it. What collapses each duplicate?

    • If one key handles everything: ask whether two channels should share one attempt.
    • If provider idempotency is assumed: remove provider support.
    • Strong evidence: tenant-scoped request hash, logical intent, unique channel attempt, distinct submission, provider event identity.

    Branch C: Preferences and quiet hours¶

    Probe: A user opts out after a campaign is scheduled but one second before send.

    • If enqueue-time check is final: ask about legal suppression.
    • If every failure retries: make the preference service unavailable.
    • Strong evidence: execution-time recheck, fail-closed promotion, recipient-local time, category-specific bypass with audit.

    Branch D: Priority and fairness¶

    Probe: Tenant A starts 500 million promotions while tenant B sends password resets.

    • If separate queues: ask how tenant C progresses inside the bulk lane.
    • If strict priority: ask whether bulk can starve forever.
    • Strong evidence: reserved capacity, bounded borrowing, fair scheduling, tenant budget, hot-tenant isolation, deadline expiry.

    Branch E: Provider limits and retries¶

    Probe: The provider times out after reading the body.

    • If retry immediately: reveal that 40% later produce accepted callbacks.
    • If never retry: ask about definitely rejected transient failures.
    • Strong evidence: outcome classification, idempotency/status lookup, jitter, retry budget, route-scoped breaker, explicit unknown.

    Branch F: Templates and evidence¶

    Probe: A scheduled legal notice renders differently after a template edit. Can support explain what was sent?

    • Strong evidence: immutable version, typed variables, locale fallback, redacted artifact/evidence, attempt-policy versions.
    • Follow-up: callback arrives before the 2xx response. Look for monotonic convergence.

    Deep-dive selection¶

    Choose the weakest consequential branch first. If all core branches are sound, choose one stretch branch.

    Observed strength Next branch
    Weak semantics Ambiguous provider timeout
    Weak isolation Campaign plus OTP burst
    Weak policy Preference outage during scheduled promotion
    Weak operations Provider slowdown lab
    Strong design Migration cutover
    Strong correctness Callback reorder, reconciliation, replay approval

    Incident injection¶

    Read only this initial clue:

    Provider p95 rose from 220 ms to 8 seconds. Worker CPU is low, but all request slots are occupied. Retry traffic is four times fresh traffic, and urgent queue age is rising.

    Reveal further clues from the failure lab only when the candidate requests relevant telemetry. Evaluate containment before root-cause elegance.

    Expected evidence by level¶

    Level Observable answer
    0 Unsafe claims or disconnected fragments
    1 Component list and shallow happy path
    2 Durable happy path with partial retries and priorities
    3 Coherent identities, current policy, fairness, uncertainty, and operations
    4 Explicit invariants, adversarial timing, controlled recovery, and migration-safe boundaries

    Use rubric.md for scoring and exemplars.md for calibration.

    Red flags¶

    • End-to-end exactly-once claim.
    • One global FIFO or strict-priority queue without starvation/fairness control.
    • Preference checked only at request creation.
    • Latest template rendered for scheduled sends.
    • All provider errors retried identically.
    • Global circuit breaker and unconditional fallback.
    • Provider 2xx labeled delivered.
    • Callback overwrite without event dedupe or state monotonicity.
    • Raw destination/body in normal logs.
    • Unscoped dead-letter replay.

    Positive signals¶

    • Candidate starts from promises and invariants.
    • Estimates burst and attempt volume rather than only daily average.
    • Revises the design after an injected failure.
    • Distinguishes policy facts from pinned content facts.
    • Treats retries as load and cost, not free reliability.
    • Names proof signals such as queue age, expiry-before-send, retry amplification, fairness, and reconciliation lag.

    Closing questions¶

    1. Which invariant would you monitor directly?
    2. What part would you simplify at one-thousandth of this scale?
    3. Which outcome remains unknowable, and how does the API represent it?
    4. What is your safest first migration cohort?
    5. What would make you halt or roll back the rollout?

    Feedback format¶

    Give three evidence-backed statements:

    1. Strongest decision: mechanism and requirement it protected.
    2. Highest-risk gap: concrete failure sequence, not a missing technology name.
    3. Next practice target: one rubric dimension and one exercise from this pack.
