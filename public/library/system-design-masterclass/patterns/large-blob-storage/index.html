    Pattern: Large Blob Storage¶

    Large blobs have different economics and access paths from metadata. A video platform that ingests 2 PB/day, serves originals and renditions globally, and supports resumable upload and deletion cannot treat a 20 GB video like a database row. Bytes need a throughput-oriented object store; ownership, lifecycle, authorization, and processing state need a transactional metadata system.

    When to use and avoid¶

    Use object storage for large, mostly immutable bytes, a metadata database for ownership and state, and a CDN for repeated delivery. Avoid storing blobs in relational rows at scale, proxying all bytes through application servers, and treating a public URL as authorization. A database BLOB can still be reasonable for small objects when atomicity matters more than independent scaling.

    Choice Benefit Tradeoff
    direct signed upload removes API bandwidth bottleneck client protocol and abandoned parts
    multipart upload resumable, parallel chunks manifest and cleanup
    content hash integrity and optional deduplication hashing cost and privacy risk from global deduplication
    CDN edge latency and origin egress reduction invalidation and signed access
    storage tiers lower retention cost restore delay and retrieval fees
    erasure coding lower durable-storage overhead than replication more reads and CPU during repair

    Baseline architecture¶

    1. The metadata API creates an upload record but does not carry the bytes.
    2. It issues scoped multipart URLs for one object key and a short expiry.
    3. The client uploads parts directly and records each part checksum and returned tag.
    4. Finalization verifies the manifest, total size, and root checksum before accepting the asset for processing. Publication waits for the required processing checks to succeed.
    5. A durable event starts malware scanning, media probing, and rendition generation.
    6. Immutable, versioned objects are delivered through a CDN.
    7. Lifecycle and deletion workers reconcile metadata with physical storage.
    sequenceDiagram
    autonumber
    participant C as Client
    participant A as Metadata API
    participant O as Object store
    participant W as Processor
    C->>A: create upload(size, root checksum)
    A-->>C: upload ID and signed part URLs
    loop Every part
        C->>O: PUT part with checksum
        O-->>C: part tag
    end
    C->>A: finalize(upload ID, manifest)
    A->>O: complete and verify object
    A->>W: durable processing event
    W->>O: write immutable renditions

    Metadata states are PENDING_UPLOAD -> FINALIZING -> PROCESSING -> READY | FAILED, followed by DELETING -> DELETED when eligible. Only READY is visible. Object keys must be access-controlled; unguessability alone is not authorization. Signed URLs are short-lived and scoped to a method, object, content length where supported, and optionally checksum.

    Worked multipart upload¶

    Choose part size from object size, object-store part-count limits, retry cost, memory, and desired concurrency. Suppose a 20 GiB file uses 64 MiB parts:

    parts = ceil(20 * 1024 MiB / 64 MiB) = 320
parallelism = 8
ideal upload time at 400 Mbit/s = 20 * 2^30 B * 8 / 400,000,000 bit/s
                               = about 429.5 s

    The client persists {upload_id, object_key, part_size, completed_parts} locally. Each worker reads one part, calculates SHA-256 while streaming, and sends part_number, Content-Length, and checksum. It retries only failed parts with exponential backoff and jitter. A resume call lists server-accepted parts and compares both length and checksum rather than trusting local state.

    Finalization is a business-level idempotent operation:

    finalize(uploadId, expectedVersion):
  short transaction: validate tenant, manifest hash and expectedVersion
  if already finalized with same manifest: return existing assetId
  CAS PENDING_UPLOAD to FINALIZING; persist manifest and object key
  outside transaction: reconcile existing completed object first
  if not already completed:
    paginate listParts for verification against saved part receipts
    require verified size and part checksums match declared manifest
    completeMultipartUpload(saved manifest, conditional create)
  verify completed object version, checksum and size
  transaction: CAS FINALIZING to PROCESSING; append AssetCreated once
  return assetId

    The object store may expose a multipart ETag that is not the SHA-256 of the complete object. Never infer integrity from an undocumented ETag format. Store an explicit whole-object checksum or a checksum tree root.

    S3's multipart contract says completed parts no longer exist, listings are paginated, and the completion manifest should come from saved upload receipts, not a listing. If completion succeeds but its response is lost, reconcile the exact immutable object and upload metadata before retrying; absence of the upload ID is not proof of failure. FINALIZING recovery must be leased/fenced, and no database row lock spans remote I/O (accessed 2026-09-08).

    Checksum tree¶

    A checksum tree verifies parts independently and permits parallel recomputation. For a new protocol, separate leaf and parent domains: hash each part as SHA256(0x00 || part_bytes) and each parent as SHA256(0x01 || left_hash || right_hash), duplicating or promoting the final unpaired leaf according to one documented convention. The client sends leaf hashes and the root; the service stores the root in canonical metadata.

    flowchart BT
    P1[Part 1 hash] --> H12[Hash 1 and 2]
    P2[Part 2 hash] --> H12
    P3[Part 3 hash] --> H34[Hash 3 and 4]
    P4[Part 4 hash] --> H34
    H12 --> R[Root checksum]
    H34 --> R

    For four 64 MiB parts with hashes h1..h4, compute a = H(0x01 || h1 || h2), b = H(0x01 || h3 || h4), and root = H(0x01 || a || b). During repair, a mismatching root triggers comparison down the tree to identify the corrupt part without rereading healthy replicas. Bind tree metadata to algorithm, part size, object length, and leaf count; otherwise two implementations can calculate incompatible roots.

    Encryption must not invalidate the integrity model. Transport checksums protect upload transit. A plaintext content hash detects logical equality but exposes confirmation attacks when used for cross-tenant deduplication. A ciphertext checksum verifies stored bytes. A safe default is per-tenant deduplication, server-side encryption with a key reference in metadata, and separate plaintext and ciphertext integrity fields where the threat model permits them.

    Range reads and media delivery¶

    Large-object clients should not fetch an entire object to seek or resume. A download endpoint validates authorization, resolves the immutable version, and either redirects to a signed CDN URL or serves a signed origin request. It supports Range: bytes=start-end, returns 206 Partial Content, Content-Range, Accept-Ranges: bytes, and a stable ETag. An unsatisfiable range returns 416 with the object length.

    For a 10 GiB object and Range: bytes=1048576-2097151, return exactly 1 MiB. Cap the number of ranges and reject pathological multi-range requests that amplify origin work. If compression changes byte offsets, store a precompressed representation as a separate immutable object rather than applying dynamic compression to arbitrary ranges. Clients send a strong version validator in If-Range. A mismatch makes the server return the full representation instead of the requested partial range; the client must restart or replace its download, never append that 200 body to old bytes.

    flowchart LR
    C[Authorized client] --> E[CDN edge]
    E -->|cache hit range| C
    E -->|cache miss| S[Signed origin request]
    S --> O[(Immutable object)]
    O --> S
    S --> E
    M[Metadata API] -->|short-lived signed URL| C

    Use versioned paths such as /asset/{asset_id}/rendition/{version} so normal publication never requires purge. The CDN cache key must include the rendition identity and every representation-changing dimension, but not incidental authorization query parameters. Signed cookies suit many segments under one entitlement; signed URLs suit one object. Keep origin private so bypassing the CDN does not bypass access control. Track byte hit ratio in addition to request hit ratio because a few large misses dominate egress.

    Validate authorization before every cache hit if immediate revocation is promised. Merely stopping issuance of signed URLs leaves existing bearer URLs usable until expiry. Otherwise state that revocation is bounded by token lifetime and cache policy; purge alone is not proof that every edge has stopped serving bytes.

    Erasure coding and durability¶

    Three full replicas cost 3x raw capacity and make reads and repair simple. A Reed-Solomon 10+4 layout splits data into ten data shards and four parity shards, stores them across distinct failure domains, and reconstructs the object from any ten shards. Its raw overhead is 14/10 = 1.4x, excluding metadata and temporary repair space.

    For a 1 GiB stripe group, each shard is roughly 102.4 MiB. Loss of up to four shards remains recoverable, but degraded reads fetch more fragments and consume decode CPU. Durability depends on independent placement and repair time, not merely parity count. Never place all fragments in one rack or power domain. A placement policy should select region, zone, rack, then host; a repair controller should rate-limit reconstruction so a zone loss does not collapse foreground traffic.

    Use replication for hot small objects, write-heavy staging, or low-latency reads. Convert sealed, colder objects to erasure coding asynchronously. During conversion, write and verify the coded generation, atomically switch the metadata generation, then garbage-collect replicas. Keep enough free capacity for the largest credible rebuild. Scrub stored checksums continuously, prioritize repairs by remaining fault tolerance, and test loss of an entire placement domain.

    Deletion lifecycle¶

    Deletion is a distributed workflow, not one DELETE call. Define the user-visible guarantee separately from physical erasure and backup expiry.

    stateDiagram-v2
    [*] --> READY
    READY --> DELETING: authorized delete
    DELETING --> HIDDEN: tombstone committed
    HIDDEN --> PURGING: retention hold cleared
    PURGING --> DELETED: all objects confirmed absent
    note right of PURGING
      Retry incomplete purges in this state.
    end note
    DELETED --> [*]

    An authorized delete transaction writes a tombstone and outbox record. Reads reject the asset immediately, CDN tokens stop being issued, and policy filters block any stale index or inbox entry. The purge worker enumerates the original, every rendition, incomplete multipart upload, replica or erasure generation, CDN key, and derived analysis artifact from an asset manifest. Deletes are idempotent: absence counts as success. It records per-location evidence and retries transient failures.

    Legal holds pause physical purge without restoring visibility. Versioned object stores require deleting every version and delete marker, not only the current version. Replication queues can resurrect data if a stale create arrives after delete, so both events carry monotonically increasing asset versions and destinations retain tombstones through maximum replay age. Backups expire by documented retention; the product should say "unavailable immediately, purged from active storage within 24 hours, expired from backups within 30 days" only when entitlement checks enforce that visibility boundary, rather than promise instantaneous physical destruction.

    A daily reconciler starts from both directions. Metadata-to-storage checks that every READY asset has its declared generation. Storage-to-metadata inventory finds unreferenced objects older than a safety delay. It quarantines before deleting when ownership is ambiguous. Report deletion age by stage and page on records beyond the contractual deadline.

    Failure semantics and operations¶

    Failure Recovery
    interrupted part upload list verified parts and resume; expire and abort abandoned uploads
    finalize response lost idempotent finalize returns the same asset
    processor retry deterministic rendition key and conditional create prevent duplicates
    metadata committed but blob absent hide asset, mark failed, and reconcile from the outbox
    corrupt shard checksum identifies it; rebuild from surviving fragments into a new placement
    CDN serves deleted content deny at entitlement layer, purge as defense in depth, rotate signing key only for broad compromise
    regional store unavailable fail or route according to explicit residency policy; never silently cross a boundary
    delete partially completes tombstone remains authoritative while asynchronous retries continue

    Operational procedures should be rehearsed. For upload failures, inspect completion latency, object-store error codes, and abandoned-part bytes; disable only the unhealthy region and preserve upload IDs if recovery is possible. For corruption, freeze lifecycle transitions, identify affected generations from checksum alarms, reconstruct to new keys, verify roots, and conditionally switch metadata. For a signing-key leak, revoke the key identifier, shorten cache authorization, issue a replacement, and audit object access; renaming every object is usually unnecessary.

    Keep checksum algorithm and root, size, sniffed MIME type, encryption key reference, owner, retention class, object version, placement generation, and processing lineage in metadata. Scan untrusted content before publication. Measure orphan bytes, checksum failures, finalize latency, processing age, repair backlog, CDN byte hit ratio, origin egress, storage overhead, incomplete upload age, and deletion completion age.

    Design checklist¶

    • Define maximum object size, part limits, retry budget, and finalization idempotency.
    • Distinguish transport, plaintext, ciphertext, and tree checksums.
    • Make object names immutable and CDN authorization explicit.
    • Specify byte-range behavior, version validators, and abuse limits.
    • Choose replication or erasure coding from latency, repair, and failure-domain requirements.
    • Inventory every derivative and version in deletion scope.
    • Test reconciliation, restore, corruption repair, regional isolation, and expired credentials.

    Interview prompts¶

    • Why are metadata and bytes separate sources with different semantics?
    • How is an upload resumed and finalized exactly once at the business level?
    • How does the checksum tree isolate a corrupt part?
    • When does 10+4 erasure coding lose to three replicas?
    • What does deletion guarantee while backups still retain bytes?
    • How do range requests and signed CDN access prevent cross-tenant exposure?
