    Pattern: Scaling Writes¶

    Write scaling is constrained by coordination, durable I/O, indexes, replication, and hot keys. Adding application servers does not make a storage engine flush disks faster or let two leaders safely assign the same sequence number. Consider telemetry ingestion growing from 2,000 to 500,000 events/s while preserving per-device ordering and acknowledging only data that can survive one node loss. The design must define what an acknowledgment means, where ordering applies, and how much delayed visibility is acceptable.

    When to use and avoid¶

    Use batching for amortizable independent records, partitioning for key-local operations, and durable logs for buffering and replay. Avoid asynchronous acknowledgment when the caller needs the committed result, sharding before removing unnecessary indexes, and random sharding when reads need key locality. First reduce work per logical write; then add parallelism.

    Technique Gain Cost
    batch/append amortized fsync and network queueing delay and partial outcomes
    remove synchronous derived writes shorter critical path projection lag
    partition by entity parallel writes, local ordering skew and rebalancing
    durable ingestion log absorbs bursts backlog and duplicate delivery
    preallocated rights local constrained writes allocation and rebalance complexity

    Start with the write contract¶

    Separate four milestones that teams often call "written": accepted by a process, appended to a leader, replicated durably, and visible in query projections. A response after a quorum log append means durably accepted, not necessarily queryable. Return an ingestion ID and publish a visibility SLO such as p99 under 10 seconds. If a balance update must be read-your-write consistent, route that operation to the authoritative store rather than weakening language around eventual visibility.

    Ordering should also be scoped. Global ordering forces all traffic through one sequencer. Per-device ordering requires records for one device_id to reach one ordering authority and carry a monotonic sequence within a producer epoch. The authority must reject duplicates, detect gaps, and define how rebooted devices obtain a new epoch. Partition placement alone orders arrival, not the intended order of concurrent or retried sends. Independent devices can proceed in parallel. Idempotency keys must identify the logical event, not an individual attempt, so a timed-out producer can safely retry.

    Fsync, batching, and group commit¶

    An fsync asks the operating system and storage device to make prior writes durable. If each event causes one 0.8 ms flush, a single serial log can perform at most about 1 / 0.0008 = 1,250 flushes/s, regardless of spare CPU. Group commit turns many logical events into one durable flush. With a 5 ms batch window and 2,500 events arriving in that window, one flush amortizes its latency across all 2,500 acknowledgments.

    Use two batch triggers: maximum records or bytes, and maximum age. A writer can collect up to 4,000 records or 5 ms, append one contiguous block, flush, then resolve each record's promise. The age trigger bounds quiet-period latency; the size trigger bounds memory and request size during bursts. Never leave a partially filled batch waiting indefinitely.

    Worked ingestion budget¶

    Assume 500,000 events/s, each 600 bytes after encoding. Raw ingress is 300 MB/s. With replication factor 3, the log writes roughly 900 MB/s across brokers before overhead. Across 20 balanced partitions, each receives 25,000 events/s and 15 MB/s. A 5 ms partition-local window collects about 125 records, so each partition produces about 200 batches/s and the fleet 4,000. Collecting 2,500 records per partition instead takes about 100 ms, not 5 ms. If network plus quorum flush p99 is 12 ms, the 5 ms collection design budgets approximately 17 ms plus queueing; validate the end-to-end percentile.

    PostgreSQL's WAL description confirms that one flush may commit multiple transactions. It does not imply one global batch across independent partition logs. Measure flush coalescing and batch occupancy per log (accessed 2026-09-08).

    This calculation exposes the real bottleneck. A cluster with aggregate disk bandwidth below 900 MB/s cannot meet the target just by increasing batch size. Provision headroom for compaction, recovery, and one-node loss; at 60% steady-state utilization, required aggregate sequential write capacity is about 900 / 0.60 = 1.5 GB/s.

    Batch results require per-item semantics. Validation failures can be rejected before append. Once a mixed batch is durably appended, downstream storage may partially succeed. Persist event IDs and report ingestion acceptance independently from projection status rather than pretending the entire end-to-end batch is atomic.

    Replication and acknowledgments¶

    Replication factor and acknowledgment policy determine durability and availability. Leader-only acknowledgment is fast but may lose acknowledged writes if the leader dies before replication. Quorum acknowledgment waits for enough replicas that one failure cannot erase the committed prefix. Requiring every replica makes a slow or unavailable replica block progress. It can increase the number of durable copies at acceptance, so evaluate that added protection against the named failure model rather than assuming it is free or always necessary.

    The leader must fence stale leaders using a term or epoch. Followers reject stale terms and update leadership state according to the protocol, and a new leader commits only after satisfying the consensus protocol's quorum rules. Client retries still produce duplicates when the response is lost, so consensus does not remove the need for application idempotency.

    flowchart LR
    D[Devices] --> A[Admission and validation]
    A --> L[(Replicated partitioned log)]
    L --> W1[Batch writer]
    L --> W2[Realtime projection]
    W1 --> S[(Sharded store)]
    W2 --> C[(Current-state cache)]
    S --> O[Outbox for derived work]
    O --> I[Index and notification workers]

    During a follower outage, continue only if the in-sync replica policy still satisfies the promised failure tolerance. Otherwise reject or pause rather than silently downgrade durability. Track replica lag in bytes and time. A replica 100 GB behind can consume enough disk and network during catch-up to destabilize healthy traffic, so throttle recovery and reserve bandwidth for it.

    Write amplification¶

    One 600-byte event rarely costs only 600 bytes. Define write amplification as physical bytes written across the system divided by logical bytes accepted. Sources include replication, write-ahead logs, database pages, secondary indexes, compaction, outbox rows, and projections.

    For 300 MB/s logical ingress, suppose log replication contributes 3x, an LSM database averages 4x compaction amplification on each projection byte, and two projections each store 40% of the source payload. The log writes 900 MB/s. Projection logical traffic is 300 * 0.8 = 240 MB/s; with WAL plus compaction approximated at 5x, one copy writes 1.2 GB/s. Total with single-copy rebuildable projections is 2.1 GB/s, or 7x; with three projection copies it is 0.9 + 1.2*3 = 4.5 GB/s, or 15x, before backups. Removing an index storing 20% of source size at 5x saves 300 MB/s per copy.

    Measure amplification rather than assuming it. Compression lowers bytes but costs CPU. LSM compaction improves append throughput but creates background I/O and tail-latency spikes. B-tree updates may perform random page writes and page splits. Select storage around workload and SLO, not a generic claim that one engine is always faster.

    Move search indexes, analytics, and notifications behind an outbox or committed log when they need not participate in the primary invariant. Keep uniqueness and balance constraints in the authoritative transaction. The outbox row and business mutation commit atomically; a relay publishes at least once, and consumers deduplicate by event ID.

    Partitioning and hot keys¶

    Hash partitioning distributes ordinary keys well, but traffic distribution matters more than key count. If one device emits 10% of 500,000 events/s, its 50,000 ordered writes/s still land on one partition. First determine whether that device truly needs one ordered stream. If ordering is only per sensor channel, partition by (device_id, channel_id). If strict per-device order is required, one owner must serialize the stream; optimize that path or impose a producer quota.

    Ordered epochs can split a hot entity only at explicit boundaries. A coordinator closes epoch 41 at sequence 8,000, assigns epoch 42 to another partition, and records the handoff durably. Readers concatenate closed epochs in order. Never hash individual events randomly and hope timestamps reconstruct causality.

    stateDiagram-v2
    [*] --> Stable
    Stable --> Copying: create target shard
    Copying --> CatchingUp: bulk snapshot complete
    CatchingUp --> DualRead: replay reaches watermark
    DualRead --> Cutover: fence source and replay final position
    Cutover --> Stable: routing epoch advanced
    Copying --> Aborted: validation or capacity failure
    CatchingUp --> Aborted: lag exceeds limit

    Repartitioning without losing writes¶

    Consistent hashing reduces movement when adding shards, but movement is still a production operation. Use versioned routing and an explicit migration state machine:

    1. Create target partitions and reserve capacity.
    2. Copy an immutable snapshot from source at watermark W.
    3. Stream changes after W to the target using event IDs and source sequence numbers.
    4. When lag is small, shadow-read or checksum ranges and compare counts and hashes.
    5. Gate and drain source writes, durably fence the old owner, record its final committed position, and verify target replay through it. Install the new epoch at the write guard before advancing routing and enabling target writes.
    6. Keep source data fenced through a rollback window. After target writes begin, rollback must gate and fence the target, reverse-replay its accepted tail to the old replica set, verify a final watermark, and grant a fresh epoch. A frozen source copy alone is not a safe rollback target. Delete retired copies only after that window.

    Dual writing from an application to old and new shards creates an atomicity gap. Prefer one authoritative write plus change-data capture. If dual writes are unavoidable, record repairable intent and continuously reconcile. During cutover, requests carrying a stale routing epoch receive a redirect or retryable error; they must not commit to the retired owner.

    Migration traffic competes with foreground writes. Rate-limit snapshot scans, cap catch-up bandwidth, and pause movement when fsync p99 or replica lag crosses a threshold. Move small ranges first and avoid migrating many hot partitions simultaneously.

    Overload and failure semantics¶

    Backpressure must propagate before memory queues fill. Admission should enforce global capacity, per-tenant rates, and bounded outstanding bytes. A token bucket allows a documented burst while protecting sustained capacity. If persistence can drain 450,000 events/s and arrivals remain at 500,000/s, backlog grows by 50,000 events/s: 180 million events per hour. At 600 bytes, that is 108 GB/hour before replication. A six-hour retention buffer only postpones failure unless operators add capacity or shed load.

    Failure Outcome
    timeout before log acknowledgment outcome unknown; retry the same event ID
    worker crashes after database commit redelivery; event ID deduplicates
    shard unavailable affected partitions pause; queue age grows
    tenant burst tenant quota rejects with a retry hint
    backlog approaches retention reject before accepting data that cannot be retained
    disk full stop leaders or affected partitions; never acknowledge volatile-only writes
    stale routing client fence by routing epoch and refresh ownership

    Use 429 for quota rejection and 503 for unavailable durable capacity, with bounded Retry-After guidance. Prefer shedding low-priority telemetry over violating high-priority audit durability. If product policy permits sampling, label sampled data explicitly and perform it before acknowledgment.

    Evolution path¶

    1. Begin with one transactional store and conditional writes for invariants.
    2. Batch noninteractive inserts and remove unnecessary synchronous indexes.
    3. Put notifications and projections behind a transactional outbox.
    4. Add a replicated ingestion log when bursts exceed database capacity.
    5. Partition log and storage by the narrowest key that preserves required ordering.
    6. Add per-tenant admission, online repartitioning, and automated skew detection.

    Each step should solve a measured limit. A log adds operational cost and eventual consistency; it is not automatically an improvement at 2,000 writes/s. Before sharding, load-test the current store with realistic index count, durability settings, record sizes, and skew.

    Observability and verification¶

    Monitor accepted, committed, and projected rates separately; oldest unprojected event age; batch fill ratio; batch wait; fsync p50/p99; quorum latency; replica lag; partition skew; duplicate rate; disk utilization; compaction debt; and physical bytes per logical byte. Alert on leading indicators such as rising queue age and fsync latency, not only dropped writes.

    Test crash points: before append, after leader flush but before response, after projection commit but before offset commit, and during routing cutover. Verify that retries neither lose events nor repeat external effects. Run a node-loss capacity test at target load, because a cluster that works only with every replica healthy has no usable failure margin.

    L5 and L6 guidance¶

    An L5 design should quantify average and peak logical throughput, choose an acknowledgment boundary, define ordering and idempotency scope, estimate batch and partition counts, and explain one safe failure path. It should distinguish durable acceptance from query visibility and identify the final invariant-enforcing write.

    An L6 design should model amplification and degraded-mode capacity, challenge whether ordering can be narrowed, and describe repartitioning as a versioned online protocol rather than "add shards." It should set overload priorities, recovery bandwidth, migration abort thresholds, and observability tied to error budgets. The key senior judgment is knowing which work stays synchronous for correctness and which work can become replayable asynchronous state.

    Interview prompts¶

    • What exactly does the producer acknowledgment guarantee?
    • Which ordering scope is required, and what parallelism does it permit?
    • How do retries avoid duplicate external effects?
    • How would one device producing 10% of writes be isolated?
    • What is the estimated physical write rate after replication and compaction?
    • How are stale writers fenced during a shard cutover?
