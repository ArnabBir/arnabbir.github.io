    AI Reliability, Capacity, and Cost¶

    AI reliability is the ability to produce acceptable outcomes within latency, safety, and cost constraints despite variable token lengths, scarce accelerators, provider limits, dependency failures, and model changes. Capacity and cost are part of the reliability design because overload and budget exhaustion change user-visible behavior.

    Service contract and invariants¶

    Define separate objectives for admission, completion, latency, quality, and recovery. A server that accepts work it cannot complete is not reliable.

    Invariants¶

    1. Admission uses the constrained resource vector, not request count alone.
    2. Queues, context, output, retries, tool calls, wall time, and spend are bounded.
    3. Fallback preserves task, data-class, safety, and compatibility requirements.
    4. Reserved recovery capacity is not consumed by best-effort or shadow work.
    5. Capacity numbers come from a declared benchmark distribution and safe operating envelope.
    6. Cost is attributed to logical outcomes and attempts without hiding failed or wasted work.
    7. Correlated provider, region, model, feature, and index failures are modeled explicitly.

    Demand and capacity flow¶

    flowchart LR
    A[Forecast and live arrivals] --> B[Classify workload]
    B --> C[Estimate tokens memory and tools]
    C --> D[Quota and admission]
    D --> E[Bounded class queue]
    E --> F[Scheduler and batcher]
    F --> G[Serving or job pool]
    G --> H[Usage and outcome]
    H --> I[Capacity and cost model]
    I --> A
    D -->|reject or defer| J[Explicit degraded contract]

    Workload resource contract¶

    DemandEstimate(
  workload_class, arrival_rate, burst_shape,
  input_token_distribution, output_token_distribution,
  context_bytes, kv_bytes_per_token, accelerator_seconds,
  cpu_seconds, storage_bytes, network_bytes,
  tool_calls, deadline, priority, max_attempts, spend_limit
)

    Use distributions or buckets for prompt length, output length, batch shape, and tool steps. Means alone hide the tail that consumes memory and misses deadlines.

    {
  "workload_class": "interactive-generation",
  "deadline_ms": 2500,
  "limits": {
    "input_tokens": 8000,
    "output_tokens": 700,
    "attempts": 2,
    "tool_calls": 0,
    "cost_minor": 12
  },
  "fallback_policy": "same-task-same-residency-v3",
  "priority": "customer-interactive"
}

    Core calculations¶

    Token demand and concurrency¶

    For arrival rate lambda requests/s:

    input_tokens_per_second = lambda * mean_input_tokens
output_tokens_per_second = lambda * mean_output_tokens
mean_concurrency = lambda * mean_end_to_end_seconds

    At 120 requests/s, 3,000 input tokens, 400 output tokens, and 2.2 seconds mean latency:

    input demand  = 360,000 tokens/s
output demand = 48,000 tokens/s
concurrency   = 264 requests

    Little's Law estimates the stable mean. It does not supply burst, tail, zone-loss, maintenance, or safety reserve.

    KV-cache memory¶

    For a decoder with L layers, two key/value tensors, Hkv key/value heads, head dimension D, sequence tokens T, and bytes per element B:

    KV_bytes_per_sequence = 2 * L * Hkv * D * T * B

    This is an architectural estimate. Runtime paging, block allocation, quantization, tensor parallelism, and prefix sharing change observed memory. Measure the exact runtime and model.

    For L=32, Hkv=8, D=128, T=8,192, and two-byte elements, one full-length sequence needs 2 * 32 * 8 * 128 * 8,192 * 2 = 1,073,741,824 bytes, or 1 GiB of logical KV storage. Sixty-four such sequences need 64 GiB before model weights, activations, fragmentation, and runtime reserve. This is the aggregate logical cache across the model, not necessarily the allocation on each device in a sharded runtime. Use KV heads, not query heads: substituting 32 query heads into this grouped-query example would overestimate the logical cache fourfold.

    Queue growth and drain¶

    queue_growth_per_second = max(0, arrival_rate - service_rate)
drain_time = queued_work / (service_rate - arrival_rate)

    These are constant-rate fluid approximations with no abandonment or shedding. Drain time is finite only when service exceeds continuing arrivals; at equal rates backlog persists, and below them it grows. When work is heterogeneous, use comparable service-work units or separate class queues rather than treating a 50-token response and a 5,000-token response as equal jobs.

    If arrivals are 900 requests/s and degraded capacity serves 700/s for 60 seconds, the queue adds 12,000 requests. After recovery at 1,100/s while arrivals remain 900/s, drain time is 12,000 / 200 = 60 seconds. If deadlines are shorter, reject early; a queue is not recovery capacity.

    Cost per accepted result¶

    provider_cost
= uncached_input_tokens * uncached_input_rate
 + cache_read_input_tokens * cache_read_rate
 + cache_write_input_tokens * cache_write_rate
 + output_tokens * output_rate
 + tool_and_storage_cost

cost_per_accepted_result
= (provider_cost + allocated_platform_cost) / accepted_results

    The token categories in this cost equation are mutually exclusive. If provider-reported total input already includes cached tokens, subtract its cache subsets before applying the uncached rate. Track failed attempts, shadows, warm reserve, idle accelerators, and review labor separately before allocation. A cheap model with high retries or low acceptance can be more expensive per useful outcome.

    State whether each rate is dollars/token or dollars/million tokens; divide counts by one million for the latter. The equation assumes cache-write prices are full category prices, not surcharges, and one output rate. If reasoning or modalities have separate prices, partition them without double-counting provider totals. The OpenTelemetry usage registry, verified 2026-09-08, specifies cached input and reasoning output as subsets of totals; it is a telemetry convention, not a provider billing contract. Report cost per accepted result as undefined when there are no accepted results, alongside the accumulated spend.

    Capacity envelope and admission¶

    Benchmark each compatible model/runtime/hardware/batch combination with production-shaped length and concurrency distributions. Sweep offered load. Record goodput, time to first token, inter-token latency, end-to-end tails, queue age, memory, utilization, errors, quality, and cost.

    The safe operating point ends before latency becomes unstable or memory safety margin disappears. Define:

    usable_capacity_per_replica
= benchmark_goodput_at_SLO * target_utilization

replicas_for_traffic
= ceil(peak_goodput_required / usable_capacity_per_replica)

    Here target_utilization is a planning derating fraction of the measured SLO-goodput envelope, not the GPU utilization percentage reported by a device. If the benchmark already included the same reserve, do not subtract it twice. Goodput counts acceptable on-time results; offered throughput, completed throughput, and GPU busy time are different measurements.

    Admission reserves estimated tokens, KV bytes, tool calls, and spend. Reconcile reservation with actual use on completion. Overestimation reduces utilization; underestimation can violate isolation. Use class- and tenant-specific correction factors from measured error.

    Resilience and fallback¶

    stateDiagram-v2
    [*] --> Healthy
    Healthy --> Constrained: saturation or dependency loss
    Constrained --> Degraded: safe fallback active
    Constrained --> Shed: no compatible fallback
    Degraded --> Recovering
    Shed --> Recovering
    Recovering --> Healthy: queues drained and SLO stable
    Recovering --> Constrained: relapse
    Failure Safe response Required reserve/evidence
    one replica retry within original deadline spare concurrency and idempotency
    one zone evacuate to remaining zones N+zone measured capacity
    one region policy-approved route or async defer residency and feature/index readiness
    provider quota alternate approved route or shed tested compatibility and quota headroom
    model defect warm previous bundle canary trigger and rollback
    retrieval outage abstain or approved no-RAG behavior answerability and safety evaluation
    cost ledger lag bounded low-risk buffer or reject reconciliation and spend reserve

    Fallback capacity is shared incident capacity. Simultaneous failures and retries can overwhelm it. Model receiver headroom after removing the failed domain and adding retry amplification.

    Multi-provider portfolio¶

    Do not assume two providers are independent when they share model weights, upstream networks, identity, regions, or a common gateway. Record concentration by demand, data class, model capability, and evacuation readiness.

    flowchart TD
    A[Task and data class] --> E[Common gateway]
    E --> B{Approved routes}
    B --> C[Provider A region 1]
    B --> D[Provider B region 2]
    F[Quota and health] --> B
    G[Compatibility evidence] --> B
    H[Spend policy] --> B

    An evacuation drill must preload artifacts, warm capacity, verify prompt and structured-output compatibility, validate safety and quality, shift bounded traffic, and measure receiver saturation. A configured fallback that cannot carry traffic is documentation, not resilience.

    Reliability and economic state¶

    CapacityPool(id, region, failure_domain, hardware, runtime,
             compatible_bundles, measured_curve, reserved, observed)
CapacityReservation(id, tenant_or_class, pool, quantity,
                    start, end, priority, state)
Admission(id, logical_request_id, estimate, reservation,
          decision, reason, expires_at)
Usage(id, logical_request_id, attempt_id, meter, quantity,
      source_sequence, time_window)
CostAllocation(id, usage_ids, price_version, shared_cost_policy,
               amount, outcome_class)

    Desired, reserved, allocatable, loaded, ready, busy, and healthy capacity are different numbers. Publish all of them with reason codes.

    Failure, security, and testing¶

    Failure Test Pass condition
    burst beyond forecast open-loop load bounded queue and explicit shedding
    long-context skew adversarial length mix tenant fairness and memory safety
    retry storm dependency fault attempt budget preserved
    zone loss remove full failure domain critical SLO within declared degraded objective
    cold fallback evacuation drill measured recovery time and no policy bypass
    cost runaway output/tool amplification spend limit stops new work safely
    capacity telemetry stale freeze allocator inputs conservative admission and alert

    Load tests must use open-loop arrivals; a closed-loop client can hide overload by waiting. Run soak tests for leaks and fragmentation. Inject cancellations, provider 429/5xx, slow streams, model load failure, scheduler delay, spot loss, feature/index lag, and metering gaps.

    Protect capacity APIs and priority changes with separate administrative authorization. Prevent tenants from selecting internal routes, forging token estimates, or consuming health lanes. Rate-limit expensive validation and reject oversized contexts before provider spend.

    Migration and evolution¶

    1. Add a new route as shadow-only and benchmark it against the same workload fixture.
    2. Validate task, schema, safety, latency, data handling, and cost compatibility.
    3. Pre-provision bounded receiver capacity and canary a stable cohort.
    4. Dual-meter old and new routes and reconcile logical outcomes.
    5. Increase traffic while preserving rollback and failure reserve.
    6. Retire old capacity only after incident, paused-workflow, and rollback windows close.

    For a model or runtime change, rebuild service curves. Old throughput numbers do not transfer automatically.

    Interview exercise¶

    Design capacity and reliability for a customer assistant with 1,500 peak requests/s, 6,000-token p95 input, 700-token p95 output, two providers, three zones, and a 2.5-second p95 objective. One provider can lose quota and one zone can fail. Calculate token demand, mean concurrency from stated assumptions, queue growth during failure, receiver capacity, and cost per accepted result. Define admission, degraded modes, evacuation evidence, fairness, and migration.

    L5 and L6 signals¶

    L5¶

    • Uses token, memory, concurrency, queue, and cost units correctly.
    • Derives capacity from measured goodput at an SLO, not peak throughput.
    • Bounds admission, retries, context, output, and spend.
    • Defines compatible fallback, zone reserve, and explicit shedding.
    • Tests bursts, long contexts, cancellations, failures, and metering.

    L6¶

    • Governs capacity classes, reservations, fairness, exceptions, and evidence across products.
    • Quantifies correlated provider/region failure and receiver headroom.
    • Connects quality, accepted outcomes, warm reserve, review load, and margin.
    • Establishes migration and retirement policy for model/runtime service curves.
    • Assigns forecast, benchmark, evacuation, and cost-allocation ownership.

    Final design checklist¶

    • Workload distributions and constrained resources are explicit.
    • Queues reject work that cannot meet its deadline.
    • Safe operating envelopes include quality and cost.
    • Failure reserve cannot be consumed by best-effort work.
    • Fallback preserves data class and task semantics.
    • Retry and tool amplification are included.
    • Costs join logical outcomes and failed attempts.
    • Evacuation and recovery are demonstrated, not assumed.
