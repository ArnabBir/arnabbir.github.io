    Typed Tool Calling and MCP¶

    Tool calling turns model output into a request to software that can read or change the world. JSON shape alone does not make that safe. Production systems need typed contracts, protocol capability declaration, principal-bound authorization, credential isolation, explicit side-effect semantics, idempotency, approval, and lifecycle-aware recovery.

    The Model Context Protocol (MCP) standardizes host-client-server communication for context and capabilities. It does not replace business authorization, transaction semantics, or safe tool implementation.

    Evidence vocabulary¶

    • [Normative] reflects requirements in the dated MCP or IETF specification cited in Sources.
    • [Source] is supported by a dated primary or official source but is not restated as a protocol requirement.
    • [Derived] follows from stated assumptions.
    • [Design] is a recommended production control beyond the protocol.
    • [Measure] requires local evaluation.

    Typed tool contract¶

    A useful tool is narrow, explicit, and hard to misuse. Separate read, prepare, commit, reconcile, and compensate operations instead of hiding them behind a broad do_anything tool.

    The example is a local registry record enriched with contract_version and authority_class, not an exact wire Tool definition. Those two fields are application-owned metadata; serialize only supported MCP fields or a declared metadata extension on the wire. The host enforces its governed registry, not a server's self-reported authority label.

    {
  "name": "refund.prepare",
  "description": "Validate and prepare a refund. Does not move money.",
  "inputSchema": {
    "type": "object",
    "additionalProperties": false,
    "required": ["payment_id", "amount_minor", "currency", "reason_code"],
    "properties": {
      "payment_id": {"type": "string", "pattern": "^pay_[A-Za-z0-9]+$"},
      "amount_minor": {"type": "integer", "minimum": 1, "maximum": 100000},
      "currency": {"type": "string", "enum": ["USD", "EUR"]},
      "reason_code": {"type": "string", "enum": ["DUPLICATE", "SERVICE_FAILURE"]}
    }
  },
  "annotations": {
    "readOnlyHint": false,
    "destructiveHint": false,
    "idempotentHint": true,
    "openWorldHint": false
  },
  "contract_version": "2.1.0",
  "authority_class": "PREPARE_ONLY"
}

    [Normative] MCP tool annotations are hints and must not be trusted when received from an untrusted server. [Design] Enforce authority from a separately governed registry keyed by trusted server identity, tool name, and contract version.

    Invariants¶

    1. The model never receives long-lived operational credentials.
    2. The caller's authenticated principal and policy determine capabilities; model text does not.
    3. Every tool input and output is validated against a versioned schema.
    4. Side-effecting calls carry a stable operation key bound to normalized arguments.
    5. Timeout or disconnect after dispatch produces UNKNOWN, not automatic FAILED.
    6. Approval binds the exact action, arguments, principal, resource versions, policy version, and expiry.
    7. Tool results are untrusted data when returned to a model.
    8. MCP capability declaration or legacy negotiation indicates protocol support, not user authorization.
    9. Application retry or explicitly selected legacy resumption never implies exactly-once business effects.

    MCP architecture¶

    flowchart LR
    U[User] --> H[MCP host]
    H --> C1[MCP client A]
    H --> C2[MCP client B]
    C1 --> S1[MCP server: documents]
    C2 --> S2[MCP server: operations]
    H --> P[Identity policy and consent]
    P --> C1
    P --> C2
    S2 --> G[Tool policy gateway]
    G --> D[Downstream API]
    G --> K[Credential broker]
    H --> L[(Audit and run ledger)]
    G --> L

    [Normative] In MCP terminology, the host is the LLM application, clients are connectors created by the host, and servers provide context and capabilities. MCP uses JSON-RPC 2.0 messages over transport bindings. In the current 2026-07-28 revision, requests are independently versioned and can be served statelessly; older revisions may establish connection- or session-scoped state.

    The host is the user-trust boundary. It decides what servers may see, what capabilities are exposed to the model, what consent UI appears, and whether a proposal reaches a tool server. A remote MCP server is not automatically trusted because it speaks the protocol.

    Versioning and capability declaration¶

    sequenceDiagram
    autonumber
    participant C as MCP client
    participant S as MCP server
    C->>S: optional server/discover
    S-->>C: supported protocol versions
    C->>S: tools/list with per-request version, identity, capabilities
    alt version and capabilities supported
    S-->>C: typed result
    else unsupported version or missing capability
    S-->>C: typed protocol error
    end

    For the current 2026-07-28 specification:

    • [Normative] there is no initialization negotiation handshake;
    • every request declares protocol version and client capabilities in _meta; clientInfo is optional and SHOULD be included unless configured otherwise;
    • server/discover is mandatory for servers and optional for clients;
    • an unsupported version returns UnsupportedProtocolVersionError with supported versions, after which the client may retry with a mutually supported version;
    • required client capabilities are validated per request;
    • optional extensions are declared under the capabilities extensions map; an unsupported extension requires core fallback or rejection, and extensions SHOULD document that behavior;
    • dual-era implementations detect and explicitly fall back to initialization-based legacy behavior rather than silently mixing eras.
    {
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientInfo": {"name": "support-host", "version": "3.8.0"},
      "io.modelcontextprotocol/clientCapabilities": {"roots": {}}
    }
  }
}

    Pin and test protocol versions. Do not silently reinterpret unknown fields or methods. Persist the effective era, request version, and capability digest with each run so a replay can explain what was available.

    [Normative, base fields verified 2026-09-08] The pinned base specification makes clientInfo self-reported, not authenticated identity. It also requires supported result types (complete or input_required in core), rejects unrecognized types, and treats absent resultType as complete for legacy compatibility. Schema validators MUST NOT automatically dereference network $ref URLs; unresolved schemas must not silently become permissive. These requirements prevent conformance checks from rejecting valid metadata omissions or turning tool schemas into SSRF requests.

    Legacy initialization-based revisions¶

    MCP 2025-11-25 and earlier use an initialize request, server-selected version, notifications/initialized, and session-scoped capability negotiation. A modern client that supports both eras probes as required by the current transport compatibility rules and falls back only when the response identifies a legacy server. Legacy semantics remain valid for a connection that explicitly selected that era; they are not current defaults.

    MCP primitives¶

    Resources¶

    Resources expose data identified by URIs. The client can list and read resources when the server advertises the capability. Resources can represent files, schemas, records, or generated views. Resource templates describe parameterized URIs.

    [Design] A resource URI is an identifier, not authorization. The server reauthorizes each read and returns only fields allowed for the principal and purpose. Bind cache entries to identity scope, policy version, and resource version.

    {
  "uri": "support://tickets/tkt-481",
  "name": "Ticket 481",
  "mimeType": "application/json",
  "annotations": {"audience": ["assistant"], "priority": 0.8}
}

    Treat resource content as untrusted when inserted into a model context. Preserve origin, server identity, URI, version, digest, and trust class.

    Prompts¶

    Prompts are server-provided templates intended for user-controlled selection and argument filling. They are not hidden policy. A prompt returned by a server can contain malicious instructions and must not receive authority over tools, credentials, or host controls.

    Version approved prompts in the host. Show the user which server supplied a prompt when trust matters. Validate arguments and cap expanded content.

    Tools¶

    Tools are callable functions exposed by servers. Listing a tool tells the client that a method is available; it does not grant the model permission to invoke it. The host should filter the list by principal, purpose, environment, risk, and run budget before showing schemas to the model.

    Tool results can contain structured content, text, images, audio, embedded resources, or error indicators depending on protocol version and implementation. Validate result size, type, schema, and trust before it enters model context.

    Roots¶

    Roots let a client expose URI or filesystem boundaries within which a server may operate. They are coordination hints, not a sandbox. A server can still attempt arbitrary filesystem or network access unless the operating-system and network boundary prevent it.

    [Design] Canonicalize paths, reject traversal and symlink escapes, mount only approved roots, use a restricted process identity, and deny network egress by default for local filesystem servers.

    Sampling¶

    Sampling allows a server to request model generations through the client. It keeps model access and provider credentials under host control, but creates a recursive control path: server -> client -> model -> possible action.

    [Normative] Sampling is deprecated as of MCP 2026-07-28. New implementations should not adopt it, and existing implementations should migrate to direct LLM-provider integration. For compatibility, sampling is delivered as an input request inside an MRTR InputRequiredResult, not as an independent server-initiated JSON-RPC request. The specification recommends human ability to deny requests and review prompts and results. [Design] While legacy sampling remains, apply separate budgets, recursion depth, data-loss prevention, model policy, and consent. A server cannot use sampling to gain capabilities not granted to its direct requests.

    Transport choices¶

    stdio¶

    In stdio, the client launches the server as a child process and exchanges newline-delimited JSON-RPC on standard input and output. [Normative] Standard output contains only valid MCP messages; logs go to standard error. The current stdio binding carries modern per-request metadata and defines explicit probing for compatibility with initialization-based servers.

    Unlike HTTP request-scoped SSE, cancelling one stdio operation uses notifications/cancelled with its request ID; closing the shared process would disrupt unrelated calls. The pinned stdio binding, verified 2026-09-08, carries server input requests inside MRTR results rather than independent server JSON-RPC requests. Restart/resend still requires application-side reconciliation for writes.

    Security boundary:

    • pin executable path and artifact digest;
    • pass a minimal environment;
    • do not place reusable secrets in command-line arguments;
    • restrict filesystem, process, device, and network access;
    • capture bounded stderr without secrets;
    • close stdin, then use bounded graceful and forced termination.

    Streamable HTTP¶

    The 2026-07-28 specification defines Streamable HTTP with one MCP endpoint that accepts POST. Each JSON-RPC request is a separate POST, and the response is either one JSON object or a request-scoped Server-Sent Events stream. [Normative] Clients must support both response types. Every POST carries matching protocol metadata in the body and MCP-Protocol-Version header, plus required Mcp-Method and, where applicable, Mcp-Name headers.

    [Normative] Servers must validate a present Origin and reject an invalid origin with HTTP 403, local servers should bind to localhost rather than all interfaces, and servers should authenticate connections. Current Streamable HTTP has no protocol-level session ID, GET stream, or DELETE session endpoint.

    [Normative, verified 2026-09-08 against the pinned transport source] HTTP clients also support tool parameters annotated with x-mcp-header: mirror valid primitive fields into Mcp-Param-*, apply the specified Base64 sentinel encoding when required, and exclude invalid annotated tool definitions. Body-processing servers validate decoded header/body agreement and reject mismatches with HTTP 400 and HeaderMismatch (-32020). [Design] Do not annotate secrets or sensitive query text for mirroring: headers often enter proxy logs outside payload-retention controls. Redact Mcp-Name too when it carries a sensitive resource URI. Header routing is not principal authorization.

    flowchart TD
    R[HTTP request] --> O{Origin absent or allowed?}
    O -->|No| X[Reject]
    O -->|Yes| T{TLS and token valid?}
    T -->|No| X
    T -->|Yes| A{Audience and scope valid?}
    A -->|No| X
    A -->|Yes| V{Protocol metadata valid?}
    V -->|No| X
    V -->|Yes| P[Method policy and schema]
    P --> B[Bounded execution]

    Current SSE responses are scoped to the originating request and are not resumable with Last-Event-ID. Closing the stream signals cancellation of that request; it does not undo a downstream effect already committed. The server stops work as soon as practical, while the application retains an unresolved operation for reconciliation. Server-to-client interactions such as elicitation, roots, and legacy sampling use Multi Round-Trip Requests: the server returns InputRequiredResult, and the client retries the original operation with matching input responses. Long-lived change notifications use the response stream of subscriptions/listen.

    MCP revisions from 2025-03-26 through 2025-11-25 allowed optional sessions, GET streams, independent server requests, and Last-Event-ID resumption. Implement these only after explicitly selecting a compatible legacy revision. Neither old redelivery nor a new application retry proves whether a business effect occurred; reconcile by operation key.

    Authorization and credentials¶

    For HTTP authorization in MCP 2026-07-28:

    • [Normative] authorization is optional at the MCP implementation level; when used with HTTP, implementations should conform to the MCP authorization specification;
    • protected MCP servers act as OAuth resource servers and MCP clients act as OAuth clients;
    • MCP servers implement RFC 9728 protected-resource metadata and clients use it to discover authorization servers;
    • authorization servers expose RFC 8414 or OpenID Connect discovery metadata, and clients support both discovery mechanisms;
    • before authorization, clients obtain a client ID through Client ID Metadata Documents, preregistration, or legacy Dynamic Client Registration in the specified priority order;
    • clients use PKCE, record the expected issuer, and validate a returned iss according to RFC 9207 before exchanging an authorization code;
    • clients include the RFC 8707 resource parameter in authorization and token requests;
    • access tokens travel in the Authorization header, not URI query strings;
    • servers validate that a token was issued for that MCP server;
    • clients request least-privilege scopes and handle bounded WWW-Authenticate scope challenges through step-up authorization;
    • token passthrough to downstream APIs is forbidden by the MCP authorization security guidance.

    The MCP server obtains separate downstream credentials for its own upstream API call. Prefer workload identity or a credential broker that mints short-lived, audience-bound credentials after policy approval.

    inbound token audience: https://mcp.example.com/mcp
downstream token audience: https://payments.example.com
these are different tokens with different scopes and lifetimes

    Store refresh tokens and client secrets in a dedicated secret store. Redact authorization headers, tool arguments containing secrets, and downstream responses. Rotation must not require prompt changes.

    Side-effect protocol¶

    Use prepare/commit/reconcile for consequential tools:

    sequenceDiagram
    autonumber
    participant H as Host
    participant G as Tool gateway
    participant A as Approver
    participant S as System of record
    H->>G: prepare typed action
    G->>S: validate current resource and policy
    S-->>G: prepared intent plus versions
    G-->>A: exact action and argument digest
    A-->>G: approve digest with expiry
    H->>G: commit intent plus operation key
    G->>G: reauthorize and revalidate
    G->>S: commit with same operation key
    S-->>G: terminal result
    G-->>H: effect ID and status

    Operation record¶

    {
  "operation_key": "run-91:refund:1",
  "tool": "refund.commit",
  "contract_version": "2.1.0",
  "normalized_args_digest": "sha256:...",
  "principal": "user-71",
  "prepared_intent": "intent-481",
  "approval_digest": "sha256:...",
  "policy_version": "policy-21",
  "state": "COMMITTED",
  "effect_id": "refund-992",
  "created_at": "2026-09-06T14:00:00Z",
  "terminal_at": "2026-09-06T14:00:01Z"
}

    The system of record atomically binds operation key to payload digest and terminal effect when possible. Same key plus same payload returns the prior result. Same key plus different payload returns conflict. A timeout after dispatch is UNKNOWN; call refund.status(operation_key) before retrying with the same key. A NOT_FOUND response is not proof that an earlier attempt cannot still commit. Redispatch requires a downstream contract that deduplicates concurrent attempts with the same key, or proof that the old attempt has been fenced and cannot take effect. Keep the deduplication record for the entire allowed retry and replay window; after its expiry, require reconciliation rather than treating the key as new.

    Compensation is a new authorized action, such as refund.reverse, with its own operation key and audit trail. It is not rollback in the database sense and may be impossible after settlement.

    Capacity calculation¶

    Suppose 200 active clients each read a resource every 10 seconds, 20 tool calls/s arrive, and 5% of tool calls require one MRTR input request:

    resource reads/s = 200 / 10 = 20
tool requests/s = 20
MRTR input requests/s = 20 * 0.05 = 1
base logical application operations/s = 20 + 20 = 40
additional MRTR continuation POSTs/s = 20 * 0.05 = 1
client-to-server POST attempts/s = 40 + 1 = 41

    If callers retry 30% of 1,000 in-flight application requests after disconnects:

    retried requests = 1,000 * 0.30 = 300
transport attempt amplification = 1,300 / 1,000 = 1.3

    [Derived] Under successful deduplication, duplicate effects per logical write remain zero and total effects per successfully committed logical write remain one. These are different denominators from transport amplification. The MRTR estimate assumes one continuation per affected call and excludes input collection, discovery, subscriptions, authentication, and ordinary retries. Load tests must include retries, cancelled streams, lost acknowledgements, slow consumers, MRTR retries, and explicitly supported legacy-session expiry.

    Failures and security controls¶

    Failure or attack Discriminator Control
    schema-valid but unsafe amount schema passes, business limit fails deterministic policy and current-state validation
    tool-name spoofing untrusted server claims privileged name registry binds server identity plus tool contract
    tool-description injection description asks host to reveal data descriptions have no authority; consent and policy outside model
    malicious resource retrieved text proposes secret exfiltration trust labels, no model-visible secrets, egress policy
    root traversal canonical path exits allowed mount OS sandbox plus canonical path validation
    deprecated sampling recursion nested requests exceed depth migrate to direct provider integration; budget remaining legacy use

    Evaluation and observability¶

    Contract tests¶

    • valid, invalid, boundary, unknown, and extra input fields;
    • output schema and size bounds;
    • operation-key same-payload deduplication and different-payload conflict;
    • lost acknowledgement after commit;
    • cancellation before and after effect boundary;
    • principal, tenant, purpose, scope, expiry, and resource-version policy;
    • approval digest mismatch and expiry;
    • root traversal, symlink escape, redirect, DNS, and egress tests;
    • MCP modern/legacy era, version, and capability matrix;
    • stdio contamination, Streamable HTTP cancellation, MRTR, subscriptions, and legacy resumption compatibility;
    • deprecated sampling migration, recursion, and budget exhaustion.

    Telemetry¶

    Record host, client, trusted server identity, protocol era and version, transport, legacy session reference when applicable, capability digest, method, tool contract, principal-scope digest, policy decision, operation key, attempt, duration, redacted result digest, and terminal status.

    Monitor logical operations versus attempts, validation failures, policy denials, approvals, unknown outcomes, reconciliation latency, deduplicated attempts, payload conflicts, capability-list changes, MRTR rounds, subscription churn, legacy session churn, deprecated sampling depth, bytes, timeouts, and downstream effects. Never place tokens or unrestricted resource contents in telemetry.

    MCP and tool migration¶

    1. Inventory hosts, clients, servers, transports, protocol versions, tool schemas, and active/paused runs.
    2. Add a new tool contract version alongside the old one; avoid changing meaning in place.
    3. Make consumers tolerant of additive output fields while rejecting unknown authority-bearing values.
    4. Shadow calls or compare prepare results without executing duplicate effects.
    5. Canary by host version, server identity, principal class, and tool risk.
    6. For transport or protocol-era migration, reconcile every in-flight side effect before retrying or reconnecting.
    7. Persist protocol and contract version in durable run state.
    8. Remove old contracts only after replay, paused-run, and rollback windows expire.

    For legacy initialization-based MCP or HTTP+SSE migration, follow the current dual-era and transport compatibility guidance rather than assuming endpoint equivalence. Test modern, dual-era, and legacy peers explicitly.

    Interview exercise¶

    Design an MCP integration that lets a support assistant read orders, prepare refunds, and commit refunds after approval. Some servers run locally over stdio; others are remote over Streamable HTTP. The design must survive disconnect after commit, server capability changes, and indirect prompt injection from order notes.

    Explain per-request versioning and capabilities, legacy initialization, resources, prompts, tools, roots, MRTR, sampling deprecation, transports, OAuth discovery and audience binding, credential exchange, schema validation, consent, approvals, operation records, reconciliation, telemetry, and migration.

    L5 and L6 signals¶

    L5¶

    • Separates protocol capability from user authorization and business authority.
    • Gives the model typed proposals but no operational credentials.
    • Describes modern per-request metadata, legacy initialization, MRTR, and both standard transports accurately.
    • Handles timeout-after-commit with same-key reconciliation.
    • Treats roots as hints plus sandboxing and tool output as untrusted.
    • Tests protocol versions, schemas, reconnects, and security boundaries.

    L6¶

    • Establishes a governed registry for server identity, tool contracts, authority classes, and exceptions.
    • Defines fleet compatibility across protocol, transport, schema, and paused-run versions.
    • Quantifies reconnect storms, correlated server loss, and receiving capacity.
    • Governs credentials, consent evidence, retention, and cross-product audit.
    • Assigns cost, risk, rollback authority, and retirement evidence to owners.

    Final design checklist¶

    • Every tool has narrow typed inputs, outputs, errors, and side-effect semantics.
    • MCP era, request version, and capabilities are declared, validated, and recorded.
    • Resources, prompts, tool results, and annotations are treated according to trust.
    • Roots are enforced by an actual sandbox.
    • New systems avoid deprecated sampling; retained legacy use has user control and separate budgets.
    • HTTP tokens are audience-bound and never passed through downstream.
    • Unknown outcomes reconcile before retry with the same operation key.
    • Transport and schema migrations account for active and paused runs.
