    Embeddings and Vector Retrieval¶

    An embedding maps an input into a numeric space where a distance function can support candidate retrieval. Production design must preserve what was embedded, with which model and preprocessing, under which authorization, and into which index generation. A vector database does not answer those questions.

    1. Scope and requirements¶

    Design semantic retrieval for an enterprise knowledge system with hundreds of millions of chunks, tenant and document ACLs, hybrid lexical/vector search, minute-scale update visibility, citations, and deletion.

    Requirements:

    • preserve immutable source version, offsets, ACLs, parser, chunker, embedding model, and vector lineage;
    • keep query and corpus embeddings in the same compatible vector space;
    • enforce tenant and authorization constraints before unauthorized content enters context;
    • meet latency while measuring approximation loss against exact search;
    • combine lexical, vector, and reranking stages deterministically;
    • publish complete index generations and support rollback;
    • expose source provenance and abstain when support is insufficient;
    • process updates and deletion within declared freshness SLOs.

    This chapter develops the embedding lifecycle and retrieval contract. Search and Indexing already explains general inverted indexes, sharding, HNSW, IVF, and search-engine operations. RAG and Agent Security covers prompt injection, citation security, and tool authority.

    Principle: Approximate nearest-neighbor search is a candidate-generation optimization. It does not define relevance, authorization, factual support, or the canonical source of truth.

    2. End-to-end architecture¶

    flowchart LR
    S[(Versioned sources)] --> P[Parse and normalize]
    P --> C[Chunk and provenance]
    C --> E[Embedding workers]
    E --> B[(Base index generation)]
    U[Source updates] --> UE[Parse chunk and embed with pinned bundle]
    UE --> D[(Fresh delta index)]
    TS[Delete and supersession map] --> H
    Q[Query] --> A[Auth and query policy]
    A --> AP[Mandatory tenant and ACL predicates]
    A --> QE[Query embedding]
    AP --> LX[ACL-filtered lexical candidates]
    AP --> VX[ACL-filtered vector candidates]
    QE --> VX
    B --> VX
    D --> VX
    LX --> F[Fusion and dedupe]
    VX --> F
    F --> H[Current-state reauthorization and hydration]
    H --> R[Reranker]
    R --> K[Context and citations]
    K --> O[Answer or search result]
    M[Index manifest controller] --> B
    M --> QE

    The canonical text and ACL live outside the vector index. The index is a rebuildable projection. Mandatory tenant and ACL predicates constrain each candidate search before fusion; candidate records carry IDs and scores, and hydration rechecks current authorization before resolving immutable source spans. Base-plus-delta supports freshness while keeping large base generations immutable.

    3. Embedding and chunk identity¶

    SourceVersion(source_id, version, tenant, uri, media_type, digest, acl_version, state)
Chunk(chunk_id, source_id, source_version, start_offset, end_offset,
      text_digest, parser_version, chunker_version, language, acl_ref)
Embedding(embedding_id, chunk_id, model_id, preprocess_version,
          dimensions, dtype, normalized, vector_digest, created_at)
IndexGeneration(id, embedding_model, distance, dimensions, base_snapshot,
                delta_watermark, build_config, manifest_digest, state)
Tombstone(chunk_id, source_version, reason, effective_at, sequence)
Retrieval(request_id, query_digest, query_model, index_generation,
          filters, lexical_version, fusion_version, reranker_version, results)

    Chunk IDs should be stable for an unchanged source version and span, but a changed parser, chunker, normalization, or source content can create a new chunk identity. Content hashes help deduplicate bytes; they do not replace tenant, source, ACL, or licensing metadata.

    Store vector dimensions and distance configuration. Cosine similarity, dot product, and Euclidean distance are not interchangeable without assumptions such as normalization. Validate query dimensions and model ID before search.

    4. Chunking and preprocessing¶

    Chunking sets the retrieval unit and citation boundary. Tiny chunks lose context and increase index entries; large chunks dilute relevance and consume reranking/model context. Choose from source structure and evaluated tasks rather than one global token count.

    Preserve headings, table context, code block boundaries, page or section identifiers, and byte/character offsets. Handle documents too large or malformed to parse through bounded resources and quarantine. OCR, language detection, transcription, and table extraction each add a versioned uncertainty-bearing stage.

    Useful policies:

    • structure-aware boundaries before token-length fallback;
    • bounded overlap only where cross-boundary context improves measured recall;
    • parent-child retrieval when a small child locates a larger coherent passage;
    • source-specific chunkers for code, tables, tickets, and policies;
    • exact canonical text hydration rather than treating stored embedding text as truth;
    • deterministic normalization and golden fixtures for offset preservation.

    Evaluate chunking at candidate recall, citation support, context tokens, latency, and index cost. A generation-quality change can originate in chunking even when the generation model is unchanged.

    5. Embedding model contract¶

    An embedding model contract includes:

    • artifact and tokenizer digest;
    • preprocessing and prompt/prefix convention;
    • input type, language, length, and truncation policy;
    • dimensions, numeric type, normalization, and distance;
    • intended task and known evaluation slices;
    • runtime, batch policy, and maximum input;
    • data-use and region restrictions;
    • release and retirement state.

    Query and corpus encoders may differ in asymmetric retrieval, but their compatibility is defined by one model bundle. Never send model-B query vectors to a model-A corpus index merely because dimensions match.

    6. Search interface and filters¶

    POST /v1/retrieval:search

{
  "tenant_id": "tenant-17",
  "query": "How long are approved refunds retained?",
  "top_k": 10,
  "filters": {
    "repository": ["policy"],
    "effective_at_lte": "2026-09-06T00:00:00Z"
  },
  "deadline_ms": 300,
  "index_generation": "policy-semantic-84"
}

    The server derives mandatory tenant, principal, purpose, and ACL predicates. The caller may add only allowlisted narrowing filters; it cannot remove mandatory policy.

    {
  "generation": "policy-semantic-84",
  "results": [{
    "chunk_id": "c-91",
    "source_id": "refund-policy",
    "source_version": "2026-08-14",
    "span": {"start": 1940, "end": 2510},
    "scores": {"vector": 0.81, "lexical_rank": 3, "reranker": 4.7}
  }],
  "partial": false
}

    Scores are not calibrated probabilities. Avoid exposing one universal threshold unless validated for that model, index, filter, and query distribution.

    7. Authorization and filter placement¶

    Partition by tenant or security domain where that boundary is strong. Within a partition, use filter-aware candidate search if the index supports it, then reauthorize during hydration. Post-filtering a global top-K can both leak information and starve authorized results.

    If only 1% of a corpus is authorized and the system retrieves 100 global neighbors then post-filters, the expected count under a uniform independence assumption is only one; real clustering can make it zero. Overfetching 10,000 candidates is expensive and still not an authorization proof.

    Security patterns:

    • separate indexes for hard isolation boundaries;
    • prefilter using immutable or correctly updated ACL dimensions;
    • oversample only within a bounded, authorized candidate space;
    • current-state reauthorization during source hydration;
    • constant or coarsened result metadata where existence is sensitive;
    • deletion tombstones consulted before serving any candidate;
    • tenant-aware cache keys and no cross-domain embedding-result cache.

    8. Candidate retrieval and index choice¶

    Exact search computes distance against every eligible vector and provides the reference top-K for a sample. ANN trades recall for less work. Use Search and Indexing for algorithm mechanics; the applied-AI decision adds model compatibility, filtered recall, and downstream task impact.

    Need Candidate approach Operational concern
    modest corpus or strict reference exact flat search linear compute
    frequent inserts, high recall, sufficient RAM HNSW graph memory, tombstones, rebuild
    very large stable base, memory pressure IVF/PQ trained centroids/codebooks, quantization loss
    huge base plus fresh updates immutable compressed base plus mutable delta dual read, dedupe, compaction
    identifiers and semantic concepts lexical plus vector fusion and evaluation

    Tune search effort - such as graph exploration or lists probed - against exact neighbors on production-shaped vectors and filters. More effort usually improves candidate recall at latency and compute cost. Index parameters are release configuration, not invisible operator knobs.

    Keep two reference sets separate. ANN_overlap@K = |ANN_topK intersect exact_topK| / |exact_topK| measures approximation against the same metric, snapshot, filters, and tie policy. relevance_Recall@K = |returned_topK intersect judged_relevant| / |judged_relevant| measures task retrieval. Exact search has perfect overlap with itself, not necessarily perfect relevance. Define empty eligible sets and distance ties explicitly; a better embedding can improve relevance while a low-effort ANN index loses overlap.

    9. Hybrid retrieval, fusion, and reranking¶

    Lexical retrieval is strong for exact identifiers, rare names, and phrases. Dense retrieval can capture semantic similarity. Retrieve bounded candidates from each, deduplicate by canonical source/chunk identity, then fuse.

    Reciprocal rank fusion (RRF) uses rank rather than incomparable raw scores:

    RRF(document) = sum over lists 1 / (k + rank_in_list)

    Version k, list depths, weights, and tie-breaks. Persist source ranks for diagnosis. A learned or cross-encoder reranker receives only the candidate set; it cannot recover a relevant item omitted upstream. Measure candidate Recall@N before final ranking quality.

    Apply hard policy filters before reranking. After ranking, enforce deduplication, source diversity, freshness, and context budget through deterministic rules. Do not let a generative model silently rewrite citations or fabricate source IDs.

    The deterministic hybrid search lab exercises fusion and candidate ceilings.

    10. Retrieval evaluation¶

    Build a versioned judgment set containing query, corpus/index epoch, relevant source spans with graded relevance, filters/identity context, unanswerable cases, and slice labels.

    Metric Measures Limitation
    Recall@K whether required relevant items appear ignores order inside K
    Precision@K fraction of K judged relevant incomplete judgments bias it
    MRR rank of first relevant item ignores later relevant items
    NDCG@K graded relevance and order needs reliable grades
    filtered Recall@K candidate quality under policy filters requires authorized ground truth
    citation precision cited evidence supports claim generation-stage measure
    supported-answer rate answer is both produced and supported combines stages
    abstention accuracy refusal when evidence is absent requires unanswerable cases

    Attribute failure by stage: corpus coverage, parser/chunker, embedding, ANN, filters, fusion, reranker, context packing, generation, or citation mapping. An end-to-end score alone cannot tell which stage to repair.

    Use paired query-level comparisons between releases and report uncertainty. Evaluate languages, source types, tenants, freshness bands, rare entities, long documents, ACL selectivity, and adversarial or conflicting evidence. Renew judgments as corpus and query distributions evolve.

    11. Memory, throughput, and cost¶

    Assumption (2026-09, illustrative): The corpus contains 120 million vectors with 768 float32 dimensions. Metadata averages 220 bytes/vector. Two complete index generations coexist during migration. Index-structure overhead is not yet included.

    Raw vector bytes:

    120,000,000 * 768 * 4
= 368,640,000,000 bytes
= 368.64 GB decimal

    Metadata is 120,000,000 * 220 = 26.4 GB. One generation needs at least 395.04 GB before graph/list structures, allocator overhead, replicas, and source text. Two generations need at least 790.08 GB. This lower bound shows why migration reserve and index choice matter; it is not a capacity forecast.

    For embedding throughput:

    Assumption (2026-09, illustrative): Re-embedding 120 million chunks averages 420 tokens/chunk and must finish in 24 hours. A measured worker sustains 18,000 input tokens/s at 70% planned utilization.

    required tokens/s = 120,000,000 * 420 / 86,400
                  = 583,333 tokens/s

usable worker rate = 18,000 * 0.70
                   = 12,600 tokens/s

workers = ceil(583,333 / 12,600)
        = 47

    Add update catch-up, failures, skew, source and output bandwidth, index build time, validation, and serving load. Cost includes parsing, embedding, dual indexes, replicas, compaction, exact-reference queries, reranking, and generated context tokens.

    Benchmark (measurement requirement, 2026-09): On a pinned corpus/query sample, sweep index configuration with the production embedding, filter selectivity, update rate, hardware, concurrency, and dataset size. Report exact-reference Recall@K, filtered Recall@K, p50/p95/p99 latency, queries/core, resident bytes/vector, build time, update visibility, deletion behavior, and cost. Measure downstream quality separately.

    The vector index lab and calculations workbook provide small deterministic exercises.

    12. Embedding and index migration¶

    Changing embedding model, preprocessing, dimensions, normalization, or distance creates a new compatibility generation.

    flowchart TD
    A[Pin source snapshot and watermark] --> B[Build embeddings B]
    B --> C[Build index B]
    C --> D[Apply ordered updates after watermark]
    D --> E[Reconcile keys digests ACLs tombstones]
    E --> F[Exact and downstream evaluation]
    F --> G[Shadow query model B with index B]
    G --> H[Stable canary bundle B]
    H --> I{Gates pass?}
    I -- no --> J[Route all traffic to bundle A]
    I -- yes --> K[Expand and retain A for rollback]

    Bundle (query encoder B, index B, fusion B, reranker B) together. Shadowing must not send B vectors to A. Reconciliation checks eligible source count, index count, duplicates, missing keys, unexpected keys, ACL version, and delete tombstones. Rollback changes the whole retrieval bundle.

    For base-plus-delta, each query reads the base and delta belonging to the same compatible retrieval bundle, not indexes from different embedding spaces. Deduplicate by latest source version/sequence and use deterministic ties. A current-version map must also suppress superseded base chunks when the newer delta chunk did not enter the candidate set. Comparing only returned duplicates would let an obsolete, highly ranked chunk survive. Bounded refill can improve coverage after suppression; report partial results when its budget runs out. Compaction creates a new base from a pinned state and advances one manifest pointer only after the delta watermark is included.

    13. Freshness, deletion, and failure recovery¶

    Failure Discriminating evidence Control
    parser coverage drops source-to-chunk counts by type/version quarantine and keep old generation
    embedding workers truncate token counts and completion reason explicit policy and gate
    ANN recall drops exact overlap stable, ANN overlap falls restore search config/index
    ACL post-filter starvation candidates before/after policy filter-aware search or partition
    source/index split citation outside active manifest atomically pin and hydrate generation
    update stream gap sequence/watermark reconciliation replay from snapshot watermark
    stale delete served tombstone sequence exceeds index version serve-time deny and repair projection
    index shard lost generation manifest and replicas rebuild or restore same generation
    query/index model mismatch model/generation compatibility check reject before search

    Define freshness stages: source accepted, parsed, embedded, indexed in delta, searchable, compacted into base. Alert on age and backlog at each stage. A single "index lag" metric cannot isolate the bottleneck.

    Deletion should first prevent serving through current authorization/tombstone state, then remove vectors, text, caches, snapshots, and future training eligibility. Verify completion by source ID across generations. Retain only legally required evidence under narrow access and expiration.

    14. Observability and testing¶

    Measure ingestion throughput and lag; parser failures; chunks/source and tokens/chunk; truncation; embedding errors and vector norms; index generation and watermark; build/compaction time; update/delete visibility; query candidate count by stage; pre/post-filter counts; lexical/vector overlap; ANN versus exact recall; reranker latency; empty and partial results; citation/support metrics; cache hits; memory; CPU/accelerator use; and cost.

    Test:

    • golden parsing/chunk/offset fixtures;
    • embedding determinism tolerance and dimension/normalization checks;
    • exact-neighbor references and ANN sweeps;
    • high-selectivity ACL filters and cross-tenant isolation;
    • duplicate, reordered, missing, and late updates;
    • deletion during base rebuild and dual-generation serving;
    • shard loss and manifest rollback;
    • malformed/oversized documents and decompression bombs;
    • multilingual, identifier-heavy, stale, conflicting, and unanswerable queries;
    • citation resolution against immutable source versions.

    15. Security and privacy¶

    Embeddings can retain information about source data and should inherit its classification. Do not treat vectors as anonymized. Encrypt and authorize indexes, isolate tenants/security domains, audit bulk export, and restrict nearest-neighbor probing. Keep raw text out of metrics and logs.

    Ingestion handles attacker-controlled files. Sandbox parsers; limit bytes, pages, recursion, decompression, CPU, and wall time; scan content; and restrict outbound network access. Source trust and signatures establish provenance and integrity, not truth. Retrieved content remains untrusted input to a model.

    16. Vendor and production evidence¶

    Vendor (pgvector 0.8.6, released 2026-07-29): pgvector documents exact and approximate nearest-neighbor search with vector distance operators and HNSW/IVFFlat indexes. Product support does not remove the need to benchmark filtered recall, replica behavior, backup/restore, write amplification, or isolation in the chosen PostgreSQL environment. pgvector 0.8.6 documentation

    [Vendor behavior, v0.8.6 documentation verified 2026-09-08] In pgvector's approximate scans, SQL filtering occurs after the index scan. A WHERE tenant_id = ... predicate is not evidence of tenant-local graph traversal. Iterative scans can seek more candidates until configured limits, but do not guarantee K results or perfect recall. Use partitions or separate tables for hard tenant index isolation, enforce database authorization, and test actual query plans. strict_order means distance ordering of found candidates, not exact-neighbor completeness. This is an implementation constraint on the architecture above, not permission to hydrate unauthorized content.

    Production report (Meta Engineering, published 2017-03-29): Meta reported releasing Faiss after building nearest-neighbor implementations for billion-scale datasets and described its speed, memory, and accuracy evaluation method. The published results use specific datasets, hardware, algorithms, and metrics; they are not a capacity guarantee for filtered enterprise retrieval. Faiss: A library for efficient similarity search

    17. Tradeoffs and evolution¶

    Choice Benefit Cost or risk
    vector-only simple semantic candidate path weak exact identifiers and unexplained misses
    hybrid lexical/vector broader coverage fusion and dual operations
    one global index operational simplicity isolation and selective-filter problems
    tenant/security partitions hard boundaries and better filter locality many small indexes and placement overhead
    HNSW strong low-latency recall in many regimes memory, tombstones, rebuilds
    IVF/PQ compressed large stable base training and approximation loss
    in-place update immediate change mixed generation and rollback difficulty
    immutable base plus delta coherent base and freshness merge, dedupe, compaction

    Begin with lexical search or exact vectors when scale permits. Add ANN only after exact-reference evaluation exists. Add hybrid retrieval when error analysis shows complementary lexical and semantic misses. Add a reranker only when candidate recall is adequate and its quality gain justifies latency and cost. Split tenant indexes when authorization, scale, or noisy-neighbor evidence requires it.

    18. Interview exercise¶

    Prompt: Design retrieval for 500 million enterprise chunks across 20,000 tenants. Updates must be searchable within five minutes, p95 retrieval is 250 ms, answers need exact citations, and an embedding-model migration occurs quarterly.

    An L5 design stores immutable source versions and offsets, uses security-domain partitions plus current ACL hydration, builds a large immutable base with fresh delta, combines lexical/vector candidates, reranks, and measures exact-reference Recall@K and citation support. It versions and atomically routes query encoder/index bundles, catches up from a watermark, reconciles deletes, and preserves rollback.

    An L6 design adds tenant placement and noisy-neighbor policy, many-small-index economics, region/residency boundaries, corpus and judgment ownership, dual-generation capacity, migration scheduling, deletion proof, exception handling, and organization-wide compatibility contracts. It explains what happens when five-minute freshness competes with a base rebuild and when a tenant changes ACLs without changing document text.

    L5 and L6 signals¶

    L5¶

    • Preserves source, chunk, embedding, ACL, and index lineage.
    • Keeps query and corpus encoders in one explicit compatibility bundle.
    • Explains filter placement, hybrid candidates, fusion, reranking, and abstention.
    • Benchmarks ANN against exact neighbors under representative filters.
    • Designs base/delta freshness, deletion, migration, and rollback.

    L6¶

    • Governs security-domain partitioning, tenant placement, residency, and noisy neighbors.
    • Plans dual-generation capacity and migration across product teams.
    • Owns corpus quality, judgments, compatibility, and deletion evidence.
    • Connects retrieval-stage metrics to end-to-end support and product outcomes.
    • Defines exception policy and retirement criteria for models, indexes, and source generations.

    Final summary¶

    Treat vectors as versioned projections of authorized source data. Preserve provenance through parsing, chunking, embedding, indexing, retrieval, and citation. Use exact search as evaluation truth for ANN candidates, apply authorization before exposure and again at hydration, and publish compatible query/index generations atomically. Optimize retrieval stages only after measuring where relevant evidence is lost.
