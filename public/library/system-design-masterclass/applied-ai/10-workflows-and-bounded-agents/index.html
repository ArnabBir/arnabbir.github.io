    Workflows and Bounded Agents¶

    Use deterministic code when the path, policy, and success condition are known. Add model-controlled choice only where it creates measured value. An agent is not a reliability mechanism: it expands the set of possible paths, costs, and failures. Production autonomy must therefore be explicit, least-privileged, durable, observable, and bounded.

    Evidence vocabulary¶

    • [Source] is supported directly by a dated source in Sources.
    • [Derived] follows from stated assumptions.
    • [Design] is a recommended production contract.
    • [Measure] must be tested on representative tasks and failures.

    Definitions¶

    • A deterministic workflow chooses transitions in code from typed state and declared conditions.
    • A model-assisted workflow has fixed topology but uses a model inside bounded steps such as classify, extract, draft, or evaluate.
    • An agent lets a model choose some next actions or tools based on state and observations.
    • Autonomy is the authority to select or execute actions without another decision maker. It is a vector, not a boolean.

    [Source] Anthropic's 2024 guidance distinguishes workflows with predefined code paths from agents whose model dynamically directs process and tool use. This chapter uses that useful distinction but adds its own production contracts.

    Start with the authority map¶

    Before choosing a pattern, classify every operation:

    Class Examples Model role Required control
    A0: pure computation summarize local text, rank options may execute schema and budget
    A1: reversible read search docs, read ticket may propose/call principal-bound scope and audit
    A2: reversible write create draft, add label may propose; limited execution idempotency, validation, undo
    A3: consequential write refund, publish, change access proposal only by default exact approval, policy, compensation
    A4: irreversible/high impact delete evidence, wire funds no autonomous execution established human workflow and separation of duties

    This is a [Design] taxonomy, not an industry standard. Organizations should map classes to their own legal and operational policy.

    Invariants¶

    1. Identity, authorization, data policy, spend policy, tool validation, and approval are deterministic controls outside the model.
    2. Every run has maximum steps, model calls, tool calls, input/output tokens, wall time, spend, and parallel fan-out.
    3. A tool call is a proposal until the tool gateway authorizes and executes it.
    4. Unknown tool outcomes are reconciled by stable operation key before retry.
    5. Repeated actions without new evidence consume a progress budget and trigger stopping.
    6. Partial and degraded outcomes are explicit; exhaustion is not reported as success.
    7. Side effects have duplicate-prevention or explicit unknown-outcome controls independently of replay; compensation is a separate authorized recovery action, not a substitute for deduplication.
    8. The runtime can remove write capabilities without disabling safe reads.

    Pattern selection¶

    flowchart TD
    A[Task] --> B{Path and rules known?}
    B -->|Yes| W[Deterministic workflow]
    B -->|No| C{Can bounded classification choose a path?}
    C -->|Yes| R[Router plus fixed workflows]
    C -->|No| D{Subtasks known and independent?}
    D -->|Yes| P[Parallel workflow]
    D -->|No| E{Success can be evaluated incrementally?}
    E -->|No| H[Human-led process]
    E -->|Yes| F{Actions reversible and low risk?}
    F -->|No| G[Agent plans; workflow approves and executes]
    F -->|Yes| I[Bounded agent]

    Prefer the least dynamic pattern that passes quality gates. A single call with retrieval may outperform a complex loop after latency, cost, and failures are counted.

    Core patterns¶

    Deterministic workflow¶

    Use a state machine for known business processes, mandatory approvals, deadlines, and compensation. A model can classify or draft inside a step, but code owns transitions.

    RECEIVED -> VALIDATED -> ENRICHED -> DRAFTED -> REVIEWED -> COMMITTED

    Best fit: regulated writes, stable forms, fixed integrations, and high-volume repeatable tasks.

    Router¶

    A router maps an input to a bounded set of specialist paths. Routing can be rules, a classifier, or an LLM with a strict enum output. Add an UNKNOWN route and confidence policy. Never let a route label grant authority; downstream policy evaluates the original principal and request.

    {
  "route": "REFUND_QUESTION",
  "confidence": 0.91,
  "alternatives": ["ORDER_STATUS"],
  "reason_codes": ["MENTIONS_DUPLICATE_CHARGE"],
  "router_version": "router-8"
}

    Evaluate route confusion by class, business impact, language, and adversarial input. A cheap router that sends hard cases to the wrong specialist can cost more than a single capable model.

    Prompt chain¶

    Chaining decomposes a task into fixed steps such as extract -> validate -> draft. Each step has a typed contract and gate. Serial chains improve focus but multiply latency and failure opportunities. Persist intermediate values only when needed for recovery, audit, or evaluation.

    Parallelization¶

    Use sectioning when independent subtasks can run concurrently and a deterministic aggregator can combine them. Use voting when independent attempts provide useful diversity and a declared decision rule exists. Correlated model errors limit the benefit of voting.

    flowchart LR
    I[Input] --> A[Worker: facts]
    I --> B[Worker: policy]
    I --> C[Worker: safety]
    A --> J[Typed join]
    B --> J
    C --> J
    J --> V[Deterministic validation]

    Bound fan-out. If one request starts 20 workers and each retries twice, the worst-case 60 attempts can overload shared inference and tools.

    Orchestrator-worker¶

    The orchestrator chooses subtasks dynamically; workers execute narrow bounded jobs. This fits tasks where decomposition depends on the input, such as investigating several unknown systems. The orchestrator does not inherit every worker capability. Give each worker the minimum read or write scope and cap spawned tasks, depth, and aggregate budget.

    Evaluator-optimizer¶

    One component produces an artifact; another evaluates it against a rubric and returns structured defects. Iterate only while the score or defect set demonstrates progress.

    stop when any condition holds:
  all mandatory checks pass
  maximum iterations reached
  marginal score gain < epsilon for two iterations
  same normalized defect set repeats
  deadline, token, or spend budget exhausted
  evaluator confidence is below review threshold

    Do not let an evaluator convert subjective confidence into permission for a consequential action. The business policy remains deterministic.

    ReAct-style agent loop¶

    [Source] ReAct interleaves reasoning-oriented model outputs with actions and observations. In production, store a concise decision record and typed actions rather than depending on hidden free-form reasoning.

    flowchart TD
    S[Load durable state] --> O[Observe bounded context]
    O --> M[Model proposes action]
    M --> P{Policy and schema allow?}
    P -->|No| D[Record denial]
    P -->|Yes| T[Execute tool with operation key]
    T --> R[Record result]
    D --> G{Stop condition?}
    R --> G
    G -->|Continue| S
    G -->|Complete| C[Validate completion]
    G -->|Exhausted| E[Partial or abstain]

    Bounded autonomy contract¶

    {
  "run_id": "run-01H...",
  "principal": "user-71",
  "purpose": "support-resolution",
  "authority_class": "A2",
  "capabilities": ["ticket.read", "draft.create", "label.add"],
  "budgets": {
    "max_steps": 12,
    "max_model_calls": 8,
    "max_tool_calls": 10,
    "max_parallelism": 3,
    "max_input_tokens": 60000,
    "max_output_tokens": 8000,
    "max_spend_usd": 0.50,
    "deadline_at": "2026-09-06T13:01:00Z"
  },
  "stopping": {
    "repeat_action_limit": 2,
    "no_progress_limit": 3,
    "require_completion_validator": true
  },
  "versions": {"workflow": "wf-9", "prompt": "agent-14", "model_route": "route-11", "policy": "policy-21"}
}

    Budgets are cumulative across retries and resumes. A retry does not create fresh spend or authority. Child-worker budgets are carved from the parent's remaining budget, not added to it. Reserve the maximum allowed attempt cost atomically before dispatch, then settle measured usage; checking a balance without reserving it lets concurrent workers overspend. Provider-enforced output limits and deadline controls bound each reservation.

    Step transition algorithm¶

    function advance(run):
    lease = acquire_fenced_lease(run)
    if not lease: return RETRY_LATER
    state = load_and_fold(run.events)
    if terminal(state): return state.result
    if state.pending_operation:
        return reconcile_without_replanning(state.pending_operation, lease)
    if any_budget_exhausted(state): return terminate(EXHAUSTED)

    reservation = reserve_attempt_budget_fenced(state, lease)
    if not reservation: return terminate(EXHAUSTED)
    observation = build_bounded_observation(state)
    proposal = model.propose(observation, allowed_action_schemas)
    append_fenced(ActionProposed(proposal, versions, budget_snapshot), lease.fencing_epoch)

    decision = policy.authorize(principal, purpose, proposal, state)
    append_fenced(PolicyDecided(decision), lease.fencing_epoch)
    if denied(decision): return schedule_next_or_stop(state)

    intent = persist_intent_once(run.id, state.logical_effect_slot,
                                 proposal, decision, lease.fencing_epoch)
    key = intent.operation_key
    prior = tool.lookup(key)
    if terminal(prior): return record_and_advance(prior, intent, lease)
    if not safe_to_dispatch_or_retry(prior, intent, tool.contract):
        return persist_unknown_and_schedule_reconciliation(intent, lease)
    reauthorize_and_check_preconditions(intent)
    append_fenced(ToolDispatchStarted(key), lease.fencing_epoch)
    result = tool.execute(key, intent.canonical_args)
    append_fenced(ToolResultRecorded(key, digest(result), redacted_result), lease.fencing_epoch)
    return schedule_next_or_stop(state)

    Budget exhaustion stops new work but does not erase an unresolved side effect. Transfer it to a bounded recovery queue with its own operational budget, retaining UNKNOWN until status lookup or human reconciliation resolves it; recovery must not replan or automatically redispatch a non-idempotent effect. A terminal user-facing run may still have a separately visible pending recovery record.

    The lease plus fencing on durable commits excludes stale planners; lease expiry alone does not stop their processes. Release leases on every exit or let a bounded lease expire. These controls do not create exactly-once external effects. The tool's idempotency record and reconciliation contract protect the side effect, including a crash after dispatch but before result persistence.

    The orchestrator assigns a durable logical-effect slot, persists its operation key and canonical payload before dispatch, and reuses them across physical attempts and resumes. Argument and resource-version digests bind approval/preconditions; a changed version cannot silently mint a new financial identity for an unresolved effect. A genuinely new effect needs an explicit new authorized intent. Model-provided IDs are correlation only. Reusing a key with a different canonical payload is a conflict.

    Stopping and progress¶

    An agent must prove progress using task-specific state rather than claiming it in prose. Examples:

    • unresolved required fields decrease;
    • failing deterministic checks decrease;
    • uncovered source set decreases;
    • test failures decrease without increasing higher-severity failures;
    • plan frontier gains a new nonduplicate observation.

    Normalize action identity as (tool, canonical_args_digest, relevant_resource_version). Repeating it with the same observation is nonprogress unless the tool contract says polling is required and bounded. Backoff polling does not reset the limit.

    Terminal reasons should include:

    SUCCEEDED
PARTIAL_BUDGET_EXHAUSTED
PARTIAL_DEADLINE_EXCEEDED
ABSTAINED_INSUFFICIENT_EVIDENCE
BLOCKED_POLICY
BLOCKED_APPROVAL
FAILED_TOOL
FAILED_VALIDATION
CANCELLED_USER
CANCELLED_KILL_SWITCH

    Reliability and cost calculations¶

    Suppose a fixed four-step workflow has independent success probabilities 0.999, 0.995, 0.998, and 0.999:

    all-step success = 0.999 * 0.995 * 0.998 * 0.999 = 0.991025

    Suppose an agent requires 10 successful steps, each with an illustrative independent success of 0.98:

    all-step success = 0.98^10 = 0.817073

    [Derived] Added mandatory steps can reduce completion reliability. Dependence invalidates the product of marginal success probabilities but does not determine the direction of error: common failures can increase joint success relative to independent fixed marginals, while changed outage exposure can worsen the marginals themselves. These products illustrate sensitivity; they are not availability forecasts. See the explicit counterexamples and primary reliability reference in Lab 07.

    For a router followed by three parallel workers and a join:

    router p95 = 80 ms
worker p95 values = 300, 420, 250 ms
join and validation = 60 ms
naive critical-path budget = 80 + max(300,420,250) + 60 = 560 ms

    Actual end-to-end p95 is not generally the sum of stage p95s. Measure joint traces under load, including queueing.

    If 50 requests/s spawn 3 workers and 5% of workers retry once:

    base worker attempts/s = 50 * 3 = 150
retry attempts/s = 150 * 0.05 = 7.5
total worker attempts/s = 157.5
attempt amplification = 157.5 / 150 = 1.05

    Failures and recovery¶

    Failure Evidence Safe behavior
    router misclassification confusion slice and downstream correction disagree route to safe general path or human
    chain schema drift producer output fails consumer version compatibility adapter or rollback
    parallel fan-out overload child attempts rise faster than parent requests admission and aggregate child budget
    worker contradiction typed results disagree on same fact/version preserve conflict and escalate
    evaluator loop repeated defects or negligible score gain stop with partial artifact
    agent nonprogress repeated normalized action and observation terminate; do not reset budget
    timeout after commit no response but operation-key lookup finds effect record reconciled result; no duplicate write
    model provider outage model stage unavailable deterministic queue, safe read-only fallback, or fail
    prompt injection proposes action untrusted content correlates with denied proposal preserve denial evidence; remove unsafe capability
    kill switch activated policy version removes write tools complete reads or stop at safe boundary

    See Failure Cards and RAG and Agent Security.

    Security and side effects¶

    • Keep credentials inside the tool gateway; the model sees tool names and bounded schemas, not secrets.
    • Bind capabilities to principal, tenant, purpose, action, resource, expiry, and policy version.
    • Treat user, retrieved, web, email, image, and tool-result text as untrusted.
    • Reauthorize every call. A prior model decision or approval is not authorization.
    • Use strict input and output schemas, business preconditions, destination controls, and response-size limits.
    • Require approval over exact normalized arguments for high-impact actions.
    • Use stable operation keys, payload digests, status lookup, and explicit unknown-outcome states.
    • Compensate only through domain-approved actions; do not pretend compensation erases history.
    • Log redacted evidence and retain a per-tool kill switch.

    Evaluation and observability¶

    Offline suite¶

    • route accuracy and cost-weighted confusion;
    • per-step schema validity and deterministic gate pass rate;
    • end-to-end task success, partial utility, and false-success rate;
    • tool selection and argument correctness;
    • unknown-outcome reconciliation and duplicate-effect tests;
    • stopping precision: unnecessary stop versus harmful continuation;
    • prompt-injection and capability-escalation suites;
    • latency, attempts, tokens, and spend distributions;
    • human override and approval-quality review.

    Production telemetry¶

    Record logical run, parent/child relationship, state transition, model/prompt/tool/policy versions, proposed action, authorization result, operation key, redacted result digest, budgets before and after, stop reason, and final validation. High-cardinality traces need sampling and protected access, but invariant counters are unsampled.

    Monitor:

    • success, partial, abstention, and false-success audits;
    • steps and repeated actions per run;
    • child fan-out and depth;
    • logical runs versus model and tool attempts;
    • token, latency, queue age, and spend percentiles;
    • policy denials and approval age;
    • unknown outcomes, reconciliations, and duplicate suppression;
    • tool error by version;
    • kill-switch activations and writes attempted after removal, which must be zero.

    Migration and rollout¶

    1. Begin with a deterministic baseline and representative task set.
    2. Add one model-assisted step in shadow mode; preserve baseline outputs.
    3. Compare task quality, route errors, latency, cost, and safety slices.
    4. Introduce read-only tools with narrow capabilities.
    5. Shadow model-proposed writes without execution.
    6. Enable low-risk reversible writes behind exact approval and low limits.
    7. Canary prompt, model, workflow, tool schema, and policy changes as compatible bundles.
    8. Keep event readers tolerant of old versions and tool adapters available through the replay window.
    9. Roll back by activating a known-good bundle and removing capabilities; do not rewrite run history.
    10. Retire old schemas only after active, paused, and replayable runs no longer require them.

    Interview exercise¶

    Design an operations assistant that investigates incidents, queries metrics and logs, drafts mitigations, and may restart one low-risk service after approval. Inputs can contain untrusted log text. The system must finish within five minutes and remain safe during tool timeouts and model outages.

    Choose among router, chain, parallel workers, orchestrator-worker, evaluator-optimizer, and a bounded ReAct loop. Define authority classes, budgets, typed state, progress, stopping, idempotency, approval, evaluation, telemetry, and migration.

    L5 and L6 signals¶

    L5¶

    • Uses deterministic workflows for known controls and model choice only where justified.
    • Defines cumulative step, tool, token, time, fan-out, and spend budgets.
    • Treats actions as typed proposals and reconciles timeout-after-commit.
    • Gives concrete progress and stopping rules.
    • Quantifies serial reliability, critical path, or fan-out attempts.
    • Evaluates route, step, tool, safety, and end-to-end outcomes separately.

    L6¶

    • Establishes organization-wide authority classes, capability policy, and exception governance.
    • Quantifies correlated provider/tool/region failure and receiver capacity.
    • Defines compatible workflow, event, prompt, model, policy, and tool migrations for paused runs.
    • Allocates autonomy cost and incident risk to owning products.
    • Names falsifying evidence, retention, review cadence, and rollback authority.

    Final design checklist¶

    • The simplest sufficient pattern was evaluated first.
    • Deterministic controls own identity, policy, spend, validation, and approval.
    • Every run and child run consumes bounded cumulative budgets.
    • Progress and every terminal reason are machine-checkable.
    • Unknown side-effect outcomes reconcile before retry.
    • Evaluation includes false success, safety, latency, and cost.
    • Write capabilities can be removed independently.
    • Migration supports active, paused, and replayed runs.
