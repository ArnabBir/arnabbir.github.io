    AI Security and Guardrails¶

    AI security protects data, model behavior, tools, and downstream effects across an untrusted content pipeline. Guardrails reduce risk, but deterministic identity, authorization, isolation, validation, and audit remain the authority boundary.

    Threat model and trust boundaries¶

    Treat user text, retrieved documents, model output, tool output, memory, and provider responses as untrusted data. A prompt is not an access-control policy. A model must not receive ambient credentials or invent authority from natural language.

    flowchart TB
    U[User and untrusted input] --> G[Identity and policy gateway]
    D[Retrieved untrusted data] --> C[Context builder]
    G --> C
    C --> M[Model]
    M --> V[Schema and safety validation]
    V --> T[Capability broker]
    T --> X[Sandboxed tool]
    X --> V
    V --> R[Response or approval]
    G --> A[(Audit)]
    T --> A
    V --> A

    Threat actors include malicious users, compromised data sources, overprivileged workloads, insiders, dependency or model-supply-chain attackers, and accidental misuse by authorized users.

    Security invariants¶

    1. Authorization is evaluated outside the model against authenticated principal, action, resource, purpose, and context.
    2. Retrieved content and tool output cannot modify system policy or grant capabilities.
    3. Every side effect uses a typed, least-privilege, short-lived capability bound to an exact principal and operation.
    4. High-impact or irreversible actions require deterministic validation and, where policy requires, approval of the exact proposed action.
    5. Secrets never enter prompts, model-visible logs, retrieval indexes, or client-visible errors.
    6. Provider and regional routing enforce data class before content leaves the trust boundary.
    7. A kill switch can disable a model route, tool, tenant, or action class without waiting for redeployment.
    8. Safety-system failure degrades capability; it never expands authority.

    Policy and capability contracts¶

    {
  "principal": "user:882",
  "action": "refund.propose",
  "resource": "order:771",
  "purpose": "support_resolution",
  "data_class": "restricted",

    "tool": "refunds.create",
    "max_amount_minor": 5000,
    "currency": "INR",

  },

    SecurityDecision(id, principal, action, resource, context_digest,
                 policy_version, result, reason_codes, evaluated_at)
Capability(id, decision_id, tool, operation_key, constraints,
           audience, issued_at, expires_at, state)

    The model may propose tool arguments. The capability broker rejects unknown fields in authority-bearing inputs, canonicalizes valid arguments, authorizes the exact operation, and issues a constrained call. Silently stripping a field can change what a caller or approver thought was requested. The tool verifies the capability again; approval of refund.propose alone cannot authorize refunds.create in the illustrative request above.

    Defense pipeline¶

    sequenceDiagram
    autonumber
    participant U as User
    participant G as Gateway
    participant M as Model
    participant B as Capability broker
    participant T as Tool
    U->>G: Request plus identity
    G->>G: Classify data and authorize task
    G->>M: Delimited untrusted context
    M-->>G: Typed proposal
    G->>B: Principal plus exact proposal
    B->>B: Policy, schema, limit, approval
    B->>T: Scoped capability and operation key
    T-->>B: Result or unknown outcome
    B-->>G: Validated result and audit ID
    G-->>U: Response or safe denial

    Controls belong at multiple layers:

    Layer Controls
    edge authentication, rate limits, abuse detection, request size
    context source trust labels, ACL filters, delimiters, content scanning
    model approved route, bounded input/output, safety configuration
    output schema validation, policy filters, citation/support checks
    tools capability, argument allowlist, egress policy, sandbox, idempotency
    effects approval, transaction limits, reconciliation, compensation
    operations audit, anomaly detection, kill switches, incident response

    Prompt injection and data exfiltration¶

    Prompt injection is a control-flow confusion problem: untrusted data attempts to act like instructions. Delimit content, preserve source identity, state that data is non-authoritative, and prefer structured extraction before generation. These techniques reduce risk but do not enforce authorization.

    Block sensitive tool output from returning to the model unless the task needs it. Apply egress allowlists, response-size limits, and field-level filtering. Detect encoded or fragmented exfiltration attempts in red-team tests, but do not rely on a classifier as the sole boundary.

    The browser is another egress sink. Sanitize rendered Markdown/HTML, reject active URL schemes, and disable or proxy external images under an explicit policy: a generated image URL can leak context without any tool call. Use parameterized database calls and typed argument arrays instead of executing model-produced SQL or shell text. OWASP LLM05:2025, verified 2026-09-08, documents these output-handling risks. Validation after provisional streaming cannot retract a disclosure already delivered to the client.

    For retrieval, enforce ACL and deletion before candidate material leaves the store. Reauthorize cache hits. A semantic cache key must include tenant, principal-scope digest, purpose, policy, model/prompt version, and relevant context epoch. Store source membership so a hit can be rechecked against current permissions and tombstones. Semantic similarity does not justify reuse when amounts, identifiers, dates, or negation change the task; require exact matching for these authority-bearing fields or bypass semantic caching.

    Risk and control calculations¶

    Track exposure with explicit denominators:

    unauthorized_effect_rate
= unauthorized_committed_effects / committed_effects

guardrail_false_negative_rate
= known_unsafe_outputs_allowed / known_unsafe_outputs

residual_risk_score
= likelihood * impact * exposure_after_controls

remaining_acceptance_window
<= remaining_token_TTL + allowed_clock_skew

    unauthorized_effect_rate has a zero target, but a zero observation does not prove impossibility. Use adversarial coverage, invariant monitoring, and independent audit. Risk scores prioritize work; they do not waive mandatory controls.

    The acceptance-window bound assumes every receiver checks expiry, bounded clock error, no refresh or token exchange, and no new delegated credential. With enforced revocation, take the minimum of that expiry bound and the time until every receiver applies revocation. It bounds acceptance of new calls, not damage: already authorized jobs, created credentials, committed effects, and copied data can outlive the token. Count unauthorized effects separately even when no legitimate effects occur; a zero denominator is undefined, not a zero rate.

    Approval and action state¶

    stateDiagram-v2
    direction LR
    [*] --> Proposed
    Proposed --> Denied: policy or validation fails
    Proposed --> AwaitingApproval: approval required
    Proposed --> Authorized: no approval required
    AwaitingApproval --> Authorized: exact proposal approved
    AwaitingApproval --> Expired
    Authorized --> Executing
    Executing --> Committed
    Executing --> Unknown
    Unknown --> Committed: reconciliation finds effect
    Unknown --> SafeToRetry: safe-retry evidence
    SafeToRetry --> Executing: reauthorize same key

    Approval binds principal, resource, canonical arguments, model/tool/policy versions, expiry, and operation key. Editing after approval creates a new proposal.

    A negative status lookup is not sufficient for SafeToRetry: it may lag or race the first call. Require authoritative terminal rejection or a receiving-system contract that safely deduplicates concurrent same-key retries within its retention window. Preserve the reservation and unknown state otherwise. Stripe's contract, verified 2026-09-08, explicitly limits retained-key behavior; local bookkeeping cannot extend a remote provider's guarantee.

    Failure, security, and testing¶

    Threat or failure Control Required evidence
    direct injection task policy and typed output malicious instruction corpus
    indirect injection untrusted-source labels and no implicit tools poisoned retrieval test
    overprivileged tool scoped capability and server-side validation denied out-of-scope arguments
    secret exposure brokered credentials and redaction seeded-secret scan across telemetry
    cross-tenant retrieval storage-layer ACL adversarial tenant fixture
    model/provider compromise signed bundle, route kill switch isolation and evacuation drill
    safety classifier outage fail-safe degraded mode dependency-failure test
    timeout after effect operation key and reconciliation crash-after-commit test

    Build a threat corpus by task, language, encoding, source type, and tool. Include multi-turn escalation, social engineering, obfuscation, data poisoning, denial-of-wallet, output parser attacks, cross-tenant cache attempts, and malicious files. Measure bypasses separately by control stage.

    Fuzz typed tool arguments and reject unknown fields. Test policy cache expiry, clock skew, revoked identities, expired approvals, egress denial, sandbox escape assumptions, provider logging settings, and audit loss. Run exercises with safety classifiers unavailable; the system should reduce capability predictably.

    Incident response¶

    Contain by principal, tenant, model route, prompt version, data source, tool, or action class. Preserve evidence before purging caches. Rotate credentials that may have entered model-visible context. Reconcile external effects and notify data/security owners under the applicable policy.

    Exit criteria include blocked exploit replay, clean secret scan, verified affected-scope query, completed effect reconciliation, patched control, restored monitoring, and approved reopening. A prompt edit alone is not sufficient incident closure.

    Migration and evolution¶

    1. Inventory every model, context source, tool, capability, provider route, and side effect.
    2. Add policy decisions and audit in observe-only mode without granting new access.
    3. Introduce the capability broker for read-only tools, then bounded writes.
    4. Shadow new guardrails and compare false positives/negatives on frozen threat sets.
    5. Rotate policy, classifier, and prompt versions through signed bundles.
    6. Remove ambient credentials only after all call paths use workload identity or brokered capabilities.
    7. Retire old routes after caches, paused workflows, audit windows, and rollback requirements expire.

    Interview exercise¶

    Design security for an incident-response copilot that reads internal telemetry, retrieves runbooks, drafts commands, and may execute a bounded rollback after approval. Attackers can place text in logs and tickets. Define trust boundaries, identities, context handling, capability contracts, approval binding, unknown outcomes, egress, audit, kill switches, red-team metrics, and incident recovery.

    L5 and L6 signals¶

    L5¶

    • Treats all content and model output as untrusted.
    • Enforces authorization and typed capabilities outside the model.
    • Binds approvals to exact actions and reconciles unknown outcomes.
    • Protects secrets, tenants, caches, routes, and audit evidence.
    • Defines threat tests, degraded modes, and kill switches.

    L6¶

    • Establishes enterprise action classes, trust labels, capability standards, and exception authority.
    • Quantifies provider, identity, and policy-system concentration risk.
    • Governs red-team corpora, incident evidence, retention, and control ownership.
    • Plans cross-product credential, policy, and tool migrations with rollback.
    • Connects safety posture to availability, review capacity, and portfolio economics.

    Final design checklist¶

    • The model has no ambient authority or credentials.
    • Authorization binds exact principal, action, resource, purpose, and context.
    • Retrieved data cannot grant capability.
    • Tool arguments are canonical, typed, bounded, and revalidated server-side.
    • Approval binds the exact effect and expires.
    • Unknown outcomes reconcile before retry.
    • Provider routes enforce data class and retention.
    • Kill switches and incident exit evidence are tested.
