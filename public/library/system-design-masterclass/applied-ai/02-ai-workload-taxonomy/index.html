    AI Workload Taxonomy¶

    AI systems fail when unlike work shares one queue, one SLO, or one scaling signal. Classify work by execution shape, resource demand, state, quality risk, and deadline before choosing infrastructure.

    1. Classification dimensions¶

    Do not classify only by model family. A transformer can power a two-second interactive request, an hour-long batch job, an embedding backfill, or a tool-using workflow. Those workloads need different contracts.

    Dimension Questions Architecture consequence
    arrival steady, bursty, scheduled, or event-driven? reserve, queue, or elastic batch
    deadline milliseconds, seconds, minutes, or none? synchronous path versus durable job
    unit of work row, document, image, sequence, token, or episode? partition and admission key
    resource vector CPU, RAM, accelerator compute, accelerator memory, I/O, network? placement and isolation
    variability bounded or long-tailed input/output? queue policy and straggler handling
    state stateless, cached context, online features, or workflow checkpoint? affinity and recovery
    result semantics score, rank, text, artifact, or side effect? validation and idempotency
    quality evidence immediate label, delayed label, rubric, or no ground truth? release and monitoring plan
    data class public, internal, confidential, regulated? route, region, retention, isolation
    reversibility advisory, user-visible, financial, or physical action? approval and audit

    Principle: Schedule and admit AI work by its constrained resources and deadline, not by request count or model name.

    2. Primary workload families¶

    Online discriminative inference¶

    Examples include fraud scores, ranking, classification, forecasting, and anomaly scores. Inputs are commonly structured features; outputs are small and bounded. The critical path often includes online feature reads, preprocessing, model execution, and decision policy. Tail latency, feature freshness, calibration, and fallback dominate.

    Read Online Model Serving and the Fraud Detection case study.

    Online generative inference¶

    Input and output length vary. Streaming exposes time to first token and inter-token latency separately. The scheduler must budget prompt processing, generated tokens, KV-cache memory, cancellation, and tenant fairness. See GPU Inference Platforms for runtime depth.

    Batch inference¶

    Millions of independent or weakly dependent records are scored against a pinned model and snapshot. Throughput, restartability, deterministic output identity, stragglers, and publication matter more than per-row latency. See Batch and Bulk Inference.

    Embedding and indexing¶

    Documents or entities are transformed into vectors, then written into a compatible index generation. It is a dual-write migration problem: a new embedding model defines a new coordinate space and cannot safely query an old index. See Embeddings and Vector Retrieval.

    Training, tuning, and evaluation¶

    These are long-running, artifact-producing jobs over versioned data. They require reproducibility, checkpointing, lineage, fair accelerator scheduling, and signed evaluation. Training completion is not release approval. See ML and AI Pipelines and Production AI Lifecycle.

    Durable AI workflow or agent¶

    A run may retrieve, call tools, wait for approval, and resume. Step count and cost vary, and tool outcomes can be unknown after timeout. The source of truth is durable workflow state, not model conversation text. Prefer deterministic workflows whenever the path is known. Use RAG and Agent Security for authority and containment.

    Streaming feature and prediction workloads¶

    Events update windows, features, indexes, or decisions continuously. Correctness depends on event time, watermarking, duplicates, late data, and replay. The online path reads a materialized projection; it should not reconstruct an unbounded stream window synchronously. See Streaming Aggregation and Messaging and Streams.

    2A. Model behavior and selection¶

    Workload shape tells the platform how to execute. Model behavior tells the product what can fail and what evidence is required. Select a model only after defining the task, answerability boundary, quality/safety errors, context distribution, latency, data class, authority, and cost ceiling.

    Base and instruction-tuned models¶

    A base model is trained primarily to continue its input distribution. An instruction-tuned model receives additional adaptation to follow instructions, conversation formats, preferences, or safety behavior. The distinction is about the artifact and training history, not a guarantee of capability or safety.

    Use an instruction-tuned model for general assistants and typed interaction unless evaluation demonstrates a reason not to. A base model can be appropriate for controlled completion, research, domain adaptation, or a pipeline that supplies its own training. Do not expose a base model as an assistant merely by adding a system prompt.

    Selection evidence must include:

    • exact model and tokenizer revision;
    • expected chat or completion template;
    • stop and structured-output behavior;
    • task and critical-slice evaluation;
    • prompt-injection and refusal behavior for the intended authority;
    • serving latency, memory, throughput, and cost under the real length distribution.

    Dense and mixture-of-experts models¶

    A dense model activates its model path broadly for each token. A mixture-of-experts (MoE) model routes token representations through a subset of expert components. Parameter count, active compute, memory footprint, and communication cost therefore answer different questions.

    flowchart LR
    A[Token representation] --> B{Architecture}
    B -- dense --> C[Shared dense blocks]
    B -- MoE --> D[Router]
    D --> E[Expert 1]
    D --> F[Expert 2]
    D --> G[Other experts]
    E --> H[Combined output]
    F --> H
    G --> H
    C --> H

    Do not infer serving cost from total parameters alone. For MoE, measure active parameters, weight residency, expert balance, interconnect traffic, batch behavior, and tail effects. Routing imbalance can create hot experts even when average accelerator utilization looks healthy. Dense models are not automatically cheaper; model size, precision, runtime, batching, and output length still dominate.

    The diagram depicts alternative selected experts, not a requirement to execute every branch per token. Switch Transformers, verified 2026-09-08, uses sparse routing; its reported training speedups are not serving-throughput guarantees. A model's context limit similarly does not establish evidence-use quality: Lost in the Middle reports position sensitivity on its evaluated tasks and models, motivating local position/length tests rather than a universal defect claim.

    Context windows and effective context¶

    The advertised context window is a hard compatibility limit, not proof that every position is equally useful for every task. Define:

    context_budget
= system_and_policy_tokens
 + tool_schema_tokens
 + conversation_tokens
 + retrieved_context_tokens
 + reserved_output_tokens
 + safety_margin_tokens

    For a 32,768-token limit with 1,200 system/policy, 2,000 tool schema, 6,000 conversation, 12,000 retrieval, 4,000 reserved output, and 10% safety margin on the hard limit:

    used_before_margin = 25,200
safety_margin      = 3,277
remaining          = 32,768 - 25,200 - 3,277 = 4,291 tokens

    Specify truncation by semantic priority, never by accidental string order. Preserve system policy and exact tool schemas. Summarize or retrieve older conversation with provenance. Drop low-value candidates before required evidence. Re-run evaluation across length and evidence-position slices because long-context behavior can degrade before the hard limit.

    Context cost also changes admission and cache pressure. Two requests with the same QPS can have radically different prefill work and KV-cache demand.

    Reasoning-oriented models¶

    Some model products expose behavior optimized for multi-step reasoning or additional internal inference work. Treat that as a different workload class when it changes latency, output accounting, cancellation, observability, or cost.

    Use reasoning-oriented models when task-level paired evaluation shows enough gain to justify their tail latency and spend. Bound total deliberation and output. Do not expose hidden reasoning as an audit explanation; preserve task evidence, citations, tool records, policy decisions, and concise user-facing reasons instead.

    Route simple classification, extraction, and deterministic transformations to smaller specialized paths when they meet the error contract. A routing model adds its own false-route error and needs evaluation by task and slice.

    Multimodal models¶

    Multimodal input changes ingestion and threat boundaries. Images, audio, video, and documents need media validation, decoding limits, malware handling, OCR or transcription provenance, temporal/positional references, and modality-specific evaluation.

    Represent work as a modality-aware resource vector:

    multimodal_demand = {
  text_tokens,
  image_patch_or_provider_units,
  audio_seconds,
  video_frames_or_seconds
}

    Provider units are not interchangeable and must not be added directly. Benchmark the exact media size, resolution, frame sampling, and preprocessing. Convert components to a scalar only through an explicit provider-specific pricing function or a measured service-time/compute model. Evaluate text-only, modality-only, conflicting-modality, low-quality, accessibility, language, and injection slices. A caption generated upstream is a derived artifact with a version and error surface, not the original image.

    Hosted, open-weight, and specialized choices¶

    Hosted model API: the provider operates weights and runtime. It can reduce time to first production use, but introduces provider policy, quota, retention, region, version, telemetry, and concentration dependencies.

    Open-weight deployment: the operator can inspect and host released weights under their license. It increases control over routing, isolation, adaptation, and lifecycle, while transferring runtime, security, evaluation, capacity, and patch responsibility to the operator. Open weights do not imply open training data, open source, or unrestricted use.

    Specialized model or deterministic system: a smaller classifier, reranker, embedding model, OCR engine, speech model, rules engine, or domain model can outperform a general generator on a bounded task's latency, cost, determinism, or evaluation burden.

    Use a model-selection ADR rather than a leaderboard screenshot:

    ModelSelectionADR(
  task_contract, candidates, baseline,
  model_and_tokenizer_versions,
  data_and_license_constraints,
  quality_and_safety_evidence,
  context_and_modality_limits,
  latency_capacity_and_cost_curves,
  provider_region_and_retention,
  portability_and_exit_plan,
  decision, owner, review_trigger, date
)

    flowchart TD
    A[Task and error contract] --> B{Deterministic or specialized path passes?}
    B -- yes --> C[Choose simpler path]
    B -- no --> D{Data may leave controlled boundary?}
    D -- no --> E[Evaluate approved self-hosted weights]
    D -- yes --> F[Evaluate hosted and self-hosted candidates]
    E --> G[Paired quality safety and operations gate]
    F --> G
    G --> H{Meets SLO and cost with reserve?}
    H -- no --> I[Adapt task prompt retrieval or capacity]
    H -- yes --> J[Record ADR and fallback]

    Minimum ADR alternatives:

    Question Hosted Open-weight/self-hosted Specialized
    quality task evidence for exact provider revision task evidence for exact artifact/runtime direct bounded-task evidence
    data retention, training-use, region, subprocessors operator controls plus infrastructure exposure depends on deployment
    operations quota, rate limits, version changes accelerator, runtime, patches, scaling often simpler but task-limited
    cost token/media/tool pricing and retry effects utilization, idle reserve, labor, energy task unit economics
    exit compatible provider route and export limits artifact/runtime portability compose with broader fallback

    Review the ADR when the task changes, critical slices regress, provider terms or regions change, a model is deprecated, utilization crosses the safe envelope, or a simpler candidate meets the contract. The approved route is a versioned portfolio, not a permanent vendor preference.

    3. Workload decision tree¶

    flowchart TD
    A[Need a result] --> B{User waits now?}
    B -- yes --> C{Bounded execution?}
    C -- yes --> D[Online serving]
    C -- no --> E[Accept job and stream status]
    B -- no --> F{Many independent items?}
    F -- yes --> G[Batch or bulk inference]
    F -- no --> H{Known step graph?}
    H -- yes --> I[Durable deterministic workflow]
    H -- no --> J[Bounded planner with tools]
    D --> K{Needs fresh features?}
    K -- yes --> L[Online feature projection]
    K -- no --> M[Request-contained input]
    G --> N{Creates new vector space?}
    N -- yes --> O[Versioned embedding and index build]

    The decision tree chooses execution semantics, not a product. A single user feature may traverse several families: asynchronous document ingestion, batch embedding, online retrieval, generative serving, and delayed evaluation.

    4. Sync, async, streaming, and deferred contracts¶

    Contract Return Best fit Failure semantics
    synchronous unary final result bounded score or short generation timeout and safe retry
    server stream partial output plus final status token generation partial prefix, cancellation, resume policy
    asynchronous job accepted job ID bulk and long-running work durable state and polling/callback
    event-driven acknowledged event projection and enrichment replay, dedupe, watermark
    human-deferred pending decision high-impact ambiguous action approval expiry and reassessment

    A synchronous HTTP timeout must not erase work that should be durable. Conversely, wrapping a 100 ms score in a job API adds state and operational surface with little value.

    5. Resource vectors and interference¶

    Represent each class as a vector rather than one utilization number:

    Demand = {
  input_tokens,
  output_tokens,
  cpu_ms,
  gpu_ms,
  gpu_memory_bytes,
  feature_reads,
  index_candidates,
  network_bytes,
  deadline,
  spend
}

    Common interference patterns:

    • large prefills delay decode iterations;
    • batch embedding fills accelerator queues needed by interactive generation;
    • feature backfills overload the same database used by online prediction;
    • one tenant's long contexts consume shared KV memory;
    • vector compaction or graph builds compete with search replicas;
    • shadow traffic consumes real capacity while appearing absent from product QPS;
    • tool retries amplify downstream writes and cost.

    Use separate pools when deadline, security boundary, failure domain, or resource shape differs materially. Use shared pools when utilization gain exceeds isolation and scheduling complexity.

    6. Capacity example¶

    Assumption (2026-09, illustrative): One regional fleet receives 80 interactive requests/s with 2,500 input and 300 output tokens on average. A nightly batch adds 60 million documents of 500 input tokens over a six-hour window. Interactive target utilization is 60%; batch may use only residual capacity.

    Interactive demand:

    input  = 80 * 2,500 = 200,000 input tokens/s
output = 80 * 300   = 24,000 output tokens/s

    Batch input demand to finish in six hours:

    60,000,000 * 500 / (6 * 3,600)
= 1,388,889 input tokens/s

    The batch is roughly seven times the interactive input-token rate. Request QPS obscures that difference. Run batch in a preemptible class with a completion forecast, and reserve measured interactive capacity. If shared workers cannot preempt safely or batch destroys cache locality, use separate pools.

    Little's Law still applies to stable queues. If interactive arrival is 80/s and mean end-to-end time is 2.5 seconds, mean concurrency is 80 * 2.5 = 200. This is not a safe concurrency limit: p95 length, bursts, and failure reserve require a distribution-aware benchmark.

    7. Admission and scheduling matrix¶

    Workload Admission unit Queue discipline Shed or preempt first Recovery unit
    online score request plus feature fan-out deadline with tenant quota optional features/shadows request
    generation prompt/output tokens plus KV bytes weighted deadline/fair queue batch, long optional output sequence
    batch score partition bytes and estimated compute weighted fair-share low-priority job partition
    training accelerator-hours and topology quota/reservation experiments checkpoint
    embedding build records, tokens, output bytes throughput/fair-share stale rebuild partition/generation
    workflow steps, tool calls, wall time, spend per-run plus tool pools optional branches durable step
    stream feature partitions and event lag lag-aware noncritical projection source offset

    Benchmark (measurement requirement, 2026-09): Build service curves per workload class by sweeping concurrency and realistic size distributions. Record queue time, service time, throughput, memory, errors, quality, and cost. The safe envelope ends before latency becomes unstable, not at the highest observed throughput point.

    8. Data, APIs, and state¶

    Expose the execution contract explicitly:

    WorkRequest(id, tenant, class, input_ref, version_bundle, budget, deadline, priority)
WorkAttempt(id, request_id, worker, start, lease, checkpoint, resource_usage, outcome)
Artifact(id, request_id, type, uri, digest, schema, created_at)
Publication(id, artifact_ids, manifest_digest, state, activated_at)

    For asynchronous work:

    POST /v1/inference-jobs
Idempotency-Key: job-key-31

GET /v1/inference-jobs/{job_id}
POST /v1/inference-jobs/{job_id}:cancel

    POST returns the same job for a repeated idempotency key and equivalent normalized request. Status distinguishes QUEUED, RUNNING, CANCELLING, SUCCEEDED, FAILED, and CANCELLED. Cancellation is cooperative and the response states whether publication already happened.

    For online work, return explicit completion reasons such as stop, length, policy_block, budget, deadline, and dependency_failure. A partial stream is not a successful final result until its terminal record is durable.

    9. Reliability by workload shape¶

    Interactive¶

    Bound queues and reject early. Propagate deadlines. Keep retries within the original budget. Separate fallback eligibility by data class and task. Preserve capacity for health and recovery traffic.

    Batch and training¶

    Lease partitions, checkpoint progress, make output identity deterministic, and commit manifests atomically. A worker loss should replay one partition, not the entire dataset. Detect poison records separately from transient infrastructure errors.

    Streaming¶

    Coordinate source positions, operator state, and sink recovery at the checkpoint boundary. A transactional sink may prepare output before checkpoint completion and publish it afterward under the recovery protocol; an idempotent sink may publish earlier and safely repeat writes. Persisting offsets alone is not an exactly-once guarantee. Expect duplicates and late events, track event-time lag and replay boundaries, and keep schema and feature versions in output keys.

    Workflows¶

    Persist the state transition before acknowledging it. Reconcile unknown external outcomes before retry. Compensation is a domain action, not database rollback. Pin tool schema and policy versions for replay.

    The failure cards map common symptoms to discriminating evidence.

    10. Observability and testing¶

    Every metric should identify workload class, tenant tier, version bundle, route, and outcome without exposing sensitive payloads.

    Measure:

    • arrivals, admissions, queue age, service time, and deadline misses;
    • input/output units, size distributions, concurrency, memory, and accelerator utilization;
    • feature and retrieval fan-out, freshness, empty results, and cache behavior;
    • attempts per logical request, cancellations, wasted work, and fallback reasons;
    • quality and safety by stage and slice;
    • job progress, stragglers, retries, poison records, and publication lag;
    • cost per successful result and reserved-but-idle capacity.

    Test each family differently: deterministic contract fixtures for APIs; load curves for online service; kill/restart and duplicate delivery for jobs; exact-neighbor comparison for ANN; replay and point-in-time tests for features; prompt injection and authorization tests for tool systems.

    11. Product and vendor boundaries¶

    Managed services can implement endpoints, queues, training jobs, or indexes, but product names do not remove workload semantics.

    Vendor (KServe 0.20.0, released 2026-08-06): KServe documents InferenceService resources for predictive and generative model serving on Kubernetes, including deployment modes and autoscaling integrations. These capabilities do not define an application's label maturity, fallback safety, or release evidence. KServe 0.20.0 source and documentation

    Production report (Netflix, published 2019-12-03): Netflix introduced Metaflow as a framework developed for its data-science workflows, emphasizing versioned code/data, execution, and scaling. The report describes Netflix's context; it does not imply that interactive serving and workflow orchestration should share one scheduler. Open-Sourcing Metaflow

    12. Tradeoffs and evolution triggers¶

    Current choice Revisit when Likely evolution
    shared online/batch fleet preemption misses SLO or cache interference rises reserved interactive plus elastic batch pools
    synchronous generation clients disconnect or work exceeds bounded deadline durable job with stream/poll status
    one regional endpoint residency or correlated provider failure matters policy-aware regional/provider routes
    full recompute corpus growth breaks completion window snapshot plus incremental delta
    one queue tenant or length skew causes starvation hierarchical class and tenant fairness
    generic autoscaling queue delay rises before utilization demand-aware scaling with warm reserve

    13. Interview exercise¶

    Prompt: Design one platform for a retailer with product embeddings, interactive recommendations, nightly demand forecasts, a customer chat assistant, and an internal agent that may draft inventory transfers.

    An L5 answer should refuse the premise that "one platform" means one runtime. Define shared control-plane capabilities - identity, registry, version bundles, evaluation, cost attribution, and policy - while assigning separate execution contracts and pools. Quantify each unit of work, choose synchronous or durable interfaces, isolate interactive capacity, and define workload-specific recovery.

    An L6 answer should also define organization-wide workload classes, exception policy, capacity reservations, region/provider concentration, artifact lineage, common telemetry dimensions, and when teams may bypass shared infrastructure. The agent remains draft-only until exact action authorization, approval, and idempotency exist.

    L5 and L6 signals¶

    L5¶

    • Classifies by deadline, resource vector, variability, state, and result semantics.
    • Separates online, batch, stream, training, embedding, and workflow contracts.
    • Uses the correct admission and recovery unit for each class.
    • Quantifies demand in tokens, records, bytes, memory, and attempts.
    • Defines workload-specific failure, observability, and evaluation.

    L6¶

    • Designs shared policy without forcing unlike workloads onto one data plane.
    • Governs reservations, fairness, preemption, evacuation, and exception paths.
    • Accounts for fleet-wide shadows, backfills, retries, and idle reserve.
    • Establishes common lineage and telemetry across independently evolving runtimes.
    • Connects workload taxonomy to team ownership and capacity economics.

    Final summary¶

    Name the workload before naming the product. Choose an interface from the deadline and durability requirement. Admit against the real resource vector. Isolate classes whose SLO, security, or interference profile differs. Recover at a deterministic unit, record versions and evidence, and evaluate the result using a contract appropriate to its error modes.
