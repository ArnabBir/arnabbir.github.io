    Online Model Serving¶

    Online model serving turns a versioned model bundle into a latency-bounded, policy-controlled prediction service. The endpoint is only the visible edge. Correctness also depends on feature time, preprocessing compatibility, overload behavior, fallback semantics, release evidence, and a durable decision record.

    1. Scope and requirements¶

    Design a multi-region serving platform for ranking and risk models. It supports unary predictions, small request batches, multiple model versions, online features, canaries, and tested fallback.

    Requirements:

    • authenticate and authorize the task, subject, tenant, and data class;
    • bind each logical request to one compatible model, feature, preprocessing, schema, and policy bundle;
    • satisfy a declared end-to-end latency and availability SLO;
    • bound queueing, feature fan-out, batch wait, memory, attempts, and spend;
    • provide deterministic idempotency for product decisions where required;
    • fail safely when features, model runtime, region, or ledger is unavailable;
    • record enough evidence to evaluate delayed outcomes and reconstruct important decisions;
    • roll forward and back without mixing incompatible versions.

    This chapter focuses on the service boundary. For accelerator-specific prefill/decode scheduling, KV cache, and continuous batching, use GPU Inference Platforms.

    Principle: Autoscaling is a delayed capacity response. Bounded admission, queues, and fallback must protect the SLO while new model capacity loads.

    2. Request path and control plane¶

    flowchart LR
    C[Caller] --> E[Edge auth and deadline]
    E --> G[Model gateway]
    G --> A[Policy and admission]
    A --> F[Feature coordinator]
    F --> S[(Online feature store)]
    F --> P[Preprocess and validate]
    P --> Q[Deadline-aware batch queue]
    Q --> R[Model replica]
    R --> D[Decision policy]
    D --> C
    G --> L[(Prediction ledger)]
    F --> L
    R --> L
    D --> L
    M[Model control plane] --> G
    M --> R
    M --> F

    The gateway applies data-class and task policy before selecting a route. The serving runtime executes a pinned bundle. The decision-policy service converts scores into product actions, thresholds, reasons, or abstention. The model must not carry authority that belongs to the caller and policy.

    The control plane maintains desired model placements, compatibility bundles, warm capacity, quotas, releases, and retirement. It should not sit synchronously in every prediction path; replicas consume signed immutable configuration and report observed state.

    3. API and canonical state¶

    POST /v1/predictions/risk.score
Idempotency-Key: payment-721-risk-decision
X-Deadline-Ms: 120

{
  "tenant_id": "merchant-41",
  "entity": {"payment_id": "p-721", "account_id": "a-62"},
  "event_time": "2026-09-06T10:15:20.114Z",
  "request_features": {"amount_minor": 4200, "currency": "INR"},
  "constraints": {"data_class": "restricted", "region": "in"}
}

    {
  "request_id": "pred-902",
  "score": 0.82,
  "decision": "REVIEW",
  "reason_codes": ["velocity_high"],
  "bundle_id": "risk-in-2026-09-06.4",
  "feature_watermark": "2026-09-06T10:15:18Z"
}

    ServingBundle(id, model_digest, runtime, preprocess_digest, feature_view,
              request_schema, output_schema, policy_id, status)
Replica(id, bundle_id, region, zone, hardware, state, loaded_at, verified)
LogicalPrediction(id, idempotency_key, principal, entity, event_time,
                  input_digest, bundle_id, deadline, state)
Attempt(id, prediction_id, route, replica, start, queue_ms, feature_ms,
        model_ms, usage, outcome)
Decision(prediction_id, score_digest, action, reason_codes, policy_id, time)

    Idempotency scope follows the business operation. A repeated payment decision should return the committed result for the same normalized input. An exploratory recommendation request may intentionally produce a fresh ranked page and use a different consistency contract.

    The caller keeps the business-scoped idempotency key stable across transport and provider retries. Attempt numbers and provider request IDs are internal records under that one logical prediction; they never appear in the key used to deduplicate the product decision.

    3A. Generative model gateway¶

    A generative gateway is the policy, compatibility, and evidence boundary between product applications and model providers or self-hosted runtimes. It should normalize stable product semantics without pretending that all providers expose identical behavior.

    Gateway invariants¶

    1. Authenticate and authorize task, tenant, data class, model entitlement, tools, and region before provider routing.
    2. Bound input, output, wall time, attempts, concurrency, and spend on the logical request.
    3. Preserve one logical request across provider attempts; never bill or measure retries as independent user demand.
    4. A route is eligible only when model, prompt, structured-output, tool, safety, region, and retention requirements are compatible.
    5. Streaming ends with a terminal record containing finish reason, usage or usage-estimation status, route, and evidence ID.
    6. Unknown provider fields are retained in a controlled raw envelope when needed, but do not silently change normalized semantics.
    7. Fallback is task policy, not a generic retry to any available model.
    flowchart LR
    C[Client] --> E[Edge identity and limits]
    E --> N[Normalize logical request]
    N --> P[Policy and data classification]
    P --> R[Provider and model router]
    R --> A[Hosted provider A]
    R --> B[Hosted provider B]
    R --> S[Self-hosted runtime]
    A --> V[Stream and schema validator]
    B --> V
    S --> V
    V --> L[(Attempt and usage ledger)]
    V --> C

    Request and attempt contracts¶

    GenerationRequest(id, tenant, task, messages, context_refs,
                  response_schema, tool_set, data_class,
                  deadline, token_budget, spend_budget,
                  route_policy, version_bundle)
GenerationAttempt(id, request_id, provider, model_revision,
                  provider_request_id, start, first_byte, end,
                  token_usage, cache_usage, outcome, retry_reason)
StreamEvent(request_id, sequence, type, delta, usage, finish_reason, time)

    Normalized stream event types should be few and stable: response.started, content.delta, tool_call.delta, tool_call.completed, usage.updated, response.completed, and response.failed. Sequence numbers are monotonic per logical stream. The final event is durable before the gateway reports clean completion.

    Streaming behavior¶

    Server-Sent Events or another explicit streaming protocol should distinguish transport closure from model completion. A client disconnect triggers cancellation, but the gateway records whether provider work continued and whether usage is final, estimated, or unavailable.

    Do not buffer the full response merely to validate a terminal schema when latency requires streaming. Choose one of three explicit contracts:

    • stream untrusted draft text and mark it provisional until terminal validation;
    • buffer and validate before release for strict structured or high-impact output;
    • stream bounded fields that can be incrementally validated, then commit a terminal object.

    Backpressure must be bounded. If the client reads too slowly, pause provider reads where supported, buffer only to a declared limit, or cancel. Measure time to first token, inter-token gaps, total time, cancellation lag, and work produced after disconnect.

    Once a content prefix has reached the client, fallback needs an explicit stream contract. Do not append a second model's restarted answer to the first model's unfinished sentence. Either terminate with a partial-result error, or send a versioned replacement event that the client understands and start a new attempt segment. A reconnect may replay durable events by sequence; it does not promise that rerunning generation will reproduce the same tokens. Incomplete tool-call arguments remain non-executable.

    Provisional is a correctness label, not a confidentiality control. Once text reaches a client, later schema or safety failure cannot retract it. For sensitive output, validate before disclosure; sanitize any streamed Markdown/HTML and constrain browser-loaded URLs. This output-sink boundary is distinct from typed tool authorization; see OWASP LLM05:2025, verified 2026-09-08.

    Structured output¶

    Treat a provider's schema mode as constrained generation, not proof of domain validity. Validate again at the gateway with a pinned schema. Reject unknown fields where security requires it. Then apply semantic checks such as currency consistency, resource existence, amount limits, citation support, and policy.

    {
  "schema_id": "refund-proposal-v4",
  "type": "object",
  "required": ["order_id", "amount_minor", "currency", "reason"],
  "additionalProperties": false,
  "properties": {
    "order_id": {"type": "string"},
    "amount_minor": {"type": "integer", "minimum": 0},
    "currency": {"type": "string"},
    "reason": {"type": "string", "maxLength": 500}
  }
}

    Parser repair can hide model regressions. Record raw invalid output, repair attempt, repaired result, and whether the product accepts repaired output. Never use free-form repair for security-sensitive tool arguments.

    Provider routing and fallback¶

    flowchart TD
    A[Logical request] --> B{Task and data policy pass?}
    B -- no --> X[Deny]
    B -- yes --> C[Eligible route set]
    C --> D{Schema tool and context compatible?}
    D -- no --> X
    D -- yes --> E{Healthy within deadline and quota?}
    E -- no --> F{Approved fallback remains?}
    F -- no --> Y[Shed or defer]
    F -- yes --> BUD[Charge attempt budget and exclude failed route]
    BUD --> C
    E -- yes --> G[Reserve budget and dispatch]

    Score eligible routes using measured task quality, deadline success, capacity, data handling, and cost. Keep hard constraints separate from optimization. A lower-cost provider cannot override residency or safety gates.

    Use circuit breakers by provider, model, region, and failure class. A provider 429 may justify another route if budget and compatibility permit; malformed structured output is a model-behavior failure and should not trigger unlimited cross-provider retries. Reserve receiver quota and capacity before declaring fallback ready.

    Gateway tests include stream ordering, duplicate terminal events, disconnect, provider timeout, partial tool call, invalid UTF-8 or JSON, schema drift, usage missing, provider quota, incompatible fallback, data-region denial, and retry budget exhaustion.

    3B. Prompt and context engineering¶

    Prompt engineering is interface engineering. Version the instruction hierarchy, context selection, examples, tool schemas, output schema, and truncation policy as one behavior-bearing bundle.

    Prompt hierarchy¶

    Use explicit layers with decreasing authority:

    1. platform safety and non-negotiable policy;
    2. product/task instructions;
    3. developer workflow and output contract;
    4. authorized user request;
    5. retrieved documents, tool output, and quoted content as untrusted data.

    Provider-specific message roles may differ. Compile the canonical hierarchy into a provider adapter and test semantic parity. Retrieved text cannot become a higher-authority instruction because it contains phrases such as "system message".

    PromptBundle(id, canonical_template, provider_adapters,
             examples_manifest, tool_schema_set, output_schema,
             context_policy, truncation_policy, safety_policy,
             compatible_models, evaluation_run, digest)

    Context assembly and token budget¶

    flowchart LR
    A[System and task policy] --> H[Priority context assembler]
    B[Current user turn] --> H
    C[Conversation state] --> H
    D[Retrieved evidence] --> H
    E[Tool schemas] --> H
    F[Reserved output] --> H
    H --> T[Tokenizer-specific count]
    T -->|fits| M[Model request]
    T -->|over| P[Compress drop or reject by policy]
    P --> T
    hard_context_limit
>= system_tokens
 + task_tokens
 + user_tokens
 + conversation_tokens
 + retrieval_tokens
 + tool_schema_tokens
 + reserved_output_tokens
 + tokenization_margin

    For a 16,384-token model with 1,000 system/task tokens, 1,500 user/conversation tokens, 5,000 retrieval tokens, 2,000 tool-schema tokens, 3,000 reserved output tokens, and 5% margin on the hard limit:

    margin    = ceil(16,384 * 0.05) = 820
committed = 1,000 + 1,500 + 5,000 + 2,000 + 3,000 + 820
          = 13,320
headroom  = 16,384 - 13,320 = 3,064 tokens

    Count with the exact tokenizer and chat template. Reject or shorten before dispatch; provider-side truncation is not a context policy.

    Versioning and release¶

    A prompt change can alter safety, latency, token cost, retrieval use, and tool behavior. Release it like code:

    1. immutable prompt bundle and diff;
    2. static checks for missing variables, authority order, and schema compatibility;
    3. deterministic fixtures and injection corpus;
    4. paired offline evaluation by task and critical slice;
    5. shadow with tools disabled or isolated;
    6. stable-cohort canary;
    7. rollback pointer and cache invalidation.

    Record effective prompt bundle on every attempt. Do not interpolate runtime policy text from mutable stores without a version and digest.

    Prompt caching¶

    Cache only stable prefixes whose provider and data policy allow retention. Cache identity includes provider, model/tokenizer revision, prompt bundle, tenant/security domain, tool schema set, and relevant policy epoch.

    prompt_cache_key
= hash(provider, model_revision, tokenizer_revision,
       prompt_bundle_digest, tenant_scope,
       tool_schema_digest, policy_epoch, stable_prefix_digest)

    Never share personalized, restricted, or tenant-specific prefixes across security domains. Cache hits still require current authorization and deletion checks. Measure hit rate, saved input work, latency change, provider cache charges, stale rejections, and cross-tenant invariant violations.

    Context compression¶

    Prefer deterministic selection first: remove duplicates, retrieve fewer stronger candidates, omit unused tool schemas, and trim stale conversation. Use extractive compression when source spans and citations must survive. Abstractive summaries create a derived artifact with model/prompt version, provenance, validity range, and evaluation.

    Compression ratio and support retention are separate:

    compression_ratio = original_context_tokens / compressed_context_tokens
evidence_retention = required_facts_preserved / required_facts_before_compression

    A 4x compression that preserves only 70% of required facts is not an optimization for an evidence-bound task. Evaluate answerability, support, instruction injection, latency, and cost before enabling compression. Keep the original source accessible for citation and audit when policy permits.

    Prompt and context failures¶

    Failure Evidence Control
    hierarchy inversion injection test by source layer typed assembly and untrusted delimiters
    silent truncation token ledger and dropped sections preflight count and semantic priority
    schema bloat tool-schema token distribution task-scoped tool sets
    stale cached prefix policy/version mismatch epoch in key and reauthorization
    lossy summary required-fact retention extractive fallback or reject
    prompt rollout regression paired slice metrics canary and atomic rollback
    provider adapter drift canonical/provider fixture diff compatibility suite

    4. Latency budget and deadline propagation¶

    Assumption (2026-09, illustrative): A fraud decision has a 120 ms server deadline and a caller-visible p99 SLO measured from the joint latency distribution. Allocate 12 ms to network and edge, 35 ms to feature access, 5 ms to preprocessing, 12 ms to queueing, 35 ms to model execution, 8 ms to decision and ledger, and 13 ms to reserve.

    Stage Deadline allocation
    edge and route 12 ms
    feature fetch 35 ms
    preprocessing 5 ms
    queue 12 ms
    model 35 ms
    policy and ledger 8 ms
    reserve 13 ms
    total 120 ms

    The allocations are timeout and admission controls, not per-stage p99 measurements. Percentiles of dependent stages are not additive; prove the end-to-end p99 from per-request traces and distribution-aware load tests, then use stage distributions to diagnose budget burn.

    Each downstream call receives the remaining deadline, not a fresh timeout. Do not start model work when there is insufficient time to finish and validate it. A request that expires in queue should be removed before execution. Cancellation metrics must show work that continued after callers left.

    Tail latency composes badly across fan-out. Batch feature reads and keep the critical feature set small. Optional features receive a shorter deadline and an explicit model-compatible missingness path. The product SLO is measured at the caller-visible boundary, not only inside the model runtime.

    5. Feature correctness¶

    The online feature view pins definitions, entity keys, schema, freshness, default behavior, and source watermark. Request-time facts such as the current transaction should travel in the request envelope rather than wait for asynchronous materialization.

    Feature invariants:

    • event identity and event time are explicit;
    • no feature value newer than the permitted decision time is used;
    • missing, stale, unavailable, and true zero are distinguishable;
    • feature order and types match the model interface;
    • freshness-critical values expose watermark or age;
    • fallback models declare compatible feature subsets;
    • regional replicas do not silently serve a watermark older than policy allows.

    Use one batch read where possible. Co-locate hot feature state with serving while preserving an authoritative rebuild path. Cache only under versioned keys and TTLs consistent with feature semantics. Point-in-time training and publication are covered in ML and AI Pipelines.

    6. Dynamic batching and queueing¶

    Microbatching waits briefly to combine compatible requests. It can improve vectorized CPU/GPU throughput, but wait time consumes the latency budget and one large input may distort the batch.

    Batch compatibility includes bundle, tensor shape or length bucket, data class, and deadline class. Bound:

    • maximum requests;
    • total input units or tokens;
    • maximum wait;
    • estimated memory;
    • earliest deadline;
    • tenant contribution.

    Use deadline-aware queues with tenant fairness. Reserve lanes for critical classes and health probes. Reject before an unbounded queue converts overload into timeouts. A model replica should expose readiness only after weights, runtime, preprocessing, and golden fixtures are verified.

    7. Capacity model¶

    Assumption (2026-09, illustrative): Peak demand is 18,000 predictions/s. A benchmarked replica sustains 1,100 predictions/s at the target input distribution and p99 model latency. Target steady utilization is 60%. One zone may be lost from a three-zone region.

    Usable capacity per replica is 1,100 * 0.60 = 660 predictions/s. Traffic needs:

    ceil(18,000 / 660) = 28 replicas

    To preserve that capacity after losing one of three equal zones, each remaining zone must carry half the demand. Provision at least ceil(28 * 3 / 2) = 42 replicas across three zones, or 14 per zone, before considering skew and maintenance. This is an illustrative N+zone calculation; real placement must use measured per-hardware capacity and actual traffic distribution.

    Little's Law estimates concurrency. At 18,000/s and 70 ms mean service time, mean in-flight work is 18,000 * 0.070 = 1,260 requests. Pools must also survive tail latency and bursts. Size each dependency separately; one global concurrency limit hides a saturated feature store behind idle model capacity.

    Benchmark (measurement requirement, 2026-09): Sweep concurrency for the exact bundle and production-shaped feature availability, payload, batch policy, hardware, runtime, and network path. Report throughput and p50/p95/p99 end-to-end, queue, feature, and model latency; errors; memory; utilization; warm-up; quality; and cost. Select the safe operating envelope before the latency knee.

    8. Routing, fallback, and overload¶

    Routing order:

    1. authenticate principal and task;
    2. classify data and residency constraints;
    3. select only compatible approved bundles;
    4. check tenant, token, concurrency, and spend quota;
    5. select healthy region/pool/replica with deadline capacity;
    6. record route reason and attempt;
    7. use fallback only if the task's policy allows it.

    Fallback is a product decision:

    Failure Eligible fallback Ineligible behavior
    primary model unavailable previous approved compatible model arbitrary model with different score semantics
    optional features unavailable tested reduced feature bundle zero-fill undeclared inputs
    critical feature stale deterministic conservative policy score as if fresh
    region unavailable approved region for data class cross residency boundary
    ledger unavailable buffer bounded low-risk evidence or reject unaudited high-impact action
    overload reject, queue briefly, or degrade by class unlimited retries

    Circuit breakers isolate a dependency or bundle, but global fallback can overload the backup. Reserve fallback capacity and precompute incident cost. Prioritize critical decisions, shed shadows and optional enrichments first, and preserve health/recovery headroom.

    9. Caching¶

    Cache deterministic outputs only when the key includes every behavior-bearing input: task, normalized input, model bundle, policy, feature versions or watermark, tenant/security domain, and relevant sampling controls. A score cache can become incorrect when volatile features change even if the entity ID does not.

    Generative semantic caching has a wider error surface: near inputs may not be policy-equivalent, source evidence may change, and personalized context can leak. Treat it as a retrieval and authorization system, not a generic performance switch. Cache hits still need current policy and deletion checks.

    10. Release, canary, and rollback¶

    Build a bundle from immutable model, runtime, preprocessing, feature view, schema, and policy references. Verify digest and interface compatibility in a staging replica. Replay representative traffic, then shadow if duplicate data processing is permitted. Canary by stable entity hash so repeated decisions do not alternate versions.

    Gates include:

    • request and output contract compatibility;
    • model task metric, calibration, and critical slices;
    • feature availability, freshness, and parity;
    • p50/p95/p99 stage latency and capacity;
    • error, timeout, fallback, and cost;
    • decision-rate and disagreement bounds;
    • safety and privacy tests;
    • mature outcomes when labels arrive.

    Rollback changes the active pointer to a warm compatible bundle. Decisions already made are not undone; identify remediation or review when a bad release caused external effects. Changing only a threshold or preprocessing rule can require the same release evidence as changing weights.

    11. Multi-region design¶

    Prefer serving close to authoritative features. Active-active inference is straightforward only when bundle availability, policy, feature freshness, idempotency scope, and ledger semantics are defined across regions.

    Options:

    • regional independence: each region owns traffic, features, and ledger; easiest isolation;
    • home-region decision: route each entity to one region; stronger consistency at network cost;
    • active-active with replicated features: lower local latency; must define lag and conflict behavior;
    • cold failover: lower cost; recovery time includes artifact loading and cache warming.

    Never assume a model artifact available in object storage is ready for failover. Preload, verify, warm, and probe required bundles. Test whether fallback-region feature state meets the decision's freshness contract. See Multi-Region Systems.

    12. Failure, observability, and testing¶

    Failure Evidence Control
    tokenizer/preprocessor mismatch golden fixture digest differs block readiness
    stale features age/watermark by feature group fail or compatible fallback
    queue saturation queue age before utilization spike admission and class isolation
    replica OOM input/batch memory envelope bounded batch and request size
    fallback storm route reasons and backup saturation reserved capacity and breaker
    retry amplification attempts/logical request one budget and backoff
    shadow affects state side-effect/exposure audit isolated shadow sink
    regional split bundle and feature generation divergence pin/route or degrade
    prediction succeeds, response lost committed idempotency result return stored decision

    Observe logical requests and attempts; arrivals, admission, queue age, and shed rate; stage latency; batch shape; feature availability and freshness; model utilization/memory; score/action distribution; bundle and route; fallback; idempotency hits; cancellation waste; quality and calibration on mature labels; cost per successful prediction; desired/observed replicas; load and warm time.

    Test contract and golden vectors, feature missing/stale cases, deterministic policy, load and soak, burst and hot tenant, zone loss, model load failure, feature-store partition, ledger outage, deadline cancellation, duplicate requests, canary rollback, and recovery with stale replicated features.

    The failure cards include tokenizer drift, fallback bypass, cost runaway, and capacity incidents.

    13. Security and privacy¶

    Authenticate service identity and end-user context where relevant. Authorize task, model entitlement, subject, feature purpose, tenant, data class, and region before routing. Restrict administrative release and traffic-shift APIs separately from inference.

    Do not log raw feature vectors or prompts by default. Use field-level redaction and access-controlled replay records. Encrypt model artifacts and verify signatures. Protect models from unapproved extraction traffic with authentication, quotas, abuse detection, and response minimization. Propagate deletion to online features, prediction caches, replay payloads, and future training eligibility.

    14. Vendor and production evidence¶

    Vendor (NVIDIA Triton Inference Server 2.72.0, released 2026-08-31; r26.08 documentation): Triton documents dynamic batching, model repositories, schedulers, and metrics. Those runtime capabilities do not supply application-specific feature-time correctness, decision idempotency, or model-quality release gates. Triton r26.08 documentation

    Production report (Uber, published 2017-09-05): Uber reported that Michelangelo supported online and offline prediction and model deployment as part of a broader internal ML platform. The report motivates integrated version and serving operations in Uber's context; it is not a throughput benchmark or universal topology. Introducing Michelangelo

    15. Tradeoffs and evolution¶

    Choice Benefit Risk
    embedded model in service low hop count, simple small deployment duplicated rollout and poor fleet utilization
    shared serving platform utilization, standardized policy and telemetry multi-tenant blast radius and platform dependency
    request-time features freshest state fan-out and tail latency
    materialized features bounded reads lag and training-serving coordination
    CPU availability and simple operations for small models lower throughput for some models
    accelerator high throughput for compatible work batching, memory, topology, and cold load
    warm fallback fast recovery ongoing cost
    cold fallback lower idle cost recovery may violate SLO

    Start with one task-specific service and an explicit bundle. Introduce a shared gateway when policy, observability, and provider routing repeat across teams. Introduce a shared runtime when workload compatibility and isolation are demonstrated. Split pools by deadline, hardware, security domain, or failure risk when interference becomes material.

    16. Interview exercise¶

    Prompt: Design real-time ranking inference for a marketplace at 50,000 requests/s across three regions. The p99 server budget is 80 ms. Each request ranks 500 candidates, uses user and item features, and returns 50 items. A previous-model fallback is acceptable; stale block and inventory state is not.

    An L5 design batches feature reads, keeps block/inventory as deterministic hard filters, pins model/feature/policy bundles, budgets every stage, benchmarks candidate batch shapes, and admits against each dependency. It canaries by user, records decisions and attempts, preserves warm previous bundles, and fails closed on stale hard constraints while degrading optional ranking features.

    An L6 design adds regional feature lag policy, user home-region/idempotency semantics, zone evacuation capacity, tenant fairness, shared-feature blast radius, model/index or feature migration, release exception ownership, privacy deletion, and fleet economics. It distinguishes model ranking quality from final policy-filtered product outcomes.

    L5 and L6 signals¶

    L5¶

    • Provides an end-to-end latency budget and propagates remaining deadlines.
    • Pins model, preprocessing, features, schema, and policy in one bundle.
    • Quantifies measured replica capacity, concurrency, zone reserve, and queue bounds.
    • Defines feature freshness, fallback compatibility, idempotency, and rollback.
    • Measures stage health, quality, safety, and cost by version and route.

    L6¶

    • Governs fleet placement, fallback reserve, regional policy, and concentration risk.
    • Separates platform and product decision ownership with auditable exceptions.
    • Plans compatibility migrations and remediation for already-made decisions.
    • Models multi-tenant fairness and correlated feature/runtime failure.
    • Connects warm capacity, quality, and availability to portfolio economics.

    Final summary¶

    An online model service is a deadline-bound decision path over a compatible version bundle. Authorize before routing, fetch features with explicit time semantics, bound queues and batches, benchmark the full path, and separate score from policy. Preserve evidence, degrade only through approved compatible paths, and keep rollback capacity ready.
