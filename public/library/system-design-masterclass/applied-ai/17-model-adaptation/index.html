    Model Adaptation¶

    Model adaptation changes behavior through prompts, retrieval, supervised fine-tuning, preference optimization, adapters, distillation, or continued pretraining. Choose the smallest reversible intervention that can satisfy the product error contract. Training completion is never release approval.

    Adaptation decision ladder¶

    flowchart TD
    A[Behavior gap] --> B{Missing current facts?}
    B -- yes --> C[Retrieval or tool access]
    B -- no --> D{Instruction or format gap?}
    D -- yes --> E[Prompt and structured output]
    D -- no --> F{Stable task behavior gap?}
    F -- yes --> G[Supervised fine-tuning or adapter]
    F -- no --> H{Preference or style tradeoff?}
    H -- yes --> I[Preference optimization]
    H -- no --> J{Need smaller or cheaper model?}
    J -- yes --> K[Distillation]
    J -- no --> L{Domain representation gap?}
    L -- yes --> M[Continued pretraining with strict evidence]
    L -- no --> N[Revisit task or base model]

    Retrieval changes available evidence. Prompting changes instructions and context. Fine-tuning changes model behavior. They solve different problems and have different rollback, privacy, and freshness properties.

    Invariants¶

    1. Every training example has provenance, purpose, license or authority, retention class, and split assignment.
    2. A version bundle binds base model, tokenizer, data manifest, training code, objective, hyperparameters, adapter, prompt, and policy.
    3. Training, tuning, judge-calibration, release, red-team, and audit sets are separated and contamination-checked.
    4. A tuned model receives no new authority; tools and data remain externally authorized.
    5. Base-model or tokenizer changes trigger compatibility and regression evaluation.
    6. Release requires quality, safety, latency, capacity, cost, and rollback evidence.
    7. Deletion and policy changes tombstone source and derived data, update future training eligibility, and mark affected checkpoints, adapters, and model artifacts for restricted use, destruction, verified unlearning, or clean retraining according to policy. Lineage propagation alone does not prove that learned influence was removed.

    Adaptation alternatives¶

    Method Best fit Main risk Rollback unit
    prompt/versioned examples instruction, format, lightweight behavior brittleness and context cost prompt version
    retrieval current or attributable knowledge retrieval and ACL failure index/pipeline version
    supervised fine-tuning stable task pattern and output style overfit, forgetting, contamination adapter/model artifact
    preference optimization relative behavior preference reward misspecification objective/data/model bundle
    parameter-efficient adapter tenant/domain specialization adapter routing and base compatibility adapter pointer
    continued pretraining broad domain representation high cost and behavior regression full checkpoint
    distillation smaller serving target inherited errors and lost tail capability student version

              code_digest, config, seed, hardware, state)

    Experiment lifecycle¶

    stateDiagram-v2
    [*] --> Proposed
    Proposed --> DataApproved
    DataApproved --> Training
    Training --> Failed
    Training --> Candidate
    Candidate --> Rejected: evaluation fails
    Candidate --> Shadow: gates pass
    Shadow --> Canary
    Canary --> Released
    Canary --> RolledBack
    Released --> RolledBack: production regression
    Released --> Retired

    Checkpointing protects compute progress; it does not make an invalid experiment reproducible. Capture data and code identity before training. Resume only when base model, tokenizer, optimizer, sharding, and code compatibility are declared.

    Data quality and contamination¶

    Normalize and deduplicate before splitting. Near-duplicate leakage can inflate evaluation even when exact IDs differ. Preserve source and transformation lineage. Balance slices based on product risk, not only population frequency.

    Synthetic data can expand format and adversarial coverage, but it inherits generator bias and may collapse variety. Label its generator, prompt, filters, and review status. Do not let synthetic examples silently replace scarce real evidence.

    For preference pairs, define the comparison rubric and tie/abstain behavior. Record both candidates, ordering randomization, annotator decisions, and adjudication. Avoid turning policy constraints into soft preferences when violations must be impossible.

    Training and memory calculations¶

    Token volume:

    training_tokens = examples * mean_tokens_per_example * epochs

    For 2 million examples, 1,200 mean tokens, and two epochs:

    2,000,000 * 1,200 * 2 = 4.8 billion training tokens

    Approximate model-state memory for full training:

    model_state_bytes
~= parameters * (weight_bytes + gradient_bytes + optimizer_state_bytes)

    The model-state multiplier depends on precision, optimizer, master weights, sharding, and implementation. Total training memory also includes activations, temporary workspaces, and communication buffers. Activation checkpointing trades recomputation for lower retained activation memory; it does not by itself shrink the optimizer state in this equation. Measure framework allocations rather than quoting one universal bytes-per-parameter constant.

    Adapter parameter count for low-rank updates to matrices can be estimated per adapted matrix with input width d_in, output width d_out, and rank r:

    adapter_parameters_per_matrix = r * (d_in + d_out)
adapter_bytes = total_adapter_parameters * bytes_per_parameter

    This estimates artifact parameters, not training activations or optimizer memory.

    [Mechanism and derived example] LoRA freezes a base matrix W and learns a low-rank update formed from matrices of shapes (d_out, r) and (r, d_in), with a declared scale. For a 4096 x 4096 matrix at rank 16, this is 16 * (4096 + 4096) = 131,072 trainable parameters, 0.78125% of the original matrix, or 256 KiB at two bytes/parameter. The base weights and forward activations still exist. The LoRA paper, verified 2026-09-08, supports frozen weights and rank decomposition; its reported memory savings do not transfer automatically to another model or serving stack. Merging an update can avoid a separate inference branch, while dynamically multiplexing unmerged tenant adapters has runtime costs to measure.

    [Objective boundary] DPO, verified 2026-09-08, learns from chosen/rejected response preferences using a classification objective relative to a reference policy, rather than requiring an independently trained reward model and an on-policy RL loop. Preference agreement is not calibrated factual correctness, and a preference pair containing two unsafe answers cannot teach an acceptable action by ranking them alone. Keep hard safety checks and held-out task evidence independent of this objective.

    Cost per accepted release:

    experiment_cost
= accelerator_hours * rate
 + storage
 + data_processing
 + human_labeling
 + evaluation

cost_per_accepted_release
= total_experiment_program_cost / accepted_releases

    Include failed and abandoned runs. Optimizing only the winning run hides exploration cost.

    Evaluation and release¶

    Compare against the current production bundle and a simple baseline. Measure task quality, critical slices, safety invariants, calibration where applicable, structured output, retrieval/tool compatibility, latency, throughput, memory, and cost.

    Use paired per-example comparison and confidence intervals. Run red-team and data-extraction probes. Shadow with tools disabled or isolated. Canary by stable entity. Keep the previous compatible bundle warm when rollback time matters.

    Changing a base model beneath an adapter is a new candidate. Changing tokenizer, chat template, quantization, runtime, or prompt can materially alter behavior and requires scoped evidence.

    Serving adapted models¶

    Adapter multiplexing can improve utilization but creates routing and isolation risks. Route by approved (base, adapter, tokenizer, runtime) compatibility. Bound loaded adapters, memory, load latency, and tenant contribution. Never choose an adapter from user-provided text without authorization.

    Merge adapters only when artifact provenance and rollback remain clear. Quantization and compilation create derived artifacts with their own digest and evaluation. Cache keys include the effective adaptation and prompt bundle.

    Failure, security, and testing¶

    Failure Evidence Control
    train/eval leakage similarity and provenance report rebuild splits and invalidate result
    catastrophic forgetting retained capability suite gate or route specialized model narrowly
    tokenizer mismatch golden token IDs block training/serving readiness
    poisoned examples source/slice anomaly and review quarantine and signed manifests
    adapter/base mismatch compatibility matrix deny route
    memorization or extraction privacy and canary probes data minimization and release block
    preference reward gaming rubric-specific failure slices direct product and safety metrics
    irreproducible run manifest/config/checkpoint gap no promotion

    Unit-test data transformations and example identity. Property-test split exclusivity and manifest determinism. Run small overfit and gradient sanity checks before expensive jobs. Inject worker loss and resume. Compare resumed and uninterrupted metrics within declared tolerance. Verify artifact signatures and access controls.

    Security tests cover malicious training rows, hidden instructions, personal-data leakage, model extraction, unapproved adapter selection, compromised artifact storage, and trainer egress. Separate training credentials from serving credentials.

    Migration and evolution¶

    1. Freeze the old production bundle and evaluation evidence.
    2. Train candidate artifacts against immutable manifests.
    3. Validate interfaces and direct behavior before shadow traffic.
    4. Dual-run old/new bundle on stable cohorts; retain per-example differences.
    5. Canary with explicit rollback triggers and capacity reserve.
    6. Propagate deletion/tombstone policy to derived data and artifact eligibility; destroy affected artifacts or retrain from an eligible checkpoint when policy requires removal, unless a validated unlearning method demonstrates the required result.
    7. Retire old artifacts only after rollback, audit, and paused-workflow windows close.

    When changing the base model, test every supported adapter or declare it incompatible. If migrating the tokenizer, rebuild token-budget assumptions, prompt caches, and any token-ID-dependent filters.

    Interview exercise¶

    Design adaptation for a multilingual support model that must follow a strict JSON schema, use current policy from retrieval, preserve general safety behavior, and reduce cost enough to run on a smaller serving tier. Data includes resolved tickets and regulated customer text. Compare prompting, retrieval, SFT, adapters, preference optimization, and distillation. Define manifests, contamination controls, calculations, release gates, privacy tests, serving compatibility, rollback, and deletion.

    L5 and L6 signals¶

    L5¶

    • Chooses the smallest intervention that matches the diagnosed behavior gap.
    • Versions data, base model, tokenizer, code, objective, adapter, prompt, and evaluation.
    • Calculates token volume, adapter size, or memory with explicit assumptions.
    • Separates checkpoint success from reproducibility and release approval.
    • Defines contamination, privacy, regression, canary, and rollback evidence.

    L6¶

    • Establishes organization-wide data-purpose, adapter-compatibility, evaluation, and retirement policy.
    • Governs base-model migrations across many downstream adaptations.
    • Connects experiment portfolio cost, label operations, serving capacity, and accepted product outcomes.
    • Defines exception ownership for data, safety, and capability regressions.
    • Names evidence that can falsify the adaptation strategy and trigger a simpler architecture.

    Final design checklist¶

    • The diagnosed gap matches the adaptation method.
    • Data authority, provenance, purpose, splits, and deletion are explicit.
    • The full compatibility bundle is immutable and reproducible.
    • Safety constraints remain deterministic where required.
    • Evaluation covers retained capability and critical slices.
    • Serving validates base/adapter/tokenizer/runtime compatibility.
    • Portfolio cost includes failed experiments and human work.
    • Migration and retirement preserve rollback and audit.

    • [Source, primary, 2022-03-04] Ouyang et al., Training language models to follow instructions with human feedback. Describes supervised and preference-based instruction alignment in the reported system.
    • [Source, primary, 2023-05-29] Rafailov et al., Direct Preference Optimization. Introduces a preference-optimization objective; product safety still requires external controls.
