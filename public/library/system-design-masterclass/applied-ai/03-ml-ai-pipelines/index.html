    ML and AI Pipelines¶

    An ML pipeline converts versioned data and code into evidence-bearing artifacts. Its correctness property is not merely "the DAG completed." The resulting dataset, model, evaluation, and publication must be reproducible, compatible, authorized, and safe to activate.

    1. Scope and requirements¶

    Design a platform that trains and releases ranking models for several product teams. It supports scheduled and event-triggered runs, offline and online features, backfills, human approval, and regional serving.

    Core requirements:

    • reproduce a released artifact from immutable inputs or explain every irreproducible dependency;
    • prevent future data and mutable dimensions from leaking into historical examples;
    • separate artifact creation, evaluation, approval, and serving activation;
    • retry work without duplicating published artifacts or corrupting lineage;
    • backfill without starving production reads or mixing feature definitions;
    • support deletion, retention, access, and regional policy across snapshots and artifacts;
    • roll model, feature, parser, schema, and policy versions forward or back as compatible bundles.

    Out of scope are optimizer internals and a universal notebook environment. The platform provides execution and evidence; teams remain responsible for task-specific labels, metrics, and risk decisions.

    Principle: A successful task exit proves process completion. It does not prove point-in-time correctness, reproducibility, model quality, authorization, or release readiness.

    2. Architecture: creation is not activation¶

    flowchart LR
    S[Versioned sources] --> C[Snapshot catalog]
    C --> V[Validation and contracts]
    V --> F[Feature materialization]
    F --> T[Training]
    T --> A[(Artifact registry)]
    A --> E[Evaluation]
    E --> G[Release gate]
    G --> P[Publication controller]
    P --> O[Online serving bundle]
    P --> B[Batch scoring bundle]
    O --> L[(Prediction ledger)]
    B --> L
    Y[Outcomes and corrections] --> L
    L --> M[Quality and drift]
    M --> G
    R[Run orchestrator] --> V
    R --> F
    R --> T
    R --> E

    The orchestrator manages durable execution. The catalog and registries are sources of truth for identity and lineage. Feature tables, online stores, indexes, and serving caches are rebuildable projections. The publication controller atomically changes a small active pointer only after every referenced artifact is present and compatible.

    3. Run and artifact model¶

    PipelineDefinition(id, version, owner, task_graph, parameter_schema)
Run(id, definition_version, trigger, parameters, principal, state, started_at)
TaskAttempt(id, run_id, task, attempt, input_manifest, lease, output_manifest, state)
DatasetSnapshot(id, source_versions, cutoff, query_digest, schema, partitions, digest)
FeatureView(id, definition_digest, entity_keys, event_time, created_time, ttl, schema)
ModelArtifact(id, training_run, bytes_digest, signature, interface, environment_digest)
Evaluation(id, model_id, dataset_id, suite_version, slices, metrics, uncertainty, decision)
ReleaseBundle(id, model, feature_view, tokenizer, prompt, policy, schema, status)
Publication(id, target, bundle_id, generation, approver, activated_at)

    Use content-addressed immutable artifacts. Human-readable aliases may move, but a run records digests, not only aliases such as latest. Sign high-impact model and evaluation artifacts. A registry state transition should be auditable and authorization-controlled.

    Suggested run states:

    stateDiagram-v2
    [*] --> QUEUED
    QUEUED --> RUNNING
    RUNNING --> SUCCEEDED
    RUNNING --> FAILED
    RUNNING --> CANCELLING
    CANCELLING --> CANCELLED
    FAILED --> RUNNING: retry eligible task
    SUCCEEDED --> PUBLISHED: separate gate
    SUCCEEDED --> REJECTED: evidence fails
    PUBLISHED --> RETIRED

    SUCCEEDED means outputs are durable and verified. It does not imply PUBLISHED.

    4. Pipeline and control interfaces¶

    POST /v1/pipeline-runs
Idempotency-Key: ranker-train-2026-09-06

{
  "pipeline": "search-ranker",
  "definition_version": "sha256:...",
  "parameters": {
    "snapshot_id": "snapshot-842",
    "cutoff": "2026-09-01T00:00:00Z"
  }
}

    POST /v1/releases/{bundle_id}:approve
If-Match: "candidate-generation-7"

POST /v1/targets/search-us:activate
Idempotency-Key: activate-bundle-482
If-Match: "active-generation-91"

    Activation uses compare-and-swap so two approvers or automation paths cannot silently overwrite one another. The target reports desired and observed generation. Rollback activates a previous compatible immutable bundle; it does not mutate model bytes in place.

    5. Orchestration semantics¶

    Tasks should be deterministic functions of declared inputs where practical. When they read time, randomness, remote mutable state, or external libraries, capture those dependencies explicitly.

    Leases and retries¶

    An orchestrator grants a renewable lease. A worker writes outputs to an attempt-scoped location, calculates checksums, and commits an output manifest conditionally. If the lease expires, another worker may rerun the task. Only one manifest becomes canonical; abandoned bytes are garbage-collected later.

    Exactly-once task execution is not required. Idempotent or fenced publication is.

    Caching¶

    Reuse output only when the cache key covers code digest, normalized parameters, input manifest digests, schema, environment, and relevant nondeterminism. Do not reuse an artifact merely because task names match. Security and deletion policy may invalidate otherwise identical cache entries.

    Dynamic DAGs¶

    Permit bounded fan-out derived from a committed manifest. Record the expanded graph. Avoid a task that discovers unlimited work while running because cancellation, cost prediction, and audit become unclear.

    6. Point-in-time data correctness¶

    For a training example representing a decision at time t, every feature must have both an eligible domain event time and an availability time no later than t, subject to the production system's actual availability semantics. A naive join against the latest customer row leaks future state.

    Maintain event time and creation or ingestion time:

    FeatureValue(entity_id, feature, value, event_time, created_time, source_version)
Label(entity_id, value, event_time, created_time, correction_version)

    An as-of join must select a feature with event_time <= t and created_time <= t, where created_time is the first time the production decision path could observe that version. The pipeline's later simulation cutoff may limit which historical records the replay process can read, but it must never make a late arrival or correction appear available to the original decision. This bitemporal distinction exposes late arrival and correction.

    [Vendor boundary, verified 2026-09-08] Feast's current point-in-time documentation says default historical joins constrain event time; a created timestamp otherwise selects the newest duplicate, which can leak later corrections. Its documented filter_by_created_timestamp=True adds availability-time filtering, excludes NULL creation timestamps, and is not supported by every offline store. Pin the installed Feast/store version and test the generated join. The flag cannot repair a timestamp that records file creation rather than actual online availability.

    Test point-in-time logic with adversarial fixtures:

    • a feature changes after the label event;
    • a late event has old event time but new creation time;
    • an entity ID is reused or merged;
    • a source correction arrives after training;
    • a daylight-saving or timezone boundary occurs;
    • a deletion request removes an entity from future dataset construction.

    7. Feature definitions and serving parity¶

    A feature view declares entity keys, transformation, source, schema, freshness, default or missing semantics, and online/offline materialization behavior. Share definitions where possible, but do not claim perfect parity when execution engines differ. Compare values on sampled entity/timestamp fixtures and preserve missingness explicitly.

    Online publication pattern:

    1. compute immutable offline partitions;
    2. validate schema, ranges, nulls, freshness, and cardinality;
    3. write online values with feature-view version and source watermark;
    4. reconcile counts and sampled values;
    5. advance the readable generation;
    6. retain the prior generation for rollback.

    A missing value is not automatically zero. The model input should include a missingness indicator or use a documented model-compatible default. Safety-critical features may require fail-closed behavior.

    8. Backfills and incremental processing¶

    Backfills are production migrations. They can overload sources, create duplicate outputs, expose old code paths, and publish inconsistent windows.

    Use a backfill contract:

    Backfill(id, definition_version, input_range, snapshot, priority, max_parallelism,
         output_namespace, validation_policy, publication_policy, owner, state)

    Controls:

    • read from snapshots or bounded source ranges rather than unrestricted live scans;
    • use separate quotas and pools from freshness-critical work;
    • partition by deterministic keys and record completion bitmaps;
    • quarantine poison partitions after bounded retries;
    • write to a new namespace or generation;
    • compare cardinality, checksums, distributions, and sampled records;
    • publish only after the full manifest passes;
    • throttle or pause automatically when online source SLOs burn.

    Incremental processing starts from a snapshot watermark and applies ordered changes after it. Reconciliation checks both missing and extra keys. Replaying a feature transformation under new code must produce a new version, not overwrite history.

    9. Capacity and cost¶

    Assumption (2026-09, illustrative): A daily pipeline reads 12 TB compressed, emits 2 TB of features, trains for 2,400 accelerator-hours, and must finish within 8 hours. Average source throughput may use at most 600 MB/s to protect shared storage. A task worker sustains 80 MB/s on the representative transform.

    The source cap is stricter than worker count:

    minimum source read time = 12,000,000 MB / 600 MB/s
                         = 20,000 s
                         = 5.56 h

workers to reach source cap = 600 / 80 = 7.5, so 8 workers

    More transform workers do not reduce the source-bound stage below 5.56 hours. The training requirement needs average 2,400 / 8 = 300 accelerators if perfectly parallel, before topology constraints, checkpoints, failures, and queue time. If only 200 accelerators are available, the nominal training floor is 12 hours and the eight-hour requirement is infeasible without changing work, capacity, or deadline.

    The 300-accelerator number is only a training-stage lower bound if training can use the entire eight-hour window. If training waits for the full scan/materialization, at most 8 - 20,000/3,600 = 2.4444 hours remain: even with perfect scaling, ceil(2,400/2.4444) = 982 accelerators are needed before validation and publication time. Sum sequential stage durations along the critical path; use a maximum only for stages whose overlap is actually supported. Extra accelerators cannot shorten a source-bound dependency.

    Cost attribution includes source scans, intermediate storage, egress, failed attempts, idle reservations, feature publication, evaluation, and retained rollback artifacts. Charge by run and owner, but preserve shared-platform costs separately so team optimization does not hide fleet waste.

    Benchmark (measurement requirement, 2026-09): Benchmark each material stage with representative schema, compression, partition size, skew, engine version, worker shape, storage path, and concurrency. Record input/output bytes, rows/s, accelerator utilization, shuffle/spill, p50/p99 partition time, failure rate, and cost. Extrapolate only after identifying the limiting resource.

    10. Validation and release gates¶

    Validation layers should identify the causal stage:

    Layer Examples
    source contract schema compatibility, required columns, ownership, freshness
    dataset row count, uniqueness, ranges, nulls, slice coverage, leakage probes
    transformation golden fixtures, determinism, online/offline comparison
    training finite loss, checkpoint integrity, reproducibility tolerance
    model interface schema, tokenizer, feature order, runtime compatibility
    quality task metric, calibration, slices, confidence, baseline comparison
    safety abuse, privacy, fairness, prohibited behavior, high-impact slices
    operations latency, memory, throughput, fallback, cost, artifact loading

    Evaluation sets are versioned products with owners and contamination controls. A generic model judge can support evaluation, but its prompt/version, repeatability, agreement with qualified humans, and slice biases must be measured. Do not let a single aggregate judge score approve a release.

    11. Failure, recovery, and observability¶

    Failure Evidence Recovery
    partial partition write missing/invalid output manifest discard attempt prefix and replay partition
    stale lease commits late fencing generation mismatch reject commit
    schema drifts mid-run source versions differ across manifest fail run and pin snapshot
    skewed hot partition p99 partition time and spill split key/range or isolate heavy entities
    poison record deterministic repeat at same record quarantine under policy; do not retry forever
    online publication partial desired/observed generation mismatch keep old readable pointer and repair
    model loads but feature order differs golden interface fixture fails block release
    deletion misses snapshot lineage query shows affected artifact restrict, rebuild, or expire by policy
    orchestrator unavailable workers retain bounded leases recover from durable run state

    Monitor run and task state age, lease expiry, attempts, queue delay, stage throughput, bytes and rows, skew, source pressure, artifact verification, lineage completeness, data-quality failures, feature freshness, online/offline mismatch, release-gate outcomes, exception approvals, publication convergence, cost, and deletion workflow age.

    12. Security and governance¶

    Pipeline identity is workload identity, not a shared user credential. Authorize source reads, artifact writes, decryption, and release transitions separately. Isolate untrusted training code from credential and control-plane access. Scan dependencies and containers, pin environments, verify artifact digests at load time, and log administrative actions.

    Training data can carry personal, licensed, confidential, or poisoned content. Record purpose and policy in snapshot construction. Keep secrets out of feature values and logs. Apply retention and deletion to intermediate tables, cached task output, checkpoints, registries, evaluation examples, and replay data.

    Separation of duties matters for high-impact releases: the training principal produces a candidate; an evaluation service produces evidence; an authorized approver changes state; the deployment controller activates exactly the approved digest.

    13. Alternatives and tradeoffs¶

    Choice Advantage Cost or risk
    general workflow engine mature retries, schedules, observability ML lineage and gates remain application work
    ML-specific platform integrated artifacts, experiments, deployment platform coupling and governance assumptions
    shared feature definitions less training-serving skew engine parity and broad blast radius
    duplicate offline/online transforms optimized execution explicit parity testing and version coordination
    full snapshots simple reproducibility scan cost and freshness
    incremental deltas lower work and latency watermark, replay, and reconciliation complexity
    automatic retraining fast candidate creation feedback loops if activation is also automatic

    Vendor (MLflow 3.16.0, released 2026-09-04): MLflow documents model lineage, versions, aliases, and tags in its Model Registry. Registry capabilities do not determine an application's approval policy, point-in-time dataset correctness, or serving compatibility bundle. MLflow 3.16.0 Model Registry

    Production report (Google, published 2017-08): The TFX paper describes a production ML platform with data analysis, transformation, training, validation, and serving components, informed by Google's deployment experience. It demonstrates one integrated approach; teams must still adapt contracts and ownership to their environment. TFX paper

    14. Rollout and migration¶

    Start with immutable snapshots, artifact digests, a prediction ledger, and manual release gates. Add task caching only after cache identity is correct. Add shared features after point-in-time and parity tests exist. Add automatic candidate creation after evaluation and rollback are reliable; never let scheduling success self-approve a high-impact model.

    For a feature or model migration:

    1. define compatibility and rollback bundles;
    2. build new offline and online generations from a pinned snapshot;
    3. catch up ordered deltas from the snapshot watermark;
    4. reconcile keys, values, freshness, and checksums;
    5. replay and shadow with the complete new bundle;
    6. canary by stable entity;
    7. expand through predefined gates;
    8. retain the old bundle until the rollback and audit windows close;
    9. retire data under retention and deletion policy.

    15. Interview exercise¶

    Prompt: Design pipelines for a delivery-time model trained daily from orders, courier locations, weather, and map data. Predictions serve at 20,000 requests/s. Weather corrections arrive late, map versions change weekly, and the company needs a 180-day historical replay.

    An L5 answer pins order, weather, and map versions in dataset manifests; uses event and creation time; builds versioned feature views; separates training success from release; gates quality, slices, latency, and fallback; and rolls model plus features as one compatible bundle. It quantifies snapshot scans, training completion, online publication, and ledger storage.

    An L6 answer adds source contracts across owning teams, correction semantics, backfill quotas, cross-region publication, deletion and retention, evaluation-set renewal, exception authority, and capacity governance. It explains how a historical replay handles information that arrived late without pretending it was known at prediction time.

    L5 and L6 signals¶

    L5¶

    • Uses immutable manifests and content digests rather than mutable queries and tags.
    • Defines leases, retry-safe output, checkpoints, and atomic publication.
    • Handles point-in-time joins, late data, online/offline parity, and backfills.
    • Separates candidate creation, evaluation, approval, and activation.
    • Defines stage-level validation, recovery, lineage, and cost.

    L6¶

    • Establishes cross-team data contracts, release policy, exceptions, and artifact retirement.
    • Governs shared source capacity, accelerator quotas, and backfill interference.
    • Plans bundle migrations, regional convergence, correction replay, and legal deletion.
    • Treats evaluation datasets, feature definitions, and lineage schemas as owned products.
    • Makes organizational and security boundaries visible in the control plane.

    Final summary¶

    A trustworthy pipeline is an evidence graph with durable execution. Pin source versions and time semantics. Commit attempt outputs through manifests. Treat features, models, evaluations, and release bundles as immutable artifacts. Validate every stage, publish atomically, preserve rollback, and make backfills respect production capacity and policy.
