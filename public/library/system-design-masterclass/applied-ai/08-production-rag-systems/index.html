    Production RAG Systems¶

    Retrieval-augmented generation (RAG) is a data system, a search system, and an answer-policy system joined by provenance. A model call is only the final stage. Production correctness depends on immutable source versions, authorized retrieval, supportable citations, explicit abstention, observable freshness, and migrations that never mix incompatible corpus and index state.

    Evidence vocabulary¶

    • [Source] is supported directly by a dated item in Sources.
    • [Derived] follows from stated numbers or invariants.
    • [Design] is a recommended production contract.
    • [Measure] must be tested on the local corpus, users, and failure environment.

    Product contract¶

    Assume a support assistant over policy manuals, release notes, tickets, and product documentation. It answers questions, quotes source spans, and must refuse when evidence is missing, stale beyond policy, contradictory, or unauthorized.

    Invariants¶

    1. No source becomes queryable until its immutable version, ACL, parser result, chunks, and indexes belong to one active corpus manifest.
    2. Deletion and access revocation take effect at the authorization boundary even while physical purge continues.
    3. Every material factual claim maps to one or more exact source spans from the same immutable source version shown to the user.
    4. The answer policy may narrow or abstain; it may not invent support.
    5. Query-time components consume a compatible tuple of corpus epoch, chunk schema, embedding, lexical index, reranker, prompt, and model.
    6. A failure response identifies the stage that failed and does not present partial evidence as complete.
    7. Reprocessing is idempotent by source version and pipeline version.
    8. Retrieved text is untrusted data, not permission or instruction.

    End-to-end architecture¶

    flowchart LR
    S[Source connectors] --> F[Fetch immutable bytes]
    F --> Q[Scan and quarantine]
    Q --> P[Parse and normalize]
    P --> C[Chunk with lineage and ACL]
    C --> X[Lexical sparse and vector indexes]
    X --> M[(Corpus manifest)]
    U[User query] --> G[Identity policy and budgets]
    Z[(Current auth and tombstone projection)] --> G
    G --> R[Hybrid retrieval]
    M --> R
    Z --> R
    R --> K[Context packer]
    K --> L[Model gateway]
    L --> V[Claim citation and policy validation]
    Z --> V
    V --> A[Answer or abstention]

    Control-plane records define immutable versions and activation. Data-plane workers fetch, parse, index, retrieve, generate, and validate. Query serving reads one atomic content manifest rather than asking each content subsystem for its latest version. It also checks a separate current, monotonic authorization and tombstone projection before retrieval, during hydration, and before returning citations, so a content rollback cannot roll back a revocation.

    Ingestion plane¶

    State machine¶

    stateDiagram-v2
    [*] --> Discovered
    Discovered --> Fetched
    Fetched --> Scanned: security and format checks pass
    Fetched --> Quarantined: scan or format risk
    Scanned --> Parsed
    Scanned --> Quarantined: parser risk
    Parsed --> Chunked
    Chunked --> Indexed
    Indexed --> Validated
    Validated --> Active: manifest publish
    Quarantined --> Fetched: remediated or new source version
    Active --> Tombstoned: delete or global source withdrawal
    Tombstoned --> Purged
    Purged --> [*]

    Only Active versions are available to ordinary queries. A new version does not overwrite the prior version. It creates a new lineage branch that becomes active only after validation. A parser that emits zero chunks from nonempty input is a failure unless the source is explicitly represented as empty.

    Idempotent ingestion API¶

    PUT /v1/sources/policy-481/versions/sha256:raw-bytes-digest
Idempotency-Key: ingest:policy-481:sha256:raw-bytes-digest:ingest-12
If-None-Match: *
Content-Type: application/json

{
  "tenant_id": "tenant-7",
  "object_ref": "object://quarantine/7/481/v9",
  "acl_version": 19,
  "pipeline_version": "ingest-12"
}

    The server binds the idempotency key to a normalized payload digest. Reuse with another payload returns a conflict. Queue delivery may be at least once; processors use (tenant, source_id, source_version, pipeline_version, stage) to avoid duplicate derived artifacts. The source-version resource identifies immutable bytes; reprocessing those bytes with a new pipeline creates a separate processing-run resource rather than changing the existing version. Define replay ordering explicitly: an exact recognized idempotency replay returns the stored outcome, while an unrecognized create with If-None-Match: * against an existing resource fails with 412 Precondition Failed. After a lost response, read the resource or operation record to resolve whether creation succeeded.

    Atomic corpus activation¶

    {
  "corpus_epoch": 42,
  "tenant_partition": "tenant-7",
  "created_at": "2026-09-06T11:30:00Z",
  "source_manifest_digest": "sha256:...",
  "lexical_index": "lex-17",
  "vector_index": "vec-22",
  "embedding_version": "embed-9",
  "sparse_index": "sparse-4",
  "chunk_schema": 6,
  "content_acl_schema": 19,
  "deny_baseline_watermark": 883112,
  "status": "ACTIVE",
  "previous_epoch": 41
}

    Activation is one compare-and-swap of the content-manifest pointer after all referenced artifacts pass validation. Index shards may be built independently, but they do not become a corpus until the manifest names a complete compatible set. deny_baseline_watermark records what the build incorporated; serving must overlay the independent current deny projection at a watermark greater than or equal to that baseline. That baseline is only a build-time lower bound: a replica at that watermark can still miss later revocations. Require an authoritative current authorization check, or a documented bounded-staleness contract with a revocation propagation SLO and freshness proof; monotonic sequence numbers alone do not establish freshness.

    Context construction¶

    1. Normalize the user question without deleting meaningful identifiers.
    2. Resolve tenant, principal, groups, purpose, and policy version outside the model.
    3. Retrieve broad bounded lexical, dense, and optional sparse candidates.
    4. Enforce ACL during candidate search and again during hydration.
    5. Rerank authorized candidates and deduplicate canonical sources.
    6. Select evidence under token, source-diversity, trust, and freshness constraints.
    7. Delimit every span with source ID, immutable version, offsets, and trust class.
    8. State that evidence is data and cannot modify policy or tool authority.
    9. Ask the model for structured claims and citation references.
    10. Validate references, source support, freshness, and answer policy before rendering.

    Context packing is a constrained selection problem. More chunks can increase evidence coverage but also consume attention, latency, and cost. [Measure] Vary candidate depth and packed evidence independently; otherwise retrieval and context effects are confounded.

    Citation semantics¶

    A citation is valid only if all conditions hold:

    • the cited source ID and immutable version exist in the active or retained manifest;
    • the principal may read the source at response time;
    • offsets resolve to the quoted span in that version;
    • the span entails or directly supports the attached atomic claim;
    • material qualifiers such as date, jurisdiction, threshold, and exception are preserved;
    • the UI does not silently render a newer version under the old citation.

    Citation presence measures formatting, not support. Evaluate claim-level citation precision and material-claim citation recall. Human adjudication remains necessary for high-risk or ambiguous support semantics.

    Abstention policy¶

    flowchart TD
    Q[Question] --> E{Authorized evidence found?}
    E -->|No| A[Abstain: no evidence]
    E -->|Yes| F{Fresh enough for policy?}
    F -->|No| S[Abstain or label stale]
    F -->|Yes| C{Material conflict?}
    C -->|Yes| H[Escalate or present conflict]
    C -->|No| V{Every material claim supported?}
    V -->|No| N[Narrow answer or abstain]
    V -->|Yes| R[Return cited answer]

    Do not abstain from a single global similarity threshold alone. Threshold distributions vary by query type, retriever, corpus, and model version. Combine evidence coverage, source authority, freshness, conflict detection, citation support, and risk policy. Calibrate on answerable and unanswerable cases.

    Suppose 500 evaluation questions include 100 truly unanswerable cases. The system abstains on 120, of which 90 are truly unanswerable:

    abstention precision = 90 / 120 = 0.75
abstention recall = 90 / 100 = 0.90
incorrect abstentions on answerable cases = 30
missed unanswerable cases = 10

    [Derived] High abstention recall can coexist with poor answer utility if too many answerable cases are refused. Report both dimensions and the cost of unsupported answers.

    Freshness model¶

    Freshness has at least four clocks:

    Clock Meaning
    source effective time when the content became valid in its domain
    connector observation time when the platform saw the source version
    index activation time when the version became queryable
    answer time when the user received the answer

    Define freshness SLOs from source change to queryability, not only ingestion duration. A connector can be healthy while missing upstream changes. Use source-specific watermarks, expected polling cadence, webhook sequence, content digests, and reconciliation scans.

    If 99% of changes activate within 10 minutes but the source connector has not successfully reconciled for 6 hours, do not report the corpus as 10 minutes fresh. Return an as_of time and policy result. High-risk sources can fail closed after maximum staleness; low-risk sources can answer with a visible stale label.

    ACLs, revocation, and deletion¶

    ACL lineage flows from source to every chunk, index posting, vector payload, cache entry, citation, and evaluation artifact. Query policy is computed from the authenticated principal, not model-generated filters.

    For revocation or deletion:

    A principal/group ACL revocation normally updates the scoped deny/authorization projection; it does not delete a shared document for still-authorized users. The source-wide tombstone/purge sequence below applies to deletion or global withdrawal. Cache invalidation and derivative reauthorization apply to both, with their actual affected scope.

    1. append a tombstone with source ID, affected versions, tenant, reason class, and sequence;
    2. enforce it immediately in retrieval and hydration filters;
    3. invalidate response and retrieval caches by source/version membership;
    4. remove source objects and derived chunks/index records asynchronously;
    5. propagate to replicas, backups, evaluation sets, and replay stores under policy;
    6. verify absence using direct artifact inventories and synthetic unauthorized queries;
    7. record completion evidence or documented retention exceptions such as legal hold.

    Physical vector deletion is not the immediate security boundary. The current authorization and deny/tombstone projection is. It is versioned independently from immutable content manifests, highly available, monotonic per source/security domain, and consulted on every retrieval, hydration, citation render, and cache hit. Cache entries record the deny epoch they were checked against and cannot be served under an older epoch. High-risk reads fail closed when the projection is unavailable, behind the caller's required revocation epoch, or cannot prove current authorization; lower-risk availability exceptions require explicit policy and cannot expose revoked content.

    Failure attribution¶

    Record one stage outcome for every logical request:

    {
  "request_id": "rag-01H...",
  "logical_request_id": "lr-88",
  "principal_scope_digest": "sha256:...",
  "versions": {"corpus_epoch": 42, "prompt": "rag-18", "model_route": "route-11"},
  "stages": [
    {"name": "policy", "status": "OK", "ms": 4},
    {"name": "retrieve", "status": "OK", "ms": 58, "candidate_count": 180},
    {"name": "authorize", "status": "OK", "ms": 7, "authorized_count": 42},
    {"name": "rerank", "status": "TIMEOUT", "ms": 91, "fallback": "FUSED_ORDER"},
    {"name": "generate", "status": "OK", "ms": 610},
    {"name": "validate", "status": "ABSTAIN", "reason": "UNSUPPORTED_MATERIAL_CLAIM"}

}

    Attribution matrix¶

    Symptom Evidence Likely boundary
    required source absent from candidates judged span missing at candidate N retrieval or indexing
    source retrieved but omitted from packed context candidate and context IDs differ packer budget/policy
    evidence present but answer wrong exact prompt evidence preserved generation
    answer correct but citation unrelated claim-span support review fails citation generation/validation
    source version not current source and index watermarks diverge connector or activation
    unauthorized source returned principal, ACL, hydration evidence disagree security incident

    Use Lab 05 to practice stage metrics and Failure Cards for incident discriminators.

    Capacity and cost¶

    Assume 120 queries/s, 40 retrieved chunks of 700 document tokens, a 100-token reranker query repeated for each pair, 20 framing/special tokens per pair, a 768-token pair limit, reranking to 8, 2,500 non-evidence model-input tokens, and 700 output tokens:

    reranker document tokens/pair = min(700, 768 - 100 - 20) = 648 tokens
reranker truncated tokens/pair = 700 - 648 = 52 tokens
reranker processed tokens/query = 40 * (648 + 100 + 20) = 30,720 tokens
reranker processed-token demand = 120 * 30,720 = 3,686,400 tokens/s
model input/query = 8 * 700 + 2,500 = 8,100 tokens
model input demand = 120 * 8,100 = 972,000 tokens/s
model output demand = 120 * 700 = 84,000 tokens/s

    The reranker sees truncated 648-token document prefixes, while the context packer may hydrate the full 700-token text for the eight selected chunks, which is why model input still uses 8 * 700. Processed tokens are only a first-order reranker work estimate: padding, truncation, attention cost, batching, and model architecture can make equal token counts consume different service time. Capacity must therefore use measured pairs/s and latency over the exact query/document length distribution as well as the token ledger.

    At illustrative prices of $3 per million input tokens and $12 per million output tokens:

    cost/query = 8,100/1,000,000 * $3 + 700/1,000,000 * $12
           = $0.0243 + $0.0084
           = $0.0327 before retrieval, reranking, retries, and storage
cost/day at 120 qps = 120 * 86,400 * $0.0327 = $339,033.60

    [Derived] These illustrative inputs expose why context depth and output caps are economic controls. Replace prices and token distributions with contracted rates and measured percentiles. Track logical requests separately from provider attempts so retry cost is visible.

    Evaluation and observability¶

    Offline evaluation¶

    • candidate Recall@N against source-span judgments;
    • MRR or nDCG for ranked evidence;
    • context recall and context precision after packing;
    • claim-level citation precision and material-claim citation recall;
    • supported-answer rate, correctness, and abstention precision/recall;
    • ACL isolation and deletion tests with adversarial principals;
    • freshness and contradiction slices;
    • latency and cost by document type, tenant, language, and query class.

    Online evidence¶

    • source change-to-active lag and connector reconciliation age;
    • zero-chunk, parse-error, quarantine, and indexing failure rates;
    • candidate and authorized counts by stage;
    • empty retrieval, stale response, abstention, and escalation reasons;
    • citation-open, reformulation, resolution, and user-correction outcomes;
    • prompt/model/index version mix and canary deltas;
    • cache hit rate keyed by scope and epoch;
    • logical requests, attempts, token distributions, and cost;
    • unauthorized-return invariant counter, which must remain zero.

    Sampled traces must preserve enough evidence for diagnosis while respecting source ACL, privacy, and retention. Aggregate metrics without version dimensions hide split rollouts.

    Security¶

    • Treat retrieved documents, OCR text, ticket text, and tool output as untrusted content.
    • Keep credentials, hidden policies, and cross-tenant metadata out of prompts.
    • Apply principal-bound filters before retrieval material reaches the model.
    • Label source trust and do not let low-trust content override authoritative policy.
    • Constrain generated queries to allowlisted fields and bounded fan-out.
    • Scan uploads, sandbox parsers, cap decompression and page counts, and quarantine failures.
    • Prevent citations and snippets from becoming cross-tenant existence oracles.
    • Encrypt raw sources, indexes, traces, and replay evidence with scoped access and audit.
    • Preserve a kill switch that stops generation while cited authorized search remains available.

    Index and pipeline migration¶

    epoch 41 active
  -> build epoch 42
  -> validate corpus, ACL, deletion, and quality
  -> shadow queries
  -> dual-read sampled traffic
  -> atomic activation if every gate passes
  -> canary and expand
  -> retain rollback window
  -> retire epoch 41

    Migration gates include source counts, chunk-count distributions, tombstone watermarks, ACL equivalence, exact-vs-ANN checks, retrieval judgments, citation resolution, latency, and cost. Dual reads compare results but return only the active path. If two epochs use different chunk IDs, compare canonical source/version/spans rather than raw IDs.

    Rollback cannot erase new deletions or revocations. When returning to an older index, layer the latest deny projection over it and prove that current policy still applies.

    Interview exercise¶

    Design a RAG assistant for global support staff over policies that change daily. Documents include private tenant tickets and shared manuals. The answer must include exact citations, meet 2-second p95 latency, expose freshness, and support monthly parser and embedding migrations.

    Address ingestion idempotency, immutable versions, chunk lineage, ACL filter placement, hybrid retrieval, context budgets, claim citations, abstention, freshness clocks, deletion, failure attribution, evaluation, capacity, and dual-index rollback.

    L5 and L6 signals¶

    L5¶

    • Traces one source from bytes through citation offsets and one query through stage evidence.
    • Separates retrieval, context, answer, citation, and abstention metrics.
    • Uses atomic corpus manifests and compatible version tuples.
    • Enforces ACL and tombstones independently of model behavior.
    • Defines safe stale, partial, timeout, and no-evidence outcomes.
    • Computes token demand and per-query cost from explicit assumptions.

    L6¶

    • Defines enterprise corpus epochs, lineage contracts, deletion evidence, and source ownership.
    • Governs evaluation judgments, high-risk freshness policy, and exceptions across products.
    • Quantifies regional or provider failure headroom and degraded capacity.
    • Attributes storage, inference, reprocessing, and evaluation cost to owners.
    • Names migration and rollback authority, evidence retention, review cadence, and retirement criteria.

    Final design checklist¶

    • Source versions and derived artifacts are immutable and linked.
    • Activation is atomic through one corpus manifest.
    • ACL, revocation, retention, and deletion survive every derived layer.
    • Citations bind claims to exact immutable spans.
    • Abstention handles absent, stale, conflicting, and unsupported evidence.
    • Failure attribution separates ingestion, retrieval, packing, generation, and validation.
    • Offline and online gates include mandatory security and freshness slices.
    • Migrations preserve compatibility, current denies, rollback, and old-epoch cleanup.
