    Durable Agents, Memory, and Human-in-the-Loop¶

    Long-running agents need two different kinds of persistence: memory that helps future decisions and durable state that proves what already happened. Conflating them creates unsafe replay, stale beliefs, duplicate effects, and unauditable approvals. Durable execution records authoritative events; memory remains a governed, fallible input.

    Evidence vocabulary¶

    • [Source] is supported by a dated source in Sources.
    • [Derived] follows from stated assumptions.
    • [Design] is a recommended production contract.
    • [Measure] must be evaluated on local tasks, users, and failure modes.

    Memory taxonomy¶

    Memory type Purpose Example Authority
    working bounded state for the current step or run current plan, retrieved evidence, remaining budget temporary input, never policy
    episodic records of prior experiences a resolved incident trace or past customer interaction historical evidence with provenance
    semantic consolidated facts or concepts product glossary, learned user preference fallible assertion requiring freshness and scope
    procedural instructions for how to perform tasks approved runbook, tool-use procedure executable only through current policy and tools

    [Source] CoALA presents an agent-memory framework influenced by cognitive memory categories and separates working from long-term memory forms. The exact production schema here is [Design], not a standard taxonomy.

    Durable state is not memory¶

    Durable truth:
  PaymentCommitted(operation_key, payment_id, amount, effect_id)

Memory:
  "The customer usually prefers account credit."

    The first is an authoritative event from a system boundary. The second is a scoped, revisable assertion that may be stale or wrong. Never decide whether to repeat a side effect by asking semantic memory. Fold the durable operation ledger or query the system of record.

    Design requirements¶

    Invariants¶

    1. A run is reconstructed from ordered immutable events plus versioned snapshots; current mutable rows are projections.
    2. Every external effect has a stable operation key and durable terminal or unknown outcome.
    3. Replay reuses recorded nondeterministic decisions and tool results unless explicitly running a forked simulation.
    4. Pause releases compute but preserves event position, budgets, capabilities, deadlines, and waiting condition.
    5. Resume reauthorizes principal, capability, policy, approval, and business preconditions.
    6. Approval binds exact normalized intent and expires; editing the intent invalidates approval.
    7. Memory carries tenant, subject, provenance, confidence, validity interval, retention, and deletion metadata.
    8. Retrieved memory and tool output are untrusted inputs, not instructions or authorization.
    9. Compensation is a new forward action with its own failure modes and audit trail.
    10. Concurrent workers cannot advance the same run without fencing.

    Architecture¶

    flowchart LR
    U[User or trigger] --> G[Run gateway]
    G --> O[Durable orchestrator]
    O --> E[(Append-only event store)]
    E --> P[State projector]
    P --> S[(Run snapshots)]
    O --> W[Workers]
    W --> T[Typed tool gateway]
    T --> X[Systems of record]
    O --> M[Memory service]
    M --> V[(Vector and structured memory indexes)]
    O --> H[Approval service]
    H --> A[Human reviewer]
    O --> Q[Timers and signal queue]

    The orchestrator owns transitions, not business credentials. Workers may disappear after any instruction. Events and independently idempotent tools make recovery safe. Memory service failures can degrade personalization or recall; they must not corrupt the event ledger.

    Fold algorithm¶

    function rebuild(run_id):
    snapshot = load_latest_valid_snapshot(run_id)
    state = snapshot.state if snapshot exists else initial_state()
    last_sequence = snapshot.last_sequence if snapshot exists else 0
    expected = last_sequence + 1
    for event in read_events(run_id, after=last_sequence):
        assert event.sequence == expected
        assert verify_digest(event)
        state = apply_versioned_reducer(state, event)
        expected += 1
    return state

    Use optimistic append with expected sequence or a fenced single-writer lease. A snapshot accelerates folding but never replaces retained events required by policy. Verify snapshot hash and event position before use.

    Durable execution and replay¶

    sequenceDiagram
    autonumber
    participant O as Orchestrator
    participant E as Event store
    participant W as Worker
    participant T as Tool
    O->>E: append ToolDispatchStarted with operation key
    O->>W: execute activity
    W->>T: call with operation key
    T-->>W: committed effect
    Note over W,O: worker crashes before reply
    O->>E: append ToolOutcomeUnknown after timeout
    O->>T: reconcile same operation key
    T-->>O: committed effect and result
    O->>E: append ToolResultRecorded

    Replay has two modes:

    • Recovery replay folds history and reuses recorded decisions/results. It may continue only from the first incomplete command after reconciliation.
    • Simulation fork copies an authorized, redacted input state into a new run ID and may invoke new model or tool simulations. It cannot write to production systems.

    Record nondeterministic values such as model output, tool result, random choice, external query response, selected clock instant, and human signal. During recovery, code reads those events instead of calling the dependency again.

    Workflow code must remain compatible with open histories. Version reducers and commands. A new deployment should pass replay tests over representative historical event streams before activation.

    Pause and resume¶

    stateDiagram-v2
    direction TB
    [*] --> Running
    state Waiting {
        WaitingApproval
        WaitingTimer
        WaitingSignal
    }
    Running --> WaitingApproval
    Running --> WaitingTimer
    Running --> WaitingSignal
    Running --> OutcomeUnknown
    WaitingApproval --> Running: approval revalidated
    WaitingApproval --> Failed: approval deadline expired
    WaitingTimer --> Running: durable timer
    WaitingSignal --> Running: signal deduplicated
    OutcomeUnknown --> Running: effect reconciled
    Waiting --> Cancelled: cancellation accepted
    Running --> Completed
    Running --> Failed
    Running --> Cancelled

    The Waiting container groups the three resumable wait states; it is not an additional stored status. Its cancellation edge applies to each enclosed state. An unknown external effect must first be reconciled.

    A pause event stores:

    {
  "run_id": "run-01H...",
  "wait_type": "APPROVAL",
  "wait_key": "approval-481",
  "last_sequence": 184,
  "resume_not_before": null,
  "expires_at": "2026-09-07T15:00:00Z",
  "remaining_budget": {"steps": 4, "tool_calls": 2, "spend_usd": 0.12},
  "required_capability": "refund.commit",
  "intent_digest": "sha256:..."
}

    Resume performs compare-and-append against last_sequence. Duplicate signals carry stable signal IDs and return their prior acceptance result. Late approval after expiry records a rejected signal; it does not wake the run. Cancellation races are resolved by event order and fencing. Durable cancellation must also wake waiting runs so they do not remain parked forever. A run with an unknown external effect can stop new work, but keeps an owned reconciliation record until the effect is resolved; cancellation cannot assert that the effect did not happen.

    Human approval¶

    An approval UI must show what the human is authorizing, not merely an agent summary:

    • principal and acting service;
    • action and target;
    • normalized arguments, amount, currency, destination, and environment;
    • evidence and source versions;
    • current resource version and material preconditions;
    • policy decision and exceptions;
    • expected effect, reversibility, and compensation limits;
    • expiry and separation-of-duties requirements.
    {
  "approval_id": "approval-481",
  "run_id": "run-01H...",
  "intent_id": "intent-992",
  "intent_digest": "sha256:normalized-exact-action",
  "resource_versions": {"payment": "v17", "case": "v9"},
  "policy_version": "policy-21",
  "required_roles": ["REFUND_APPROVER"],
  "quorum": 1,
  "requested_at": "2026-09-06T15:00:00Z",
  "expires_at": "2026-09-07T15:00:00Z",
  "status": "PENDING"
}

    At commit time, verify approval signature, intent digest, role, quorum, expiry, current principal authority, resource versions, policy, and limits. If anything material changed, prepare and approve a new intent.

    This new-intent rule applies before an effect has been dispatched. After dispatch, reconcile the existing operation first; changed policy, expiry, or resource version cannot justify issuing another payment while the original is unresolved. Preserve required capability names across a pause, not reusable credentials or an assumption that old authority remains valid. Temporal's workflow execution documentation, verified 2026-09-08, describes command/history replay; it does not turn a retried external Activity into an exactly-once business effect.

    Track approval queue age, abandonment, rejection, modification, override, and downstream incident outcomes. Optimizing approval rate alone encourages rubber-stamping.

    Compensation and sagas¶

    [Source] The Sagas paper describes long-lived transactions as sequences of transactions with compensating transactions. Compensation semantically counteracts prior work; it does not make history disappear.

    flowchart LR
    A[Reserve inventory] --> B[Charge payment]
    B --> C[Create shipment]
    C -->|authoritative rejection| D[Void or refund payment]
    C -->|unknown outcome| U[Reconcile shipment before compensation]
    U -->|proved not shipped| D
    D --> E[Release inventory]
    E --> F[Record compensated outcome]

    For each forward step define:

    Field Meaning
    commit evidence authoritative proof the step occurred
    operation key deduplication and reconciliation identity
    compensation domain action that counteracts the effect
    compensation deadline last time reversal is allowed
    preconditions resource versions and states required
    failure owner team responsible for manual resolution

    Compensations can fail and require their own retries, idempotency, alerts, and approval. Some actions have no valid compensation. Keep those outside autonomous authority or require human confirmation before the irreversible boundary.

    An unknown shipment is not a proved failure: refunding and releasing inventory while it is actually shipping can compound the incident. Conflicting or still-pending shipment evidence remains in reconciliation or an owned manual queue; it does not flow automatically to compensated success.

    Working memory¶

    Working memory is a bounded projection of current run state: goal, current plan, verified observations, unresolved requirements, recent tool results, and remaining budgets. Keep authoritative events outside the model context. Summaries can reduce tokens, but retain links to the events they summarize and validate critical values directly.

    Episodic memory¶

    Episodic memory stores prior interactions or run episodes. Retrieve it by tenant, subject, purpose, time, and similarity. Before reuse, check outcome quality, policy compatibility, source availability, and whether the episode was later corrected. A successful past action is an example, not permission to repeat it.

    Semantic memory¶

    Semantic memory stores consolidated assertions. Consolidation should preserve supporting and contradicting evidence, confidence, validity, and last verification. Use deterministic sources of record for account status, balances, permissions, and other operational facts.

    Procedural memory¶

    Procedural memory stores methods such as runbooks or approved playbooks. Version and sign authoritative procedures. A model-generated procedure remains a proposal until reviewed. Current tool schemas and policy override stale procedure text.

    Memory write policy¶

    function consider_memory(candidate):
    reject if source is missing or unauthorized
    reject secrets and prohibited sensitive classes
    reject operational facts owned by a system of record
    reject low-confidence or contradicted assertions for automatic promotion
    normalize subject, tenant, kind, validity, and provenance
    deduplicate against active memories
    require review for procedural or high-impact semantic memory
    append accepted version; never silently mutate prior record

    Memory poisoning can come from users, retrieved documents, tool results, or a compromised server. Separate observation from consolidation. A memory writer has less authority than the original system of record and cannot broaden ACLs.

    Memory retrieval and forgetting¶

    Filter before semantic search by tenant, subject, purpose, ACL, status, and validity interval. Then rank by relevance, recency, confidence, source authority, and contradiction state. Include provenance in the model-visible memory envelope.

    Forgetting includes:

    • natural expiry;
    • supersession by a newer assertion;
    • user correction;
    • retention expiry;
    • consent withdrawal;
    • legal deletion;
    • source invalidation;
    • policy-driven deactivation.

    Deletion tombstones memory immediately at read time, then removes text, embeddings, caches, snapshots, and exports according to retention and legal-hold rules. Put sensitive event payloads behind encrypted references so their keys and payload objects can be destroyed without rewriting the append-only event ledger; retain only non-sensitive event facts, tombstones, and minimum deletion proof allowed by policy. If an authorized replay no longer has a deleted payload, it must produce an explicit redacted-input outcome rather than inventing the old value. Cryptographic erasure and reference deletion do not prove removal from an already trained model.

    Capacity and reliability calculations¶

    Event storage¶

    Assume 2 million runs/day, 24 events/run, 1.2 KB/event after encoding, 30-day hot retention, and three stored copies:

    events/day = 2,000,000 * 24 = 48,000,000
logical bytes/day = 48,000,000 * 1.2 KB = 57.6 GB decimal
30-day replicated hot storage = 57.6 * 30 * 3 = 5.184 TB decimal

    [Derived] This excludes indexes, snapshots, encryption overhead, transaction logs, and object-store history. Large model/tool payloads should live in separately protected content-addressed storage with bounded event references.

    Approval capacity¶

    If 4% of 120,000 daily runs require approval, reviewers handle 20 approvals/hour, and demand arrives uniformly over an 8-hour staffed window:

    approvals/day = 120,000 * 0.04 = 4,800
required reviewer-hours/day = 4,800 / 20 = 240
mean concurrent reviewers over 8 hours = 240 / 8 = 30

    With 25% absence and surge reserve:

    scheduled reviewers = ceil(30 / 0.75) = 40

    [Derived] Forty reviewers cover the stated mean under the simplistic assumptions. Arrival bursts, case complexity, second approvals, and service-level targets require queueing analysis.

    Replay recovery¶

    If 600,000 paused runs average 30 unsnapshotted events and one worker folds 3,000 events/s:

    events to fold = 600,000 * 30 = 18,000,000
one-worker time = 18,000,000 / 3,000 = 6,000 s = 100 minutes
50-worker ideal time = 100 / 50 = 2 minutes

    Actual recovery includes storage bandwidth, hot partitions, downstream reconciliation, and admission control. Do not resume every run at once after an outage.

    Failure modes¶

    Failure Evidence Containment and recovery
    replay repeats side effect effect exists but terminal event is missing reconcile operation key, append result, then continue
    duplicate run advancement two workers append from same sequence expected-sequence reject and fenced lease
    poison semantic memory assertion traces to untrusted or later-retracted input deactivate descendants and re-evaluate affected runs
    stale procedure tool or policy version newer than runbook block execution and require compatible procedure
    summary loses qualifier summary digest maps to events containing omitted constraint rebuild working projection from source events
    approval after mutation current intent digest differs reject approval and prepare new intent
    compensation fails compensation operation remains unknown or failed reconcile, retry within policy, then manual queue
    resume storm timers and signals release large paused cohort partitioned admission, jitter, and priority queues
    event schema break new reducer cannot fold old fixture stop rollout and restore compatible reader
    deletion misses snapshot active projection hides item but snapshot still contains it deny reads, rebuild/purge snapshots, verify closure

    See Lab 09, Failure Cards, and Typed Tool Calling and MCP.

    Security and privacy¶

    • Encrypt events, snapshots, memory, approvals, and payload objects with tenant-aware access control.
    • Keep credentials out of events and model-visible state; store opaque secret references only.
    • Separate audit-reader, replay-operator, approver, policy-admin, and deletion roles.
    • Treat memory search as a cross-session data disclosure boundary.
    • Apply purpose limitation and prevent one product from reusing another product's memory by default.
    • Redact free text from ordinary telemetry and cap event payload size.
    • Sign approvals or preserve tamper-evident identity, intent digest, and timestamp evidence.
    • Sandbox simulation forks and deny production write capabilities.
    • Test indirect prompt injection through episodic and procedural memories.
    • Maintain a kill switch that stops new actions while preserving audit and reconciliation access.

    Evaluation and observability¶

    Durable-execution tests¶

    • crash before dispatch, after dispatch, after commit, and after result append;
    • duplicate delivery, out-of-order signal, stale worker, and lease expiry;
    • pause/resume across deployment and policy changes;
    • historical replay across event and reducer versions;
    • approval expiry, digest mismatch, role loss, and resource-version conflict;
    • compensation success, failure, timeout, and manual escalation;
    • regional event-store recovery and controlled resume rate.

    Memory evaluation¶

    • retrieval precision/recall for useful memories;
    • unsupported-memory rate and provenance completeness;
    • stale, contradictory, cross-tenant, and wrong-subject retrieval rate;
    • impact on task success compared with no-memory baseline;
    • correction and deletion propagation latency;
    • procedural adherence and current-tool compatibility;
    • privacy red-team cases and membership-inference probes where applicable.

    Telemetry¶

    Monitor append latency and conflicts, event lag, snapshot age, fold duration, stuck wait states, timer lag, duplicate signals, unknown tool outcomes, reconciliation age, compensation backlog, approval queue age, expiry, reviewer overrides, memory reads/writes, contradiction rate, stale-memory use, deletion backlog, and resume admission.

    Invariant counters are unsampled:

    duplicate_external_effects = 0
unauthorized_memory_reads = 0
commit_with_invalid_approval = 0
production_writes_from_simulation = 0
events_with_sequence_gap = 0

    Migration¶

    Event and workflow migration¶

    1. Keep event envelopes stable and add versioned payload readers.
    2. Add new event types rather than changing the meaning of old facts.
    3. Run deterministic replay tests over sampled and adversarial historical streams.
    4. Deploy readers before writers for additive schema changes.
    5. Route new runs to the new workflow while old code remains available for paused histories.
    6. If migrating open runs, append an explicit migration event with source and target workflow versions.
    7. Canary resume and reconciliation before fleet expansion.
    8. Remove old reducers and activities only when no retained or open history requires them.

    Memory migration¶

    Build a new memory projection or embedding index from immutable accepted memory records. Dual-read under the same ACL and validity filters, compare retrieval by memory ID, and activate through an atomic manifest. Tombstones remain newer than either index and apply to both. Re-embedding does not create new authority or extend retention.

    Regional recovery¶

    Define one write authority for a run or use a consensus-backed event store. After regional failover, fence the old writer before resuming. Reconcile unknown side effects against systems of record, then release paused runs through rate-limited queues. Recovery-point and recovery-time objectives must include event payload objects, timers, signals, approvals, and keys, not only the event table.

    Interview exercise¶

    Design a durable claims agent that gathers documents, asks adjusters for missing information, proposes payouts, waits up to 14 days for approval, executes approved payments, and remembers claimant communication preferences. Deployments occur daily and a region can fail while a payment result is in flight.

    Address memory taxonomy, authoritative state, event schema, fold and snapshot behavior, pause/resume, timers and signals, model nondeterminism, operation-key reconciliation, exact approvals, compensation, deletion, regional recovery, evaluation, capacity, and version migration.

    L5 and L6 signals¶

    L5¶

    • Separates working/episodic/semantic/procedural memory from authoritative events.
    • Reconstructs runs from ordered events and handles crash-after-commit safely.
    • Persists budgets and capabilities across pause/resume.
    • Reauthorizes and revalidates exact approval at commit.
    • Treats compensation as a fallible forward action.
    • Computes event storage, approval staffing, or replay throughput.

    L6¶

    • Defines fleet event, memory, authority, approval, and deletion standards with owners.
    • Supports compatible replay across daily deployments and explicit open-run migrations.
    • Quantifies regional failure, fencing, reconciliation, and controlled resume capacity.
    • Governs memory purpose, retention, correction, provenance, and exceptions across products.
    • Connects operational and review economics to SLOs and capacity commitments.
    • Names evidence that can falsify exactly-once, replay, memory-quality, and HITL assumptions.

    Final design checklist¶

    • Durable events and fallible memory have separate contracts.
    • Every side effect has operation-key reconciliation and terminal evidence.
    • Replay reuses recorded nondeterminism; simulations cannot write production.
    • Pause/resume preserves budgets, versions, authority, and waiting condition.
    • Approvals bind exact intent and are revalidated at commit.
    • Compensation has idempotency, deadlines, failure ownership, and audit.
    • Memory preserves provenance, ACL, validity, correction, retention, and deletion.
    • Migrations retain readers and activities for open and replayable histories.
    • Regional recovery fences writers and rate-limits resume.
