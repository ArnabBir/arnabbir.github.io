    Eight Executable Fault Labs¶

    These are offline-first teaching fixtures, not production libraries. Download fixtures.py, or run the repository copy from its root. Python 3.9+ and its standard library are the only requirements. SQLite support must be present in the Python installation. Temporary databases are isolated and automatically removed; no existing service or user database is modified.

    python3 docs/engineering/fixtures.py
python3 docs/engineering/fixtures.py --lab durable-counter --seed 17 --seeds 1
python3 docs/engineering/fixtures.py --lab versioned-cache --seed 1 --seeds 20
python3 docs/engineering/fixtures.py --lab fenced-worker --mode broken --seeds 1
python3 docs/engineering/fixtures.py --lab fenced-worker --mode fixed --seeds 1

    The standalone broken command intentionally exits 1. verify is the default: it requires an oracle failure from the broken variant for every seed, then requires the fixed variant to pass. It emits one JSON result per lab and exits zero only when all selected checks pass. Unexpected implementation errors are not accepted as proof that the intended mutation was caught. Fixed paths use explicit comparisons, not Python assertions that vanish under optimization.

    Evidence protocol¶

    For every lab, first write the invariant and predict the shortest failure trace without reading the implementation. Run broken mode and capture the reported seed and counterexample. Inspect the oracle separately from the update path. Explain the guard, run fixed mode, then run verify across multiple seeds. Add a new regression and write one limitation that would matter in deployment.

    Each lab is independently selectable. Randomness varies payloads, epochs, arrival counts, or delivery order; it is not a claim of exhaustive exploration. The cache fixture explicitly enumerates all six orders of three updates. The outbox fixture crosses two producer and two consumer crash boundaries. The counter tests four process termination boundaries.

    Durable counter¶

    Canonical explanation: storage recovery. Fixture: durable-counter. Model: actual file-backed SQLite, independent child processes, abrupt os._exit, explicit journal_mode=DELETE, and synchronous=FULL in the worker. The runtime's actual SQLite version and filesystem still matter.

    Invariant: acknowledged effects survive process restart; unique command IDs apply once; repeated IDs return the original result; conflicting reuse is rejected. The parent oracle chooses the delta and expected state by crash boundary, records the child response, then reopens the DB. It does not derive the expected total from the tested receipts.

    Seed 17 selects an illustrative increment. The broken child mutates within a transaction, prints success, and exits before commit. The parent observes a success response but a recovered zero. Fix: commit the mutation and receipt before acknowledgment. A lost response after commit remains ambiguous to the caller but is resolved by retrying the same ID.

    Regressions include termination before work, after update, after commit, and after acknowledgment; two retries; different intent under one ID; a second independent ID; and replay of the first ID after the second increments the counter. The second ID returns the new total while replay of the first must keep its old response.

    Limitations: This is not power-loss testing, disk-corruption injection, concurrent-writer stress, or a new WAL implementation. SQLite's transaction protocol supplies the durability mechanism. The kernel and device remain alive during a process exit. A successful fixture is not actual machine-failure durability proof.

    Fenced worker¶

    Canonical explanation: leases need fencing. Fixture: fenced-worker. Model: serialized authority installation and atomic sink mutations.

    Invariant: only the currently installed epoch may mutate protected state. The independent expected acceptance list contains the initial owner and the new owner, not stale or invented future epochs. Broken mode trusts the worker's earlier authorization; a paused worker overwrites newer work.

    Fix: compare the presented epoch with installed authority atomically with the effect. Regressions issue stale writes both before and after the new worker's first write and reject an arbitrary larger token. Current-epoch writes must still succeed.

    Limitations: No real lease clock, consensus allocator, network authentication, or multi-sink atomicity. Exact installed-epoch equality is stronger than a maximum-seen-token design; do not confuse the two. An external sink without fencing remains an unresolved side-effect boundary.

    Outbox and inbox¶

    Canonical explanation: API replay and distributed transactions. Fixture: outbox-inbox. Model: explicit atomic transaction versus split-write transitions; simulated persistent dictionaries survive logical process crashes.

    Invariant: every accepted source command has an event, and each event causes one local effect with one receipt. The oracle is the original command list and its multiset, independent of outbox and inbox contents. Broken producer commits business state before creating an event; retry sees the business row and never emits it. Broken consumer commits an effect before its receipt; redelivery repeats it.

    Fix both boundaries: business plus outbox in one transaction, inbox receipt plus local effect in another. Delivery remains duplicate-prone. Regressions cross producer and consumer cut points, shuffle triple deliveries, verify all source IDs, and require exactly one effect per ID rather than only the correct aggregate sum. Broken-mode checks require both the producer-only gap and the consumer-only gap to be detected, so the first cannot mask the second.

    Limitations: Atomic commit is assumed in this model; only the counter exercises a real database transaction. This does not prove broker retention, relay liveness, consumer concurrency, or external exactly-once effects. A full broker outage needs explicit retry, retention, and reconciliation tests.

    Versioned cache¶

    Canonical explanation: caching and migration version guards. Fixture: versioned-cache. Model: per-key authoritative revisions, retained version knowledge, and cache eviction.

    Invariant: late fills cannot replace newer state or resurrect a deletion. The independent oracle requires revision 3 after all three authoritative updates, absence after deletion/eviction, and the new payload after revision 4 recreates the object. Broken mode uses arrival order.

    Fix: install only a newer revision and retain the deletion/version watermark when evicting cached payloads. Regressions enumerate all six delivery permutations, evict the payload, deliver an old fill, recreate with a newer revision, and replay the same version without mutating its payload.

    Limitations: Revision allocation is assumed authoritative, and conflicting payloads with the same revision are ignored rather than diagnosed. Retained watermarks consume memory; deleting them needs a safe replay/expiry boundary or a canonical revalidation path. No TTL timing or cache stampede is simulated.

    Shard movement¶

    Canonical explanation: brownfield migration. Fixture: shard-movement. Model: snapshot, shuffled change records, versioned tombstones, epoch transfer, and reverse catchup.

    Invariant: the target at cutover equals the source command ledger, and the old route cannot acknowledge writes after transfer. The oracle is a hand-derived key/value map, not a count or checksum of copied rows. Broken backfill overwrites a newer change or resurrects a deleted row.

    Fix: compare revisions when merging snapshot and change records; preserve tombstones; fence old-owner writes. Regressions include reordered changes, a duplicate record, stale routing, a post-cutover write, and reverse copying that preserves the new write and deletion.

    Limitations: There is no real CDC connector, distributed routing propagation, or contiguous-watermark tracker. The input change set is complete by construction. Learners must separately test missing offsets and snapshot/log consistency before claiming a safe migration implementation.

    Temporal corrections¶

    Canonical explanation: temporal data. Fixture: temporal-corrections. Model: immutable valid-time assertions with knowledge cutoffs and explicit precedence.

    Invariant: answering a past-valid-time query respects both validity and what was known then. The oracle is a hand-written set of point answers. Broken mode chooses the latest known assertion even when it does not apply to the requested valid time.

    Fix: filter by half-open valid interval and knowledge cutoff before selecting precedence. Regressions cover before/inside/after the correction, exact boundaries, a query before any knowledge, shuffled insertion order, and duplicate assertions.

    Limitations: One entity, integer-day timestamps, no calendar/time-zone conversion, no competing-authority corrections, and no real incremental aggregate. A versioned correction policy is still needed for concurrent domain updates.

    Permission revocation¶

    Canonical explanation: revocation contract. Fixture: permission-revocation. Model: policy installed at the effect sink and atomic effect-time comparison.

    Invariant: an old decision cannot authorize an effect after revocation or across tenant boundaries. The independent acceptance list includes only the pre-revocation effect and a fresh capability after regrant. Broken mode trusts a cached allow decision.

    Fix: scope policy by tenant/principal and compare current version and permission at the effect boundary. Regressions include unknown principal, cross-tenant replay, revoke then regrant, rejection of an old capability after regrant, and successful current authorization.

    Limitations: No cryptographic credentials, distributed policy propagation, object/action hierarchy, or data already downloaded by a user. The simulation checks only its scoped effect contract; it cannot prove globally instantaneous revocation.

    Bounded scheduling¶

    Canonical explanation: runtime ownership and operations. Fixture: bounded-scheduling. Model: finite tenant burst, bounded waiting queues, cancellation, round-robin dispatch, and drain.

    Invariant: global queued work is at most four, each tenant queues at most two, every admitted ID completes or cancels once, and rejected work never executes. The oracle checks bounds and conservation from the original arrivals, not the scheduler's own success counter. Broken mode admits the full burst without bounds.

    Fix: reject before enqueue when either budget is exhausted; dispatch across tenant queues. Regressions vary burst size, ensure the small tenant runs within two dispatches, cancel queued work twice, reuse the released slot, verify ID conservation, and drain all remaining work.

    Limitations: Queue bounds exclude active workers because dispatch completes immediately in this model. There are no variable job durations, deadlines, byte budgets, continuous arrivals, or preemption. Finite round-robin dispatch evidence is not a proof of production fairness. Extend to explicit active permits and deadline/cancellation races before adapting the idea to a real executor.

    Assessment handoff¶

    For L5, submit the failing trace, guard, independent oracle, and one added boundary regression. For L6, additionally identify an unmodeled physical or organizational assumption and design a safe integration drill to test it. Use the assessment gates and capstone; passing the default command alone is not completion of the learning exercise.
