    Local-First Systems and CRDTs¶

    Local-first software treats a local replica as the primary interaction surface and synchronizes replicas when networks permit. Conflict-free replicated data types (CRDTs) can make selected concurrent operations converge without central serialization, but they do not choose product intent, authorization, retention, or a usable undo model.

    Generalist boundary¶

    A generalist can design offline caching, optimistic updates, and server reconciliation. Specialist depth begins when multiple replicas accept writes while disconnected, operation order differs, deletes must dominate late updates, metadata must be compacted, and users expect undo to preserve other people's work. If edits always require connectivity or one server can serialize all writes, a simpler version check may be better.

    Requirements and invariants¶

    Design a collaborative field notebook used offline for days on phones and laptops. Notes contain text, checklists, tags, and attachments. Teams can revoke access.

    • Local accepted operations survive process and device restart before the UI confirms them.
    • Applying the same operation more than once has no additional effect.
    • Replicas that receive the same authorized operations converge.
    • Conflict behavior is defined per field; no generic merge silently discards intent.
    • Delete, restore, retention, and garbage-collection semantics are explicit.
    • Undo creates a new operation and never rewinds another replica's history.
    • Revocation blocks future server-mediated access but does not claim to erase plaintext already obtained offline.
    • Sync works incrementally and can recover from lost cursors and compacted history.

    Architecture and state¶

    flowchart LR
    U[Local UI] --> O[(Durable operation log)]
    O --> L[(Local materialized state)]
    O --> S[Sync client]
    S <--> G[Sync gateway]

    P --> N

    Use a unique operation ID such as (replica_id, counter). The client appends locally before materializing. The server deduplicates, authorizes against a membership epoch, assigns a journal sequence for transport, and returns missing operations. Journal sequence is not the semantic conflict order.

    Conflict models and CRDT tradeoffs¶

    Choose a type that matches user intent:

    Data Candidate Tradeoff
    membership/tag set observed-remove set remove carries observed add identities; metadata grows
    counter grow-only or PN-counter converges, but per-replica components require retirement
    one selected value multi-value or LWW register multi-value exposes conflict; LWW can lose intent and trusts ordering
    ordered text/list sequence CRDT concurrent insertion converges; identifiers and indexing cost grow
    object map map of nested CRDTs deletion versus nested update needs an explicit rule

    State-based CRDTs merge join-semilattice states and tolerate message loss, but naive transfer is large; delta-state forms reduce it. Operation-based CRDTs send compact operations but require reliable causal delivery or additional metadata. A central sync journal often makes op-based transport practical while clients remain offline-capable.

    For an observed-remove tag set, A adds urgent with dot A:1. B observes A:1 and removes that dot while disconnected A adds a new dot A:2. Merge retains A:2, so urgent remains: remove means "remove observed additions," not "ban every future or concurrent addition." Duplicate delivery of A:2 must not create another tag. The Delta-state CRDT paper explicitly separates joinable delta dissemination from operation-based delivery assumptions (primary abstract accessed 2026-09-08).

    Lamport timestamps order events consistently but do not identify concurrency. Vector clocks identify causal relationships but have one component per replica unless compressed. Dotted version vectors represent a new event plus summarized causal history. Hybrid logical clocks aid observability and LWW ordering, but clock order still does not equal user intent.

    For text, index-based patches are unsafe: concurrent inserts shift positions. Sequence CRDTs assign stable position identifiers. Interleaving surprises remain possible, and metadata or identifier length can grow. Operational transformation is a valid alternative when a server orders operations and transforms them; it has different offline and correctness assumptions.

    Tombstones, compaction, undo, and permissions¶

    A remove must remember enough causal information to reject or distinguish delayed adds. Garbage-collect a tombstone only when every relevant replica has acknowledged a causal frontier, or after the system intentionally expires old replicas and forces them to resync from a fresh snapshot. Time-based deletion alone can resurrect state from a device offline longer than the retention window.

    Compaction writes a snapshot plus causal summary, then retains post-snapshot operations. A returning client with an old generation receives the snapshot and rebases or replays still-valid local operations. If its replica identity has expired, reject raw pre-expiry operations: preserve a private export and let an authorized user re-express intended edits as new operations against the current snapshot. Copying old dots into the new generation can resurrect deleted data. Test this path; it is the common path for devices offline for months.

    Undo emits a semantic inverse tied to the original operation. Undoing "add tag" removes the observed add dot, not all concurrent adds of the same tag. Undoing a text insertion deletes the elements created by that insertion. Some actions, such as accepting another user's conflict resolution, may need a new forward edit rather than a mechanical inverse.

    Authorization is not monotonic. A user may create valid operations offline after an administrator has revoked access. The server must reject operations from stale membership epochs. Product policy decides whether the client exports those changes privately, discards them, or asks an authorized owner to import them. End-to-end encryption further limits server-side validation and deletion guarantees.

    Calculations¶

    Suppose 100,000 active users produce 300 operations/day at 220 bytes each:

    operations/day = 30 million
raw log/day = 30,000,000 * 220 = 6.6 GB

    Using an explicit planning assumption of three replicas and 3x per-replica storage amplification for indexes plus envelopes:

    physical log/day = 6.6 GB * 3 replicas * 3 storage amplification
                 = 59.4 GB/day

    The multipliers must be replaced with measured encoding, compression, and index ratios before capacity approval. Under this illustrative assumption, a 30-day uncompacted hot journal is roughly 1.8 TB. Partition by team and server sequence; one large team needs subpartitions or object routing without losing a resumable team feed.

    If a sequence element ID averages 24 bytes and a 1 MB document has 500,000 characters, IDs alone consume about 12 MB before payload and indexes. Character-level CRDTs can dominate document size. Chunked runs reduce metadata but make split, merge, and concurrent edit logic harder.

    A reconnecting device with 200,000 pending operations over a 256 Kbit/s link cannot upload a 44 MB raw log in less than about 23 minutes. Compress, exchange causal summaries first, batch operations, prioritize visible objects, and resume by acknowledged batch.

    Failure, security, and operations¶

    Failure Control
    duplicate or reordered sync idempotent op IDs and causal merge
    ancient device resurrects delete tombstone frontier or forced snapshot resync
    corrupted local log checksummed records, atomic append, last-good recovery
    replica counter rollback persist counter transactionally or rotate replica ID
    compromised device floods ops per-device revocation, quotas, signed session, server validation
    rejected offline edits after revocation explicit export/recovery product flow
    metadata explosion snapshots, replica retirement, measured compaction
    attachment referenced before upload content hash, pending state, retryable blob transfer

    Monitor local append failures, unsynced operation age and count, sync bytes and duration, deduplication, authorization rejection by epoch, merge failures, snapshot fallback, tombstone age, metadata-to-payload ratio, active replica cardinality, and convergence probes. For state-based CRDTs, property-test merge commutativity, associativity, and idempotence. For operation-based CRDTs, test duplicate delivery and permutations of concurrent operations while preserving required causal-delivery preconditions; do not require arbitrary operations to commute. Fuzz reorder only where the algorithm's metadata or transport contract permits it, plus partition, crash, delete/update, and stale-snapshot cases.

    Rollout and evolution¶

    Begin with one offline writer per object and explicit conflict copies. Add durable local logs and resumable sync. Introduce CRDTs field by field where concurrent intent is understood, starting with sets or counters before rich text. Dual-materialize old and new representations, replay recorded traces, and compare visible state.

    Version operation schemas and keep old decoders through the maximum offline period. A migration must define how stale clients submit old operations. Roll out compaction only after frontier accounting is observable. Retire replicas through an explicit epoch transition and require old devices to bootstrap from a snapshot. Preserve export before destructive migrations.

    Interview case¶

    Design an offline-first incident notebook. Up to 50 responders edit during network partitions. Notes, task status, and timeline events must converge. Access may be revoked during an incident, and the final record is exported for audit.

    Clarify offline duration, object sizes, ordering needs, whether edits may be rewritten, conflict visibility, device trust, encryption, membership changes, retention, attachment handling, and audit expectations.

    Worked answer¶

    Store a checksummed local operation log and materialized view on every device. Use append-only timeline events, an observed-remove set for assignees/tags, a register with explicit conflict display for task status, and a sequence CRDT for note text. Each operation has a replica counter, causal context, incident membership epoch, and actor signature where device identity is required.

    The server authorizes the operation epoch, deduplicates it, and appends it to an incident journal. Devices sync causal summaries and journal cursors, then exchange missing batches. Snapshots contain CRDT state plus a causal frontier. Tombstones remain until all active replicas pass the frontier; expired replicas must bootstrap and cannot replay pre-expiry state. Revoked users' later offline operations are rejected and offered as a private export, not merged automatically.

    Undo emits inverse operations scoped to the original dots or sequence elements. The audit export contains canonical operations, actors, wall-clock observations, and final materialized state, while acknowledging that causal order is stronger than device clock order. Rollout starts with timeline and tasks before collaborative text because sequence metadata and UX need separate validation.

    Staff-level signals¶

    • Defines convergence separately from user-intent preservation.
    • Selects conflict semantics per field instead of saying "use a CRDT."
    • Explains causal metadata, tombstone safety, and stale-replica expiry.
    • Treats undo as a new operation and permissions as non-monotonic state.
    • Quantifies metadata and reconnect bandwidth, not only document payload.
    • Includes operation-version evolution and forced snapshot bootstrap.
    • States honest limits of revocation and offline plaintext.
