    Thread Safety and the Java Memory Model¶

    Thread safety is not "the program usually prints the right value." A class is thread-safe when it preserves its contract under every permitted interleaving of its public operations, without requiring callers to add undocumented coordination.

    The Java Memory Model (JMM) defines which writes a read may observe and which reorderings are legal. It is a language-level contract across compilers, the JIT, processors, and caches. Hardware intuition alone is not a correctness proof.

    Learning goals¶

    After this chapter, you should be able to:

    • distinguish atomicity, visibility, and ordering;
    • identify conflicting accesses and data races;
    • construct a happens-before proof using Java's rules;
    • explain safe uses and limits of final and volatile;
    • design immutable objects and safe publication paths;
    • diagnose lost updates, check-then-act races, and unsafe compound actions;
    • prevent this escape during construction;
    • implement and justify double-checked locking correctly in Java 21.

    1. Three separate correctness dimensions¶

    Atomicity¶

    An operation is atomic relative to other operations when no thread can observe it partially completed. Reading or writing an individual int is atomic, but count++ is a read-modify-write sequence:

    read count
compute count + 1
write result

    Visibility¶

    A write is visible to another thread when the JMM requires the later read to observe that write or a still later write. Elapsed wall-clock time does not create visibility.

    Ordering¶

    The compiler, JIT, and processor may reorder actions as long as single-thread behavior remains legal and the JMM's inter-thread constraints are preserved. A happens-before relationship constrains which effects must be visible and ordered across threads.

    Requirement Broken assumption Mechanism examples
    Atomicity "The statement is one line." Lock, atomic read-modify-write, thread confinement
    Visibility "The other core will refresh eventually." Volatile edge, monitor/lock edge, start/join, concurrent API contract
    Ordering "Source order is global order." Happens-before relationships

    A mechanism may solve one requirement but not another. A volatile counter write is visible, but counter++ on a volatile field is still not an atomic increment.

    2. Conflicting accesses and data races¶

    Two accesses conflict when they access the same variable, at least one is a write, and they occur in different threads. A program has a data race when conflicting accesses are not ordered by happens-before.

    Data-race freedom is a powerful design target. Correctly synchronized programs appear sequentially consistent: their actions can be understood as an interleaving that preserves each thread's program order and synchronization rules.

    Do not confuse a data race with a higher-level race condition:

    • A data race is defined by unsafely ordered conflicting memory accesses.
    • A race condition is a broader outcome that depends on timing or ordering.
    • A program can have no data race and still violate a compound business invariant because individually synchronized methods are composed incorrectly.

    3. Lost updates¶

    Broken counter:

    final class BrokenCounter {
    private int value;

    void increment() {
        value++;
    }

    int get() {
        return value;
    }
}

    A possible interleaving from zero:

    Step Thread A Thread B value
    1 reads 0 0
    2 reads 0 0
    3 computes 1 0
    4 computes 1 0
    5 writes 1 1
    6 writes 1 1

    Two increments produce one. Marking value volatile fixes neither the read-modify-write atomicity nor the lost update.

    If the state is one independent counter:

    final class Counter {
    private final java.util.concurrent.atomic.AtomicLong value =
            new java.util.concurrent.atomic.AtomicLong();

    long increment() {
        return value.incrementAndGet();
    }

    long get() {
        return value.get();
    }
}

    incrementAndGet is one atomic read-modify-write and is the operation's linearization point. If the invariant spans the counter and another field, one AtomicLong is not enough; put the compound state under one lock or encode it in one immutable value updated atomically.

    4. Check-then-act and method composition¶

    Even thread-safe method calls can form an unsafe compound action:

    var users = java.util.Collections.synchronizedMap(
        new java.util.HashMap<String, User>());

if (!users.containsKey(id)) {
    users.put(id, loadUser(id));
}

    Interleaving:

    Step Thread A Thread B
    1 containsKey(id) returns false
    2 containsKey(id) returns false
    3 computes user A computes user B
    4 put(id, userA)
    5 put(id, userB) overwrites A

    Each method is synchronized, but the invariant "initialize once" spans two calls. Use a compound API whose contract provides per-key atomicity:

    private final java.util.concurrent.ConcurrentHashMap<String, User> users =
        new java.util.concurrent.ConcurrentHashMap<>();

User user(String id) {
    return users.computeIfAbsent(id, this::loadUser);
}

    Tradeoffs matter. The mapping function should be short, must not recursively update the same mapping, and may be invoked again if an invocation fails or does not establish a mapping. Do not perform irreversible external effects and assume exactly-once execution. If loading is slow, consider caching a future, explicit single-flight state, timeout, and failure eviction policy.

    5. Happens-before: the proof vocabulary¶

    If action A happens-before action B, A's effects are visible to B and A is ordered before B for JMM reasoning. The relation is transitive.

    Core rules used in interviews:

    Rule Edge
    Program order Earlier action in one thread -> later action in that thread
    Monitor Unlock of monitor M -> every later lock of M
    Explicit lock Unlock of lock L -> later successful lock of L
    Volatile Write to volatile V -> every subsequent read of V that observes that order
    Thread start Actions before t.start() -> actions in thread t
    Thread termination Actions in t -> successful return from t.join()
    Transitivity A -> B and B -> C implies A -> C
    Concurrent utilities Library-specific edges for submission, Future.get, latch, queue handoff, and others

    The JLS defines additional details, including synchronization order and default initialization. In an interview, use the smallest chain that proves the relevant read.

    Example proof¶

    final class ResultBox {
    private int result;

    int calculate() throws InterruptedException {
        Thread worker = new Thread(() -> result = 42);
        worker.start();
        worker.join();
        return result;
    }
}

    Proof:

    1. The worker's write result = 42 precedes its termination by program order.
    2. All actions in the worker happen-before the successful return from join.
    3. The return reads result after join by caller program order.
    4. By transitivity, the write happens-before the read, which must see 42 absent another write.

    6. Visibility failure in a stop flag¶

    final class BrokenRunner {
    private boolean stop;

    void run() {
        while (!stop) {
            doWork();
        }
    }

    void stop() {
        stop = true;
    }
}

    The read and write conflict and have no happens-before edge. The worker may observe a stale value. The JIT is also allowed to optimize under the JMM's data-racy semantics in ways that invalidate the intuition "it rereads on every loop."

    For a single independent flag:

    final class Runner {
    private volatile boolean stop;

    void run() {
        while (!stop) {
            doWork();
        }
    }

    void stop() {
        stop = true;
    }
}

    A write to stop happens-before a subsequent read that observes it. This design assumes doWork returns often enough to check the flag. If it blocks in interruptible APIs, interruption may be the appropriate cancellation mechanism. A volatile flag does not wake a blocked socket read, condition wait, or queue operation by itself.

    7. Volatile: publication and state flags¶

    A volatile field provides:

    • atomic reads and writes for that field;
    • visibility and ordering through the volatile happens-before rule;
    • no mutual exclusion;
    • no automatic atomicity for compound expressions or invariants across fields.

    Publishing related data with a volatile flag¶

    final class SnapshotPublisher {
    private int[] snapshot;
    private volatile boolean ready;

    void publish(int[] source) {
        snapshot = source.clone();
        ready = true;
    }

    int[] current() {
        if (!ready) {
            throw new IllegalStateException("not ready");
        }
        return snapshot.clone();
    }
}

    The write to snapshot precedes the volatile write to ready by program order. A reader's subsequent volatile read of ready == true creates an edge from the volatile write. By transitivity, the initialized array reference and contents are visible. Cloning on both boundaries prevents callers from mutating the published representation.

    This one-time publication design would be wrong if a publisher later wrote ready = false, replaced snapshot, and allowed readers to infer versions from one Boolean. Prefer a single volatile immutable snapshot reference:

    record Snapshot(long version, java.util.List<String> values) {
    Snapshot {
        values = java.util.List.copyOf(values);
    }
}

final class Snapshots {
    private volatile Snapshot current = new Snapshot(0, java.util.List.of());

    Snapshot current() {
        return current;
    }

    void publish(Snapshot next) {
        current = next;
    }
}

    Each read obtains one coherent immutable version. Writers still need coordination if version monotonicity or compare-and-set semantics matter.

    8. Final fields and immutability¶

    final prevents reassignment after construction. The JMM also gives final fields special initialization safety: when an object is properly constructed and its reference does not escape during construction, another thread that obtains the reference is guaranteed to see the initialized final fields, including the reachable state covered by the final-field rule.

    Final does not recursively make an object immutable:

    final class BrokenConfig {
    private final java.util.List<String> hosts;

    BrokenConfig(java.util.List<String> hosts) {
        this.hosts = hosts;
    }

    java.util.List<String> hosts() {
        return hosts;
    }
}

    The caller can mutate the original list or the returned list. Correct it with defensive copies:

    final class Config {
    private final java.util.List<String> hosts;

    Config(java.util.List<String> hosts) {
        this.hosts = java.util.List.copyOf(hosts);
    }

    java.util.List<String> hosts() {
        return hosts;
    }
}

    List.copyOf rejects null elements and produces an unmodifiable list, which is suitable only if element objects are themselves immutable or safely shared. Deep immutability is a property of the entire reachable object graph.

    Immutable-object checklist¶

    • Make state private and final.
    • Validate constructor arguments.
    • Copy mutable inputs before storing them.
    • Do not expose mutable internals.
    • Ensure referenced elements are immutable or copied.
    • Do not let this escape during construction.
    • Place mutable caches outside the value or synchronize them separately.

    9. Safe publication¶

    Publication makes an object reference reachable by another thread. Safe publication uses a JMM mechanism that guarantees the receiving thread sees a valid initialized state.

    Common safe publication mechanisms include:

    • storing the reference into a properly used volatile field;
    • storing it under a lock and reading it under the same lock;
    • completing construction before placing it in a thread-safe collection;
    • static initialization;
    • passing state to a thread before calling start();
    • using concurrent utility methods with documented memory-consistency effects.

    Broken publication:

    final class Registry {
    private Config config;

    void initialize() {
        config = new Config(java.util.List.of("a", "b"));
    }

    Config config() {
        return config;
    }
}

    If different threads call these methods without ordering, there is a data race on config. Make the reference volatile for independently replaceable immutable snapshots:

    final class Registry {
    private volatile Config config;

    void initialize() {
        config = new Config(java.util.List.of("a", "b"));
    }

    Config config() {
        Config value = config;
        if (value == null) {
            throw new IllegalStateException("not initialized");
        }
        return value;
    }
}

    The volatile write publishes the constructed immutable object to a subsequent volatile read. If initialization must happen exactly once, add a lock, static holder, or atomic transition; volatile alone permits multiple writers. In the broken version, the reference race can keep a reader seeing null; it does not negate Config's properly constructed final-field guarantees when a non-null reference is observed. Do not generalize this final-field exception to mutable or non-final state. The earlier SnapshotPublisher is strictly one-shot; even a second publish without resetting ready would race on the ordinary array reference.

    10. this escape¶

    An object escapes when another thread can reach it before construction and initialization are complete.

    Broken registration from a constructor:

    final class BrokenListener {
    private final String topic;

    BrokenListener(EventBus bus, String topic) {
        bus.register(this);
        this.topic = topic;
    }

    void onEvent(Event event) {
        System.out.println(topic.length());
    }
}

    The bus may invoke onEvent before topic is assigned. Final-field guarantees require proper construction; publishing this during construction defeats that premise.

    Use a factory that publishes only after construction:

    final class Listener {
    private final String topic;

    private Listener(String topic) {
        this.topic = java.util.Objects.requireNonNull(topic);
    }

    static Listener createAndRegister(EventBus bus, String topic) {
        Listener listener = new Listener(topic);
        bus.register(listener);
        return listener;
    }

    void onEvent(Event event) {
        System.out.println(topic.length());
    }
}

    The bus itself must safely publish registrations to dispatch threads. Moving code out of the constructor fixes premature escape but does not excuse the bus from its own synchronization policy.

    Other escape routes include:

    • starting a thread with this::run in a constructor;
    • submitting a lambda that captures this;
    • assigning this to a static or externally reachable field;
    • invoking an overridable method from a constructor when a subclass can expose state.

    11. Double-checked locking¶

    The historical broken form lacks volatile:

    final class BrokenLazyService {
    private Service instance;

    Service get() {
        if (instance == null) {
            synchronized (this) {
                if (instance == null) {
                    instance = new Service();
                }
            }
        }
        return instance;
    }
}

    The unsynchronized outer read races with the write. Without the required ordering, a reader is not guaranteed to observe a properly initialized Service.

    Correct Java 21 form:

    final class LazyService {
    private volatile Service instance;

    Service get() {
        Service value = instance;
        if (value == null) {
            synchronized (this) {
                value = instance;
                if (value == null) {
                    value = new Service();
                    instance = value;
                }
            }
        }
        return value;
    }
}

    Reasoning:

    1. Construction completes before instance = value by program order.
    2. The assignment is a volatile write.
    3. A fast-path volatile read that sees the non-null reference occurs after that write in synchronization order.
    4. The volatile write happens-before that read, publishing construction effects.
    5. The inner check under the monitor ensures only one value is installed.
    6. The local variable avoids repeated volatile reads on the fast path.

    This idiom relies on the memory model in Java 5 and later; for pre-Java-5 code, its semantics were not sufficient. In Java 21, prefer simpler initialization when possible:

    final class Services {
    private Services() {}

    static Service instance() {
        return Holder.INSTANCE;
    }

    private static final class Holder {
        private static final Service INSTANCE = new Service();
    }
}

    Class initialization is synchronized by the JVM and safely publishes static fields. Use an enum singleton or eager static final field when laziness is unnecessary. Complexity is not free merely because the idiom is valid.

    12. Multi-field invariants and volatile snapshots¶

    Broken attempt:

    final class BrokenRange {
    private volatile int lower;
    private volatile int upper;

    void set(int lower, int upper) {
        if (lower > upper) {
            throw new IllegalArgumentException();
        }
        this.lower = lower;
        this.upper = upper;
    }
}

    Each field is visible, but a reader can combine values from different updates. For transitions (0, 10) -> (20, 30), a reader might observe (20, 10), violating lower <= upper.

    Publish one immutable value:

    record Range(int lower, int upper) {
    Range {
        if (lower > upper) {
            throw new IllegalArgumentException("lower exceeds upper");
        }
    }
}

final class Ranges {
    private volatile Range current = new Range(0, 10);

    Range get() {
        return current;
    }

    void set(int lower, int upper) {
        current = new Range(lower, upper);
    }
}

    The reference update is atomic and volatile-published. If writers must reject stale versions or derive updates from the current value, use an AtomicReference compare-and-set loop or a lock.

    13. API memory-consistency reasoning¶

    High-level concurrency APIs document ordering guarantees. Use them instead of reverse-engineering implementations.

    Examples from Java 21 contracts include:

    • Actions before submitting a task to an Executor happen-before its execution begins.
    • Actions in an asynchronous computation happen-before actions following a successful Future.get() in another thread.
    • Actions before CountDownLatch.countDown() happen-before actions after a corresponding successful await().
    • Actions before placing an element into a concurrent collection happen-before another thread's access or removal of that element where the API specifies it.

    Example handoff:

    Message message = new Message(payload);
queue.put(message);

// In another thread:
Message received = queue.take();
received.process();

    The BlockingQueue memory-consistency contract safely hands off actions before insertion to actions after removal. If Message remains mutable and both threads continue changing it after handoff, those later accesses need another policy.

    14. Testing memory-model claims¶

    This test is suggestive but not a proof:

    for (int round = 0; round < 100_000; round++) {
    // Start racing operations and assert observed outcomes.
}

    Passing means only that sampled executions did not reveal a defect. Failing once is useful evidence. For low-level JMM questions, jcstress provides a harness designed to classify outcomes across generated schedules and runtime optimizations.

    At the class-design level:

    1. Prove every conflicting access is ordered or intentionally atomic.
    2. Write deterministic tests for public invariants using barriers and latches.
    3. Add stress tests for schedule diversity.
    4. Bound every wait so broken code fails rather than hanging the suite.
    5. Capture worker exceptions.
    6. Run on more than one core and, when practical, more than one supported JDK and architecture.

    Tradeoffs¶

    Technique Best fit Strength Limitation
    Immutability Read-mostly values and snapshots Minimal synchronization after publication Copying and update allocation
    Volatile field Independent flag or snapshot reference Cheap visibility and ordering No compound mutual exclusion
    Intrinsic/explicit lock Multi-field invariant Simple atomic transition proof Blocking and contention
    Atomic variable One value with CAS-friendly updates Non-blocking atomic RMW Retry cost; awkward compound state
    Concurrent collection Shared collection operations Scalable documented compound APIs Cross-operation invariants still need design
    Thread confinement Per-request or single-owner state Removes sharing and races Handoff and ownership limits

    Choose the mechanism from the invariant. Do not choose atomics because they appear more advanced, or locks because they feel safer without defining scope.

    Interview traps¶

    • Saying an int counter is safe because reads and writes are atomic.
    • Adding volatile to count++ and claiming lost updates are fixed.
    • Using thread-safe collection methods in a non-atomic check-then-act sequence.
    • Treating happens-before as elapsed-time order.
    • Assuming final makes referenced collections immutable.
    • Publishing a fully constructed object through an ordinary raced field.
    • Starting a thread or registering a callback inside a constructor.
    • Writing double-checked locking without volatile.
    • Using two volatile fields for one cross-field invariant.
    • Quoting hardware cache behavior instead of a JMM or API guarantee.
    • Assuming a stress test proves race freedom.

    Exercise 1: Fix a check-then-act race¶

    final class CouponBook {
    private final java.util.Set<String> used =
            java.util.concurrent.ConcurrentHashMap.newKeySet();

    boolean redeem(String code) {
        if (used.contains(code)) {
            return false;
        }
        used.add(code);

    }
}

    Exercise 4: Find this escape¶

    class BaseProcessor {
    BaseProcessor(Registry registry) {
        registry.register(this::process);
    }

    void process(Item item) {}
}

final class Processor extends BaseProcessor {
    private final Validator validator;

    Processor(Registry registry, Validator validator) {
        super(registry);
        this.validator = validator;
    }

    @Override
    void process(Item item) {
        validator.validate(item);
    }
}

    Explain the failure and redesign construction.

    Solutions

    Solution 1¶

    Use the return value of the atomic set operation:

    boolean redeem(String code) {
    if (!used.add(code)) {
        return false;
    }
    chargeDiscount(code);
    return true;
}

    The successful add is the in-memory linearization point. Exactly one thread in this process reaches chargeDiscount for a code. This is not end-to-end exactly once: the process can crash after recording the code but before charging, or charging can succeed before an ambiguous exception. Durable redemption requires a transactional record, idempotency key accepted by the discount system, and reconciliation or an outbox-style workflow. If charging fails permanently, define whether the code remains consumed or whether a guarded rollback permits retry.

    Solution 2¶

    1. Builder actions initialize the immutable Rules before submission by program order.
    2. Actions before task submission happen-before task execution under the executor contract.
    3. Task reads and result production occur before task completion by program order.
    4. Task actions happen-before actions after successful Future.get under the Future contract.
    5. By transitivity, construction is visible both inside the task and to caller actions after get that consume the result.

    Immutability prevents later mutation from introducing a new race.

    Solution 3¶

    record Metrics(long requests, long failures) {
    Metrics {
        if (requests < 0 || failures < 0 || failures > requests) {
            throw new IllegalArgumentException("invalid metrics");
        }
    }
}

final class MetricsView {
    private volatile Metrics current = new Metrics(0, 0);

    Metrics current() {
        return current;
    }

    void publish(long requests, long failures) {
        current = new Metrics(requests, failures);
    }
}

    One volatile reference yields a coherent pair. The tradeoff is allocation per publication. Multiple writers need a lock or AtomicReference update protocol if updates derive from current state; blind publication can otherwise lose a newer generation.

    Solution 4¶

    The base constructor registers a method reference that captures the not-yet-completed subclass object. A dispatch can invoke overridden process before Processor.validator is assigned, causing a null dereference and violating proper-construction assumptions.

    Construct first, then register through a factory:

    final class Processor {
    private final Validator validator;

    private Processor(Validator validator) {
        this.validator = java.util.Objects.requireNonNull(validator);
    }

    static Processor create(Registry registry, Validator validator) {
        Processor processor = new Processor(validator);
        registry.register(processor::process);
        return processor;
    }

    void process(Item item) {
        validator.validate(item);
    }
}

    The registry must safely publish the callback and define deregistration/lifecycle. Avoid calling overridable methods from constructors; composition makes the initialization boundary clearer.

    Chapter summary¶

    1. Start from shared mutable state and invariants.
    2. Treat atomicity, visibility, and ordering as distinct requirements.
    3. Order every conflicting access with a happens-before edge or an atomic API contract.
    4. Prefer immutable snapshots and safe publication for read-heavy state.
    5. Use volatile for independent state or immutable references, not arbitrary compound transactions.
    6. Prevent construction-time escape.
    7. Use double-checked locking only with volatile and only when simpler initialization is unsuitable.
