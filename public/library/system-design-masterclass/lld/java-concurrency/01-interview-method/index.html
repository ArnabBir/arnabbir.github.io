    The 45-Minute Concurrency Interview Method¶

    A concurrency design answer needs a proof, not merely a class diagram. Start with observable behavior and state. Derive invariants. Assign every shared mutable field to a synchronization policy. Only then choose APIs and optimize contention.

    Learning goals¶

    After this chapter, you should be able to:

    • structure a 45-minute concurrency LLD interview;
    • separate required behavior from implementation choices;
    • inventory state, ownership, invariants, and wait conditions;
    • define synchronization and cancellation policies;
    • identify linearization points for successful and failed operations;
    • evaluate safety, liveness, fairness, and performance separately;
    • propose deterministic unit tests and bounded stress tests.

    1. Use the interview clock deliberately¶

    Time Deliverable Questions to answer
    0-5 min Contract What operations exist? May they block? What are capacity and failure semantics?
    5-10 min State and invariants What changes? What must never be observed? Who owns each value?
    10-18 min Baseline API and model What are the public methods, results, and lifecycle states?
    18-28 min Synchronization proof What protects each field? Where does each operation linearize?
    28-34 min Liveness and cancellation Can threads deadlock, starve, wait forever, or ignore shutdown?
    34-40 min Tests Which schedules prove boundaries, and how will tests terminate?
    40-45 min Tradeoffs and summary Why this primitive? What changes under different load or semantics?

    Do not force every interview into exact minute boundaries. The purpose of the clock is to prevent ten minutes of class modeling followed by an unexamined synchronized keyword.

    2. Establish a concurrency contract¶

    Consider this prompt:

    Design an in-memory key pool. A caller acquires an unused key, uses it, and releases it. At most capacity keys may be checked out. Callers may wait up to a timeout.

    Ask questions whose answers change correctness or the API:

    • Are keys interchangeable, or does the caller receive a stable identity?
    • Is a duplicate release an error, a no-op, or undefined behavior?
    • Must acquisition be first-in-first-out?
    • Does timeout include time spent contending for internal locks?
    • How does shutdown affect current holders and waiters?
    • Must waiting acquisition react to thread interruption?
    • Can capacity change after construction?

    Turn answers into explicit operations and outcomes:

    interface KeyPool extends AutoCloseable {
    KeyLease acquire(Duration timeout)
            throws InterruptedException, TimeoutException;

    @Override
    void close();
}

    A lease can make ownership and one-time return explicit:

    interface KeyLease extends AutoCloseable {
    String key();

    @Override
    void close();
}

    The signature already encodes three decisions: acquisition can block, interruption remains visible, and release is attached to a lease that supports try-with-resources.

    3. Inventory state before choosing a primitive¶

    Write a state table on the whiteboard:

    State Mutable? Shared? Owner or guard Relevant invariant
    availableKeys yes yes pool lock no key appears twice
    checkedOut yes yes pool lock disjoint from available
    closed yes yes pool lock no acquire succeeds after close
    lease released yes potentially lease monitor complete return takes effect once
    configured capacity no yes final field, safely published positive and fixed

    Thread confinement means state is reachable by only one thread during the period it is mutable. Guarded state is shared mutable state accessed only while holding a designated lock. Ownership transfer moves exclusive responsibility from one thread or component to another using a publication mechanism.

    Do not say "the class is synchronized." Say, for example:

    The private lock guards availableKeys, checkedOut, and closed. Every read and write of those fields occurs while holding that lock. The lease monitor guards its release flag and the entire return, because clients may close the same lease concurrently.

    That statement is a synchronization policy. It is reviewable and testable.

    4. Write invariants as predicates¶

    For a fixed key universe allKeys:

    availableKeys intersection checkedOut == empty
availableKeys union checkedOut == allKeys
availableKeys.size + checkedOut.size == capacity
each lease returns at most one key
closed implies no future acquire succeeds

    Distinguish three types of condition:

    Type Meaning Example
    Representation invariant Internal state is valid whenever no operation is mid-transition. Available and checked-out sets are disjoint.
    Safety property An externally bad result never occurs. Two live leases never expose the same key.
    Liveness property Progress eventually occurs under stated assumptions. A waiter completes after a key is released, unless interrupted, timed out, or closed.

    Liveness needs assumptions. "Every waiter eventually succeeds" is false if leases are never returned or an unfair scheduler never runs a thread.

    5. Show the broken design and an interleaving¶

    final class BrokenCounterPool {
    private final int capacity;
    private int inUse;

    BrokenCounterPool(int capacity) {
        this.capacity = capacity;
    }

    boolean tryAcquire() {
        if (inUse == capacity) {
            return false;
        }
        inUse++;
        return true;
    }

    void release() {
        inUse--;
    }
}

    With capacity == 1, the check-then-act sequence is not atomic:

    Step Thread A Thread B inUse
    1 reads inUse == 0 0
    2 reads inUse == 0 0
    3 computes and writes 1 1
    4 computes and writes 1 1
    5 returns true returns true 1

    The field does not exceed capacity, yet two permits were issued. Internal state alone cannot reconstruct the externally visible violation. Also, an unmatched release() can make inUse negative.

    6. Build the smallest correct baseline¶

    The following sketch uses a fair ReentrantLock because the contract includes blocking acquisition and a timeout. Fairness is a policy choice, not a universal improvement.

    import java.time.Duration;
import java.util.ArrayDeque;
import java.util.HashSet;
import java.util.Set;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.TimeoutException;
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

final class LockedKeyPool implements KeyPool {
    private final ReentrantLock lock = new ReentrantLock(true);
    private final Condition keyReturnedOrClosed = lock.newCondition();
    private final ArrayDeque<String> available;
    private final Set<String> checkedOut = new HashSet<>();
    private boolean closed;

    LockedKeyPool(Set<String> keys) {
        if (keys.isEmpty()) {
            throw new IllegalArgumentException("keys must not be empty");
        }
        available = new ArrayDeque<>(Set.copyOf(keys));
    }

    @Override
    public KeyLease acquire(Duration timeout)
            throws InterruptedException, TimeoutException {
        if (timeout.isNegative()) {
            throw new IllegalArgumentException("timeout must not be negative");
        }

        long budgetNanos = saturatedNanos(timeout);
        long startedNanos = System.nanoTime();
        if (!lock.tryLock(budgetNanos, TimeUnit.NANOSECONDS)) {
            throw new TimeoutException("timed out acquiring pool lock");
        }
        try {
            while (available.isEmpty() && !closed) {
                long remaining = remainingNanos(startedNanos, budgetNanos);
                if (remaining == 0L) {
                    throw new TimeoutException("no key became available");
                }
                keyReturnedOrClosed.awaitNanos(remaining);
            }
            if (closed) {
                throw new IllegalStateException("pool is closed");
            }

            String key = available.removeFirst();
            boolean added = checkedOut.add(key);
            if (!added) {
                throw new IllegalStateException("pool invariant violated");
            }
            return new Lease(this, key);
        } finally {
            lock.unlock();
        }
    }

    private void release(String key) {
        lock.lock();
        try {
            if (!checkedOut.remove(key)) {
                throw new IllegalStateException("key is not checked out");
            }
            available.addLast(key);
            keyReturnedOrClosed.signal();
        } finally {
            lock.unlock();
        }
    }

    @Override
    public void close() {
        lock.lock();
        try {
            closed = true;
            keyReturnedOrClosed.signalAll();
        } finally {
            lock.unlock();
        }
    }

    private static long saturatedNanos(Duration timeout) {
        try {
            return timeout.toNanos();
        } catch (ArithmeticException tooLarge) {
            return Long.MAX_VALUE;
        }
    }

    private static long remainingNanos(long startedNanos, long budgetNanos) {
        long elapsed = System.nanoTime() - startedNanos;
        return elapsed <= 0L ? budgetNanos
                : elapsed >= budgetNanos ? 0L : budgetNanos - elapsed;
    }

    private static final class Lease implements KeyLease {
        private final LockedKeyPool pool;
        private final String key;
        private boolean released;

        private Lease(LockedKeyPool pool, String key) {
            this.pool = pool;
            this.key = key;
        }

        @Override
        public String key() {
            return key;
        }

        @Override
        public synchronized void close() {
            if (!released) {
                pool.release(key);
                released = true;
            }
        }
    }
}

    For interview code, call out the deliberate simplifications:

    • Extreme positive durations are clamped to Long.MAX_VALUE nanoseconds. The elapsed-time calculation avoids overflow from adding a budget to System.nanoTime().
    • Closing prevents new acquisition and wakes waiters, but existing leases remain valid and return normally.
    • Fair locking gives waiting threads a stronger admission preference under contention, but costs throughput and still does not promise perfect end-to-end FIFO completion.
    • Lock acquisition and every condition wait consume one end-to-end timeout. The condition wait uses a while loop because wakeups can be spurious and another thread can consume the key first.

    7. Mark linearization points¶

    An operation is linearizable when each completed call can be viewed as taking effect once, between invocation and response, while respecting real-time order.

    Operation outcome Linearization point
    Successful acquire Removal from available while holding lock
    Timed-out acquire Failed timed lock acquisition, or protected empty observation after the wait budget expires
    Acquire rejected by close Protected observation of closed == true
    First lease close Removal from checkedOut while holding lock
    Duplicate lease close Observation of released under the lease monitor, after the first return completed
    Pool close Protected write closed = true

    The lease monitor serializes complete returns, not merely election of a returning caller. An atomic flag set before pool.release would allow a second close to return while the key was still unavailable, violating a completed-close return contract. Lock order is lease monitor then pool lock; no pool path acquires a lease monitor. The lease's key() must not be used after close: returning a key cannot revoke a string already held by the caller.

    8. Explain memory ordering, not just mutual exclusion¶

    Unlocking a ReentrantLock happens-before a later successful lock of that same lock. Therefore, writes to available, checkedOut, and closed made before unlock become visible to the next holder.

    The lease monitor publishes released; the pool lock publishes pool state. Timeout bounds waiting, not a hard real-time response: after a wake the implementation may take an available key even if scheduling delayed reacquisition beyond the budget. A strict deadline-wins contract would check remaining time again before removal, while retaining a separate zero-budget immediate-attempt policy.

    An interviewer may ask whether signal() publishes the returned key. The complete answer is:

    1. The releaser changes the predicate while holding lock.
    2. It signals a waiter before unlocking.
    3. The waiter cannot return from awaitNanos and inspect the predicate until it reacquires the lock.
    4. The releaser's unlock happens-before that successful reacquisition.

    The signal is notification; the lock edge provides memory visibility.

    9. Analyze liveness and cancellation¶

    Ask these questions explicitly:

    • Deadlock: Does any path acquire multiple locks in inconsistent order?
    • Starvation: Can a runnable waiter be bypassed indefinitely?
    • Livelock: Can threads keep changing state without completing useful work?
    • Bounded waiting: Is there a timeout, cancellation path, or shutdown policy?
    • Notification: Does every transition that can make a wait predicate true signal appropriate waiters?
    • Interruption: Is interruption propagated, translated, restored, or intentionally consumed?

    The corrected pool uses timed interruptible tryLock and interruptible condition waits. If interrupted during either wait, acquire throws InterruptedException and issues no lease. Interruption after acquisition can race with success. close() uses signalAll() because every waiter must wake to observe terminal state. release() can use signal() because one returned key enables at most one acquisition.

    10. Test the contract¶

    Prefer orchestration primitives over sleeps. A safety test can align contenders at a start gate and record leases. The gates control when work is admitted and released; scheduling among contenders remains nondeterministic:

    import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertTrue;

import java.time.Duration;
import java.util.Set;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicInteger;
import org.junit.jupiter.api.Test;

class LockedKeyPoolTest {
    @Test
    void neverIssuesMoreThanCapacity() throws Exception {
        var pool = new LockedKeyPool(Set.of("k1", "k2"));
        var start = new CountDownLatch(1);
        var release = new CountDownLatch(1);
        var holdersReady = new CountDownLatch(2);
        var active = new AtomicInteger();
        var maximum = new AtomicInteger();
        var keys = ConcurrentHashMap.<String>newKeySet();

        var executor = Executors.newFixedThreadPool(12);
        var futures = new java.util.ArrayList<java.util.concurrent.Future<Void>>();
        try {
            for (int i = 0; i < 12; i++) {
                futures.add(executor.submit(() -> {
                    start.await();
                    try (var lease = pool.acquire(Duration.ofSeconds(2))) {
                        int now = active.incrementAndGet();
                        maximum.accumulateAndGet(now, Math::max);
                        if (!keys.add(lease.key())) {
                            throw new AssertionError("duplicate live key");
                        }
                        holdersReady.countDown();
                        release.await();
                        keys.remove(lease.key());
                        active.decrementAndGet();
                    }
                    return null;
                }));
            }
            start.countDown();
            assertTrue(holdersReady.await(1, TimeUnit.SECONDS));
            release.countDown();
            for (var future : futures) future.get(2, TimeUnit.SECONDS);
        } finally {
            start.countDown();
            release.countDown();
            for (var future : futures) future.cancel(true);
            executor.shutdownNow();
            pool.close();
            assertTrue(executor.awaitTermination(2, TimeUnit.SECONDS));
        }

        assertEquals(2, maximum.get());
    }
}

    The holders latch replaces an unbounded spin, every future is observed, and cleanup releases gates before cancelling workers. Timed waits bound the cooperative paths. Still use a child-JVM timeout for deliberately mutated non-interruptible deadlocks: an in-process test cannot forcibly terminate arbitrary Java code.

    Build a test matrix:

    Property Controlled setup Assertion
    Capacity safety Hold all keys, start one more acquire No additional lease before release
    Uniqueness Run many holders and track live keys No duplicate live key
    Timeout Exhaust pool, use a short budget TimeoutException, no state change
    Interruption Block a known waiter, interrupt it Prompt InterruptedException, no lease
    Shutdown Block several waiters, call close All terminate with closed outcome
    Idempotent lease close Concurrently close one lease One return only; capacity unchanged
    Reuse Release then reacquire Returned key becomes available

    Stress tests increase schedule coverage by repeating operations with randomized yields or durations. They do not replace the invariant and happens-before proof. Tools such as jcstress are useful when testing Java Memory Model outcomes; ordinary unit tests are poor at proving an outcome impossible.

    11. Compare design options¶

    Design Strength Cost Choose when
    One intrinsic lock Small proof surface No timed lock acquisition or multiple conditions State and waiting rules are simple
    ReentrantLock plus Condition Interruptible/timed lock, explicit conditions More code; unlock discipline required Wait predicates or lock features matter
    Semaphore plus key queue Capacity primitive is explicit Must keep permit count and queue consistent Permits are independent or composition is carefully designed
    BlockingQueue<String> take, timed poll, and return map naturally Shutdown and duplicate returns need extra policy Keys themselves are the bounded resources
    Lock-free structure Potential progress under narrow contention Hard proof, retries, allocation, ABA concerns Measurement shows blocking is the bottleneck and algorithm is well understood

    For this prompt, a bounded BlockingQueue may be the simplest production answer if duplicate return and shutdown semantics are wrapped correctly. In an interview, presenting the lock-based baseline first makes invariants and linearization visible; then comparing the queue demonstrates API knowledge without outsourcing the proof.

    Interview traps¶

    • Drawing classes before deciding whether operations block or fail.
    • Naming a lock without listing every field it guards.
    • Protecting writes but exposing unsynchronized getters or iterators.
    • Defining a linearization point only for successful operations.
    • Equating fairness with guaranteed FIFO completion.
    • Calling signal outside the lock or waiting with if rather than while.
    • Ignoring timeout accounting across lock acquisition and condition waiting.
    • Testing with Thread.sleep and assuming the desired state has been reached.
    • Forgetting that task exceptions submitted to an executor are often captured in Future.
    • Discussing throughput while cancellation and shutdown remain undefined.

    Review questions¶

    1. What belongs in a synchronization policy?
    2. Why is available.size() <= capacity insufficient as the only invariant?
    3. Where does a timed-out operation linearize?
    4. Why does a condition wait always recheck its predicate?
    5. Which edge publishes a released key to an awakened waiter?
    6. When is signal() preferable to signalAll(), and what must be true?
    7. How can a test fail inside a worker without failing the test method?
    8. Why might a fair lock reduce throughput?

    Hands-on exercises¶

    Exercise 1: Repair the synchronization policy¶

    A cache protects entries with synchronized put, but get and size are unsynchronized. State the defect and propose a complete policy.

    Exercise 2: Find the linearization points¶

    For a bounded queue, identify plausible linearization points for successful offer, failed offer, successful poll, and timed-out poll.

    Exercise 3: Design a cancellation test¶

    Describe a deterministic test proving that a blocked acquisition reacts to interruption without consuming a key.

    Solutions

    Solution 1¶

    The lock does not protect a field; a protocol does. Unsynchronized reads can race with writes, observe stale state, and interact unsafely with a non-concurrent collection. Guard every access to entries, including compound iteration and size reads, with the same private lock. Alternatively, replace the representation with a suitable concurrent map, then separately prove any multi-call invariant because thread-safe map methods do not automatically compose.

    Solution 2¶

    • Successful offer: insertion into the queue's protected representation.
    • Failed immediate offer: protected observation that capacity is exhausted.
    • Successful poll: removal from the protected representation.
    • Timed-out poll: final protected observation that the queue is empty after the remaining wait budget reaches zero.

    Exact points depend on the implementation contract, but each must occur between invocation and response and produce an order consistent with real time.

    Solution 3¶

    1. Create a capacity-one pool and acquire its only key.
    2. Start a waiter and use a latch immediately before it calls blocking acquire.
    3. Establish that the task has started; where possible, add an injectable test hook or inspect a documented waiting state rather than sleeping.
    4. Interrupt the waiter thread.
    5. Require the future to complete within a short outer deadline with InterruptedException as its cause.
    6. Release the original lease and acquire once successfully.
    7. Assert no second key or duplicate lease exists.

    The outer deadline protects the suite from a broken implementation. Cleanup closes the first lease and pool in finally.
