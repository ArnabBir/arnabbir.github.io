    09. Liveness, Debugging, and Concurrency Testing¶

    Safety asks whether something bad happens. Liveness asks whether something good eventually happens. A design can preserve every data invariant and still fail because no thread can make progress. Production diagnosis and deterministic tests are therefore part of low-level design, not afterthoughts.

    Goals¶

    After this chapter, you should be able to:

    • distinguish deadlock, livelock, starvation, and priority inversion;
    • repair multi-lock code with global ordering or timed rollback;
    • identify lock cycles and blocked owners from thread dumps;
    • use jcmd and Java Flight Recorder for live investigation;
    • reproduce races with deterministic gates rather than sleeps;
    • design stress, invariant, history, shutdown, and leak tests;
    • explain what JCStress proves and does not prove; and
    • state linearization points and completion semantics in an interview.

    1. Progress properties¶

    Failure What happens Typical signal
    Deadlock Participants wait in a cycle; none can proceed Stable blocked threads and a wait-for cycle
    Livelock Participants keep changing state but make no useful progress CPU/activity without completed operations
    Starvation One participant is repeatedly denied service Overall throughput exists, one request waits excessively
    Priority inversion High-priority work waits for lower-priority work holding a resource Priority and latency do not align

    Java thread priorities are scheduler hints and are platform-dependent. Do not build correctness around them. Priority inversion also occurs at the application level: a latency-critical task can wait behind bulk work in one FIFO executor even without OS thread priorities.

    Safety, liveness, and bounded liveness¶

    • Safety: an account balance never reflects a half-transfer.
    • Liveness: an admitted transfer eventually reaches a terminal result.
    • Bounded liveness: it reaches a terminal result before its deadline.

    Interviews should make the bound explicit. "Eventually" is not useful to a caller with a 200 ms budget.

    2. Deadlock as a wait-for cycle¶

    Four conditions commonly characterize lock deadlock:

    1. mutual exclusion;
    2. hold and wait;
    3. no forced lock preemption; and
    4. circular wait.

    Breaking any one prevents that deadlock class. Global lock ordering breaks circular wait. tryLock with complete rollback breaks indefinite hold-and-wait. Removing nested acquisition can eliminate the structure entirely.

    Broken transfer¶

    public static void transfer(Account from, Account to, long cents) {
    synchronized (from) {
        synchronized (to) {
            from.debit(cents);
            to.credit(cents);
        }
    }
}

    Two threads executing transfer(a, b, 10) and transfer(b, a, 20) can each hold one monitor and wait forever for the other.

    State and invariants¶

    For an in-memory transfer:

    • account IDs are immutable and unique;
    • balances do not become negative;
    • the sum of the two balances is unchanged by a successful transfer;
    • either both balance changes become visible as one operation or neither does; and
    • every acquired lock is released on every exit path.

    The linearization point is the mutation performed while both account locks are held. If readers acquire the same locks, no reader can observe the intermediate debit-only state.

    Corrected: global lock order¶

    public final class Transfers {
    private Transfers() {}

    public static void transfer(Account from, Account to, long cents) {
        Objects.requireNonNull(from);
        Objects.requireNonNull(to);
        if (cents <= 0) {
            throw new IllegalArgumentException("cents must be positive");
        }
        if (from == to) {
            return;
        }

        Account first = from.id() < to.id() ? from : to;
        Account second = first == from ? to : from;
        synchronized (first) {
            synchronized (second) {
                if (from.balance() < cents) {
                    throw new InsufficientFundsException(from.id());
                }
                long credited = Math.addExact(to.balance(), cents);
                from.setBalance(from.balance() - cents);
                to.setBalance(credited);
            }
        }
    }
}

    Identity hash codes can collide and mutable business attributes cannot define order. Prefer a unique immutable key. If keys can be equal for distinct objects, add a tie lock or a unique sequence.

    Corrected alternative: tryLock with rollback¶

    public static boolean transferBefore(
        LockingAccount from,
        LockingAccount to,
        long cents,
        Duration timeout) throws InterruptedException {
    if (cents <= 0) throw new IllegalArgumentException("positive cents required");
    if (timeout.isNegative()) {
        throw new IllegalArgumentException("negative timeout");
    }
    long budgetNanos = saturatedNanos(timeout);
    long startedNanos = System.nanoTime();
    boolean fromLocked = false;
    boolean toLocked = false;
    try {
        fromLocked = from.lock().tryLock(
                remainingNanos(startedNanos, budgetNanos),
                TimeUnit.NANOSECONDS);
        if (!fromLocked) {
            return false;
        }

        long remaining = remainingNanos(startedNanos, budgetNanos);
        toLocked = to.lock().tryLock(remaining, TimeUnit.NANOSECONDS);
        if (!toLocked) {
            return false;
        }

        if (from.balance() < cents) {
            throw new InsufficientFundsException(from.id());
        }
        if (from == to) return true;
        long credited = Math.addExact(to.balance(), cents);
        from.setBalance(from.balance() - cents);
        to.setBalance(credited);
        return true;
    } finally {
        if (toLocked) {
            to.lock().unlock();
        }
        if (fromLocked) {
            from.lock().unlock();
        }
    }
}

private static long saturatedNanos(Duration timeout) {
    try {
        return timeout.toNanos();
    } catch (ArithmeticException tooLarge) {
        return Long.MAX_VALUE;
    }
}

private static long remainingNanos(long startedNanos, long budgetNanos) {
    long elapsed = System.nanoTime() - startedNanos;
    return elapsed <= 0L ? budgetNanos
            : elapsed >= budgetNanos ? 0L : budgetNanos - elapsed;
}

    Both acquisitions use one elapsed-time budget, not a fresh timeout per lock. This avoids overflow from constructing an absolute nanosecond deadline. Reverse-order release is conventional and important when lock relationships evolve. Returning false means no transfer occurred.

    If callers immediately retry in lockstep, deadlock can become livelock. Add bounded randomized backoff outside all locks, impose a retry limit, or prefer global ordering.

    3. Starvation and priority inversion¶

    Starvation can result from:

    • an unfair lock under sustained contention;
    • a hot producer filling a shared queue;
    • readers continuously delaying a writer;
    • tasks blocking all workers while waiting for tasks queued behind them; or
    • one tenant monopolizing a shared pool.

    Fair ReentrantLock and Semaphore variants reduce barging but generally reduce throughput. Fairness is not a real-time guarantee. Better designs often isolate workloads, use per-tenant admission limits, avoid nested executor waits, and monitor queue age by class.

    Broken: thread-pool starvation deadlock¶

    ExecutorService one = Executors.newSingleThreadExecutor();
Future<String> outer = one.submit(() -> one.submit(this::load).get());

    The only worker waits for an inner task that only that worker can run.

    Corrected: compose or execute directly¶

    Future<String> result = one.submit(this::load);

    For asynchronous APIs, return and compose the inner stage rather than blocking a worker on work submitted to the same constrained executor.

    Priority inversion should be handled structurally: keep critical sections short, avoid performing I/O under locks, separate latency classes, and apply admission control. Raising Java thread priority is not a portable repair.

    4. Failure, cancellation, and lock hygiene¶

    Locks do not release automatically when a method throws unless the language construct guarantees it. Monitors exit automatically; explicit locks require finally.

    lock.lockInterruptibly();
try {
    updateState();
} finally {
    lock.unlock();
}

    Prefer lockInterruptibly when cancellation while waiting is meaningful. A thread blocked on monitor entry cannot be interrupted out of that acquisition. Never call unknown code, remote I/O, listener callbacks, or blocking queue operations while holding a lock unless the contract and bound are explicit.

    Shutdown can expose liveness defects. A task that ignores interruption, waits for a callback that shutdown has disabled, or holds a lock needed by the shutdown thread can prevent termination. Design cancellation paths alongside normal paths.

    5. Production debugging workflow¶

    Step 1: preserve evidence¶

    Before restarting, capture at least two or three thread dumps several seconds apart. A single dump shows state; repeated dumps show whether stacks and lock ownership are stable. Also preserve process metrics, request latency, queue depth, CPU, GC, and deployment events.

    Step 2: capture thread information with jcmd¶

    jcmd <pid> Thread.print -l > thread-dump-1.txt
jcmd <pid> VM.command_line
jcmd <pid> VM.flags
jcmd <pid> GC.heap_info

    Run another Thread.print -l after a short diagnostic interval. -l includes ownable synchronizer information. jcmd <pid> help shows commands supported by that exact JDK.

    Look for:

    • BLOCKED threads waiting to enter monitors;
    • WAITING or TIMED_WAITING threads parked on locks, futures, queues, or conditions;
    • locked objects and waiting to lock object IDs;
    • the thread that owns each required lock;
    • repeated stacks across dumps;
    • executor workers waiting on child futures; and
    • a deadlock report emitted by the JVM at the end of a thread dump.

    Thread state alone is not guilt. Healthy idle workers are often WAITING. Build the ownership chain.

    Step 3: draw the wait-for graph¶

    thread transfer-a -> waits for Account B -> held by transfer-b
thread transfer-b -> waits for Account A -> held by transfer-a

    A cycle is evidence of deadlock. A long chain without a cycle may be contention, slow I/O under a lock, or starvation.

    Step 4: record JFR¶

    Use settings, duration, and filenames approved for the environment:

    jcmd <pid> JFR.start name=liveness settings=profile duration=120s \
  filename=/safe/path/liveness.jfr
jcmd <pid> JFR.check

    Inspect Java monitor blocked events, thread park events, socket/file I/O, CPU samples, allocation pressure, and virtual-thread events available in the deployed JDK. JFR event names and virtual-thread diagnostics vary by JDK release. Verify with the exact runtime and Mission Control version.

    Continuous JFR with conservative settings often provides better pre-incident context than starting a recording after saturation. Protect recordings because they may contain class, thread, path, or application data.

    Step 5: repair the design¶

    Do not stop at changing a timeout. Determine whether the root cause is lock order, I/O under lock, nested executor dependence, missing admission control, an unbounded retry loop, or cancellation that cannot reach the blocked operation. Add a regression test for the progress property.

    6. Making races reproducible¶

    Thread.sleep does not establish a happens-before relationship and does not prove another thread reached a line. It creates slow, flaky tests.

    Broken race test¶

    executor.submit(counter::increment);
Thread.sleep(50);
assertEquals(1, counter.get());

    Corrected completion test¶

    Future<?> completion = executor.submit(counter::increment);
completion.get(1, TimeUnit.SECONDS);
assertEquals(1, counter.get());

    To expose a particular interleaving, add gates to a test seam.

    public final class TransferProbe {
    private final CountDownLatch firstLockHeld = new CountDownLatch(2);
    private final CountDownLatch continueToSecond = new CountDownLatch(1);

    public void afterFirstLock() throws InterruptedException {
        firstLockHeld.countDown();
        continueToSecond.await();
    }

    public boolean bothAtBoundary(Duration timeout) throws InterruptedException {
        return firstLockHeld.await(timeout.toNanos(), TimeUnit.NANOSECONDS);
    }

    public void release() {
        continueToSecond.countDown();
    }
}

    The gate belongs in injected test instrumentation, not in production synchronization. A test timeout is still needed so a defect fails the suite instead of hanging it.

    Useful deterministic primitives¶

    • CountDownLatch: one-shot event or start gate;
    • CyclicBarrier: repeated rendezvous among a fixed party count;
    • Phaser: phased coordination with dynamic parties;
    • Semaphore: control when an operation may enter;
    • Future.get(timeout): observe completion with a test bound; and
    • controllable fakes: hold dependency completion until the test releases it.

    7. A deterministic deadlock-repair test¶

    The corrected transfer should complete opposite-direction operations and preserve total value.

    import static org.junit.jupiter.api.Assertions.*;

import java.time.Duration;
import java.util.concurrent.*;
import org.junit.jupiter.api.Test;

final class TransfersTest {
    @Test
    void oppositeTransfersCompleteAndPreserveMoney() throws Exception {
        Account left = new Account(1, 1_000);
        Account right = new Account(2, 1_000);
        CyclicBarrier start = new CyclicBarrier(3);

        try (ExecutorService executor = Executors.newFixedThreadPool(2)) {
            Future<?> one = executor.submit(() -> {
                await(start);
                Transfers.transfer(left, right, 100);
            });
            Future<?> two = executor.submit(() -> {
                await(start);
                Transfers.transfer(right, left, 200);
            });

            start.await(1, TimeUnit.SECONDS);
            assertTimeoutPreemptively(Duration.ofSeconds(1), () -> {
                one.get(900, TimeUnit.MILLISECONDS);
                two.get(900, TimeUnit.MILLISECONDS);
            });
        }

        assertEquals(2_000, left.balance() + right.balance());
        assertEquals(1_100, left.balance());
        assertEquals(900, right.balance());
    }

    private static void await(CyclicBarrier barrier) {
        try {
            barrier.await();
        } catch (InterruptedException interrupted) {
            Thread.currentThread().interrupt();
            throw new CancellationException("test worker interrupted");
        } catch (BrokenBarrierException broken) {
            throw new AssertionError(broken);
        }
    }
}

    assertTimeoutPreemptively runs its body on a different thread and interrupts it on timeout. Avoid it around code that depends on test-thread ThreadLocal state or performs non-rollbackable external effects. Plain timed Future.get is often enough.

    This test demonstrates completion for one controlled start, not mathematical deadlock freedom. The argument for freedom comes from the global order; repeated and stress tests defend the implementation.

    If the transfer regresses to monitor deadlock, executor close() can hang after the timed assertion. Interruption cannot break monitor acquisition. Run deliberately deadlocking variants in a child JVM with an external timeout; neither Future.get(timeout) nor JUnit preemptive interruption can forcibly stop those workers. Account setters in these sketches must be non-throwing after validation, and pair snapshots must hold both account locks.

    8. Stress testing¶

    A stress test repeats many operations across many threads and checks invariants after coordinated completion. It increases the probability of harmful interleavings but cannot prove their absence.

    @Test
void concurrentTransfersPreserveTotalAndNonNegativeBalances() throws Exception {
    int accountCount = 16;
    Account[] accounts = IntStream.range(0, accountCount)
            .mapToObj(id -> new Account(id, 10_000))
            .toArray(Account[]::new);
    long expectedTotal = 160_000;
    int workers = 8;
    int operationsPerWorker = 20_000;
    CountDownLatch start = new CountDownLatch(1);

    try (ExecutorService executor = Executors.newFixedThreadPool(workers)) {
        List<? extends Future<?>> futures = IntStream.range(0, workers)
                .mapToObj(worker -> executor.submit(() -> {
                    SplittableRandom random = new SplittableRandom(worker);
                    start.await();
                    for (int i = 0; i < operationsPerWorker; i++) {
                        Account from = accounts[random.nextInt(accountCount)];
                        Account to = accounts[random.nextInt(accountCount)];
                        if (from != to) {
                            try {
                                Transfers.transfer(from, to, 1);
                            } catch (InsufficientFundsException allowed) {
                                // Rejection preserves state.
                            }
                        }
                    }
                    return null;
                }))
                .toList();
        start.countDown();
        for (Future<?> future : futures) {
            future.get(10, TimeUnit.SECONDS);
        }
    }

    assertEquals(expectedTotal,
            Arrays.stream(accounts).mapToLong(Account::balance).sum());
    assertTrue(Arrays.stream(accounts).allMatch(account -> account.balance() >= 0));
}

    Use several deterministic seeds in normal CI and broader randomized seeds in a dedicated stress job. Record the seed on failure. Avoid adding logging in hot race windows because it changes scheduling.

    9. JCStress overview¶

    JCStress is the OpenJDK concurrency stress harness for testing outcomes under the Java Memory Model. It repeatedly runs small actor methods under varied generated conditions and classifies observed outcomes.

    A conceptual lost-update test is:

    @JCStressTest
@Outcome(id = "2", expect = Expect.ACCEPTABLE, desc = "Both increments visible")
@Outcome(id = "1", expect = Expect.FORBIDDEN, desc = "Lost update")
@State
public class AtomicIncrementStress {
    private final AtomicInteger value = new AtomicInteger();

    @Actor
    public void actor1() {
        value.incrementAndGet();
    }

    @Actor
    public void actor2() {
        value.incrementAndGet();
    }

    @Arbiter
    public void observe(I_Result result) {
        result.r1 = value.get();
    }
}

    Use the JCStress Maven archetype/plugin and version compatible with the target JDK; annotations and result-holder imports come from the harness. Do not run a JCStress test as an ordinary JUnit test.

    JCStress is strong for small memory-model litmus tests: publication, reordering, atomicity, and allowed outcomes. It does not prove a large service linearizable, validate remote side effects, or replace lifecycle and load tests.

    10. Linearizability and invariant testing¶

    An invariant constrains valid states. Linearizability additionally requires each concurrent operation to appear atomic at one point between invocation and response, while respecting real-time order.

    For a bounded counter:

    • invariant: 0 <= value <= limit;
    • successful increment linearizes at the winning compare-and-set;
    • rejected increment linearizes at the read/CAS attempt that establishes the limit;
    • history records invocation, response, arguments, result, and operation ID.

    History record¶

    record Event(long operationId, String phase, String operation,
             int argument, Object result, long sequence) {}

    Use an AtomicLong sequence only to capture recorder order; do not mistake it for the data structure's linearization order. A checker searches for a legal sequential history that respects observed results and the real-time precedence of non-overlapping calls.

    For small histories, exhaustive backtracking is practical:

    1. collect invocation and response events; for this simple checker, require all invocations to have completed;
    2. derive happens-before constraints from response-before-invocation;
    3. choose an operation whose predecessors are already chosen;
    4. apply it to a simple reference model;
    5. reject branches whose model result differs; and
    6. succeed if one complete legal order exists.

    If a captured history has pending operations, do not simply discard them: a pending write may explain a completed read. A full checker considers legal completions of some pending calls and removal of the others under the linearizability definition. Keep histories small because the search can grow factorially. Use model-based random command generation and shrink failing histories. Invariant checks are cheaper and scale farther, but may miss a non-linearizable history whose final state is valid.

    11. Shutdown and thread-leak tests¶

    Lifecycle tests need positive evidence that admission stops, queued work is handled by policy, running work sees cancellation, and owned threads terminate.

    @Test
void closeInterruptsBlockedWorkerAndLeavesNoOwnedThread() throws Exception {
    String prefix = "shipment-worker-test-";
    CountDownLatch started = new CountDownLatch(1);
    CountDownLatch interrupted = new CountDownLatch(1);
    ExecutorService executor = Executors.newSingleThreadExecutor(
            Thread.ofPlatform().name(prefix, 0).factory());

    executor.submit(() -> {
        started.countDown();
        try {
            new CountDownLatch(1).await();
        } catch (InterruptedException expected) {
            interrupted.countDown();
            Thread.currentThread().interrupt();
        }
    });

    assertTrue(started.await(1, TimeUnit.SECONDS));
    executor.shutdown();
    if (!executor.awaitTermination(50, TimeUnit.MILLISECONDS)) {
        executor.shutdownNow();
    }
    assertTrue(interrupted.await(1, TimeUnit.SECONDS));
    assertTrue(executor.awaitTermination(1, TimeUnit.SECONDS));
    assertTrue(Thread.getAllStackTraces().keySet().stream()
            .noneMatch(thread -> thread.isAlive() && thread.getName().startsWith(prefix)));
}

    The 50 ms grace period is policy input, not a claim that work should finish in 50 ms. The assertions depend on latches and termination. Use unique prefixes to avoid confusing unrelated threads. For virtual threads, thread enumeration APIs and observability differ; assert executor termination and component-owned task completion rather than relying only on global enumeration.

    Also test:

    • rejection after shutdown begins;
    • repeated close if idempotence is promised;
    • shutdown while the queue is full;
    • task that restores interrupt status;
    • task that ignores interruption, to verify bounded close behavior;
    • scheduled-task cancellation; and
    • resource closure only after workers stop using the resource.

    12. A reusable race harness¶

    This harness starts actors together, stores actor failures in futures, and applies a completion bound. It propagates the first failure encountered while joining; it does not aggregate every concurrent failure.

    public final class ConcurrentHarness {
    private ConcurrentHarness() {}

    public static void run(List<? extends Runnable> actors, Duration timeout)
            throws Exception {
        if (timeout.isNegative()) {
            throw new IllegalArgumentException("negative timeout");
        }
        if (actors.isEmpty()) return;
        long budgetNanos = saturatedNanos(timeout);
        long startedNanos = System.nanoTime();
        CountDownLatch ready = new CountDownLatch(actors.size());
        CountDownLatch start = new CountDownLatch(1);
        ExecutorService executor = Executors.newFixedThreadPool(actors.size(),
                Thread.ofPlatform().daemon().name("race-actor-", 0).factory());
        try {
            List<? extends Future<?>> futures = actors.stream()
                    .map(actor -> executor.submit(() -> {
                        ready.countDown();
                        start.await();
                        actor.run();
                        return null;
                    }))
                    .toList();

            if (!ready.await(remainingNanos(startedNanos, budgetNanos),
                    TimeUnit.NANOSECONDS)) {
                throw new TimeoutException("actors did not become ready");
            }
            start.countDown();
            for (Future<?> future : futures) {
                long remaining = remainingNanos(startedNanos, budgetNanos);
                future.get(remaining, TimeUnit.NANOSECONDS);
            }
        } finally {
            start.countDown();
            executor.shutdownNow();
            if (!executor.awaitTermination(
                    budgetNanos,
                    TimeUnit.NANOSECONDS)) {
                throw new AssertionError("test actors leaked");
            }
        }
    }

    private static long saturatedNanos(Duration timeout) {
        try {
            return timeout.toNanos();
        } catch (ArithmeticException tooLarge) {
            return Long.MAX_VALUE;
        }
    }

    private static long remainingNanos(long startedNanos, long budgetNanos) {
        long elapsed = System.nanoTime() - startedNanos;
        return elapsed <= 0L ? budgetNanos
                : elapsed >= budgetNanos ? 0L : budgetNanos - elapsed;
    }
}

    One overflow-safe elapsed-time budget bounds readiness and every get rather than granting each phase a fresh timeout. Cleanup gets a separate bounded termination allowance so an operation timeout does not skip leak detection. Future.get surfaces actor exceptions. This harness coordinates starts; it does not force an exact operation-level interleaving. Use injected gates for that.

    Daemon actors prevent a leaked test worker from keeping a child JVM alive; they do not make continuing in the same JVM safe after a leak. Run hostile actors in an isolated process and terminate it on timeout. Cleanup failure may mask the original actor exception in this compact harness; retain both as suppressed causes in a diagnostic runner.

    13. Tradeoffs¶

    Technique Strength Limitation
    Global lock order Simple proof against order-cycle deadlock Every code path must follow the same stable order
    Timed tryLock Bounded waiting and cancellation opportunity Rollback and retry can cause livelock
    Fair lock Reduces barging Lower throughput; no strict timing guarantee
    Thread dump Low-cost lock and stack snapshot Transient races may disappear between samples
    JFR Time-correlated production evidence Requires event knowledge, storage, and privacy controls
    Deterministic gate Reproduces a chosen boundary Instrumentation can perturb behavior
    Stress test Explores many schedules Passing does not prove correctness
    JCStress Tests JMM outcomes rigorously Best for small state machines, not whole services
    Linearizability checker Validates observable histories Search cost and modeling complexity

    14. Exercises¶

    Exercise 1: repair two-lock update¶

    Two objects have unique immutable string IDs. Write a helper that acquires their ReentrantLock values in one global order and runs an update. It must handle the same object.

    Solution 
    static void withBoth(Node left, Node right, Runnable update) {
    Objects.requireNonNull(left);
    Objects.requireNonNull(right);
    Objects.requireNonNull(update);
    if (left == right) {
        left.lock().lock();
        try {
            update.run();
        } finally {
            left.lock().unlock();
        }
        return;
    }

    Node first = left.id().compareTo(right.id()) < 0 ? left : right;
    Node second = first == left ? right : left;
    first.lock().lock();
    try {
        second.lock().lock();
        try {
            update.run();
        } finally {
            second.lock().unlock();
        }
    } finally {
        first.lock().unlock();
    }
}

    Unique IDs make the order total. If IDs were not unique, equal IDs for distinct nodes would need a tie-break mechanism.

    Exercise 2: test a lost update without sleep¶

    Create two actors that start together, each increments a thread-safe counter 10,000 times, and assert completion and final value.

    Solution 
    @Test
void atomicCounterDoesNotLoseUpdates() throws Exception {
    AtomicInteger counter = new AtomicInteger();
    int increments = 10_000;
    Runnable actor = () -> {
        for (int i = 0; i < increments; i++) {
            counter.incrementAndGet();
        }
    };

    ConcurrentHarness.run(List.of(actor, actor), Duration.ofSeconds(2));
    assertEquals(2 * increments, counter.get());
}

    The harness supplies simultaneous release, exception propagation, and bounded completion. Repeating this against a plain int may reveal a race but cannot prove it on every run.

    Exercise 3: diagnose a dump¶

    Thread A owns lock X and waits for Y. Thread B owns Y and waits for X. Thread C is parked on an empty executor queue. Which thread is part of the deadlock, and what evidence should be captured before restart?

    Solution

    A and B form the lock-ownership cycle and are deadlocked. C is likely an idle worker and is not implicated merely because it is WAITING. Capture multiple jcmd <pid> Thread.print -l dumps, relevant metrics and queue depths, runtime flags and command line, and a bounded JFR recording if operationally safe. Preserve object IDs, owner names, and full stack frames that establish both edges of the cycle.

    Exercise 4: state a completion contract¶

    Define terminal outcomes for a cancellable queued command.

    Solution

    An admitted command reaches exactly one caller-visible terminal outcome: success, application failure, or cancellation. Cancellation before execution prevents its body from starting when cancellation wins. Cancellation after start requests cooperative termination and may race with normal completion. A timeout while waiting is not itself proof of cancellation. Rejection occurs before admission and is not a command completion. External side effects require idempotency because local cancellation cannot roll them back automatically.

    15. Interview traps and questions¶

    Traps¶

    • Calling every long wait a deadlock without finding a cycle.
    • Treating WAITING as inherently unhealthy.
    • Repairing deadlock with retries that create livelock.
    • Ordering locks by a mutable field or a non-unique hash.
    • Using a fresh timeout for every acquisition or future wait.
    • Writing sleep-based assertions.
    • Checking only final state when operation histories may be non-linearizable.
    • Assuming one successful stress run proves thread safety.
    • Ignoring exceptions thrown inside worker futures.
    • Testing shutdown without asserting owned threads or tasks terminate.
    • Relying on thread priorities for correctness.

    Questions to practice¶

    1. Draw the wait-for graph for a three-lock cycle and break it by design.
    2. When is tryLock preferable to global ordering, and how do you avoid livelock?
    3. How do starvation and priority inversion differ from deadlock?
    4. What would you inspect in three consecutive thread dumps?
    5. Which JFR events would help distinguish CPU spin, monitor contention, and blocked I/O?
    6. How do deterministic gates change the probability of reproducing a race?
    7. State a linearization point for a CAS counter, a lock-based transfer, and a rejected queue offer.
    8. What can JCStress establish that a JUnit loop usually cannot?
    9. How do you prove shutdown is bounded when a task ignores interruption?

    Summary¶

    • Liveness failures differ: find cycles, activity, service denial, or priority dependencies.
    • Global lock ordering provides a clean deadlock-freedom argument when the order is total and universal.
    • Timed acquisition needs one deadline, complete rollback, and bounded retry.
    • Diagnose from repeated thread dumps, ownership chains, metrics, and JFR evidence.
    • Coordinate tests with latches, barriers, futures, and controllable fakes, not sleeps.
    • Stress and invariant tests find bugs but do not prove linearizability.
    • JCStress targets small Java Memory Model outcomes; history checking targets observable atomic behavior.
    • Shutdown tests must verify rejection, cancellation policy, termination, and resource order.
