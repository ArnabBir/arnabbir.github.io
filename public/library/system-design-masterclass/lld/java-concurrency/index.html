    Java Concurrency for LLD Interviews¶

    Java concurrency questions are small system-design interviews. The objects may fit on a whiteboard, but the design still needs explicit state, invariants, ownership, failure behavior, and tests. This track develops those skills from thread mechanics through the Java Memory Model, synchronization, executors, asynchronous composition, and production diagnostics.

    The code targets Java 21. Unless a chapter explicitly discusses virtual threads, examples use platform threads so scheduling and shared-memory hazards remain visible.

    Core examples target Java 21; several test fixtures intentionally use virtual threads for independently blocked actors. Complete class blocks, method sketches requiring surrounding types/imports, and intentionally broken examples are different artifacts. The targeted review runner extracts an explicit allowlist, adds imports and explicitly declared fake dependency methods for lifecycle sketches, compiles with --release 21, and runs bounded child JVMs. Run it with JAVA_HOME set to JDK 21 or newer. JDK 24 execution does not validate Java 21 monitor pinning or Java 21 preview APIs; JDK 17 cannot compile the full baseline. JUnit and JCStress snippets require their own harness/dependencies and are not all exercised by this runner.

    Learning goals¶

    By the end of the track, you should be able to:

    • turn an underspecified concurrency prompt into state, invariants, and a synchronization policy;
    • distinguish atomicity, visibility, ordering, progress, and cancellation requirements;
    • explain correctness with explicit interleavings and happens-before edges;
    • select locks, concurrent collections, atomics, executors, or immutability for stated reasons;
    • identify a design's linearization points and liveness risks;
    • write deterministic tests for safety properties and useful stress tests for races;
    • discuss Java 21 platform threads and virtual threads without mixing their cost models.

    Prerequisite map¶

    You should be comfortable with Java syntax, classes, interfaces, exceptions, generics, and collections. The track introduces concurrency concepts from first principles, but it assumes you can read ordinary Java 21 code.

    flowchart LR
    J[Core Java] --> M[Interview method]
    J --> T[Threads and tasks]
    M --> MM[Thread safety and JMM]
    T --> MM
    MM --> L[Locks and conditions]

    Before Chapter 3, make sure these terms are precise:

    Term Working definition
    State Data whose value can affect later behavior or results.
    Shared Reachable by more than one thread during overlapping lifetimes.
    Mutable Able to change after construction.
    Invariant A predicate that must hold at every externally observable boundary.
    Synchronization policy The rule that says which mechanism protects each piece of state and when callers must use it.
    Linearization point The conceptual instant at which a concurrent operation takes effect.
    Safety Nothing bad happens, such as a duplicate allocation or corrupted value.
    Liveness Something good eventually happens, such as a blocked caller making progress.

    Roadmap¶

    Chapter Core question Interview deliverable
    1. The 45-minute method How do I structure the discussion? Contract, state model, invariants, policy, linearization points, liveness, tests
    2. Threads, tasks, and lifecycle What actually executes, blocks, and stops? Correct lifecycle and cancellation reasoning
    3. Thread safety and the Java Memory Model When may another thread observe a write? Data-race analysis and happens-before proof
    4. Synchronization, locks, and conditions How should compound state transitions be protected? Locking protocol and wait-condition design
    5. Coordination primitives How do threads rendezvous, hand off permits, and advance phases? Primitive selection, interruption policy, and group-completion proof
    6. Atomics and concurrent collections When is one atomic transition or concurrent collection enough? CAS loop, per-operation atomicity boundary, and collection tradeoff
    7. Executors, capacity, and backpressure How is work admitted, bounded, rejected, and stopped? Executor ownership, capacity calculation, overload policy, and shutdown protocol
    8. Async composition, parallelism, and virtual threads Which execution model fits waiting, CPU work, and fan-out? Completion/failure graph, end-to-end deadline, and resource-bound design
    9. Liveness, debugging, and concurrency testing How do I prove progress and investigate failures? Deadlock analysis, diagnostic workflow, and deterministic race tests
    10. Concurrency patterns Which reusable ownership and coordination shape fits the state? Pattern choice with invariants, failure modes, and lifecycle semantics
    11. Classic problems: solved workbook Can I apply the method to canonical synchronization exercises? Complete solution, correctness argument, and adversarial test plan
    12. Concurrent LLD problems: solved workbook Can I combine concurrency semantics with component design? Interview-ready API, implementation, operational limits, and evaluation rubric

    Later chapters should build on the same proof discipline rather than replacing it with API memorization.

    How to study each chapter¶

    1. Predict every broken example before running it.
    2. Write one failing interleaving as numbered thread steps.
    3. State the invariant independently of the implementation.
    4. Mark the synchronization action or API contract that establishes ordering.
    5. Identify the operation's linearization point.
    6. Name at least one safety test and one liveness test.
    7. Re-deliver the design aloud under a five-minute limit.

    One successful run proves almost nothing

    A race may need a rare schedule, a different processor, or a different JIT decision. Tests can reveal concurrency defects, but a correctness argument must cover all permitted executions.

    A running example: bounded seat allocation¶

    Suppose multiple threads call reserve() on a pool with one remaining seat.

    final class BrokenSeatPool {
    private int remaining = 1;

    boolean reserve() {
        if (remaining > 0) {
            remaining--;
            return true;
        }
        return false;
    }
}

    The desired invariant is:

    0 <= remaining <= initialCapacity
successfulReservations + remaining == initialCapacity

    An invalid execution is:

    Step Thread A Thread B remaining
    1 reads remaining == 1 1
    2 reads remaining == 1 1
    3 writes 0; returns true 0
    4 writes 0; returns true 0

    Both callers report success for one seat. The final field value looks plausible, so an assertion on remaining alone misses the violation. A corrected design must make the check and decrement one atomic state transition:

    final class SeatPool {
    private int remaining = 1;

    synchronized boolean reserve() {
        if (remaining == 0) {
            return false;
        }
        remaining--;
        return true;
    }

    synchronized int remaining() {
        return remaining;
    }
}

    The monitor protects every access to remaining. The successful call linearizes at remaining--; an unsuccessful call linearizes at its observation of zero while holding the same monitor. Monitor release happens-before a later acquisition of that monitor, so callers using these methods receive both atomicity and visibility.

    Tool-selection preview¶

    Need Likely starting point Main cost or trap
    Publish fixed configuration Immutable object plus safe publication A final reference does not freeze mutable children.
    Protect a small compound invariant synchronized Blocking and accidental lock scope.
    Timed or interruptible lock acquisition ReentrantLock Unlock must be in finally; fairness reduces throughput.
    One independent numeric update AtomicLong Multiple atomics do not create one multi-field transaction.
    High-contention statistics LongAdder sum() is not an atomic snapshot for control decisions.
    Per-key atomic map operation ConcurrentHashMap.compute Mapping functions must remain short and non-recursive.
    Bound asynchronous work ThreadPoolExecutor plus bounded queue Rejection and shutdown are part of the design.
    Many blocking I/O tasks Virtual threads in Java 21 They do not make CPU work faster or remove shared-state races.

    Interview traps¶

    • Saying "thread-safe" without naming the protected state and invariant.
    • Treating volatile as a general replacement for locking.
    • Assuming thread-safe methods compose into a thread-safe workflow.
    • Using sleep as coordination or as proof that another thread finished.
    • Catching InterruptedException and continuing without a cancellation policy.
    • Optimizing contention before establishing correctness.
    • Claiming an API is lock-free, fair, or linearizable without knowing its contract.

    Review questions¶

    1. Why can remaining == 0 coexist with two successful reservations?
    2. What is the difference between a safety property and a liveness property?
    3. Why must a synchronization policy cover readers as well as writers?
    4. What does a linearization point let an interviewer reason about?
    5. Why are virtual threads not a fix for data races?

    Hands-on exercise¶

    Write a two-minute opening for this prompt: "Design an in-memory component that allocates at most ten permits to concurrent callers and allows permits to be returned." Include state, two invariants, one policy decision, and one question for the interviewer.

    Solution

    I will model ten interchangeable permits. The canonical mutable state is either an available count or a set of checked-out permit IDs; I would choose IDs only if ownership or duplicate returns must be diagnosed. The safety invariants are 0 <= available <= 10 and one permit cannot be checked out to two callers. A return must not increase capacity after a duplicate or foreign release. I will put every allocation and return transition under one private lock first, then consider a semaphore or a more scalable representation only if requirements justify it. Do callers wait, time out, or fail immediately when exhausted, and must cancellation remove waiting callers promptly?

    This opening exposes the ambiguity around waiting and return identity. If duplicate returns are impossible by contract, a count may suffice. If the component must detect them, track lease IDs or owner tokens.
