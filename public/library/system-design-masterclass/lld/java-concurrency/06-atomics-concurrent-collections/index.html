    06. Atomics and Concurrent Collections¶

    Lock-free APIs do not remove synchronization; they move it into atomic instructions and library protocols. Correct use still starts with shared state, an invariant, and a precise linearization point. This chapter covers Java 21 atomics and collections as building blocks for interview-grade low-level designs.

    Learning goals¶

    By the end of this chapter, you should be able to:

    • explain compare-and-set and retry loops;
    • select AtomicInteger, AtomicLong, AtomicReference, or LongAdder;
    • keep atomic update functions pure because they may run repeatedly;
    • identify and prevent ABA with AtomicStampedReference;
    • use ConcurrentHashMap atomic compound methods correctly;
    • explain computeIfAbsent recursion and blocking hazards;
    • choose copy-on-write, concurrent, or blocking collections by workload;
    • reason about weakly consistent iteration;
    • identify linearization points in counters, state machines, reservations, and registries; and
    • test concurrent behavior deterministically.

    Conceptual model: one atomic transition¶

    An atomic variable provides indivisible operations on one logical location. A concurrent collection provides atomicity for documented operations, usually one key or one queue action at a time. Neither automatically preserves an invariant spanning several independent locations.

    For every operation, state:

    1. Shared state: the atomic reference, counter, map entry, or queue.
    2. Invariant: the legal values or relationships.
    3. Transition: old state to new state.
    4. Linearization point: the successful CAS or documented atomic collection operation.
    5. Contention policy: retry, block, reject, stripe, or serialize.

    Atomic does not mean transaction

    Two atomic increments are two atomic operations, not one transaction. If available + reserved must remain constant, represent them in one immutable state behind one AtomicReference, or use a lock.

    Compare-and-set¶

    Compare-and-set (CAS) means: if the current value equals the expected value, replace it with the update atomically; otherwise report failure. A CAS loop reads, derives a candidate, and retries after interference.

    import java.util.concurrent.atomic.AtomicInteger;

final class CappedCounter {
    private final int maximum;
    private final AtomicInteger value = new AtomicInteger();

    CappedCounter(int maximum) {
        if (maximum < 0) {
            throw new IllegalArgumentException("negative maximum");
        }
        this.maximum = maximum;
    }

    boolean tryIncrement() {
        while (true) {
            int current = value.get();
            if (current == maximum) {
                return false;
            }
            if (value.compareAndSet(current, current + 1)) {
                return true; // Successful CAS is the linearization point.
            }
        }
    }
}
    • Shared state: value.
    • Invariant: 0 <= value <= maximum.
    • Linearization point: successful compareAndSet; a failure due to the cap linearizes at the read that observes maximum.

    Assuming the underlying CAS has non-blocking progress, a failed strong CAS here means another increment won. Generic CAS retry loops are normally lock-free rather than wait-free: an individual caller may repeatedly lose. This particular capped, increment-only example has a stronger bound because only finitely many increments can succeed before every caller observes the cap. Do not transfer that bound to a counter that can decrease or reset. Expensive candidate computation and hot single locations can still create retry storms.

    Atomic number and reference types¶

    AtomicInteger and AtomicLong support increments, additions, swaps, CAS, and functional updates. AtomicReference<T> atomically replaces object references and can hold an immutable aggregate state.

    Broken: check then increment¶

    if (reserved.get() < capacity) {
    reserved.incrementAndGet();
}

    The read and increment are separate. Several threads can pass the check and exceed capacity.

    Corrected stock reservation¶

    import java.util.concurrent.atomic.AtomicInteger;

final class Stock {
    private final AtomicInteger remaining;

    Stock(int quantity) {
        if (quantity < 0) {
            throw new IllegalArgumentException("negative quantity");
        }
        remaining = new AtomicInteger(quantity);
    }

    boolean tryReserve(int quantity) {
        if (quantity <= 0) {
            throw new IllegalArgumentException("quantity must be positive");
        }
        while (true) {
            int current = remaining.get();
            if (current < quantity) {
                return false;
            }
            if (remaining.compareAndSet(current, current - quantity)) {
                return true; // Reservation linearization point.
            }
        }
    }

    int remaining() {
        return remaining.get();
    }
}
    • Shared state: remaining stock.
    • Invariant: remaining stock never becomes negative.
    • Linearization point: successful CAS; rejected reservation linearizes at an observed insufficient value.

    This only reserves in memory inside one process. Durable inventory requires an authoritative database transition, idempotency, and failure recovery.

    Functional updates must tolerate retries¶

    updateAndGet, getAndUpdate, and accumulateAndGet may reapply their functions after CAS contention. Keep these functions deterministic from their arguments and free of externally visible side effects. Map contracts differ: ConcurrentHashMap.computeIfAbsent invokes the mapping function at most once per call, while other concurrent-map implementations may retry a computation. Even with ConcurrentHashMap, a later call may load again after removal, failure, or a null result; no map callback supplies durable exactly-once effects.

    Broken: side effect inside retryable update¶

    balance.updateAndGet(current -> {
    auditLog.append("charged");
    return current - charge;
});

    If CAS loses, the function may append again. The final atomic value can be correct while the audit log contains duplicates.

    Corrected: CAS first, side effect after success¶

    boolean charge(AtomicInteger balance, int amount, java.util.function.IntConsumer audit) {
    if (amount <= 0) throw new IllegalArgumentException("positive amount required");
    while (true) {
        int current = balance.get();
        if (current < amount) {
            return false;
        }
        int updated = current - amount;
        if (balance.compareAndSet(current, updated)) {
            audit.accept(amount);
            return true;
        }
    }
}

    This prevents duplicate audit calls due to CAS retry, but a crash between CAS and audit still loses the audit. If both effects must be atomic, an in-memory atomic cannot provide that guarantee; use a transactional store or durable outbox.

    Immutable state machine with AtomicReference¶

    One reference can atomically replace a state containing several related values.

    import java.util.concurrent.atomic.AtomicReference;

final class Job {
    enum Status { CREATED, RUNNING, SUCCEEDED, FAILED }

    record Snapshot(Status status, int attempts, String result) {
        Snapshot {
            if (attempts < 0) {
                throw new IllegalArgumentException("negative attempts");
            }
            if (status == Status.SUCCEEDED && result == null) {
                throw new IllegalArgumentException("success requires result");
            }
            if (status != Status.SUCCEEDED && result != null) {
                throw new IllegalArgumentException("result only on success");
            }
        }
    }

    private final AtomicReference<Snapshot> state =
            new AtomicReference<>(new Snapshot(Status.CREATED, 0, null));

    boolean start() {
        while (true) {
            Snapshot current = state.get();
            if (current.status() != Status.CREATED
                    && current.status() != Status.FAILED) {
                return false;
            }
            Snapshot next = new Snapshot(
                    Status.RUNNING, current.attempts() + 1, null);
            if (state.compareAndSet(current, next)) {
                return true;
            }
        }
    }

    boolean succeed(String result) {
        java.util.Objects.requireNonNull(result, "result");
        while (true) {
            Snapshot current = state.get();
            if (current.status() != Status.RUNNING) {
                return false;
            }
            Snapshot next = new Snapshot(
                    Status.SUCCEEDED, current.attempts(), result);
            if (state.compareAndSet(current, next)) {
                return true;
            }
        }
    }

    Snapshot snapshot() {
        return state.get();
    }
}
    • Shared state: one reference to an immutable snapshot.
    • Invariant: attempts are non-negative; only success carries a result; transitions follow the allowed graph.
    • Linearization point: successful CAS for each transition.

    Immutability prevents a caller from changing fields behind the atomic reference. Validate transitions against the current snapshot on every retry.

    LongAdder versus AtomicLong¶

    AtomicLong maintains one linearizable value. Under heavy write contention, all writers compete on that location. LongAdder spreads updates across cells and sums them when read.

    Requirement Prefer
    sequence number or unique ID AtomicLong
    compare-and-set transition AtomicLong
    exact value used for admission AtomicLong or lock
    high-rate metrics increment LongAdder
    approximate live telemetry LongAdder

    LongAdder.sum() is not an atomic snapshot with concurrent updates. It may miss or include updates racing with the sum. sumThenReset() is also not atomic with concurrent increments and is unsuitable when losing counts is forbidden.

    import java.util.concurrent.atomic.LongAdder;

final class RequestMetrics {
    private final LongAdder completed = new LongAdder();

    void recordCompletion() {
        completed.increment();
    }

    long approximateCompleted() {
        return completed.sum();
    }
}

    The increment is thread-safe, but do not claim one global linearization point for a concurrent sum. This makes LongAdder a poor stock counter.

    ABA and stamped references¶

    CAS compares the observed value with the current value. If state changes from A to B and back to A, value-only CAS cannot detect the intermediate change. That is the ABA problem.

    Consider a reusable slot represented by node reference A:

    1. Thread T1 reads A.
    2. T2 replaces A with B, retires A, then reuses A as the head.
    3. T1 sees A again and its CAS succeeds, although assumptions about A's history may be invalid.

    Garbage collection prevents raw memory reuse errors common in unmanaged languages, but ABA still matters when identity can leave and re-enter a logical state.

    import java.util.concurrent.atomic.AtomicStampedReference;

final class VersionedValue<T> {
    private final AtomicStampedReference<T> value;

    VersionedValue(T initial) {
        value = new AtomicStampedReference<>(initial, 0);
    }

    record View<T>(T value, int stamp) {}

    View<T> view() {
        int[] stampHolder = new int[1];
        T current = value.get(stampHolder);
        return new View<>(current, stampHolder[0]);
    }

    boolean replace(View<T> expected, T update) {
        return value.compareAndSet(expected.value(), update,
                expected.stamp(), expected.stamp() + 1);
    }
}
    • Shared state: reference and stamp as one atomic pair.
    • Invariant: each successful replacement advances the stamp.
    • Linearization point: successful stamped CAS.

    An int stamp can wrap. Decide whether wrap is plausible within the lifetime of a stale operation. Another approach is an immutable wrapper containing a wider logical version and value.

    The caller must retain the stamp from the original observation. Reading a fresh stamp inside replace(expectedValue, update) only detects interference during that call, not an A-B-A cycle since the caller read A.

    ConcurrentHashMap: atomicity is per operation¶

    ConcurrentHashMap supports concurrent retrievals and updates without one global map lock. Its compound methods provide atomic behavior for a key.

    Broken frequency counter¶

    counts.put(word, counts.getOrDefault(word, 0) + 1);

    Two threads can read the same count and overwrite one increment.

    Frequency counter with LongAdder¶

    import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.LongAdder;

final class FrequencyCounter {
    private final ConcurrentHashMap<String, LongAdder> counts =
            new ConcurrentHashMap<>();

    void record(String key) {
        counts.computeIfAbsent(key, ignored -> new LongAdder()).increment();
    }

    long count(String key) {
        LongAdder adder = counts.get(key);
        return adder == null ? 0 : adder.sum();
    }
}
    • Shared state: key-to-adder registry and each adder's cells.
    • Invariant: each key maps to at most one installed adder at a time.
    • Linearization point: map installation for a new key; increments are thread-safe, while concurrent sums are not exact snapshots.

    If exact linearizable counts per key are required, use AtomicLong values. If exact consistency across keys is required, this map is insufficient by itself.

    Useful atomic map methods¶

    Method Use
    putIfAbsent publish one value if no mapping exists
    computeIfAbsent derive and install a missing value
    computeIfPresent update or remove an existing mapping
    compute derive mapping from present or absent state
    merge combine an existing and supplied value
    replace(key, old, next) conditional per-key transition
    remove(key, value) conditional removal

    Cache registry¶

    import java.util.concurrent.ConcurrentHashMap;
import java.util.function.Function;

final class CacheRegistry<K, V> {
    private final ConcurrentHashMap<K, V> values = new ConcurrentHashMap<>();

    V getOrLoad(K key, Function<? super K, ? extends V> loader) {
        return values.computeIfAbsent(key, loader);
    }

    boolean invalidate(K key, V expectedValue) {
        return values.remove(key, expectedValue);
    }
}
    • Shared state: map entries.
    • Invariant: each key has at most one current non-null mapping.
    • Linearization point: successful installation/removal performed by the map operation.

    ConcurrentHashMap forbids null keys and values. A mapping function that returns null installs nothing.

    Keep remapping functions short and non-recursive

    computeIfAbsent may block other updates to the same internal region while computing. Do not perform slow I/O when latency isolation matters. Do not recursively update the same map from the mapping function; detectable recursive computation can throw IllegalStateException, and cross-key recursion can create cycles or deadlock-like stalls. For expensive asynchronous loads, store futures and define failure eviction explicitly.

    Asynchronous single-flight registry¶

    import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ConcurrentHashMap;
import java.util.function.Supplier;

final class AsyncRegistry<K, V> {
    private final ConcurrentHashMap<K, CompletableFuture<V>> loads =
            new ConcurrentHashMap<>();

    CompletableFuture<V> getOrLoad(
            K key, Supplier<CompletableFuture<V>> loader) {
        CompletableFuture<V> future = loads.computeIfAbsent(key, ignored -> {
            try {
                return java.util.Objects.requireNonNull(loader.get(), "loader future");
            } catch (Throwable failure) {
                return CompletableFuture.failedFuture(failure);
            }
        });
        future.whenComplete((value, failure) -> {
            if (failure != null) {
                loads.remove(key, future);
            }
        });
        return future.copy();
    }
}

    This shares one installed future per key and conditionally evicts only that failed future. A loader that itself calls getOrLoad for the same key can still recurse. Also, loader.get() runs during map computation; a stronger design inserts an incomplete future quickly, starts I/O outside map computation, and completes the future afterward.

    Return a dependent copy so one caller cannot cancel or complete the shared root for everyone. The loader still owns the root; document its lifecycle and bound registry cardinality. The Job snapshot above is a one-run example with no fail method: adding retries requires passing the claimed attempt/version to completion, or a late old worker could succeed a newer RUNNING attempt. An atomic snapshot alone does not fence stale actors.

    Copy-on-write collections¶

    CopyOnWriteArrayList creates a fresh backing array for each mutation. Reads require no lock and iterators observe an immutable snapshot taken when the iterator was created.

    import java.util.concurrent.CopyOnWriteArrayList;

final class ListenerRegistry<E> {
    private final CopyOnWriteArrayList<java.util.function.Consumer<E>> listeners =
            new CopyOnWriteArrayList<>();

    void add(java.util.function.Consumer<E> listener) {
        listeners.addIfAbsent(listener);
    }

    void publish(E event) {
        for (var listener : listeners) {
            listener.accept(event);
        }
    }
}
    • Shared state: current immutable backing-array snapshot.
    • Invariant: with addIfAbsent, a listener appears at most once by equality.
    • Linearization point: publication of the replacement array for mutation; iterator creation fixes its snapshot.

    Use copy-on-write when reads and traversals vastly outnumber writes and the collection is modest. Avoid it for frequent writes, large lists, or memory-sensitive bursts. Iterator remove is unsupported, and an existing iterator does not see later changes.

    Concurrent and blocking queues¶

    Queue choice encodes backpressure and ordering semantics.

    Type Capacity Waiting behavior Typical use
    ConcurrentLinkedQueue unbounded non-blocking offer/poll lightweight shared work list
    ArrayBlockingQueue bounded blocking and timed methods fixed-memory producer-consumer
    LinkedBlockingQueue optional bound blocking and timed methods buffered pipeline
    PriorityBlockingQueue unbounded blocking take, priority order priority scheduling without backpressure
    SynchronousQueue zero producer meets consumer direct handoff
    DelayQueue unbounded take waits for delay expiry and delayed tasks

    For BlockingQueue:

    • add throws if capacity is unavailable;
    • offer returns false immediately;
    • timed offer waits up to a bound;
    • put waits until capacity exists;
    • remove throws if empty;
    • poll returns null immediately;
    • timed poll waits up to a bound;
    • take waits for an element.
    boolean submit(java.util.concurrent.BlockingQueue<Job> queue, Job job)
        throws InterruptedException {
    return queue.offer(job, 100, java.util.concurrent.TimeUnit.MILLISECONDS);
}

    The successful offer that links or stores the element is the enqueue linearization point. A successful poll or take removal is the dequeue linearization point. Queue internal state is shared; its invariant is that each enqueue occurrence is removed at most once and capacity is not exceeded for bounded queues.

    An unbounded queue does not provide overload control. It converts overload into growing memory and latency. Prefer a bounded queue plus explicit reject, caller-runs, drop, or shed policy when producers can outrun consumers.

    Weakly consistent iteration¶

    Iterators from ConcurrentHashMap and many concurrent queues are weakly consistent. They do not throw ConcurrentModificationException; they may reflect some updates that happen after iterator creation and may omit others. They do not provide one atomic snapshot.

    Use weak iteration for diagnostics, best-effort maintenance, or approximate metrics. Do not use it to enforce invariants such as "sum all balances, then authorize a withdrawal" or to perform exactly-once processing. For a stable snapshot, coordinate writers, copy under the relevant protocol, use immutable snapshots, or query a transactional source.

    Bulk map operations such as forEach, reduce, and search also observe concurrent state. Their functions should not depend on encounter order and should avoid side effects that require exactly-once execution.

    Choosing locks, atomics, and concurrent collections¶

    Situation First choice Reason
    one numeric independent transition atomic number direct linearizable operation
    several related fields lock or immutable atomic snapshot preserve cross-field invariant
    per-key independent updates ConcurrentHashMap compound method atomic key-scoped operation
    hot metrics counter LongAdder spreads write contention
    bounded producer-consumer bounded BlockingQueue storage plus backpressure
    rare listener changes CopyOnWriteArrayList cheap stable traversal
    complex blocking protocol lock and conditions explicit predicates and waits

    Lock-free is not automatically faster. Measure contention, allocation, retry rate, and tail latency. Prefer the simplest mechanism that expresses the invariant.

    Deterministic tests¶

    Stock cannot oversell¶

    import static org.junit.jupiter.api.Assertions.assertEquals;

import java.util.concurrent.CountDownLatch;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicInteger;
import org.junit.jupiter.api.Test;

class AtomicExamplesTest {
    @Test
    void stockNeverOversells() throws Exception {
        int initial = 100;
        var stock = new Stock(initial);
        var successes = new AtomicInteger();
        var start = new CountDownLatch(1);

        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            var futures = java.util.stream.IntStream.range(0, 500)
                    .mapToObj(ignored -> executor.submit(() -> {
                        start.await();
                        if (stock.tryReserve(1)) {
                            successes.incrementAndGet();
                        }
                        return null;
                    })).toList();
            start.countDown();
            for (var future : futures) {
                future.get(2, TimeUnit.SECONDS);
            }
        }

        assertEquals(initial, successes.get());
        assertEquals(0, stock.remaining());
    }

    @Test
    void oneCacheValueIsPublishedPerKey() throws Exception {
        var registry = new CacheRegistry<String, Object>();
        var loadCalls = new AtomicInteger();
        var start = new CountDownLatch(1);

        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            var futures = java.util.stream.IntStream.range(0, 100)
                    .mapToObj(ignored -> executor.submit(() -> {
                        start.await();
                        return registry.getOrLoad("key", key -> {
                            loadCalls.incrementAndGet();
                            return new Object();
                        });
                    })).toList();
            start.countDown();
            Object expected = futures.getFirst().get(1, TimeUnit.SECONDS);
            for (var future : futures) {
                org.junit.jupiter.api.Assertions.assertSame(
                        expected, future.get(1, TimeUnit.SECONDS));
            }
        }

        assertEquals(1, loadCalls.get());
    }
}

    The start latch increases overlap without claiming a specific scheduler order. Future timeouts detect hangs. Final invariants, not observed thread interleavings, determine correctness.

    Deterministically force one CAS failure¶

    Production classes can accept a package-private test hook immediately before CAS. A test uses barriers to let both threads read the same old value, allows one CAS, then verifies the other retries. Do not retain such hooks in public APIs; alternatively test a small CAS-loop helper whose candidate function counts invocations and whose atomic is changed at a controlled barrier.

    Common pitfalls¶

    • Splitting check-and-act across separate atomic operations.
    • Assuming multiple atomic fields form an atomic snapshot.
    • Putting I/O, logging, metrics, random generation, or mutation in retryable update functions.
    • Using LongAdder.sum() for admission or exact sequencing.
    • Ignoring ABA when a value can leave and return to the same representation.
    • Treating ConcurrentHashMap.get followed by put as a compound atomic action.
    • Recursively mutating a map from computeIfAbsent.
    • Running slow loaders inside map computation without considering contention.
    • Assuming a weakly consistent iterator is a snapshot.
    • Using copy-on-write for a write-heavy or large collection.
    • Selecting an unbounded queue without an overload policy.
    • Assuming thread-safe callbacks make a compound workflow safe.

    Exercises¶

    Exercise 1: reserve and release with one invariant¶

    Extend stock so reservations can be released without exceeding the initial capacity. Keep the transition in one atomic value.

    Complete solution 
    final class ReleasableStock {
    private final int capacity;
    private final java.util.concurrent.atomic.AtomicInteger remaining;

    ReleasableStock(int capacity) {
        if (capacity < 0) {
            throw new IllegalArgumentException("negative capacity");
        }
        this.capacity = capacity;
        this.remaining = new java.util.concurrent.atomic.AtomicInteger(capacity);
    }

    boolean tryReserve(int quantity) {
        if (quantity <= 0) {
            throw new IllegalArgumentException("quantity must be positive");
        }
        while (true) {
            int current = remaining.get();
            if (current < quantity) {
                return false;
            }
            if (remaining.compareAndSet(current, current - quantity)) {
                return true;
            }
        }
    }

    void release(int quantity) {
        if (quantity <= 0) {
            throw new IllegalArgumentException("quantity must be positive");
        }
        while (true) {
            int current = remaining.get();
            if (quantity > capacity - current) {
                throw new IllegalStateException("release exceeds reservations");
            }
            if (remaining.compareAndSet(current, current + quantity)) {
                return;
            }
        }
    }
}

    Shared state is remaining capacity. The invariant is 0 <= remaining <= capacity. Each successful CAS is a linearization point. This API trusts callers to release each reservation once. A robust domain model would return a reservation token with idempotent lifecycle state rather than expose an uncorrelated quantity release.

    Exercise 2: exact per-key frequency¶

    Implement exact linearizable counts per key and explain what remains non-atomic.

    Complete solution 
    final class ExactFrequencyCounter {
    private final java.util.concurrent.ConcurrentHashMap<
            String, java.util.concurrent.atomic.AtomicLong> counts =
            new java.util.concurrent.ConcurrentHashMap<>();

    long record(String key) {
        return counts.computeIfAbsent(
                key, ignored -> new java.util.concurrent.atomic.AtomicLong())
                .incrementAndGet();
    }

    long count(String key) {
        var counter = counts.get(key);
        return counter == null ? 0 : counter.get();
    }
}

    Installation is atomic per key, and each increment is linearizable on that key's AtomicLong. Reading several keys is not one atomic snapshot. Removal concurrent with increment would require an additional lifecycle protocol because a thread could increment an atomic no longer installed in the map.

    Exercise 3: safe state transition with a version¶

    Model a document that transitions from DRAFT to PUBLISHED. It may return to DRAFT after retraction, but an editor must detect that a publish-retract cycle occurred.

    Complete solution 
    final class VersionedDocument {
    enum Status { DRAFT, PUBLISHED }

    private final java.util.concurrent.atomic.AtomicStampedReference<Status> state =
            new java.util.concurrent.atomic.AtomicStampedReference<>(Status.DRAFT, 0);

    record View(Status status, int version) {}

    View view() {
        int[] stamp = new int[1];
        Status status = state.get(stamp);
        return new View(status, stamp[0]);
    }

    boolean publish(View expected) {
        if (expected.status() != Status.DRAFT) {
            return false;
        }
        return state.compareAndSet(
                Status.DRAFT, Status.PUBLISHED,
                expected.version(), expected.version() + 1);
    }

    boolean retract(View expected) {
        if (expected.status() != Status.PUBLISHED) {
            return false;
        }
        return state.compareAndSet(
                Status.PUBLISHED, Status.DRAFT,
                expected.version(), expected.version() + 1);
    }
}

    The state and version form one atomic pair. Every successful transition increments the stamp. An editor holding the original DRAFT view cannot publish after another publish-retract cycle because the status matches but the stamp does not. Successful stamped CAS is the linearization point.

    Exercise 4: choose a queue¶

    A service accepts image jobs, has 16 consumers, must cap memory at 1,000 queued jobs, and should reject after waiting 50 ms. Choose an API and state the overload behavior.

    Complete solution

    Use an ArrayBlockingQueue<Job> with capacity 1,000 and timed offer:

    final class ImageJobBuffer {
    private final java.util.concurrent.ArrayBlockingQueue<Job> queue =
            new java.util.concurrent.ArrayBlockingQueue<>(1_000);

    boolean submit(Job job) throws InterruptedException {
        return queue.offer(job, 50, java.util.concurrent.TimeUnit.MILLISECONDS);
    }

    Job take() throws InterruptedException {
        return queue.take();
    }
}

    A successful offer linearizes at insertion. A false result is explicit overload and must become a stable caller response such as rejection or retry-after; it must not be silently dropped. take blocks consumers without polling. The queue bounds queued jobs, not executing jobs, so total in-flight capacity is up to 1,016 plus producer-local references.

    Summary¶

    • CAS atomically commits a transition only when the observed state is still current.
    • A failed CAS requires recomputation; retryable functions must not perform side effects.
    • Atomic variables preserve one-location invariants, while immutable snapshots can combine related fields.
    • LongAdder improves hot metric writes but does not provide an exact concurrent snapshot.
    • Stamps or versions detect value histories hidden by ABA.
    • ConcurrentHashMap compound methods are atomic per key, not across the map.
    • Copy-on-write favors frequent traversal and rare mutation.
    • Blocking queues combine transfer semantics with explicit capacity and waiting policy.
    • Weakly consistent iteration is useful for observation, not transactional decisions.
    • The simplest mechanism that directly expresses the invariant is usually the strongest interview answer.
