    07. Executors, Capacity, and Backpressure¶

    Executors separate task submission from task execution. That separation is useful only when the queue, rejection behavior, and shutdown protocol are part of the design. An executor with an accidental unbounded queue is not a capacity plan.

    Goals¶

    After this chapter, you should be able to:

    • choose between Executor, ExecutorService, Callable, and Future;
    • predict how every ThreadPoolExecutor parameter affects admission;
    • derive a starting pool size from measured workload data;
    • design bounded overload behavior instead of hiding overload in a queue;
    • explain scheduled task semantics and failure behavior;
    • implement graceful and forced shutdown correctly;
    • prevent ThreadLocal state from leaking between pooled tasks; and
    • build and test a bounded worker service.

    1. The execution model¶

    Executor has one operation:

    void execute(Runnable command);

    The interface does not specify which thread runs the command or when it starts. ExecutorService adds lifecycle control and result-bearing submission. A Callable<V> may return a value or throw a checked exception. Future<V> represents the eventual completion of one submitted task.

    submit -> admission -> queued/running -> completed
                 |                       |-- value
                 |                       |-- failure
                 |                       `-- cancellation
                 `-- rejected

    Completion semantics¶

    For a successful Future.get(), actions in the task happen-before actions after get() returns. get() wraps task failure in ExecutionException. Interrupting the waiting caller does not cancel the task. cancel(true) requests interruption if the task has started; it does not forcibly stop Java code.

    State model¶

    A useful conceptual state machine is:

    NEW -> QUEUED -> RUNNING -> SUCCESS
  |       |         |------> FAILED
  |       |         `------> CANCELLED (cooperative)
  |       `----------------> CANCELLED
  `------------------------> REJECTED (no Future-owned execution)

    The exact internal FutureTask states are implementation details. The interview invariant is simpler:

    A one-shot task submitted once to a standard ExecutorService is invoked at most once for that submission. Its future reaches a terminal outcome only if it completes or is explicitly cancelled; accepted work can otherwise remain pending forever.

    Do not confuse that with exactly-once business processing. A process crash can occur after an external side effect but before durable acknowledgement.

    CANCELLED is a future outcome, not proof that the task body stopped. A running body can ignore interruption and continue after get() reports cancellation. Executor.execute also permits caller-thread execution; the interface alone promises no queue or thread creation.

    2. Broken submission and corrected ownership¶

    Broken: fire-and-forget with no lifecycle¶

    public final class BrokenIndexer {
    private final ExecutorService pool = Executors.newFixedThreadPool(16);

    public void index(Document document) {
        pool.submit(() -> repository.save(document));
    }
}

    Problems:

    • newFixedThreadPool uses an unbounded queue;
    • failures disappear inside ignored Future objects;
    • callers cannot observe completion or rejection;
    • the service has no shutdown contract; and
    • accepted work can be lost when the process exits.

    Corrected: explicit result and lifecycle¶

    public final class Indexer implements AutoCloseable {
    private final ExecutorService pool;

    public Indexer(int workers, int capacity) {
        this.pool = new ThreadPoolExecutor(
                workers,
                workers,
                0L,
                TimeUnit.MILLISECONDS,
                new ArrayBlockingQueue<>(capacity),
                Thread.ofPlatform().name("indexer-", 0).factory(),
                new ThreadPoolExecutor.AbortPolicy());
    }

    public Future<IndexResult> index(Document document) {
        Objects.requireNonNull(document);
        return pool.submit(() -> repository.save(document));
    }

    @Override
    public void close() {
        ExecutorShutdown.graceful(pool, Duration.ofSeconds(20));
    }
}

    This is better because queue capacity and rejection are visible design choices. Production code should also expose active threads, queue depth, completed tasks, rejected tasks, and task latency.

    3. ThreadPoolExecutor admission algorithm¶

    Given corePoolSize, maximumPoolSize, keepAliveTime, and a work queue, execute broadly follows this order:

    1. If fewer than corePoolSize workers exist, start a worker for the task.
    2. Otherwise, try to enqueue the task.
    3. If the queue is full and fewer than maximumPoolSize workers exist, start another worker.
    4. Otherwise, invoke the rejection handler.

    This ordering causes a common interview trap: maximumPoolSize has no practical effect with an unbounded queue because step 2 almost always succeeds.

    Parameter interactions¶

    Choice Admission effect Operational consequence
    Small core, bounded queue, larger max Queues before growing past core Can add queue delay before using spare threads
    Core equals max, bounded queue Fixed concurrency and bounded backlog Predictable capacity and simpler tuning
    SynchronousQueue No storage; direct handoff only Grows toward max quickly, rejects when all workers are busy
    Unbounded queue Almost every task queues Max is ineffective; latency and memory can grow without bound
    allowCoreThreadTimeOut(true) Even core workers may retire Saves idle resources but adds cold-start cost

    Non-core workers retire after keepAliveTime while idle. Core workers do so only when core timeout is enabled. Prestarting core threads trades startup cost for idle resource use.

    Bounded versus unbounded queues¶

    A bounded queue turns capacity into a finite quantity:

    in-flight capacity = active workers + queue slots

    It does not solve overload by itself. It creates the point at which the system must shed, block, redirect, or degrade work. An unbounded queue delays that decision until latency or memory fails elsewhere.

    Queue choice also changes scheduling:

    • ArrayBlockingQueue is bounded and allocation-stable. Optional fairness reduces barging but usually costs throughput.
    • LinkedBlockingQueue(capacity) is bounded when a capacity is supplied, but allocates linked nodes.
    • PriorityBlockingQueue is unbounded and does not preserve FIFO among equal priorities unless tasks include a sequence tie-breaker.
    • SynchronousQueue has zero capacity and pairs producers with workers.

    4. Rejection and backpressure¶

    The built-in policies express different contracts:

    Policy Behavior Appropriate when
    AbortPolicy Throws RejectedExecutionException Caller can fail fast, retry elsewhere, or return overload
    CallerRunsPolicy Submitter runs the task Slowing that submitter safely propagates pressure
    DiscardPolicy Silently drops the task Rarely; only explicitly disposable, measured work
    DiscardOldestPolicy Drops queue head and retries Rarely; semantics tolerate loss and ordering changes

    CallerRunsPolicy is not universally safe. It may execute blocking work on an event-loop thread, hold a lock while running user code, or make request latency unbounded. Also, after shutdown it silently discards under the JDK implementation. Prefer an explicit rejection contract.

    Broken: retry storm¶

    while (true) {
    try {
        executor.execute(task);
        break;
    } catch (RejectedExecutionException overloaded) {
        // Immediate retry adds more load and burns CPU.
    }
}

    Corrected: bounded admission wait¶

    public final class BoundedExecutor {
    private final ThreadPoolExecutor executor;
    private final Semaphore inFlight;

    public BoundedExecutor(int workers, int queueCapacity) {
        if (workers <= 0 || queueCapacity <= 0) {
            throw new IllegalArgumentException("capacity must be positive");
        }
        int capacity = Math.addExact(workers, queueCapacity);
        inFlight = new Semaphore(capacity, true);
        executor = new ThreadPoolExecutor(
                workers, workers, 0L, TimeUnit.MILLISECONDS,
                new ArrayBlockingQueue<>(queueCapacity),
                new ThreadPoolExecutor.AbortPolicy());
    }

    public boolean execute(Runnable task, Duration budget)
            throws InterruptedException {
        Objects.requireNonNull(task, "task");
        Objects.requireNonNull(budget, "budget");
        if (budget.isNegative()) {
            throw new IllegalArgumentException("negative budget");
        }
        long nanos;
        try {
            nanos = budget.toNanos();
        } catch (ArithmeticException tooLarge) {
            nanos = Long.MAX_VALUE;
        }
        if (!inFlight.tryAcquire(nanos, TimeUnit.NANOSECONDS)) {
            return false;
        }
        try {
            executor.execute(() -> {
                try {
                    task.run();
                } finally {
                    inFlight.release();
                }
            });
            return true;
        } catch (RejectedExecutionException rejected) {
            inFlight.release();
            return false;
        }
    }

    public void shutdown() {
        executor.shutdown();
    }
}

    The semaphore bounds running plus queued work and makes producers wait only for their admission budget. After a permit is obtained, execute remains the sole executor-admission operation. Therefore a shutdown race is resolved by ThreadPoolExecutor: either submission commits before shutdown, or rejection releases the permit and returns false. A permit does not guarantee a queue slot at that instant: a finishing worker may release its permit before taking the next queued task, so a permitted submission can still be rejected. Never repair rejection with executor.getQueue().offer(...); a direct enqueue can race with shutdown and leave work in a queue that has no worker allowed to start it.

    Backpressure options¶

    1. Reject quickly and return a retryable overload result.
    2. Wait for a bounded admission budget.
    3. Make the producer perform safe work.
    4. Drop explicitly classified low-value work and count every drop.
    5. Reduce work quality, batch, or route to durable storage.

    The invariant is:

    Running work plus queued work never exceeds the declared in-process bound, and every non-accepted request receives an explicit outcome.

    5. Pool sizing with Little's Law¶

    Little's Law states L = lambda * W for a stable system:

    • L: average number of requests in the system;
    • lambda: average arrival or completion rate; and
    • W: average time in the system.

    If a dependency sustains 800 operations/second and each operation occupies a worker for 25 ms, expected concurrency is:

    L = 800/s * 0.025s = 20 concurrent operations

    Twenty is a measured starting point, not a promise. Account for tail latency, burst tolerance, dependency quotas, CPU, connection-pool capacity, and memory per task. A downstream connection pool of 12 makes a 100-thread pool mostly a waiting room.

    For CPU-bound work, begin near the number of available processors and benchmark. For mixed blocking work, a traditional approximation is:

    threads = processors * target_utilization * (1 + wait_time / compute_time)

    The formula assumes measured, reasonably stable times. Validate it with load tests. Virtual threads change the cost of waiting threads, not downstream capacity or Little's Law.

    Queue capacity should follow an explicit latency budget. If the pool completes 500 tasks/second and at most 100 ms of queueing is acceptable, a rough average queue bound is 50 tasks. Bursts and service-time variance require measurement, not arbitrary multiplication.

    6. Scheduled executors¶

    ScheduledExecutorService supports delayed and periodic work.

    • schedule runs once after at least the delay.
    • scheduleAtFixedRate targets a cadence measured from planned start times. It does not overlap executions of the same periodic task. A slow run can cause subsequent runs to start late.
    • scheduleWithFixedDelay waits the delay after one run completes before scheduling the next.

    If a periodic task throws, later executions are suppressed. Catch and report expected failures at the task boundary.

    ScheduledExecutorService scheduler = Executors.newSingleThreadScheduledExecutor(
        Thread.ofPlatform().name("lease-renewer").factory());

ScheduledFuture<?> handle = scheduler.scheduleWithFixedDelay(() -> {
    try {
        renewLeases();
    } catch (Exception failure) {
        failureReporter.accept(failure);
    }
}, 0, 10, TimeUnit.SECONDS);

    Scheduled delays use relative timing. Wall-clock jumps can still affect application logic that reads calendar time. Keep scheduled tasks short or hand off bounded work to a separate executor. Otherwise one slow maintenance action delays unrelated schedules.

    Cancellation of a scheduled task should usually remove it from the delay queue:

    ScheduledThreadPoolExecutor scheduler = new ScheduledThreadPoolExecutor(2);
scheduler.setRemoveOnCancelPolicy(true);
scheduler.setExecuteExistingDelayedTasksAfterShutdownPolicy(false);
scheduler.setContinueExistingPeriodicTasksAfterShutdownPolicy(false);

    7. Shutdown is a protocol¶

    shutdown() rejects new tasks but lets accepted tasks finish. shutdownNow() attempts to interrupt running tasks and returns tasks that never started. Neither method waits.

    public final class ExecutorShutdown {
    private ExecutorShutdown() {}

    public static void graceful(ExecutorService executor, Duration timeout) {
        Objects.requireNonNull(executor);
        Objects.requireNonNull(timeout);
        if (timeout.isNegative()) throw new IllegalArgumentException("negative timeout");
        long nanos;
        try { nanos = timeout.toNanos(); }
        catch (ArithmeticException tooLarge) { nanos = Long.MAX_VALUE; }
        executor.shutdown();
        boolean interrupted = false;
        try {
            if (!executor.awaitTermination(nanos, TimeUnit.NANOSECONDS)) {
                cancelQueued(executor.shutdownNow());
                if (!executor.awaitTermination(nanos, TimeUnit.NANOSECONDS)) {
                    System.err.println("Executor did not terminate");
                }
            }
        } catch (InterruptedException interruptedException) {
            interrupted = true;
            cancelQueued(executor.shutdownNow());
        } finally {
            if (interrupted) {
                Thread.currentThread().interrupt();
            }
        }
    }

    static void cancelQueued(java.util.List<Runnable> queued) {
        for (Runnable task : queued) {
            if (task instanceof Future<?> future) future.cancel(false);
        }
    }
}

    The service-level order usually is:

    1. stop external admission;
    2. mark the component as draining;
    3. stop producers and periodic submissions;
    4. call shutdown on workers;
    5. await a bounded grace period;
    6. call shutdownNow and cancel outstanding work;
    7. close dependencies after tasks stop; and
    8. report work that did not complete.

    Tasks must cooperate with interruption. Restore interrupt status when a layer cannot complete the cancellation policy itself.

    The helper grants two separate waits of timeout, so total grace plus forced wait may approach twice that duration, excluding scheduling delays. It handles queued standard FutureTask wrappers; custom wrappers need their own completion hook. shutdownNow alone does not cancel returned futures. A running task may outlive both waits, so the diagnostic is not permission to close dependencies still in use.

    Broken interruption handling¶

    try {
    queue.put(item);
} catch (InterruptedException ignored) {
    // Cancellation was consumed, so shutdown may hang.
}

    Corrected interruption handling¶

    try {
    queue.put(item);
} catch (InterruptedException cancelled) {
    Thread.currentThread().interrupt();
    throw new CancellationException("worker interrupted");
}

    8. ThreadLocal hygiene¶

    Pool threads outlive tasks. A value left in a ThreadLocal can be observed by an unrelated request and can retain a large object graph.

    private static final ThreadLocal<String> REQUEST_ID = new ThreadLocal<>();

public static Runnable withRequestId(String requestId, Runnable task) {
    return () -> {
        String previous = REQUEST_ID.get();
        try {
            REQUEST_ID.set(requestId);
            task.run();
        } finally {
            if (previous == null) {
                REQUEST_ID.remove();
            } else {
                REQUEST_ID.set(previous);
            }
        }
    };
}

    Restoring the previous value makes nesting safe. Clearing in afterExecute can add defense in depth, but it must know every context holder and does not replace lexical cleanup. Prefer explicit parameters where practical.

    9. Case study: bounded worker service¶

    Contract¶

    The service processes jobs with these semantics:

    • at most workers + queueCapacity jobs are admitted;
    • submission never waits indefinitely;
    • every accepted submission returns a Future;
    • rejected submissions fail immediately;
    • task failure completes only that task exceptionally;
    • close stops admission, drains, then interrupts; and
    • business actions must be idempotent because process failure can cause external retries.

    Implementation¶

    import java.time.Duration;
import java.util.List;
import java.util.Objects;
import java.util.concurrent.*;
import java.util.concurrent.atomic.LongAdder;

public final class BoundedWorkerService implements AutoCloseable {
    public record Stats(long accepted, long completed, long failed, long rejected,
                        int active, int queued) {}

    private final ThreadPoolExecutor executor;
    private final Duration shutdownTimeout;
    private final LongAdder accepted = new LongAdder();
    private final LongAdder completed = new LongAdder();
    private final LongAdder failed = new LongAdder();
    private final LongAdder rejected = new LongAdder();

    public BoundedWorkerService(int workers, int queueCapacity,
                                Duration shutdownTimeout) {
        if (workers <= 0 || queueCapacity <= 0) {
            throw new IllegalArgumentException("capacity must be positive");
        }
        this.shutdownTimeout = Objects.requireNonNull(shutdownTimeout);
        if (shutdownTimeout.isNegative()) throw new IllegalArgumentException("negative timeout");
        this.executor = new ThreadPoolExecutor(
                workers,
                workers,
                0L,
                TimeUnit.MILLISECONDS,
                new ArrayBlockingQueue<>(queueCapacity),
                Thread.ofPlatform().name("bounded-worker-", 0).factory(),
                (task, ignored) -> {
                    rejected.increment();
                    throw new RejectedExecutionException("worker service overloaded");
                });
    }

    public <T> Future<T> submit(Callable<T> job) {
        Objects.requireNonNull(job);
        Future<T> future = executor.submit(() -> {
            try {
                T value = job.call();
                completed.increment();
                return value;
            } catch (Exception | Error failure) {
                failed.increment();
                throw failure;
            }
        });
        accepted.increment();
        return future;
    }

    public Stats stats() {
        return new Stats(accepted.sum(), completed.sum(), failed.sum(),
                rejected.sum(), executor.getActiveCount(), executor.getQueue().size());
    }

    public List<Runnable> forceShutdown() {
        List<Runnable> queued = executor.shutdownNow();
        ExecutorShutdown.cancelQueued(queued);
        return queued;
    }

    @Override
    public void close() {
        ExecutorShutdown.graceful(executor, shutdownTimeout);
    }
}

    Linearization and accounting¶

    For an accepted task, submission linearizes when ThreadPoolExecutor.execute commits it to a worker or queue. Rejection linearizes when the rejection handler runs. accepted increments after submit returns, so snapshots are intentionally approximate: a task can complete before its accepted counter increments. This is valid for telemetry, not billing.

    The exact capacity invariant applies at executor admission. Metrics observed concurrently need not satisfy accepted = completed + failed + queued + active because counters and executor gauges are not one atomic snapshot, cancellation is omitted, and a running task can finish between reads.

    Failure and cancellation¶

    • A thrown exception is stored in the Future; it does not kill the worker.
    • Future.cancel(false) prevents a queued task from running when cancellation wins.
    • Future.cancel(true) also interrupts a running worker, but the callable must cooperate.
    • shutdownNow returns queued FutureTask instances. The service must define whether callers, a durable queue, or a recovery process owns them.
    • A JVM crash bypasses close; durable jobs require durable intake and idempotent effects.

    10. Tests without timing guesses¶

    The following JUnit 5 tests use latches as deterministic gates. Timeouts bound a broken test; they are not assertions about scheduler speed.

    import static org.junit.jupiter.api.Assertions.*;

import java.time.Duration;
import java.util.concurrent.*;
import org.junit.jupiter.api.Test;

final class BoundedWorkerServiceTest {
    @Test
    void rejectsBeyondWorkersAndQueue() throws Exception {
        CountDownLatch started = new CountDownLatch(1);
        CountDownLatch release = new CountDownLatch(1);

        try (var service = new BoundedWorkerService(1, 1, Duration.ofSeconds(1))) {
            Future<Integer> running = service.submit(() -> {
                started.countDown();
                release.await();
                return 1;
            });
            assertTrue(started.await(1, TimeUnit.SECONDS));
            Future<Integer> queued = service.submit(() -> 2);

            assertThrows(RejectedExecutionException.class,
                    () -> service.submit(() -> 3));

            release.countDown();
            assertEquals(1, running.get(1, TimeUnit.SECONDS));
            assertEquals(2, queued.get(1, TimeUnit.SECONDS));
            assertEquals(1, service.stats().rejected());
        } finally {
            release.countDown();
        }
    }

    @Test
    void cancellationInterruptsCooperativeTask() throws Exception {
        CountDownLatch started = new CountDownLatch(1);
        CountDownLatch interrupted = new CountDownLatch(1);

        try (var service = new BoundedWorkerService(1, 1, Duration.ofSeconds(1))) {
            Future<Void> future = service.submit(() -> {
                started.countDown();
                try {
                    new CountDownLatch(1).await();
                    return null;
                } catch (InterruptedException expected) {
                    interrupted.countDown();
                    throw expected;
                }
            });
            assertTrue(started.await(1, TimeUnit.SECONDS));
            assertTrue(future.cancel(true));
            assertTrue(interrupted.await(1, TimeUnit.SECONDS));
            assertThrows(CancellationException.class, future::get);
        }
    }
}

    Also test: task exceptions, rejection after close, restoration of interrupt status, queued-task cancellation, metric monotonicity, and absence of worker threads after shutdown.

    11. Tradeoffs¶

    Decision Benefit Cost or risk
    Fixed bounded pool Predictable concurrency and memory Rejects bursts; may underuse variable capacity
    Elastic pool with handoff Handles short bursts without queue delay Thread growth and downstream overload
    Caller-runs Natural producer throttling Unsafe on event loops or while holding locks
    Fail-fast rejection Preserves latency and resources Callers need retry, fallback, or error handling
    Large queue Absorbs brief bursts Stale work, high tail latency, retained memory
    Small queue Fast overload signal More rejection during harmless microbursts
    Platform pool Mature controls for CPU and bounded concurrency Blocking consumes expensive OS threads

    12. Exercises¶

    Exercise 1: explain an idle maximum¶

    A pool has core 8, max 64, and an unbounded LinkedBlockingQueue. Under load it has 8 active workers and 50,000 queued tasks. Why did it not grow to 64, and what is the smallest defensible correction?

    Solution

    ThreadPoolExecutor queues after all core workers are busy. Because the queue accepts every task, the executor never reaches the branch that creates workers above core. If the required concurrency is fixed, set core and max to the measured worker count and use a bounded queue plus explicit rejection. If elasticity is required, use a bounded queue or SynchronousQueue, set a justified max, and cap the downstream dependency separately. Reducing the queue without defining rejection behavior is incomplete.

    Exercise 2: write a safe context wrapper¶

    Wrap a Callable<T> so it installs a request ID and always restores the previous ThreadLocal value.

    Solution 
    static <T> Callable<T> withRequestId(String id, Callable<T> task) {
    Objects.requireNonNull(task);
    return () -> {
        String previous = REQUEST_ID.get();
        try {
            REQUEST_ID.set(id);
            return task.call();
        } finally {
            if (previous == null) {
                REQUEST_ID.remove();
            } else {
                REQUEST_ID.set(previous);
            }
        }
    };
}

    The finally block handles success, exception, and interruption. Restoration, rather than unconditional removal, preserves nested scope.

    Exercise 3: choose a schedule¶

    A cache refresh takes 2 to 20 seconds. The requirement is to wait 30 seconds after each refresh ends before starting another. Choose the API and show failure containment.

    Solution 
    ScheduledFuture<?> refresh = scheduler.scheduleWithFixedDelay(() -> {
    try {
        cache.refresh();
    } catch (Exception failure) {
        metrics.refreshFailure();
        logger.log(System.Logger.Level.ERROR, "refresh failed", failure);
    }
}, 0, 30, TimeUnit.SECONDS);

    Fixed delay matches completion-to-next-start semantics. Catching expected operational failures prevents one failure from suppressing all future executions. Cancellation and scheduler shutdown still stop it.

    13. Interview traps and questions¶

    Traps¶

    • Saying max threads limits an executor that has an unbounded queue.
    • Treating queue capacity as backpressure without defining rejection behavior.
    • Assuming Future.cancel(true) kills arbitrary code.
    • Calling shutdownNow and assuming running tasks have stopped.
    • Swallowing InterruptedException.
    • Ignoring periodic-task suppression after an exception.
    • Using CallerRunsPolicy from an event loop or lock-protected path.
    • Treating executor telemetry as an atomic accounting ledger.
    • Forgetting that pooled ThreadLocal values outlive requests.

    Questions to practice¶

    1. Walk through admission for core 4, max 16, queue 100 at the 1st, 5th, 105th, and 117th simultaneous submissions.
    2. How would you expose overload to an HTTP caller and prevent retry amplification?
    3. Which capacity should dominate: worker threads, queue slots, database connections, or dependency quota?
    4. What is the linearization point for accepted submission and for rejection?
    5. How do graceful shutdown and process-crash recovery differ?
    6. When is a SynchronousQueue better than a bounded buffer?
    7. Why can a long queue reduce throughput even before memory exhaustion?

    Summary¶

    • Executors are admission and lifecycle components, not just thread factories.
    • Queue type determines whether and when a pool can grow beyond its core size.
    • Bound both concurrency and backlog, then make overload explicit.
    • Use Little's Law and dependency limits to establish a measured starting size.
    • Cancellation is cooperative, and shutdown must be a bounded service protocol.
    • Scheduled tasks need explicit cadence, failure, cancellation, and shutdown semantics.
    • Clean ThreadLocal state in lexical finally blocks.
    • Test concurrency with deterministic gates and bounded test timeouts, not sleeps.
