    05. Coordination Primitives¶

    Locks protect state. Coordination primitives control when work may proceed. An interview-quality design distinguishes resource capacity from phase completion, reusable rendezvous, and pairwise handoff instead of using one primitive for every problem.

    Learning goals¶

    By the end of this chapter, you should be able to:

    • distinguish permits from lock ownership;
    • choose among Semaphore, CountDownLatch, CyclicBarrier, Phaser, and Exchanger;
    • model one-shot and reusable coordination explicitly;
    • implement alternating output, zero-even-odd, and H2O grouping;
    • define shared state, invariants, and linearization points for each design;
    • handle interruption without leaking permits or stranding peers;
    • explain broken barriers and recovery policy; and
    • test coordination deterministically without timing guesses.

    Conceptual model¶

    Coordination answers one of four questions:

    Question Primitive
    May another operation enter a capacity-limited region? Semaphore
    Have a fixed number of one-time events completed? CountDownLatch
    Have all fixed participants reached this reusable phase? CyclicBarrier
    Which dynamic participants have reached this phase? Phaser
    Can two peers swap values at a rendezvous? Exchanger

    Every design should identify:

    • Participants: which threads or tasks coordinate.
    • Shared state: counters, queues, phase numbers, or output.
    • Invariant: what must remain true across interleavings.
    • Linearization point: when admission, arrival, or handoff logically occurs.
    • Failure policy: what interruption, timeout, or participant failure means to peers.

    Semaphore: permits are not ownership¶

    A semaphore maintains a permit count. acquire decrements it when positive or waits; release increments it. Unlike a lock, the releasing thread need not be the acquiring thread. That makes a semaphore suitable for capacity and signaling, but dangerous if code assumes ownership.

    Broken: unconditional release¶

    void callRemote() throws InterruptedException {
    try {
        permits.acquire();
        client.call();
    } finally {
        permits.release();
    }
}

    If interruption occurs before acquisition succeeds, finally creates a permit. Capacity silently grows.

    Corrected: release only after successful acquisition¶

    import java.util.concurrent.Semaphore;

final class Bulkhead {
    private final Semaphore permits;

    Bulkhead(int maximumConcurrentCalls) {
        if (maximumConcurrentCalls <= 0) {
            throw new IllegalArgumentException("capacity must be positive");
        }
        permits = new Semaphore(maximumConcurrentCalls);
    }

    <T> T execute(java.util.concurrent.Callable<T> task) throws Exception {
        boolean acquired = false;
        try {
            permits.acquire();
            acquired = true; // Record that successful acquisition already admitted us.
            return task.call();
        } finally {
            if (acquired) {
                permits.release();
            }
        }
    }
}
    • Shared state: semaphore permit count and in-flight calls.
    • Invariant: availablePermits + inFlight = capacity when each operation holds one permit.
    • Linearization point: successful permit acquisition for admission; release for departure.

    A fair semaphore reduces barging for blocking acquisition but costs throughput. Multi-permit acquisition can create head-of-line blocking. availablePermits() is an observation, not a reservation; never check it and then assume a later acquisition will succeed.

    Semaphores do not protect arbitrary invariants

    A binary semaphore can limit entry to one participant, but it has no thread ownership and is not reentrant. Prefer a lock for ownership-based mutual exclusion.

    CountDownLatch: one-shot completion¶

    A latch starts with a non-negative count. await blocks until countDown has reduced the count to zero. It cannot reset.

    import java.util.concurrent.CountDownLatch;

final class ServiceGate {
    private final CountDownLatch ready;

    ServiceGate(int dependencies) {
        ready = new CountDownLatch(dependencies);
    }

    void dependencyReady() {
        ready.countDown(); // Linearizes one completion if count was positive.
    }

    void awaitReady() throws InterruptedException {
        ready.await();
    }
}
    • Shared state: latch count.
    • Invariant: count never increases and never becomes negative.
    • Linearization point: a successful decrement; for await, observation of zero.

    Actions before countDown happen-before actions after another thread successfully returns from await. Additional countDown calls at zero do nothing, which can hide duplicate completion signals. If identity matters, track completed dependency IDs separately.

    Start gate and finish gate¶

    Tests often use one latch to release workers together and another to observe completion:

    var start = new CountDownLatch(1);
var done = new CountDownLatch(workerCount);

for (int i = 0; i < workerCount; i++) {
    executor.submit(() -> {
        try {
            start.await();
            runCase();
        } finally {
            done.countDown();
        }
        return null;
    });
}
start.countDown();
done.await();

    The finally prevents one failed worker from stranding the observer. It does not report the failure; retain futures or collect exceptions separately.

    CyclicBarrier: fixed reusable rendezvous¶

    A cyclic barrier releases a fixed number of parties when all have called await. It then advances to the next generation and can be reused.

    import java.util.concurrent.CyclicBarrier;

var barrier = new CyclicBarrier(3, () -> publishCompletedBatch());

void processPartition() throws Exception {
    loadPartition();
    barrier.await();
    consumePublishedBatch();
}

    The barrier action runs once per generation in the last arriving thread before other participants are released.

    • Shared state: arrival count, generation, and any phase data.
    • Invariant: no participant starts the next phase before all parties complete the current phase.
    • Linearization point: the last arrival trips the barrier and advances its generation.

    Broken barriers¶

    If a waiting participant is interrupted or times out, that generation becomes broken. Other waiters receive BrokenBarrierException; later await calls also fail until reset begins a new generation.

    try {
    barrier.await();
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    cancelWholeRound();
} catch (java.util.concurrent.BrokenBarrierException e) {
    cancelWholeRound();
}

    Do not blindly retry await: the failed participant may never arrive. Decide whether to cancel the round, reconstruct the workers and barrier, or reset only after all old-generation tasks are contained. A reset while old tasks continue can mix logical rounds.

    Phaser: dynamic, multi-phase coordination¶

    A phaser combines a phase number with dynamic registration. Participants register, arrive, and optionally deregister. Unlike CyclicBarrier, its party count can change.

    import java.util.concurrent.Phaser;
import java.util.concurrent.RejectedExecutionException;

final class TwoStagePipeline {
    private final Phaser phaser = new Phaser(1); // Coordinator.

    void submit(Runnable stageOne, Runnable stageTwo,
                java.util.concurrent.Executor executor) {
        phaser.register();
        try {
            executor.execute(() -> {
                try {
                    stageOne.run();
                    phaser.arriveAndAwaitAdvance();
                    stageTwo.run();
                } finally {
                    phaser.arriveAndDeregister();
                }
            });
        } catch (RejectedExecutionException rejected) {
            phaser.arriveAndDeregister();
            throw rejected;
        }
    }

    void runPhases() {
        phaser.arriveAndAwaitAdvance();
        phaser.arriveAndAwaitAdvance();
        phaser.arriveAndDeregister();
    }
}

    This sample assumes submission completes before the coordinator advances. If registration races with phase advance, a task may join a later phase. Close registration through an external lifecycle protocol when phase membership matters. Registration occurs before submission, so rejection must deregister synchronously; otherwise the coordinator waits forever for a task that cannot run.

    The executor must run every admitted party concurrently; a small fixed pool can deadlock with running tasks awaiting queued parties. A stage-one exception currently deregisters that task and allows surviving tasks into stage two: this is a drop-failed-party policy, not an all-inputs-succeeded guarantee. If stage two requires every stage-one output, record shared failure, terminate the phaser, and check termination before consuming results. Never run this pipeline on a direct executor.

    • Shared state: registered, unarrived, and phase counts.
    • Invariant: a phase advances only when every registered party for that phase arrives or deregisters.
    • Linearization point: arrival that reduces unarrived parties to zero and advances phase.

    arriveAndAwaitAdvance is not interruptible. Use awaitAdvanceInterruptibly(phase) when cancellation is required:

    int phase = phaser.arrive();
try {
    phaser.awaitAdvanceInterruptibly(phase);
} catch (InterruptedException e) {
    phaser.forceTermination(); // Policy: cancel this whole pipeline.
    throw e;
}

    Be careful: after arrive, the party has already fulfilled its obligation for that phase. Failure handling must not arrive twice. This example terminates the whole protocol. A design that cancels only one party needs an external lifecycle that deregisters it in a phase where it has not already arrived.

    Exchanger: pairwise handoff¶

    Exchanger<V> pairs two threads. Each supplies a value and receives the other's value. It is useful for double buffering, where a producer hands off a full buffer and receives an empty one.

    import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.Exchanger;

final class BufferHandoff {
    private final Exchanger<List<String>> exchanger = new Exchanger<>();

    List<String> exchange(List<String> mine) throws InterruptedException {
        return exchanger.exchange(mine); // Pairwise handoff linearization point.
    }

    static List<String> emptyBuffer() {
        return new ArrayList<>();
    }
}

    The invariant is exclusive logical ownership after each successful exchange: each buffer belongs to one side. Timeout or interruption means no successful exchange for that caller. It is a poor fit for more than two participants, unbalanced arrival rates, or cases where a queue should absorb bursts.

    Pattern: alternating printer¶

    Two semaphores encode whose turn it is. One initial permit lets the first printer run; the other starts at zero.

    import java.util.function.IntConsumer;
import java.util.concurrent.Semaphore;

final class AlternatingPrinter {
    private final Semaphore oddTurn = new Semaphore(1);
    private final Semaphore evenTurn = new Semaphore(0);
    private final int maximum;

    AlternatingPrinter(int maximum) {
        if (maximum < 0 || maximum > Integer.MAX_VALUE - 2)
            throw new IllegalArgumentException("maximum out of range");
        this.maximum = maximum;
    }

    void printOdd(IntConsumer output) throws InterruptedException {
        for (int value = 1; value <= maximum; value += 2) {
            oddTurn.acquire();
            try {
                output.accept(value); // Output linearization point.
            } finally {
                evenTurn.release();
            }
        }
    }

    void printEven(IntConsumer output) throws InterruptedException {
        for (int value = 2; value <= maximum; value += 2) {
            evenTurn.acquire();
            try {
                output.accept(value); // Output linearization point.
            } finally {
                oddTurn.release();
            }
        }
    }
}
    • Shared state: turn permits and the output sink.
    • Invariant: before each output, exactly the required side can proceed; values appear in ascending order.
    • Linearization point: each call to output.accept.

    The finally permits one more peer turn after callback failure; it does not prevent that peer from becoming stranded on its following turn. Both callbacks must return normally for this compact protocol. A coordinator must observe any failure and cancel both tasks. Interruption before handoff can also strand the peer. Limit maximum to 0..Integer.MAX_VALUE-2 here so the int step cannot wrap; the same bound applies to n below.

    Pattern: zero-even-odd¶

    One thread prints zero before every integer. Separate semaphores make the legal transitions explicit.

    import java.util.concurrent.Semaphore;
import java.util.function.IntConsumer;

final class ZeroEvenOdd {
    private final int n;
    private final Semaphore zero = new Semaphore(1);
    private final Semaphore odd = new Semaphore(0);
    private final Semaphore even = new Semaphore(0);

    ZeroEvenOdd(int n) {
        if (n < 0 || n > Integer.MAX_VALUE - 2)
            throw new IllegalArgumentException("n out of range");
        this.n = n;
    }

    void zero(IntConsumer output) throws InterruptedException {
        for (int value = 1; value <= n; value++) {
            zero.acquire();
            output.accept(0);
            (value % 2 == 0 ? even : odd).release();
        }
    }

    void odd(IntConsumer output) throws InterruptedException {
        for (int value = 1; value <= n; value += 2) {
            odd.acquire();
            output.accept(value);
            zero.release();
        }
    }

    void even(IntConsumer output) throws InterruptedException {
        for (int value = 2; value <= n; value += 2) {
            even.acquire();
            output.accept(value);
            zero.release();
        }
    }
}
    • Shared state: the three permit counts and output.
    • Invariant: legal states cycle from zero-enabled to exactly one parity-enabled and back.
    • Linearization point: each output callback.

    In an interview, mention failure semantics. The compact solution assumes callbacks do not fail and all three tasks remain alive. Production code should coordinate cancellation because permit protocols do not automatically propagate failure.

    Pattern: H2O grouping¶

    The requirement is not merely "at most two hydrogen threads and one oxygen thread run." Output must be partitionable into complete groups containing exactly two H and one O. A barrier closes each molecule before permits for the next one are released.

    import java.util.concurrent.Phaser;
import java.util.concurrent.Semaphore;
import java.util.Objects;

final class H2O {
    private final Semaphore hydrogenSlots = new Semaphore(2, true);
    private final Semaphore oxygenSlots = new Semaphore(1, true);
    private final Phaser molecule = new Phaser(3);

    void hydrogen(Runnable releaseHydrogen) throws InterruptedException {
        Objects.requireNonNull(releaseHydrogen, "releaseHydrogen");
        hydrogenSlots.acquire();
        releaseHydrogen.run();
        molecule.arriveAndAwaitAdvance();
    }

    void oxygen(Runnable releaseOxygen) throws InterruptedException {
        Objects.requireNonNull(releaseOxygen, "releaseOxygen");
        oxygenSlots.acquire();
        releaseOxygen.run();
        molecule.arriveAndAwaitAdvance();
        hydrogenSlots.release(2);
        oxygenSlots.release();
    }
}

    This compact interview solution has an explicit precondition: each callback is a short, non-blocking output action that does not throw. Interruption can abort semaphore acquisition before a slot is owned. After admission there is no interruptible wait: Phaser.arriveAndAwaitAdvance completes the participant's generation even when its interrupt flag is set, so interruption cannot leak a slot or strand peers. If callbacks can fail or block, this is not a sufficient service design; use a generation object that buffers output and atomically commits or aborts all three participants instead of pretending a partial molecule can be repaired.

    • Shared state: two slot semaphores, one phaser generation, and output.
    • Invariant: only two hydrogen and one oxygen participant enter a generation; the next generation receives no slots until all three current callbacks finish and arrive.
    • Linearization point: the third barrier arrival commits the molecule group. Individual character output occurs earlier and should remain buffered if externally visible atomic grouping is required.

    Group completion versus output order

    The barrier guarantees groups of two hydrogen participants and one oxygen participant. It does not require HHO order within a group. If exact order is required, model another turn protocol or buffer the three symbols and publish the completed group in the barrier action.

    One-shot versus reusable coordination¶

    Primitive Parties Reusable Ownership Typical failure effect
    Semaphore dynamic yes no caller must avoid permit leak
    CountDownLatch fixed count no no missing countdown waits forever
    CyclicBarrier fixed parties yes no generation becomes broken
    Phaser dynamic parties yes no application decides termination
    Exchanger pairs yes no unmatched peer waits or times out

    Choose from lifecycle semantics, not surface syntax. A latch cannot represent repeated rounds. A barrier should not model a capacity pool. A semaphore does not tell you that a whole cohort has completed.

    Interruption and cancellation rules¶

    1. Decide whether interruption cancels one participant or the whole protocol.
    2. Release only resources that were definitely acquired.
    3. Do not count down a success latch for work that did not satisfy its contract; use a separate completion latch if failures also unblock an observer.
    4. Treat a broken barrier as a failed generation, not a transient wakeup.
    5. Deregister abandoned phaser parties so surviving participants can advance.
    6. Bound waits at system boundaries and surface timeout as a domain outcome.
    7. Retain futures so coordinator code can observe worker failures.

    Deterministic tests¶

    The output sequence itself is the assertion for turn-taking algorithms. Launch tasks together and place one timeout around completion.

    import static org.junit.jupiter.api.Assertions.assertEquals;

import java.util.ArrayList;
import java.util.Collections;
import java.util.List;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;
import org.junit.jupiter.api.Test;

class CoordinationTest {
    @Test
    void alternatesOddAndEven() throws Exception {
        var printer = new AlternatingPrinter(6);
        List<Integer> output = Collections.synchronizedList(new ArrayList<>());
        var start = new CountDownLatch(1);

        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            var odd = executor.submit(() -> {
                start.await();
                printer.printOdd(output::add);
                return null;
            });
            var even = executor.submit(() -> {
                start.await();
                printer.printEven(output::add);
                return null;
            });
            start.countDown();
            odd.get(1, TimeUnit.SECONDS);
            even.get(1, TimeUnit.SECONDS);
        }

        assertEquals(List.of(1, 2, 3, 4, 5, 6), output);
    }

    @Test
    void formsCompleteMolecules() throws Exception {
        var h2o = new H2O();
        List<Character> output = Collections.synchronizedList(new ArrayList<>());
        List<Character> input = List.of('O', 'H', 'H', 'H', 'O', 'H');

        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            var futures = input.stream().map(atom -> executor.submit(() -> {
                if (atom == 'H') {
                    h2o.hydrogen(() -> output.add('H'));
                } else {
                    h2o.oxygen(() -> output.add('O'));
                }
                return null;
            })).toList();
            for (var future : futures) {
                future.get(1, TimeUnit.SECONDS);
            }
        }

        for (int start = 0; start < output.size(); start += 3) {
            List<Character> group = new ArrayList<>(output.subList(start, start + 3));
            Collections.sort(group);
            assertEquals(List.of('H', 'H', 'O'), group);
        }
    }
}

    The H2O test validates each contiguous group, not only global totals. Global totals would miss an illegal output such as HHHHOO. Oxygen alone releases the next group's slots after phase advance; onAdvance is too early because the new phase has not yet been installed. Interrupting an atom before admission can still leave an insufficient mix; the caller must supply replacement participants or terminate the whole exercise. See the Phaser lifecycle contract.

    These test sketches need process-level isolation for a broken non-interruptible barrier: a timed Future.get does not bound try-with-resources executor closure. Cancel cooperative tasks in finally, release test gates, and use a child-JVM timeout for deliberately broken monitor/barrier code.

    Common pitfalls¶

    • Releasing a semaphore permit after failed or interrupted acquisition.
    • Treating availablePermits() as an atomic admission check.
    • Using a semaphore as a reentrant ownership lock.
    • Forgetting that CountDownLatch is one-shot.
    • Hiding worker failure by counting down only a completion signal.
    • Retrying a broken barrier without rebuilding the logical round.
    • Registering with a phaser after the intended phase has already advanced.
    • Arriving twice during phaser interruption cleanup.
    • Using an exchanger when producers and consumers need buffering.
    • Validating only aggregate H2O counts instead of group boundaries.
    • Ignoring the fact that one failed turn-taking participant can strand peers.

    Exercises¶

    Exercise 1: bounded, timed bulkhead¶

    Implement a bulkhead that rejects an operation if no permit is available within a duration. Ensure interruption does not change capacity.

    Complete solution 
    final class TimedBulkhead {
    private final java.util.concurrent.Semaphore permits;

    TimedBulkhead(int capacity) {
        permits = new java.util.concurrent.Semaphore(capacity);
    }

    <T> java.util.Optional<T> execute(
            java.time.Duration timeout,
            java.util.concurrent.Callable<T> task) throws Exception {
        boolean acquired = permits.tryAcquire(
                timeout.toNanos(), java.util.concurrent.TimeUnit.NANOSECONDS);
        if (!acquired) {
            return java.util.Optional.empty();
        }
        try {
            return java.util.Optional.ofNullable(task.call());
        } finally {
            permits.release();
        }
    }
}

    The permit is released only on the path where tryAcquire returned true. Admission linearizes at successful acquisition. Rejection linearizes when timed acquisition reports failure. Optional cannot distinguish a successful null result from rejection, so a production API should prohibit null or return a dedicated result type.

    Exercise 2: reusable three-stage workers¶

    Three fixed workers must all finish stage A before any starts stage B, and all finish B before any starts C. Choose and use a primitive.

    Complete solution 
    final class ThreeStageWorker implements java.util.concurrent.Callable<Void> {
    private final java.util.concurrent.CyclicBarrier barrier;
    private final Runnable stageA;
    private final Runnable stageB;
    private final Runnable stageC;

    ThreeStageWorker(java.util.concurrent.CyclicBarrier barrier,
                     Runnable stageA, Runnable stageB, Runnable stageC) {
        this.barrier = barrier;
        this.stageA = stageA;
        this.stageB = stageB;
        this.stageC = stageC;
    }

    @Override
    public Void call() throws Exception {
        stageA.run();
        barrier.await();
        stageB.run();
        barrier.await();
        stageC.run();
        return null;
    }
}

    The barrier is reusable and party count is fixed. Each last arrival advances a generation and is the phase transition's linearization point. If any worker fails before arrival, cancel all peers; otherwise they wait forever. Futures and a coordinator should implement that cancellation policy.

    Exercise 3: repair a flaky latch test¶

    A test starts workers, sleeps for 100 ms, and checks a counter. Replace timing with explicit coordination.

    Complete solution 
    var start = new java.util.concurrent.CountDownLatch(1);
var done = new java.util.concurrent.CountDownLatch(workerCount);
var counter = new java.util.concurrent.atomic.AtomicInteger();

try (var executor = java.util.concurrent.Executors
        .newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < workerCount; i++) {
        executor.submit(() -> {
            try {
                start.await();
                counter.incrementAndGet();
            } finally {
                done.countDown();
            }
            return null;
        });
    }
    start.countDown();
    if (!done.await(1, java.util.concurrent.TimeUnit.SECONDS)) {
        throw new AssertionError("workers did not finish");
    }
}
org.junit.jupiter.api.Assertions.assertEquals(workerCount, counter.get());

    The start latch creates a defined release point. The done latch proves every worker reached completion. The timeout detects a defect rather than attempting to schedule the workers.

    Summary¶

    • Semaphores represent permits, not thread ownership.
    • Latches represent one-shot completion; barriers and phasers represent phases.
    • A broken barrier is a failed generation that needs an explicit recovery policy.
    • Phasers support dynamic registration but require careful lifecycle control.
    • Exchangers provide pairwise handoff, not buffering.
    • Turn-taking algorithms are small state machines whose permits encode legal transitions.
    • H2O grouping needs a generation boundary, not only aggregate capacity limits.
    • Interruption handling must preserve permit counts, party counts, and peer liveness.
    • Deterministic tests use explicit start and completion gates plus bounded hang detection.
