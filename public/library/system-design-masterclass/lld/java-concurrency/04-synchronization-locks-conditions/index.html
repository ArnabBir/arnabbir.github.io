    04. Synchronization, Locks, and Conditions¶

    Mutual exclusion is not the goal by itself. The goal is to preserve an invariant while making state changes visible as one atomic operation. This chapter develops that reasoning from intrinsic monitors to explicit locks, conditions, read-write locks, and optimistic reads.

    Learning goals¶

    By the end of this chapter, you should be able to:

    • identify the shared state and invariant before choosing a lock;
    • explain monitor ownership, reentrancy, visibility, and linearization points;
    • use wait, notify, and notifyAll with guarded loops;
    • implement bounded queues with both a monitor and Condition objects;
    • select lock, lockInterruptibly, tryLock, and fairness deliberately;
    • compare ReadWriteLock with StampedLock;
    • prevent deadlock through ordering, granularity, and encapsulation; and
    • write deterministic concurrency tests without relying on sleep.

    Conceptual model: protect transitions, not fields¶

    A lock protects a protocol over shared state. State may span several fields, and an invariant usually relates them.

    For a bounded queue:

    • Shared state: the element array, read index, write index, and count.
    • Invariant: 0 <= count <= capacity; exactly count logical slots contain queued elements; indices remain in range.
    • Linearization point for put: while holding the lock, the element is stored and count is incremented.
    • Linearization point for take: while holding the lock, the element is removed and count is decremented.

    The linearization point is the instant at which a concurrent operation appears to take effect. Naming it makes an LLD answer testable. If the fields are guarded by different locks, or callers can mutate the backing array, no single atomic transition exists.

    Happens-before

    An unlock of a monitor or Lock happens-before a later successful lock of the same object. This gives both mutual exclusion and visibility. A lock on one object does not publish state to code locking another object.

    Intrinsic monitors and synchronized¶

    Every Java object can act as an intrinsic monitor. A thread entering a synchronized method locks this; a static synchronized method locks the Class object; a synchronized block locks its explicit monitor.

    Broken: check and act under different locks¶

    final class BrokenInventory {
    private int remaining = 1;

    synchronized boolean inStock() {
        return remaining > 0;
    }

    void reserve() {
        if (inStock()) {
            remaining--; // Outside the monitor.
        }
    }
}

    Two threads can both observe stock and decrement. Synchronizing an accessor does not make a multi-call workflow atomic.

    Corrected: one transition under one monitor¶

    final class Inventory {
    private int remaining;

    Inventory(int initialStock) {
        if (initialStock < 0) {
            throw new IllegalArgumentException("negative stock");
        }
        remaining = initialStock;
    }

    synchronized boolean tryReserve(int quantity) {
        if (quantity <= 0) {
            throw new IllegalArgumentException("quantity must be positive");
        }
        if (remaining < quantity) {
            return false;
        }
        remaining -= quantity; // Linearization point.
        return true;
    }

    synchronized int remaining() {
        return remaining;
    }
}
    • Shared state: remaining.
    • Invariant: remaining >= 0.
    • Linearization point: remaining -= quantity.

    Keep the monitor private in effect: do not call unknown code while holding it, and do not expose mutable protected state.

    Reentrancy¶

    Java monitors and ReentrantLock are reentrant. A thread that already owns a lock may acquire it again. The lock tracks a hold count and becomes available only after matching releases.

    final class Account {
    private long cents;

    synchronized void credit(long amount) {
        requirePositive(amount); // Reentrant call on the same receiver.
        cents = Math.addExact(cents, amount);
    }

    private synchronized void requirePositive(long amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("amount must be positive");
        }
    }
}

    Reentrancy prevents self-deadlock during nested synchronized calls. It does not make a compound operation across two objects atomic, and it can hide callbacks that execute while an outer lock remains held.

    Guarded suspension with wait and notification¶

    wait, notify, and notifyAll operate on an object's wait set. The caller must own that object's monitor.

    wait atomically releases the monitor and suspends the thread. Before returning, it reacquires the monitor. It releases only this monitor, not any other locks held by the caller. Entering a synchronized block is not interruptible, so the monitor-based queue cannot promise prompt cancellation while blocked on monitor entry. notify moves one arbitrary waiter toward lock reacquisition; notifyAll does so for all waiters. Neither transfers ownership immediately.

    Broken: testing once and waiting on if¶

    synchronized E take() throws InterruptedException {
    if (count == 0) {
        wait();
    }
    return remove();
}

    This fails because:

    • a thread may wake spuriously;
    • another consumer may remove the item before this thread reacquires the monitor;
    • a notification means "state may have changed," not "your predicate is true."

    The rule is always:

    synchronized (monitor) {
    while (!predicate()) {
        monitor.wait();
    }
    changeState();
}

    Monitor-based bounded queue¶

    import java.util.Objects;

public final class MonitorBoundedQueue<E> {
    private final Object[] elements;
    private int head;
    private int tail;
    private int size;

    public MonitorBoundedQueue(int capacity) {
        if (capacity <= 0) {
            throw new IllegalArgumentException("capacity must be positive");
        }
        elements = new Object[capacity];
    }

    public synchronized void put(E element) throws InterruptedException {
        Objects.requireNonNull(element, "element");
        while (size == elements.length) {
            wait();
        }
        elements[tail] = element;
        tail = (tail + 1) % elements.length;
        size++; // Linearization point.
        notifyAll();
    }

    public synchronized E take() throws InterruptedException {
        while (size == 0) {
            wait();
        }
        @SuppressWarnings("unchecked")
        E element = (E) elements[head];
        elements[head] = null;
        head = (head + 1) % elements.length;
        size--; // Linearization point.
        notifyAll();
        return element;
    }

    public synchronized int size() {
        return size;
    }
}

    Both producers and consumers share one wait set. notifyAll avoids waking only producers when the queue is full or only consumers when it is empty. Awakened threads recheck their predicates in while loops. The cost is unnecessary wakeups.

    Interruption is part of the contract

    wait throws InterruptedException after the thread reacquires the monitor. Do not swallow it. A low-level blocking method should usually propagate it. Code that cannot propagate should restore status with Thread.currentThread().interrupt() and terminate or return a documented cancellation result.

    ReentrantLock and Condition¶

    ReentrantLock separates locking from lexical scope and adds interruptible acquisition, timed acquisition, optional fairness, and multiple condition queues. That flexibility creates a new obligation: every successful acquisition must have a finally-guarded unlock.

    Broken: leaked lock on failure¶

    lock.lock();
update();
lock.unlock();

    If update throws, all future callers may block forever.

    Correct lock shape¶

    lock.lock();
try {
    update();
} finally {
    lock.unlock();
}

    Do not place lock.lock() inside the try: if an interruptible or custom acquisition fails before ownership, finally must not unlock a lock the thread does not own.

    Condition-based bounded queue¶

    import java.util.Objects;
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

public final class ConditionBoundedQueue<E> {
    private final Object[] elements;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notEmpty = lock.newCondition();
    private final Condition notFull = lock.newCondition();
    private int head;
    private int tail;
    private int size;

    public ConditionBoundedQueue(int capacity) {
        if (capacity <= 0) {
            throw new IllegalArgumentException("capacity must be positive");
        }
        elements = new Object[capacity];
    }

    public void put(E element) throws InterruptedException {
        Objects.requireNonNull(element, "element");
        lock.lockInterruptibly();
        try {
            while (size == elements.length) {
                notFull.await();
            }
            elements[tail] = element;
            tail = (tail + 1) % elements.length;
            size++; // Linearization point.
            notEmpty.signal();
        } finally {
            lock.unlock();
        }
    }

    public E take() throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (size == 0) {
                notEmpty.await();
            }
            @SuppressWarnings("unchecked")
            E element = (E) elements[head];
            elements[head] = null;
            head = (head + 1) % elements.length;
            size--; // Linearization point.
            notFull.signal();
            return element;
        } finally {
            lock.unlock();
        }
    }

    public int size() {
        lock.lock();
        try {
            return size;
        } finally {
            lock.unlock();
        }
    }
}

    The invariants and linearization points match the monitor implementation. Two condition queues make signaling selective. Conditions still permit spurious wakeups, so await belongs in a guarded while loop.

    Acquisition policies¶

    Interruptible locking¶

    Use lockInterruptibly() when waiting for a lock is cancellable. A request with an expired deadline should not remain stuck behind an owner.

    lock.lockInterruptibly();
try {
    performShortTransition();
} finally {
    lock.unlock();
}

    Plain lock() does not abort acquisition on interruption. The thread's interrupt status is restored after it eventually acquires the lock.

    Timed tryLock¶

    Timed acquisition bounds waiting and can help avoid deadlock when several locks cannot share a global order.

    if (!lock.tryLock(50, java.util.concurrent.TimeUnit.MILLISECONDS)) {
    return false;
}
try {
    return performShortTransition();
} finally {
    lock.unlock();
}

    Untimed tryLock() is immediate. A failed acquisition changes no protected state and is not a linearization point for the requested mutation; it linearizes as a failed attempt at the read of lock availability.

    Fairness¶

    new ReentrantLock(true) prefers the longest-waiting contender under contention. It reduces starvation risk but often lowers throughput by reducing barging and increasing context switches. Fairness does not imply scheduler-level strict FIFO, and untimed tryLock() may barge even on a fair lock. Start non-fair unless the requirement is bounded overtaking or starvation resistance.

    Read-heavy state¶

    ReadWriteLock¶

    ReentrantReadWriteLock allows concurrent readers and one exclusive writer. It helps only when reads are frequent and long enough to offset bookkeeping. Tiny getters often perform better with a plain lock or immutable snapshot.

    import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.locks.ReentrantReadWriteLock;

final class PriceBook {
    private final Map<String, Long> cents = new HashMap<>();
    private final ReentrantReadWriteLock rw = new ReentrantReadWriteLock();

    long priceOf(String sku) {
        rw.readLock().lock();
        try {
            Long value = cents.get(sku);
            if (value == null) {
                throw new IllegalArgumentException("unknown sku");
            }
            return value;
        } finally {
            rw.readLock().unlock();
        }
    }

    void setPrice(String sku, long value) {
        if (value < 0) {
            throw new IllegalArgumentException("negative price");
        }
        rw.writeLock().lock();
        try {
            cents.put(sku, value); // Linearization point.
        } finally {
            rw.writeLock().unlock();
        }
    }
}
    • Shared state: the mutable map.
    • Invariant: every stored price is non-negative.
    • Linearization point: put for writes; successful map read while the read lock is held for reads.

    Lock upgrading from read to write is unsafe with ReentrantReadWriteLock: two readers can both wait forever for a write lock while retaining read locks. Release the read lock, acquire the write lock, and recheck the predicate. Downgrading is possible by acquiring the read lock before releasing the write lock.

    StampedLock optimistic reads¶

    StampedLock is not reentrant. Its optimistic read does not lock; it copies state and then validates that no writer acquired the lock during the copy.

    import java.util.concurrent.locks.StampedLock;

final class Point {
    private final StampedLock lock = new StampedLock();
    private double x;
    private double y;

    void move(double dx, double dy) {
        long stamp = lock.writeLock();
        try {
            x += dx;
            y += dy; // The pair becomes visible as one write transition.
        } finally {
            lock.unlockWrite(stamp);
        }
    }

    double distanceFromOrigin() {
        long stamp = lock.tryOptimisticRead();
        double currentX = x;
        double currentY = y;
        if (!lock.validate(stamp)) {
            stamp = lock.readLock();
            try {
                currentX = x;
                currentY = y;
            } finally {
                lock.unlockRead(stamp);
            }
        }
        return Math.hypot(currentX, currentY);
    }
}

    Validation must occur after all fields are copied. A failed validation discards the snapshot and retries under a read lock. Do not perform irreversible actions, dereference temporarily inconsistent object graphs, or call unknown code before validation. StampedLock has no ownership concept, so the correct stamp and unlock mode are essential.

    Granularity, ordering, and encapsulation¶

    Choice Benefit Cost or risk
    one coarse lock simple invariant and ordering unrelated operations contend
    striped locks parallelism across keys cross-stripe operations need ordering
    per-entry lock high concurrency lifecycle, memory, and lock-map races
    read-write lock parallel readers overhead and writer starvation policy
    optimistic read reader avoids acquisition validation and fallback complexity

    For multiple locks, define one total order and use it everywhere. Account transfers can order by immutable account ID. Equal IDs require one lock, not locking the same non-reentrant mechanism twice.

    static void transfer(AccountLocking from, AccountLocking to, long amount) {
    AccountLocking first = from.id() < to.id() ? from : to;
    AccountLocking second = from.id() < to.id() ? to : from;
    first.lock();
    second.lock();
    try {
        from.debitUnderLock(amount);
        to.creditUnderLock(amount);
    } finally {
        second.unlock();
        first.unlock();
    }
}

    The cross-account invariant is conservation: total balance is unchanged by a transfer. The linearization point is the completed debit-and-credit transition while both locks are held. In production code, hide lock, debitUnderLock, and creditUnderLock behind a package-private coordinator so callers cannot violate the protocol.

    This sketch requires distinct immutable IDs for distinct account objects, positive amounts, sufficient funds, and destination overflow validation before either mutation. Both mutations must be non-throwing after validation; locks do not roll back a debit when credit throws. Readers requiring a pair snapshot must acquire both locks in the same order, not call two individually locked getters. A self-transfer must be handled before acquiring two locks.

    Avoid these encapsulation leaks:

    • returning the mutable collection guarded by the lock;
    • using an interned string, boxed primitive, class object, or caller-provided object as a monitor;
    • exposing methods that require callers to remember a lock;
    • calling listeners, remote services, or overridable methods while locked;
    • changing which lock guards a field across methods.

    Deterministic tests¶

    Concurrency tests should establish ordering with latches, barriers, futures, or observable states. Thread.sleep is neither an assertion nor a reliable scheduler.

    import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertFalse;

import java.time.Duration;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.Executors;
import org.junit.jupiter.api.Test;

class MonitorBoundedQueueTest {
    @Test
    void producerBlocksUntilConsumerCreatesCapacity() throws Exception {
        var queue = new MonitorBoundedQueue<Integer>(1);
        queue.put(10);
        var entered = new CountDownLatch(1);

        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            var blockedPut = executor.submit(() -> {
                entered.countDown();
                queue.put(20);
                return null;
            });

            entered.await();
            assertFalse(blockedPut.isDone());
            assertEquals(10, queue.take());
            blockedPut.get();
            assertEquals(20, queue.take());
        }
    }

    @Test
    void waitingConsumerRespondsToInterruption() throws Exception {
        var queue = new ConditionBoundedQueue<Integer>(1);
        var started = new CountDownLatch(1);

        Thread consumer = Thread.ofVirtual().start(() -> {
            started.countDown();
            try {
                queue.take();
                throw new AssertionError("take should not complete");
            } catch (InterruptedException expected) {
                // Expected termination path.
            }
        });

        started.await();
        consumer.interrupt();
        consumer.join(Duration.ofSeconds(1));
        assertFalse(consumer.isAlive());
    }
}

    isDone() immediately after a latch is useful here because the queue is already full and no consumer exists; completion would violate the queue contract. A timeout belongs at the test boundary to fail a hang, not to manufacture ordering.

    The examples are test sketches, not hang-safe harnesses: bound entered.await and Future.get, capture raw-thread failures through a future or error queue, and release/cancel tasks before closing an executor. Executor close() may otherwise wait forever after a timed assertion fails. Use child-JVM isolation when deliberately testing non-interruptible monitor deadlock.

    Common pitfalls¶

    • Treating a thread-safe field or getter as proof that a compound action is safe.
    • Using if around wait or await instead of a guarded while loop.
    • Calling wait or signal without owning the corresponding monitor or lock.
    • Assuming notify selects the waiter whose predicate became true.
    • Forgetting finally around explicit lock release.
    • Swallowing interruption and continuing an operation with a cancelled caller.
    • Holding locks across I/O, callbacks, or another subsystem's lock.
    • Upgrading a read lock directly to a write lock.
    • Using an optimistic snapshot before validating its stamp.
    • Splitting one invariant across independently acquired locks.

    Exercises¶

    Exercise 1: add timed offer¶

    Add boolean offer(E element, Duration timeout) to ConditionBoundedQueue. It must tolerate spurious wakeups and preserve the remaining timeout.

    Complete solution 
    public boolean offer(E element, java.time.Duration timeout)
        throws InterruptedException {
    Objects.requireNonNull(element, "element");
    if (timeout.isNegative()) {
        throw new IllegalArgumentException("negative timeout");
    }
    long budgetNanos = saturatedNanos(timeout);
    long startedNanos = System.nanoTime();

    if (!lock.tryLock(budgetNanos, java.util.concurrent.TimeUnit.NANOSECONDS)) {
        return false;
    }
    try {
        while (size == elements.length) {
            long remaining = remainingNanos(startedNanos, budgetNanos);
            if (remaining == 0L) {
                return false;
            }
            notFull.awaitNanos(remaining);
        }
        elements[tail] = element;
        tail = (tail + 1) % elements.length;
        size++;
        notEmpty.signal();
        return true;
    } finally {
        lock.unlock();
    }
}

private static long saturatedNanos(java.time.Duration timeout) {
    try {
        return timeout.toNanos();
    } catch (ArithmeticException tooLarge) {
        return Long.MAX_VALUE;
    }
}

private static long remainingNanos(long startedNanos, long budgetNanos) {
    long elapsed = System.nanoTime() - startedNanos;
    return elapsed <= 0L ? budgetNanos
            : elapsed >= budgetNanos ? 0L : budgetNanos - elapsed;
}

    Lock acquisition and condition waiting consume the same timeout. Recomputing from monotonic elapsed time prevents spurious wakeups from restarting the budget, and avoids overflow from constructing an absolute nanosecond deadline. The insertion and size++ form the successful operation's linearization point. Timeout failure changes no queue state. As with the key pool, this bounds waiting rather than enforcing a deadline-wins result: if space is available after delayed reacquisition, this implementation may still insert.

    Exercise 2: repair a two-lock transfer¶

    Two threads transfer in opposite directions and sometimes deadlock. Define a locking protocol and state its invariant.

    Complete solution 
    static boolean transfer(AccountLocking from, AccountLocking to, long amount) {
    if (amount <= 0) throw new IllegalArgumentException("positive amount required");
    if (from == to) {
        return true;
    }
    AccountLocking first = from.id() < to.id() ? from : to;
    AccountLocking second = from.id() < to.id() ? to : from;

    first.lock();
    second.lock();
    try {
        if (from.balanceUnderLock() < amount) {
            return false;
        }
        Math.addExact(to.balanceUnderLock(), amount);
        from.debitUnderLock(amount);
        to.creditUnderLock(amount);
        return true;
    } finally {
        second.unlock();
        first.unlock();
    }
}

    All callers acquire by immutable ID, eliminating a circular wait. Shared state is both balances. The invariants are non-negative balances and conservation of their sum for successful transfers. The successful linearization point is completion of the paired mutations while both locks remain held. A failed transfer linearizes at the insufficient-funds check.

    Exercise 3: explain optimistic-read safety¶

    Why is computing Math.hypot after validation preferable to doing arbitrary work before validation?

    Complete solution

    Before validation, copied fields may represent different write epochs. Pure local computation is harmless but may be wasted. Arbitrary work can publish, persist, or act on an invalid snapshot and cannot be undone by falling back to a read lock. Copy the minimum primitive or safely dereferenceable state, validate, retry under a read lock if needed, and only then perform side effects.

    Summary¶

    • A lock protects an invariant and its state transition, not an isolated variable.
    • Intrinsic monitors are reentrant and provide visibility through monitor release and acquisition.
    • wait and await release the lock, may wake spuriously, and require guarded loops.
    • Conditions separate wait sets; monitor code often needs notifyAll when predicates differ.
    • Explicit locks add cancellation, timeout, fairness, and condition choices at the cost of manual release.
    • Read-write and stamped locks help only when workload shape justifies their complexity.
    • Stable lock ordering, small critical sections, and private ownership prevent many deadlocks.
    • Deterministic tests control phases with synchronization primitives and reserve timeouts for hang detection.
