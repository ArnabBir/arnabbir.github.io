    Threads, Tasks, and Lifecycle¶

    A thread is an execution path scheduled by the runtime and operating system. A task is a unit of work. Keeping those concepts separate lets a design change execution policy without rewriting business logic.

    Learning goals¶

    After this chapter, you should be able to:

    • distinguish processes, threads, concurrency, and parallelism;
    • explain Java thread states without treating them as an application state machine;
    • use start, join, sleep, interruption, and daemon status correctly;
    • separate task definitions with Runnable or Callable from thread creation;
    • choose execution strategies for CPU-bound and I/O-bound work;
    • define lifecycle, failure, cancellation, and shutdown behavior;
    • explain Java 21 virtual-thread caveats at interview depth.

    1. Process, thread, and task¶

    A process is an operating-system isolation boundary with its own virtual address space and resources. Processes communicate through mechanisms such as sockets, pipes, files, or shared memory. A crash or memory corruption is usually contained more strongly across processes than across threads.

    Threads inside one Java process share the heap and process resources. Each thread has its own call stack, program counter, and execution state. Sharing makes communication cheap, but an unsafely shared object can be corrupted by any participating thread.

    Concept Owns Shares Typical design concern
    Process Address space, OS identity, resource limits Explicit IPC endpoints Isolation, deployment, crash boundary
    Thread Stack, instruction position, scheduling state Heap and process resources Races, blocking, scheduling, lifecycle
    Task Inputs, logic, result or failure Depends on captured references Cancellation, idempotency, execution policy

    In Java, creating new Thread(task) binds one task to one thread directly. Submitting a task to an ExecutorService separates what should run from where and when it runs.

    2. Concurrency is not parallelism¶

    Concurrency means multiple tasks can make progress over overlapping time. Parallelism means multiple computations execute at the same physical instant, usually on different cores.

    One core can run concurrent tasks by time-slicing. Many cores can run parallel tasks. A concurrent program is not necessarily faster: coordination, cache misses, allocation, and context switching can dominate.

    Concurrent on one core:  A A | B B | A | B B | A
Parallel on two cores:   A A A A A
                         B B B B B

    Interview answers should connect the goal to the workload:

    • Use concurrency to keep serving other work while one task waits.
    • Use parallelism to reduce elapsed time for divisible CPU computation.
    • Use isolation even when throughput is unchanged, for example a dedicated thread for a single-writer state machine.

    3. Java thread states¶

    Thread.State reports six JVM-level states:

    State Meaning Common cause
    NEW Constructed but not started new Thread(...)
    RUNNABLE Eligible to run or running in the JVM Computation, native execution, or scheduler-ready
    BLOCKED Waiting to enter a synchronized monitor Another thread owns that monitor
    WAITING Waiting indefinitely for a defined action Object.wait(), Thread.join(), LockSupport.park()
    TIMED_WAITING Waiting up to a deadline sleep, timed join, timed wait, timed park
    TERMINATED run completed normally or abruptly Return or uncaught exception 
    stateDiagram-v2
    [*] --> NEW
    NEW --> RUNNABLE: start
    RUNNABLE --> BLOCKED: monitor unavailable
    BLOCKED --> RUNNABLE: monitor acquired
    RUNNABLE --> WAITING: indefinite wait or join
    WAITING --> RUNNABLE: notification, completion, interrupt
    WAITING --> BLOCKED: Object.wait must reacquire monitor
    RUNNABLE --> TIMED_WAITING: sleep or timed wait
    TIMED_WAITING --> RUNNABLE: timeout, notification, interrupt
    TIMED_WAITING --> BLOCKED: timed Object.wait must reacquire monitor
    RUNNABLE --> TERMINATED: run returns or throws
    TERMINATED --> [*]

    This is an observation model, not a protocol for coordinating application logic. A sampled state may change immediately. RUNNABLE does not prove that a thread is on a CPU, and an I/O implementation may report states differently. Never spin until another thread's state equals WAITING as the production coordination mechanism.

    4. start() is not run()¶

    Broken code:

    Thread worker = new Thread(() -> importFile(), "import-worker");
worker.run();
System.out.println("caller continues");

    Calling run() is an ordinary method call. importFile executes on the current thread and completes before the print. Calling start() requests a new execution thread, which later invokes run():

    Thread worker = new Thread(() -> importFile(), "import-worker");
worker.start();
System.out.println("caller may continue before import finishes");

    A Thread can be started at most once. Calling start() again throws IllegalThreadStateException; terminated threads are not restartable. Reuse tasks or create new threads through an execution service.

    Happens-before reasoning¶

    The Java Memory Model gives start() a crucial guarantee: actions in the calling thread before worker.start() happen-before actions in the started thread. Therefore, initialization before start is visible to the worker.

    final class StartVisibility {
    private int value;

    void runExample() throws InterruptedException {
        value = 42;
        Thread worker = new Thread(() -> {
            if (value != 42) {
                throw new AssertionError();
            }
        });
        worker.start();
        worker.join();
    }
}

    Do not reverse the edge. Writes performed after start() are not automatically ordered before worker reads.

    5. join() waits and publishes completion¶

    Broken code assumes scheduling order:

    int[] result = {0};
new Thread(() -> result[0] = 42).start();
System.out.println(result[0]);

    The caller can print 0; it neither waits for completion nor establishes the required visibility edge.

    Corrected code:

    int[] result = {0};
Thread worker = new Thread(() -> result[0] = 42);
worker.start();
worker.join();
System.out.println(result[0]);

    All actions in a terminated thread happen-before another thread returns from join after observing that termination. Joining a thread that has not started does not establish completion of future work. join supplies both completion coordination and visibility.

    join does not propagate the worker's exception. An uncaught exception terminates the worker; the joining thread returns normally. If a result or failure must cross the task boundary, use Future, CompletableFuture, or another explicit result channel.

    Timed join can return while the worker remains alive. Check the postcondition:

    worker.join(500);
if (worker.isAlive()) {
    worker.interrupt();
    throw new IllegalStateException("worker exceeded deadline");
}

    The timeout does not stop the worker. Interruption is only a request, and the caller still needs a policy for final cleanup or bounded escalation.

    6. sleep() pauses; it does not coordinate¶

    Thread.sleep makes the current thread temporarily not runnable. It does not release monitors the thread owns. Its timing depends on system timers and scheduling, and interruption can end it early; it is not an exact wake-time guarantee.

    Broken coordination:

    worker.start();
Thread.sleep(100);
assert cache.isReady();

    This test can fail on a slow machine and waste 100 ms on a fast one. Use a completion mechanism:

    var ready = new java.util.concurrent.CountDownLatch(1);
Thread worker = new Thread(() -> {
    initializeCache();
    ready.countDown();
});
worker.start();

if (!ready.await(2, java.util.concurrent.TimeUnit.SECONDS)) {
    throw new IllegalStateException("cache initialization timed out");
}

    The CountDownLatch contract also supplies memory consistency: actions before countDown() happen-before actions after a corresponding successful await() return.

    Never sleep while holding a lock to "give another thread time." The other thread may need that same lock and be unable to make progress.

    7. Interruption is cooperative cancellation¶

    Calling interrupt() does not forcibly kill a Java thread. It sets the target's interrupt status, unless the thread is blocked in certain interruptible methods. Methods such as sleep, join, and BlockingQueue.take respond by clearing the status and throwing InterruptedException.

    Broken code loses the cancellation request:

    try {
    queue.take();
} catch (InterruptedException ignored) {
    // Continue as if nothing happened.
}

    If the method cannot propagate InterruptedException, restore the status and terminate or return:

    void consumeUntilStopped() {
    try {
        while (!Thread.currentThread().isInterrupted()) {
            Message message = queue.take();
            process(message);
        }
    } catch (InterruptedException interrupted) {
        Thread.currentThread().interrupt();
    }
}

    If the method can propagate it, prefer that:

    Message nextMessage() throws InterruptedException {
    return queue.take();
}

    Interrupt-status API distinctions¶

    API Which thread? Clears status?
    thread.interrupt() Target thread Not by itself
    thread.isInterrupted() Target thread no
    Thread.interrupted() Current thread yes

    The static Thread.interrupted() is often used when code intentionally acknowledges and consumes an interrupt. Accidental calls can erase cancellation evidence.

    Interleaving: interrupt before blocking¶

    Interruption is not merely a wakeup delivered only after blocking:

    Step Controller Worker
    1 calls worker.interrupt() running computation
    2 later calls queue.take()
    3 interruptible call detects status and throws

    A sound cancellation design handles requests that arrive before, during, or after a blocking boundary. Also, CPU loops must poll status at useful intervals:

    for (int i = 0; i < records.size(); i++) {
    if ((i & 1023) == 0 && Thread.currentThread().isInterrupted()) {
        throw new java.util.concurrent.CancellationException();
    }
    transform(records.get(i));
}

    The polling interval trades cancellation latency against checking overhead.

    8. Daemon threads are not a shutdown strategy¶

    The JVM begins shutdown when no started non-daemon thread remains, or when shutdown is otherwise initiated. Daemon threads do not keep the JVM alive. They can stop without completing finally blocks when the process exits.

    Thread metrics = new Thread(this::publishLoop, "metrics-publisher");
metrics.setDaemon(true);
metrics.start();

    setDaemon must occur before start. Use daemon threads only for work that may be abandoned at process termination. Never rely on a daemon thread to flush critical records, commit data, or release an external lease. Prefer explicit close, interruption, executor shutdown, bounded wait, and a documented final policy.

    Work Daemon appropriate? Reason
    Best-effort local diagnostics sampler possibly Losing the final sample is acceptable
    Payment settlement writer no Abandonment violates durability
    Lock-renewal loop no as sole policy Requires explicit release/fencing and shutdown
    Test-only leak detector possibly Must not keep a failed suite alive

    9. Runnable and Callable¶

    Runnable.run() returns no value and declares no checked exception. Callable<V>.call() returns V and may throw Exception.

    Runnable refresh = () -> cache.refresh();

java.util.concurrent.Callable<Report> buildReport =
        () -> reportService.build(reportId);

    These interfaces describe task shape, not scheduling. Avoid embedding thread creation in domain methods:

    // Broken ownership: every call creates an unmanaged thread.
void sendReceipt(Order order) {
    new Thread(() -> mailer.send(order)).start();
}

    Inject an execution policy or return a task:

    final class ReceiptService {
    private final java.util.concurrent.Executor executor;

    ReceiptService(java.util.concurrent.Executor executor) {
        this.executor = executor;
    }

    void sendReceipt(Order order) {
        executor.execute(() -> mailer.send(order));
    }
}

    The corrected design still needs answers for overload, rejection, retries, exception reporting, shutdown, and whether asynchronous acceptance is valid. Dependency injection makes those policies selectable; it does not define them.

    10. CPU-bound versus I/O-bound work¶

    A CPU-bound task spends most time computing. An I/O-bound task spends substantial time waiting for storage, network, or another blocking resource.

    Workload Starting execution policy Constraint to measure
    CPU-bound independent calculations Pool near available processor count Core utilization, task size, memory bandwidth
    Blocking I/O with scarce downstream connections Concurrency bounded by downstream capacity Connection count, latency, queue age, timeout rate
    Mixed CPU and blocking I/O Separate pools or isolate stages Head-of-line blocking and saturation
    Many simple blocking I/O tasks on Java 21 Virtual thread per task Downstream limits, pinning, memory, task admission

    For CPU work, adding threads beyond cores usually increases context switching rather than throughput. For blocking work, more concurrent tasks can hide wait time, but only until another resource saturates.

    A rough sizing intuition for platform threads is:

    threads ~= cores * targetUtilization * (1 + waitTime / computeTime)

    This is a measurement hypothesis, not a configuration theorem. Request bursts, service-time variance, memory, connection pools, and downstream quotas still matter.

    Java 21 virtual threads¶

    Virtual threads are final in Java 21. They make thread-per-task style practical for large numbers of mostly blocking tasks. They do not:

    • provide extra CPU cores;
    • make unsafe shared mutation safe;
    • remove the need for timeouts, cancellation, or admission control;
    • increase database connection limits;
    • justify creating unbounded work.

    Long blocking operations while inside synchronized or native/foreign calls can pin a virtual thread to its carrier in Java 21. Later JDKs may improve implementation details, so state the version when discussing pinning. Prefer APIs whose semantics fit the design, measure with Java 21 tooling, and avoid rewriting correct locking solely from folklore.

    11. Lifecycle is part of the API¶

    A component that starts threads owns these decisions:

    1. When are threads created?
    2. Who requests shutdown?
    3. Are new tasks rejected after shutdown?
    4. Are queued tasks drained, cancelled, or returned?
    5. How are running tasks asked to stop?
    6. How long does the owner wait?
    7. Where do uncaught failures go?

    A raw-thread component can expose explicit lifecycle:

    final class Poller implements AutoCloseable {
    private enum State { NEW, RUNNING, STOPPING, TERMINATED }

    private final Object lifecycle = new Object();
    private final Thread worker;
    private State state = State.NEW;

    Poller() {
        worker = new Thread(this::runLoop, "event-poller");
    }

    void start() {
        synchronized (lifecycle) {
            if (state != State.NEW) {
                throw new IllegalStateException("poller cannot start from " + state);
            }
            state = State.RUNNING; // Linearizes start before the thread is launched.
            worker.start();
        }
    }

    private void runLoop() {
        try {
            while (!Thread.currentThread().isInterrupted()) {
                Event event = source.next();
                handle(event);
            }
        } catch (InterruptedException interrupted) {
            Thread.currentThread().interrupt();
        } catch (RuntimeException failure) {
            reportFailure(failure);
            throw failure;
        } finally {
            synchronized (lifecycle) {
                state = State.TERMINATED;
            }
        }
    }

    @Override
    public void close() {
        synchronized (lifecycle) {
            if (state == State.NEW) {
                state = State.TERMINATED;
                return;
            }
            if (state == State.RUNNING) {
                state = State.STOPPING; // Linearizes shutdown against start.
            }
        }
        worker.interrupt();
        try {
            worker.join(5_000);
        } catch (InterruptedException interrupted) {
            Thread.currentThread().interrupt();
            return;
        }
        if (worker.isAlive()) {
            reportFailure(new IllegalStateException("poller did not stop"));
        }
    }
}

    This is illustrative, not universal. source.next() and handle must honor the chosen cancellation policy. Starting in the constructor would publish this before construction completes, a defect covered in Chapter 3. The lifecycle monitor prevents double start and makes concurrent start/close deterministic: whichever guarded transition wins decides whether the worker is launched, and close before start permanently terminates the component.

    Lifecycle invariants and linearization points¶

    For a component with states NEW, RUNNING, STOPPING, and TERMINATED, state the legal transitions before writing synchronization code:

    NEW -> RUNNING -> STOPPING -> TERMINATED
NEW -> TERMINATED
RUNNING -> TERMINATED (unexpected worker exit)

    Useful invariants are:

    • at most one worker thread is started;
    • no task is accepted after the component commits to stopping;
    • TERMINATED implies the worker can perform no more component work;
    • every accepted task either completes or receives the documented cancellation outcome;
    • resource closure happens at most once, after no code can begin using that resource.

    Guard the lifecycle state and task-admission decision with one policy. If close() writes STOPPING under a lock but submit() checks state without that lock, a task can slip in after shutdown appears to succeed.

    Plausible linearization points are the guarded NEW -> RUNNING transition for start, the guarded RUNNING -> STOPPING transition for close, and the guarded insertion into an accepted-work queue for submission. A failed submission linearizes at its protected observation that state is no longer RUNNING.

    The liveness contract also needs bounds. For example: after close, an interruptible idle worker reaches TERMINATED within five seconds unless a named external call violates its cancellation contract. This is more useful than promising that shutdown is "graceful" without defining completion, abandonment, or a deadline.

    12. Tests for lifecycle and cancellation¶

    Use controlled dependencies. A fake source can announce entry into next() and block interruptibly on a latch. Then a test can:

    1. start the poller;
    2. wait until the fake confirms it is blocked;
    3. call close;
    4. assert that close returns within a deadline;
    5. assert that no event runs after closure;
    6. assert that failure reporting receives unexpected runtime failures.

    Every concurrency test needs an outer timeout and cleanup. Capture task failures through Future.get, an uncaught-exception handler, or a test-owned error queue. Do not let worker failures disappear on background threads.

    Tradeoffs¶

    Choice Benefit Cost or caveat
    Raw Thread Explicit mechanics and naming Manual lifecycle; one thread per task
    Fixed platform-thread pool Bounded execution concurrency Queueing and thread starvation under blocking
    Cached/unbounded pool Absorbs short bursts Can create excessive threads and overload dependencies
    Virtual thread per task Simple blocking code at high task counts Requires explicit resource bounds; Java 21 pinning caveats
    Interrupt cancellation Standard cooperative signal Code and dependencies must respond correctly
    Custom cancellation token Domain-specific reasons/deadlines Must integrate with interruptible Java APIs
    Daemon thread Does not delay JVM exit Work may be abandoned

    Interview traps¶

    • Calling run() and claiming a new thread was started.
    • Assuming start() means the worker has already executed.
    • Assuming join() forwards the worker's exception.
    • Using sleep for readiness or mutual exclusion.
    • Swallowing InterruptedException.
    • Calling Thread.interrupted() without realizing it clears status.
    • Treating daemon threads as graceful cleanup.
    • Choosing thread count from request rate while ignoring task service time and downstream capacity.
    • Saying virtual threads make blocking free or CPU work parallel without bound.
    • Starting a worker in a constructor and leaking a partially constructed object.

    Review questions¶

    1. Can concurrent work happen on one CPU core? Can parallel work happen without concurrency?
    2. What is the difference between BLOCKED and WAITING in Thread.State?
    3. Which happens-before edges do start and successful join provide?
    4. Why does timed join require an isAlive check?
    5. Does sleep release an intrinsic lock?
    6. What should code do when it catches InterruptedException but cannot throw it?
    7. Why can a virtual-thread design still overload a database?
    8. Why should a task not decide unilaterally to create a new thread?

    Exercise 2: Choose an execution policy¶

    An API performs 2 ms of CPU validation, waits about 80 ms for a database, and the database permits 100 concurrent requests. Should Java 21 use a 100-thread platform pool, virtual threads, or a CPU-sized pool?

    Exercise 3: Preserve interruption¶

    Write a helper that waits for a worker to finish and returns false after a timeout. If the caller is interrupted, it must not erase the request.

    Solutions

    Solution 1¶

    Problems include a data race on stop, unbounded shutdown if doOneUnit blocks despite the timed join returning, failure to check isAlive, no response to interruption in blocking operations, no double-start policy, and no reporting for worker failure.

    final class Service implements AutoCloseable {
    private final Thread worker;
    private boolean started;
    private boolean closed;

    Service() {
        worker = new Thread(this::runLoop, "service-worker");
        worker.setUncaughtExceptionHandler((thread, failure) ->
                reportFailure(thread.getName(), failure));
    }

    synchronized void start() {
        if (started || closed) {
            throw new IllegalStateException("already started or closed");
        }
        started = true;
        worker.start();
    }

    private void runLoop() {
        while (!Thread.currentThread().isInterrupted()) {
            doOneInterruptibleUnit();
        }
    }

    @Override
    public void close() {
        synchronized (this) {
            closed = true;
            if (!started) {
                return;
            }
        }
        worker.interrupt();
        try {
            worker.join(1_000);
        } catch (InterruptedException interrupted) {
            Thread.currentThread().interrupt();
            return;
        }
        if (worker.isAlive()) {
            reportFailure("service-worker",
                    new IllegalStateException("shutdown timed out"));
        }
    }
}

    This assumes doOneInterruptibleUnit either uses interruptible operations or checks status. The shared monitor serializes start with closing admission, including close-before-start. Call close from the external lifecycle owner, not the worker itself, which cannot join its own termination. The earlier enum lifecycle makes intermediate stopping and terminated states explicit.

    Solution 2¶

    The database's limit is the binding resource. Either a platform pool of at most 100 database-active tasks or virtual threads gated by a 100-permit semaphore can work. Virtual threads simplify blocking composition and may support many waiting requests, but they must not bypass the 100-call limit or admission control. A CPU-sized pool would underuse the database because each task spends most time waiting. Also bound queued/admitted requests and apply deadlines; do not allow unlimited virtual threads to accumulate.

    Solution 3¶

    static boolean joinWithin(Thread worker, Duration timeout) {
    if (timeout.isNegative()) throw new IllegalArgumentException("negative timeout");
    try {
        return worker.join(timeout);
    } catch (InterruptedException interrupted) {
        Thread.currentThread().interrupt();
        return false;
    }
}

    This Java 21 helper requires an already-started worker and intentionally translates interruption to false while restoring status. join(Duration.ZERO) only checks termination; converting a sub-millisecond duration to join(0) would instead wait forever. A successful termination observation publishes worker writes; a timeout does not. See the Thread.join(Duration) contract.
