    08. Async Composition, Parallelism, and Virtual Threads¶

    Asynchrony is about waiting without tying up the caller. Parallelism is about executing work at the same time. Virtual threads make blocking code cheaper to scale, but they do not increase CPU, connection limits, or dependency quotas. Strong interview answers separate these concerns before choosing an API.

    Goals¶

    After this chapter, you should be able to:

    • compose and combine CompletableFuture stages without accidental serialization;
    • control execution placement and exception semantics;
    • implement end-to-end deadlines and explain cancellation limits;
    • reason about work stealing, blocking, and nested fork/join work;
    • use parallel streams only where their ownership and cost are acceptable;
    • design Java 21 thread-per-task services with virtual threads;
    • bound scarce dependencies with semaphores rather than pooling virtual threads;
    • discuss pinning and version-specific preview APIs accurately;
    • build a fan-out aggregator and parallel merge sort; and
    • test completion, failure, timeout, cancellation, and shutdown behavior.

    1. Choose the model from the work¶

    Work Primary need Typical Java 21 tool
    One blocking request per task Scalable waiting Virtual thread per task
    Several independent remote calls Composition and deadlines CompletableFuture with explicit executor
    Recursive CPU computation Parallel divide and conquer ForkJoinPool / RecursiveTask
    Pure bulk collection transform Data parallelism Carefully evaluated parallel stream
    Limit calls to scarce dependency Admission control Fair or non-fair Semaphore

    Do not select an asynchronous API merely to avoid blocking syntax. A synchronous call on a virtual thread is often simpler than a graph of callbacks. Conversely, virtual threads do not provide result composition, deadlines, or sibling cancellation by themselves.

    2. CompletableFuture completion model¶

    A stage reaches one terminal outcome:

    INCOMPLETE -> NORMAL(value)
           -> EXCEPTIONAL(cause)
           `-> CANCELLED(CancellationException)

    Ordinary completion is single-winner. Attempts to complete or completeExceptionally an already completed future return false and do not replace its outcome. The exceptional recovery methods obtrudeValue and obtrudeException can override later observations and must not be part of this normal protocol. Actions before completion happen-before dependent actions triggered by that completion.

    Transformation, composition, and combination¶

    • thenApply: transform T into U; analogous to map.
    • thenCompose: use T to start a future CompletionStage<U> and flatten it; analogous to flatMap.
    • thenCombine: wait for two independent stages and combine both values.
    • allOf: wait for all stages, but does not collect typed results.
    • anyOf: complete from one stage, returning Object.

    Broken: nested future and accidental serialization¶

    CompletableFuture<CompletableFuture<Order>> nested =
        loadCustomer(id).thenApply(customer -> loadLatestOrder(customer.id()));

Customer customer = loadCustomer(id).join();
Order order = loadLatestOrder(customer.id()).join();

    The first form leaves a nested future. The second blocks before launching the second operation. If the operations are dependent, use composition; if independent, start both before combining.

    Corrected composition¶

    CompletableFuture<Order> order = loadCustomer(id)
        .thenCompose(customer -> loadLatestOrder(customer.id()));

    Corrected combination¶

    CompletableFuture<CustomerView> view(String id) {
    CompletableFuture<Customer> customer = loadCustomer(id);
    CompletableFuture<List<Order>> orders = loadOrders(id);
    return customer.thenCombine(orders, CustomerView::new);
}

    The combination completes normally only after both inputs complete normally. If either fails, the combined stage completes exceptionally. Do not rely on which failure wins when both fail concurrently.

    3. Execution placement must be explicit¶

    Non-Async continuations may run on the thread that completes the previous stage, or immediately on the caller if the stage is already complete. Async variants without an executor normally use ForkJoinPool.commonPool().

    ExecutorService io = Executors.newFixedThreadPool(32);
ExecutorService cpu = Executors.newFixedThreadPool(
        Runtime.getRuntime().availableProcessors());

CompletableFuture<Report> report = CompletableFuture
        .supplyAsync(() -> repository.load(id), io)
        .thenApplyAsync(this::calculateReport, cpu);

    Execution placement is part of correctness when a stage blocks, consumes substantial CPU, requires thread context, or shares a bounded resource. Passing an executor only to the first stage does not make every later Async stage use it.

    Broken: blocking the common pool¶

    return CompletableFuture.supplyAsync(() -> httpClient.blockingGet(uri));

    This sends blocking I/O to the common fork/join pool, which is shared by unrelated code and parallel streams.

    Corrected: owned executor¶

    return CompletableFuture.supplyAsync(() -> httpClient.blockingGet(uri), ioExecutor);

    For Java 21 blocking I/O, an owned virtual-thread-per-task executor is another clear option:

    try (ExecutorService tasks = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<Response> response = tasks.submit(() -> httpClient.blockingGet(uri));
    return response.get();
}

    4. Exception semantics¶

    join() throws unchecked CompletionException; get() throws checked ExecutionException and is interruptible. Both preserve the underlying cause.

    Method Runs on success Runs on failure Can recover
    thenApply Yes No No
    exceptionally No Yes Yes, with fallback value
    handle Yes Yes Yes, transforms either outcome
    whenComplete Yes Yes No intended transformation

    Broken: converting every bug to an empty result¶

    return fetchAccount(id).exceptionally(failure -> Account.empty());

    This hides programming errors, cancellation, authentication failures, and overload behind the same fallback.

    Corrected: classify causes¶

    return fetchAccount(id).exceptionally(failure -> {
    Throwable cause = unwrap(failure);
    if (cause instanceof AccountNotFoundException) {
        return Account.empty();
    }
    if (cause instanceof CancellationException cancellation) {
        throw cancellation;
    }
    throw new CompletionException(cause);
});

static Throwable unwrap(Throwable failure) {
    Throwable current = failure;
    while ((current instanceof CompletionException
            || current instanceof ExecutionException)
            && current.getCause() != null) {
        current = current.getCause();
    }
    return current;
}

    whenComplete is useful for telemetry, but if its callback throws while the input succeeded, the returned stage fails. Keep observability hooks defensive.

    5. Deadlines, timeouts, and cancellation¶

    A timeout is local to one wait or stage. A deadline is an absolute end-to-end budget. Recomputing a fresh timeout at every layer can exceed the caller's total budget.

    public record Deadline(long startedNanos, long budgetNanos) {
    public Deadline {
        if (budgetNanos < 0) throw new IllegalArgumentException("negative budget");
    }

    public static Deadline after(Duration budget) {
        if (budget.isNegative()) {
            throw new IllegalArgumentException("negative budget");
        }
        long nanos;
        try {
            nanos = budget.toNanos();
        } catch (ArithmeticException tooLarge) {
            nanos = Long.MAX_VALUE;
        }
        return new Deadline(System.nanoTime(), nanos);
    }

    public Duration remaining() {
        long elapsed = System.nanoTime() - startedNanos;
        long remaining = elapsed <= 0L ? budgetNanos
                : elapsed >= budgetNanos ? 0L : budgetNanos - elapsed;
        return Duration.ofNanos(remaining);
    }
}

    Use monotonic System.nanoTime() for elapsed budgets. Storing start plus budget instead of adding them avoids absolute-deadline overflow; extreme positive durations saturate at Long.MAX_VALUE nanoseconds. Pass the remaining budget to dependency clients that can enforce their own connect, request, and read timeout.

    orTimeout completes the same CompletableFuture exceptionally with TimeoutException. completeOnTimeout completes it normally with a fallback. Neither guarantees interruption or termination of the underlying supplier.

    CompletableFuture<Quote> bounded = quoteFuture
        .orTimeout(deadline.remaining().toNanos(), TimeUnit.NANOSECONDS);

    Cancellation limitations¶

    CompletableFuture.cancel(true) completes the future with cancellation, but its mayInterruptIfRunning argument has no interrupting effect on tasks created through ordinary CompletableFuture async methods. The supplier may continue consuming resources. Incomplete dependent stages complete exceptionally as specified by their combinators; this is downstream outcome propagation, not interruption of their running work. Cancellation does not automatically cancel upstream or sibling work. See the Java 21 CompletableFuture cancellation contract.

    For interruptible blocking work, retain the Future returned by an ExecutorService, cancel it, and make the task interruption-aware. Prefer clients with native deadline/cancellation support. Design side effects as idempotent because timeout at the caller does not prove non-execution remotely.

    6. Case study: deadline-aware fan-out aggregator¶

    Contract and invariants¶

    The aggregator requests inventory, price, and recommendations in parallel.

    • inventory and price are required;
    • expected recommendation I/O failures and timeouts degrade to an empty list; unexpected bugs remain failures;
    • all calls receive one shared deadline;
    • remaining time is checked before task submission and again before dependency invocation; scheduling can still cross the deadline after a check;
    • executor ownership belongs to the aggregator;
    • close rejects new work and interrupts outstanding tasks after a grace period.

    Completion semantics:

    • success linearizes when the final combined future is completed with all required values;
    • required-call failure completes the aggregate exceptionally;
    • expected optional-call failure is recorded and converted to its documented fallback;
    • caller cancellation of the returned CompletableFuture does not reliably stop suppliers.

    Implementation¶

    import java.io.IOException;
import java.time.Duration;
import java.util.List;
import java.util.Objects;
import java.util.concurrent.*;
import java.util.function.Supplier;

public final class ProductAggregator implements AutoCloseable {
    public record Inventory(boolean inStock) {}
    public record Price(long minorUnits, String currency) {}
    public record Recommendation(String sku) {}

    public interface CatalogClient {
        Inventory inventory(String sku, Duration timeout) throws Exception;
        Price price(String sku, Duration timeout) throws Exception;
        List<Recommendation> recommendations(String sku, Duration timeout)
                throws Exception;
    }

    public record ProductView(Inventory inventory, Price price,
                              List<Recommendation> recommendations) {}

    private final CatalogClient client;
    private final ExecutorService executor;

    public ProductAggregator(CatalogClient client) {
        this.client = Objects.requireNonNull(client);
        this.executor = Executors.newVirtualThreadPerTaskExecutor();
    }

    public CompletableFuture<ProductView> aggregate(String sku, Duration budget) {
        Objects.requireNonNull(sku);
        Deadline deadline = Deadline.after(budget);

        CompletableFuture<Inventory> inventory = call(deadline,
                () -> client.inventory(sku, requireTime(deadline)));
        CompletableFuture<Price> price = call(deadline,
                () -> client.price(sku, requireTime(deadline)));
        CompletableFuture<List<Recommendation>> recommendations =
                this.<List<Recommendation>>call(deadline,
                        () -> client.recommendations(sku, requireTime(deadline)))
                        .exceptionally(failure -> {
                            Throwable cause = failure;
                            while (cause instanceof CompletionException
                                    && cause.getCause() != null) {
                                cause = cause.getCause();
                            }
                            if (cause instanceof IOException
                                    || cause instanceof TimeoutException) {
                                System.err.println("Recommendations unavailable: "
                                        + cause.getClass().getSimpleName());
                                return List.of();
                            }
                            throw new CompletionException(cause);
                        });

        CompletableFuture<ProductView> result = inventory
                .thenCombine(price, Required::new)
                .thenCombine(recommendations,
                        (required, optional) -> new ProductView(
                                required.inventory(), required.price(), optional));

        long remaining = deadline.remaining().toNanos();
        return result.orTimeout(remaining, TimeUnit.NANOSECONDS);
    }

    private <T> CompletableFuture<T> call(Deadline deadline, CheckedSupplier<T> supplier) {
        try {
            requireTime(deadline);
            return CompletableFuture.supplyAsync(() -> {
                try {
                    return supplier.get();
                } catch (InterruptedException interrupted) {
                    Thread.currentThread().interrupt();
                    throw new CompletionException(interrupted);
                } catch (Exception failure) {
                    throw new CompletionException(failure);
                }
            }, executor);
        } catch (TimeoutException | RejectedExecutionException failure) {
            return CompletableFuture.failedFuture(failure);
        }
    }

    private static Duration requireTime(Deadline deadline) throws TimeoutException {
        Duration remaining = deadline.remaining();
        if (remaining.isZero()) {
            throw new TimeoutException("aggregate deadline expired");
        }
        return remaining;
    }

    @Override
    public void close() {
        executor.shutdown();
        boolean restoreInterrupt = false;
        try {
            if (!executor.awaitTermination(5, TimeUnit.SECONDS)) {
                executor.shutdownNow();
                if (!executor.awaitTermination(5, TimeUnit.SECONDS)) {
                    System.err.println("Aggregator tasks did not terminate");
                }
            }
        } catch (InterruptedException interrupted) {
            restoreInterrupt = true;
            executor.shutdownNow();
        } finally {
            if (restoreInterrupt) {
                Thread.currentThread().interrupt();
            }
        }
    }

    private record Required(Inventory inventory, Price price) {}

    @FunctionalInterface
    private interface CheckedSupplier<T> {
        T get() throws Exception;
    }
}

    Replace the example's bounded failure-class diagnostic with production metrics and use clients whose timeout aborts network work. thenCombine is not a fail-fast sibling-cancellation mechanism: a failed required call can still wait for other inputs, bounded here by the aggregate timeout. Submission rejection is represented by a failed future; already submitted work is not rolled back. The virtual-thread executor removes the need to size threads around blocking duration, but dependency concurrency remains unbounded unless separately limited.

    7. Fork/join and work stealing¶

    A ForkJoinPool gives each worker a deque. A worker usually processes its own tasks in stack-like order and steals older tasks from other workers when idle. This reduces contention and suits recursively generated CPU work.

    The usual pattern is:

    1. stop splitting below a measured threshold;
    2. fork one subproblem;
    3. compute the other directly;
    4. join the forked result; and
    5. combine.

    Forking both halves can create unnecessary queueing. Tiny thresholds create overhead; huge thresholds lose parallelism.

    Managed blocking concern¶

    Fork/join parallelism assumes workers mostly compute. Blocking a worker can reduce available parallelism. ForkJoinPool.managedBlock lets the pool compensate for recognized blocking, but adapters are difficult to make correct and do not raise downstream capacity. Prefer moving blocking work to a suitable executor or using virtual threads for blocking workflows.

    Nested parallel operations on the common pool can interfere with unrelated components. Although fork/join joins are cooperative, external locks, I/O, and cyclic waits can still starve progress. Own a pool when isolation is a requirement.

    8. Case study: parallel merge sort¶

    State, invariant, and completion¶

    Each task owns the half-open range [low, high) of one array. Child ranges do not overlap, so they may sort concurrently. After both children complete, merge writes one sorted permutation into the parent range.

    Invariants:

    • elements outside [low, high) are untouched by that task;
    • after task completion, its range is sorted;
    • the completed range contains exactly the input multiset from that range; and
    • no merge begins until both child ranges complete.

    The task's completion point is return from compute after the merge. join establishes visibility of child writes.

    import java.util.Arrays;
import java.util.concurrent.ForkJoinPool;
import java.util.concurrent.RecursiveAction;

public final class ParallelMergeSort {
    private ParallelMergeSort() {}

    public static void sort(int[] values, int threshold, ForkJoinPool pool) {
        if (threshold < 2) {
            throw new IllegalArgumentException("threshold must be at least 2");
        }
        int[] scratch = new int[values.length];
        pool.invoke(new SortTask(values, scratch, 0, values.length, threshold));
    }

    private static final class SortTask extends RecursiveAction {
        private final int[] values;
        private final int[] scratch;
        private final int low;
        private final int high;
        private final int threshold;

        private SortTask(int[] values, int[] scratch, int low, int high,
                         int threshold) {
            this.values = values;
            this.scratch = scratch;
            this.low = low;
            this.high = high;
            this.threshold = threshold;
        }

        @Override
        protected void compute() {
            int size = high - low;
            if (size <= threshold) {
                Arrays.sort(values, low, high);
                return;
            }

            int middle = low + size / 2;
            SortTask left = new SortTask(values, scratch, low, middle, threshold);
            SortTask right = new SortTask(values, scratch, middle, high, threshold);
            left.fork();
            right.compute();
            left.join();
            merge(values, scratch, low, middle, high);
        }
    }

    private static void merge(int[] values, int[] scratch,
                              int low, int middle, int high) {
        System.arraycopy(values, low, scratch, low, high - low);
        int left = low;
        int right = middle;
        int target = low;
        while (left < middle && right < high) {
            values[target++] = scratch[left] <= scratch[right]
                    ? scratch[left++] : scratch[right++];
        }
        while (left < middle) {
            values[target++] = scratch[left++];
        }
        while (right < high) {
            values[target++] = scratch[right++];
        }
    }
}

    This implementation has one shared scratch array, but sibling tasks write disjoint ranges. Benchmark the threshold for representative arrays. Sorting mutates the input; callers must not read or write it concurrently.

    9. Parallel streams¶

    Parallel streams use the common fork/join pool in ordinary usage. They are concise for large, in-memory, CPU-heavy, stateless transformations with associative reductions.

    Avoid them when:

    • operations block on I/O or locks;
    • encounter order matters and ordered operations dominate;
    • input is small or splitting is poor;
    • lambdas mutate shared state;
    • request isolation or executor ownership matters;
    • the code already runs inside constrained parallel work; or
    • latency predictability matters more than aggregate throughput.

    Broken shared mutation¶

    List<Result> output = new ArrayList<>();
inputs.parallelStream().map(this::compute).forEach(output::add);

    ArrayList mutation races, and encounter order is not guaranteed by forEach.

    Corrected reduction¶

    List<Result> output = inputs.parallelStream()
        .map(this::compute)
        .toList();

    Correct does not imply faster. Measure against a sequential stream with production-like data and co-tenant load.

    10. Virtual threads in Java 21¶

    Virtual threads are final in Java 21. The JVM schedules many virtual threads onto a smaller set of carrier platform threads. Blocking in supported JDK operations usually parks the virtual thread and releases its carrier.

    try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<Response>> futures = requests.stream()
            .map(request -> executor.submit(() -> client.call(request)))
            .toList();
    for (Future<Response> future : futures) {
        consume(future.get());
    }
}

    Virtual threads improve thread scalability for blocking workloads. They do not make CPU work faster and do not make unsafe shared state safe.

    Why not pool virtual threads¶

    Pooling is primarily a way to reuse expensive platform threads and limit concurrency. Virtual threads are cheap and intended to be created per task. Pooling them adds queueing and obscures task identity without solving scarce-resource admission.

    Use a semaphore, rate limiter, connection pool, or dependency-native limit around the scarce operation:

    public final class LimitedClient {
    private final Semaphore permits;
    private final RemoteClient client;

    public LimitedClient(int maxConcurrent, RemoteClient client) {
        this.permits = new Semaphore(maxConcurrent);
        this.client = client;
    }

    public Response call(Request request) throws InterruptedException {
        permits.acquire();
        try {
            return client.call(request);
        } finally {
            permits.release();
        }
    }
}

    Permit ownership invariant: every successful acquire has exactly one release in finally; a failed or interrupted acquire has no release. The linearization point for admission is successful permit acquisition. Fair semaphores reduce barging but can lower throughput.

    For bounded waiting, use tryAcquire(timeout, unit) and return an explicit overload or deadline result. Do not hold a permit across unrelated computation.

    Pinning and version caveats¶

    In Java 21, a virtual thread can be pinned to its carrier while blocking inside a synchronized method or block, and in some native or foreign-function calls. Long, frequent pinned blocking can reduce scalability. Short uncontended synchronized sections remain reasonable; do not replace every monitor blindly. Java Flight Recorder and Java 21's jdk.tracePinnedThreads property help locate some problematic pinning cases.

    Version boundary (accessed 2026-09-08): JEP 491, delivered in JDK 24, removes monitor-related pinning and removes the effect of jdk.tracePinnedThreads. Remaining native/callback and class-initialization cases still need version-appropriate diagnostics, including JFR. Keep the Java 21 baseline distinct from JDK 24 behavior; an old pinning workaround is not automatically required on a newer runtime.

    ThreadLocal works with virtual threads, but millions of per-thread values can consume substantial memory. Prefer explicit context and avoid expensive thread-local caches.

    Preview and version-specific APIs

    In Java 21, ScopedValue and Structured Concurrency are preview APIs. They require --enable-preview at compile and run time, their package/API shapes may change, and production use requires an explicit upgrade policy. They are not used by the Java 21 baseline examples in this chapter. Structured concurrency aims to make child-task lifetime, failure propagation, and cancellation follow a lexical parent scope; it is not safe to present a later JDK API signature as Java 21 code.

    11. Tests¶

    Aggregator completion tests¶

    Use controllable fakes rather than sleeping network stubs.

    import static org.junit.jupiter.api.Assertions.*;

import java.io.IOException;
import java.time.Duration;
import java.util.List;
import java.util.concurrent.*;
import org.junit.jupiter.api.Test;

final class ProductAggregatorTest {
    @Test
    void launchesRequiredCallsBeforeEitherCompletes() throws Exception {
        CountDownLatch entered = new CountDownLatch(2);
        CountDownLatch release = new CountDownLatch(1);
        ProductAggregator.CatalogClient fake = new StubClient(
                timeout -> { entered.countDown(); release.await(); return inStock(); },
                timeout -> { entered.countDown(); release.await(); return tenDollars(); },
                timeout -> List.of());

        try (var aggregator = new ProductAggregator(fake)) {
            CompletableFuture<ProductAggregator.ProductView> result =
                    aggregator.aggregate("sku-1", Duration.ofSeconds(2));
            assertTrue(entered.await(1, TimeUnit.SECONDS));
            assertFalse(result.isDone());
            release.countDown();
            assertEquals(tenDollars(), result.get(1, TimeUnit.SECONDS).price());
        } finally {
            release.countDown();
        }
    }

    @Test
    void requiredFailurePropagates() {
        ProductAggregator.CatalogClient fake = new StubClient(
                timeout -> inStock(),
                timeout -> { throw new IllegalStateException("pricing unavailable"); },
                timeout -> { throw new IOException("recommendations unavailable"); });

        try (var aggregator = new ProductAggregator(fake)) {
            CompletionException failure = assertThrows(CompletionException.class,
                    () -> aggregator.aggregate("sku-1", Duration.ofSeconds(1)).join());
            assertEquals("pricing unavailable", rootCause(failure).getMessage());
        }
    }

    @Test
    void optionalFailureDegradesToEmptyRecommendations() {
        ProductAggregator.CatalogClient fake = new StubClient(
                timeout -> inStock(),
                timeout -> tenDollars(),
                timeout -> { throw new IOException("recommendations unavailable"); });

        try (var aggregator = new ProductAggregator(fake)) {
            ProductAggregator.ProductView view = aggregator
                    .aggregate("sku-1", Duration.ofSeconds(1)).join();
            assertEquals(tenDollars(), view.price());
            assertEquals(List.of(), view.recommendations());
        }
    }

    private static ProductAggregator.Inventory inStock() {
        return new ProductAggregator.Inventory(true);
    }

    private static ProductAggregator.Price tenDollars() {
        return new ProductAggregator.Price(1_000, "USD");
    }

    private static Throwable rootCause(Throwable failure) {
        Throwable current = failure;
        while (current.getCause() != null) {
            current = current.getCause();
        }
        return current;
    }

    @FunctionalInterface
    private interface TimedCall<T> {
        T call(Duration timeout) throws Exception;
    }

    private record StubClient(
            TimedCall<ProductAggregator.Inventory> inventory,
            TimedCall<ProductAggregator.Price> price,
            TimedCall<List<ProductAggregator.Recommendation>> recommendations)
            implements ProductAggregator.CatalogClient {
        @Override
        public ProductAggregator.Inventory inventory(String sku, Duration timeout)
                throws Exception {
            return inventory.call(timeout);
        }

        @Override
        public ProductAggregator.Price price(String sku, Duration timeout)
                throws Exception {
            return price.call(timeout);
        }

        @Override
        public List<ProductAggregator.Recommendation> recommendations(
                String sku, Duration timeout) throws Exception {
            return recommendations.call(timeout);
        }
    }
}

    The fixture makes every dependency independently controllable. Tests should additionally verify timeout classification, fallback metrics, rejection after close, interrupt-aware client cancellation, and absence of virtual threads owned by the component after close.

    12. Tradeoffs¶

    Choice Strength Cost or limitation
    CompletableFuture graph Rich non-blocking composition Complex cancellation and execution placement
    Virtual thread per task Direct blocking style and cheap waiting Dependency limits still required; pinning can matter
    Fork/join Efficient recursive CPU parallelism Poor fit for unmanaged blocking and isolation
    Parallel stream Compact bulk parallelism Common-pool coupling and weak operational control
    Explicit platform pool Strong concurrency and resource bounds Expensive blocked threads and tuning burden
    Semaphore around dependency Limits the actual scarce resource Adds waiting/rejection policy and fairness choice

    13. Exercises¶

    Exercise 1: compose a dependent call¶

    authenticate(token) returns CompletableFuture<User>. loadCart(userId) returns CompletableFuture<Cart>. Return one future without blocking or nesting.

    Solution 
    CompletableFuture<Cart> cart(String token) {
    return authenticate(token)
            .thenCompose(user -> loadCart(user.id()));
}

    thenCompose preserves the dependency and flattens CompletableFuture<CompletableFuture<Cart>> into one completion stage. Failure or cancellation of authentication prevents the cart function from running.

    Exercise 2: bound virtual-thread calls¶

    Allow at most 20 concurrent calls and wait no more than the caller's remaining deadline for a permit.

    Solution 
    Response call(Request request, Deadline deadline) throws Exception {
    long nanos = deadline.remaining().toNanos();
    if (nanos == 0 || !permits.tryAcquire(nanos, TimeUnit.NANOSECONDS)) {
        throw new TimeoutException("dependency admission deadline expired");
    }
    try {
        Duration remaining = deadline.remaining();
        if (remaining.isZero()) {
            throw new TimeoutException("deadline expired after admission");
        }
        return client.call(request, remaining);
    } finally {
        permits.release();
    }
}

    The permit bounds dependency concurrency, not virtual-thread creation. The second remaining-time calculation prevents permit waiting from resetting the downstream timeout.

    Exercise 3: repair exceptional recovery¶

    The code future.exceptionally(error -> null).thenApply(Item::id) fails later with an unhelpful null dereference. Preserve absence explicitly.

    Solution 
    CompletableFuture<Optional<String>> id = future
        .thenApply(item -> Optional.of(item.id()))
        .exceptionally(error -> {
            Throwable cause = unwrap(error);
            if (cause instanceof ItemNotFoundException) {
                return Optional.empty();
            }
            throw new CompletionException(cause);
        });

    The type now represents documented absence. Unexpected failure still remains exceptional.

    14. Interview traps and questions¶

    Traps¶

    • Calling thenApply when the function already returns a future.
    • Assuming every continuation runs on the supplied first-stage executor.
    • Blocking the common fork/join pool with remote I/O.
    • Treating orTimeout as cancellation of the remote operation.
    • Pooling virtual threads to protect a database instead of limiting database calls.
    • Claiming virtual threads improve CPU-bound throughput.
    • Mutating shared state from a parallel stream.
    • Forking recursively below useful granularity.
    • Presenting preview structured-concurrency APIs as stable Java 21 APIs.
    • Ignoring that optional fallback can hide an outage without metrics.

    Questions to practice¶

    1. When do thenCompose and thenCombine express different dependency graphs?
    2. Which thread can execute a non-async continuation?
    3. How would you propagate one request deadline through three dependencies?
    4. Why can a timed-out CompletableFuture still consume a connection?
    5. When is a virtual thread preferable to a future chain?
    6. How do you cap a virtual-thread service against a 50-connection database pool?
    7. State the invariants that make shared-scratch parallel merge sort safe.
    8. How would you detect and investigate virtual-thread pinning on your deployed JDK?

    Summary¶

    • Composition models dependency; combination models independent results.
    • Explicitly own executors for blocking, CPU-heavy, or isolated work.
    • Preserve typed failure and define optional fallback narrowly.
    • A deadline is end-to-end; stage timeouts do not guarantee work cancellation.
    • Fork/join fits recursive CPU work when task granularity is measured.
    • Parallel streams trade control for concision and share global resources.
    • Create a virtual thread per task; limit scarce dependencies directly.
    • Treat pinning diagnostics and preview APIs as JDK-version-specific.
    • Test completion graphs with controllable gates and observable terminal outcomes.
