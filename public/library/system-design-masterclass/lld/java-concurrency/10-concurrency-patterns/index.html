    10. Concurrency Patterns¶

    Concurrency patterns are reusable answers to recurring ownership, coordination, and shutdown problems. The interview skill is not naming a pattern. It is choosing the smallest library-backed mechanism whose correctness argument fits the requirements.

    Goals¶

    By the end of this chapter, you should be able to:

    • map a requirement to an ownership and synchronization strategy;
    • state shared state, invariants, and linearization points before writing code;
    • compare blocking, lock-free reads, partitioned locking, and message passing;
    • reason about contention, starvation, interruption, cancellation, and shutdown;
    • test protocols with barriers and controlled dependencies rather than sleeps; and
    • recognize when a custom concurrency primitive is an unnecessary risk.

    The interview framework¶

    Use SCALE for every concurrent component:

    1. S - State: Which fields are shared? Who may mutate them?
    2. C - Contract: What must always be true? What may block or fail?
    3. A - Atomic event: At which instruction does each operation logically occur?
    4. L - Liveness: Can callers deadlock, starve, or wait forever? How does cancellation propagate?
    5. E - Evidence: Which deterministic test forces each important interleaving?
    Requirement Prefer Avoid by default
    Bounded handoff with backpressure BlockingQueue hand-written wait/notify queue
    Many reads, occasional whole-state update immutable snapshot + atomic publication locking every getter
    One owner per mutable object actor-style mailbox or confinement sharing internals across workers
    Independent keys with hot-key risk striping or ConcurrentHashMap one global lock
    Duplicate expensive requests memoization/single-flight check-then-act around a plain map
    Cooperative service shutdown two-phase termination Thread.stop, swallowed interrupts
    Irregular CPU work ForkJoinPool blocking I/O inside common pool tasks

    1. Producer-consumer¶

    A producer-consumer pipeline separates submission rate from processing rate. A bounded queue is usually part of the correctness contract: it limits retained work and turns overload into backpressure.

    import java.time.Duration;
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.BlockingQueue;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicBoolean;
import java.util.concurrent.locks.ReentrantReadWriteLock;
import java.util.function.Consumer;
import java.util.Objects;

public final class BoundedWorker<T> implements AutoCloseable {
    private final BlockingQueue<T> queue;
    private final Consumer<T> handler;
    private final Consumer<? super Throwable> failureReporter;
    private final AtomicBoolean accepting = new AtomicBoolean(true);
    private final List<Thread> workers = new ArrayList<>();
    private final ReentrantReadWriteLock lifecycle = new ReentrantReadWriteLock();

    public BoundedWorker(int capacity, int workerCount, Consumer<T> handler,
                         Consumer<? super Throwable> failureReporter) {
        if (capacity <= 0 || workerCount <= 0) throw new IllegalArgumentException();
        this.queue = new ArrayBlockingQueue<>(capacity);
        this.handler = Objects.requireNonNull(handler, "handler");
        this.failureReporter = Objects.requireNonNull(failureReporter, "failureReporter");
        for (int i = 0; i < workerCount; i++) {
            Thread worker = Thread.ofPlatform().name("bounded-worker-" + i).start(this::run);
            workers.add(worker);
        }
    }

    public boolean submit(T item, Duration timeout) throws InterruptedException {
        Objects.requireNonNull(item, "item");
        Objects.requireNonNull(timeout, "timeout");
        if (timeout.isNegative()) throw new IllegalArgumentException("negative timeout");
        long budgetNanos = saturatedNanos(timeout);
        long startedNanos = System.nanoTime();
        if (!lifecycle.readLock().tryLock(
                budgetNanos, TimeUnit.NANOSECONDS)) return false;
        try {
            if (!accepting.get()) return false;
            return queue.offer(item,
                    remainingNanos(startedNanos, budgetNanos),
                    TimeUnit.NANOSECONDS);
        } finally {
            lifecycle.readLock().unlock();
        }
    }

    private void run() {
        try {
            while (accepting.get() || !queue.isEmpty()) {
                T item = queue.poll(100, TimeUnit.MILLISECONDS);
                if (item != null) {
                    try {
                        handler.accept(item);
                    } catch (Throwable failure) {
                        reportFailure(failure);
                    }
                }
            }
        } catch (InterruptedException interrupted) {
            Thread.currentThread().interrupt();
        }
    }

    private void reportFailure(Throwable failure) {
        try {
            failureReporter.accept(failure);
        } catch (Throwable reportingFailure) {
            if (reportingFailure != failure) {
                failure.addSuppressed(reportingFailure);
            }
            failure.printStackTrace();
        }
    }

    private static long saturatedNanos(Duration timeout) {
        try {
            return timeout.toNanos();
        } catch (ArithmeticException tooLarge) {
            return Long.MAX_VALUE;
        }
    }

    private static long remainingNanos(long startedNanos, long budgetNanos) {
        long elapsed = System.nanoTime() - startedNanos;
        return elapsed <= 0L ? budgetNanos
                : elapsed >= budgetNanos ? 0L : budgetNanos - elapsed;
    }

    @Override public void close() throws InterruptedException {
        lifecycle.writeLock().lockInterruptibly();
        try { accepting.set(false); }
        finally { lifecycle.writeLock().unlock(); }
        for (Thread worker : workers) worker.join();
    }
}
    • Shared state: queue contents and accepting.
    • Invariant: queue size is in [0, capacity]; accepted items are either queued or handed to one consumer. This implementation is at-most-once after process failure, not durable delivery.
    • Linearization: successful offer; queue removal inside poll; shutdown begins at accepting.set(false) under the lifecycle write lock.
    • Cost/contention: O(1) queue operations; producers and consumers contend on queue coordination. A small capacity rejects bursts; a large one increases memory and stale work.
    • Liveness: one timeout covers lifecycle-lock acquisition and queue admission. The lifecycle lock makes admission atomic with respect to closing; close then drains accepted work. A blocked handler can still delay shutdown, so a production API should offer a bounded close and forced-stop policy.
    • Failure policy: a handler failure is reported and contained at the item boundary, so one bad item cannot silently kill a worker and strand accepted queue entries. Even a broken reporter is contained with a last-resort uncaught-style print; production code should route this fallback to service health telemetry.
    • Deterministic test: block the handler on a latch, fill the queue, assert a timed third submission fails, release the latch, close, and assert all accepted items ran exactly once. Also submit a throwing handler item and assert its failure is reported while a later item still runs.

    2. Guarded suspension¶

    An operation waits until a predicate over shared state becomes true. Always test the predicate in a loop: signals are hints, and another thread may consume the condition first.

    import java.time.Duration;
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

public final class OneShotGate<T> {
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition completed = lock.newCondition();
    private boolean done;
    private T value;

    public void complete(T result) {
        lock.lock();
        try {
            if (done) throw new IllegalStateException("already completed");
            value = result;
            done = true;
            completed.signalAll();
        } finally {
            lock.unlock();
        }
    }

    public T await(Duration timeout) throws InterruptedException {
        if (timeout.isNegative()) throw new IllegalArgumentException("negative timeout");
        long budgetNanos = saturatedNanos(timeout);
        long startedNanos = System.nanoTime();
        if (!lock.tryLock(budgetNanos, java.util.concurrent.TimeUnit.NANOSECONDS)) {
            throw new IllegalStateException("timed out");
        }
        try {
            while (!done) {
                long remaining = remainingNanos(startedNanos, budgetNanos);
                if (remaining == 0L) throw new IllegalStateException("timed out");
                completed.awaitNanos(remaining);
            }
            return value;
        } finally {
            lock.unlock();
        }
    }

    private static long saturatedNanos(Duration timeout) {
        try {
            return timeout.toNanos();
        } catch (ArithmeticException tooLarge) {
            return Long.MAX_VALUE;
        }
    }

    private static long remainingNanos(long startedNanos, long budgetNanos) {
        long elapsed = System.nanoTime() - startedNanos;
        return elapsed <= 0L ? budgetNanos
                : elapsed >= budgetNanos ? 0L : budgetNanos - elapsed;
    }
}
    • Invariant: done == false implies no observable result; done == true never becomes false.
    • Linearization: completion occurs when done becomes true while holding the lock; a completed read occurs while observing that state under the same lock.
    • Liveness: one overflow-safe elapsed-time budget bounds interruptible lock acquisition and condition waiting. signalAll is correct when several waiters need the one-shot result.
    • Tradeoff: CompletableFuture<T> already implements this one-shot protocol and should normally replace this educational class.

    3. Reader-writer locking¶

    Use a reader-writer lock only when reads are frequent, read-side work is long enough to amortize lock overhead, and concurrent reads materially improve throughput.

    import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.locks.ReentrantReadWriteLock;

public final class ReadMostlyCatalog {
    private final ReentrantReadWriteLock lock = new ReentrantReadWriteLock(true);
    private final Map<String, String> values = new HashMap<>();

    public String get(String key) {
        lock.readLock().lock();
        try { return values.get(key); }
        finally { lock.readLock().unlock(); }
    }

    public void put(String key, String value) {
        java.util.Objects.requireNonNull(key);
        java.util.Objects.requireNonNull(value);
        lock.writeLock().lock();
        try { values.put(key, value); }
        finally { lock.writeLock().unlock(); }
    }

    public Map<String, String> snapshot() {
        lock.readLock().lock();
        try { return Map.copyOf(values); }
        finally { lock.readLock().unlock(); }
    }
}
    • Invariant: every map mutation holds the write lock; returned snapshots cannot mutate the catalog.
    • Linearization: Map.get under the read lock and Map.put under the write lock.
    • Contention: get and put are O(1) average; copying a snapshot is O(n) and keeps the read lock for that copy. A writer excludes all readers. Fair mode reduces starvation risk and usually reduces throughput.
    • Trap: Java's ReentrantReadWriteLock does not support safe read-to-write upgrade. Release the read lock and revalidate under the write lock.

    4. Immutable snapshot¶

    If readers need a coherent whole-state view, publish a new immutable value atomically. Readers perform no locking and never observe a partially updated configuration.

    import java.util.Map;
import java.util.concurrent.atomic.AtomicReference;
import java.util.function.UnaryOperator;

public final class RoutingTable {
    public record Snapshot(long version, Map<String, String> routes) {
        public Snapshot { routes = Map.copyOf(routes); }
    }

    private final AtomicReference<Snapshot> current =
            new AtomicReference<>(new Snapshot(0, Map.of()));

    public Snapshot current() { return current.get(); }

    public Snapshot update(UnaryOperator<Map<String, String>> change) {
        while (true) {
            Snapshot before = current.get();
            Snapshot after = new Snapshot(Math.incrementExact(before.version()), change.apply(before.routes()));
            if (current.compareAndSet(before, after)) return after;
        }
    }
}
    • Invariant: a snapshot's map never changes; versions increase by one per successful publication.
    • Linearization: successful compareAndSet.
    • Cost/contention: reads are O(1); writes copy affected state and may retry. The updater must be side-effect-free because CAS retries can invoke it repeatedly.
    • Use when: state is modest, reads dominate, and cross-field consistency matters. Avoid for huge, frequently rewritten maps.

    5. Thread confinement and actor-style ownership¶

    One thread owns mutable state. Other threads submit messages and receive futures. This replaces data races with queue ordering, but does not make multi-actor workflows atomic.

    import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public final class AccountActor implements AutoCloseable {
    private final ExecutorService mailbox = Executors.newSingleThreadExecutor();
    private final Map<String, Long> balances = new HashMap<>();

    public CompletableFuture<Long> add(String account, long delta) {
        CompletableFuture<Long> reply = new CompletableFuture<>();
        mailbox.execute(() -> {
            try {
                long next = Math.addExact(balances.getOrDefault(account, 0L), delta);
                if (next < 0) throw new IllegalStateException("negative balance");
                balances.put(account, next);
                reply.complete(next);
            } catch (Throwable failure) {
                reply.completeExceptionally(failure);
            }
        });
        return reply;
    }

    @Override public void close() { mailbox.close(); }
}
    • Invariant: only the mailbox thread touches balances; balances are non-negative.
    • Linearization: mutation in the mailbox task, not task submission or future completion.
    • Cost/contention: O(1) average operations; no lock contention inside the actor, but one mailbox is a serial bottleneck. Partition actors by stable key to scale.
    • Shutdown: ExecutorService.close() waits for orderly termination in Java 21. Define admission behavior during closure and bound waits at the application boundary.

    Cancelling or completing the returned CompletableFuture does not retract the mailbox mutation. Submission after close throws synchronously. A callback attached to reply may execute inline on the mailbox worker, so it must not call blocking close() on that same mailbox. The unbounded mailbox and account map make this an ownership example, not a production capacity policy.

    6. Striped locking¶

    Striping maps many keys onto a fixed number of locks. It bounds lock memory while allowing unrelated stripes to proceed concurrently.

    import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.locks.ReentrantLock;

public final class StripedCounter<K> {
    private final ReentrantLock[] locks;
    private final Map<K, Long>[] maps;

    @SuppressWarnings("unchecked")
    public StripedCounter(int stripes) {
        if (stripes <= 0 || Integer.bitCount(stripes) != 1)
            throw new IllegalArgumentException("positive power of two");
        locks = new ReentrantLock[stripes];
        maps = (Map<K, Long>[]) new Map<?, ?>[stripes];
        for (int i = 0; i < stripes; i++) {
            locks[i] = new ReentrantLock();
            maps[i] = new HashMap<>();
        }
    }

    public long add(K key, long delta) {
        int stripe = spread(key.hashCode()) & (locks.length - 1);
        locks[stripe].lock();
        try {
            long next = Math.addExact(maps[stripe].getOrDefault(key, 0L), delta);
            maps[stripe].put(key, next);
            return next;
        } finally { locks[stripe].unlock(); }
    }

    private static int spread(int hash) { return hash ^ (hash >>> 16); }
}
    • Invariant: keys retain stable equality and hash codes, so a key always maps to one stripe; that stripe's map is accessed only under its lock.
    • Linearization: map update while holding the stripe lock.
    • Complexity: O(1) average and O(stripes + keys) memory. Colliding hot keys serialize. Resizing the stripe array would change ownership and requires global coordination.
    • Multi-key operations: acquire distinct stripe locks in ascending index order, deduplicate equal stripes, and release in reverse order to avoid deadlock.

    7. Memoization and single-flight¶

    Memoization reuses completed results. Single-flight additionally ensures concurrent requests for one key share one in-flight computation.

    import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ConcurrentHashMap;
import java.util.function.Function;

public final class SingleFlight<K, V> {
    private final ConcurrentHashMap<K, CompletableFuture<V>> flights = new ConcurrentHashMap<>();

    public CompletableFuture<V> execute(K key, Function<K, V> loader) {
        CompletableFuture<V> mine = new CompletableFuture<>();
        CompletableFuture<V> existing = flights.putIfAbsent(key, mine);
        if (existing != null) return existing.copy();

        try {
            Thread.ofVirtual().start(() -> {
                try { mine.complete(loader.apply(key)); }
                catch (Throwable failure) { mine.completeExceptionally(failure); }
                finally { flights.remove(key, mine); }
            });
        } catch (RuntimeException | Error failure) {
            mine.completeExceptionally(failure);
            flights.remove(key, mine);
            throw failure;
        }
        return mine.copy();
    }
}
    • Invariant: at most one mapped future exists per key; only its elected owner invokes the loader.
    • Linearization: putIfAbsent elects the owner. Removal uses (key, value) so an old completion cannot remove a newer flight.
    • Semantics: this deduplicates only overlapping calls; it is not a cache. Dependent copies isolate caller cancellation/completion from the root. Loader lifetime, distinct-key admission, and shutdown remain unbounded; a stronger service owns an executor and retains cancellation handles. Completion callbacks can run inline before root removal, so recursive same-key loads must not block awaiting themselves.
    • Test: hold the loader on a latch, issue 100 same-key calls, assert one invocation, release, and compare every result.

    8. Balking¶

    Balking rejects an operation when the object is not in a state where the operation makes sense. It does not wait for the state to change.

    import java.util.concurrent.atomic.AtomicReference;

public final class StartOnceService {
    enum State { NEW, RUNNING, STOPPED }
    private final AtomicReference<State> state = new AtomicReference<>(State.NEW);

    public boolean start() {
        if (!state.compareAndSet(State.NEW, State.RUNNING)) return false;
        // Publish or launch resources only for the elected starter.
        return true;
    }

    public boolean stop() {
        return state.compareAndSet(State.RUNNING, State.STOPPED);
    }

    public State state() { return state.get(); }
}
    • Invariant: legal transitions are NEW -> RUNNING -> STOPPED; no restart.
    • Linearization: successful CAS.
    • Tradeoff: a boolean result is suitable for an expected duplicate command. Throw when the state indicates caller misuse. If startup can fail after the CAS, add a STARTING state and explicit rollback/failure semantics.

    9. Two-phase termination¶

    First request stop; then let the worker observe that request, clean up, and terminate. Interruption is a wake-up/cancellation signal, not a substitute for state.

    import java.time.Duration;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.atomic.AtomicBoolean;

public final class PollingService implements AutoCloseable {
    private final AtomicBoolean stopping = new AtomicBoolean();
    private final CountDownLatch terminated = new CountDownLatch(1);
    private final Thread worker;

    public PollingService(Runnable pollOnce) {
        worker = Thread.ofPlatform().name("polling-service").start(() -> {
            try {
                while (!stopping.get()) pollOnce.run();
            } finally {
                terminated.countDown();
            }
        });
    }

    public boolean stop(Duration timeout) throws InterruptedException {
        if (timeout.isNegative()) throw new IllegalArgumentException("negative timeout");
        long nanos;
        try { nanos = timeout.toNanos(); }
        catch (ArithmeticException tooLarge) { nanos = Long.MAX_VALUE; }
        stopping.set(true);
        worker.interrupt();
        return terminated.await(nanos, java.util.concurrent.TimeUnit.NANOSECONDS);
    }

    @Override public void close() throws InterruptedException {
        if (!stop(Duration.ofSeconds(10))) throw new IllegalStateException("shutdown timed out");
    }
}
    • Invariant: the latch announces that the poll loop has exited and reached its final cleanup, not that the Java thread has terminated. An uncaught-exception handler may still run afterward.
    • Linearization: stop is requested when stopping becomes true; successful latch waiting publishes actions before countDown. Use join as well if the contract requires actual thread termination.
    • Caveat: pollOnce must cooperate with interruption or return regularly. Preserve interrupt status when catching InterruptedException at a layer that cannot complete cancellation.

    10. Work stealing¶

    Work stealing gives each worker a deque. Idle workers steal tasks from others, which balances irregular recursive work with less contention than one central queue. Java's ForkJoinPool implements this strategy.

    import java.util.concurrent.ForkJoinPool;
import java.util.concurrent.RecursiveTask;

public final class ParallelSum extends RecursiveTask<Long> {
    private static final int THRESHOLD = 10_000;
    private final long[] values;
    private final int from;
    private final int to;

    public ParallelSum(long[] values, int from, int to) {
        this.values = values;
        this.from = from;
        this.to = to;
    }

    @Override protected Long compute() {
        if (to - from <= THRESHOLD) {
            long sum = 0;
            for (int i = from; i < to; i++) sum += values[i];
            return sum;
        }
        int middle = (from + to) >>> 1;
        ParallelSum left = new ParallelSum(values, from, middle);
        left.fork();
        long right = new ParallelSum(values, middle, to).compute();
        return right + left.join();
    }

    public static long sum(long[] values, int parallelism) {
        try (ForkJoinPool pool = new ForkJoinPool(parallelism)) {
            return pool.invoke(new ParallelSum(values, 0, values.length));
        }
    }
}
    • Invariant: leaf ranges are disjoint and cover [0, values.length) exactly once.
    • Linearization: a pure aggregate has no shared-state update; invoke completion publishes the result.
    • Complexity: O(n) work, O(log n) span for balanced splits, plus task overhead. Tune the threshold from measurements.
    • Liveness: do not perform unmanaged blocking I/O in fork/join tasks. Use virtual threads for blocking request-style work or managedBlock for exceptional cases.

    When not to create a custom concurrency primitive¶

    Do not build a lock, semaphore, future, queue, executor, scheduler, or barrier in an interview solution unless implementing that primitive is the problem.

    Prefer a JDK primitive when it already provides:

    • a documented Java Memory Model happens-before relationship;
    • interruption and timeout behavior;
    • protection against spurious wakeups and lost notifications;
    • years of race, overflow, and cancellation fixes; and
    • operationally familiar behavior.

    A custom abstraction can be justified when the policy is domain-specific, such as per-tenant admission or dependency scheduling. Build that policy on java.util.concurrent; do not recreate its mechanism. If requirements include fairness, reentrancy, condition queues, lock-free progress, or recovery after owner death, explicitly narrow scope rather than casually promising them.

    Deterministic testing checklist¶

    • Inject executors, clocks, loaders, and blocking dependencies.
    • Use CountDownLatch, CyclicBarrier, or Phaser to establish a known interleaving.
    • Assert externally visible state and invariants, not thread names or incidental timing.
    • Give every blocking assertion a deadline so a failure terminates.
    • Repeat stress tests as additional evidence, not as the only proof.
    • Test interruption before waiting, during waiting, and during shutdown.
    • Test admission racing with shutdown.
    • Test exceptions at the point where ownership has changed.
    • Run static analyzers and race-oriented tools where available, but retain a written correctness argument.

    1. How would queue capacity follow from service time, memory budget, and latency SLO?
    2. When does StampedLock optimistic reading help, and what validation is mandatory?
    3. How would you prevent one hot actor or stripe from monopolizing capacity?
    4. Should single-flight cache failures? How do retry storms change the answer?
    5. What happens when an updater passed to a CAS loop has a side effect?
    6. How would you make two-phase termination drain accepted work without accepting new work?
    7. Why can a fair lock reduce throughput?
    8. How do virtual threads change thread-per-task economics without removing data races?
    9. Which operations in your design are linearizable, and which offer only eventual observation?
    10. What evidence would convince you that a custom primitive is necessary?

    Summary¶

    • Start with ownership and invariants, then select synchronization.
    • Bounded queues encode backpressure; unbounded queues hide overload.
    • Immutable publication and confinement often remove more races than intricate locking.
    • Striping improves independent-key concurrency but needs lock ordering for multi-key work.
    • Single-flight coordinates in-flight work; it is not automatically a cache.
    • Liveness, cancellation, and shutdown are API semantics, not cleanup details.
    • Prefer JDK concurrency primitives and keep custom code at the policy layer.
