    11. Classic Concurrency Problems: Solved Workbook¶

    These exercises are protocol-design drills. For each one, say what may happen next, encode that rule with a standard primitive, and identify the state transition that makes an operation take effect.

    Goals¶

    • translate output-order and resource constraints into explicit invariants;
    • produce complete Java 21 solutions with interruption and termination behavior;
    • compare semaphores, conditions, barriers, and fork/join decomposition;
    • identify linearization points and contention costs; and
    • design deterministic tests that do not rely on arbitrary sleeps.

    Workbook framework¶

    For each prompt use SCALE: shared State, correctness Contract, Atomic event, Liveness, and test Evidence. Unless stated otherwise, callbacks must return normally, remain short, and not re-enter the coordinator. A propagated failure stops only that caller, not its peers: the owner must observe failures promptly, cancel all peer tasks, and bound cleanup. These compact protocols are not reusable after partial failure unless explicitly stated.

    1. Alternating output¶

    Problem¶

    Two threads share one object. One calls printLeft and the other calls printRight. Invoke the supplied callbacks in the sequence L R L R ... exactly rounds times. Do not busy-spin.

    Constraints and reasoning¶

    • rounds >= 0; exactly one caller invokes each method.
    • A binary semaphore is a turn token. Initially the left side owns it.
    • Acquiring the next token before printing prevents duplicate turns; releasing transfers ownership.
    import java.util.concurrent.Semaphore;

public final class Alternator {
    private final int rounds;
    private final Semaphore left = new Semaphore(1);
    private final Semaphore right = new Semaphore(0);

    public Alternator(int rounds) {
        if (rounds < 0) throw new IllegalArgumentException("negative rounds");
        this.rounds = rounds;
    }

    public void printLeft(Runnable output) throws InterruptedException {
        for (int i = 0; i < rounds; i++) {
            left.acquire();
            output.run();
            right.release();
        }
    }

    public void printRight(Runnable output) throws InterruptedException {
        for (int i = 0; i < rounds; i++) {
            right.acquire();
            output.run();
            left.release();
        }
    }
}
    • State/invariant: permit ownership alternates; total permits are one between callbacks. The output prefix is always a prefix of (LR)^rounds.
    • Linearization: successful acquisition claims a turn; callback completion followed by release hands it over.
    • Complexity/contention: O(rounds) work, O(1) state, one handoff per symbol.
    • Liveness/cancellation: interruption cancels a waiter, but can strand its peer. A reusable library component would share a failure flag and release both waiters.
    • Deterministic test: append callbacks to a synchronized buffer, launch right before left through an executor, join with a deadline, and assert the exact string.

    Alternative: one ReentrantLock, one Condition per side, and a leftTurn boolean make lifecycle failure handling easier. Use while (!leftTurn) condition.await() and signal the opposite condition after toggling.

    2. Zero-even-odd¶

    Problem¶

    For positive n, three threads call zero, even, and odd. Produce 0 1 0 2 ... 0 n, using the supplied integer consumer.

    Solution¶

    import java.util.concurrent.Semaphore;
import java.util.function.IntConsumer;

public final class ZeroEvenOdd {
    private final int n;
    private final Semaphore zeroTurn = new Semaphore(1);
    private final Semaphore oddTurn = new Semaphore(0);
    private final Semaphore evenTurn = new Semaphore(0);

    public ZeroEvenOdd(int n) {
        if (n < 0) throw new IllegalArgumentException("negative n");
        this.n = n;
    }

    public void zero(IntConsumer output) throws InterruptedException {
        for (long value = 1; value <= n; value++) {
            zeroTurn.acquire();
            output.accept(0);
            (value % 2 == 0 ? evenTurn : oddTurn).release();
        }
    }

    public void odd(IntConsumer output) throws InterruptedException {
        for (long value = 1; value <= n; value += 2) {
            oddTurn.acquire();
            output.accept((int) value);
            zeroTurn.release();
        }
    }

    public void even(IntConsumer output) throws InterruptedException {
        for (long value = 2; value <= n; value += 2) {
            evenTurn.acquire();
            output.accept((int) value);
            zeroTurn.release();
        }
    }
}
    • Invariant: after every nonzero value, zero owns the next permit; after zero, exactly the required parity owns one permit.
    • Linearization: each permit acquisition fixes the next output position.
    • Cost: O(n) output and handoffs, O(1) state. The protocol intentionally serializes output.
    • Shutdown: interrupt all three tasks if any callback fails. Do not swallow InterruptedException.
    • Test: submit the methods in every launch order for n values 0, 1, 2, and 101; collect under a lock and compare with a sequential oracle.

    3. Concurrent FizzBuzz¶

    Problem¶

    Four worker methods print numbers, fizz, buzz, or fizzbuzz for the range 1..n. Every value must produce exactly one output in numeric order.

    Reasoning and solution¶

    The shared counter determines both eligibility and completion. One shared condition wakes waiters to recheck their individual predicates. Every waiter loops because a signal does not reserve the condition.

    import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;
import java.util.function.IntConsumer;

public final class ConcurrentFizzBuzz {
    private final int n;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition changed = lock.newCondition();
    private long current = 1;

    public ConcurrentFizzBuzz(int n) {
        if (n < 0) throw new IllegalArgumentException("negative n");
        this.n = n;
    }

    public void fizz(Runnable output) throws InterruptedException {
        runWhen(v -> v % 3 == 0 && v % 5 != 0, ignored -> output.run());
    }

    public void buzz(Runnable output) throws InterruptedException {
        runWhen(v -> v % 5 == 0 && v % 3 != 0, ignored -> output.run());
    }

    public void fizzBuzz(Runnable output) throws InterruptedException {
        runWhen(v -> v % 15 == 0, ignored -> output.run());
    }

    public void number(IntConsumer output) throws InterruptedException {
        runWhen(v -> v % 3 != 0 && v % 5 != 0, output);
    }

    private void runWhen(java.util.function.IntPredicate eligible, IntConsumer output)
            throws InterruptedException {
        while (true) {
            lock.lockInterruptibly();
            try {
                while (current <= n && !eligible.test((int) current)) changed.await();
                if (current > n) {
                    changed.signalAll();
                    return;
                }
                output.accept((int) current);
                current++;
                changed.signalAll();
            } finally { lock.unlock(); }
        }
    }
}
    • Invariant: current is the smallest unprinted value; exactly one predicate matches each value.
    • Linearization: incrementing current after the callback.
    • Contention: O(n) work and broadcasts. Four dedicated conditions reduce wakeups but increase protocol code.
    • Race to discuss: callbacks run under the lock to preserve output order. Slow callbacks block all workers. A sequenced output sink or prepared result can move safe work outside the lock.
    • Test: use callbacks that append tokens; start all workers behind a barrier; compare with a sequential FizzBuzz list and enforce a deadline.

    4. H2O grouping¶

    Problem¶

    Hydrogen and oxygen threads arrive independently. Release callbacks in groups containing exactly two H callbacks and one O callback. Groups must not overlap. Order inside a group does not matter.

    Solution¶

    import java.util.concurrent.Semaphore;
import java.util.concurrent.Phaser;

public final class H2O {
    private final Semaphore hydrogens = new Semaphore(2, true);
    private final Semaphore oxygens = new Semaphore(1, true);
    private final Object terminationLock = new Object();
    private volatile Throwable failure;
    private final Phaser molecule = new Phaser(3);

    public void hydrogen(Runnable output) throws InterruptedException {
        participate(hydrogens, output);
    }

    public void oxygen(Runnable output) throws InterruptedException {
        participate(oxygens, output);
    }

    private void participate(Semaphore slots, Runnable output)
            throws InterruptedException {
        try {
            slots.acquire();
            throwIfTerminated();
            output.run();
            int phase = molecule.arrive();
            int next = molecule.awaitAdvanceInterruptibly(phase);
            if (next < 0) throwIfTerminated();
            if (slots == oxygens) {
                synchronized (terminationLock) {
                    throwIfTerminated();
                    hydrogens.release(2);
                    oxygens.release();
                }
            }
        } catch (InterruptedException interrupted) {
            terminate(interrupted);
            throw interrupted;
        } catch (RuntimeException | Error failed) {
            terminate(failed);
            throw failed;
        }
    }

    private void throwIfTerminated() {
        Throwable cause = failure;
        if (cause != null) throw new IllegalStateException("H2O coordinator terminated", cause);
    }

    private void terminate(Throwable cause) {
        synchronized (terminationLock) {
            if (failure != null) return;
            failure = cause;
            molecule.forceTermination();
            // Wake current and future semaphore callers so they observe termination.
            hydrogens.release(Integer.MAX_VALUE - hydrogens.availablePermits());
            oxygens.release(Integer.MAX_VALUE - oxygens.availablePermits());
        }
    }
}
    • Invariant: at most two H and one O pass permits in a phase; the next phase receives permits only after all three arrive.
    • Linearization: semaphore acquisition assigns a thread to a molecule; phase advance completes that molecule.
    • Complexity/contention: O(1) per atom and a three-party barrier per molecule. Fair semaphores reduce overtaking at a throughput cost.
    • Liveness/failure: insufficient atoms wait forever while the coordinator is healthy. Interruption or callback failure is fail-stop: one synchronized termination transition records the cause, terminates the phaser, and wakes semaphore waiters. Peers fail rather than forming later molecules from an uncertain phase. awaitAdvanceInterruptibly makes barrier waiting cancellable; the interrupted caller separately rethrows InterruptedException.
    • Test: submit shuffled atoms, block callbacks at a test barrier, and verify each consecutive completed phase contains exactly two H and one O.

    Only the oxygen participant replenishes the next group's slots, and only after observing phase advance. Releasing slots inside onAdvance is unsafe: that hook runs before the next phase is installed, so a newly admitted atom could arrive in the exhausted old phase. Cancellation can leave partial output and a callback already past its failure check may finish; termination is not rollback of output.

    flowchart LR
    S[Acquire two H slots and one O slot] --> C[Three callbacks finish]
    C --> A[Three arrivals advance phase]
    A --> O[O observes advance and releases next slots]
    O --> S
    S -. interrupt or callback failure .-> F[Fail stop and wake peers]
    C -. failure .-> F

    The arrows describe normal phase order, not atomic visibility of three characters. Chapter 5 develops a smaller non-cancellable-after-admission variant with the same Phaser; see Pattern: H2O grouping.

    5. Dining philosophers¶

    Problem¶

    Five philosophers repeatedly need their left and right forks before eating. Prevent deadlock. The API should not hold one fork while waiting without a global ordering rule.

    Solution: resource ordering¶

    import java.util.concurrent.locks.ReentrantLock;

public final class DiningTable {
    private final ReentrantLock[] forks = new ReentrantLock[5];

    public DiningTable() {
        for (int i = 0; i < forks.length; i++) forks[i] = new ReentrantLock(true);
    }

    public void dine(int philosopher, Runnable pickLeft, Runnable pickRight,
                     Runnable eat, Runnable putLeft, Runnable putRight)
            throws InterruptedException {
        if (philosopher < 0 || philosopher >= 5) throw new IllegalArgumentException();
        int left = philosopher;
        int right = (philosopher + 1) % 5;
        int first = Math.min(left, right);
        int second = Math.max(left, right);

        forks[first].lockInterruptibly();
        try {
            forks[second].lockInterruptibly();
            try {
                if (first == left) { pickLeft.run(); pickRight.run(); }
                else { pickRight.run(); pickLeft.run(); }
                eat.run();
                putLeft.run();
                putRight.run();
            } finally { forks[second].unlock(); }
        } finally { forks[first].unlock(); }
    }
}
    • Invariant: a fork is held by at most one philosopher; all threads acquire lower-numbered fork before higher-numbered fork.
    • Deadlock proof: a wait-for cycle would require strictly increasing fork numbers around a cycle, which is impossible.
    • Linearization: there is no single atomic dine; ownership of both forks becomes established at the second lock acquisition.
    • Liveness: fair locks reduce starvation risk but do not promise bounded completion under arbitrary scheduling. Interruptible acquisition supports cancellation.
    • Cost: O(1) work; neighbors contend while non-neighbors can eat concurrently.
    • Alternative: a four-permit waiter semaphore prevents all five philosophers from holding one fork. It is simpler but centralizes contention and still needs careful release on interruption.
    • Test: start five workers on a barrier, execute thousands of meals, track fork ownership atomically, fail on duplicate ownership, and require every worker to finish by a deadline.

    6. Bounded blocking queue¶

    Problem¶

    Implement a fixed-capacity FIFO queue with interruptible put and take. Do not use BlockingQueue for this exercise. Handle spurious wakeups.

    Solution¶

    import java.util.ArrayDeque;
import java.util.Deque;
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

public final class BoundedQueue<E> {
    private final int capacity;
    private final Deque<E> items = new ArrayDeque<>();
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notEmpty = lock.newCondition();
    private final Condition notFull = lock.newCondition();

    public BoundedQueue(int capacity) {
        if (capacity <= 0) throw new IllegalArgumentException("non-positive capacity");
        this.capacity = capacity;
    }

    public void put(E item) throws InterruptedException {
        if (item == null) throw new NullPointerException("item");
        lock.lockInterruptibly();
        try {
            while (items.size() == capacity) notFull.await();
            items.addLast(item);
            notEmpty.signal();
        } finally { lock.unlock(); }
    }

    public E take() throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (items.isEmpty()) notEmpty.await();
            E item = items.removeFirst();
            notFull.signal();
            return item;
        } finally { lock.unlock(); }
    }

    public int size() {
        lock.lock();
        try { return items.size(); }
        finally { lock.unlock(); }
    }
}
    • Invariant: 0 <= size <= capacity; removals preserve insertion order; all deque access holds the lock.
    • Linearization: addLast for put, removeFirst for take.
    • Complexity/contention: O(1) per operation, O(capacity) memory, one lock for both ends. Separate locks can improve throughput but complicate empty/full transitions.
    • Cancellation/shutdown: interrupted waiters make no state change. A closable queue needs a closed flag under the same lock, signalAll, rejection of future puts, and a documented drain policy.
    • Test: force full and empty states with latches; interrupt blocked producers/consumers; run multiple producers with unique sequence ranges and verify no loss, duplication, or per-producer reordering.

    7. Readers-writers¶

    Problem¶

    Build a small integer register that allows concurrent reads and exclusive writes. Prevent a continuous stream of new readers from indefinitely bypassing a waiting writer.

    Solution: writer-aware monitor¶

    import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;
import java.util.function.IntSupplier;

public final class WriterAwareRegister {
    private final ReentrantLock lock = new ReentrantLock(true);
    private final Condition mayRead = lock.newCondition();
    private final Condition mayWrite = lock.newCondition();
    private int readers;
    private int waitingWriters;
    private boolean writing;
    private int value;

    public int read() throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (writing || waitingWriters > 0) mayRead.await();
            readers++;
        } finally { lock.unlock(); }
        try { return value; }
        finally {
            lock.lock();
            try {
                readers--;
                if (readers == 0) mayWrite.signal();
            } finally { lock.unlock(); }
        }
    }

    public int write(IntSupplier update) throws InterruptedException {
        lock.lockInterruptibly();
        try {
            waitingWriters++;
            try {
                while (writing || readers > 0) mayWrite.await();
            } finally {
                waitingWriters--;
                if (!writing && waitingWriters == 0) mayRead.signalAll();
                else if (!writing && readers == 0) mayWrite.signal();
            }
            writing = true;
        } finally { lock.unlock(); }

        try { return value = update.getAsInt(); }
        finally {
            lock.lock();
            try {
                writing = false;
                if (waitingWriters > 0) mayWrite.signal();
                else mayRead.signalAll();
            } finally { lock.unlock(); }
        }
    }
}
    • State/invariant: writing excludes readers and another writer; readers >= 0; new readers wait behind queued writers.
    • Visibility: lock release/acquisition publishes value, although reading outside the bookkeeping lock makes the proof subtle. The active-reader protocol ensures no writer overlaps that read.
    • Linearization: read samples value; write assigns value while holding logical write ownership.
    • Liveness: writer preference bounds reader bypass but can starve readers under a continuous writer stream. Fair ReentrantReadWriteLock is the normal library choice.
    • Cancellation: removing the last waiting writer can make the reader predicate true without a write completing. Signal readers on that transition, including interruption; otherwise readers can remain asleep forever. The update callback must not re-enter read or write, which would wait on its own logical ownership.
    • Test: inject update callbacks blocked on latches, assert no reader enters during a write, assert two readers can overlap using a test hook in an extended API, and place a writer between reader waves.

    8. Parallel merge sort¶

    Problem¶

    Sort an int[] using divide-and-conquer parallelism. Bound task creation and avoid allocating a new array at every merge.

    Solution¶

    import java.util.concurrent.ForkJoinPool;
import java.util.concurrent.RecursiveAction;

public final class ParallelMergeSort {
    private static final int THRESHOLD = 8_192;

    public static void sort(int[] values, int parallelism) {
        if (parallelism <= 0) throw new IllegalArgumentException("parallelism");
        int[] scratch = new int[values.length];
        try (ForkJoinPool pool = new ForkJoinPool(parallelism)) {
            pool.invoke(new SortTask(values, scratch, 0, values.length));
        }
    }

    private static final class SortTask extends RecursiveAction {
        private final int[] a;
        private final int[] scratch;
        private final int lo;
        private final int hi;

        SortTask(int[] a, int[] scratch, int lo, int hi) {
            this.a = a; this.scratch = scratch; this.lo = lo; this.hi = hi;
        }

        @Override protected void compute() {
            if (hi - lo <= THRESHOLD) {
                java.util.Arrays.sort(a, lo, hi);
                return;
            }
            int mid = (lo + hi) >>> 1;
            invokeAll(new SortTask(a, scratch, lo, mid),
                      new SortTask(a, scratch, mid, hi));
            merge(a, scratch, lo, mid, hi);
        }
    }

    private static void merge(int[] a, int[] scratch, int lo, int mid, int hi) {
        int i = lo, j = mid, k = lo;
        while (i < mid && j < hi) scratch[k++] = a[i] <= a[j] ? a[i++] : a[j++];
        while (i < mid) scratch[k++] = a[i++];
        while (j < hi) scratch[k++] = a[j++];
        System.arraycopy(scratch, lo, a, lo, hi - lo);
    }
}
    • Invariant: sibling tasks own disjoint array and scratch ranges; both halves are sorted before their parent merges.
    • Linearization: sorting is a batch mutation rather than a concurrent object operation; successful invoke completion publishes the sorted array to the caller.
    • Complexity: O(n log n) work and O(n) scratch. With sequential merges, span satisfies S(n) = S(n/2) + O(n), hence O(n), not O(log n). Parallel speedup is limited by the serial root merge and memory bandwidth.
    • Cancellation/shutdown: pool closure follows completion. ForkJoinTask.cancel(true) does not interrupt its worker. Responsive cancellation needs an explicit shared token checked in splitting and merge loops, plus joining all children before returning the mutable array to the caller.
    • Test: compare random, sorted, reverse, duplicate-heavy, empty, and singleton arrays against Arrays.sort. Fix the random seed. Verify the input multiset as well as ordering.

    Cross-problem tradeoffs¶

    Primitive Best fit here Common interview mistake
    Semaphore fixed permits and turn tokens forgetting permit rollback after failure
    Condition state predicate under one lock using if instead of while
    Phaser/barrier reusable group completion ignoring party failure or interruption
    Lock ordering multiple resources deriving inconsistent order per caller
    Fork/join irregular CPU decomposition creating tiny tasks or blocking workers

    Interview follow-ups¶

    1. How does each solution behave if a callback throws?
    2. Which protocols remain reusable after interruption?
    3. Where would signal be correct, and where is signalAll required?
    4. Which fairness statement is guaranteed by the API, and which is only probable?
    5. Can the output callbacks run outside the lock without violating order?
    6. How would you add timed methods while preserving one absolute deadline?
    7. How would you prove the dining solution cannot deadlock?
    8. At what array size does parallel merge sort lose to Arrays.sort, and how would you measure it?
    9. How do virtual threads affect blocking cost but not protocol correctness?
    10. Which exercise should use a JDK class instead of custom code outside an interview?

    Summary¶

    • Model turns, eligibility predicates, resource ownership, and phase membership explicitly.
    • Wait in predicate loops and make interruption part of the contract.
    • Identify whether the linearization point is token acquisition, state mutation, or phase advance.
    • Deadlock freedom does not imply starvation freedom.
    • Deterministic barriers and injected callbacks expose interleavings more reliably than sleeps.
    • Outside a primitive-building exercise, prefer BlockingQueue, executor, future, and lock implementations from the JDK.
