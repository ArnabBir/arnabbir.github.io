    Network Calculations Workbook¶

    Use this workbook to turn network claims into testable capacity and latency decisions. Every problem carries units, states its simplifying assumptions, and ends with an operational implication.

    Working conventions¶

    • Network rates use decimal units: 1 Mbps = 1,000,000 bit/s and 1 MB = 1,000,000 bytes.
    • Address sizes use powers of two.
    • Unless stated otherwise, RTT includes the round trip but not application work.
    • Little's Law uses mean arrival rate and mean time in system. A p99 latency is not a valid substitute for the mean.
    • Protocol overhead is workload- and path-dependent. Treat each supplied percentage as a fixture, not a universal constant.
    • Round only after completing the calculation.

    Formula sheet¶

    Topic Formula
    IPv4 addresses in prefix 2^(32 - prefix_length)
    IPv6 addresses in prefix 2^(128 - prefix_length)
    Serialization delay bits / link_rate_bit_per_s
    One-way propagation delay distance_km / propagation_km_per_s
    Bandwidth-delay product rate_bit_per_s * RTT_s
    Window-limited throughput window_bytes / RTT_s
    Little's Law mean_in_flight = mean_rate * mean_time_in_system
    Retry amplification product of attempts at each retrying layer
    Goodput useful_payload / elapsed_time
    Wire efficiency useful_bytes / wire_bytes
    NAT churn ceiling usable_source_ports / non_reuse_seconds per source/destination tuple
    TLS cores handshakes_per_s * CPU_seconds_per_handshake
    Cross-zone cost billable_bytes * price_per_GB

    1. CIDR and address planning¶

    Problem 1: Count a subnet¶

    A service receives 10.42.16.0/20. How many IPv4 addresses exist? How many /24 blocks fit inside it?

    Worked solution

    Solution. The host width is 32 - 20 = 12 bits, so the prefix contains 2^12 = 4,096 addresses. Moving from /20 to /24 adds 4 prefix bits, so 2^4 = 16 /24 blocks fit. The arithmetic counts all addresses; platform reservations determine usable host count.

    Problem 2: Find the containing network¶

    Which /26 contains 192.0.2.141, and what is its address range?

    Worked solution

    Solution. A /26 has blocks of 2^(32 - 26) = 64 addresses. The fourth-octet boundaries are 0, 64, 128, and 192. Address 141 is in 192.0.2.128/26, covering 192.0.2.128 through 192.0.2.191. Do not automatically subtract two addresses when estimating a cloud subnet; reservation rules vary.

    Problem 3: Split failure domains¶

    Split 10.8.0.0/21 evenly across four zones. Give each resulting prefix.

    Worked solution

    Solution. Four equal pieces require 2 more prefix bits: /21 + 2 = /23. The subnets are 10.8.0.0/23, 10.8.2.0/23, 10.8.4.0/23, and 10.8.6.0/23. Each contains 512 addresses. Equal address space does not imply equal workload; capacity still needs per-zone headroom.

    Problem 4: Summarize routes¶

    Can 172.16.8.0/24, 172.16.9.0/24, 172.16.10.0/24, and 172.16.11.0/24 be represented by one prefix?

    Worked solution

    Solution. Four contiguous /24 blocks can form a /22 only when aligned on a multiple-of-four third octet. Eight is aligned, so the summary is 172.16.8.0/22, covering third octets 8 through 11. Announcing 172.16.8.0/21 would also include 12 through 15 and could black-hole unrelated traffic.

    Problem 5: Size dual-stack growth¶

    A zone needs 1,500 IPv4 interface addresses now and 40 percent growth. The platform reserves 5 addresses per subnet. Is a /21 sufficient?

    Worked solution

    Solution. Required interfaces are 1,500 * 1.40 = 2,100. A /21 contains 2,048 addresses and 2,043 after the fixture's reservations, so it is insufficient. A /20 contains 4,096, or 4,091 after reservations. Choose /20, then test whether blast-radius policy favors several smaller subnets instead.

    Problem 6: IPv6 hierarchy¶

    A company receives 2001:db8:1200::/40 and assigns one /48 per region. How many region prefixes are available, and how many /64 subnets fit in each region?

    Worked solution

    Solution. Region selection has 48 - 40 = 8 bits, giving 2^8 = 256 /48 prefixes. Each /48 has 64 - 48 = 16 subnet bits, giving 65,536 /64 subnets. The large count is for hierarchy and stable allocation, not permission to ignore route aggregation.

    2. Serialization, propagation, BDP, and windows¶

    Problem 7: Serialize an object¶

    How long does a 1.5 MB response take to serialize onto a 100 Mbps link, ignoring overhead and contention?

    Worked solution

    Solution. 1.5 MB * 8 = 12 Mbit; 12 Mbit / 100 Mbit/s = 0.12 s = 120 ms. This delay is paid at a bottleneck link even if propagation is near zero.

    Problem 8: Compare packet and object serialization¶

    A 1,500-byte packet and a 10 MB object traverse a 1 Gbps egress link. Find each serialization time.

    Worked solution

    Solution. Packet: 1,500 * 8 / 1e9 = 0.000012 s = 12 us. Object: 10,000,000 * 8 / 1e9 = 0.08 s = 80 ms. Packet latency can look excellent while large-response completion remains bandwidth-bound.

    Problem 9: Estimate propagation floor¶

    Two sites are 6,000 route-km apart. Use a fiber propagation speed of 200,000 km/s. What is the propagation-only RTT?

    Worked solution

    Solution. One way is 6,000 / 200,000 = 0.03 s = 30 ms; RTT is 60 ms. Routers, queuing, path inflation, serialization, and processing make observed RTT higher. A 20 ms cross-site SLO is physically inconsistent with this fixture.

    Problem 10: Calculate BDP¶

    A 2 Gbps path has an 80 ms RTT. How much data must be in flight to fill it?

    Worked solution

    Solution. 2e9 bit/s * 0.080 s = 160 Mbit = 20 MB. Flow and congestion windows must jointly permit about 20 MB in flight. More server threads cannot overcome a 4 MB transport window.

    Problem 11: Find a window-limited ceiling¶

    A flow has a 3 MB effective window and 75 ms RTT. What is its maximum throughput before loss and overhead?

    Worked solution

    Solution. 3,000,000 bytes / 0.075 s = 40 MB/s = 320 Mbps. On a 1 Gbps link, this flow can use at most 32 percent of capacity under the simplified fixture.

    Problem 12: Parallel flows and fairness¶

    Four independent flows each have the 3 MB window from Problem 11 over the same 1 Gbps bottleneck. What aggregate does the window math suggest, and what is the actual ceiling?

    Worked solution

    Solution. Window math suggests 4 * 320 = 1,280 Mbps, but the shared link caps aggregate wire throughput at 1,000 Mbps before overhead. The flows now compete through congestion control. Adding connections can consume a larger share of a shared bottleneck; it does not create capacity.

    3. Handshakes, payload efficiency, and goodput¶

    Problem 13: Fresh HTTPS request latency¶

    DNS is warm. RTT is 45 ms, TCP setup costs 1 RTT, TLS 1.3 costs 1 RTT after TCP, server work is 30 ms, and the response returns in one final RTT. Estimate completion time.

    Worked solution

    Solution. 3 * 45 + 30 = 165 ms. A warm connection removes the first two RTTs and gives roughly 45 + 30 = 75 ms. This simplified serial model does not include TCP/TLS implementation overlap.

    Problem 14: QUIC handshake comparison¶

    For the same 45 ms path, assume a fresh QUIC connection can authenticate and become ready for request data in 1 RTT, followed by server work and one response RTT. Compare with Problem 13.

    Worked solution

    Solution. QUIC completion is 2 * 45 + 30 = 120 ms, 45 ms lower than the fixture's fresh TCP plus TLS path. This is not a universal HTTP/3 gain: resumed connections, 0-RTT replay constraints, packet loss, and implementation CPU change the result.

    Problem 15: Wire efficiency¶

    A batch sends 1,000 records. Each useful record is 900 bytes. Per-record framing is 36 bytes, and the batch adds 4,000 bytes of transport/TLS/IP overhead. Find wire bytes and efficiency.

    Worked solution

    Solution. Useful data is 1,000 * 900 = 900,000 bytes. Framing is 36,000 bytes, so wire data is 900,000 + 36,000 + 4,000 = 940,000 bytes. Efficiency is 900,000 / 940,000 = 95.74 percent. The 4.26 percent overhead must appear in bandwidth and cost estimates.

    Problem 16: Goodput under retransmission¶

    A transfer delivers 400 MB of useful data in 10 seconds. The sender puts 460 MB on the wire because of headers and retransmissions. Find useful goodput, wire rate, and efficiency.

    Worked solution

    Solution. Goodput is 400 MB / 10 s = 40 MB/s = 320 Mbps. Wire rate is 460 MB / 10 s = 46 MB/s = 368 Mbps. Efficiency is 400 / 460 = 86.96 percent. Actual egress is 15 percent higher than an estimate based only on application bytes; equivalently, that estimate is 13.04 percent below actual egress.

    Problem 17: Small-message overhead¶

    A telemetry sample has 80 useful bytes and incurs 70 bytes of combined framing. At 100,000 samples/s, compare useful and wire bandwidth.

    Worked solution

    Solution. Useful rate is 80 * 100,000 = 8 MB/s = 64 Mbps. Wire rate is 150 * 100,000 = 15 MB/s = 120 Mbps. Efficiency is only 80 / 150 = 53.33 percent. Batching can save bandwidth if its latency and failure coupling are acceptable.

    4. Conntrack, NAT, and TLS CPU¶

    Problem 18: NAT churn ceiling¶

    A NAT has 28,000 usable source ports for one source IP and destination tuple. Closed mappings cannot be reused for 60 seconds. What is the rough sustainable new-connection rate?

    Worked solution

    Solution. 28,000 / 60 = 466.7 connections/s is an idealized ceiling when active connection lifetime is negligible. Add mean active lifetime to the 60-second non-reuse period for a more realistic bound. A workload opening 900 connections/s to that tuple will eventually exhaust ports even if active concurrency appears low. Reuse connections or add independently usable source addresses.

    Problem 19: Add source addresses¶

    How many equivalent source IPs are needed for 3,000 new connections/s under Problem 18's assumptions, with 25 percent headroom?

    Worked solution

    Solution. Define 25 percent headroom as 25 percent installed capacity unused: required ceiling is 3,000 / 0.75 = 4,000/s. ceil(4,000 / (28,000 / 60)) = ceil(8.5714) = 9 source IPs. Adding 25 percent to load is a different policy, although rounding also gives nine here. Validate allocation skew and destination sharing.

    Problem 20: Conntrack occupancy¶

    A gateway sees 12,000 new flows/s. Mean tracked lifetime is 40 seconds, including closing states. Estimate mean conntrack occupancy. If the table limit is 600,000, what utilization does the mean imply?

    Worked solution

    Solution. Little's Law gives 12,000 * 40 = 480,000 entries. Mean utilization is 480,000 / 600,000 = 80 percent. Burst and lifetime tails can still overflow the table, so 80 percent mean is not safe proof.

    Problem 21: Time to exhaustion¶

    A conntrack table has 100,000 free entries. During an incident, arrivals exceed expirations by 8,000 entries/s. How long until the table fills if nothing changes?

    Worked solution

    Solution. 100,000 / 8,000 = 12.5 seconds. Autoscaling in minutes cannot help the immediate gateway. Shed new flows, stop retry amplification, or redirect only to known spare capacity.

    Problem 22: TLS handshake CPU¶

    A full TLS handshake consumes 1.2 ms of CPU on the server. Traffic creates 8,000 full handshakes/s. How many continuously busy CPU cores does handshake work require?

    Worked solution

    Solution. 8,000 * 0.0012 CPU-s = 9.6 cores. At a 60 percent CPU policy ceiling, provision at least 9.6 / 0.60 = 16 cores solely for handshake work under this fixture, before application and kernel costs.

    Problem 23: Resumption mix¶

    Full handshakes cost 1.2 ms CPU, resumed handshakes cost 0.25 ms, and the server receives 10,000 handshakes/s with an 80 percent resumption hit rate. Find total handshake cores.

    Worked solution

    Solution. Full rate is 2,000/s and resumed rate is 8,000/s. CPU is 2,000 * 0.0012 + 8,000 * 0.00025 = 2.4 + 2.0 = 4.4 cores. Losing the resumption cache would raise this to 12 cores, so cache health is capacity evidence, not a minor optimization.

    5. Pools, queues, and retries¶

    Problem 24: Pool concurrency from the mean¶

    A service makes 18,000 dependency calls/s. Mean dependency time is 22 ms. Estimate mean useful concurrency.

    Worked solution

    Solution. 18,000/s * 0.022 s = 396 calls in flight. Begin load testing near this concurrency with bounded acquisition, burst allowance, and a downstream ceiling. Do not calculate pool occupancy with the 180 ms p99; Little's Law requires the mean time.

    Problem 25: Why p99 is not the mean¶

    Problem 24 has p99 latency 180 ms. A team sizes the pool as 18,000 * 0.180 = 3,240. What is wrong with that conclusion?

    Worked solution

    Solution. The multiplication is arithmetically correct but semantically wrong: 3,240 would be the mean concurrency only if 180 ms were the mean time. The measured mean predicts 396. The p99 still matters for acquisition deadlines, tail risk, and burst tests, but using it in Little's Law can inflate the pool and overload the dependency.

    Problem 26: Queue fill time¶

    A pool serves 14,000 calls/s while arrivals spike to 19,000/s. Its waiting queue holds 7,500 calls. How quickly does it fill?

    Worked solution

    Solution. Net growth is 19,000 - 14,000 = 5,000 calls/s. Fill time is 7,500 / 5,000 = 1.5 seconds. A 30-second autoscaling response arrives too late; admission control and early shedding are required.

    Problem 27: Layered retry amplification¶

    A mobile client makes up to 3 attempts, an edge makes up to 2, and a service library makes up to 2. How many dependency attempts can one logical operation produce?

    Worked solution

    Solution. 3 * 2 * 2 = 12 attempts. At 5,000 logical operations/s, the theoretical attempted rate is 60,000/s. Assign one retry owner and a shared attempt/deadline budget.

    Problem 28: Retry load during failure¶

    Normal traffic is 20,000 operations/s. Thirty percent receive a retryable error and each affected operation makes one retry. Ignore retry success and latency. What attempted rate reaches the dependency?

    Worked solution

    Solution. Original rate is 20,000/s. Retry rate is 20,000 * 0.30 = 6,000/s, so attempted rate is 26,000/s, a 30 percent increase exactly when capacity is impaired. A retry budget capped at 5 percent of normal traffic would permit only 1,000 retries/s.

    6. DNS, failover, TURN, anycast, and cost¶

    Problem 29: DNS migration hold time¶

    The old DNS TTL was 20 minutes. At 12:00 the team lowers it to 30 seconds. When is the earliest well-behaved cache that fetched just before 12:00 expected to expire the old value?

    Worked solution

    Solution. Near 12:20, because the cache retains the TTL attached to the answer it already has. The new 30-second TTL affects later answers. Expiration does not guarantee removal from all responses: a resolver's serve-stale policy can extend use during failures. Endpoint removal must also wait for connection drain and account for resolver floors and client caches.

    Problem 30: Load-balancer failover headroom¶

    Three zones each receive 10,000 requests/s and have a tested safe ceiling of 16,000/s. Can the system lose one zone without shedding?

    Worked solution

    Solution. After one-zone loss, 30,000/s spreads across two zones, or 15,000/s each under perfect balance. That is below 16,000/s with only 1,000 / 16,000 = 6.25 percent remaining headroom. It passes steady arithmetic but is operationally fragile under skew, retries, or cold caches. A policy requiring 20 percent post-failover headroom would cap each survivor at 12,800/s and fail this design.

    Problem 31: Drain duration¶

    A target has 24,000 established connections. Clients naturally close 300 connections/s, while 40 new connections/s still arrive because one discovery cache is stale. Estimate net drain time if rates remain constant.

    Worked solution

    Solution. Net drain is 300 - 40 = 260 connections/s. Time is 24,000 / 260 = 92.3 seconds. If long-lived connections do not follow the mean, enforce a maximum drain deadline and close them in bounded batches with reconnect jitter.

    Problem 32: TURN relay capacity¶

    During a video event, 18,000 calls require TURN. Each call has two directions with an average 1.2 Mbps media rate per direction. Add 15 percent protocol and safety overhead. What relay bandwidth is required?

    Worked solution

    Solution. Each call contributes 2 * 1.2 Mbps = 2.4 Mbps to relay ingress and the same amount to relay egress because every relayed media bit enters and leaves the relay. Per direction, load is 18,000 * 2.4 Mbps = 43.2 Gbps; with overhead, each direction requires 43.2 * 1.15 = 49.68 Gbps. The relay therefore needs at least 49.68 Gbps ingress and 49.68 Gbps egress, or 99.36 Gbps aggregate RX plus TX processing if a platform reports their sum. Confirm whether NIC and provider limits are full-duplex, per direction, or aggregate and whether billing counts ingress, egress, or both.

    Problem 33: Anycast catchment shift¶

    An anycast site normally serves 220 Gbps. On withdrawal, 55 percent shifts to site B, 30 percent to C, and 15 percent to D. Current loads and safe ceilings are B 500/650, C 300/390, and D 140/210 Gbps. Which site overloads?

    Worked solution

    Solution. Shifted loads are B 121, C 66, and D 33 Gbps. New totals are B 621, C 366, and D 173 Gbps. None exceeds its ceiling, but remaining headroom is B 29, C 24, and D 37 Gbps. B has only 4.46 percent ceiling headroom and is the first concern under route variance or retries.

    Problem 34: Cross-zone service cost¶

    A service sends 75,000 responses/s averaging 32 KB. Forty percent cross a zone boundary. Assume one billable transfer direction and $0.01/GB, with decimal units. Estimate daily cross-zone bytes and cost.

    Worked solution

    Solution. Total response rate is 75,000 * 32,000 = 2.4 GB/s. Cross-zone rate is 2.4 * 0.40 = 0.96 GB/s. Daily transfer is 0.96 * 86,400 = 82,944 GB; cost is $829.44/day, or about $24,883 per 30-day month. Include requests, replicas, retries, and bidirectional billing when they apply.

    Problem 35: Locality versus resilience¶

    Changing routing lowers cross-zone traffic in Problem 34 from 40 percent to 10 percent, but requires 12 extra instances at $180 each per month. What is the simple monthly delta?

    Worked solution

    Solution. Avoided transfer is 75 percent of $24,883, or about $18,662/month. Extra compute costs 12 * $180 = $2,160/month. Simple net savings are about $16,502/month. The decision still needs zone-failure tests: strict locality can strand capacity or amplify a zonal outage.

    Problem 36: Combined incident budget¶

    A service has a 700 ms deadline and 80 ms response reserve. A fresh connection costs 2 RTTs before a request can start. RTT is 90 ms, and mean server work is 250 ms. How much budget remains for queueing and one backoff? Can a 250 ms retry fit sequentially?

    Worked solution

    Solution. Assume symmetric transit: after setup the request still needs 90/2 = 45 ms to reach the server. The 80 ms response reserve covers 45 ms return transit and 35 ms other return work. Usable budget is 620 ms; setup, outbound transit and service consume 180 + 45 + 250 = 475 ms, leaving 145 ms, not 190 ms. Another 250 ms service attempt cannot fit even on a reused connection. These means are not guarantees; report unknown/pending for ambiguous effects, not an unconditional retry signal.

    Review checklist¶

    • I wrote units beside every input and intermediate result.
    • I separated useful bytes from wire bytes.
    • I separated propagation, serialization, setup, queueing, and service time.
    • I used mean time, not p99, in Little's Law.
    • I identified the tuple or scope behind every NAT limit.
    • I converted retry policy into attempted dependency load.
    • I modeled stale DNS and long-lived connections during change.
    • I checked post-failover headroom, not only normal utilization.
    • I included TURN and cross-zone traffic in network cost.
    • I tied each result to a design, alert, test, or rollout gate.
