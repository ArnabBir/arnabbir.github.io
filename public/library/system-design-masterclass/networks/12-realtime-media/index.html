    12. Real-Time Delivery and Interactive Media¶

    “Real time” covers different contracts. A dashboard may tolerate seconds and replay events over one-way HTTP. Chat needs bidirectional delivery and reconnection semantics. Interactive audio and video need latency-sensitive, loss-tolerant media transport, congestion control, and relay capacity. Choose the mechanism from directionality, latency, replay, network reachability, and failure behavior.

    Learning goals¶

    • Explain WebSocket upgrade, framing, masking, fragmentation, liveness, close, and replay requirements.
    • Operate Server-Sent Events (SSE) through buffering proxies and resume with Last-Event-ID.
    • Design long polling without overlap, gaps, or synchronized reconnect waves.
    • Separate WebRTC signaling from media and trace ICE, STUN, TURN, and candidate selection.
    • Explain DTLS-SRTP, RTP/RTCP, jitter buffers, NACK, and forward error correction (FEC).
    • Choose peer-to-peer, selective forwarding unit (SFU), or broadcast delivery from fan-out and latency.
    • Calculate SFU and TURN bandwidth with protocol and failure headroom.
    • Define evidence, L5/L6 depth, and common traps.

    1. Choose the delivery contract first¶

    Mechanism Direction Typical transport Server state Best fit Key limitation
    long polling request/response, repeated HTTP pending request + cursor broad compatibility, sparse events repeated headers and reconnect churn
    SSE server to client long-lived HTTP response stream subscription + replay cursor browser notifications, progress, feeds browser API is one-way; proxy buffering matters
    WebSocket bidirectional messages framed protocol after HTTP handshake connection/session state chat, control, collaborative updates replay and reconnect are application concerns
    WebRTC data/media bidirectional peer media/data ICE-selected UDP/TCP paths, secured media signaling plus media/session state interactive audio/video NAT traversal, congestion, codec, and relay complexity
    segmented streaming server/CDN to viewer HTTP object delivery manifests/segments massive video audiences higher latency than interactive media

    The canonical Video Conferencing case study integrates SFUs, moderation, recording, and regional topology. The YouTube case study covers upload and CDN-based video playback. This chapter explains transport mechanics and does not duplicate those systems.

    For application-level delivery contracts, replay, fan-out, and gateway ownership, use the canonical Realtime Updates pattern.

    2. Shared invariants¶

    1. A connection is not a durable session. Reconnect creates a new connection epoch.
    2. Delivery claims state their scope: connection-local ordering, at-most-once attempt, replayable event log, or durable consumer acknowledgment.
    3. Every buffer has byte, message, time, and ownership bounds.
    4. Slow consumers have an explicit policy: backpressure, coalesce, drop, spill, or disconnect.
    5. Liveness detects a failed path within a stated interval without making heartbeat traffic an overload source.
    6. Reconnect uses exponential backoff, jitter, admission control, and a resumable identity where continuity matters.
    7. Media packets that miss their playout deadline are useless; reliability mechanisms remain deadline-aware.
    8. Relay and SFU egress are provisioned from peak concurrent bitrate and failure scenarios, not daily averages.

    3. WebSocket mechanism¶

    Handshake¶

    A client starts an HTTP/1.1 Upgrade handshake with Upgrade: websocket, Connection: Upgrade, version 13, and a fresh Sec-WebSocket-Key. The server returns status 101, Upgrade: websocket, and a derived Sec-WebSocket-Accept. The accept value proves protocol participation; it is not authentication. The connection then carries WebSocket frames rather than HTTP messages. Extended CONNECT provides WebSockets over HTTP/2 when client, proxy, and server support RFC 8441.

    GET /v1/chat HTTP/1.1
Host: api.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Version: 13
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Origin: https://app.example.com
Authorization: ...

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: ...

    Authenticate and authorize before or immediately after upgrade. For browsers, validate Origin against an allow list; it is a browser-origin signal, not a substitute for credentials. Avoid long-lived bearer tokens in query strings because URLs leak through logs and history. Define token refresh and revocation for connections that outlive token validity.

    The Authorization header illustrates a non-browser client: native browser WebSocket constructors cannot set arbitrary headers. Use a reviewed cookie/origin policy or bounded post-upgrade authentication; allow no effects before auth and expire unauthenticated sockets promptly. The sample nonce is not reusable in production. HTTP/2 extended CONNECT uses a successful 2xx, not 101/Upgrade.

    Framing¶

    WebSocket provides text and binary messages over frames. A message may be fragmented across a first data frame and continuation frames. Control frames, close, ping, and pong, have special constraints and may appear between fragments. Client-to-server frames are masked; server-to-client frames are not. Masking is not encryption; use wss for TLS.

    TCP byte stream
  [binary FIN=0][continuation FIN=0][PING][continuation FIN=1]
  <---------------- one fragmented message ---------------->

    Enforce maximum frame, message, decompressed-message, and fragmentation counts. Validate UTF-8 for text. A compressed tiny wire message can expand dramatically; negotiate extensions deliberately and cap decompression. Use one logical writer or a library-supported concurrency model so fragments from different messages do not interleave incorrectly.

    Liveness and close¶

    TCP can remain apparently established after a peer or path disappears. Protocol Ping/Pong measures transport-peer responsiveness. Browser JavaScript does not directly expose WebSocket control Ping/Pong, so an application heartbeat uses ordinary messages with correlation IDs. An application acknowledgment can additionally prove the handler ran; neither proves durable business processing. Choose intervals above normal jitter and coordinated with proxy/NAT idle limits. Add randomized phase so millions of clients do not ping simultaneously.

    stateDiagram-v2
  [*] --> Connecting
  Connecting --> Open: handshake and auth succeed
  Open --> Suspect: pong or application ack late
  Suspect --> Open: response arrives
  Suspect --> Reconnecting: liveness deadline expires
  Open --> Closing: local or remote close
  Closing --> Closed: close handshake or timeout
  Reconnecting --> Open: new epoch and resume
  Reconnecting --> Closed: session expires

    A graceful close exchanges close control frames, then closes transport. A lost path may prevent the handshake; enforce a bounded close timeout. Record close code and initiator, but do not treat every abnormal closure as server failure.

    Replay and session continuity¶

    WebSocket itself offers no durable replay across reconnection. Add application envelopes:

    {"stream":"room-42","epoch":8,"eventId":10421,"type":"message","payload":{}}

    The client stores the last applied event ID and reconnects with a resume cursor. The server replays from a retained log, then switches atomically to live delivery so events are neither skipped between replay and subscription nor reordered. If the cursor expired, return an explicit reset requiring a snapshot plus a new cursor. Deduplicate by event ID; an acknowledgment can represent transport receipt, application apply, or durable processing: name which one.

    For client commands, include command IDs and session epochs. Replayed commands must be idempotent or return their existing result. A higher connection epoch fences delayed traffic from an old connection.

    Fencing requires a trusted session authority and an atomic current-epoch check at the effect sink. A client-incremented field, or a gateway check followed by an unguarded write, does not exclude an old connection's effect.

    4. Server-Sent Events¶

    SSE is a UTF-8 event stream served as text/event-stream. Fields include data, event, id, and retry; a blank line dispatches an event. Multiple data lines join with newlines. Comment lines beginning with : can act as keepalives.

    HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

id: 10421
event: stock
data: {"item":"A7","available":12}

: keepalive

    Flush the entire path¶

    Writing in application code does not prove the client received an event. Language buffers, compression, reverse proxies, and CDN buffering can hold bytes. Configure streaming routes to avoid response buffering, disable transformations that delay chunks, and test time-to-event through the production path. Keepalive comments must exceed intermediary minimum chunk behavior and remain below idle timeouts without generating excessive traffic.

    Resume with Last-Event-ID¶

    When reconnecting, the browser can send Last-Event-ID from the last dispatched event. Treat it as a cursor scoped to the authenticated stream: not as authorization and not necessarily as a global sequence.

    sequenceDiagram
    autonumber
  participant C as Browser
  participant E as SSE endpoint
  participant L as Event log
  C->>E: GET /events
  E->>L: subscribe after cursor 10420
  E-->>C: id 10421, id 10422
  Note over C,E: path closes
  C->>E: GET /events + Last-Event-ID: 10422
  E->>L: replay after 10422, then tail
  E-->>C: id 10423 ...

    Define retention and cursor-expiry behavior. If only current state matters, coalesce updates and return a fresh snapshot on expiry. If every event matters, use durable storage and application acknowledgment outside browser-native SSE where necessary. Native EventSource has constrained request customization in browsers; credential and authorization design must account for the actual client API and origin policy.

    5. Long polling¶

    The client sends GET /events?after=cursor. The server responds when an event is available or a bounded hold expires. The client immediately issues the next request with the last applied cursor.

    client                         server
  |-- GET after=90 ------------->| hold
  |<-- events 91..94 -------------|
  |-- GET after=94 ------------->| hold
  |<-- 204/no events at 25 s -----|
  |-- GET after=94 ------------->|

    Allow at most one outstanding poll per logical subscription unless the protocol defines ordering across overlaps. A timeout response is normal and should not advance the cursor. Bound pending polls per user/tenant and globally. Distinguish load-balancer idle timeout from application hold time; return before the shortest path timeout.

    Long polling needs the same replay and deduplication semantics as WebSocket/SSE. Without a cursor, a response lost between server and client creates ambiguity. Without stable ordering scope, concurrent polls can deliver out of order.

    6. Reconnect storms¶

    A regional proxy restart, certificate rotation, mobile carrier outage, or Wi-Fi recovery can disconnect millions of clients together. Immediate reconnect turns recovery into a second outage.

    bad:  1,000,000 reconnects at t = 0

good: client backoff + full jitter + server Retry-After/load hint
      admission tokens + session-resume cache protection
      staged proxy drain + randomized connection max age

    Assumption (illustrative): 1.2 million clients must reconnect over ten minutes. The unavoidable average is 1,200,000 / 600 s = 2,000 handshakes/s. At 4 ms CPU per authentication/handshake, that is eight CPU-seconds per wall second before application work. Provision above 2,000/s for variance, retries, normal arrivals, and a failed zone; cap admission so queues do not grow without bound.

    Clients use exponential backoff with full jitter and a maximum delay. Servers may return retry hints. If a minimum wait exceeds client policy or the useful deadline, defer or stop reconnecting under that policy instead of shortening the wait and retrying early. Preserve authenticated resume state only within bounded memory and expiry; otherwise a resume-cache stampede replaces a database stampede. Prioritize established sessions and critical control traffic over fresh optional subscriptions. Test full-fleet reconnect, not only steady-state connection count.

    7. WebRTC: signaling is separate from media¶

    WebRTC does not standardize the application signaling channel. The application uses HTTPS, WebSocket, or another mechanism to exchange session descriptions, ICE credentials/candidates, and control messages. Signaling authenticates the participant and meeting; media connectivity is negotiated separately.

    sequenceDiagram
    autonumber
  participant A as Client A
  participant S as Signaling service
  participant T as STUN/TURN
  participant F as Peer or SFU
  A->>S: authenticate, join, capabilities
  S-->>A: session authorization and ICE servers
  A->>T: gather server-reflexive/relay candidates
  A->>S: SDP and ICE candidates
  S-->>F: authorized description/candidates
  A->>F: ICE connectivity checks
  A->>F: DTLS handshake
  A->>F: SRTP/SRTCP media and control

    Session Description Protocol (SDP) communicates codecs, media sections, RTP parameters, fingerprints, and transport details. Treat it as untrusted structured input with size and count bounds. “Trickle ICE” sends candidates as discovered, reducing setup latency compared with waiting for complete gathering.

    8. ICE, STUN, and TURN¶

    Interactive Connectivity Establishment (ICE) gathers candidate addresses, exchanges them through signaling, checks candidate pairs, nominates a working pair, and monitors consent/connectivity.

    Candidate/path Learned from Meaning
    host local interfaces direct local address
    server-reflexive STUN response public mapped address observed through NAT
    peer-reflexive connectivity check mapped address learned during checks
    relay TURN allocation address on a relay that forwards packets

    STUN helps discover mapped addresses and test connectivity; it is not a media relay. TURN allocates relay transport when direct paths fail or policy requires relaying. TURN improves reachability at substantial bandwidth cost and must authenticate allocations, enforce quotas, expire permissions/channels, and defend against amplification/abuse.

    Preferred: client ===== direct UDP ===== peer/SFU
Fallback:  client ====> TURN relay ====> peer/SFU
                       ingress + egress billed/carried by relay

    ICE candidate priority prefers useful paths but actual selection also reflects checks and policy. Enterprise networks may force TURN over TCP or TLS; this increases reachability but TCP retransmission can conflict with media’s playout deadlines. Observe selected candidate type and transport rather than assuming most sessions are direct.

    9. DTLS-SRTP, RTP, and RTCP¶

    WebRTC media is protected with SRTP. DTLS authenticates the negotiated endpoint fingerprint and derives/export keys for SRTP according to the DTLS-SRTP profile. This provides transport security per peer connection. In an SFU topology, ordinary hop-by-hop SRTP terminates at the SFU; end-to-end frame encryption above SRTP is a separate design with tradeoffs for recording, moderation, and transcoding.

    RTP carries timestamped media packets with sequence numbers and synchronization source identifiers. Sequence numbers help detect loss and reorder packets; timestamps drive playout timing rather than serving as wall-clock timestamps. RTCP carries reception reports, sender timing, feedback, and control information used for synchronization and congestion/quality adaptation.

    encoder -> RTP packets -> network jitter/loss -> jitter buffer -> decoder -> playout
               ^                 |                    |
               |---- RTCP feedback / NACK ------------|

    Jitter buffer¶

    The receiver delays playout to absorb packet arrival variation. A larger buffer hides more jitter but adds interactive latency. Adapt within bounds from observed delay variation. Audio continuity usually takes priority over high video quality. Drop packets arriving after their playout deadline.

    NACK and retransmission¶

    Negative acknowledgment (NACK) asks for recent missing RTP packets. Retransmission helps only if round-trip time plus processing leaves time before playout. Senders/SFUs need a bounded recent-packet cache. During burst loss, unlimited NACKs can add congestion; deduplicate and rate-limit feedback.

    FEC¶

    Forward error correction sends redundant information so some loss can be recovered without a round trip. It consumes bandwidth even when no loss occurs but helps when RTT is too high for retransmission or loss is bursty within the code’s capability. Adapt FEC to path and media priority; combining aggressive retransmission and FEC can worsen congestion.

    Congestion and quality adaptation¶

    Estimate available bitrate from loss, delay, and transport feedback. Preserve audio, then screen-share legibility, then prioritized video. Use simulcast or scalable coding so an SFU can forward an appropriate layer without transcoding every stream. Apply hysteresis to avoid layer oscillation, coalesce keyframe requests, and shed low-priority video before queues create seconds of latency.

    10. Topologies: mesh, SFU, and broadcast¶

    Topology Publisher upload Server work Receiver download Fit
    peer mesh one encoded stream per peer, roughly O(N) signaling/relay only O(N) very small calls with reachable peers
    SFU one or several simulcast layers forwards selected packets, often no decode selected participant layers interactive multiparty meetings
    MCU/compositor usually one stream decodes/mixes/encodes one composed stream constrained clients, recording, legacy interop
    CDN broadcast one ingest transcode/package/cache adaptive segments huge audiences accepting added latency

    For N users in a full mesh, there are N*(N-1)/2 peer relationships and each user sends to N-1 peers. At 10 participants and 1.5 Mbps per outgoing encode, each publisher may need 13.5 Mbps: often impractical. An SFU lets a publisher send a bounded simulcast ladder once and moves fan-out to server egress.

    The SFU is primarily an egress and packet-processing system. It needs per-receiver congestion decisions, packet caches, subscription state, and failure headroom. Do not size it from participant count alone.

    11. SFU and TURN calculations¶

    SFU egress¶

    Assumption (illustrative): 20,000 concurrent participants each receive 2.2 Mbps of selected video/audio on average. Protocol, retransmission, and FEC add 20%. Normal SFU egress is 20,000 * 2.2 Mbps * 1.2 = 52.8 Gbps. With 30% evacuation headroom, provision at least 52.8 / 0.7 = 75.4 Gbps of usable fleet egress before additional maintenance and regional risk margins.

    Dividing by a nominal NIC rate is insufficient. Measure packets/s, encryption, forwarding-table lookups, kernel/network overhead, burst behavior, and safe sustained utilization. Reserve inter-SFU and recording traffic separately.

    TURN relay¶

    TURN sizing counts both sides of relayed traffic at the relay.

    Here each relayed user has one client-to-SFU allocation. Do not count both ends of one peer-to-peer leg again as independent traffic. RX+TX is processing load, not automatically billed egress or one direction's NIC capacity; check each full-duplex direction separately.

    Assumption (illustrative): 100,000 concurrent media sessions send 1.0 Mbps and receive 2.5 Mbps per user. Twelve percent require TURN. Each relayed payload byte crosses the relay boundary twice: once entering TURN and once leaving it. Aggregate relay-interface throughput is therefore 100,000 * 0.12 * (1.0 + 2.5) Mbps * 2 = 84 Gbps. Adding 20% protocol/retransmission overhead gives 100.8 Gbps. Surviving loss of one of three equal failure domains without overload requires each remaining domain to carry at least half of 100.8 Gbps, or 50.4 Gbps usable, plus maintenance margin.

    Do not confuse user media bitrate with aggregate relay-interface throughput: summing user send and receive counts both media directions, while multiplying by two counts the ingress and egress traversal of each direction at TURN. If a capacity metric deliberately measures only one interface or one traffic direction, name that scope and do not apply the aggregate factor again. Draw byte direction explicitly and count every relay interface once. Track allocation count, selected transport, ingress/egress bitrate, packets/s, allocation failures, abuse drops, and cost by region.

    12. Failures, evidence, and implications¶

    Failure Evidence Design implication
    proxy buffers SSE server write time is low; client event delay is periodic/large disable buffering/compression that delays flush; production-path test
    WebSocket half-open missing pong/application ack while socket appears open liveness deadline and bounded reconnect
    replay gap cursor jumps or retention expired atomic replay-to-live handoff; snapshot/reset contract
    slow consumer per-session queue bytes/age rise coalesce, drop, spill, or disconnect before process OOM
    reconnect storm handshake/auth rate spikes after fleet event jitter, retry hints, admission, staged drain, resume-cache protection
    ICE direct failure relay candidate selected; check-pair failure reasons regional TURN capacity and enterprise-network testing
    media freezes but signaling healthy RTP gap, jitter-buffer/NACK metrics separate signaling from media health and recovery
    audio degrades under video load queue delay/loss by media type prioritize audio and shed video layers
    NACK storm feedback and retransmit rate rise with loss deadline-aware bounded packet cache and feedback suppression
    SFU zone loss subscription migration and remaining egress jump reserve evacuation bandwidth and reconnect gradually
    TURN bill spike relay ratio/bitrate shifts by region/client version investigate path regression; quotas and routing policy

    Evidence must join control and media timelines: signaling state/epoch, ICE gathering/check duration, selected candidate pair and transport, DTLS setup, time to first audio/video, RTP loss/reorder/jitter, RTCP feedback, NACK/FEC/retransmit rate, jitter-buffer delay, encode bitrate/layers, SFU ingress/egress, slow-consumer drops, reconnect attempts, and close reasons. Protect privacy: do not log raw SDP, IP candidates, meeting content, or tokens without strict need and handling.

    The Notification System case study covers durable multi-channel fan-out; use it when “real time” actually means eventually delivered alerts rather than a live socket.

    13. L5, L6, and traps¶

    L5 expectations¶

    • Choose WebSocket, SSE, long polling, WebRTC, or segmented delivery from a stated contract.
    • Define connection/session identity, ordering scope, replay cursor, slow-consumer policy, and liveness.
    • Trace signaling, ICE, STUN/TURN, DTLS-SRTP, RTP/RTCP, and media feedback.
    • Quantify concurrent sessions, buffer memory, handshake recovery rate, SFU egress, and TURN relay load.
    • Describe production-path evidence and failure injection for reconnect, loss, jitter, relay fallback, and zone loss.

    L6 extensions¶

    • Design multi-region session placement, SFU cascading, TURN sovereignty, and evacuation capacity.
    • Establish fleet-wide reconnect control across clients, DNS, edge, auth, signaling, and media tiers.
    • Govern codecs, protocol changes, browser/client-version compatibility, privacy, and deprecation.
    • Balance quality, cost, fairness, accessibility, moderation, recording, and end-to-end encryption.
    • Build closed-loop capacity policy from relay ratio, media quality, regional egress, and failure forecasts with canary/rollback controls.

    Interview traps¶

    • Saying WebSocket guarantees replay or exactly-once delivery.
    • Treating the WebSocket accept key or browser Origin as authentication.
    • Ignoring fragmentation, decompression limits, and slow consumers.
    • Assuming an SSE write() flushed through every proxy.
    • Advancing a long-poll cursor on timeout or allowing overlapping unordered polls.
    • Reconnecting every client immediately after failure.
    • Saying STUN relays media or TURN only helps discovery.
    • Calling signaling the WebRTC media path.
    • Claiming DTLS-SRTP through an SFU is automatically end-to-end encryption among users.
    • Retrying media packets after their playout deadline.
    • Sizing an SFU by CPU or participants while ignoring egress and packets/s.
    • Calculating TURN from average users without relay ratio, both relay directions, overhead, locality, and failover.

    14. Exercises¶

    Exercise 1: design WebSocket replay¶

    A chat client applies event 500, loses the connection while event 501 may be in flight, and reconnects. Specify the protocol behavior.

    Solution¶

    Open after your attempt

    The client reconnects with room scope, authenticated session identity, a higher connection epoch, and after_event_id=500. The server reads a durable ordered log after 500 and atomically bridges replay to live subscription. If 501 had reached the old connection but was not applied, it is delivered again and deduplicated by event ID. If retention expired, the server returns an explicit snapshot/reset response. Client commands use separate idempotent command IDs; the new epoch fences delayed old-socket commands.

    Exercise 2: diagnose delayed SSE¶

    The application emits one 200-byte SSE event each second, but clients receive 20 events every 20 seconds. Server timestamps show prompt writes. What evidence and changes do you seek?

    Solution¶

    Open after your attempt

    Compare timestamps/bytes at application, sidecar, ingress, CDN, and client; inspect response buffering, compression, minimum chunking, caching, HTTP version, and idle policies. Configure text/event-stream routes for streaming and no inappropriate buffering/transformation, flush complete events, and use bounded comment keepalives if needed. Validate through the real production path; increasing application write frequency alone does not fix downstream buffering.

    Exercise 3: bound reconnect recovery¶

    Three million clients disconnect. Authentication safely handles 5,000 reconnects/s while preserving normal traffic. What is the fastest theoretical recovery and what policy is required?

    Solution¶

    Open after your attempt

    At the full safe reconnect allocation, 3,000,000 / 5,000 = 600 s, or ten minutes. Actual recovery needs longer for failed attempts, variance, and normal joins. Enforce server admission near the safe rate, return retry hints, and have clients use exponential backoff with full jitter. Staged drains and randomized connection age prevent recurrence. Measure queue age and reject rather than allowing millions of blocked handshakes.

    Exercise 4: calculate TURN capacity¶

    There are 60,000 concurrent users. Each sends 0.8 Mbps and receives 2.0 Mbps. Fifteen percent use TURN, and overhead is 25%. Calculate aggregate relay throughput using this model.

    Solution¶

    Open after your attempt

    Relayed users are 60,000 * 0.15 = 9,000. Per-user media is 0.8 + 2.0 = 2.8 Mbps; each byte enters and exits TURN, so aggregate relay-interface traffic is 2.8 * 2 = 5.6 Mbps per relayed user. Base throughput is 9,000 * 5.6 = 50.4 Gbps; with 25% overhead, 50.4 * 1.25 = 63 Gbps. Add regional imbalance, safe NIC/packets-per-second limits, maintenance, and failure-domain headroom before provisioning.

    Exercise 5: choose NACK or FEC¶

    A mobile audio path has 180 ms RTT and a 60 ms remaining playout margin when loss is detected. Should the receiver depend on retransmission?

    Solution¶

    Open after your attempt

    No. A NACK round trip cannot return the packet inside a 60 ms margin on a 180 ms RTT path. Prefer bounded FEC/redundancy appropriate to the codec and path, conceal loss, and adapt bitrate. NACK can still help paths with enough playout margin; both mechanisms must avoid adding congestion and prioritize audio continuity.

    Exercise 6: compare mesh and SFU¶

    Eight participants each send 1.2 Mbps video. Estimate each user’s upload in a full mesh and compare it with sending a 2.4 Mbps simulcast ladder to an SFU.

    Solution¶

    Open after your attempt

    In full mesh, each user sends seven copies: 7 * 1.2 = 8.4 Mbps upload, before overhead. With the assumed SFU ladder, upload is about 2.4 Mbps regardless of participant count, while SFU egress carries selected copies to receivers. The SFU improves client uplink scaling but transfers cost and failure responsibility to server egress, packet processing, and regional capacity.
