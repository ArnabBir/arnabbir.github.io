    09. Proxies and Load Balancing¶

    Proxies change who opens each connection, which identity is visible at each hop, and where policy executes. Load balancing is not merely “spread requests evenly.” It must preserve trust boundaries, protocol semantics, capacity limits, locality, and safe removal while connections and requests have different lifetimes.

    The canonical Global Load Balancer case study owns the complete service and control-plane design; this chapter supplies its data-path mechanics.

    Learning goals¶

    • Distinguish forward, reverse, and transparent proxies by who selects them and whose traffic they represent.
    • Define trusted forwarded-header handling instead of trusting client-supplied identity.
    • Choose L4 or L7 balancing from required visibility and protocol behavior.
    • Reason about TLS termination, re-encryption, passthrough, and identity at every hop.
    • Select and test balancing algorithms under HTTP/2 and other multiplexed protocols.
    • Design active health checks, passive outlier detection, locality, affinity, draining, and retries as one system.
    • Separate gateway, ingress, service discovery, and data-plane load-balancing responsibilities.

    1. The mechanism: one logical request, several transport legs¶

    client                  edge proxy                 service proxy             instance
  |-- TCP/TLS leg A ------>|                           |                         |
  |-- HTTP request ------->|-- TCP/TLS leg B -------->|                         |
  |                        |-- forwarded request ----->|-- TCP/TLS leg C ------>|
  |                        |                           |-- application request ->|

Identity visible by default:
leg A: client address       leg B: edge address         leg C: service-proxy address

    A proxy terminates one transport leg and creates another unless it performs transparent packet forwarding. Consequently, source IP, TLS peer identity, connection lifetime, congestion control, and failure scope can differ at every leg. Application code sees only what the immediate peer and an explicitly trusted identity chain provide.

    Proxy roles¶

    Role Selected by Represents Common purpose Primary trust question
    forward proxy client or client network clients egress policy, caching, anonymity, access control may this proxy act for this client?
    reverse proxy service operator origin services edge termination, routing, protection, balancing which client facts may the origin accept?
    transparent proxy network interception/routing neither endpoint explicitly policy without client configuration, sidecar interception can interception preserve destination and protocol semantics?

    A transparent proxy is transparent to configuration, not to physics. Interception still changes routing and may terminate connections. Original source and destination recovery is platform-specific; TLS remains opaque unless deliberately terminated.

    2. Invariants¶

    1. Untrusted clients cannot assert trusted hop identity. The first trusted proxy removes or overwrites identity-bearing forwarding headers received from an untrusted peer.
    2. Every hop has an authenticated peer or an explicit unauthenticated boundary. Source IP alone is not workload identity.
    3. A request uses one coherent route and policy snapshot. Mid-request configuration changes do not mix versions.
    4. Only eligible endpoints receive new work. Eligibility includes health, locality policy, protocol, capacity, deployment state, and tenant constraints.
    5. Draining removes new work before closing old work. Long-lived streams have a documented maximum drain policy.
    6. Retries do not create an unbounded second load balancer. Attempts share one deadline, retry budget, and replay-safety rule.
    7. No health mechanism can eject all capacity silently. Minimum healthy capacity, maximum ejection, and panic behavior are explicit.

    3. Forwarded identity is a trust-chain problem¶

    Common fields include standardized Forwarded, de facto X-Forwarded-For, X-Forwarded-Proto, and X-Forwarded-Host, plus proxy-to-proxy protocols that carry connection metadata. Their presence does not make them true.

    Internet client sends:
X-Forwarded-For: 10.0.0.7

Trusted edge receives peer 203.0.113.24 and rewrites:
Forwarded: for=203.0.113.24;proto=https;host=api.example.com

Internal proxy receives the edge as its authenticated peer and appends its hop.
Application accepts only the suffix produced by configured trusted proxies.

    Safe processing rule¶

    1. Determine whether the immediate peer belongs to the configured proxy trust set and, where possible, authenticate it with mTLS.
    2. If the peer is untrusted, discard inbound forwarding identity and construct a new chain from the observed connection.
    3. If the peer is trusted, parse with strict size and element bounds; reject malformed ambiguity.
    4. Walk from the nearest hop outward only through trusted proxies. The first untrusted address is the candidate client network address, not proof of a user identity.
    5. Keep authentication and authorization tied to credentials. Use client IP mainly for network policy, abuse signals, and audit with documented NAT/privacy limits.

    Host, scheme, and path normalization also cross a trust boundary. Generate redirects and absolute URLs from an allow-listed external origin, not arbitrary forwarded values. Ensure every proxy agrees whether it appends, overwrites, or rejects duplicate headers.

    4. L4 versus L7 balancing¶

    Property L4 transport balancer L7 application proxy
    sees addresses, ports, transport state; sometimes TLS ClientHello metadata method, authority, path, headers, status, RPC metadata
    routing unit flow/connection request or stream
    protocol coupling low high; parser and codec must match protocol
    TLS usually passthrough, NAT, or TCP proxy commonly terminates TLS; may re-encrypt upstream
    policy coarse auth, quotas, route matching, retries, transformations
    failure blast radius fewer parser features malformed messages, filters, and config can affect all traffic
    multiplexing visibility connection only individual HTTP/2 or RPC streams

    L4 fits encrypted passthrough, arbitrary TCP, and very high connection rates when per-request policy is unnecessary. L7 is required for path routing, request-level telemetry, gRPC method policy, content limits, and request-aware retries. A common stack uses L4 to distribute connections across an L7 proxy fleet, then L7 to select service endpoints.

    flowchart LR
  C[Clients] --> L4[L4 connection balancer]
  L4 --> P1[L7 proxy A]
  L4 --> P2[L7 proxy B]
  P1 --> S1[Service instance 1]
  P1 --> S2[Service instance 2]
  P2 --> S1
  P2 --> S2

    5. TLS placement and end-to-end identity¶

    Termination choices¶

    • Edge termination: The client authenticates the edge's presented public server identity. The edge decrypts requests and separately authenticates client credentials where required; it authenticates the upstream server on the next TLS leg.
    • TLS passthrough: The balancer routes opaque connections, often using destination address or ClientHello server name. The backend owns certificates and application-layer policy.
    • Mutual TLS upstream: The proxy and service authenticate workload identities. Decide whether the service authorizes the proxy, the original principal conveyed in a signed token, or both.
    • TLS bridging: The proxy terminates one TLS session and initiates another. This is not end-to-end TLS between client and service, even though every wire hop is encrypted.

    TLS termination makes plaintext available to the proxy process, memory, extensions, and observability pipeline. Minimize privileges, redact logs, bound body capture, rotate certificates, and separate certificate/config rollout from the request path. If client certificates terminate at the edge, never forward an unsigned “client certificate” header from arbitrary peers; pass a verified, integrity-protected identity assertion.

    6. Algorithms under connection multiplexing¶

    The unit matters¶

    Round robin over connections approximates round robin over work only when connections carry similar work. HTTP/2, gRPC, WebSocket, and database protocols violate that assumption: one connection may carry hundreds of concurrent streams or one long-lived hot session.

    Connection-level round robin:
proxy A <- one HTTP/2 connection, 400 active streams
proxy B <- one HTTP/2 connection,   4 active streams
proxy C <- one HTTP/2 connection,   2 active streams

Connection count says 1 : 1 : 1. Work says 400 : 4 : 2.
    Algorithm Useful when Failure mode
    round robin homogeneous short requests and endpoints ignores outstanding work and request cost
    weighted round robin stable known capacity ratios static weights lag degradation
    least connections connection work is comparable multiplexed streams and long idle sockets distort load
    least requests/streams proxy observes request lifecycle expensive requests still count as one
    power of two choices many endpoints, cheap load signal stale or incomparable load signals mislead
    EWMA latency latency correlates with congestion routes away from cold/new endpoints; mixes request classes
    random large homogeneous fleets variance at small fleet sizes
    consistent/rendezvous hash affinity and bounded remapping matter hot keys create hot endpoints; membership churn moves state

    Use a load measure close to the constrained resource: active streams, queued work, CPU-weighted cost, or explicit endpoint utilization. Keep admission limits even with an adaptive chooser; selection cannot create capacity.

    Calculation: why stream-aware balancing matters¶

    Assumption (illustrative): Four upstream HTTP/2 connections each permit 100 concurrent streams. A proxy has 300 active requests averaging 200 ms, while a second proxy has 30.

    The implied completion rates are approximately 300 / 0.2 s = 1,500 requests/s and 30 / 0.2 s = 150 requests/s if service time and steady-state assumptions hold. Both may report four connections. Connection-based balancing hides a 10x work difference. Prefer request-aware distribution across the proxy fleet or open enough independently distributed connections to reduce concentration; still measure active streams and queue delay.

    7. Health, outliers, and evidence¶

    Active and passive signals¶

    • Active health checks test readiness when user traffic is absent. They must exercise necessary dependencies without becoming an expensive synthetic workload.
    • Passive health observes connect failures, resets, protocol errors, and latency from real attempts. It detects path-specific failures but can confuse overload with host failure.
    • Readiness answers “may this endpoint receive new work now?” Liveness answers “should the process be restarted?” Combining them can turn a dependency outage into a restart storm.
    stateDiagram-v2
  [*] --> Warming
  Warming --> Healthy: readiness successes and warm-up complete
  Healthy --> Suspect: passive threshold crossed
  Suspect --> Ejected: confidence and fleet guard permit
  Suspect --> Healthy: recovery evidence
  Ejected --> Probing: ejection interval expires
  Probing --> Healthy: bounded successful probes
  Probing --> Ejected: probe fails
  Healthy --> Draining: deployment or discovery removal
  Draining --> Removed: no streams remain
  Draining --> ForcedClose: deadline with residual streams
  ForcedClose --> Removed: count disruptions and reconcile outcomes

    Outlier detection requires a minimum request volume, comparison within the same request class/locality, a bounded ejection percentage, and recovery probing. Otherwise one correlated dependency failure can eject every endpoint. Evidence should include:

    • eligible, healthy, suspect, ejected, warming, and draining endpoint counts;
    • attempts, active streams, queue delay, latency, and errors by endpoint and locality;
    • ejection reason, duration, false-ejection review, and panic-mode time;
    • retry attempts per logical request and retry success versus added load;
    • connection age, stream concentration, drain duration, and forced closures.

    8. Locality, affinity, draining, and retries¶

    Locality¶

    The health graph is a proposed policy, not Envoy's exact state machine. Envoy can uneject after an interval or active-check success; panic mode can select unhealthy hosts. Test those interactions and never let a capacity panic bypass authentication, revocation, or tenant policy.

    Prefer same-zone or same-region endpoints only while they retain failure headroom. Define spillover in priority order and reserve cross-zone bandwidth. Strict locality reduces latency and transfer cost but may overload a partial zone; global least-load can spread every request across failure domains and increase correlated blast radius.

    Affinity¶

    Affinity is justified by state locality, cache reuse, or ordered sessions: not by habit. Use a stable key with consistent or rendezvous hashing and bounded remapping. Provide fallback when the target is unhealthy. Hot tenants need key splitting, per-tenant admission, or replication; hashing alone preserves the hotspot.

    Draining¶

    The sequence is:

    mark not eligible for new requests
        -> advertise drain / send graceful protocol signal
        -> wait for bounded in-flight work
        -> cancel or migrate according to protocol contract
        -> close transport
        -> remove endpoint

    For HTTP/2 and gRPC, graceful shutdown communicates the last accepted stream before closure. For WebSockets, “wait until empty” may never complete; send an application reconnect hint, allow a grace window, then close. Preserve session epoch so a late old connection cannot overwrite state from its replacement.

    Retries¶

    Retry policy belongs above endpoint selection but below the logical request contract. Retry only a replay-safe operation, select a different eligible endpoint when the failure suggests endpoint scope, and stop at the shared deadline and budget. A gateway retry plus client retry plus service-mesh retry multiplies attempts; assign one layer as owner or divide an explicit total budget.

    9. Gateway, ingress, discovery, and balancer¶

    Component Scope Owns Does not inherently own
    service discovery service identity to endpoint set registration/watch, endpoint metadata, epochs packet forwarding or application policy
    load balancer one eligible endpoint per connection/request selection, health integration, locality public API lifecycle or business authorization
    ingress traffic entering a cluster external listeners and cluster routes organization-wide API product policy
    API gateway client-facing API boundary authentication integration, quotas, API routing/version policy canonical domain authorization or workflows

    Products can combine these roles, but the design should not. State which control plane publishes routes and trust roots, which data plane forwards traffic, what remains available when control is down, and which component owns each retry and rate limit. See the canonical API Gateway case study for an integrated design; do not recreate that product design here.

    10. Failure analysis and design implications¶

    Failure Evidence that distinguishes it Design implication
    one endpoint hangs endpoint queue/latency rises; peers normal passive outlier signal, per-attempt bound, different-endpoint retry if safe
    whole zone slows correlated locality metrics preserve remote headroom; avoid ejecting every local endpoint independently
    health endpoint lies probes pass while real methods fail use representative passive signals and dependency-aware readiness
    stale discovery endpoint epoch/age exceeds bound last-known-good policy with expiry; fail closed for revoked identity
    hot affinity key per-key/tenant load concentrated split key, quota tenant, replicate state, or relax affinity
    proxy overload downstream healthy; proxy queues and accept failures rise admission at edge; scale on streams/CPU, not connection count alone
    drain never completes long-lived streams remain application reconnect protocol and maximum drain time
    spoofed client IP forwarding chain begins at untrusted peer overwrite at first trust boundary; authenticate proxy hops
    retry amplification attempts/logical request rises with failure single retry owner, shared budget, fast overload rejection

    L5 expectations¶

    • Draw each connection/TLS leg and state what identity each hop trusts.
    • Choose L4 versus L7 and an algorithm using the protocol’s actual work unit.
    • Define readiness, passive outliers, locality spillover, drain, and retry ownership.
    • Quantify connections, active requests/streams, bandwidth, and failover headroom.
    • Name dashboards and fault injections that would validate the design.

    L6 extensions¶

    • Separate control-plane and data-plane failure domains with signed, versioned, last-known-good configuration.
    • Design multi-region locality policy, capacity reservation, and correlated-failure safeguards.
    • Establish organization-wide header trust, workload identity, retry ownership, and deprecation policy.
    • Plan algorithm rollout with shadow decisions, canaries, rollback, and fairness/cost evidence.
    • Resolve tensions among platform standardization, tenant isolation, regional sovereignty, and operational ownership.

    Interview traps¶

    • Treating X-Forwarded-For as authenticated because a header exists.
    • Saying “least connections” for multiplexed traffic without defining active work.
    • Calling TLS bridging end-to-end encryption.
    • Using liveness checks for dependency readiness and causing restart cascades.
    • Ejecting unhealthy endpoints without a maximum-ejection or panic policy.
    • Claiming sticky sessions solve state management or hot keys.
    • Draining forever because WebSockets never become idle.
    • Allowing client, gateway, mesh, and library retries to stack.
    • Calling gateway, ingress, discovery, and load balancer synonyms.

    11. Exercises¶

    Exercise 1: reconstruct a trusted client address¶

    An application receives peer 10.2.0.8 and X-Forwarded-For: 198.51.100.9, 10.1.0.7. Only 10.2.0.0/16 and 10.1.0.0/16 are trusted proxy networks. Which address may be treated as the network client address? What changes if the immediate peer is 203.0.113.4?

    Solution¶

    Open after your attempt

    With peer 10.2.0.8, walk right-to-left through trusted hops: 10.2.0.8, then 10.1.0.7. The first untrusted address is 198.51.100.9, so it is the candidate client network address. It is not user identity. If the immediate peer is untrusted 203.0.113.4, discard the entire inbound header and use 203.0.113.4; trusting the supplied list would permit spoofing.

    Exercise 2: expose multiplexing imbalance¶

    Eight L7 proxies each hold 10 HTTP/2 connections. Their active stream counts are 900, 110, 105, 100, 95, 90, 85, 80. Explain why an L4 least-connections balancer cannot repair this state and propose two mitigations.

    Solution¶

    Open after your attempt

    Every proxy has 10 connections, so L4 sees a tie and cannot observe the 11.25x stream difference between 900 and 80. Mitigations include distributing more independently established client connections and performing request/stream-aware selection at L7. The L7 tier should advertise or measure active work, cap concurrent streams/queued requests, and reject overload rather than depending only on selection.

    Exercise 3: design safe outlier ejection¶

    A 20-endpoint cluster sees five connection failures from every endpoint because a shared database is down. A rule ejects an endpoint after five failures. Repair the rule.

    Solution¶

    Open after your attempt

    Classify correlated cluster/dependency failure separately from endpoint failure. Require minimum volume and comparative evidence, cap the ejected fraction, preserve a minimum probe set, and enter explicit overload/fail-fast behavior instead of ejecting all 20. Readiness may remove the cluster if it cannot serve correctly, but liveness should not restart every process solely because the database is unavailable. Record ejection and dependency evidence.

    Exercise 4: plan a long-lived drain¶

    A deployment has 40,000 WebSockets and must finish in ten minutes. State a safe sequence and one capacity calculation.

    Solution¶

    Open after your attempt

    Stop assigning new sockets, send a reconnect hint with randomized delay, keep old and new fleets concurrently available, and close remaining old sockets after the bounded grace period with resumable session state. The average migration rate is at least 40,000 / 600 s = 66.7 reconnects/s; provision above that for randomness, retries, and normal joins. Preserve connection epochs and spread reconnects so the new fleet and authentication service do not receive a synchronized wave.
