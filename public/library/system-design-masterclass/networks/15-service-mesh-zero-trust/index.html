    15. Service Mesh and Zero Trust¶

    A service mesh moves selected traffic policy into a shared data plane. Zero trust removes implicit trust based on network location and requires continuously evaluated identity, device/workload state, policy, and context. They overlap, but neither implies the other: a mesh can encrypt traffic while authorizing everything, and a system can apply zero-trust principles without a mesh.

    Learning goals¶

    After this chapter, you should be able to:

    • separate north-south gateways from east-west service communication;
    • compare sidecar and ambient or node-level data planes;
    • explain desired configuration, discovery, xDS-like distribution, and stale-state behavior;
    • design workload identity, mTLS, authorization, retries, telemetry, and certificate rotation;
    • evaluate control-plane outage, bypass, cost, and multi-tenant isolation; and
    • prove policy and recovery at workload, proxy, and application boundaries.

    1. Define the boundaries first¶

    North-south traffic crosses a system boundary: user to edge, partner to API, or workload to the public internet. East-west traffic moves between internal services. The labels describe trust and operational boundaries, not compass directions.

    flowchart LR
    U[User or partner] --> G[North-south gateway]
    G --> A[Service A]
    A --> B[Service B]
    B --> D[(Database)]
    A --> E[Egress gateway]
    E --> X[External API]
    CP[Mesh control plane] -. desired config .-> G
    CP -. desired config .-> A
    CP -. desired config .-> B

    An ingress gateway commonly terminates public TLS, validates user credentials, applies coarse policy, and routes HTTP. East-west policy authenticates workload identities and authorizes service-to-service actions. An egress gateway can constrain external destinations and provide audit or stable egress identity, but it becomes a stateful capacity and availability dependency.

    Draw every bypass path: host networking, loopback, direct pod IP, node port, unmanaged workload, UDP protocol, external load balancer, debug container, and cloud metadata endpoint. A policy enforced only in the proxy is not enforced on traffic that avoids the proxy.

    2. Data-plane architectures¶

    Sidecar¶

    A sidecar proxy runs beside each workload instance, usually sharing its network namespace or receiving redirected traffic.

    pod A                                  pod B
+-------------+                       +-------------+
| app -> proxy| === authenticated ==> |proxy -> app |
+-------------+                       +-------------+

    Strengths: per-workload policy boundary, mature L7 controls, local telemetry, independent rollout by workload. Costs: one proxy per workload, CPU/memory overhead, connection and file-descriptor duplication, startup ordering, version skew, and difficult transparent interception.

    Ambient or node-level¶

    Ambient designs move secure L4 transport into a shared node or network-layer component and add optional L7 waypoint proxies where policy requires them.

    flowchart LR
    A[Workload A] --> ZA[Node secure tunnel A]
    ZA --> W[Optional L7 waypoint]
    W --> ZB[Node secure tunnel B]
    ZB --> B[Workload B]

    Strengths: lower per-pod overhead, fewer injected containers, infrastructure-managed upgrades. Costs: a larger shared blast radius, identity attribution at the shared layer, node interception complexity, and possible extra waypoint hops for L7 policy.

    Neither architecture is universally cheaper. Benchmark actual requests/s, connection count, payload sizes, TLS handshakes, filter chains, telemetry sampling, and node density. Include cross-zone hops and gateway processing in the Cost Engineering model.

    3. Desired state is not observed state¶

    Most meshes separate:

    • a control plane, which accepts intent, validates and compiles policy, discovers endpoints, and distributes desired configuration; and
    • a data plane, which serves traffic from locally held configuration and credentials.

    An xDS-like protocol streams versioned listeners, routes, clusters/endpoints, secrets, and related resources. The important concepts are generic: version, nonce or acknowledgement, dependency ordering, rejection detail, and eventual convergence.

    sequenceDiagram
    autonumber
    participant O as Operator or API
    participant C as Control plane
    participant P as Proxy
    participant W as Workload
    O->>C: Submit desired policy version 42
    C->>C: Validate and compile
    C->>P: Push snapshot or delta 42
    P->>P: Validate dependencies
    P-->>C: ACK 42 or NACK with error
    P->>W: Serve using accepted state

    Track at least four versions:

    authored -> accepted by API -> compiled/distributed -> active in each data plane

    An API success proves only acceptance, not fleet activation. A control-plane dashboard showing version 42 does not prove that a disconnected proxy left on version 39 is safe. Define convergence SLOs and maximum permissible staleness for routes, authorization, revocation, and trust bundles separately.

    Discovery is routing input¶

    Discovery maps a service identity to endpoints and metadata such as zone, health, protocol, and subset. Stale discovery can keep terminated endpoints, omit new capacity, or mislabel a tenant. Define:

    • source of truth and readiness semantics;
    • endpoint removal and drain ordering;
    • locality preference and spillover;
    • outlier ejection and minimum healthy capacity;
    • stale-cache behavior during control-plane loss; and
    • whether application DNS and mesh discovery can disagree.

    Outlier ejection is not a substitute for capacity management. If 20% of endpoints are slow because the dependency is overloaded, ejecting them can overload the remainder.

    4. Workload identity and mTLS¶

    IP addresses identify interfaces and routes, not durable principals. A workload identity should bind an authenticated workload to a trust domain and service account or equivalent principal. SPIFFE defines URI-form identities such as:

    spiffe://prod.example/payments/settlement-worker

    The identity issuer must attest workload properties before issuing short-lived credentials. The mesh then uses mutual TLS (mTLS): both peers authenticate, traffic is encrypted in transit, and the receiving policy can authorize the authenticated source.

    identity issuance:
node/workload evidence -> attestor -> identity document + private key

request:
source proxy presents identity -> destination validates trust chain/name
destination presents identity -> source validates expected service

    mTLS answers “which certified workload is at the other end?” It does not answer “may it refund order 123?” Authorization must evaluate source identity, destination, operation, tenant, and request context. Keep end-user identity distinct from proxy workload identity; propagate user claims through a constrained, integrity-protected mechanism rather than trusting arbitrary headers.

    See Security Architecture for threat modeling, authentication, and key ownership.

    5. Authorization: default deny with explicit ownership¶

    A useful policy model is:

    allow if
  authenticated source in approved trust domain
  AND destination workload matches policy target
  AND method/path or RPC is allowed
  AND tenant/context constraints pass
  AND no higher-priority deny applies

    Prefer stable identities and named operations over IP ranges. Separate platform guardrails from application-owned grants:

    Layer Example Owner
    organization deny unknown trust domains security/platform
    environment production cannot receive from development platform
    service checkout may call payment authorization destination team
    resource caller may mutate this merchant's order application/data layer

    L7 mesh policy sees only what the proxy parses. End-to-end encrypted, custom, tunneled, or unsupported protocols may expose only L4 identity. If the destination application alone knows resource ownership, keep that authorization there.

    Safe rollout¶

    1. Inventory observed flows, including jobs, probes, failover, and break-glass paths.
    2. Create policy in audit/dry-run mode where available.
    3. Investigate denied flows; do not automatically permit every observed flow.
    4. Enforce on a canary subset.
    5. Compare user success, authorization denies, and bypass probes.
    6. Expand with an immediate rollback that does not require the failed control plane.

    Observed traffic includes compromise and accidental dependencies. It is evidence, not the policy specification.

    6. Certificate and trust-bundle rotation¶

    Short-lived credentials reduce exposure but increase dependence on issuance and time. Let certificate lifetime be L, renewal begin after fraction r, and maximum issuer outage tolerance before expiry be approximately:

    renewal reserve = L * (1 - r)

    For a 24-hour certificate renewed at 50% lifetime, nominal reserve is 12 hours. Clock skew, retry delay, rollout lag, and already-failed renewals reduce it. Monitor remaining lifetime distribution, issuance success, and signer availability.

    Rotate roots with overlap:

    1. distribute trust bundle containing old + new roots
2. prove receivers accept credentials from both
3. issue leaf credentials from new root
4. prove fleet adoption and drain old sessions
5. remove old root only after maximum leaf/connection lifetime and rollback window

    Rotating issuer and trust bundle simultaneously can partition the fleet. A control-plane outage during rotation must have an explicit policy: continue with cached, unexpired material; fail closed after expiry; and preserve a narrowly controlled recovery path.

    Leaf expiry is checked during certificate validation; it does not automatically terminate live TLS sessions or all resumption tickets. Force non-resumed canaries and govern session/ticket age and invalidation separately. A no-effects-after- expiry policy needs request/effect-boundary enforcement, not just TLS sockets.

    7. Retries, deadlines, and traffic policy¶

    A mesh can standardize connect timeouts, circuit breaking, load balancing, and retries, but it cannot infer business idempotency. Default retries at a proxy can repeat non-idempotent application actions or multiply application retries.

    If a client makes 2 attempts, the ingress makes 2, service A makes 3, and its sidecar makes 2:

    maximum dependency attempts = 2 * 2 * 3 * 2 = 24

    Choose one retry owner per call boundary, propagate an end-to-end deadline, restrict retries to transient failures and replay-safe operations, and cap retry traffic with a budget. Account for per-try timeout plus connection acquisition and response reserve. See Deadlines, Retries, and Pools.

    Traffic splitting also needs denominator clarity. A 1% canary by requests may receive more than 1% of CPU if requests are larger or long-lived. Hash-based splits can stick tenants to one version. Track requests, bytes, concurrent streams, tenant distribution, and outcomes.

    8. Telemetry without accidental explosion¶

    The mesh can emit transport and request signals without application changes:

    • connection attempts, resets, handshake failures, and certificate identity;
    • request rate, response codes, latency, retries, and upstream endpoint;
    • policy allow/deny decisions and active config version; and
    • bytes, protocol, source/destination workload, zone, and route.

    It cannot know whether a 200 response violated a business invariant or whether a timeout happened after a durable commit. Application telemetry remains necessary.

    High-cardinality labels, source workload, destination, route, response code, zone, tenant, certificate, and version, multiply. At 2,000 sources, 500 destinations, 20 routes, 10 status classes, and 3 zones, the theoretical space is:

    2,000 * 500 * 20 * 10 * 3 = 600,000,000 series

    Do not pre-aggregate every combination. Keep bounded service-level metrics, sampled traces, short-retention structured access logs, and targeted debug capture. Redact credentials and sensitive headers. Link mesh cost to Cost Engineering.

    9. Control-plane outage and stale state¶

    A robust data plane continues serving with its last accepted configuration during a temporary control-plane outage. That improves availability but delays endpoint changes, revocation, routes, and trust updates.

    This depends on resource validity and policy: Envoy resource TTLs can expire while disconnected. A NACK reports at least one invalid resource; it does not prove that every resource in the response was rejected. Likewise, an ACK records validation and intent to apply, not successful activation. Inspect each resource's accepted, active, warming, and expired state instead of treating one response version as an atomic fleet-wide configuration.

    Define per-resource failure posture:

    Resource Cached operation Staleness risk Expiry response
    route/listener continue accepted version stale destination or policy reject unknown config; preserve known routes if safe
    endpoints use last set with local health dead endpoint, missing capacity eject locally; avoid inventing endpoints
    authorization continue accepted policy delayed revocation high-risk deny may need independent emergency path
    leaf certificate use until expiry issuance outage alert before reserve consumed; fail closed at expiry
    trust bundle retain validated bundle cannot trust newly rotated issuer overlap roots; block unsafe single-step rotation

    The control plane itself needs multi-zone deployment, durable desired state, admission validation, backpressure, bounded fan-out, versioned rollback, and tenant/resource quotas. A bad global policy can be more dangerous than control-plane unavailability.

    10. Bypass and multi-tenancy¶

    Zero-trust claims fail if traffic can bypass enforcement. Test, do not assume:

    • direct workload IP and localhost paths;
    • host-networked or privileged workloads;
    • DNS changes and alternate ports/protocols;
    • egress through unmanaged nodes or NAT;
    • control-plane/admin APIs;
    • packet redirection failure after restart; and
    • namespace or service-account impersonation.

    In multi-tenant platforms, protect both data plane and control plane:

    • namespace policy objects and prevent cross-tenant references;
    • validate that a tenant cannot select another tenant's workloads;
    • partition certificate names and private-key access;
    • quota routes, endpoints, filters, telemetry, and config churn;
    • avoid shared gateway connection pools when credentials or tenant context differ; and
    • test noisy-neighbor CPU, memory, connection, and config-push effects.

    See Multi-Tenant Isolation for cell and control-plane boundaries.

    11. Failure evidence and recovery¶

    Failure Distinguishing evidence Recovery proof
    proxy config rejected NACK/error, active version behind desired, dependency detail accepted version equal across canary; expected route works
    mTLS trust break handshake alert, presented identity, chain/root version, clock both directions authenticate with rotated bundle
    authorization regression deny decision with source/destination/policy rule; app not reached intended flow succeeds; forbidden fixture still fails
    stale discovery proxy endpoint dump differs from registry; calls to terminated IP stale endpoint absent; new endpoint receives bounded traffic
    retry amplification attempt count in trace exceeds request count; retry response flags one owner and bounded ratio under injected fault
    control-plane outage streams disconnected while data path continues on known version existing routes meet SLO; reconnect converges without surge
    transparent-capture bypass packet capture reaches app without proxy identity/log bypass probe blocked at independent network/app control
    noisy tenant proxy/gateway resource and config fan-out dominated by tenant quota isolates healthy tenants under repeated test

    Recovery needs a positive and negative proof. Show that the required call works and a forbidden call remains denied. Also record desired/active versions, identity chain, retry count, and latency/capacity after recovery.

    12. Design review checklist¶

    • Mark north-south, east-west, egress, admin, and bypass paths.
    • Choose sidecar, ambient, gateway, or no mesh per protocol and boundary.
    • Record authored, accepted, distributed, and active config versions.
    • Define stale behavior and convergence SLO per resource type.
    • Bind mTLS credentials to attested workload identity, not mutable IP.
    • Keep workload authentication, end-user identity, and resource authorization distinct.
    • Assign one retry owner and propagate deadlines.
    • Rotate roots with trust overlap and measurable fleet adoption.
    • Bound telemetry cardinality and redact sensitive fields.
    • Test control-plane outage, config rejection, bypass, noisy tenant, and rollback.

    13. Exercises with worked solutions¶

    Exercise 1: Control-plane outage during deployment¶

    The control plane becomes unavailable after 60% of proxies activate route version 18. Version 18 sends 5% of traffic to a new service version. What should the system do?

    Worked solution

    Solution: Do not claim a coherent fleet state. Freeze further rollout and inspect whether mixed versions preserve correctness. Data planes should continue with their last accepted state if safe. If the canary is harmful, use a preplanned rollback path that remains available without the failed control plane; otherwise hold and restore control-plane quorum. Prove per-proxy active versions, canary traffic distribution, user outcomes, and no retry/connection surge when streams reconnect.

    Exercise 2: Calculate rotation reserve¶

    Leaf certificates last 12 hours and renewal starts at 60% of lifetime. Issuance is unavailable for 4 hours. Ignoring skew, do all certificates survive?

    Worked solution

    Solution: Renewal starts after 12 * 0.60 = 7.2 hours, leaving 4.8 hours nominal reserve. Certificates that had just reached renewal should survive a 4-hour outage, but those with prior failures or skew may not. Alert on remaining lifetime, not average age, and validate the minimum across the fleet. Preserve cached unexpired credentials; fail closed after expiry.

    Exercise 3: Stop retry multiplication¶

    An application retries twice and its sidecar retries twice, while the ingress retries once after the original attempt. How many downstream attempts can one user request create?

    Worked solution

    Solution: Interpreting “retries twice” as three application attempts, sidecar three attempts, and ingress two attempts gives 3 * 3 * 2 = 18. Disable implicit retries at layers that do not know idempotency, choose one owner, propagate the remaining deadline, and enforce a retry budget. Verify attempt counts in traces during a forced transient failure.

    Exercise 4: Prove zero-trust enforcement¶

    A policy allows checkout to call payments and denies all others. What constitutes proof?

    Worked solution

    Solution: Show an authenticated checkout identity completing the intended operation, an authenticated unrelated identity denied with the matching rule, an unauthenticated/bypass fixture denied before the application effect, and application resource authorization rejecting a checkout identity for an unauthorized tenant. Include active policy versions and destination logs. Reachability success alone is insufficient.

    Takeaways¶

    • A mesh is a policy delivery and enforcement system, not automatic zero trust.
    • Desired configuration, accepted configuration, and fleet-active state are different facts.
    • mTLS authenticates workloads; application authorization still protects resources and tenants.
    • Data planes should survive bounded control-plane loss without accepting unknown state.
    • Retries, telemetry, gateways, and proxies consume finite capacity and can amplify failures.
    • Every enforcement claim needs a tested bypass path and a negative authorization proof.
