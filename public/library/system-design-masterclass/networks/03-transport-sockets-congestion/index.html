    03. Transport, Sockets, and Congestion¶

    Transport protocols turn best-effort IP delivery into communication usable by applications. TCP offers an ordered reliable byte stream with flow and congestion control. UDP offers message-oriented datagrams with minimal transport machinery. QUIC builds secure multiplexed transport over UDP in user space. None of them defines business message boundaries or proves application success.

    Goals¶

    After this chapter, you should be able to:

    • model TCP as endpoint state over numbered bytes rather than a sequence of application messages;
    • explain handshake, acknowledgement, retransmission, flow control, congestion control, and teardown;
    • distinguish receiver window, congestion window, MSS, RTT, RTO, and bandwidth-delay product;
    • reason about slow start, loss, serialization, latency, and achievable throughput;
    • explain TIME_WAIT, CLOSE_WAIT, listen queues, accept queues, socket buffers, and file-descriptor limits;
    • design application framing over a stream and handle partial reads/writes;
    • choose TCP, UDP, or QUIC from application requirements and deployment constraints;
    • correlate application symptoms with socket, kernel, packet, and peer evidence;
    • establish bounded connection, buffer, queue, and retry budgets.

    1. First-principles model¶

    IP may lose, duplicate, reorder, or delay packets. A transport protocol adds endpoint behavior. TCP maintains state that maps an application byte stream onto IP packets and reconstructs the ordered stream at the peer.

    Application bytes
  + endpoint identity and protocol state
  + sequence/acknowledgement state
  + retransmission timers
  + receiver capacity
  + network-capacity estimate
  = TCP's reliable ordered byte-stream service

    A TCP connection is conventionally identified by protocol plus source IP, source port, destination IP, and destination port. Names, processes, and users are not part of this network tuple. NAT or proxies can create different tuples on different path segments.

    flowchart LR
    A[App writes stream bytes] --> S[Send buffer]
    S --> X[Sequence and segment]
    X --> N[Network]
    N --> R[Peer receive and reorder]
    R --> B[Receive buffer]
    B --> P[Peer app reads bytes]
    C[cwnd] -.network bound.-> X
    W[rwnd] -.receiver bound.-> X
    T[RTO and loss recovery] -.retransmit.-> X

    2. Packet and state flow: TCP handshake¶

    The three-way handshake establishes bidirectional sequence state and confirms both directions sufficiently to create a connection:

    sequenceDiagram
    autonumber
    participant C as Client
    participant S as Server
    C->>S: SYN, seq=x
    S-->>C: SYN-ACK, seq=y, ack=x+1
    C->>S: ACK, ack=y+1
    Note over C,S: established byte-stream state

    SYN and FIN each consume one sequence number. Sequence numbers count bytes, not packets. ACK value N identifies the next expected sequence position and cumulatively acknowledges the preceding contiguous sequence space. TCP sequence numbers wrap modulo 2^32, so implementations use serial-number comparisons within the valid window rather than ordinary unsigned less-than. Modern TCP may also use selective acknowledgement information to report noncontiguous received blocks.

    2.1 Simplified active/passive states¶

    stateDiagram-v2
    [*] --> CLOSED
    CLOSED --> SYN_SENT: active open
    CLOSED --> LISTEN: passive open
    LISTEN --> SYN_RECEIVED: receive SYN
    SYN_SENT --> ESTABLISHED: receive SYN-ACK, send ACK
    SYN_RECEIVED --> ESTABLISHED: receive ACK
    ESTABLISHED --> FIN_WAIT_1: active close
    ESTABLISHED --> CLOSE_WAIT: receive FIN
    CLOSE_WAIT --> LAST_ACK: app closes
    FIN_WAIT_1 --> FIN_WAIT_2: FIN acknowledged
    FIN_WAIT_2 --> TIME_WAIT: receive FIN, send ACK
    LAST_ACK --> CLOSED: FIN acknowledged
    TIME_WAIT --> CLOSED: timer expires

    This omits simultaneous open/close and intermediate variants, but exposes ownership: receiving a FIN moves the kernel side toward CLOSE_WAIT; only the local application closing moves it onward.

    2.2 Handshake failure signatures¶

    Observation Likely boundary Alternatives to test
    SYN retransmits, no SYN-ACK route, policy, listener, return path capture loss, server SYN handling pressure
    SYN-ACK arrives, no final ACK client path/state client abort or capture point mismatch
    Handshake completes, immediate RST no valid socket/app policy/late tuple proxy rejection or process restart
    Connect latency spikes only on new connections setup path or listen pressure DNS/TLS included in timer

    3. TCP is a byte stream: application framing¶

    TCP does not preserve write boundaries. If a sender writes "ABC" then "DEF", a receiver may read "ABCDEF", "AB" then "CDEF", or other contiguous partitions. It cannot assume one read equals one message.

    Common framing schemes:

    Scheme Example Strength Trap
    Fixed length every record 64 B simple wasted space, inflexible evolution
    Delimiter newline-terminated record inspectable escaping and unbounded missing delimiter
    Length prefix 4-byte length + payload efficient binary framing malicious/invalid length allocation
    Self-describing protocol HTTP headers/chunks, protobuf envelope rich semantics parser complexity and limits still required

    Length-prefixed receiver logic must:

    1. accumulate enough bytes for the length field;
    2. validate length against a configured maximum before allocation;
    3. accumulate exactly that payload length across any number of reads;
    4. decode one message and retain excess bytes for the next;
    5. handle EOF in a partial header or body as truncation.

    Framing invariant: each accepted message consumes exactly its declared bytes under a bounded, validated grammar. Transport ordering does not make the grammar safe.

    4. ACKs, loss, and retransmission timeout¶

    TCP retains unacknowledged bytes. Acknowledgements advance the send window. Loss can be inferred from acknowledgement patterns or a retransmission timer. Exact algorithms evolve; reason from principles and consult implementation evidence before claiming a specific threshold.

    4.1 RTT estimation and RTO¶

    Round-trip time varies. TCP maintains a smoothed RTT and variation estimate, then derives a retransmission timeout with a safety margin. RFC 6298 describes the standard estimator:

    RTTVAR <- (1 - beta) * RTTVAR + beta * |SRTT - R'|
SRTT   <- (1 - alpha) * SRTT + alpha * R'
RTO    <- SRTT + max(G, K * RTTVAR)

    where R' is a measured RTT sample, G is clock granularity, alpha = 1/8, beta = 1/4, and K = 4 in the RFC algorithm. Bounds and implementation behavior apply. Timeout retransmissions back off because repeated immediate retransmission would worsen overload.

    An application deadline and TCP RTO are different clocks. The application can abandon a request before transport gives up, or wait long after the business outcome is no longer useful.

    Update RTTVAR using the previous SRTT before updating SRTT. RFC 6298 initializes the first sample separately and recommends a one-second minimum computed RTO; implementation-specific lower bounds are not the formula itself. Exclude RTT samples from ambiguously retransmitted data unless timestamps resolve the ambiguity (Karn's rule).

    4.2 Duplicate ACKs and selective acknowledgement¶

    If later data arrives while a gap remains, cumulative ACKs repeat the next expected sequence. This can trigger fast loss recovery before RTO. SACK-capable peers can describe received blocks so the sender retransmits missing ranges more efficiently. Reordering can produce duplicate ACK patterns without actual loss.

    4.3 ACK is not commit¶

    A TCP ACK proves reception by peer transport state according to TCP semantics. It does not prove:

    • peer application read;
    • request parsing succeeded;
    • authorization passed;
    • database committed;
    • response will arrive.

    Application protocols need explicit responses, identifiers, idempotency, and reconciliation for ambiguous failures.

    5. Flow control versus congestion control¶

    These solve different capacity problems.

    Mechanism Protects Signal/state Sender limit
    Flow control receiving endpoint and buffer advertised receive window rwnd do not outrun receiver capacity
    Congestion control network path congestion window cwnd, ACK/loss/ECN-derived state do not overload path estimate

    Approximate outstanding-data bound:

    in-flight bytes <= min(cwnd, rwnd)

    Additional sender/application/socket constraints can lower actual flight size.

    5.1 Receive window pressure¶

    If the peer application stops reading, its receive buffer fills and advertised window shrinks, potentially to zero. The sender may have a successful established connection but cannot advance useful data. The root cause can be application saturation, not network congestion.

    RFC 9293 section 3.8.6.1 requires zero-window probes so a lost window update cannot deadlock progress. Probe ACKs establish responsive transport state, not useful application work. Bound application deadlines and retained resources separately.

    5.2 Congestion window¶

    cwnd is sender state estimating safe network flight. Congestion-control algorithms differ, but all must share path capacity responsibly. A large receiver window cannot authorize sending beyond congestion control.

    5.3 Slow start¶

    At connection start or after certain recovery conditions, the sender does not know path capacity. Slow start increases flight size rapidly as ACKs return, roughly doubling per RTT under an idealized ACK model until a threshold or congestion event changes growth.

    If initial congestion window is 10 MSS, MSS is 1460 B, and no other bound applies:

    initial flight = 10 * 1460 B = 14,600 B

    An object of 200 KiB cannot all be sent in the first flight. Under an idealized sequence of full growth rounds, flight opportunities might be about 14.6 KB, 29.2 KB, 58.4 KB, 116.8 KB. Real ACK behavior, protocol overhead, pacing, loss, implementation, and object framing alter completion.

    Connection reuse avoids repeated handshake and initial growth but can inherit stale path state, head-of-line blocking at some layers, or failure coupling. Pool decisions need both latency and resilience reasoning.

    6. Calculations with units: latency, loss, serialization, and BDP¶

    6.1 Propagation versus serialization¶

    Propagation delay is travel time through the medium. Serialization delay is time to place bits on the link.

    serialization (s) = bytes * 8 bit/B / rate (bit/s)

    A 1 MiB response over a 100 Mbit/s bottleneck needs at least:

    1,048,576 B * 8 / 100,000,000 bit/s = 0.0839 s = 83.9 ms

    This excludes headers, contention, propagation, retransmission, and server work. A 50 ms timeout cannot succeed for that transfer over this bottleneck even with zero propagation.

    6.2 Bandwidth-delay product¶

    BDP is the amount of data needed in flight to fill a path:

    BDP (bit) = bottleneck bandwidth (bit/s) * RTT (s)

    For 1 Gbit/s and 80 ms RTT:

    BDP = 1,000,000,000 bit/s * 0.080 s = 80,000,000 bit
    = 10,000,000 B = 10 MB decimal

    To approach 1 Gbit/s for one flow, the effective flight window must be around 10 MB or more, and endpoints plus application must sustain the rate. With only a 1 MiB effective window:

    window-limited throughput <= 1,048,576 B / 0.080 s
                          = 13,107,200 B/s
                          = 104.9 Mbit/s

    6.3 Loss and throughput¶

    Loss can impose at least one recovery interval and reduce cwnd; repeated loss can collapse throughput even when average link utilization looks low. Small random loss is especially costly on high-BDP paths because regrowing flight takes time. Do not use one universal closed-form throughput formula as a capacity promise: congestion algorithm, RTT, loss pattern, pacing, offloads, ACK strategy, and competing flows matter.

    6.4 Queueing¶

    If arrival rate persistently exceeds service rate, queue occupancy grows until admission slows or data drops. A 20 MB queue before a 1 Gbit/s bottleneck represents:

    20,000,000 B * 8 / 1,000,000,000 bit/s = 0.160 s = 160 ms

    Buffering can convert loss into deadline violation. Active queue management, pacing, admission control, and bounded concurrency address different parts of this problem.

    7. Concrete lifecycle example: teardown, TIME_WAIT, and CLOSE_WAIT¶

    TCP closes each byte-stream direction independently. A FIN means "I will send no more bytes"; the receiver can still send in the other direction until it closes.

    7.1 TIME_WAIT¶

    The endpoint performing the active close commonly enters TIME_WAIT after acknowledging the peer's FIN. The state allows retransmission of the final ACK and helps prevent delayed segments from an old incarnation being confused with a later connection using the same tuple.

    Many TIME_WAIT sockets are not automatically a leak. They can indicate high connection churn. Risks include ephemeral-port pressure, state memory, NAT table pressure, and load balancer churn. Prefer connection reuse and measured capacity planning over unsafe timer reductions.

    Approximate concurrent TIME_WAIT entries:

    entries = active closes/s * TIME_WAIT duration (s)

    At 5,000 active closes/s and 60 s retention:

    5,000 /s * 60 s = 300,000 entries

    This is a sizing estimate, not a universal OS duration or limit.

    7.2 CLOSE_WAIT¶

    CLOSE_WAIT means the local TCP stack received the peer's FIN, but the local application has not closed its side. Persistent growth strongly suggests application lifecycle failure: leaked sockets, stuck cleanup, blocked handlers, or ownership confusion. Kernel tuning does not substitute for closing resources.

    7.3 Reset versus graceful close¶

    FIN supports orderly EOF after preceding bytes. RST aborts connection state and can discard unread or unsent expectations. Applications must define whether EOF before a complete framed message is valid, retryable, or an ambiguous operation.

    8. Listening, accepting, and server queues¶

    A listening socket represents passive-open state. Conceptually, servers face at least two connection stages:

    1. handshakes in progress;
    2. established connections waiting for the application to accept them.

    Operating systems name and implement these queues differently. The application also has worker/event-loop/request queues after accept.

    flowchart LR
    S[SYN arrivals] --> H[Handshake state]
    H --> A[Completed accept queue]
    A --> P[Application accept]
    P --> R[Request parsing and work]
    R --> D[Downstream capacity]

    Increasing a listen backlog can absorb a short burst but cannot repair an application that accepts or serves slower than arrivals. It adds waiting and state. Observe handshake drops, completed-queue overflow, accept rate, active connections, request queue age, and downstream saturation together.

    8.1 Little's Law for connections¶

    If a service completes 8,000 requests/s and average connection-held request time is 250 ms with one in-flight request per connection:

    average in-flight requests = 8,000 request/s * 0.250 s
                           = 2,000 requests

    At 70% target utilization for a relevant constrained pool:

    provisioned capacity = ceil(2,000 / 0.70) = ceil(2857.143) = 2,858 slots

    Tail latency and multiplexing change the relationship. Use distributions and burst tests, not only averages.

    9. Socket buffers and file descriptors¶

    9.1 Buffers¶

    Send buffers hold application bytes not yet fully acknowledged; receive buffers hold arrived bytes not yet consumed. Larger buffers may support high BDP and bursts but consume memory and can hide backpressure.

    For 40,000 connections with an illustrative committed average of 128 KiB combined socket memory each:

    memory = 40,000 * 128 KiB
       = 5,120,000 KiB
       = 4.883 GiB

    Actual kernels autotune and account memory differently. Measure committed and pressured memory rather than multiplying configured maxima as if fully allocated.

    9.2 File descriptors¶

    On Unix-like systems, sockets consume file descriptors. A process limit must cover listening sockets, accepted connections, outbound connections, files, pipes, logs, and operational headroom.

    FD budget >= inbound sockets + outbound sockets + non-socket FDs + surge + diagnostics reserve

    If each of 20,000 inbound requests can hold one outbound connection, naive worst-case socket demand already approaches 40,000 plus overhead. Pools and multiplexing change counts but introduce queueing and per-connection stream limits.

    An EMFILE-style per-process exhaustion can prevent logs, config reads, and recovery connections as well as accepts. Alert before exhaustion and preserve operational reserve.

    10. UDP boundaries¶

    UDP supplies ports, a checksum, and datagram boundaries over IP. It does not supply connection handshake, reliable delivery, ordering, duplicate suppression, flow control, congestion control, or path migration.

    Use UDP directly when application semantics can tolerate loss or implement the necessary behavior, such as bounded real-time media, simple request protocols with explicit transaction IDs, or a substrate for a protocol such as QUIC.

    Application responsibilities may include:

    • request/response correlation and duplicate handling;
    • authentication and anti-replay;
    • retransmission and deadline policy;
    • congestion-responsive sending;
    • fragmentation avoidance and payload bounds;
    • source spoofing/amplification defense;
    • session continuity across address changes.

    One UDP send preserves one datagram boundary at the receiver if delivered. Oversized datagrams may be fragmented or dropped. A receive buffer smaller than the datagram can truncate it according to API semantics.

    11. QUIC boundaries¶

    QUIC runs over UDP and integrates transport security using TLS. It provides reliable streams, congestion control, flow control, connection IDs, and path-related mechanisms in the QUIC protocol rather than kernel TCP.

    Important boundaries:

    • QUIC streams avoid transport head-of-line blocking between streams when loss affects one stream; ordered bytes within the affected stream still wait for gaps.
    • Encryption limits middlebox visibility into transport internals while exposing selected header fields needed for routing.
    • Connection IDs can support continuity across address/port changes under protocol validation; application identity and authorization remain separate.
    • QUIC still shares path capacity and must perform congestion control.
    • UDP blocking, idle timeouts, NAT state, MTU, and load-balancer connection-ID routing remain operational concerns.
    • HTTP/3 uses QUIC; QUIC itself is not the HTTP application protocol.
    Requirement TCP UDP directly QUIC
    Reliable ordered bytes one connection stream application-defined per QUIC stream
    Message boundaries application framing datagram boundary application framing within streams; optional DATAGRAM extension
    Built-in encryption no no yes, integrated TLS
    Multiplexed streams application protocol, e.g. HTTP/2 application-defined transport-native streams
    Kernel/middlebox maturity broad broad primitive deployment path must support UDP/QUIC
    Address migration connection usually tuple-bound application-defined connection-ID-based protocol support

    12. Transport invariants¶

    1. Sequence invariant: TCP acknowledges byte positions, not application operations.
    2. Ordering invariant: a TCP reader sees ordered bytes or EOF/error; message boundaries require application framing.
    3. Flight invariant: useful unacknowledged flight cannot sustainably exceed receiver and congestion constraints.
    4. Queue invariant: sustained admission above completion grows queueing until backpressure, rejection, timeout, or exhaustion.
    5. Close invariant: peer FIN does not release the local application's resource ownership.
    6. Tuple/state invariant: packets must match live endpoint state; stale packets and tuple reuse require protection.
    7. Resource invariant: every accepted connection consumes bounded state, memory, descriptors, and processing opportunity.
    8. Completion invariant: transport delivery is not business commit.
    9. Congestion invariant: reliability mechanisms must not retransmit without bound into a congested path.

    Minimum transport telemetry¶

    Record by service, zone, endpoint, and protocol:

    • connection attempts, setup latency, failures, and reuse;
    • active/idle connections and open/close rates;
    • RTT distribution, retransmitted bytes, loss/reordering indicators;
    • send/receive queue and window pressure;
    • listen/accept overflows and accept latency;
    • socket memory, file descriptors, ephemeral-port and NAT utilization where relevant;
    • application pool wait, request queue age, deadline expiry, and retry count;
    • QUIC handshake, version, stream resets, path migration, and fallback where deployed.

    Kernel counters are cumulative and host-local. Use rates, resets/restarts awareness, and workload dimensions. Packet retransmission classification by analyzers is inference, not oracle truth.

    14. Design implications¶

    Connection lifecycle¶

    • Reuse connections to amortize setup and congestion warm-up, but cap age/idle time and validate stale endpoints.
    • Drain before termination: stop new admission, allow bounded completion, then close.
    • Add jitter to connection recycling so a fleet does not reconnect simultaneously.
    • Budget client source ports, NAT state, server FDs, memory, TLS/QUIC state, and load balancer entries end to end.

    Deadlines and retries¶

    • Set an end-to-end deadline from the caller's useful-work budget.
    • Allocate sub-deadlines while preserving time for cleanup and a bounded retry only when semantics permit.
    • Retry ambiguous writes only with idempotency or reconciliation.
    • Apply backoff, jitter, attempt limits, and a retry budget; congestion loss is a reason to reduce load, not multiply it.

    Framing and protection¶

    • Bound message length before allocation.
    • Bound decompressed size, nesting, and parse time as well as wire bytes.
    • Treat EOF mid-message as explicit truncation.
    • Apply per-connection and global concurrency limits so one peer cannot monopolize buffers or workers.

    Protocol choice¶

    Choose UDP/QUIC because semantics and path support justify it, not because "UDP is faster." Choose TCP because an ordered stream matches the protocol, not because it provides exactly-once operations. Maintain fallback only if its complexity and monitoring are owned.

    16. Traps¶

    • Treating one TCP write as one receive or one request.
    • Saying an ACK means the application processed the operation.
    • Conflating receiver flow control with network congestion control.
    • Treating RTO as the application timeout.
    • Assuming more socket buffer always improves latency.
    • Treating every TIME_WAIT socket as a leak or tuning protocol safety away first.
    • Ignoring persistent CLOSE_WAIT as a kernel cleanup problem.
    • Increasing listen backlog without fixing accept/service capacity.
    • Sizing only server FDs while a NAT, proxy, or client exhausts earlier.
    • Claiming UDP is inherently low latency without adding required reliability and congestion behavior.
    • Claiming QUIC removes all head-of-line blocking.
    • Estimating throughput from bandwidth alone while ignoring RTT, flight window, loss, and application rate.

    17. Exercises with worked solutions¶

    Exercise 1: framing across reads¶

    A length-prefixed protocol uses a 4-byte unsigned length. Reads return 2 bytes, then 7 bytes, then 20 bytes. The decoded length is 10 bytes. Describe receiver state.

    Worked solution

    After 2 bytes, retain a partial header. After the next 7, complete the 4-byte header and hold 5 payload bytes. Validate 10 against the maximum before allocation. The final 20-byte read supplies the remaining 5 bytes for message one and 15 bytes belonging to later framing. Decode exactly 10 payload bytes and retain the 15 excess bytes. Never discard excess or assume read boundaries match messages.

    Exercise 2: BDP and window bound¶

    A path offers 2 Gbit/s with 50 ms RTT. Calculate BDP. What throughput bound does a 4 MiB effective window impose?

    Worked solution 
    BDP = 2,000,000,000 bit/s * 0.050 s
    = 100,000,000 bit = 12,500,000 B = 12.5 MB

window throughput = 4,194,304 B / 0.050 s
                  = 83,886,080 B/s
                  = 671,088,640 bit/s
                  = 671.1 Mbit/s

    Ignoring overhead and loss, the 4 MiB window limits one flow well below the 2 Gbit/s path.

    Exercise 3: socket memory budget¶

    A proxy expects 80,000 established connections. Measured average charged socket memory is 96 KiB per connection. Add 30% surge. Estimate memory.

    Worked solution 
    surged connections = 80,000 * 1.30 = 104,000
memory = 104,000 * 96 KiB = 9,984,000 KiB
       = 9,750 MiB = 9.52 GiB

    This excludes process objects, TLS/QUIC state, request buffers, allocator overhead, and kernel global structures. Validate with measured accounting under representative traffic.

    Exercise 4: diagnose close states¶

    After a deploy, CLOSE_WAIT rises continuously while TIME_WAIT remains stable. What does this suggest and what evidence comes next?

    Worked solution

    Peers are closing, but the new application is not closing its local sockets promptly. Correlate sockets to process/connection owners, inspect stacks or async task state, review EOF/error cleanup paths, and compare peer close timing. Test cancellation and exception paths. Do not shorten TIME_WAIT; it is not the growing state.

    Exercise 5: slow start estimate¶

    Using the idealized model in this chapter, initial window 10 MSS, MSS = 1460 B, how many complete growth rounds are needed before a single flight can exceed 100 KiB?

    Worked solution

    Flights are approximately 14,600 B, 29,200 B, 58,400 B, then 116,800 B. Since 100 KiB = 102,400 B, the fourth flight exceeds it, after three completed growth rounds following the initial flight. This is pedagogical, not a prediction of a specific implementation or transfer completion time.

    Exercise 6: protocol choice¶

    A mobile collaboration client needs encrypted multiplexed streams, tolerates IP/port changes, and must avoid one lost stream blocking unrelated streams. Corporate networks may block UDP. Propose a boundary-aware design.

    Worked solution

    Prefer HTTP/3 over QUIC where path validation succeeds: integrated security, stream multiplexing, and connection-ID-based migration fit. Keep a measured fallback to HTTP/2 over TLS/TCP for blocked UDP. Define connection and application session identity separately, preserve request idempotency across fallback, monitor QUIC attempt/success/fallback by network, and ensure the load balancer routes connection IDs correctly. QUIC does not remove ordered waiting within one stream or application dependency ordering.
