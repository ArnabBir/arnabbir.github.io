    14. BGP, Anycast, and Global Routing¶

    Global routing is a policy system under delayed, partial information. BGP exchanges reachability between autonomous systems; it does not understand application correctness or choose the mathematically shortest geographic path. Anycast, DNS steering, and CDNs build different control loops on top of that reality.

    Learning goals¶

    After this chapter, you should be able to:

    • explain ASes, eBGP/iBGP, route advertisements, attributes, import/export policy, and convergence;
    • reason about leaks, hijacks, route-origin validation, and the limits of RPKI;
    • model anycast catchments, withdrawal, state, and evacuation headroom;
    • combine DNS, anycast, CDN, and application failover without conflicting controllers; and
    • demand evidence for routing changes and global recovery.

    1. Autonomous systems and reachability¶

    An autonomous system (AS) is a network or group of networks under one routing policy, identified by an autonomous system number (ASN). BGP speakers advertise IP prefixes plus path attributes. External BGP (eBGP) exchanges routes between ASes. Internal BGP (iBGP) distributes externally learned and internal reachability inside an AS, commonly with route reflectors at scale.

    flowchart LR
    U[Client network<br/>AS 64510] --> T[Transit<br/>AS 64520]
    T --> E1[Edge A<br/>AS 64530]
    T --> E2[Edge B<br/>AS 64530]
    E1 --> R1[Region A]
    E2 --> R2[Region B]

    Conceptually, an update says: “I can reach this prefix through this path, with these attributes.” Each neighbor applies import policy, selects a best path using its implementation and policy, installs eligible routes, and applies export policy before advertising onward.

    receive routes -> reject/filter -> modify attributes -> select best
               -> install/resolve next hop -> export selected/eligible routes

    BGP is path-vector, not link-state. The AS_PATH helps detect loops and expresses traversed ASes, but operators can prepend ASNs and apply local policy. Reachability is economic and administrative, not simply geographic.

    2. Attributes and policy¶

    Exact selection order varies by implementation. The following attributes are core reasoning tools:

    Attribute Scope and purpose Operational implication
    LOCAL_PREF internal preference within an AS; higher commonly preferred primary policy lever for outbound path choice
    AS_PATH sequence of ASes; shorter often preferred after local policy prepending is a hint, not a guarantee
    ORIGIN route-origin mechanism (IGP, EGP, incomplete) usually late in selection; not origin authorization
    MED suggestion to a neighboring AS about entry point; lower commonly preferred comparison and propagation rules vary
    NEXT_HOP address used to resolve forwarding a valid BGP route can fail if next hop is unreachable
    communities policy labels interpreted by agreement semantics are provider-specific unless standardized

    The selection that matters to your service can happen several ASes away. Changing MED at one provider may do nothing for clients whose networks prefer another transit. AS-path prepending can be outweighed by customer routes, local preference, paid peering, or more-specific prefixes.

    Prefix specificity dominates many intentions¶

    Forwarding uses longest-prefix match. If one site announces 203.0.113.0/24 and another leaks 203.0.113.0/25, networks accepting both usually forward the first half to the /25, regardless of the aggregate's BGP attributes. Filters and global routing norms constrain acceptable prefix lengths, but never rely on “our normal route should be preferred” as protection.

    Policy as code¶

    For every peering session define:

    • expected neighbor ASN and authenticated session protections where available;
    • accepted prefix allowlist or maximum prefix length/count;
    • origin and AS-path constraints;
    • communities set, accepted, stripped, or acted upon;
    • default-route policy;
    • maximum-prefix shutdown behavior; and
    • change, canary, rollback, and out-of-band access.

    Generate and test policy from an authoritative prefix/ASN inventory. A syntactically valid route map can still export the full internet table or an internal prefix.

    3. Convergence is not one timer¶

    A route change propagates hop by hop. Each router processes updates, selects a path, updates forwarding state, and advertises according to policy. Some networks never receive or accept the change. Existing flows may survive, reset, or move depending on topology and state.

    sequenceDiagram
    autonumber
    participant S as Edge site
    participant P as Transit/peer
    participant R as Client AS router
    participant C as Client
    participant N as Surviving site
    S->>P: Withdraw prefix
    P->>P: Recompute and update forwarding
    P->>R: Propagate withdrawal or alternate path
    R->>R: Apply local policy
    C->>R: Next packet
    R->>N: Forward next packet via selected alternate
    N-->>C: Response if connection and service state permit

    Measure at least:

    Tdetect + Tdecision + Texport + Tpropagation + Tremote decision + Ttraffic shift

    BGP session timers are only part of Tdetect. Bidirectional Forwarding Detection can detect some forwarding failures quickly, but aggressive timers can create false churn. Route flap damping can delay recovery and is not a universal answer. Application drain, DNS cache age, connection lifetimes, and load-balancer health add independent timelines.

    4. Leaks, hijacks, and RPKI¶

    A route leak propagates legitimate reachability beyond its intended policy scope: for example, a customer accidentally announces provider-learned routes to another provider. A prefix hijack originates or propagates unauthorized reachability, accidentally or maliciously. Both can attract, intercept, or black-hole traffic.

    Defenses are layered:

    1. strict import/export prefix and path filters;
    2. maximum-prefix limits;
    3. Internet Routing Registry data used carefully;
    4. RPKI Route Origin Authorizations (ROAs) and Route Origin Validation (ROV);
    5. route monitoring from independent vantage points; and
    6. rehearsed withdrawal, deaggregation where accepted and safe, provider escalation, and customer communication.

    RFC 9234 adds negotiated BGP Roles for eBGP relationships and the transitive Only-to-Customer (OTC) attribute. Role pairs let peers detect incompatible relationship configuration during session establishment. OTC marks routes so compliant ASes can reject propagation that violates the customer-to-provider/peer export model and can detect several route-leak classes. It complements rather than replaces prefix/path filters and RPKI: deployment is incremental, both parties must configure compatible roles for negotiation, legacy neighbors may not set or enforce OTC, and incorrect business-relationship configuration can reject legitimate routes. Define fail-closed or exception behavior per neighbor and monitor role mismatch and OTC rejection explicitly.

    RPKI origin validation classifies a route as commonly Valid, Invalid, or NotFound by checking whether a ROA authorizes the origin ASN and prefix length. It has important limits:

    • it validates route origin, not the entire AS path;
    • NotFound is not proof of legitimacy;
    • coverage and enforcement are incomplete;
    • stale or incorrect ROAs can invalidate the owner's route;
    • max-length choices can authorize more-specific announcements more broadly than intended; and
    • it does not prove that the application at the routed address is authentic.

    TLS remains necessary even when routing is valid. BGPsec aims at path validation but deployment is not universal. ASPA is intended to help detect some route leaks; treat deployment status as an evolving ecosystem property, not a completed control.

    5. Anycast mechanics and catchments¶

    With anycast, multiple sites originate the same service prefix. A client's catchment is the set of sources whose routing policy currently sends traffic to one site. Catchments depend on peering, transit policy, failures, and route propagation; they do not form stable geographic circles.

    flowchart TD
    A[One anycast service prefix] --> P1[PoP A announcement]
    A --> P2[PoP B announcement]
    A --> P3[PoP C announcement]
    C1[Client AS group 1] -->|policy-selected path| P1
    C2[Client AS group 2] -->|policy-selected path| P2
    C3[Client AS group 3] -->|policy-selected path| P3
    P1 --> O1[Regional service]
    P2 --> O2[Regional service]
    P3 --> O3[Regional service]

    Anycast works well for stateless or rapidly reconstructable edge functions such as authoritative DNS, recursive DNS, DDoS absorption, and CDN ingress. Stateful transports need care. A route change can send subsequent packets to another site that lacks connection, QUIC, NAT, or TLS-session state. QUIC connection IDs can support migration only when the implementation, routing, keys, and server state are designed for it; anycast alone does not provide migration.

    Health must control advertisements safely¶

    Do not connect one flaky process health check directly to global route withdrawal. Use layered gates:

    instance health -> local pool eligibility -> site capacity/readiness
                -> advertisement policy -> external traffic evidence

    Apply hysteresis, minimum hold times, quorum or aggregate site health, manual override, and fail-safe behavior. Preserve out-of-band management when the service prefix is withdrawn.

    6. Catchment and evacuation calculations¶

    Suppose normal peak demand is:

    Site Normal peak Tested safe capacity
    A 800k req/s 1.20M req/s
    B 600k req/s 1.05M req/s
    C 400k req/s 0.80M req/s

    Tests show that withdrawing A shifts 55% of A to B, 35% to C, and 10% to an external fallback.

    B after withdrawal = 600k + 0.55 * 800k = 1.04M req/s
C after withdrawal = 400k + 0.35 * 800k = 680k req/s

    B is below its tested ceiling by only 10k req/s, less than 1% headroom. The design is not robust to forecast error, retry amplification, uneven object mix, or loss of a B cluster. Either add B capacity, alter catchments/overflow policy, shed optional traffic, or stage A's withdrawal while observing external traffic.

    Do not assume proportional redistribution. Measure with controlled announcements and independent vantage points. Capture request rate, bandwidth, connection rate, cache misses, TLS handshakes, origin load, latency, errors, and per-client-AS movement.

    7. DNS steering, anycast, CDN, and global failover¶

    These mechanisms operate at different scopes:

    Mechanism Decision granularity State/staleness Best use
    BGP anycast destination prefix and network policy routing convergence nearest-policy edge ingress, DDoS distribution
    authoritative DNS name lookup recursive/client TTL caches coarse region/provider steering
    CDN request mapping request/connection at edge provider mapping and cache state content delivery and origin shielding
    L4/L7 load balancer connection/request local health and affinity site/region pool selection
    application routing operation/key/tenant business state home-region and correctness decisions 
    flowchart LR
    U[User] --> DNS[DNS chooses provider or service IP]
    DNS -. returned address constrains destination .-> AC
    U --> AC[Anycast catchment chooses edge]
    AC --> CDN[CDN or edge policy]
    CDN --> RG[Regional gateway]
    RG --> APP[Application chooses data home]

    Assign one owner to each decision. If DNS shifts users west while the CDN independently shifts origin east and the application redirects writes west, control loops can oscillate or create transoceanic hairpins.

    DNS failover is bounded by cached records and resolver behavior. Anycast withdrawal can move traffic faster for many networks but with less precise destination control. A CDN can keep serving cached objects during origin failure while dynamic requests fail. Global failover must therefore define behavior per operation, not only per hostname; see Multi-Region Architecture.

    8. Withdrawal and failback procedure¶

    1. Establish baseline: route visibility, catchment request/byte/connection mix, downstream headroom, cache state, and error budget.
    2. Prepare survivors: prewarm safe cache/state, reserve autoscaling quota, lower optional traffic, and verify origin/dependency capacity.
    3. Canary policy: use a community, one peer, or a less-preferred advertisement to shift a bounded catchment where supported.
    4. Observe externally: route collectors, RIPE Atlas-style probes, DNS checks, synthetic transactions, client-AS telemetry, and service signals.
    5. Withdraw in stages: avoid taking multiple peers/sites at once unless security requires immediate withdrawal.
    6. Prove recovery: user success, not merely route absence; surviving sites must remain within tested envelopes.
    7. Fail back slowly: restore announcement preference in stages. Cold caches and synchronized reconnection can overload the recovered site.

    Security incidents may require immediate full withdrawal despite availability risk. Pre-authorize who can make that tradeoff. The Reliability Engineering chapter covers recovery ownership and degraded modes.

    9. Failure evidence¶

    Symptom Evidence to collect Likely classes
    one ISP/ASN cannot connect looking-glass path, route visibility, traceroute boundary, client-AS errors missing propagation, import filter, RPKI invalid, provider fault
    latency jumps for one geography edge site ID, client ASN, route path, DNS answer catchment shift, DNS steering, peering congestion
    all traffic leaves a healthy site local BGP session/advertisement, upstream received routes, ROV state export error, peer rejection, invalid ROA
    site withdrawal overloads neighbor measured redistribution, connection/TLS/cache-miss rates insufficient evacuation headroom
    TCP resets during route change five-tuples and site IDs before/after, connection-state locality stateful anycast path change
    valid route but wrong service TLS certificate/name, HTTP authority, destination ownership misbound VIP, stale config, hijack beyond origin validation
    intermittent global oscillation timelines of DNS, BGP, CDN, autoscaling controllers competing health loops or insufficient hysteresis

    Route collectors show control-plane views, not guaranteed packet delivery. Traceroute shows selected ICMP/TTL-expiry behavior, not necessarily the application path. Combine control-plane, data-plane, and user-journey evidence.

    10. Design review checklist¶

    • Inventory prefixes, ASNs, owners, peers, ROAs, and maximum lengths.
    • Specify import/export policy and maximum-prefix behavior per session.
    • Separate routing reachability from application and capacity health.
    • Measure catchments by request, bytes, connection churn, client ASN, and workload type.
    • Calculate each withdrawal scenario with non-proportional redistribution and retries.
    • Keep every survivor inside a tested safe envelope with degradation policy.
    • Define which controller owns BGP, DNS, CDN, regional, and application decisions.
    • Test stale DNS, route rejection, invalid ROA, site withdrawal, and cold-cache failback.
    • Use independent external route and transaction evidence.
    • Preserve emergency authority and out-of-band access.

    11. Exercises with worked solutions¶

    Exercise 1: Test an AS-path-prepend proposal¶

    A team wants to prepend its ASN three times at Site A so all traffic moves to Site B. Is the claim valid?

    Worked solution

    Solution: No. Remote ASes first apply local policy; some may prefer customer or peering routes regardless of path length, and some may not receive both routes. Define the target catchments, canary the prepend by peer/community, and measure external route selection plus actual traffic. If deterministic evacuation is required, staged withdrawal is stronger but has greater blast radius.

    Exercise 2: Validate failover capacity¶

    Site X serves 500k req/s. On withdrawal, 70% moves to Y and 30% to Z. Y normally serves 900k with a tested ceiling of 1.30M; Z serves 300k with a ceiling of 700k. Retries can add 10% to shifted traffic. Is failover safe?

    Worked solution

    Solution: Y receives 500k * 0.70 * 1.10 = 385k, reaching 1.285M, only 15k below its ceiling. Z receives 165k, reaching 465k. Y has about 1.2% headroom and is unsafe against ordinary skew. Add capacity or shed/redirect enough load before withdrawal, then verify with measured catchments.

    Exercise 3: Explain an RPKI incident¶

    After adding a ROA for 203.0.113.0/24 with origin AS 64530 and maximum length /24, a disaster procedure announces two /25s from AS 64530. Some networks lose reachability.

    Worked solution

    Solution: The /25 announcements are RPKI Invalid because the ROA's maximum length is /24, even though the origin ASN matches. Prefer keeping the authorized aggregate strategy if operationally viable. If more-specific emergency announcements are truly required, change the ROA through a reviewed procedure before the event and understand that broader max length increases authorization scope. Verify propagation from ROV-enforcing and non-enforcing networks.

    Exercise 4: Choose steering layers¶

    A payments API needs stable regional data ownership; static assets need low-latency global delivery.

    Worked solution

    Solution: Use CDN/anycast edge ingress for static assets, with cache and origin shielding. Use DNS or edge routing for coarse API region selection, but let application routing enforce account/home-region write correctness. Do not let BGP movement silently change the data owner. Document independent failure behavior and the handoff between edge and application policy.

    Takeaways¶

    • BGP distributes policy-qualified reachability, not geographic truth or application health.
    • More-specific prefixes and remote local preference can override intended traffic engineering.
    • RPKI origin validation is valuable but does not validate the whole AS path or service identity.
    • Anycast catchments are measured external outcomes, not circles drawn around PoPs.
    • Withdrawal is a capacity event; failback is a cold-cache and reconnection event.
    • Combine DNS, CDN, routing, and application controls only with explicit ownership and evidence.
