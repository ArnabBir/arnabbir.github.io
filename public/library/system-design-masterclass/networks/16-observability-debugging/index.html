    16. Network Observability and Debugging¶

    Network debugging is evidence-driven boundary isolation. “The network is slow” is not a diagnosis: name resolution, route selection, packet filtering, socket queues, transport loss, TLS policy, proxies, application queues, and downstream work expose different evidence. Work from the user symptom toward the narrowest failing boundary, one hypothesis at a time.

    Learning goals¶

    After this chapter, you should be able to:

    • run a layered DNS-to-application troubleshooting method;
    • interpret dig, curl, openssl, ss, tcpdump, and mtr within their limits;
    • combine metrics, traces, flow logs, socket state, and packet captures;
    • distinguish connect, TLS, HTTP, routing, MTU, saturation, and dependency failures;
    • command an incident with safe rollout, rollback, and recovery proof; and
    • design fixture-based alternatives when production shell or packet access is unavailable.

    1. Define the failed contract¶

    Before opening a dashboard, capture:

    who:       client population, ASN/network, zone, workload, tenant
what:      operation, hostname, method, protocol, payload size
when:      first/last seen, continuous or intermittent, deployment timeline
expected:  SLI and threshold
observed:  error, phase duration, status, affected fraction
scope:     one host/zone/region/version/path or global

    Use one correlation bundle when possible:

    timestamp + request/trace ID + client/source + hostname
+ resolved address + destination port + region/zone + deployment version

    Compare a failing request with a known-good control that differs by one dimension. Aggregate graphs establish scope; one trace or packet path explains mechanism.

    2. The layered method¶

    flowchart TD
    S[Reproduce exact symptom] --> D{DNS answer correct?}
    D -- no --> DE[Inspect resolver, authority, TTL, DNSSEC]
    D -- yes --> R{Route and policy permit path?}
    R -- no --> RE[Inspect route, flow logs, ACL, NAT, firewall]
    R -- yes --> T{Transport established?}
    T -- no --> TE[Inspect SYN path, loss, MTU, sockets, capacity]
    T -- yes --> L{TLS established and identity valid?}
    L -- no --> LE[Inspect SNI, chain, trust, time, policy]
    L -- yes --> H{HTTP response valid and timely?}
    H -- no --> HE[Inspect proxy route, queue, retry, upstream]
    H -- yes --> A[Validate application/business outcome]

    The layers are not a rigid OSI checklist. A proxy can terminate TCP/TLS and open a different upstream flow. Repeat the method for each hop and record where identity, protocol, tuple, deadline, and ownership change.

    Evidence ladder¶

    1. User journey: did the intended operation succeed within contract?
    2. Application/proxy: what route, upstream, code, deadline, and retry state were used?
    3. TLS: which name, certificate chain, version, alert, and peer identity?
    4. Transport/socket: did connection setup complete; were there retransmissions, resets, queueing, or exhaustion?
    5. Packet/flow: where was the tuple accepted, rejected, translated, or lost?
    6. Routing/DNS control plane: which answer and route should have produced that data path?

    Start at the cheapest decisive evidence. Escalate capture depth only when the current layer cannot distinguish hypotheses.

    Commands below are templates for authorized test endpoints/namespaces, not localhost fixtures. Documentation addresses require an approved substitution. Prefer the bounded labs; do not elevate privileges or send production payloads merely to reproduce a template.

    3. DNS evidence¶

    dig can query a chosen resolver or authoritative server and show answer, TTL, response code, flags, and delegation. It does not prove which resolver an application used, whether the application cached an older answer, or whether connecting to the address succeeds.

    dig api.example.com A
dig api.example.com AAAA
dig @resolver.example api.example.com A +dnssec
dig +trace api.example.com

    Record:

    • queried name, type, resolver address, response code, and flags;
    • answer/CNAME chain and TTLs;
    • authoritative serial and delegation when relevant;
    • positive versus negative caching;
    • DNSSEC validation status where enabled; and
    • application/runtime cache and search-domain behavior.

    Fixture alternative without production DNS access:

    fixture fields:
queried_at, resolver, qname, qtype, rcode, answers[], ttl[], flags[], transport

    Replay the fixture through the same parser/decision logic. For integration tests, run an isolated authoritative DNS container with scripted stale, NXDOMAIN, delayed, truncated, and split-horizon answers.

    Common DNS traps¶

    • Testing the apex while the application requests a CNAME target or different hostname.
    • Ignoring AAAA when clients prefer IPv6 and its path is broken.
    • Lowering a TTL after old high-TTL answers are already cached.
    • Treating NXDOMAIN and empty successful answers as equivalent.
    • Using /etc/hosts or curl --resolve and then claiming resolver behavior works.

    4. Routes, filtering, and flow logs¶

    A route lookup should answer which source, destination, table, rule, interface, and next hop the host selects. Platform route tables and transit policy may add more hops.

    ip route get 198.51.100.40 from 10.20.4.17

    On systems without ip, use the platform-native route inspection command or an exported route fixture. Capture the effective route, not only intended configuration.

    Cloud flow logs usually summarize accepted/rejected tuples at selected interfaces or boundaries. They are not packet captures: sampling, aggregation, delayed delivery, and provider fields vary. A missing record may mean no packet reached the capture boundary, logging was disabled, the record was sampled out, or filters excluded it.

    Build a boundary ledger:

    Boundary Request tuple/status Response tuple/status Clock/source
    client interface emitted received or absent pcap/socket
    subnet/interface policy accept/reject accept/reject flow log
    NAT/firewall pre/post translation reverse state gateway metrics/log
    server interface received emitted pcap/socket

    If the server sees the SYN and sends SYN-ACK but the client sees no SYN-ACK, do not debug HTTP. Isolate return routing, stateless return rules, NAT state, or asymmetric middleboxes; see NAT and Cloud Networking.

    5. Socket and TCP evidence¶

    ss shows local socket state and queue information. Exact options and exposed TCP diagnostics depend on privileges and kernel.

    ss -s
ss -tanp
ss -ti dst 198.51.100.40

    Interpret patterns rather than one count:

    Observation Hypotheses Next evidence
    many SYN-SENT destination/filter loss, wrong route, listener absent captures at both ends; flow logs
    many SYN-RECV client return path loss, accept pressure, SYN flood server queues, SYN-ACK capture, backlog counters
    accept queue full application not accepting fast enough listener backlog, CPU/thread profile
    send queue persists receiver/window/path congestion TCP info, receiver state, pcap ACK/window
    receive queue persists application not reading app thread/GC/CPU evidence
    high TIME-WAIT connection churn at active closer connection reuse, port range, NAT metrics
    resets explicit endpoint/middlebox termination packet flags, process logs, timing

    Handshake interpretation¶

    client                       server
SYN ------------------------>
    <---------------- SYN,ACK
ACK ------------------------>
    • Repeated SYN with no SYN-ACK: request or return path, filter, listener, or overload.
    • SYN-ACK visible at server but not client: return path/filter/middlebox.
    • ACK followed by immediate RST: wrong listener/protocol, application close, or middlebox policy.
    • Handshake succeeds but payload stalls: TLS/application, receive window, PMTU, or downstream queue.

    TCP retransmission is evidence of missing acknowledgement, not proof of physical packet loss. Reordering, capture loss, asymmetric observation, delayed ACK, or receiver pressure can mislead. Capture both boundaries and use sequence/acknowledgement numbers.

    6. TLS evidence¶

    Use openssl s_client to inspect a handshake explicitly:

    openssl s_client -connect 203.0.113.20:443 \
  -servername api.example.com -verify_hostname api.example.com \
  -showcerts -verify_return_error

    Record SNI, destination address, negotiated TLS version/cipher, ALPN, certificate subject/SAN, issuer chain, validity, verification result, and alert. -servername supplies SNI so shared endpoints select the intended certificate and route; it does not verify that the certificate matches that name. -verify_hostname performs that identity check. If the installed s_client lacks this option, use a hostname-validating client such as curl --resolve with the application trust store rather than treating chain validation alone as success.

    Test the actual trust store and client-certificate behavior used by the application. A shell OpenSSL build may trust a different root bundle. For mTLS, capture which client identity was presented and what destination policy authorized it; see Service Mesh and Zero Trust.

    Failure distinctions:

    Error Likely evidence
    hostname mismatch SAN lacks requested SNI/hostname
    unknown CA incomplete chain or trust bundle lacks issuer
    expired/not yet valid certificate validity versus both endpoint clocks
    no shared protocol/cipher offered/selected versions and policy
    handshake timeout TCP established but TLS records/response absent
    mTLS rejection server requests client cert; identity or chain rejected

    Do not use -k or disabled verification as a fix. It is a diagnostic comparison only, and the insecure result must not be used as recovery proof.

    7. HTTP and proxy evidence with curl¶

    curl can expose phase timings and force one variable while preserving hostname identity:

    curl --fail-with-body --silent --show-error \
  --connect-timeout 2 --max-time 8 \
  --resolve api.example.com:443:203.0.113.20 \
  -o /dev/null \
  -w 'code=%{http_code} ip=%{remote_ip} dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} first_byte=%{time_starttransfer} total=%{time_total}\n' \
  https://api.example.com/health/ready

    Interpret cumulative timestamps correctly:

    DNS phase       = time_namelookup
TCP after DNS   = time_connect - time_namelookup
TLS after TCP   = time_appconnect - time_connect
TTFB after TLS  = time_starttransfer - time_appconnect
body transfer   = time_total - time_starttransfer

    For example:

    dns=0.030 connect=0.090 tls=0.180 first_byte=0.780 total=0.800 seconds

TCP increment  = 0.060 s
TLS increment  = 0.090 s
server/proxy   = 0.600 s
body transfer  = 0.020 s

    The dominant phase is after TLS and before first byte. Investigate proxy queue, upstream calls, retries, and application work before changing DNS.

    The 600 ms includes request transmission and path transit, not just server CPU. These differences assume fresh direct TLS-over-TCP without redirects; reuse, proxy CONNECT, and QUIC need different interpretation. The 30 ms DNS fixture models normal resolution, not the preceding --resolve bypass command.

    --resolve bypasses normal DNS lookup while retaining URL hostname for SNI and HTTP authority. That makes it a useful A/B test, not proof that DNS is healthy. A health endpoint can also bypass the failing dependency or tenant path; replay a safe representative transaction when possible.

    Fixture alternative:

    {
  "url_host": "api.example.com",
  "remote_ip": "203.0.113.20",
  "status": 504,
  "dns_ms": 30,
  "connect_ms": 60,
  "tls_ms": 90,
  "ttfb_after_tls_ms": 600,
  "total_ms": 800,
  "trace_id": "fixture-7"
}

    Use deterministic proxy/application fixtures to teach classification without contacting production.

    8. Packet capture and path probes¶

    tcpdump¶

    Capture narrowly to reduce sensitive data and volume:

    timeout 30s tcpdump -i any -nn -c 200 -s 128 -w incident.pcap \
  'host 198.51.100.40 and tcp port 443'

    -nn avoids reverse lookups and service-name conversion. A short snap length can retain headers while limiting payload, but VLAN, IPv6 extension, encapsulation, and TLS metadata may require more. Obtain authorization, set duration/size limits, protect the file, and delete it under retention policy. Packet captures can contain credentials or personal data.

    This form requires GNU timeout and Linux's any interface. Otherwise use an approved platform wrapper or skip capture. Run in a new restricted disposable directory with umask 077 to avoid overwriting an existing capture. Packet count alone does not bound time on an idle interface. Snaplen 128 can retain payload and is not a privacy guarantee.

    Capture can lie through:

    • NIC offloads that coalesce or segment packets differently from the wire;
    • dropped capture packets under CPU pressure;
    • the any pseudo-interface's link-layer differences;
    • clock skew between hosts;
    • asymmetric routing; and
    • capture at the wrong side of NAT, proxy, or tunnel.

    Record interface, namespace, pre/post-NAT location, filter, snap length, drop count, clock source, and tool version.

    mtr and traceroute boundaries¶

    mtr repeatedly sends probes with increasing TTL/hop-limit and combines latency/loss statistics. Routers may deprioritize, rate-limit, or block probe responses while forwarding application traffic normally. Different protocols and ECMP hashes can take different paths. Loss at an intermediate hop that does not continue at later hops is not evidence of forwarding loss.

    mtr --report --report-cycles 50 --tcp --port 443 api.example.com

    Use a protocol/port close to the application where legal, compare both directions if possible, and correlate the last common healthy boundary with packet/flow evidence. Never identify an intermediate router as root cause from one mtr output alone.

    Fixture alternatives include saved pcap files, sanitized flow-log rows, route-table snapshots, socket-state dumps, and deterministic network namespaces with injected delay/loss. These are preferable for exercises and CI because they are repeatable and avoid production access.

    9. Metrics, traces, logs, and pcap together¶

    Each evidence type answers different questions:

    Evidence Strength Blind spot
    metrics scope, rate, percentiles, saturation aggregation hides individual path and causality
    distributed traces per-request hop timing and retries sampling, missing propagation, work after timeout
    structured logs decisions, errors, config/version context volume, clock/order, missing events
    flow logs tuple, accept/reject, bytes at cloud boundary not packets; delayed/aggregated/sampled
    socket state endpoint queues and TCP state local view only
    pcap packet-level sequence and timing at capture point privacy, volume, capture artifacts, one boundary

    Correlate by stable request/trace ID where possible and by bounded timestamp, tuple, connection ID, proxy upstream, and deployment version otherwise.

    USE and RED at network boundaries¶

    For resources, inspect utilization, saturation, and errors (USE): NIC bytes/packets, conntrack occupancy, NAT ports, socket queues, CPU, drops, gateway limits. For request paths, inspect rate, errors, and duration (RED) by route, status, zone, and version. Histograms must use compatible buckets and units; averages hide tails.

    Avoid unbounded source-IP, URL, tenant, or trace-ID metric labels. Keep high-cardinality context in sampled traces or indexed logs. Observability itself has ingestion and incident-query failure modes; see Cost Engineering.

    10. Symptom matrix¶

    Symptom First discriminating checks Common causes
    NXDOMAIN resolver, qname/type, authority, negative TTL wrong name/view, stale delegation, negative cache
    connect timeout SYN at source/destination, route, flow rejects route/filter, no listener, NAT exhaustion, black hole
    connection refused RST source, listener/socket closed port, wrong target, process restart
    intermittent connect failures destination/zone/IP split, NAT and conntrack one bad target/path, port exhaustion, asymmetric ECMP
    TLS alert SNI, chain, time, ALPN, client identity expiry, trust rotation, hostname, mTLS policy
    fast 503 response issuer and route/upstream state no healthy upstream, admission rejection, deployment
    slow 504 proxy timeout, trace attempt timeline downstream deadline, queue, retries, stale endpoint
    high TTFB, low connect/TLS proxy/app queue and dependencies saturation, lock/GC, slow dependency
    small requests work, large stall PMTU, ICMP, MSS, packet sizes PMTUD black hole, proxy/body limits
    one ISP/geography fails DNS answer, client ASN, route visibility BGP propagation/filter/catchment
    recovery causes second spike connection/TLS/cache-miss/retry rates synchronized reconnect, cold cache, retry storm

    11. Incident command and hypothesis control¶

    Use explicit roles:

    • incident commander: owns objective, priority, risk, decisions, and cadence;
    • operations lead: executes approved mitigations and records change IDs;
    • investigation lead: maintains hypotheses and requests evidence;
    • communications lead: updates stakeholders with impact and uncertainty; and
    • scribe: records timeline, observations, commands, and recovery proof.

    Keep a hypothesis table:

    Hypothesis Prediction Evidence Status Next safe test
    DNS serves old IP failures correlate with resolver/answer answer + remote IP open/rejected query affected resolver
    NAT ports exhausted new connections fail; reused survive allocation metric open/rejected canary extra IP/reuse
    bad release errors correlate with version trace + deployment open/rejected remove canary

    Do not run multiple uncontrolled changes. Timestamp every action. Preserve pre-change evidence when safe. Announce uncertainty rather than turning a plausible story into fact.

    Mitigation selection¶

    Prefer the smallest reversible action that protects the user journey:

    1. stop a harmful rollout;
    2. shed optional load or disable amplification;
    3. drain a bounded target/path;
    4. restore last-known-good policy/configuration;
    5. fail over only after proving destination headroom; and
    6. make invasive network or trust changes with explicit security review.

    Use the Reliability Engineering framework for degraded modes and error-budget decisions. Global path changes require the headroom and withdrawal analysis in BGP, Anycast, and Global Routing.

    12. Rollout and recovery proof¶

    A safe network-related rollout defines:

    scope -> canary -> observation window -> success guardrails
      -> automatic stop -> rollback path -> fleet convergence proof

    Segment outcomes by version, zone, route, destination, protocol, and client cohort. Fleet averages can hide a dead zone or one stale proxy.

    Recovery proof should include:

    • the original representative user operation succeeds;
    • error and latency return inside SLO for a sustained window;
    • DNS, route, proxy, and policy versions match intended state;
    • connection, retry, TLS-handshake, cache-miss, and queue rates stabilize;
    • NAT/conntrack/socket/resource headroom remains under peak replay;
    • forbidden paths and security controls still fail as intended;
    • no delayed queue, replay, or failback wave is accumulating; and
    • rollback remains available until the observation window completes.

    “Pods are healthy” and “ping works” do not meet this bar. Recovery closes the causal chain from user contract through each changed boundary.

    13. Troubleshooting checklist¶

    • Preserve the exact hostname, tuple, timestamp, trace ID, client cohort, and version.
    • Compare one failing and one controlled-good request.
    • Resolve cumulative timings into DNS, connect, TLS, TTFB, and transfer increments.
    • Repeat the layered method at every proxy or translation hop.
    • Record both directions and both sides of stateful boundaries.
    • State tool limitations before drawing conclusions.
    • Bound and protect packet captures and sensitive diagnostics.
    • Change one variable at a time and log the result.
    • Prove user recovery, capacity headroom, and negative security behavior.
    • Keep monitoring through failback, cache warming, and connection drain.

    14. Exercises with worked solutions¶

    Exercise 1: Classify phase timings¶

    curl reports time_namelookup=0.120, time_connect=0.170, time_appconnect=0.260, time_starttransfer=1.060, and time_total=1.080 seconds. Calculate the phases and select the first investigation boundary.

    Worked solution

    Solution: DNS is 120 ms; TCP after DNS is 170 - 120 = 50 ms; TLS after TCP is 260 - 170 = 90 ms; time from completed TLS to first byte is 1,060 - 260 = 800 ms; body transfer is 20 ms. The dominant phase is proxy/application/upstream processing before first byte. Inspect route selection, queue time, retry timeline, and downstream spans. DNS is nontrivial but does not explain most latency.

    Exercise 2: Interpret an mtr result¶

    Hop 5 shows 60% probe loss, but hops 6 through 12 and the destination show 0% loss with stable latency. Is hop 5 dropping application packets?

    Worked solution

    Solution: The evidence does not support that conclusion. Hop 5 likely rate-limits or deprioritizes TTL-expired probe responses while forwarding packets. Test the application protocol, destination loss, and packet/flow evidence. Only loss that persists downstream and correlates with the affected flow is meaningful.

    Exercise 3: Isolate a TLS failure¶

    Connecting by IP succeeds with certificate verification disabled. Connecting to the hostname fails with certificate verify failed. What next?

    Worked solution

    Solution: Do not declare the network fixed or ship disabled verification. Repeat with the correct SNI and application trust bundle. Inspect SAN, chain completeness, issuer, validity, clock, and destination IP. Compare a known-good client. Recovery requires verified hostname authentication and, if applicable, client identity: not merely encrypted bytes.

    Exercise 4: Prove NAT recovery¶

    After adding two egress IPs, new connection errors disappear for five minutes. What additional proof is required?

    Worked solution

    Solution: Show allocation failures remain zero through representative peak and reconnect churn, per-IP port utilization is balanced with N+1 headroom, conntrack and gateway throughput are below tested limits, vendor logs observe approved source IPs, reused and new connections succeed, and retry rate has normalized. Keep rollback and observe beyond old mapping lifetimes.

    Exercise 5: Debug “small works, large hangs”¶

    TCP and TLS complete. A 200-byte request succeeds, while a 4 KiB request stalls after initial packets. What hypothesis and evidence come first?

    Worked solution

    Solution: Suspect PMTU/MSS or a size policy before DNS. Capture packet sizes, acknowledgements, retransmissions, ICMP Packet Too Big/fragmentation-needed messages, negotiated MSS, and proxy body-limit logs at both boundaries. Reproduce with increasing fixture sizes. Correct the MTU/PMTUD path or policy, then prove both small and large representative payloads.

    Takeaways¶

    • Define the failed user contract and preserve one correlation bundle before changing anything.
    • Isolate DNS, route, transport, TLS, HTTP, and application boundaries with discriminating evidence.
    • Every tool has a viewpoint and blind spot; no single command proves end-to-end health.
    • Pair aggregate metrics with request traces and boundary-level packet or flow evidence.
    • Incident command controls hypotheses, risky changes, and communication under uncertainty.
    • Recovery proof includes sustained user success, remaining headroom, converged state, and intact security controls.
