    11. gRPC and RPC Systems¶

    RPC makes a network operation look like a procedure call, but it does not inherit local-call guarantees. gRPC combines a schema contract, generated APIs, HTTP/2 streams, metadata, deadlines, cancellation, and status. A sound design keeps those layers visible and treats retries, streaming, flow control, and compatibility as distributed-system concerns.

    Learning goals¶

    • Evolve Protocol Buffer schemas without corrupting old readers or writers.
    • Choose unary, client-streaming, server-streaming, or bidirectional-streaming RPCs from interaction semantics.
    • Distinguish channel, transport connection, HTTP/2 stream, and protobuf message lifetimes.
    • Propagate deadlines and cancellation while preserving unknown-outcome semantics.
    • Design status, error details, and metadata as stable contracts.
    • Apply backpressure and message limits at every buffering boundary.
    • Define retry safety and load balancing for multiplexed connections.
    • Diagnose proxy and intermediary behavior that breaks gRPC semantics.

    1. Keep the layers separate¶

    application method:   Inventory.Reserve(ReserveRequest) -> ReserveResponse
generated RPC API:    stub, interceptor, serializer, status mapping
gRPC framing:         metadata + length-prefixed messages + trailers
HTTP/2 stream:        one RPC, ordered frames, flow-control windows
HTTP/2 connection:    many concurrent streams to one transport peer
TCP + TLS:            bytes, congestion, peer authentication
network path:         proxies, load balancers, NAT, failures

    A channel is the client’s logical handle to a target. It may resolve names, maintain connectivity state, own one or more HTTP/2 connections, balance calls, and reconnect over time. It is not synonymous with one socket. One HTTP/2 connection multiplexes many RPC streams; one streaming RPC carries many protobuf messages.

    At wire level, one HTTP/2 stream is one RPC attempt. A logical RPC retried by the framework can create multiple streams over its lifetime. Count both logical calls and physical attempts rather than assuming their stream counts are equal.

    2. Service and schema contract¶

    syntax = "proto3";

package inventory.v1;

service InventoryService {
  rpc GetItem(GetItemRequest) returns (Item);
  rpc Reserve(ReserveRequest) returns (ReserveResponse);
  rpc UploadAdjustments(stream Adjustment) returns (UploadSummary);
  rpc WatchStock(WatchStockRequest) returns (stream StockEvent);
  rpc Synchronize(stream SyncMessage) returns (stream SyncMessage);
}

message ReserveRequest {
  string item_id = 1;
  int32 quantity = 2;
  string idempotency_key = 3;
}

    The .proto file defines wire field numbers and generated API names. Wire compatibility, source compatibility, and semantic compatibility are different:

    These schema blocks are excerpts, not standalone compilable fixtures: referenced messages and ItemState are omitted. Compile a complete schema with pinned protoc/runtime versions before claiming generated-source compatibility.

    • A change can remain parseable but alter meaning for old clients.
    • Generated source can break even when the wire remains compatible.
    • Unknown fields can survive parsing/serialization in supported runtimes, but application transformations may still discard them.

    Evolution rules¶

    1. Never reuse a field number, including after deletion. Mark deleted numbers and names reserved.
    2. Adding a field is usually wire-compatible when absence has a safe meaning.
    3. Do not change a field’s meaning while retaining its number.
    4. Avoid changing scalar types unless the official compatibility rules explicitly permit the pair and semantic ranges are safe.
    5. Moving fields into an existing oneof can change presence and clearing behavior; treat it as a migration.
    6. Enum consumers must tolerate unknown numeric values. Do not assume the generated UNRECOGNIZED behavior is identical across languages.
    7. Presence matters. Use explicit optional/presence-aware modeling when “not provided” differs from a scalar default.
    8. Evolve request and response semantics with mixed-version tests, not compilation alone.
    message Item {
  string item_id = 1;
  reserved 2, 4;
  reserved "legacy_price", "warehouse_code";
  optional string display_name = 3;
  ItemState state = 5;
}

    For a semantic migration, add a new field, have new writers populate both where safe, make readers prefer the new representation with fallback, measure old-client usage, stop old writes, and only then retire the old field. Keep its number reserved forever.

    3. Four RPC interaction shapes¶

    Shape Request messages Response messages Fits Does not imply
    unary 1 1 lookup, command, bounded result local-call reliability
    client streaming many 1 upload/aggregate with one final result resumability after disconnect
    server streaming 1 many watch, scan, incremental results durable replay
    bidirectional streaming many many independent interactive exchange globally ordered request/response pairs

    In a bidirectional stream, each direction preserves its own message order. The application must define correlation, causality, completion, and concurrent-send rules. A stream is not a queue: unless the service persists messages and offsets, a disconnect can lose in-flight state.

    sequenceDiagram
    autonumber
  participant C as Client
  participant S as Server
  C->>S: open Synchronize(deadline, metadata)
  par client-to-server order
    C->>S: command seq=41
    C->>S: command seq=42
  and server-to-client order
    S-->>C: event seq=900
    S-->>C: ack command=41
  end
  C->>S: half-close request direction
  S-->>C: final event and OK trailers

    Use explicit message IDs, sequence/offsets, epochs, and acknowledgments when recovery requires them. Half-close means one direction has ended; the other may continue according to the RPC shape and implementation.

    4. Protocol mechanism over HTTP/2¶

    gRPC commonly sends initial metadata in HTTP/2 headers, messages in DATA frames using gRPC message framing, and final status in trailers. HTTP/2 flow control operates on bytes per stream and per connection. A large or unread stream can affect shared connection capacity even though streams are logically independent.

    HTTP/2 connection
  stream 1: unary GetItem      HEADERS DATA TRAILERS
  stream 3: WatchStock         HEADERS DATA DATA DATA ... TRAILERS
  stream 5: Reserve            HEADERS DATA TRAILERS

Connection window is shared; each stream also has a window.

    Each gRPC message has a five-byte prefix independent of HTTP/2 DATA-frame boundaries:

    byte 0:    compressed flag, 0 or 1
bytes 1-4: unsigned message length in network byte order
remaining: exactly that many serialized message bytes

    A flag of 1 means the message bytes use the encoding named by grpc-encoding; compression state is not shared between messages. One message can span several DATA frames, and one DATA frame can contain several messages, so applications must parse the gRPC prefix rather than infer message boundaries from HTTP/2 frames.

    An illustrative unary protobuf exchange is:

    request HEADERS
  :method: POST
  :scheme: https
  :path: /inventory.v1.InventoryService/GetItem
  :authority: api.example.com
  grpc-timeout: 250m
  te: trailers
  content-type: application/grpc+proto

request DATA + END_STREAM
  00 00 00 00 07 <7 protobuf bytes>

response HEADERS
  :status: 200
  content-type: application/grpc+proto

response DATA
  00 00 00 00 12 <18 protobuf bytes>

response trailing HEADERS + END_STREAM
  grpc-status: 0

    grpc-timeout is at most eight decimal digits followed by H, M, S, m, u, or n; here 250m means 250 milliseconds. Reserved pseudo-fields precede ordinary fields, te: trailers detects incompatible intermediaries, and final grpc-status is required even for success. An immediate error may use trailers-only: one terminating HEADERS block containing HTTP status, gRPC content type, grpc-status, and optional grpc-message/details, with no DATA. If a broken intermediary returns a non-gRPC HTTP response without grpc-status, the client synthesizes a gRPC status using the defined HTTP fallback mapping; that lossy fallback never overrides a valid gRPC status.

    HTTP/2 multiplexing removes HTTP/1.1 application head-of-line blocking between responses, but all streams on one TCP connection still share packet-loss recovery and congestion control. One connection failure can fail many in-flight RPCs. Opening unlimited connections avoids neither overload nor fairness problems.

    Invariants¶

    1. Each accepted call uses one service/method contract version and authenticated principal.
    2. Deadlines never increase downstream.
    3. Cancellation releases local resources promptly, while durable side effects follow their idempotency contract.
    4. A stream has bounded messages, bytes, buffered elements, and lifetime or liveness policy.
    5. The producer cannot outrun the slowest required consumer without a documented drop, spill, aggregate, or disconnect policy.
    6. Retries preserve one logical operation identity and occur only when replay-safe.
    7. Load balancing uses call/stream load, not only channel or connection count.
    8. Final status and application state cannot contradict silently.

    5. Deadlines and cancellation¶

    Set a deadline at the caller and propagate remaining time through downstream RPCs. A server should check cancellation before expensive work, stop child calls, release leases, and avoid publishing a result after a cancellation-won state transition. Still, cancellation is cooperative.

    flowchart TD
  A[RPC arrives with deadline] --> B{Enough useful time remains?}
  B -- no --> C[DEADLINE_EXCEEDED]
  B -- yes --> D[Acquire bounded capacity]
  D --> E[Execute and propagate child deadline]
  E --> F{Cancelled?}
  F -- yes --> G[Stop future work and release resources]
   F -- no --> H[Atomically arbitrate cancellation versus effect commit]
  H --> I[Send response and final status]

    DEADLINE_EXCEEDED at the client does not prove the server did nothing. The effect may have committed while the response was delayed. Mutations need idempotency keys or a queryable operation resource. For a client-streaming upload, define whether acknowledged chunks are durable and resumable; otherwise retry starts a new upload.

    Checking a cancellation flag before a later unguarded COMMIT leaves a race. If the domain promises cancellation prevents effects, arbitrate both against the same durable operation state/transaction; otherwise document best-effort cancellation and unknown outcomes.

    6. Status, details, and metadata¶

    Use gRPC status codes for transport-neutral outcome classes and typed error details for stable machine handling. Do not encode every outcome as OK plus {success:false}, and do not expose stack traces or arbitrary internal strings as contracts.

    Status Typical meaning Retry posture
    INVALID_ARGUMENT invalid regardless of current system state do not retry unchanged
    FAILED_PRECONDITION system state blocks the operation caller must change state or workflow
    ABORTED concurrency/transaction conflict retry whole operation only if contract says so
    NOT_FOUND named resource absent usually terminal for that version
    ALREADY_EXISTS create conflicts with existing identity may query existing result
    RESOURCE_EXHAUSTED quota or capacity exhausted honor policy/hint; avoid amplification
    UNAVAILABLE transient service/path unavailable candidate for bounded safe retry
    DEADLINE_EXCEEDED deadline elapsed outcome may be unknown
    INTERNAL / DATA_LOSS invariant or integrity failure do not blindly retry mutations

    Metadata carries cross-cutting context such as authentication, tracing, request identity, deadlines handled by the framework, and routing hints. Bound total metadata size and key/value cardinality. Treat received metadata as untrusted until the immediate peer and issuer are authenticated. Do not place secrets or high-cardinality payloads into routinely logged metadata. Binary metadata and ASCII metadata have different conventions; use generated/typed application messages for domain data.

    Final gRPC status is normally carried in trailers. Proxies must preserve trailers; an intermediary that returns an HTTP error page or strips trailers can collapse precise statuses into UNKNOWN or UNAVAILABLE.

    7. Backpressure and message limits¶

    Flow control prevents unlimited byte transmission on one hop. It does not bound objects already decoded, application queues, fan-out to consumers, database work, or retry buffers.

    network bytes -> HTTP/2 window -> gRPC decoder -> application queue -> worker -> sink
                   bounded            ?                ?             ?

    Bound every ?:

    • maximum receive and send message size;
    • maximum metadata size;
    • messages and bytes buffered per stream and per connection;
    • concurrent streams per peer, tenant, and method;
    • application work queue and executor concurrency;
    • total stream duration, idle/liveness interval, and replay retention;
    • decompressed size, not only compressed wire bytes.

    Read the next message only when downstream capacity exists. For server streaming, slow clients need a policy: backpressure upstream, coalesce state updates, spill durably, drop explicitly labeled lossy updates, or disconnect with a resumable cursor. Never buffer an unbounded “reliable” stream in memory.

    Assumption (illustrative): 5,000 streams each buffer up to 64 messages averaging 8 KiB decoded. Payload memory alone is 5,000 * 64 * 8 KiB = 2,560,000 KiB, about 2.44 GiB, before object, queue, compression, and runtime overhead. A per-stream bound must also fit a process-wide budget.

    Large unary messages delay failure recovery, monopolize windows, and require large buffers. Prefer object storage plus references for blobs, or chunked streaming with checksum, offset, idempotent chunk identity, and resumable state when the use case truly requires transfer through RPC.

    8. Retry safety¶

    Automatic retry depends on both method semantics and how far the attempt progressed. gRPC transparent retry and configured retry are implementation/spec-defined; applications must not infer that an absent response means absent execution.

    The gRPC retry guide calls a call "committed" when response headers arrive and that retry mechanism stops. This is not business transaction commit. Transparent retries before application handling can occur without an explicit policy; configured maxAttempts is not a count of every internal setup operation. Propagate deadlines and measure actual attempts.

    Classify methods:

    GetItem:             read-only; bounded retry may be safe
Reserve(key):        mutation; retry only with durable idempotency key
UploadAdjustments:   stream; retry unsafe unless chunks/session are resumable
WatchStock(after):   stream; reconnect from durable cursor if history retained
Synchronize:         bidi; reconnect requires protocol-specific epochs and replay

    Retries and hedges share the original deadline, attempt cap, and global budget. Service-config policies should be reviewed with gateway and mesh policies so attempts do not multiply. RESOURCE_EXHAUSTED and explicit pushback should reduce load. A retry after partial client-stream transmission must not silently concatenate or duplicate data.

    9. Channels, balancing, and discovery¶

    Reuse channels; creating one per call defeats connection reuse and can cause handshake storms. A channel resolves a logical target into addresses and receives service configuration according to the implementation. Client-side balancing chooses endpoints directly; proxy balancing chooses a proxy connection first and may choose the backend later.

    Multiplexing trap¶

    client channel -- one HTTP/2 connection --> proxy A -- 1,000 RPC streams
client channel -- one HTTP/2 connection --> proxy B --    10 RPC streams

    An L4 balancer sees two connections, not 1,010 streams. Long-lived channels can pin all calls to one proxy. Mitigations include L7 request-aware proxying, client-side endpoint balancing, multiple deliberately managed connections, server load reporting, or maximum connection age with jitter. The right choice depends on trust boundaries and topology; do not churn channels per RPC.

    Balance by endpoint eligibility, locality, active calls/streams, observed load, and method class. Streams may last hours, so draining must stop new calls, send graceful HTTP/2 shutdown, and bound old-stream lifetime or provide application reconnection with cursors/epochs.

    The canonical API Gateway case study integrates gRPC routing, policy, and control-plane rollout. This chapter stays at protocol and client/server mechanics.

    10. Proxy and intermediary failure modes¶

    Problem Evidence Consequence Design response
    proxy supports HTTP/2 from client but HTTP/1.1 upstream negotiated protocols and proxy config native gRPC fails or is translated require end-to-end compatible mode; test trailers and streaming
    trailers stripped wire trace shows missing grpc-status status becomes ambiguous preserve HTTP/2 trailers; synthetic conformance tests
    idle timeout shorter than quiet stream closes at repeatable idle interval watches/bidi streams reset application keepalive/liveness within policy; resumable cursor
    keepalive too aggressive server sends throttling/GOAWAY; fleet sees probe load connection churn or self-induced load coordinate client/server limits and add jitter
    body buffering enabled memory/latency grows with stream streaming becomes store-and-forward disable buffering for streaming routes; bound proxy buffers
    message limit mismatch failures correlate with payload size RESOURCE_EXHAUSTED or intermediary reset publish compatible limits; chunk/reference large objects
    L4 connection pinning streams concentrated on few proxy sockets hotspot despite equal connection count call-aware L7/client balancing and graceful age rotation
    retry at multiple layers trace shows attempt tree amplification and duplicate effects one owner or explicit total budget
    DNS/discovery stale under long channels address generation lags control plane calls stay on retired endpoint resolver updates plus graceful connection rotation

    Test the real path, including sidecars, ingress, cloud load balancers, and TLS modes. A direct local client proving streaming works does not prove production intermediaries preserve HTTP/2, trailers, cancellation, or long idle streams.

    11. Capacity and evidence¶

    Assumption (illustrative): A service receives 30,000 unary RPC/s at 50 ms mean service time and 2,000 streaming calls averaging 20 minutes. Unary mean concurrency is 30,000/s * 0.050 s = 1,500. Streaming concurrency is already 2,000, independent of unary throughput. If each stream buffers 128 KiB across all layers, streaming buffers consume about 250 MiB before connection/runtime overhead.

    Mean concurrency does not establish p99 or a safe limit. Measure:

    • logical calls and physical attempts by service/method/status;
    • deadline remaining at client send and server admission;
    • queue, handler, serialization, and network durations;
    • active channels, connections, streams, and streams per connection;
    • connection age, handshake rate, resolver generation, GOAWAY/reset reasons;
    • sent/received messages and bytes, compressed and decompressed sizes;
    • flow-control stalls and application queue depth/age;
    • cancellation received, cancellation honored, and work completed afterward;
    • retry/hedge amplification and success yield;
    • status-detail parsing failures and unknown-status rate.

    Avoid user IDs and call IDs as metric labels. Put them in sampled traces or controlled logs.

    12. L5, L6, and traps¶

    L5 expectations¶

    • State the proto evolution rules and demonstrate a mixed-version migration.
    • Choose an RPC shape and define ordering, completion, reconnect, and replay semantics.
    • Draw channel, connection, stream, and message boundaries.
    • Define deadline, cancellation, status, limits, backpressure, and retry safety.
    • Explain load balancing and verify every production intermediary.

    L6 extensions¶

    • Govern schemas across languages with compatibility checks, ownership, deprecation evidence, and rollout sequencing.
    • Standardize deadline and attempt budgets across SDK, gateway, mesh, and services.
    • Design global discovery/locality and graceful migration for millions of long-lived channels.
    • Establish method-class admission, tenant fairness, and process-wide memory budgets for streams.
    • Plan protocol/library upgrades through conformance tests, canaries, telemetry, and rollback.

    Interview traps¶

    • Saying RPC is “just a local function call over the network.”
    • Reusing a deleted protobuf field number.
    • Claiming every added field is semantically safe.
    • Treating bidirectional streaming as a durable ordered queue.
    • Equating a channel with one connection or a stream with one message.
    • Assuming flow control bounds application memory.
    • Mapping every domain error to INTERNAL or every failure to OK.
    • Assuming cancellation rolls back a committed mutation.
    • Retrying an entire partially consumed stream without a replay protocol.
    • Using least-connections at L4 for thousands of multiplexed calls.
    • Testing direct-to-server while ignoring production proxies and trailers.

    13. Exercises¶

    Exercise 1: review schema changes¶

    Version 1 has string state = 3. A proposal deletes it and adds State state = 3, where State is an enum. Is this safe? Provide a migration.

    Solution¶

    Open after your attempt

    It is unsafe to reinterpret field 3 from length-delimited string to varint enum and reuse the number. Keep field 3 during migration. Add the enum with explicit presence under a new number, for example optional State state_v2 = 7; make new writers populate both where mappings are exact, make new readers prefer field 7 only when present and otherwise fall back to 3, and measure old-version traffic. After retirement, reserve field number 3 and name state; never assign 3 again.

    Exercise 2: bound stream memory¶

    A process permits 8,000 streams. Each stream may queue 32 decoded messages averaging 16 KiB. Calculate payload memory and repair the design if the process budget for all stream queues is 1 GiB.

    Solution¶

    Open after your attempt

    Payload memory is 8,000 * 32 * 16 KiB = 4,096,000 KiB, about 3.91 GiB, already nearly four times the budget before overhead. If all 8,000 streams remain possible, the average maximum payload allowance is at most 1 GiB / 8,000, about 131 KiB per stream, or roughly eight 16 KiB messages: and practical limits must be lower for overhead and unequal streams. Use process-wide byte accounting, per-stream message/byte limits, demand-driven reads, and a slow-consumer policy.

    Exercise 3: make a watch resumable¶

    WatchStock emits updates but has no event identity. A proxy closes idle connections during deployment. Define the minimum recovery contract.

    Solution¶

    Open after your attempt

    Assign monotonic offsets or versioned cursors within a defined stock scope. The client records the last fully applied cursor and reconnects with after_cursor. The server retains replay history for a published window or returns a specific “cursor expired” status that instructs the client to fetch a snapshot and resume from its version. Updates must be idempotent by entity version. Add jittered reconnect, deadline/liveness policy, and bounded server replay.

    Exercise 4: classify a reserve timeout¶

    Reserve returns DEADLINE_EXCEEDED after the request was fully sent. May the client create a new request and retry?

    Solution¶

    Open after your attempt

    Not with a new logical identity. The reservation may have committed. The client may query by operation identity or retry the identical request with the same scoped idempotency key and fingerprint if the server contract stores/reconciles that key atomically with the effect. The original deadline still governs automatic retry; a later user-driven status query can have its own operation deadline.

    Exercise 5: diagnose false balancing¶

    Four clients each create one long-lived channel through an L4 balancer to four proxies. By chance, three channels land on proxy A and one on B; C and D receive none. Each channel carries 5,000 calls/minute. What does the balancer observe, and what changes help?

    Solution¶

    Open after your attempt

    The L4 balancer observes only four long-lived connections and cannot redistribute their streams. Proxy A receives 15,000 calls/minute while B receives 5,000. Use request-aware L7 balancing, client-side balancing to service endpoints where appropriate, or a bounded set of independently distributed connections with call-aware selection. Jittered maximum connection age can eventually remix placement but is not a primary real-time load signal.
