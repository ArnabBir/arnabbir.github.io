    02. IP, CIDR, and Routing¶

    IP routing is repeated local choice, not one global path reservation. Each forwarding node consults installed state, selects the most specific matching prefix, and sends the packet toward a next hop. Correct system design requires both the address arithmetic and the operational consequences of distributed, changing route state.

    Goals¶

    After this chapter, you should be able to:

    • use Ethernet as the architectural baseline for one-hop delivery;
    • explain ARP and IPv6 Neighbor Discovery state and failure behavior;
    • distinguish IPv4/IPv6 addresses, prefixes, subnets, interfaces, and routes;
    • calculate network ranges and subnet plans with units and capacity margins;
    • apply longest-prefix match to a concrete route table;
    • distinguish a routing control plane, RIB, FIB, and packet data plane;
    • reason about ECMP hashing, flow distribution, asymmetry, and stateful devices;
    • diagnose route, neighbor, policy, and return-path failures from evidence;
    • turn topology mechanics into address, availability, and observability decisions.

    1. First-principles model¶

    An IP packet carries a destination address. A node compares that address against prefixes in a forwarding table. Among matching entries, the longest prefix wins because it describes the smallest, most specific destination set.

    destination IP + local policy + installed forwarding state
    -> selected route
    -> next hop and egress interface
    -> on-link neighbor resolution
    -> frame transmission

    The route is local. The next router repeats the decision from its own state. Forward and reverse traffic can therefore take different paths.

    flowchart LR
    H[Host route lookup] --> N[Resolve next-hop neighbor]
    N --> R1[Router FIB lookup]
    R1 --> R2[Next router FIB lookup]
    R2 --> D[Destination subnet]
    C[Routing control plane] -.installs prefixes.-> R1
    C -.installs prefixes.-> R2

    2. Ethernet as the link baseline¶

    Ethernet provides frame delivery within a link-layer domain. A frame includes source and destination MAC addresses and an EtherType identifying the carried protocol. Switches forward using MAC-related state; routers forward IP packets between links.

    Architecturally:

    • a MAC address is meaningful for delivery on the current link;
    • an IP address supports delivery across routed links;
    • a broadcast domain bounds Ethernet broadcast propagation;
    • a router separates IP subnets and rewrites link framing per hop;
    • VLANs create logical Ethernet segments but do not eliminate the need for routing between subnets.

    For an off-subnet destination, a host sends the frame to the router's MAC while preserving the remote IP destination. This single distinction resolves many interview mistakes.

    2.1 Switch learning baseline¶

    A learning bridge observes source MAC addresses and associates them with ingress ports. For a known unicast destination, it forwards toward the learned port. Unknown unicast and broadcast frames are flooded within the applicable broadcast domain, subject to policy. Entries age; loops require prevention or a controlled fabric design.

    Modern datacenters may use routed fabrics, overlays, or centrally programmed forwarding rather than one large learning domain. Ethernet remains useful as the local-delivery model, not as a claim about the whole topology.

    3. ARP and Neighbor Discovery¶

    3.1 IPv4 ARP¶

    ARP resolves an on-link IPv4 next-hop address to a MAC address. A simplified miss is:

    sequenceDiagram
    autonumber
    participant H as Host
    participant L as Local link
    participant G as Next hop
    H->>L: ARP request: who has next-hop IP?
    L->>G: broadcast request
    G-->>H: ARP reply with MAC
    H->>G: queued IP packet in Ethernet frame

    ARP resolves the next hop, which may be the destination host for an on-link route or a router for a remote route. Cache states and timers vary by implementation. Duplicate addresses, stale entries, suppressed replies, link isolation, or policy can prevent resolution.

    3.2 IPv6 Neighbor Discovery¶

    IPv6 Neighbor Discovery uses ICMPv6 messages for address resolution, router discovery, prefix information, reachability confirmation, and duplicate-address detection. It uses multicast rather than IPv4 ARP broadcast. Blocking ICMPv6 indiscriminately can break basic IPv6 operation.

    Neighbor Discovery and routing remain separate:

    • routing chooses an on-link next hop;
    • ND resolves and tracks that neighbor's link-layer reachability;
    • a reachable neighbor does not prove the final destination is reachable;
    • an unresolved neighbor can stop traffic even when the route table looks correct.

    3.3 Neighbor invariants¶

    1. Resolve only addresses considered on-link by local routing state.
    2. A neighbor-cache entry has scope on one interface/link.
    3. Neighbor reachability is time-varying state, not a permanent identity fact.
    4. Gratuitous ARP or unsolicited advertisements can update caches during legitimate movement, but require security controls in hostile domains.

    4. IPv4 and IPv6 addressing¶

    4.1 Prefix notation¶

    CIDR notation writes an address and prefix length, such as 192.0.2.64/26. The first 26 bits identify the prefix; the remaining 6 bits identify addresses inside that block.

    IPv4 address bits = 32
host bits          = 32 - prefix length
block size         = 2 ^ host bits addresses

    For IPv6:

    IPv6 address bits = 128
addresses in /64  = 2 ^ (128 - 64) = 2 ^ 64

    IPv6 subnet planning should not copy IPv4 conservation habits blindly. A /64 is the standard subnet size for mechanisms that depend on 64-bit interface identifiers, including SLAAC. Plan hierarchy and route aggregation rather than counting individual host addresses.

    4.2 Address scope and semantics¶

    Family/type Example Design meaning
    IPv4 private-use 10.0.0.0/8 not globally routed on the public Internet; overlap is still possible
    IPv4 loopback 127.0.0.0/8 local host only
    IPv4 link-local 169.254.0.0/16 local link behavior, not general routed service addressing
    IPv6 global unicast commonly 2000::/3 space globally scoped unicast addressing subject to allocation/routing
    IPv6 link-local fe80::/10 required local-link scope; interface context matters
    IPv6 loopback ::1/128 local host only
    IPv6 unspecified ::/128 absence of an address; never a normal destination

    An address assigned to an interface is not necessarily a promise of reachability. ACLs, routes, security groups, source selection, neighbor state, service binding, and return paths must all agree.

    5. CIDR calculations¶

    5.1 Find a network range¶

    For 10.24.37.142/20, /20 corresponds to mask 255.255.240.0. The third-octet block size is 256 - 240 = 16. Blocks begin at 0, 16, 32, 48, and so on. 37 lies in 32-47.

    network = 10.24.32.0/20
range   = 10.24.32.0 through 10.24.47.255
count   = 2 ^ (32 - 20) = 4096 addresses

    Traditional IPv4 subnet terminology reserves the all-zero host address as the subnet identifier and all-one host address as directed broadcast, yielding 4094 conventional host addresses. Platform reservation rules can reserve additional addresses. /31 point-to-point semantics and /32 host routes are special cases; never apply 2^h - 2 mechanically to every context.

    5.2 Subdivide a block¶

    Split 10.40.0.0/22 into /24 blocks:

    new prefix bits = 24 - 22 = 2
subnet count    = 2 ^ 2 = 4

10.40.0.0/24
10.40.1.0/24
10.40.2.0/24
10.40.3.0/24

    Split it into /26 blocks:

    new prefix bits = 26 - 22 = 4
subnet count    = 2 ^ 4 = 16
addresses each = 2 ^ (32 - 26) = 64

    5.3 Size with headroom¶

    Suppose a zone needs 180 workload interfaces, 30 infrastructure interfaces, and 25% growth on the combined 210:

    planned interfaces = 210 * 1.25 = 262.5 -> 263

    A conventional /24 has 256 total addresses and is already too small before platform reservations. A /23 has 512 total addresses. The correct choice still depends on cloud reservations, rolling deployments, surge, failure replacement, and whether each workload consumes multiple addresses.

    Address capacity is deploy capacity

    A subnet can exhaust during a rollout even when steady-state hosts fit. Include old and new replicas, load balancer interfaces, managed-service endpoints, node churn, and emergency headroom.

    6. Longest-prefix match¶

    Given this simplified table:

    Prefix Next hop Interface
    0.0.0.0/0 192.0.2.1 eth0
    10.0.0.0/8 10.1.0.1 eth1
    10.24.0.0/16 10.2.0.1 eth2
    10.24.8.0/24 directly connected eth3
    10.24.8.128/25 10.3.0.1 eth4

    Selections are:

    Destination Winning prefix Reason
    8.8.8.8 /0 only default matches
    10.9.4.5 /8 /8 is most specific match
    10.24.7.5 /16 /24 does not cover third octet 7
    10.24.8.40 /24 /25 covers only 128-255
    10.24.8.200 /25 all broader routes match, /25 wins

    Administrative preference and route metrics choose among candidate routes according to implementation/control-plane rules. Longest-prefix selection comes first for forwarding specificity; a more attractive default cannot override a matching specific route.

    The table assumes usable next-hop adjacencies not shown here. Policy-routing rules select a lookup table before its longest-prefix match; a more-specific route in another VRF/table need not apply. ECMP flow affinity also assumes stable membership and hashing: reconvergence can move an existing connection's packets.

    7. Packet and state flow: route tables, RIBs, and FIBs¶

    Terms vary by implementation, but the conceptual separation is stable:

    • Routing information base (RIB): candidate routes learned from connected networks, static configuration, or routing protocols.
    • Route selection: policy chooses preferred route or next-hop set per prefix.
    • Forwarding information base (FIB): optimized installed state used to forward packets.
    • Control plane: learns, computes, validates, and distributes state.
    • Data plane: applies installed forwarding state to packets.
    flowchart TD
    A[Connected and static routes] --> R[RIB]
    B[Routing protocols] --> R
    P[Import and preference policy] --> R
    R --> S[Best-route selection]
    S --> F[FIB and next-hop objects]
    F --> D[Packet forwarding]

    A control plane can report intended convergence while one device, line card, host namespace, or virtual switch retains stale data-plane state. L6 diagnosis compares desired route, selected route, installed FIB, and observed packet forwarding.

    7.1 Recursive next hops¶

    A route can name a next-hop IP that itself requires another route lookup to resolve an egress adjacency. Operationally, a visible prefix is usable only if its next-hop chain resolves to a valid interface/neighbor. A route shown in a control table may therefore remain inactive or fail forwarding.

    7.2 Policy routing¶

    Some systems use source address, mark, interface, tenant, VRF, or other fields in addition to destination. "Show the route to X" is incomplete if the actual packet carries policy selectors. Reproduce the source, namespace, and policy context.

    8. ECMP, hashing, and asymmetry¶

    Equal-cost multipath installs multiple eligible next hops for a prefix. Implementations usually hash packet fields so packets from one flow tend to follow one path, avoiding widespread transport reordering.

    Common hash inputs include some combination of:

    source IP, destination IP, protocol, source port, destination port

    8.1 Distribution is statistical¶

    With N equal links and many independent, similarly sized flows, expected average flow count per link is roughly total flows divided by N. Real traffic is skewed:

    • one elephant flow usually remains on one member;
    • a small number of flows distributes unevenly;
    • correlated tuples can hash poorly;
    • member removal remaps some or many flows depending on algorithm;
    • encapsulation can hide or expose inner fields to the hash.

    Four 10 Gbit/s paths do not guarantee one TCP flow 40 Gbit/s. They provide aggregate capacity across distributable flows, bounded by endpoint and path constraints.

    8.2 Asymmetric routing¶

    The reverse flow performs independent lookups and may traverse different links or devices. Asymmetry is valid IP behavior but interacts with stateful systems:

    • a firewall that sees only one direction may reject traffic;
    • NAT state created on one appliance may be absent on another;
    • captures on one path can miss the response;
    • latency and MTU can differ by direction;
    • failure detection can remove only one direction's route.

    Stateful service insertion requires symmetry, synchronized/distributed state, or an architecture that does not require one box to observe both directions.

    8.3 ECMP failure example¶

    If one of eight ECMP members black-holes traffic and flow hashes are stable, approximately one eighth of sufficiently diverse new flows may fail under a simple uniform model:

    expected failing-flow fraction = 1 / 8 = 12.5%

    That is an expectation, not a guaranteed observed percentage. Retries with a new source port may hash to another path and appear to "fix" the request, while retries reusing a connection remain pinned to the failed path.

    9. Routing invariants¶

    1. Prefix invariant: a /p fixes the first p address bits; all remaining combinations belong to the block.
    2. Selection invariant: forwarding chooses the most specific matching installed prefix before considering equal candidates for that prefix.
    3. Hop invariant: each router chooses only the next hop from local state; no ordinary IP header guarantees the complete path.
    4. Return-path invariant: reachability is directional until the reverse path is proven.
    5. Adjacency invariant: a route that cannot resolve its next-hop adjacency cannot forward useful traffic.
    6. Aggregation invariant: advertising a summary claims reachability for the entire summary unless more specific routing or discard policy safely handles holes.
    7. Stateful-path invariant: a stateful middlebox must receive packets needed to create and use its flow state.
    8. Capacity invariant: usable subnet capacity includes platform reservations and deployment surge, not only steady-state application interfaces.

    10. Failure signatures and observability evidence¶

    Failure Typical signature Evidence to collect Common confusion
    No matching route immediate local error or drop route lookup in exact namespace/source context remote firewall
    Bad more-specific route one prefix fails while aggregate works RIB/FIB entry and route provenance DNS because hostnames correlate
    Neighbor failure same-subnet or gateway traffic stalls neighbor state, ARP/ND exchange, interface/VLAN remote service outage
    Routing loop TTL/Hop Limit expires, repeating hops traceroute-style evidence, device FIBs application retry loop
    ECMP bad member stable subset of flows fail tuple-correlated failures, per-member counters random endpoint errors
    Asymmetric stateful drop one direction visible, return denied both-direction flow logs and appliance state server never responded
    Address overlap destination follows unintended local/private route full route/policy tables at both domains packet loss
    Subnet exhaustion deployments cannot allocate interfaces address manager/platform allocation errors compute quota
    Stale FIB control plane correct, packets wrong intended route vs installed FIB vs capture slow application propagation

    Evidence sequence¶

    1. Resolve the actual destination address used by the failing request.
    2. Identify source address, namespace/VRF, interface, and policy marks.
    3. Obtain the host's route decision for that exact context.
    4. Verify next-hop neighbor state on the selected interface.
    5. Compare packet observation before and after each owned boundary.
    6. Inspect flow/ACL/NAT evidence in both directions.
    7. Compare desired control-plane route, selected route, and installed FIB.
    8. Group failures by source/destination prefix and five-tuple to expose ECMP correlation.

    Read-only inspection is usually enough for diagnosis. Do not add routes, clear neighbor caches, or alter interfaces on a shared or production host merely to test a theory.

    11. Design implications¶

    Address plans¶

    • Allocate hierarchical prefixes by region, environment, zone, and function so summaries remain meaningful.
    • Reserve growth and migration space; renumbering is a cross-system project.
    • Prevent overlap across networks that may later connect through peering, VPN, acquisition, or disaster recovery.
    • Treat IPv4 scarcity and translation as operational costs; design dual-stack behavior explicitly where used.
    • Track address utilization as a capacity SLI, not an inventory footnote.

    Routing and failure domains¶

    • Prefer smaller failure domains and aggregated external announcements, while preserving specific internal steering where needed.
    • Withdraw a route only when the serving unit cannot safely handle traffic; avoid route flaps from noisy health checks.
    • Ensure failover capacity can absorb shifted traffic. Reachability without capacity is not resilience.
    • Test both directions and long-lived flows. Existing flows may retain old state while new flows use new routes.
    • Put stateful appliances in a topology with explicit symmetry or state sharing.

    ECMP-aware applications¶

    • Use many connections only when concurrency and backend semantics justify them; do not multiply connections solely to game hashes.
    • Keep retries bounded and understand whether a retry reuses the same tuple/path.
    • Measure by path-relevant dimensions such as zone, interface, tunnel, source/destination prefix, and backend.
    • Plan draining for member removal so remapped traffic does not overload survivors.

    L5 expectation L6 expectation
    Computes CIDR ranges and capacity correctly Creates an aggregateable plan with surge, migration, and overlap strategy
    Applies longest-prefix match Distinguishes desired RIB state, selected route, FIB, and observed forwarding
    Explains default gateway and neighbor resolution Diagnoses adjacency, policy-routing, namespace, and overlay interactions
    Uses ECMP for aggregate scale Quantifies skew, remapping, elephant flows, and survivor capacity
    Notes return-path requirements Designs stateful boundaries under asymmetry and partial convergence
    Suggests route and flow telemetry Defines cross-domain evidence, rollout, rollback, and ownership

    13. Traps¶

    • Treating a subnet mask as a decimal naming convention rather than fixed leading bits.
    • Using 2^(32-p)-2 for /31, /32, or provider-specific usable capacity without checking semantics.
    • Assuming private IPv4 ranges cannot overlap or cannot be routed internally.
    • Confusing the remote IP with the first-hop MAC destination.
    • Believing a route table entry proves forwarding hardware or virtual-switch state.
    • Saying ECMP "bonds bandwidth" for one flow.
    • Assuming reverse traffic follows the same path.
    • Advertising a summary without handling unreachable holes safely.
    • Fixing an apparent neighbor issue by clearing production state before collecting evidence.
    • Blocking all ICMPv6 and expecting IPv6 Neighbor Discovery to work.

    14. Exercises with worked solutions¶

    Exercise 1: range and membership¶

    Find the network, final address, and total address count for 172.20.77.9/21. Does 172.20.80.1 belong?

    Worked solution

    /21 has mask 255.255.248.0; third-octet blocks have size 8. 77 is in the 72-79 block.

    network = 172.20.72.0/21
final   = 172.20.79.255
count   = 2 ^ 11 = 2048 addresses

    172.20.80.1 belongs to the next /21, so it does not match.

    Exercise 2: deployment sizing¶

    A subnet must support 220 current workload interfaces, a 50% rolling surge, 24 infrastructure addresses, and 15 provider-reserved addresses. Select the smallest IPv4 prefix with enough total addresses.

    Worked solution 
    surged workload = 220 * 1.5 = 330
required total  = 330 + 24 + 15 = 369 addresses

    A /24 has 256 total addresses and fails. A /23 has 512 and is the smallest power-of-two CIDR block that fits. Operational policy may choose a larger aggregate for future growth.

    Exercise 3: longest-prefix route¶

    Routes are 10.0.0.0/8 -> A, 10.64.0.0/10 -> B, 10.80.0.0/16 -> C, and 10.80.4.0/22 -> D. Select paths for 10.80.6.7, 10.80.9.1, and 10.100.1.1.

    Worked solution
    • 10.80.6.7 is inside 10.80.4.0-10.80.7.255, so /22 -> D wins.
    • 10.80.9.1 misses /22 but matches /16 -> C.
    • 10.100.1.1 is inside 10.64.0.0/10 (second octet 64-127), so /10 -> B wins over /8.

    Exercise 4: ECMP partial failure¶

    Four ECMP members carry 40,000 short flows/s uniformly in expectation. One member silently drops. Estimate affected new flows and explain why retries may distort measurement.

    Worked solution 
    expected affected flows/s = 40,000 / 4 = 10,000 flows/s

    Actual load varies with hash and flow sizes. A retry on a new connection may choose a new source port and member, masking the defect while adding traffic. A retry on the same connection remains on its established path. Measure first attempts by tuple and member-correlated evidence rather than only terminal success.

    Exercise 5: asymmetric firewall¶

    Requests traverse firewall A, but route convergence sends responses through firewall B. Both keep local connection state. Predict the failure and propose three design options.

    Worked solution

    Firewall B may see return traffic without state created by the request and drop it. Options are:

    1. enforce symmetric routing through the same state owner;
    2. synchronize/distribute state with defined convergence and failure semantics;
    3. remove the stateful dependency from that path or use stateless policy where requirements permit.

    The evidence plan compares directional flow logs, state-table entries, routes/FIBs, and endpoint captures. Merely loosening policy hides the architecture defect and may weaken security.
