    HTTP/2, HTTP/3, and QUIC¶

    HTTP versions preserve HTTP semantics while changing how messages share transport state. The key design question is not “which version is fastest?” but which handshake, loss, multiplexing, resource, and fallback behavior matches the path and workload.

    Mental model¶

    HTTP/1.1: HTTP messages -> ordered bytes on one TCP connection
HTTP/2:   HTTP messages -> frames -> multiplexed streams -> one TCP connection
HTTP/3:   HTTP messages -> frames -> QUIC streams -> UDP datagrams

    HTTP/2 removes application-level serialization between streams, but TCP still delivers one ordered byte stream. HTTP/3 places streams directly on QUIC, so packet loss need not block unrelated streams. Both protocols still share connection-level congestion and flow-control limits.

    HTTP/1.1 connection behavior¶

    Persistent connections amortize TCP and TLS handshakes. In common practice, one connection has one active request/response at a time; pipelining exists but is difficult to deploy because responses remain ordered and intermediaries vary. Parallelism therefore uses a bounded pool. Closing-delimited bodies prevent safe reuse. Idle timeouts, NAT state, server draining, and synchronized reconnects shape capacity.

    At 2,000 requests/s with 50 ms mean response time, Little's Law gives 2,000 * 0.050 = 100 active requests. With one active request per connection, roughly 100 busy connections are required before burst and tail headroom. More connections do not increase throughput after the origin saturates.

    HTTP/2 wire and stream state¶

    After protocol negotiation and the client connection preface, peers exchange frames. Important types include SETTINGS, HEADERS, DATA, WINDOW_UPDATE, RST_STREAM, PING, and GOAWAY. Frames carry a stream identifier; stream 0 is connection control. Client-initiated streams use odd identifiers.

    stateDiagram-v2
    [*] --> idle
    idle --> open: HEADERS
    open --> halfClosedLocal: local END_STREAM
    open --> halfClosedRemote: remote END_STREAM
    halfClosedLocal --> closed: remote END_STREAM
    halfClosedRemote --> closed: local END_STREAM
    open --> closed: RST_STREAM
    halfClosedLocal --> closed: RST_STREAM
    halfClosedRemote --> closed: RST_STREAM

    Frame ordering and legality depend on stream state. A stream can close while the connection remains reusable. SETTINGS_MAX_CONCURRENT_STREAMS limits peer-created concurrent streams; it is not a promise of application capacity.

    This diagram is the common request-stream subset, not the complete RFC 9113 state machine: reserved push states and a HEADERS frame that also carries END_STREAM are omitted. Both open and half-closed streams count toward the peer's concurrency limit. A client must respect a lower advertised limit even if its local configured cap is larger.

    HPACK¶

    HPACK compresses fields using static and dynamic tables. Encoder and decoder maintain synchronized connection state. Sensitive fields can be marked never-indexed, but compression still consumes memory and CPU. Bound field count, field size, compressed block size, and dynamic-table size. Cross-origin compression contexts require careful isolation because secret-dependent compression can leak information.

    Flow control and GOAWAY¶

    HTTP/2 has per-stream and connection receive windows for DATA; control frames are not flow-controlled the same way. Receivers send WINDOW_UPDATE as they consume bytes. A blocked connection window stalls every data stream even if individual stream windows remain.

    GOAWAY announces the last stream identifier the sender might have processed and starts graceful drain. The peer opens a replacement connection and may retry streams above that identifier if application semantics permit. A reset or missing response does not prove that an unsafe operation had no effect.

    Coalescing and TCP head-of-line blocking¶

    A client may reuse one HTTP/2 connection for multiple origins when authority, certificate, DNS/address, and client policy satisfy RFC requirements. Coalescing saves handshakes but couples origins to one congestion, failure, and privacy domain. Never route solely because a certificate wildcard matches.

    TCP delivers bytes in sequence. If segment 20 is lost, bytes from segment 21 onward wait even if they contain another HTTP/2 stream. This is transport head-of-line (HoL) blocking.

    QUIC transport behavior¶

    QUIC integrates TLS 1.3 and exposes reliable ordered streams without exposing a reliable connection-wide byte stream. QUIC packets carry frames such as ACK, STREAM, CRYPTO, MAX_DATA, MAX_STREAM_DATA, and connection-close frames.

    sequenceDiagram
    autonumber
    participant C as Client
    participant S as Server
    C->>S: Initial: ClientHello, token if available
    S-->>C: Initial/Handshake: ServerHello and TLS flight
    C->>S: Handshake completion plus application data
    S-->>C: 1-RTT HTTP/3 data
    Note over C,S: Connection state survives path change using issued CIDs

    Connection IDs and migration¶

    QUIC connection IDs decouple a connection from a network 4-tuple. A client changing from Wi-Fi to cellular can validate the new path and continue. Servers issue multiple IDs and retirement rules; load balancers need routable, privacy-conscious ID design. Migration does not preserve path congestion assumptions: validate reachability and reset congestion state as required.

    The connection, not one immutable wire CID, persists. RFC 9000 section 9.5 prohibits intentional reuse of a CID from multiple local addresses. Use an unused peer-issued CID for a new client path; unintentional NAT rebinding is a different case. Migration requires a confirmed handshake and compatible peer policy. Under section 9.2, a client can send to the already-known server before its new-path probe completes; the server independently validates the new client address and obeys anti-amplification. CID routing must still reach the endpoint holding connection keys and stream state; it does not make arbitrary anycast server replacement transparent. See the migration lab.

    Loss, congestion, and flow control¶

    QUIC acknowledges packet-number spaces and detects loss using acknowledgments and timers. Retransmission sends the lost information in new packets with new numbers. Congestion control limits aggregate sending on a path. Connection MAX_DATA and stream MAX_STREAM_DATA independently bound received application bytes; stream-count limits bound concurrency. Advertised credit must fit a finite receive-memory budget; extending credit faster than a slow application can consume bytes eventually exhausts that budget.

    Amplification and address validation¶

    Before validating a client's address, a server must not send more than three times the bytes it has received on that path. A 1,200-byte Initial therefore permits at most 3,600 bytes before validation. Large certificate chains can hit this limit, causing an extra round trip or Retry. Tokens let a server validate return routability while controlling replay and privacy exposure.

    0-RTT¶

    With prior session state, a client may send early data before the fresh handshake completes. Early data can be replayed by an attacker; transport acceptance does not make an application action exactly once. Restrict 0-RTT to replay-safe operations, bind policy to remembered settings, and expose acceptance/rejection telemetry. TLS and PKI covers ticket and trust lifecycle.

    HTTP/3 and QPACK¶

    HTTP/3 maps request/response exchanges to QUIC streams and uses separate unidirectional control and QPACK streams. QPACK avoids requiring each request stream to carry the entire compression context. Dynamic-table references can still block decoding until encoder instructions arrive, so implementations bound blocked streams and table capacity. Losing one request's packets does not block unrelated stream delivery, but congestion control, CPU, connection flow control, or QPACK dependencies can still affect all work.

    Invariants¶

    1. HTTP meaning and retry safety remain identical across protocol versions.
    2. Stream and connection limits bound memory, CPU, and queued work.
    3. A graceful drain does not assign new work to a connection after its accepted-stream boundary.
    4. Origin coalescing occurs only when DNS, certificate, authority, and policy all authorize it.
    5. 0-RTT application data is replay-safe or rejected.
    6. QUIC path changes are validated before unrestricted sending.
    7. Every deployment retains a tested fallback path without hiding protocol-specific failures.

    Calculations¶

    Bandwidth-delay product and windows¶

    A 500 Mbit/s path at 80 ms RTT needs:

    BDP = 500,000,000 bit/s * 0.080 s = 40,000,000 bits = 5 MB

    A 1 MiB connection window cannot fill that path if credit replenishment takes about one RTT. Raising it to 8 MiB removes this particular ceiling, not TCP congestion, stream-window, receiver, or CPU limits. Budget permitted unconsumed bytes across connections; connection credit is not necessarily preallocated RAM.

    Multiplexing capacity¶

    At 6,000 requests/s and 40 ms mean duration, mean concurrency is 240. If each HTTP/2 connection allows 100 concurrent streams, the arithmetic floor is three connections. Use more than the floor for draining and congestion isolation, but not hundreds without evidence.

    Handshake impact¶

    At 100 ms RTT, cold TCP plus a normal TLS 1.3 handshake costs roughly two RTTs before the client sends its request, or about 200 ms, absent TCP Fast Open, HelloRetryRequest, and DNS. Request/response transit and server work follow; 200 ms is not time to first response byte. QUIC combines transport establishment and TLS in one handshake progression; resumed 0-RTT may send early application data, but replay restrictions apply.

    Design choices and fallback¶

    Use ALPN to negotiate HTTP/2 (h2) over TLS. HTTP/3 can be discovered from an Alt-Svc HTTP response or, for capable clients, from an RFC 9460 HTTPS DNS record whose alpn includes h3; the DNS route can expose the option before the first HTTP connection. HTTPS records can also bind an alternate target or port and provide address hints, but clients still authenticate the original origin and must reject records with unsupported mandatory parameters. Attempt QUIC over UDP while retaining a working HTTP/2 or HTTP/1.1 route. Race or delay fallback deliberately: waiting too long on blocked UDP hurts users; abandoning QUIC too quickly prevents recovery and masks path quality. Apply the bounded lifetime and authenticated-failure rules of the discovery mechanism, clear stale state on relevant network change or repeated failure, and compare DNS-advertised and HTTP-advertised alternatives during rollout.

    Choice Strong fit Cost / risk
    HTTP/1.1 pool universal compatibility, simple debugging more connections and handshake churn
    HTTP/2 mature multiplexing on reliable low-loss networks TCP HoL and connection concentration
    HTTP/3 lossy/high-RTT clients, mobile path changes UDP blocking, CPU, newer tooling
    one multiplexed connection maximal reuse one failure/congestion domain
    small connection set isolation and drain headroom extra handshakes and state

    Failure matrix¶

    Failure Symptom Evidence Response
    HTTP/1 pool exhaustion queue delay before connect/use pool wait, active/idle counts bound queue; reuse; add only measured capacity
    HTTP/2 TCP loss all streams pause together retransmissions plus stream latency path repair; small connection set; evaluate H3
    exhausted H2 window DATA stalls but control works zero windows, missing updates fix consumer; tune windows with memory budget
    bad GOAWAY handling failed requests during deploy last-stream ID and retry logs drain; replace connection; retry only safe work
    HPACK/QPACK pressure CPU/memory spike or decode errors table size, blocked streams, field bytes cap fields/table/blocked streams; reject abuse
    UDP blocked H3 attempt delays then H2 succeeds QUIC timeout by network quick bounded fallback; retain telemetry
    amplification limit handshake stalls with large cert bytes received/sent before validation shrink chain; token/Retry strategy
    migration routing failure connection dies on network switch connection ID/path validation logs fix LB CID routing; fall back to reconnect
    0-RTT replay duplicate effect early-data and operation logs reject unsafe early data; deduplicate application command

    Evidence and diagnostics¶

    curl --max-time 5 -sv --http1.1 https://example.com/
curl --max-time 5 -sv --http2 https://example.com/
curl --max-time 5 -sv --http3 https://example.com/
openssl s_client -connect example.com:443 -servername example.com -verify_hostname example.com -verify_return_error -alpn 'h2,http/1.1' </dev/null
nghttp -nv https://example.com/
# qlog is an implementation telemetry format, not a universal executable.

    These are command templates for an authorized test endpoint, not the offline lab path. Check curl -V for compiled HTTP/2 and HTTP/3 support. --http3 can fall back, so record the negotiated result; a successful command alone does not prove H3. OpenSSL/nghttp need an operator-enforced time limit and synthetic traffic. Skip public probing and use offline labs by default.

    Capture negotiated ALPN/version, handshake/resumption time, connections per origin, active/queued streams, frame errors, GOAWAY last-stream ID, reset codes, flow-control stalls, compressed/uncompressed field bytes, TCP retransmissions, QUIC loss/PTO, congestion window, RTT, path migrations, validation state, 0-RTT acceptance, H3 attempt/fallback reason, and latency by network type. Correlate packet evidence with application request IDs; either alone is incomplete.

    L5 and L6 signals¶

    An L5 answer explains streams, frames, flow control, HoL, GOAWAY, QUIC migration, 0-RTT risk, capacity math, and fallback. An L6 answer defines fleet protocol policy, resource defaults, connection/coalescing isolation, abuse controls, rollout cohorts, UDP and mobile-path evidence, regional fallback capacity, and rollback ownership.

    Traps¶

    • Claiming HTTP/2 eliminates HoL blocking.
    • Equating MAX_CONCURRENT_STREAMS with server worker capacity.
    • Retrying every stream after GOAWAY without checking the boundary and method semantics.
    • Treating QUIC as unreliable because it uses UDP.
    • Saying HTTP/3 makes loss irrelevant; congestion and connection limits remain shared.
    • Enabling 0-RTT for mutations because the request has an idempotency key without an actual deduplication store.
    • Comparing versions using only warm, lossless localhost tests.

    Exercises and solutions¶

    1. Window sizing¶

    A 1 Gbit/s inter-region path has 60 ms RTT and an HTTP/2 connection window of 2 MiB. What is the ceiling from that window?

    Worked solution

    Solution: BDP is 1e9 * .06 / 8 = 7.5 MB. With one RTT per credit cycle, 2 MiB / .06 s = 33.33 MiB/s = 34.95 MB/s = 279.62 Mbit/s, not 35 MiB/s. Increase carefully or use more isolated connections, while budgeting receiver memory.

    2. Deployment drain¶

    A server sends GOAWAY with last stream 101. The client had streams 99, 101, and 103.

    Worked solution

    Solution: Streams 99 and 101 may have been processed and require their normal outcomes. Stream 103 was not processed by that endpoint according to the boundary and may be retried on a new connection. Preserve request deadlines and idempotency contracts across other ambiguous attempts; GOAWAY does not erase effects from an earlier application retry.

    3. H3 rollout¶

    Design a safe mobile HTTP/3 rollout.

    Worked solution

    Solution: Advertise bounded Alt-Svc to a small cohort, keep H2 fallback, cap QUIC attempt delay, and compare handshake, p50/p99, loss, CPU, bytes, fallback, and network-change success by carrier/OS. Expand only with server and fallback headroom; withdraw the advertisement to roll back while existing alternatives age out. Coordinate HTTPS DNS records too if both discovery mechanisms are enabled; merely omitting a later Alt-Svc field does not immediately clear a previously cached alternative.
