    Interviewer Packet¶

    Practice home | Rubric | Exemplars | Failure lab

    Keep this file closed to candidates during the blind phase.

    Interview objective¶

    Evaluate whether the candidate can reason from mTLS and HTTP/2 properties, preserve authorization independently from identity, separate control-plane intent from data-plane fact, diagnose mixed evidence, and lead a reversible migration under load.

    Mode selection¶

    Mode Use when Required evidence Optional extension
    20 min Focused screen Invariants, plane split, safe sequence, one rollback Fresh versus reused connection
    35 min Standard L5 Add drain, retries, observability, gates Stale cohort
    50 min Deep L5/L6 Add fixtures, calculations, flow control, migration Zone loss
    70 min Staff calibration Add ownership, compromise policy, governance, alternatives Executive debrief

    Opening script¶

    "Design a zero-downtime CA rotation for the path in the prompt. Start by stating invariants and boundaries. You may ask for details. I will provide incident evidence only when you request a relevant category. Keep identity authentication separate from request authorization."

    Do not mention the unsafe rollout order, stale cohort, connection masking, short drain, retry multiplication, or flow-control stall in the opening.

    Assumptions available on request¶

    Candidate asks about Disclosure Signal to observe
    Certificate model Proxies receive trust bundles and short-lived workload leaves from the mesh control plane Separates root trust, issuer choice, and leaf identity
    mTLS direction Both peers authenticate; inventory and database paths have independent policy Expands receiver trust on both sides
    Configuration status Distributor success does not guarantee proxy activation Requests active version and rejection evidence
    Connections HTTP/2 sessions can last 45 minutes Requires fresh-connect probes
    Streams Long requests exist; active stream duration p99 is 38 seconds Derives drain deadline rather than guessing
    Retries SDK max_attempts=2; client proxy max_attempts=3; DB client max_attempts=2; each count includes the initial attempt Calculates 6 inventory and 24 DB attempts maximum
    Staleness 264 of all 2,400 API client sidecars, or 11%, missed the bundle; all belong to z2-v40 Quarantines and blocks old-root removal
    Authorization Policy maps workload identity and action; it is not encoded by root trust alone Preserves negative tests
    Failure symptoms TLS errors cluster by client config version; some authenticated DB streams also stall Looks for multiple causes
    Compromise The planned case is expiry, not compromise Keeps overlap; can articulate emergency exception

    Checkpoints¶

    Minute 5¶

    Look for scope, zero-downtime definition, trust compatibility, least privilege, and explicit identity-versus-authorization separation.

    If absent, ask: "What does validating a certificate prove, and what does it not prove?"

    Minute 12¶

    Look for control-plane desired/active distinction, data-plane handshakes, and trust expansion before issuer change.

    If absent, ask: "Can a successful config push prove a fresh connection will work?"

    Minute 22¶

    Look for dual trust, credential cohorts only after all receiver trust is active, fresh non-resumed canaries, and rollback. Server-before-client issuance is this pack's operational choice, not a TLS requirement once every receiver has dual trust; accept an equivalently safe alternate order.

    If absent, ask: "What happens to an old-only client when the server presents a new-issued leaf?"

    Minute 35¶

    Look for GOAWAY, active-stream completion, drain capacity, reconnect shaping, and one retry budget.

    If absent, disclose the 45-minute connection lifetime and retry counts.

    Minute 50¶

    Look for evidence joins across trust, issuer, config, TLS, frames, GOAWAY, retry traces, and authorization.

    If absent, provide Fixture E from the failure lab and ask what it disproves.

    Minute 65¶

    Look for ownership, stale exception expiry, audit proof, completion criteria, rejected alternatives, and emergency-compromise policy.

    Branching follow-ups¶

    Branch A: Candidate rotates servers before expanding trust¶

    Ask: "A client is disconnected and trusts only the old CA. The server reconnect presents a new-issued leaf. Walk the handshake."

    • Strong recovery: identifies unknown_ca, pauses issuance, restores compatible server credentials if needed, distributes dual trust, and proves active state.
    • Weak recovery: adds retries or disables verification.
    • Apply the 17-point safety cap if the final design remains unsafe.

    Branch B: Candidate says dual trust solves everything¶

    Ask: "A certificate from a trusted CA identifies an analytics workload calling inventory.write. Should the call pass?"

    • Strong: authentication succeeds; separate authorization denies the action.
    • Weak: any trusted certificate is accepted.
    • Apply the identity-equals-authorization cap if uncorrected.

    Branch C: Candidate trusts rollout status¶

    Reveal Fixture C from the failure lab.

    Ask: "Which field is authority for active proxy behavior, and what data-plane proof remains necessary?"

    • Strong: uses active version/digest plus fresh handshake probes.
    • L6: redesigns readiness and rollout accounting so desired, acked, active, and observed states remain separate.

    Branch D: Candidate overlooks long-lived HTTP/2¶

    Ask: "Your canary sent 10,000 successful requests over one 40-minute-old connection. What did it prove?"

    • Strong: only the established session and request path; it did not test the new chain.
    • Follow-up: request a fresh/reused probe matrix and graceful drain plan.

    Branch E: Candidate proposes a short restart¶

    Reveal Fixture F.

    Ask: "Calculate reconnect demand and explain the 63 resets."

    • Strong: computes 3,600/s mean for five seconds, compares with 300/s tested capacity, then proposes GOAWAY, stream-aware deadline, and shaping.
    • L6: reserves zone capacity and defines overload ordering.

    Branch F: Candidate calls every timeout TLS failure¶

    Reveal Fixture E.

    Ask: "PING is acknowledged but DATA is blocked. What hypothesis fits, and what evidence would confirm it?"

    • Strong: connection-level flow-control stall; inspect WINDOW_UPDATE, windows, reader progress, proxy version, and downstream consumption.
    • Weak: rotate certificates again or increase timeout.

    Branch G: Candidate says retries will hide the event¶

    Reveal Fixture G.

    Ask: "Show the attempt tree and choose retry owners."

    • Strong: computes 6 inventory and 24 DB attempts; removes independent retries, propagates deadlines, adds jitter and retry budgets.
    • L6: sheds retries before primary traffic and quantifies retry tax.

    Branch H: Candidate handles stale workloads well¶

    Ask: "Eight percent cannot receive config for seven days; leaves expire in 24 hours. Do you wait, fail open, or isolate?"

    • Strong: removes them from service, replaces or repairs them, gives exceptions an owner and expiry, and blocks old-root removal until proof.
    • L6: distinguishes availability policy from a compromised-root emergency.

    Branch I: Candidate is migration strong¶

    Ask: "Where is the point of no easy return? What evidence permits destruction of old signing material?"

    • Strong: old-trust removal and key destruction follow zero old use, fresh matrices, expired exceptions, rollback drill, and joint approval.
    • L6: distinguishes disabling routine issuance, retaining protected rollback, revocation, trust removal, and key destruction.

    Branch J: Candidate is technically strong but organizationally vague¶

    Ask: "Security wants immediate removal, platform sees config lag, and inventory owns the SLO. Who decides?"

    • Strong L6: preassigns pause and rollback authority, uses explicit gates, records risk acceptance, and gives security final CA-retirement approval.

    Evidence notes¶

    Capture exact statements, not impressions.

    Area Evidence heard Contradiction Follow-up used Score
    Invariants
    Identity/access
    Planes/config
    Sequence
    HTTP/2/drain
    Diagnosis
    Retries/overload
    Observability
    Migration/rollback
    Leadership

    Calibration anchors¶

    Below target¶

    Changes issuers before trust, removes old trust too early, weakens verification, or treats trusted identity as authorization. Uses retries and restarts as the main recovery.

    Weak L5¶

    Finds dual trust but misses fresh-connection proof, graceful drain, active-state evidence, or retry multiplication.

    Borderline L5¶

    Safe sequence and rollback exist. Diagnosis or stale-fleet policy remains shallow, and calculations need interviewer prompting.

    Strong L5¶

    Runs a safe end-to-end migration, separates both planes and security decisions, handles HTTP/2 lifecycle, bounds retries, and gives actionable evidence.

    Borderline L6¶

    Adds quantified gates, mixed-failure diagnosis, cohort governance, and completion proof, but leaves one material ownership or emergency-policy gap.

    Strong L6¶

    Shapes requirements, distinguishes routine and compromise paths, quantifies reconnect and retry risk, assigns decision rights, and makes removal auditable and reversible until the declared boundary.

    Scoring procedure¶

    1. Select the mode before the interview.
    2. Score only dimensions available in that mode.
    3. Record exact evidence and contradictions.
    4. Normalize using the rubric formula.
    5. Apply the lowest safety cap.
    6. Report mode, subtotal/available -> normalized/40, cap, and level.

    Example: 35 min, 26/32 -> 33/40 (round-half-up), no cap, borderline L6 numeric band for mode; I/J unassessed, no L6 leadership conclusion.

    The fixtures are synthetic disclosure cards, not an executable mesh. Read the RFC 9113 flow-control and GOAWAY rules before treating PING, WINDOW_UPDATE absence, or a reset as causal proof. Ask for receiver consumption/version evidence before accepting a proxy-version rollback; the supplied trace does not identify a defective version.

    Debrief script¶

    1. "Your strongest demonstrated evidence was..."
    2. "The highest-risk gap was..."
    3. "To close it, I needed to see..."
    4. "A next-level exercise is..."

    Do not reveal fixture answers before the candidate commits to a hypothesis. Reward corrections when new evidence appears, but distinguish independent discovery from interviewer-led repair.

    Interviewer anti-patterns¶

    • Leading with the unsafe server-first event instead of allowing sequence discovery.
    • Calling a control-plane acknowledgement proof of data-plane activation.
    • Treating every 403, reset, or timeout as a certificate symptom.
    • Rewarding product names without protocol behavior.
    • Penalizing a candidate for choosing controlled unavailability during confirmed CA compromise.
    • Comparing normalized scores without stating the mode.
