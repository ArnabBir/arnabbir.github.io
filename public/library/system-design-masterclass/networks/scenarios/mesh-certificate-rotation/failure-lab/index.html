    Failure Lab: The Rotation That Failed Twice¶

    Practice home | Workbook | Migration

    Mission¶

    Diagnose a partial outage during CA rotation. Build a causal graph from fixtures, separate concurrent failure modes, choose immediate actions, and define safe recovery. Do not assume every timeout has one cause.

    Architecture context¶

    flowchart LR
    API[API app] --> CP[Client proxy]
    CP -->|mTLS HTTP/2| SP[Server proxy]
    SP --> INV[Inventory app]
    INV -->|mTLS HTTP/2| DP[DB proxy]
    DP --> DB[(DB)]
    CTRL[Control plane] -. trust, issuer, config, policy .-> CP
    CTRL -. trust, issuer, config, policy .-> SP
    CTRL -. trust, issuer, config, policy .-> DP

    All timestamps are UTC on 2026-09-06. These are offline synthetic transcripts, not captured production traffic or an executable mesh. Do not inject these faults into a shared cluster. Configuration and certificate metadata exclude private keys and credentials.

    Incident timeline¶

    Time Event
    09:00 Control plane begins trust bundle version 41 rollout
    09:06 Rollout reports 89% client proxies acknowledged version 41
    09:08 Inventory server issuer switches from ca-old to ca-new
    09:09 Fresh TLS handshake failures appear in zone z2; aggregate success remains high
    09:11 Operator requests a five-second connection drain fleet-wide; some disconnected proxies miss the command
    09:12 Resets, reconnects, and retries spike across all zones
    09:14 Database latency rises although database CPU remains at 42%
    09:17 Inventory p99 reaches 4.8 seconds; 18% of requests fail
    09:20 Rotation is paused; no configuration is rolled back
    09:23 Old HTTP/2 cohorts on proxies that missed the drain still show successful inventory calls

    Fixture A: trust inventory¶

    Snapshot at 09:08:30:

    Proxy cohort Count Active trust roots Last control-plane contact
    API client z1-v41 790 ca-old,ca-new under 30 s
    API client z2-v40 264 ca-old 2 h to 19 h
    API client z3-v41 1,346 ca-old,ca-new under 30 s
    Inventory server 240 ca-old,ca-new under 30 s
    Database proxy 180 ca-old,ca-new under 45 s

    Fixture B: issuer inventory¶

    Time Endpoint cohort Presented leaf issuer Leaf expiry
    09:07 Inventory server ca-old 2026-09-07 09:07
    09:08 Inventory server ca-new 2026-09-07 09:08
    09:08 API client mixed: 93% ca-old, 7% ca-new within 24 h
    09:08 Database proxy ca-old within 24 h

    Fixture C: active configuration¶

    proxy=api-z2-117 desired=41 acked=40 active=40 trust_sha=7f-old issuer=ca-old stale_for=11h
proxy=api-z1-044 desired=41 acked=41 active=41 trust_sha=91-dual issuer=ca-old stale_for=0s
proxy=inv-z2-008 desired=52 acked=52 active=52 trust_sha=91-dual issuer=ca-new stale_for=0s
proxy=db-z2-019 desired=63 acked=63 active=63 trust_sha=91-dual issuer=ca-old stale_for=3s

    The rollout dashboard counts a proxy as complete when the distributor accepts the desired version. It does not query the proxy's active version.

    Fixture D: fresh TLS and authorization records¶

    09:09:03 conn=f912 src=api-z2-117 dst=inv-z2-008 tls=fail alert=unknown_ca peer_issuer=ca-new
09:09:04 conn=f913 src=api-z1-044 dst=inv-z2-008 tls=ok peer_issuer=ca-new peer_id=inventory
09:09:04 conn=f913 request=r101 authz=deny principal=spiffe://prod/analytics action=inventory.write status=403
09:09:05 conn=f914 src=api-z1-044 dst=inv-z2-008 tls=ok peer_issuer=ca-new peer_id=inventory

    The 403 record proves successful authentication for that connection and a separate authorization denial. It is not a CA-rotation failure.

    Fixture E: HTTP/2 frame trace¶

    Connection db-c771 was established at 08:51 with valid ca-old credentials and remains cryptographically valid.

    09:13:40.010 stream=301 HEADERS end_stream=0
09:13:40.011 stream=301 DATA_total bytes=65535 frames=4 conn_send_window=0
09:13:40.050 type=PING ack=0
09:13:40.052 type=PING ack=1
09:13:41.000 stream=303 HEADERS end_stream=0
09:13:44.900 stream=301 DATA blocked_ms=4889 conn_send_window=0
09:13:44.901 stream=303 DATA blocked_ms=3901 conn_send_window=0
09:13:45.000 type=WINDOW_UPDATE observed=none duration_ms=4990

    The trace aggregates four DATA frames, each at most the default 16,384-byte frame payload; it is not one oversized frame. It shows connection liveness but no DATA progress after the connection-level send window reaches zero. PING and HEADERS are not DATA flow-controlled. The missing update alone does not establish whether the receiver stopped consuming, a proxy bug withheld updates, or the trace vantage point missed them.

    Fixture F: GOAWAY and drain records¶

    09:11:00.000 conn=inv-c441 active_streams=187 action=GOAWAY last_stream_id=781 drain_deadline_ms=5000
09:11:05.001 conn=inv-c441 active_streams=63 action=force_close
09:11:05.002 conn=inv-c441 rst_streams=63 reason=connection_termination
09:11:05.020 cohort=all reconnect_rate_s=1840 handshake_p99_ms=920

    Before the drain, the fleet had 18,000 established API-to-inventory connections. A planned reconnect capacity test sustained 300 handshakes/s with p99 below 250 ms.

    Fixture G: layered retry trace¶

    root_request=u77 sdk_attempts=2
sdk=1 mesh_attempts=3 db_operations_per_inventory_attempt=2 db_attempts_per_operation=2
sdk=2 mesh_attempts=3 db_operations_per_inventory_attempt=2 db_attempts_per_operation=2
root_request=u77 inventory_attempts=6 database_attempts=24 final=deadline_exceeded

    At 12,000 original requests/s, primary inventory traffic normally causes 24,000 database operations/s before retries.

    Fixture H: aggregate signals¶

    Window Fresh TLS failure (% of fleet fresh attempts) Reused-connection success Authorization deny Forced stream reset Retry tax DB CPU
    09:00-09:08 0.00% 99.97% 0.04% 0.00% 3% 41%
    09:09-09:11 10.8%, attributed to z2-v40 99.94% 0.05% 0.00% 21% 41%
    09:12-09:17 7.1%, attributed to z2-v40 81.6% 0.05% 6.4% 286% 42%

    These are fleet-attempt denominators, not success fractions within the old-only cohort: fresh calls from that cohort to new-only-issued servers fail trust validation. For this pack, retry tax = retry inventory attempts / primary inventory attempts, including failed primaries, within the same window. It is not the fraction of all attempts that failed or an SLO error fraction.

    Candidate tasks¶

    1. Build a causal graph¶

    Connect only claims supported by fixtures. Include at least two independent causes.

    flowchart TD
    A[Observed symptom] --> B[Candidate cause]
    B --> C[Evidence]
    B --> D[Safe action]

    2. Rank hypotheses¶

    Rank Hypothesis Supporting fixtures Disconfirming fixtures Next query
    1
    2
    3

    3. Calculate impact¶

    1. Maximum inventory attempts per original request.
    2. Maximum database operation attempts per original request.
    3. Maximum attempted inventory calls/s and database operations/s at 12,000 requests/s.
    4. Mean reconnect rate required to drain 18,000 connections in 5 seconds and in 10 minutes.
    5. For a hypothetical constant 18% failure lasting 14 minutes, calculate equivalent full-outage minutes and compare with a 99.95% 30-day error budget. The timeline does not supply enough interval data to claim this as the incident's actual budget consumption.

    4. Choose immediate actions¶

    Order actions for the first 15 minutes. State what to pause, what to restore, what not to disable, how to shed load, and which traffic to quarantine.

    5. Define recovery and exit criteria¶

    Specify the evidence required to resume issuance, complete draining, clear stale cohorts, fix frame progress, re-enable bounded retries, and close the incident.

    Facilitator diagnosis¶

    Open after committing to hypotheses, calculations, and recovery actions

    There are four interacting faults and one correctly functioning control:

    1. Trust/issuer incompatibility. New-issued inventory server credentials appeared while 264 z2 clients still trusted only ca-old. Fresh handshakes from that cohort failed with unknown_ca.
    2. Long-lived connection masking. Old HTTP/2 connections remained successful because they did not perform new handshakes. Aggregate success hid the fresh-path failure.
    3. Unsafe drain. A five-second fleet-wide deadline forced 63 streams closed on one sampled connection and drove 1,840 reconnects/s against tested capacity of 300/s.
    4. Retry amplification and a separate flow-control stall. Layered retries amplified one request into 6 inventory and 24 database attempts. Connection db-c771 was alive and authenticated, but its connection window reached zero without WINDOW_UPDATE, so certificate rollback alone could not restore DATA progress.
    5. Authorization worked. The analytics principal authenticated and then received 403. Do not weaken policy or classify that denial as a trust failure.

    Worked calculations¶

    Inventory attempts/request = 2 SDK attempts * 3 mesh attempts = 6
Database attempts/request = 6 * 2 operations * 2 attempts = 24
Inventory attempts/s = 12,000 * 6 = 72,000
Database operation attempts/s = 12,000 * 24 = 288,000

Reconnects/s over 5 s = 18,000 / 5 = 3,600/s
Reconnects/s over 10 min = 18,000 / 600 = 30/s

30-day minutes = 30 * 24 * 60 = 43,200
99.95% error budget = 43,200 * 0.0005 = 21.6 full-outage minutes
Hypothetical equivalent outage = 14 min * 0.18 = 2.52 min
Hypothetical budget consumed = 2.52 / 21.6 = 11.7%

    This is a constant-volume sensitivity calculation, not the actual request-based SLO consumption. Time-equivalent outage is sum(duration * failure fraction); request-based consumption is failed eligible requests / (0.0005 * total eligible requests in the 30-day window). Unequal traffic across intervals makes the two different. Layered retries produce up to 24 DB attempts versus a two-operation baseline, so database attempt amplification is 12x, not 24x.

    The 5-second mean of 3,600 reconnects/s is already 12x tested capacity; the observed 1,840/s can still overload handshakes. At 10 minutes, 30/s leaves 10x mean headroom below the 300/s tested limit, though zone skew and burst behavior still require measurement.

    Immediate response¶

    1. Stop new-CA issuance and the global drain; keep dual trust installed.
    2. Route new traffic away from stale z2-v40 clients and preserve healthy established sessions temporarily.
    3. Restore old-issued inventory credentials by verified cohort if fresh-connect availability requires it.
    4. Disable optional retries first, enforce propagated deadlines, and shed excess traffic before primary work.
    5. Inspect receiver consumption, both flow-control windows, and version-split traces for the database path. No supplied fixture proves a bad proxy version. Roll one back only with supporting cohort evidence and compatibility checks; otherwise isolate stalled work or shift to a verified healthy path under replay-safety and capacity limits. Verify resumed DATA progress.
    6. Do not disable certificate verification or broaden authorization.
    7. Resume only after active-state inventory and forced-fresh probes pass by cohort.

    Prevention review¶

    • Gate issuer changes on active dual-trust proof, not distributor acceptance.
    • Include disconnected and stale proxies in a quarantine or replacement workflow.
    • Probe fresh and reused connections separately.
    • Derive drain duration from connections, active streams, handshake latency, and tested reconnect capacity.
    • Keep frame-level progress signals for HTTP/2 dependencies.
    • Enforce one end-to-end retry budget and alert on retry tax.
    • Preserve independent authorization tests throughout security migrations.

    Sources: RFC 9113 sections 4.2, 5.2, and 6.8, RFC 9846 section 4.5.1, and Envoy xDS eventual consistency. The offline mTLS lab checks a two-sided compatibility matrix; it does not execute this incident or establish its cause.
