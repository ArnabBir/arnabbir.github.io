    Migration: Fragile Checkout Path to a Robust Edge¶

    Practice home | Failure lab | Interviewer packet

    Starting point¶

    The current path has mutable DNS endpoints, inconsistent forwarding rules, independent retries, fixed-size checkout and payment pools, CPU-only scaling, and time-based termination. Mobile clients and resolvers retain network state longer than one deployment.

    The service cannot stop for a big-bang replacement. Existing checkout operations must keep their payment identity and processing generation through retries, rollout, rollback, and regional recovery.

    Target properties¶

    • Versioned edge endpoints with measured compatibility overlap.
    • TLS at the public edge and authenticated encrypted origin transport.
    • Canonical forwarded metadata written only by trusted proxies.
    • One absolute request deadline and one bounded retry policy.
    • Durable checkout operation identity, established before payment, reused as the payment idempotency key.
    • Bounded queues, dependency-aware concurrency, and explicit load shedding.
    • Endpoint lifecycle driven by readiness, route withdrawal, connection drain, and active-work completion.
    • Hop-level traces and cohort metrics.
    • Single-owner payment writes with fenced regional failover.

    Candidate tasks¶

    1. Order the risks by customer and payment harm.
    2. Define compatibility contracts for mobile clients, resolvers, edge generations, headers, deadlines, and operation IDs.
    3. Produce stages with entry, observation, promotion, and rollback gates.
    4. Preserve in-flight ownership when feature flags or traffic generations change.
    5. Prove the new admission and retry behavior under payment slowdown.
    6. Remove old endpoints and legacy headers only after usage reaches a measured exit condition.

    Required control plane¶

    Every accepted checkout records a stable operation ID and processing generation. Retries follow that record rather than the current traffic flag. Endpoint generations have explicit states: WARMING, SERVING, DRAINING, and RETIRED. A generation may be retired only after address, connection, and active-operation evidence reaches its exit threshold.

    Stage Authority and generation Shadow or comparison Promotion gate Rollback behavior
    0. Baseline evidence
    1. Identity and trace contract
    2. Trusted edge contract
    3. Deadline and retry control
    4. Admission and pool control
    5. Versioned endpoint lifecycle
    6. Regional recovery
    7. Legacy retirement

    Draft the migration before opening the reference plan.

    Reference migration and facilitator notes

    Target architecture¶

    flowchart LR
    M[Mobile clients] -. lookup .-> D[Versioned DNS]
    D -. answer .-> M
    M --> E[TLS edge and admission]
    E -->|mTLS, canonical headers, deadline| X[Bounded proxy]
    X --> C[Checkout operation owner]
    C -->|stable key, concurrency limit| P[Payment]
    C --> S[(Operation store)]
    O[Observability] --- E
    O --- X
    O --- C

    Stage 0: Baseline evidence¶

    Instrument the existing path without changing authority. Record one correlation ID across DNS answer when available, edge endpoint, connection age, proxy, checkout generation, operation ID, physical attempt, and payment key. Measure cache age, handshake failures, forwarded-header variants, queue age, pool wait, retries, resets during drain, and provider effects per operation.

    Gate: normal peak and one controlled payment-slowdown window are represented; dashboards expose mixed endpoint and app-version cohorts.

    Stage 1: Identity and trace contract¶

    At first trusted ingress, create or validate a bounded request ID. Before any payment attempt, execute an idempotent create-operation protocol: use a stable merchant or order identifier when one already exists, otherwise persist a new opaque operation ID and return it to the client before payment can begin. Persist the operation ID, request hash, processing generation, canonical state, and payment idempotency key. A retry of create-operation returns the same record. Old clients that cannot retain the returned ID must use a compatibility adapter backed by a stable order identifier; never derive a payment key heuristically from payload contents, timing, or a deduplication window. If no collision-safe identity exists, reject payment initiation rather than guess.

    Rollback: stop assigning new operations to the wrapper. Existing operations retain their generation and key. Never create a fresh payment identity because traffic moved backward.

    An atomic operation claim authorizes one dispatcher; a stable provider key alone does not serialize concurrent calls. Unknown outcomes require reconciliation, not concurrent takeover. Create-operation needs a stable client/order key even when the server first assigns an opaque operation ID: returning it before dispatch does not prove the client received the reply.

    Stage 2: Trusted edge contract¶

    Deploy edge generation E2 in shadow and synthetic modes. Strip inbound forwarding headers, then set canonical scheme, authority, client chain, trace context, and signed or authenticated origin identity. Add mTLS from edge to proxy or an equivalent authenticated encrypted channel. Compare redirect, cookie, callback URL, and policy decisions between generations.

    Gate: spoofing tests pass; no unexpected redirect or secure-cookie delta; origin accepts metadata only from authenticated edge identities.

    Stage 3: Deadline and retry control¶

    Introduce an absolute deadline header on trusted internal hops. Old clients still receive server-side budgets. Disable inner write retries first, then enable one checkout-owned retry only for proven-safe transport conditions, with the same payment key, jitter, remaining budget, and a global attempt token. Return a stable processing response when an accepted payment outcome is unresolved.

    Gate: physical calls per operation remain within budget during reset, timeout, and late-response tests; no call begins without response reserve.

    Stage 4: Admission and pool control¶

    Add short bounded proxy queues, checkout concurrency limits, and payment-specific adaptive concurrency. Scale on admitted concurrency, queue age, pool wait, payment latency, and deadline exhaustion rather than CPU alone. Reserve capacity for status and reconciliation. Test the 4,000/s baseline and 8,000/s sensitivity with 900 ms payment latency.

    Gate: queues remain bounded, accepted work meets its deadline target, payment offered load stays within contract, and shedding is fair and observable.

    Stage 5: Versioned endpoint lifecycle¶

    Publish new endpoints before shifting traffic. Warm TLS, origin connections, caches, and health. Move cohorts through 1, 5, 25, and 100 percent. Keep old endpoints serving for more than the measured resolver cache and connection-age window. To remove checkout instances: mark not ready, confirm route withdrawal, send the protocol-appropriate drain signal, reject new streams, wait for active operations to finish or reach their owned recovery state, then terminate.

    Gate: zero requests reach a retired endpoint, active work at exit is zero, drain reset rate is within budget, and rollback has been rehearsed.

    Stage 6: Regional recovery¶

    Keep each accepted checkout operation in one home region. Replicate operation evidence and serve safe status reads from a secondary region. Promotion requires fencing the prior writer generation and deciding how in-flight payment operations finish. Never replay an ambiguous operation in a new region with a new key.

    Gate: a game day proves stale-writer rejection, operation lookup, dependency credential readiness, and RPO/RTO targets without duplicate effects.

    A database generation flag does not fence a partitioned worker's external API call. Before transferring dispatch, stop/fence that caller at an enforced egress or provider boundary and resolve outstanding calls. If strict no-concurrent-call proof is unavailable, pause new payment dispatch; global key deduplication can protect effects but is not proof that calls did not overlap.

    Stage 7: Legacy retirement¶

    Inventory mobile versions, resolver cohorts, edge addresses, forwarding variants, retry paths, dashboards, and manual runbooks. Remove one compatibility path at a time after no-use and fault-recovery windows. Archive generation mappings and operation evidence for the required retry and dispute horizon.

    Promotion scorecard¶

    Gate Example threshold Stop authority
    Payment effects per operation No unexplained value above 1 Payments on-call
    Physical attempt amplification p99 at or below approved budget Checkout owner
    Queue age p99 below admission budget Edge SRE
    Header correctness 100 percent canonical in canary Security owner
    Endpoint retirement Zero traffic after retirement Network owner
    Active work at process exit Zero, except recorded recoverable operations Checkout owner
    SLO regression Within approved canary error budget Incident commander

    Cost and reversal triggers¶

    • More edge overlap increases address, certificate, and egress cost but protects cached clients.
    • More checkout instances do not fix a hard payment concurrency limit; scale only after dependency budgets are enforced.
    • mTLS adds certificate and handshake operations; revisit termination placement if measured latency or ownership cost exceeds the security benefit, not to bypass authentication.
    • A managed global edge may replace bespoke DNS control when it can expose endpoint cohorts, drain state, and origin trust evidence.
    • Active-active payment writes remain rejected until the provider and checkout authority can enforce global idempotency and fence stale writers.
