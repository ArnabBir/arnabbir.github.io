    TLS 1.3 and Public Key Infrastructure¶

    TLS protects a connection only after peers agree on protocol parameters, authenticate required identities, derive fresh traffic keys, and enforce application policy. PKI makes identity scalable; it also creates lifecycle, clock, revocation, and ownership dependencies.

    Mental model¶

    DNS/address selection chooses where to connect.
SNI requests a virtual server identity at that endpoint.
Certificate validation decides whether that identity is trusted.
TLS key exchange derives connection keys.
ALPN selects the application protocol.
Authorization decides what the authenticated peer may do.

    Authentication is not authorization. Encryption is not endpoint health. TLS termination is not end-to-end protection unless every later hop has an explicit protection and identity contract. See Security Architecture for the broader threat model.

    TLS 1.3 handshake¶

    TLS 1.3 has three key-establishment modes: asymmetric key exchange, PSK, and PSK combined with asymmetric key exchange. The common first-connection flow below uses asymmetric key establishment and certificate-based server authentication; certificates are omitted when a PSK authenticates the handshake. A PSK can be externally provisioned or derived from an earlier connection for resumption. PSK-only mode does not provide forward secrecy for application data, while combining a PSK with fresh asymmetric key establishment does. RFC 9846 uses generic asymmetric-key-exchange language so extensions can define KEM-based groups as well as finite-field or elliptic-curve Diffie-Hellman.

    sequenceDiagram
    autonumber
    participant C as Client
    participant S as Server
    C->>S: ClientHello: versions, key_share, SNI, ALPN
    S-->>C: ServerHello: selected key_share
    S-->>C: EncryptedExtensions, Certificate, CertificateVerify, Finished
    Note over C: Validate chain, name, policy, and server proof
    C->>S: Finished
    C->>S: application data
    S-->>C: NewSessionTicket

    In this illustrated mode, ephemeral asymmetric key establishment provides forward secrecy. CertificateVerify proves possession of the certificate's private key; Finished authenticates the handshake transcript. In PSK-authenticated modes, the PSK authenticates the handshake and certificate messages are omitted. After ServerHello, most handshake messages are encrypted. A HelloRetryRequest can add a round trip when the offered key shares are unsuitable. TLS alerts and transport closure are distinct failure evidence.

    PKI chain and name validation¶

    A leaf certificate is signed by an intermediate CA, which chains toward a locally trusted root. Servers normally send the leaf and required intermediates, not the root. Clients build and validate a path using their trust store and policy: signatures, constraints, key usage, validity interval, and revocation behavior where configured.

    The Subject Alternative Name (SAN) extension carries DNS or IP identities. Modern hostname verification uses SAN, not the legacy Common Name fallback. Wildcards match only constrained name patterns and do not prove tenant authorization.

    SNI in ClientHello tells a shared endpoint which certificate/configuration to use; it is not application authentication and, without ECH, is generally visible on the path. ALPN negotiates protocols such as h2 or http/1.1; accepting the wrong protocol can create downgrade or routing failure.

    Termination, re-encryption, and passthrough¶

    Model Strength Tradeoff
    edge termination, plaintext upstream simple L7 policy internal hop lacks cryptographic protection
    edge termination, TLS upstream L7 controls plus hop protection edge sees plaintext; two trust contexts
    TLS passthrough end service owns keys and end-to-end TLS load balancer has limited L7 routing/telemetry
    service-mesh mTLS workload identity and policy per hop certificate/control-plane/sidecar complexity

    Draw every plaintext boundary. The downstream client authenticates the terminating proxy's presented server identity. The proxy then becomes a separate TLS client to the upstream and must validate its SAN and trust roots; verify=false silently removes upstream server authentication.

    Mutual TLS¶

    In mTLS the server requests a client certificate and validates its chain and acceptable identity. Identity should come from a stable SAN form governed by issuance policy, not arbitrary subject strings. Map identity to authorization separately. Define behavior for missing certificates, expired credentials, unknown issuers, workload decommissioning, and emergency trust removal.

    Trusting a CA means trusting every certificate it is permitted to issue. Use constrained issuers, short lifetimes, scoped trust bundles, and auditable issuance. Do not share one broad root across unrelated environments without accepting the blast radius.

    Resumption, PSKs, tickets, and 0-RTT¶

    TLS 1.3 resumption uses a pre-shared key established from an earlier connection. A ticket is an opaque identity: it can reference server-side state or carry self-encrypted/authenticated state. In the latter design ticket-encryption keys are fleet secrets. Planned overlap preserves resumption; it is not mandatory to accept every still-live ticket. A server can reject tickets and require full handshakes, trading CPU for narrower exposure, especially after compromise.

    RFC 9846 (July 2026) obsoletes RFC 8446 while still specifying TLS 1.3. Its section 2.2 covers PSK resumption, section 4.5.1 certificate authentication, and section 4.7.1 tickets; these section numbers differ from the older RFC. New TCP connections that resume PSKs do not prove the new certificate path. Force full handshakes for rotation canaries and separately test ticket rejection, client-identity binding, and capacity when resumption disappears.

    0-RTT data lacks full replay protection. An attacker can replay the same early data to multiple nodes behind a load balancer unless the application or shared anti-replay design prevents effects. Permit only replay-safe reads or commands with robust deduplication; reject early data when policy, ticket age, ALPN, SNI, or remembered settings do not match.

    Rotation and trust overlap¶

    Certificate rotation has two independent planes:

    identity rotation: deploy new leaf/key -> verify serving -> retire old leaf/key
trust rotation:    distribute new root -> issue/use new chain -> remove old root

    For root migration, trust both old and new roots before serving chains that require the new root. Keep dual trust through the slowest client/config propagation and rollback window, then remove old trust. Cross-signing can help path building but also makes actual client behavior less predictable; test representative trust stores.

    Private-key rotation should be gradual and observable. Avoid synchronizing certificate reloads, connection closures, and ticket-key changes across the fleet. Preserve old serving capacity until new-chain handshakes succeed from every required vantage point.

    Revocation and clocks¶

    CRLs list revoked certificates; OCSP answers status for a certificate. Client behavior varies on network failure, freshness, stapling, and certificate type. OCSP stapling lets the server carry a signed status response; Must-Staple is only useful when the ecosystem enforces it. Short-lived certificates reduce, but do not eliminate, the exposure window and make issuance availability more important.

    Certificate validity uses wall-clock time. A fast clock can make a certificate appear expired; a slow clock can make it not yet valid or extend acceptance of retired credentials. Secure, redundant time synchronization is part of PKI reliability. Monitor offset independently from certificate expiry.

    Invariants¶

    1. Every TLS client validates the intended peer identity against an explicit trust policy.
    2. Private keys remain scoped, access-controlled, auditable, and replaceable.
    3. Trust is added before dependents use it and removed only after old chains drain.
    4. No unsafe operation relies on TLS 0-RTT for exactly-once execution.
    5. Every plaintext hop and termination owner is documented.
    6. Certificate, trust-bundle, ticket-key, and clock lifecycles are observable before failure.
    7. TLS CPU and handshake queues remain bounded under cold-start and attack load.

    Calculations and capacity¶

    Handshake CPU¶

    If one core sustains 2,500 measured full handshakes/s at the chosen cipher, key type, chain, and implementation, a cold reconnect burst of 20,000 handshakes/s needs:

    raw cores = 20,000 / 2,500 = 8
at 60% target utilization = 8 / 0.60 = 13.3 -> 14 cores

    This excludes application traffic and kernel/network cost. Benchmark on production hardware. Resumption hit rate helps normal load but must not be the only protection against ticket-key loss or mass reconnect.

    Certificate-chain bandwidth¶

    A 4 KiB chain sent on 10,000 full handshakes/s costs 40,960,000 bytes/s = 39.0625 MiB/s = 40.96 MB/s before records and packets. Removing unnecessary intermediates lowers bandwidth and can prevent QUIC amplification-limit stalls, but never omit an intermediate required by clients.

    Expiry runway¶

    Assume a leaf issued at t=0 expires at t=24 h, and renewal first starts at t=8 h, leaving 16 hours. A 12-hour issuance outage ends at t=20 h; only 4 hours then remain. A further 6-hour rollout finishes at t=26 h, 2 hours after expiry, not with 2 hours to spare. Earlier renewal or a shorter outage and rollout budget is required, plus clock-skew and rollback margin.

    flowchart LR
    I[Issue at 0 h] --> R[Renewal due at 8 h]
    R --> O[Issuance outage until 20 h]
    O --> E[Old leaf expires at 24 h]
    E --> L[Six-hour rollout finishes at 26 h]

    Alert on minimum fleet expiry and actual oldest credential age. A periodic 8-hour job is not proof that every serving leaf is at most 8 hours old if reloads lag or prior jobs failed. Established connections may continue after leaf expiry; that masks fresh-handshake outage rather than repairing the certificate.

    Design choices¶

    Decision Prefer Tradeoff
    public CA public clients and broad trust external issuance and transparency exposure
    private CA controlled workload identities distribute/protect roots and run issuance reliably
    short-lived certs automated fleets issuance availability and clock discipline
    revocation checks rapid invalidation requirement responder reachability and client variance
    RSA leaf legacy compatibility larger keys/signatures and cost profile
    ECDSA leaf modern clients and smaller signatures legacy support must be measured
    terminate at edge L7 routing/WAF edge is a plaintext/key trust boundary
    passthrough service-owned end-to-end identity less L7 control at ingress

    Failure matrix¶

    Failure Symptom Evidence Containment / recovery
    expired/not-yet-valid leaf handshake alert by cohort validation error and client clock correct clock; serve valid overlap certificate
    missing intermediate some clients fail, others build path served chain and trust-store differences serve complete ordered chain
    SAN/SNI mismatch hostname validation failure requested SNI versus leaf SAN correct routing/certificate; never disable verification
    ALPN mismatch protocol fallback/failure offered and selected ALPN align listeners and clients; retain safe fallback
    unknown private CA mTLS/server validation failure issuer and trust-bundle version restore overlap; roll trust before identity
    revoked credential still accepted unauthorized connection revocation freshness/client policy remove authorization, rotate trust/identity, assess exposure
    ticket-key desynchronization resumption collapses resume hit by node/key epoch overlapping fleet-wide key distribution; accept full handshake capacity
    replayed early data duplicate side effect early-data flag plus command ID reject unsafe 0-RTT; deduplicate and reconcile
    mass reconnect TLS CPU/accept queue saturation full handshakes, CPU, queue drops jitter, rate limit, shed, preserve control capacity
    termination confusion plaintext or wrong identity upstream hop-by-hop TLS telemetry enforce upstream TLS/mTLS and SAN policy

    Evidence and diagnostics¶

    openssl s_client -connect example.com:443 -servername example.com -verify_hostname example.com -showcerts -verify_return_error
openssl s_client -connect example.com:443 -servername example.com -alpn 'h2,http/1.1' -status
openssl x509 -in leaf.pem -noout -subject -issuer -dates -ext subjectAltName
openssl verify -CAfile roots.pem -untrusted intermediates.pem leaf.pem
curl -sv --cert client.pem --key client.key https://service.example/

    -servername sends SNI but does not perform hostname verification; -verify_hostname checks the certificate identity. Some LibreSSL or older OpenSSL builds lack that option. In that case, use a hostname-validating client such as curl with the application trust store rather than interpreting successful chain validation as a hostname match.

    From each hop record TLS version, cipher suite, SNI, selected ALPN, peer SAN/issuer/serial, chain-validation result, expiry runway, trust-bundle version, full/resumed/0-RTT mode, handshake duration, alert, ticket-key epoch, and mTLS authorization identity. Never log private keys, ticket plaintext, bearer tokens, or full sensitive certificate subject data unnecessarily.

    Packet captures locate alerts and round trips; endpoint logs explain validation policy. Test from old and new trust stores, multiple client platforms, each ingress route, and a skewed-clock canary.

    Operations and migration¶

    1. Inventory names, issuers, roots, key custody, termination points, client populations, and maximum connection/ticket lifetime.
    2. Canary the new leaf or trust bundle without removing the old path.
    3. Validate SAN, SNI, ALPN, chain building, mTLS mapping, resumption, and expiry from representative clients.
    4. Roll out with bounded cohorts and enough full-handshake capacity for resumption loss.
    5. Drain old connections and tickets; remove old identity or trust only after evidence shows no dependent clients.
    6. Retain a tested rollback chain and an emergency authorization-revocation path.

    L5 and L6 signals¶

    An L5 answer traces TLS 1.3, validates SAN/chain/SNI/ALPN, selects termination and mTLS policy, estimates handshake capacity, and designs overlap rotation. An L6 answer establishes CA and key ownership, trust-domain boundaries, issuance SLOs, revocation policy, client-compatibility evidence, ticket/0-RTT standards, clock controls, mass-reconnect capacity, staged migrations, and emergency rollback authority.

    Traps¶

    • Saying “TLS is enabled” without identifying termination and plaintext hops.
    • Trusting any certificate from a broad CA without checking SAN and usage.
    • Rotating the issuing root and leaf simultaneously without trust overlap.
    • Assuming revocation always fails closed or works uniformly.
    • Ignoring clock skew during certificate incidents.
    • Sizing for average resumed traffic rather than cold full-handshake bursts.
    • Treating mTLS identity as authorization.
    • Enabling 0-RTT because TLS accepted it.

    Exercises and solutions¶

    1. Root migration¶

    Ten thousand workloads refresh trust bundles within six hours; connections live two hours. Give the safe sequence.

    Worked solution

    Solution: Distribute a bundle containing old and new roots, wait beyond measured six-hour propagation, canary and then serve new-root chains, retain old trust and serving rollback through at least connection drain and straggler evidence, then remove the old root in cohorts. Do not infer completion from control-plane publication alone.

    Include non-resumed handshakes in that proof. Old leaf, session, and ticket lifetimes can differ; no removal timestamp follows from just six-hour trust refresh plus two-hour connections.

    2. Reconnect capacity¶

    Fifty thousand clients reconnect over 20 seconds. Each full handshake consumes 0.4 ms of one CPU core. Estimate raw cores.

    Worked solution

    Solution: Arrival is 2,500 handshakes/s. CPU demand is 2,500 * 0.0004 = 1 core-second/s, so one core at 100% in the ideal benchmark. At a 50% target, reserve at least two measured-equivalent cores, then add network, application, skew, and attack headroom. Jitter reconnects because average arithmetic hides bursts.

    3. mTLS outage¶

    After a trust-bundle rollout, 8% of calls fail with unknown issuer.

    Worked solution

    Solution: Stop rollout and compare failing client/server bundle versions and served chains. Restore the dual-trust bundle on the affected hop before changing identities. Verify control-plane delivery and actual process reload separately; keep authorization containment available if the removed root was compromised.

    In the compromise case, do not restore a known-bad trust anchor just to repair availability. Quarantine and issue safe credentials under incident authority.
