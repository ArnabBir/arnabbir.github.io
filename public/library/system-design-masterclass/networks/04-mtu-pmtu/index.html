    04. MTU and Path MTU¶

    MTU failures are boundary failures: an endpoint emits a packet valid for its local interface, but some later link cannot carry it under the applicable forwarding rules. Small requests may work while larger responses hang. TCP may connect successfully before data stalls. The reliable design skill is to calculate every encapsulation layer, preserve MTU feedback, and prove behavior by packet size and direction.

    Goals¶

    After this chapter, you should be able to:

    • distinguish link MTU, IP packet size, TCP MSS, application payload, and wire overhead;
    • explain IPv4 and IPv6 fragmentation boundaries;
    • calculate MSS and overlay/tunnel payload budgets with units;
    • explain classical PMTUD and packetization-layer PMTUD;
    • recognize ICMP filtering and PMTU black-hole signatures;
    • account for VPN, overlay, encryption, and nested-tunnel overhead;
    • select MSS clamping, endpoint MTU, tunnel MTU, or PLPMTUD mitigations deliberately;
    • build safe observability and test plans without modifying shared hosts;
    • translate MTU mechanics into platform contracts, rollout gates, and ownership.

    1. First-principles model¶

    A link MTU is the largest network-layer packet that a link can carry under its interface contract without network-layer fragmentation. A path crosses links with potentially different MTUs. The path MTU is bounded by the smallest effective link limit after considering encapsulation at each segment.

    effective inner-packet budget at a tunnel boundary
    = outer link MTU - outer encapsulation overhead

advertised TCP MSS baseline
    = IP packet budget - fixed IP header - fixed TCP header
actual TCP data budget
    = IP packet budget - transmitted IP header - transmitted TCP header

    The sender may know its local interface MTU but not a smaller remote bottleneck. Path MTU discovery learns or probes the path limit.

    flowchart LR
    S[Sender MTU 1500] --> E[Encapsulator]
    E -->|outer packet| L[Path link MTU 1500]
    L --> D[Decapsulator]
    D --> R[Receiver]
    O[Tunnel overhead] -.reduces inner budget.-> E
    I[ICMP or probe feedback] -.updates PMTU.-> S

    2. Vocabulary and boundaries¶

    Term Boundary Meaning
    Link MTU one interface/link maximum IP packet accepted for ordinary transmission on that link
    Path MTU one directional path minimum effective MTU across the current path
    IPv4 total length IPv4 packet header plus IPv4 payload, maximum encoded size 65,535 B
    IPv6 payload length IPv6 base header field bytes after the 40-byte base header, with separate jumbogram rules
    TCP MSS one TCP direction maximum TCP payload a peer says it will receive in one segment
    Application chunk application/runtime write, record, frame, or message size; not an IP packet promise
    Frame size link link header/trailer plus payload according to technology
    Tunnel overhead encapsulation boundary outer headers added around an inner packet/frame

    MSS is directional and negotiated in SYN options. It constrains TCP segment payload, not UDP datagrams and not total application messages. TCP options consume additional header space; a conservative implementation derives segment size from current path state.

    Each peer independently advertises an MSS, not one shared bidirectional value. RFC 6691 subtracts fixed headers for that option; the sender separately accounts for transmitted IP/TCP options when choosing actual segment data length.

    3. Baseline calculations¶

    3.1 Ethernet MTU and TCP MSS¶

    With 1500-byte IP MTU:

    TCP/IPv4 MSS = 1500 B - 20 B IPv4 - 20 B TCP = 1460 B
TCP/IPv6 MSS = 1500 B - 40 B IPv6 - 20 B TCP = 1440 B

    Those values assume minimum headers. Twelve bytes of TCP timestamp and padding/options would reduce actual data fitting in the same packet if not otherwise accounted for:

    IPv4 TCP payload = 1500 B - 20 B - 32 B = 1448 B

    3.2 Tunnel budget¶

    Assume an illustrative IPv4 VXLAN-style outer envelope:

    outer IPv4 20 B + UDP 8 B + VXLAN 8 B + inner Ethernet 14 B = 50 B

    On a 1500-byte outer IP MTU, the inner frame budget under this simplified accounting is:

    1500 B - 20 B - 8 B - 8 B = 1464 B for the inner Ethernet frame
1464 B - 14 B inner Ethernet = 1450 B inner IP packet

    If the inner TCP uses IPv4 with minimum headers:

    inner TCP MSS = 1450 B - 20 B - 20 B = 1410 B

    VLAN tags, outer IPv6, encryption, integrity tags, optional headers, and provider framing can change the result. Draw the exact stack and consult the implementation contract.

    3.3 Nested overhead¶

    If an overlay is decapsulated before a VPN adds 76 B around the workload IP packet, their separate 1500-byte boundaries impose independent constraints:

    VPN inner budget = 1500 B - 76 B = 1424 B
effective workload packet budget = min(1450 B, 1424 B) = 1424 B

    For TCP/IPv6 with minimum headers inside:

    MSS = 1424 B - 40 B - 20 B = 1364 B

    The tightest boundary wins. Stacking platforms that each assumed they owned the same 50-byte margin causes hidden failure.

    If the VPN wraps the still-encapsulated overlay packet, both envelopes coexist:

    nested workload IP budget = 1500 - 76 VPN - 50 overlay = 1374 B
nested TCP/IPv6 data budget with fixed headers = 1374 - 40 - 20 = 1314 B

    flowchart LR
    W[Workload IP up to 1374 B] --> O[Overlay adds 50 B]
    O --> V[VPN adds 76 B]
    V --> L[1500 B outer IP bottleneck]

    Taking min(1450,1424) for this nested stack overstates the safe workload packet by 50 bytes. Draw the actual simultaneous headers before choosing the formula.

    4. IPv4 fragmentation¶

    IPv4 supports fragmentation. Relevant header fields identify the original datagram, fragment offset, and whether more fragments follow. A router that encounters a packet larger than outgoing MTU may fragment it only when fragmentation is permitted. If the Don't Fragment flag is set, it drops the packet and should send ICMP Destination Unreachable, Fragmentation Needed with MTU information.

    4.1 Fragment arithmetic¶

    An IPv4 packet has 20-byte header and 3980-byte payload, total 4000 B. It must cross a 1500-byte MTU link. Each fragment has a 20-byte IPv4 header. Except the final fragment, payload length must align to an 8-byte fragment-offset unit.

    max payload per nonfinal fragment = floor((1500 B - 20 B) / 8 B) * 8 B
                                  = floor(1480 / 8) * 8
                                  = 1480 B

payloads = 1480 B + 1480 B + 1020 B = 3980 B
fragment sizes = 1500 B, 1500 B, 1040 B
offsets = 0, 1480/8 = 185, 2960/8 = 370

    All fragments carry the identification value needed for reassembly. The first two set More Fragments; the final does not.

    4.2 Why fragmentation is operationally costly¶

    • Losing one fragment prevents reassembly of the complete original packet.
    • Every fragment consumes forwarding and reassembly work.
    • ACLs, NAT, and load balancers may lack transport headers in noninitial fragments.
    • Reassembly consumes bounded memory and timers at the destination.
    • Packet captures become harder to interpret.
    • Fragmentation can amplify packet rate and attack surface.

    Avoid relying on in-path IPv4 fragmentation as a normal application strategy. Size packets to the path and preserve discovery feedback.

    5. IPv6 fragmentation boundary¶

    IPv6 routers do not fragment forwarded packets. When a router cannot forward due to MTU, it discards the packet and sends ICMPv6 Packet Too Big with the supported MTU. A source may use an IPv6 Fragment extension header when appropriate, but fragmentation occurs at the source, not an intermediate router.

    IPv6 requires every link to support an MTU of at least 1280 bytes at the IPv6 layer. A link unable to carry 1280 directly must provide link-specific fragmentation/reassembly beneath IPv6. This does not mean every end-to-end path should be forced to 1280; PMTUD should discover larger usable values.

    ICMPv6 is protocol machinery

    Blanket ICMPv6 blocking can break Neighbor Discovery and Path MTU Discovery. Apply typed, rate-aware policy rather than treating every ICMP message as optional diagnostics.

    6. Packet and state flow: classical Path MTU Discovery¶

    Classical PMTUD sends packets that routers cannot fragment and learns from ICMP feedback:

    sequenceDiagram
    autonumber
    participant S as Sender
    participant R as Small-MTU router
    participant D as Destination
    S->>R: packet larger than outgoing MTU
    R--xD: packet dropped
    R-->>S: ICMP too big with MTU
    S->>S: reduce cached path size
    S->>D: retransmit smaller packet

    For IPv4, the signal is ICMP Destination Unreachable, Fragmentation Needed. For IPv6, it is ICMPv6 Packet Too Big. Implementations cache PMTU with scope and timers because paths can change.

    6.1 The feedback dependency¶

    The control message must return to the sender and be associated with the flow. Failure can occur when:

    • an ACL blocks the ICMP type;
    • a tunnel or firewall mishandles quoted packet information;
    • NAT cannot map feedback to the originating flow;
    • rate limits suppress all useful feedback;
    • an encapsulator does not propagate the inner-path constraint;
    • anycast or asymmetric changes make cached PMTU stale;
    • the sender ignores or cannot authenticate/validate the feedback appropriately.

    Security policy should validate and rate-limit control traffic, not erase required signals.

    7. Packetization-Layer PMTUD¶

    Packetization-Layer Path MTU Discovery, generalized by RFC 8899, confirms transport reachability using probes and protocol feedback rather than depending only on ICMP. It maintains a search state over candidate packet sizes, detects probe loss, and distinguishes ordinary congestion loss from repeated size-specific failure as safely as the packetization layer allows.

    Conceptual state:

    stateDiagram-v2
    direction LR
    [*] --> Base
    Base --> Searching: base verified
    Searching --> Searching: probe succeeds
    Searching --> Confirmed: converged
    Searching --> Base: fallback required
    Confirmed --> Searching: revalidate

    Revalidation includes a path change or validation-timer expiry. The fallback edge applies when the protocol requires fallback, not on every individual lost probe. Short labels keep the state transitions legible; the full protocol and its bounds remain in the surrounding explanation.

    PLPMTUD does not mean "keep sending giant packets until something works." A sound implementation has:

    • a known safe base size;
    • uniquely identifiable probes or protocol confirmation;
    • bounded search and retransmission;
    • congestion-responsive behavior;
    • loss handling and fallback according to the probe state machine;
    • revalidation after path change.

    TCP's Packetization Layer PMTUD specification is RFC 4821. Datagram transports and QUIC have protocol-specific considerations and probe mechanisms.

    8. Concrete failure example: PMTU black holes¶

    A PMTU black hole occurs when oversized packets are dropped and usable feedback does not cause the sender to reduce size. Characteristic behavior is size dependent.

    8.1 Typical lifecycle¶

    1. Small SYN/SYN-ACK/ACK packets cross the path.
    2. TLS or other small records may also work.
    3. A larger data packet exceeds a hidden MTU after encapsulation.
    4. A router or tunnel endpoint drops it.
    5. ICMP feedback is absent, filtered, misrouted, or ignored.
    6. TCP retransmits the same-size data until a fallback or timeout.
    7. The application reports handshake success followed by body timeout.

    8.2 Failure signatures¶

    Signature PMTU interpretation Alternative to rule out
    Small requests work, large response stalls response direction has smaller effective PMTU server body generation/backpressure
    TCP connects, TLS stalls at larger records setup packets fit but record packets do not certificate/crypto CPU or protocol mismatch
    One VPN/region fails by payload size tunnel overhead or path differs endpoint version/config difference
    Repeated same-size retransmissions, no progress feedback absent or ineffective severe loss unrelated to size
    Lowering packet size fixes path strong MTU evidence timing/load changed simultaneously
    ICMP too-big visible at router but not sender return policy/NAT/control handling capture filter or wrong sender vantage
    UDP large datagrams fail, small succeed fragmentation/drop/size policy receiver truncation or socket buffer drop

    "Ping works" is weak evidence because its payload is usually small and its treatment may differ. A large probe with the relevant no-fragment semantics is more informative, but should be run only through approved tooling and rate limits.

    9. Tunnel and overlay accounting¶

    9.1 Write the entire envelope¶

    For each boundary, enumerate bytes:

    outer link payload budget
  - outer IP
  - UDP or tunnel transport
  - tunnel shim
  - encryption nonce/IV/header
  - authentication tag/trailer
  - optional metadata
  - encapsulated link header, if any
  = maximum inner packet/frame budget

    Common sources of overhead include GRE, IP-in-IP, VXLAN, Geneve options, WireGuard/IPsec modes, service-mesh or node tunnels, and provider-specific encapsulation. Header size may vary with IPv4 versus IPv6, options, encryption mode, padding, and extension metadata.

    9.2 Fragment before or after encapsulation¶

    Where fragmentation occurs matters. Fragmenting an inner IPv4 packet before encapsulation creates several inner fragments, each with outer overhead. Fragmenting an outer packet can make tunnel processing and middleboxes depend on outer fragment handling. IPv6 outer paths require source behavior rather than router fragmentation. Prefer a tunnel contract that emits packets valid for the outer path.

    9.3 MTU ownership contract¶

    For every overlay, document:

    Question Required answer
    Outer path MTU minimum supported and how verified
    Maximum overhead worst case including options and encryption
    Advertised inner MTU value exposed to workloads
    TCP MSS handling endpoint calculation or controlled clamping boundary
    ICMP propagation how outer errors update inner sender behavior
    Datagram policy maximum safe UDP payload and fragmentation behavior
    Path change cache invalidation and reprobe behavior
    Telemetry owner counters, probes, alerts, and incident escalation

    10. MSS negotiation and clamping¶

    TCP peers advertise MSS in SYNs based on what they can receive. The sender combines peer MSS with local/path knowledge. If a tunnel reduces usable MTU but endpoints cannot learn it, an authorized network boundary may rewrite advertised MSS during the handshake so TCP emits smaller segments.

    MSS clamping is a targeted compatibility tool, not universal PMTU repair:

    • it affects TCP, not UDP or other IP traffic;
    • it must account for direction and exact overhead;
    • too high still black-holes; too low wastes capacity and increases packet rate;
    • it can hide broken ICMP/PMTUD and complicate ownership;
    • encrypted or encapsulated locations may limit visibility;
    • path changes may require a conservative value.

    Prefer correct endpoint/tunnel MTU and functional PMTUD/PLPMTUD. Use clamping where the architecture owns the boundary and cannot otherwise expose the right constraint.

    11. Invariants¶

    1. Link invariant: every emitted packet must fit the next link or invoke protocol-defined fragmentation/error behavior.
    2. Path invariant: usable packet size is bounded by the smallest effective directional path limit.
    3. Encapsulation invariant: every added outer byte reduces inner capacity unless the outer link MTU increases.
    4. MSS invariant: MSS limits TCP payload, not complete IP packet size or non-TCP datagrams.
    5. IPv6 invariant: routers do not fragment forwarded IPv6 packets.
    6. Reassembly invariant: delivery of some fragments is not delivery of the original datagram.
    7. Feedback invariant: classical PMTUD needs usable control feedback from the constraining point to the sender.
    8. Probe invariant: a failed large probe is not conclusive without controlling ordinary loss; repeated size-correlated results are stronger.
    9. Direction invariant: request and response can have different paths and PMTUs.
    10. Change invariant: cached PMTU is path state and must recover when routing changes.

    12. Calculations with units¶

    12.1 Packet-rate cost of conservative MSS¶

    A service sends 1 GiB = 1,073,741,824 B of TCP payload. Compare MSS 1460 B and MSS 1360 B, ignoring retransmission and application framing:

    segments at 1460 B = ceil(1,073,741,824 / 1460) = 735,440
segments at 1360 B = ceil(1,073,741,824 / 1360) = 789,517
additional segments = 54,077
increase = 54,077 / 735,440 = 7.35%

    A safer smaller MSS may be correct, but it increases per-packet CPU, headers, and device work. Quantify both safety and efficiency.

    12.2 Fragment loss amplification¶

    If one datagram becomes three fragments and each fragment independently has delivery probability 0.999, complete datagram delivery probability under the simplified model is:

    P(all fragments arrive) = 0.999 ^ 3 = 0.997003
P(datagram loss)        = 1 - 0.997003 = 0.002997 = 0.2997%

    The independent-loss model is illustrative; real loss is often bursty and correlated. It still shows why more required pieces increase failure opportunity.

    12.3 Goodput impact of overhead¶

    With inner TCP payload 1360 B and total outer transmitted bytes of 1500 B at the evaluated boundary:

    payload efficiency = 1360 / 1500 = 90.67%

    At 1 Gbit/s outer serialization with no other loss:

    maximum payload bit rate = 1 Gbit/s * 0.9067 = 906.7 Mbit/s

    This excludes link framing and inter-frame overhead, ACKs, encryption padding variation, loss, and application headers.

    13. Observability evidence and diagnostic workflow¶

    13.1 Evidence to collect¶

    • interface and tunnel MTU at both endpoints and encapsulation boundaries;
    • exact route and selected interface in each direction;
    • SYN MSS advertisements and resulting segment sizes;
    • IP length, IPv4 DF/fragment fields, IPv6 Packet Too Big, and ICMP quoted headers;
    • retransmitted ranges and whether failed packets share a size threshold;
    • tunnel encapsulation/error/drop counters;
    • firewall/NAT logs for ICMP and fragments;
    • application success/latency grouped by request and response size, path, protocol, and zone;
    • PMTU cache or transport path metrics where safely exposed;
    • changes in routing, VPN, CNI, encryption, or interface configuration.

    13.2 Investigation sequence¶

    1. Establish direction: request upload, response download, or both.
    2. Find the smallest repeatable failing size and largest repeatable successful size.
    3. Capture at sender before encapsulation and after/beyond the suspected boundary when authorized.
    4. Enumerate exact headers and calculate expected outer size.
    5. Check for ICMP too-big/fragmentation-needed at the constraining and sender sides.
    6. Compare TCP MSS and actual packet sizes; for UDP, preserve datagram boundaries in evidence.
    7. Rule out receiver truncation, application limits, rate limits, and ordinary congestion.
    8. Test a mitigation in a disposable environment or narrow canary.
    9. Validate both directions, cold/new flows, long-lived flows, failover paths, and representative payload distributions.

    13.3 Safe experiments¶

    Prefer read-only inspection and application-level size sweeps. Any command that changes MTU, routing, firewall behavior, or packet loss must be optional and run only in a disposable VM, container network, or explicitly isolated namespace approved for the experiment. Record and restore state even there. Never lower a shared production interface MTU as an ad hoc test.

    14. Failure-response matrix¶

    Failure Immediate containment Durable correction Validation
    Tunnel inner MTU too high canary lower workload/tunnel MTU publish computed MTU contract size sweep across all paths
    TCP only black-holes controlled MSS clamp at owned boundary repair PMTUD and endpoint MTU SYN MSS plus large transfer
    ICMP blocked allow required typed feedback with safeguards policy-as-code and regression probe observe sender adjustment
    UDP oversized reduce protocol datagram size PLPMTUD/protocol segmentation loss by datagram size
    Stale PMTU after reroute reconnect/reprobe where safe correct cache/path-change handling failover test with long-lived flows
    Nested tunnel added pause rollout recalculate worst-case envelope and capacity canary old/new topology
    Fragment reassembly pressure rate-limit abusive fragments, preserve service avoid fragmentation and harden policy reassembly counters and goodput

    Do not "fix" a black hole by allowing arbitrary ICMP, disabling security controls, or selecting an unexplained small MTU globally. Preserve least privilege and document the capacity cost.

    15. Design implications¶

    Platform contracts¶

    • Publish workload MTU as an API contract of the network platform.
    • Test the worst supported path: cross-zone, VPN, encrypted overlay, failover, and provider interconnect.
    • Reserve an explicit overhead budget for future tunnel options; reject changes that exceed it or coordinate an MTU migration.
    • Expose PMTU/ICMP/tunnel drops and packet-size distributions by boundary.

    Application protocols¶

    • Bound UDP datagrams below the verified safe payload or implement robust PLPMTUD and segmentation.
    • Stream large objects rather than constructing giant datagrams.
    • Make retries idempotent; a size-dependent timeout can occur after partial application progress.
    • Do not infer safe payload from a successful small health check.
    • Include representative large requests and responses in synthetic tests.

    Rollout and migration¶

    An MTU change is a compatibility migration. A safe sequence is:

    1. inventory every encapsulation and path class;
    2. calculate old/new inner budgets and packet-rate cost;
    3. make receivers and intermediate paths accept the target behavior;
    4. canary senders with size-distributed traffic;
    5. monitor fragmentation, too-big feedback, retransmission, CPU, and goodput;
    6. expand by failure domain;
    7. retain a rollback value that remains compatible with already-updated nodes;
    8. test reroute while long-lived connections exist.

    Increasing MTU can fail if any middle path remains smaller. Decreasing MTU is usually compatibility-safe for packet size but can raise packets/s and CPU enough to overload the fleet.

    16. L5 and L6 expectations¶

    L5 expectation L6 expectation
    Calculates MTU/MSS and tunnel overhead Establishes a versioned cross-platform overhead budget
    Explains IPv4/IPv6 fragmentation difference Designs PMTUD/PLPMTUD and ICMP security policy by protocol
    Recognizes size-dependent black holes Builds a multi-vantage, directional, falsifiable evidence plan
    Suggests lower MTU or MSS clamp Chooses containment versus durable repair and quantifies packet-rate cost
    Tests a large payload Tests path classes, failover, long-lived flows, and size distributions
    Mentions tunnel overhead Owns nested-overlay changes, rollout gates, rollback, and team contracts

    17. Traps¶

    • Calling 1500 bytes the Ethernet frame size instead of the common IP MTU at that boundary.
    • Subtracting only one tunnel's overhead in a nested path.
    • Treating MSS as the maximum application message or UDP payload.
    • Assuming routers fragment IPv6.
    • Blocking all ICMP/ICMPv6 as a security default.
    • Concluding the path is healthy because a small ping or TCP handshake works.
    • Diagnosing all large-response stalls as PMTU without size-correlated evidence.
    • Clamping TCP MSS and claiming UDP is fixed.
    • Lowering MTU globally without quantifying additional packet rate and CPU.
    • Trusting a configured MTU without observing emitted outer packet size.
    • Ignoring directionality and cached state after route changes.

    18. Exercises with worked solutions¶

    Exercise 1: overlay MSS¶

    An outer IPv6 path has MTU 1500 B. A tunnel adds outer IPv6 40 B, UDP 8 B, tunnel header 8 B, and inner Ethernet 14 B. The inner flow is TCP/IPv4 with 20-byte IP and TCP headers. Calculate inner IP MTU and MSS.

    Worked solution 
    encapsulated UDP payload budget = 1500 - 40 - 8 - 8 = 1444 B
inner IP MTU = 1444 - 14 = 1430 B
inner TCP/IPv4 MSS = 1430 - 20 - 20 = 1390 B

    Any encryption tag, option, VLAN, padding, or additional metadata must also be subtracted.

    Exercise 2: IPv4 fragmentation¶

    A 3000-byte IPv4 packet includes a 20-byte header and crosses a 1000-byte MTU. Compute fragment payloads, total sizes, and offsets.

    Worked solution

    Original payload is 3000 - 20 = 2980 B. Maximum aligned nonfinal payload is:

    floor((1000 - 20) / 8) * 8 = 976 B

    Payloads are 976, 976, 976, 52 B. Total fragment sizes are 996, 996, 996, 72 B. Offsets in 8-byte units are 0, 122, 244, 366. The first three have More Fragments set; the final does not.

    Exercise 3: black-hole evidence¶

    Requests under 900 B work. Responses above 1380 B stall only through a VPN. TCP handshake succeeds. Give the leading hypothesis and a proof plan.

    Worked solution

    Leading hypothesis: response packets exceed the effective VPN path MTU and PMTU feedback does not reduce sender packetization. Prove rather than assume:

    1. sweep response sizes to establish a stable threshold;
    2. inspect server-side MSS, emitted IP sizes, DF semantics, and retransmitted ranges;
    3. calculate VPN outer size from exact headers;
    4. capture before/after encapsulation and search for fragmentation-needed/Packet Too Big feedback;
    5. compare a non-VPN path and rule out application response thresholds;
    6. canary a computed smaller endpoint/tunnel MTU or TCP MSS in isolation;
    7. test UDP separately because TCP clamping does not cover it.

    Exercise 4: packet-rate sensitivity¶

    A service sends 20 Gbit/s of application payload. Reducing effective payload per packet from 1400 B to 1250 B changes approximate packet rate by how much?

    Worked solution 
    payload bytes/s = 20,000,000,000 / 8 = 2,500,000,000 B/s
pps at 1400 B = 2,500,000,000 / 1400 = 1,785,714 packets/s
pps at 1250 B = 2,500,000,000 / 1250 = 2,000,000 packets/s
increase = 214,286 packets/s = 12%

    This payload-only estimate excludes ACKs, retransmissions, and framing. Benchmark CPU and device capacity before a fleet-wide reduction.

    Exercise 5: migration review¶

    A platform team will add 24 B of optional tunnel metadata to a network whose inner MTU is already set from the previous maximum overhead. What must an L6 review require?

    Worked solution

    Require an exact worst-case envelope for every outer family/path, proof of remaining headroom, and packet captures from representative boundaries. If no headroom exists, version the inner-MTU contract and migrate receivers/path support before senders. Canary by failure domain with realistic size distributions and monitor ICMP too-big, fragments, retransmissions, tunnel drops, packets/s, CPU, and goodput. Test failover and long-lived flows. Define rollback that remains compatible with packets emitted by both versions, and assign ownership for endpoint configuration, tunnel behavior, and policy.
