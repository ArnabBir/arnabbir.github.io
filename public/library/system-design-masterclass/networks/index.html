    Networks for System Design Engineers¶

    Networks turn local function calls into uncertain distributed interactions. Bytes cross queues, links, routing domains, translators, load balancers, kernels, and application runtimes. Each boundary can delay, duplicate, reorder, fragment, reject, or silently discard traffic. This track builds the packet-level model needed to design and operate reliable systems rather than treating "the network" as one box.

    The curriculum targets experienced L5/L6 software and system design engineers. It starts at encapsulation and routing, then develops transport, naming, secure connectivity, traffic management, overload, observability, and multi-region failure reasoning.

    Competency outcomes¶

    By the end of the track, you should be able to:

    • trace one request from an application write to the peer process and back;
    • distinguish names, addresses, routes, connections, sockets, and application sessions;
    • calculate CIDR ranges, usable capacity, serialization delay, bandwidth-delay product, MTU budgets, queue bounds, and retry amplification;
    • explain how routing, ECMP, NAT, load balancing, TLS, TCP, UDP, and QUIC divide responsibility;
    • diagnose failures from packet captures, socket state, route state, counters, flow logs, and application telemetry;
    • separate loss, corruption, congestion, policy rejection, endpoint overload, and dependency delay;
    • design deadlines, retries, connection pools, health checks, failover, and overload controls from explicit invariants;
    • reason about asymmetric paths and partial failure across hosts, zones, regions, and providers;
    • specify an evidence plan that can disprove a networking hypothesis;
    • lead L6 tradeoffs involving blast radius, control-plane safety, capacity, cost, migration, and ownership.

    Prerequisites¶

    You should already understand processes, threads, HTTP request/response semantics, basic Linux-style observability, binary and hexadecimal notation, powers of two, percentiles, and Little's Law. Root access and production packet capture are not prerequisites.

    flowchart LR
    A[Processes and HTTP] --> B[Packet journey]
    C[Binary and powers of two] --> D[IP CIDR routing]
    B --> D
    D --> E[Transport and sockets]
    E --> F[MTU and PMTU]
    D --> G[DNS and service discovery]
    E --> H[TLS and identity]
    F --> I[Proxies and load balancing]
    G --> I
    H --> I
    I --> J[Resilience and operations]

    Before Chapter 1, make these distinctions precise:

    Concept Working definition
    Link One local delivery domain with a specific frame format and MTU.
    Packet A network-layer datagram routed by destination IP address.
    Segment A TCP protocol data unit; UDP usually calls its unit a datagram.
    Flow A related packet sequence, commonly identified by protocol and source/destination IP/port.
    Route A rule selecting a next hop and egress interface for a destination prefix.
    Socket An OS communication endpoint and its protocol state, not the physical connection itself.
    Connection Transport state between endpoints; TCP uses tuples, while QUIC can use multiple connection IDs across path changes.
    Session Application-level continuity, which may survive or span transport connections.
    Control plane Computes and distributes intended forwarding or policy state.
    Data plane Applies installed state to packets at line or host speed.

    The 16-chapter route¶

    Chapter Core question L5/L6 deliverable
    01. Request and packet journey What transforms and forwards one request? Layered trace with ownership, state, queues, and evidence
    02. IP, CIDR, and routing How does each hop choose where a packet goes? Address plan, route proof, ECMP and asymmetry analysis
    03. Transport, sockets, and congestion How do endpoints create reliable byte streams under loss and load? TCP/UDP/QUIC boundary, capacity math, queue and lifecycle policy
    04. MTU and path MTU Why do some packet sizes fail while small probes work? Encapsulation budget, PMTUD failure diagnosis, mitigation plan
    05. DNS and service discovery How do names become changing endpoint sets? Cache/TTL model, authority chain, stale-state and failover policy
    06. HTTP semantics and caching Which protocol semantics make retries, caching, and intermediaries correct? Method/status/cache contract and ambiguity handling
    07. HTTP/2, HTTP/3, and QUIC How do multiplexing and transport choices change latency and failure coupling? Protocol choice tied to loss, concurrency, migration, and cost
    08. TLS and PKI How are peers authenticated and traffic protected? Handshake trace, trust boundary, rotation, and failure evidence
    09. Proxies and load balancing Where should traffic terminate and how is a backend selected? L4/L7 choice, affinity, draining, health, and overload semantics
    10. Deadlines, retries, and pools How do client policies prevent ambiguous failure from becoming overload? End-to-end budget, bounded amplification, and connection capacity
    11. gRPC and RPC How should service calls frame, multiplex, cancel, and report status? RPC contract, deadline propagation, streaming, and evolution
    12. Realtime and media Which transport behavior fits interactive streams and sessions? Latency/loss budget, reconnect, ordering, and fanout design
    13. NAT and cloud networking Which hidden virtual and translation state carries cloud flows? Tuple/state capacity, overlay path, timeout, and exhaustion analysis
    14. BGP, anycast, and global routing How does traffic cross administrative domains and converge? Routing-policy, edge selection, capacity, and route-risk analysis
    15. Service mesh and zero trust Where should service identity, policy, and traffic control live? Trust bootstrap, data/control-plane failure, and migration plan
    16. Observability and debugging What evidence distinguishes competing network hypotheses? Layered telemetry, capture plan, and incident decision tree

    Learning route by goal¶

    Goal Route
    Debug intermittent request failure 01 -> 02 -> 03 -> 04 -> 13 -> 16
    Design service-to-service RPC 01 -> 03 -> 05 -> 08 -> 09 -> 10 -> 11
    Design global ingress 02 -> 05 -> 08 -> 09 -> 14
    Diagnose throughput collapse 03 -> 04 -> 07 -> 09 -> 10 -> 16
    Prepare for an L6 infrastructure interview 01-15, then 16 as an evidence review

    Practical work¶

    The lab and scenario routes use stable repository paths. All 16 labs are available in the lab index, and each scenario link points to a complete practice package.

    Artifact Exercise Purpose
    Request journey evidence Lab 01: request trace Correlate application phases with bounded network inferences.
    Latency and throughput Lab 03: network math Check BDP, concurrency, serialization, churn, and retry calculations with units; CIDR is in Chapter 02.
    TCP connection pressure Lab 07: connection pool Observe pool wait, active work, throughput, and rejection.
    Retry amplification Lab 08: retry storm Compare synchronized retries with bounded backoff and jitter.
    QUIC path behavior Lab 10: QUIC migration Reason about connection identity and path migration.
    Load-balancer lifecycle Lab 11: load-balancer draining Verify admission stop, bounded completion, and close behavior.
    NAT capacity Lab 12: NAT exhaustion Calculate finite tuple state under connection churn.
    Global failover scenario Global realtime failover Design routing, capacity, session continuity, and recovery.
    Edge brownout scenario Checkout edge brownout Diagnose partial edge failure and contain retries.
    Identity rotation scenario Mesh certificate rotation Rotate trust without splitting service connectivity.

    Safe lab boundary

    Labs should prefer unprivileged inspection. Commands that create namespaces, alter routes, change MTUs, or inject loss must be marked optional and confined to a disposable VM, container, or explicitly isolated network namespace. Never apply them to a shared workstation or production host.

    How to study each chapter¶

    1. Redraw the first-principles model without looking.
    2. Trace packet and state transitions in both directions.
    3. Write the invariants before selecting a product or protocol option.
    4. Recalculate every example with one changed input.
    5. For each failure, name evidence that would confirm it and evidence that would falsify it.
    6. Convert the mechanics into one system-design decision.
    7. Answer the L5 prompt in five minutes and the L6 pivot in ten.
    8. Complete exercises before opening worked solutions.

    Evidence discipline¶

    Do not diagnose by symptom association alone. "Timeout" does not imply packet loss, and "retransmission" does not prove congestion. Build a time-bounded hypothesis table:

    Layer Example evidence What it can establish What it cannot establish alone
    Application phase timers, errors, request IDs where the application waited whether the host sent a packet
    Socket states, queue sizes, kernel errors local transport condition remote application intent
    Packet headers, flags, timing, retransmissions traffic visible at one capture point what happened outside that point
    Host network interface drops, route and neighbor state local forwarding health every intermediate hop
    Network devices/cloud flow logs, ACL decisions, tunnel counters policy or path evidence within scope end-to-end application correctness
    Peer correlated logs and captures remote receipt and response behavior missing middle-hop evidence

    L5 and L6 bar¶

    L5: Draw a coherent path, identify the controlling protocol state, calculate the relevant bound, handle the principal failure modes, and propose concrete metrics. Avoid magical network assumptions.

    L6: Frame ambiguity, identify hidden shared state and blast radius, compare alternatives across failure domains, quantify overload and recovery, design safe rollout and rollback, align ownership across platform/application teams, and require evidence that distinguishes control-plane intent from data-plane reality.

    Standards snapshot: TLS 1.3 is now specified by RFC 9846 (July 2026), which obsoletes RFC 8446. Older implementation documentation can still cite RFC 8446; record that historical context and check current section numbers rather than assuming an old RFC number implies a different negotiated TLS version. A full certificate handshake, resumed TLS connection, and reused HTTP connection are different evidence categories.
