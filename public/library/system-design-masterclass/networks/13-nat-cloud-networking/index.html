    13. NAT and Cloud Networking¶

    The stateful NAT/NAPT commonly used for cloud egress is a tuple-rewrite system, not a synonym for security. Stateless algorithmic translation also exists: SIIT translates IPv4 and IPv6 headers without per-flow mappings, while NPTv6 translates IPv6 prefixes without transport-port state. This chapter focuses on stateful SNAT, DNAT, port allocation, and conntrack; cloud networking adds routes, virtual firewalls, gateways, and provider-managed failure domains around that state. At L5, design the packet path and size its finite tables. At L6, standardize address ownership, egress identity, isolation, evidence, and recovery across accounts and regions.

    Learning goals¶

    After this chapter, you should be able to:

    • trace SNAT, DNAT, conntrack, routing, and filtering for both directions of a flow;
    • calculate port and translation capacity under connection churn;
    • distinguish public/private subnets, security groups, NACLs, and host firewalls;
    • design transit, hybrid, overlapping-address, hairpin, and asymmetric paths; and
    • prove cloud-egress behavior and recovery with packet, flow-log, and gateway evidence.

    1. Start with the tuple¶

    A transport flow is commonly identified by:

    (protocol, source IP, source port, destination IP, destination port)

    For outbound TCP, SNAT changes the source. For inbound publishing, DNAT changes the destination. Port address translation may change a port so many private flows share one public address.

    Before SNAT: TCP 10.20.4.17:49152 -> 198.51.100.40:443
After SNAT:  TCP 203.0.113.8:62001 -> 198.51.100.40:443

Return packet received by NAT:
             TCP 198.51.100.40:443 -> 203.0.113.8:62001
Reverse map:
             TCP 198.51.100.40:443 -> 10.20.4.17:49152

    The translator records enough state to reverse the transformation. A packet that misses that state is not the same flow, even if an operator believes it is a reply.

    SNAT and DNAT are independent decisions¶

    flowchart LR
    C[Private client<br/>10.20.4.17:49152] -->|original tuple| N[NAT gateway<br/>conntrack]
    N -->|SNAT<br/>203.0.113.8:62001| I[Internet server<br/>198.51.100.40:443]
    I -->|reply tuple| N
    N -->|reverse translation| C
    P[Public client] -->|203.0.113.10:443| D[DNAT or public LB]
    D -->|10.20.8.25:8443| S[Private service]

    DNAT makes an internal target reachable; it does not by itself authenticate the caller. SNAT hides private addressing from the destination; it does not make a malicious connection safe. Routing establishes a possible path. Stateful and stateless policy then decides whether packets may traverse it. Application authorization remains separate; see Security Architecture.

    2. Conntrack is finite distributed state¶

    Linux netfilter connection tracking classifies packets into states such as NEW, ESTABLISHED, RELATED, and INVALID. NAT normally selects a mapping on the first packet and applies it to later packets in that tracked flow. Managed gateways implement equivalent behavior, although their exact allocation and limits are provider-specific.

    Important resource dimensions include:

    • active conntrack entries;
    • mappings per public source address and destination tuple;
    • ephemeral source ports;
    • packet and byte throughput;
    • new-flow allocation rate;
    • idle and closing-state retention; and
    • per-destination concentration.

    TCP TIME_WAIT belongs to an endpoint that actively closed a connection; a gateway can have different translation-retention rules. Do not infer gateway capacity from host TIME_WAIT counts alone. Both can limit churn, but they are different state machines.

    Port arithmetic¶

    Assume one egress IP has 55,000 usable translated ports for one destination (IP, port, protocol). If mappings remain unavailable for an average of 70 seconds, an idealized steady-state churn ceiling is:

    new-flow ceiling = usable ports / occupancy time
                 = 55,000 / 70
                 = 786 new flows/s

    At 4,000 new connections/s to that destination:

    required simultaneous mappings = 4,000 * 70 = 280,000
minimum egress IPs by ports      = ceil(280,000 / 55,000) = 6

    Six is only a port-space floor. Add headroom for skew, retries, health checks, deployment reconnects, provider reservations, and failure of one gateway or address. If N+1 requires losing one of eight equal egress addresses, normal utilization should remain below 7/8 = 87.5% before skew; an operational target may be materially lower.

    The 55,000 ports and 70 seconds are fixture inputs, not universal cloud quotas or TCP timers. A mean occupancy calculation is an arithmetic ceiling, not a conservative tail guarantee; skew can exhaust one allocation pool earlier.

    Destination diversity can allow reuse of the same source port in distinct five-tuples. Provider allocation rules vary, so validate with the exact gateway and workload. The most effective fix is often persistent connection reuse or multiplexing, not an ever-larger NAT fleet.

    3. Packet-processing order matters¶

    A useful conceptual path is:

    ingress interface
  -> destination translation
  -> route lookup
  -> stateful/stateless policy
  -> source translation
  -> egress interface

    Implementations differ in hook order and optimization. Diagnose against the platform's documented datapath rather than memorizing one universal chain.

    For every failed flow, write a two-row packet ledger:

    Direction Tuple at source Tuple at gateway/public boundary Expected route and policy
    request 10.20.4.17:49152 -> 198.51.100.40:443 203.0.113.8:62001 -> 198.51.100.40:443 default route to NAT; outbound permitted
    response 198.51.100.40:443 -> 203.0.113.8:62001 198.51.100.40:443 -> 10.20.4.17:49152 same stateful device; return route to subnet

    This reveals wrong assumptions about which address a firewall, allowlist, log, or peer actually observes.

    4. Public and private are routing properties¶

    A subnet is not private because its instances lack public DNS names. In common cloud designs:

    • a public subnet has a route to an internet gateway, and a workload also needs a usable public address or public front end;
    • a private subnet has no direct internet-gateway path for workload addresses;
    • an egress subnet hosts NAT, proxies, or firewalls through which private workloads reach external destinations; and
    • an isolated subnet has no general internet route in either direction.
    flowchart TB
    Internet((Internet)) --> IGW[Internet gateway]
    IGW --> ALB[Public load balancer]
    ALB --> App[Private application subnets]
    App --> DB[(Isolated data subnets)]
    App --> NAT[NAT or egress proxy]
    NAT --> IGW
    App --> EP[Private service endpoints]
    Corp[Corporate network] --> TGW[Transit hub]
    TGW --> App

    Route tables choose next hops by longest-prefix match. A default route is less specific than a private endpoint, peering prefix, or propagated hybrid route. Record both the selected route and the alternatives; “the route table looks right” is not evidence that the expected route won.

    5. Layered filtering without false confidence¶

    Control Typical state Scope Frequent failure
    security group stateful interface/workload correct request rule but wrong group attachment
    network ACL stateless subnet boundary request allowed, ephemeral return ports denied
    host firewall implementation-dependent operating system cloud policy allows flow but local chain drops it
    managed firewall/proxy often stateful and L7-capable centralized path asymmetric return misses state; TLS identity unavailable
    application authorization request-aware API/resource network reachability mistaken for permission

    Stateful policy usually permits return traffic for an admitted flow. Stateless policy needs explicit rules for both directions. For a client connecting to destination port 443, the response's destination is the client's ephemeral port, not 443. Avoid opening 0-65535 reflexively: derive the actual client port range, direction, protocol, and subnet boundaries.

    This table uses AWS-style security-group/NACL semantics, not a universal mapping to Azure NSGs or Google Cloud firewall policies. A post-SNAT boundary can see a translated port range instead of the original client's ephemeral range.

    Security groups and NACLs cannot compensate for an unintended route, a public address on the wrong workload, or a proxy that can reach every tenant. Use independent controls, but assign a test and owner to each one.

    6. Transit and hybrid routing¶

    A transit hub reduces a full mesh, but centralization introduces route-policy and throughput blast radius. Separate route domains for production, non-production, shared services, inspection, and partners. Propagate only intended prefixes; do not turn every attachment into universal reachability.

    Overlapping address space¶

    Two networks that both own 10.20.0.0/16 cannot be unambiguously routed through one ordinary IP forwarding domain. Options are:

    1. renumber one side: the cleanest long-term answer;
    2. expose services through load balancers, proxies, or private service endpoints instead of routing whole networks;
    3. translate one or both sides into non-overlapping ranges and maintain identity outside the translated address; or
    4. isolate them in distinct routing domains and join only through application gateways.

    Translation solves address ambiguity, not service identity, audit attribution, DNS views, or policy lifecycle. A translated partner source may collapse many principals into one address.

    Hybrid route ownership¶

    For VPN or dedicated circuits, define:

    • which side originates each prefix;
    • whether static and dynamic routes coexist and which wins;
    • maximum accepted prefixes and explicit filters;
    • primary/backup preference and equal-cost behavior;
    • bidirectional maximum transmission unit (MTU) and fragmentation behavior; and
    • what evidence proves failover and failback.

    A broad on-premises route can accidentally attract cloud-to-cloud traffic. A more-specific stale route can black-hole one subnet while aggregate probes remain green.

    7. Hairpins and asymmetry¶

    A hairpin occurs when traffic exits toward a public or shared front door and returns to a target near its source. It may incur two translations, extra zones, inspection cost, source-identity loss, or unsupported same-interface forwarding.

    Bad surprise:
app A -> public service name -> internet/NAT/LB -> app B in same VPC

Often preferable:
app A -> private service name -> private LB/endpoint -> app B

    Split-horizon DNS can expose private and public answers, but now DNS view is part of correctness. Test from every resolver domain.

    Stateful middleboxes require flow symmetry:

    request:  client -> firewall A -> server
response: server -> firewall B -> client   # B has no state: drop/reset

    Asymmetry can result from equal-cost routing, a changed default route, multiple VPNs, zone-specific appliances, or failover during long-lived connections. Either preserve affinity to the same stateful device, synchronize state where explicitly supported, or remove that device from the stateful path. Do not assume route symmetry merely because both endpoints are reachable.

    8. Cloud egress architecture¶

    Choose deliberately among:

    Pattern Strength Cost and risk
    NAT per zone avoids cross-zone dependency; scalable failure domains more gateways and public IPs; destination allowlists grow
    centralized NAT/firewall common policy and stable egress identity transit cost, hairpins, large blast radius, scaling complexity
    explicit forward proxy domain/user policy and richer logs application compatibility, TLS policy, proxy outage
    private service endpoint avoids public path and often NAT provider/service coverage, endpoint and DNS complexity
    no default egress strongest exfiltration reduction dependency inventory and update paths required

    Include processing charges, cross-zone bytes, transit bytes, firewall bytes, log ingestion, and failure traffic. The Cost Engineering chapter provides the broader model.

    At L6, assign egress identities by trust domain rather than sharing one organization-wide public IP. A compromised development workload must not inherit a production partner allowlist. Maintain a destination inventory, expiry for exceptions, emergency deny capability, and controlled DNS because a domain allowlist ultimately resolves to addresses.

    9. Failure evidence and recovery¶

    Failure Evidence that distinguishes it Recovery and proof
    port exhaustion gateway allocation errors; active mappings near limit; old connections work while new ones fail reduce churn, add source capacity; prove new-flow success and falling utilization
    conntrack saturation kernel/gateway insertion drops, INVALID packets, table occupancy shed or scale; prove insert failures cease under peak replay
    missing return route request seen at target, no response at source boundary; flow logs differ by direction repair route propagation; capture both directions
    NACL return denial reject log on ephemeral destination port narrow corrective rule; synthetic handshake from affected subnet
    asymmetric firewall path request and response observed on different appliances; state miss restore symmetric route/affinity; prove long-lived and new flows
    stale partner allowlist peer sees unexpected translated source IP restore approved egress identity; peer log plus local tuple evidence
    zonal NAT loss one zone's new outbound flows fail; other zones healthy fail locally or controlled reroute; verify capacity and cross-zone cost
    MTU/PMTUD failure handshake works, larger payload stalls; ICMP too-big absent correct MTU or permit PMTUD; test increasing payload sizes

    Recovery is not “the graph is green.” Capture the failed tuple, change identifier, restored request rate, allocation headroom, reject count, path/zone distribution, and rollback readiness. Follow the recovery discipline in Reliability Engineering.

    10. Design review checklist¶

    • Draw forward and reverse tuples before and after every translation.
    • Name every route table, longest-prefix winner, and stateful hop.
    • Calculate ports, conntrack entries, new flows/s, throughput, and N+1 headroom.
    • Keep NAT, routing, network filtering, workload identity, and authorization distinct.
    • Test ephemeral return ports for every stateless boundary.
    • Eliminate or justify hairpins and cross-zone egress.
    • Resolve overlapping ranges with an explicit identity and DNS plan.
    • Prove hybrid failover, route withdrawal, MTU, and asymmetric-flow behavior.
    • Partition egress identities by trust domain and audit destination exceptions.
    • Price normal traffic, retries, failover, transit, processing, and telemetry.

    11. Exercises with worked solutions¶

    Exercise 1: Size an egress pool¶

    A worker fleet opens 9,000 TLS connections/s to one vendor endpoint. Connections are not reused. A mapping occupies a port for 50 seconds, each egress IP provides 60,000 usable ports for that destination, and the design must survive one egress IP failure while staying below 70% port utilization. How many IPs are required?

    Worked solution

    Solution: Required mappings are 9,000 * 50 = 450,000. One IP's operating capacity is 60,000 * 0.70 = 42,000. After one failure, N - 1 IPs must provide capacity: ceil(450,000 / 42,000) = 11, so N = 12. This is a port bound only. Verify gateway new-flow and throughput limits. Connection reuse would reduce both risk and cost.

    Twelve addresses do not imply one gateway supports twelve: for example, the checked AWS NAT gateway limit is up to eight IPv4 addresses and public-address quota increases can be required. Distribute capacity across supported gateways and separately test loss of a whole gateway, not just one source address.

    Exercise 2: Diagnose a one-way flow¶

    Flow logs show an accepted SYN from 10.1.2.8:53000 to 10.50.4.9:443. The server capture shows SYN arrival and SYN-ACK departure. The client never receives it. Two VPN attachments advertise 10.1.0.0/16; the return route changed during maintenance.

    Worked solution

    Solution: The application and inbound policy are not the first suspects because the server received the SYN and emitted a SYN-ACK. Correlate the response tuple at each boundary and inspect the selected return route. The likely failure is asymmetric return through an attachment without matching state or reachability. Restore deterministic preference, withdraw the unintended advertisement, then prove request and response traverse the intended attachment for new and long-lived flows.

    Exercise 3: Design partner connectivity with overlap¶

    Both the company and a partner use 10.20.0.0/16. The partner needs two HTTPS APIs, not general network access.

    Worked solution

    Solution: Do not route both full ranges into one table. Publish the two APIs through narrowly scoped private endpoints or application proxies with non-overlapping endpoint addresses. Authenticate partner workloads independently of source IP, authorize only the required APIs, and log original identity. If translation is unavoidable, allocate explicit translated ranges in both directions and test DNS, callbacks, logs, and policy against translated tuples. Plan renumbering if the relationship expands.

    Takeaways¶

    • NAT consumes tuple state, ports, allocation rate, bytes, and operational attention.
    • Public/private classification follows addresses and routes, not subnet names.
    • Stateful and stateless filters fail differently; neither replaces application authorization.
    • Hybrid transit needs prefix ownership, filtering, symmetry, MTU, and failover proof.
    • Egress identity is a security and partner contract as well as a networking detail.
    • Recovery evidence must show the restored bidirectional packet path and remaining headroom.
