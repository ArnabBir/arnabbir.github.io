    01. Request and Packet Journey¶

    An application writes bytes, not "a request across the network." Kernels and network devices wrap those bytes in protocol headers, queue them, choose next hops, transmit finite-size frames, validate them, remove headers, and deliver bytes to a peer socket. A defensible system design names those transitions and the state each transition depends on.

    Goals¶

    After this chapter, you should be able to:

    • distinguish application messages, transport units, IP packets, and link frames;
    • trace a request across user space, kernel space, interfaces, switches, routers, and the peer;
    • explain encapsulation and decapsulation without treating OSI layers as physical boxes;
    • identify state consulted at each step: DNS, socket, route, neighbor, forwarding, and application state;
    • calculate payload efficiency, serialization delay, packet count, and first-order latency;
    • locate queues and explain how they create delay, drops, and backpressure;
    • construct an evidence plan using application traces, socket data, packet captures, and device telemetry;
    • translate packet mechanics into timeout, retry, pooling, and observability decisions.

    1. First-principles model¶

    A network delivers bounded units over one link at a time. End-to-end communication is composed from four responsibilities:

    1. Application semantics: what the bytes mean and where one message ends.
    2. Transport: endpoint demultiplexing and, depending on protocol, reliability, ordering, flow control, and congestion control.
    3. Network: best-effort packet delivery across multiple links using IP destinations and routing state.
    4. Link: local delivery over one medium or virtual link using frames.
    Application message
  -> transport header + application bytes
  -> IP header + transport unit
  -> link header + IP packet + link trailer
  -> signals/bits on one link

    Each router removes the incoming link framing, processes the IP packet, and creates new framing for the outgoing link. The TCP or UDP header normally remains end to end, although NAT or a terminating proxy may rewrite or terminate transport state.

    Layers are contracts, not a promise of untouched headers

    Firewalls, NATs, tunnels, load balancers, offload engines, and proxies can inspect, add, remove, rewrite, or terminate protocol state. Draw the actual boundaries in the system under discussion.

    2. Encapsulation by example¶

    Assume an HTTP/1.1 client sends 900 application bytes over TCP/IPv4 on Ethernet without TCP options or VLAN tags. The simplified frame carries:

    [Ethernet 14 B][IPv4 20 B][TCP 20 B][HTTP bytes 900 B][Ethernet FCS 4 B]

    The frame from destination MAC through FCS is 14 + 20 + 20 + 900 + 4 = 958 B. For the classic Ethernet accounting model, add 8 byte-times for preamble/start delimiter and 12 byte-times for the interpacket gap: this frame occupies 978 byte-times, giving 900/978 = 92.02% application efficiency before acknowledgments. The gap consumes link time but is not a field inside the frame. Physical transmission also has medium-specific overhead not represented as frame payload. Ethernet's common 1500-byte MTU limits the IP packet, not the complete wire representation.

    Real TCP SYNs and established packets often contain options; TLS adds records inside the TCP byte stream; HTTP/2 creates frames inside TLS; a VXLAN overlay adds an outer Ethernet/IP/UDP/VXLAN envelope. Count the headers at the boundary whose MTU or capacity you are evaluating.

    Unit Scope Identifier used for delivery Typical integrity/check field
    Application message application protocol method, path, stream ID, message length protocol dependent
    TCP segment transport endpoints source/destination ports plus IPs TCP checksum
    UDP datagram transport endpoints source/destination ports plus IPs UDP checksum
    IP packet routed path destination IP prefix IPv4 header checksum; no IPv6 header checksum
    Ethernet frame one link destination MAC frame check sequence

    Checksums have different coverage and strength. They detect classes of corruption; they do not authenticate a peer or provide application-level integrity against an attacker. TLS supplies cryptographic integrity above transport.

    3. One request, end to end¶

    Consider https://api.example.test/orders from a client to a server on another subnet. Assume DNS is already resolved and a TCP/TLS connection already exists so the trace focuses on data delivery.

    sequenceDiagram
    autonumber
    participant A as Client app
    participant K as Client kernel
    participant R as Routers
    participant S as Server kernel
    participant P as Server process
    A->>K: write application bytes
    K->>K: segment, sequence, queue
    K->>R: framed IP packets
    R->>R: route, queue, forward each hop

    3.1 Before the write¶

    The application may already have performed:

    • name resolution and endpoint selection;
    • a route lookup indirectly triggered by connection establishment;
    • neighbor discovery for the first-hop next hop;
    • TCP handshake, TLS handshake, and HTTP connection setup;
    • connection-pool admission and stream selection.

    A warm request omits these costs. A cold request may include DNS round trips, TCP setup, TLS setup, proxy hops, certificate validation, and authentication. Always say which path a latency estimate represents.

    3.2 The application-to-kernel boundary¶

    The client serializes a request into bytes and calls a socket API. A successful write commonly means the kernel accepted some bytes into a local send buffer. It does not mean:

    • a frame reached the NIC;
    • a remote kernel acknowledged the bytes;
    • the server process read them;
    • the server committed the operation.

    Blocking, nonblocking, and asynchronous APIs report acceptance differently. Partial writes are legal for stream sockets. The application or runtime must retain unwritten bytes and continue from the correct offset.

    3.3 Transport processing¶

    For TCP, the sender assigns byte sequence numbers, divides the stream according to MSS and current state, and retains unacknowledged data for possible retransmission. The amount in flight is bounded by the smaller of the receiver-advertised window and congestion-control window.

    For UDP, one application send normally creates one datagram boundary. UDP does not retransmit, order, pace for congestion, or recover loss by itself. The application protocol must choose any needed behavior.

    3.4 IP route selection¶

    The host route lookup chooses an egress interface and next hop using the destination IP and policy. If the destination is off-link, the frame's destination MAC is the next-hop router, not the final server. The IP destination remains the server unless translation or tunneling changes it.

    Client IP:       10.10.1.20
Default gateway: 10.10.1.1
Server IP:       10.40.8.50

First frame destination MAC = gateway MAC
IP packet destination        = 10.40.8.50

    3.5 Neighbor resolution¶

    IPv4 ARP or IPv6 Neighbor Discovery maps the on-link next-hop IP to link-layer reachability information. A cache miss can queue the packet while resolution runs. Failure appears before TCP can receive any response. A stale neighbor entry can create intermittent loss during movement or failover.

    3.6 Interface and link transmission¶

    The kernel queues a packet for an interface. Offloads may let the kernel represent a larger logical buffer while hardware segments or combines packets. A packet capture at different hooks can therefore show sizes or checksums that never appeared in that form on the wire.

    The interface serializes bits at a finite line rate. Switches learn or consult forwarding state and queue frames on output contention. The link validates its frame, but successful local delivery says nothing about later hops.

    3.7 Router processing¶

    At each routed hop:

    1. validate and remove incoming link framing;
    2. inspect the destination IP and policy state;
    3. decrement IPv4 TTL or IPv6 Hop Limit;
    4. perform a longest-prefix route lookup;
    5. apply relevant ACL, NAT, QoS, or tunnel actions;
    6. queue the packet for an outgoing interface;
    7. create link framing suitable for the next hop.

    If TTL/Hop Limit reaches zero, the router discards the packet and normally sends an ICMP Time Exceeded message. If no route exists, a node may send an unreachable indication or silently drop according to policy.

    3.8 Destination delivery¶

    The server interface and kernel validate the frame and packet, identify the transport protocol, and demultiplex using local address/port plus connection state. TCP checks sequence space, queues out-of-order bytes, acknowledges received ranges according to its rules, and exposes only an ordered byte stream to the application.

    The server process may not read immediately. Scheduler delay, event-loop backlog, worker exhaustion, garbage collection, or a full downstream pool can leave bytes queued after the network has delivered them.

    Packet flow is visible movement. State flow determines whether movement is possible.

    5. Invariants¶

    Use invariants to keep a trace honest:

    1. Layer-boundary invariant: a receiver may interpret bytes only according to the protocol and state agreed at that boundary.
    2. Next-hop invariant: an Ethernet destination identifies an on-link recipient; an IP destination identifies the routed destination before translation.
    3. Demultiplexing invariant: an arriving transport unit reaches only an endpoint whose local tuple and protocol state match it.
    4. Stream invariant: TCP preserves byte order, not application message boundaries.
    5. Buffer invariant: queued bytes occupy finite memory; sustained arrival above departure must lead to backpressure or loss.
    6. Hop-scope invariant: link-layer success is evidence for one hop, not end-to-end success.
    7. Completion invariant: transport acknowledgement is not proof of application processing or durable commit.
    8. Evidence invariant: absence at one capture point proves only that the packet was not observed there under that capture's scope and filters.

    6. Calculations with units¶

    6.1 Serialization delay¶

    Serialization delay is the time to put a unit's bits onto a link:

    serialization delay (s) = size (bits) / line rate (bits/s)

    A 1500-byte IP packet on a 100 Mbit/s link, ignoring additional wire overhead:

    1500 B * 8 bit/B / 100,000,000 bit/s = 0.00012 s = 120 us

    On 10 Gbit/s, the same calculation is 1.2 us. This is not propagation delay and not total latency.

    6.2 Payload efficiency¶

    For 1460 bytes of application data in one TCP/IPv4 packet with 20-byte IPv4 and 20-byte TCP headers:

    IP-level payload efficiency = 1460 B / 1500 B = 0.9733 = 97.33%

    With 40-byte IPv6 and 20-byte TCP headers under the same 1500-byte MTU, MSS is 1440 bytes and efficiency is 1440 / 1500 = 96%. TLS, HTTP, tunneling, and link overhead reduce end-to-end application efficiency further.

    6.3 Packet count¶

    For a 64 KiB = 65,536 B stream payload and MSS = 1460 B:

    full segments = floor(65,536 B / 1460 B) = 44
remainder     = 65,536 B - 44 * 1460 B = 1,296 B
segments      = 45

    This is a logical estimate. Segmentation offload, delayed writes, TLS record boundaries, ACK behavior, and retransmission change what captures show and what crosses each link.

    6.4 Latency decomposition¶

    one-way latency = processing + queueing + serialization + propagation
request latency = setup + outbound path + server work + inbound path

    Illustrative assumption: one-way propagation is 20 ms, forwarding/serialization contributes 1 ms, server work is 8 ms, and no queueing occurs. A warm request/response is about 21 + 8 + 21 = 50 ms. Adding 30 ms of egress queueing in one direction raises it to 80 ms without changing geography or server execution.

    7. Concrete trace: what can a timeout mean?¶

    An API client times out at 500 ms. The server logs show 12 ms handler time for successful requests. Plausible paths include:

    Hypothesis Packet/state story Confirming evidence Falsifying evidence
    Client pool wait request never reaches a socket client span has long pool phase SYN/data leaves immediately
    Neighbor failure packets wait/drop before gateway failed/stale neighbor state packet visible beyond first hop
    Path loss data or ACK disappears retransmission and capture gap no retransmission; peer receives promptly
    Server not accepting handshake incomplete or queued SYN retransmission, listen pressure established flow and prompt request ACK
    Server not reading receive queue grows peer receive queue and app backlog request consumed immediately
    Downstream stall server receives but handler waits server trace child span no server request correlation
    Response-path policy request arrives; response disappears server capture sends, client capture absent client receives bytes before deadline

    The 12 ms handler metric may exclude queue time, connection setup, serialization, downstream work, or failed requests. Define timer boundaries before comparing them.

    8. Failure signatures and observability evidence¶

    Application evidence¶

    Record phase timings rather than one total:

    dns | pool_wait | connect | tls | request_write | first_byte | body_read | total

    Include destination identity, protocol, connection reuse, retry attempt, deadline, and a correlation ID. Do not log secrets or full payloads.

    Socket and host evidence¶

    Useful read-only evidence includes:

    • socket states and local/remote tuples;
    • send and receive queue occupancy;
    • TCP retransmission, reset, timeout, and listen-overflow counters;
    • interface errors, drops, queue drops, and link state;
    • route lookup result and neighbor state;
    • CPU scheduling, event-loop lag, and application queue depth.

    Packet evidence¶

    A packet capture can establish observed sequence, timing, flags, addresses, ports, TTL/Hop Limit, ICMP, advertised windows, and retransmission patterns. Capture near both endpoints when permitted. Synchronize clocks and document capture location, filter, direction, offload context, and sampling.

    Capture safely

    Packet captures may contain credentials, tokens, personal data, and payloads. Follow authorization and retention policy. Prefer header-only capture, narrow filters, short duration, and isolated reproductions. The examples here do not require changing host networking.

    Common signatures¶

    Signature Strong possibilities Important alternative
    Repeated SYN, no SYN-ACK remote down, policy drop, wrong route return path failure
    SYN-ACK arrives, client sends reset no matching client socket, late response capture artifact or policy injection
    Data retransmissions and duplicate ACKs loss or reordering capture point missed packets
    Zero advertised receive window receiver buffer/application not draining stale or misdecoded capture
    Clean packet exchange, long first byte server/app/downstream delay capture taken after hidden proxy
    Interface drops increase local queue/ring pressure unrelated traffic on same interface
    ICMP Time Exceeded loop or TTL too small deliberate low-TTL probing

    9. Design implications¶

    • Budget cold and warm paths separately. Pooling removes setup from most requests but creates pool queues, stale connections, and connection storms.
    • Propagate deadlines. A server should not begin expensive work after the caller's useful deadline has expired.
    • Retry outcomes, not vague errors. A write accepted locally but timed out remotely is ambiguous. Use idempotency and reconciliation.
    • Bound every queue. Socket buffers, proxy queues, thread pools, and downstream pools trade temporary absorption for latency and memory.
    • Keep endpoint identity observable. Record resolved endpoint, selected backend, protocol, and connection reuse without exposing secrets.
    • Do not equate health checks with request success. Health may traverse a different protocol, path, payload size, or dependency set.
    • Place telemetry at ownership boundaries. Client, proxy, server kernel, and application evidence answer different questions.

    10. L5 and L6 expectations¶

    L5 expectation L6 expectation
    Traces request and response through layers Identifies where overlays, proxies, NAT, and policy change the model
    Separates setup, network, and server latency Defines phase-level SLOs and cross-team evidence contracts
    Names finite queues and principal drops Quantifies overload propagation and chooses shedding boundaries
    Explains TCP ACK versus application success Designs idempotency and recovery for ambiguous outcomes
    Proposes client/server metrics and capture Builds a falsifiable multi-vantage incident plan
    Handles one path failure Reasons about asymmetric paths, failover, and control/data-plane disagreement

    11. Traps¶

    • Saying a request "goes down the OSI stack" without naming bytes, state, and queues.
    • Using packet, frame, segment, message, and request interchangeably.
    • Assuming the default gateway becomes the IP destination.
    • Treating a successful socket write or TCP ACK as business completion.
    • Forgetting the response path or assuming it mirrors the request path.
    • Reading an offloaded host capture as an exact wire image.
    • Attributing every retransmission to congestion; corruption, reordering, receiver behavior, and capture artifacts also matter.
    • Increasing buffers without calculating the added queueing delay.
    • Capturing broad production traffic without authorization or data controls.

    12. Exercises with worked solutions¶

    Exercise 1: calculate encapsulation¶

    An Ethernet link has a 1500-byte IP MTU. TCP over IPv4 uses 20-byte IP and 32-byte TCP headers. How much application data fits in one full-sized packet? How many packets carry 10,000 bytes?

    Worked solution 
    effective TCP data per packet = 1500 B - 20 B - 32 B = 1448 B
full packets = floor(10,000 B / 1448 B) = 6
remainder = 10,000 B - 6 * 1448 B = 1,312 B
total data packets = 7

    This excludes TLS/application framing and assumes the route really supports 1500-byte IP packets.

    This is effective data length, not the SYN MSS option. Under RFC 6691 section 2, advertised MSS subtracts fixed IP/TCP headers, not options; the sender reduces actual data length for options it sends. An MSS of 1460 can coexist with 1448-byte data.

    Exercise 2: locate the destination MAC¶

    A host 192.0.2.10/24 sends to 198.51.100.20 through gateway 192.0.2.1. Which address identifies the gateway in the first transmitted unit, and which identifies the final server?

    Worked solution

    The first Ethernet frame uses the gateway's MAC as destination. The enclosed IP packet uses 198.51.100.20 as destination. At every router, link framing changes. The IP destination remains the server unless a translator or tunnel changes the packet.

    Exercise 3: reason from two captures¶

    The client capture shows request data at 10:00:00.100 and retransmission at 10:00:00.350. The server capture shows the first copy at 10:00:00.105 and emits an ACK at 10:00:00.106. The client never observes that ACK. What is established, and what remains unknown?

    Worked solution

    The outbound request reached the server capture point quickly, and an ACK was visible leaving that server capture point. The missing ACK lies after the server capture and before or at the client capture, subject to capture loss and clock/filter correctness. The evidence points toward the return path or client-side processing, not outbound request loss. It does not locate the exact dropping hop or prove the server application read the request.

    Exercise 4: queue delay¶

    A 1 Gbit/s egress has 12 MiB queued ahead of a latency-sensitive packet. Estimate the drain time, ignoring new arrivals and framing overhead.

    Worked solution 
    queued bits = 12 MiB * 1,048,576 B/MiB * 8 bit/B = 100,663,296 bit
drain time = 100,663,296 bit / 1,000,000,000 bit/s
           = 0.1007 s = 100.7 ms

    A large buffer can prevent a drop while violating a 50 ms latency objective. Capacity and queue policy must be evaluated together.

    Exercise 5: design an evidence plan¶

    One percent of requests exceed two seconds, but server handler p99 is 40 ms. Give a minimum evidence plan.

    Worked solution
    1. Verify timer boundaries and compare the same request IDs.
    2. Split client latency into DNS, pool wait, connect, TLS, write, first byte, and body.
    3. Record endpoint, protocol, reuse, attempt, and deadline.
    4. Compare proxy and server arrival timestamps, queue time, handler time, and response completion.
    5. Inspect socket queues, retransmission/reset/timeout counters, listen pressure, interface drops, and event-loop or worker queues during the same window.
    6. For an authorized narrow sample, capture headers near both endpoints or proxies with synchronized clocks.
    7. Group by zone, endpoint, connection age, payload size, and retry attempt. A size or topology correlation changes the next hypothesis.
