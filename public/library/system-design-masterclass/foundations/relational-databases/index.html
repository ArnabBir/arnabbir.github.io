    Relational Databases¶

    Engineering extension: Storage recovery and query execution connects commit boundaries, interrupted recovery, checkpoint/restore budgets, and physical query work to a file-backed durable-counter fixture.

    A relational database is a concurrency-control and durability system with a declarative query engine. Its central advantage is not merely tables: it can enforce invariants across related data while exposing transactions, constraints, indexes, recovery logs, and an optimizer through one coherent boundary.

    This chapter uses PostgreSQL 17-style terminology to make internals concrete. Exact lock, replication, and DDL behavior varies by engine. See Database Indexing for access-path mechanics and Partitioning and Sharding for distributed placement.

    When relational wins¶

    Prefer a relational system when several of these are true:

    • Correctness depends on uniqueness, references, checks, or atomic changes across rows.
    • Commands update a bounded set of related records and must expose a clear commit point.
    • Access paths will evolve and a query optimizer is more valuable than one fixed key API.
    • Operators need ad hoc reconciliation, audits, joins, and repair queries.
    • Data size and write rate fit one primary or a deliberately partitioned/sharded topology.
    • The team benefits from mature backup, point-in-time recovery, migration, and observability tools.

    A key-value store can be better for a narrow key API, independently partitionable records, extreme horizontal write scale, or predictable tail latency without joins. A search engine is better for text relevance and broad candidate retrieval. An analytical column store is better for scans and aggregations over large immutable histories. These systems are often projections around relational canonical state, not replacements for every responsibility.

    Start with invariants and failure semantics. "No two active bookings own the same seat" is a reason for a unique constraint and transaction. "Fetch a document by ID" alone is not a reason to require a relational database.

    Logical model and enforced invariants¶

    Normalization gives each fact one authoritative owner. Foreign keys prevent dangling relationships; unique and exclusion constraints serialize conflicting claims; checks constrain row-local facts. Denormalize only for a measured read path and define freshness and repair.

    CREATE TABLE account (
    account_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id bigint NOT NULL,
    external_ref text NOT NULL,
    balance_cents bigint NOT NULL CHECK (balance_cents >= 0),
    version bigint NOT NULL DEFAULT 0,
    UNIQUE (tenant_id, external_ref),
    UNIQUE (account_id, tenant_id)
);

CREATE TABLE transfer (
    transfer_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id bigint NOT NULL,
    request_key text NOT NULL,
    debit_account_id bigint NOT NULL,
    credit_account_id bigint NOT NULL,
    amount_cents bigint NOT NULL CHECK (amount_cents > 0),
    state text NOT NULL CHECK (state IN ('POSTED', 'REVERSED')),
    UNIQUE (tenant_id, request_key),
    CHECK (debit_account_id <> credit_account_id),
    FOREIGN KEY (debit_account_id, tenant_id)
        REFERENCES account(account_id, tenant_id),
    FOREIGN KEY (credit_account_id, tenant_id)
        REFERENCES account(account_id, tenant_id)
);

    The composite foreign keys make a cross-tenant transfer unrepresentable even when account IDs are globally unique. The database must still be given the right invariant. A nonnegative balance check on each account cannot prove conservation across two accounts. Put both balance updates and the immutable transfer record in one transaction; verify that the lock query found exactly two accounts and that each balance update affected exactly one row. For ledgers, balanced postings and append-only correction entries provide stronger evidence than mutable balances alone.

    This teaching schema assumes one fixed currency/asset. For multiple assets, carry an immutable asset code on accounts and postings, reject cross-asset transfers on this path, and balance each asset independently. Equal integer amounts in two currencies do not prove conservation; foreign exchange needs its own quoted-rate and posting contract.

    Constraints are executable concurrency controls, not documentation. Application-side SELECT followed by INSERT races under concurrency. Let a unique constraint arbitrate, then map its specific violation to a stable domain conflict. Use NOT NULL, foreign keys, and checks after validation/backfill rather than relying indefinitely on optional application checks.

    PostgreSQL-style physical path¶

    PostgreSQL stores table tuples in fixed-size heap pages. A tuple carries transaction visibility metadata; an update commonly writes a new tuple version and leaves the old version for existing snapshots. Index leaves point to heap tuple locations. Vacuum later marks dead space reusable after no active snapshot can observe those versions.

    flowchart LR
    C[Client transaction] --> B[Shared buffers]
    B --> H[Dirty heap and index pages]
    B --> W[WAL records]
    W --> F[WAL flush]
    F --> A[Commit acknowledged]
    H --> K[Checkpoint writes pages]
    F --> R[Streaming replica]
    K --> D[(Data files)]

    The write-ahead rule requires relevant WAL to reach durable storage before dirty data pages may be considered safely persisted. Commit ordinarily waits for the commit WAL record according to configured durability. The heap page itself may be written later. Recovery replays WAL from a checkpoint to reproduce committed changes and discard incomplete transactions logically.

    WAL, checkpoints, and group commit¶

    WAL turns scattered page mutations into an ordered append path and supports crash recovery, physical replication, and point-in-time recovery. It does not remove storage cost: indexes, full-page images after checkpoints, large transactions, and replication slots can produce substantial WAL volume.

    A checkpoint establishes a recovery starting point and schedules dirty-page writes. Frequent checkpoints shorten recovery but increase write pressure and full-page-image frequency. Infrequent checkpoints need more WAL and longer replay. Spread checkpoint I/O to avoid a burst that competes with foreground reads and fsync.

    Group commit lets transactions arriving close together share a durable flush. If an fsync takes 2 ms, serially flushing every commit caps one path near 500 commits/s. Batching 40 ready commits behind one flush can theoretically expose about 40 / 0.002 = 20,000 commits/s on that path, although lock, WAL insertion, CPU, and storage bandwidth impose lower real limits. Group commit amortizes flush latency; it does not acknowledge before the required flush.

    Durability settings define product semantics. Asynchronous commit can lose recently acknowledged transactions on process or machine failure. It can be valid for disposable telemetry, not for a payment merely because latency improved.

    MVCC and transaction boundaries¶

    MVCC gives each statement or transaction a visibility snapshot while writers create new row versions. Readers often avoid blocking writers, but concurrency anomalies still depend on isolation level and write predicates. Keep transactions short: an idle transaction retains snapshots, delays vacuum, holds locks, and may prevent WAL or schema cleanup.

    Use one transaction for one invariant boundary:

    BEGIN;

-- Lock both tenant-owned accounts in one deterministic order. Require exactly
-- two rows; otherwise abort before either balance changes.
SELECT account_id
FROM account
WHERE tenant_id = 8
  AND account_id IN (101, 202)
ORDER BY account_id
FOR UPDATE;

UPDATE account
SET balance_cents = balance_cents - 2500,
    version = version + 1
WHERE account_id = 101
  AND tenant_id = 8
  AND balance_cents >= 2500;

-- Require exactly one affected row; zero means missing account or insufficient funds.
UPDATE account
SET balance_cents = balance_cents + 2500,
    version = version + 1
WHERE account_id = 202
  AND tenant_id = 8;

-- Require exactly one affected row; otherwise roll back the whole transaction.

INSERT INTO transfer
    (tenant_id, request_key, debit_account_id, credit_account_id, amount_cents, state)
VALUES
    (8, 'req-774', 101, 202, 2500, 'POSTED');

COMMIT;

    The transaction runner checks all three cardinalities before commit: two locked rows, one debited row, and one credited row. Any mismatch causes ROLLBACK, so an absent credit account cannot leave a lone debit. Acquire multiple explicit row locks in a stable key order to reduce deadlocks. Deadlocks remain normal recoverable outcomes: the database aborts one participant, and the application retries the entire idempotent transaction with bounded backoff.

    The unique transfer key rolls back a duplicate attempt, but returning the prior result also requires comparing its debit account, credit account, amount, tenant, and currency policy with the new request. A key reused for different input is not a successful duplicate. Store that request fingerprint and result durably. Use checked integer arithmetic for the credit as well as the debit. PostgreSQL 17 transaction isolation documents whole-transaction retries; WAL documents the flush-before-data rule, not external-provider atomicity (accessed 2026-09-08).

    Anomaly and remedy matrix¶

    Anomaly Example Common exposure Remedy
    dirty read observe a balance another transaction later aborts read-uncommitted semantics read committed or stronger; PostgreSQL maps read uncommitted to read committed
    non-repeatable read rereading one row returns a newer committed value statement snapshots under read committed repeatable read snapshot or lock/validate version
    phantom rerunning a predicate finds newly matching rows read committed predicate reads repeatable read for stable snapshot; serializable for predicate-dependent writes
    lost update two clients derive a value and last writer overwrites first read-modify-write without guard atomic update, FOR UPDATE, or optimistic version predicate
    write skew two doctors each go off call after seeing the other on call snapshot isolation across different rows serializable isolation, explicit lock on shared guard row, or remodel constraint
    serialization failure engine rejects a dangerous dependency cycle serializable execution retry the complete transaction with same command identity
    deadlock transfers lock accounts in opposite order any lock-based level stable lock order plus full-transaction retry

    Isolation names alone are insufficient across products. State the anomaly to prevent and test the chosen engine behavior. PostgreSQL's serializable isolation uses dependency tracking and can abort transactions that would form a nonserializable history. Applications must treat serialization failures as expected retryable outcomes; swallowing them or retrying only the last statement breaks the abstraction.

    Optimistic concurrency is useful when conflicts are rare:

    UPDATE document
SET body = :body, version = version + 1
WHERE document_id = :id AND version = :expected_version;

    Zero affected rows means conflict or absence. Pessimistic row locking fits short high-contention decisions, but queues waiters and can amplify latency. Neither strategy fixes a predicate-wide invariant unless the locked or validated data represents that predicate.

    Indexes and query planning¶

    The planner chooses scans, joins, ordering, and parallelism from estimated row counts and cost parameters. An index is useful only if its ordering and columns reduce the work of a real query enough to repay maintenance. Composite left prefixes, equality-before-range, covering, partial, and specialized indexes are developed in Database Indexing.

    Use EXPLAIN for estimates and EXPLAIN (ANALYZE, BUFFERS) for measured execution in a safe environment. Compare estimated and actual cardinality at every node. A join problem that looks like insufficient memory can begin with a 10,000x estimate error; a slow index scan can actually be millions of random heap fetches.

    Connections, sessions, and pooling¶

    A database connection consumes backend memory, process/thread scheduling, session state, and lock-table participation even while idle. Setting the maximum to thousands does not create database throughput. Once CPU, cache, WAL, or storage saturates, more active queries increase queueing and p99.

    Use a bounded pool per service and a fleet-wide connection budget. A rough initial concurrency bound follows Little's Law. If one database can safely complete 6,000 simple operations/s and average database service time is 8 ms:

    useful in-flight work = throughput * service time
                      = 6,000/s * 0.008 s
                      = 48 operations

    This is not a prescription for exactly 48 connections: transactions make several calls, workload classes differ, and headroom matters. It shows why 2,000 simultaneously active connections are likely a queue, not capacity. Load-test pool size, use short acquisition deadlines, reject or shed before requests pile up, and reserve connections for migrations, operators, and correctness-critical work.

    Transaction-level proxies improve multiplexing but can break assumptions about session variables, temporary tables, prepared statements, advisory locks, and LISTEN/NOTIFY. Know whether affinity is session, transaction, or statement scoped before introducing a proxy.

    Replicas, positions, and read-your-writes¶

    Physical streaming replicas replay WAL from a primary. They provide read scale and availability copies, but asynchronous replicas can be stale and are not backups. A long replica query can conflict with replay cleanup; delaying replay preserves the query while increasing staleness.

    Track freshness by WAL/log position, not wall-clock guesswork. A write response can carry an integrity-protected session token containing topology epoch and commit position P. A later read follows this policy:

    flowchart TD
    Q[Read with required position P] --> C{Replica replay position at least P?}
    C -->|Yes| R[Read through a fresh replica snapshot]
    C -->|No| D{Deadline permits waiting?}
    D -->|Yes| W[Wait for replay up to budget]
    D -->|No| H{Current primary contains required history?}
    H -->|Yes| P[Read fresh snapshot on primary]
    H -->|No| E[Return unavailable or explicit lost-write outcome]
    W --> C

    This provides read-your-writes only if the chosen snapshot includes the required position on a compatible timeline. Check replay before acquiring a fresh read snapshot; a repeatable-read transaction opened earlier can remain stale even after the replica catches up. Following asynchronous failover, the new primary may lack the acknowledged write, so primary fallback must not silently return old data as if the token had been honored. Sticky routing by itself fails after topology changes, and "replica lag below one second" does not prove one particular commit is visible.

    Synchronous replication can require one or more standbys to durably receive WAL before commit returns. It reduces acknowledged-loss risk but couples write availability and latency to those standbys. Define whether acknowledgement means remote memory, remote durable flush, or replay/application.

    Failover without two primaries¶

    Failover is a fencing problem, not only promotion:

    1. Determine that the old primary cannot continue accepting writes through a lease, quorum, or external fence.
    2. Choose an eligible replica from durable replay/receive positions and timeline history.
    3. Promote it under a new topology epoch and redirect writers.
    4. Rewind or rebuild the old primary before allowing it to rejoin; never attach two divergent timelines casually.
    5. Reconcile connection pools, replication slots, backup lineage, and read-your-writes tokens.

    With asynchronous replication, data acknowledged by the old primary but absent from the promoted replica can be lost. State that RPO explicitly. Automatic failover cannot manufacture missing WAL.

    Partitioning versus sharding¶

    These terms describe different boundaries:

    Technique Location Transaction/query implication Primary purpose
    table partitioning child tables inside one database system planner can prune; one transaction manager remains lifecycle, pruning, maintenance
    sharding rows split across independent database authorities cross-shard joins and transactions coordinate or move to application capacity, write scale, fault isolation
    replication copies of the same logical data writes coordinate; reads choose freshness availability and read scale

    Partitioning a 2 TB event table monthly does not add write capacity if every partition uses the same WAL, CPU, and storage bottleneck. It can make retention a metadata operation, bound vacuum/index work, and prune time queries. Too many partitions increase planning, metadata, and connection overhead; predicates must include partition bounds for pruning.

    Sharding introduces routing, resharding, cross-shard constraints, backups at a common point, and failover per shard. Choose a shard key from transaction locality and access paths. Global uniqueness may need key construction, a synchronously owned registry, or acceptance of scoped uniqueness. See Partitioning and Sharding for placement and migration mechanics.

    Extensions and projections¶

    Relational systems can stretch through extensions: spatial operator classes, full-text search, time-series helpers, vector types, foreign data access, and logical decoding. An extension runs inside or beside a critical state system, so evaluate upgrade compatibility, WAL/replica behavior, backup/restore, crash safety, resource isolation, and operational ownership. Syntax convenience is not an architecture proof.

    Keep canonical tables narrow and correctness-focused. Build read models through materialized views, summary tables, caches, warehouses, or search indexes when a workload needs another layout. A projection needs:

    • A source position or entity version that rejects stale replay.
    • A freshness SLO and observable lag.
    • Delete/tombstone handling.
    • A complete rebuild path from canonical data and ordered changes.
    • Validation at the canonical source for correctness-sensitive decisions.

    Triggers can maintain local invariants atomically but add hidden work and deployment coupling. Transactional outboxes make external projection intent durable in the same commit and let asynchronous consumers retry. Do not dual-write the database and an external index and call both authoritative.

    Schema evolution and constraint rollout¶

    Use expand, migrate, validate, contract. Adding a nullable metadata-only column may be fast; adding a volatile default, rewriting a type, validating a large constraint, or building an index can scan/rewrite data and generate WAL. Test with production-like size and locks.

    Example: require every transfer to have a purpose without a flag day:

    ALTER TABLE transfer ADD COLUMN purpose text;

-- Deploy writers that populate purpose and readers that tolerate NULL.
-- Backfill bounded primary-key ranges with commits and throttling.

ALTER TABLE transfer
ADD CONSTRAINT transfer_purpose_present
CHECK (purpose IS NOT NULL) NOT VALID;

ALTER TABLE transfer
VALIDATE CONSTRAINT transfer_purpose_present;

ALTER TABLE transfer
ALTER COLUMN purpose SET NOT NULL;

    NOT VALID is PostgreSQL-specific: new writes are checked while historical rows can be validated separately. Lock behavior still matters, and converting to NOT NULL should be rehearsed for the exact server version. For foreign keys, indexes on referencing columns often prevent expensive parent deletes/updates; they are not automatically created by the foreign key declaration.

    Backfills should be idempotent, checkpointed, and guarded against overwriting newer writes:

    UPDATE transfer
SET purpose = 'legacy-import'
WHERE transfer_id > :low
  AND transfer_id <= :high
  AND purpose IS NULL;

    Use short batches, pause on replica lag/WAL/disk/latency guardrails, and record progress outside an unbounded transaction. Deploy tolerant readers first, dual-read or shadow-compare when semantics change, and remove old columns only after rollback and old-binary windows end.

    Capacity calculations¶

    Estimate the physical system rather than table payload alone. Suppose 18,000 transactions/s each produce:

    heap tuple and metadata             700 bytes
three index entries                 3 * 80 = 240 bytes
logical change before WAL           940 bytes
WAL bytes / logical-change bytes    2.4x (illustrative assumption)
primary WAL stream                18,000 * 940 * 2.4 = 40.6 MB/s
two physical replicas               about 81.2 MB/s additional network receive

    This models WAL volume only. Dirty heap/index writes, vacuum, checkpoints, and storage replication add physical work and need their own budget. The 2.4x factor is an assumption to replace with observed WAL bytes per transaction.

    At 40.6 MB/s, the primary generates about 40.6 * 86,400 = 3.51 TB/day of WAL before compression and workload variation. A replication slot stalled for 18 hours could pin roughly 40.6 * 64,800 = 2.63 TB. Disk alerts must include retained WAL and time-to-full, not only table growth.

    For recovery, if the latest base backup leaves 900 GB of WAL to replay and sustained recovery throughput is 250 MB/s, replay alone is about 900,000 / 250 = 3,600 seconds, or one hour, before restore download, verification, and service warmup. Recovery objectives must be proved by restore drills.

    Operations and failure semantics¶

    Monitor transaction rate and latency by workload; active/waiting/idle-in-transaction sessions; lock waits and deadlocks; buffer hit/read/write rates; checkpoint duration; WAL generation, flush latency, and retained bytes; replica receive/replay positions; vacuum age and dead tuples; table/index growth; estimate errors and plan changes; pool acquisition time; backup age; and tested restore time.

    Failure Required behavior
    client timeout after commit retry through idempotency key; do not infer rollback
    primary process crash recover from checkpoint plus WAL; reconnect with bounded jitter
    replica lag enforce position token or route to primary for freshness-sensitive read
    disk nearly full preserve WAL/recovery reserve; stop optional writes and maintenance safely
    long transaction blocks vacuum identify owner, cancel by policy, repair bloat after snapshots release
    online DDL waits on lock use lock timeout, inspect blocker, retry later rather than queue the fleet
    asynchronous failover loses tail expose stated RPO and reconcile external effects
    backup job says success restore and validate constraints/checksums in isolation

    Design checklist¶

    • State why relational constraints and transactions fit the invariants.
    • Put one command's invariant inside one bounded transaction where feasible.
    • Name the required isolation behavior and retryable aborts.
    • Trace heap, index, WAL flush, checkpoint, vacuum, and recovery paths.
    • Bound application and fleet connections from measured database capacity.
    • Define replica positions, freshness tokens, synchronous acknowledgement, and failover RPO.
    • Distinguish table partitioning, sharding, and replication.
    • Treat extensions and external stores as operated projections with rebuild paths.
    • Roll out constraints and schema changes through expand, backfill, validate, and contract.
    • Calculate WAL, replica traffic, retained-log risk, restore time, and maintenance headroom.
