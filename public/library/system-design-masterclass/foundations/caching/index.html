    Caching Without Losing Correctness¶

    Executable extension: The versioned-cache lab enumerates reordered updates, deletion, eviction, and late-fill resurrection. Its retained-watermark assumption and production limits are explicit; apply it in Atlas read scaling.

    A cache trades freshness and operational complexity for latency, cost, or dependency protection. It is derived state unless the design explicitly makes it durable and authoritative.

    Start with the objective¶

    For a product service at 30,000 reads/s, 2 KB responses, 80% repeated keys, and a database safe limit of 8,000 reads/s, a 75% hit rate reduces database load to 7,500 reads/s. The cache is justified by dependency capacity, not fashion.

    Pattern Use when Main risk
    cache-aside general read caching stale data and miss races
    read-through centralized loading policy library/platform coupling
    write-through immediate cache visibility needed dual-system write latency
    write-behind write coalescing is acceptable data loss and ordering
    refresh-ahead predictable hot keys wasted refresh and stale refresh races
    request memoization duplicate work within one request limited reuse

    Cache-aside flow¶

    sequenceDiagram
    autonumber
    participant C as Client
    participant S as Service
    participant K as Cache
    participant D as Database
    C->>S: GET product/42
    S->>K: get(42)
    alt hit
        K-->>S: value, version
    else miss
        S->>D: read product 42
        D-->>S: value, version 9
        S->>K: set if newer(version 9, TTL)
    end
    S-->>C: product

    Use versioned values so a slow miss cannot overwrite a newer invalidation or refresh. TTL limits how long an entry can remain resident after its fill. It does not by itself bound age relative to the latest canonical write: a lagging replica or delayed fill can supply an already-old value. Correctness-sensitive reads need a stronger contract.

    Invalidation choices¶

    Requirement Approach
    seconds of staleness acceptable TTL plus jitter
    read-your-writes update/invalidate after commit plus session bypass
    many derived keys version namespace or event-driven invalidation
    correctness-critical decision read canonical store or validate version
    negative lookup protection short negative cache, never indefinite

    For a price shown in search, stale cache may be acceptable; checkout must re-read canonical price and inventory. Separate display correctness from transaction correctness.

    Stampedes, hot keys, and overload¶

    flowchart LR
    M[Concurrent misses] --> C[Per-key request coalescing]
    C --> R[One origin read]
    R --> J[TTL with jitter]
    R --> S[Serve stale on bounded error]
    • Coalesce concurrent misses per key, but bound waiters and loader time.
    • Randomize TTLs to avoid synchronized expiry.
    • Replicate or locally cache hot keys; adding shards does not split one key.
    • Apply admission policies so one-hit objects do not evict frequently reused data.
    • Reserve origin capacity and shed optional traffic when cache hit rate collapses.

    Failure semantics¶

    Failure Safe behavior
    cache unavailable bypass under a strict origin budget; otherwise fail fast
    invalidation lost expire the resident entry, reload from a sufficiently fresh source, and replay the change stream
    origin unavailable serve stale only for explicitly stale-safe reads
    cache returns corrupt data schema/version validation, evict, fetch canonical
    regional cold start warm top keys gradually; rate-limit origin access

    Measure hit rate by endpoint and key popularity, origin requests saved, p99 latency, eviction rate, value age, loader concurrency, and stale-served count. A high global hit rate can hide a zero-hit expensive endpoint.

    Quantify the cache contract¶

    Define what the cache protects and what freshness the caller can observe. "Cache product data for five minutes" is incomplete. A useful contract says: product description reads may be five minutes stale; price display may be 30 seconds stale; checkout must validate price and stock against canonical state; cache loss may increase browse latency but must not corrupt orders.

    Work the load before selecting a pattern. At 30,000 reads/s and a 75% hit ratio, origin load is 7,500 reads/s. If one expensive endpoint contributes 6,000 of those reads at 4 ms database CPU each and all other misses cost 0.5 ms, the expensive endpoint uses 24 CPU-seconds/s by itself. Weighted hit ratio is therefore more useful:

    origin work saved = sum(request_rate * hit_rate * origin_cost)
origin work remaining = sum(request_rate * (1 - hit_rate) * origin_cost)

    Memory also includes keys, metadata, allocator fragmentation, replication, and headroom. Ten million 2 KB values with 300 bytes overhead, two total copies, and 25% free headroom need about 10M * 2,300 B * 2 / 0.75 = 61.3 GB, not the 20 GB of single-copy payload. If only 5% of keys receive 90% of reads, admission and eviction can provide most benefit without caching the full corpus.

    flowchart TD
    R[Read requirements] --> F[Freshness by field or operation]
    R --> C[Origin cost and safe capacity]
    R --> W[Working-set distribution]
    F --> P[Cache pattern]
    C --> P
    W --> P
    P --> O[Overload and invalidation contract]
    O --> M[Metrics and rollout gates]

    Cache-aside race: the stale fill¶

    Versioning in the baseline flow prevents a common race:

    1. Reader A misses cache key product:42 and reads database version 9.
    2. Writer B commits version 10 and invalidates the key.
    3. Reader A, delayed in the network, stores version 9 after the invalidation.
    4. Every later reader sees stale version 9 until TTL expiry.

    Deleting after the database write is not enough because the delayed fill occurs after the delete. set-if-newer(version=9) works if the cache retains a version-10 tombstone or value. Alternatives include short TTLs, invalidation sequence watermarks, or double deletion after a delay, but delayed deletion only narrows the race and must be treated as probabilistic.

    sequenceDiagram
    autonumber
    participant A as Reader A
    participant K as Cache
    participant D as Database
    participant B as Writer B
    A->>K: get product 42
    K-->>A: miss
    A->>D: read
    D-->>A: value v9
    B->>D: commit value v10
    B->>K: invalidate / tombstone v10
    A->>K: set-if-newer value v9
    K-->>A: rejected because 9 < 10

    A database version, log sequence number, or monotonic entity revision is safer than a wall-clock timestamp. Two hosts' clocks can disagree, and last-write-wins timestamps may let an older value dominate. If versions are only ordered within a shard, include shard identity and epoch.

    Eviction must not erase the only rejection watermark while an older loader remains in flight. Retain the watermark beyond the maximum loader/replay lifetime, or use a cache-generation change that invalidates old fills after cache loss. The comparison and fill must be atomic. For invalidation from PostgreSQL CDC, logical decoding can resend recent changes after a crash; never advance the durable consumer cursor ahead of applied invalidations (accessed 2026-09-08).

    Write-path choices and their failure windows¶

    Cache-aside writes usually commit canonical state and then invalidate. If invalidation fails, stale data remains until TTL or replay. Use a transactional outbox or database change stream to make invalidation recoverable, accepting propagation lag. Invalidation events should carry the entity version, and consumers must be idempotent.

    Write-through puts a caching layer on the synchronous path. It can make subsequent reads immediately visible, but a cache acknowledgment must not precede the required durable database commit. If database succeeds and cache update fails, invalidate and recover rather than roll back an already visible business transaction through an unrelated write.

    Write-behind makes the cache temporarily authoritative. This is suitable only when lost/coalesced updates match the product contract, such as approximate telemetry. Acknowledging a bank transfer from a non-durable cache is not safe. If write-behind is justified, persist a log, define ordering per key, fence stale workers, expose drain lag, and reconcile the destination.

    Sequence Failure window Consequence Mitigation
    DB commit, then cache delete process dies before delete stale cache change stream/outbox plus TTL
    cache update, then DB commit DB commit fails cache shows nonexistent state avoid for canonical writes
    DB commit, then cache update slow old update races new update version regression set-if-newer
    durable log, cache apply, async DB worker outage or reorder lag or lost ordering per-key sequence, replay, fencing

    TTL is a probability and load decision¶

    TTL controls an upper bound only when entries expire correctly and readers do not refresh from lagging sources. It also determines miss load. If one million keys are populated uniformly with a 300-second TTL, steady expiration causes roughly 3,333 reloads/s. If all keys were warmed at deployment and receive the same TTL, they can expire together and overwhelm origin.

    Apply jitter, for example a uniformly random TTL from 240 to 360 seconds. This spreads expiration but does not solve a single hot key. For a key receiving 50,000 reads/s, use request coalescing so one loader refreshes while others wait or receive bounded stale data. Bound the waiter count and loader deadline; otherwise one failed loader consumes memory and request threads.

    Probabilistic early refresh avoids a sharp edge. As an item nears expiry, a small increasing fraction of callers attempts refresh under a per-key lock. Refresh-ahead should use popularity: refreshing every cold key wastes origin work and cache capacity.

    Negative caching protects origin from repeated misses for nonexistent IDs. Keep negative TTL short because object creation must become visible. Never turn an authorization failure into a shared negative cache entry; cache keys must include every dimension that changes the result.

    Key design and invalidation graphs¶

    A safe key includes namespace, tenant, logical identity, representation version, and material variants such as language or authorization class. Omitting tenant_id can leak data. Omitting schema version can make old serialized values crash new code. Do not place secrets or raw personal data in keys because keys appear in logs and metrics.

    Derived pages create invalidation fan-out. Updating one product might affect product:42, category pages, search results, recommendations, and promotion summaries. Tracking and deleting every derived key becomes fragile. Prefer one of these:

    • Cache smaller canonical fragments and assemble the page.
    • Put a version in a namespace, such as category:7:v83:page:2, and advance the namespace pointer.
    • Consume canonical change events into rebuildable projections.
    • Accept bounded staleness for discovery while validating on the transaction path.

    Version namespaces make old entries unreachable immediately but do not free memory immediately. TTL and eviction reclaim them, so budget temporary duplication during high update rates.

    flowchart LR
    DB[(Canonical DB)] --> O[Outbox or change stream]
    O --> I[Invalidation consumer]
    I --> E[Entity keys]
    I --> V[Version namespace pointer]
    I --> T[Version tombstones]
    O --> R[Replay checkpoint]
    R --> I

    Eviction, admission, and hot keys¶

    LRU assumes recent access predicts reuse and can be polluted by scans. A one-time analytics scan can evict the product working set. Admission policies such as TinyLFU estimate frequency and reject low-value newcomers; segmented policies protect frequently reused entries from transient bursts. Match policy to traces, not intuition.

    Sharding distributes many keys but not one key. A celebrity profile at 100,000 reads/s still lands on one cache shard. Replicate hot values into process-local caches, read from replica keys, or have the cache platform replicate based on measured heat. Local caches reduce network latency but make invalidation slower and memory usage multiplicative. Include process restarts and fleet-wide cold starts in the origin budget.

    Large values can create network and eviction problems. A 5 MB object requested 2,000/s is 10 GB/s of cache egress. Compression trades CPU for bandwidth; chunking complicates atomic versioning. Often a CDN or object store is the right cache tier while Redis-like storage keeps metadata.

    Failure scenarios and controlled degradation¶

    Cache outage. Blind bypass converts 30,000 reads/s into origin traffic against an 8,000/s safe limit. Reserve perhaps 5,000/s for cache misses, admit only that budget during outage, serve bounded stale local values where allowed, and reject optional browse traffic early. Protect checkout's canonical capacity in a separate pool.

    Regional cold start. Warming every object competes with user traffic and caches cold data. Prewarm a measured top-key set, ramp instances gradually, coalesce misses, and cap warmup to origin headroom. Persisting snapshots can help, but validate age and schema before loading.

    Invalidation stream lag. Continue serving only if each endpoint's staleness budget exceeds observed lag. Expose value version/age internally, alarm on the oldest unprocessed event, and bypass cache for correctness-sensitive reads. Catch-up should be rate-limited so replay does not evict hot values or overload origin.

    Poisoned or corrupt value. Validate schema and checksums, evict the specific key, and fetch canonical state. Add a circuit breaker if a bad writer repeatedly repopulates it. Never deserialize untrusted cached objects with unsafe polymorphic types.

    Hot-key expiry. One absent key creates thousands of waiters. Elect one bounded loader, serve stale within a declared grace window, and fail quickly after the grace period. "Serve stale" must not apply to permissions, revocations, inventory decisions, or legal deletion.

    Migration and rollout¶

    Introduce caching as a reversible optimization:

    1. Measure origin request shape, safe capacity, key popularity, and acceptable age.
    2. Deploy cache writes or fills while reads still use origin; validate serialization and memory estimates.
    3. Shadow cache reads and compare value version and semantics without serving them.
    4. Enable a stale-safe endpoint for 1% of traffic, then ramp while watching origin work saved, p99, value age, and errors.
    5. Inject cache failure and invalidation lag before full rollout; confirm admission control protects origin.
    6. Keep a kill switch that stops cache reads without causing unrestricted bypass.
    7. Change key schemas with a new namespace. Read old then new only for a bounded migration, and avoid permanent compatibility branches.

    For cache-cluster resharding, consistent hashing reduces movement but does not remove miss bursts. Add nodes gradually, limit migration bandwidth, and account for temporary replication. If clients have an outdated ring, they can produce split caches; version topology and observe misses by client version.

    Interview traps and L5/L6 reasoning¶

    • "Add Redis" without an objective: quantify latency, origin protection, or cost and the required hit ratio.
    • TTL as correctness: expiration reduces stale duration but cannot enforce an inventory or authorization invariant.
    • Global hit ratio: segment by endpoint, tenant, key heat, bytes, and origin work.
    • Unlimited bypass: cache failure becomes an origin outage.
    • Deleting after write solves races: a delayed fill can reinsert old data; use versions or ordered invalidation.
    • Ignoring cache-key authorization dimensions: shared values can leak tenant or permission-specific responses.
    • Caching large objects in a general KV: bandwidth and memory fragmentation may dominate; choose the right tier.

    An L5 candidate identifies canonical state, chooses a fitting pattern, explains stale-fill and stampede defenses, calculates origin load, and gives safe outage behavior. An L6 candidate defines freshness per operation, models weighted cost and hot-key skew, chooses admission and eviction from workload evidence, designs versioned invalidation and replay, and stages a reversible rollout with failure injection. L6 reasoning explicitly reserves capacity for critical paths and challenges whether a cache should exist at all when a projection, index, CDN, or query redesign better addresses the bottleneck.
