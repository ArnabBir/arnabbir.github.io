    Messaging and Streams¶

    Executable extension: The outbox/inbox lab tests producer crash gaps and duplicate consumer effects with an independent command oracle. API lifecycle and Atlas worker separation show how the contract evolves.

    Messaging decouples producers from consumers in time. It does not remove coupling: schemas, ordering keys, retention, and overload policies become the contract.

    Queue, log, or direct call?¶

    Mechanism Choose when Avoid when
    direct RPC caller needs immediate result dependency latency exceeds request budget
    work queue one worker should perform each task multiple independent consumers need history
    partitioned log replay, ordering, and projections matter tiny operational footprint is the priority
    pub/sub transient fan-out notifications durable recovery is required but unsupported

    Example: order creation commits canonical rows and an outbox row in one transaction. A relay publishes OrderCreated; inventory, email, and analytics consume independently.

    flowchart LR
    API --> DB[(Orders + outbox)]
    DB --> R[Relay]
    R --> L[(Partitioned log)]
    L --> I[Inventory]
    L --> E[Email]
    L --> A[Analytics]

    Delivery and ordering¶

    At-least-once delivery plus idempotent effects is the robust default. Broker-level "exactly once" does not include an email provider, payment rail, or arbitrary database unless all effects share its transaction boundary.

    Need Design
    per-order order partition by order_id
    global order one partition or external sequencer; expensive
    duplicate-safe update event ID inbox or conditional version
    replayable projection immutable events plus checkpoints
    command cancellation state check at execution, not queue deletion alone 
    sequenceDiagram
    autonumber
    participant B as Broker
    participant C as Consumer
    participant D as Database
    B->>C: event E, attempt 1
    C->>D: transaction: if unseen(E), apply + mark E
    D-->>C: committed
    C--xB: ack lost
    B->>C: event E, attempt 2
    C->>D: E already seen
    C-->>B: ack

    Backpressure and poison events¶

    Bound concurrency by downstream capacity, not broker throughput. Pause partitions or reduce pulls when database latency rises. Exponential backoff without a retry budget merely delays overload.

    After bounded retries, quarantine an event with payload reference, schema version, error, attempt count, and original position. Alert on age and rate. Replay through the normal idempotent path after remediation; preserve ordering-sensitive streams by blocking that key or routing it to a dedicated repair lane.

    Schema evolution and retention¶

    • Give events semantic names such as OrderAccepted, not table-change names.
    • Add optional fields; never reinterpret existing ones.
    • Keep producers compatible with the oldest supported consumer during rollout.
    • Retention must exceed maximum outage plus replay time.
    • Compaction provides latest keyed state, not a complete audit trail.
    • Carry event time, producer time, trace ID, entity version, and event ID.

    Failure semantics¶

    Failure Outcome and recovery
    publish after DB commit fails outbox relay retries
    handler crashes before ack redelivery; idempotency suppresses duplicate effect
    handler acks before side effect message loss; forbidden ordering
    consumer falls behind retention rebuild snapshot, then resume from checkpoint
    partition unavailable producers block/fail by acknowledgment policy
    downstream saturated stop intake; expose queue age; shed low-priority work

    Monitor oldest-message age, throughput, redelivery ratio, partition skew, handler latency, quarantine rate, and time to drain. Queue depth alone is meaningless without arrival and service rates.

    Define the contract before the broker¶

    For every channel, document the producer acknowledgment, delivery scope, ordering key, retention, maximum event size, and overload behavior. "Published" can mean accepted in process memory, written to one broker, or replicated to a quorum. A local durable write may survive a process restart but not loss of its disk. Replicated acceptance survives only the failures covered by replica placement, persistence, and election rules. None of these acknowledgments means a consumer has applied the event.

    Commands request work and can be rejected: ReserveInventory. Events record a fact that already happened: InventoryReserved. Treating a command as a fact lets downstream systems act on an outcome that may never occur. Give events stable semantic names and include an envelope:

    {
  "event_id": "evt-01J7...",
  "event_type": "OrderAccepted",
  "schema_version": 3,
  "aggregate_id": "order-817",
  "aggregate_version": 12,
  "occurred_at": "2026-09-06T10:15:02Z",
  "produced_at": "2026-09-06T10:15:03Z",
  "trace_id": "4fd...",
  "payload": {}
}

    occurred_at supports event-time reasoning; produced_at reveals publication delay. The aggregate version detects gaps and stale updates. The event ID supports deduplication but is not a business idempotency key: two distinct events may represent retries of one client command, so preserve the command key too when relevant.

    Delivery semantics end to end¶

    At-most-once processing acknowledges before or without retrying the effect; it can lose work. At-least-once processing retries until acknowledgment; it can repeat work. "Exactly once" normally describes a bounded broker or stream-processor transaction, not an end-to-end property across databases and external APIs.

    For a database effect, use an inbox table in the same transaction:

    BEGIN;
INSERT INTO consumed_event(consumer, event_id)
VALUES ('inventory', :event_id)
ON CONFLICT DO NOTHING;
-- Pseudocode runner: if rowcount = 0, COMMIT and ACK without the UPDATE.
-- Validate positive qty and require exactly one inventory row; else ROLLBACK.
UPDATE inventory SET reserved = reserved + :qty WHERE sku = :sku;
COMMIT;

    Retain deduplication records at least as long as the broker can redeliver or an operator can replay. If indefinite replay is supported, a compact event ID structure, permanent business ledger, or naturally idempotent version check is required. Calling a payment provider needs the same stable idempotency key on every attempt; a local inbox alone cannot prevent a duplicate after a crash between the provider response and local commit.

    These SQL comments specify required runner branches, not executable SQL control flow. The example records a reservation already authorized elsewhere; it is not an oversell-safe reservation algorithm. For a provider call, persist an intent without marking the event fully consumed, commit, call outside the transaction, then record the result. Restrict retries to the provider's retention contract: Stripe can prune keys after at least 24 hours, after which reuse is a new request (accessed 2026-09-08).

    A Bloom filter may avoid many negative inbox lookups, but a positive result must still consult authoritative state when skipping an event would lose a business effect. Its sizing, false-positive cost, and rebuild lifecycle are covered in Probabilistic Data Structures.

    sequenceDiagram
    autonumber
    participant C as Consumer
    participant DB as Inbox and state DB
    participant P as Payment provider
    C->>DB: durably record pending intent and command key
    DB-->>C: intent committed, event not yet complete
    C->>P: charge with command key
    P-->>C: charge result
    Note over C,DB: Consumer crashes before saving the provider result
    Note over C,DB: Restart finds the pending intent with no recorded result
    C->>P: retry with same command key
    P-->>C: same charge result
    C->>DB: commit result and mark event complete
    DB-->>C: committed

    Ordering is always scoped¶

    A partitioned log usually orders records only within one partition. Partition by order_id to order one order's events, but do not infer order across two orders. Producer retries can reorder records unless the producer protocol supports sequence numbers and bounded in-flight requests. Consumer concurrency can also reorder completion even when delivery is ordered.

    Use aggregate_version to enforce 11 after 10. On receiving version 12 while version 11 is absent, the consumer can pause that key, fetch canonical state, or wait in a bounded gap buffer. Silently applying 12 may be correct for a latest-state projection but wrong for an additive ledger. State the choice per consumer.

    Global order is expensive because it creates one serialization point. Most claimed global-order requirements are actually key order plus a deterministic tie-breaker for display. If a financial ledger truly needs one sequence, partition it by account or ledger and use a leader per partition; do not promise unlimited global throughput.

    flowchart TD
    E[Incoming event] --> V{Expected aggregate version?}
    V -->|Yes| A[Apply transactionally]
    V -->|Older| D[Deduplicate or discard]
    V -->|Newer with gap| G[Pause key and buffer]
    G --> F[Fetch missing event or snapshot]
    F --> A
    A --> K[Advance checkpoint]

    Backpressure with numbers¶

    Let arrival rate be 12,000 events/s and sustainable processing rate be 10,000 events/s. Backlog grows by 2,000 events/s, or 7.2 million per hour. If traffic later falls to 8,000 events/s, only 2,000 events/s remains for catch-up; draining one hour of overload takes another hour. A 10-million-event retention margin is therefore less than 90 minutes at the overload rate.

    Concurrency should follow downstream capacity. If a handler holds one database connection for 40 ms on average, one connection handles at most 25 operations/s. A 200-connection pool has a theoretical 5,000 operations/s ceiling before overhead and variance. Running 2,000 consumer threads does not raise that ceiling; it raises wait time and timeout probability.

    Use a layered response:

    1. Bound in-process queues and worker concurrency.
    2. Pause or reduce pulls when downstream latency or pool saturation rises.
    3. Preserve capacity for high-priority topics or tenants.
    4. Reject or defer producers before retention or disk is exhausted.
    5. Expose Retry-After or an explicit admission result rather than timing out ambiguously.
    stateDiagram-v2
    [*] --> Normal
    Normal --> Throttled: downstream p95 high
    Throttled --> Paused: queue age above limit
    Paused --> Shedding: retention margin threatened
    Throttled --> Normal: sustained recovery
    Paused --> Throttled: backlog draining
    Shedding --> Paused: arrival below safe rate

    Retry topics can prevent one delayed message from blocking a partition, but they relax ordering because later events proceed. For ordering-sensitive keys, pause only the affected key or partition, and make the availability cost explicit. Add jitter and cap attempts. A fleet allowing five total attempts can turn 10,000 failing operations into 50,000 dependency calls. Five retries after an initial attempt would instead produce up to 60,000 calls.

    Replay is a planned operation¶

    Replay supports projection repair, bug correction, and new consumers. It also repeats every side effect unless replay mode and idempotency are designed. Separate pure projection consumers from effecting consumers such as email or payments. An email consumer should either retain permanent send evidence or reject historical replay by policy.

    A safe projection rebuild follows this sequence:

    1. Create a new projection namespace; do not destroy the serving one.
    2. Record the replay start and target high-water mark.
    3. Load a consistent snapshot when full history is unavailable.
    4. Replay from the snapshot position with the new consumer version.
    5. Compare counts, key checksums, sampled records, and business invariants.
    6. Catch up to within a defined lag, briefly coordinate cutover if needed, then atomically switch readers.
    7. Keep feeding the old projection during the rollback window, or catch it up to a verified cutover watermark before routing reads back. Retaining a frozen copy alone does not make rollback fresh.

    Consumer checkpoints must be committed after the corresponding state transaction, or atomically with it when supported. A checkpoint ahead of state loses updates; a checkpoint behind state causes duplicates, which the idempotent path should tolerate. With concurrent processing, advance only through the contiguous completed prefix: if offsets 101 and 103 are durable but 102 is not, checkpointing through 103 would skip 102 after a crash.

    Schema evolution across independent deployments¶

    Compatibility has direction. With backward compatibility, a new consumer reads old events. With forward compatibility, an old consumer tolerates events from a new producer. During rolling deployment, both are often required.

    Prefer additive optional fields with defaults. Never change amount_cents from integer cents to decimal dollars under the same field name, reuse an enum value, or change a field's meaning. Create a new field or event version. Consumers should preserve unknown fields when they transform and republish an envelope if the serialization format supports it.

    For a required semantic change, use expand-contract:

    1. Register a compatible schema that adds currency as optional with a safe interpretation for historical data.
    2. Deploy consumers that understand both old and new representations.
    3. Deploy producers that populate currency.
    4. Measure the oldest active consumer and the fraction of new records populated.
    5. Only after retention and replay requirements permit it, remove support for the old form in a major event version.

    A schema registry checks structural compatibility, not business meaning. Contract tests should use real historical payloads, maximum sizes, unknown enum values, missing optional fields, and malformed records. Put large blobs in object storage and publish an immutable reference plus checksum; oversized events harm broker replication and consumer memory.

    Poison records and quarantine¶

    Distinguish transient dependency errors, permanent validation errors, code defects, and unsupported schemas. Retry only transient failures. A quarantine record should contain the original topic, partition, offset, payload reference, schema ID, exception class, first and last failure times, attempts, consumer version, and trace context. Encrypt and access-control it like the source data.

    Quarantine is not completion. Give it an owner, age SLO, alert, remediation status, and auditable replay command. Replay to the original processing path with the same event ID. If a corrected payload is necessary, publish a new correction event linked to the original rather than silently editing immutable history.

    Retention and recovery sizing¶

    Retain an operational recovery cushion. If detection/outage lasts 24 hours and repair adds 4 hours, no consumption occurs for 28 hours. At recovery throughput twice ongoing input, draining that backlog takes another 28 hours. Keeping the entire incident interval replayable until recovery finishes requires more than 56 hours plus margin. This conservative full-history requirement is stronger than the minimum for an oldest-first consumer that continuously advances its committed cursor; time retention expires records by age, not total backlog count.

    Monitor ingress and egress rates, oldest unprocessed event age, bytes remaining before retention, per-partition skew, producer acknowledgment latency, consumer error classes, redelivery ratio, checkpoint movement, schema rejection, and quarantine age. Alert on time-to-data-loss and user delay, not raw depth alone.

    Design review checklist¶

    • Define what producer acknowledgment guarantees and what it does not.
    • Name ordering scope, partition key, and hot-key behavior.
    • Place acknowledgment after durable idempotent effects.
    • Quantify downstream capacity, backlog growth, drain time, and retention.
    • Separate replayable projections from irreversible external effects.
    • Test old producers with new consumers and new producers with old consumers.
    • Specify poison-record ownership and ordered-stream behavior.
    • Rehearse snapshot restore, replay, cutover, and rollback.
