    Distributed Transactions and Workflows¶

    Executable extension: Run the outbox/inbox fixture, then review correctness methods to separate simulated atomicity, actual process-restart evidence, and unsupported external-effect guarantees.

    A distributed transaction coordinates one business outcome across state owned by different failure and concurrency domains. The central problem is not making every step atomic. It is preserving explicit invariants when messages, responses, processes, and coordinators fail at inconvenient times.

    Learning goals¶

    After this chapter, you should be able to:

    • define local ACID boundaries and avoid distributing an invariant unnecessarily;
    • explain two-phase commit, blocking, recovery, and heuristic danger;
    • implement transactional outbox and idempotent inbox protocols;
    • choose sagas, TCC, escrow, or reconciliation from business semantics;
    • handle unknown outcomes and retries without duplicate effects; and
    • demonstrate L5 protocol depth and L6 cross-domain operating policy.

    First principles: invariants and knowledge¶

    Start with a business invariant, not a workflow diagram:

    I1: available inventory never becomes negative
I2: one checkout request creates at most one charge
I3: every accepted order eventually becomes fulfilled, cancelled, or escalated

    I1 and I2 are safety properties: a forbidden outcome must never occur. I3 is a liveness property: accepted work must eventually make progress. A system can preserve safety by refusing all work and still fail liveness. State the recovery assumptions and escalation deadline that make I3 achievable.

    Classify each business requirement:

    • Immediate: must hold before success is acknowledged.
    • Convergent: may be temporarily false but must repair within a bound.
    • Compensatable: a later semantic action can offset an earlier action.
    • Reconciled: independent evidence can detect and repair divergence.

    Atomicity does not eliminate uncertainty for a remote caller. If a server commits and its response is lost, the caller cannot distinguish commit from failure. Stable command identity and outcome lookup are therefore part of the protocol.

    stateDiagram-v2
    [*] --> Received
    Received --> Committed: local transaction commits
    Received --> Rejected: validation or conflict
    Committed --> Returned: response delivered
    Committed --> UnknownToCaller: response lost
    UnknownToCaller --> Returned: retry with same key reads outcome

    Local ACID before distributed coordination¶

    Put data that participates in one tight invariant in one transactional boundary when scale and ownership allow it. A local transaction can atomically write canonical state, command outcome, and an outbox record:

    BEGIN;

INSERT INTO command_result(command_key, request_hash, state)
VALUES (:key, :hash, 'IN_PROGRESS');

UPDATE inventory
SET available = available - :quantity
WHERE sku = :sku AND available >= :quantity;
-- Require exactly one affected row.

INSERT INTO reservation(reservation_id, sku, quantity, state)
VALUES (:reservation_id, :sku, :quantity, 'HELD');

INSERT INTO outbox(event_id, aggregate_id, event_type, payload)
VALUES (:event_id, :reservation_id, 'InventoryHeld', :payload);

UPDATE command_result SET state = 'SUCCEEDED', result_id = :reservation_id
WHERE command_key = :key;

COMMIT;

    The unique command key prevents duplicate execution. Scope it to the authenticated tenant and operation, validate a strictly positive quantity before mutation, and enforce nonnegative inventory and positive reservation quantities with database constraints. Store a request hash so reuse of the same key with different input is rejected. The affected-row check must abort the transaction on zero rows; a SQL comment does not implement that branch. On a duplicate key, roll back this attempt and read the committed outcome rather than continuing with the stock update. No broker transaction is needed for the invariant.

    Two-phase commit¶

    Two-phase commit, or 2PC, coordinates participants that can prepare and later commit or abort.

    sequenceDiagram
    autonumber
    participant C as Coordinator
    participant A as Participant A
    participant B as Participant B
    C->>A: PREPARE transaction X
    C->>B: PREPARE transaction X
    A-->>C: YES, durable prepared state
    B-->>C: YES, durable prepared state
    C->>C: Durably record COMMIT X
    C->>A: COMMIT X
    C->>B: COMMIT X
    A-->>C: ACK
    B-->>C: ACK

    In phase one, each participant validates and durably records enough state to commit later while retaining required locks or reservations. If all vote yes, the coordinator durably chooses commit; otherwise it chooses abort. Phase two communicates the decision. Participants recover prepared transactions from durable logs and query the coordinator or recovery peers for the outcome.

    2PC provides atomic commitment under its model; it does not provide arbitrary distributed serializability unless concurrency control across participants does so. It can block a prepared participant while the decision is unavailable. Long-lived locks amplify tail latency and deadlocks. Operationally dangerous manual outcomes can create heuristic mixed states.

    Use 2PC when participants expose compatible prepare/commit semantics, the transaction is short, availability loss during coordinator uncertainty is acceptable, and atomicity is more valuable than loose coupling. Avoid holding a prepared database transaction while waiting for a human, shipping provider, or unbounded remote API.

    Transactional outbox and idempotent inbox¶

    The dual-write problem appears when a service writes its database and broker separately. Either order has a crash window. An outbox writes the business state and event in one local transaction. A relay publishes unprocessed rows and records progress. Publication is at least once, so consumers deduplicate.

    sequenceDiagram
    autonumber
    participant API
    participant DB as Orders and outbox DB
    participant R as Relay
    participant B as Broker
    participant C as Consumer
    API->>DB: Commit order plus event E
    R->>DB: Read unsent E
    R->>B: Publish E
    B--xR: acknowledgment lost
    B->>C: deliver E
    C->>C: commit effect and inbox E atomically
    R->>B: publish E again
    B->>C: deliver duplicate E
    C->>C: inbox E exists, skip repeated effect

    An inbox is a unique (consumer, event_id) record written in the same transaction as the consumer's database effect. Acknowledgment follows commit. Retain dedup evidence for the maximum redelivery and replay horizon, or use permanent business identity/version semantics.

    Outbox details matter:

    • preserve aggregate ID, aggregate version, event ID, schema version, and occurred time;
    • partition relay work without publishing two versions of one aggregate out of order;
    • monitor oldest unpublished age, attempts, poison rows, and table growth;
    • delete or archive only after publication evidence and replay requirements permit;
    • rebuild downstream projections from canonical state or retained events.

    Sagas¶

    A saga is a sequence of local transactions connected by messages, with compensating actions for completed steps. Compensation is business logic, not database rollback. A refund does not erase that a charge occurred; a cancellation may incur a fee; an email cannot be unsent.

    flowchart TD
    O[Create order] --> I[Reserve inventory]
    I --> P[Authorize payment]
    P --> F[Confirm fulfillment]
    I -->|fails| C1[Cancel order]
    P -->|fails| C2[Release inventory]
    F -->|fails| C3[Void or refund payment]
    C3 --> C2
    C2 --> C1

    Orchestration centralizes state transitions, deadlines, and visibility. Choreography lets services react to events but can hide the global state machine and create cycles. Prefer an explicit durable workflow for long or high-value processes. Store current state, step attempts, next wake time, external references, and compensation state.

    Every forward and compensating command needs stable identity. Model terminal states including SUCCEEDED, COMPENSATED, FAILED_MANUAL, and EXPIRED. Do not retry permanent business rejection. Bound retries and escalate when automation cannot restore the invariant.

    Try-confirm-cancel¶

    Try-confirm-cancel, or TCC, asks each participant to reserve a resource, then confirm or cancel it.

    TRY:     create hold H with quantity, owner, and expires_at
CONFIRM: consume H exactly once and create final allocation
CANCEL:  release H exactly once

    TCC exposes reservation semantics and avoids holding database locks across services. It needs capacity reserved during the decision window, idempotent operations, authorization of the holder, expiry, and a sweeper. Expiry races with confirm: use an atomic state transition such as HELD -> CONFIRMED only if current time and policy permit, and make the caller observe the definitive result.

    TCC works for inventory, credit limits, seats, and quotas when resources can be held. It is awkward for irreversible effects or resources with no reservation API.

    Also handle CANCEL arriving before a delayed TRY: record a terminal cancellation tombstone for the reservation ID so a later TRY cannot create a stranded hold. CONFIRM and CANCEL must arbitrate on the same versioned state; repeat calls return that terminal decision. The tombstone lifetime must cover delayed commands and replay, just as provider idempotency retention bounds safe remote retries. This is a designed TCC contract, not a claim that every participant API implements it.

    Escrow and rights allocation¶

    Escrow partitions a global bounded resource into local rights. If 1,000 units exist, region A may receive 600 sell rights and region B 400. Each region spends only local rights without synchronous cross-region coordination. Rights transfer between regions through a durable protocol.

    global invariant: sold_A + sold_B <= 1,000
local invariant:  sold_A <= rights_A; sold_B <= rights_B
allocation invariant: rights_A + rights_B + rights_in_transfer = 1,000

    Here, each region's rights include units it has already sold plus its remaining allowance. Transfer only unused rights: to move 50 from A to B, durably subtract 50 from A and record transfer T before idempotently crediting B. While T is unresolved, keep those 50 in rights_in_transfer; they are unavailable for either side to spend. An uncertain acknowledgment must not credit B again or restore A's rights blindly.

    Escrow trades utilization for availability. Region B can reject while A has unused rights. Rebalance thresholds, in-flight transfers, expiry, loss recovery, and audit must prevent double allocation. This pattern is powerful when the invariant is numeric and decomposable; it does not generalize to arbitrary cross-entity constraints.

    Unknown outcomes and idempotency¶

    Network errors create epistemic uncertainty: the caller does not know what happened. Classify results as successful, business-rejected, definitely not executed, or unknown. Never map every timeout to failure and start a new command identity.

    A robust command endpoint accepts an idempotency key and canonical request hash:

    Existing state Same request hash Response
    absent n/a claim key and execute
    in progress yes return pending or wait within deadline
    succeeded yes return stored result
    failed terminally yes return stored failure
    any no reject key misuse

    If an external provider supports idempotency, propagate a stable business key and record its retention horizon. A retry after the provider forgets the key can create a new effect even though the local key is unchanged. Vendor (accessed 2026-09-08): Stripe's idempotent requests contract permits pruning keys once they are at least 24 hours old; reuse after pruning creates a new request. It also retains the first executed response, including some server errors, so repeated errors are not proof that no effect occurred.

    If the provider lacks idempotency, a merchant-reference lookup is useful evidence but a negative result is not permission to retry unless the provider contract rules out a still-running or not-yet-visible original attempt. Otherwise keep the outcome unknown, constrain duplicate impact, and reconcile provider statements or escalate. A local lock cannot cover a crash after the provider commits but before local state records the result.

    Reconciliation is a correctness mechanism¶

    Reconciliation compares independent evidence and drives idempotent repair. It is required even with carefully designed protocols because software defects, operator actions, retention errors, and external systems escape transaction boundaries.

    For payments:

    internal orders + payment attempts + ledger postings
                    compared with
provider transaction export + settlement statement + bank movement

    Store discrepancy type, source versions, amount, owner, first seen, attempts, and resolution. Use a high-water mark plus overlap window so late records are revisited. Never silently overwrite history; post correction entries and retain evidence. Define an age SLO for unresolved discrepancies.

    Quantitative workflow design¶

    Suppose checkout starts 4,000 sagas/s. Measurements show 99.5% complete in a mean of 3 seconds within that cohort, while 0.5% remain pending for a mean of 15 minutes.

    normal arrival rate      = 4,000/s * 0.995 = 3,980/s
normal in-flight         = 3,980/s * 3 s = 11,940
long-tail arrival rate   = 4,000/s * 0.005 = 20/s
long-tail in-flight      = 20/s * 900 s = 18,000
total mean in-flight     = 29,940

    Little's Law uses mean residence time, not p99. The small pending fraction dominates durable workflow count even in this simplified two-cohort model. Size state, timers, provider polling, and reconciliation from the measured distribution. If each pending record and indexes consume 2 KB, only the long-tail working set is about 36 MB, but retries, history, and partitions add overhead.

    For outbox capacity, 50,000 events/s at 1.2 KB/event is 60 MB/s. A four-hour broker outage creates 864 GB of payload before indexes, WAL, and replication. The database must retain and later drain that backlog without starving foreground traffic.

    If recovery publication sustains 90 MB/s while new events still arrive at 60 MB/s, net drain is only 30 MB/s. Clearing 864 GB takes 864,000 MB / 30 MB/s = 28,800 s, or eight hours, using decimal units. A relay that merely matches arrival rate never catches up. Measure this spare capacity under foreground load and include it in outbox retention and recovery objectives.

    Decision framework¶

    1. Separate safety invariants from liveness goals, then identify convergence, compensation, and reconciliation requirements.
    2. Minimize the number of owners inside each immediate invariant.
    3. Define command identity, commit point, and externally visible outcomes.
    4. Choose local transaction, 2PC, outbox/inbox, saga, TCC, or escrow per boundary.
    5. Write the durable state machine, including unknown and manual states.
    6. Allocate deadlines, retry budgets, hold expiry, and dedup retention.
    7. Define compensation limits and independent reconciliation evidence.
    8. Test every crash point before/after commit, publish, effect, acknowledgment, and compensation.

    Failure cases and tradeoffs¶

    Failure Dangerous assumption Recovery
    response lost after commit timeout means failure same key returns stored result
    outbox published twice broker ack means exactly once inbox or versioned idempotent effect
    coordinator unavailable after prepare participants can decide alone recover durable decision; block or use specified termination protocol
    saga compensation fails rollback is automatic retry boundedly, escalate, reconcile
    hold expires during confirm clocks settle the race one authoritative atomic state transition
    stale event arrives delivery order equals business order aggregate version and gap policy
    provider lacks idempotency local dedup prevents duplicate charge provider reference lookup and reconciliation
    workflow definition changes in-flight instances follow new logic safely version definitions and migrate explicitly

    L5 and L6 expectations¶

    An L5 candidate names invariants, draws exact commit and message order, handles every crash window, and supplies idempotency, compensation, timeout, and reconciliation data. An L6 candidate also decides service ownership boundaries, protocol standards, workflow versioning, multi-region authority, financial or regulatory evidence, operational escalation, migration safety, and acceptable periods of reduced availability.

    Interview traps¶

    • Saying "exactly once" without defining the transactional boundary.
    • Using a distributed lock as atomic commit across two databases.
    • Calling a saga a rollback.
    • Omitting the response-lost-after-commit case.
    • Retrying with a new idempotency key.
    • Publishing before local commit and treating the event as fact.
    • Letting TCC holds live forever or expire without a race-safe transition.
    • Treating reconciliation as a dashboard rather than an owned repair loop.

    Exercises with worked answers¶

    1. Order and event dual write¶

    An API inserts an order, commits, then publishes OrderCreated. The process can crash between steps. Repair it without 2PC.

    Worked answer

    Insert the order, stable command outcome, and outbox event in one local transaction. A relay publishes the event at least once and tracks progress. Consumers use an inbox or aggregate version in the same transaction as their effect. Monitor outbox age and retain a replay/rebuild path. Return the stored command result for duplicate client requests.

    2. Seat reservation¶

    A booking spans seat inventory and payment. Payment authorization can take 30 seconds. Should a database transaction hold the seat row lock throughout?

    Worked answer

    No. Create a durable expiring seat hold with an atomic AVAILABLE -> HELD transition, authorize payment using stable identity, then atomically confirm the live hold. On rejection or expiry, release it idempotently. Define the expiry/confirm race in the inventory owner, compensate or void payment if confirmation fails, and reconcile provider outcomes.

    3. 2PC uncertainty¶

    Both participants voted yes, then lost contact with the coordinator. One operator proposes aborting locally to release locks.

    Worked answer

    A prepared participant cannot unilaterally abort if the coordinator may have durably chosen commit. Recover or query the authoritative decision according to the protocol. A heuristic abort can produce mixed outcomes and requires explicit exceptional policy and repair. Bound transaction duration and improve coordinator recovery rather than improvising normal behavior.

    Takeaways¶

    • Keep immediate invariants within one owner when possible.
    • A timeout can mean success, failure, or unknown; command identity resolves retries.
    • 2PC coordinates atomic commitment but can block and hold resources.
    • Outbox/inbox provides durable at-least-once propagation with idempotent effects.
    • Sagas compensate semantically; TCC reserves; escrow partitions rights.
    • Reconciliation is part of correctness, especially across external systems.
