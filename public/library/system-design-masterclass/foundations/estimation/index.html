    Estimation That Changes the Design¶

    Engineering extension: Performance science and queueing derives saturation, variability, benchmark boundaries, and backlog drain; machine/runtime budgets connects estimates to real resource ownership.

    Estimation is useful only when it eliminates an option, sizes a boundary, or reveals skew. Prefer ranges and sensitivity analysis over false precision.

    A repeatable worksheet¶

    1. Convert monthly users into active users and actions per active user.
    2. Compute average QPS, then apply a measured or assumed peak factor.
    3. Estimate bytes per durable object, index overhead, replicas, and retention.
    4. Estimate ingress, egress, fan-out, and background amplification.
    5. Identify the largest uncertainty and test both ends of its range.

    Core formulas:

    average QPS = actions per day / 86,400
peak QPS = average QPS * peak factor
storage = writes/s * bytes/write * retention seconds * replication factor
bandwidth = QPS * payload bytes
effective work = input QPS * fan-out * write amplification

    Worked example: photo sharing¶

    Assume 50M daily users, two feed opens/user/day, 20 items/page, 5M uploads/day, 3 MB average original, 200 KB total metadata and thumbnails, 365-day retention, and 3x replication. For API egress, assume a 2 KB metadata response per item, or 40 KB per 20-item page; media bytes are fetched separately.

    Quantity Calculation Result
    average feed QPS 100M / 86,400 1,160/s
    peak feed QPS average x 8 9,300/s
    metadata item reads peak x 20 186,000/s
    original ingress 5M x 3 MB/day 15 TB/day
    one-year originals 15 TB x 365 x 3 16.4 PB
    peak API egress 9,300 x 40 KB 372 MB/s

    Consequences: blobs do not belong in the metadata database; a CDN matters more than sharding metadata; batch thumbnail generation needs capacity above 58 average jobs/s; feed fan-out, not request QPS alone, may dominate.

    flowchart LR
    U[User assumptions] --> Q[QPS]
    U --> S[Storage]
    Q --> F[Fan-out and skew]
    S --> C[Cost and retention]
    F --> A[Architecture thresholds]
    C --> A

    Model distributions, not averages¶

    Averages conceal launch spikes, celebrity keys, large objects, and retries. State at least:

    • peak-to-average ratio, with an explicitly assumed range such as 3-10x;
    • hottest-key share, such as 2% of requests to one creator;
    • p50/p99 payload size;
    • replication and index multipliers;
    • replay, retry, and compaction overhead;
    • growth horizon and safety margin.
    Unknown Low case High case Design impact
    peak factor 3x 12x autoscaling and admission capacity
    fan-out 20 10,000 push versus pull feed
    retention 30 days 7 years storage tiering and deletion
    hot-key share 0.1% 10% ordinary sharding versus key splitting

    Capacity is multi-dimensional¶

    Do not say "one database handles 20K QPS" without specifying query shape, row size, indexes, consistency, and hardware. CPU-bound JSON transformations, IOPS-bound random reads, bandwidth-bound blob delivery, and lock-bound counters scale differently.

    Little's Law catches concurrency limits: in-flight = throughput * latency. At 20,000 requests/s and 250 ms dependency latency, 5,000 operations are in flight. If every operation holds one connection for those 250 ms, a 500-connection pool can complete at most about 2,000 operations/s. A queue absorbs a brief burst but cannot sustain 20,000/s. Shorten connection occupancy, reduce admitted load, or prove that additional connections or protocol multiplexing fit the dependency's capacity.

    Failure and overload budget¶

    Capacity must include degraded states. If one of three zones fails, each survivor receives 50% more load. A fleet operated at 75% before failure reaches 112.5%, causing cascading failure. Operate below the post-failure safe threshold or shed load.

    flowchart TD
    P[Peak demand] --> H[Headroom]
    H --> Z{One zone lost}
    Z -->|capacity remains| S[Serve core traffic]
    Z -->|capacity exhausted| L[Admission control]
    L --> D[Drop optional work]

    Use estimates as hypotheses. Name the production metrics that replace them: per-key QPS, queue age, bytes transferred, lock wait, cache hit rate, and cost per successful operation.

    Keep units visible¶

    Most estimation mistakes are unit mistakes hidden by prose. Carry units through every calculation and round only after finding the architectural order of magnitude. Use decimal units for network rates unless the organization explicitly budgets in binary units.

    Suppose a messaging service has 12 million daily active users. Each sends 18 messages/day, an average message is 900 bytes including row metadata but excluding secondary indexes, 4% include a 2.5 MB attachment, and traffic peaks at 6x average.

    messages/day = 12M users * 18 messages/user/day = 216M messages/day
average write QPS = 216M / 86,400 seconds/day = 2,500 messages/s
peak write QPS = 2,500 * 6 = 15,000 messages/s
metadata ingress = 216M * 900 bytes = 194.4 GB/day
attachment ingress = 216M * 0.04 * 2.5 MB = 21.6 TB/day

    With 3x metadata replication, two secondary indexes whose entries total 40% of the base record, and 365 days online, metadata occupies approximately 194.4 GB/day * 1.4 * 3 * 365 = 298 TB. Attachments at 1.5x erasure-coding overhead occupy 21.6 TB/day * 1.5 * 365 = 11.8 PB. This immediately separates object storage from message metadata. It also says attachment lifecycle policy matters much more than shaving bytes from a message row.

    Do not multiply every quantity by the same replication factor. Database replicas, object erasure coding, cross-region copies, temporary upload chunks, indexes, and backups have different amplification. Show each explicitly to avoid both undercounting and double counting.

    flowchart TD
    V[User and action volume] --> OP[Operations per second]
    V --> BYTES[Logical bytes]
    OP --> AMP[Read, write, and fan-out amplification]
    BYTES --> DUR[Retention and durability copies]
    AMP --> RES[CPU, IOPS, connections, bandwidth]
    DUR --> COST[Storage and transfer cost]
    RES --> LIMIT[Capacity limit]
    COST --> LIMIT

    Translate throughput into resources¶

    QPS is not capacity until tied to a resource model. If a database read consumes 1.5 ms of CPU and a write consumes 4 ms, then at 40,000 reads/s and 15,000 writes/s the fleet demands 40,000 * 0.0015 + 15,000 * 0.004 = 120 CPU-seconds/second, or 120 fully utilized cores. At a safer 60% target, allow about 200 effective cores before replication, background compaction, failover headroom, and skew. This is a sanity check, not a hardware benchmark; production load tests replace it.

    Use dated benchmark cards¶

    Hardware throughput is an observation with an expiry date, not a universal constant. Keep a short benchmark card beside each capacity model:

    Field Illustrative observation (not a measured result)
    measured on 2026-09-06; repeat after runtime, instance, or storage changes
    hardware 16 allocated vCPU, 64 GiB RAM, local SSD; one zone
    software and data runtime/build ID, compression, three indexes, 1.2 KB p50 and 8 KB p99 rows
    workload 70% point reads, 25% inserts, 5% updates; 2% hot-key share
    durability quorum acknowledgment; synchronous WAL
    background work compaction and one incremental checkpoint enabled
    pass criteria p99 under 80 ms, errors under 0.1%, no growing queue for 30 minutes
    result 14,000 operations/s sustained; CPU 68%, disk 72%, network 41%

    The card is evidence only for that envelope. Record the load generator, dataset size relative to memory, warm-up, test duration, percentile method, and confidence range in the benchmark artifact. Re-run it when payload distributions, indexes, consistency, encryption, runtime, kernel, or hardware change. A vendor maximum from a different request shape is an upper bound at best.

    Calculate a measured hardware envelope¶

    For each resource j, convert measured headroom into an operation-rate ceiling and take the minimum:

    capacity_j = measured_rate * target_utilization_j / measured_utilization_j
node_envelope = min(capacity_cpu, capacity_disk, capacity_network, capacity_lock, ...)
fleet_nodes = ceil(peak_rate / (node_envelope * surviving_fraction))

    Using the dated card, suppose policy caps CPU at 65%, disk at 70%, and network at 70%. The extrapolated ceilings are 14K * 0.65/0.68 = 13.4K for CPU, 14K * 0.70/0.72 = 13.6K for disk, and 14K * 0.70/0.41 = 23.9K for network. The estimated envelope from this illustrative card is therefore about 13.4K operations/s per node, limited by CPU. Do not extrapolate far beyond the measured point: rerun near the proposed limit because queues, cache misses, lock contention, GC, and compaction are nonlinear.

    For a 240K operations/s peak across three equal zones with one-zone tolerance, surviving_fraction=2/3. The arithmetic minimum is ceil(240K / (13.4K * 2/3)) = 27 nodes, or nine per zone. Add explicit deployment, skew, and growth margins only once; naming each margin prevents a hidden blanket multiplier. Then test all 240K operations/s on the 18 surviving nodes, about 13.33K per node, not just normal load spread over 27 nodes.

    For disks, distinguish sequential bandwidth from random IOPS. A node capable of 30,000 random write IOPS cannot sustain 20,000 logical writes/s if a write creates one WAL operation, one table operation, and two index operations: 20,000 * 4 = 80,000 IOPS. Batching and LSM buffering alter the physical pattern, but also create compaction bandwidth and tail-latency costs.

    For network, include protocol overhead and fan-out. At 15,000 messages/s, average fan-out 3.2 devices, and a 1.2 KB delivered envelope, server egress is 15,000 * 3.2 * 1.2 KB = 57.6 MB/s before TLS and transport overhead. A group with 100,000 members is not "average." Large groups require a separate fan-out strategy, bounded batches, and queue-age SLO.

    Work a latency and concurrency budget¶

    Start from the user-visible percentile and allocate it. For a 400 ms p99 send-message target:

    Stage p99 budget
    edge, authentication, routing 45 ms
    application processing 30 ms
    database replication and commit 140 ms
    event publication handoff 35 ms
    network variance reserve 100 ms
    remaining safety margin 50 ms

    Budgets are not additive percentiles in a statistically exact sense, but they expose impossible dependency contracts. A downstream API with a 500 ms timeout cannot sit synchronously inside a 400 ms endpoint.

    Little's Law converts each stage to concurrency. If commit throughput is 15,000/s and average commit latency is 80 ms, about 15,000 * 0.08 = 1,200 commits are in flight. If each transaction pins one database connection, a 400-connection pool guarantees an application queue unless requests multiplex or the latency/throughput assumptions change. With a bounded queue of 2,000 and a net arrival excess of 5,000/s, the queue fills in 2,000 / 5,000 = 0.4 seconds; autoscaling that takes two minutes cannot prevent immediate shedding.

    flowchart LR
    A[Arrival rate] --> Q[Bounded queue]
    Q --> W[Concurrent workers]
    W --> D[Dependency]
    D --> L[Observed latency]
    L --> I[In-flight via Little's Law]
    I -->|exceeds limit| S[Shed or degrade]
    I -->|within limit| O[Serve]

    Estimate caches and partitions honestly¶

    A cache hit ratio must be weighted by cost, not just request count. Suppose endpoint A serves 90,000 cheap reads/s with a 95% hit rate and endpoint B serves 10,000 expensive reads/s with a 20% hit rate. The global hit rate is 87.5%, yet B sends 8,000 reads/s to the database and may dominate CPU. Report origin QPS and origin work by endpoint.

    To size cache memory for 40 million objects averaging 1.4 KB, include key and allocator overhead. At 250 bytes/object overhead and two cache copies, memory is 40M * 1,650 B * 2 = 132 GB. If the budget is 30 GB, the cache cannot hold the full set. A popularity model, admission policy, compression, or smaller representation is required. Adding a TTL does not guarantee the working set fits.

    Keep the observation boundary consistent: gRPC's deadline guide distinguishes client waiting from server work that must be cancelled by the application. A timed-out operation can continue consuming the CPU and concurrency estimated here. Count attempts and work still running after timeout, not only successful responses (accessed 2026-09-08).

    Partition counts must consider write concentration and operations, not only bytes. If one shard safely handles 4,000 peak writes/s and total peak is 60,000/s, the arithmetic minimum is 15 shards. With 2x growth and 50% post-failure utilization, plan roughly 60,000 * 2 / (4,000 * 0.5) = 60 shard-equivalents. Precreating 60 physical databases may still be wasteful; use enough logical partitions to redistribute later, while beginning with fewer operational units.

    Queue and replay calculations¶

    Queues move work in time; they do not remove it. If producers emit 50,000 events/s and consumers process 42,000/s, backlog grows by 8,000 events/s. A 20 million-event retention cushion fills in 20M / 8,000 = 2,500 seconds, about 42 minutes. Catching up a one-hour outage that accumulated 180 million events requires spare capacity. At 70,000/s after recovery, net drain is 20,000/s and catch-up takes 2.5 hours while live traffic continues.

    Size retention in bytes as well as count. At 1.8 KB/event and 50,000/s, one day is 7.8 TB before replication. Seven days at 3x is about 163 TB. Replays also hit databases, caches, and external providers; throttle them against a separate recovery budget.

    sequenceDiagram
    autonumber
    participant P as Producers
    participant Q as Durable log
    participant C as Consumers
    participant D as Downstream store
    P->>Q: 50K events/s
    Q->>C: 42K events/s during degradation
    Note over Q: backlog +8K/s
    C->>D: idempotent writes
    Note over C,D: recovery limit protects live traffic
    Q->>C: 70K events/s after recovery
    Note over Q: backlog drains at 20K/s

    Failure-domain arithmetic¶

    Capacity planning should survive the failure named in the SLO. With four equal zones and one-zone tolerance, surviving zones absorb 4/3 = 1.33x their normal load. To remain at or below 70% after failure, normal utilization must be no more than 70% / 1.33 = 52.5%. Autoscaling is additional protection, not a substitute when failure is sudden.

    For five mandatory dependencies with independent success events, 0.9995^5 = 99.75% estimates the probability that all are available. That misses a 99.9% endpoint goal. Independence is a modeling assumption, not a conservative bound: perfectly overlapping outages would produce 99.95% joint availability, while disjoint outages consume more total downtime. Shared failures also defeat redundancy. Measure joint failures for the actual request path, then remove unnecessary synchronous dependencies or make effects asynchronous.

    Retries need an amplification model. At 30,000 requests/s, if 10% time out and each gets two retries, offered load becomes 36,000 requests/s. If the timeouts are caused by saturation, those retries deepen it. A 2% global retry budget caps additional attempts at 600/s and forces callers to fail or degrade predictably.

    Sensitivity, rollout, and calibration¶

    Present a base case plus the two variables most likely to change the design. For messaging, attachment rate from 1% to 8% changes annual object storage from about 3 PB to 24 PB; peak factor from 3x to 12x changes write capacity fourfold. Message metadata size changing from 800 to 1,000 bytes probably does not reverse a storage choice. Spend interview time on the first two.

    Turn estimates into rollout gates:

    1. Instrument per-tenant and per-key rates before repartitioning.
    2. Load-test realistic payload distributions, hot keys, retries, and one-zone loss rather than uniform average requests.
    3. Launch at 1% while comparing estimated and observed CPU milliseconds, IOPS, bytes, and latency.
    4. Refit the model and scale to 10%, 50%, and 100% only while post-failure headroom remains above the target.
    5. Predefine rollback at queue age, error budget burn, or saturation thresholds.

    Interview traps and level signals¶

    • False precision: 9,287 QPS from invented inputs is weaker than 9-10K peak QPS with sensitivity to a 4-10x peak factor.
    • Ignoring amplification: one upload may produce replicas, indexes, thumbnails, moderation jobs, and fan-out events.
    • Using vendor limits as constants: capacity depends on request shape, consistency, hardware, and tail latency. State a benchmark assumption.
    • Undated benchmarks: a result without hardware, software, workload, pass criteria, and measurement date cannot safely size a current fleet.
    • Forgetting degraded mode: a design at 80% normal utilization often cannot survive a zone failure.
    • Confusing storage and working set: ten years of data may be cheap in object storage while only one day belongs in memory.
    • Assuming autoscaling is instant: queue fill time can be milliseconds while instances need minutes to become ready.

    An L5 candidate computes a defensible peak, storage, bandwidth, concurrency, and a clear bottleneck, then maps each number to a design choice. An L6 candidate models skew and correlated failure, distinguishes logical from physical amplification, quantifies cost and recovery, and defines the telemetry and rollout gates that retire assumptions. L6 judgment also identifies when not to optimize: if metadata needs 300 TB but attachments need 12 PB, debating a 10% metadata encoding reduction is not the priority.

    Check your reasoning¶

    A dependency takes 100 ms of connection occupancy per request. You have 200 connections and receive a sustained 3,000 requests/s. Would a queue of 10,000 requests fix the capacity gap?

    Work the bound before choosing a fix

    The optimistic service ceiling is 200 / 0.1 s = 2,000 requests/s. With 3,000/s arriving, a previously empty 10,000-request queue fills in 10,000 / (3,000 - 2,000) = 10 seconds. The queue postpones rejection while increasing waiting time. It does not repair sustained overload. Admit at a safe rate, reduce occupancy, or increase capacity after testing the dependency. Real variability and headroom lower the safe ceiling below this arithmetic limit.
