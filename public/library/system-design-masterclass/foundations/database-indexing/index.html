    Database Indexing¶

    Engineering extension: From SQL to physical work traces cardinality estimation, joins, spills, and maintenance load; performance science explains how to measure the resulting bottleneck without misleading percentile claims.

    An index is a second physical representation of selected table values. It trades storage and write work for a cheaper way to locate rows. Good indexing starts with a concrete query shape, expected cardinality, and measured plan; it does not start with indexing every filterable column.

    This chapter uses PostgreSQL 17-style examples, but the page, fanout, selectivity, and write-amplification reasoning applies broadly. For transaction, WAL, replica, and schema context, see Relational Databases. Search-engine inverted indexes are a different projection described in Search and Indexing.

    Heap storage versus clustered storage¶

    In a heap-organized table, rows live in data pages without being physically ordered by a secondary index. A B+ tree leaf entry normally contains the indexed key plus a row locator. Finding one row is therefore two access paths: traverse the index, then fetch the heap page. PostgreSQL tables are heap-organized; an index scan can touch heap pages in scattered order.

    A clustered table stores rows in primary-key order, or stores full rows in the primary B+ tree leaves. Range scans gain locality, but every secondary index must identify the primary key and primary-key changes become expensive. Some engines cluster by primary key continuously. PostgreSQL's CLUSTER rewrites a heap once in index order; later writes do not preserve that order automatically.

    Layout Leaf points to Strength Cost
    heap plus secondary index physical or logical row locator stable row placement; multiple peers extra heap lookup; random I/O
    clustered primary index full row or clustered key primary-key ranges are local secondary leaves are wider; page splits move layout
    index-only access projected values in leaf avoids many heap reads wider index; visibility checks and writes remain

    PostgreSQL's MVCC can leave multiple tuple versions in a heap page. An index entry may lead to a dead or invisible tuple until vacuum reclaims it. An index-only scan can avoid heap access only when all required columns are in the index and the visibility map proves the heap page is visible to all relevant snapshots. Heap Fetches: 0 in EXPLAIN (ANALYZE) is evidence; the words Index Only Scan alone are not.

    flowchart LR
    Q[Predicate] --> R[Root page]
    R --> I[Internal page]
    I --> L[Leaf page with key and row locator]
    L --> H[Heap page]
    H --> T[Visible tuple version]

    B+ tree pages, fanout, and height¶

    A B+ tree stores separator keys and child pointers in root and internal pages; leaves store sorted keys and row locators and are linked for ordered traversal. All leaves are at the same depth. A lookup does one binary search per visited page, while the page cache and storage device determine whether that visit is memory-speed or an I/O.

    Suppose an 8 KiB internal page has 256 bytes of headers and safety space. If an average separator plus child pointer consumes 24 bytes, the rough fanout is:

    fanout = floor((8192 - 256) / 24) = 330

    Real pages reserve free space, keys vary, and prefix compression differs by engine, so use a conservative fanout of 250. Here, a page level includes the root and leaf, while a branch step is one parent-to-child edge. A three-page-level tree (root, one internal level, leaves) has two branch steps and addresses about 250^2 = 62,500 leaf pages. If each leaf averages 200 entries, that is about 62,500 * 200 = 12.5 million rows. A four-page-level tree (root, two internal levels, leaves) has three branch steps and covers about 250^3 * 200 = 3.125 billion rows. Point lookup visits three or four index pages respectively, plus a heap page when the index does not cover the query. This is why B+ tree lookup height grows slowly. The bigger operational cost is often random heap access, cache misses, or returning many rows, not a handful of page-local comparisons.

    Wide keys reduce fanout and cache density. Replacing a 48-byte text key with a compact surrogate may remove a level at large scale, but a surrogate is not automatically useful: the query may still need a separate wide-key index and a heap lookup. Calculate complete access paths rather than optimizing one tree in isolation.

    Equality and range mechanics¶

    For customer_id = 42, the tree descends to the first matching leaf entry and reads adjacent entries until the value changes. For created_at >= T1 AND created_at < T2, it descends once to T1, then follows leaf pages sequentially until T2. Sorting is free only when the required order matches the index ordering, including direction and tie-breakers.

    CREATE INDEX order_customer_history
ON customer_order (customer_id, created_at DESC, id DESC);

SELECT id, total_cents, created_at
FROM customer_order
WHERE customer_id = 42
  AND (created_at, id) < (TIMESTAMPTZ '2026-09-01 10:00:00+00', 9000)
ORDER BY created_at DESC, id DESC
LIMIT 50;

    The equality on customer_id selects one contiguous section. The tuple range starts at the cursor, and the ordering matches the index. This supports bounded keyset pagination. An index on (created_at, customer_id) would mix every customer in the time range and filter afterward.

    Composite indexes and the left prefix¶

    For a B+ tree on (a, b, c), rows are ordered by a, then by b within equal a, then by c. Efficient navigation generally uses a contiguous left prefix:

    Predicate Useful navigation on (tenant_id, status, created_at)
    tenant_id = ? yes, first key
    tenant_id = ? AND status = ? yes, first two keys
    tenant_id = ? AND status = ? AND created_at >= ? yes, equality prefix then range
    tenant_id = ? AND created_at >= ? only tenant_id bounds navigation; status is a gap
    status = ? usually cannot seek by the leading key

    Place equality columns before the first range or ordering column when that matches the workload. After a range begins, later columns usually cannot narrow the contiguous leaf interval, although they may be checked in the index and avoid heap work. "Most selective first" is not a universal composite-index rule. Leading equality, required ordering, reusable query prefixes, and range position matter together.

    Two superficially similar queries can need different indexes:

    -- Operations queue: equality, equality, then oldest first.
CREATE INDEX job_claim_path
ON job (region, state, available_at, id)
WHERE state IN ('READY', 'RETRY');

-- Tenant audit history: equality, then newest range.
CREATE INDEX audit_tenant_time
ON audit_event (tenant_id, occurred_at DESC, event_id DESC);

    The queue example assumes one fixed region and one fixed state in each scan. If the query instead asks for state IN ('READY', 'RETRY') ORDER BY available_at, the index contains separate state-ordered runs, not one global time order. The planner may need a sort or merged scans. A partial index on (region, available_at, id) with the same active-state predicate is an alternative when both states share one queue and the query predicate permits that index.

    Do not append every output column to the key portion. Key columns determine ordering and can enlarge internal separators as well as leaves; PostgreSQL may truncate unnecessary trailing key columns from upper levels. Payload columns that only support index-only reads belong in an INCLUDE clause where supported.

    Selectivity, cardinality, and correlation¶

    Selectivity is the fraction of rows expected to pass a predicate. If a table has 100 million rows and state = 'READY' selects 18 million, an index may cause millions of row locators and scattered heap reads; a sequential scan can be cheaper. If tenant_id = 71 AND state = 'READY' selects 900 rows, a composite index is likely valuable.

    The break-even point is not a fixed percentage. It depends on row width, cached pages, physical correlation, storage latency, parallelism, and whether the index covers the query. A rough cold-I/O comparison illustrates the decision:

    table: 80 GiB / 8 KiB = 10,485,760 heap pages
sequential scan at 1.5 GiB/s: about 53 seconds before CPU
index result: 120,000 rows on about 95,000 scattered heap pages
random reads at effective 25,000 IOPS: about 3.8 seconds

    At 5 million matching rows scattered over 3.8 million pages, the same estimate is 152 seconds, so the table scan wins. If matching rows are physically correlated and occupy 70,000 adjacent pages, the index range can win again. Estimates must model pages, not just row percentages.

    Planners estimate cardinality from sampled statistics: distinct counts, null fraction, common values, histograms, and sometimes cross-column dependency or correlation statistics. Independent-column assumptions fail for facts such as country = 'IN' and currency = 'INR'. Create extended statistics where supported, increase statistics targets for skewed columns, and refresh statistics after material distribution changes. An index cannot repair a cardinality estimate the planner does not understand.

    Specialized index concepts¶

    Covering indexes¶

    A covering index contains every column needed by a query. In PostgreSQL, INCLUDE carries non-key values without making them part of ordering:

    CREATE INDEX invoice_account_due
ON invoice (account_id, due_at, id)
INCLUDE (amount_cents, currency, status);

    Coverage can remove heap reads for stable pages, but it widens leaves, lowers fanout, consumes cache, and amplifies updates. Included columns still have maintenance cost. Cover a frequent, latency-sensitive query after measuring heap fetches; do not cover SELECT *.

    Partial indexes¶

    A partial index stores only rows satisfying a predicate:

    CREATE INDEX payment_unsettled_retry
ON payment_attempt (next_retry_at, id)
WHERE settled_at IS NULL AND terminal = false;

    It is smaller and avoids indexing rows outside the active set. Moving a row out of that set still creates cleanup work for its old index entry. The planner must be able to prove that the query predicate implies the index predicate. Parameterized or logically equivalent but opaque expressions can prevent use. Partial unique indexes can enforce scoped invariants, such as one active lease per resource.

    Hash indexes¶

    Hash indexes map equality keys to buckets and do not support ordering, prefix, or range scans. They can suit equality-only access, but a B+ tree also handles equality and is usually more versatile. Choose hash only from measured engine-specific behavior, collision handling, durability, and operational support, not from an assumed O(1) slogan.

    Bitmap access¶

    A bitmap represents candidate row locations compactly and combines predicates with bitwise AND or OR. PostgreSQL commonly builds transient bitmaps from ordinary indexes, then visits heap pages in physical order:

    Bitmap Index Scan on color_idx ----+
                                    +--> BitmapAnd --> Bitmap Heap Scan
Bitmap Index Scan on region_idx ---+

    This can beat independent random row fetches for medium-selectivity predicates. Some analytical systems maintain persistent bitmap indexes, which compress low-cardinality values well but can be costly under high-concurrency updates. Distinguish a bitmap execution plan from a persisted bitmap index.

    GIN and GiST¶

    GIN is an inverted mapping from contained keys to rows. It fits arrays, document keys, and full-text terms where one row emits many index entries. Reads can be excellent; writes and pending-list cleanup can be expensive.

    GiST is a framework for hierarchical, possibly overlapping predicates. Operator classes define concepts such as bounding boxes and distance. It supports spatial, range-overlap, and nearest-neighbor access where ordinary total ordering is insufficient. Because internal bounds may be lossy, the engine can return candidates and recheck the original predicate.

    The operator and operator class must match. "Create a GIN/GiST index" is incomplete without naming the query operators, data distribution, recheck behavior, and update rate.

    Write amplification and page splits¶

    Every secondary index turns one logical row change into more physical work: WAL records, dirty index pages, cache pressure, replica bytes, backup growth, and vacuum or cleanup. If 12,000 updates/s touch a table and four indexes, a lower-bound logical count is 12,000 * (1 table + 4 indexes) = 60,000 structure mutations/s before WAL, full-page images, replication, and page rewrites.

    An insert into a full leaf page splits it, allocates a sibling, moves entries, and inserts a separator into the parent. A parent can split recursively. Random keys spread insert pressure but fragment many pages; monotonically increasing keys concentrate writes at the right edge but preserve locality. Fill factor reserves space to reduce splits for update-heavy or randomly inserted indexes at the cost of a larger tree.

    In PostgreSQL, an update that changes no indexed column may use a heap-only tuple update when the page has room, avoiding new entries in every index. Adding a frequently changing column to an index disables that advantage for those updates. Dead entries persist until vacuum can remove them; long transactions delay cleanup and can turn a logically small table into a large physical one.

    Read plans as evidence¶

    Use a controlled loop rather than intuition:

    1. Capture the exact SQL, bind-value distribution, result count, frequency, and latency objective.
    2. Run EXPLAIN (ANALYZE, BUFFERS, WAL, SETTINGS, FORMAT TEXT) in a safe environment with representative data and parameters.
    3. Read from the leaves upward: actual rows, loops, time, buffer hits/reads, sorts, heap fetches, and rows removed by filters.
    4. Compare estimated rows with actual rows per execution. Multiply actual rows and node time by loops only to estimate cumulative work; multiplying only the actual side falsely reports a cardinality error. A large per-execution error points to stale statistics, correlation, or parameter sensitivity before a missing index.
    5. Create the smallest candidate index in a test environment, refresh statistics, rerun warm and cold-enough trials, and compare total write/storage cost.
    6. Test worst credible tenants, common values, empty results, large ranges, and prepared-statement behavior. One fast literal is not a workload.
    EXPLAIN (ANALYZE, BUFFERS, WAL, SETTINGS)
SELECT id, amount_cents, created_at
FROM payment_attempt
WHERE merchant_id = 771
  AND state = 'FAILED'
  AND created_at >= TIMESTAMPTZ '2026-09-01 00:00:00+00'
ORDER BY created_at DESC, id DESC
LIMIT 100;

    Key evidence:

    Signal Interpretation
    sequential scan with many rows removed candidate access-path problem, unless predicate is broad
    index scan returning far more rows than output weak bounds or filtering after the scan
    estimate 50, actual 500,000 statistics/distribution problem that can distort joins and memory
    large shared reads, few hits working set is not resident; test realistic cache state
    sort spills to temporary blocks ordering/index or memory decision, not just scan time
    index-only scan with many heap fetches visibility churn limits actual coverage benefit
    fast node repeated many loops cumulative nested-loop cost may dominate

    EXPLAIN ANALYZE executes the statement. Use an isolated writable test database for mutations; a read-only replica is suitable only for supported reads. A rollback does not undo sequence increments or external trigger effects. Never run an unbounded expensive plan on production merely to inspect it; plain EXPLAIN does not execute. PostgreSQL 17, Using EXPLAIN documents per-loop averages and execution side effects (accessed 2026-09-08).

    Online index lifecycle¶

    An index is an operated object, not a one-time DDL statement.

    stateDiagram-v2
    [*] --> Proposed
    Proposed --> Building: workload evidence
    Building --> Validating: online build complete
    Validating --> Serving: plan and latency gates pass
    Validating --> Dropped: regression or invalid build
    Serving --> Rebuilding: bloat or definition change
    Rebuilding --> Serving: replacement validated
    Serving --> Dropped: observation window proves unused

    A PostgreSQL-style rollout is:

    CREATE INDEX CONCURRENTLY payment_merchant_failed_v2
ON payment_attempt (merchant_id, created_at DESC, id DESC)
INCLUDE (amount_cents)
WHERE state = 'FAILED';

ANALYZE payment_attempt;

SELECT indexrelid::regclass, indisvalid, indisready
FROM pg_index
WHERE indexrelid = 'payment_merchant_failed_v2'::regclass;

    Concurrent creation avoids a long write-blocking table lock, but it takes longer, performs extra scans, consumes I/O, waits on old transactions, and can leave an invalid index after failure. Verify validity, build progress, replica lag, disk reserve, WAL rate, and query plans. Throttle or cancel when foreground SLOs or recovery headroom are threatened.

    Before removal, identify overlapping definitions and observe query plans over a full business cycle. Usage counters reset and prepared plans can hide dependencies, so zero scans is evidence, not proof. Remove with the engine's online form where available:

    DROP INDEX CONCURRENTLY payment_merchant_failed_v1;

    Changing a definition is normally create-new, validate, shift, then drop-old. Preserve enough disk for both indexes and build workspace. Rehearse cancellation and cleanup; schema migration tools need non-transactional handling for concurrent index commands.

    Design checklist¶

    • Name the query, predicates, order, limit, selected columns, and expected rows.
    • Draw the complete index-to-heap path and estimate pages, not only Big-O.
    • Use equality prefixes before the first range when the access pattern supports it.
    • Check selectivity, skew, correlation, and estimate error with representative binds.
    • Treat coverage and partial predicates as write/storage tradeoffs.
    • Match specialized structures to operators, not data type names alone.
    • Quantify table, WAL, replica, vacuum, and page-split amplification.
    • Validate with actual rows, loops, buffers, heap fetches, spills, and latency.
    • Build, verify, observe, replace, and drop through an online lifecycle.

    Check the plan you expect¶

    A tenant history index is (tenant_id, status, created_at DESC). Your query fixes tenant_id, filters no status, and requests the newest 50 rows across every status. Does this index inherently provide the requested order?

    Trace the sorted runs

    No. Within that tenant, rows are grouped by status before time. The first 50 entries can belong to one status rather than the newest 50 across all statuses. A (tenant_id, created_at DESC, id DESC) index fits this query and supplies a deterministic tie-breaker. The original index may still help other queries, but retaining both has a write and storage cost. Verify the actual plan and representative tenants before adding it.

    Vendor scope (PostgreSQL 17, accessed 2026-09-19): The left-prefix discussion follows multicolumn indexes. Coverage still requires the visibility-map condition, and online DDL follows the restrictions in CREATE INDEX. Optimizer features differ across versions; this is not a promise that every later planner uses the same access path.
