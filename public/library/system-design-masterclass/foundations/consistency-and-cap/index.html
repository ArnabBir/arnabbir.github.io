    Consistency, Consensus, and CAP¶

    Engineering extension: Distributed theory, clocks, and authority adds explicit fault models, FLP scope, logical-clock counterexamples, durable consensus assumptions, and a fenced-worker fixture.

    Consistency is an operation-specific promise. Ask "consistent for which read after which write, under what failure?" before selecting a mechanism.

    Useful guarantees¶

    Guarantee Example Typical mechanism
    read-your-writes profile edit is immediately visible to editor sticky leader read or version token
    monotonic reads order status never moves backward session watermark
    causal ordering reply does not precede parent causal metadata or partition ordering
    linearizability one username has one owner leader/consensus conditional write
    serializability inventory and reservation obey transaction rules serializable transaction
    eventual convergence like count becomes accurate idempotent events plus reconciliation

    Linearizability concerns one operation appearing atomic in real time. Serializability concerns transaction equivalence to a serial order; without strict serializability it need not honor wall-clock order.

    CAP without slogans¶

    CAP's consistency property is linearizability, not every useful consistency guarantee. Its availability property requires every request received by a non-failing node to complete, not merely a high uptime percentage. During a partition, a replicated read/write object cannot guarantee both properties. Rejecting a request or waiting indefinitely sacrifices this availability. "CA" is not a meaningful partition-time choice for such an object.

    The diagram below is an application-invariant decision aid, not a proof that every invariant requires coordination. Mergeable operations and preallocated escrow rights can preserve some invariants without global linearizability. See Gilbert and Lynch (2002), formal model and impossibility result.

    flowchart TD
    P[Network partition] --> Q{Operation requires coordination?}
    Q -->|yes, preserve invariant| CP[Reject or wait]
    Q -->|accept availability| AP[Record concurrent state]
    AP --> M[Detect and merge conflict]
    Q -->|no| L[Serve partition-local operation]

    A checkout inventory decrement against a single global stock owner usually rejects on the minority side to preserve its linearizable conditional-update contract. A cart add may remain available if concurrent additions can merge. A single product can therefore use different guarantees per operation; stock sold from preallocated regional rights is a different contract, discussed below.

    Quorums are conditional¶

    With replication factor N, writes to W, and reads from R, W + R > N creates overlap only under assumptions about replica membership, clocks/versioning, sloppy quorums, and repair. It does not automatically provide linearizability.

    Design Benefit Cost/risk
    leader writes simple total order leader latency and failover pause
    quorum reads/writes tunable availability conflict resolution and tail latency
    consensus group durable ordered decisions cross-node coordination
    CRDT deterministic merge only fits mergeable semantics
    escrow/leases local operations within allocated rights rebalancing and expiry complexity

    Concrete example: unique usernames¶

    Invariant: at most one account owns a normalized username. Route a username to one consensus-backed partition and perform put-if-absent. During loss of quorum, reject claims rather than create two owners. Profile reads can still come from stale replicas if the UI tolerates it.

    sequenceDiagram
    autonumber
    participant A as Region A
    participant L as Username leader
    participant B as Region B
    A->>L: claim("sam", account1)
    L-->>A: committed at version 42
    B-xL: partitioned
    B->>B: reject claim because uniqueness cannot be proven

    Failure semantics and repair¶

    • A timeout is an unknown outcome, not proof of failure; retry with the same command ID.
    • Leader failover can expose stale followers unless promotion checks committed logs.
    • Asynchronous replication has a measurable recovery point objective: acknowledged writes may be lost after region loss.
    • Last-write-wins can discard valid concurrent updates and depends on clocks; use only when that policy matches the domain.
    • Anti-entropy repairs replicas but does not repair external side effects. Reconcile payments, emails, and indexes separately.

    Choose the weakest guarantee that preserves each invariant, then offer session-level guarantees where users notice anomalies. State the unavailable path explicitly instead of hiding it behind "eventual consistency."

    Define the history you need¶

    Consistency models constrain observable histories. Begin with an operation and an invariant, not a database label. For a username claim, clients need a single real-time order for conditional writes. For a user's profile, read-your-writes may be enough. For a collaborative counter, convergence may be enough if increments commute.

    These guarantees are related but not interchangeable:

    • Linearizability: each operation appears to occur atomically between invocation and response, respecting real-time precedence. It composes across individual objects.
    • Sequential consistency: operations fit one total order that preserves each client's program order, but the order need not respect wall-clock precedence between clients.
    • Serializability: committed transactions are equivalent to some serial execution. Plain serializability may reorder transactions in a way that violates real-time expectations.
    • Strict serializability: combines serializability with real-time order and is the strongest common transaction contract.
    • Snapshot isolation: transactions read a stable snapshot and conflicting writes are detected, but write skew can violate multi-row invariants.

    Availability is also scoped. A system that serves stale reads during a partition but rejects writes is available for one operation and unavailable for another. State the behavior per API and failure domain.

    flowchart TD
    OP[Operation] --> INV{Cross-request invariant?}
    INV -->|No, mergeable| EV[Eventual or causal merge]
    INV -->|Yes| OBJ{Single object conditional?}
    OBJ -->|Yes| LIN[Linearizable conditional operation]
    OBJ -->|No| TX[Serializable transaction or redesigned boundary]
    EV --> UX[Add session guarantees where visible]
    LIN --> FAIL[Reject when quorum cannot prove safety]
    TX --> FAIL

    This second decision tree is also a conservative coordination aid, not a necessity theorem: cross-request numeric invariants may admit escrow, and some causal dependencies span partitions. A serializable transaction does not inherently require a distributed quorum if all data is local. Check the actual engine and fault model rather than treating every edge as a universal implication.

    Quorum overlap does not eliminate stale reads¶

    Take N=3, W=2, R=2, with replicas A, B, and C. A write of value v2 reaches A and B, so it is acknowledged. A later read from B and C sees v2 and old v1; with a correct comparable version, the coordinator returns v2. The inequality W + R > N ensures at least one overlap between successful sets.

    Now inspect the assumptions. If acknowledgments occur before durable persistence, A and B can both restart and lose v2. If versions use unsynchronized wall clocks, v1 may carry a later timestamp. If the read coordinator returns the first response rather than reconciling all R, overlap is irrelevant. If membership changed between operations without joint coordination, the sets may not belong to the same replica universe. Quorums improve overlap; they do not by themselves establish one-copy linearizable semantics.

    Even a normal quorum can return stale data with concurrent writes. Client X writes v2 to A and B while client Y's read contacts B and C before B receives v2; it returns v1. This is allowed because the write had not completed before the read began. If the write completed first, a properly implemented strict quorum read should encounter v2, but sloppy membership or failed durability can break that assumption.

    A sharper counterexample is a partial write present only on A. Read 1 from A+B returns v2, then Read 2 from B+C returns v1 after Read 1 completed. Both use R=2, but the completed reads regress. A linearizable register protocol must prevent that new-old inversion, for example with protocol-defined read write-back; asynchronous repair alone is insufficient. This does not contradict etcd's strict-serializable KV contract, which is stronger than bare quorum counting (accessed 2026-09-08).

    sequenceDiagram
    autonumber
    participant X as Writer
    participant A as Replica A
    participant B as Replica B
    participant C as Replica C
    participant Y as Reader
    X->>A: put v2, version 8
    X->>B: put v2, version 8
    A-->>X: durable ack
    B-->>X: durable ack (W=2)
    Y->>B: get
    Y->>C: get
    B-->>Y: v2, version 8
    C-->>Y: v1, version 7
    Y-->>Y: reconcile and return v2
    Y->>C: async repair to v2

    Sloppy quorum and hinted handoff¶

    During a partition, suppose A and B are the natural replicas for key K but unavailable from the coordinator. A sloppy quorum may store v2 on fallback nodes D and E and acknowledge W=2. A read routed through another coordinator may query natural replicas A, B, and C after A recovers but before hinted handoff. It can collect R=2 old responses and return v1, even though W + R > N. The write and read quorums overlapped numerically but not in node membership.

    Sloppy quorum improves write availability and is reasonable where temporary stale reads and conflict reconciliation are accepted. It is not appropriate evidence for strict uniqueness. Hints need durable storage, expiry policy, backpressure, and observability. If D is down when A returns, handoff can be delayed further. If concurrent writes occur on both sides, version vectors or another causal version can preserve siblings for domain resolution; last-write-wins silently discards one.

    sequenceDiagram
    autonumber
    participant C1 as Coordinator 1
    participant A as Natural A
    participant B as Natural B
    participant D as Fallback D
    participant E as Fallback E
    participant C2 as Coordinator 2
    Note over C1,B: A and B unreachable
    C1->>D: store v2 as hint for A
    C1->>E: store v2 as hint for B
    D-->>C1: ack
    E-->>C1: ack, write accepted
    Note over A,B: natural replicas later reachable
    C2->>A: read before hinted handoff
    C2->>B: read before hinted handoff
    A-->>C2: v1
    B-->>C2: v1
    Note over C2: stale despite nominal W=2, R=2

    Read repair and anti-entropy¶

    When a quorum read sees versions 8, 8, and 7, it can return version 8 and asynchronously write it to the stale replica. Blocking repair waits for repair before responding; asynchronous repair improves latency but leaves a wider stale window. Read repair only touches keys that are read. Cold keys need background anti-entropy, often Merkle-tree comparison by key range followed by transfer of differing records.

    Repair must not overwrite concurrent siblings when the domain requires preserving them. A scalar total order, even one constructed from logical timestamps and writer IDs, does not distinguish concurrency from causality. In multi-writer systems that must retain concurrent updates, use causal metadata and a merge policy. Tombstones must remain until every relevant replica has observed deletion; removing a tombstone too early can resurrect an old value during repair. Set tombstone grace from maximum outage and repair time, then alert when a replica exceeds it.

    Leader election and committed logs¶

    Consensus protocols such as Raft establish one ordered log per group while a quorum is connected. Terms or ballots distinguish leadership epochs. A simplified election proceeds:

    1. A follower misses heartbeats, increments its term, votes for itself, and requests votes.
    2. A voter grants at most one vote per term and rejects a candidate whose log is less up to date.
    3. A majority elects the candidate. Two leaders cannot each hold a majority in the same term because majorities overlap.
    4. The leader appends a command and sends it to followers.
    5. Once the entry is stored on a majority under the protocol's commit rules, it becomes committed and is applied in order.

    In Raft, the leader advances commitment by counting replicas for an entry from its current term. That commitment also commits preceding log entries; it must not declare an old-term entry committed solely because that old entry now appears on a majority. The distinction prevents unsafe failover histories. See the Raft paper, section 5.4.2.

    An acknowledgment should mean the entry is committed, not merely present on the leader. Suppose leader A appends entry 12 locally and responds before replication. A fails; B, without entry 12, wins an election and commits a different entry at that index. The client observed a write that vanished. Majority commit and election log checks prevent this history.

    sequenceDiagram
    autonumber
    participant C as Client
    participant L as Leader term 7
    participant F1 as Follower 1
    participant F2 as Follower 2
    C->>L: conditional claim command K
    L->>L: durably append index 42, term 7
    L->>F1: AppendEntries(42, term 7)
    L->>F2: AppendEntries(42, term 7)
    F1-->>L: durable ack
    Note over L,F1: majority has entry 42
    L->>L: advance commit index and apply
    L-->>C: committed result
    L-->>F1: commit index 42
    L-->>F2: retry replication

    Leader leases can make reads cheaper, but consensus safety and read freshness are separate. A follower read may lag. A leader read needs proof it still leads, commonly a quorum round or a valid bounded lease. On failover, an old leader may continue accepting requests while partitioned; followers reject its stale term, and it must not acknowledge without quorum. Clients retry commands with IDs because failover timeouts leave outcomes unknown.

    Committed log entries survive minority failure, not every disaster. If a three-node group places all nodes in one region, region loss defeats the durability claim. Placement determines the failure model. Cross-region quorums improve disaster tolerance but add wide-area latency to every coordinated write.

    Transaction isolation anomalies¶

    Single-key linearizability does not automatically preserve a multi-key invariant. Consider two doctors, Alice and Bob, each on call. The rule is that at least one remains on call.

    Under snapshot isolation:

    1. Transaction T1 reads Alice=on and Bob=on.
    2. Transaction T2 reads the same snapshot.
    3. T1 sets Alice=off; T2 sets Bob=off.
    4. They write different rows, so no write-write conflict occurs.
    5. Both commit, leaving nobody on call.

    This is write skew. Serializable isolation, explicit locking of a shared invariant row, or encoding the rule into one conditional object prevents it when every writer follows that protocol. With explicit locking, acquire the lock before the decision reads and use a snapshot that includes the preceding holder's committed changes; a pre-lock snapshot can remain stale. PostgreSQL 17, transaction isolation, sections 13.2.2-13.2.3 documents snapshot isolation and whole-transaction retries (accessed 2026-09-08).

    Other anomalies matter:

    Isolation weakness Trace Risk
    dirty read T2 reads T1's uncommitted value; T1 aborts action based on state that never existed
    non-repeatable read T1 reads row twice; T2 changes it between reads inconsistent decision inside transaction
    phantom T1 repeats a predicate query and sees new matching rows broken range/count invariant
    lost update T1 and T2 read 10, both write 11 one increment disappears
    write skew transactions update different rows from same snapshot cross-row invariant fails 
    sequenceDiagram
    autonumber
    participant T1 as Txn 1
    participant DB as Snapshot-isolated DB
    participant T2 as Txn 2
    T1->>DB: read Alice=on, Bob=on
    T2->>DB: read Alice=on, Bob=on
    T1->>DB: write Alice=off
    T2->>DB: write Bob=off
    T1->>DB: commit (no row conflict)
    T2->>DB: commit (no row conflict)
    Note over DB: invariant violated: nobody on call

    Do not answer "the database is ACID" without naming isolation, retry behavior, and invariant encoding. Serializable databases may abort transactions to prevent anomalies; applications must retry the entire transaction with a stable command ID and avoid repeating non-transactional side effects.

    Session tokens make weak replication usable¶

    Users notice when their own update disappears or an order status moves backward. Session guarantees can hide those anomalies without making every read globally linearizable.

    After a write, return a token containing the shard, committed version or log position, topology epoch, and integrity protection. On a later read, the router chooses a replica whose applied position is at least the token. If none has caught up before the deadline, it can wait, route to the leader, or return a retryable response. It must not silently return an older version when read-your-writes is promised.

    For monotonic reads, the client carries the greatest observed watermark and never accepts a lower one. For causal consistency across shards, a single scalar may be insufficient; dependency vectors or a causal service track that a reply depends on a parent write. Keep tokens opaque and signed so callers cannot demand impossible positions or cross tenant boundaries.

    sequenceDiagram
    autonumber
    participant C as Client
    participant W as Write leader
    participant R as Read router
    participant F as Follower
    C->>W: update profile
    W-->>C: success + token(shard 3, pos 918, epoch 12)
    C->>R: get profile + token
    R->>F: applied position?
    F-->>R: 912
    R->>R: wait, choose leader, or retry
    F-->>R: advances to 918
    R->>F: read with minimum position 918
    F-->>R: value from snapshot at or beyond 918
    R-->>C: value at position >= 918

    Tokens need lifecycle rules. A resharding epoch maps old positions to the new ownership or forces a leader read. A token from deleted history cannot be honored forever; document expiration. Browser multi-tab and multi-device sessions may not share tokens, so decide whether the guarantee is per request chain, account, device, or global user experience.

    Leases, fencing, and clock hazards¶

    A lease grants temporary authority, but expiry does not stop the old holder. Consider worker A holding a 30-second lease. A pauses for 40 seconds during garbage collection. The lease service expires A and grants worker B a new lease. A resumes and writes to storage. Without fencing, both act as owner.

    Issue a monotonically increasing fencing token with every lease: A has token 41 and B has 42. The protected storage atomically checks and records the highest token with each mutation. It rejects A after observing 42, but may still accept 41 before 42 reaches it. If transfer must immediately revoke A, install 42 at the sink before reporting transfer complete; see the authority handoff protocol. A lease library alone cannot fence an external system.

    Wall clocks create additional hazards. Clock steps from NTP correction, VM suspension, leap handling, or drift can make a client believe a lease remains valid after the authority expired it. Use the lease service's ordered epochs and monotonic elapsed time for local deadlines, allow drift margins, and keep lease duration much larger than expected timing uncertainty. Do not use client timestamps to order money movement or resolve concurrent writes unless clock assumptions and error bounds are part of the protocol.

    sequenceDiagram
    autonumber
    participant A as Worker A token 41
    participant LS as Lease service
    participant B as Worker B token 42
    participant S as Protected store
    A->>LS: acquire lease
    LS-->>A: token 41
    Note over A: long pause beyond expiry
    B->>LS: acquire expired lease
    LS-->>B: token 42
    B->>S: write with token 42
    S-->>B: accepted, highest=42
    A->>S: late write with token 41
    S-->>A: rejected as fenced

    Failure choices by operation¶

    For a network partition, explicitly walk both sides:

    • Username claim: only the side with consensus quorum may accept. The minority returns unavailable because two accepted owners cannot be merged.
    • Shopping-cart add: both sides may accept an operation ID and merge a grow-only set or observed-remove structure, subject to product deletion semantics.
    • Inventory decrement: coordinate against one owner or preallocate escrow rights. If region A has 60 rights and region B has 40, each may sell locally within allocation; transferring rights requires coordination.
    • Profile read: a stale replica may respond, but a session token can require read-your-writes for the editor.
    • Payment notification: record idempotent intent locally, but reconcile the external provider because replica repair cannot undo or rediscover every side effect safely.

    Last-write-wins is a business policy, not a neutral repair algorithm. Two users concurrently changing a delivery address can lose valid work, and a fast clock can dominate. Use LWW only where replacing one register is acceptable; preserve siblings, field-level merges, or user conflict resolution otherwise.

    Migrate from eventual state to consensus safely¶

    Suppose an eventually consistent username store has accumulated duplicates and must move to consensus-backed ownership. A flag-day switch can strand writes or canonize conflicts arbitrarily. Use a staged migration:

    1. Define normalization precisely, including case folding and Unicode policy, and create a stable owner identifier.
    2. Inventory all existing values and detect conflicts. Resolve them with an explicit product policy before enforcement; do not let migration timing choose winners.
    3. Create consensus partitions keyed by normalized username and import resolved ownership with source versions.
    4. Start shadow claims: the old path remains authoritative while the new service evaluates each request and records disagreement without responding.
    5. Introduce one durable command log or outbox from the authoritative path. Avoid independent dual writes whose partial failures cannot be ordered.
    6. Catch up to a recorded watermark, verify counts and sampled ownership, then make the consensus service authoritative for a small tenant or hash cohort.
    7. During cutover, route both claim and release for a username to the same authority. Reads can fall back only if fallback cannot violate the new guarantee.
    8. Expand cohorts while monitoring rejection differences, quorum latency, unavailable rate, and reconciliation backlog.
    9. Roll back routing through the command log. Do not accept new claims in both stores during rollback.
    10. After the compatibility window, stop old writes and retain an audited mapping for support and recovery.
    flowchart LR
    OLD[(Eventual store)] --> SCAN[Conflict inventory]
    SCAN --> POLICY[Product resolution]
    POLICY --> NEW[(Consensus ownership)]
    OLD --> LOG[Ordered change log]
    LOG --> NEW
    NEW --> SHADOW[Shadow comparison]
    SHADOW --> COHORT[Authority by cohort]
    COHORT --> FULL[Consensus authoritative]
    COHORT -->|rollback| LOG

    The same pattern applies to counters or configuration: resolve historical ambiguity, establish one ordered source, backfill to a watermark, shadow, cut over by disjoint ownership, and retain a rollback path. Consensus does not repair past external effects; duplicates already used in emails, URLs, or ACLs need domain reconciliation.

    Interview traps and concrete level signals¶

    • "Choose CP": CAP is not a whole-system database personality. Name the operation, partition behavior, and invariant.
    • R + W > N means strong consistency: overlap depends on stable membership, durable acknowledgments, version comparison, and non-sloppy placement; linearizability needs a protocol.
    • Follower promotion by health check: a reachable follower may lack committed entries. Election terms, log checks, and quorum define safe leadership.
    • Snapshot isolation means serializable: write skew can violate cross-row rules.
    • Lease expiry means old owner stopped: pauses and partitions require fencing at the protected resource.
    • Timestamps solve conflicts: clock skew and concurrent valid writes make LWW lossy.
    • Eventual means random: convergence requires deterministic merge, idempotency, repair, tombstone policy, and bounded operational lag.
    • Consensus means no duplicates: client retries still repeat commands; the state machine needs command deduplication.

    An L5 candidate maps each operation to a guarantee, explains quorum overlap and leader failover, handles timeout as unknown, and distinguishes canonical correctness from stale reads. They can trace one transaction anomaly and select a mechanism that preserves the stated invariant.

    An L6 candidate tests protocol assumptions: durable acknowledgments, membership epochs, clock bounds, placement failure domains, repair of cold keys, tombstone retention, and side effects outside the replicated log. They offer session guarantees where global coordination is unnecessary, quantify the availability cost of quorum, and design an eventual-to-consensus migration with explicit conflict policy, single authority per key, rollout cohorts, and rollback. The L6 answer connects the mechanism to product policy: who wins an existing username conflict is not a Raft decision.
