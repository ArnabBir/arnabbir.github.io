    API and Data Modeling¶

    Engineering extensions: Temporal and general data modeling develops identity, units, valid/recorded time, and late corrections. API contract lifecycle develops compatibility, retry horizons, rollout, and retirement with assessment and executable evidence.

    An API is a concurrency and failure contract. A data model is an encoded set of invariants and access paths. Design them together from user operations, not independently from entity nouns.

    Example: reservation service¶

    Requirements: create a five-minute hold, confirm it after payment, cancel it, and list a user's reservations. No seat may have two active owners.

    POST /v1/holds
Idempotency-Key: 8f2...
{"show_id":"s1","seat_ids":["A10","A11"]}

201 Created
{"hold_id":"h7","status":"HELD","expires_at":"2026-09-05T12:05:00Z"}

    The following is a schema sketch, not executable DDL; a concrete database migration must declare types, foreign keys, and its partial-index syntax.

    reservation(id, user_id, show_id, status, expires_at, version, created_at, confirmed_at)
reserved_seat(show_id, seat_id, reservation_id, state)
idempotency(principal_id, key, request_hash, response, expires_at)

UNIQUE (show_id, seat_id) WHERE state IN ('HELD', 'CONFIRMED')
INDEX reservation_by_user (user_id, created_at DESC, id DESC)

    The database constraint is the final guard; a read-then-write availability check is not atomic. Expiry should transition ownership through a transaction or conditional write, not rely solely on a delayed timer.

    Interface decisions¶

    Concern Recommended contract Why
    retries idempotency key scoped to caller and operation resolves lost responses safely
    concurrency version or ETag on updates detects lost updates
    pagination opaque cursor over stable sort (time,id) avoids offset drift and deep scans
    async work 202 plus operation resource separates acceptance from completion
    errors stable machine code plus retryability clients should not parse prose
    bulk calls per-item outcomes and bounded batch size partial failure is inevitable

    Reject reuse of an idempotency key with a different request hash. Store the final status and response atomically with the business write where possible.

    sequenceDiagram
    autonumber
    participant C as Client
    participant A as API
    participant DB as Database
    C->>A: POST hold + key K
    A->>DB: transaction: claim seats + save K
    alt seats free
        DB-->>A: hold H
        A-->>C: 201 H
    else conflict
        DB-->>A: constraint violation
        A-->>C: 409 SEAT_UNAVAILABLE
    end

    Canonical state and projections¶

    Canonical state answers correctness-sensitive questions. Projections optimize specific reads and may lag. For example, reservation rows are canonical; "available seats by section" in Redis and a search index are projections. Label this boundary explicitly.

    flowchart LR
    API --> DB[(Canonical rows)]
    DB --> O[Transactional outbox]
    O --> S[Event stream]
    S --> P1[(Availability projection)]
    S --> P2[(User history projection)]

    Choose normalization for invariants and updates; denormalize for proven read paths. Every duplicate needs an owner, freshness expectation, and rebuild path.

    Evolution rules¶

    • Add fields as optional before making them required.
    • Use tolerant readers, but validate commands strictly.
    • Deploy dual-read or shadow verification before changing canonical storage.
    • Backfill with checkpoints, throttling, and per-row version guards.
    • Never reuse enum values or change field meaning in place.
    • Treat deletion as a workflow across canonical rows, caches, indexes, backups, and audit policy.

    Failure semantics¶

    Event Client-visible result Recovery
    validation fails 400, no state change correct request
    business conflict 409, no state change refresh or choose another seat
    timeout before commit unknown retry same idempotency key
    commit succeeds, response lost retry returns original response idempotency record
    projection update fails write remains committed replay outbox; expose lag
    partial bulk failure item-level success/error retry only failed items

    Model states and legal transitions, not free-form status strings. Authorization belongs at both API and data access boundaries: a valid reservation ID must not permit cross-tenant reads.

    Derive the contract from commands and queries¶

    Start with user intent, not CRUD. POST /reservations says less than POST /holds: a hold has a duration, ownership rule, conflict outcome, and legal next actions. Separate commands that change canonical state from queries that may use projections.

    For each operation, write six facts before choosing HTTP, gRPC, or messaging:

    Fact Hold example
    principal and authorization authenticated buyer may hold at most eight seats
    precondition all requested seats are unowned at commit time
    invariant a seat has at most one active owner
    successful effect one HELD reservation with five-minute expiry
    retry identity (principal_id, idempotency_key)
    observable failure validation, conflict, throttling, unknown outcome

    This framing prevents an attractive API from requiring an impossible storage operation. For example, atomically holding arbitrary seats across independently owned partitions requires distributed coordination. The product can instead limit a hold to one show partition, allocate seat pools to owners, or pay for a cross-partition transaction. The API boundary and partition boundary should agree.

    flowchart TD
    UI[User intent] --> CMD[Commands]
    UI --> QRY[Queries]
    CMD --> INV[Preconditions and invariants]
    QRY --> AP[Sort, filter, and freshness]
    INV --> TX[Transaction and partition boundary]
    AP --> IDX[Indexes and projections]
    TX --> CONTRACT[API contract]
    IDX --> CONTRACT

    Model the state machine explicitly¶

    A reservation is not a row whose status can take any string. It is a state machine. Assume the legal transitions are HELD -> CONFIRMED, HELD -> EXPIRED, and HELD -> CANCELLED; a confirmed reservation may later become REFUNDED, but never EXPIRED. Enforce transitions with conditional updates such as:

    UPDATE reservation
SET status = 'CONFIRMED', version = version + 1, confirmed_at = :now
WHERE id = :id
  AND user_id = :principal
  AND status = 'HELD'
  AND expires_at > :now
  AND version = :expected_version;

    Zero updated rows can mean not found, unauthorized, expired, wrong state, or stale version. Do not leak resource existence across tenants. The service can first query through an authorization-scoped access path or return one stable conflict code where disclosure is unsafe.

    The :now above is an authority-sampled decision time, not a caller-supplied timestamp or an application time captured before waiting for a lock. Define expiry as evaluated when the storage authority grants the transition. If a transaction can wait, lock the ownership row and sample a fresh trusted time before evaluating the predicate. Transaction-start timestamps alone can admit a hold that expired during the wait. This contract does not promise that the response reaches the buyer before expiry.

    Expiry races illustrate why the transition belongs in storage. At 12:05:00, a confirmation worker and expiry worker may run together. If both read HELD then update unconditionally, the last writer wins and can produce an illegal state. Conditional transitions ensure only one changes the row. The loser rereads and maps the current state to a deterministic response.

    stateDiagram-v2
    [*] --> HELD: seats claimed
    HELD --> CONFIRMED: payment accepted before expiry
    HELD --> CANCELLED: buyer cancels
    HELD --> EXPIRED: conditional expiry
    CONFIRMED --> REFUNDED: refund workflow completes
    CANCELLED --> [*]
    EXPIRED --> [*]
    REFUNDED --> [*]

    The seat ownership row should become CONFIRMED in the same transaction that confirms the reservation, and be released in the same transaction that transitions a hold to EXPIRED or CANCELLED. A timer merely proposes the transition. Correctness comes from the predicate and transaction, so duplicate and late timer delivery is harmless.

    Idempotency is stored protocol state¶

    An idempotency key is not just a header forwarded to the database. Define scope, payload equality, lifetime, and concurrent behavior. A robust algorithm is:

    1. Canonicalize the command and compute request_hash.
    2. Attempt to insert (principal, operation, key, hash, IN_PROGRESS) under a uniqueness constraint.
    3. If the row exists with another hash, return 422 IDEMPOTENCY_KEY_REUSED.
    4. If it exists with a final response, return that response exactly.
    5. If it is IN_PROGRESS, wait briefly, poll an operation resource, or return a retryable conflict; do not execute concurrently.
    6. In one transaction, perform the business change and store the final response or stable result reference.

    When the idempotency table and business data cannot share a transaction, use a domain-unique command ID in the canonical record and reconcile incomplete protocol rows. Do not promise atomicity from two ordinary writes to separate systems.

    For a local transaction, include the initial key claim in that same transaction; otherwise a crash between steps 2 and 6 strands IN_PROGRESS. An intentionally separately committed claim needs a lease, takeover fencing, and canonical-outcome lookup. Expiry alone must not permit repeating an unknown effect. PostgreSQL 17 isolation also means a duplicate insert can wait on an uncommitted contender; bound that wait and retry the entire aborted transaction, not only its final statement (accessed 2026-09-08).

    Retention must exceed the maximum credible retry period. If mobile clients retry for 24 hours, expiring keys after ten minutes reopens duplicate creation. Storing full responses for 24 hours has a cost: at 20,000 commands/s and 600 bytes/record, one day is roughly 20,000 * 86,400 * 600 = 1.04 TB before indexes and replicas. Store compact result references where possible, partition expiry data, and document what happens after expiration.

    Pagination under concurrent writes¶

    Offset pagination is simple but unstable. If a client requests rows 1-20 ordered newest-first and a new row arrives, OFFSET 20 may repeat the old row 20. Deletions can cause omissions, and deep offsets scan discarded rows.

    Use keyset pagination over a unique stable order:

    SELECT id, show_id, status, created_at
FROM reservation
WHERE user_id = :user
  AND (created_at, id) < (:cursor_time, :cursor_id)
ORDER BY created_at DESC, id DESC
LIMIT :page_size_plus_one;

    The opaque cursor should encode the last (created_at,id), query filters, sort version, and optionally an expiry, then be integrity-protected. Fetch one extra row to determine has_more. Keyset pagination gives traversal stability relative to the cursor, not a full snapshot: later status changes can still appear. If export requires snapshot semantics, issue a snapshot watermark and retain the necessary versions, or create an asynchronous export job.

    Indexes are executable access paths¶

    For every query, show the leading index fields and expected cardinality. reservation_by_user(user_id, created_at DESC, id DESC) supports one user's history. It does not efficiently answer "all expiring holds" because user_id is absent. Add an expiry work index such as (status, expires_at, id), or publish delayed work, but account for write amplification and cleanup.

    Use Database Indexing to validate left-prefix, equality-before-range, covering, selectivity, and planner behavior. Use Relational Databases when the access path also depends on MVCC visibility, constraints, WAL, replicas, or schema evolution.

    Suppose 15,000 holds/s update the reservation table, seat table, three secondary indexes, and one outbox row. The logical write amplification is at least six records per request, or 90,000 record mutations/s before replication. This may change the partition and storage decision even though API QPS looks modest. Remove speculative indexes; projections can serve access paths that do not require transactional freshness.

    Hot partitions also follow the API. Partitioning reservations by user_id spreads history reads, but seat claims for one popular show must coordinate by (show_id,seat_id). One table need not satisfy both. Keep canonical ownership partitioned for its invariant and build user history as an asynchronously rebuildable projection.

    Asynchronous APIs need observable operations¶

    For work exceeding a request deadline, return acceptance only after durable intent:

    POST /v1/exports
Idempotency-Key: exp-91

202 Accepted
Location: /v1/operations/op-44
Retry-After: 5
{"operation_id":"op-44","status":"PENDING"}

    202 does not mean completion. The operation resource needs terminal states, progress if meaningful, error codes, creation and expiry timestamps, and authorization. Cancellation is another command with race semantics: it may return that cancellation was requested while the worker concurrently completes. Define whether completed output remains downloadable.

    sequenceDiagram
    autonumber
    participant C as Client
    participant A as API
    participant DB as Canonical DB and outbox
    participant W as Worker
    C->>A: POST export, key K
    A->>DB: commit operation PENDING + job event
    DB-->>A: operation op-44
    A-->>C: 202, Location op-44
    DB-->>W: job event (at least once)
    W->>DB: claim op-44 if PENDING
    W->>DB: mark SUCCEEDED, output reference
    C->>A: GET op-44
    A-->>C: SUCCEEDED, signed download URL

    Workers claim with a lease or conditional state change and make output publication idempotent. A lease expiry can cause two workers; it is not proof the first stopped. Fence writes with an attempt number so an old worker cannot overwrite the newer result.

    Schema and API evolution without a flag day¶

    Use expand-migrate-contract. To replace full_name with given_name and family_name:

    This is a representation example, not a rule that names always have two parts. Do not split legacy names on the first space: preserve the original display name and ask for structured fields only where the product genuinely needs them. Mark uncertain backfills instead of inventing identity data.

    1. Add nullable new columns and deploy readers that understand both forms.
    2. Write the new representation while preserving the old compatibility path through one owner, not unrelated dual writes.
    3. Backfill in small primary-key ranges with checkpoints and a predicate that avoids overwriting newer rows.
    4. Compare old and new reads in shadow traffic; measure mismatch by reason.
    5. Switch reads progressively behind a reversible flag.
    6. Stop old writes only after every deployed client is compatible.
    7. Enforce new constraints, then remove old data in a later release.

    Event schemas require the same order. Add optional fields, preserve old meanings, and version genuinely incompatible semantics. A database rollback does not undo events already consumed, so rollout plans must include consumer compatibility and replay.

    For a storage migration, make one store canonical. Change capture is safer than application dual writes because it gives an ordered repair source. Backfill to a watermark, tail live changes, shadow-read, shift a small cohort, and retain reverse routing until confidence is high. Define rollback before cutover, including whether writes made on the new store can be replayed back.

    Failure and abuse scenarios¶

    • A client times out after commit and retries: return the prior result through the idempotency record.
    • Two users claim the same seat: one conditional claim commits; the other receives 409, regardless of stale availability views.
    • The outbox consumer is down for six hours: canonical writes continue if outbox storage and recovery SLO permit; queue age alerts before retention is exhausted.
    • A backfill overwrites a recent edit: prevent it with source version predicates and record mismatches for repair.
    • A tenant enumerates IDs: authorization-scoped queries and non-disclosing errors prevent cross-tenant reads; random IDs alone are not authorization.
    • A caller submits a 100,000-item bulk request: enforce byte and item limits, bound parallelism, and return per-item results or an asynchronous operation.

    Rate limits should reflect scarce resources. A flat requests-per-second limit does not protect a bulk endpoint or expensive search. Charge weighted units by items, bytes, or estimated work, isolate tenants, and include a machine-readable Retry-After response.

    Interview traps and L5/L6 reasoning¶

    • CRUD-only modeling: entity endpoints omit transitions, preconditions, and conflict meaning.
    • Read then write: application checks do not enforce uniqueness under concurrency; use constraints or conditional writes.
    • Exactly-once claims: retries and consumers duplicate; design idempotent commands and effects.
    • Offset by default: concurrent inserts and deep pages produce drift and cost.
    • Dual writing casually: partial success creates two truths without an authoritative repair log.
    • Cache as canonical: derived availability must not decide the final seat claim.
    • Status as free text: illegal transitions and ambiguous terminal states become production bugs.

    An L5 answer links each command to an invariant, transaction, index, failure code, and retry behavior. It distinguishes canonical rows from projections and traces a timeout after commit. An L6 answer finds the product constraint hidden in the partition key, estimates index and protocol-state cost, defines tenant isolation and abuse controls, and presents a reversible migration with compatibility windows, shadow verification, and rollback. L6 reasoning also assigns ownership: the API team owns compatibility, the domain team owns state transitions, and projection consumers own freshness SLOs and rebuild procedures.
