    Security Architecture¶

    Engineering extension: Authorization, revocation, and privacy develops effect-time policy checks, stale decisions, tenant isolation, deletion/restore obligations, and an independently checked permission-revocation fixture.

    Security architecture controls who can cause which state transition, on whose data, under what evidence and limits. Encryption and login are mechanisms inside that system. Begin with assets, adversaries, trust boundaries, and abuse cases.

    Learning goals¶

    After this chapter, you should be able to:

    • produce a threat model tied to concrete controls and residual risk;
    • separate authentication, authorization, session, and tenant-isolation decisions;
    • trace OAuth 2.0 and OpenID Connect without confusing tokens or actors;
    • design workload identity, mTLS, key rotation, privacy, deletion, and audit paths;
    • reason about abuse and software-supply-chain failures; and
    • distinguish L5 implementation depth from L6 program and blast-radius ownership.

    First principles: assets, actions, and boundaries¶

    Security preserves confidentiality, integrity, availability, authenticity, and accountability for defined assets. It is risk management, not a claim that compromise is impossible.

    risk = likelihood * impact
residual risk = inherent risk reduced by effective controls

    Use a data-flow diagram before selecting controls:

    flowchart LR
    U[User agent] -->|public network| E[Edge]
    E -->|authenticated request| A[Application]
    A -->|workload identity| D[(Tenant data)]
    A --> K[Key service]
    A --> Q[(Audit log)]
    O[Operator] -->|privileged path| P[Admin plane]
    P --> A

    Mark where data changes owner, privilege, protocol, persistence, or administration domain. For each flow, ask STRIDE-style questions: spoofing, tampering, repudiation, information disclosure, denial of service, and elevation of privilege. Add product abuse that STRIDE may not reveal, such as account farming, scraping, credential stuffing, or refund fraud.

    Threat Prevent Detect Recover
    stolen user credential phishing-resistant MFA, rate limits impossible-travel and device signals revoke sessions; recover account
    cross-tenant access tenant-bound authorization and storage keys denied-access and invariant metrics contain tenant scope; investigate reads
    service impersonation workload identity and mTLS identity and policy audit revoke identity; rotate trust material
    malicious release reviewed provenance and admission policy deployment and runtime evidence halt rollout; restore known-good artifact
    destructive operator action least privilege and dual control immutable admin audit revoke access; restore and reconcile

    Authentication, sessions, and authorization¶

    Authentication establishes an identity with a confidence level. Authorization decides whether that principal may perform one action on one resource in one context. Do not encode authorization only in UI visibility or trust caller-supplied roles.

    Centralize policy semantics while enforcing close to the resource. A useful decision tuple is:

    allow(principal, action, resource, tenant, context, policy_version)

    RBAC assigns permissions to roles and is operationally simple. ABAC evaluates attributes such as tenant, ownership, device posture, region, and time. ReBAC derives access from relationships such as document member or team parent. Most systems combine them. Default deny, make precedence explicit, and version policy so an audit can reconstruct a decision.

    Session cookies should be Secure, HttpOnly, and use an appropriate SameSite policy. Rotate session identifiers after privilege changes. Protect state-changing browser requests against CSRF. Short token lifetime limits exposure but increases dependency on refresh and identity availability; revocation needs session state, a deny list, or short expiry plus risk-based controls.

    OAuth 2.0 and OpenID Connect¶

    OAuth delegates authorization. OpenID Connect adds an identity layer. The actors are resource owner, client, authorization server, and resource server. An ID token tells the client about authentication. An access token is presented to the resource server. They are not interchangeable.

    For browser and mobile clients, use Authorization Code with PKCE (S256). This OIDC example additionally requests the openid scope; an OAuth-only response need not contain an ID token. Bind the redirect URI and transaction state to the initiating client session:

    sequenceDiagram
    autonumber
    participant U as User agent
    participant C as Client
    participant AS as Authorization server
    participant API as Resource server
    C->>U: Redirect with state, nonce, code challenge
    U->>AS: Authenticate and consent
    AS-->>U: Authorization code
    U->>C: Code and state
    C->>AS: Code plus PKCE verifier
    AS-->>C: ID token and access token
    C->>API: Access token
    API-->>C: Authorized resource

    For JWT tokens, validate issuer, audience, signature algorithm, signature, expiry, and required claims. Opaque access tokens instead require the authorization server's supported validation or introspection contract. The client also validates state and OIDC nonce. Pin accepted algorithms; never accept a token merely because it decodes. Resource servers should receive audience-restricted, scope-minimized tokens. Sender-constrained tokens reduce bearer-token replay when the ecosystem supports them.

    Do not put secrets or excessive personal data in JWT claims: signed does not mean encrypted, and issued tokens persist until expiry. Opaque tokens permit central introspection and rapid revocation at the cost of a runtime dependency and cache-consistency choices.

    Workload identity and mTLS¶

    For handshake evidence, trust distribution, and mesh data/control-plane failure, use TLS and PKI and Service Mesh and Zero Trust.

    Static service credentials spread, age, and survive ownership changes. Prefer short-lived workload identities issued from attested runtime facts: workload, namespace, service account, environment, and deployment identity. Authorize the workload, not only its network address.

    mTLS authenticates both transport peers and encrypts the hop. It does not decide whether service A may read tenant B's invoices; an authorization policy must bind identity, method, resource, and tenant. If a sidecar terminates mTLS, define how the application trusts identity metadata and prevent direct bypass to its plaintext port.

    A rotation plan overlaps trust safely:

    1. Publish a new trust root or issuer while retaining the old one.
    2. Verify every verifier has accepted the new trust bundle.
    3. Issue leaf credentials from the new authority.
    4. Observe old-credential use until bounded lifetime drains it.
    5. Remove the old root and retain audit evidence.

    Emergency revocation needs shorter leaf lifetimes, policy denial, or both. Certificate revocation mechanisms alone may not meet the response time of an internal fleet.

    Key and secret lifecycle¶

    Keys pass through generation, distribution, activation, use, rotation, revocation, archival, and destruction. Generate strong keys in an approved cryptographic module or managed KMS. Separate key-encryption keys from data-encryption keys and use envelope encryption:

    ciphertext = Encrypt(DEK, plaintext, authenticated_context)
wrapped_DEK = Encrypt(KEK, DEK)

    Authenticated context should bind stable metadata such as tenant ID, object ID, schema version, and purpose. A ciphertext copied to another tenant or field then fails authentication. Store key IDs and algorithm versions with ciphertext, but not plaintext keys.

    That claim assumes an authenticated-encryption construction and that the decryptor derives expected context from trusted identity and metadata. If the attacker can copy both ciphertext and a caller-controlled tenant context, context binding does not authorize access. Check authorization before key use, and ensure every nonce satisfies the chosen algorithm's uniqueness requirements. As with the OWASP authorization guidance, encryption is not a substitute for restricting the application's authority (accessed 2026-09-08).

    Rotation does not always require rewriting all data. New writes use the current key; old data can be rewrapped or lazily re-encrypted under a measured migration. Deletion by destroying a dedicated key works only when the key's scope matches the deletion subject and no plaintext copies, caches, logs, backups, or derived datasets remain.

    Secrets must not appear in source, images, logs, metrics labels, crash dumps, or broad environment inspection. Deliver them at runtime, scope them narrowly, rotate automatically, and alert on anomalous access.

    Tenant isolation¶

    Tenant isolation is defense in depth across identity, policy, queries, storage, encryption, quotas, and operations.

    Layer Control Failure it contains
    API derive tenant from authenticated context caller changes tenant_id parameter
    authorization action and resource check authenticated user crosses role boundary
    data access tenant predicate or row policy missing application filter
    schema/database composite tenant keys or dedicated database cross-tenant reference and blast radius
    cryptography tenant-scoped key where justified storage snapshot or key-scope compromise
    capacity per-tenant quotas and fair queues noisy-neighbor denial of service
    operations tenant-scoped support tools and audit broad operator access

    Shared tables maximize efficiency but demand excellent policy and testing. Separate schemas, databases, accounts, or cells increase isolation and restore flexibility at operational cost. Choose tiers from impact and regulatory needs, not customer size alone. Test guessed IDs, stale memberships, confused-deputy calls, cache-key omissions, exports, and support tooling.

    Privacy, retention, and deletion¶

    Create a data inventory with category, purpose, legal basis, owner, location, residency, retention, recipients, and deletion method. Minimize collection and purpose. Tokenization replaces a sensitive value with a scoped surrogate; pseudonymized data can still be personal data if re-identification remains possible.

    Deletion is a workflow across canonical records, indexes, caches, search, streams, analytical copies, vendor systems, and backups:

    flowchart TD
    R[Verified deletion request] --> I[Inventory affected objects]
    I --> C[Atomically tombstone canonical state and record deletion intent]
    C --> P[Outbox relay retries deletion intent]
    P --> D[Derived stores and vendors]
    D --> V[Verify completion]
    V --> A[Record minimal audit evidence]
    C --> B[Backup expiry policy]

    Commit the canonical denial/tombstone and durable deletion intent together where possible. If those stores cannot transact together, persist a recoverable workflow before acknowledging the request. Otherwise a crash after canonical deletion but before publication can strand a still-visible search copy. Record a separate receipt for each sink and retry idempotently.

    State whether backups are selectively edited, cryptographically erased, or allowed to expire under a documented isolation and restoration policy. A restore must not resurrect deleted records; replay deletion evidence before reopening service.

    Audit and repudiation resistance¶

    An audit event records actor, effective identity, action, target, tenant, decision, policy version, request ID, time source, outcome, and privileged justification. Avoid secrets and unnecessary payloads. Protect append paths with restricted writers, immutable retention, hashes or signatures where required, independent export, and monitored gaps.

    Application logs are not automatically audit logs. Debug logs may be sampled, mutable, and short-lived. Audit availability also matters: decide whether a sensitive action fails closed when durable audit recording is unavailable, or writes through a local durable buffer with a strict recovery objective.

    Abuse resistance and availability¶

    Rate limiting must bind the scarce resource and likely attacker dimension: account, credential, device, IP prefix, tenant, endpoint, or expensive backend key. IP-only limits punish shared networks and are easy to distribute around. Layer coarse edge limits, authenticated quotas, per-tenant fairness, concurrency limits, and business invariants.

    Prevent enumeration with uniform external errors while retaining internal reason codes. Bound decompression ratios, parser depth, regex work, upload size, fan-out, pagination, and query complexity. Challenge or delay suspicious traffic before expensive dependencies. Abuse controls need appeal, false-positive, and emergency-disable paths.

    Software supply chain¶

    Treat source, build service, dependencies, artifact registry, deployment controller, and runtime as one trust chain. Pin dependencies and verify integrity; generate an SBOM; isolate builds; minimize build credentials; sign provenance and artifacts; enforce admission policy; scan, patch, and monitor runtime drift.

    Signing an artifact proves association with a key, not that code is safe. Protect signing identity, make builds reproducible or attestable, require reviewed source provenance, and support rapid revocation. Avoid unreviewed install scripts and mutable tags in production manifests.

    Quantitative security decisions¶

    Suppose 10 million active sessions have 24-hour access tokens. Reducing lifetime to 15 minutes lowers the maximum lifetime of a stolen access token by 96x, assuming the attacker cannot refresh it. With all sessions continuously active and evenly distributed, the steady-state average is 10,000,000 / 900 = 11,111 refreshes/s; synchronized expiry can create a much larger peak. Add jitter, scalable refresh infrastructure, device-bound sessions where appropriate, and emergency revocation.

    For online guessing, an account with 20 allowed attempts/hour and a uniformly random six-digit code faces an upper-bound success probability near 20 / 1,000,000 = 0.002% per hour before expiration and telemetry effects. Distributed attacks require account-based limits, not only IP limits. Use standards-approved authenticators rather than inventing code schemes.

    Decision framework¶

    1. List assets, sensitive actions, adversaries, regulations, and impact tiers.
    2. Draw data and admin flows with trust boundaries.
    3. Enumerate misuse and failure cases; rank inherent risk.
    4. Bind identities to least-privilege authorization at each resource.
    5. Minimize data and choose encryption, retention, deletion, and audit semantics.
    6. Add abuse, tenant, operator, and supply-chain controls.
    7. Define prevention, detection, containment, recovery, owner, and residual risk.
    8. Validate with design review, tests, staged attack exercises, and incident drills.

    Failure cases and tradeoffs¶

    Failure Why it happens Response
    signing key exposed broad CI or operator access revoke, rotate, invalidate sessions/artifacts, investigate provenance
    authorization cache stale policy changed before cache expiry version decisions; short TTL; push invalidation for high-risk changes
    mTLS sidecar bypass application port reachable directly network policy, loopback binding, application verification
    deletion misses search index incomplete data inventory durable workflow, per-sink receipt, periodic reconciliation
    audit pipeline down synchronous sink unavailable fail closed for critical actions or durable local buffer by policy
    one tenant exhausts workers shared queue without fairness tenant quotas, weighted scheduling, admission control
    security control causes outage global policy or certificate rollout canary, overlap trust, break-glass with expiry and audit

    L5 and L6 expectations¶

    An L5 design gives a concrete threat model, protocol-correct identity flow, resource-level authorization, tenant-safe data access, key rotation, abuse limits, and recovery for likely compromise. An L6 design also defines control ownership across teams, impact tiers, policy distribution and rollback, cell boundaries, organization-wide identity migration, audit evidence, regulatory lifecycle, supply-chain trust, and accepted residual risk.

    Interview traps¶

    • Saying "JWT is secure" without validation, audience, storage, expiry, and revocation.
    • Using an ID token to call an API.
    • Treating mTLS as authorization.
    • Accepting tenant IDs from request bodies without binding them to identity.
    • Claiming encryption at rest solves application or operator misuse.
    • Describing deletion only in the primary database.
    • Logging full tokens or personal payloads for audit.
    • Adding rate limits without naming the scarce resource or attacker key.
    • Trusting signed artifacts without protecting the signer and source-to-build path.

    Exercises with worked answers¶

    1. Cross-tenant document API¶

    An API receives /tenants/{tenant}/documents/{id} and checks only that the caller is logged in. Repair the design.

    Answer: Derive allowed tenant memberships from authenticated identity; authorize read on the document; query by both tenant_id and document_id; bind cache keys and encryption context to tenant; prevent cross-tenant references with schema constraints where possible; audit denied and privileged access; and test guessed IDs, stale roles, support impersonation, exports, and caches. The path tenant is a requested scope, not authority.

    2. OAuth token choice¶

    A single-page application sends its OIDC ID token to three internal APIs because it contains the user's email.

    Answer: The ID token is intended for the client and may have the wrong audience and permissions. Obtain access tokens audience-restricted to the resource APIs, validate issuer/audience/signature/expiry at each trust boundary, minimize scopes and claims, and keep user profile data separate from authorization. Use Authorization Code with PKCE and protect browser session/token storage.

    3. Key rotation¶

    A database holds one billion envelope-encrypted objects. The key-encryption key must rotate within seven days.

    Answer: Introduce the new KEK, make new writes use it, and rewrap DEKs without decrypting every plaintext where the KMS and format permit. Process in resumable partitions with rate limits, record key version per object, verify counts and failed objects, retain the old key for rollback until coverage is proven, then disable and finally destroy it according to policy. Emergency compromise may require a faster path and wider containment. Rewrapping does not undo exposure if an attacker already obtained the old KEK and wrapped DEKs or plaintext. In that case, assess which data keys and ciphertext copies are compromised; recovery may require new DEKs and data re-encryption as well as access revocation.

    Takeaways¶

    • Start with assets, actions, adversaries, and trust boundaries.
    • Authentication names a principal; authorization governs a resource action.
    • Scope short-lived user and workload credentials and plan rotation before issuance.
    • Enforce tenant identity in policy, query, key, quota, and operator paths.
    • Treat privacy deletion and audit as distributed workflows with verification.
    • Protect the source-to-runtime supply chain and design compromise recovery.
