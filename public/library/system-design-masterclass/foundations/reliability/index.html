    Reliability Engineering for Designs¶

    Engineering extension: Service operations turns reliability into SLI definitions, incident authority, configuration and drain gates, and a quantified recovery runbook. Practice the bounded scheduler and Atlas incident.

    Reliability is the probability that a defined operation succeeds within its contract. Build it from user journeys, failure domains, and recovery paths rather than a collection of retries.

    Turn goals into budgets¶

    A 99.9% time-based SLO permits 43.2 bad minutes in a 30-day month. A request-based SLO instead permits 0.1% of eligible requests to be bad; converting that to outage minutes assumes uniform traffic. Define the SLI precisely: eligible checkout attempts receiving a terminal accepted or business-rejected response within 800 ms. Exclude invalid requests, not dependency failures.

    Goal Mechanism Hidden cost
    higher availability redundancy across failure domains correlated software/config failures remain
    lower RTO automated failover false failover and split brain
    lower RPO synchronous replication write latency and partition unavailability
    graceful overload admission control and prioritization rejected optional work
    safe retries idempotency and budgets state and dedup retention

    Failure-oriented architecture¶

    flowchart LR
    C[Client] --> A[Admission control]
    A --> S[Stateless service]
    S --> D[(Replicated DB)]
    S --> Q[(Durable queue)]
    Q --> W[Workers]
    S -. timeout/breaker .-> X[Dependency]

    Use deadlines propagated from the caller. A service with 200 ms remaining must not start a dependency call with a 500 ms timeout. Retries need exponential backoff, jitter, a cap, and a shared attempt budget. Retry only transient and idempotent operations.

    Overload is a correctness problem¶

    When arrival rate exceeds service rate, queues increase latency until all requests time out while still consuming work. Reject before expensive work, bound every queue, reserve capacity for health/control traffic, and prioritize core operations.

    stateDiagram-v2
    [*] --> Healthy
    Healthy --> Degraded: saturation threshold
    Degraded --> ShedOptional: queue age grows
    ShedOptional --> Healthy: sustained recovery
    Degraded --> FailClosed: invariant dependency unavailable

    Failure semantics table¶

    Failure point Semantics Recovery
    server proves rejection before durable commit not accepted safe retry with same command identity
    response lost after commit unknown to caller same idempotency key returns result
    cache lost performance degradation bounded bypass and gradual warmup
    async consumer down accepted but delayed durable backlog and replay
    database replica lost continue within quorum replace and verify replication
    entire region lost RTO/RPO-specific failover fence old writer before promotion
    bad deployment correlated errors canary, automatic halt, rollback/roll-forward

    Recovery is a product feature¶

    Backups are useful only after restore tests. Specify snapshot interval, log retention, encryption keys, restore duration, and consistency checks. Reconciliation compares independent evidence: orders versus payments, object metadata versus blobs, source tables versus projections.

    Game days should test dependency latency, partial packet loss, expired credentials, full disks, queue poison, zone loss, and operator mistakes. Fault injection without assertions merely creates outages.

    Observability and ownership¶

    Track user-success rate and latency first, then saturation, dependency outcomes, queue age, replication lag, and invariant violations. Logs need correlation IDs but must not leak secrets. Alerts should be actionable and budget-based; page on user harm or imminent exhaustion, ticket on trends.

    An L6 design names degradation policy and authority: who declares failover, what operations become unavailable, how tenant isolation works, and how a migration is aborted. Reliability includes runbooks, capacity ownership, and a path to return from degraded state.

    Define reliability per user journey¶

    A service is not simply "up." Browse, checkout, cancellation, and administration can have different contracts. Define an SLI as a ratio over eligible events:

    availability = good eligible requests / total eligible requests

    For checkout, a good request may be one that receives an accepted or valid business rejection within 800 ms. A card decline is a successful system outcome; a timeout caused by the payment dependency is not. Excluding all 4xx responses without classifying them can hide authentication or validation regressions. Measure at the boundary closest to the user, then retain internal SLIs to localize failures.

    Time-window aggregation matters. Request-based availability weights busy minutes more heavily. Time-slice availability might mark each minute good only if at least 99.9% of eligible requests succeed. The latter prevents a quiet, completely broken hour from disappearing beneath peak volume. State which method the SLO uses.

    Worked availability and error budgets¶

    A 30-day month has 43,200 minutes. The approximate unavailable time permitted by common availability goals is:

    SLO Error fraction Monthly budget Average daily budget
    99.0% 1% 432 min 14.4 min
    99.9% 0.1% 43.2 min 86.4 sec
    99.95% 0.05% 21.6 min 43.2 sec
    99.99% 0.01% 4.32 min 8.64 sec

    For a request-based 99.9% SLO over 200 million eligible requests, the budget is 200,000 bad requests. If 80,000 have failed ten days into the window, 40% of the budget is consumed while 33% of time has elapsed. At uniform traffic, this pace would exhaust the budget before the window ends. For seasonal traffic, compare failures with the eligible-request forecast rather than elapsed time alone.

    Burn rate compares observed error rate with the allowed error rate. For a 99.9% SLO, the allowed rate is 0.1%. An observed 1.4% error rate is a 14x burn. At constant traffic, a 30-day budget disappears in about 30 / 14 = 2.14 days. Google's multiwindow, multi-burn-rate example pages on (burn_1h > 14.4 AND burn_5m > 14.4) OR (burn_6h > 6 AND burn_30m > 6). The short window confirms the error is still occurring; the two pairs catch different burn speeds. These are starting thresholds, not universal defaults (accessed 2026-09-08).

    flowchart LR
    R[Eligible requests] --> G[Good within contract]
    R --> B[Bad or too slow]
    G --> S[SLI ratio]
    B --> S
    S --> E[Error budget remaining]
    E -->|Healthy| C[Normal change velocity]
    E -->|Fast burn| F[Freeze risky rollout]
    E -->|Exhausted| P[Reliability work and exception process]

    Budgets guide decisions; they are not permission to schedule outages until every minute is consumed. Keep planned maintenance in the same user-impact accounting unless the product contract explicitly excludes it.

    Compose dependency availability carefully¶

    For independent serial dependencies required on every request, availability multiplies. If the API, database, and payment adapter are each 99.9%, the path is 0.999^3 = 99.7003%, before network and client failures. The product is valid only for independent success events under a common observation boundary. Shared outages can overlap rather than add: perfect correlation here yields 99.9%, while disjoint outages yield about 99.7%. Model the joint failure behavior; independence is not a guaranteed upper or lower bound for a required serial path.

    Parallel redundancy helps only when failures are sufficiently independent and failover works. Two independent 99% replicas with successful failover yield 1 - (0.01 * 0.01) = 99.99%. Shared power, a bad schema migration, or a malformed request can defeat both. Redundancy addresses component failure; canaries, compatibility, and blast-radius controls address correlated failure.

    Optional dependencies should not sit in the critical path. If recommendations fail, return checkout without recommendations. For correctness dependencies, failing open can violate an invariant; fraud authorization or entitlement checks may need to fail closed. Record this as a product decision.

    Deadlines, retries, and amplification¶

    For the transport, connection-pool, and retry-budget mechanics behind this reliability policy, use Deadlines, Retries, and Pools.

    Propagate one end-to-end time budget through the call graph. Use local monotonic clocks and transmit remaining duration rather than comparing unsynchronized absolute clocks; gRPC deadline propagation subtracts elapsed time. Suppose the client budget is 800 ms. The edge consumes 40 ms and the service has spent 110 ms, leaving 650 ms. Reserve 100 ms to form and transmit the response, so downstream work has at most 550 ms. Starting three sequential calls with 500 ms timeouts ignores the contract.

    Retries consume both time and capacity. If a frontend makes one call to service A, which retries service B up to three total attempts, and B retries database operations up to three attempts, one user request can create 3 * 3 = 9 database attempts. At 10,000 requests/s, a total dependency failure can drive 90,000 attempts/s before client retries. This retry amplification can prevent recovery.

    flowchart TD
    U[10k user requests/s] --> A[Service A: up to 3 attempts]
    A --> B[Service B: up to 30k calls/s]
    B --> D[Database: up to 90k attempts/s]
    D --> X[Saturation extends failure]
    X -->|timeouts trigger more retries| A

    Prefer retries at one layer, usually the layer with end-to-end context. Use an attempt budget carried with the request, exponential backoff with full jitter, and a retry cap. Retry only when the remaining deadline permits useful work and the operation is idempotent. Hedged reads send a second attempt after a latency percentile, not immediately; cap them globally because they deliberately add load.

    A circuit breaker prevents repeated work against a known failing dependency, but it does not create capacity. Its open state should fail quickly or use an explicitly safe fallback. Probe recovery with limited half-open traffic. A fleet of synchronized probes can itself overload a recovering dependency, so jitter and centrally bound them.

    Capacity, queues, and graceful degradation¶

    Little's Law states L = lambda * W: average work in the system equals arrival rate multiplied by time in system. At 5,000 requests/s and 200 ms average latency, about 1,000 requests are in flight. If latency rises to two seconds at unchanged arrival rate, 10,000 are in flight, consuming connections and memory. Unbounded queues turn a capacity shortage into latency, timeout, and retry failures.

    Admission should happen before expensive parsing, allocation, and downstream calls. Bound queues by time as well as count. Reserve capacity for health checks, lease renewal, operator access, and high-value operations. Degrade deliberately: omit recommendations, lower result depth, serve bounded stale data, or delay analytics. Never degrade an invariant silently.

    Load shedding should return a clear retryable status quickly. Fairness controls prevent one tenant from occupying all workers. Adaptive concurrency can lower in-flight limits as latency rises, but retain static safety ceilings and test oscillation behavior.

    Failure domains and zonal evacuation¶

    Deploying three replicas across three zones does not guarantee survival of one zone if each zone normally runs at 70% utilization. With 100 capacity units per zone, total demand is 210 units and surviving capacity is 200, producing 105% utilization. To survive one of three equal zones without shedding, normal fleet utilization must stay at or below roughly 66.7%, and lower in practice for skew and repair.

    A zonal evacuation is controlled load transfer, not just instance replacement:

    1. Detect zone-specific symptoms using independent signals: request errors, network reachability, and infrastructure health.
    2. Stop placing new work and new leaders in the suspect zone.
    3. Verify healthy zones have headroom; shed optional traffic before shifting if needed.
    4. Drain traffic gradually while watching p99, queue age, connection pools, and dependency quotas per destination zone.
    5. Fence stateful leaders and restore replication factor without violating anti-affinity.
    6. Hold the zone out until a defined stable period passes. Reintroduce a small canary, then ramp.
    stateDiagram-v2
    [*] --> Balanced
    Balanced --> Suspect: zone signals disagree
    Suspect --> Evacuating: incident authority confirms
    Evacuating --> Evacuated: traffic and leaders drained
    Evacuating --> Balanced: false alarm and healthy
    Evacuated --> CanaryReturn: repair verified
    CanaryReturn --> Balanced: ramp guardrails pass
    CanaryReturn --> Evacuated: regression

    Avoid automatic evacuation on one noisy metric. A traffic shift can overload healthy zones and convert a partial incident into a regional outage. Define who can override automation and how routing converges.

    Data durability, RPO, and recovery¶

    Availability and durability differ. A replicated database can serve requests while an operator mistake deletes data from every replica. Backups need separate credentials and failure domains, immutable retention where appropriate, and tested restore procedures.

    Quantify recovery. Hourly snapshots plus continuous logs can offer an RPO near zero only if logs are durable, complete, and replayable. If restoring a 20 TB snapshot at an effective 500 MB/s, transfer alone takes about 11.1 hours, before validation and log replay. An RTO of two hours is incompatible with that method; use incremental snapshots, parallel restore, a warm standby, or a smaller recovery unit.

    A restore test must verify more than process startup. Compare record counts by partition, checksums, referential integrity, business totals, encryption key availability, and application read/write behavior. Preserve evidence about uncertain requests around the failure boundary and reconcile with external systems.

    Safe change and blast radius¶

    Changes can cause correlated incidents that hardware redundancy does not contain. Progressive delivery sends a small representative slice to the new version, compares success and latency, and halts automatically on guardrail breaches. Include schema, configuration, credentials, feature flags, and traffic policy in change control; rolling back application code may not reverse an incompatible data migration.

    Use expand-contract database migrations. Add a field or table first, deploy code that handles both forms, backfill under throttles, switch reads, and remove the old form only after rollback and old-version windows end. Assign idempotent checkpoints to backfills and pause them when foreground SLOs burn.

    Limit blast radius by cell, tenant, zone, or shard. A global control plane can publish configuration, but data planes should continue with the last valid version during a control-plane outage. Validate configuration before publication and support rapid rejection of a bad epoch.

    Observability and game-day assertions¶

    Dashboards should connect user harm to causes: SLI and latency, admitted and shed rates, saturation, dependency outcomes, queue age, replica lag, and remaining error budget. High-cardinality dimensions such as tenant or shard need controlled aggregation but are essential for blast-radius analysis.

    Every game day needs expected assertions. During a zone-loss exercise, verify that error rate remains within the test budget, no stale leader accepts writes, healthy-zone utilization stays below its evacuation ceiling, replication factor recovers, and traffic can return safely. Stop conditions protect production if assumptions are wrong.

    Design review checklist¶

    • Define good, bad, eligible, and too-slow events per journey.
    • Calculate monthly budget, current burn rate, and alert windows.
    • Quantify serial dependency composition and correlated risks.
    • Show deadline allocation and worst-case retry multiplication.
    • Bound queues, concurrency, fallback freshness, and shedding priority.
    • Demonstrate N-1 zone capacity with skew and repair headroom.
    • State RTO and RPO alongside measured restore and replay time.
    • Fence old writers before promotion or evacuation.
    • Make rollout, rollback, reconciliation, and return-to-normal executable.
