    Multi-Region Architecture¶

    Multi-region design is a business decision about latency, continuity, regulation, and cost. It adds failure modes even when no region fails: lag, routing mistakes, conflicting writes, and divergent configuration.

    Begin with objectives¶

    For each operation define latency target, RTO, RPO, residency, and partition behavior. Example:

    Operation Latency RTO/RPO Partition policy
    browse catalog 200 ms 5 min / 15 min serve stale locally
    place order 800 ms 10 min / 0 acknowledged orders single write home, reject if unreachable
    update cart 300 ms 1 min / 30 sec accept locally and merge
    admin price change 2 sec 1 hour / 0 leader region only

    Deployment models¶

    Model Strength Cost and risk
    active-passive simplest write ordering idle cost, failover RTO, cold dependencies
    active-active, single home per key local reads, no concurrent key writes home routing and evacuation
    active-active multi-writer local writes during partitions conflicts and invariant limits
    global synchronous database strong semantics WAN latency and quorum availability

    An active-passive or per-account-home design simplifies order authority. Asynchronous DR replication permits acknowledged loss and therefore does not meet the table's zero-order-loss RPO. That contract requires durable replication across the named regional failure boundary before acknowledgement, or staying unavailable until missing acknowledged data can be recovered. Route correctness-sensitive writes to the home.

    flowchart LR
    G[Global traffic manager] --> A[Region A - writer]
    G --> B[Region B - read/standby]
    A --> DA[(Primary)]
    DA -. async log .-> DB[(Replica)]
    B --> DB

    Failover protocol¶

    Failover is a state machine, not a DNS edit.

    sequenceDiagram
    autonumber
    participant O as Orchestrator
    participant A as Old region
    participant B as New region
    O->>A: revoke write authority epoch 17
    O->>O: verify durable fence at every old commit path
    O->>B: verify replay through committed offset
    O->>B: grant epoch 18
    O->>O: switch traffic
    O->>B: reconcile uncertain operations

    If A cannot be contacted, a quorum-based lease or external fencing authority must ensure it cannot continue writing. Promotion chooses an explicit data-loss boundary. Returning traffic later requires resynchronization; never simply reverse DNS.

    Conflict policy¶

    Multi-writer works only where domain merge is valid. Sets can often union with tombstones; counters can use CRDTs; a username claim or finite inventory cannot safely use last-write-wins. Allocate inventory rights per region or coordinate claims.

    Conflict Better policy
    concurrent profile edits field-level/version conflict, ask user if needed
    cart additions merge item quantities under documented rule
    duplicate payment commands globally scoped idempotency key
    account deletion versus update deletion tombstone dominates

    Failure semantics and operations¶

    • Region isolation: local stale-safe reads continue; home writes reject or use preallocated rights.
    • Replication lag: expose data age; prevent stale replicas from serving read-after-write using a version token.
    • Global control-plane outage: data planes continue with last valid configuration and bounded leases.
    • Traffic-manager error: per-region admission prevents overload.
    • Simultaneous schema versions: expand-contract changes preserve cross-region compatibility.

    Test evacuation at production-like load and measure detection, decision, fencing, promotion, routing convergence, backlog drain, and reconciliation. Include third-party endpoints, secrets, queues, object stores, and quotas; a database replica alone is not regional resilience.

    Separate traffic, compute, and data topology¶

    For DNS, anycast, BGP convergence, asymmetric paths, and failover capacity at this boundary, use BGP, Anycast, and Global Routing.

    "Active-active" is incomplete. A system can run compute in two regions while maintaining one write region, serve local reads from asynchronous replicas, or allow writes in both. Describe topology separately for each data set and operation.

    The global traffic layer directs users according to health, latency, residency, and tenant home. Regional ingress performs authentication and admission even if the global control plane is unavailable. Stateless compute should not require a cross-region control-plane call for every request. Canonical databases, caches, queues, object stores, secrets, and third-party dependencies each need their own regional story.

    flowchart TD
    U[Users] --> G[Global traffic policy]
    G --> EA[Region A ingress]
    G --> EB[Region B ingress]
    EA --> SA[Regional services]
    EB --> SB[Regional services]
    SA --> CA[(Regional cache A)]
    SB --> CB[(Regional cache B)]
    SA --> PA[(Canonical primary)]
    PA -. encrypted replication .-> RB[(Replica B)]
    SB --> RB
    CP[Global control plane] -. versioned policy .-> EA
    CP -. versioned policy .-> EB

    For a commerce system, catalog content might use active-active local reads and last-writer policy, carts might merge, while orders and payments have one home writer. Applying one consistency model to every entity either weakens critical invariants or adds unnecessary WAN coordination.

    Choose a topology from operation contracts¶

    Active-passive keeps one serving writer and a standby. It has the clearest conflict model, but standby readiness determines RTO. Exercise dependencies and continuously replay production-like synthetic traffic; an idle region can have expired secrets, missing indexes, cold caches, and insufficient quotas.

    Active-active compute with a home region per key gives local handling for users near their home and prevents concurrent writes to one key. A global directory maps account_id to home and carries a version. Requests arriving elsewhere proxy or redirect to home. The directory must remain available from cached, versioned state, and moving a home is a fenced migration.

    Multi-writer accepts local writes in more than one region. It is suitable only when operations commute or conflicts have a domain-approved resolution. A CRDT counter can merge increments; finite inventory, unique usernames, and account balances cannot generally use last-write-wins. Allocate rights per region or coordinate those operations.

    Synchronous global quorum provides stronger semantics but adds WAN latency and partition tradeoffs. If round-trip time between quorum regions is 80 ms, a write cannot complete below that coordination floor plus processing. During a partition, the minority must reject writes to preserve consistency.

    Data residency and sovereignty¶

    Residency is a data-flow constraint, not just database placement. Classify canonical records, derived indexes, caches, logs, backups, traces, support exports, and encryption keys. "EU data remains in the EU" is violated if payloads stay local but debugging logs or backups cross the boundary.

    Create a policy matrix:

    Data class Canonical location May replicate Derived use Deletion obligation
    account identity tenant jurisdiction approved paired region tokenized lookup only erase within policy window
    order ledger legal entity region approved DR region aggregate analytics retain by statutory policy
    product catalog global authoring region all serving regions search and cache normal lifecycle
    secrets and keys regional KMS boundary never export raw key envelope encryption rotate and revoke

    Route from trusted tenant metadata, not user-supplied headers. Reject a request rather than silently writing it to an unapproved fallback region. Replication filters must default deny for new fields and topics until classification is complete. Deletion propagates to replicas, projections, caches, and future restores; keep tombstones long enough that an old backup cannot resurrect deleted records without reapplying the deletion log.

    flowchart LR
    W[Write request] --> T[Trusted tenant directory]
    T --> P{Residency policy}
    P -->|EU allowed| EU[EU data plane]
    P -->|US allowed| US[US data plane]
    P -->|No eligible region| X[Reject explicitly]
    EU --> ER[(EU canonical and backup)]
    US --> UR[(US canonical and backup)]
    ER -. tokenized aggregate only .-> A[Global analytics]
    UR -. tokenized aggregate only .-> A

    Replication, freshness, and session guarantees¶

    Asynchronous replication yields a nonzero RPO when the source disappears before shipped changes become durable elsewhere. Measure lag in both time and log position. A replica reporting two seconds of time lag can still be millions of writes behind during a burst.

    For read-your-writes, return a commit version or log position with the write. A subsequent read may use a local replica only after that replica reaches the token; otherwise wait within the deadline, route to home, or report that the result is not yet visible. Do not infer freshness from wall clocks across regions.

    Monotonic reads require session state too. If a user first reads version 120 in home and then reaches a replica at version 115, routing should wait or choose a fresher replica. Bounded-staleness browse can instead return as_of and a product-approved age.

    Replication must preserve schema compatibility during staggered deployments. Use expand-contract formats and keep old readers tolerant of new optional fields. Regional deployment waves should not put a new writer ahead of every region capable of decoding its records.

    Fencing prevents two primaries¶

    Health detection cannot prove the old region is dead; it may only prove it is unreachable. Promoting a new writer without fencing creates split brain. Use a consensus-backed external lease, storage-level epoch, or irreversible infrastructure fence. Every mutation carries the current epoch, and the canonical store rejects lower epochs.

    Suppose A writes under epoch 17. The failover authority reaches quorum, expires or revokes 17, and grants B epoch 18. A later reconnects and sends a delayed write with epoch 17; the database rejects it even if A's process still believes it is primary. A timestamp is insufficient because clocks can skew and old requests can arrive late.

    The sink must first install epoch 18 atomically with its mutation guard. Maximum-seen fencing only rejects 17 after the sink has observed 18. Separate regional databases do not share that watermark automatically: fence every old write path or use an authority check at the actual commit boundary. etcd's API guarantees cover its own KV operations, not an external database write (accessed 2026-09-08).

    sequenceDiagram
    autonumber
    participant Q as Fencing quorum
    participant A as Region A writer
    participant B as Region B writer
    participant D as Canonical store
    A->>D: write with epoch 17
    Q->>Q: revoke 17 and commit 18
    Q->>D: install epoch 18 and reject epoch 17
    D-->>Q: fence durable
    Q->>B: lease epoch 18
    B->>D: write with epoch 18
    A->>D: delayed write with epoch 17
    D-->>A: reject stale epoch

    Lease duration trades failover speed against false overlap and availability. A writer that cannot renew before the safety margin must stop accepting writes, even if its local dependencies look healthy. Keep lease renewal on reserved capacity and monitor remaining lease time.

    Worked regional failover¶

    Assume a single-home order system with RTO 10 minutes and zero loss of acknowledged orders. Region A acknowledges only after its order log is synchronously durable to a witness-approved replica set satisfying that RPO. Region B maintains a warm replica and regional dependencies.

    1. Detect sustained regional failure using user probes, replication signals, and infrastructure health. Record the last known durable offset.
    2. Declare incident authority. Freeze automation that might concurrently change routing or capacity.
    3. Fence A through the external lease or infrastructure control. If fencing cannot be established, preserve the invariant and keep order writes unavailable.
    4. Prove B contains and has replayed every acknowledged order through the required durable boundary. A last observed lag metric alone is insufficient evidence. If that proof fails, keep order writes unavailable under the zero-loss contract and recover the missing data. Promoting with loss would be an explicit change to the product contract, not successful zero-RPO failover.
    5. Promote B under the next epoch, run invariant checks, and allow a small write canary.
    6. Shift traffic in steps while watching capacity, errors, dependency quotas, cache misses, and queue lag. Keep browse degradation available to reserve order capacity.
    7. Reconcile requests whose clients timed out around the transition using globally stable idempotency keys.
    8. Establish new backups and replication before declaring recovery complete.

    DNS TTL does not define full RTO. Clients cache addresses, connection pools persist, queues retain destinations, and mobile clients may ignore TTLs. Regional ingress should redirect or reject stale routes, and global plus local routing convergence must be measured.

    Returning home and moving tenant ownership¶

    Failback is another migration, not the reverse of failover. The old primary may contain unreplicated divergent writes and stale derived state. Rebuild it from the current authority, validate checksums and lag, add it as a fenced follower, and only then perform a planned epoch transition.

    Moving tenant T9 from A to B uses the same discipline:

    1. Mark T9 as MOVING at directory version 51; route new mutations through A.
    2. Snapshot T9 at log offset 940 and copy canonical plus required derived state.
    3. Stream changes after 940 to B and verify versions and business totals.
    4. Gate new T9 writes at A, drain in-flight mutations, and durably fence A's old authority. Record final committed position F, verify B durably contains and has applied through F, then grant B home epoch 52.
    5. Routers with directory version 51 receive a redirect. A rejects all new T9 mutations after fencing, including requests carrying stale epoch 51; checking only for incoming epoch 52 would leave the old write path open. It may proxy reads to B during convergence.
    6. Observe, retain rollback data, and erase old copies according to residency policy only after the rollback window.
    stateDiagram-v2
    [*] --> HomeA
    HomeA --> CopyingToB: directory marks moving
    CopyingToB --> CatchingUp: snapshot verified
    CatchingUp --> HomeB: fence A and grant epoch
    HomeB --> Observing: route convergence
    Observing --> StableB: validation passes
    Observing --> HomeA: reverse replay, fence B, grant fresh epoch

    Capacity and overload during evacuation¶

    Two regions each running at 60% cannot necessarily absorb the other; shifting all load creates 120% demand before cache-cold and retry effects. N+1 regional capacity, partial degradation, or a documented traffic-shedding policy is required. Capacity must include regional third-party rate limits and database connection ceilings, not only compute.

    Warm the destination gradually using bounded prefetches. A cold cache can multiply database demand exactly when replicas are catching up. Rate-limit global traffic independently from local admission so a routing mistake cannot overwhelm the destination. Preserve control and reconciliation capacity while shedding low-priority browse or analytics.

    Multi-writer conflict examples¶

    Last-write-wins chooses a winner but does not preserve intent. Two regions selling the last item can each observe stock one and decrement successfully; merging timestamps cannot undo two promises. Allocate 60 units to A and 40 to B as regional rights, transfer rights through a coordinated ledger, and reject locally when rights are exhausted.

    For carts, item additions can merge by item key, but concurrent "set quantity to one" and "remove item" needs a rule, often a deletion tombstone with a version. For payments, use one globally scoped command ID and route the account to one writer. For profile fields, retain per-field versions or surface conflicts rather than overwriting an unrelated edit.

    Operational readiness checklist¶

    • Specify topology per operation and data set, not one label for the service.
    • Record latency, RTO, RPO, partition behavior, and residency policy.
    • Inventory regional dependencies, quotas, keys, logs, backups, and projections.
    • Use version tokens for read-your-writes and monotonic sessions.
    • Demonstrate fencing with a stale writer, not merely planned shutdown.
    • Calculate destination capacity under cache loss, retries, and backlog drain.
    • Reconcile uncertain operations with stable idempotency keys.
    • Test failover, failback, tenant movement, and control-plane loss.
    • Audit every copy and deletion path against residency obligations.
