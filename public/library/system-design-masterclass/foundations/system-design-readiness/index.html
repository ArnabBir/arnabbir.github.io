    System Design Readiness¶

    For deeper mechanism and lifecycle practice, follow Engineering Foundations and Practice. Its three waves connect runtime budgets, distributed theory, performance, storage recovery, contracts, operations, and safe evolution to eight executable fault fixtures and an evolving capstone. This is an extension to the canonical route below, not a replacement.

    System design interviews test structured engineering judgment under incomplete information. Readiness means you can derive architecture from requirements, quantify limits, trace protocols, preserve invariants through failures, and communicate tradeoffs at the expected scope. Memorized diagrams are not enough.

    Learning goals¶

    After this chapter, you should be able to:

    • diagnose prerequisite gaps before practicing more case studies;
    • connect requirements, estimates, data, protocols, reliability, security, and cost;
    • answer component and end-to-end questions at L5 depth;
    • add organizational scope, migrations, and policy at L6 depth;
    • use a repeatable practice and review loop; and
    • score diagnostic answers against an explicit key.

    The first-principles design model¶

    A defensible design connects five artifacts:

    requirements -> invariants -> operations -> resource model -> failure policy
    1. Requirements: user journeys, scale, latency, availability, geography, privacy, and exclusions.
    2. Invariants: safety facts that must never become false. State eventual-progress and bounded-freshness requirements separately.
    3. Operations: commands, queries, events, identities, and consistency needs.
    4. Resource model: QPS, bytes, CPU, memory, connections, partitions, and cost.
    5. Failure policy: deadlines, idempotency, retries, degradation, recovery, and ownership.

    An architecture box is justified only when it implements one of these. "Kafka for scale" is weak. "A partitioned log decouples ingestion from three replayable projections; order ID scopes ordering; seven-day retention exceeds the four-hour outage plus six-hour rebuild objective" is design reasoning.

    Readiness dimensions¶

    Dimension Ready behavior Warning sign
    requirements prioritizes journeys and SLOs asks only DAU and QPS
    estimation keeps units and models peaks/skew guesses machine counts
    data states invariants, keys, indexes, retention lists databases by brand
    protocols traces commit, ack, retry, and timeout order draws arrows without semantics
    distribution names partition key, consistency, failover says "eventual" without operation scope
    reliability quantifies budgets, queues, RTO/RPO adds retries and replicas generically
    security binds identity, tenant, resource, and action says "encrypt everything"
    cost calculates dominant unit drivers treats price as post-design concern
    communication records decisions and revises visibly silently changes assumptions

    Calculation baseline¶

    You should derive these without prompts:

    requests/day          = requests/s * 86,400
ingest/day            = writes/s * bytes/write * 86,400
retained storage      = ingest/day * retention * replicas / compression
concurrency           = throughput * time in system
backlog growth        = arrival rate - service rate
drain time            = backlog / (service rate - new arrival rate)
availability in series = product of required independent component availability
error budget          = eligible events * (1 - SLO)

    Always add peak-to-average ratio, replication, indexes, protocol overhead, write amplification, failure headroom, and uncertainty where relevant. A correct formula with unsupported inputs is not evidence; state how benchmarks and production measurements will calibrate it.

    Protocol-tracing baseline¶

    For every state-changing request, answer:

    1. What identity authorizes it?
    2. What stable command or idempotency key names it?
    3. Where is the invariant checked under concurrency?
    4. What exact durable write defines acceptance?
    5. What is published, and before or after which commit?
    6. What happens if the response or acknowledgment is lost?
    7. Which layer retries, with what deadline and budget?
    8. How are duplicates, stale events, and gaps handled?
    9. How does an operator reconcile and repair it?
    sequenceDiagram
    autonumber
    participant C as Client
    participant A as API
    participant D as Canonical DB
    participant B as Broker
    participant P as Projection

    A->>D: Transaction: invariant, result, outbox

    If you cannot explain the crash before and after each arrow, the design is not finished.

    Decision framework: the 45-minute execution loop¶

    Time Output
    0-5 min top journeys, constraints, assumptions, and explicit non-goals
    5-10 min scale worksheet and SLO/RTO/RPO targets
    10-18 min API, data model, invariants, and primary access paths
    18-28 min smallest end-to-end architecture and one protocol trace
    28-36 min bottleneck evolution, partitioning, caching, async work, multi-region
    36-42 min failure table, security, observability, cost, and operations
    42-45 min tradeoff summary, migration path, and unanswered risks

    This is a control loop, not a script. Spend more time where the interviewer probes. Keep a visible decision log:

    Decision Why Rejected alternative Revisit trigger
    partition by account ID account-local ordering and writes region key creates hot partitions cross-account workload dominates
    async analytics outside checkout latency contract synchronous write couples failure legal rule requires immediate evidence

    L5 expectations¶

    An L5 answer owns a service or bounded system deeply:

    • converts product requirements into measurable APIs and SLOs;
    • estimates scale with distributions and identifies the first bottleneck;
    • gives concrete schemas, keys, indexes, partitioning, and retention;
    • traces one write and one read through all dependencies;
    • explains concurrency control, idempotency, deadlines, and backpressure;
    • handles instance, zone, dependency, and data-recovery failures;
    • includes tenant-safe authorization, abuse limits, and observability;
    • compares at least one credible alternative and states migration triggers.

    L5 depth is not the number of technologies. It is the precision of one coherent system.

    L6 expectations¶

    An L6 answer adds scope and durable organizational judgment:

    • separates control and data planes and defines degraded operation;
    • establishes cells, regions, tenants, and administrative blast radii;
    • chooses standards for identity, APIs, events, SLOs, and migrations across teams;
    • models correlated failures and N-1 or regional evacuation capacity;
    • provides versioned rollout, rollback, reconciliation, and decommission paths;
    • explains cost allocation, capacity commitments, and platform leverage;
    • names owners, decision authority, audit evidence, and incident recovery;
    • recognizes where consistency or availability is a product decision.

    L6 breadth without protocol depth is hand-waving. Show one path at L5 precision, then expand its fleet and organizational implications.

    Exercises with worked answers: diagnostic questions¶

    Answer these in 45 to 90 seconds each before reading the key. Show calculations where requested.

    Requirements and estimation¶

    1. A service averages 20,000 requests/s, peaks at 5x, and returns 8 KB. Estimate peak response bandwidth.
    2. Why is daily active users insufficient for capacity planning?
    3. At 6,000 jobs/s arriving and 5,000 jobs/s processing, how large is the backlog after 20 minutes?
    4. A handler sustains 2,000 requests/s per instance at the target p99. How many instances serve a 30,000 requests/s peak while keeping 40% of provisioned capacity spare, before zone-loss and deployment reserve?

    Data and consistency¶

    1. Design a key for fetching a user's newest 100 notifications without one unbounded partition.
    2. When is a relational database a better canonical store than a document store?
    3. What does a tombstone do in an LSM store, and why can early removal resurrect data?
    4. Does R + W > N prove linearizability? Explain.
    5. A user writes then immediately reads from a replica. Give two ways to provide read-your-writes.
    6. Why can a secondary index turn a one-shard query into scatter-gather?

    Protocols and transactions¶

    1. The database commits but the client times out. What should retry do?
    2. Explain the outbox pattern and its delivery semantics.
    3. When is 2PC a defensible choice over a saga?
    4. Distinguish saga compensation from rollback.
    5. Design expiry for a seat hold without racing confirmation.
    6. Why does broker-level exactly-once not guarantee exactly one payment charge?

    Networking and reliability¶

    1. Why does lowering a DNS TTL immediately before migration not guarantee fast convergence?
    2. At 10,000 requests/s and 40 ms mean service time, estimate useful mean concurrency.
    3. A client, gateway, and service each make three attempts. What is the worst-case dependency amplification?
    4. Why can one HTTP/2 connection be a bottleneck or failure domain despite multiplexing?
    5. Three equal zones run at 70% utilization. Can the service survive one zone loss without shedding?
    6. A 99.9% SLO sees 1.5% errors. What is the burn rate?

    Security and cost¶

    1. Distinguish an OIDC ID token from an OAuth access token.
    2. Why is mTLS insufficient for tenant authorization?
    3. List four places a deletion workflow must consider beyond the primary row.
    4. What must an audit record contain to reconstruct an authorization decision?
    5. A service logs 5 KB/request at 50,000 requests/s. Estimate daily raw log volume.
    6. Why can raising utilization reduce cost but violate an availability design?
    7. What is the difference between request hit ratio and byte hit ratio?
    8. Name the minimum inputs for cost per successful operation.

    Answer key¶

    Reveal the diagnostic answer key after your first attempt

    Requirements and estimation¶

    1. Peak is 20,000 * 5 = 100,000 requests/s. Payload bandwidth is 100,000 * 8 KB = 800 MB/s, or about 6.4 Gbit/s before protocol overhead and retries.
    2. DAU hides requests per user, object size, peak-to-average ratio, geography, skew, session concurrency, background work, and growth. Convert journeys into per-second and byte distributions.
    3. Growth is 1,000 jobs/s. In 1,200 seconds the backlog reaches 1.2 million jobs, assuming rates remain constant.
    4. Keeping 40% of provisioned capacity spare means a 60% target utilization. Required capacity is 30,000 / 0.60 = 50,000 requests/s, so the service needs 50,000 / 2,000 = 25 instances. Zone-loss and deployment surge are separate reserves. If a problem instead defines "40% extra over demand," the result would be 21; always state which convention is used.

    Data and consistency¶

    1. Use a partition key such as (tenant_id, user_id, time_bucket) and a descending sort key (created_at, notification_id). Query current then prior buckets until 100 results are collected. Choose bucket size from hot-user rate and retention.
    2. Choose relational when correctness needs cross-row uniqueness/references/transactions, access paths evolve, joins and reconciliation matter, and the workload fits its scaling plan. Document shape alone is not a reason to abandon constraints.
    3. A tombstone is a newer delete marker that masks older immutable values. If removed before old replicas/files are repaired or compacted, an older value can reappear and win during merge or repair.
    4. No. Overlap is insufficient without assumptions about membership, version selection, concurrent operations, sloppy quorums, and topology change. Cite the engine's operation-level guarantee.
    5. Route to the current authority that contains the acknowledged write, or carry a commit position/session token and wait or route to a replica that has replayed at least that position. Acquire a fresh snapshot after this check. An asynchronous failover may lose the required history; report that explicitly instead of silently returning stale data. Sticky routing alone is not a proof across topology changes.
    6. If the index is not colocated or partitioned by the query predicate, every shard may need to search its local index and return candidates, increasing latency and work with shard count.

    Protocols and transactions¶

    1. Retry with the same idempotency key and request hash. The server returns the stored committed outcome or continues the in-progress command; it must not create a second command because timeout is an unknown outcome.
    2. Commit canonical state and an outbox row in one local transaction. A relay publishes later and may publish duplicates. Consumers apply with inbox deduplication or versioned idempotency. The end-to-end default is at least once plus idempotent effects.
    3. Use 2PC when all short-lived participants support prepare/commit, atomic commitment is required, blocking during uncertainty is acceptable, and one coordinator/recovery domain is operationally manageable. Atomic cross-participant visibility additionally requires suitable reader isolation; 2PC alone does not provide it. Use a saga for long, autonomous, compensatable steps.
    4. Rollback removes uncommitted database effects. Saga compensation is a new committed business action, such as refunding a charge, and may be incomplete or irreversible.
    5. Inventory owns an atomic transition from HELD to CONFIRMED only if the hold is eligible under its authoritative time/policy. Expiry transitions HELD to EXPIRED. Exactly one wins; retries read the terminal state.
    6. The broker transaction does not include the external payment provider and local database crash window. Use a stable provider idempotency key, durable local state, outcome lookup, and reconciliation.

    Networking and reliability¶

    1. Resolvers can retain the previous long TTL, impose cache floors, and clients can reuse old connections. Lower TTL before migration, wait out the prior TTL, overlap endpoints, and drain connections.
    2. Little's Law gives 10,000 * 0.040 = 400 active requests on average. Tail, bursts, and headroom require testing around a bounded limit.
    3. 3 * 3 * 3 = 27 attempts. Choose one retry owner and propagate deadline and attempt budget.
    4. All streams share one TCP congestion and loss domain; connection flow control, server stream limits, CPU, or one reset can affect many requests. A few bounded connections may improve isolation.
    5. No. Losing one-third of capacity raises survivor utilization to 70% / (2/3) = 105% before skew. Keep lower normal utilization or define shedding.
    6. Allowed error is 0.1%. Burn rate is 1.5 / 0.1 = 15x; a 30-day budget would exhaust in about two days if sustained at uniform eligible traffic.

    Security and cost¶

    1. An ID token tells the client about the user's authentication and is audience-bound to that client. An access token conveys delegated authorization to a resource server. An API should not accept an ID token as a substitute.
    2. mTLS authenticates the peer workload and encrypts the hop. Authorization must still decide whether that workload and effective user may perform one action on one tenant resource.
    3. Any four of caches, search indexes, streams, analytical stores, object blobs, vendor systems, logs, materialized views, and backups/restores, subject to legal retention policy.
    4. Actor and effective identity, action, resource, tenant, context, decision, policy version, outcome, request/correlation ID, trustworthy timestamp, and privileged justification where applicable, without secrets.
    5. 50,000 * 5 KB = 250 MB/s; multiplied by 86,400 gives 21.6 TB/day raw, before replication and index overhead.
    6. Higher normal utilization leaves less capacity for peaks, retries, deployments, and zone loss. Queueing sharply increases p99 near saturation. Validate target utilization against the failure SLO.
    7. Request hit ratio counts requests, including repeated requests for one object; byte hit ratio weights by bytes. Many tiny cache hits can coexist with expensive large misses, so egress and origin load follow byte hit ratio more closely.
    8. Allocated monthly fixed and variable costs, count of eligible operations, successful-operation count, and a consistent definition of success. Useful decomposition also needs resource use, shared-cost policy, and failure/retry waste.

    Scoring and remediation¶

    These bands are course self-assessment heuristics, not validated predictors of hiring outcomes. Record the actual reasoning and failed checks alongside the number.

    Score each answer:

    • 0: absent, materially incorrect, or only a product name.
    • 1: correct concept but no mechanism, scope, or failure reasoning.
    • 2: correct, concrete, scoped, and includes the key tradeoff or calculation.
    Score Interpretation Next action
    52-60 strong integrated readiness run timed mocks and tighten communication
    42-51 interview-capable with visible gaps drill every zero and weak protocol trace
    30-41 foundations not yet integrated follow prerequisite map and repeat diagnostics
    below 30 foundational gaps dominate study core chapters before case-study memorization

    Any zero on questions 8, 11, 12, 19, 21, 23, or 24 is a correctness risk even if the total is high. Revisit the linked foundation and explain one real workflow aloud from request to recovery.

    Keep the first attempt and elapsed time before opening the key. Re-answer missed questions on a new scenario rather than editing the recorded attempt. In particular, compare question 13 against the PostgreSQL isolation contract: commit decisions and the snapshot a reader observes are separate promises (accessed 2026-09-08).

    Practice loop¶

    1. Pick one case and write a five-line design contract.
    2. Estimate load, storage, concurrency, and failure headroom.
    3. Model one command, one query, and their data structures.
    4. Trace commit, publish, retry, and unknown outcomes.
    5. Inject dependency latency, zone loss, bad rollout, and tenant abuse.
    6. Calculate one cost sensitivity and one migration trigger.
    7. Score using Interview Scorecard.
    8. Record the weakest reasoning step and drill that foundation next.

    Use retrieval practice. Redraw from a blank page, explain aloud, and compare against invariants. Reading a polished solution feels fluent but does not prove you can produce one.

    Common interview traps¶

    • Beginning with architecture before defining the design contract.
    • Optimizing for global scale when one primary and a migration path suffice.
    • Listing caches, queues, and databases without data ownership.
    • Using average estimates and ignoring skew, tails, and failure capacity.
    • Claiming exactly once, strong consistency, or zero downtime without scope.
    • Adding retries without idempotency, deadline, and amplification math.
    • Discussing happy-path scale while omitting recovery and deletion.
    • Treating security and cost as closing remarks rather than constraints.
    • Giving an L6 platform answer without one precise end-to-end protocol.

    Failure cases and course corrections¶

    Failure mode Evidence during the interview Course correction
    scope explosion every feature becomes mandatory restate top journeys and move the rest to non-goals
    architecture by habit components appear before operations return to invariants, access paths, and measured constraints
    arithmetic drift units disappear or totals contradict write units, recompute one baseline, and state uncertainty
    protocol ambiguity commit, publish, and acknowledgment order is unclear trace one command and inject a crash after each step
    premature distribution multi-region machinery hides the core design establish the smallest correct single-region path first
    hidden overload queues and retries are unbounded calculate concurrency and amplification; add admission control
    correctness hand-wave "eventual consistency" replaces an invariant state what may be stale, for whom, and for how long
    shallow L6 breadth policy language lacks a working protocol zoom into one path at L5 depth, then expand ownership and migration

    Final readiness checklist¶

    • I can turn an ambiguous prompt into prioritized journeys and non-goals.
    • I can calculate traffic, bytes, concurrency, backlog, and N-1 capacity.
    • I can state invariants and show where concurrency enforces them.
    • I can provide concrete API, schema, partition, index, and event examples.
    • I can trace DNS, connection, deadline, commit, publish, and retry behavior.
    • I can classify timeout outcomes and design idempotent recovery.
    • I can explain consistency per operation and multi-region authority.
    • I can define SLI/SLO, degradation, RTO/RPO, restore, and reconciliation.
    • I can bind identity, authorization, tenant, privacy, audit, and abuse controls.
    • I can calculate cost per unit and test its most sensitive assumption.
    • I can compare alternatives and name a reversible migration trigger.
    • I can finish with risks, owners, and evidence required before launch.

    Takeaways¶

    • Readiness is integrated reasoning, not architecture recall.
    • Requirements, invariants, operations, resources, and failures must connect.
    • L5 demonstrates precise ownership of one system; L6 extends it across domains and time.
    • Calculations expose bottlenecks and invalid promises early.
    • Protocol traces and crash points reveal correctness gaps hidden by diagrams.
    • Practice from a blank page, score evidence, and remediate the weakest prerequisite.
