Production architecture and implementation blueprint

Design date: 26 September 2026. Reference stack: Google Cloud Spanner, stateless regional services, database-backed workflow state, an at-least-once event bus, and isolated provider adapters. Intended readers: staff engineers, payments engineers, finance controllers, security engineers, SREs, and operations leaders.

This is a proposed architecture for a Stripe-like platform, not a description of Stripe's internal implementation. It is a build-and-review blueprint, not a claim that an unimplemented system has achieved five nines. Numerical workload, latency, retention, and operational thresholds below are explicit starting assumptions, not measured results. SQL and pseudocode require implementation-specific validation. Legal entities, licenses, supported corridors, safeguarding arrangements, accounting policies, and bank contracts must be approved before money moves.

The central design is: one strongly consistent financial authority per cell; immutable balanced journals; atomic economic-effect deduplication; separately modeled reservations; durable workflows; contract-aware external execution; independent reconciliation.

Safety boundary: The system never invents success, spends an eventually consistent balance, or repeats an ambiguous bank payment merely to preserve an availability number. Inside the financial database, we can enforce at-most-one committed effect per economic identity. Outside it, safe retry depends on the bank's actual contract and evidence.

1. Requirements, assumptions, and scope

1.1 What the platform must do

The platform accepts payment instructions, holds customer funds, prices and books currency conversion, reserves destination liquidity, submits payouts, observes bank outcomes, records fees, handles returns and reversals, and reconciles its books against independent evidence. It supports multiple tenants and legal entities, many currencies, asynchronous rails, duplicate and reordered messages, partial operations, and delayed settlement.

The ledger must answer both operational and accounting questions: what is spendable now, what is reserved, which obligation exists, which legal entity owns it, where cash is expected, what was known at a historical point, and why a correction was posted. A status such as SUCCEEDED cannot answer all of these questions.

The system excludes cryptocurrency consensus, a bespoke distributed database, and universal synchronous settlement across banks. It also excludes credit creation except through explicitly authorized credit limits and accounting templates. Incoming provisional funds are not automatically spendable cash.

1.3 Non-negotiable safety properties

Every committed journal balances within one book and one currency. No reserved unit can be captured or released twice. Each economic occurrence has at most one committed financial effect. A customer's protected spendable balance cannot go below its configured floor. Corrections append new evidence rather than changing history. Unknown external execution cannot be converted to "not executed" merely by waiting. An acknowledged durable intent or journal is not silently dropped during failover.

These are invariants, not 99.999% objectives. A correctness violation is a severe financial incident even if the API remains responsive.

2. Define five nines before choosing infrastructure

2.1 Separate availability, durability, correctness and settlement

Command availability measures whether a valid request gets its contractually correct response within the deadline. Durability measures whether acknowledged data survives the stated failures. Correctness concerns invariants such as conservation and uniqueness. Settlement completion concerns an external financial outcome. The same percentage cannot honestly stand in for all four.

Use separate service indicators:

Indicator Good event Proposed objective
Payment-intent acceptance Authorized, well-formed, in-quota request has a durable operation and payment identity, or a correct deterministic rejection, within 2 s 99.999%
Ledger command A valid command returns its committed result, an identical replay, or an accurate business rejection within 2 s 99.999%
Authoritative balance query Correct tenant-authorized strong result within the deadline 99.999%
Ready-to-dispatch processing An eligible, fully approved payment advances without avoidable internal delay A separate age-based objective; begin with p99 < 5 s
Bank execution and delivery Payment reaches the rail-defined outcome within the disclosed corridor promise Corridor-specific; include bank operating windows
Reconciliation freshness Expected evidence arrives and is matched or assigned to a case Rail- and statement-specific

Do not classify an infrastructure-caused false "insufficient funds," unexpected throttling below agreed quotas, or a queued intent returned as "money moved" as a good event. Acceptance can legitimately succeed while compliance or bank execution is pending, but the response must say exactly that. A ledger-posting API cannot count 202 accepted as successful posting.

For valid requests, a 503, an unhandled error, or a response beyond the deadline is bad. Correct authentication failures and malformed requests belong in separate security/client metrics, not in the eligible command denominator. Known business rejections count as correct service behavior only if independently validated as accurate. Measure logical operations as well as HTTP attempts so retries do not manufacture a flattering denominator.

2.2 Error-budget arithmetic

1 - 0.99999 = 0.00001. At continuous complete outage, this is 315.36 seconds per 365-day year, or 25.92 seconds per 30-day month. These are wall-clock equivalents, not substitutes for request-weighted measurement. A 10-second complete monthly outage consumes 38.58% of that month's time-equivalent budget.

Six independent serial dependencies, each available 99.999%, produce about 0.99999^6 = 99.99400015%, not five nines. Real dependencies are often correlated, so this product is only an explanatory model, not a forecast. The design therefore removes live calls to analytics, search, notification systems, external identity services, and the event broker from the posting commit path.

Spanner's published SLA lists 99.999% for qualifying multi-region and dual-region instances. That is a provider contract with definitions and exclusions, not proof that the assembled payment service achieves the same objective. The architecture still needs measured headroom, failure drills, sensible deadlines, and an application-level budget. [S03]

2.3 Declared fault model

The target covers ordinary process crashes, a service-instance loss, an availability-zone disruption within the supported topology, duplicated or reordered messages, temporary network interruptions, and one supported regional failure. It does not claim uninterrupted financial writes after loss of a database quorum, corruption of every independent recovery copy, compromise of all privileged authorities, or arbitrary bank unavailability.

When quorum is unavailable, financial writes fail closed. Returning a retryable error is correct behavior but still consumes availability budget. Stale read-only views may remain available with an explicit freshness marker; they must not authorize spending.

3. High-level architecture

3.1 Financial Core is deliberately cohesive

The Financial Core owns accounts, authoritative balances, reservation events, journals, economic-effect records, relevant payment state transitions, and transactional outbox rows. Keep these modules in the same transactional database boundary and initially in the same deployable write service. A separate microservice for every table would turn a small atomic transaction into a distributed consistency problem.

The Core exposes commands such as ReservePayment, BookFundingAndAuthorizeDispatch, RecordCashDebit, RecordDelivery, ReleaseReservation, and ApplyReturn. External callers cannot submit arbitrary account IDs and arbitrary debit/credit lists. Approved posting templates translate business commands into entries.

Workflow workers orchestrate progress by calling these commands. They do not own a second authoritative version of balances or journal state. Their scheduling leases and task progress live in the same cell's durable workflow tables. A mature external workflow engine can replace the scheduler later, but it must remain reconstructible from authoritative payment state and must not become a second financial truth.

3.2 Surrounding components

The global edge handles DDoS protection, request limits, connection management and routing. Regional APIs authenticate requests and route them to the payment's home cell using a cached, versioned directory. A missing or stale routing entry is not permission to create a second payment in a new cell.

Compliance, risk and quote services create versioned decisions and immutable evidence references. Their outputs are validated for scope and freshness at each irreversible boundary. Provider adapters own message translation, credentials, idempotency scope, request inquiry and bank-specific error interpretation. They cannot bypass the Core's dispatch authorization.

An outbox relay delivers committed events to Pub/Sub or an equivalent broker. Read models, customer webhooks, reporting and analytics consume those events. Reconciliation independently compares journals, provider evidence and bank statements. It opens cases or submits approved correction commands rather than editing balances directly.

3.3 Critical paths

Acceptance path: edge -> regional API -> Financial Core -> one durable database transaction -> response. It can persist PENDING_VALIDATION without calling a bank or a quote provider.

Posting path: authenticated command -> local validation and authoritative reads -> one serializable transaction -> response. Any required external decision must already exist as admissible evidence; otherwise the command does not claim posting success.

Execution path: committed authorization -> adapter claim -> external call -> immutable observation -> Core command. This path is asynchronous and explicitly supports uncertainty.

4. Storage, deployment and consistency

4.1 Reference database choice

Use a supported multi-region Spanner configuration per financial cell. Explicitly use serializable read-write transactions for financial mutations and strong reads for authorization. Spanner documents external consistency for serializable transactions; this provides a strong foundation for a single observable financial commit order where the application requires it. Its transaction runner can retry a callback, so callbacks must have no external side effects. [S01, S06]

This choice reduces the amount of distributed-systems machinery the payments team must implement: consensus, synchronous replication, multi-row atomicity and transaction conflict handling are database responsibilities. It does not implement accounting, economic deduplication, bank finality, or application recovery for us.

CockroachDB is a credible alternative where operational constraints favor its ecosystem; its documented region-survival mode uses five replicas across three regions and trades additional write latency for regional resilience. Validate its precise consistency and recovery contract rather than treating all "serializable" systems as identical. TigerBeetle is another strong candidate for a specialized financial kernel, with immutable transfers and pending-transfer resolution; the application must then design the metadata/ledger boundary rather than assuming it is one SQL transaction. [S16, S17]

Do not start by building Raft, a custom lock service, or a financial database on eventually consistent key-value replication. The distinguishing application logic here is the financial contract and its recovery semantics.

4.2 Multi-region topology

A common Spanner multi-region topology has two read-write regions with two read-write replicas each, plus a witness region. The witness votes but does not maintain a full database copy or serve reads. A majority of voters commits writes; leadership and supported failover behavior are managed by Spanner. Select an actual supported configuration and verify its full topology, including any read-only replicas, rather than constructing an arbitrary three-region combination. [S02, S04]

The diagram is not a five-node self-managed deployment recipe. Application services should be warm in the serving regions, with independent instance pools, network paths and egress. The passive-looking read-write region is not an asynchronously restored backup.

If data residency permits only a topology that cannot survive the required regional failure, record the conflict explicitly. Resolve it through an approved deployment option or a different availability contract. Never silently place a witness, backup, log or personally identifiable dataset in an unapproved jurisdiction.

4.3 Home cells and authority

A cell is a deliberately bounded financial failure domain: its own database, worker pools, quotas, adapter scheduling and operational dashboards. Accounts, their holds, effect keys, operation identities, and authoritative payment state have one home cell at a time. Tenant-to-cell routing is immutable during ordinary operations.

A single database can contain multiple legal-entity books where residency allows it; those books remain accounting boundaries even if a database transaction can span them. Different databases do not share a Spanner read-write transaction. Cross-cell movement therefore uses the protocol in Section 16, not an imagined cross-database transaction.

5. Domain model and invariants

5.1 Key concepts

A book belongs to one legal entity and defines an accounting policy and functional currency. An account belongs to one book, has exactly one transaction currency, one normal side, a purpose, and an owner. A journal contains balanced entries for one book and one currency. A journal group links journals that implement one business event, such as an FX trade.

A reservation reduces spending rights without creating a second source of money. A payment is the business instruction. An economic effect identifies one meaningful accounting occurrence, such as initial funding, cash debit, final discharge, or one particular return. A provider attempt is an immutable external instruction plus operational progress. A provider observation is evidence about that instruction. A reconciliation case records an unresolved discrepancy and its resolution.

5.2 Conservation and uniqueness

For each committed journal J:

sum(entry.amount_minor where side = DEBIT)
  = sum(entry.amount_minor where side = CREDIT)

All entries share J.book_id and J.currency.
Every amount is a strictly positive bounded integer.

For each economic identity (payment_id, effect_type, occurrence_id):

number_of_committed_effect_records <= 1
same_identity + same_fingerprint -> same result
same_identity + different_fingerprint -> conflict, never a new effect

Use an occurrence identifier for repeatable business actions: the first payout cash debit, a specific partial capture, a specific return, or a specific fee adjustment. Do not use a random worker execution ID; a worker retry is not a new economic occurrence.

5.3 Balance representation

Store a signed natural-side posted net balance, not a universal "credit minus debit" for every account. For a debit-normal asset or expense account, posted_net = debits - credits. For a credit-normal liability, equity or revenue account, posted_net = credits - debits.

For protected spending accounts:

spendable = posted_net - reserved_out
spendable >= configured_floor

A zero floor forbids overdrafts; a negative floor represents an explicitly approved credit facility. Accounts such as FX positions can have a different policy and must not inherit an accidental zero-floor restriction. Reservations always consume the account's economically spendable natural-side units; the posting template knows which entry side reduces that account.

Stored balances are a transactionally maintained operational projection of immutable entries. They are the immediate authority for spending because they are updated in the same commit as the journal, not because a cache has replayed events quickly enough. Independent replay must be able to reconstruct them exactly.

5.4 Reservation invariants

For each reservation:

original = captured_total + released_total + remaining
original >= 0; each component >= 0
account.reserved_out = sum(remaining of its active reservations)

Partial capture is permitted only by the product contract and has its own occurrence key. Full resolution sets remaining to zero. Capture, release, reservation events, balance changes, and payment-state guards are committed atomically. Expiry is a guarded command, not a timer that blindly increments a balance.

5.5 Operational invariants

At most one active or unresolved provider attempt may exist for a given disbursement obligation. Multiple historical attempts are allowed only after a prior one is conclusively non-executing, rejected, or safely cancelled. Cumulative refunds, returns or captures cannot exceed their authorized parent amounts except through separately approved adjustment flows. Every correction links to its original evidence and reason.

The system does not confuse cash movement with customer-obligation discharge. A bank debit can precede beneficiary delivery, and a delivery notification can arrive before a statement. Different observations must map to the right effects without double-posting cash.

6. Currency, FX and accounting design

6.1 Exact money

Accept money as integer strings, for example { "currency": "USD", "amount_minor": "10200" }. Convert to an exact checked integer internally. Never use JSON floating-point money, database floating-point amounts, or a language's approximate arithmetic for ledger calculations.

Account currency metadata includes the exponent and the reference-data version used at creation. ISO 4217 defines currency codes and minor-unit relationships; do not assume every currency has two decimal places. Maintain a versioned currency registry and explicit provider-specific wire-format adapters. [S11]

The reference schema uses INT64 for individual amounts and net balances. Define conservative business maxima below the type boundary and use a wider exact accumulator for sums, multiplication, fee calculation and range checks before storage. Do not store lifetime cumulative debit/credit turnover in an unbounded-use 64-bit counter. Large-turnover statistics can be rebuilt or stored in appropriately sized exact numeric fields.

6.2 Quote contract

An immutable FX quote records source and destination currencies, source and destination integer amounts, fee components, rate direction, exact decimal or rational rate, rounding mode, expiry, legal entity, beneficiary snapshot, liquidity allocation, customer acceptance, provider hedge reference and pricing-policy version.

For a rational destination-major/source-major rate n/d:

raw_destination_minor = source_minor * n * 10^destination_exponent
                        / (d * 10^source_exponent)

Apply the contracted rounding rule exactly once. For a guaranteed destination amount, derive the required source amount using the correct inverse/round-up rule rather than reusing a forward-rounding formula. Persist the agreed amounts; never recompute a historical payment using today's rate table.

Explicitly identify the rounding residual and FX spread. A currency's journal must balance on its own; USD 100 and EUR 92 do not "sum to zero" by numerical coincidence. Functional-currency valuation, realization, revaluation and hedge accounting are additional approved accounting layers, not a reason to alter the transaction-currency journal.

6.3 Worked payout example

Assume one licensed legal entity, an existing funded customer liability of USD 1,000, available EUR prefunding, a USD 100 principal, USD 2 fee, and a contractual destination amount of EUR 92. This is an operational subledger example; a controller must approve the actual account classifications, revenue timing and functional-currency treatment.

Reserve: place a USD 102 customer hold and EUR 92 destination-liquidity hold. The posted customer balance stays USD 1,000; its spendable balance becomes USD 898. Holds are operational controls, not ordinary spendable journal credits.

Book funding and FX before authorizing dispatch: commit the following journals in one database transaction, consuming the USD hold while retaining the EUR liquidity hold:

Book currency Debit Credit
USD Customer liability 102.00 FX position 100.00; fee revenue 2.00
EUR FX position 92.00 Beneficiary payout payable 92.00

The customer liability becomes USD 898. Releasing the consumed hold must not restore spendable funds; the posted debit already reflects the economic use. An immutable dispatch attempt is created in the same command. The payout obligation now exists even though the external request has not yet succeeded.

Confirmed bank cash debit: debit EUR outbound-settlement receivable 92 and credit EUR nostro/bank asset 92. Release the matching destination liquidity hold in that same commit. Cash has left the bank account, but the beneficiary liability remains until the contractual obligation is discharged.

Confirmed beneficiary finality: debit EUR payout payable 92 and credit EUR outbound-settlement receivable 92. The payout obligation is extinguished and the in-flight asset clears.

If debit and finality are evidenced together, the Core may apply both distinct effects in one transaction. If finality arrives first, use an approved outstanding-bank-debit/accrual template or retain a specifically classified pending evidence state. Do not manufacture a cash debit twice when the statement later arrives.

Rejection before external debit: only after conclusive non-execution, reverse the original source/destination funding journals under the refund contract and release unused liquidity. A hedge may already have executed; its unwind and FX profit/loss are separate economic events. Do not assume the market can be rolled back.

Return after delivery: preserve the successful original payout and create a return case. Record incoming cash, return fees, FX treatment and customer credit using new effect identities. A return is not deletion of the original transaction.

6.4 Intercompany movements

Where the source and destination belong to different legal entities, each entity needs its own balanced due-to/due-from or settlement entries, documented ownership of cash and liabilities, and an approved transfer arrangement. Shared infrastructure does not permit one entity's cash to be silently treated as another's customer funds. Reconcile the intercompany pair, exchange-rate valuation and any settlement separately.

7. Payment state machines

7.1 Separate state dimensions

Store separate dimensions rather than relying on a single linear enum:

compliance: PENDING | APPROVED | REJECTED | EXPIRED
funding: UNRESERVED | RESERVED | BOOKED | UNWOUND
execution: NOT_READY | READY | SENDING | UNKNOWN | ACCEPTED | REJECTED
cash: NOT_OBSERVED | DEBIT_OBSERVED | RETURN_OBSERVED | RECONCILED
delivery: PENDING | DELIVERED | FAILED | RETURN_CASE_OPEN

A public status is a projection of these dimensions plus evidence. SENDING is a local scheduling state, not proof that the bank received a message. ACCEPTED by a provider is not necessarily final delivery. RECONCILED means matched evidence, not that the underlying payment can never be returned under its rail rules.

7.2 Important transition guards

ACCEPTED -> RESERVED requires an admissible compliance decision, a valid quote or pricing contract, customer authorization, sufficient customer funds, sufficient destination liquidity rights, and an open account. Read all financial constraints inside the transaction; do not rely on an earlier balance query.

RESERVED -> READY consumes source funding, creates the paired FX journals, persists the immutable provider request, records dispatch authorization, and advances versions. Recheck the quote's acceptance policy and control evidence. Define expiry against a documented transaction-time/authorization rule; do not claim that an application timestamp comparison alone proves a deadline was met at commit. Apply a safety margin for external execution deadlines and obtain a new customer acceptance where the quote changes.

READY -> UNKNOWN is possible after any send attempt whose outcome is inconclusive. A destination-liquidity reservation cannot be released by a generic expiry job after dispatch authorization. The source hold is already consumed, so compensation requires explicit journals, not simply deleting a hold.

UNKNOWN -> REJECTED requires contractually conclusive non-execution evidence. A provider returning "not found" from a delayed search index is not sufficient. DELIVERED -> RETURN_CASE_OPEN appends a later event; it does not rewrite the original delivery evidence.

7.3 Durable scheduler

Workers claim tasks using a database transaction that checks eligibility and advances a monotonically increasing lease generation. Every state-changing completion checks the expected task generation and payment version. Leases reduce redundant work, but financial correctness comes from effect identities, state guards, and serializable transactions.

A local fencing token does not prevent an already-sent network packet from reaching a bank after the lease expires. That boundary still requires provider idempotency or conservative unknown-outcome handling. Timers are persisted as due-work records, and sweepers find stranded payments from authoritative state even if a broker message disappears.

8. End-to-end idempotency

8.1 API identity

For each mutating endpoint, require an Idempotency-Key and define its scope as (tenant_id, API operation family, key). Keys have sufficient entropy and contain no customer personal data. Hash keys for efficient lookup and minimize exposure in logs; use an unambiguous length-prefixed encoding for tuples rather than concatenating strings that can collide structurally.

The request fingerprint includes every material input: source account, beneficiary token and immutable version, legal entity, source/destination amounts and currencies, quote identity, fee mode, business reference, and semantic API version. It excludes tracing IDs and connection metadata. Preserve array order when meaningful. Canonicalization rules and default values are versioned; compare a replay using the originally persisted canonicalization contract, not newly deployed defaults.

Same key and same fingerprint returns the same operation/result. Same key and a different fingerprint returns a conflict. Reauthorize access on every replay: possession of a previous key is not authorization to read another tenant's response.

Stripe's public API documentation describes storing the original response for an idempotency key, comparing parameters, and allowing key pruning after at least 24 hours. That is a useful public API reference, not an adequate lifetime for our ledger's economic uniqueness records. Our proposed key retention and economic tombstones are separate contracts. [S07]

8.2 Business identity survives a new HTTP key

Require a merchant payment reference unique within the tenant's defined namespace. Persist (tenant_id, merchant_reference) -> payment_id, original_fingerprint atomically with the payment. Two requests with different HTTP keys but the same business reference converge on the same payment or a fingerprint conflict.

The platform cannot infer that two entirely different business references represent the same human intention. That is why the merchant contract must identify retries unambiguously. "Same amount, same recipient, close in time" is not a safe deduplication key because legitimate repeated payments exist.

8.3 Economic-effect identity

Examples are payment/P/funding/initial, payment/P/cash-debit/leg-1, payment/P/discharge/leg-1, and payment/P/return/return-R. The effect record, journal group, balance deltas, hold resolution, payment state and outbox event are one transaction.

Do not derive funding uniqueness from a bank's event ID: two distinct provider events can describe the same cash debit. Event deduplication and economic deduplication are different protections. Likewise, a repeated execution of a worker with a newly generated journal ID must still find the same effect key.

8.4 Retention and recovery

A proposed API-response retention might be 30 days, subject to the product contract. After response archival, retain a compact mapping or return an explicit archived-operation result; do not silently treat a known financial identity as a new payment. Economic-effect identities and business-reference tombstones must survive every supported replay, restore, dispute and migration horizon.

Choose retention with legal and privacy review rather than assuming a universal number of years. Store minimal opaque identities and digests where full responses need not remain online. Any archive restoration must restore uniqueness evidence before enabling financial writes. A backup that restores balances but forgets executed payment identities is dangerous.

Provider key lifetime is independent. A stable key does not make replay safe after the provider forgets it, or outside the provider account/region scope. Adyen explicitly documents that idempotency keys are not checked for duplication across separate regional endpoints; this illustrates why adapter failover must preserve the actual deduplication domain. [S08]

9.2 Other commands

Expose cancellation, return/refund initiation, payment lookup by business reference, authoritative balance queries, and paginated account entries. Each mutation has its own business identity and idempotency scope. Cancellation is a request subject to the actual execution boundary, not a guaranteed rollback.

The private financial API accepts typed commands, expected entity/version constraints, immutable evidence references, and stable effect identities. A generic POST /journals should be restricted to carefully controlled accounting operations, not exposed to merchant callers or arbitrary workflow code.

Situation Contract
Invalid syntax or missing authorization 400/401/403; no financial effect
Same key, different material request 409 idempotency conflict
Correctly evaluated business rejection on a synchronous command Stable 422-style domain result; persist the result under the operation identity

10. Atomic posting algorithm

10.1 Command preparation

Authenticate the caller and validate the structural schema before entering the transaction. Resolve immutable command data, canonicalization version, typed identifiers, and candidate IDs once. Do not perform live bank calls, publish broker messages, send customer notifications, or fetch changing FX prices inside the transaction callback.

The database driver may rerun the callback. A timeout during commit can still mean that the transaction committed; Spanner documents this explicitly. The safe recovery path is therefore the operation/effect identity, not a newly minted replacement payment. A strong lookup that temporarily finds no row is not proof that an in-flight original transaction can never commit: re-enter through the same uniquely guarded command, rather than creating a new identity. [S05, S06]

10.2 Reference pseudocode

def apply_financial_command(command, authenticated_context):
    # Pseudocode: adapter and DB APIs intentionally abstract.
    prepared = prepare_immutable_command(command, authenticated_context)

    def transaction_body(tx):
        existing = tx.read_effect(prepared.effect_key)
        if existing is not None:
            require_authorized_result_access(existing, authenticated_context)
            require_same_fingerprint(existing, prepared)
            return existing.persisted_result

        payment = tx.read_payment(prepared.payment_id)
        accounts = tx.read_accounts_in_sorted_order(prepared.account_ids)
        balances = tx.read_balances_in_sorted_order(prepared.account_ids)
        holds = tx.read_required_reservations(prepared.reservation_ids)
        controls = tx.read_admissible_control_evidence(prepared.control_ids)

        require_authorized_scope(accounts, authenticated_context)
        require_valid_state_transition(payment, prepared, controls)
        plan = build_versioned_posting_plan(prepared, accounts, holds)
        validate_balanced_per_book_and_currency(plan.journals)
        deltas = aggregate_all_account_deltas(plan)
        new_balances = checked_apply(balances, deltas)
        validate_spending_floors_and_reservation_invariants(new_balances, plan)

        # A deterministic domain rejection is persisted as a result,
        # not raised after partially changing any financial state.
        result = construct_stable_result(prepared, plan)
        tx.insert_effect(prepared.effect_key, prepared.fingerprint, result)
        tx.insert_journal_groups(plan.groups)
        tx.insert_journals_and_entries(plan.journals)
        tx.update_balances(new_balances)
        tx.append_reservation_events_and_update_remaining(plan)
        tx.advance_payment_version_and_state(payment, plan)
        tx.insert_outbox_events(plan.events)
        return result

    # SERIALIZABLE is explicit, not an accidental driver default.
    # ABORTED callbacks may repeat. Unknown COMMIT is recovered by key.
    return run_serializable_with_bounded_retry(transaction_body)

A production implementation must implement rejection persistence before the write phase, check database errors precisely, and distinguish a known abort from an unknown commit. Catch only typed deterministic domain rejections: insert their REJECTED effect/result and return normally so that record commits; propagate infrastructure errors for the transaction runner. Insert parent effect/group rows before dependent DML when immediate foreign-key checking requires that order; all rows remain invisible until the same commit. The pseudocode is an algorithm outline, not an executable financial service.

10.3 Why this prevents double effects

Concurrent retries contend on the same unique economic-effect key and the same protected balances. At most one transaction can commit the new effect. A losing transaction aborts or observes the existing effect on retry. Because entries, balances and the effect key share the commit, there is no state in which an acknowledged journal exists but its deduplication key does not.

Two distinct spends from the same account both read and update the same authoritative balance. Serializable isolation prevents both from committing based on an obsolete shared balance. A rejected spend must be re-evaluated after a conflict; never reuse a precomputed "sufficient funds" answer from outside the transaction.

This is a safety argument under the database's stated guarantees and the approved writer implementation. It is not protection against arbitrary privileged SQL, a wrong posting template, or colluding administrators. Those threats require access control, independent audit, testing and operational separation.

10.4 Retry budget and no side effects

Use the supported database SDK's retry semantics, a total command deadline, jitter where appropriate, and load-aware admission. Avoid stacked retries at gateway, service, client library and worker layers that multiply one operation into hundreds of attempts. The command's economic identity remains unchanged across every layer.

Generate no fresh business identity inside a callback. Candidate journal IDs may be allocated outside the callback; only the committed winning result matters. Notifications, event publication and external execution happen from the committed outbox after the callback completes.

11. Reservations, spending and concurrent controls

11.1 Reserve

Read the account's posted net, remaining reservations, configured floor, account state and applicable spending-right allocation. Compute the new reserve using exact checked arithmetic. If it would violate the floor, persist a deterministic rejection for the synchronous command without changing money. Otherwise create the reservation event and update reserved_out and balance version atomically.

For customer USD 100 available, concurrent requests to reserve USD 80 and USD 30 cannot both succeed. Their transactions share the same balance row or the same explicitly allocated spending-right partition. An eventually consistent sum of reservations is not a valid substitute.

11.2 Capture

Capture checks the reservation identity, owner, currency, remaining amount and payment state. It consumes Y of remaining reserve, reduces reserved_out by Y, and posts the customer debit in the same transaction. For a customer liability, the posted net and reserved amount both decrease by Y, so spendable balance does not jump unexpectedly.

The entire posting plan is aggregated by account before checking final balance constraints. A multi-entry command that debits and credits the same account must not depend on arbitrary entry iteration order. However, netting is permitted only within an approved atomic business template, not across unrelated customer obligations.

11.3 Release, expiry and credit facilities

Release reduces remaining reserve and restores spending rights without reversing a posted economic debit. It is allowed only while the reservation still exists and the execution state makes release safe. Once source funding is booked, cancellation uses explicit reversal/compensation journals instead.

A payment queued for manual review can expire only under an approved policy that checks no external authorization or execution is outstanding. An unknown payout cannot become an ordinary expired hold. Authorized overdrafts use a configured negative floor and a separately tracked credit exposure; they must not emerge from a race or a signed-integer underflow.

12. External provider protocol

12.1 Adapter capability contract

Each provider integration must declare: account and regional idempotency scope, key format and lifetime, supported replay behavior, whether inquiry is authoritative, reference uniqueness, cancellation guarantees, partial execution support, callback authentication, statement availability, rate limits, business-day behavior, and the distinction between receipt, acceptance, debit and finality.

Version that capability contract alongside adapter code and bank certification evidence. A provider's informal statement that requests are "usually deduplicated" is not a safe basis for automatic retry of money movement.

12.2 Persist before sending

Create an immutable provider attempt before network egress. It contains payment/disbursement identity, bank account and endpoint domain, stable request key, exact amount and currency, beneficiary snapshot, request schema version, canonical payload digest, applicable approval evidence and an explicit authorization state.

The worker obtains a fenced claim, reads that saved request, and sends the same economic instruction. Request bytes may contain transport-layer differences such as a new authenticated timestamp only where the provider permits them without changing the idempotency fingerprint. Never regenerate beneficiary details or FX amounts from mutable current records during retry.

12.3 Unknown outcomes

There are three meaningful results: proven execution, proven non-execution, and unknown. A timeout is the third, not the second.

For a provider with a valid strong idempotency contract, retry the original key and payload within its scope and retention window. Query by the original reference, ingest callbacks, and reconcile statements. For a provider without that guarantee, prefer inquiry and manual/automated investigation over resubmitting an unresolved debit. There is no local database transaction that can atomically commit with an arbitrary bank HTTP server.

UNKNOWN must have operational deadlines, an accountable owner, and the consumer-protection treatment required by the actual product and jurisdiction. If a customer must be credited before execution is resolved, record a separately approved, platform-funded compensation or loss provision. Keep the original payout unresolved and do not reuse its identity for a replacement disbursement.

A worker lease or local fencing token cannot retract a delayed packet already sent to the bank. A stale worker can still reach an external server unless the server itself enforces a fence or the economic idempotency key. Consequently, the design does not claim unconditional exactly-once external payment execution.

12.4 Provider failover

Fail over to another provider only before any potentially executing attempt, after conclusive non-execution, or after a cancellation whose contract proves no later execution is possible. Reusing the same text key at another provider does not share the first provider's deduplication store.

Persist the failover decision, evidence and new attempt identity. The new attempt still belongs to the same disbursement obligation, so funding and payout-liability effects are not booked again. For an unresolved first attempt, failover is blocked even if that reduces corridor throughput.

12.5 Files, batches and ISO 20022

Some banks require files or batches rather than one payment per API request. Preserve both batch identity and item identity, immutable file digest, submission receipts, per-item outcomes, and resubmission rules. Do not resend an entire partially accepted batch as a fresh file.

Use the bank's supported ISO 20022 or proprietary message versions, validate schemas and business usage rules, preserve originator/beneficiary information and reference mapping, and test truncation/character-set behavior. The ISO 20022 catalogue provides message definitions, schemas and usage documentation, but an individual bank's implementation guide determines the accepted profile. [S19]

13. Outbox, inbox, callbacks and delivery

13.1 Producer outbox

Insert an outbox record in the same transaction as each authoritative state transition. Give the event a stable ID, aggregate identity, aggregate version, schema version, payload digest and commit timestamp. The relay publishes the event and only then marks its delivery attempt successful.

A crash after publish and before marking success causes a duplicate; that is intentional. A crash before publish leaves durable work. Never mark an event sent before the broker acknowledges it. Pub/Sub's default subscription behavior is at-least-once delivery without ordering guarantees, so consumers must tolerate both duplicate and reordered messages. [S09]

Use bucketed due-work indexes, bounded claims, retry times and periodic scans of unpublished rows. Do not use a naked created_at > last_seen query that can skip commits or equal timestamps. Commit timestamps are useful metadata, not an automatically unique global event sequence. A polling design must prove completeness; the simple initial design scans durable due/unpublished work rather than guessing a global high-water mark.

The outbox is a delivery mechanism, not a permanent guarantee that every consumer will run before message retention expires. Keep sufficient replayable domain history, expose consumer lag and reconcile stranded authoritative payment states with periodic sweepers. Restore and migration procedures must also rebuild scheduling from state.

13.2 Consumer inbox

A financial consumer atomically inserts (consumer_id, event_id) into its inbox, applies the permitted state/economic effect and writes any resulting outbox event. It acknowledges the broker only after that database transaction commits. If the ACK is lost, the next delivery finds the inbox record and does not repeat the effect.

Where two different events describe the same financial occurrence, the economic-effect key is the final duplicate guard. This prevents "deduplicated event delivery" from being mistaken for "deduplicated money." A broker's exactly-once feature, where available, is not a substitute for this database boundary.

13.3 Ordering

Every payment state change advances an aggregate version. Read-model consumers detect gaps and can fetch an authoritative snapshot. A projection may replace its older state with a newer snapshot after validating version semantics. A financial consumer may not skip a missing financial event merely because a newer payment snapshot exists; it must apply the required economic effects or recover them from authoritative evidence.

Ordering keys can improve efficiency, but they are not the correctness mechanism. No design relies on a single worldwide Kafka partition, one global sequential journal ID, or provider wall-clock timestamps for causal order.

13.4 Callback ingestion

Verify the provider signature against the raw body, authenticate the endpoint scope, enforce size limits, check replay policy, and persist the raw payload or encrypted evidence reference plus digest. Return success after durable ingestion, not after all downstream business processing. If durability is unavailable, return a failure that preserves the provider's retry opportunity.

Separate duplicate delivery ID from duplicate economic content. When payloads with the same provider event ID disagree, quarantine the discrepancy instead of overwriting the first evidence. Provider callbacks can be duplicated and out of order; Stripe documents this explicitly for its webhook model. [S10]

Match unmatched callbacks to a durable investigation queue. A callback arriving before the synchronous submit response is normal and must be matchable by the saved request/reference, without needing the original worker to still be alive.

13.5 Customer webhooks

Expose stable platform event IDs, aggregate versions and a GET endpoint that gives current truth. Sign outbound payloads, rotate keys with an overlap policy, retry with bounded backoff, and provide replay tooling. Customer webhook failure must not roll back a financial journal. Persist delivery history without leaking account numbers or personal data into generic logs.

14.2 Physical key design

Use random or hash-distributed primary identities for high-volume insert tables. Spanner documents that monotonically increasing leading keys can create hotspots; a timestamp or sequential ID at the front of every journal key is therefore a poor default. [S12]

Keep an account-history index beginning with account_id, followed by an account version or commit marker and a unique tie-breaker. Do not let clients choose that prefix. Benchmark the actual index layout, including write amplification and contention, before deployment.

14.3 Transaction shape and bounds

As an initial guardrail, bound ordinary posting commands to a small number of accounts and at most 32 journal entries; tune this after measurement. The limit protects latency, contention and reviewability. Huge settlement batches should be decomposed into independently identifiable balanced items and linked by a batch manifest, not one enormous financial transaction.

Use prepared statements and explicit field lists. Reject unexpected account classes, currencies and legal entities before constructing entries. Avoid ORM-generated full-table scans and hidden autocommit transitions. Keep the transaction body free of cross-service RPCs and unbounded reads.

14.4 Constraints are necessary but not sufficient

Row-level checks can enforce positive amounts, legal enum values, nonnegative reserve components, and local arithmetic. Foreign keys can enforce parent relationships and book/currency alignment. A normal row CHECK cannot prove that all entries of an arbitrary multi-row journal balance.

Therefore the posting engine is the only authorized writer, with approved templates and transaction-level sum validation. Restrict direct table modification, separate routine and break-glass roles, record administrative access, and run independent consistency scans. A database constraint does not replace controller approval of a financially wrong but mathematically balanced template.

15. Treasury, liquidity and hot accounts

15.1 Cash is not identical to a cached bank balance

Maintain a destination-liquidity budget derived from ledger cash, known outgoing reservations, bank-credit arrangements, unsettled debits, expected incoming funds, and an uncertainty buffer. Only sufficiently evidenced incoming cash increases spendable rights. A stale statement or provisional credit must not automatically finance a payout.

Where other systems can debit the same bank account, the platform cannot mathematically guarantee non-overdraft using only its own ledger. Either control all debits, establish a bank-enforced limit or credit facility, or model the residual uncertainty as an explicit treasury risk with conservative allocation.

15.2 Partition shared spending rights

A single omnibus account updated by every payment becomes a serialization hotspot. Partition its operational budget into explicit subaccounts or buckets. Each bucket owns real spending rights; the sum of allocated rights is bounded by the authoritative budget. Rebalancing atomically transfers rights between buckets rather than copying a shared balance to multiple writers.

Likewise, post fee revenue to purpose-equivalent partitioned accounts and consolidate in reporting. Do not perform a synchronous update of one global revenue-total row for every payment.

A truly indivisible customer account with arbitrary concurrent spending has an unavoidable coordination point. More application pods cannot remove that constraint. Use backpressure, per-account fairness, batching of compatible operations, and explicit subaccount products rather than claiming unlimited per-account write scaling.

15.3 Quote liquidity and hedging

Separate customer quote commitment, destination cash availability, and market hedge execution. Their risks differ. A quote accepted by the customer may create market exposure before a hedge executes; an executed hedge may survive a payout rejection. Record those obligations and link the hedge independently.

Stress test corridor liquidity under provider outage, delayed incoming settlement, concentrated merchant demand, holidays, and abrupt FX movement. Provider routing must consider liquidity and execution uncertainty, not merely choose the cheapest API at the moment.

16. Cross-cell and cross-entity orchestration

16.1 Prefer local atomicity when lawful

When both legs are in the same database and approved residency domain, commit the multi-journal group atomically. This is the simplest correct path. Do not introduce a saga merely because the system is described as distributed.

When legs are in different databases, simultaneous visibility and global atomic rollback are not available from the local transaction mechanism. Use a documented business protocol with explicit in-transit obligations.

16.2 Durable cross-cell protocol

Assign a globally unique transfer identity, immutable terms digest, source participant, destination participant, coordinator home and protocol version. Each participant records its own reservation/preparation idempotently and returns durable evidence. Preparation must include the legal credit/liquidity permissions needed to honor a later commit.

After all required preparations, the coordinator writes a single durable decision: COMMIT or ABORT. A recorded COMMIT cannot become an ABORT because a worker timed out. Each participant applies its local balanced due-to/due-from or in-transit entries using stable effect identities and acknowledges the committed result.

The destination's customer-spend or bank-dispatch gate opens only after the required source and destination committed-leg evidence exists. Incomplete committed legs remain recoverable obligations; sweepers and reconciliation drive them forward. The overall transfer can be IN_TRANSIT while each local book remains balanced.

16.3 Important limitations

This protocol has distributed-commit-like blocking behavior during partitions. After preparation, participants cannot independently expire reservations while a durable commit decision might exist. They must resolve the coordinator decision, or the protocol must explicitly guarantee that commit is impossible after a pre-agreed expiry. Do not combine an unconstrained coordinator commit with independent participant timeout release.

A coordinator outage can therefore reduce liveness. That is an explicit safety tradeoff, not an implementation bug to "fix" with blind refunds. Prefer bounded financial cells and local atomic groups to minimize this path.

Across separate legal entities, intercompany balances, transfer limits, functional-currency valuation and settlement evidence remain required. Across independent banks or FX markets, this application saga is not a payment-versus-payment settlement guarantee. External settlement risk needs a separate approved arrangement.

17. Read APIs, history and auditability

17.1 Read consistency contract

Authoritative balance and reservation decisions read the financial database in the same transaction that changes spending rights. Customer timelines, search and analytics may use projections, but expose an as_of marker or version and never silently represent a stale view as a current authorizing balance.

A command response identifies the resulting payment/account versions. A subsequent client read can request at least that version or be routed to an authoritative strong read. A follower/stale-read optimization is acceptable for statements and browsing only when the product explicitly allows it.

17.2 Time and periods

Store database commit time, provider event time, receipt time, contractual effective/value date, accounting period, and evidence source separately. They answer different questions. Do not use an untrusted provider timestamp to reorder committed account mutations.

Backdated evidence creates a newly recorded event with an earlier effective date. Closed-period corrections follow controller policy, typically using an adjustment in an open period with a reference to the original period. Never rewrite historical commit time or pretend late-arriving evidence was known earlier.

For reports, distinguish "effective by date D" from "known as of time T." Reconstruct reports from immutable entries, period snapshots and manifests. Short database version retention is not a substitute for a multi-year accounting-history design.

17.3 Tamper evidence

Create immutable journal/evidence manifests in an independently permissioned storage domain. A manifest contains the complete deterministic set of included records, their hashes, range or batch identity, prior-manifest hash, generation time and signature. Seal only a range whose completeness is established; a casually sampled timestamp interval is not sufficient.

Hash chains or Merkle roots help detect later tampering when roots are independently retained. They do not stop an authorized service from posting a fraudulent but balanced journal, and they do not create trust if the same compromised administrator can replace both data and roots. Separate administration, approval, retention locks and periodic external verification matter.

Keep signing asynchronous to the posting path and alert on seal lag. Never let an unavailable audit dashboard or signing job silently disable journaling; retain pending evidence durably and apply a defined maximum-lag risk policy.

18. Reconciliation and financial controls

18.1 Internal consistency controls

Continuously sample and regularly fully scan journal balance, journal/account currency alignment, account-balance replay equality, reservation sum equality, unique effects, valid state transitions, and linked journal-group completeness. Run these from independent code paths rather than reusing the same posting function that might contain the original bug.

Some full checks are expensive; partition them with coverage manifests so that "the checker ran" is not mistaken for "all data was checked." Alert on the last fully verified interval and on uncovered partitions.

18.2 External matching

Reconcile three independent evidence sets: internal financial entries, provider execution facts, and bank/settlement cash movements. Match first by immutable references and scopes, then verify currency, amount, account, value date and relevant fee components.

Support one-to-many and many-to-one relations: one bank batch debit can settle many payouts; one payment can generate principal, fee and return movements. Keep statement versions and correction records. A corrected statement is new evidence, not an overwrite of the original observation.

Fuzzy matches may suggest a case resolution but must not automatically create money. Unexplained cash becomes a controlled suspense or investigation item using an approved template. Preserve the uncertainty rather than force-balancing to make a dashboard green.

Deduplicate repeated reports of the same cash movement, not distinct cash movements. If a provider actually executes two bank debits for one intended payout, both real debits must be represented. The unexpected second debit gets its own evidence-scoped adjustment/suspense effect and incident, rather than being discarded by the original payment effect key. Business idempotency prevents intended duplicate execution; it must never hide an externally created cash loss.

18.3 Exception operations

Every break has amount, currency, affected entity, expected evidence, age, owner, severity, investigation log and resolution. Prioritize monetary exposure as well as count: one large unknown payout can matter more than thousands of harmless delayed notifications.

Operational adjustments require a typed correction command, reason code, supporting evidence, two-person approval above defined limits, and an idempotency identity. The correction links to the case and original journal. No analyst edits an account's balance field directly.

Reconciliation freshness targets vary by rail and statement delivery frequency. Real-time reconciliation should not claim knowledge that only the bank's end-of-day statement can establish. Conversely, daily statements do not justify ignoring available real-time callbacks and inquiry results.

19. Availability engineering and capacity

19.1 Regional service design

Run stateless APIs and workers across independent failure domains, with warm connections, pre-established identity credentials, pre-approved provider egress IPs, and capacity in surviving serving regions. Do not rely on an autoscaler, container registry, DNS change or certificate issuance completing during the incident.

Use provider-supported database endpoints and transaction clients rather than attempting application-side consensus. Readiness checks should verify meaningful service capability without making every pod flap because a noncritical reporting dependency is down. Circuit breakers isolate banks and downstream consumers; they do not fabricate financial success.

19.2 Capacity envelope

With the explicit reference assumptions:

1,000 payments/s average * 86,400 s/day = 86.4 million payments/day
10,000 payments/s peak * 5 write transactions/payment = 50,000 tx/s peak
1,000 payments/s average * 10 journal entries/payment = 864 million entries/day

At 6 KiB total logical data/payment:
86.4 million * 6,144 bytes = 530.84 GB/day, before replicas,
secondary-index amplification, backups, archives and operational evidence.

At 16 uniformly loaded cells:
50,000 / 16 = 3,125 financial/workflow write transactions/s/cell at peak.

These are workload calculations, not throughput claims about a particular database configuration. Large-tenant skew, hot accounts, index maintenance, response payloads and legal placement can dominate the uniform calculation. The 6 KiB assumption includes the modeled journal and workflow metadata; do not add the same entry bytes again without distinguishing categories.

Benchmark actual posting shapes and conflict rates. Separate new-payment load, retries, callbacks, inquiry, sweeps, reporting, backfill and restore validation. A retry storm can exceed normal business traffic even when new payments decrease.

19.3 Failover headroom

Each surviving application region must be able to handle the full admitted workload plus a measured retry and recovery margin. As a simple illustration, provisioning each of two serving regions for 1.5 times total peak load means normal split traffic uses roughly one-third of each region's capacity and single-region operation uses roughly two-thirds. This is application capacity arithmetic, not a Spanner sizing formula.

Test database capacity under regional failover separately. Managed replication does not imply that latency, lock contention and client routing remain unchanged. Keep admission thresholds below the point where retries amplify overload.

19.4 Backpressure and fairness

Use bounded queues and per-tenant/per-account concurrency controls. Prefer shedding new, nonessential work over starving callbacks that resolve existing financial exposure. Give unknown-outcome inquiry, return processing, reconciliation and already-authorized execution explicit reserved capacity.

A temporarily queued payment can remain accepted, but expose its age and enforce a product-level maximum delay or cancellation policy. Infinite acceptance into an unbounded queue is not a viable five-nines payment product.

19.5 Control-plane independence

Cache public verification keys, signed routing metadata and bounded-lifetime configuration. Keep deployment orchestration, feature-flag control services, provisioning and analytics out of the ordinary financial transaction path. However, authoritative account freezes, spending controls and evidence freshness must still be checked in the financial command's scope.

Cache tolerance is a specific policy. It is not permission to ignore sanctions freshness, credential revocation or a customer-account freeze. When a mandatory control cannot be satisfied, pause the affected execution safely and report its real state.

21. Security, privacy and regulatory architecture

21.1 Trust boundaries

Use workload identity, authenticated encrypted service communication, least-privilege database roles and strongly separated provider credentials. Merchant credentials cannot call private posting APIs. Adapters cannot choose arbitrary debit accounts. Operators cannot execute unrestricted balance updates.

Bind every request and evidence record to tenant, legal entity, provider account and intended operation. Tenant IDs supplied in JSON are not authorization. Resolve scope from authenticated identity and validate every referenced account and beneficiary against it.

21.2 Sensitive data and cryptography

Store opaque beneficiary/account tokens in the journal and keep sensitive bank details in an access-controlled vault. Preserve immutable beneficiary versions so retries do not silently pay a newly edited account. Separate key-management and data-administration privileges; test rotation and recovery without assuming keys can be fetched during a regional incident.

Our design prohibits storing card verification codes, PIN material or full sensitive authentication payloads in ledger rows, generic logs, outbox messages or analytics. Where card data is in scope, the actual environment and controls require PCI assessment; tokenization reduces exposure but is not a blanket compliance claim.

HSM-backed or managed signing/encryption keys are appropriate for provider messages, audit roots and sensitive data protection. Avoid a fresh remote KMS call for every non-sensitive ledger arithmetic operation. At the same time, design for the real failure behavior of encryption-key dependencies; an unavailable or revoked key can make otherwise healthy storage unusable.

21.3 Financial-crime controls

Record originator/beneficiary information references, screening decision, source-list/model version, purpose, corridor, approval time, expiry and reviewer evidence. Re-screen or block execution under the approved risk policy when details change or evidence becomes stale. A compliance outage can leave a durable intent pending; it cannot justify releasing an unscreened payment.

FATF revised Recommendation 16 in June 2025 and describes implementation changes taking effect by the end of 2030. That is a reason to version message and control schemas, not to claim that every future requirement already applies in every jurisdiction. Local implementation dates and the platform's obligations require current jurisdiction-specific legal review. [S20]

21.4 Abuse and insider risk

Protect idempotency endpoints from unbounded key creation, oversize stored responses and cross-tenant key probing. Limit record sizes and request rates without evicting financial uniqueness evidence. Rate-limit inquiry and replay tools separately from customer payments.

Require step-up authorization and two-person approval for high-risk adjustments, bank-credential changes, payout-route changes and recovery egress reactivation. Log the approving identities and exact command fingerprint. A cryptographically signed but financially unauthorized adjustment is still unauthorized.

22. Observability and incident detection

22.1 Technical indicators

Track eligible command success and latency, database abort/retry rates, unknown commits, connection/session health, worker claim age, outbox/inbox lag, regional request distribution, per-account contention, queue depth, admitted versus rejected traffic, and error-budget consumption. Use exemplars or traces for payment IDs; do not make every account or payment a metric label.

Trace one operation across API, payment, effect, journal group, provider attempt, observation and reconciliation case. Keep those identifiers in structured logs with field-level redaction. A request ID alone is insufficient because retries have different request IDs but the same economic identity.

22.2 Financial indicators

Monitor unexplained journal imbalance, replay mismatch, reserve mismatch, negative protected balances, duplicate economic-effect conflicts, unmatched cash, suspense aging, unknown external amount, unhedged FX exposure, intercompany breaks, unexpected fees, and near-exhausted liquidity buckets.

A single nonzero integrity violation should page and trigger a scoped financial-write quarantine. Do not average it away as an acceptable error rate. Technical availability can be excellent while the money is wrong.

22.3 Error-budget alerting

For five nines, the target bad-event ratio is 1e-5. A burn rate of 14.4 corresponds to a bad-event ratio of 1.44e-4 (0.0144%); a burn rate of 6 corresponds to 6e-5 (0.006%). Multiwindow alerts can combine 1-hour/5-minute and 6-hour/30-minute windows, with low-volume safeguards and separate integrity paging. This follows the SRE multiwindow burn-rate approach; tune it to actual traffic and incident response. [S13]

Do not aggregate away a broken cell or low-volume corridor. Use per-cell objectives, synthetic authenticated probes, time-based black-box checks and amount-weighted exposure views alongside the platform-wide request ratio.

23. Backups, disaster recovery and replay

23.1 Backups are not regional failover

Regional failover should use the synchronously replicated live database. Backups protect against logical corruption, operator mistakes and catastrophic scenarios. They have different recovery time and recovery-point properties.

Spanner PITR is a bounded historical-version facility, not indefinite accounting storage; its documentation currently describes a maximum seven-day retention option and recovery into a new database for full restoration. Preserve longer-lived evidence and backups independently according to the approved policy. [S14, S15]

23.2 Restore protocol

First fence financial egress and stop unsafe resubmission. Restore into an isolated database, verify schema and privileges, compare balances and manifests, and recover identities and evidence for activity after the chosen snapshot. External banks do not roll back when the database does.

Reconstruct missing economic effects from independent immutable evidence, provider inquiries and bank statements. Mark unresolved attempts UNKNOWN. A retained outbox from the restored snapshot must not be blindly replayed to external rails: some of those payments may already have executed after the snapshot.

Apply the correct access policies and operational configuration to the restored environment; do not assume every IAM, stream, retention or scheduling setting is contained in database data. Validate the actual restore procedure in an isolated project and record its measured runtime. [S15]

Resume only classified-safe financial work, beginning with a canary and two-person approval. Reconciliation and callback ingestion need dedicated recovery capacity. A rare full restore may exceed the five-nines outage budget; this must be disclosed in the fault model rather than hidden behind an ordinary regional-failover claim.

23.3 Replay modes

Define separate tools and permissions for read-model rebuild, internal ledger verification, missing-effect recovery and external resubmission. Default all replay tooling to no external egress. Restoring a customer timeline must never trigger a bank transfer.

Preserve original economic keys across replays. Use a separate replay-job identity for audit, not as a replacement payment/effect key. Require explicit authorization and provider-contract checks before any external resubmission.

24. Verification and adversarial testing

24.1 Reference model and property tests

Build a small exact-arithmetic model independent of production persistence. Generate operations including deposits, reserves, partial captures, releases, fees, FX pairs, cancellations, returns and duplicate requests. After every operation, check conservation per book/currency, protected spending floors, reservation equations, unique effects, and deterministic replay.

Test arithmetic boundaries, currencies with different exponents, fee rounding, zero/negative amounts, oversized values, and malformed canonicalization. Two syntactically different but semantically identical requests must behave according to the explicitly defined canonical contract, not an accidental serializer behavior.

24.2 Concurrency histories

Run concurrent spends against the same account, capture-versus-release races, expiry-versus-dispatch races, duplicate effects with changed payloads, and cross-account cycles. Record invocation, completion and commit evidence. Check histories against the intended serializable/state-machine model, including unknown outcomes.

A unit test using a mocked transaction object cannot prove distributed correctness. Test the deployed database client, schema, network behavior and retry configuration in a production-like environment. The emulator is useful for development but is not a substitute for regional failure and performance testing.

24.3 Failure injection matrix

Kill a process before and after every durable boundary. Drop the API response after commit. Drop the bank response after executing the fake bank debit. Redeliver callbacks with reordered versions. Expire a provider's deduplication window. Partition a worker after its claim and let a replacement proceed. Disable a serving region. Exhaust a connection pool. Delay compliance evidence. Restore an old snapshot while the fake bank retains its newer state.

The fake provider should maintain an independently modeled bank account and support deliberate weak behaviors: delayed search visibility, duplicate callback IDs, partial acceptance, batch-item failures, and final delivery before statement arrival. Test both strong-idempotency and no-idempotency capability profiles.

24.4 Formal state exploration

Model reservation and execution authorization with a small state space: two workers, a finite balance, a source hold, one provider attempt, a coordinator decision, and delayed messages. Check that no state allows both unsafe release and possible execution, and that a recorded COMMIT cannot be followed by an abort-driven refund.

Distinguish safety from liveness. A model may correctly block forever under permanent quorum loss; it must not "solve" liveness by allowing both sides to spend. Document the recovery assumptions required for eventual progress.

24.5 Acceptance evidence

Before launch, require: no invariant violations in generated and adversarial tests; independent controller approval of every posting template; observed behavior under regional loss; proven unknown-outcome recovery; exact restore-and-reconcile exercise; capacity tests with tenant/account skew; and operational ownership of all exception types.

Passing these tests increases confidence but does not certify the actual five-nines result. That objective is measured in service over time, including deployments and operational errors.

25. Runbooks

25.1 Serving-region failure

Confirm the fault and supported database failover state; avoid operator promotion of an independent stale copy. Verify surviving application capacity, provider allowlists and key availability. Reduce nonessential reporting/backfill load, monitor retries and protected queues, and keep unresolved external attempts on their original identities. Record actual SLO impact and compare it with the budget.

25.2 Unknown payout

Freeze unsafe reroute and refund actions. Inspect immutable request, scope, send history, provider-key expiry and latest evidence. Inquire by original reference and match callbacks/statements. If execution is proven, apply only missing effects; if non-execution is conclusive, authorize a controlled unwind or replacement attempt; otherwise retain UNKNOWN and escalate by age and amount.

25.3 Ledger or reserve mismatch

Quarantine the smallest affected financial scope. Preserve evidence, stop risky automated corrections and run an independent reconstruction. Determine whether the cause is an incorrect template, unauthorized write, incomplete migration, or software defect. Correct using approved new entries and repair materialized state only under a verified recovery procedure. Never force the balance to an expected number just to clear an alert.

25.4 Provider outage

Stop opening additional exposure beyond the corridor's risk limits. Continue ingestion of delayed evidence and resolution of existing attempts. Queue safe new instructions only within the disclosed product delay policy. Fail over only for unsubmitted or conclusively non-executing obligations. Communicate execution delay separately from ledger availability.

25.5 Compromised credentials

Disable affected egress and credentials, preserve provider observations and audit data, scope possible unauthorized attempts, rotate through an approved recovery route and reconcile the bank account independently. A credential incident may require financial containment even while the ledger itself is healthy.

26. Deployments, schema evolution and cell migration

26.1 Release safety

Deploy to one low-risk cell and corridor first, with a staged traffic increase and separate technical/integrity gates. Use expand/contract schemas, backward-compatible event envelopes, pinned posting-template versions and deterministic migration tools. An application rollback must not reinterpret historical journals under a newer or older rule.

Never update all cells and all provider adapters simultaneously. Feature flags controlling financial behavior require signed/versioned configuration, an audit trail and a defined stale-policy fallback. Keep the ability to stop new dispatch while preserving callbacks and reconciliation.

26.2 Shadow operation

A shadow ledger computes proposed entries and compares outcomes against the current authoritative system. It has no bank egress and cannot create customer-spend authority. Shadow balances are validation evidence, not a second live financial book.

Compare exact amounts, currencies, fees, hold behavior and case handling, not merely transaction counts. Investigate every difference rather than auto-accepting a numerical tolerance for ledger amounts.

26.3 Authority migration

Move accounts and business identities only with a deliberate authority protocol. Establish a migration epoch, fence writes in the old authority for the migrating scope, copy a consistent snapshot and replay complete deltas, migrate operation/effect tombstones, verify balances and holds, and atomically switch the routing authority according to the migration design.

Old endpoints must forward or return a stable relocation response; they must not become writable again because their local directory cache is stale. Retain sufficient tombstones and evidence so retries crossing the migration boundary converge on the same payment. A migration cannot solve latency by temporarily permitting two independent authorities for the same funds.

A brief scoped write pause may be the safest first migration implementation. Account for that in the affected service objective; do not label a pause as zero-downtime without measuring its actual client impact.

28. Production readiness gates and implementation sequence

28.1 Build order

First define legal-entity books, account purposes, money types, posting templates and invariants. Implement the exact-arithmetic model and a single-cell financial kernel with economic deduplication, reservations and immutable journal history. Add independent replay verification before adding multiple banks.

Next implement durable payment acceptance, database-backed tasks, outbox/inbox and the provider simulator. Exercise unknown outcomes and reconciliation using one corridor. Introduce the first real provider only after request identity, finality semantics and recovery behavior are contractually understood.

Then implement regional failover, capacity isolation, control-evidence freshness, audited operator tooling and full recovery drills. Add additional cells only when residency, risk isolation or measured load requires them. Add cross-cell transfers last, after the local invariant model is stable.

28.2 Go-live evidence checklist

Finance: approved account chart; fee/revenue timing; FX and hedge treatment; safeguarding/intercompany policy; late-return and period-close templates; suspense ownership.

Correctness: effect uniqueness; same-key conflict behavior; overspend and hold-race tests; replay equivalence; independent invariant checker; no external side effects in retried database callbacks.

Providers: documented deduplication scope/lifetime; authoritative inquiry semantics; callback authentication; batch partial-success behavior; regional egress readiness; statement mapping; unknown-outcome operating procedure.

Reliability: per-cell SLO measurement; warm regional capacity; retry limits; dependency outage tests; measured failover impact; replay/backlog capacity; overload fairness; release rollback procedure.

Recovery and security: fenced egress during restore; preserved identity/evidence; proven restore-and-reconcile drill; least privilege; key recovery; adjustment approvals; privacy and jurisdiction-specific retention review.

Operations: 24/7 accountable ownership; trained incident commander; ledger/treasury/controller escalation; unknown-payout and mismatch runbooks; bank escalation contacts; client-facing delay semantics.

28.3 Decisions that cannot responsibly be invented

Before a production launch, the team must supply its actual legal entities and country/corridor matrix, cloud and residency approvals, bank agreements, settlement-finality definitions, supported funding types, credit policies, customer contract, expected account/tenant skew, retention obligations, staffing model and acceptable tail latency. These are configuration and governance inputs to this architecture, not details that a generic system diagram can determine.

The proposed architecture preserves a clear safety boundary while those choices are finalized. It does not substitute an assumed license, an unverified bank promise or a vendor SLA for production evidence.

Appendix C. Acceptance and external-send algorithms

C.1 Durable acceptance transaction

authenticate and validate the API envelope
read scoped idempotency key
  if present: reauthorize; compare using stored canonicalization; return saved response
read tenant/business reference
  if present: compare immutable business fingerprint; reuse payment identity
  otherwise: create payment identity and immutable request snapshot
insert the new API-key mapping and stable acceptance result
insert payment event/outbox only when the underlying payment is new
commit
return 202 only after an acknowledged commit
on commit uncertainty: retain the same key and business reference for recovery

The original business request snapshot must be sufficient to reconstruct the creation contract without live calls to mutable beneficiary, pricing or defaults tables. A newly submitted key must not bypass the merchant reference's uniqueness.

C.2 Provider-send worker

claim authorized attempt using a transactional generation check
load immutable request + capability profile + provider scope
if any earlier attempt for the same obligation is unresolved:
    do not create a replacement attempt
if state or key lifetime makes replay unsafe:
    schedule inquiry / case; keep UNKNOWN
else:
    send only the saved economic request under its original provider key
    persist response or timeout observation durably
    invoke the idempotent normalization command
    release the local scheduling claim conditionally

The claim is not an external exactly-once guarantee. The capability profile determines whether concurrent/late sends are harmless duplicates or unsafe requests. The worker must never call the provider from inside a retryable database transaction.

C.3 Effect recovery

read operation/effect using the original identity
if a committed result exists:
    return it without reapplying money
if no result is visible:
    repeat the guarded command with the same identity
    do not infer original abort merely from one negative lookup
if authoritative reads are unavailable:
    preserve uncertainty and return a retryable result

Caller-provided request identities, semantic-equivalence checks and treatment of late-arriving requests are also described in AWS's retry-design guidance. Our design extends that contract across the full financial recovery horizon. [S18]
