Orientation and evidence

Research snapshot: 27 September 2026. Independent engineering study. Public documentation, historical architecture disclosures, versioned API contracts and an original reference implementation are treated as different kinds of evidence.

This playbook is for storage engineers, distributed-systems engineers, backup administrators, platform architects, security teams and founders building a data-protection company. Its central question is not simply whether a system can copy bytes. It is whether an authorized operator can reconstruct a trustworthy application, from the correct point in time, after infrastructure, identity or production data has been damaged.

Cohesity's portfolio spans more than one storage and protection engine. A useful engineering analysis must preserve those boundaries. The book therefore studies DataProtect and SpanFS, the NetBackup lineage and its integration with SpanFS, cyber-vault and recovery services, management APIs, and adjacent file and AI services. It then develops a separate build-from-scratch design. It does not claim access to private source code, unpublished protocols, production configurations or customer deployments.

The recovery contract: A backup is useful only when its content, metadata, cryptographic keys, authorization path and application dependencies can be recovered together. A green backup job, an immutable object and a running virtual machine are three different facts, none of which alone proves business recovery.

Evidence labels

PUBLIC identifies a documented product capability or API contract. HISTORICAL identifies an older technical disclosure or patent; it is not a current implementation specification. PROPOSED identifies this book's engineering design. VERIFY identifies a compatibility, version, entitlement, performance or operational fact that requires the deployed environment and current vendor support evidence.

Source references such as [S04] link to the source registry. Vendor performance claims are not treated as independently reproduced benchmarks. A page advertising a capability does not establish every workload, release or topology that supports it. Some DataProtect 7.4 documentation requires authentication; inaccessible contents were not reconstructed or invented. [S10]

Reading paths

For storage internals, read Chapters 3-12, 21, and 36-38. For protection and recovery operations, read Chapters 13-24, 33-35 and 41-43. For NetBackup integration, read Chapters 27-29 before assuming any SpanFS behavior applies. For APIs, begin with Chapters 31-32 and then the proposed schema and transaction boundary in Chapters 37-39. Founders should add Chapters 2, 34, 40, 42 and 44.

The companion is a small local model for reasoning about snapshot publication, retention, shared chunks, approvals and uncertain external restore outcomes. It is not SpanFS, NetBackup, a distributed database, an encryption system or a production backup agent.

01. Portfolio boundaries and the engineering map

PUBLIC. Cohesity completed its combination with Veritas' enterprise data protection business on 10 December 2024. This brought NetBackup and associated enterprise protection capabilities into the portfolio; it did not imply that every product previously sold by Veritas became Cohesity, or that all acquired software was rewritten on one engine. [S02]

Think in layers rather than one product list. The first layer is the storage substrate: SpanFS for the Cohesity lineage and supported storage mechanisms, including MSDP, in NetBackup deployments. The second is protection orchestration: source discovery, consistency coordination, policy scheduling, cataloging and restores. The third is management and security: Helios, access control, posture, threat analysis and cyber recovery. SmartFiles exposes file/object services, while Gaia makes selected protected information usable for retrieval and grounded assistance. The public documentation directory is the starting map, not a compatibility matrix. [S01]

A product-to-engine map prevents three expensive mistakes. First, a performance feature in one deduplication path cannot be assumed in another. Second, an API field in a cluster endpoint cannot be transferred unchanged to a Helios multi-cluster endpoint. Third, a security statement about management metadata does not describe the payload flow of a cloud backup, vault or AI service.

For an actual deployment, create a qualification record containing product, edition, exact release/build, source application and version, target platform, authentication mode, data path, supported restore types and support-document revision. Attach the evidence that proves the combination. Record desired capabilities separately from enabled capabilities. A lab operating successfully is valuable evidence, but it does not automatically establish vendor supportability.

PROPOSED evaluation rule. Review each integration using four questions: who owns the recovery catalog, who moves the payload, who decides retention, and which trust domain can make the copy unreadable? The answers reveal the architecture much faster than a feature checklist. For DirectIO, for example, source-to-SpanFS data movement does not remove the NetBackup catalog's role. For a vault, an independent copy is not independent if the same compromised authority can revoke every required key.

VERIFY. Cloud Protection Service, DataProtect self-managed, Cloud Edition, Helios variants, NetBackup, appliance families, FortKnox, SmartFiles and Gaia have different operational and support boundaries. This book covers their engineering relationships, not every licensed configuration or appliance command.

02. Define the recovery contract before the architecture

A useful contract separates capture consistency, recovery-point age, restoration time, durability, availability and cyber-recovery confidence. The workload owner should sign off on these independently. An application that tolerates an hour of stale analytics may not tolerate an hour of missing financial events.

Let t_source be the time represented by the newest usable application-consistent recovery point, and t_incident the incident time. The observed recovery-point loss is t_incident - t_source. A policy scheduled every fifteen minutes does not prove a fifteen-minute RPO: captures can start late, fail partially, wait for logs, or finish locally while a remote copy remains incomplete.

Define RTO from the relevant business event to application validation, not to the moment a restore task starts or a VM powers on. A useful decomposition is:

T_business_recovery = T_detect_and_decide + T_bootstrap
                   + T_select_and_authorize + T_fetch
                   + T_restore_or_mount + T_replay
                   + T_validate_and_promote

Some terms overlap; a measured critical path is better than summing every phase blindly. The definition must also say whether clean-room investigation and approval are included. They usually dominate a cyber incident differently from an ordinary disk failure.

PROPOSED safety properties. A published snapshot references complete, durable content. Its manifest cannot change invisibly. A retained recovery point is not reclaimed. A denied principal cannot infer protected content through indexes, previews or error messages. Recovery into a production network requires an explicit authorized target. Repeating an uncertain restore does not silently create a second workload. These are invariants, not percentage objectives.

PROPOSED availability objectives. Measure catalog reads, protection admission, protection completion, restore admission and successful validated recovery separately. A management console may be unavailable while an existing capture proceeds. Conversely, an available console can display a failed recovery pipeline. Establish per-tenant and per-workload indicators so a large healthy estate cannot conceal an unavailable critical application.

For perspective, 99.999% corresponds to 315.36 seconds of complete unavailability in a 365-day year, or 25.92 seconds in a thirty-day month. This is arithmetic, not a Cohesity SLA claim. Such an objective would require evidence about every serial dependency and failover path. A recoverability goal often benefits more from an independent tested copy and reliable key recovery than from a superficially high dashboard uptime number.

Acceptance test. Disconnect production identity and assume the primary site is lost. Ask a separate team to identify a recovery point, obtain authorized keys, restore the application and validate a business transaction. Record every hidden dependency and elapsed interval.

03. SpanFS: what is publicly known, and what is not

PUBLIC / HISTORICAL. Cohesity describes SpanFS as a distributed file-system substrate with scale-out services, global deduplication, distributed metadata and snapshots. Its published SpanFS and SnapTree white paper presents a layered architecture, while a separate fault-tolerance paper discusses data and metadata resilience. These are valuable conceptual disclosures, not a current source-code map or an exact supported hardware configuration. [S03] [S04] [S06]

The important engineering idea is decoupling logical content from its physical placement. A file offset or backup extent is resolved through metadata to immutable or versioned content. That content can be located, replicated, encoded, repaired or moved without rewriting every client-visible name. A snapshot identifies a stable metadata view rather than requiring an immediate full copy of all payload bytes.

This decomposition creates distinct critical paths. A write must obtain durable payload placement and publish trustworthy metadata. A read must resolve the correct version and retrieve enough valid content. Background work reclaims, repairs, compacts and migrates storage. The same nodes may run several services, but logical responsibilities remain separate.

A distributed data path can remove a single payload-serving bottleneck without eliminating metadata leadership or quorum coordination. Avoid reading phrases such as "no master bottleneck" as permission for two partitions to publish conflicting authoritative roots. Metadata consistency, membership changes and ownership transfer still require a precise protocol.

PROPOSED decomposition. Use protocol front ends, source-specific protection adapters, a catalog authority, a chunk-placement service, immutable object writers, background repair and a recovery executor. Keep namespace and snapshot decisions transactional; keep payload I/O resumable and parallel. Reserve storage and bandwidth for repair and restore instead of allowing ingest to consume every resource.

Public materials do not establish every current internal RPC, consensus configuration, chunk size, on-disk format, hash choice, garbage-collection rule or service boundary. Patents may reveal additional possible designs, but an embodiment in a patent is not evidence that it ships. In particular, historical mentions of particular hash functions or coordination algorithms should not become new implementation recommendations.

Design review. Draw the authoritative state for a file, snapshot, chunk and storage placement. Then kill the process that owns each item. For every operation, identify who can decide it committed, who can discover that decision later, and which evidence survives the failure. Without these answers, a scale-out diagram is only a deployment picture.

04. Ingestion: turn a source checkpoint into a recoverable snapshot

The following is a PROPOSED write path, not a reconstructed SpanFS implementation. The distinction matters because payload durability and metadata publication are different operations.

Start by capturing an immutable source descriptor: tenant, source instance identity, object/version, application consistency mode, source checkpoint, requested policy version and run identity. Source paths alone are insufficient; a deleted and recreated VM or database can reuse a human-readable name while representing a new object.

Stream content through bounded workers. Each worker emits a logical extent mapping and a digest. New unique content is compressed, encrypted using the chosen storage security model, and written to durable locations. A receipt should identify the content, generation, storage policy and successful durable placement. It must not merely mean that a process accepted bytes into RAM.

Once all required extents exist, validate manifest closure: no unintended gaps, no invalid overlaps, correct logical length, valid sparse-zero representation, all referenced objects available under the required durability policy, and a recorded source-consistency result. Commit the snapshot root, protection-run state, operation deduplication record and notification intent in one catalog transaction. Only then report the local recovery point as published.

PREPARE source checkpoint and immutable run identity
INGEST resumable chunks under writer epoch
VERIFY complete extent map and durable receipts
COMMIT manifest root + run outcome + outbox event
ACKNOWLEDGE source cursor advancement

A crash before publication can leave unreferenced objects. That is safe storage leakage to reclaim later, not a half-visible snapshot. A crash after publication but before the client receives success is an ambiguous response: repeat the same operation identity or inspect its authoritative result. Do not create another logical capture merely because the first acknowledgment was lost.

Source cursor advancement deserves special care. An incremental source can discard old change history. Advance the durable acknowledged cursor only after the promised recovery point is complete. If the product promises remote durability, local publication alone does not justify treating remote replication as complete. Record local and remote recovery states independently.

Tradeoff. A short atomic catalog commit simplifies correctness but can become hot. Partition by tenant/source where independent, batch extent metadata before committing a root, and avoid one global monotonically increasing write key. Never split publication across unrelated databases without explicitly solving its decision and recovery protocol.

Failure drill. Terminate workers after data placement, after manifest validation, after catalog commit, and before acknowledgment. In each case, verify that the catalog exposes either no recovery point or one complete recovery point, never an apparently successful partial one.

05. Reads and restores: verify all the way to the application

The restore path begins with authorization and snapshot selection, not storage reads. Resolve the requested tenant, source identity, recovery point, destination and permitted operation. A user allowed to browse filenames is not necessarily allowed to restore those files into another tenant or export their content.

PROPOSED read sequence. Resolve an immutable manifest root, obtain a read pin or equivalent stable-generation protection, walk logical extents, and fetch the required objects. Verify framing and ciphertext integrity before using decrypted data. Decode compression only under resource limits, then verify the logical content digest. Reconstruct missing fragments only from sufficient individually validated fragments. A successful network read is not proof that the right historical content was retrieved.

Reads should exploit locality without compromising identity. Coalesce adjacent extents, prefetch metadata pages, and schedule parallel streams bounded by target write capacity. A cache key must include tenant/security domain, content identity, codec version and relevant key context. A filename-only or snapshot-name-only cache can return a wrong version or leak data.

For a full restore, persist progress at a granularity that can be safely replayed. The target writer must understand whether a repeated write is an identical offset overwrite, a file replacement, a new object version or a destructive API action. These have different retry semantics. For instant access, expose a read-only base and isolate new writes in a clearly owned overlay. The overlay becomes another object that must survive until migration or abandonment completes.

Verify the target at more than one level. Content digests prove restored bytes against the manifest. File counts and ACLs prove namespace reconstruction. Database startup and consistency checks prove more. A synthetic business transaction proves something different again. Report these separately rather than compressing them into one green status.

Practical edge cases. Missing keys must fail distinctly from missing chunks. A cold object waiting for retrieval is not corrupt. A target out of space is not a source-backup error. A user cancellation must preserve enough state to identify partially created resources. A last-stage failure must not delete the original recovery point or its diagnostic evidence.

Performance rule. Optimize the critical path of a representative restore under damaged conditions. Deduplicated random reads, encrypted-object fetches and database log replay may behave very differently from sequential backup ingestion. Benchmark both warm and cold caches and record whether the measured endpoint was first byte, boot, complete data copy or validated service.

06. SnapTree and persistent metadata

HISTORICAL. Cohesity's SnapTree explanation describes a B+ tree-based metadata approach that shares structure across snapshots, avoiding a recovery dependency proportional to a long chain of incremental backups. This is the conceptual result to understand; public descriptions do not disclose every node layout or present implementation detail. [S05]

Consider a logical map from (file_id, extent_offset) to immutable content references. A snapshot retains a root pointer. To change an extent, create a new leaf and the path of parent nodes needed to reach it; unchanged subtrees remain shared. Publish a new root only after the referenced nodes and content are durable. Readers of the old root continue to observe its former mappings.

If a balanced tree has height h, changing one key typically changes a path of order h, subject to splitting, batching and implementation details. Reading a snapshot follows its own root rather than replaying every preceding snapshot. This is fundamentally different from an unbounded sequence of "apply increment 1, then 2, then 3" during restore.

Do not translate structural sharing into "snapshots cost nothing." New roots, changed paths, extent metadata, retained content, indexes and reclamation work still consume resources. Many tiny updates can create substantial metadata amplification. Large numbers of recovery points increase inventory, verification and retention-management work even when unchanged payload is shared. Tree depth depends on indexed content and fan-out, not merely the number of retained snapshots.

PROPOSED representation. Give every immutable metadata page a digest and format version. A root record includes tenant, source generation, source checkpoint, logical size, tree format, publication generation and retention policy version. Distinguish the snapshot's immutable content definition from mutable administrative attributes such as labels or an extended retention deadline. Audit those administrative changes.

Deletion removes a root's eligibility to protect content; it does not immediately delete every page or chunk reachable from that root. Other roots, active readers and in-flight writers may share those objects. A root lifecycle therefore belongs to the same correctness analysis as garbage collection.

Review question. A snapshot with one changed block is deleted while another snapshot still references an unchanged subtree. Which roots and generations prove that subtree remains live? A design that answers only "decrement a counter" must explain crash recovery, duplicate decrements, counter reconstruction and concurrent publication before it is safe.

07. Deduplication, MegaFile and data granularity

PUBLIC. MegaFile addresses large-file data movement by parallelizing work across nodes. It is a throughput feature, not a statement that every parallel work part is also a deduplication unit or an erasure-coding fragment. [S07]

A proposed data path can have at least four sizes: a scheduling range, a deduplication chunk, a packed object and a redundancy fragment. Parallel work ranges help balance large jobs. Dedup chunks identify repeated content. Packing amortizes small-object I/O and metadata overhead. Redundancy fragments allow reconstruction after failures. Choosing one size for all four simplifies diagrams but often harms real performance.

Fixed-size chunks are straightforward and support direct offset calculations. An insertion near the beginning of a file can shift later boundaries and reduce reuse. Content-defined chunking chooses boundaries from local content, improving resilience to such shifts but adding CPU, boundary variability and implementation complexity. FastCDC is one published approach to efficient content-defined chunking; citing it here does not mean Cohesity uses it. [S53]

PROPOSED identity. Use a modern cryptographic digest for content identity, validate the length and bytes on suspicious collisions, and scope deduplication to an explicitly approved tenant or encryption domain. Cross-tenant deduplication can create privacy side channels and retention/key-management coupling. An attacker should not learn whether another tenant stores a known file by measuring upload behavior or billing differences.

A distributed dedup index needs race handling. Two workers may upload the same unseen content simultaneously. It is acceptable to create temporary duplicate physical objects if publication selects a canonical usable identity and eventual cleanup is safe. It is not acceptable to publish a reference to an object whose only writer crashed before durability. A "present" bit should therefore distinguish reserved, writing, durable and retiring states or encode equivalent guarantees.

Compression ratio and deduplication ratio are not interchangeable. Record logical protected bytes, logical retained snapshot bytes, unique uncompressed bytes, compressed data bytes, metadata/index bytes and physical replicated/encoded bytes separately. A small denominator can produce a dramatic ratio while hiding expensive metadata or poor restore locality.

Benchmark. Use at least VM images, database files, compressed media, encrypted content and small-file trees. Measure CPU per ingested byte, index cache hit rate, chunk distribution, physical writes, restore amplification and rebuild rate. A dataset chosen only because it deduplicates well cannot establish a general sizing factor.

08. Compression, encryption and recoverable keys

PUBLIC. Cohesity's security-hardening guidance covers controls such as access hardening, external key management and audit integration. Exact algorithms, hardware support and key-management procedures must be checked for the installed product and release. [S27]

The following is a PROPOSED envelope-encryption design. Compute the dedup identity inside an authorized plaintext-processing boundary, compress new content, then encrypt using an authenticated encryption scheme and unique nonces as required by that scheme. Store a wrapped data-encryption key and key version with enough metadata to decrypt later. Keep master-key authority separate from bulk storage.

Do not use a content hash as an encryption key. Do not invent a nonce scheme. Deterministic or convergent encryption can improve cross-client deduplication but has information-leakage tradeoffs that require dedicated cryptographic review. A simpler design keeps deduplication within a controlled service/tenant domain and encrypts stored unique objects using approved envelope encryption.

Key rotation has two forms. Rewrapping data keys can change a wrapping key without rewriting all payload bytes. Re-encrypting data changes ciphertext and may require a complete storage rewrite. Specify which operation a "rotate" button performs. Also record how old snapshots retain access to old key versions until their retention and legal obligations end.

An immutable backup can become unrecoverable if its only key is deleted or an external KMS account is disabled. Retention control must therefore cover the key lifecycle and bootstrap material, not only object deletion. Conversely, retaining keys indefinitely may violate an approved erasure policy. Treat cryptographic erasure, retention and legal hold as an explicit conflict-resolution policy rather than an accidental consequence of KMS administration.

The recovery runbook should specify who can activate break-glass key access, which independent authority approves it, where offline recovery instructions live, how credentials are rotated afterward and how use is audited. Test recovery when production SSO, DNS and the primary KMS network path are unavailable. A document saying "contact the identity administrator" is not a recovery mechanism if that identity system is part of the failure.

Failure handling. Differentiate unavailable KMS, denied key permission, unknown key version, malformed ciphertext and digest mismatch. Retry only transient conditions. Repeatedly attempting decryption with unrelated keys is neither useful nor safe. Preserve the object, key version and authenticated error evidence for investigation.

09. Metadata coordination, transactions and fencing

HISTORICAL. Public Cohesity architecture materials discuss replicated metadata and coordinated operations. Patent disclosures also describe possible distributed journal and snapshot mechanisms. Neither establishes the exact consensus algorithm, transaction protocol or service names in every current deployment. [S06] [S51]

PROPOSED. Use a proven transactional metadata system as the initial catalog authority. It must support atomic publication, uniqueness constraints and well-defined failure recovery. Do not build a custom consensus layer merely because the product is distributed. The distinguishing work is source correctness, durable content, recovery semantics and operating discipline.

Ownership leases are useful but insufficient on their own. A paused worker can resume after its lease has expired. Assign a monotonically increasing fencing epoch to each protected source/run ownership domain. Every publication or state-changing command carries that epoch, and the authoritative catalog rejects stale epochs. Where a downstream service performs side effects, it must also enforce a compatible fence or use immutable operation identities with safe reconciliation.

Transactions should contain bounded metadata decisions, not large payload streams or remote source calls. Prepare immutable IDs and manifests outside the transaction. Inside it, verify ownership, expected state, source generation, effect identity and references, then publish. If the database retries the callback, it must not freeze an application twice or trigger a second external restore.

A commit timeout creates uncertainty. The client might not know whether the transaction committed, but the database authority eventually can. Recover by the original operation identity. An immediate negative lookup does not prove that an earlier in-flight command can never commit. Guarded resubmission must still use the same key and payload fingerprint.

Partitioning requires careful domain selection. Independent tenants and sources can have independent transaction streams. A single shared snapshot root or policy update should not be duplicated into independently writable authorities. During loss of authoritative quorum, do not publish competing recovery points under the same identity. Continue safe existing reads where the consistency contract permits, and expose the degraded condition honestly.

Operational metric. Track transaction retries, hot keys, ownership churn, lease expiry, rejected stale epochs and publication age. Large retry counts often reveal poor partitioning, oversized transactions or badly synchronized scheduling before they become outages.

10. Replication, erasure coding and fault domains

HISTORICAL. Cohesity's fault-tolerance paper distinguishes protection for payload from protection for metadata and discusses replication and erasure coding. Its example tables are not a current support matrix. In particular, a minimum deployment that survives a failure may still need replacement capacity before it can heal fully. [S06]

For a proposed Reed-Solomon-style k+m layout, an object is divided into k data fragments and m parity fragments. Ignoring headers and metadata, storage overhead is (k+m)/k. A 4+2 example uses 1.5 times the protected payload and can reconstruct from any four valid fragments under the codec's assumptions. This does not mean it survives any two racks: placement determines how many fragments each rack loss removes.

Replication is simpler and often attractive for small metadata, write journals and latency-sensitive data. Three full replicas consume approximately three times the payload before compression and overheads. Erasure coding can reduce capacity cost but increases write coordination, reconstruction work and sensitivity to small I/O packing. Use the right mechanism for each class instead of forcing one redundancy policy onto everything.

Failure domains include disk, process, node, chassis, rack, power feed, network fabric, zone and region. Independence cannot be inferred from different node IDs. A placement policy should encode hard anti-affinity and soft balancing constraints. Admission must reject or explicitly downgrade a placement that cannot meet its declared durability contract; silent co-location of redundant fragments is not normal success.

The surviving data fragments are only one requirement. Readers also need the authoritative manifest, extent mappings, location metadata, codec version and keys. A cluster with enough data fragments but unavailable metadata quorum may still be unable to serve correct writes or discover the right recovery point. Report these states independently.

Healing budget. Reserve both free capacity and bandwidth. If a 20 TB node must be rebuilt at an effective 200 MB/s, the ideal transfer-only time is about 27.8 hours; real repair is slower when it competes with reads, writes and verification. During that interval, the system operates with reduced redundancy. Model a second failure and not only the initial outage.

Qualification test. Fail one fault domain during a large restore and a protection burst. Observe whether placement remains valid, whether repair can progress, whether metadata stays authoritative, and whether promised restore objectives still hold.

11. Repair, rebalance, compaction and garbage collection

Background storage work is not optional maintenance. It is the mechanism that keeps the durability and capacity contract true after time passes, hardware fails and retention expires.

PROPOSED repair. Periodically scrub stored objects with checksums and authenticated integrity checks. Repair from verified surviving copies/fragments, write the replacement durably, then atomically update placement metadata. Preserve a generation so a late completion cannot replace a newer repair decision. A failed source device must not be trusted simply because it responded.

Rebalance moves valid content to improve capacity and fault-domain distribution. Keep the old location readable until the new placement is durable and discoverable. Compaction repacks small or fragmented objects; it must preserve stable logical content identity while changing physical offsets. Rate-limit both operations against a restore-reserved resource budget.

Garbage collection has a subtler race. A collector sees chunk X as unreferenced. A writer prepares a new manifest referencing X. If the collector deletes X before the root is published, the writer can create a broken snapshot. A grace period alone does not prove safety if a writer can pause longer than that period.

A robust distributed design needs a coherent protocol: root enumeration at a known catalog boundary, protection for in-flight writers and readers, publication barriers or write shading, immutable generations and a final eligibility check before deletion. The collector must include retained roots, held roots, active restore pins, uncommitted ingest pins and any durable remote-copy obligations that depend on local data. Choose a documented algorithm and test adversarial interleavings.

Reference counting can accelerate decisions but introduces its own problems: duplicate increment/decrement commands, lost updates, abandoned transactions and reconstruction after corruption. Mark-and-sweep avoids some counting issues but requires a trustworthy root set and concurrency barrier. Hybrid designs can use counts as hints while periodic tracing verifies reachability.

The local companion intentionally serializes publication and collection under one lock. That makes its invariants inspectable; it is not a distributed GC implementation. Its tests demonstrate why an active read or staged ingest must keep shared chunks alive.

Runbook guardrail. Do not respond to a full cluster by deleting low-level objects manually. Stop or throttle new admission, verify expiration and hold policy, inspect reclaimable candidates, add qualified capacity and protect repair headroom. A storage emergency is not permission to invalidate retained recovery points.

12. Protection orchestration as a durable state machine

PUBLIC. DataProtect provides policy-based protection and recovery across supported workloads. The exact source adapters, application versions and recovery types require the applicable support documentation. [S08]

PROPOSED states. DISCOVERED -> PREPARING -> INGESTING -> VERIFYING -> PUBLISHED describes local capture. Remote replication, archive, vault transfer, indexing and threat analysis are separate child workflows. A parent status must not pretend those children completed because the local snapshot exists.

A job record contains immutable input, policy version, source generation, operation key, current state, owner epoch, attempt count, checkpoint, deadline and structured error. A task record has a stable identity independent of the worker process. A worker crash should move execution, not create a new business operation.

Scheduling needs fairness. Limit concurrent source snapshots, application freezes, source API calls, network streams and target writes separately. A single large tenant must not exhaust all data movers. Reserve resources for restore and repair, which are more urgent than new backups during an incident. Apply jitter to periodic schedules to avoid a top-of-hour thundering herd.

Retries are classified by operation. Re-reading a known immutable extent is usually straightforward. Retrying a source freeze, snapshot creation, target VM creation or destructive cleanup requires operation-specific semantics. If a source supports stable task IDs, record and inquire about them. If it does not, retain enough observation evidence for reconciliation and avoid declaring non-execution merely because the local call timed out.

A transactional outbox records events with state changes. A publisher can send an event twice after a crash; consumers need inbox/effect deduplication. The queue is a scheduling aid, not the only copy of pending work. Periodic sweeps should discover durable tasks whose messages were lost or delayed.

Cancellation is another transition, not an abrupt process kill. It must stop new work, preserve a consistent checkpoint where possible, release source-side temporary resources safely and retain evidence of partially created targets. A cancellation after snapshot publication cannot erase the fact that a recovery point was created; it can cancel later child work subject to policy.

Acceptance test. Restart the entire worker fleet while thousands of tasks are active. Every task should eventually reach a valid state or an owned investigation, with no orphaned source snapshots, duplicate restores or false success caused by missing workers.

13. Policies, schedules, retention and real recovery-point age

A protection policy is an executable contract. Its important fields are not only frequency and retention, but consistency mode, eligible sources, destinations, copy dependencies, failure handling, retry limits and the meaning of completion.

PUBLIC. The versioned protection-policy API includes retention and copy-related configuration. Its 7.4 schema marks an older dataLock field as deprecated in favor of newer configuration and includes a last-modification timestamp mechanism for stale updates. Automation should use the pinned schema rather than recycle a payload from an older release. [S44]

PROPOSED policy model. Store a versioned immutable policy definition and associate each run with the version it used. A policy edit should not reinterpret historical completion evidence. Represent local retention, remote retention, archive retention, legal restrictions and minimum copy requirements explicitly. Document whether a newly increased retention period affects existing snapshots, future snapshots or both.

A scheduled capture at time t is not its recovery point. The protected application checkpoint may be earlier than the job start, and a log-based system may advance its recoverable point continuously after a base backup. Report the newest validated source checkpoint for each required destination. Distinguish wall-clock capture age from remote-copy lag and application-consistency age.

Retention and failure interact. If the remote copy fails, deleting the last local predecessor might violate the promised recovery horizon. A design can extend local retention until a required downstream copy succeeds, but must also model capacity exhaustion and maximum extension. Never hide the resulting backlog. Raising retention without capacity analysis can cause future captures to fail and paradoxically worsen recovery-point coverage.

Calendar schedules need a clear timezone and daylight-saving policy. Store timestamps and durations with explicit units; public APIs may use microseconds where clients expect milliseconds. For a missed run, decide whether to catch up, coalesce, skip or create a new full baseline. Running every missed hourly job after a two-day outage can overload the source without improving recoverability.

Example. A fifteen-minute local policy has a capture representing 10:00 that publishes at 10:08 and reaches the vault at 10:22. At an incident at 10:25, the newest usable remote point may still be 10:00, a twenty-five-minute gap. Reporting "last job completed three minutes ago" would obscure the actual data-loss exposure.

Validation. Build a timeline from source checkpoints, local publication and remote completion. Check coverage gaps, not merely counts of successful jobs. The policy dashboard should identify the oldest unfulfilled obligation, its bytes, its cause and the application owner who accepts the risk.

14. VMware capture: source snapshots, CBT and application consistency

PUBLIC. Cohesity's VMware guidance discusses supported vSphere data protection, transport and restore workflows. It distinguishes full-copy recovery from instant recovery using a temporary datastore. Exact transport options, vSphere releases and operational limits require the current support matrix. [S11]

A VMware snapshot is a source-side coordination artifact, not itself an independent backup. It preserves a point-in-time disk view while the backup reader transfers content elsewhere. Changed Block Tracking can identify extents since a known baseline, but the protection system must maintain the correct source identity and tracking generation.

PROPOSED adapter. Discover the VM and its disks, check exclusions and credentials, request the required consistency mode, create or identify a source snapshot, record the source-side task ID, read the needed extents, and publish the destination recovery point. Remove the temporary source snapshot only through a tracked cleanup workflow. Monitor consolidation, because leaving temporary snapshots indefinitely can affect production storage.

CBT state must be treated as fallible external metadata. A reset, source re-creation, disk change or inconsistent checkpoint can invalidate incremental assumptions. When the required baseline cannot be proved, take a qualified new baseline rather than interpreting an empty change set as "nothing changed." A VM rename must not accidentally change identity; a deleted and recreated VM with the same name must not inherit the former identity.

Application consistency is separate. Windows VSS coordinates a requester, application writers and a provider to produce a suitable shadow-copy state. A successful storage snapshot is not evidence that every database writer quiesced successfully. Capture writer results, consistency mode and any fallback. A policy promising application consistency should not silently report a crash-consistent fallback as equivalent. [S14]

Resource scheduling includes per-host and per-datastore pressure, transport concurrency and snapshot age. Avoid freezing too many databases at the same time or creating a source snapshot that outlives its safe operating window. Restore-reserved capacity should not be consumed by a backlog of new captures.

Test matrix. Cover VM power states, disk addition/removal, CBT reset, source snapshot timeout, guest quiesce failure, network failure halfway through a large disk, and cleanup failure after destination publication. For every test, inspect both the backup catalog and vSphere's temporary resources. Correct destination data does not excuse leaving harmful source-side artifacts behind.

15. Instant recovery, full-copy recovery and the boot-storm problem

PUBLIC. The documented VMware instant-recovery pattern mounts a Cohesity view as an NFS datastore, powers on the VM and supports migration back to primary storage with storage vMotion. Full-copy recovery follows a different path. These are meaningful capabilities, not promises that every application becomes healthy immediately. [S11]

Instant access shortens the delay before a workload can read its backup image. It does not eliminate data movement, random-read pressure, writable state, network preparation, security validation or eventual cleanup. The workload may run temporarily on storage optimized for protection density rather than production latency.

PROPOSED implementation. Expose the immutable recovery image as a base, maintain a writable overlay for new changes, and make their lifecycle explicit. Reads check the overlay first and then the base. During migration, copy the base while tracking writes; coordinate the final cutover so no write is lost. The actual hypervisor/storage mechanism should be delegated to supported interfaces rather than reproduced casually.

A mass-recovery event creates a boot storm. Operating systems request many small reads concurrently; databases replay logs; applications contact directory services and dependent APIs. A system that sustains fast sequential backup ingest may not sustain thousands of cold random reads at acceptable latency. Pre-stage metadata, prioritize critical services and cap concurrent starts based on measured storage and application behavior.

Recovery ordering matters. Identity, DNS, time, key services, databases and queues may have to come before front ends. Restoring all VMs simultaneously can produce misleading failures because dependencies are missing. A dependency graph with readiness and business checks is more useful than a flat machine list.

Expose stages separately: resources created, disks attached, VM running, guest reachable, application consistent, traffic approved, migration complete and temporary resources removed. An administrator should know whether the application still depends on the protection cluster and what capacity it consumes there.

Failure drill. Interrupt storage migration after new writes have accumulated. Demonstrate which copy is authoritative, how the process resumes and how the overlay is preserved. Then fail a protection node while several recovered VMs run from the temporary datastore. Record latency and application impact, not only whether the mount survived.

16. Databases: consistency, redo/WAL and exact recovery targets

PUBLIC. Cohesity describes native RMAN integration for Oracle protection. NetBackup has versioned PostgreSQL recovery documentation. These adapters have database-specific contracts; they should not be flattened into "copy database files." [S12] [S13]

For PostgreSQL physical point-in-time recovery, a valid base backup and continuous WAL coverage are needed, with attention to timeline and recovery-target semantics. A logical pg_dump is not interchangeable with a physical base backup for this workflow. The database's own recovery documentation is the authority for these rules. [S55]

PROPOSED recovery descriptor. Record database instance identity, database engine/version, backup type, start/end checkpoints, log sequence ranges, timeline/incarnation, encryption/wallet dependencies and consistency evidence. A restore target is not just a wall-clock string; specify inclusive/exclusive semantics and the engine's exact target representation. Human clocks, transaction commit time and source log position may differ.

A base backup can be complete while the log stream has a gap. A catalog must compute a continuous recoverable interval, not assume every timestamp between oldest and newest files is valid. Duplicate logs are normal under retry; conflicting bytes for the same log identity are an integrity incident. Do not truncate the source's only required logs before the protection obligations are satisfied.

For Oracle, preserve the RMAN catalog/control-file information and recovery materials needed by the chosen workflow, including TDE wallets where applicable. For SQL Server, distinguish full, differential and log chain requirements and record VSS writer or native backup evidence. For distributed databases, a per-volume snapshot may not represent a globally consistent application state; use supported cluster-aware mechanisms or explicitly documented crash-recovery semantics.

Tradeoff. Frequent logs can reduce recovery-point loss but increase request count, catalog churn and operational sensitivity to gaps. Less frequent base backups save ingest bandwidth but lengthen log replay during restore. Choose the base/log cadence by measuring the maximum acceptable replay time, not only the cheapest backup schedule.

Acceptance test. Insert labeled transactions around a chosen target, capture and archive the required data, restore into an isolated instance, and prove which transactions are present. Repeat after a timeline change, source promotion and key rotation. A database opening successfully does not prove it stopped at the intended historical point.

17. NAS, files and object data: preserve semantics, not just bytes

A file-protection adapter must represent content, namespace and security together. Renames, sparse regions, hard links, extended attributes, access-control lists, alternate streams and versioned objects are all potential sources of silent fidelity loss.

PROPOSED discovery. Use stable file/object identifiers when available, source change journals where reliable, and periodic reconciliation scans to detect missed events. A path is a presentation key, not always durable identity. Store enough metadata to distinguish a rename from delete-and-create when the source exposes that distinction.

A scan runs while the source changes. Without a source snapshot or a journal/checkpoint protocol, the resulting tree can mix moments in time. A directory listing might include a file whose content was already replaced or omit one created during the scan. Label the resulting consistency contract honestly. "Every file copied successfully" does not establish a single point-in-time namespace.

Normalize metadata only where the destination semantics are known. Windows security identifiers and POSIX user IDs are not interchangeable. Preserve original identities and explicit mapping rules. A restore that recreates bytes but accidentally grants broad access is a security failure. Where a target cannot represent a feature, report the loss before execution rather than silently dropping it.

Object stores add version IDs, delete markers, legal retention, multipart-upload state, checksums and metadata headers. A delete marker can hide an object without deleting a retained historical version. List operations can be paginated and permission-filtered; an incomplete listing is not proof that missing objects were deleted. Checkpoint pagination without turning a transient access failure into destructive catalog pruning.

Small-file workloads are often metadata-limited. Batch source calls where supported, cache directory traversal carefully, and separate metadata queues from large-file data queues. Large-file parallelism should not starve millions of tiny files. Preserve fairness at source and destination.

Fidelity test. Construct a synthetic tree with sparse files, empty files, long paths, Unicode names, duplicate content, links, ACLs, denied objects, and concurrent renames/deletes. Restore to each supported target type and compare semantics. Mark unsupported cases explicitly. The goal is a precise restore contract, not a misleading universal "file backup" checkbox.

18. Kubernetes, SaaS and modern workload adapters

PUBLIC. Cohesity markets Kubernetes protection and Microsoft 365 protection, including a distinct Microsoft 365 Backup Storage integration. Its April 2026 DataProtect announcement discusses expanded cloud and AI-workload coverage. These sources establish product directions and supported categories, not every item-level restore capability. [S15] [S17] [S18] [S09]

For Kubernetes, protect the objects needed to recreate the application and the state needed for it to function: CRDs, operators, namespace resources, persistent volumes, application-consistency hooks and external dependencies. Secrets need a secure recovery strategy; images need a reachable registry; service identities need valid authority. A pod becoming Ready is not proof that its data or external integrations are correct.

A CSI snapshot can preserve volume state, but a snapshot remaining in the same failed storage account or region is not an independent backup. A proposed adapter may combine source snapshots with a data-movement layer and durable external metadata. Upstream Velero's CSI documentation is a useful reference for designing such adapters; it is not evidence that Cohesity uses Velero internally. [S16]

SaaS protection is governed by source APIs, throttling, pagination, object IDs and permission scopes. Microsoft 365 includes different content and relationships across Exchange, SharePoint, OneDrive and Teams. A protection engine must map those relationships and declare supported restore destinations and fidelity. The traditional connector and Microsoft's Backup Storage integration can have different data paths, timing and feature boundaries; do not infer one from the other.

PROPOSED SaaS controls. Persist delta tokens with the capture generation, detect token invalidation and rebaseline safely, retain tombstones only after authoritative deletion evidence, and track partial failures per object. Refreshing a credential should not create a new source identity. Revoked read permission should mark content inaccessible, not immediately erase the only retained recovery point.

For AI systems, backing up a vector database alone may not reproduce the application. Preserve source data lineage, embedding model and dimensionality, index schema, collection metadata, application code/configuration and secrets needed for the environment. If the vector index can be rebuilt, quantify rebuild cost and time rather than assuming it is free. Model weights and data may have separate licenses and access restrictions.

Qualification gate. For every new workload, publish a table of capture consistency, incremental mechanism, supported versions, object coverage, restore destinations, encryption dependencies and known exclusions. Only broaden the marketing category after these engineering contracts are tested.

19. Replication, archive, tiering and vaulting are not synonyms

All four mechanisms can move data away from an ingest node, but they make different recovery promises. Treating them as interchangeable is a common architectural error.

PROPOSED distinctions. Replication maintains another recovery-capable copy, including the metadata required to use it. Archive optimizes long retention and may require a retrieval/rehydration stage. Tiering relocates content for cost or capacity while the original control and metadata plane may remain necessary. Vaulting adds an intentionally separate security and operational boundary. A remote tier is not automatically a disaster-recovery copy.

A snapshot copy protocol should transfer or make available all required chunks and manifest pages, verify the destination closure, publish a destination root, and only then acknowledge destination recoverability. If deduplication avoids sending existing chunks, the sender must know those chunks are durable and protected from concurrent reclamation at the destination. A stale "already present" hint is insufficient.

Retaining a root without its encryption key, schema version or catalog-discovery mechanism is not a complete copy. Store an independently discoverable inventory and recovery instructions. Test reconstruction without the source cluster rather than assuming the destination UI can find every object after a total loss.

Archive economics include capacity, request counts, retrieval latency, retrieval fees, egress, temporary rehydration storage and operator time. A low monthly price can produce an unacceptable disaster-recovery bill or multi-day retrieval delay. Model the critical application's recovery set separately from the entire estate and maintain an appropriate hot or warm copy for its requirements.

Bandwidth example. A 100 TB recovery over a link delivering 1 GB/s of verified payload takes about 27.8 hours just to transfer the bytes. Decryption, metadata walks, replays and validation add work. Dedupe-aware replication can reduce steady-state traffic, but an isolated restore target may still need substantial materialized data.

VERIFY. Product-specific copy topologies, archive formats, supported cloud targets, retention behavior and direct recovery capabilities vary. Public patents discuss possible snapshot-archive management techniques, but they do not establish the shipping archive format or compatibility contract. [S52]

20. Disaster recovery is an application dependency graph

PUBLIC. Cohesity's disaster-recovery portfolio includes orchestration and recovery capabilities. Those capabilities should be evaluated against the application's measured recovery process rather than a universal zero-loss assumption. [S29]

Build a directed graph where nodes are recoverable services and edges mean "requires this dependency before a specified validation step." Identity, DNS, time synchronization, key access, registries, network routes, databases and queues often precede customer-facing applications. Some services can start in a degraded state; encode that explicitly rather than forcing every dependency into a strict serial chain.

A recovery plan needs more than VM order. Specify recovery points, acceptable cross-service skew, credentials, alternate IP/DNS mappings, startup scripts, validation probes, traffic cutover, rollback criteria and ownership. Two individually consistent databases restored to incompatible times can produce an inconsistent business workflow. Applications may need reconciliation or a coordinated checkpoint across services.

PROPOSED blueprint. Version the plan alongside application changes. Each step has immutable input, expected evidence, timeout, retry policy and compensation where appropriate. Retrying infrastructure creation must preserve operation identity. A compensation should not delete valuable forensic evidence or undo a recovery step that an external system actually completed after a timeout.

Clean-room recovery differs from ordinary failover. It assumes production credentials, binaries or network paths may be compromised. Use isolated networks, controlled tool images, restricted egress and separate administrative identities. Scan and validate in isolation, then approve promotion. Avoid connecting a restored domain controller directly to the infected environment simply because it boots.

Test failback too. After running in the recovery site, new data exists there. Returning to the original site requires an explicit authority decision and data synchronization plan. Running two independently writable primaries can create divergence that no backup product can automatically interpret correctly.

Exercise. Remove access to the primary management network, production SSO and internal wiki. Give the recovery team only the independent bootstrap package. Every instruction, secret or dependency they cannot obtain becomes a concrete improvement item. Record application-validated RTO and the responsible decision-maker for each delay.

21. Immutability, DataLock, retention and legal hold

Immutability constrains mutation or deletion under a defined authority. It is not a universal statement that data can never disappear, keys can never be lost, or malicious administrators cannot affect other dependencies.

PUBLIC. Cohesity's policy and run-metadata APIs expose product-specific retention and hold controls. Their roles, configuration fields and semantics must be read in the relevant version. In particular, a Cohesity API operation named legal hold should not be assumed identical to another platform's hold mechanism. [S44] [S49]

AWS S3 Object Lock distinguishes governance and compliance modes and operates on object versions; delete markers can still affect how a key is listed. A protected historical version and its visible current name are different objects of reasoning. AWS documentation is the authority for S3 behavior, not a general description of Cohesity DataLock. [S54]

PROPOSED retention invariant. A content object remains readable while any published snapshot, legal restriction, replication obligation or active read pin requires it. Shared deduplication means the deletion deadline for one snapshot cannot be blindly applied to every chunk it references. The storage system needs a safe aggregate retention mechanism.

Separate three state changes: hiding an item from ordinary browsing, expiring a recovery point, and physically reclaiming its content. Each needs authorization and audit evidence. A user-friendly "delete" action must disclose which state it changes. Physical cleanup can occur later, but it must never precede the strongest remaining obligation.

Clock handling matters. A local wall clock that jumps forward must not silently shorten retention. Use trusted time, bounded uncertainty and an explicit policy for clock anomalies. Extending a retention period is often safer than shortening it, but both must be authorized and reflected in capacity planning. A legal-hold release should not retroactively validate earlier forbidden deletion attempts.

Threat boundary. If a backup administrator can delete the KMS account, modify the restore binary, destroy the only catalog or disable the vault identity, immutable payload is not enough. Protect the whole recovery dependency graph. A contractual or legal retention requirement also needs policy interpretation outside the software; this book does not determine statutory retention periods.

Test. Create two snapshots sharing a chunk. Expire one, hold the other, run reclamation, and restore the held snapshot. Then rotate keys and repeat with the primary catalog unavailable. This exercise exposes the difference between an immutable-object feature and end-to-end recoverability.

22. FortKnox: isolated copies and controlled recovery

PUBLIC. FortKnox provides cyber-vaulting capabilities in SaaS and self-managed forms. A 22 September 2026 announcement describes clean-room recovery, Digital Jump Bag recovery assets and deployment-specific vaulting-window controls. Verify the exact release and enabled capabilities before using the announcement as an operating procedure. [S22] [S23]

The engineering objective is to reduce correlated compromise. A primary-site attacker should not automatically obtain credentials that can erase the vault, change its retention, destroy its keys and approve a restore into an attacker-controlled destination. Isolation can involve identities, networks, accounts, storage policy, management plane and operational approvals. A virtual air gap is not the same as a physically disconnected device.

PROPOSED copy protocol. A restricted exporter sends immutable recovery content through an authorized window or channel. The vault validates manifests and policy, commits its own recoverable root and returns completion evidence. The source records the independently completed copy. Permissions to ingest should not imply permissions to shorten retention or delete previously protected data.

The recovery path has different risk. It exports valuable historical data and can reintroduce compromised workloads. Require a target definition, requester authorization, independent approvals for sensitive actions, evidence of snapshot selection and controlled network placement. Where a clean room is used, validate there before promotion.

A bootstrap pack should include the assets needed before applications can recover: catalog instructions, trusted tooling, infrastructure definitions, key-access procedures, identity recovery and contact/decision authority. Store it under an independent protection strategy and test that it can be accessed during the intended failure. Do not put its only decryption password in the failed production password manager.

Retentions may differ between primary and vault copies. A vault copy is not automatically older, longer retained or complete for every source. Expose its source checkpoint, copy completion, expiration and dependency status. A successful upload into a vault does not prove the next restore will have sufficient egress or target capacity.

Acceptance drill. Revoke production access and deny the normal backup administrator. Have the designated recovery authority obtain one qualified recovery point through the supported process, reconstruct it in isolation and validate the application. Record controls that were bypassed, unavailable or dependent on the compromised environment.

23. Threat detection: distinguish lookup, scanning and proof

PUBLIC. Cohesity Threat Protection describes threat feeds, malware analysis and YARA-related capabilities. A November 2025 engineering post discusses fast searches over indexed SHA-256 file hashes. Searching an index for known hashes is not the same operation as reading and scanning every byte in the estate. [S25] [S26]

A hash indicator can identify an exact known file efficiently. It does not detect every modified variant, encrypted payload, memory-resident threat, malicious configuration or legitimate tool used by an attacker. YARA or malware-engine scanning examines more content but still depends on rules, file support, resource limits and accessible plaintext. An anomaly model can surface unusual change patterns without proving malware.

PROPOSED evidence record. For every analysis, store snapshot identity, scan engine/version, rule or feed version, covered objects and bytes, skipped/encrypted/unsupported items, execution environment, findings and completion status. "No findings" with ten percent coverage is different from a fully completed scan. Preserve the evidence even if a later scan reaches a different conclusion.

An incident workflow can combine source timeline, change-rate anomalies, known-indicator matches, content scans, configuration inspection and application-level checks. Select candidate recovery points from before likely compromise, then validate them in a controlled environment. The conclusion should express confidence and remaining uncertainty, not a mathematical claim that data is clean.

Scanning can compete with backup and restore. Separate job classes, cache immutable results by content identity where safe, and re-evaluate when engine or rule versions change. A cached negative result must include the scanner version and coverage context. A threat feed update can invalidate the usefulness of an old negative assessment without changing the snapshot bytes.

Treat filenames, extracted text and scan reports as sensitive. A hash index can expose content identity; a report can reveal customer names or security architecture. Apply tenant isolation and permissions to analysis results as well as payload. A user who cannot read a document should not receive its sensitive text in a malware-preview panel.

Measurement. Report lookup latency, content bytes scanned per second, coverage, false-positive investigation load, time to qualify a recovery point and time to business recovery. Do not substitute one very fast index query for the full cyber-recovery process.

24. RecoveryAgent, blueprints and controlled promotion

PUBLIC. Cohesity positions RecoveryAgent around recovery blueprints, rehearsals, investigation, validation and orchestration across supported DataProtect and NetBackup scenarios. This does not establish universal parity across every workload or version. [S28]

PROPOSED blueprint semantics. A blueprint is a versioned executable plan with application dependencies, recovery point constraints, isolated network placement, preconditions, recovery actions, validation checks, approval gates and rollback/cleanup instructions. It should be reviewable before an incident, not dynamically improvised by a privileged agent after production is lost.

Separate planning from execution. A recommendation system can propose a recovery point or order, but an execution service should enforce permissions, immutable action identity and the approved target. Tool output and restored documents are untrusted data, not instructions to expand privileges. An AI-generated suggestion must not bypass a retention lock, change a network target or approve its own destructive action.

Human approvals and distributed consensus are different quorums. One decides whether authorized people accept an action; the other decides an authoritative machine state. A September 26, 2026 Cohesity post describes deferred quorum execution with an approved window, explicit execution, reauthorization and expiry behavior. Confirm availability and use the documented workflow rather than assuming approvals automatically schedule execution. [S24]

A rehearsal should be non-destructive and isolated from production traffic. It must still exercise realistic data, identity and key access. Merely validating the syntax of a blueprint does not prove that restores work. Record the plan version, recovery point, infrastructure shape, dependencies, elapsed phases and validation evidence.

Promotion to production is a separate decision. Confirm that external integrations, secrets, network routes, data-loss window and application correctness are acceptable. Monitor for reinfection or hidden dependency failures after cutover. Preserve the clean-room investigation evidence and record which snapshot and plan produced the promoted environment.

Failure case. The orchestrator calls a target API to create a VM, the VM is created, and the response is lost. The action becomes UNKNOWN, not FAILED. Inquire using the original identity and reconcile before issuing another create. The local teaching adapter demonstrates this boundary because reliable orchestration depends more on it than on a visually impressive workflow graph.

25. Helios, multitenancy and control-plane boundaries

PUBLIC / HISTORICAL. Helios provides management across deployments. An older multicloud engineering article describes control/data-plane separation. A NetBackup security brief specifically describes management metadata rather than backup payload flowing into that management context. Neither statement should be generalized to every cloud backup, vault or Gaia workflow. [S20] [S21]

Metadata is still sensitive. Hostnames, users, file paths, policy names, job errors and infrastructure relationships can reveal the organization's topology and confidential activity. A "metadata only" design therefore still needs encryption, authorization, regional placement review and a retention policy.

PROPOSED tenant model. Scope every object by tenant and, where relevant, organization, cluster, source and security domain. Derive scope from the authenticated principal rather than trusting a tenant ID supplied in a request body. Enforce authorization inside the service that performs the action, not only at a global gateway. A forged cluster routing header must not redirect an authorized request into another customer's data.

Control-plane outages should have explicitly defined consequences. Existing scheduled local protection can continue if policies, credentials and execution authority remain valid locally. New policy changes or cross-cluster actions may pause. Never treat control-plane loss as a reason to bypass an expired credential or permission restriction. Record which decisions are cached, their version, maximum age and revocation behavior.

Telemetry pipelines need backpressure and bounded retention. If the management endpoint is unavailable, local execution should not fail merely because a noncritical metric cannot be uploaded. Security audit events, however, require durable buffering and overflow alarms. A buffer that silently drops privileged actions during an incident undermines the recovery record.

A management command can traverse several boundaries: user identity, tenant control plane, cluster connector and local privilege enforcement. Preserve correlation IDs without logging secrets. Bind approvals to the exact target cluster and resource identity. Recheck authority when a delayed action finally runs; permission at request time is not always permission hours later.

Qualification. Ask where each data class travels: operational metadata, credentials/tokens, protected content, extracted text, embeddings, audit logs and support bundles. Obtain a service-specific answer. A single cloud-region diagram from an older white paper is not proof of current placement for every component.

26. SmartFiles and multiprotocol storage services

PUBLIC. SmartFiles exposes file and object-oriented storage services, data mobility and security capabilities on the Cohesity platform. The supported protocol features and interoperability rules depend on the deployment and version. [S19]

A multiprotocol service is not merely several network ports in front of identical semantics. SMB users can carry directory-based identities and richer ACLs; NFS clients may use numeric identities or other negotiated security; object clients use key-based APIs and object versions. Mapping these into one namespace requires explicit choices about ownership, permissions, names, locks and metadata representation.

PROPOSED design. Keep one authoritative namespace and version model. Protocol gateways translate requests into typed internal operations that enforce a common authorization policy. Preserve source-specific metadata where a lossless common representation is impossible. Do not make an object public because a file permission could not be translated.

Live file service and backup storage have different workload shapes. Interactive reads care about tail latency and locking. Protection ingestion values throughput and sequential batching. Background scanning, indexing and tiering compete with both. Establish resource classes, queue limits and admission controls instead of assuming that shared hardware automatically yields predictable behavior.

Snapshots can provide prior versions and recovery points, but application consistency remains the application's responsibility unless an explicit coordination mechanism exists. An SMB share snapshot of active database files is not automatically equivalent to a native database backup. Tiered content may also require cold retrieval when accessed, affecting application latency and timeout behavior.

Capacity controls should account for snapshots, clones, active writes, locked content and background-work headroom. A quota on visible current files can understate retained historical data. Conversely, charging all shared chunks independently to each user may overstate physical usage. Define logical quota, retained logical usage and physical billing separately.

Verification. Test permission translation, rename behavior, open-file semantics, concurrent writes, sparse data, namespace size and recovery from a snapshot under each supported protocol. Include a denied-access test after a group membership change. Ensure search, preview and analytics results follow the same visibility policy as actual data access.

27. NetBackup architecture: primary, media, clients and catalog

PUBLIC. NetBackup has distinct primary-server, media-server, client and storage responsibilities. Its primary catalog includes backup-image information, relational data and configuration needed for operation and recovery. That catalog is a critical protection target in its own right. [S30] [S37]

The primary server coordinates policy and scheduling and maintains authoritative knowledge about protected images and jobs. Media services handle supported transport and storage coordination. Clients integrate with workloads and may perform source-side processing. The precise data path varies by storage target and feature; diagrams must distinguish control messages, metadata and bulk content.

A storage backend can contain useful backup data while a lost catalog makes normal discovery and recovery difficult. Conversely, a catalog can list an image whose media or required keys are unavailable. Monitoring should compare catalog claims with storage and restore evidence rather than treating either side as sufficient alone.

PROPOSED operating model. Protect the NetBackup catalog, disaster-recovery materials, certificates, encryption dependencies and infrastructure configuration through a documented independent process. Rehearse rebuilding the primary server in a clean environment. Record prerequisites that would otherwise be found only on the failed system.

Scaling has several independent dimensions: number of clients, job concurrency, catalog size, metadata transaction rate, media throughput, deduplication working set, restore concurrency and operational complexity. Adding media servers can improve payload capacity without solving a primary catalog bottleneck. Similarly, a faster deduplication target does not remove slow application hooks or source API limits.

Use separate privileges for policy management, recovery, storage administration and security approval where the product supports them. An operator who can initiate a restore may be able to exfiltrate large amounts of historical data even without deleting backups. Restore destination controls and audit evidence are therefore as important as deletion restrictions.

Migration caution. Keeping existing NetBackup policies and catalogs while changing the storage path can reduce operational change, but every image lifecycle must be tested: new backup, incremental continuation, old-image restore, retention expiry, duplication, catalog recovery and mixed-version rollback. "New backups succeed" is not enough to certify a storage migration.

28. MSDP and the difference between deduplication engines

PUBLIC. NetBackup's MSDP documentation describes segmentation, SHA-2 fingerprints, lookup/cache behavior, unique-segment storage and reclamation. Separate versioned documentation discusses variable-length versus fixed-length client deduplication. These details belong to that engine and release, not automatically to SpanFS. [S35] [S36]

The pipeline turns a backup stream into references to stored unique segments. Recovery reassembles the stream from those references, so segment metadata and indexes are part of the recovery dependency graph. Storage efficiency is useful only if the reference structure remains correct and recoverable.

Engineering tradeoff. Source-side deduplication can reduce network traffic and downstream ingest work, but it consumes client CPU and memory and introduces lookup/control traffic. Media-side processing centralizes work but may require transporting more bytes. The best path depends on source capacity, network cost, reuse and the supported client/target combination.

Fingerprint caches improve throughput when the active working set fits. A cache miss is not inherently an error, but a poorly sized index can convert sequential backup into expensive random metadata access. Measure fingerprint lookup latency and storage amplification rather than only end-to-end job duration. Data with little reuse can make hashing and lookup mostly overhead.

Reclamation must account for every live backup image that references a segment. A segment is not disposable because one image expired. Index recovery and rebuild procedures need to be tested under crash and storage-loss conditions. Never delete internal deduplication objects manually as a shortcut to capacity recovery.

Version boundary. A historical fixed-length segment size or a configuration switch in a 10.5 document does not establish the defaults in every 11.x deployment. Do not tune using folklore from another engine. Record the exact configuration and test the source-side and target-side performance together.

Benchmark set. Compare source deduplication and media processing for full backups, incremental changes, encrypted/compressed files and restore-heavy workloads. Include index warm-up, cold restart, full storage, repair contention and retention cleanup. For a migration to another target, verify old recovery points independently; reusing a product name does not imply interchangeable physical formats.

30. Gaia: making protected data useful without weakening its boundary

PUBLIC. Gaia provides retrieval and grounded answers over selected enterprise information, with citations and deployment options. A self-managed guide dated February 2026 describes an AI engine with Helios self-managed and Data Cloud components. Some related product-page capabilities are marked coming soon and are not treated here as generally available. [S38] [S39] [S40]

Backup data is valuable for retrieval because it includes historical information, but that creates a difficult authorization problem. PROPOSED RAG pipeline. 32. Protection and recovery API workflows

PUBLIC. Versioned endpoints create protection groups and recoveries and list recovery tasks. Recovery bodies depend on the workload and include source/snapshot context and target-specific parameters; there is no one universal restore JSON body. Helios list APIs use pagination, and some bulk metadata operations can return HTTP 207 with per-entity outcomes. [S43] [S45] [S46] [S47] [S48]

Only then submit the version-correct request. Persist the returned task/recovery identifier before polling or subscribing to completion evidence.

An HTTP success response may mean admission, not completed recovery. Inspect the operation state and child results. A bulk request returning partial success must not be retried wholesale without understanding which entities already changed. Process each result under a stable local entity-operation identity, then retry only operations for which the vendor contract and observed state make retry safe.

33. Observability and service-level engineering

A backup platform needs technical metrics and recovery evidence. Requests per second and API uptime say little about whether a business can recover.

PROPOSED indicator families. Capture measures source checkpoint age, scheduled-run lateness, failed objects, consistency-mode results and source cleanup backlog. Storage measures durable-placement failures, repair debt, corruption findings, metadata latency and free healing capacity. Copy services measure destination checkpoint age and unfulfilled replication/vault obligations. Recovery measures admission latency, fetch/restore throughput, dependency delays and application validation.

Use explicit states for partial protection. A job that protects 999 of 1,000 objects may be operationally acceptable only if the missing object is understood; an aggregate 99.9% success rate can hide the most important database. Weight business criticality through separately visible objectives, not a denominator trick that masks failures.

An error budget should correspond to a defined operation. A correct authorization denial is not service unavailability. An inaccurate "snapshot not found" caused by a stale index is not a successful business response. A console that accepts a restore request but cannot execute it should not count that request as a validated-recovery success.

Trace a source checkpoint through run ID, snapshot ID, manifest root, copy ID, recovery ID and target identity. Logs should preserve these relationships without recording secrets or unrestricted file contents. Export privileged audit events to an independently controlled destination. A compromised backup administrator should not be able to erase the only evidence of their own actions.

Alert on symptoms and actionable risk: critical recovery point older than objective, vault lag exceeding tolerance, repeated key-access failures, repair backlog with shrinking redundancy, imminent loss of healing headroom, failed restore drill, or catalog/payload reconciliation mismatch. Avoid paging for every individual retry when the operation is still progressing safely.

Operational dashboard. For each critical application, show newest qualified local and isolated recovery points, consistency class, dependencies, keys last tested, last successful application restore, measured RTO, current exceptions and responsible owner. This is more useful than a chart of cumulative bytes backed up.

Capacity isolation. During an incident, prioritize recovery and integrity repair over nonurgent scans and new low-priority captures. Make that policy explicit and test it. An emergency resource policy that exists only in a runbook may fail if operators cannot access the control plane.

34. Capacity, bandwidth and restore economics

The following is a worked sizing example, not a Cohesity benchmark or recommendation. Replace every input with measured workload data and a supported hardware design.

Assume 1 PB of protected logical data, a 2% daily change rate, thirty days of daily recovery points and an eight-hour daily transfer window. Under a simplifying assumption that each day's changed data is new and retained, the logical retained content before deduplication is approximately:

Initial baseline                      = 1,000 TB
Thirty daily change sets              = 30 x 20 TB = 600 TB
Logical content represented           = 1,600 TB
Assumed unique fraction               = 0.40
Assumed compression factor            = 0.70
Illustrative encoded payload (4+2)    = 1,600 x .40 x .70 x 1.5
                                      = 672 TB

The independence of the deduplication and compression assumptions is not guaranteed. Actual repeated changes can reuse data; databases, encrypted files and compressed media behave differently. Metadata, indexes, manifests, snapshots, journals, working space, spares and free repair headroom are additional. A 20% free-space policy would make total provisioned capacity greater than 672 / 0.8 = 840 TB even before those other costs; it is not the same as simply adding 20% to used data.

Twenty TB over eight hours requires about 694 MB/s of source logical throughput. At 70% usable network efficiency, that corresponds to roughly 7.94 Gbit/s of nominal bandwidth before safety headroom. Deduplication can reduce transferred bytes on a qualifying path, but sizing should include a rebaseline case with much less reuse.

Restore sizing works backward from the objective. Restoring 100 TB in eight hours requires about 3.47 GB/s of materialized payload, before replay and validation. If two hours are reserved for bootstrap and validation, six hours of copying requires about 4.63 GB/s. The slowest surviving link among storage read, decoding, network, target write and application replay bounds the result.

Metadata scale can be surprising. A 1 PB dataset divided into average 256 KiB unique chunks would produce about 3.8 billion references before reuse and packing effects. A simplistic fixed 64-byte record would already imply hundreds of GB of raw metadata, before indexes and replication. This is a hypothetical design calculation, not a SpanFS chunk-size claim.

Commercial model. Include hardware/cloud capacity, requests, retrieval, egress, standby compute, support, supportability testing, source-agent maintenance, incident response and recovery drills. The cheapest storage tier can be the most expensive recovery strategy. Measure cost per protected application with a proven recovery objective, not only cost per raw TB.

35. Upgrades, format evolution and migrations

A storage upgrade changes software that interprets years of retained data. Its compatibility contract is more demanding than a stateless web-service rollout.

PROPOSED format rule. New readers must understand old retained formats. New writers should not emit an incompatible format until the rollback boundary is understood and the cluster is qualified. Use explicit feature gates for format changes, not implicit behavior based on which worker happened to handle a request.

Test mixed-version operation, retries across versions, catalog migration, encryption-key metadata, compression codecs, manifest formats and old snapshot restores. Preserve version tags in durable objects. A rolling upgrade that keeps new backups running but breaks a two-year-old recovery point is not successful.

Schema migrations should separate expansion from contraction. Add compatible fields and readers, migrate or backfill under throttling, verify coverage, then remove old dependencies only after the retention and rollback policy permits. A catalog column that appears unused by the latest binary may still be needed to interpret historical data or a recovery export.

Source adapters create another compatibility axis. A vSphere or database upgrade can change APIs, consistency hooks or supported restore paths even if the backup cluster is unchanged. Maintain a tested source/target compatibility matrix and block unsupported combinations before they create unrecoverable images.

For a storage migration, run a canary cohort and validate both newly written and previously retained images. Compare policy behavior, source resource usage, throughput, restore correctness, retention enforcement and catalog disaster recovery. Do not delete the old copy merely because the new system lists the expected snapshot names.

Rollback. Define the last reversible step. A new on-disk format, new key authority or migrated immutable retention can make rollback more complex than reinstalling an older binary. Record the supported fallback and the maximum period in which it remains possible. Make operators acknowledge irreversible transitions intentionally.

VERIFY. Cohesity appliance and software upgrade sequences, firmware dependencies, qualified releases and support windows are product-specific. This book supplies the engineering review method, not a substitute for the vendor's exact upgrade procedure or an authorization to run unsupported mixed versions.

36. Build-from-scratch architecture: start with recoverability

Everything in Chapters 36-44 is a PROPOSED reference architecture, not a claim about Cohesity's private implementation. The first product should support one carefully qualified source, one durable target and one thoroughly tested restore path. Broad source coverage is expensive because each adapter carries years of compatibility obligations.

Separate control and data concerns. The control plane owns tenant identity, authorization, policy versions, inventory, scheduling and user-facing operations. A catalog authority owns immutable snapshot roots, operation identities, metadata transactions and retention decisions. Data workers chunk, encode, verify and move payload. Recovery executors reconstruct targets under explicit authority. An independent recovery domain contains vaulting, bootstrap materials and critical audit evidence.

Use a mature transactional database for the initial catalog and durable object storage for payload. Prefer a small number of well-defined services over one microservice per table. A local database transaction should encompass publication decisions; object writes occur outside it and become reachable only after commit. This creates reclaimable orphans on failure rather than partially valid recovery points.

Build versus adopt. Adopt vetted cryptography, transport libraries, source SDKs, consensus databases, object storage and identity integration where possible. Build the source checkpoint model, snapshot/manifest contract, catalog closure validation, retention/GC coordination, restore workflow and independent verification. A company gains little differentiation from an unreviewed encryption format or custom consensus implementation.

Do not let the search index become the catalog. Search is eventually consistent and rebuildable; the authoritative root inventory must not be. Do not let a message queue become the only record of pending work. A scheduler can reconstruct work from durable state. Do not let an AI planner become a privileged execution authority. The execution service enforces preconditions independently.

For an initial implementation, a relational catalog plus immutable packed objects may be sufficient. A specialized distributed filesystem becomes justified when measured workload and service requirements exceed that approach: low-latency multi-protocol serving, granular snapshots, high parallelism, integrated repair and efficient global metadata. Evolve from measured constraints, not from an ambition to reproduce a proprietary engine immediately.

Service ownership. Assign clear teams for source integrations, catalog/metadata, storage/data movement, recovery/security and platform operations. Each team owns an invariant and its test evidence. Product features that cross teams need an end-to-end recovery owner, not only local service SLAs.

38. Atomic publication and safe reclamation algorithms

Snapshot publication is the point at which a capture becomes a promised recovery object. It must be a small, authoritative decision over content already made durable.

publish(command):
  prepare canonical manifest and stable operation identity
  write immutable content outside the catalog transaction
  obtain durable placement evidence under the required policy

  transaction:
    authorize tenant, source and requested operation
    if operation key exists:
      require same request digest; return stored outcome
    require current owner epoch and expected source generation
    require run is in a publishable state
    validate extent closure and referenced content generations
    require durable receipts satisfy the declared fault model
    insert immutable snapshot root and manifest identity
    record policy retention and source checkpoint
    record operation result and advance run state
    append outbox and audit event
  commit

Durability evidence is meaningful only under a stated fault model. No receipt promises survival after every independent copy and key is destroyed. The catalog/data protocol must guarantee that referenced generations cannot be retired while publication is in progress. A database transaction cannot lock an unrelated object-store deletion unless an explicit coordination mechanism connects them.

A scalable GC design can use tracing with epochs and barriers. First establish a catalog boundary for committed roots. Protect writer/read pins and objects created during the cycle. Trace reachable metadata and chunks. Quarantine candidate generations. Before physical deletion, use an atomic final transition that proves no new references or pins can be admitted to that retiring generation. Writers encountering a retiring generation must obtain a new durable generation or retry under the protocol, not publish the stale reference.

LIVE -> RETIRING(generation, gc_epoch) -> DELETED

A raw DELETE WHERE refcount=0 is unsafe if another process can publish a reference concurrently. Likewise, a time delay does not solve an unbounded paused-writer race. Correctness requires an admission barrier, not merely patience.

Object identifiers must avoid ABA confusion: an old reference to generation 7 cannot suddenly mean a new generation 8 stored under the same mutable location. Immutable content addressing helps, but the storage lifecycle and encryption metadata must still be versioned. A digest identifies logical bytes; it does not by itself prove a valid durable placement exists right now.

The companion uses a single lock for stage, publish, pin, expire and GC decisions. That deliberately reduces the protocol to an inspectable serial model. A production implementation must replace that lock with a proven distributed protocol and repeat tests under real concurrency and storage failures. The model is a specification aid, not evidence that a distributed GC implementation has been verified.

39. Restore idempotency, approvals and external uncertainty

A restore is an externally visible side effect: it may create infrastructure, overwrite data, attach networks or expose sensitive content. It deserves the same identity and uncertainty discipline as any irreversible operation.

Proposed intent. Bind tenant, source snapshot, target environment, target resource name, network policy, overwrite mode, data scope and plan version into a canonical digest. The requester and approvers review this exact content. Any material change invalidates the approval. Store an execution window, policy version and required independent approver count.

At execution, recheck requester authority, approver validity, expiry, target availability and the unchanged digest. Separate approval consumption from external completion: an approved execution identity may require inquiry and retries, but it must not authorize a different restore. Do not allow the requester to satisfy their own independence requirement through a second session.

The external adapter should accept a stable request identity when the target contract supports it. Persist that identity and immutable payload before network I/O. If the target returns success, record its task/resource ID. If it proves rejection without execution, record non-execution. If the response is lost or inconsistent, record UNKNOWN and reconcile.

NOT_STARTED -> SUBMITTING -> CONFIRMED
                        \-> PROVEN_REJECTED
                        \-> UNKNOWN -> INQUIRY -> CONFIRMED / unresolved

A lease only controls local workers. It cannot retract a delayed packet already sent to an external API. Starting a second worker under a new execution ID can duplicate a VM or overwrite a target twice. Safe recovery depends on the target's real deduplication and inquiry semantics, not the presence of a local lock.

A target that lacks reliable inquiry or idempotency may require human investigation after an ambiguous create. This is an honest liveness limitation. It is safer than declaring failure and reissuing a destructive action blindly. Inquiry returning "not found" can also be inconclusive if the target index is eventually consistent.

Companion example. The fake provider creates a resource, then raises a lost-response exception. The orchestrator records UNKNOWN. Inquiry later returns the original resource, and the operation becomes CONFIRMED without a second create. Tests also reject changed payloads, expired approvals, self-approval and permission revocation. This demonstrates a boundary condition, not universal exactly-once execution across arbitrary target systems.

40. Threat model and security architecture

The threat model must include accidental operators, compromised production credentials, compromised backup administrators, malicious tenants, supply-chain compromise, hostile source files and loss of external key/identity services. "Ransomware" is not a sufficiently precise attacker model.

Proposed controls. Use tenant-scoped identity, narrow service credentials, separate recovery permissions, strong administrator authentication, restricted management networks, independently retained audit logs and isolated recovery tooling. Protect deletion and key-destruction paths with stronger approval than routine ingest. Separate the authority to approve from the authority to execute where the risk justifies it.

Data-plane parsers are an attack surface. Backup agents process untrusted filenames, archive formats, filesystem metadata and application responses. Sandboxing, input limits, memory-safe components where practical, signed updates and rapid patching matter as much as control-plane access. A malformed backup object should not execute code in the catalog authority.

Restore operations can exfiltrate data. Limit target accounts, locations and networks, audit exports, and reauthorize at execution time. A user should not obtain restricted history by restoring a snapshot into an unrestricted share. Search, file preview, malware reports and AI-generated answers must obey equivalent visibility constraints.

Immutability and separation protect against different failures. An immutable object can still depend on one compromised key authority. A separate account can still be controlled by the same production administrator. A vault can still be ineffective if recovery requires an unavailable primary catalog. Draw the authority graph and test correlated compromise, not just network topology.

Recovery-image trust. Store signed or otherwise independently verified recovery tooling and versioned infrastructure definitions. A clean room built from compromised automation can reproduce the original compromise. Preserve a path to verify software without relying on the failed environment's internal package mirror.

Security validation. Test cross-tenant IDs, stale group membership, expired service credentials, changed approval payloads, denied target exports, malicious file metadata and audit-buffer exhaustion. Conduct independent penetration and supply-chain reviews before production. The teaching code does not implement production authentication, encryption, tenant-grade sandboxing or a certified security boundary.

41. Recover the protection system itself

A recovery platform must not require its own lost control plane to discover and restore the information needed to rebuild that control plane.

Proposed bootstrap package. Include trusted software/configuration versions, infrastructure definitions, independent credential procedures, catalog recovery instructions, key version inventory, manifest/inventory verification tools and operational contacts. Encrypt sensitive contents, retain recoverable keys independently and test the package on replacement infrastructure.

Protect the catalog through a supported consistent backup and recovery process. Catalog replay or reconstruction must preserve snapshot identities, operation deduplication history, holds, retention decisions and outstanding external recovery intents. Losing deduplication records while retaining target resources can cause dangerous re-execution after restart.

Independent storage inventory helps diagnose catalog loss, but scanning object storage is not automatically a complete catalog restore. Packed objects, encryption, retained generations and snapshot roots need their interpretation metadata. A content-addressed store cannot tell you which tenant was authorized to restore which historical application merely from raw chunk hashes.

A recovered system should start in a restricted mode. Disable automatic destructive cleanup, external restores and outbound automation until the catalog, permissions, keys and outstanding operations are reconciled. Old schedules can otherwise trigger inappropriate work against current infrastructure. Retention clocks and legal holds also need verification before reclamation resumes.

External-world rule. Restoring yesterday's catalog does not undo a VM created today or a vault copy completed after the snapshot. Reconcile with external target evidence before resubmitting operations. Preserve original operation identities when reconstructing outcomes. A recovery-job ID is not a new business identity for every historical action.

Test three different scenarios: loss of a catalog node within the supported redundancy model; loss requiring catalog backup restoration; and compromise requiring a clean-room rebuild with new identities. Their trust assumptions and recovery procedures differ. A fast failover test does not validate recovery from corrupt or malicious catalog history.

Exit gate. Resume normal automation only after catalog integrity checks, sample content restores, retained-snapshot inventory reconciliation, key tests, target-operation reconciliation and explicit approval. Keep uncertainty visible and owned rather than deleting difficult records to make the dashboard green.

42. Testing: invariants, fault injection and recoverability benchmarks

A storage product is not validated by successful happy-path backups. Its key properties are about what cannot happen during concurrency, failure and recovery.

Model tests. Generate sequences of stage, publish, duplicate publish, expire, hold, pin, restore and collect operations. Assert that published content remains reconstructible, shared chunks are not deleted while required, tenant boundaries hold, stale epochs fail and changed idempotent payloads conflict. Include malformed manifests and intentional digest corruption.

Distributed tests. Kill processes during object writes and catalog commits. Partition metadata replicas. Delay a former owner until after leadership changes. Drop acknowledgments. Corrupt fragments. Exhaust disks. Pause the collector while a new snapshot references a candidate chunk. Reorder event delivery. Test lost messages independently from duplicate messages.

Source/target conformance. Real adapters require real workload tests: VMware snapshot cleanup and CBT resets, database log gaps and timeline changes, file metadata fidelity, SaaS throttling and token invalidation, and Kubernetes dependency recovery. The local companion cannot establish any of those integrations.

Performance tests. Use representative data distributions and report warm/cold caches, deduplication reuse, compression, chunk counts, object sizes, concurrency and source bottlenecks. Measure p50/p95/p99 where appropriate, but do not hide failed operations outside the latency histogram. Run restore and repair together under one failed fault domain.

Recovery correctness. Check bytes against manifests, namespace/security fidelity, database consistency and application transactions. Record the exact recovery point and target. A successful restore of a small sample does not prove the entire estate; maintain a risk-based sampling and full-drill schedule.

Release evidence. Store test configuration, build IDs, source versions, results and known exceptions. A security patch may still require targeted old-format and recovery regressions. A performance optimization that weakens durability acknowledgment or GC barriers is a correctness regression even if throughput improves.

The companion test suite is deliberately labeled a local specification exercise. Its passing result shows that the tested model behavior matches the written assertions. It does not prove distributed safety, physical durability, production cryptography, Cohesity compatibility or a service-level objective.

43. Operational runbooks and incident decision points

A runbook should identify evidence, authority and safe next actions. It should not be a list of destructive commands copied from an unrelated release.

Backup lag. Determine whether the bottleneck is source consistency, source API quotas, data movement, catalog commit, downstream copy or indexing. Protect the last good recovery point. Do not run unlimited retries against an already overloaded production database. Report the actual recoverable source time and the affected applications.

Capacity emergency. Pause noncritical admission, quantify retained/held data and repair headroom, inspect safe reclaimable candidates, and add qualified capacity. Do not shorten locked retention or manually delete chunk files. Determine whether the storage system can still complete an in-progress restore and repair its declared failures.

Node or disk loss. Verify the failed domain, remaining data and metadata protection, repair progress and available destinations. A replacement node may need version/firmware qualification. Prioritize integrity and critical recovery over new low-priority ingestion. Escalate when redundancy remains degraded beyond the accepted window.

KMS or identity outage. Distinguish unavailable service from denied authorization and unknown key version. Use the approved break-glass process; do not weaken cryptographic checks or use unrelated keys. Record which snapshots are currently inaccessible and whether independent recovery materials work.

Cyber incident. Preserve evidence, restrict risky automation, isolate management access, validate the recovery authority and inspect vault status. Select candidate snapshots using incident timing and analysis evidence. Restore into a clean room, validate application behavior, then approve promotion. A negative malware result alone is not the promotion criterion.

Unknown external restore. Freeze automatic resubmission for that intent. Inspect provider/target task and resource evidence. Reconcile the exact approved identity. If uncertainty persists, assign an owner and a business decision rather than marking failure to clear the queue.

After recovery. Reconcile partial resources, rotate emergency credentials, preserve logs, confirm new protection coverage, validate failback plans and update the blueprint. A recovered service running without fresh backups is a new risk. Close the incident only when ongoing protection and operating authority are understood.

44. Company roadmap, teams and launch gates

A credible company begins with a narrow recoverability promise and expands it with evidence. Supporting many workload names before building reliable restores creates a large, expensive liability surface.

Phase 1: one workload. Build a precise source checkpoint model, complete manifest publication, durable storage and a verified restore. Establish identity, audit and secret handling immediately. A lab demonstration should survive process failure and reconstruct the application from independent artifacts.

Phase 2: durable operations. Add scheduling, retention, shared-content reclamation, catalog recovery, remote copying and operator tooling. Define supportable configurations and measured capacity. Introduce a release test matrix and preserve compatibility with retained formats.

Phase 3: scale and isolation. Add fault-domain-aware placement, resource fairness, tested failover, restore-reserved capacity and independent vaulting. Expand only after recovery and repair work under degraded conditions. A larger cluster is not a substitute for a coherent metadata protocol.

Phase 4: cyber recovery and broader sources. Build clean-room orchestration, exact approval binding, threat-evidence integration and application blueprints. Add adapters through conformance suites and source-vendor qualification. Treat every new workload as a long-term maintenance commitment.

Staffing must include source integration engineers, storage/metadata engineers, recovery specialists, SREs, security engineers and a support/qualification function. Customer success for this product includes restore readiness, not just deployment adoption. A named application owner should accept recovery-point and validation outcomes.

Economics. Price and plan for ongoing source compatibility, storage/cloud costs, support escalations, security response, hardware qualification, retrieval/egress and periodic drills. Backup software often encounters customers' least documented infrastructure during their worst incidents. The operational cost is not captured by storage margin alone.

Production launch gate. Require a supported matrix, independent security review, verified catalog/key recovery, application restore evidence, retention/GC fault tests, incident runbooks, source cleanup tests, target idempotency analysis, rollback procedures and honest service objectives. No local code package or architecture document can replace these gates.

The durable principle is simple: protect the ability to recover, not merely the appearance of having backups. That principle connects SpanFS's metadata ideas, NetBackup's catalog discipline, vault isolation, API orchestration and the proposed implementation into one engineering standard.

45. Hands-on companion and laboratory guide

The companion contains a local Python teaching model, tests, a proposed SQLite schema and a proposed OpenAPI skeleton. It does not call Cohesity, NetBackup, cloud storage, a hypervisor or a database server. All identifiers and data are synthetic.

Lab A: shared content. Stage two captures with an identical chunk. Publish both. Expire one and collect garbage. Restore the other. Observe that snapshot expiration and physical chunk deletion are different events.

Lab B: publication failure. Stage only part of a proposed manifest and attempt publication. It must fail without exposing a partial snapshot. Stage the missing content and publish under the original operation identity. Repeat publication and receive the same snapshot identity; alter the manifest under the same key and receive a conflict.

Lab C: retention and read pins. Publish a snapshot, hold it, advance the synthetic clock and try to expire it. Release the hold through the explicit model operation. Start a restore pin, expire the snapshot and run collection. Content remains until the active reader releases its pin.

Lab D: stale ownership. Start an ingest under one epoch, advance ownership and attempt to publish with the previous epoch. The stale publisher must fail. Renew the model's ingest ownership explicitly and retry under the current epoch.

Lab E: integrity and scope. Supply an incorrect digest, corrupt stored bytes through the test-only hook and attempt cross-tenant restore. Each operation must fail for a distinct reason. The tests demonstrate policy checks, not a hardened authentication boundary.

Lab F: uncertain restore. Obtain independent approval for a target-bound intent. Make the fake external provider execute and lose the response. Reconcile by inquiry and prove that only one target was created. Try self-approval, changed payload, expired approval and revoked authority.

Run the package using a supported local Python installation:

cd companion
python -m unittest discover -s tests -v
python demo.py
python validate_schema.py

The model stores payloads in process memory and serializes operations. A restart loses its content unless a caller reconstructs it; it is not a durable store. The SQL file is a separate structural reference, not the model's persistence backend. There is no real replication, erasure coding, distributed GC, encryption, KMS, network authorization or application adapter.

Use the model to review invariants and extend tests before implementing a real service. Do not import it into a production backup agent or treat passing tests as proof of Cohesity compatibility.
