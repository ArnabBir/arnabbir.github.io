Chapter 52 — POSIX Message Queues

POSIX message queues offer priority-ordered message delivery with async notification — cleaner than System V, with better integration into event-driven architectures. Each message has discrete boundaries (not a byte stream) and an unsigned priority that determines receive order.

This chapter covers mq_open, sending and receiving with priorities, queue attributes (mq_attr), async notification via mq_notify, and timed operations for deadline-aware designs.

Invariant
mq_receive always returns the highest-priority message first. Within the same priority, messages are delivered FIFO.
Gotcha
The receive buffer must be at least mq_attr.mq_msgsize bytes, or mq_receive fails with EMSGSIZE. Check attributes after open.
Debugging
cat /dev/mqueue/<name> shows QSIZE (total bytes), NOTIFY (registered PID), SIGNO, and current/max messages.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • mq_open(name, flags, mode, attr) creates or opens a queue. The attr parameter sets mq_maxmsg (max messages in queue) and mq_msgsize (max bytes per message) at creation time — cannot be changed later.
  • mq_send(mqd, buf, len, priority) enqueues a message. Higher priority number = delivered first. Blocks when queue is full (unless O_NONBLOCK).
  • mq_receive(mqd, buf, len, &prio) dequeues the highest-priority message. The buffer must be ≥ mq_msgsize or the call fails with EMSGSIZE.
  • mq_notify(mqd, sigevent) registers for async notification when a message arrives on an empty queue. Only one process can register at a time. Notification fires once — must re-register after each delivery.
  • mq_timedreceive/mq_timedsend accept an absolute struct timespec deadline — useful for avoiding indefinite blocking.
  • Messages have boundaries: each send/receive is one complete message, unlike pipe byte streams.
  • Backed by /dev/mqueue filesystem. Queue descriptors are NOT regular fds — select/poll/epoll support is Linux-specific (via mq_getattr returning an fd on some kernels).

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
Buffer sizing pitfall
  • mq_receive requires a buffer ≥ mq_msgsize (the queue's max message size), NOT the actual message length. This catches many first-time users.
  • Always call mq_getattr after open to discover the actual mq_msgsize, then allocate accordingly.
  • The default mq_msgsize (if attr is NULL on creation) is system-defined — often 8192 bytes on Linux.
mq_notify semantics
  • Notification fires only when a message arrives on a previously empty queue — not on every message.
  • After notification fires, you must re-register before the next drain-to-empty cycle.
  • Only one process can be registered per queue at a time. A second mq_notify returns EBUSY.
  • With SIGEV_THREAD: the kernel spawns a thread for the callback. Be careful with thread safety and re-registration timing.
  • Best pattern: in the notification callback, drain all messages (loop until EAGAIN), then re-register.
Priority ordering
  • Higher numeric priority = dequeued first. Priority 10 is delivered before priority 1.
  • Within the same priority, messages are FIFO.
  • Maximum priority is at least 31 (MQ_PRIO_MAX - 1); on Linux typically 32767.
  • If you don't need priorities, use 0 for all messages — the queue becomes a simple FIFO.
Timed operations and deadlines
  • mq_timedreceive/mq_timedsend use absolute struct timespec values (CLOCK_REALTIME).
  • Calculate deadline as: clock_gettime(CLOCK_REALTIME, &ts); ts.tv_sec += timeout;
  • Returns ETIMEDOUT if the deadline passes. Returns EINTR if interrupted by a signal.
  • Be aware of clock adjustments (NTP, settimeofday) affecting CLOCK_REALTIME deadlines.

Code patterns (C / POSIX)

Producer-consumer with priorities and mq_notify thread callback. 
/* Producer: send messages with priorities */
struct mq_attr attr = { .mq_maxmsg = 10, .mq_msgsize = 256 };
mqd_t mq = mq_open("/work", O_CREAT|O_WRONLY, 0600, &attr);
mq_send(mq, "low-pri task",  12, 1);   /* priority 1 */
mq_send(mq, "high-pri task", 13, 10);  /* priority 10 */
mq_close(mq);

/* Consumer: receive (highest priority first) */
mqd_t mq = mq_open("/work", O_RDONLY);
struct mq_attr a; mq_getattr(mq, &a);
char buf[a.mq_msgsize];
unsigned prio;
ssize_t n = mq_receive(mq, buf, sizeof(buf), &prio);
/* buf = "high-pri task", prio = 10 (delivered first) */

/* Async notification with thread callback */
static void on_msg(union sigval sv) {
    mqd_t mq = *(mqd_t *)sv.sival_ptr;
    struct mq_attr a; mq_getattr(mq, &a);
    char buf[a.mq_msgsize]; unsigned p;
    while (mq_receive(mq, buf, sizeof(buf), &p) > 0)
        process(buf, p);            /* drain all */
    struct sigevent sev = { .sigev_notify = SIGEV_THREAD,
        .sigev_notify_function = on_msg,
        .sigev_value.sival_ptr = sv.sival_ptr };
    mq_notify(mq, &sev);           /* re-register */
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Set mq_maxmsg and mq_msgsize explicitly at creation — don't rely on defaults.
  • Always allocate receive buffers to mq_msgsize (from mq_getattr), not the expected message size.
  • Use mq_timedsend/mq_timedreceive with deadlines to avoid indefinite blocking.
  • If using mq_notify: drain all messages in the callback, then re-register before returning.
  • Call mq_unlink during cleanup; design idempotent startup that unlinks stale queues.

Exercises

Hands-on tasks to make the chapter "stick". These are intentionally practical and debugging-heavy.
  • Write a producer that sends messages at priorities 0, 5, 10. Write a consumer that receives them and verify the order is 10, 5, 0.
  • Implement mq_notify with SIGEV_THREAD. Send messages from another process and verify the callback fires. Test what happens if you forget to re-register.
  • Fill a queue to capacity and observe mq_send behavior with and without O_NONBLOCK. Use cat /dev/mqueue/<name> to watch mq_curmsgs.
