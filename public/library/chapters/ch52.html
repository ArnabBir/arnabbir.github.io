    TOPIC 52 / 64 · POSIX Message Queues

    POSIX queues combine priority with capacity

    Low-priority work starves despite being enqueued first.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    POSIX message queues retain message boundaries and return higher-priority messages before lower-priority ones. Equal-priority messages retain FIFO ordering. Priority is a scheduling policy, not a fairness guarantee. A finite maximum count and maximum message size force explicit backpressure decisions.

    Contract and implementation boundary

    mq_receive requires a buffer at least as large as the queue's configured mq_msgsize, even for a smaller pending message. mq_notify is a one-shot registration, not a persistent subscription; a robust consumer rearms and drains with careful race handling. Timed operations use their documented absolute clock basis.

    Contract references: mq_overview.7 · mq_receive.3 · mq_notify.3. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    Registering once and expecting endless notifications stalls after the first event. A stream of urgent messages can indefinitely delay ordinary work. Oversized queue settings may be rejected by system or per-user limits.

    Worked reasoning trace

    Assumptions: Queue has A at priority 1, B at 3, C at 3; no further arrivals.

    1. Starting state

      Receiver has a correctly sized buffer.

    2. Operation

      Receive three messages.

    3. Expected observation

      Order is B, C, A: priority first, FIFO within equal priority.

    Tradeoff: Priority improves urgent work latency but can starve low-priority work.

    This is a hand-authored prediction, not captured runtime output.

    Original practice problem

    Trace messages A(priority 1), B(3), C(3). Predict B, C, A, then add a continuous high-priority arrival stream and propose aging or separate capacity quotas at the application level.
