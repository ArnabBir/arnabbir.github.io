    TOPIC 2 / 64 · Fundamental Concepts

    Names, handles, and kernel objects

    A file is removed while a worker still reads it. Why does the worker continue?

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    A pathname is a lookup instruction. A descriptor is a small integer in one process. Its open file description carries state such as an offset and status flags. The underlying inode represents the file object. These are separate lifetimes: removing a directory entry does not invalidate an existing open reference.

    Contract and implementation boundary

    open returns a descriptor or -1. close releases that descriptor. unlink removes a name; storage can remain until the final link and final open reference disappear. A reused integer does not identify the old object.

    Contract references: open.2 · unlink.2 · inode.7. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    Logging only descriptor 7 across asynchronous operations can hide a reuse bug. After close, another open may return 7 for an unrelated file. Keep ownership explicit and do not let a delayed callback close a newly reused handle.

    Worked reasoning trace

    Assumptions: Regular file; one link; one open reference; calls succeed.

    1. Starting state

      notes has bytes OK and fd 3 points to its object.

    2. Operation

      unlink removes notes; read uses fd 3.

    3. Expected observation

      The old descriptor can read OK; a new open of notes fails.

    Tradeoff: Handle-based work tolerates renames but retains resources until close.

    This is a hand-authored prediction, not captured runtime output.

    Original practice problem

    In a private temporary directory, open a file, unlink its name, then read through the open descriptor. Contrast that success with a new open of the removed pathname. Close the original descriptor to release the remaining reference.
