Chapter 02 — Fundamental Concepts

This chapter lays the conceptual foundation for everything that follows. The kernel is the privileged resource manager that arbitrates access to the CPU, memory, and devices on behalf of all processes. Every process runs in its own isolated virtual address space — a fiction maintained by hardware page tables — and interacts with the outside world exclusively through system calls: the narrow gate between user mode and kernel mode.

The file descriptor is Linux's universal I/O handle: a small integer that can point to a regular file, a pipe, a socket, or a device. The permissions model (uid/gid/mode bits) governs who may do what. Mastering these abstractions — kernel as arbiter, processes as containers, virtual memory as illusion, file descriptors as uniform handles, and permissions as access gates — is the prerequisite for every chapter ahead.

Invariant
Every user-space operation that touches hardware goes through a syscall — there are no shortcuts.
Gotcha
User mode cannot access kernel memory directly; attempted access triggers SIGSEGV.
Debugging
Use /proc/PID/maps to see the process memory layout and /proc/PID/status for process state.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • The kernel is the resource arbitrator: it owns all hardware and exposes controlled operations via syscalls. User code never touches a disk controller or NIC directly.
  • The user/kernel mode boundary is enforced by the CPU itself. A mode switch (trap/interrupt) is required to enter kernel code; this has measurable cost (~100ns+ per syscall).
  • A process is an isolated resource container: it has its own PID, virtual address space, file descriptor table, signal dispositions, credentials (uid/gid), and resource limits.
  • The virtual address space is divided into segments: text (read-only code), initialized data, BSS (zero-initialized), heap (grows up via brk/mmap), memory-mapped regions, and stack (grows down). The kernel maintains page tables mapping virtual to physical pages.
  • File descriptors are uniform I/O handles — small non-negative integers indexing into a per-process table. Whether the underlying object is a file, pipe, socket, or device, the same read()/write()/close() interface applies.
  • The permission model combines user IDs (real, effective, saved), group IDs, and per-file mode bits (rwx for owner/group/other). The superuser (uid 0) bypasses most checks — a powerful but dangerous privilege.
Key terms & kernel objects
Term / objectMeaning
KernelThe privileged core of the OS that manages hardware resources, enforces isolation, and provides services to processes via syscalls.
System callThe mechanism for user-space code to request kernel services. The CPU traps into kernel mode, executes the requested operation, and returns the result.
ProcessAn instance of a running program with its own virtual address space, file descriptor table, credentials, and scheduling state. Identified by a unique PID.
Virtual memoryAn abstraction giving each process the illusion of a large, contiguous, private address space. The MMU translates virtual addresses to physical frames via page tables.
File descriptorA small non-negative integer that serves as a handle to an open file, pipe, socket, or device within a process. Indexes into the kernel's per-process open file table.
InodeAn on-disk data structure that stores a file's metadata (ownership, permissions, size, block pointers). Directory entries map names to inode numbers.
SuperuserThe privileged account (uid 0) that bypasses most permission checks. Modern systems prefer capabilities over full root to limit exposure.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
User/kernel boundary crossing cost
  • Every syscall requires a mode switch: saving user registers, switching to kernel stack, executing the handler, restoring state, and returning. This costs ~100-300ns even for trivial calls like getpid().
  • vDSO (virtual dynamic shared object) optimizes a few read-only syscalls (gettimeofday, clock_gettime) by mapping kernel data into user space — no actual mode switch needed.
  • Batching I/O (e.g., buffered stdio, readv/writev, io_uring) amortizes crossing cost. Never call write() per byte in a hot loop.
  • Context switches between processes are even more expensive: TLB flushes, cache pollution, and scheduler overhead add up.
Virtual vs physical memory misconceptions
  • malloc() returning non-NULL does not mean physical memory is available. Linux overcommits by default: pages are backed by physical RAM only on first write (demand paging).
  • The OOM killer may terminate your process long after allocation "succeeded" if the system runs out of physical memory.
  • A process's virtual size (VSZ) can be much larger than its resident set (RSS). Reading VSZ alone is misleading.
  • Stack size is limited (typically 8MB via ulimit); exceeding it causes SIGSEGV, not a graceful error. Deep recursion or large stack allocations are dangerous.
Permission inheritance subtleties
  • fork() copies the parent's credentials (real/effective/saved UIDs and GIDs) to the child. The child inherits the same permissions.
  • execve() of a set-uid binary changes the effective UID to the file's owner — this is how programs like passwd gain temporary privilege.
  • File descriptors survive fork() and (unless O_CLOEXEC) execve(). A privileged fd leaked to an unprivileged child is a security hole.
  • umask subtracts permission bits from the mode argument of open()/mkdir(). A permissive umask (0000) in production can expose files unintentionally.

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
/* ch02_fundamentals.c — Query process identity and system limits */
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <errno.h>
#include <string.h>

int main(void) {
    /* Process identity — these calls always succeed */
    printf("PID  = %ld\n", (long)getpid());
    printf("PPID = %ld\n", (long)getppid());
    printf("UID  = %ld  (effective = %ld)\n",
           (long)getuid(), (long)geteuid());
    printf("GID  = %ld  (effective = %ld)\n",
           (long)getgid(), (long)getegid());

    /* System limits via sysconf — proper error handling */
    errno = 0;
    long open_max = sysconf(_SC_OPEN_MAX);
    if (open_max == -1) {
        if (errno) { perror("sysconf _SC_OPEN_MAX"); exit(1); }
        printf("OPEN_MAX: indeterminate\n");
    } else {
        printf("OPEN_MAX = %ld\n", open_max);
    }

    long page_sz = sysconf(_SC_PAGE_SIZE);
    if (page_sz == -1) { perror("sysconf _SC_PAGE_SIZE"); exit(1); }
    printf("PAGE_SIZE = %ld bytes\n", page_sz);

    long clk_tck = sysconf(_SC_CLK_TCK);
    if (clk_tck == -1) { perror("sysconf _SC_CLK_TCK"); exit(1); }
    printf("CLK_TCK = %ld Hz\n", clk_tck);

    return 0;
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Set O_CLOEXEC on every open() to prevent file descriptor leaks across exec boundaries.
  • Never assume malloc() success means physical memory is available; handle OOM gracefully or use mlockall() for critical pages.
  • Check and set umask explicitly in daemons; do not rely on the inherited value.
  • Run as a non-root user with minimal capabilities instead of full superuser privileges.
  • Use /proc/PID/maps and /proc/PID/fd/ to audit memory layout and open descriptors in production.
  • Validate sysconf() return values before using them as array sizes or loop bounds — indeterminate limits return -1 without setting errno.
  • Prefer getresuid()/getresgid() to inspect all three UID/GID values when debugging permission issues.

Exercises

Hands-on tasks to make the chapter "stick". These are intentionally practical and debugging-heavy.
  • Compile and run the code pattern above. Then inspect /proc/self/maps from within the program (open and read it) to see text, heap, stack, and vDSO segments.
  • Write a program that calls getpid() in a tight loop 1 million times. Time it with clock_gettime(). Then compare with the vDSO-accelerated clock_gettime() to feel the syscall cost difference.
  • Create a set-uid program that prints real vs effective UID. Observe how execve() of that binary changes euid while keeping ruid unchanged.
