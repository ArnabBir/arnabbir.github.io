Chapter 46 — System V Message Queues

System V message queues provide typed message passing — each message has a long mtype field enabling selective receipt. This makes client-server multiplexing possible on a single queue: the server reads requests by one type, and each client reads responses by its own unique type (typically its PID).

Unlike pipes, message queues preserve message boundaries and support priority-like retrieval via the type field. However, they lack file-descriptor-based interfaces, making integration with poll/epoll impossible.

Invariant
Each message starts with a long mtype (> 0). The mtype enables selective receive: msgrcv can filter by exact type, any type, or lowest type up to a bound.
Gotcha
Queue limits (MSGMAX per message, MSGMNB total bytes) can cause msgsnd to block indefinitely or return EAGAIN. Always check and tune limits.
Tip
Client-server pattern: server reads type=1 (requests), clients read type=own_pid (responses). One queue handles bidirectional multiplexed communication.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • msgget(key, flags) creates or opens a message queue, returning an integer msqid. Use IPC_CREAT | 0660 to create with permissions; use 0 to open existing.
  • Message structure: every message must start with long mtype (must be > 0), followed by your payload data. The kernel uses mtype for routing but does not interpret the payload.
  • msgsnd(qid, &msg, size, flags): sends a message. size is the payload size (excluding the mtype long). If the queue is full (total bytes ≥ MSGMNB), msgsnd blocks unless IPC_NOWAIT is set (returns EAGAIN).
  • msgrcv(qid, &msg, size, type, flags): receives a message. The type argument controls filtering: type=0 reads the first message (FIFO); type>0 reads the first message with exactly that mtype; type<0 reads the message with the lowest mtype ≤ |type| (priority queue behavior).
  • Queue limits: MSGMAX is the maximum size of a single message (default 8192 bytes). MSGMNB is the maximum total bytes in one queue (default 16384). MSGMNI is the maximum number of queues system-wide. Tunable via /proc/sys/kernel/msg*.
  • Client-server multiplexing: a common pattern uses one queue for both directions. Clients send requests with mtype=1 (or a server-known type). Each client embeds its PID in the message body. The server reads type=1 requests, processes them, and sends responses with mtype=client_pid. Each client calls msgrcv with type=getpid(), receiving only its own responses.
  • msgctl(qid, IPC_RMID, NULL) destroys the queue immediately. All blocked msgsnd/msgrcv calls return with errno=EIDRM. Any messages remaining in the queue are lost.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
Queue full: blocking vs non-blocking
  • When total bytes in queue reach MSGMNB, msgsnd() blocks by default. The process sleeps until space is available or the queue is destroyed (EIDRM).
  • With IPC_NOWAIT, msgsnd returns -1 with errno=EAGAIN immediately. Use this for non-blocking designs, but you must implement your own retry/backoff logic.
  • A single large message can also be rejected if it exceeds MSGMAX — this returns EINVAL regardless of available space.
  • EINTR is returned if msgsnd/msgrcv is interrupted by a signal while blocked. Always retry on EINTR.
Client-server multiplexing with message types
  • Pattern: server reads type=1 requests. Each request includes the client's PID. Server sends response with mtype=client_pid.
  • Each client does msgrcv(qid, &msg, size, getpid(), 0) — receiving only messages addressed to it.
  • Risk: if a client crashes without reading its response, that message remains in the queue consuming MSGMNB space.
  • Mitigation: server can set a timeout or periodically clean up unclaimed messages. Or use MSG_NOERROR and bound message sizes tightly.
Message size limits and E2BIG
  • If a message in the queue is larger than the msgsz argument to msgrcv(), the call fails with E2BIG by default.
  • The MSG_NOERROR flag tells msgrcv to truncate the message silently to msgsz bytes instead of failing. The excess data is lost.
  • MSGMAX (default 8192) limits individual message payload size at send time. Increase via /proc/sys/kernel/msgmax if needed.
  • Design messages with fixed or bounded sizes to avoid E2BIG surprises. Include a size field in your protocol header.
Priority inversion with negative type selection
  • msgrcv with type < 0 selects the message with the lowest mtype ≤ |type|. This enables priority-queue semantics: lower mtype = higher priority.
  • Risk: if many low-type (high-priority) messages arrive continuously, higher-type (lower-priority) messages may starve and never be received.
  • Mitigation: bound the range of mtype values. Periodically drain all types. Or use separate queues for different priority levels.
  • With type=0, messages are received in FIFO order regardless of mtype — simplest but no prioritization.

Code patterns (C / POSIX)

Client-server pattern using message types for request/response routing on a single queue. 
// System V message queue: client-server with type-based routing
#include <sys/msg.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>

struct req_msg {
    long mtype;           // must be 1 (server reads type=1)
    pid_t client_pid;     // for routing response back
    char  body[128];
};
struct resp_msg {
    long mtype;           // set to client_pid
    char body[128];
};

// --- Server side ---
void server(int qid) {
    struct req_msg req;
    struct resp_msg resp;
    while (msgrcv(qid, &req, sizeof(req)-sizeof(long), 1, 0) > 0) {
        printf("server: got '%s' from pid %d\n", req.body, req.client_pid);
        resp.mtype = req.client_pid;   // route to this client
        snprintf(resp.body, sizeof(resp.body), "ACK: %s", req.body);
        msgsnd(qid, &resp, sizeof(resp)-sizeof(long), 0);
    }
}

// --- Client side ---
void client(int qid) {
    struct req_msg req = { .mtype = 1, .client_pid = getpid() };
    strncpy(req.body, "hello", sizeof(req.body));
    msgsnd(qid, &req, sizeof(req)-sizeof(long), 0);

    struct resp_msg resp;
    msgrcv(qid, &resp, sizeof(resp)-sizeof(long), getpid(), 0);
    printf("client %d: got '%s'\n", getpid(), resp.body);
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Always check msgsnd/msgrcv return values; handle EINTR (retry), EAGAIN (backoff), EIDRM (queue destroyed), and E2BIG (message too large).
  • Set mtype > 0 on every message. mtype ≤ 0 causes msgsnd to fail with EINVAL.
  • Tune MSGMAX and MSGMNB (/proc/sys/kernel/msg*) to match your workload. Default limits are small (8 KB / 16 KB).
  • In client-server patterns, handle client crashes: unclaimed response messages leak queue space. Implement a timeout or cleanup sweep.
  • Always call msgctl(IPC_RMID) on shutdown. Use atexit() or signal handlers for crash resilience. Monitor with ipcs -q.
