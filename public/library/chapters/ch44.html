Chapter 44 — Pipes and FIFOs

Pipes are the simplest IPC — a unidirectional byte stream between related processes. FIFOs extend this to unrelated processes via filesystem names. Both are stream-oriented (no message boundaries), kernel-buffered, and automatically cleaned up when all file descriptors are closed.

The key constraints to internalize: PIPE_BUF atomicity for writes, SIGPIPE/EPIPE when readers vanish, and the default 64 KB capacity limit that creates natural backpressure.

Invariant
Writes of PIPE_BUF bytes or fewer (4096 on Linux) are atomic — they will never interleave with other writers on the same pipe.
Gotcha
Writing to a pipe with no readers delivers SIGPIPE (default: terminate) and returns EPIPE. Handle or ignore SIGPIPE in long-running servers.
Tip
Use pipe2(pfd, O_CLOEXEC | O_NONBLOCK) instead of pipe() + fcntl() to avoid fd-leak races in multithreaded programs.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • pipe() creates two file descriptors: pfd[0] for reading, pfd[1] for writing. Data flows in one direction only. For bidirectional communication, use two pipes or a socketpair.
  • pipe2(pfd, O_CLOEXEC | O_NONBLOCK) sets flags atomically at creation — critical for avoiding races where a concurrent fork+exec leaks the pipe fd to a child, or a concurrent thread blocks on a read.
  • Write atomicity: writes ≤ PIPE_BUF (4096 bytes on Linux) are guaranteed atomic. Writes > PIPE_BUF may be interleaved with data from other writers. This matters when multiple children write to a shared pipe.
  • Pipe capacity: default 64 KB on Linux (16 pages). Adjustable per-pipe via fcntl(F_SETPIPE_SZ) up to /proc/sys/fs/pipe-max-size. When the pipe is full, write() blocks (or returns EAGAIN with O_NONBLOCK).
  • FIFOs (named pipes): created with mkfifo(path, mode). They have a filesystem name so unrelated processes can open them. open() on a FIFO blocks until both a reader and writer have opened it (unless O_NONBLOCK).
  • SIGPIPE / EPIPE: writing to a pipe whose read end is closed delivers SIGPIPE to the writer (default action: terminate). If SIGPIPE is blocked or ignored, write() returns -1 with errno=EPIPE. This is how shell pipelines terminate cleanly.
  • Pipes are stream-oriented: no message boundaries. Two writes of 100 bytes may be read as one read of 200 bytes, or 50+150, or any other split. You must frame messages yourself (length prefix, delimiter, or fixed-size records).
  • splice() and tee(): zero-copy data transfer between a pipe and another fd (splice) or between two pipes (tee). Avoids user-space buffer copies for high-throughput scenarios like proxying.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
Write atomicity and interleaving
  • Writes ≤ PIPE_BUF (4096) are atomic: the kernel will not interleave them with other writes, even from concurrent processes. This is a POSIX guarantee.
  • Writes > PIPE_BUF may be split and interleaved. If two processes each write 8192 bytes, the reader may see: 4096 from A, 4096 from B, 4096 from A, 4096 from B.
  • For reliable multi-writer pipes, keep messages ≤ PIPE_BUF or use a mutex/lock to serialize writes.
  • In O_NONBLOCK mode, a write ≤ PIPE_BUF that would block returns EAGAIN (all or nothing). A write > PIPE_BUF may return a short write count.
SIGPIPE handling in pipelines and servers
  • SIGPIPE's default action is to terminate the process. This is intentional for shell pipelines: yes | head -1 needs "yes" to die when "head" closes its stdin.
  • In servers and daemons, you must handle SIGPIPE. Common approaches: signal(SIGPIPE, SIG_IGN) globally, then check for EPIPE on write(); or use MSG_NOSIGNAL flag with send().
  • In multithreaded programs, SIGPIPE is delivered to the thread that called write(). Ignoring it globally is safest.
  • When writing a pipeline of child processes, close unused pipe ends promptly — failing to close the write end in the reader prevents it from ever seeing EOF.
Deadlocks and single-process pipes
  • A single process reading and writing the same pipe can deadlock: if the pipe is full, write blocks; if it's empty, read blocks. No one can make progress.
  • Even with fork(), deadlock occurs if both parent and child try to read and write without proper sequencing. Close unused ends immediately after fork.
  • Common pattern: parent closes pfd[0] (read end), child closes pfd[1] (write end). Parent writes, child reads. Any other arrangement needs careful analysis.
FIFO open semantics
  • Opening a FIFO for reading blocks until a writer opens it (and vice versa), unless O_NONBLOCK is set.
  • With O_NONBLOCK: open for reading succeeds immediately (even with no writer). Open for writing fails with ENXIO if no reader has the FIFO open.
  • A FIFO can have multiple readers and multiple writers. Data is interleaved — same atomicity rules as pipes (PIPE_BUF).
  • Removing the FIFO file (unlink) does not affect existing open file descriptors — they continue working until closed.

Code patterns (C / POSIX)

Pipe + fork: parent sends data to child, child reads with short-read handling. 
// pipe + fork: parent writes, child reads
#include <unistd.h>
#include <stdio.h>
#include <string.h>
#include <sys/wait.h>

int main(void) {
    int pfd[2];
    if (pipe2(pfd, O_CLOEXEC) == -1) { perror("pipe2"); return 1; }

    pid_t pid = fork();
    if (pid == -1) { perror("fork"); return 1; }

    if (pid == 0) {                    // child: read from pipe
        close(pfd[1]);                 // close unused write end
        char buf[256];
        ssize_t n;
        while ((n = read(pfd[0], buf, sizeof(buf))) > 0)
            write(STDOUT_FILENO, buf, n);  // echo to stdout
        if (n == -1) perror("read");
        close(pfd[0]);
        _exit(0);
    }
    // parent: write to pipe
    close(pfd[0]);                     // close unused read end
    const char *msg = "Hello from parent via pipe!\n";
    write(pfd[1], msg, strlen(msg));
    close(pfd[1]);                     // EOF for child
    waitpid(pid, NULL, 0);
    return 0;
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Always use pipe2() with O_CLOEXEC; add O_NONBLOCK for event-loop integration.
  • Close unused pipe ends immediately after fork — prevents fd leaks and ensures EOF propagation.
  • Handle or ignore SIGPIPE in daemons; check for EPIPE on write().
  • Keep multi-writer messages ≤ PIPE_BUF (4096) for atomicity, or serialize writes externally.
  • Loop on read() to handle short reads; loop on write() to handle short writes on non-blocking pipes.
  • Consider splice() for high-throughput proxying to avoid user-space copy overhead.
