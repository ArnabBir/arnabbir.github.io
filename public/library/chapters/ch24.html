Chapter 24 — Process Creation

Process creation on Linux centers on fork(), which duplicates the calling process via copy-on-write semantics — page table entries are cloned but physical pages are shared until either process writes. The underlying syscall is actually clone(), whose flags (CLONE_VM, CLONE_FILES, CLONE_NEWNS) give fine-grained control over what parent and child share. vfork() exists as a dangerous optimization that suspends the parent entirely; in modern code, posix_spawn() is the preferred alternative, combining fork+exec into a single safe operation with explicit file actions.

The critical window between fork() and exec() is a minefield in multithreaded programs: only async-signal-safe functions may be called. Understanding this constraint — and the alternatives — is essential for writing reliable process-creation code.

Invariant
fork() returns twice: 0 in child, child PID in parent; address space is copy-on-write.
Gotcha
Between fork and exec in a multithreaded program, only async-signal-safe functions are safe (no malloc, no printf).
Debugging
Use strace -ff -o trace to capture separate trace files for parent and child.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • fork() copies the task_struct; CoW means page table entries are cloned but physical pages are shared until written — a write triggers a page fault, and only then is the page duplicated.
  • vfork() suspends the parent until the child calls exec or _exit — faster than fork (no page table copy) but extremely dangerous; modifying any data corrupts the parent. Prefer posix_spawn instead.
  • clone() is the underlying syscall beneath fork and pthread_create: CLONE_VM shares address space, CLONE_FILES shares the fd table, CLONE_SIGHAND shares signal handlers. Combining flags controls exactly what is shared vs. copied.
  • After fork, the child inherits: open file descriptors, signal dispositions, cwd, environment, umask, resource limits, and mmap regions.
  • After fork, the child gets NEW: PID, PPID (set to parent), pending signals cleared, file locks NOT inherited, POSIX timers NOT inherited, async I/O operations NOT inherited.
  • posix_spawn combines fork+exec with declarative file actions (dup2, close, open) — it avoids the dangerous post-fork/pre-exec window entirely and is the recommended approach for simple process creation.
Key terms & kernel objects
Term / objectMeaning
CoW (Copy-on-Write)Memory optimization where fork() shares physical pages between parent and child; pages are duplicated only when written. Makes fork O(page-table-size) not O(RSS).
clone flagsBitmask controlling resource sharing: CLONE_VM (address space), CLONE_FILES (fd table), CLONE_SIGHAND (signal handlers), CLONE_NEWNS (mount namespace), CLONE_THREAD (thread group).
vforkCreates child that shares parent's address space; parent is suspended until child calls exec/_exit. Avoids page table copy but is extremely fragile.

file_actionsposix_spawn_file_actions_t: a list of fd operations (dup2, close, open) applied in the child before exec, replacing manual post-fork fd manipulation.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
Copy-on-write cost model
  • fork() is cheap: it copies page table entries, not pages. Cost is O(page-table-size), not O(RSS). But the moment either process writes, a page fault fires and the kernel copies that page.
  • In large-process servers (e.g., Redis with 20 GB RSS), fork() for background save can cause massive RSS inflation: every written page doubles memory usage. This is the "Redis fork problem."
  • Transparent Huge Pages (THP) amplify CoW cost: a single byte write to a 2 MB huge page forces a 2 MB copy. Disable THP for fork-heavy workloads or use jemalloc's THP-aware settings.
  • Monitor CoW faults via /proc/<pid>/status (VmRSS growth) and perf stat -e page-faults during the fork window.
Post-fork/pre-exec safety
  • After fork() in a multithreaded program, only the calling thread exists in the child. All other threads vanish — along with any locks they held. This means malloc, printf, syslog, and any function taking internal locks can deadlock.
  • The ONLY safe operations are async-signal-safe functions: execve, _exit, signal manipulation (sigaction, sigprocmask), dup2, close, open, read, write, fork, getpid.
  • Even atexit handlers and stdio buffer flushing are unsafe — use _exit(), not exit(), if exec fails in the child.
  • This is why posix_spawn exists: it performs all fd manipulation and signal setup atomically, without exposing the dangerous post-fork window to user code.
clone() flag combinations
  • CLONE_VM without CLONE_THREAD: creates a separate process sharing the address space — extremely dangerous without careful synchronization. One process's stack can corrupt the other.
  • CLONE_NEWNS, CLONE_NEWPID, CLONE_NEWNET: namespace flags used by container runtimes. Each creates an isolated view of mounts, PIDs, or network.
  • unshare() is an alternative to clone() for namespaces: the calling process enters new namespaces without creating a child. Used by unshare(1) CLI and container setup.
  • CLONE_THREAD | CLONE_VM | CLONE_SIGHAND: the combination used by pthread_create. Removing any one flag creates unusual semantics — e.g., threads with separate fd tables.
posix_spawn file actions
  • posix_spawn_file_actions_adddup2(&actions, oldfd, newfd): redirects fd in the child, replacing manual dup2 between fork and exec.
  • posix_spawn_file_actions_addclose(&actions, fd): closes fd in child, replacing close-on-exec for fds you don't control.
  • posix_spawn_file_actions_addopen(&actions, fd, path, flags, mode): opens a file and assigns it to a specific fd in the child.
  • File actions execute in order; this lets you chain: open a log file, dup2 it to stderr, close the original — all declaratively and safely.

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// fork+exec+wait with proper error handling
pid_t pid = fork();
if (pid < 0) { perror("fork"); exit(1); }
if (pid == 0) {
  // Child: only async-signal-safe calls here
  execvp(argv[1], &argv[1]);
  _exit(127);  // _exit, NOT exit — avoid flushing parent's buffers
}
// Parent: wait for child
int status;
if (waitpid(pid, &status, 0) < 0) { perror("waitpid"); exit(1); }
if (WIFEXITED(status))
  printf("child exited %d\n", WEXITSTATUS(status));
else if (WIFSIGNALED(status))
  printf("child killed by signal %d\n", WTERMSIG(status));

// posix_spawn: safer alternative
#include <spawn.h>
extern char **environ;
posix_spawn_file_actions_t actions;
posix_spawn_file_actions_init(&actions);
posix_spawn_file_actions_addopen(&actions, STDOUT_FILENO,
  "/tmp/out.log", O_WRONLY|O_CREAT|O_TRUNC, 0644);
pid_t spid;
char *sp_argv[] = {"ls", "-la", NULL};
int err = posix_spawn(&spid, "/bin/ls", &actions, NULL, sp_argv, environ);
if (err) { fprintf(stderr, "posix_spawn: %s\n", strerror(err)); exit(1); }
waitpid(spid, &status, 0);
posix_spawn_file_actions_destroy(&actions);

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Set O_CLOEXEC on every fd at creation time (open, socket, pipe2, accept4) — never leak fds into children by default.
  • After fork, call exec or _exit immediately; never call exit() (it flushes parent's stdio buffers in the child).
  • In multithreaded programs, prefer posix_spawn over fork+exec to avoid the async-signal-safety minefield.
  • Always check fork() return value for -1 (EAGAIN/ENOMEM) — failing to check causes the parent to execute child logic.
  • Monitor CoW page fault overhead when forking large-RSS processes; consider posix_spawn or external helper processes.
  • Reap all children with waitpid(-1, ..., WNOHANG) in a loop or a SIGCHLD handler to prevent zombie accumulation.
