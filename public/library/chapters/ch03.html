    Reading an API like a protocol

    A diagnostic prints an unrelated error even though the operation succeeded.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    An API contract includes argument lifetime, success result, error representation, and side effects. errno is thread-local diagnostic state, not a global last-operation verdict. It is meaningful only when the function's documented result says an error occurred. Library calls can change it on success.

    Contract and implementation boundary

    Most system-call wrappers report -1 and set errno. Many pthread functions return an error number directly. Functions such as getpriority need special treatment because -1 can be a valid success result. Save errno immediately before cleanup that could overwrite it.

    Contract references: errno.3 · pthreads.7 · getpriority.2. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    A universal CHECK macro that assumes every nonzero result is an error will reject successful read byte counts and misreport pthread errors. Error conventions belong to individual interfaces.

    Worked reasoning trace

    Assumptions: A pthread function returns EINVAL directly.

    1. Starting state

      errno contains an unrelated earlier error.

    2. Operation

      Store the pthread return value and pass it to strerror.

    3. Expected observation

      The diagnostic describes the actual pthread failure.

    Tradeoff: Per-interface wrappers take more care than one universal error macro.

    This is a hand-authored prediction, not captured runtime output.

    Original practice problem

    Write two tiny wrappers: one for open and one for pthread_mutex_lock. Give each a deliberately invalid setup in a throwaway program and compare where the error number comes from. Do not unlock a mutex you did not acquire.
