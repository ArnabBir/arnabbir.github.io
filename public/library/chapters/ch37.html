Chapter 37 — Daemons

Daemons are long-running background processes — no controlling terminal, proper signal handling, single-instance enforcement via PID files, and logging via syslog.

Traditional daemon creation involves a careful sequence of fork, setsid, and fd management. Modern systems (systemd) simplify this dramatically, but understanding the mechanics remains critical for debugging and portability.

Invariant
A properly daemonized process has no controlling terminal, runs in /, and logs via syslog or journald.
Gotcha
PID file race conditions: checking existence then writing is not atomic. Use flock() on the PID file instead.
Debugging
systemctl status shows PID, memory, logs; journalctl -u <service> for full daemon output.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • Traditional daemon recipe: fork → parent exits → child calls setsid() → fork again → close all fds → redirect stdin/stdout/stderr to /dev/null → chdir("/") → write PID file.
  • The double-fork ensures the daemon cannot accidentally reacquire a controlling terminal (it's not a session leader).
  • Modern approach: let systemd handle daemonization. Use Type=simple (main process is the service) or Type=notify (service signals readiness via sd_notify).
  • Syslog provides structured logging: facility (LOG_DAEMON, LOG_LOCAL0-7) + priority (LOG_ERR, LOG_INFO, LOG_DEBUG). openlog() sets identity and options.
  • Single-instance enforcement: open PID file → flock(LOCK_EX|LOCK_NB) → write PID. If flock fails, another instance is running.
  • Signal handling conventions: SIGHUP = reload configuration; SIGTERM = graceful shutdown; SIGUSR1/2 = application-specific (rotate logs, dump state).
  • sd_notify(0, "READY=1") tells systemd the service is ready to accept connections (Type=notify).

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
PID file race conditions
  • Never use "check if file exists → create": between check and create, another instance can start (TOCTOU race).
  • Correct pattern: open(O_CREAT|O_WRONLY) → flock(LOCK_EX|LOCK_NB) → ftruncate → write PID. If flock fails, exit.
  • The lock is automatically released when the process exits (even on crash) because flock is tied to the open file description.
  • Don't unlink the PID file on shutdown — the flock approach doesn't need it, and unlinking creates a new race window.
systemd vs traditional daemonization
  • Type=forking: systemd expects the main process to fork and exit; it reads PIDFile= to find the daemon PID. Fragile and error-prone.
  • Type=simple: systemd considers the exec'd process as the main PID. No forking needed. Readiness is assumed at exec time.
  • Type=notify: like simple, but the daemon calls sd_notify(0, "READY=1") when actually ready. Best for services with initialization phases.
  • If your daemon does traditional double-fork under systemd Type=simple, systemd will think it crashed (main PID exited). Don't mix patterns.
Syslog and log rotation
  • syslog() is thread-safe but can block if the syslog socket buffer is full (especially with LOG_NDELAY).
  • Traditional log rotation: logrotate renames the file, then sends SIGHUP to syslogd to reopen. Daemon's own log files need similar handling.
  • With journald, syslog() messages go to the journal; use journalctl --identifier=<ident> to filter.
  • LOG_PERROR option additionally prints to stderr — useful during development but not in production daemons (stderr is /dev/null).
Signal handling in daemons
  • SIGHUP convention: reload configuration files without restart. Use a flag variable set in the handler, checked in the main loop.
  • SIGTERM: initiate graceful shutdown. Finish current requests, close connections, flush buffers, then exit.
  • Avoid doing real work in signal handlers — only set flags or write to a self-pipe/signalfd. Handler context is restrictive (async-signal-safe only).
  • With systemd, TimeoutStopSec= defines how long to wait after SIGTERM before sending SIGKILL. Default is 90s.

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// Traditional daemonize + syslog + PID file locking
#include <fcntl.h>
#include <syslog.h>
#include <unistd.h>
#include <stdlib.h>
#include <sys/file.h>
#include <stdio.h>

static int lock_pidfile(const char *path) {
    int fd = open(path, O_CREAT | O_WRONLY, 0644);
    if (fd < 0) return -1;
    if (flock(fd, LOCK_EX | LOCK_NB) < 0) return -1;
    ftruncate(fd, 0);
    dprintf(fd, "%d\n", getpid());
    return fd;  // keep open to hold lock
}

void daemonize_and_run(void) {
    if (fork() > 0) _exit(0);
    setsid();
    if (fork() > 0) _exit(0);

    chdir("/");
    close(0); close(1); close(2);
    open("/dev/null", O_RDONLY);
    open("/dev/null", O_WRONLY);
    open("/dev/null", O_WRONLY);

    openlog("mydaemon", LOG_PID | LOG_NDELAY, LOG_DAEMON);
    if (lock_pidfile("/var/run/mydaemon.pid") < 0) {
        syslog(LOG_ERR, "already running or pidfile error");
        _exit(1);
    }
    syslog(LOG_INFO, "started successfully");
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Use flock-based PID files for single-instance enforcement — never rely on file existence checks alone.
  • Handle SIGHUP for config reload and SIGTERM for graceful shutdown; use signalfd or self-pipe for safe handler dispatch.
  • For systemd services, prefer Type=notify with sd_notify("READY=1") over traditional forking daemons.
  • Log startup, shutdown, config reload, and errors via syslog with appropriate priority levels (LOG_ERR vs LOG_INFO).
  • Set appropriate resource limits, umask, and working directory at daemon startup — don't inherit random values from the launcher.
