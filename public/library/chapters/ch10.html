    Choose the clock before the timestamp

    A timeout expires too late after the wall clock is adjusted.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    Wall time answers calendar questions. Monotonic time answers elapsed-time questions without discontinuous wall-clock jumps. Linux CLOCK_BOOTTIME includes suspended time; CLOCK_MONOTONIC does not. CPU clocks measure execution consumption rather than waiting. A timestamp is incomplete without its clock domain.

    Contract and implementation boundary

    clock_gettime writes a timespec and returns 0 or -1. Normalize nanosecond arithmetic and avoid mixing clock domains. For deadlines, calculate an absolute target in the selected clock rather than repeatedly subtracting rounded relative sleeps.

    Contract references: clock_gettime.3 · clock_nanosleep.2. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    A monotonic clock need not measure suspend-inclusive time, and its values are not portable timestamps for exchange between machines. time_t width and the target ABI matter when storing long-lived calendar values.

    Worked reasoning trace

    Assumptions: Local timeout excludes machine suspension.

    1. Starting state

      Monotonic time is 20 seconds; timeout is 3 seconds.

    2. Operation

      Choose a monotonic deadline of 23 seconds.

    3. Expected observation

      A realtime clock adjustment does not move that deadline.

    Tradeoff: Monotonic values support elapsed time but are not cross-machine timestamps.

    This is a hand-authored prediction, not captured runtime output.

    Original practice problem

    Sample realtime, monotonic, and process CPU time around a short sleep. The CPU clock should advance much less than elapsed time, but no exact scheduler latency is guaranteed. Never change the system clock for this experiment.
