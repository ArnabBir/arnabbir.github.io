Chapter 55 — File Locking

File locking coordinates concurrent access to files — advisory locks rely on cooperation between processes, while mandatory locks (mostly deprecated) are enforced by the kernel. Choose flock for whole-file locking and fcntl for byte-range locking.

This chapter covers flock, fcntl record locks (F_SETLK/F_SETLKW), lockf, the critical differences in lock ownership semantics, OFD locks, mandatory locking, and deadlock detection.

Invariant
flock locks are tied to the open file description (OFD) — shared across dup and fork. fcntl locks are tied to (pid, inode) — released when ANY fd to that file is closed by that process.
Gotcha
fcntl locks have surprising close semantics: closing ANY file descriptor referring to the same inode releases ALL locks held by that process on that file, even from different open calls.
Debugging
Inspect active locks via /proc/locks. Each line shows lock type, process, inode, and byte range.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • flock() operates on open file descriptions (OFDs). Locks are shared across dup() and inherited across fork(). Closing the last fd referencing the OFD releases the lock. Simple whole-file advisory lock.
  • fcntl() F_SETLK/F_SETLKW operates on (pid, inode, byte-range). Supports read locks (F_RDLCK, shared) and write locks (F_WRLCK, exclusive). F_SETLKW blocks until the lock is available.
  • Critical fcntl gotcha: locks are released when ANY close of that file by that process occurs. If you open the same file twice and lock via fd1, closing fd2 releases the lock. This breaks library code that opens files independently.
  • lockf() is a simplified wrapper around fcntl — same semantics, fewer options. Locks from current position to len bytes.
  • Advisory locks: the kernel does not enforce them. All processes must cooperate by checking locks before access. This is the standard model.
  • Mandatory locks (mount -o mand + chmod g+s,-x): kernel enforces locks on read/write. Mostly deprecated and removed in Linux 5.15+. Avoid in new code.
  • Deadlock detection: the kernel detects deadlocks for fcntl locks and returns EDEADLK from F_SETLKW. flock does not have kernel-level deadlock detection.
  • OFD locks (F_OFD_SETLK/F_OFD_SETLKW, Linux 3.15+): fix the close semantics of fcntl locks. Tied to the open file description (like flock) but support byte ranges. Preferred for new code needing byte-range locks.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
fcntl lock release on ANY close
  • If process P opens file F as fd3 and fd7 (two separate open calls), locks via fd3, then closes fd7 — the lock on fd3 is released. This is because fcntl locks are keyed by (pid, inode), not by fd.
  • This breaks library code: if a library opens a file for its own purposes and your code has a lock on the same file, the library closing its fd releases your lock.
  • OFD locks (F_OFD_SETLK) fix this: locks are tied to the open file description, not (pid, inode). Closing one fd does not affect locks held via a different OFD.
  • Rule: if you use fcntl locks, ensure only one code path opens/closes a given file in the process.
flock across fork and dup
  • flock locks are on the open file description (kernel struct file). dup() shares the OFD, so both fds share the lock.
  • After fork(), parent and child share the OFD — both hold the same lock. Either can unlock it, affecting the other.
  • Separate open() calls create separate OFDs. Two processes opening the same file independently have independent flock locks.
  • flock is not reliable across NFS on many implementations. Use fcntl locks for NFS (NFSv4 supports them).
Deadlock detection
  • The kernel performs deadlock detection for fcntl F_SETLKW: if process A waits for a lock held by B, and B waits for a lock held by A, F_SETLKW returns EDEADLK (for one of them).
  • Detection works for simple cycles but may not catch complex multi-resource deadlocks involving non-lock waits.
  • flock has NO kernel deadlock detection. Two processes can deadlock indefinitely on flock.
  • OFD locks (F_OFD_SETLKW) also lack deadlock detection since locks are not tied to PIDs.
Mandatory locking (deprecated)
  • Mandatory locking required: mount with -o mand, and file with set-group-ID bit on and group-execute off (chmod g+s,g-x).
  • When active, the kernel blocks or errors on read()/write() to locked byte ranges, even if the process didn't check locks.
  • Removed from Linux 5.15+ (CONFIG_MANDATORY_FILE_LOCKING dropped). Do not use in new code.
  • It was also unreliable: races existed between lock check and I/O, and not all filesystems supported it.

Code patterns (C / POSIX)

flock-based PID file lock and fcntl byte-range lock pattern. 
/* --- flock: PID file for single-instance daemon --- */
int fd = open("/var/run/myapp.pid", O_CREAT|O_RDWR, 0644);
if (flock(fd, LOCK_EX | LOCK_NB) == -1) {
    if (errno == EWOULDBLOCK)
        die("another instance is running");
    die("flock: %s", strerror(errno));
}
ftruncate(fd, 0);
dprintf(fd, "%d\n", getpid());
/* keep fd open for lifetime of process */

/* --- fcntl: byte-range lock on a database file --- */
struct flock fl = {
    .l_type   = F_WRLCK,       /* exclusive write lock */
    .l_whence = SEEK_SET,
    .l_start  = record_offset,
    .l_len    = record_size,   /* 0 = lock to EOF */
};
if (fcntl(db_fd, F_SETLKW, &fl) == -1) {
    if (errno == EDEADLK)
        handle_deadlock();
    else
        die("fcntl lock: %s", strerror(errno));
}
/* ... update record ... */
fl.l_type = F_UNLCK;
fcntl(db_fd, F_SETLK, &fl);   /* unlock */

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Use flock for simple whole-file locking (PID files, single-instance daemons).
  • Use fcntl or OFD locks for byte-range locking (database records, concurrent file updates).
  • Be aware of fcntl's close-releases-all semantics. Prefer OFD locks (F_OFD_SETLK) on Linux 3.15+ for robust byte-range locking.
  • Handle EDEADLK from F_SETLKW: implement retry or abort logic.
  • Do not rely on mandatory locking — it is deprecated and removed in modern kernels.
  • Test locking behavior on your target filesystem (NFS, FUSE, etc.) — semantics vary.
