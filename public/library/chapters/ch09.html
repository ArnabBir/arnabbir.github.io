Chapter 09 — Process Credentials

Process credentials determine what a process can do — the real/effective/saved UID/GID triple, privilege escalation via setuid binaries, and the art of dropping privileges safely.

Invariant
Permission checks use the effective UID/GID; the real UID identifies who actually started the process.
Gotcha
Dropping privileges with seteuid(getuid()) is reversible; use setresuid() or setuid() (when euid==0) for permanent drop.
Debugging
cat /proc/PID/status | grep -i uid shows Real, Effective, Saved, and FS UIDs on a single line.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world credential and privilege issues.
  • Every process carries three UIDs (real, effective, saved) and three GIDs — the effective IDs are what the kernel checks for permissions.
  • The set-user-ID bit on an executable causes exec() to set the process's effective UID to the file's owner UID, enabling controlled privilege escalation.
  • Permission checks for file access, signal delivery, and IPC all use the effective UID (euid), not the real UID.
  • setresuid() gives atomic control over all three UIDs in one call — essential for correct, race-free privilege dropping.
  • Supplementary group IDs are checked alongside the effective GID during file access — a process can belong to multiple groups simultaneously.
  • Since Linux 2.6.26, capabilities offer finer-grained privilege than the all-or-nothing root model — prefer capabilities over full setuid-root where possible.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
Permanent vs temporary privilege drop
  • seteuid(getuid()) drops privileges temporarily — euid changes but suid retains the privileged UID, allowing restoration via seteuid(saved_uid).
  • For permanent drop, use setresuid(getuid(), getuid(), getuid()) to overwrite all three, eliminating any path back to privilege.
  • When euid==0, setuid(newuid) also does a permanent drop (sets all three). But when euid!=0 it only sets euid — the semantics are asymmetric and dangerous.
  • After dropping, always verify with getresuid() that all three are set correctly — a failed drop is a critical vulnerability.
Setuid-root vs capabilities
  • A setuid-root binary gives full root privileges — any vulnerability in the binary is a full system compromise.
  • Linux capabilities (CAP_NET_BIND_SERVICE, CAP_DAC_OVERRIDE, etc.) allow granting only specific privileges without full root.
  • File capabilities (setcap) can be set on executables as an alternative to the setuid bit entirely.
  • Capability-aware programs should use cap_set_proc() and drop unneeded capabilities immediately after use.
The fsuid anomaly
  • Linux has a fourth UID: fsuid. It is used exclusively for filesystem permission checks (open, stat, etc.).
  • Normally fsuid tracks euid automatically — if you set euid, fsuid follows. You almost never need to set it independently.
  • setfsuid() exists for NFS servers that need to assume a client's identity for file access without changing euid for signal delivery checks.
  • The return value of setfsuid() is the previous fsuid, not a success/error indicator — unique among set*uid calls.
Exec of setuid from setgid process
  • When a setuid binary is exec'd, only the effective UID changes — the effective GID is unaffected unless the binary also has the setgid bit.
  • Supplementary groups are inherited across exec and are not affected by setuid/setgid bits on the file.
  • A process can simultaneously have elevated euid (from setuid) and elevated egid (from setgid) — both must be dropped.
  • Order matters: drop group privileges first, then user privileges. Reversing this order may leave you unable to drop groups.

Code patterns (C / POSIX)

Permanent privilege drop with verification. This is the pattern every setuid program should use. 
// Permanent privilege drop using setresuid + verification
#define _GNU_SOURCE
#include <unistd.h>
#include <stdio.h>
#include <stdlib.h>

void drop_privileges_permanently(void) {
    uid_t ruid = getuid();   // who really started us

    // Drop group privs first (while we still have root euid)
    if (setresgid(ruid, ruid, ruid) == -1) {
        perror("setresgid");
        _exit(EXIT_FAILURE);
    }
    // Now drop user privs — permanent, all three UIDs
    if (setresuid(ruid, ruid, ruid) == -1) {
        perror("setresuid");
        _exit(EXIT_FAILURE);
    }
    // Verify: paranoia is correct here
    uid_t r, e, s;
    if (getresuid(&r, &e, &s) == -1 ||
        r != ruid || e != ruid || s != ruid) {
        fprintf(stderr, "privilege drop verification failed!\n");
        _exit(EXIT_FAILURE);
    }
    // Confirm we cannot regain privilege
    if (setresuid(0, 0, 0) != -1) {
        fprintf(stderr, "CRITICAL: regained root after drop!\n");
        _exit(EXIT_FAILURE);
    }
}

Production checklist

If you are shipping code that manipulates credentials, satisfy each item explicitly.
  • Drop group privileges before user privileges — once euid is unprivileged, you lose the ability to change groups.
  • After any privilege drop, verify all three UIDs/GIDs with getresuid()/getresgid() and confirm regain fails.
  • Prefer capabilities over setuid-root; use setcap to grant only the specific capabilities needed.
  • Clear dangerous environment variables (LD_PRELOAD, LD_LIBRARY_PATH) in setuid programs before doing anything else.
  • Log the real UID at startup for audit trails — the effective UID shows what you can do, the real UID shows who you are.
