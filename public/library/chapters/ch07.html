    TOPIC 7 / 64 · Memory Allocation

    Allocation, ownership, and address space

    A service allocates a huge buffer successfully and then dies while touching it.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    malloc manages user-space allocations backed by a process address space. Virtual allocation, resident physical memory, and committed storage are different quantities. Linux overcommit can allow an allocation whose later page faults cannot all be satisfied. free ends the C object's lifetime, even if allocator caches keep pages mapped.

    Contract and implementation boundary

    Check multiplication before allocating count times element-size. On realloc failure the original nonzero-sized allocation remains valid; assign the result to a temporary pointer. Avoid zero-size realloc portability traps by spelling out free when the desired size is zero.

    Contract references: malloc.3 · proc.5. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    A successful malloc is not a promise that a memory-intensive phase cannot hit resource or OOM limits. A stale pointer is invalid after free even if a debugger shows its old bytes. RSS not falling after free does not prove a leak.

    Worked reasoning trace

    Assumptions: A nonzero realloc request fails.

    1. Starting state

      p owns a 64-byte allocation.

    2. Operation

      tmp = realloc(p, 128) yields NULL.

    3. Expected observation

      p still owns 64 bytes; reporting failure must not discard it.

    Tradeoff: A temporary pointer costs one variable and prevents an ownership leak.

    This is a hand-authored prediction, not captured runtime output.

    Original practice problem

    Allocate only a bounded one-megabyte region, touch each page, and compare process maps and RSS before allocation, after touching, and after free. Expect allocator and kernel variation; do not attempt an OOM demonstration on a shared host.
