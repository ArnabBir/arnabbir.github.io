    TOPIC 58 / 64 · Sockets: Fundamentals of TCP/IP Networks

    TCP reliability is not application acknowledgement

    A client times out after sending a payment request and cannot tell whether it was processed.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    IP delivers packets with best-effort semantics; TCP builds an ordered reliable byte stream with retransmission, flow control, and congestion control. TCP acknowledgements concern transport bytes, not business completion. An application timeout can occur after a remote side effect, requiring application-level deduplication or reconciliation.

    Contract and implementation boundary

    TCP close is directional. In an ordinary active/passive close, the endpoint that initiates the active close eventually enters TIME_WAIT, regardless of whether it was client or server. Simultaneous close has additional paths. Sequence numbers and TIME_WAIT help handle delayed traffic and final acknowledgement loss.

    Contract references: tcp.7 · ip.7 · udp.7. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    Assigning TIME_WAIT permanently to the client mistakes role for state. SO_REUSEADDR is not a universal bypass for connection lifetime rules. UDP's lack of a stream handshake does not mean delivery, ordering, or congestion handling can be ignored.

    Worked reasoning trace

    Assumptions: Established TCP connection; server initiates ordinary close; no loss or simultaneous close.

    1. Starting state

      Server sends FIN; client acknowledges.

    2. Operation

      Client later sends FIN; server acknowledges.

    3. Expected observation

      Server enters TIME_WAIT, not the client merely because of its role.

    Tradeoff: TIME_WAIT protects protocol reuse at a temporary state/resource cost.

    This is a hand-authored prediction, not captured runtime output.

    Original practice problem

    Use the close model with each endpoint as active closer. Trace FIN, ACK, peer FIN, final ACK. Then annotate a request/response timeline where a server commits work before the reply is lost: what can a retry safely infer?

    Which endpoint normally reaches TIME_WAIT in an ordinary non-simultaneous close?
