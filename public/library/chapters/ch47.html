Chapter 47 — System V Semaphores

System V semaphores are kernel-persistent counting semaphores that support atomic operations on sets — used for multi-resource locking and producer/consumer patterns across processes. Unlike POSIX semaphores, a single System V semaphore object can contain multiple semaphores operated on atomically in a single call.

The key trade-off: System V semaphores are powerful (atomic multi-semaphore operations, SEM_UNDO for crash safety) but complex (obtuse API, kernel-persistent lifetime requiring explicit cleanup, race conditions around initialization).

Invariant
semop() atomically adjusts one or more semaphores in a set; the kernel blocks or proceeds based on resulting values.
Gotcha
Semaphore creation and initialization are separate steps — a race window exists between semget() and semctl(SETVAL).
Debugging
Use ipcs -s to list semaphore sets and ipcrm -s to remove them; check ncount/zcount for blocked processes.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • semget() creates or opens a semaphore set containing N semaphores in one kernel object, identified by a key_t.
  • semop() atomically adjusts semaphore values via an array of sembuf structs: {sem_num, sem_op, sem_flg}.
  • sem_op > 0: increment value (V / signal / release) — never blocks.
  • sem_op < 0: decrement or block until value ≥ |sem_op| (P / wait / acquire).
  • sem_op == 0: wait until semaphore value becomes exactly zero (used for barrier-like patterns).
  • SEM_UNDO flag: kernel tracks adjustments per-process and reverses them on exit, preventing deadlock from crashed holders.
  • semctl(SETVAL) initializes a single semaphore; semctl(SETALL) initializes entire set — must be done before first semop().
  • Binary semaphore (value 0 or 1) acts as a mutex; counting semaphore (value 0..N) controls access to N identical resources.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
Initialization race condition
  • semget(IPC_CREAT) and semctl(SETVAL) are separate calls — another process can semop() between them on uninitialized values.
  • Solution: use IPC_CREAT | IPC_EXCL; the creator initializes, others retry until sem_otime becomes nonzero (indicates first semop completed).
  • Alternatively, use a separate flag (file lock or shared memory flag) to coordinate initialization.
  • POSIX named semaphores avoid this because sem_open() creates and initializes atomically.
SEM_UNDO limits and behavior
  • SEM_UNDO adjustments are tracked per-process per-semaphore; on exit, the kernel applies the reverse adjustment.
  • The undo value can overflow SEMVMX (max semaphore value); in that case the kernel silently caps or ignores the undo.
  • SEM_UNDO does not work across exec() — undo adjustments are cleared on exec.
  • If multiple threads in a process use SEM_UNDO, the undo is process-wide, not per-thread — can lead to incorrect adjustments.
Semaphore limits (SEMMNI, SEMMSL, SEMMNS)
  • SEMMNI: max number of semaphore sets system-wide. SEMMSL: max semaphores per set. SEMMNS: max semaphores system-wide.
  • These are tunable via /proc/sys/kernel/sem (four space-separated values: SEMMSL SEMMNS SEMOPM SEMMNI).
  • Hitting limits returns ENOSPC from semget(); check ipcs -ls for current limits.
  • Leaked semaphore sets (creator exits without IPC_RMID) consume kernel resources indefinitely.
Debugging semaphore issues
  • ipcs -s shows all semaphore sets with semid, owner, permissions, nsems, and last operation time.
  • ipcs -s -i <semid> shows per-semaphore values within a set.
  • Check semncnt (processes waiting on sem_op < 0) and semzcnt (waiting on sem_op == 0) via semctl(GETNCNT/GETZCNT).
  • strace shows semop/semget/semctl calls with full arguments for debugging hangs.

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// Binary semaphore for mutual exclusion between processes
#include <sys/sem.h>
#include <stdio.h>
#include <stdlib.h>

union semun { int val; };

static int sem_lock(int semid) {
    struct sembuf op = {0, -1, SEM_UNDO};   // P (wait)
    return semop(semid, &op, 1);
}
static int sem_unlock(int semid) {
    struct sembuf op = {0, +1, SEM_UNDO};   // V (signal)
    return semop(semid, &op, 1);
}

int main(void) {
    int semid = semget(IPC_PRIVATE, 1, 0600);
    if (semid == -1) { perror("semget"); exit(1); }

    union semun arg = {.val = 1};            // init to 1 (unlocked)
    semctl(semid, 0, SETVAL, arg);

    sem_lock(semid);
    printf("critical section (pid %d)\n", getpid());
    sem_unlock(semid);

    semctl(semid, 0, IPC_RMID);              // cleanup
    return 0;
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Always use SEM_UNDO for lock operations so the kernel releases on process crash.
  • Handle EINTR from semop() — signals interrupt blocking waits; retry in a loop.
  • Use semtimedop() instead of semop() to avoid indefinite hangs.
  • Define clear ownership: one process creates + initializes + destroys with IPC_RMID.
  • Clean up stale semaphore sets on startup (check sem_otime == 0 for uninitialized sets).
