Chapter 50 — Virtual Memory Operations

Advanced VM operations give you fine-grained control over page permissions, residency, and behavior. Guard pages with mprotect catch buffer overflows at the hardware level. mlock prevents sensitive data (crypto keys, real-time buffers) from being swapped to disk. madvise tunes kernel paging strategy for your access pattern.

These APIs operate at the page granularity and interact with kernel memory management policies (overcommit, OOM killer, swap). Understanding them is essential for security-sensitive applications, real-time systems, and high-performance data processing.

Invariant
mprotect, mlock, and madvise all require page-aligned addresses; they operate on whole pages regardless of the length argument.
Gotcha
mlock is limited by RLIMIT_MEMLOCK (often 64KB for unprivileged processes); exceeding it silently fails or returns ENOMEM.
Debugging
Use mincore() to check which pages are resident; /proc/<pid>/smaps shows Locked pages per mapping.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • mprotect(addr, len, prot) changes page permissions: PROT_NONE creates guard pages (any access causes SIGSEGV), PROT_READ|PROT_WRITE restores normal access. Used for stack overflow detection and buffer overflow hardening.
  • mlock(addr, len) pins pages in RAM — they cannot be evicted to swap. Essential for cryptographic keys (prevent swap exposure) and real-time audio/video (prevent page fault latency spikes).
  • mlockall(MCL_CURRENT | MCL_FUTURE) locks all current and future pages — used by real-time processes to guarantee no page faults after startup.
  • mincore(addr, len, vec) queries page residency: each byte in vec indicates whether the corresponding page is in RAM (bit 0 set) or not.
  • madvise(addr, len, advice) gives the kernel paging hints: MADV_SEQUENTIAL enables aggressive readahead, MADV_DONTNEED immediately discards pages (anonymous pages are zeroed on next access), MADV_FREE marks pages as reclaimable but keeps them until memory pressure.
  • RLIMIT_MEMLOCK limits how much memory an unprivileged process can lock; CAP_IPC_LOCK bypasses this limit.
  • Overcommit policy (/proc/sys/vm/overcommit_memory): 0 = heuristic (default), 1 = always allow, 2 = strict (commit ≤ swap + ratio*RAM). When overcommit is exhausted, the OOM killer terminates processes.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
Guard pages and mprotect patterns
  • Allocate N+1 pages; set the last page to PROT_NONE. Any buffer overflow into the guard page triggers SIGSEGV immediately.
  • The stack guard page is set up automatically by the kernel — stack overflow hits PROT_NONE and raises SIGSEGV (stack smashing detected).
  • mprotect can also implement W^X (write XOR execute) — pages are writable during JIT compilation, then switched to PROT_READ|PROT_EXEC.
  • mprotect on a MAP_SHARED file mapping cannot add PROT_WRITE if the file was opened O_RDONLY — returns EACCES.
mlock for crypto and real-time
  • Crypto keys in swap can be read by an attacker with disk access. mlock() the key buffer, then mlock + explicit_bzero + munlock when done.
  • Real-time audio: mlockall(MCL_CURRENT|MCL_FUTURE) during init ensures no page faults during playback — page faults cause audible glitches.
  • mlock does NOT prevent the data from appearing in core dumps — use madvise(MADV_DONTDUMP) or prctl(PR_SET_DUMPABLE, 0) for that.
  • After fork(), locked pages are NOT locked in the child — the child must call mlock() again if needed.
Overcommit and OOM killer
  • Default overcommit (mode 0): kernel uses heuristics to reject "obviously" excessive allocations but generally allows more than physical memory.
  • Mode 1 (always overcommit): malloc never fails; OOM killer is the only safety net. Dangerous for production.
  • Mode 2 (strict): total commit ≤ swap + (overcommit_ratio/100) * RAM. malloc fails with ENOMEM when exceeded. Safest but may reject valid workloads.
  • OOM killer selects victim by oom_score (RSS-based heuristic); tune with /proc/<pid>/oom_score_adj (-1000 to +1000).
madvise performance patterns
  • MADV_SEQUENTIAL: kernel reads ahead aggressively and drops pages after they're read — ideal for log processing, sequential scans.
  • MADV_RANDOM: disables readahead — better for hash table or B-tree lookups in mapped files.
  • MADV_DONTNEED: immediately releases pages; anonymous pages are zeroed on re-access; file pages are re-read from disk. Used for cache eviction.
  • MADV_FREE (Linux 4.5+): marks pages as reclaimable but keeps them if no memory pressure — cheaper than DONTNEED for ephemeral caches.

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// Guard page + mlock for crypto key material
#include <sys/mman.h>
#include <string.h>
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    size_t pgsz = sysconf(_SC_PAGESIZE);

    // 1. Guard page: allocate 2 pages, protect the second
    char *buf = mmap(NULL, 2 * pgsz, PROT_READ | PROT_WRITE,
                     MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    mprotect(buf + pgsz, pgsz, PROT_NONE);  // guard page
    // buf[0..pgsz-1] is usable; buf[pgsz] triggers SIGSEGV

    // 2. mlock crypto key to prevent swap exposure
    unsigned char key[32];
    mlock(key, sizeof(key));         // pin in RAM
    // ... use key for encryption ...
    explicit_bzero(key, sizeof(key)); // wipe
    munlock(key, sizeof(key));        // allow swap again

    munmap(buf, 2 * pgsz);
    return 0;
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Use guard pages (mprotect PROT_NONE) around sensitive buffers in custom allocators.
  • mlock all crypto key material; explicit_bzero before munlock; also set MADV_DONTDUMP.
  • For real-time processes: mlockall(MCL_CURRENT|MCL_FUTURE) during init; pre-fault all memory before entering the real-time loop.
  • Check RLIMIT_MEMLOCK before calling mlock — raise it with setrlimit() or configure in /etc/security/limits.conf.
  • Set oom_score_adj to -1000 for critical services that must not be OOM-killed; monitor /proc/meminfo for memory pressure.
