Chapter 32 — Threads: Thread Cancellation

Thread cancellation is tricky -- it must respect resource cleanup. Deferred cancellation at defined cancellation points is the safe default; asynchronous cancellation is almost never correct because the thread could be cancelled in the middle of any instruction, including malloc or mutex operations.

The pattern: use pthread_cleanup_push/pop to register cleanup handlers that release locks and free resources, then rely on deferred cancellation happening only at well-defined cancellation points like read(), write(), sleep(), and pthread_cond_wait().

Invariant
Deferred cancellation (the default) acts only at cancellation points. Cleanup handlers run in LIFO order on cancellation.
Gotcha
PTHREAD_CANCEL_ASYNCHRONOUS is unsafe for nearly all code -- the thread can be cancelled inside malloc, mutex_lock, or any non-async-cancel-safe function.
Debugging
If a cancelled thread leaves a mutex locked, other threads will deadlock. Always push a cleanup handler to unlock before entering a cancellation point.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • pthread_cancel sends a cancellation request -- it does NOT immediately kill the thread. The thread checks for cancellation at defined cancellation points.
  • PTHREAD_CANCEL_DEFERRED (default): cancellation happens only at cancellation points -- blocking syscalls like read(), write(), sleep(), pthread_cond_wait(), and explicitly with pthread_testcancel().
  • PTHREAD_CANCEL_ASYNCHRONOUS: cancellation can happen at any point. Only safe if the thread is executing purely computational code with no library calls. Almost never correct in practice.
  • Cleanup handlers (pthread_cleanup_push/pop) are a LIFO stack. On cancellation, they run in reverse order of registration. Use them to unlock mutexes, close fds, and free heap memory.
  • pthread_cleanup_push/pop are macros that expand to { and }. They must appear in matched pairs in the same lexical scope.
  • A cancelled thread's return value is PTHREAD_CANCELED (typically (void*)-1), retrievable via pthread_join.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
Cancellation and mutexes
  • If a thread is cancelled while holding a mutex, the mutex remains locked and other threads waiting on it will deadlock.
  • Solution: push a cleanup handler that unlocks the mutex BEFORE calling any cancellation point (e.g., pthread_cond_wait).
  • pthread_cond_wait is both a cancellation point and atomically releases/reacquires the mutex. If cancelled during cond_wait, the mutex is re-acquired before cleanup handlers run.
  • Disable cancellation (pthread_setcancelstate(PTHREAD_CANCEL_DISABLE)) around non-cancellation-safe critical sections.
Cleanup handler rules
  • pthread_cleanup_push and pthread_cleanup_pop are macros expanding to { and }. They MUST be paired in the same function at the same lexical level.
  • Handlers run in LIFO order (last pushed = first executed) on cancellation, pthread_exit, or pop with execute != 0.
  • Handlers do NOT run on normal return from the thread function. If you need cleanup on normal exit too, call pthread_cleanup_pop(1).
  • In C++, prefer RAII destructors over cleanup handlers. Cancellation in C++ can interact poorly with exception handling.
Asynchronous cancellation dangers
  • PTHREAD_CANCEL_ASYNCHRONOUS means the thread can be cancelled between any two machine instructions.
  • This makes malloc, free, mutex_lock, printf, and virtually all library calls unsafe -- they can leave data structures in inconsistent states.
  • The only safe use case: pure computation loops with no library calls (e.g., a tight numerical calculation).
  • Even then, consider using pthread_testcancel() in a deferred-cancellation loop instead -- it is much safer.
Alternatives to cancellation
  • Many production systems avoid pthread_cancel entirely and use a "stop flag" pattern: set a shared atomic/volatile flag and have the thread check it periodically.
  • The stop-flag approach gives the thread full control over when and how it cleans up.
  • For threads blocked on I/O, use a self-pipe or eventfd to wake them, combined with poll/select.
  • In modern C++ (std::jthread in C++20), cooperative cancellation via stop_token replaces pthread_cancel.

Code patterns (C / POSIX)

Cancellation with cleanup handler to unlock a mutex. 
// Safe cancellation with cleanup handler
#include <pthread.h>
#include <stdio.h>
#include <unistd.h>

static pthread_mutex_t mtx = PTHREAD_MUTEX_INITIALIZER;

void unlock_mutex(void *arg){
  printf("cleanup: unlocking mutex\n");
  pthread_mutex_unlock((pthread_mutex_t*)arg);
}

void *worker(void *arg){
  pthread_mutex_lock(&mtx);
  pthread_cleanup_push(unlock_mutex, &mtx);

  // This is a cancellation point -- if cancelled here,
  // unlock_mutex runs automatically
  while(1){
    sleep(1);  // cancellation point
    printf("working...\n");
  }

  pthread_cleanup_pop(1);  // 1 = execute handler on normal exit too
  return NULL;
}

int main(void){
  pthread_t t;
  pthread_create(&t, NULL, worker, NULL);
  sleep(3);
  pthread_cancel(t);       // request cancellation
  pthread_join(t, NULL);   // wait for thread to finish cleanup
  printf("thread cancelled and joined\n");
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Push cleanup handlers before any cancellation point where the thread holds a mutex or owns a resource.
  • Never use PTHREAD_CANCEL_ASYNCHRONOUS unless the code is pure computation with zero library calls.
  • Consider using a stop-flag pattern instead of pthread_cancel for simpler, more predictable shutdown.
  • Disable cancellation around non-cancellation-safe sections (e.g., complex data structure updates spanning multiple cancellation points).
  • Always join cancelled threads to retrieve PTHREAD_CANCELED and confirm cleanup completed.
