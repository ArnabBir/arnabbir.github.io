    TOPIC 49 / 64 · Memory Mappings

    Mappings separate visibility from durability

    A mapped file changes in one process, but the update is absent after a crash.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    mmap connects a virtual address range to backing storage or anonymous memory. MAP_SHARED permits shared updates; MAP_PRIVATE gives copy-on-write behavior for modifications. Visibility, synchronization between threads or processes, and persistence are three separate questions. Mapping does not make arbitrary struct updates atomic.

    Contract and implementation boundary

    Check for MAP_FAILED. File offsets must meet page-alignment requirements. Size the backing object before accessing mapped bytes, and do not access beyond the valid file extent: truncation can cause SIGBUS. msync has synchronization semantics for mapped storage but does not replace a complete crash-consistency protocol.

    Contract references: mmap.2 · munmap.2 · msync.2. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    Closing the descriptor does not unmap an established mapping. Treating MAP_PRIVATE writes as a file update silently loses intended changes. Keeping pointers after munmap is a lifetime bug even if those addresses are later reused.

    Worked reasoning trace

    Assumptions: File has bytes AB; two mappings exist; writer uses MAP_PRIVATE.

    1. Starting state

      Reader sees the backing file's A.

    2. Operation

      Writer changes its private first byte to Z.

    3. Expected observation

      The file is not thereby changed to ZB.

    Tradeoff: Private mappings isolate modifications; shared mappings need synchronization and durability policy.

    This is a hand-authored prediction, not captured runtime output.

    Run mappings.c to modify a private file-backed mapping and verify that pread still observes the original file byte. In a separate extension, state what changes when MAP_PRIVATE becomes MAP_SHARED and how concurrent truncation is prevented.

    Check your understanding

    Does closing the original file descriptor automatically invalidate a successful mmap?

    Explain the answer

    No. The mapping has a separate lifetime until it is unmapped or the process ends.
