Chapter 49 — Memory Mappings

mmap is one of Linux's most powerful APIs — map files into memory for zero-copy I/O, create shared anonymous mappings for IPC, and use private mappings for copy-on-write. It is the foundation for dynamic linking, large allocations in malloc, and memory-mapped databases.

The flags matrix (SHARED vs PRIVATE, file-backed vs anonymous) produces four distinct behaviors. Understanding which combination you need — and what happens to dirty pages, visibility, and persistence — is essential for correct use.

Invariant
MAP_SHARED changes are visible to all mappers and (for files) written back to disk; MAP_PRIVATE changes are copy-on-write and private to the process.
Gotcha
Mapping past end-of-file and writing can cause SIGBUS; always ensure the file is large enough (ftruncate) before writing to a MAP_SHARED file mapping.
Debugging
Check /proc/<pid>/maps for all mappings with flags; use mincore() to check page residency; perf stat for fault counts.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • mmap(addr, length, prot, flags, fd, offset) creates a virtual memory mapping; pages are faulted in on first access.
  • MAP_SHARED + file: changes are visible to other processes mapping the same file and are eventually written back to disk.
  • MAP_PRIVATE + file: copy-on-write — reads see the file, writes create private copies that are never written to disk.
  • MAP_ANONYMOUS (no file): pages are zero-initialized; used by malloc for large allocations (>128KB typically).
  • MAP_SHARED + MAP_ANONYMOUS: shared zero-initialized region between parent and child after fork() — lightweight IPC without a file.
  • munmap() removes the mapping; accessing the address after unmapping causes SIGSEGV.
  • msync(MS_SYNC) flushes dirty pages from a MAP_SHARED file mapping to disk; durability still requires fsync on the fd.
  • madvise() gives the kernel optimization hints: MADV_SEQUENTIAL enables readahead, MADV_DONTNEED drops pages immediately.
  • mremap() resizes an existing mapping without unmapping (Linux-specific); avoids the cost of copy + remap.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
The flags matrix: SHARED/PRIVATE x file/anonymous
  • MAP_SHARED + file: multi-process file I/O; changes written to page cache and eventually to disk. msync() for explicit flush.
  • MAP_PRIVATE + file: used by dynamic linker for .text sections; CoW means each process can diverge without affecting the file.
  • MAP_SHARED + MAP_ANONYMOUS: zero-initialized shared region; inherited by fork(). No file on disk. Good for parent-child IPC.
  • MAP_PRIVATE + MAP_ANONYMOUS: standard anonymous allocation (what malloc uses for large blocks). Private, zero-initialized.
SIGBUS and file-backed mappings
  • If you map a file and access pages beyond the file's size, you get SIGBUS (not SIGSEGV).
  • If another process truncates the file while you have it mapped, accessing now-beyond-EOF pages causes SIGBUS.
  • Always ftruncate() or write() to extend the file before writing to a MAP_SHARED mapping at those offsets.
  • The partial page at the end of a file (between file size and next page boundary) is zero-filled on read and discarded on unmap.
Performance: mmap vs read/write
  • mmap avoids the kernel-to-user copy (zero-copy for reads); beneficial for large files accessed randomly.
  • For sequential reads, read() with a large buffer can outperform mmap due to better TLB and prefetch behavior.
  • mmap has per-page fault overhead on first access; for small files, the overhead dominates. read() may be faster.
  • MAP_POPULATE pre-faults all pages at mmap time; useful when you know you'll touch everything (avoids per-page faults).
Debugging mmap issues
  • /proc/<pid>/maps shows all VMAs with address range, permissions, offset, device, inode, and pathname.
  • /proc/<pid>/smaps adds per-mapping RSS, PSS, Shared/Private dirty/clean page counts.
  • perf stat -e page-faults,major-faults shows total fault counts for a process.
  • For SIGBUS crashes, check if the file was truncated or if you're accessing beyond file size.

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// 1. mmap a file for reading (zero-copy)
#include <sys/mman.h>
#include <fcntl.h>
#include <sys/stat.h>
#include <unistd.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>

int main(void) {
    int fd = open("data.txt", O_RDONLY);
    struct stat st; fstat(fd, &st);
    char *p = mmap(NULL, st.st_size, PROT_READ, MAP_PRIVATE, fd, 0);
    close(fd);  // fd can be closed after mmap
    // Use p[0..st.st_size-1] directly as read-only memory
    printf("first byte: %c\n", p[0]);
    munmap(p, st.st_size);

    // 2. Anonymous shared mapping for fork IPC
    int *shared = mmap(NULL, sizeof(int),
                       PROT_READ | PROT_WRITE,
                       MAP_SHARED | MAP_ANONYMOUS, -1, 0);
    *shared = 0;
    if (fork() == 0) {
        *shared = 42;   // child writes
        exit(0);
    }
    wait(NULL);
    printf("parent sees: %d\n", *shared);  // prints 42
    munmap(shared, sizeof(int));
    return 0;
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Always check mmap() return against MAP_FAILED, not NULL.
  • For MAP_SHARED file mappings, ensure file size covers the mapped region (ftruncate before writing).
  • Use msync() + fsync() for durability guarantees; msync alone may not flush to stable storage on all filesystems.
  • Use madvise(MADV_SEQUENTIAL) for sequential scans and MADV_RANDOM for random access patterns.
  • Avoid frequent mmap/munmap in hot paths — the TLB shootdown and VMA manipulation overhead is significant.
