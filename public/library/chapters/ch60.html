Chapter 60 — Sockets: Server Design

Server architecture determines scalability — from simple iterative servers to fork-per-connection, thread pools, and event-driven designs. The choice depends on connection lifetime, concurrency requirements, and resource constraints.

This chapter surveys the spectrum: iterative (one client at a time), fork-per-connection (isolation), thread-per-connection (shared state), pre-forked/pre-threaded pools (amortized creation cost), event-driven with epoll (maximum throughput), and the inetd super-server pattern. Modern production servers often use a hybrid: event loop for I/O multiplexing plus a thread pool for blocking operations.

Invariant
Server design is about bounding work per connection, isolating failures, and choosing the right concurrency model for the workload profile.
Gotcha
Pre-forked servers with a shared listen socket cause "thundering herd" — all workers wake on one connection. SO_REUSEPORT gives each worker its own accept queue.
Debugging
Measure accept latency, connections/sec, and per-worker CPU. Use ss -s for socket statistics and /proc/net/sockstat for kernel queue depths.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • Iterative server: one client at a time in a simple accept-handle-close loop. Adequate for fast requests (DNS, time services) but blocks all other clients during processing.
  • Fork-per-connection: accept() then fork(). Child handles the client, parent continues accepting. Strong isolation (crash in child doesn't affect others) but expensive (fork copies page tables, ~ms per connection).
  • Thread-per-connection: accept() then pthread_create(). Cheaper than fork (shared address space) but requires careful synchronization. Thread stack memory limits scalability (~8MB default stack * 10K threads = 80GB).
  • Pre-forked / pre-threaded: create a pool of N workers at startup; each calls accept() in a loop. Avoids per-connection creation overhead. Thundering herd problem: use SO_REUSEPORT so each worker has its own accept queue.
  • Event-driven: single thread (or few threads) using epoll to multiplex all connections. O(k) where k = ready fds. Highest throughput for I/O-bound workloads but requires all operations to be nonblocking — complex state machines per connection.
  • inetd super-server: listens on multiple ports defined in /etc/inetd.conf. On connection, forks and exec's the appropriate service binary with socket on stdin/stdout. Simple deployment but high per-connection overhead.
  • Hybrid: event loop for I/O multiplexing + thread pool for CPU-intensive or blocking operations (disk I/O, DNS resolution). This is what nginx, Node.js libuv, and most modern servers use.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
Fork-per-connection: zombie processes and fd leaks
  • After fork(), the parent must close the client fd (it has its own copy). The child must close the listen fd. Failing to close leaks fds and prevents port release.
  • Child processes that exit become zombies until the parent calls waitpid(). Use SIGCHLD handler with waitpid(-1, NULL, WNOHANG) in a loop to reap all finished children.
  • Alternatively, double-fork (fork, child forks again, first child exits) to orphan the grandchild to init/systemd, avoiding zombie management entirely.
  • Under heavy load, fork() can fail with EAGAIN if process limits are hit. Have a fallback: reject the connection or serve it in the parent.
Thundering herd and SO_REUSEPORT
  • Classic pre-fork: all workers share one listen socket and block on accept(). When a connection arrives, all workers wake up but only one wins — the rest waste CPU.
  • SO_REUSEPORT (Linux 3.9+): each worker binds its own socket to the same port. Kernel distributes connections to individual accept queues — no contention, no thundering herd.
  • With SO_REUSEPORT, worker death means its queued connections are lost (RST). Use EPOLLEXCLUSIVE (Linux 4.5+) as a lighter alternative that wakes only one waiter.
  • Balance worker count: too few leaves CPU idle; too many causes context-switch overhead. N = CPU cores is a good starting point for CPU-bound work.
Event-driven: edge-triggered vs level-triggered epoll
  • Level-triggered (default): epoll_wait reports a fd as ready as long as the condition holds. Simpler but may cause redundant wakeups if you don't fully drain the fd.
  • Edge-triggered (EPOLLET): epoll_wait reports only on state transitions (not-ready → ready). You MUST read/write until EAGAIN or you'll miss events permanently.
  • With ET, forgetting to drain means the fd is never reported again until a new event arrives. This manifests as "stuck" connections — hard to debug.
  • EPOLLONESHOT: fires only once; must re-arm with epoll_ctl(MOD) after handling. Useful for thread-pool dispatching to avoid two threads handling the same fd.
inetd and systemd socket activation
  • inetd reads /etc/inetd.conf, opens listen sockets for all configured services, and select()/poll() on them. On connection, fork+exec the service binary with the socket as fd 0/1.
  • Advantage: no listen/bind/accept code in the service binary. Disadvantage: fork+exec overhead per connection; unsuitable for high-rate services.
  • systemd socket activation is the modern equivalent: systemd holds the listen socket, starts the service on first connection, passes the fd via SD_LISTEN_FDS_START.
  • Socket activation enables on-demand service startup and zero-downtime restarts (systemd holds the listen socket during service restart).

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// Pre-forked server skeleton with SO_REUSEPORT
#include <sys/socket.h>
#include <netinet/in.h>
#include <unistd.h>
#include <stdio.h>
#include <stdlib.h>

#define WORKERS 4
#define PORT    8080

void worker_loop(void) {
    int lfd = socket(AF_INET, SOCK_STREAM | SOCK_CLOEXEC, 0);
    int on = 1;
    setsockopt(lfd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof(on));
    setsockopt(lfd, SOL_SOCKET, SO_REUSEPORT, &on, sizeof(on));
    struct sockaddr_in addr = { .sin_family=AF_INET,
        .sin_port=htons(PORT), .sin_addr.s_addr=htonl(INADDR_ANY) };
    bind(lfd, (struct sockaddr*)&addr, sizeof(addr));
    listen(lfd, 128);
    for (;;) {
        int cfd = accept4(lfd, NULL, NULL, SOCK_CLOEXEC);
        if (cfd < 0) continue;
        // handle client on cfd (read/write/close)
        close(cfd);
    }
}
int main(void) {
    for (int i = 1; i < WORKERS; i++)
        if (fork() == 0) { worker_loop(); exit(0); }
    worker_loop();  // parent is also a worker
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Choose concurrency model based on workload: event-driven for many idle connections, thread-pool for CPU-bound, pre-forked for isolation.
  • Use SO_REUSEPORT for pre-forked/pre-threaded servers to eliminate thundering herd and accept queue contention.
  • In fork-per-connection servers, install a SIGCHLD handler that reaps all zombies with waitpid(-1, NULL, WNOHANG) in a loop.
  • For event-driven servers, use edge-triggered epoll only if you guarantee draining until EAGAIN; otherwise prefer level-triggered.
  • Implement graceful shutdown: stop accepting, drain in-flight requests, then exit. Use signalfd or a self-pipe to integrate signal handling with the event loop.
