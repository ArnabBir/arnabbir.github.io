    TOPIC 60 / 64 · Sockets: Server Design

    Servers need admission and shutdown policies

    A server accepts connections faster than workers can drain them and runs out of memory.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    A server is a collection of finite queues: connection backlog, accepted descriptors, request buffers, worker tasks, and pending responses. Thread-per-connection, process-per-connection, and event loops move costs between these queues rather than eliminating them. Backpressure needs a place to act before resources are exhausted.

    Contract and implementation boundary

    A listening descriptor and accepted descriptors have independent lifetimes. On Linux accept4 can set SOCK_NONBLOCK and SOCK_CLOEXEC atomically. Define per-connection input limits, output limits, idle deadlines, and work budgets. During shutdown, stop admission first, drain within a deadline, then terminate remaining work deliberately.

    Contract references: accept.2 · listen.2 · epoll.7. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    An unbounded executor queue behind a bounded thread pool remains unbounded admission. A slow peer can retain output buffers indefinitely. Retrying EMFILE in a tight loop consumes CPU while capacity remains unavailable.

    Original practice problem

    Budget a toy server for 64 connections, 4 KiB input and 8 KiB output per connection: 768 KiB of payload buffers before metadata and workers. Specify rejection, idle expiration, and graceful-shutdown rules. Label this as a design calculation, not a benchmark.
