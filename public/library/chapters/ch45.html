Chapter 45 — Introduction to System V IPC

System V IPC provides kernel-persistent objects — message queues, semaphores, and shared memory segments — identified by integer keys. The API is older and less clean than POSIX IPC, but remains widespread in legacy codebases and is fully supported by modern kernels.

All three System V IPC types share a common framework: ftok() generates keys, *get() creates or opens objects, *ctl() controls them, and *op() performs operations. Understanding this common pattern makes learning all three straightforward.

Invariant
System V IPC objects persist in the kernel until explicitly removed with IPC_RMID or until the system reboots. They are not reference-counted.
Gotcha
ftok() can produce collisions: two different paths with the same inode number and proj_id yield the same key. Always check for EEXIST.
Tip
Use ipcs to list all System V IPC objects and ipcrm to remove orphaned ones. Check /proc/sysvipc/* for detailed kernel state.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • Common pattern across all three types: msgget/semget/shmget create or open an object; msgctl/semctl/shmctl query or modify metadata (permissions, limits, IPC_RMID); msgsnd+msgrcv / semop / shmat+shmdt perform the actual IPC operation.
  • key_t from ftok(pathname, proj_id): converts a filesystem path + 8-bit project ID into an integer key. The key identifies the IPC object across unrelated processes. ftok uses the file's inode number and device — it does not read the file contents.
  • IPC_CREAT: flag passed to *get(). Creates the object if it doesn't exist. If it exists, opens it. Combined with IPC_EXCL, it fails with EEXIST if the object already exists — useful for ensuring you are the creator.
  • IPC_PRIVATE (key=0): creates a private object not associated with any key. Only accessible by processes that inherit the identifier (via fork). Useful for parent-child IPC without name collisions.
  • Permissions: each IPC object has a struct ipc_perm with uid, gid, and mode bits (similar to files but no execute bit). Checked on each operation. Set at creation time; modifiable via *ctl(IPC_SET).
  • Kernel persistence: unlike pipes (which vanish when fds close), System V IPC objects live until IPC_RMID or reboot. A crashed process leaves orphaned objects. Always plan cleanup: startup scripts, atexit handlers, or cron jobs running ipcrm.
  • Resource limits: controlled via /proc/sys/kernel/msgmax, msgmnb, msgmni (message queues), semmsl, semmns, semmni (semaphores), shmmax, shmall, shmmni (shared memory). Hitting limits returns ENOSPC or ENOMEM.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
ftok collisions and key generation
  • ftok() uses the file's st_ino (inode) and st_dev (device) plus proj_id. If two files on the same device have the same inode number (unlikely but possible after file deletion and recreation), ftok returns the same key.
  • If the file is deleted and recreated, its inode may change — causing ftok to return a different key. Existing IPC objects become orphaned.
  • proj_id is truncated to 8 bits. Only values 1-255 are useful. 0 is technically valid but discouraged (some implementations handle it poorly).
  • Alternative: use IPC_PRIVATE to avoid key collisions entirely, sharing the ID via fork or a side channel (file, environment variable).
Orphaned IPC objects after crashes
  • If a process crashes without calling IPC_RMID, the IPC object remains in the kernel indefinitely. This is the most common operational problem with System V IPC.
  • Use ipcs to list orphaned objects. Automate cleanup: check for stale objects on application startup or via a cron job.
  • For shared memory, IPC_RMID marks the segment for deletion but it persists until the last process calls shmdt(). For message queues and semaphores, IPC_RMID destroys immediately — pending operations get EIDRM.
  • Resource limits (msgmni, semmni, shmmni) cap the total number of objects system-wide. Orphaned objects eat into these limits.
Permissions and security
  • IPC permissions are checked like file permissions (read/write for owner, group, other) but there is no execute bit.
  • The creator (cuid/cgid) and owner (uid/gid) are tracked separately. Only the creator, owner, or root can call IPC_RMID or IPC_SET.
  • System V IPC has no pathname-based access control (unlike POSIX IPC in /dev/mqueue or /dev/shm). Security depends entirely on the permission bits and UID/GID matching.
  • In containerized environments, IPC namespaces (CLONE_NEWIPC) isolate System V IPC objects between containers.
Resource limits tuning
  • Message queues: msgmax (max message size, default 8192), msgmnb (max bytes per queue, default 16384), msgmni (max queues, default 32000).
  • Semaphores: semmsl (max sems per set, default 32000), semmns (max sems system-wide), semmni (max sets, default 32000).
  • Shared memory: shmmax (max segment size, default varies), shmall (max total pages), shmmni (max segments, default 4096).
  • Tune via sysctl or writing to /proc/sys/kernel/*. Changes take effect immediately for new objects.

Code patterns (C / POSIX)

ftok + msgget pattern with proper error handling and cleanup. 
// System V IPC: create or open a message queue
#include <sys/msg.h>
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    // Generate key from a well-known path + project ID
    key_t key = ftok("/tmp/myapp", 'A');  // proj_id = 'A' (65)
    if (key == -1) { perror("ftok"); exit(1); }

    // Create queue (fail if exists) with rw-rw---- perms
    int qid = msgget(key, IPC_CREAT | IPC_EXCL | 0660);
    if (qid == -1) {
        if (errno == EEXIST) {
            qid = msgget(key, 0);        // open existing
            if (qid == -1) { perror("msgget open"); exit(1); }
        } else { perror("msgget create"); exit(1); }
    }
    printf("queue id = %d\n", qid);

    // ... use the queue (msgsnd / msgrcv) ...

    // Cleanup: remove the queue
    if (msgctl(qid, IPC_RMID, NULL) == -1)
        perror("msgctl IPC_RMID");
    return 0;
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Always plan IPC object cleanup: atexit handler, signal handler, or startup cleanup routine that removes stale objects.
  • Use IPC_CREAT | IPC_EXCL for the creator process; just IPC_CREAT (or 0) for clients that attach.
  • Set restrictive permissions (0600 or 0660) and verify with ipcs -p to check creator/owner PIDs.
  • Monitor resource limits: check /proc/sys/kernel/msg*, sem*, shm* and tune before deployment.
  • Prefer POSIX IPC (mq_open, sem_open, shm_open) for new projects — cleaner API, fd-based, better cleanup semantics.
