    TOPIC 20 / 64 · Signals: Fundamental Concepts

    Signals: pending is not a message count

    A worker receives ten SIGUSR1 sends but handles fewer than ten notifications.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    A standard signal has pending state, not an unbounded queue of occurrences. Repeated generation while the same standard signal is pending coalesces. Disposition is process-wide, while each thread has a signal mask. Blocking postpones delivery; ignoring selects a different disposition.

    Contract and implementation boundary

    Use sigaction to establish handling and pthread_sigmask for masks in threaded programs. SIGUSR1 and SIGTERM terminate by default; SIGKILL and SIGSTOP cannot be caught or blocked. Real-time signals support queued instances within resource limits and have different ordering rules.

    Contract references: signal.7 · sigaction.2 · pthread_sigmask.3. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    A counter incremented by a handler cannot reliably count standard-signal sends. Unblocking a pending SIGTERM with its default disposition terminates the process; a teaching model must not silently treat it as a harmless callback.

    Worked reasoning trace

    Assumptions: SIGUSR1 is blocked; one process; no synchronous acceptance yet.

      No standard signal is pending.

    2. Operation

    Tradeoff: Signals are light notifications; use queued IPC for counted work.

    Check your understanding

    Three SIGUSR1 occurrences are generated while blocked and already pending. How many pending instances are represented?

    Explain the answer

    One standard-signal pending instance, not three queued messages.

    One pending instance exists; disposition decides what delivery does.
