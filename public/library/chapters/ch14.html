Chapter 14 — File Systems

How files actually live on disk — partitions, superblocks, inode tables, data blocks, and the VFS abstraction. A disk is just a linear array of blocks; the filesystem imposes structure (superblock, inode table, data region) that makes those blocks addressable by name. The VFS layer abstracts over concrete filesystem implementations so that open/read/write work identically whether the backing store is ext4, xfs, btrfs, or NFS.

Understanding disk layout explains why you can run out of inodes with free space remaining, why journaling prevents corruption after crashes, and why mount() is the mechanism that attaches a filesystem into the global namespace.

Invariant
VFS provides a uniform interface; concrete filesystems implement superblock/inode/dentry operations behind it.
Gotcha
Inode exhaustion: a filesystem can have free blocks but zero free inodes — no new files can be created.
Debugging
Use df -i for inode usage, dumpe2fs for superblock info, mount | grep for mount options.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • VFS is a uniform interface: every filesystem registers super_operations, inode_operations, file_operations. User code never touches concrete FS directly.
  • The superblock tracks filesystem-wide metadata: block size, total/free blocks, total/free inodes, mount state, journal location.
  • An inode contains all file metadata (size, permissions, timestamps, block pointers) but NOT the filename — filenames live in directory entries.
  • Journaling (ext3/ext4) writes metadata changes to a log before committing; on crash, replay the journal to restore consistency without full fsck.
  • mount() attaches a filesystem's root inode to a directory in the namespace; mount namespaces allow per-process views.
  • statfs()/statvfs() query filesystem parameters (block size, free space, free inodes) — essential for capacity monitoring.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
Inode exhaustion vs space exhaustion
  • A filesystem can report free blocks but have zero free inodes (common with many tiny files, e.g. mail spools).
  • df -i shows inode usage; ext4 inode count is fixed at mkfs time (unless flex_bg/resize).
  • XFS allocates inodes dynamically — less prone to this issue but can still hit limits.
  • Symptoms: ENOSPC on creat() despite df showing free space.
Journal replay and crash recovery
  • On unclean shutdown, the filesystem replays the journal to restore consistent metadata state.
  • journal=data mode journals file data too (slower but stronger guarantees); default is journal=ordered (data written before metadata commit).
  • Journal replay is automatic at mount time; if it fails the FS may require manual fsck.
  • Barriers (write ordering) must be honored by the disk; disable write cache or use barriers=1.
Mount namespace isolation
  • unshare(CLONE_NEWNS) creates a new mount namespace; mounts/unmounts in child are invisible to parent.
  • Containers rely on mount namespaces to provide isolated filesystem views.
  • pivot_root() or chroot() combined with mount namespaces implements root filesystem isolation.
  • Shared vs private vs slave mount propagation controls visibility of mount events across namespaces.
Filesystem type differences
  • ext4: mature, fixed inode count, journaling, max file 16TB, max FS 1EB. Good general-purpose.
  • XFS: excellent for large files, dynamic inode allocation, extent-based, online defrag/resize (grow only).
  • Btrfs: copy-on-write, snapshots, checksums, multi-device, but still less battle-tested for some workloads.
  • Behavior of O_DIRECT, fallocate, hole-punching varies by FS — always test your assumptions.

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// Query filesystem capacity
struct statfs sfs;
if (statfs("/data", &sfs) == -1) { perror("statfs"); exit(1); }
printf("Block size: %ld\n", sfs.f_bsize);
printf("Free blocks (avail): %ld\n", sfs.f_bavail);
printf("Free inodes: %ld\n", sfs.f_ffree);

// Mount a filesystem programmatically
if (mount("/dev/sdb1", "/mnt/data", "ext4",
          MS_NOATIME | MS_NOSUID, NULL) == -1) {
    perror("mount");  // EBUSY if already mounted
}

// Lazy unmount when target is busy
umount2("/mnt/data", MNT_DETACH);

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Monitor both block usage AND inode usage (df -i) — alert on either approaching limits.
  • Understand your journal mode (ordered vs data vs writeback) and its crash guarantees.
  • Use mount options appropriate for workload: noatime for read-heavy, nosuid/nodev for untrusted data.
  • Test filesystem behavior under crash (power-cut simulation) for data integrity code paths.
  • For containers: understand mount propagation (shared/private/slave) to avoid mount leaks.
