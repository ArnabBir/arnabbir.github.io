Chapter 21 — Signals: Signal Handlers

Writing correct signal handlers is one of the hardest parts of systems programming. The key constraint: only async-signal-safe functions may be called inside a handler. Everything else must use the flag-and-check pattern.

A handler executes in the context of the interrupted thread, on the same stack (unless SA_ONSTACK is set). Because the main program might be in the middle of malloc or printf when interrupted, calling those functions from a handler creates undefined behavior. The safe approach: set a volatile sig_atomic_t flag in the handler, check it in the main loop.

Invariant
Only async-signal-safe functions (write, _exit, sig_atomic_t assignment) may be called in a handler.
Gotcha
A handler can corrupt errno; always save and restore errno at handler entry/exit.
Alternative
signalfd + event loop avoids handlers entirely, eliminating all reentrancy issues.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • A signal handler executes in the interrupted context: same thread, same stack (unless SA_ONSTACK configured an alternate signal stack).
  • Only async-signal-safe functions may be called: write(), _exit(), sig_atomic_t assignment, and a defined POSIX list of about 100 functions.
  • The volatile sig_atomic_t flag pattern: handler sets flag to 1, main loop checks and clears it. This is the canonical safe communication channel.
  • SA_RESTART causes most blocking syscalls to restart automatically after handler returns; but select(), poll(), connect(), accept(), and sleep functions are NOT restartable.
  • Without SA_RESTART, interrupted syscalls return -1 with errno=EINTR, giving the application explicit control.
  • Handlers cannot safely use stdio (printf/fprintf), malloc/free, or lock mutexes (deadlock risk if main code holds the same lock).
  • The signalfd alternative: block the signal, read signal info from an fd in the event loop. No handler needed, no reentrancy issues.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
Handler interrupting non-reentrant code
  • If main code is inside malloc() and the handler calls malloc(), heap corruption results (double-entry into non-reentrant allocator).
  • If main code holds a mutex and the handler tries to lock the same mutex, instant deadlock (single thread, will never release).
  • stdio functions use internal locks and buffers; calling printf from a handler while main code is in printf causes undefined behavior.
  • The only safe approach: handlers must be trivially simple or use exclusively async-signal-safe functions.
Nested signals and SA_NODEFER
  • By default, the signal that invoked a handler is blocked during handler execution (prevents reentrancy of same handler).
  • SA_NODEFER removes this protection: the same signal can interrupt its own handler, causing recursive handler invocations.
  • The sa_mask field in struct sigaction specifies additional signals to block during handler execution.
  • Nested handlers multiply all reentrancy risks; avoid SA_NODEFER unless you have a very specific design reason.
errno corruption in handlers
  • Async-signal-safe functions like write() can modify errno. If the handler calls write() and it fails, errno changes.
  • The interrupted main code might be about to check errno from its own syscall; the handler has now corrupted that check.
  • Fix: save errno at handler entry (int saved_errno = errno;) and restore at exit (errno = saved_errno;).
  • This pattern is mandatory in any handler that calls functions which may set errno.
longjmp from handlers (dangerous)
  • siglongjmp from a handler is technically possible but almost always wrong; it bypasses cleanup of interrupted code.
  • If the interrupted code held locks, allocated memory, or was mid-update of a data structure, all of that is leaked or corrupted.
  • The signal mask may or may not be restored depending on whether siglongjmp or longjmp is used.
  • Prefer the flag pattern or signalfd; if you must longjmp, ensure all code between setjmp points is signal-safe.

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// Correct signal handler pattern: flag + errno save/restore
#include <signal.h>
#include <errno.h>
#include <unistd.h>

static volatile sig_atomic_t got_signal = 0;

static void handler(int sig) {
    int saved_errno = errno;   // save errno before any call
    got_signal = 1;            // atomic flag for main loop
    // Optionally write to self-pipe for event-loop wakeup:
    // write(self_pipe_wr, "x", 1);  // async-signal-safe
    errno = saved_errno;       // restore errno
}

// Installation with SA_RESTART
void install_handler(void) {
    struct sigaction sa = {0};
    sa.sa_handler = handler;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = SA_RESTART;  // restart interrupted syscalls
    sigaction(SIGTERM, &sa, NULL);
}

// Main loop checks the flag
while (!got_signal) {
    // do work, poll, read, etc.
    // If SA_RESTART is NOT set, handle EINTR explicitly
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Every handler saves/restores errno and only calls async-signal-safe functions.
  • Communication from handler to main code uses volatile sig_atomic_t or self-pipe/eventfd.
  • SA_RESTART policy is documented per-signal; non-restartable syscalls are handled explicitly.
  • No stdio, malloc, or mutex operations inside handlers.
  • Consider signalfd + epoll as a superior alternative that eliminates handler complexity entirely.
