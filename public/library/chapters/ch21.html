    TOPIC 21 / 64 · Signals: Signal Handlers

    A signal handler interrupts invariants

    A handler logs through printf and occasionally deadlocks.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    A handler can interrupt code while library internal state is halfway through an update. Ordinary thread safety is not sufficient for asynchronous interruption. The handler may reenter the same lock or allocator it interrupted. Keep its work minimal and hand control back to ordinary execution.

    Contract and implementation boundary

    Use only async-signal-safe operations in handlers. A volatile sig_atomic_t flag can communicate a simple condition to interrupted code under its defined constraints; it is not a general inter-thread synchronization primitive. Preserve errno when the handler makes calls that can change it.

    Contract references: signal-safety.7 · sigsuspend.2. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    printf, malloc, and mutex locking are not general handler-safe tools. Checking a flag and then calling pause creates a lost-wakeup window. Block the signal while testing and use sigsuspend to atomically change the mask and wait.

    Assumptions: A handler may interrupt a library call holding internal state.

    Does marking a function thread-safe make it safe inside an asynchronous signal handler?
