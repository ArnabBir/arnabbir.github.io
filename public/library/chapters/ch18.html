Chapter 18 — Directories and Links

Directories are just files that map names to inode numbers. A hard link is simply another name pointing to the same inode -- the file's link count tracks how many names reference it. A symbolic link is a separate inode whose data is a pathname string, providing indirection that can cross filesystem boundaries but can also dangle. Understanding this name-to-inode mapping is essential for safe path traversal, atomic file replacement, and recursive directory walking.

This chapter covers creating and removing directories (mkdir/rmdir), iterating directory contents (opendir/readdir), walking directory trees (nftw), and resolving symlinks to canonical paths (realpath). Each of these operations interacts with the kernel's dentry layer and has specific atomicity and race-condition implications.

Invariant
A directory entry is a name-to-inode mapping. Hard links share an inode; symlinks store a path string in their own inode.
Gotcha
Hard links cannot cross filesystem boundaries (EXDEV). Symlinks can dangle or form loops (ELOOP).
Debugging
Use ls -li to see inode numbers and link counts. Use readlink -f to resolve symlink chains.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • A directory entry (dentry) is a name→inode mapping. The directory file itself is a list of these mappings.
  • A hard link is another directory entry pointing to the same inode. The inode's link count (st_nlink) tracks how many names reference it. When the last hard link is removed (and no open fds remain), the kernel frees the inode and its data blocks.
  • A symlink is a special inode that stores a target path string. The kernel follows it transparently during path resolution, but the target may not exist (dangling) or may loop (ELOOP after too many hops).
  • "." and ".." are real hard links maintained by the kernel. This is why st_nlink for an empty directory is 2 (the directory's own entry in its parent, plus "." inside it).
  • mkdir and rmdir are atomic operations. rmdir fails with ENOTEMPTY if the directory has entries other than "." and "..".
  • opendir/readdir iterate directory contents without providing a snapshot -- concurrent modifications can cause entries to appear twice or be missed.
  • nftw (file tree walk) recursively traverses directory trees, calling a user callback per entry. It handles symlinks, depth-first/breadth-first, and crossing mount points via flags.
  • rename() is atomic within a single filesystem -- the target appears to change instantaneously. Cross-filesystem rename fails with EXDEV.
  • realpath() resolves all symlinks, ".", and ".." components to produce a canonical absolute path. Beware of TOCTOU: the resolved path may become stale immediately.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
Hard link restrictions and behavior
  • Hard links cannot cross filesystem boundaries -- link() returns EXDEV. This is because inode numbers are only unique within a filesystem.
  • Most Linux filesystems prohibit hard links to directories (EPERM) to prevent cycles in the directory graph. Only the kernel creates ".." entries.
  • Removing the last hard link (unlink) does not immediately free data if any process holds an open fd. The inode persists until the last fd is closed.
  • st_nlink for a directory counts its own "." entry plus all ".." entries in immediate subdirectories, plus the entry in its parent.
Symlink pitfalls
  • Dangling symlinks: the target path does not exist. open() fails with ENOENT but lstat() succeeds (it examines the symlink inode itself).
  • Symlink loops: A points to B, B points to A. The kernel detects this after SYMLOOP_MAX hops and returns ELOOP.
  • Symlinks are followed transparently by most syscalls. Use lstat/lchown/O_NOFOLLOW to operate on the symlink itself.
  • Relative symlink targets are resolved relative to the directory containing the symlink, not the current working directory.
Directory reading under concurrent modification
  • readdir does not provide a snapshot. Files created or deleted during iteration may or may not appear.
  • POSIX guarantees that readdir will not return an entry that was never present, but entries may be duplicated or skipped under concurrent mutation.
  • For safety, collect all entries first (into a list), then operate on them after closedir().
  • rewinddir() restarts iteration from the beginning but still provides no snapshot guarantee.
rename atomicity and realpath TOCTOU
  • rename() is atomic only within the same filesystem. It atomically replaces the target name if it already exists.
  • Cross-filesystem rename returns EXDEV. You must implement copy + fsync + rename-within-target-fs manually.
  • realpath() resolves the path at call time. By the time you use the result, symlinks or directories may have changed (TOCTOU).
  • For security-sensitive code, prefer opening with O_NOFOLLOW and using fstat on the fd rather than trusting realpath output.

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// Safe directory listing with opendir/readdir/closedir
void list_dir(const char *path) {
    DIR *dp = opendir(path);
    if (!dp) { perror("opendir"); return; }
    struct dirent *ep;
    errno = 0;
    while ((ep = readdir(dp)) != NULL) {
        if (ep->d_name[0] == '.' &&
            (ep->d_name[1] == '\0' ||
             (ep->d_name[1] == '.' && ep->d_name[2] == '\0')))
            continue;  // skip "." and ".."
        printf("%s (ino %lu)\n", ep->d_name, (unsigned long)ep->d_ino);
    }
    if (errno) perror("readdir");
    closedir(dp);
}

// Atomic file replace via rename
int atomic_replace(const char *dst, const void *buf, size_t len) {
    char tmp[PATH_MAX];
    snprintf(tmp, sizeof(tmp), "%s.tmp.XXXXXX", dst);
    int fd = mkstemp(tmp);
    if (fd < 0) return -1;
    if (write(fd, buf, len) != (ssize_t)len) goto fail;
    if (fsync(fd) < 0) goto fail;
    close(fd);
    if (rename(tmp, dst) < 0) { unlink(tmp); return -1; }
    int dfd = open(".", O_RDONLY|O_DIRECTORY|O_CLOEXEC);
    if (dfd >= 0) { fsync(dfd); close(dfd); }
    return 0;
fail:
    close(fd); unlink(tmp); return -1;
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Always skip "." and ".." when iterating directories with readdir.
  • Use linkat/symlinkat/renameat for fd-relative operations to avoid TOCTOU path races.
  • For atomic file updates: write to temp (mkstemp) -> fsync file -> rename over target -> fsync directory.
  • Handle EXDEV from rename() gracefully: fall back to copy + fsync + rename within the target filesystem.
  • When walking trees with nftw, use FTW_PHYS to avoid following symlinks into unexpected locations.
  • Use lstat (not stat) when you need to detect symlinks rather than follow them.
  • Close DIR* streams promptly -- each holds an fd and memory.
