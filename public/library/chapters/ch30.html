    TOPIC 30 / 64 · Threads: Thread Synchronization

    Synchronization protects a predicate

    A worker wakes from a condition wait although the queue is still empty.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    A mutex protects the invariant of shared state. A condition variable lets a thread wait until that state may have changed. Notification is not stored work, and waking does not prove the predicate is true. Another consumer may win the mutex first, or a spurious wakeup may occur.

    Contract and implementation boundary

    pthread_cond_wait atomically releases the associated mutex while waiting and reacquires it before returning. Test the predicate in a while loop under that mutex. Writers update the predicate under the same synchronization discipline and then notify as appropriate. Use a global lock order to prevent cycles.

    Contract references: pthread_cond_wait.3 · pthread_mutex_lock.3. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    Replacing while with if can consume nonexistent work. Holding a mutex while performing unbounded network I/O can serialize the entire service. Robust mutex EOWNERDEAD requires state repair and pthread_mutex_consistent, not blind success handling.

    Worked reasoning trace

    Assumptions: Two consumers, one queued item, shared mutex and predicate.

    1. Starting state

      Both consumers are awakened.

    2. Operation

      First consumes; second reacquires the mutex later.

    3. Expected observation

      Second sees empty and waits again in its while loop.

    Tradeoff: Predicate loops tolerate contention and spurious wakes at the cost of retesting.
