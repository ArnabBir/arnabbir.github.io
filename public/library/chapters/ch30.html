Chapter 30 — Threads: Thread Synchronization

Shared mutable state requires synchronization. Mutexes protect invariants by providing mutual exclusion over critical sections. Condition variables coordinate producers and consumers by allowing threads to wait for a predicate to become true. Read-write locks optimize read-heavy workloads by allowing concurrent readers.

The core discipline: always pair lock/unlock, always check condition variable predicates in a while loop (spurious wakeups are permitted by POSIX), and measure contention before adding complexity.

Invariant
A mutex protects a data invariant, not a code region. Every access to the protected data must hold the same mutex.
Gotcha
Condition variables must be checked with a while loop, not if. Spurious wakeups are allowed by POSIX and happen in practice.
Debugging
Use PTHREAD_MUTEX_ERRORCHECK to catch double-locks and wrong-thread unlocks during development.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • A mutex provides mutual exclusion: only one thread can hold it at a time, defining a critical section where shared state can be safely modified.
  • Always pair lock/unlock. In C++ use RAII (lock_guard); in C, ensure every code path (including error paths) unlocks.
  • A condition variable lets a thread sleep until a predicate becomes true. The pattern is: lock mutex, while(!predicate) cond_wait, do work, unlock mutex.
  • Spurious wakeups are allowed -- the kernel may wake a thread without a corresponding signal/broadcast. The while loop handles this.
  • pthread_rwlock allows multiple concurrent readers OR one exclusive writer. Useful for read-heavy data structures, but can starve writers depending on implementation.
  • pthread_barrier synchronizes N threads at a rendezvous point: all must arrive before any can proceed.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
Mutex correctness
  • A normal (default) mutex deadlocks if the same thread locks it twice. Use PTHREAD_MUTEX_ERRORCHECK to get EDEADLK instead.
  • Unlocking a mutex from a thread that does not own it is undefined for normal mutexes. ERRORCHECK returns EPERM.
  • Destroying a locked mutex is undefined behavior. Ensure all threads have released the lock before calling pthread_mutex_destroy.
  • Lock ordering: if you need multiple mutexes, always acquire them in a consistent global order to prevent deadlocks.
Condition variable subtleties
  • pthread_cond_signal wakes at least one waiter; pthread_cond_broadcast wakes all. Use broadcast when the predicate may satisfy multiple waiters.
  • Signaling without holding the mutex can cause lost wakeups: thread checks predicate (false), context switch, producer sets predicate + signals, consumer then waits forever.
  • The mutex associated with a condvar must remain the same for all waiters. Mixing mutexes on the same condvar is undefined.
  • pthread_cond_timedwait uses an absolute time (struct timespec), not a relative timeout. Clock must match the condvar's clock attribute.
Read-write lock and barrier pitfalls
  • Read-write locks can starve writers if readers arrive continuously. The POSIX spec does not mandate fairness -- measure your implementation.
  • Upgrading a read lock to a write lock is not supported by POSIX. You must release the read lock first, which creates a TOCTOU window.
  • pthread_barrier_wait returns PTHREAD_BARRIER_SERIAL_THREAD to exactly one thread -- use this to designate a "leader" for post-barrier work.
  • Reusing a barrier requires all threads to have returned from the previous wait. Destroying and re-initializing while threads are still inside is undefined.
Performance and contention
  • Lock contention manifests as futex() syscalls in strace and high context-switch rates in /proc/PID/status.
  • Keep critical sections short: do all computation outside the lock, then lock-modify-unlock.
  • Consider per-CPU or per-thread data structures to eliminate contention entirely for hot paths.
  • Spin locks (pthread_spinlock_t) are only useful for very short critical sections on multicore systems where threads do not get preempted.

Code patterns (C / POSIX)

Mutex + condition variable producer/consumer pattern. 
// Producer/consumer with mutex + condvar
#include <pthread.h>
#include <stdio.h>

#define QMAX 8
static int queue[QMAX], head, tail, count;
static pthread_mutex_t mtx = PTHREAD_MUTEX_INITIALIZER;
static pthread_cond_t  not_empty = PTHREAD_COND_INITIALIZER;
static pthread_cond_t  not_full  = PTHREAD_COND_INITIALIZER;

void enqueue(int val){
  pthread_mutex_lock(&mtx);
  while(count == QMAX) pthread_cond_wait(&not_full, &mtx);
  queue[tail] = val; tail = (tail+1) % QMAX; count++;
  pthread_cond_signal(&not_empty);
  pthread_mutex_unlock(&mtx);
}

int dequeue(void){
  pthread_mutex_lock(&mtx);
  while(count == 0) pthread_cond_wait(&not_empty, &mtx);
  int val = queue[head]; head = (head+1) % QMAX; count--;
  pthread_cond_signal(&not_full);
  pthread_mutex_unlock(&mtx);
  return val;
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Document which mutex protects which data. Every shared mutable field should have a comment naming its lock.
  • Use PTHREAD_MUTEX_ERRORCHECK in debug/test builds to catch double-locks and wrong-thread unlocks.
  • Always check condvar predicates in a while loop -- never if.
  • Establish a global lock ordering and document it. Use lock-order checking tools (e.g., Helgrind, TSan) in CI.
  • Prefer pthread_cond_broadcast over pthread_cond_signal unless you are certain exactly one waiter should wake.

Exercises

Hands-on tasks to make the chapter "stick". These are intentionally practical and debugging-heavy.
  • Implement a bounded producer/consumer queue. Verify with TSan that no data races exist. Test with more producers than consumers and vice versa.
  • Create a deadlock by locking two mutexes in opposite order from two threads. Then fix it by enforcing a consistent lock order.
  • Use a pthread_barrier to synchronize N worker threads: each does setup, waits at the barrier, then proceeds. Verify all threads start work simultaneously.
