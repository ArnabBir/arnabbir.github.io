    TOPIC 6 / 64 · Processes

    A process is more than a PID

    An exec trace shows the same PID executing two different programs. Is the trace corrupt?

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    A process combines a virtual address space, credentials, descriptors, signal state, and execution contexts. PID identifies the process within a PID namespace; it is not a permanent identity token. exec replaces a program image while retaining process identity. fork creates a child identity with inherited state.

    Contract and implementation boundary

    getpid returns the process ID and getppid its parent ID as visible in the namespace. argv and environ are user-space startup data. Changing a string in the environment does not alter the parent's environment. Successful execve does not return to the old program.

    Contract references: execve.2 · getpid.2 · pidfd_open.2. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    PID reuse makes a delayed kill(pid, ...) unsafe as a stable ownership mechanism. Linux pidfds provide a handle-oriented alternative for supported operations. Multiple successful execve calls over a process lifetime are entirely possible.

    Worked reasoning trace

    Assumptions: A single process successfully execs an absolute path.

    1. Starting state

      PID P runs launcher with a local variable x.

    2. Operation

      execve replaces the image.

    3. Expected observation

      PID P remains; x and the old code no longer exist.

    Tradeoff: Image replacement keeps selected resources but requires inheritance auditing.

    This is a hand-authored prediction, not captured runtime output.

    Original practice problem

    Trace a shell that execs a small helper and compare PID before and after the replacement. Contrast it with a forked child. Treat the observed PID value as run-specific, not a fixed expected number.

    Check your understanding

    Must a successful execve allocate a new PID?

    Explain the answer

    No. It replaces the calling process's program image.

    PID P remains; x and the old code no longer exist.
