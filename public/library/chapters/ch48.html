Chapter 48 — System V Shared Memory

System V shared memory is the fastest IPC mechanism — data is mapped directly into multiple process address spaces with no kernel copy on read or write. The trade-off: you must handle synchronization yourself, typically with semaphores.

Once attached, shared memory behaves like regular memory (pointer arithmetic, structs, arrays). The kernel only intervenes during creation, attachment, detachment, and removal — actual data access is pure user-space memory operations at RAM speed.

Invariant
Shared memory segments persist in the kernel until explicitly removed with IPC_RMID, even after the creator exits.
Gotcha
No built-in synchronization — concurrent reads/writes without semaphores or mutexes cause data races and corruption.
Debugging
ipcs -m shows segments with size, nattch (attached process count), and status; ipcrm -m removes leaked segments.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • shmget() creates a shared memory segment (size rounded up to PAGE_SIZE); returns shmid.
  • shmat() maps the segment into the calling process's address space; returns a pointer you use like malloc'd memory.
  • shmdt() unmaps the segment from the process; the segment still exists in the kernel.
  • shmctl(IPC_RMID) marks the segment for deletion; it is actually destroyed when the last process detaches (nattch drops to 0).
  • No kernel involvement during reads/writes — this is what makes shared memory the fastest IPC.
  • You MUST synchronize access with semaphores, mutexes in shared memory (PTHREAD_PROCESS_SHARED), or other mechanisms.
  • SHM_RDONLY flag on shmat() prevents writes; useful for read-only consumers.
  • Segments persist across process lifetimes — leaked segments consume kernel memory until reboot or ipcrm.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
Segment lifecycle and IPC_RMID
  • IPC_RMID marks the segment for deletion but does not immediately free it — the kernel waits until nattch drops to 0.
  • After IPC_RMID, new shmat() calls fail; only already-attached processes can still use the segment.
  • If the creator crashes without IPC_RMID, the segment leaks permanently (visible in ipcs -m).
  • Always call shmctl(IPC_RMID) immediately after all processes have attached — this ensures cleanup even if processes crash later.
Synchronization requirements
  • Shared memory has zero built-in synchronization. Two processes writing the same offset simultaneously cause data corruption.
  • Use System V semaphores (ch47), POSIX semaphores, or a pthread mutex with PTHREAD_PROCESS_SHARED attribute.
  • For lock-free patterns, use C11 atomics (__atomic builtins) and memory barriers — but only if you deeply understand the memory model.
  • Even read-only consumers need synchronization if the data structure is being updated (partial reads of multi-field structs).
Size, alignment, and addressing
  • shmget() rounds size up to PAGE_SIZE; requesting 100 bytes allocates 4096 bytes.
  • shmat() with shmaddr==NULL lets the kernel choose the virtual address — always prefer this for portability.
  • The returned pointer can be used with structs, but beware: different processes may compile with different struct padding. Use fixed-layout types.
  • Across fork(), the child inherits all attached segments at the same addresses — both parent and child access the same physical pages.
Debugging shared memory issues
  • ipcs -m lists all segments: key, shmid, owner, perms, bytes, nattch, and status.
  • Check /proc/<pid>/maps for SysV shm entries (shown as /SYSV<key>).
  • A segment with nattch==0 and no IPC_RMID pending is leaked — remove with ipcrm -m <shmid>.
  • For data corruption, add a magic number or checksum to the shared structure and validate on each access.

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// Shared memory + semaphore for producer-consumer
#include <sys/shm.h>
#include <sys/sem.h>
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <stdlib.h>

union semun { int val; };

int main(void) {
    // Create shared memory (1 page)
    int shmid = shmget(IPC_PRIVATE, 4096, IPC_CREAT | 0600);
    char *shm = shmat(shmid, NULL, 0);

    // Create binary semaphore (initially 0 = consumer waits)
    int semid = semget(IPC_PRIVATE, 1, IPC_CREAT | 0600);
    union semun arg = {.val = 0};
    semctl(semid, 0, SETVAL, arg);

    if (fork() == 0) {
        // Child = consumer: wait for data
        struct sembuf wait = {0, -1, 0};
        semop(semid, &wait, 1);
        printf("child read: %s\n", shm);
        shmdt(shm);
        exit(0);
    }
    // Parent = producer: write then signal
    strcpy(shm, "hello from producer");
    struct sembuf post = {0, +1, 0};
    semop(semid, &post, 1);
    wait(NULL);

    shmdt(shm);
    shmctl(shmid, IPC_RMID, NULL);
    semctl(semid, 0, IPC_RMID);
    return 0;
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Always pair shared memory with explicit synchronization (semaphores, mutexes, atomics).
  • Call shmctl(IPC_RMID) as early as possible — ideally right after all processes attach.
  • Check shmat() return against (void *)-1, not NULL.
  • Use fixed-layout data types in shared memory to avoid struct padding mismatches across compilers.
  • Monitor for leaked segments: add startup cleanup that removes stale segments by known key values.
