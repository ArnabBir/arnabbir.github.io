    TOPIC 25 / 64 · Process Termination

    Exit has user-space and kernel phases

    A forked child unexpectedly emits its parent's buffered log line again.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    Returning from main behaves like exit: registered cleanup and stdio flushing run in user space. _exit bypasses those user-space callbacks and buffers, while kernel teardown releases process resources. A terminated child can leave a waitable status until its parent reaps it.

    Contract and implementation boundary

    exit accepts an integer status whose low eight bits are available through the usual wait status interface. _exit is the appropriate failure path after exec fails in a restricted post-fork child. Closing descriptors during termination can still involve kernel work; immediate does not imply hard real-time completion.

    Contract references: exit.3 · _exit.2 · wait.2. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    Calling exit after fork can duplicate a pre-fork stdio buffer or run cleanup intended only for the parent. A destructor is not a substitute for a durable storage protocol and will not run for every kind of termination.

    Worked reasoning trace

    Assumptions: Single-threaded fork with an unflushed redirected stdio buffer.

    1. Starting state

      Parent's buffer contains one log prefix.

    2. Operation

      Both branches later call exit.

    3. Expected observation

      Each copied buffer may flush the prefix; flush before fork to avoid duplication.

    Tradeoff: exit runs cleanup; _exit avoids inherited user-space cleanup in the restricted child.
