Chapter 25 — Process Termination

Process termination is more than return 0 — there are exit handlers, stdio flushing, the exit status protocol, and the zombie state waiting for the parent to reap. Understanding the difference between _exit() and exit() prevents subtle double-flush bugs after fork and ensures deterministic cleanup.

The exit status is the process's last message to its parent: 8 bits encoding success/failure/signal information, delivered via wait macros. Getting this right is essential for shell scripting, supervisors, and CI pipelines.

Invariant
_exit() is immediate; exit() flushes stdio + runs atexit handlers + calls _exit(). return from main() calls exit(n).
Gotcha
After fork(), child stdio buffers are copies — calling exit() in the child can double-flush parent's buffered output.
Debugging
Use WIFEXITED/WEXITSTATUS/WIFSIGNALED/WTERMSIG macros to decode wait status; never inspect raw int bits directly.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • _exit(status) is the raw syscall: terminates immediately, no stdio flush, no atexit handlers. Use in child after failed exec.
  • exit(status) is the libc wrapper: flushes all stdio streams, calls atexit/on_exit handlers in LIFO order, then calls _exit.
  • return n from main() is equivalent to exit(n) — the C runtime startup code calls exit with main's return value.
  • Exit status is only 8 bits (0–255); the kernel stores it in bits 8–15 of the wait status word. Use WEXITSTATUS() to extract.
  • Abnormal termination (unhandled signal) sets different bits: WIFSIGNALED(status) is true, WTERMSIG gives the signal number.
  • _Exit() (C99) is identical to _exit — no cleanup, guaranteed by the standard.
  • atexit() registers up to ATEXIT_MAX (≥32) handlers; they run in reverse registration order (LIFO).
  • on_exit() is a GNU extension that also passes the exit status and a user arg to the handler.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
Double-flush after fork
  • stdio buffers (especially line-buffered stdout redirected to a file becomes fully-buffered) are duplicated on fork.
  • If both parent and child call exit(), buffered data is flushed twice — producing duplicate output.
  • Fix: use _exit() in the child, or fflush(NULL) before fork, or use unbuffered I/O in the child.
  • This is the #1 reason to always use _exit() in a child that fails to exec.
atexit handler crashes
  • If an atexit handler calls exit(), behavior is undefined (C standard). In practice, glibc re-enters the handler list, risking infinite recursion.
  • If a handler crashes (SIGSEGV), remaining handlers are not called — the process terminates abnormally.
  • Keep atexit handlers minimal: close files, remove temp files, log. Never call exit() from within a handler.
  • In forked children, atexit handlers inherited from parent may not be appropriate — another reason to use _exit().
exit() in signal handlers
  • exit() is NOT async-signal-safe. Calling it from a signal handler can deadlock (e.g., handler interrupts malloc, atexit handler calls malloc).
  • Use _exit() or _Exit() in signal handlers if you must terminate.
  • Better pattern: set a volatile sig_atomic_t flag in the handler and check it in the main loop.
  • Only functions listed in signal-safety(7) are safe to call from signal handlers.
Exit status encoding
  • Wait status is NOT the exit code directly. It's a bit field: bits 8-15 = exit status, bits 0-6 = signal, bit 7 = core dump.
  • WIFEXITED(s): true if normal exit. WEXITSTATUS(s): the 8-bit exit code.
  • WIFSIGNALED(s): true if killed by signal. WTERMSIG(s): the signal. WCOREDUMP(s): core produced.
  • Exit codes > 128 in shells conventionally mean "killed by signal (code - 128)" — e.g., 137 = SIGKILL (128+9).

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// atexit handler pattern + wait status decoding
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/wait.h>

static void cleanup_tmpfiles(void) { unlink("/tmp/myapp.lock"); }
static void flush_logs(void)       { fprintf(stderr, "flushing logs\n"); }

int main(void) {
    atexit(flush_logs);        // called second (LIFO)
    atexit(cleanup_tmpfiles);  // called first

    pid_t pid = fork();
    if (pid == 0) {
        execlp("false", "false", (char*)NULL);
        _exit(127);  // exec failed — use _exit, NOT exit
    }
    int status;
    waitpid(pid, &status, 0);
    if (WIFEXITED(status))
        printf("child exited: %d\n", WEXITSTATUS(status));
    else if (WIFSIGNALED(status))
        printf("child killed by signal %d%s\n",
               WTERMSIG(status), WCOREDUMP(status) ? " (core)" : "");
    return 0;  // triggers exit() → atexit handlers
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Always use _exit() (not exit()) in the child after a failed exec to avoid double-flushing and running parent's atexit handlers.
  • Keep atexit handlers idempotent and minimal — they should tolerate being called in unexpected states.
  • Never call exit() from a signal handler; use _exit() or _Exit() instead.
  • Check wait status with WIFEXITED/WIFSIGNALED macros — never assume normal termination.
  • Document your process's exit codes (0 = success, 1 = usage error, 2 = runtime error, 127 = exec failed, etc.).
