Chapter 01 — History and Standards

UNIX was born at Bell Labs in 1969 and its lineage — from Research UNIX through BSD and System V to Linux — directly shapes every API you will call today. The fork/exec process model, the "everything is a file" philosophy, and the small-composable-tools convention are not historical curiosities; they are load-bearing design decisions baked into the kernel ABI. Understanding this heritage tells you *why* the interfaces look the way they do and which guarantees you can rely on across systems.

Equally important is the standards landscape that grew around UNIX: POSIX (IEEE 1003.1) defines the portable baseline, the Single UNIX Specification (SUS) extends it, and the Linux Standard Base (LSB) narrows the gap between distributions. For production systems programming, you must know where the portability boundary sits — which calls are POSIX-guaranteed, which are Linux extensions, and how feature test macros like _POSIX_C_SOURCE and _GNU_SOURCE control what your compiler sees. Getting this wrong means silent build failures on other platforms or, worse, runtime behavior differences that only surface in production.

Invariant
POSIX is the portable foundation: any API documented in POSIX behaves identically across conforming systems (Linux, macOS, FreeBSD, Solaris). Code to POSIX first, then layer platform-specific extensions behind feature detection.
Gotcha
Defining _GNU_SOURCE exposes hundreds of Linux/glibc-specific extensions (e.g., pipe2, accept4, epoll) that silently break portability. Code compiles fine on Linux but fails on other POSIX systems. Always know which macro you actually need.
Debugging
Use man 2 <syscall> vs man 3 <func> to distinguish kernel interfaces from libc wrappers. Check the CONFORMING TO section to know which standard guarantees the behavior. Define _POSIX_C_SOURCE to the exact version you need (e.g., 200809L) to catch accidental use of non-portable APIs at compile time.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • UNIX heritage: The fork/exec/wait process model, "everything is a file" (regular files, pipes, sockets, devices all accessed via file descriptors), and the philosophy of small composable tools connected by pipes — these are not conventions, they are the kernel's architecture.
  • Standards hierarchy: POSIX defines the portable baseline → SUS (Single UNIX Specification) extends POSIX with XSI extensions → LSB (Linux Standard Base) standardizes across Linux distributions → Linux-specific APIs (epoll, inotify, signalfd) sit outside all of these. Know which layer you're coding to.
  • Feature test macros (_POSIX_C_SOURCE, _XOPEN_SOURCE, _GNU_SOURCE) control which API declarations are visible in header files. They act as compile-time portability gates — define them before any #include to get exactly the API surface you intend.
  • Man page sections are your primary reference: section 2 = syscalls (kernel interface), section 3 = library functions (libc wrappers and utilities), section 7 = overviews and concepts (e.g., man 7 signal, man 7 pthreads). Always check the CONFORMING TO and NOTES sections.
  • errno is thread-local (since POSIX.1c / pthreads) and is only valid immediately after a failed call, before any other function that might overwrite it. Successful calls are not required to reset errno to zero — never test errno without first checking the return value.
  • System call ABI vs libc wrapper: A syscall is a CPU instruction (e.g., syscall on x86-64) that traps into the kernel. The libc wrapper (e.g., open() in glibc) sets up registers, invokes the trap, and translates the kernel return value into errno. Same concept, different layers — and occasionally different semantics (e.g., glibc's getpid() caches the result).
Key terms & kernel objects
Term / objectMeaning
POSIXIEEE 1003.1 — the Portable Operating System Interface. Defines the core API contract (file I/O, processes, signals, threads) that conforming systems must implement. The current revision is POSIX.1-2008 (with 2017 technical corrigendum).
SUSSingle UNIX Specification — a superset of POSIX maintained by The Open Group. Adds XSI (X/Open System Interfaces) extensions such as mmap shared memory semantics and strftime locale handling. Systems branded "UNIX" must conform.
LSBLinux Standard Base — a specification that standardizes the binary interface across Linux distributions, covering packaging, shared library versions, and filesystem layout. Primarily relevant for ISV binary compatibility.
Feature test macrosPreprocessor symbols (_POSIX_C_SOURCE, _XOPEN_SOURCE, _GNU_SOURCE, _DEFAULT_SOURCE) that control which function declarations and constants are exposed by system headers. Must be defined before any #include.
System callThe mechanism by which user-space requests kernel services. On x86-64 Linux, the syscall instruction transfers control to the kernel with a syscall number in %rax. Libc wraps this with C-callable functions that set errno on failure.
errnoA thread-local integer set by syscalls and many libc functions on failure. Only meaningful immediately after a failed call. Common values: ENOENT (no such file), EACCES (permission denied), EINTR (interrupted by signal). Use strerror(errno) for human-readable messages.
Man page sectionsSection 1 = commands, 2 = syscalls, 3 = library functions, 4 = devices, 5 = file formats, 7 = concepts/overviews. Use man 2 open vs man 3 printf to disambiguate. The CONFORMING TO section tells you which standard guarantees the behavior.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
POSIX vs Linux extensions
  • Defining _GNU_SOURCE implicitly defines _POSIX_C_SOURCE, _XOPEN_SOURCE, and more — it's an "everything on" switch. Code that compiles with it may silently depend on Linux-only APIs like epoll_create1(), splice(), or pipe2().
  • To isolate platform-specific code: use #ifdef __linux__ guards around Linux-only calls, and provide POSIX fallbacks (e.g., poll() instead of epoll, pipe() + fcntl(FD_CLOEXEC) instead of pipe2()).
  • Some "Linux extensions" have since been standardized — e.g., openat() is POSIX.1-2008. Always check CONFORMING TO in the man page before assuming non-portability.
  • Build CI should test with strict _POSIX_C_SOURCE only (no _GNU_SOURCE) on at least one target to catch accidental GNU dependencies.
Feature test macros and header ordering
  • _POSIX_C_SOURCE must be defined before any #include, including <stdio.h>. If a header is included first without the macro, the feature gates have already been evaluated and subsequent definitions have no effect.
  • _GNU_SOURCE is a glibc-specific umbrella that enables everything: POSIX, XSI, BSD, and GNU extensions. It's convenient but dangerous for portable code because it masks accidental use of non-standard APIs.
  • _DEFAULT_SOURCE (glibc ≥ 2.19) replaces the deprecated _BSD_SOURCE and _SVID_SOURCE. If you define _POSIX_C_SOURCE or _XOPEN_SOURCE without _DEFAULT_SOURCE, some traditional BSD/SysV functions (e.g., endian.h macros) become unavailable.
  • Best practice: define exactly the macro you need at the top of each source file (or via -D in CFLAGS). Avoid relying on compiler or build-system defaults, which vary across toolchains.
Navigating man pages effectively
  • man -k <keyword> (equivalent to apropos) searches all man page names and descriptions. Use it to discover related APIs: e.g., man -k signal reveals sigaction(2), signal(7), sigprocmask(2), etc.
  • When a name exists in multiple sections, specify the section: man 2 open (syscall) vs man 3 fopen (libc). Without a section number, man returns the first match (usually section 1), which may not be what you want.
  • The CONFORMING TO section is critical for portability: it tells you exactly which standard(s) guarantee the function's existence and behavior (e.g., "POSIX.1-2001" vs "Linux-specific").
  • The NOTES section often contains thread-safety information, async-signal-safety caveats, and glibc-specific implementation details that differ from the POSIX specification. Never skip it.

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
/* Feature test macro: define BEFORE any #include.
 * 200809L = POSIX.1-2008, which gives us openat(), etc. */
#define _POSIX_C_SOURCE 200809L

#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <errno.h>
#include <fcntl.h>
#include <unistd.h>

/* Proper errno-checking pattern:
 * 1. Check return value FIRST (not errno).
 * 2. Read errno IMMEDIATELY — before any other call.
 * 3. Use strerror() for human-readable output. */
int main(int argc, char *argv[])
{
    const char *path = (argc > 1) ? argv[1] : "/no/such/file";

    int fd = open(path, O_RDONLY);
    if (fd == -1) {
        /* errno is valid here — right after the failed call */
        fprintf(stderr, "open(\"%s\"): %s (errno=%d)\n",
                path, strerror(errno), errno);
        return EXIT_FAILURE;
    }

    printf("opened \"%s\" as fd %d\n", path, fd);
    close(fd);
    return EXIT_SUCCESS;
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Always define feature test macros (_POSIX_C_SOURCE, _XOPEN_SOURCE) before any #include — never rely on implicit defaults from the compiler or build system.
  • Read the CONFORMING TO section in man pages to know exactly which standard guarantees the behavior you depend on, and whether your code is portable or Linux-specific.
  • Check errno immediately after a failed call, before invoking any other function. Even fprintf or close can overwrite errno.
  • Use strerror(errno) or perror() for human-readable error output. Never print raw errno integers in user-facing messages — they are meaningless without translation.
  • Isolate Linux-specific code behind #ifdef __linux__ guards and provide POSIX-compliant fallbacks. This keeps the codebase portable and makes platform dependencies explicit.
  • Test on your target kernel and libc versions; document the minimum required versions. APIs and behaviors can differ between kernel 4.x and 5.x, and between glibc, musl, and other libc implementations.

Exercises

Hands-on tasks to make the chapter "stick". These are intentionally practical and debugging-heavy.
  • Write a program that calls openat(AT_FDCWD, "test.txt", O_RDONLY) with only #define _POSIX_C_SOURCE 200809L. Verify it compiles cleanly without _GNU_SOURCE. Then try replacing openat() with the Linux-specific open(..., O_PATH) and observe the compilation error — this demonstrates the portability boundary.
  • Use man -k signal to list all signal-related pages. Read man 7 signal end-to-end and write down: (a) the difference between signal() and sigaction(), (b) which signals cannot be caught, and (c) what "async-signal-safe" means.
  • Write an errno-printing wrapper function: void die(const char *msg) that prints the message, the errno string, and the errno number, then exits. Test it by calling open() on a nonexistent path, a directory with wrong permissions, and a path exceeding PATH_MAX.
