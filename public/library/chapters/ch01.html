    Portability is a contract

    A utility builds on your laptop but fails on a production distribution. Which promise did the program actually depend on?

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    Separate the C language, the C library, the operating-system interface, and the kernel implementation. POSIX specifies observable behavior; Linux adds interfaces; glibc exposes wrappers and feature-test macros. A function appearing in a header does not prove that every deployment supports it. POSIX Issue 8 is the 2024 edition, not an alias for the older 2008 baseline.

    Contract and implementation boundary

    Define feature-test macros before any header. Use _POSIX_C_SOURCE=200809L when deliberately targeting that older interface set; _GNU_SOURCE requests GNU/Linux extensions in glibc. Check both compile-time availability and runtime failure where the kernel may lag behind the library.

    Contract references: standards.7 · feature_test_macros.7 · dup.2. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    Calling an interface Linux-only forever because it originated on Linux can become inaccurate: dup3 entered POSIX.1-2024. A newer standard does not retroactively update an older operating system.

    Worked reasoning trace

    Assumptions: glibc on Linux; source targets an older POSIX baseline.

    1. Starting state

      A declaration is hidden by feature-test macros.

    2. Operation

      Define the intended macro before headers and rebuild.

    3. Expected observation

      A declaration may become visible; runtime support still needs checking.

    Tradeoff: A broader extension set simplifies Linux code but narrows portability.

    This is a hand-authored prediction, not captured runtime output.

    Original practice problem

    Compile a small declaration probe with strict warnings under two feature-macro settings. Record compiler, libc, kernel, and intended standard separately. A compile failure answers a declaration question, not a runtime-support question.

    Check your understanding

    An API is in POSIX.1-2024. Does that guarantee it on an older POSIX.1-2008 system?

    Explain the answer

    No. Select a deployment baseline and provide a checked fallback or require an upgrade.
