Chapter 36 — Process Resources

Resource limits prevent runaway processes from consuming all system resources — file descriptors, memory, CPU time, core dump size, and more.

Every process inherits a set of rlimits from its parent. These limits act as guardrails: soft limits are the effective cap (can be raised by the process up to the hard limit), while hard limits are the ceiling that only privileged processes can increase.

Invariant
soft limit ≤ hard limit. Unprivileged processes can lower hard limits irreversibly but cannot raise them.
Gotcha
RLIMIT_NOFILE default (1024) is too low for servers; hitting it causes mysterious EMFILE errors on accept/open.
Debugging
cat /proc/<pid>/limits shows all current rlimits; prlimit --pid=<pid> can query and set them live.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • Each rlimit has two values: rlim_cur (soft/effective) and rlim_max (hard/ceiling).
  • Unprivileged processes can raise soft up to hard, or irreversibly lower hard. Only CAP_SYS_RESOURCE can raise hard limits.
  • RLIMIT_NOFILE: max number of open file descriptors. Default 1024 soft / 1048576 hard on modern Linux.
  • RLIMIT_AS: max virtual address space (mmap, brk). Exceeding causes ENOMEM.
  • RLIMIT_CORE: max core dump size. Set to 0 to disable core dumps; unlimited for full debugging.
  • RLIMIT_NPROC: max number of processes for a UID (not per-process — a common misconception).
  • getrusage() reports accumulated resource usage: user/system CPU time, max RSS, page faults, context switches.
  • prlimit() (Linux-specific): query or set rlimits of another process by PID — useful for live tuning.
  • systemd LimitNOFILE=, LimitAS=, etc. set rlimits for services at launch — the modern way to configure limits.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
RLIMIT_NOFILE pitfalls
  • The kernel has a system-wide cap: /proc/sys/fs/nr_open (default 1048576). You cannot set RLIMIT_NOFILE hard limit above this.
  • select() is limited to FD_SETSIZE (typically 1024) regardless of RLIMIT_NOFILE — use poll/epoll instead.
  • After raising RLIMIT_NOFILE, close-on-exec loops that iterate 0..getrlimit() become expensive with high limits. Use close_range() (Linux 5.9+).
  • Docker containers inherit the host's nr_open but may have different default ulimits set by the runtime.
RLIMIT_NPROC and threads
  • RLIMIT_NPROC counts all tasks (processes + threads) for the real UID, not per-process.
  • A single multi-threaded application can exhaust RLIMIT_NPROC for all processes owned by that UID.
  • fork() and clone() both check RLIMIT_NPROC; exceeding returns EAGAIN.
  • Root (UID 0) is exempt from RLIMIT_NPROC — it can always create new processes.
RLIMIT_STACK and threads
  • RLIMIT_STACK sets the main thread's stack size. Additional threads get their stack size from pthread_attr (default often 8MB).
  • Lowering RLIMIT_STACK after program start does not shrink existing stacks — only affects new threads/processes.
  • Stack overflow does not return ENOMEM; it delivers SIGSEGV (guard page hit).
  • Unlimited RLIMIT_STACK disables ASLR for the main stack on some kernels (security concern).
getrusage accuracy and accounting
  • ru_maxrss is in kilobytes on Linux (not bytes as on some BSDs). It represents the peak resident set size.
  • RUSAGE_CHILDREN only reports for waited-for children. Un-reaped children's usage is lost.
  • ru_minflt (minor faults) counts COW faults and demand-zero pages; ru_majflt (major faults) counts disk I/O.
  • On multi-core systems, ru_utime + ru_stime can exceed wall-clock time (parallel CPU consumption).

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// Query and raise RLIMIT_NOFILE; report CPU usage
#include <sys/resource.h>
#include <stdio.h>

void raise_nofile(rlim_t target) {
    struct rlimit rl;
    getrlimit(RLIMIT_NOFILE, &rl);
    printf("NOFILE: soft=%lu hard=%lu\n",
           (unsigned long)rl.rlim_cur, (unsigned long)rl.rlim_max);

    if (target > rl.rlim_max)
        target = rl.rlim_max;  // can't exceed hard limit
    rl.rlim_cur = target;
    if (setrlimit(RLIMIT_NOFILE, &rl) == -1)
        perror("setrlimit NOFILE");
}

void report_usage(void) {
    struct rusage ru;
    getrusage(RUSAGE_SELF, &ru);
    printf("user: %ld.%06lds  sys: %ld.%06lds  maxrss: %ldKB\n",
           ru.ru_utime.tv_sec, ru.ru_utime.tv_usec,
           ru.ru_stime.tv_sec, ru.ru_stime.tv_usec,
           ru.ru_maxrss);
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Set RLIMIT_NOFILE appropriately for network servers (at least max_connections + headroom); check at startup and log a warning if too low.
  • Use RLIMIT_CORE = unlimited in development/staging; consider 0 in production or route cores to coredumpctl.
  • Monitor getrusage() in long-running services to detect memory leaks (growing maxrss) and excessive syscalls (context switches).
  • Configure limits via systemd unit files (LimitNOFILE=, LimitNPROC=) rather than shell ulimit or /etc/security/limits.conf for services.
  • Use prlimit to adjust limits of running processes during incidents without restart.
