    TOPIC 51 / 64 · Introduction to POSIX IPC

    POSIX IPC names and open references

    A named object disappears from the namespace while an existing user keeps using it.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    POSIX IPC families offer name-based creation with distinct handle types and operations. Removing a name prevents future opens by that name but does not necessarily destroy the object while users retain references. Shared memory, semaphores, and message queues have similar naming ideas but different APIs.

    Contract and implementation boundary

    Use a leading slash and a simple name for portable named-object conventions. O_CREAT|O_EXCL distinguishes fresh creation from attachment. mq_close, sem_close, and close act on different handle types; mq_unlink, sem_unlink, and shm_unlink remove their respective names. Check deployment support and permissions.

    Contract references: mq_overview.7 · sem_overview.7 · shm_overview.7. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    Casting mqd_t or sem_t * to an integer descriptor because Linux happens to implement some handles that way is not portable. A predictable name without exclusive creation and permission checks can attach to an unexpected object.

    Worked reasoning trace

    Assumptions: A POSIX shared-memory name exists and one mapping remains open.

    1. Starting state

      Owner unlinks the name.

    2. Operation

      A new participant tries shm_open without O_CREAT.

    3. Expected observation

      New lookup fails while the old mapping can remain usable.

    Tradeoff: Early unlink simplifies cleanup but prevents late attachment by name.

    This is a hand-authored prediction, not captured runtime output.
