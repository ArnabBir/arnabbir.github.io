Chapter 51 — Introduction to POSIX IPC

POSIX IPC offers a cleaner API than System V — objects have filesystem-like names (/name), are reference-counted, and integrate better with standard UNIX operations. Three mechanisms share this design: message queues (mq_*), semaphores (sem_*), and shared memory (shm_*).

This chapter covers the common design principles: naming conventions, the create/open/unlink lifecycle, reference-counting semantics, and how POSIX IPC compares to the older System V equivalents.

Invariant
POSIX IPC names start with / and contain no other slashes. Objects persist until explicitly unlinked, and are destroyed when the last reference closes.
Gotcha
Unlinking removes the name but not the object — existing descriptors remain valid until closed. Forgetting to unlink leaks objects across reboots (on tmpfs, until reboot).
Debugging
Inspect /dev/shm and /dev/mqueue to see live POSIX IPC objects. Use ls -la to check permissions and ownership.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • Three POSIX IPC types: message queues (mq_*), semaphores (sem_*), shared memory (shm_*). Each follows the same open/close/unlink pattern.
  • Names must start with / and contain no further path separators (e.g., /myqueue is valid; /my/queue is not, though Linux may accept it).
  • Objects persist in the kernel until *_unlink() is called. Unlinking marks the name for removal; actual destruction happens when the last reference (descriptor or mapping) is closed.
  • Backed by tmpfs virtual filesystems: /dev/shm for shared memory, /dev/mqueue for message queues. Named semaphores live under /dev/shm (as sem.<name> on Linux).
  • Permissions model uses standard UNIX mode bits (owner/group/other) — simpler than System V's ipc_perm structure.
  • POSIX IPC is generally preferred over System V for new code: cleaner API, no numeric key generation (ftok), filesystem-visible objects, and reference-counted cleanup.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
POSIX vs System V IPC
  • System V uses numeric keys (via ftok) — fragile and prone to collisions. POSIX uses readable /name strings.
  • System V objects are removed with IPC_RMID — immediate destruction even if processes are attached (for shm, mapping stays valid but object is gone). POSIX uses reference-counted unlink.
  • System V semaphores support atomic operations on sets of semaphores. POSIX semaphores are simpler: one counter, one wait/post.
  • System V IPC limits are system-wide and configured via /proc/sys/kernel/msg*, sem*, shm*. POSIX limits are per /proc/sys/fs/mqueue/* and filesystem size for shm.
Naming rules and portability
  • POSIX requires names to start with /. Some systems (Linux) accept further slashes; for portability use only /simplename.
  • Maximum name length is NAME_MAX (typically 255). Some systems limit to fewer characters.
  • Names are global to the system (within a namespace). Use prefixes to avoid collisions between applications.
  • On Linux, named semaphores appear as /dev/shm/sem.<name>; directly deleting the file is equivalent to sem_unlink.
Reference counting and cleanup
  • Unlink removes the name from the namespace immediately. New opens will fail with ENOENT.
  • The underlying object survives until all descriptors/mappings are closed. This is analogous to unlinking a file while it is open.
  • If a process crashes without unlinking, the object persists (visible in /dev/shm or /dev/mqueue). Design startup cleanup.
  • For shared memory: even after shm_unlink, existing mmap regions remain valid. The kernel frees pages when the last munmap occurs.
Debugging POSIX IPC
  • ls -la /dev/shm/ shows shared memory objects and named semaphores with permissions and sizes.
  • cat /dev/mqueue/<name> shows queue attributes: max messages, message size, current count.
  • strace -e trace=mq_open,shm_open,sem_open traces IPC creation/opening.
  • System V objects still need ipcs/ipcrm. POSIX objects use standard filesystem tools.

Code patterns (C / POSIX)

Comparison: POSIX vs System V shared memory setup. POSIX is fewer lines, uses filesystem names, and integrates with standard fd operations. 
/* --- POSIX shared memory (preferred) --- */
int fd = shm_open("/myshm", O_CREAT | O_RDWR, 0600);
ftruncate(fd, 4096);
void *p = mmap(NULL, 4096, PROT_READ|PROT_WRITE,
               MAP_SHARED, fd, 0);
close(fd);                 /* mapping stays valid */
/* use *p ... */
munmap(p, 4096);
shm_unlink("/myshm");     /* remove when done */

/* --- System V shared memory (legacy) --- */
key_t key = ftok("/tmp/tok", 'A');   /* fragile! */
int id = shmget(key, 4096, IPC_CREAT | 0600);
void *q = shmat(id, NULL, 0);
/* use *q ... */
shmdt(q);
shmctl(id, IPC_RMID, NULL);  /* immediate destroy */

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Use POSIX IPC over System V for new code — cleaner naming, reference-counted cleanup, standard permissions.
  • Always call *_unlink() when the object is no longer needed; design idempotent startup cleanup for crash recovery.
  • Use a naming convention with application prefix (e.g., /myapp_shm_region1) to avoid collisions.
  • Set restrictive permissions (0600/0660) and verify with ls -la /dev/shm.
  • Link with -lrt (for shm_open/mq_open) and -lpthread (for sem_*) as needed.
