Chapter 43 — Interprocess Communication Overview

IPC lets processes share data and coordinate. Linux offers pipes, FIFOs, message queues, semaphores, shared memory, and sockets — each with different trade-offs in latency, bandwidth, and complexity. The fundamental division is between data-transfer IPC (where the kernel copies bytes between processes) and shared-memory IPC (where processes access the same physical pages directly).

This chapter surveys every major IPC mechanism, classifies them, and provides a decision framework so you can pick the right one for your use case.

Invariant
Data-transfer IPC (pipes, message queues, sockets) involves kernel-mediated copies; shared-memory IPC avoids copies but requires explicit synchronization.
Gotcha
System V IPC objects persist in the kernel until explicitly removed (IPC_RMID) or reboot — they are not reference-counted like pipes.
Tip
AF_UNIX sockets are the most versatile local IPC: bidirectional, support fd-passing, datagrams, and integrate with poll/epoll.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • Data-transfer IPC (kernel copies data): pipes, FIFOs, message queues (SysV & POSIX), and sockets. The sender writes into kernel buffers; the receiver reads from them. Simple but adds copy overhead.
  • Shared-memory IPC (zero copy): mmap with MAP_SHARED, POSIX shm_open, System V shmget/shmat. Processes map the same physical pages. Fastest for bulk data, but requires explicit synchronization (mutexes, semaphores, futexes).
  • Synchronization primitives: semaphores (SysV semget or POSIX sem_open), mutexes in shared memory (pthread_mutex with PTHREAD_PROCESS_SHARED), futex for low-level locking, eventfd for lightweight signaling.
  • POSIX IPC vs System V IPC: POSIX IPC (mq_open, sem_open, shm_open) uses filesystem-like names ("/myqueue"), has cleaner APIs, and integrates with select/poll via file descriptors. System V IPC (msgget, semget, shmget) uses integer keys from ftok(), has no fd-based interface, but is more widely deployed on legacy systems.
  • AF_UNIX sockets are the most versatile local IPC: bidirectional, support SOCK_STREAM and SOCK_DGRAM, can pass file descriptors (SCM_RIGHTS), and work with epoll. Prefer them for new designs unless you need the simplicity of pipes.
  • Decision criteria: related vs unrelated processes (pipes need fork; FIFOs/sockets/SysV work across unrelated processes), latency requirements (shared memory wins), message boundaries needed (use datagrams or message queues, not byte streams), persistence needed (SysV/POSIX named objects persist; pipes vanish when fds close).
Key terms & kernel objects
Term / objectMeaning
pipeUnidirectional byte stream; anonymous, only between related processes (via fork). Kernel-buffered, reference-counted — gone when all fds close.
FIFONamed pipe with a filesystem path (mkfifo). Connects unrelated processes. Same byte-stream semantics as pipes.
message queueKernel-managed queue of discrete, typed messages. SysV (msgget) or POSIX (mq_open). Preserves message boundaries.
semaphoreCounting synchronization primitive. SysV (semget/semop) or POSIX (sem_open/sem_wait). Used to guard shared resources.
shared memoryMultiple processes map the same physical pages. SysV (shmget/shmat) or POSIX (shm_open + mmap). No kernel copy overhead.
AF_UNIX socketLocal socket: bidirectional, supports streams/datagrams, fd-passing (SCM_RIGHTS), credentials (SO_PEERCRED). Works with epoll.
POSIX IPCModern IPC APIs: mq_open, sem_open, shm_open. Name-based ("/name"), fd-oriented, cleaner than System V.
System V IPCLegacy IPC APIs: msgget, semget, shmget. Key-based (ftok), no fd interface, kernel-persistent until IPC_RMID.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
Data-transfer vs shared-memory trade-offs
  • Data-transfer IPC (pipes, sockets, message queues) involves at least two copies: sender→kernel, kernel→receiver. For small messages the overhead is negligible; for large transfers (MB+) it dominates.
  • Shared memory eliminates copies but you must synchronize access. A missing memory barrier or lock causes silent corruption — the hardest bugs to find.
  • Hybrid approach: use shared memory for data, use a pipe or eventfd for notification ("data is ready"). This combines zero-copy with event-loop integration.
POSIX IPC vs System V IPC
  • POSIX IPC names are paths ("/myqueue") visible in /dev/mqueue or /dev/shm. System V IPC keys are integers from ftok() — prone to collisions and harder to debug.
  • POSIX IPC objects are reference-counted after unlink (like files): existing users keep access. System V IPC_RMID on a message queue destroys it immediately, possibly losing messages.
  • POSIX message queues support mq_notify for async notification (SIGEV_THREAD or SIGEV_SIGNAL). System V message queues have no notification mechanism.
  • System V semaphores support atomic operations on multiple semaphores in one semop() call. POSIX semaphores are simpler but only operate on one at a time.
AF_UNIX sockets as universal IPC
  • AF_UNIX SOCK_STREAM gives bidirectional reliable byte stream — like TCP but local, with lower overhead.
  • AF_UNIX SOCK_DGRAM gives message boundaries without the complexity of message queues. No need for length-prefix framing.
  • SCM_RIGHTS ancillary messages let you pass open file descriptors between processes — essential for privilege separation (e.g., passing a bound socket from a privileged parent to an unprivileged child).
  • SO_PEERCRED lets you authenticate the peer process (get its PID, UID, GID) without application-level auth.
Choosing IPC: decision checklist
  • Related processes only? pipe() or socketpair() are simplest — no naming, auto-cleanup on close.
  • Unrelated processes? Use AF_UNIX socket (most flexible), FIFO (simplest), or named POSIX IPC objects.
  • Need message boundaries? Use SOCK_DGRAM, POSIX mq, or System V msgqueue. Pipes/SOCK_STREAM are byte streams — you must frame yourself.
  • Need lowest latency for bulk data? Shared memory + eventfd notification.
  • Need to pass file descriptors? Only AF_UNIX sockets support SCM_RIGHTS.
  • Need persistence across process restarts? System V IPC objects or POSIX named objects persist until explicit removal.

Code patterns (C / POSIX)

Comparison: pipe vs AF_UNIX socket — showing when each is appropriate. 
// Option A: pipe — simple, unidirectional, related processes
int pfd[2];
pipe2(pfd, O_CLOEXEC);           // pfd[0]=read, pfd[1]=write
if (fork() == 0) {               // child reads
    close(pfd[1]);
    read(pfd[0], buf, sizeof(buf));
    _exit(0);
}
close(pfd[0]);                   // parent writes
write(pfd[1], "hello", 5);

// Option B: AF_UNIX socketpair — bidirectional, fd-passing capable
int sv[2];
socketpair(AF_UNIX, SOCK_STREAM | SOCK_CLOEXEC, 0, sv);
if (fork() == 0) {               // child: full duplex on sv[1]
    close(sv[0]);
    write(sv[1], "request", 7);
    read(sv[1], buf, sizeof(buf));
    _exit(0);
}
close(sv[1]);                    // parent: full duplex on sv[0]
read(sv[0], buf, sizeof(buf));
write(sv[0], "response", 8);

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Classify your IPC need: stream vs message vs shared memory. Pick the simplest mechanism that fits.
  • For shared memory: always pair with explicit synchronization (mutex, semaphore, or atomic + barrier). Document the protocol.
  • For named IPC objects (FIFO, POSIX mq/shm, SysV): define who creates, who unlinks, and handle stale objects on startup.
  • Prefer POSIX IPC over System V for new code — cleaner API, fd-based, better cleanup semantics.
  • Use AF_UNIX sockets as default for local IPC between unrelated processes unless you have a specific reason for alternatives.
