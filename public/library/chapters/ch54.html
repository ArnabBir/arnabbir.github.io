Chapter 54 — POSIX Shared Memory

POSIX shared memory combines shm_open + mmap — it creates a named shared memory object backed by tmpfs that multiple processes can map into their address spaces. This is the fastest IPC mechanism: no kernel-mediated data copying, just direct memory access.

This chapter covers object creation with shm_open, sizing with ftruncate, mapping with mmap, cleanup with shm_unlink, and synchronizing access with process-shared mutexes or semaphores.

Invariant
Shared memory is just memory — it provides no synchronization. You must use mutexes, semaphores, or atomics to coordinate access between processes.
Gotcha
You must call ftruncate after shm_open with O_CREAT — new objects have size 0. Mapping size 0 results in SIGBUS on access.
Debugging
ls -la /dev/shm/ shows objects with permissions and sizes. /proc/<pid>/maps shows which processes have mapped the region.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • shm_open(name, O_CREAT|O_RDWR, mode) creates or opens a shared memory object. Returns a regular file descriptor backed by tmpfs.
  • ftruncate(fd, size) sets the object size. New objects start at size 0 — you must set the size before mapping or face SIGBUS.
  • mmap(NULL, size, PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0) maps the object into the process address space. Multiple processes mapping the same object see the same physical pages.
  • After mmap, you can close(fd) — the mapping remains valid. The fd is only needed for ftruncate and initial setup.
  • shm_unlink(name) removes the name from /dev/shm. The object persists until the last munmap or process exit. Reference-counted like file unlink.
  • Synchronization must be explicit: use pthread_mutex_t with PTHREAD_PROCESS_SHARED attribute (placed in the shared region), or POSIX semaphores, or atomic operations.
  • Backed by /dev/shm (tmpfs). Objects are visible as regular files — you can inspect size, permissions, even hexdump contents.
  • vs System V: shm_open returns a real fd (fstat, fchmod work). System V shmget/shmat uses opaque IDs and has less flexible permissions.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
SIGBUS from unmapped pages
  • A new shm object has size 0. If you mmap it without calling ftruncate first, any access to the mapped region causes SIGBUS (not SIGSEGV).
  • Shrinking with ftruncate after processes have mapped the region can also cause SIGBUS for pages beyond the new size.
  • Always ftruncate before mmap. If multiple processes race to create, use O_EXCL or a semaphore to coordinate initialization.
Process-shared mutexes
  • A pthread_mutex_t can be used across processes if: (a) it is placed in shared memory (MAP_SHARED), and (b) initialized with PTHREAD_PROCESS_SHARED via pthread_mutexattr_setpshared.
  • If a process holding the mutex crashes, the mutex is left locked. Use PTHREAD_MUTEX_ROBUST attribute — the next locker gets EOWNERDEAD and can call pthread_mutex_consistent to recover.
  • Condition variables can also be process-shared with the same attribute pattern.
Sizing and resizing
  • You can grow a shm object with ftruncate after creation. Existing mappings do NOT automatically see the new pages — you must munmap and remap (or use mremap on Linux).
  • For fixed-size regions, agree on size at design time and document it. Dynamic resizing with multiple processes is complex and error-prone.
  • tmpfs is backed by RAM+swap. Large shm objects consume physical memory. Monitor df /dev/shm.
Cleanup and crash recovery
  • If the creating process crashes without calling shm_unlink, the object persists in /dev/shm until reboot or manual removal.
  • Pattern: unlink immediately after all processes have opened/mapped. New processes can't attach, but existing mappings remain valid.
  • For crash recovery: design startup to check for and clean up stale objects in /dev/shm.
  • Use restrictive permissions (0600) to prevent other users from attaching to sensitive shared data.

Code patterns (C / POSIX)

Create shared memory object, map it, use with a process-shared robust mutex. 
/* Shared region with process-shared mutex */
struct region {
    pthread_mutex_t mtx;
    int counter;
};

/* Creator process */
int fd = shm_open("/myregion", O_CREAT|O_RDWR, 0600);
ftruncate(fd, sizeof(struct region));
struct region *r = mmap(NULL, sizeof(*r),
    PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0);
close(fd);

/* Init process-shared robust mutex */
pthread_mutexattr_t ma;
pthread_mutexattr_init(&ma);
pthread_mutexattr_setpshared(&ma, PTHREAD_PROCESS_SHARED);
pthread_mutexattr_setrobust(&ma, PTHREAD_MUTEX_ROBUST);
pthread_mutex_init(&r->mtx, &ma);
r->counter = 0;

/* Worker process (opens existing) */
int fd = shm_open("/myregion", O_RDWR, 0);
struct region *r = mmap(NULL, sizeof(*r),
    PROT_READ|PROT_WRITE, MAP_SHARED, fd, 0);
close(fd);
int err = pthread_mutex_lock(&r->mtx);
if (err == EOWNERDEAD) {       /* previous holder crashed */
    r->counter = 0;            /* repair state */
    pthread_mutex_consistent(&r->mtx);
}
r->counter++;
pthread_mutex_unlock(&r->mtx);

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Always ftruncate before mmap on newly created objects. Check for SIGBUS in crash reports.
  • Use PTHREAD_PROCESS_SHARED + PTHREAD_MUTEX_ROBUST for mutexes in shared memory.
  • Handle EOWNERDEAD from pthread_mutex_lock: repair shared state, call pthread_mutex_consistent.
  • Monitor /dev/shm usage (df -h /dev/shm) — shared memory consumes RAM+swap.
  • Design startup cleanup: unlink stale objects, re-create with known initial state.
