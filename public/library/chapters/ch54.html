    TOPIC 54 / 64 · POSIX Shared Memory

    Shared storage needs a bootstrap protocol

    A consumer opens a newly named shared-memory object before the creator has sized it.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    shm_open creates or opens an object that can be mapped with mmap. A new object begins with size zero. Naming, sizing, mapping, initialization, and publishing readiness are separate transitions. Shared bytes do not tell a late consumer whether initialization completed successfully.

    Contract and implementation boundary

    The creator uses ftruncate before accessing the intended mapping extent. MAP_SHARED makes updates shared, but application synchronization is still required. close can release the descriptor after mapping; munmap and shm_unlink address separate lifetimes. Use a versioned layout and reject incompatible attachments.

    Contract references: shm_open.3 · ftruncate.2 · mmap.2. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    Opening a name is not proof that a mutex embedded in the region is initialized. Using ordinary process-private pthread synchronization inside shared storage does not establish process-shared semantics. Never resize underneath readers without a coordinated protocol.

    Worked reasoning trace

    Assumptions: New shm_open with exclusive creation succeeds.

    1. Starting state

      Object length is zero.

    2. Operation

      Creator sizes, maps, initializes, then publishes readiness on a separate channel.

    3. Expected observation

      Consumer attaches only after the bootstrap signal and validates layout version.

    Tradeoff: Explicit bootstrap avoids torn initialization but adds recovery states.

    This is a hand-authored prediction, not captured runtime output.

    Original practice problem

    Design states absent, created, sized, initialized, ready, closing. Choose a separate bootstrap channel that publishes readiness only after all shared synchronization objects are usable. Explain how a crashed creator is distinguished from a slow one.
