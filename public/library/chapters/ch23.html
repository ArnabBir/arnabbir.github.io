Chapter 23 — Timers and Sleeping

Timers and sleeping are signal-adjacent — interval timers deliver SIGALRM, POSIX timers offer flexible notification, and timerfd integrates deadline-driven logic into event loops.

The evolution of Linux timer APIs reflects a shift from signal-based notification (setitimer, alarm) toward fd-based integration (timerfd). Modern servers should use timerfd_create with epoll for periodic tasks and timeouts, reserving POSIX timer_create for cases requiring thread notification or overrun counting.

Invariant
clock_nanosleep with TIMER_ABSTIME avoids cumulative drift in periodic tasks.
Gotcha
nanosleep is interrupted by signals (EINTR); the remaining time output may have rounding errors.
Best practice
Use timerfd_create + epoll for server timeouts; avoids signals and integrates with the event loop.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • setitimer delivers SIGALRM (ITIMER_REAL), SIGVTALRM (ITIMER_VIRTUAL), or SIGPROF (ITIMER_PROF) at intervals. It is deprecated — only one timer per type per process.
  • POSIX timer_create + timer_settime offers: choice of clock (CLOCK_MONOTONIC recommended), signal OR thread notification (via sigevent), and overrun counting (timer_getoverrun).
  • nanosleep suspends the calling thread; if interrupted by a signal, it returns -1/EINTR and writes remaining time to the second argument.
  • clock_nanosleep with TIMER_ABSTIME sleeps until an absolute deadline, avoiding cumulative drift from repeated relative sleeps.
  • timerfd_create returns a file descriptor that becomes readable when the timer expires; integrates directly with epoll/poll (best for servers).
  • Sleep granularity depends on kernel CONFIG_HZ (typically 1ms on modern kernels) and timer slack (kernel may delay wakeup to batch interrupts for power savings).

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
nanosleep + EINTR + remaining time
  • When nanosleep is interrupted by a signal, it returns -1 with errno=EINTR and writes the remaining time to the rem argument.
  • The remaining time may be slightly rounded (kernel tick granularity); do not assume exact precision.
  • A naive retry loop using rem accumulates rounding error. For precision, use clock_nanosleep with TIMER_ABSTIME instead.
  • If rem is NULL and EINTR occurs, you lose track of how much sleep remains.
Timer overruns (timer_getoverrun)
  • If a POSIX timer expires multiple times before the signal is delivered (e.g., handler was blocked), overruns accumulate.
  • timer_getoverrun() returns the overrun count for the most recent signal delivery; it does NOT accumulate across multiple deliveries.
  • For timerfd, reading the fd returns the total overrun count as a uint64_t; this is simpler and more reliable.
  • Overruns indicate the application cannot keep up with the timer rate; consider increasing the interval or shedding load.
timerfd and TFD_TIMER_CANCEL_ON_SET
  • If using CLOCK_REALTIME with timerfd, an NTP or admin clock adjustment can silently shift your deadline.
  • TFD_TIMER_CANCEL_ON_SET causes the timerfd to return an error (readable with an ECANCELED-like indication) when the clock is discontinuously set.
  • This allows the application to detect the clock change and recalculate deadlines rather than firing at the wrong time.
  • Best practice: use CLOCK_MONOTONIC for interval timers to avoid this class of issues entirely.
Absolute vs relative timers and clock discontinuities
  • Relative timers (default): "fire in 5 seconds". Safe with CLOCK_MONOTONIC but drift if used in a retry loop.
  • Absolute timers (TIMER_ABSTIME / TFD_TIMER_ABSTIME): "fire at time T". No drift, but vulnerable to clock adjustments on CLOCK_REALTIME.
  • For periodic tasks: compute next absolute deadline on CLOCK_MONOTONIC, arm with TIMER_ABSTIME. This gives both drift-free operation and immunity to wall-clock changes.
  • sleep()/usleep() are POSIX wrappers with coarser guarantees; prefer clock_nanosleep for production code.

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// timerfd_create + epoll for periodic tasks
#include <sys/timerfd.h>
#include <sys/epoll.h>
#include <stdint.h>
#include <unistd.h>

void periodic_loop(int interval_ms) {
    int tfd = timerfd_create(CLOCK_MONOTONIC, TFD_NONBLOCK | TFD_CLOEXEC);
    struct itimerspec its = {
        .it_interval = { interval_ms / 1000, (interval_ms % 1000) * 1000000L },
        .it_value    = { interval_ms / 1000, (interval_ms % 1000) * 1000000L }
    };
    timerfd_settime(tfd, 0, &its, NULL);

    int epfd = epoll_create1(EPOLL_CLOEXEC);
    struct epoll_event ev = { .events = EPOLLIN, .data.fd = tfd };
    epoll_ctl(epfd, EPOLL_CTL_ADD, tfd, &ev);

    for (;;) {
        struct epoll_event events[4];
        int n = epoll_wait(epfd, events, 4, -1);
        for (int i = 0; i < n; i++) {
            uint64_t expirations;
            read(events[i].data.fd, &expirations, sizeof(expirations));
            // expirations > 1 means we missed ticks (overrun)
            do_periodic_work();
        }
    }
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Use CLOCK_MONOTONIC for all interval and timeout timers; reserve CLOCK_REALTIME for wall-clock display only.
  • Prefer timerfd for event-loop servers; it avoids signal handler complexity and integrates with epoll.
  • Use TIMER_ABSTIME / TFD_TIMER_ABSTIME for periodic tasks to eliminate cumulative drift.
  • Always handle EINTR from nanosleep/clock_nanosleep; recompute remaining time from a deadline, not from the rem output.
  • Monitor overrun counts (timerfd read value or timer_getoverrun); sustained overruns indicate capacity problems.
