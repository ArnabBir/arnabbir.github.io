    TOPIC 23 / 64 · Timers and Sleeping

    Timers schedule eligibility, not precision

    A periodic task drifts farther behind after each interrupted sleep.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    A timer expiration makes work eligible; scheduler delays still affect when user code runs. Repeated relative sleeps include the duration of previous work and interruptions, causing drift. Absolute deadlines preserve the intended phase, but missed periods still require an application policy.

    Contract and implementation boundary

    clock_nanosleep with TIMER_ABSTIME can retry the same deadline after EINTR and returns an error number directly. timerfd exposes expiration counts through an eight-byte read on Linux. A count greater than one reports accumulated expirations, not repeated executions of your task.

    Contract references: clock_nanosleep.2 · timerfd_create.2. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    Calling the body once for every missed interval can create an unbounded catch-up storm. Skipping missed work may be better for telemetry but wrong for accounting. State the policy before choosing the loop.

    Worked reasoning trace

    Assumptions: Monotonic absolute deadline; clock_nanosleep interrupted before the target.

    1. Starting state

      Target is 5.000 seconds in the clock domain.

    2. Operation

    3. Expected observation

    Tradeoff: Fixed phase avoids drift but needs a missed-period policy.

    Original practice problem

    Run timers.c for one short monotonic timerfd expiration. Extend it to three bounded periodic reads and add deliberately slow work in a local variant to inspect accumulated expiration counts. Do not assert an exact wakeup time or use a real-time scheduling policy.
