Chapter 35 — Process Priorities and Scheduling

The Linux scheduler determines which process runs when. Nice values provide hints for timesharing; real-time policies guarantee strict priority ordering.

Understanding scheduling is essential for latency-sensitive applications, real-time systems, and diagnosing performance anomalies where CPU time is unfairly distributed among competing tasks.

Invariant
CFS approximates ideal fairness using virtual runtime; higher-weight tasks accumulate vruntime slower and thus run more.
Gotcha
SCHED_FIFO tasks at high priority can starve the entire system — including the shell you need to fix it.
Debugging
Use chrt -p <pid> to inspect scheduling policy; schedtool or /proc/<pid>/sched for runtime stats.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • CFS (Completely Fair Scheduler) tracks virtual runtime (vruntime) per task; the task with lowest vruntime runs next.
  • Nice value (-20 to +19) adjusts task weight: nice -20 gets ~88x more CPU share than nice +19 under full contention.
  • Nice values only matter under CPU contention — an idle system runs everything instantly regardless of nice.
  • Real-time policies (SCHED_FIFO, SCHED_RR) preempt all normal (SCHED_OTHER) tasks unconditionally.
  • SCHED_FIFO: runs until it blocks or yields; SCHED_RR: same but with a time quantum for round-robin among equal-priority RT tasks.
  • SCHED_DEADLINE: earliest-deadline-first scheduling for periodic tasks with declared runtime/deadline/period.
  • CPU affinity (sched_setaffinity) pins a task to specific CPUs — useful for cache locality and NUMA optimization.
  • Priority inversion: a high-priority RT task blocked on a mutex held by a low-priority task; solved by priority inheritance (PI mutexes).

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
Nice values and CFS weight
  • Nice differences are multiplicative, not additive: each nice level is roughly 1.25x weight difference. Nice 0 vs nice 1 = ~10% less CPU.
  • getpriority() can legitimately return -1 (nice = -1). Always clear errno before calling and check errno after.
  • RLIMIT_NICE (since Linux 2.6.12) allows unprivileged users to set nice values down to a configured floor without CAP_SYS_NICE.
  • In a cgroup with cpu.shares, nice values only affect distribution within that cgroup — not across cgroups.
Real-time scheduling hazards
  • A SCHED_FIFO task at priority 99 that never blocks will starve all other tasks, including the login shell.
  • Linux has RT throttling: /proc/sys/kernel/sched_rt_runtime_us (default 950000) limits RT tasks to 95% of each period (1s).
  • Setting sched_rt_runtime_us to -1 disables throttling — dangerous in production; do this only in hard-RT environments.
  • Priority inversion: use PTHREAD_PRIO_INHERIT (PI mutexes) so the low-priority lock holder temporarily inherits the waiter's priority.
  • RT priorities are per-CPU: a priority-50 task on CPU 0 does not preempt a priority-40 task on CPU 1.
CPU affinity and NUMA
  • sched_setaffinity sets a "hard" mask, but cpuset cgroups can further restrict it. The effective mask is the intersection.
  • On NUMA systems, pinning to remote CPUs means memory accesses cross the interconnect — higher latency, lower bandwidth.
  • The scheduler's load balancer respects affinity masks; overly restrictive masks prevent balancing and can cause hotspots.
  • Use numactl --cpunodebind / --membind for combined CPU+memory NUMA pinning in production.
Debugging scheduling issues
  • chrt -p <pid> shows current policy and priority. chrt -f -p 50 <pid> sets SCHED_FIFO priority 50.
  • /proc/<pid>/sched shows nr_switches, wait_sum, exec_runtime — useful for detecting scheduling starvation.
  • perf sched record/latency reveals scheduler wake-up latency and preemption delays.
  • For tail-latency issues, check if the task is being migrated across CPUs (context_switches in /proc/<pid>/status).

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// Set real-time SCHED_FIFO priority and CPU affinity
#include <sched.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

void set_realtime_affinity(int cpu, int priority) {
    // Set SCHED_FIFO with given priority (1-99)
    struct sched_param sp;
    memset(&sp, 0, sizeof(sp));
    sp.sched_priority = priority;
    if (sched_setscheduler(0, SCHED_FIFO, &sp) == -1) {
        perror("sched_setscheduler");
        return;
    }

    // Pin to a specific CPU
    cpu_set_t mask;
    CPU_ZERO(&mask);
    CPU_SET(cpu, &mask);
    if (sched_setaffinity(0, sizeof(mask), &mask) == -1) {
        perror("sched_setaffinity");
    }
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Never deploy SCHED_FIFO/RR without RT throttling enabled (sched_rt_runtime_us > 0) unless you have hardware watchdogs.
  • Use PI mutexes (PTHREAD_PRIO_INHERIT) whenever RT tasks share locks with normal tasks.
  • Prefer cgroup cpu.shares or cpu.max for workload isolation over per-process nice tuning.
  • On NUMA systems, co-locate CPU affinity with memory allocation (numactl or set_mempolicy).
  • Measure scheduling latency under load (cyclictest, perf sched) before claiming real-time guarantees.
