    TOPIC 35 / 64 · Process Priorities and Scheduling

    Scheduling promises and weighted shares

    A team expects nice 10 to mean exactly ten percent CPU.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    Nice values influence relative weights for ordinary scheduling, not fixed CPU percentages. Under simplified equal-group, one-CPU contention, Linux nice 0 has weight 1024 and nice 5 has weight 335, yielding roughly 75% versus 25% between those two continuously runnable tasks. Cgroups, affinity, sleeping, and load balancing change real outcomes.

    Contract and implementation boundary

    Linux began replacing CFS task selection with EEVDF in kernel 6.6. EEVDF uses eligibility and virtual deadlines rather than a promise that the smallest raw runtime always runs next. Real-time policies have different rules and can starve ordinary work if misused. getpriority needs errno disambiguation for a valid -1 result.

    Contract references: sched.7 · getpriority.2 · Kernel EEVDF design. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    A browser weight calculator is not a scheduler emulator. Ratios between nice levels are approximately multiplicative, not a linear subtraction from 100%. Kernel-version-specific details should not be presented as timeless POSIX requirements.

    Tradeoff: Weights express relative preference, not absolute CPU reservations.

    Original practice problem

    Compute 1024/(1024+335) and identify every assumption needed to interpret it as a share. Compare the historical CFS documentation with current EEVDF documentation. Do not run unbounded real-time loops as a lab.
