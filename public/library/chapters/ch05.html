Chapter 05 — File I/O: Further Details

Chapter 4 introduced the basic I/O syscalls. This chapter digs into what happens when file descriptors are *shared* — via dup(), dup2(), or fork() — and the kernel objects that make sharing work. The key abstraction is the three-level model: fd → open file description (OFD) → inode. Understanding which level owns the offset vs. the flags is the difference between correct concurrent I/O and silent data corruption.

We also cover fcntl() (the Swiss Army knife of fd manipulation), positional I/O with pread/pwrite, the atomicity guarantees of O_APPEND, temporary file creation (mkstemp, O_TMPFILE), and the /dev/fd virtual directory. These are the tools that let you build robust I/O redirection, safe temp files, and correct multithreaded file access.

Invariant
dup() creates a new fd pointing to the same OFD — they share offset and status flags.
Gotcha
After fork(), parent and child share OFDs; uncoordinated writes interleave bytes.
Debugging
Use /proc/PID/fd and /proc/PID/fdinfo to inspect live fd→OFD mappings.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • fd → OFD → inode: dup() creates a new fd pointing to the *same* OFD; a separate open() creates a *new* OFD pointing to the same inode. This is why dup'd fds share offset but independently opened fds do not.
  • O_APPEND atomically seeks to EOF before each write — the kernel holds the inode lock across the seek+write, so concurrent appenders never overwrite each other (on local filesystems).
  • fcntl() is the Swiss Army knife of fd control: F_DUPFD for dup-with-minimum-fd, F_GETFL/F_SETFL for reading/changing status flags, F_SETFD for setting FD_CLOEXEC on individual descriptors.
  • File *status* flags (O_APPEND, O_NONBLOCK, O_SYNC) live on the OFD and are shared by all fds pointing to it. File *descriptor* flags (FD_CLOEXEC) live on the fd itself and are per-fd even after dup.
  • pread()/pwrite() bypass the shared offset entirely — they take an explicit offset argument and leave the OFD offset unchanged. This makes them essential for multithreaded file access.
  • Temporary files: mkstemp() atomically creates and opens a unique file (no TOCTOU race). O_TMPFILE (Linux 3.11+) creates an unnamed inode with no directory entry — link it later with linkat() for atomic publish, or let it vanish on close.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
dup() vs open() sharing semantics
  • dup(fd) creates a new fd that shares the *same* OFD: same offset, same status flags. A write on one fd advances the offset seen by the other.
  • Two separate open() calls on the same file create *independent* OFDs: each has its own offset and flags. Writes can silently overwrite each other unless O_APPEND is used.
  • Implication for log files: if two processes must append without overwriting, they must each open() with O_APPEND — sharing via dup/fork is not enough if they lseek independently.
  • After dup2(oldfd, STDOUT_FILENO), writes to stdout go to the same OFD as oldfd. This is the classic I/O redirection pattern before exec.
O_APPEND atomicity guarantees
  • O_APPEND causes write() to atomically seek to EOF and write. The kernel holds the inode mutex across both operations, preventing interleaving on local filesystems.
  • NFS may break O_APPEND atomicity: some NFS implementations do not honor atomic append, leading to overwrites in concurrent-append workloads. Test your NFS version.
  • O_APPEND vs pwrite: pwrite ignores O_APPEND — it always writes at the specified offset. This is POSIX-specified behavior and catches people off guard.
  • O_APPEND does not prevent reads from any offset; it only affects the write path. lseek + read still works normally on an O_APPEND fd.
fcntl pitfalls
  • F_SETFL can change O_APPEND, O_NONBLOCK, O_ASYNC, etc. — but it *cannot* change the access mode (O_RDONLY/O_WRONLY/O_RDWR). Those are fixed at open() time.
  • F_DUPFD_CLOEXEC (Linux 2.6.24+) atomically duplicates with CLOEXEC, avoiding the race between fcntl(F_DUPFD) + fcntl(F_SETFD, FD_CLOEXEC). Prefer dup3() when the target fd is known.
  • Race window: if you set FD_CLOEXEC via fcntl(F_SETFD) after open/dup, another thread could fork+exec between the two calls, leaking the fd. Always prefer O_CLOEXEC at creation time.
  • F_GETFL returns status flags *and* access mode bits. Mask with O_ACCMODE to extract just the access mode.
Temporary file security
  • mktemp() is dangerous: it returns a name but does not open the file, creating a TOCTOU race. An attacker can create a symlink at that path between mktemp and open. Never use it.
  • mkstemp() atomically creates and opens the file with mode 0600. Immediately unlink() the path if you only need the fd — this gives you an anonymous temp file that disappears on close.
  • O_TMPFILE (Linux 3.11+) creates an inode with no directory entry at all. For atomic publish: write contents, fsync, then linkat(AT_EMPTY_PATH) to give it a name. If you crash before linkat, nothing is visible.
  • tmpfile() (libc) calls mkstemp + unlink under the hood but returns a FILE*. Useful for stdio-based temp usage but less control than mkstemp.

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
/* dup2 for I/O redirection before exec */
int log_fd = open("output.log", O_WRONLY|O_CREAT|O_TRUNC|O_CLOEXEC, 0644);
if (log_fd == -1) { perror("open"); exit(1); }
if (dup2(log_fd, STDOUT_FILENO) == -1) { perror("dup2"); exit(1); }
close(log_fd);  /* stdout now points to the OFD; log_fd is redundant */
execlp("make", "make", "-j4", (char *)NULL);

/* pread: concurrent access without shared-offset races */
ssize_t read_chunk(int fd, off_t off, void *buf, size_t len) {
    ssize_t n;
    do { n = pread(fd, buf, len, off); } while (n == -1 && errno == EINTR);
    return n;  /* offset in OFD is unchanged */
}

/* mkstemp: safe temporary file pattern */
char tpl[] = "/tmp/myapp-XXXXXX";
int tmp_fd = mkstemp(tpl);       /* tpl is modified in place */
if (tmp_fd == -1) { perror("mkstemp"); exit(1); }
unlink(tpl);                      /* anonymous: gone when fd closes */
write(tmp_fd, "secret data\n", 12);
/* use tmp_fd ... */
close(tmp_fd);                    /* file disappears from disk */

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Set O_CLOEXEC at creation time (open, dup3, pipe2, accept4) — never rely on a separate fcntl(F_SETFD) due to the fork+exec race window.
  • After fork(), coordinate or close shared fds immediately. Uncoordinated writes to a shared OFD will interleave and corrupt output.
  • Use pread/pwrite for any multithreaded file access to avoid offset races on the shared OFD.
  • Create temp files with mkstemp() + unlink() or O_TMPFILE. Never use mktemp() or predictable names in /tmp.
  • Audit dup2() call sites: the target fd is silently closed first — ensure no other thread is using that fd number concurrently.

Exercises

Hands-on tasks to make the chapter "stick". These are intentionally practical and debugging-heavy.
  • Write a program that uses dup2() to redirect stdout to a file, then execs a child. Verify the child's output lands in the file. Extend it to redirect both stdout and stderr to the same file.
  • Fork a process after opening a file. Have both parent and child write 1000 lines each without O_APPEND, then repeat with O_APPEND. Diff the output files and explain why the non-append version has corrupted/overwritten lines.
  • Open a large file and spawn two pthreads that each read different regions using pread(). Verify they get correct data and the file offset (lseek SEEK_CUR) is unchanged after both threads finish.
