    TOPIC 5 / 64 · File I/O: Further Details

    Descriptor flags and shared offsets

    Two workers each write two bytes through duplicated descriptors. Will one overwrite the other?

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    dup creates another descriptor pointing to the same open file description. Offset and O_APPEND/O_NONBLOCK status belong to that shared description. FD_CLOEXEC belongs to each descriptor entry. A separate open of the same file creates a different description with an independent offset.

    Contract and implementation boundary

    dup clears close-on-exec on the new descriptor. dup3 with O_CLOEXEC requests it atomically. dup2 atomically replaces a target and, when both arguments are identical and valid, does nothing. pread and pwrite specify an offset without advancing the shared one; Linux pwrite with O_APPEND has a documented append caveat.

    Contract references: dup.2 · open.2 · pread.2. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    For successful serialized writes through a shared description at offset zero, writing AB then CD yields ABCD, not CD overwriting AB. Concurrent order can vary; shared-offset atomicity is not a multi-call transaction. Two independent opens starting at zero can overwrite instead.

    Worked reasoning trace

    Assumptions: Empty regular file; serialized successful calls.

    1. Starting state

      fd 3 has CLOEXEC and offset zero.

    2. Operation

      dup creates fd 4; write AB on 3 then CD on 4.

    3. Expected observation

      Bytes are ABCD; offset is four; fd 4 has CLOEXEC cleared.

    Tradeoff: dup shares position; use a fresh open or positional I/O for independent position.
