Chapter 16 — Extended Attributes

Extended attributes add arbitrary key-value metadata to files beyond traditional inode fields — used for SELinux labels, file capabilities, and custom application metadata. Each xattr is a namespace-prefixed key (e.g., "user.mime_type") with an opaque byte-string value.

The four namespaces (user, security, system, trusted) have different access rules. user.* xattrs are freely readable/writable by the file owner; security.* requires CAP_SYS_ADMIN and is used by SELinux/AppArmor; system.* stores POSIX ACLs; trusted.* requires CAP_SYS_ADMIN and is invisible to unprivileged users.

Invariant
Xattr operations are atomic per attribute; each xattr is independently set/get/removed without affecting others.
Gotcha
Not all filesystems support xattrs (e.g., FAT, old NFS); always handle ENOTSUP gracefully.
Debugging
Use getfattr -d -m '.*' to dump all xattrs including security namespace; strace setxattr/getxattr calls.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • Xattrs are namespace-prefixed key-value pairs stored alongside the inode (often in inode spare space or a dedicated block).
  • user.* namespace: accessible to file owner for read/write; only works on regular files and directories (not symlinks/devices on most FS).
  • security.* namespace: used by SELinux (security.selinux), AppArmor, and file capabilities (security.capability). Requires CAP_SYS_ADMIN to set.
  • system.* namespace: used internally for POSIX ACLs (system.posix_acl_access, system.posix_acl_default). Managed via ACL APIs.
  • trusted.* namespace: requires CAP_SYS_ADMIN for both read and write; invisible to unprivileged processes.
  • Size limits: typically ~64KB per value (ext4), but filesystem-dependent. Total xattr space per inode is also limited.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
Filesystem support varies
  • ext4, XFS, Btrfs: full xattr support. FAT/VFAT: no xattr support at all (ENOTSUP).
  • NFS: xattr support depends on server filesystem and NFS version (NFSv4 with server support).
  • tmpfs: supports xattrs but they consume memory; no persistence across reboot.
  • Always handle ENOTSUP gracefully — your code may run on a filesystem without xattr support.
Size limits and storage
  • ext4: max value size ~64KB; total xattr space per inode limited (one block, typically 4KB, unless large EA inode feature).
  • XFS: attribute values up to 64KB; stored inline in inode or in separate extents for large values.
  • Btrfs: xattrs stored as regular tree items; practical limit per value is 64KB.
  • ENOSPC from setxattr can mean the xattr storage area (not the filesystem) is full.
Security implications
  • SELinux labels (security.selinux) are critical for MAC enforcement; incorrect labels break access.
  • File capabilities (security.capability) grant specific privileges without full setuid-root — verify with getcap.
  • Backup/restore tools may not preserve security.* xattrs unless run as root with --xattrs flag.
  • Container images must preserve xattrs; tar --xattrs --xattrs-include='*' is needed.
Backup and preservation
  • cp by default does NOT copy xattrs; use cp --preserve=xattr or cp -a (which includes xattr).
  • rsync requires -X (--xattrs) flag to transfer extended attributes.
  • tar: use --xattrs to store and --xattrs-include='*' to restore all namespaces.
  • Some network transfers (scp, sftp) do not preserve xattrs at all.

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// Set a user xattr
const char *val = "application/json";
if (setxattr("data.json", "user.mime_type", val, strlen(val), 0) == -1) {
    if (errno == ENOTSUP) fprintf(stderr, "xattrs not supported\n");
    else perror("setxattr");
}

// Get xattr (query size first, then read)
ssize_t len = getxattr("data.json", "user.mime_type", NULL, 0);
if (len > 0) {
    char *buf = malloc(len + 1);
    getxattr("data.json", "user.mime_type", buf, len);
    buf[len] = '\0';
    printf("mime: %s\n", buf);
    free(buf);
}

// List all xattrs on a file
char list[1024];
ssize_t llen = listxattr("data.json", list, sizeof(list));
for (char *p = list; p < list + llen; p += strlen(p) + 1)
    printf("  %s\n", p);

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Always handle ENOTSUP — not all filesystems or mount configurations support xattrs.
  • Use the two-call pattern (size query then read) to avoid buffer overflows with getxattr/listxattr.
  • Verify backup/restore pipelines preserve xattrs (test with getfattr before and after).
  • For SELinux environments: restorecon after file operations that may lose security context.
  • Be aware of xattr size limits per-value and per-inode; don't use xattrs as a general-purpose database.
