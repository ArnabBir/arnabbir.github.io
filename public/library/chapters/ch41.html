    TOPIC 41 / 64 · Fundamentals of Shared Libraries

    Shared objects and ABI boundaries

    A library update links successfully but crashes an old application.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    A shared library supplies code and data through an application binary interface: symbol names, calling conventions, object layouts, and lifecycle rules. Source compatibility does not imply binary compatibility. The static linker records dependencies, and the runtime loader resolves them when the process starts or loads more objects.

    Contract and implementation boundary

    Build position-independent shared objects with the toolchain's supported flags and assign an intentional SONAME for ABI compatibility. Export only the intended interface. The dynamic loader's search rules involve recorded paths, configuration, and environment, with secure-execution restrictions.

    Contract references: ld.so.8 · elf.5. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    Changing a public structure layout can break callers compiled against the old layout even if function names stay unchanged. Relying on the current working directory for library lookup is fragile and potentially unsafe.

    Worked reasoning trace

    Assumptions: Old caller compiled against a public struct with two fields.

    1. Starting state

      New library inserts a field before the second one.

    2. Operation

      Caller and library use different offsets for the same member.

    3. Expected observation

      Symbol lookup can succeed while binary behavior is broken.

    Tradeoff: Opaque handles limit layout coupling at the cost of accessor calls.

    This is a hand-authored prediction, not captured runtime output.

    Original practice problem

    Design a library API around an opaque handle and explicit create/destroy functions. Compare that with exporting the whole structure. Inspect dependency and symbol tables of a local binary using readelf rather than executing an untrusted binary with diagnostic tooling.

    Check your understanding

    Does preserving exported function names alone guarantee ABI compatibility?

    Explain the answer

    No. Calling conventions, layouts, semantics, and ownership also form the ABI.
