    TOPIC 22 / 64 · Signals: Advanced Features

    Accepting signals synchronously

    A multithreaded server needs one place to handle shutdown signals.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    Blocking a chosen set before creating threads causes those threads to inherit the mask. A dedicated waiter can then accept signals synchronously, where ordinary control flow is easier to reason about than asynchronous handlers. Linux signalfd integrates selected blocked signals with descriptor-based event loops.

    Contract and implementation boundary

    sigwait returns an error number directly, while sigwaitinfo returns a signal number or -1. Ensure the selected signals remain blocked in every thread that could otherwise receive them. Real-time queueing is bounded by resource policy; sigqueue can fail rather than queue forever.

    Contract references: sigwait.3 · sigwaitinfo.2 · signalfd.2. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    Creating workers before setting their inherited mask leaves a delivery window. Passing a pointer as a real-time signal value does not make that address meaningful in another process's address space.

    Worked reasoning trace

    Assumptions: Shutdown set is blocked before pthread_create.

    1. Starting state

      The main thread establishes the mask.

    2. Operation

      Workers inherit it; one dedicated thread calls sigwait.

    3. Expected observation

      Shutdown can be handled in ordinary thread control flow.

    Tradeoff: A waiter simplifies handlers but adds lifecycle coordination.

    This is a hand-authored prediction, not captured runtime output.

    Original practice problem

    Design a two-thread shutdown path: main blocks the set, creates a waiter and worker, waiter requests cooperative stop, main joins both. Include the case of repeated standard shutdown signals without assuming one event per send.
