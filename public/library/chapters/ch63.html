Chapter 63 — Alternative I/O Models

Blocking I/O is simple but doesn't scale: one thread per connection collapses under load. This chapter traces the evolution from select() (O(N) per call, FD_SETSIZE limit) through poll() (no bitmap limit, still O(N)) to epoll (kernel-maintained interest list, O(k) ready-set return). It then covers the critical distinction between level-triggered semantics (report readiness as long as data exists) and edge-triggered semantics (report only on *new* activity, requiring nonblocking drain loops). Finally, it introduces the unified event-loop philosophy — signalfd, timerfd, eventfd fold signals, timers, and inter-thread notifications into a single epoll fd — and previews io_uring's submission/completion queue model that eliminates syscall overhead entirely.

Invariant
epoll_wait returns only the ready fds (O(k)), not the entire monitored set (O(N)) — this is the fundamental scaling advantage over select/poll.
Gotcha
Edge-triggered (EPOLLET) requires draining until EAGAIN; missing this causes silent stalls — the fd has pending data but epoll never reports it again.
Debugging
Use /proc/PID/fdinfo/N on an epoll fd to inspect the interest list entries, registered events, and associated target fds.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world event-loop incidents.
  • select/poll copy the entire fd set to the kernel and scan ALL fds each call → O(N) per wakeup even if only k fds are ready. epoll maintains a kernel-side interest list (red-black tree) and returns only the ready set via a linked list → O(k) per epoll_wait return.
  • Level-triggered (default): epoll_wait reports an fd as ready as long as data remains available. Safe and forgiving — you can read partial data and epoll will remind you — but can cause redundant wakeups under high throughput.
  • Edge-triggered (EPOLLET): epoll_wait reports an fd as ready only when NEW activity occurs (e.g., new data arrives). You must drain with nonblocking reads in a loop until EAGAIN; failing to drain means the fd goes silent with unread data still in the buffer.
  • EPOLLONESHOT: disarms the fd after delivering one event. Essential for thread-safe dispatch — prevents two threads from handling the same fd simultaneously. After processing, re-arm with epoll_ctl(EPOLL_CTL_MOD).
  • Thundering herd: multiple threads/processes blocked in epoll_wait on the same epoll fd all wake on one event. EPOLLEXCLUSIVE (Linux 4.5+) limits wakeup to one waiter. SO_REUSEPORT with separate epoll instances is an alternative that also provides load balancing.
  • signalfd, timerfd, and eventfd convert signals, timers, and cross-thread notifications into file descriptors that can be monitored in the same epoll loop — eliminating the need for signal handlers, alarm-based timers, or pipe-based wakeup hacks.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
Edge-triggered draining pitfalls
  • With EPOLLET, you must read() in a loop until it returns -1 with EAGAIN. A single read() that returns fewer bytes than requested does NOT mean the buffer is empty — another segment may have arrived between the kernel check and the copy.
  • Partial drain is the #1 epoll bug: the fd has pending data, but epoll never fires again because no *new* event occurred. The connection appears hung.
  • EPOLLOUT with edge-triggered: after getting EAGAIN from write(), register EPOLLOUT. When it fires, write what you can, then remove EPOLLOUT interest if the buffer is fully flushed — otherwise you spin on writable notifications.
  • Combine EPOLLET with EPOLLONESHOT for maximum safety: you get exactly one event, process it fully, then re-arm. This is the recommended pattern for multi-threaded servers.
Thundering herd and EPOLLEXCLUSIVE
  • When multiple threads call epoll_wait on the same epoll fd, a single incoming connection wakes ALL of them. Only one succeeds at accept(); the rest get EAGAIN and wasted context switches.
  • EPOLLEXCLUSIVE (Linux 4.5+) ensures only one waiter is woken per event. Add it to the listen socket's EPOLLIN mask.
  • SO_REUSEPORT is an alternative: each thread gets its own listen socket and epoll instance. The kernel distributes connections across sockets. This also avoids lock contention on the accept queue.
  • Accept storms: even with EPOLLEXCLUSIVE, a burst of connections can cause contention. Drain the accept queue (loop accept until EAGAIN) to amortize wakeup cost.
epoll and fork/exec
  • An epoll fd is a regular fd: it survives fork(). But the interest list is a *kernel object* shared between parent and child (like an open file description). Both processes see the same interest list — adding/removing in one affects the other.
  • If the child closes a monitored fd, the kernel removes that fd from the interest list — which also affects the parent's epoll monitoring. This is a common source of silent bugs after fork().
  • Always use EPOLL_CLOEXEC (or fcntl FD_CLOEXEC) on epoll fds to prevent them from leaking into exec'd children.
  • After fork(), the child should typically create its own epoll instance rather than sharing the parent's. The shared interest list semantic is almost never what you want.
io_uring: the future
  • io_uring (Linux 5.1+) uses two shared ring buffers: the submission queue (SQ) and completion queue (CQ). The application writes submission queue entries (SQEs) and the kernel writes completion queue entries (CQEs) — no syscall per I/O operation.
  • IORING_SETUP_SQPOLL creates a kernel thread that polls the SQ, eliminating io_uring_enter() calls entirely. True zero-syscall I/O for sustained workloads.
  • io_uring supports registered buffers (IORING_REGISTER_BUFFERS) and registered fds (IORING_REGISTER_FILES) to avoid per-operation map/unmap overhead.
  • When to use io_uring vs epoll: io_uring excels at high-throughput storage I/O and when syscall overhead is the bottleneck. For network servers with moderate connection rates, epoll is simpler and well-understood. io_uring's network support is maturing but the API surface is larger and the debugging story is less developed.

Code patterns (C / POSIX)

Edge-triggered epoll event loop: nonblocking accept + read with drain-until-EAGAIN pattern. 
int epfd = epoll_create1(EPOLL_CLOEXEC);
struct epoll_event ev = { .events = EPOLLIN | EPOLLET, .data.fd = listen_fd };
epoll_ctl(epfd, EPOLL_CTL_ADD, listen_fd, &ev);

struct epoll_event ready[MAX_EVENTS];
for (;;) {
  int n = epoll_wait(epfd, ready, MAX_EVENTS, -1);
  if (n < 0) { if (errno == EINTR) continue; break; }
  for (int i = 0; i < n; i++) {
    if (ready[i].data.fd == listen_fd) {
      // Drain accept queue (edge-triggered)
      for (;;) {
        int c = accept4(listen_fd, NULL, NULL, SOCK_NONBLOCK|SOCK_CLOEXEC);
        if (c < 0) { if (errno == EAGAIN) break; continue; }
        ev = (struct epoll_event){ .events = EPOLLIN|EPOLLET, .data.fd = c };
        epoll_ctl(epfd, EPOLL_CTL_ADD, c, &ev);
      }
    } else {
      // Drain read buffer (edge-triggered)
      char buf[4096];
      for (;;) {
        ssize_t nr = read(ready[i].data.fd, buf, sizeof buf);
        if (nr > 0) { write(ready[i].data.fd, buf, nr); continue; } // echo
        if (nr == 0) { close(ready[i].data.fd); break; }             // EOF
        if (errno == EAGAIN) break;                                    // drained
      }
    }
  }
}

Production checklist

If you are shipping an event-loop server, satisfy each item explicitly.
  • Set all fds to O_NONBLOCK before adding to epoll. Blocking fds with edge-triggered epoll will deadlock.
  • Always drain until EAGAIN in edge-triggered mode — for both reads and accepts.
  • Set EPOLL_CLOEXEC on the epoll fd and SOCK_CLOEXEC on accepted sockets to prevent leaks across exec.
  • Implement backpressure: when write() returns EAGAIN, buffer the data, register EPOLLOUT, and remove EPOLLOUT interest once the buffer is flushed. Never busy-loop on write.
  • Use EPOLLONESHOT for multi-threaded dispatch to prevent two threads from handling the same fd simultaneously.
  • Handle EINTR from epoll_wait — it is normal when signals are delivered.
  • Set connection timeouts: use timerfd or epoll_wait timeout to reap idle connections and prevent fd exhaustion.
  • Monitor /proc/sys/fs/file-nr and ulimit -n; epoll scales to millions of fds but the system must have headroom.

Exercises

Hands-on tasks to make the chapter "stick". These are intentionally practical and debugging-heavy.
  • Build a multi-connection echo server using epoll with EPOLLET. Verify correctness by sending messages larger than the socket buffer size — confirm no data is lost by comparing checksums. Intentionally remove the drain loop and observe the stall.
  • Benchmark select vs epoll: create 10,000 idle TCP connections and 10 active ones. Measure CPU usage and latency for both. Graph the results as N increases from 100 to 50,000.
  • Integrate signalfd for clean shutdown: block SIGINT/SIGTERM with sigprocmask, create a signalfd, add it to the epoll loop, and perform graceful connection draining when the signal is received.
