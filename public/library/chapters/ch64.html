Chapter 64 — Pseudoterminals

Pseudo-terminals create virtual terminal pairs — a master side (controlled by the application) and a slave side (looks like a real terminal to the child process). The foundation of SSH, tmux, expect, and terminal recording.

The POSIX API (posix_openpt, grantpt, unlockpt, ptsname) provides portable pty creation, while forkpty() wraps the entire sequence into a single call. Understanding the master/slave data flow is key to building terminal-aware tools.

Invariant
A pty is a bidirectional pipe with a terminal line discipline on the slave side — isatty() returns true for the slave.
Gotcha
The master fd must be kept open — closing it sends EIO to the slave (hangup). Handle this in your relay loop.
Debugging
ls -la /dev/pts/ shows active pty slaves; /proc/<pid>/fd reveals which side a process holds.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • A pty is a master + slave file descriptor pair. The master is held by the controlling application (terminal emulator, sshd, tmux); the slave looks like a real terminal to the child process.
  • posix_openpt(O_RDWR | O_NOCTTY) opens the master side (/dev/ptmx on Linux). This allocates a new pty pair in the kernel.
  • grantpt(master_fd) sets correct ownership and permissions on the corresponding slave device — typically changes owner to the calling user and mode to 0620.
  • unlockpt(master_fd) unlocks the slave side so it can be opened. Without this call, open() on the slave path will fail.
  • ptsname(master_fd) returns the path to the slave device (e.g., /dev/pts/3). The child process opens this path to get its terminal fd.
  • forkpty(&master, NULL, NULL, NULL) combines all the above steps + fork: parent gets master fd, child gets slave as stdin/stdout/stderr with a new session and controlling terminal.
  • Data flow: write to master appears as input on slave (as if the user typed it); write to slave appears as output on master (as if the program printed it). The line discipline sits on the slave side.
  • Applications: sshd proxies remote I/O through a pty (remote user types into master via network); tmux creates one pty per pane; expect scripts interactive programs by driving the master; script(1) records sessions by sitting between user and pty.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
The posix_openpt / grantpt / unlockpt sequence
  • The three calls must be made in order: posix_openpt, then grantpt, then unlockpt. Skipping grantpt may leave the slave inaccessible to the calling user.
  • On Linux, grantpt may internally fork a setuid helper (pt_chown) if the kernel doesn't handle permissions directly via devpts mount options.
  • ptsname returns a pointer to a static buffer — not thread-safe. Use ptsname_r(fd, buf, buflen) in multithreaded programs.
  • After unlockpt, the slave can be opened with open(ptsname(master_fd), O_RDWR). The first open of the slave in a new session makes it the controlling terminal.
forkpty internals and the child setup
  • forkpty() calls setsid() in the child to create a new session, then opens the slave (which becomes the controlling terminal), then dup2's it to stdin/stdout/stderr.
  • The parent receives the master fd and the child PID. The parent must close the slave fd if it was opened separately.
  • If you pass termp/winp to forkpty, those are applied to the slave before exec — useful for setting initial terminal size and modes.
  • On error, forkpty returns -1 and sets errno. Common failures: too many ptys open (EAGAIN/ENFILE) or permission issues.
Master/slave data flow and hangup
  • Closing the master fd causes the slave to see a hangup condition: read() returns EIO, and SIGHUP is sent to the session leader's process group.
  • Closing all slave fds causes read() on the master to return 0 (EOF) — this is how the parent detects child exit in a pty relay loop.
  • The line discipline on the slave processes input: in canonical mode, writes to the master are line-buffered before the slave's read() returns them.
  • Be careful with blocking: if neither side reads, the internal pty buffer (typically 4KB) fills and writes block or return EAGAIN.
Real-world pty applications
  • sshd: for each session, creates a pty pair. Network data from the client is written to the master; the child shell reads from the slave. Shell output goes to slave, read from master, sent over the network.
  • tmux/screen: each pane has its own pty. The tmux server holds the master fds and multiplexes them to the client's terminal. Detach/reattach works because the master stays open.
  • expect: drives interactive programs by writing to the master (simulating user input) and reading from the master (capturing program output). Matches patterns to decide what to "type" next.
  • script(1): interposes a pty between the user and a shell to record everything written to the terminal into a typescript file.

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// forkpty + exec: run a command inside a pty
#include <pty.h>
#include <unistd.h>
#include <stdio.h>
#include <sys/wait.h>

int main(void) {
    int master;
    pid_t pid = forkpty(&master, NULL, NULL, NULL);
    if (pid < 0) { perror("forkpty"); return 1; }

    if (pid == 0) {
        // Child: slave is already stdin/stdout/stderr
        execlp("bash", "bash", "--norc", NULL);
        _exit(127);
    }

    // Parent: relay between our stdin/stdout and master
    char buf[256];
    fd_set rfds;
    for (;;) {
        FD_ZERO(&rfds);
        FD_SET(STDIN_FILENO, &rfds);
        FD_SET(master, &rfds);
        if (select(master + 1, &rfds, NULL, NULL, NULL) < 0) break;
        if (FD_ISSET(master, &rfds)) {
            ssize_t n = read(master, buf, sizeof(buf));
            if (n <= 0) break;          // child exited
            write(STDOUT_FILENO, buf, n);
        }
        if (FD_ISSET(STDIN_FILENO, &rfds)) {
            ssize_t n = read(STDIN_FILENO, buf, sizeof(buf));
            if (n <= 0) break;
            write(master, buf, n);       // send to child
        }
    }
    close(master);
    waitpid(pid, NULL, 0);
    return 0;
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Always call grantpt + unlockpt before accessing the slave — skipping these causes permission errors or undefined behavior.
  • Use forkpty() for simple cases; use the manual sequence (posix_openpt/grantpt/unlockpt/ptsname) when you need fine-grained control over session setup.
  • Handle master close gracefully: read() on slave returns EIO, and the child's session receives SIGHUP.
  • Propagate SIGWINCH (window size change) from the controlling terminal to the pty slave via ioctl(slave_fd, TIOCSWINSZ, &ws).
  • In the relay loop, handle both directions (user-to-master, master-to-stdout) and detect EOF on both sides to avoid zombie processes.
