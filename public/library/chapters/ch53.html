Chapter 53 — POSIX Semaphores

POSIX semaphores come in two flavors — named (persist in the filesystem, for unrelated processes) and unnamed (placed in shared memory, for threads or related processes). Both provide a simpler API than System V semaphore sets.

This chapter covers sem_open for named semaphores, sem_init for unnamed, the wait/post/trywait/timedwait operations, and key differences between the two forms.

Invariant
sem_post is one of the few functions that is async-signal-safe — it can be safely called from a signal handler.
Gotcha
Unnamed semaphores shared between processes must reside in shared memory (MAP_SHARED) with pshared=1. Placing one on the stack or heap and forking does not work.
Debugging
Named semaphores appear as /dev/shm/sem.<name> on Linux. Use sem_getvalue or inspect the file to check the current count.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • Named semaphores: sem_open("/name", O_CREAT, mode, initial_value) creates/opens. sem_close releases the handle. sem_unlink removes the name (refcounted: destroyed when last close).
  • Unnamed semaphores: sem_init(sem, pshared, value) initializes a sem_t in caller-allocated memory. pshared=0 for threads, pshared=1 for processes (must be in shared memory).
  • sem_wait() decrements the counter (P operation). If counter is 0, blocks until another thread/process calls sem_post.
  • sem_post() increments the counter (V operation). Wakes one blocked waiter. Async-signal-safe — can be called from signal handlers.
  • sem_trywait() returns EAGAIN immediately if counter is 0. Non-blocking alternative.
  • sem_timedwait() blocks until the counter becomes positive or the absolute deadline expires (ETIMEDOUT).
  • sem_getvalue() reads the current count. If negative on some implementations, its absolute value indicates the number of waiters (but Linux returns 0 instead of negative).
  • Unnamed semaphores between processes: the sem_t must live in a MAP_SHARED mmap region. Allocating on stack and forking gives each process a private copy.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
Named vs unnamed: when to use which
  • Use named semaphores when unrelated processes need to coordinate and you want filesystem-visible objects.
  • Use unnamed semaphores for threads within a single process (pshared=0) or for related processes sharing a mmap region (pshared=1).
  • Named semaphores have filesystem cleanup overhead (unlink). Unnamed semaphores are destroyed with sem_destroy and the shared memory region.
  • For high-frequency synchronization between threads, unnamed semaphores avoid the overhead of filesystem namespace operations.
Unnamed semaphore placement
  • For inter-process use, the sem_t must be in MAP_SHARED memory (e.g., via shm_open + mmap or mmap(MAP_SHARED|MAP_ANONYMOUS)).
  • Common bug: allocating sem_t on the stack, calling sem_init(..., 1, ...), then forking. Each process gets a private copy — no synchronization occurs.
  • sem_destroy must be called before unmapping the shared memory. Using a destroyed semaphore is undefined behavior.
Signal safety and sem_post
  • sem_post is async-signal-safe. Pattern: signal handler calls sem_post; main loop calls sem_wait to wake up and handle the event.
  • sem_wait is NOT async-signal-safe. Never call it from a signal handler.
  • sem_wait can return EINTR when interrupted by a signal. Always check and retry: while (sem_wait(&s) == -1 && errno == EINTR) continue;
Comparison with System V semaphores
  • System V semaphores operate on sets of semaphores atomically (semop on multiple semaphores). POSIX has one counter per semaphore.
  • System V supports "undo" operations (SEM_UNDO flag) that reverse on process exit. POSIX has no equivalent — a process dying while holding a semaphore leaves it in a decremented state.
  • POSIX semaphores have no built-in deadlock detection or undo. Design your protocol to handle process crashes explicitly.
  • POSIX semaphores are generally faster (futex-based on Linux) than System V semaphores (always a syscall).

Code patterns (C / POSIX)

Unnamed semaphore for producer/consumer in shared memory between two processes. 
/* Shared structure in MAP_SHARED memory */
struct shared {
    sem_t sem_items;     /* counts available items */
    sem_t sem_spaces;    /* counts free slots */
    int   buf[8];
    int   in, out;
};
/* Setup (before fork) */
struct shared *s = mmap(NULL, sizeof(*s),
    PROT_READ|PROT_WRITE, MAP_SHARED|MAP_ANONYMOUS, -1, 0);
sem_init(&s->sem_items,  1, 0);   /* pshared=1, start=0 */
sem_init(&s->sem_spaces, 1, 8);   /* 8 free slots */
s->in = s->out = 0;

if (fork() == 0) {  /* Consumer */
    sem_wait(&s->sem_items);       /* block until item */
    int val = s->buf[s->out % 8];
    s->out++;
    sem_post(&s->sem_spaces);      /* signal free slot */
} else {            /* Producer */
    sem_wait(&s->sem_spaces);      /* block until space */
    s->buf[s->in % 8] = 42;
    s->in++;
    sem_post(&s->sem_items);       /* signal new item */
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Choose named vs unnamed based on process relationship: named for unrelated, unnamed for threads or fork+mmap.
  • For unnamed inter-process semaphores, verify the sem_t is in MAP_SHARED memory with pshared=1.
  • Handle sem_wait EINTR: wrap in a retry loop.
  • Design for process crash: POSIX semaphores have no SEM_UNDO. Use a watchdog or robust mutex protocol if crash recovery matters.
  • Use sem_timedwait with deadlines to avoid indefinite blocking in production code.
