    TOPIC 53 / 64 · POSIX Semaphores

    A semaphore counts permits, not owners

    A consumer posts a permit twice and another worker enters a region that should be full.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    A POSIX semaphore represents an available count. Waiting consumes one permit; posting adds one. Unlike a mutex, it does not require that the posting thread be the thread that waited. This supports producer-consumer coordination but places permit accounting on the application.

    Contract and implementation boundary

    sem_wait can be interrupted and needs a cancellation or retry policy. sem_trywait fails with EAGAIN when no permit is available. An unnamed process-shared semaphore must be placed in shared storage and initialized with a nonzero pshared on a supporting implementation. sem_getvalue is an observation, not a reservation.

    Contract references: sem_overview.7 · sem_wait.3 · sem_init.3. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    Checking sem_getvalue and then entering a critical region races other consumers. Destroying a semaphore while waiters still use it is invalid. Initializing a process-shared semaphore on one process's private stack does not create shared storage.

    Worked reasoning trace

    Assumptions: A ring has four slots and one producer/consumer ownership protocol.

    1. Starting state

      free=4; ready=0.

    2. Operation

      Producer waits free, writes one slot, then posts ready.

    3. Expected observation

      free=3; ready=1, with publication ordered by synchronization.

    Tradeoff: Counters bound capacity; multiple producers also need index coordination.

    This is a hand-authored prediction, not captured runtime output.

    Original practice problem

    For a ring with four slots, start free=4 and ready=0. Trace reserve-free, write-payload, post-ready, wait-ready, read-payload, post-free. Add a separate index-ownership rule for multiple producers and explain why the counters alone are insufficient.

    Check your understanding

    Must sem_post be called only by the thread that previously called sem_wait?

    Explain the answer

    No. Semaphores do not carry mutex-style ownership.
