Chapter 17 — Access Control Lists

ACLs extend the basic user/group/other permission model with fine-grained per-user and per-group entries. Traditional Unix permissions allow only one owner and one group; ACLs let you grant read access to alice, write access to the dev group, and deny access to bob — all on the same file.

POSIX ACLs add complexity through the mask entry (which caps effective permissions of named entries), default ACLs (which propagate to newly created files in a directory), and subtle interactions with chmod. Understanding these mechanics prevents the common surprise where chmod silently truncates your carefully-set ACL permissions.

Invariant
The mask entry defines the maximum permissions for all named user/group entries and the owning group entry.
Gotcha
chmod sets the ACL mask to the group permission bits — silently reducing effective ACL permissions.
Debugging
Use getfacl to inspect ACLs; look for #effective comments showing mask-limited permissions.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • A minimal ACL has exactly three entries (owner, group, other) and is equivalent to traditional Unix permissions.
  • An extended ACL adds named user and/or named group entries, plus a mandatory mask entry.
  • The mask entry limits the effective permissions of all named user entries, named group entries, AND the owning group entry. Only owner and other are unaffected by the mask.
  • Default ACLs on directories are templates: new files/subdirectories created within inherit the default ACL as their access ACL.
  • chmod(path, mode) sets the ACL mask to the group bits of mode — this is why chmod can silently reduce ACL permissions.
  • Permission check algorithm: if process is file owner, use owner entry; else if process matches a named user entry, use that (masked); else if process is in owning group or a named group, use the best match (masked); else use other entry.
Key terms & kernel objects
Term / objectMeaning
ACL_USER_OBJOwner entry — corresponds to traditional owner permission bits. Not affected by mask.
ACL_USERNamed user entry — grants specific permissions to a non-owner user. Limited by mask.
ACL_GROUP_OBJOwning group entry — corresponds to traditional group bits. Limited by mask in extended ACLs.
ACL_GROUPNamed group entry — grants specific permissions to an additional group. Limited by mask.
ACL_MASKMaximum effective permissions for named users, named groups, and owning group. Mapped to chmod group bits.
ACL_OTHEROther/world entry — permissions for everyone else. Not affected by mask.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
chmod truncating ACL mask
  • chmod(path, 0750) sets the ACL mask to r-x — any named entry with write permission loses effective write access.
  • getfacl shows this as "user:alice:rwx #effective:r-x" — the #effective comment reveals mask limitation.
  • This is the most common ACL surprise: "I set ACL to rwx but alice can't write" — check if someone ran chmod.
  • To fix: setfacl -m m::rwx to restore the mask, or use setfacl -m which auto-recalculates mask.
Default ACL inheritance
  • Default ACLs on a directory are applied as the access ACL of newly created files within that directory.
  • For new subdirectories, the default ACL is also inherited as their default ACL (recursive propagation).
  • The umask does NOT affect permissions of files created in a directory with a default ACL — the default ACL completely replaces umask's role.
  • Existing files are NOT affected by changing a directory's default ACL — only future files.
ACL-aware applications
  • cp -a / cp --preserve=all preserves ACLs; plain cp does not.
  • rsync -A (--acls) is needed to transfer ACLs; without it, only traditional permissions are synced.
  • tar does NOT preserve ACLs by default; use star or tar with --acls on supported versions.
  • mv within the same filesystem preserves ACLs (same inode); mv across filesystems may lose them.
Permission check algorithm detail
  • Kernel checks in order: 1) owner match (use owner entry, no mask), 2) named user match (use that entry AND mask), 3) group match (owning or named group, use best entry AND mask), 4) other entry.
  • If a named user entry exists for the process UID but denies access, the check STOPS — group entries are NOT consulted.
  • This means a deny ACL for a specific user is effective even if that user is in a group with broader access.
  • Root (CAP_DAC_OVERRIDE) bypasses all ACL checks for read/write; CAP_DAC_READ_SEARCH for read/execute on directories.

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// Grant user alice (uid 1001) rw access via ACL
// Command-line equivalent: setfacl -m u:alice:rw myfile

#include <sys/acl.h>
acl_t acl = acl_get_file("myfile", ACL_TYPE_ACCESS);
acl_entry_t entry;
acl_create_entry(&acl, &entry);
acl_set_tag_type(entry, ACL_USER);
uid_t uid = 1001;
acl_set_qualifier(entry, &uid);

acl_permset_t perms;
acl_get_permset(entry, &perms);
acl_add_perm(perms, ACL_READ | ACL_WRITE);

acl_calc_mask(&acl);  // recalculate mask
if (acl_valid(acl) == 0)
    acl_set_file("myfile", ACL_TYPE_ACCESS, acl);
acl_free(acl);

// Set default ACL on directory (for inheritance)
// setfacl -d -m u:alice:rwx /shared/
// setfacl -d -m g:dev:rx /shared/

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • After setting ACLs, verify with getfacl and check #effective comments for mask interactions.
  • Avoid running chmod on files with extended ACLs unless you intend to reset the mask.
  • Set default ACLs on shared directories to ensure consistent permissions on new files.
  • Ensure backup/restore tools preserve ACLs: rsync -A, cp --preserve=all, tar --acls.
  • Document ACL usage — they are invisible to ls -l (only shows a "+" indicator); use getfacl for the full picture.
