    TOPIC 42 / 64 · Advanced Features of Shared Libraries

    Runtime loading needs an ownership protocol

    A plugin is unloaded while another thread is still calling one of its functions.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    dlopen adds an object to a runtime linking environment. dlsym resolves a symbol; dlclose releases a loader reference. Application references to functions and objects are a separate lifetime problem. Loader reference counting does not know whether an arbitrary thread retained a function pointer.

    Contract and implementation boundary

    Clear dlerror before dlsym and inspect dlerror afterward because a NULL symbol value alone does not universally identify an error. Choose RTLD_NOW versus RTLD_LAZY and symbol visibility deliberately. Establish a versioned plugin entry point and a stop/join/destroy protocol before closing the handle.

    Contract references: dlopen.3 · dlsym.3 · dlerror.3. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    Calling through a saved pointer after unload can jump into unmapped or reused memory. Passing allocator-owned objects across incompatible runtimes can break deallocation. RTLD_GLOBAL can expose symbols to unrelated later loads and create hidden coupling.

    Worked reasoning trace

    Assumptions: A worker retains a plugin function pointer.

    1. Starting state

      Loader reference count is about to drop to zero.

    2. Operation

      Host first blocks new calls, joins outstanding work, and destroys owned plugin objects.

    3. Expected observation

      Only then can the application safely release its loader reference.

    Tradeoff: Unloading saves resources but greatly complicates pointer lifetimes.

    This is a hand-authored prediction, not captured runtime output.

    Original practice problem

    Specify a plugin ABI with a version, structure size, function table, and host-provided callbacks. Trace shutdown: reject new calls, finish outstanding calls, free plugin objects through the owning API, then close the loader reference.

    Check your understanding

    Can a loader reference count prove that no worker still holds a function pointer?

    Explain the answer

    No. The application must coordinate outstanding calls and pointer lifetimes.

    Only then can the application safely release its loader reference.
