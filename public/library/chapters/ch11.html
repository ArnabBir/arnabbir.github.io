Chapter 11 — System Limits and Options

Portable programs cannot hardcode system limits. The number of open files, the maximum path length, and the page size all vary across systems and even across filesystems on the same host. POSIX defines a three-tier scheme for discovering these limits: compile-time constants in <limits.h>, runtime queries via sysconf() for system-wide limits, and pathconf()/fpathconf() for filesystem-specific limits.

The subtlest challenge is the indeterminate limit: when a limit has no fixed value, sysconf() returns -1 without setting errno. Your code must distinguish this from an error (which also returns -1 but sets errno). Failing to handle indeterminate limits correctly leads to silent buffer overflows or unnecessary failures.

Invariant
sysconf() queries are always safe and never fail for valid _SC_ names—they return the limit or -1 for indeterminate (without setting errno).
Gotcha
Indeterminate means sysconf() returns -1 WITHOUT setting errno. No fixed limit exists. You must provide a sensible fallback default—do not treat this as an error.
Debugging
The getconf command-line tool mirrors sysconf/pathconf. Run getconf PATH_MAX / or getconf OPEN_MAX to quickly check limits without writing code.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • Compile-time limits (#define in <limits.h>) are known at build time but may be conservative minimums. Runtime queries may reveal higher actual limits.
  • sysconf(name) queries system-wide runtime limits. For example, sysconf(_SC_OPEN_MAX) returns the maximum number of open file descriptors per process. This may differ from RLIMIT_NOFILE (which is per-process and adjustable via setrlimit).
  • pathconf(path, name) and fpathconf(fd, name) query filesystem-specific limits. For example, _PC_NAME_MAX gives the maximum filename length on a specific filesystem—255 for ext4, potentially different for NFS or FUSE mounts.
  • Some limits are truly indeterminate. PATH_MAX is the classic example: on procfs, FUSE, and some network filesystems, there is no fixed maximum path length. sysconf/pathconf returns -1 without setting errno.
  • _POSIX_* constants (e.g., _POSIX_OPEN_MAX = 20) are POSIX-mandated minimum guarantees. They are a floor, not a ceiling. Real systems almost always support higher values.
  • OPEN_MAX via sysconf(_SC_OPEN_MAX) reports the system default. The actual per-process limit is controlled by getrlimit(RLIMIT_NOFILE). These can disagree—always check RLIMIT_NOFILE for the authoritative per-process value.
  • Always have a fallback default for indeterminate limits. A common pattern: try pathconf(); if indeterminate, use a reasonable constant (e.g., 4096 for PATH_MAX) and document the assumption.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
PATH_MAX is unreliable
  • PATH_MAX is defined as 4096 on Linux, but this is not a hard guarantee. On procfs (/proc/self/exe), FUSE filesystems, and some NFS configurations, paths can exceed PATH_MAX.
  • pathconf("/", _PC_PATH_MAX) returns the limit for a specific mount point. It may differ from the compile-time PATH_MAX constant.
  • The safest approach: dynamically allocate path buffers using realpath() which allocates when passed NULL, or use readlink() with growing buffers and retry on ENAMETOOLONG.
  • getcwd() with a NULL argument (GNU extension) allocates a buffer of the needed size, sidestepping PATH_MAX entirely.
OPEN_MAX vs RLIMIT_NOFILE
  • sysconf(_SC_OPEN_MAX) returns the system default maximum open file descriptors. This is a starting value, not the current process limit.
  • getrlimit(RLIMIT_NOFILE) returns the actual per-process soft and hard limits. The soft limit is what the kernel enforces; the hard limit is the ceiling for unprivileged setrlimit() calls.
  • These can disagree: a process may have raised RLIMIT_NOFILE beyond the _SC_OPEN_MAX default. Always check getrlimit() for the authoritative per-process limit.
  • In containers, RLIMIT_NOFILE is often set by the runtime (Docker defaults to 1048576). The host _SC_OPEN_MAX may differ.
_POSIX_* as floor, not ceiling
  • _POSIX_OPEN_MAX is 20. This is the minimum that any POSIX-compliant system must support. Linux typically supports 1024 or more by default.
  • _POSIX_NAME_MAX is 14. Real filesystems support 255 (ext4) or more.
  • Never use _POSIX_* constants as buffer sizes or limits in production code. They exist for compile-time portability checks, not for sizing allocations.
  • Pattern: use _POSIX_* as compile-time fallback only if sysconf/pathconf returns indeterminate and you have no better default.

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// --- sysconf with indeterminate handling ---
errno = 0;
long open_max = sysconf(_SC_OPEN_MAX);
if (open_max == -1) {
    if (errno == 0)
        open_max = 256;   // indeterminate; use fallback
    else
        perror("sysconf _SC_OPEN_MAX");
}
printf("open_max = %ld\n", open_max);

// --- pathconf for PATH_MAX with fallback ---
errno = 0;
long path_max = pathconf("/", _PC_PATH_MAX);
if (path_max == -1) {
    if (errno == 0)
        path_max = 4096;  // indeterminate; use safe default
    else
        perror("pathconf _PC_PATH_MAX");
}
char *buf = malloc(path_max + 1);
// ... use buf for path operations, then free(buf)

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Always clear errno before calling sysconf()/pathconf(). Check both the return value and errno to distinguish indeterminate from error.
  • Never hardcode PATH_MAX for buffer allocation. Use dynamic allocation with realpath(NULL) or growing buffers.
  • Use getrlimit(RLIMIT_NOFILE) for the authoritative per-process open-file limit, not sysconf(_SC_OPEN_MAX).
  • Provide documented fallback defaults for all indeterminate limits. Log when a fallback is used.
  • Do not use _POSIX_* constants as buffer sizes. They are minimums for portability checking, not practical limits.
  • Use the getconf command-line tool to verify limits during deployment and container image builds.
