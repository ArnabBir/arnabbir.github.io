Chapter 34 — Process Groups, Sessions, and Job Control

Sessions and process groups organize processes for job control — the mechanism behind Ctrl-C sending SIGINT to the foreground group, shell backgrounding, and terminal management.

A session is a set of process groups (one foreground, rest background) tied to a controlling terminal. The shell manipulates these abstractions to implement job control: suspending, resuming, and signaling groups of cooperating processes.

Invariant
Ctrl-C/Ctrl-Z sends signal to the entire foreground process group, not a single process.
Gotcha
Orphaned process groups receive SIGHUP+SIGCONT when the session leader exits — easy to miss in daemon code.
Debugging
Use ps -o pid,pgid,sid,tty,comm to visualize session/group membership.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • A session is a collection of process groups; exactly one group is the foreground group at any time.
  • A process group (pgrp) is a set of related processes — typically the stages of a single pipeline.
  • The controlling terminal is attached to exactly one session; terminal-generated signals (SIGINT, SIGTSTP) go to the foreground process group.
  • setsid() creates a new session: the caller becomes session leader with no controlling terminal — the first step of daemonization.
  • setpgid() moves a process into a different process group; shells use this to create job groups.
  • When a session leader with a controlling terminal exits, SIGHUP is sent to the foreground process group; orphaned process groups also get SIGHUP+SIGCONT.
  • Daemon creation pattern: fork → setsid → fork again (prevents reacquiring a terminal) → close fds → redirect stdio to /dev/null.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
Orphaned process groups
  • A process group is orphaned when no member has a parent in a different process group within the same session.
  • If an orphaned process group has any stopped members, the kernel sends SIGHUP followed by SIGCONT to every member.
  • This mechanism ensures stopped jobs don't hang forever after the shell exits — they get a chance to clean up.
  • A common bug: background jobs that ignore SIGHUP (via nohup or signal masking) survive but may lose their terminal I/O.
Terminal disconnect cascade
  • When a controlling terminal hangs up (SSH disconnect, terminal close), the kernel sends SIGHUP to the session leader.
  • The session leader (typically the shell) then sends SIGHUP to its foreground job. Default SIGHUP action is termination.
  • Background jobs may or may not receive SIGHUP depending on the shell (bash sends it if huponexit is set).
  • nohup works by ignoring SIGHUP and redirecting output — it doesn't detach from the session.
  • disown (bash) removes the job from the shell's job table, preventing the shell from signaling it on exit.
setsid and daemon creation pitfalls
  • setsid() fails with EPERM if the caller is already a process group leader — solution: fork first, then setsid in the child.
  • After setsid(), the process has no controlling terminal. But opening a terminal device can reacquire one (on Linux, only if O_NOCTTY is not set and the process is a session leader).
  • The double-fork trick: after setsid(), fork again so the grandchild is not a session leader and cannot accidentally acquire a controlling terminal.
  • systemd's Type=simple makes double-fork unnecessary — systemd tracks the main PID directly.
Shell job control implementation
  • The shell creates a new process group for each job (pipeline). It calls setpgid() in both parent and child to avoid races.
  • The foreground job's process group is set via tcsetpgrp(); background jobs never get terminal access.
  • When a background job tries to read from the terminal, it receives SIGTTIN and stops.
  • When a background job tries to write (with tostop set), it receives SIGTTOU and stops.
  • The shell must restore itself as the foreground group after each foreground job completes (tcsetpgrp back to shell's pgid).

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// Proper daemon creation: double-fork + setsid
#include <unistd.h>
#include <stdlib.h>
#include <fcntl.h>
#include <sys/stat.h>

void daemonize(void) {
    pid_t pid = fork();
    if (pid < 0) _exit(1);
    if (pid > 0) _exit(0);       // parent exits

    if (setsid() < 0) _exit(1);  // new session, no ctty

    pid = fork();                  // second fork
    if (pid < 0) _exit(1);
    if (pid > 0) _exit(0);       // session leader exits

    // Now: not session leader, cannot acquire ctty
    umask(0);
    chdir("/");

    // Close inherited fds, redirect stdio to /dev/null
    close(STDIN_FILENO);
    close(STDOUT_FILENO);
    close(STDERR_FILENO);
    open("/dev/null", O_RDONLY);  // fd 0
    open("/dev/null", O_WRONLY);  // fd 1
    open("/dev/null", O_WRONLY);  // fd 2
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Use setpgid() in both parent and child after fork to avoid race conditions in group assignment.
  • Always restore the shell's process group as foreground after a foreground job finishes (tcsetpgrp).
  • Handle SIGHUP gracefully in long-running services: reload config or shut down cleanly.
  • For daemons, prefer systemd Type=notify or Type=simple over traditional double-fork when possible.
  • When using nohup or disown, ensure output is redirected — orphaned terminal writes cause SIGTTOU stops.
