    TOPIC 19 / 64 · Monitoring File Events

    File events are hints to reconcile

    A directory watcher misses a rename during a burst of changes.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    inotify places filesystem notifications in a bounded queue. Watches identify observed objects, and rename cookies help correlate move events, but the application must tolerate gaps and races. An event stream is a prompt to update a view of state, not an infallible audit log.

    Contract and implementation boundary

    Use inotify_init1 with appropriate nonblocking and close-on-exec flags. Parse each variable-length record using its reported length. Handle IN_Q_OVERFLOW by rebuilding the relevant state. Recursive trees require deliberate watch management because one directory watch is not recursive.

    Contract references: inotify.7 · inotify_init.2. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    Pairing rename events with an assumption of immediate adjacency fails under interleaving. A path can disappear before the consumer inspects it. Keeping only events without a reconciliation strategy makes overflow unrecoverable.

    Worked reasoning trace

    Assumptions: A watcher maintains a cache of directory contents.

    1. Starting state

      The event queue overflows during a burst.

    2. Operation

      The consumer receives IN_Q_OVERFLOW.

    3. Expected observation

      Invalidate confidence in the event history and reconcile from the directory.

    Tradeoff: Events are efficient for updates; rescans are the recovery path.

    This is a hand-authored prediction, not captured runtime output.

    Original practice problem

    In a private directory, record create, rename, and delete activity. Then design a synthetic overflow input for your parser and verify that it requests a rescan rather than reporting a perfectly complete history.
