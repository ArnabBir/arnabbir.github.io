Chapter 19 — Monitoring File Events

inotify lets you watch files and directories for changes -- create, modify, delete, move -- without polling. You get an fd that delivers structured events when watched paths change. This is the foundation for build tools (make, webpack), file synchronization (rsync, Dropbox), editors (auto-reload), and security monitoring (audit trails).

The API is simple: inotify_init1() creates an inotify instance (an fd), inotify_add_watch() registers interest in specific paths and event types, and read() on the inotify fd returns batched inotify_event structs. The critical caveat is that inotify does NOT recurse into subdirectories automatically -- you must add watches for each directory yourself. fanotify is the modern alternative for filesystem-wide or mount-wide monitoring.

Invariant
inotify_init1 returns an fd; inotify_add_watch registers path+mask; read() delivers batched inotify_event structs.
Gotcha
inotify does not recurse into subdirectories. You must add a watch for every directory you care about.
Debugging
Use inotifywait (inotify-tools) from the command line to prototype watches before writing code.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • inotify_init1(IN_NONBLOCK | IN_CLOEXEC) creates an inotify instance and returns an fd. This fd is pollable (epoll/poll/select compatible).
  • inotify_add_watch(fd, path, mask) registers interest in events on a specific path. The mask is a bitwise OR of event types: IN_CREATE, IN_MODIFY, IN_DELETE, IN_MOVED_FROM, IN_MOVED_TO, IN_ATTRIB, IN_CLOSE_WRITE, etc.
  • read() on the inotify fd returns one or more variable-length inotify_event structs. Each contains: wd (watch descriptor identifying which watch), mask (events that occurred), cookie (links MOVED_FROM/MOVED_TO pairs), len (name length), and name (filename within watched directory).
  • Watch descriptors (wd) identify which registered watch triggered an event. You maintain a wd-to-path mapping in your application.
  • inotify does NOT recurse into subdirectories. To monitor a tree, you must walk it and add a watch for each directory. When IN_CREATE fires for a new subdirectory, you must add a watch for it too.
  • A file rename generates an IN_MOVED_FROM event on the source directory and an IN_MOVED_TO event on the destination directory. The cookie field in both events shares the same value, letting you correlate them as a single rename operation.
  • Under heavy load, the kernel event queue can overflow. When this happens, you receive a special IN_Q_OVERFLOW event (with wd = -1). You must treat this as "events were lost" and rescan the watched directories to resync state.
  • fanotify is a newer API that can monitor entire filesystems or mount points. It supports permission events (allow/deny access) and is used by anti-malware scanners. It requires CAP_SYS_ADMIN for many features.
  • dnotify is the predecessor to inotify, using fcntl(F_NOTIFY). It is per-directory, signal-based, and effectively deprecated. Prefer inotify or fanotify.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
No automatic recursion
  • inotify watches a single directory or file. It does NOT automatically watch subdirectories.
  • To monitor a directory tree, you must walk the tree at startup and add a watch for each directory.
  • When IN_CREATE fires for a new subdirectory, you must immediately add a watch for it. There is a race: files may be created in the new subdirectory before your watch is in place. After adding the watch, rescan the subdirectory to catch anything you missed.
  • This recursive watch management is the most common source of bugs in inotify-based tools.
Event overflow (IN_Q_OVERFLOW)
  • The kernel maintains a per-inotify-instance event queue with a bounded size (default 16384 events, tunable via /proc/sys/fs/inotify/max_queued_events).
  • When the queue fills up, the kernel drops events and enqueues a single IN_Q_OVERFLOW event with wd = -1.
  • You MUST handle this: treat it as "an unknown number of events were lost" and do a full rescan of all watched directories to rebuild consistent state.
  • High-frequency writers (log rotation, build systems) can easily trigger overflow. Increase max_queued_events or drain the fd faster.
Rename detection and the cookie field
  • A rename (mv) within a watched directory generates IN_MOVED_FROM followed by IN_MOVED_TO with the same cookie value.
  • If the destination directory is also watched, you get both events and can correlate them. If only the source is watched, you see only IN_MOVED_FROM (the file "disappeared").
  • A rename from a watched directory to an unwatched one looks like a delete. A rename from unwatched to watched looks like a create.
  • The cookie is a non-zero uint32_t unique within the inotify instance for correlating move pairs.
Network and virtual filesystems
  • inotify relies on kernel VFS hooks. NFS, CIFS, FUSE, and other network/virtual filesystems may not generate inotify events because changes happen outside the local kernel.
  • For NFS: another host modifying a file will NOT trigger inotify on your machine. Only local operations generate events.
  • For FUSE: depends on the FUSE implementation. Some generate events, many do not.
  • If you need cross-machine notification, use a polling fallback or an application-level notification protocol.

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// inotify setup + event loop
#include <sys/inotify.h>
#include <limits.h>
#include <stdio.h>
#include <unistd.h>
#include <errno.h>

int main(int argc, char *argv[]) {
    const char *dir = argc > 1 ? argv[1] : ".";
    int fd = inotify_init1(IN_NONBLOCK | IN_CLOEXEC);
    if (fd < 0) { perror("inotify_init1"); return 1; }

    int wd = inotify_add_watch(fd, dir,
        IN_CREATE | IN_DELETE | IN_MODIFY | IN_MOVED_FROM | IN_MOVED_TO);
    if (wd < 0) { perror("inotify_add_watch"); return 1; }

    char buf[4096] __attribute__((aligned(__alignof__(struct inotify_event))));
    for (;;) {
        ssize_t len = read(fd, buf, sizeof(buf));
        if (len < 0) {
            if (errno == EAGAIN) { usleep(100000); continue; }
            perror("read"); break;
        }
        for (char *p = buf; p < buf + len; ) {
            struct inotify_event *ev = (struct inotify_event *)p;
            if (ev->mask & IN_Q_OVERFLOW) {
                fprintf(stderr, "OVERFLOW -- rescan needed\n");
            } else {
                printf("wd=%d mask=0x%x cookie=%u name=%s\n",
                       ev->wd, ev->mask, ev->cookie,
                       ev->len ? ev->name : "(none)");
            }
            p += sizeof(*ev) + ev->len;
        }
    }
    close(fd);
    return 0;
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Always pass IN_NONBLOCK | IN_CLOEXEC to inotify_init1.
  • Handle IN_Q_OVERFLOW by rescanning all watched directories to rebuild consistent state.
  • When watching directory trees, add watches for new subdirectories on IN_CREATE and rescan them immediately to close the race window.
  • Maintain a wd-to-path mapping so you can identify which directory triggered each event.
  • Use the cookie field to correlate IN_MOVED_FROM and IN_MOVED_TO events as a single rename.
  • Check /proc/sys/fs/inotify/max_user_watches and increase it if you need to watch large directory trees (e.g., echo 524288 > max_user_watches).
  • Do not rely on inotify for NFS, CIFS, or FUSE filesystems -- fall back to polling.
  • Integrate the inotify fd into your event loop (epoll/poll) rather than busy-looping on read.
