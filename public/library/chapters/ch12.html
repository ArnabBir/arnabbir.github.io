Chapter 12 — System and Process Information

/proc is a live window into kernel state. It is not a real filesystem—no data is stored on disk. Instead, the kernel generates file contents on each read, exposing process state, memory maps, file descriptors, and system tunables as ordinary-looking files. This pseudo-filesystem is the foundation of nearly every Linux monitoring and debugging tool.

Beyond /proc, the uname() syscall provides kernel identification (version, architecture), and sysinfo() returns basic system-wide statistics (uptime, load averages, memory usage). Together, these APIs enable runtime introspection without external tools.

Invariant
/proc files are generated on-read by the kernel. They consume no disk space and always reflect the current state at the moment of the read() call.
Gotcha
/proc/PID/ can disappear mid-read if the process exits. PID reuse means you might inadvertently read data from a different process than intended.
Debugging
/proc/self always points to the calling process. Use /proc/self/fd to audit open file descriptors and /proc/self/maps to inspect memory layout without knowing your own PID.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • /proc is a pseudo-filesystem (type proc). Reads trigger kernel code that formats internal data structures into text. There are no actual files on any block device.
  • /proc/PID/ contains per-process information: status (UIDs, state, memory), maps (virtual memory regions), fd/ (symlinks to open file descriptors), fdinfo/ (offset, flags per fd), smaps (detailed per-mapping memory stats), and cmdline (process arguments).
  • /proc/sys/ exposes kernel tunables. For example, /proc/sys/fs/file-max controls the system-wide open-file limit. Writing to these files changes kernel parameters at runtime (equivalent to sysctl).
  • uname() fills a struct utsname with kernel release, version, machine architecture, hostname, and domain. This is how programs detect the running kernel version at runtime.
  • sysinfo() returns system uptime, load averages (1/5/15 min), total/free/shared/buffered RAM, swap usage, and process count. It is a lightweight alternative to parsing /proc/meminfo and /proc/loadavg.
  • /proc is subject to race conditions: a process can exit between your opendir(/proc/PID) and subsequent read. PID reuse means /proc/PID might refer to a completely different process if the original exited and a new one received the same PID.
  • /proc/PID/mem allows reading the virtual memory of another process, but requires PTRACE_ATTACH permission (same rules as ptrace). This is heavily restricted by YAMA security module on most distributions.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
/proc race conditions
  • A process can exit between your open(/proc/PID/status) and read(). The open may succeed but read returns ESRCH or 0 bytes. Always handle this gracefully.
  • PID reuse: Linux recycles PIDs. After process A (PID 1234) exits, a new process B may receive PID 1234. If you cached the PID, /proc/1234/ now describes process B. Use /proc/PID/starttime or pidfd to detect reuse.
  • Directory enumeration of /proc/ (listing all PIDs) is inherently racy. Processes appear and disappear between readdir() calls. Tools like ps and top handle this by tolerating ENOENT on subsequent reads.
  • Mitigation: use pidfd_open() (Linux 5.3+) to get a stable reference to a process. pidfd does not suffer from PID reuse races.
Format changes and portability
  • /proc file formats can change across kernel versions. Fields may be added, reordered, or renamed. Parse defensively: search by field name, not by line number or column position.
  • /proc/PID/status uses "Key:\tValue\n" format. Parse by matching the key prefix, not by fixed offsets.
  • /proc/PID/stat packs many fields into a single space-delimited line. The comm field (field 2) is in parentheses and may contain spaces, which breaks naive splitting. Parse the last ')' to find the end of comm.
  • /proc is Linux-specific. Other Unixes use different mechanisms (sysctl on BSD, /proc on Solaris has a different format). For portable code, abstract /proc access behind an OS-specific layer.
/proc/PID/mem access restrictions
  • Reading /proc/PID/mem requires the same permissions as ptrace(PTRACE_ATTACH). On most distributions, the YAMA security module restricts this to direct parent processes (yama.ptrace_scope=1).
  • Even with access, you must lseek() to a valid mapped address before reading. Reading unmapped regions returns EIO.
  • /proc/PID/smaps provides detailed per-mapping statistics (RSS, PSS, shared/private) without needing ptrace permissions. Prefer smaps for memory analysis.
  • Root (CAP_SYS_PTRACE) bypasses YAMA restrictions. In containers, this capability is typically dropped.

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// --- Read /proc/self/status ---
int fd = open("/proc/self/status", O_RDONLY);
if (fd < 0) { perror("open"); return 1; }
char buf[4096];
ssize_t n = read(fd, buf, sizeof(buf) - 1);
close(fd);
if (n > 0) { buf[n] = '\0'; printf("%s", buf); }

// --- Iterate /proc/self/fd to list open descriptors ---
DIR *d = opendir("/proc/self/fd");
if (!d) { perror("opendir"); return 1; }
struct dirent *ent;
while ((ent = readdir(d)) != NULL) {
    if (ent->d_name[0] == '.') continue;
    char link[64], target[256];
    snprintf(link, sizeof(link), "/proc/self/fd/%s", ent->d_name);
    ssize_t len = readlink(link, target, sizeof(target) - 1);
    if (len > 0) { target[len] = '\0';
        printf("fd %s -> %s\n", ent->d_name, target);
    }
}
closedir(d);

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Always handle ENOENT/ESRCH when reading /proc/PID files. The target process may have exited.
  • Use /proc/self/ instead of constructing /proc/<getpid()>/ to avoid PID reuse races on your own process.
  • Parse /proc files by field name, not by line number. Kernel updates may add or reorder fields.
  • For monitoring other processes, prefer pidfd_open() (Linux 5.3+) over raw PID to avoid race conditions with PID reuse.
  • Use uname() to detect kernel version at startup. Log it for debugging—/proc format and feature availability depend on kernel version.
  • Prefer sysinfo() over parsing /proc/meminfo and /proc/loadavg when you only need basic stats. It is a single syscall with no parsing.

Exercises

Hands-on tasks to make the chapter "stick". These are intentionally practical and debugging-heavy.
  • Write a program that reads and prints /proc/self/status, /proc/self/maps, and the number of entries in /proc/self/fd/. Compare the fd count with the result of sysconf(_SC_OPEN_MAX).
  • Write a PID monitor: given a PID, read /proc/PID/status every second and print state changes. Handle the process exiting gracefully (ENOENT).
  • Use readlink on each /proc/self/fd/N to identify all open file descriptors in your process. Detect leaked fds by opening and closing files and checking the fd list before and after.
  • Call uname() and sysinfo() and print all fields. Verify the uname output matches uname -a from the shell.
