    Launching safely from a larger process

    A threaded application needs to launch a helper with redirected output.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    A launch is a protocol: choose the executable, prepare descriptors, create the child, establish its environment, detect replacement failure, and collect termination. posix_spawn packages common setup through attributes and file actions, reducing the amount of custom post-fork code.

    Contract and implementation boundary

    posix_spawn returns an error number, not the usual -1/errno convention. A successful launch still requires waitpid to collect child completion. File actions are ordered; a close before a duplication can invalidate the source. system invokes a shell and has its own signal and status semantics.

    Contract references: posix_spawn.3 · system.3 · vfork.2. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    vfork is not a drop-in faster fork: the child shares constrained execution state until exec or _exit. Returning from the child path or modifying arbitrary data is unsafe. An implementation's fast path is not an application contract.

    Worked reasoning trace

    Assumptions: Spawn file actions redirect stdout; destination already happens to be fd 1.

    1. Starting state

      The destination descriptor equals the target descriptor.

    2. Operation

      Avoid an unconditional surplus-close action on fd 1.

    3. Expected observation

      The launched helper retains its intended stdout.

    Tradeoff: Declarative spawn setup reduces post-fork code but action order still matters.

    This is a hand-authored prediction, not captured runtime output.

    Write a launch plan for stdout redirection using posix_spawn file actions: open destination, duplicate to stdout if needed, close surplus handles, spawn, destroy actions, wait. Analyze the case where the opened descriptor already equals stdout.
