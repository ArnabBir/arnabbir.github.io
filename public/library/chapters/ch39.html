Chapter 39 — Capabilities

Capabilities split root's monolithic power into approximately 40 discrete privileges. A web server needs only CAP_NET_BIND_SERVICE to listen on port 80, not the full unconstrained authority of UID 0.

The capability model replaces the binary root/non-root distinction with fine-grained tokens. Each thread carries capability sets that determine exactly which privileged operations it may perform, enabling precise least-privilege enforcement without setuid binaries.

Invariant
A capability must be in the thread's permitted set before it can appear in the effective set. You cannot grant yourself capabilities you do not already possess.
Gotcha
CAP_SYS_ADMIN is "the new root" — it grants mount, swapon, BPF, namespace creation, and dozens more operations. Granting it defeats most of the purpose of capabilities.
Debugging
getpcaps PID shows a thread's current capabilities; getcap /path/to/binary shows file capabilities. Decode hex from /proc/PID/status CapEff/CapPrm with capsh --decode=.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • Five capability sets per thread: permitted (ceiling of what can be activated), effective (actually checked by kernel), inheritable (preserved across exec), bounding (limits what can ever be gained), and ambient (Linux 4.3+, auto-raised into permitted+effective across exec without file caps).
  • File capabilities (set via setcap) attach privilege to binaries without the setuid bit: the kernel merges file caps into the thread's sets during execve() according to the capability transformation rules.
  • The capability bounding set is a one-way filter: bits can only be dropped, never added. Once removed from the bounding set, a capability cannot be reacquired even by a process with CAP_SETPCAP.
  • Ambient capabilities (Linux 4.3) solve the inheritance problem: they survive exec without requiring file capabilities on the target binary, enabling unprivileged helper programs to inherit specific caps from their parent.
  • PR_SET_NO_NEW_PRIVS combined with seccomp-BPF creates a robust sandbox: no_new_privs prevents gaining capabilities via exec (file caps ignored), while seccomp restricts the syscall surface.
  • Capability-aware programs use the libcap API: cap_get_proc() retrieves current sets, cap_set_flag() modifies individual bits, and cap_set_proc() applies changes atomically to the thread.
Key terms & kernel objects
Term / objectMeaning
CAP_NET_BIND_SERVICEPermits binding to TCP/UDP ports below 1024 without full root. The minimal capability for most network daemons.
CAP_SYS_ADMINOverloaded "catch-all" capability covering mount, BPF, namespace ops, and more. Effectively equivalent to root for most practical purposes.
Permitted setUpper bound of capabilities available to the thread. Effective and inheritable sets cannot contain caps not in permitted.
Effective setThe set actually checked by the kernel when a privileged operation is attempted. Must be a subset of permitted.
Inheritable setCapabilities preserved across execve() if also present in the new binary's inheritable file cap set.
Ambient setCapabilities automatically added to permitted and effective sets of a non-setuid child after exec, without requiring file caps.
Bounding setOne-way limiting set: caps removed from bounding can never be regained. Restricts what file caps or ambient caps can grant.
setcap / getcapUserspace tools to set and query file capabilities stored in the security.capability extended attribute.
PR_SET_NO_NEW_PRIVSprctl flag preventing the thread (and descendants) from gaining new privileges via execve: file caps and setuid bits are ignored.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
CAP_SYS_ADMIN breadth and danger
  • CAP_SYS_ADMIN gates over 30 distinct operations: mount/umount, swapon, BPF program load, namespace creation (clone NEWNS/NEWPID), keyctl, ioctl on many devices, and quotactl.
  • Granting CAP_SYS_ADMIN to a container or service effectively gives it root-equivalent power: it can mount proc/sysfs, escape namespaces via mount manipulation, or load BPF programs to observe all system traffic.
  • Prefer decomposing needs: CAP_NET_ADMIN for network config, CAP_DAC_OVERRIDE for file access, CAP_FOWNER for chown — rather than the blanket CAP_SYS_ADMIN.
  • Kernel developers acknowledge the problem; new operations are being split into dedicated capabilities (e.g., CAP_BPF, CAP_PERFMON added in Linux 5.8).
Capability leakage across exec
  • Without ambient caps (pre-4.3 kernels), capabilities are lost across exec unless the target binary has file capabilities set. This made capability inheritance impractical for many years.
  • The inheritable set only matters if the exec'd binary also has matching inheritable file caps — a double-opt-in that confused many administrators.
  • Ambient caps fix this: if a cap is in both permitted and inheritable, it can be added to ambient, and will automatically appear in the child's permitted+effective sets after exec.
  • Security implication: ambient caps persist across exec of non-setuid binaries. A compromised child inherits the parent's ambient caps. Use PR_SET_NO_NEW_PRIVS + cap_clear to prevent propagation when spawning untrusted programs.
no_new_privs + seccomp sandboxing
  • PR_SET_NO_NEW_PRIVS is irreversible and inherited by all descendants. Once set, execve() ignores setuid/setgid bits and file capabilities, preventing privilege escalation via exec.
  • seccomp-BPF requires either CAP_SYS_ADMIN or no_new_privs to be set. The common pattern: set no_new_privs, then install a seccomp filter to whitelist only needed syscalls.
  • systemd's CapabilityBoundingSet= directive drops caps from the bounding set before exec'ing the service, permanently preventing those capabilities from being acquired.
  • Combining CapabilityBoundingSet, NoNewPrivileges=yes, and SystemCallFilter= in a systemd unit creates defense-in-depth: even if the service is compromised, it cannot escalate.

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// Drop all capabilities except CAP_NET_BIND_SERVICE
#include <sys/capability.h>
#include <sys/prctl.h>
#include <stdlib.h>
#include <stdio.h>

static void restrict_to_net_bind(void) {
    cap_t caps = cap_get_proc();
    if (!caps) { perror("cap_get_proc"); _exit(1); }

    // Clear all capabilities from all sets
    cap_clear(caps);

    // Retain only CAP_NET_BIND_SERVICE in permitted + effective
    cap_value_t keep[] = { CAP_NET_BIND_SERVICE };
    cap_set_flag(caps, CAP_PERMITTED, 1, keep, CAP_SET);
    cap_set_flag(caps, CAP_EFFECTIVE, 1, keep, CAP_SET);

    if (cap_set_proc(caps) < 0) {
        perror("cap_set_proc");
        _exit(1);
    }
    cap_free(caps);

    // Lock down: prevent regaining caps via exec
    prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0);
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Use file capabilities (setcap) instead of setuid root: e.g., setcap cap_net_bind_service=ep /usr/bin/myserver eliminates the need for root entirely.
  • Drop all unneeded capabilities immediately after startup using cap_clear + cap_set_flag for only the required set.
  • Set PR_SET_NO_NEW_PRIVS after dropping caps to prevent any child process from escalating via exec of setuid or file-capable binaries.
  • In systemd units, use CapabilityBoundingSet= to restrict the bounding set, AmbientCapabilities= for non-root services, and NoNewPrivileges=yes.
  • Audit running services with getpcaps and /proc/PID/status CapEff; alert on any service holding CAP_SYS_ADMIN that does not strictly require it.
