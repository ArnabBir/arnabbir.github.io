Chapter 31 — Threads: Thread Safety and Per-Thread Storage

Thread safety means a function can be called concurrently from multiple threads without corrupting shared data. The #1 source of thread-unsafety in legacy C code is functions that use static internal buffers (strtok, ctime, gethostbyname). This chapter covers making code thread-safe and two mechanisms for per-thread storage.

Reentrant functions are a stronger guarantee: safe even when called from a signal handler that interrupted the same function. The _r variants (strtok_r, localtime_r) are the standard solution. For custom per-thread state, use pthread_key (destructor support) or the simpler __thread keyword.

Invariant
Thread-safe means no shared mutable state without synchronization. Reentrant is stricter: safe even from signal handlers interrupting the same function.
Gotcha
Functions like strtok, ctime, and gethostbyname use internal static buffers and are NOT thread-safe. Always use the _r variants in threaded code.
Debugging
grep your codebase for non-_r libc calls (strtok, asctime, readdir without _r). Each is a latent thread-safety bug.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • Thread-safe: function can be called from multiple threads concurrently without data corruption. Achieved via mutexes, atomics, or eliminating shared mutable state.
  • Reentrant: function is safe even when re-entered from a signal handler. Reentrant implies thread-safe, but thread-safe does not imply reentrant (a function using a mutex is thread-safe but not reentrant from a signal handler).
  • Static buffers are the #1 thread-safety problem in classic C libraries. Functions like strtok, ctime, getpwnam return pointers to internal static storage that is overwritten on the next call.
  • The _r variants (strtok_r, localtime_r, getpwnam_r) take a caller-supplied buffer, making them thread-safe and reentrant.
  • pthread_key_create + pthread_setspecific: the POSIX API for thread-specific data. A destructor function is called with the value when the thread exits.
  • __thread (or _Thread_local in C11): simpler thread-local storage. Each thread gets its own copy of the variable. No destructor support.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
Thread-safety vs. reentrancy
  • A function that uses a mutex is thread-safe but NOT reentrant: if a signal handler calls it while the mutex is held, it deadlocks.
  • Reentrant functions use only local variables and caller-supplied buffers. They never touch global/static state.
  • errno is thread-safe (it's a per-thread macro in modern libc) but you must read it immediately after a failed call before any other function overwrites it.
  • Even "read-only" access to shared data is unsafe if another thread writes concurrently -- this is a data race.
pthread_key pitfalls
  • PTHREAD_KEYS_MAX limits the number of keys (typically 1024). Libraries that each create keys can exhaust this limit.
  • The destructor is called only if the thread's value for that key is non-NULL at thread exit. It is NOT called if the thread calls _exit() or exit().
  • Destructors may be called multiple times (up to PTHREAD_DESTRUCTOR_ITERATIONS) if a destructor sets another key's value to non-NULL.
  • Use pthread_once to create keys lazily and safely. Without it, two threads racing to create the same key is a bug.
__thread limitations
  • __thread variables must have static storage duration. You cannot apply __thread to automatic (stack) variables.
  • __thread does not support destructors. If the variable points to heap memory, you must free it manually before thread exit.
  • __thread is faster than pthread_getspecific (no function call, just a segment-register offset) but less portable to non-GCC compilers.
  • In C11, use _Thread_local instead of __thread for standard compliance.
Common non-thread-safe functions
  • strtok (use strtok_r), ctime/asctime (use ctime_r/asctime_r), localtime (use localtime_r).
  • gethostbyname/gethostbyaddr (use getaddrinfo/getnameinfo instead).
  • readdir (use readdir_r, though it is deprecated in glibc 2.24+ because readdir is now thread-safe per-directory).
  • getpwnam/getpwuid (use getpwnam_r/getpwuid_r with a caller-supplied buffer).

Code patterns (C / POSIX)

pthread_key usage vs __thread comparison. 
// Thread-specific data with pthread_key
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>

static pthread_key_t buf_key;
static pthread_once_t key_once = PTHREAD_ONCE_INIT;

static void free_buf(void *ptr){ free(ptr); }
static void make_key(void){ pthread_key_create(&buf_key, free_buf); }

char *get_thread_buf(size_t sz){
  pthread_once(&key_once, make_key);
  char *buf = pthread_getspecific(buf_key);
  if(!buf){ buf = malloc(sz); pthread_setspecific(buf_key, buf); }
  return buf;
}

// Simpler alternative: __thread (no destructor)
static __thread int call_count = 0;

void *worker(void *arg){
  call_count++;                       // each thread has its own copy
  char *buf = get_thread_buf(256);    // per-thread buffer, freed on exit
  snprintf(buf, 256, "thread %ld: calls=%d",
           (long)pthread_self(), call_count);
  puts(buf);
  return NULL;
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Audit all libc calls for non-_r variants. Replace strtok with strtok_r, localtime with localtime_r, etc.
  • Document thread-safety guarantees for every public function in your library.
  • Use pthread_once for lazy one-time initialization of shared resources (keys, singletons, config).
  • Prefer __thread for simple per-thread counters and caches. Use pthread_key only when you need destructor-based cleanup.
  • Verify with TSan that no data races exist in your thread-safe wrappers.
