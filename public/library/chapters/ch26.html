Chapter 26 — Monitoring Child Processes

After fork, the parent must reap children with wait/waitpid to collect exit status and free kernel resources. Unreaped children become zombies — they consume a PID and a slot in the process table indefinitely until the parent collects their status or itself exits.

The wait family of calls is how parents learn about child state changes: exit, signal death, stop, and continue. Mastering waitpid flags and SIGCHLD handling is essential for writing robust servers, shells, and supervisors.

Invariant
A zombie exists from child exit until parent calls wait*(). Orphans are re-parented to init (PID 1), which reaps them.
Gotcha
SIGCHLD can coalesce — one signal for multiple exits. Always call waitpid() in a loop with WNOHANG.
Debugging
ps aux | grep Z shows zombies. Check parent PID — if parent isn't reaping, fix the parent (or kill it to let init reap).

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • Zombie = exited child whose termination status hasn't been collected. It holds a PID + exit info, nothing else (no memory, no fds).
  • waitpid(pid, &status, flags) blocks until the specified child changes state. Returns child PID or -1 on error.
  • WNOHANG: return immediately if no child has exited (non-blocking poll). Returns 0 if nothing to reap.
  • WUNTRACED: also report stopped children (e.g., SIGTSTP). WCONTINUED: report continued children (SIGCONT).
  • waitid(P_PID, pid, &siginfo, opts) provides more detail (siginfo_t) and separates "peek" vs "consume" (WNOWAIT).
  • SIGCHLD is delivered to the parent when a child exits, is killed, stops, or continues. Default disposition: ignore.
  • Setting SIGCHLD to SIG_IGN (Linux-specific) causes automatic reaping — children never become zombies. Portable code cannot rely on this.
  • Double-fork trick: parent forks child, child forks grandchild then exits immediately; parent reaps child; grandchild is orphaned to init which auto-reaps it.
  • Orphan: a process whose parent has exited. Kernel re-parents it to the nearest subreaper (prctl PR_SET_CHILD_SUBREAPER) or PID 1.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
Zombie accumulation under load
  • A server forking thousands of children without reaping will exhaust the PID space (default max ~32768, tunable via /proc/sys/kernel/pid_max).
  • Zombies don't consume memory or CPU, but each holds a PID and process table entry.
  • Fix: install a SIGCHLD handler that loops waitpid(-1, NULL, WNOHANG) until it returns 0 or -1.
  • Alternative: use SIG_IGN for SIGCHLD (Linux) or the double-fork pattern.
SIGCHLD handler calling waitpid in a loop
  • SIGCHLD is a standard (non-queuing) signal — if 3 children exit while handler runs, only 1 SIGCHLD may be pending.
  • The handler MUST loop: while (waitpid(-1, &s, WNOHANG) > 0) { /* process */ }
  • Without the loop, you miss exits and zombies accumulate silently.
  • The handler must be async-signal-safe: no printf, malloc, or non-reentrant functions.
Race between fork and signal delivery
  • A child can exit before the parent even returns from fork(). SIGCHLD arrives before the parent stores the child PID.
  • If using a PID table, block SIGCHLD around fork + table update, then unblock (sigprocmask).
  • Alternative: use signalfd or a self-pipe to handle SIGCHLD synchronously in an event loop.
  • waitpid with a specific PID works fine even if the child already exited — the zombie is queued.
Orphan process groups and SIGHUP
  • When a process group becomes orphaned (no member has a parent in a different pgrp in the same session) and has stopped members, the kernel sends SIGHUP then SIGCONT.
  • This prevents stopped processes from being permanently stuck with no one to send SIGCONT.
  • Shells must handle this for correct job control behavior during logout/disconnect.
  • A common pattern in daemons: fork, parent exits, child calls setsid() — explicitly choosing orphan status.

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// SIGCHLD handler with waitpid loop + double-fork pattern
#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

static void sigchld_handler(int sig) {
    int saved_errno = errno;
    pid_t pid;
    int status;
    // Loop: SIGCHLD can coalesce multiple exits into one signal
    while ((pid = waitpid(-1, &status, WNOHANG)) > 0) {
        // log or record status (async-signal-safe only!)
    }
    errno = saved_errno;
}

// Double-fork: avoid zombies without a SIGCHLD handler
void spawn_detached(const char *cmd) {
    pid_t pid = fork();
    if (pid == 0) {
        // First child — fork again, then exit immediately
        if (fork() == 0) {
            // Grandchild: orphaned to init, runs the real work
            execlp(cmd, cmd, (char*)NULL);
            _exit(127);
        }
        _exit(0);  // first child exits; parent reaps quickly
    }
    waitpid(pid, NULL, 0);  // reap first child (instant)
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Always reap children: SIGCHLD handler with waitpid loop, or periodic waitpid(-1, WNOHANG), or SIG_IGN, or double-fork.
  • Handle EINTR from waitpid — signals can interrupt the blocking call.
  • In SIGCHLD handlers, save and restore errno; call only async-signal-safe functions.
  • Block SIGCHLD around fork + bookkeeping if you maintain a child PID table to avoid races.
  • Monitor zombie count in production: alert if /proc shows unexpected Z-state processes.
