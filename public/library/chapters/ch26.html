    TOPIC 26 / 64 · Monitoring Child Processes

    Reaping is resource accounting

    A server handles SIGCHLD once but leaves several zombie children.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    Child termination and parent observation are separate events. The kernel retains status for the parent to collect. Since standard SIGCHLD occurrences can coalesce, a signal tells the parent to inspect child state rather than counting exactly one termination.

    Contract and implementation boundary

    waitpid with WNOHANG returns a positive PID when a status was collected, zero when matching children exist but none is ready, or -1 on error. Decode status with WIFEXITED before WEXITSTATUS and WIFSIGNALED before WTERMSIG. A stopped child is not a terminated child.

    Contract references: wait.2 · signal.7. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    Calling waitpid only once per SIGCHLD can leave other children unreaped. Polling without a bound wastes CPU. Treat ECHILD distinctly from EINTR and ensure one component owns each child's wait lifecycle.

    Worked reasoning trace

    Assumptions: One child exited with status 7; waitpid succeeds.

    1. Starting state

      Parent holds a packed wait status.

    2. Operation

      Check WIFEXITED, then WEXITSTATUS.

    3. Expected observation

      The decoded exit status is 7, not the raw packed integer.

    Tradeoff: Explicit reaping retains diagnostics but requires clear wait ownership.

    This is a hand-authored prediction, not captured runtime output.

    Original practice problem

    Run processes.c and verify child status 9. Design a draining waitpid(-1, ..., WNOHANG) loop that stops on zero or ECHILD, retries permitted EINTR, and records other failures. Do not interpret the packed status as the direct exit code.
