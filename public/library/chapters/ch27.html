Chapter 27 — Program Execution

exec replaces the current process image — same PID, same open fds (unless CLOEXEC), new program. Understanding exec semantics is critical for daemon design, shell implementation, and security-sensitive fd management.

There is only one real syscall: execve. The rest (execl, execlp, execle, execv, execvp, execvpe) are libc convenience wrappers that differ in how they accept arguments, search PATH, and pass the environment.

Invariant
PID, PPID, pgid, sid, cwd, umask, rlimits survive exec. Text/data/heap/stack are replaced. Fds without CLOEXEC survive.
Gotcha
Signal handlers are reset to SIG_DFL on exec (the code is gone). Ignored signals stay ignored. Pending signals are preserved.
Debugging
Use strace -f -e trace=execve to see exactly what path, args, and env are passed. Check /proc/pid/fd for leaked fds.

Mental model

Internalize these bullets. If you can explain them clearly, you can debug most real-world incidents in this area.
  • execve(path, argv, envp) is the only syscall. It loads a new program from path, replacing text/data/heap/stack entirely.
  • The "l" variants (execl, execlp, execle) take args as a variadic list terminated by (char*)NULL.
  • The "v" variants (execv, execvp, execvpe) take args as a NULL-terminated char* array.
  • The "p" variants search PATH for the executable. Without "p", the path must be absolute or relative.
  • The "e" variants accept an explicit envp array. Without "e", the current environ is passed.
  • File descriptors survive exec unless marked O_CLOEXEC (or FD_CLOEXEC via fcntl). This is how pipes work across exec.
  • Signal dispositions: handled signals reset to SIG_DFL (handler code is gone); SIG_IGN stays ignored; pending signals preserved.
  • #! (shebang) scripts: kernel reads first 2 bytes; if "#!", it parses the interpreter path and re-execs as interpreter [arg] script argv...
  • After exec: new text/data/heap/stack. Preserved: PID, PPID, pgid, sid, controlling tty, cwd, root dir, umask, rlimits, real UID/GID.
  • Set-UID/Set-GID bits on the executable change effective UID/GID on exec — a security-critical mechanism.

Edge cases & invariants

This is where production bugs live. Expand each panel and treat the bullets as test cases.
execve after fork in multithreaded programs
  • fork() in a multithreaded program only clones the calling thread. Other threads vanish. Mutexes they held are now permanently locked.
  • Between fork and exec, only async-signal-safe functions are safe. This means no malloc, no printf, no mutex operations.
  • posix_spawn() exists specifically to avoid this problem — it combines fork+exec atomically (on Linux, implemented via clone+exec).
  • If you must fork in MT code, exec immediately. The exec replaces everything, so the broken mutex state doesn't matter.
Script with no execute permission or bad shebang
  • execve returns EACCES if the file lacks execute permission (even if readable).
  • If the file has execute permission but an invalid format and no shebang, execve returns ENOEXEC.
  • execlp/execvp fall back to /bin/sh script on ENOEXEC — a legacy behavior that can be surprising.
  • Shebang line length is limited (typically 128 bytes on Linux). Extra args are passed as a single string, not split by spaces.
PATH search semantics
  • execvp searches each directory in PATH left-to-right. It stops at the first match with execute permission.
  • If PATH contains "." or empty components (":/usr/bin" or "/usr/bin:"), the current directory is searched — a security risk.
  • If no "/" in the filename, PATH is searched. If "/" is present, it's treated as a path (no PATH search).
  • confstr(_CS_PATH) gives the standard safe PATH (/usr/bin:/bin) for privilege-safe execution.
File descriptor leaks across exec
  • Any fd without CLOEXEC survives exec. This is a common security and resource leak vector.
  • Modern practice: always open with O_CLOEXEC; selectively clear CLOEXEC only for fds the child needs (stdin/stdout/stderr, pipe ends).
  • Legacy fds (socket inherited from inetd, etc.) rely on fd inheritance by design — but document this explicitly.
  • Use /proc/self/fd or fcntl(fd, F_GETFD) to audit which fds will survive an exec.

Code patterns (C / POSIX)

These are compact patterns to internalize. Treat them as starting points: add proper error handling, timeouts, and logging. 
// execvp with error handling + O_CLOEXEC fd management
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <unistd.h>

int run_command(char *const argv[]) {
    pid_t pid = fork();
    if (pid < 0) return -1;
    if (pid == 0) {
        // Child: exec the command
        execvp(argv[0], argv);
        // exec failed — report and use _exit (not exit)
        perror(argv[0]);
        _exit(127);  // 127 = command not found (shell convention)
    }
    int status;
    waitpid(pid, &status, 0);
    return WIFEXITED(status) ? WEXITSTATUS(status) : -1;
}

// O_CLOEXEC pattern: open a log fd that won't leak to children
int open_log_safe(const char *path) {
    int fd = open(path, O_WRONLY | O_CREAT | O_APPEND | O_CLOEXEC, 0640);
    // fd is automatically closed on exec — no leak to child processes
    return fd;
}

Production checklist

If you are shipping code in this area, try to satisfy each checklist item explicitly.
  • Always open fds with O_CLOEXEC unless they explicitly need to survive exec (pipe ends for child I/O).
  • After fork, exec immediately in multithreaded programs. Use only async-signal-safe functions before exec.
  • Check execvp return (it only returns on failure). Always _exit(127) in the child on exec failure.
  • Validate and sanitize PATH before execvp in security-sensitive contexts. Never include "." in PATH for privileged programs.
  • For set-UID programs, drop privileges before exec if the child doesn't need them.
