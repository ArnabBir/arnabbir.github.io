Appendix A — Tracing System Calls

strace is the most important debugging tool for systems programming. It shows every syscall a process makes, reveals errno values, measures timing, and traces child processes. When a program misbehaves, strace turns "I have no idea" into "openat returned EACCES on /etc/shadow" in seconds.

This appendix is a practical field guide: flags you need, output you'll read, and companion tools (perf trace, ltrace) for when strace's ptrace overhead is too high.

Invariant
strace -f follows forks; every child process inherits tracing so no syscall escapes observation.
Gotcha
strace uses ptrace and slows the target 10-100x; use perf trace for lower overhead in production.
Debugging
strace -e trace=file,network,process filters by category; strace -c gives a syscall histogram.

Deep dive

Practical panels: strace workflows, output interpretation, and companion tools.
Essential strace flags
  • -f: follow fork/clone/exec and trace the full process tree. Without this, child processes run untraced and you miss half the story.
  • -tt: prefix each line with wall-clock time (HH:MM:SS.usec). -T appends per-call elapsed time in angle brackets.
  • -e trace=file: only show file-related syscalls (openat, stat, unlink, rename). Use network, process, signal, desc, memory for other categories.
  • -c: suppress per-call output; print a summary table of syscall counts, errors, and time at exit. Combine with -S to sort by time or calls.
  • -o file: redirect trace output to a file, keeping the program's stderr clean.
  • -s N: increase the maximum string size printed (default 32). Use -s 256 or -s 4096 to see full paths and buffer contents.
  • -y / -yy: decode file descriptor numbers into paths (-y) or socket addresses (-yy).
Reading strace output
  • Each line: syscall(args...) = return_value. A return of -1 means failure; the errno name follows (e.g., ENOENT).
  • Focus on the *first* failing syscall. Later failures are often cascades from the first.
  • Signals appear as --- SIGCHLD {si_signo=SIGCHLD, ...} --- between syscall lines.
  • Unfinished/resumed pairs (... and <resumed>) appear when -f shows interleaved threads.
  • Compare expected vs actual syscall sequences: missing close() reveals fd leaks; unexpected openat() reveals config file searches.
Companion tools: perf trace and ltrace
  • perf trace: uses kernel tracepoints instead of ptrace, adding ~2% overhead vs strace's 10-100x. Ideal for production profiling.
  • ltrace: intercepts dynamic library calls (malloc, free, pthread_mutex_lock) via PLT hooking. Useful for understanding library-level behavior.
  • -e fault=openat:error=ENOENT: inject faults to test error paths without modifying code. Invaluable for resilience testing.
  • strace -k: print kernel stack traces for each syscall (requires debuginfo). Helps identify which code path triggered a syscall.

Code patterns

strace command examples for different debugging scenarios. 
# Trace all syscalls with timestamps and per-call timing
strace -f -tt -T -o trace.log -- ./my_server --config /etc/app.conf

# Filter: only file-related syscalls
strace -e trace=file -y -- ls /nonexistent 2>&1

# Filter: only network syscalls (connect, accept, sendto, recvfrom, ...)
strace -e trace=network -f -- curl -s https://example.com

# Attach to a running process and trace signals + process events
strace -p 12345 -e trace=signal,process -tt

# Syscall histogram: counts, errors, time spent per syscall
strace -c -f -- make -j4

# Show wall-clock time per call and decode fd paths
strace -f -T -y -s 256 -- ./my_app

# Fault injection: make openat fail with ENOENT for testing
strace -e fault=openat:error=ENOENT:when=3 -- ./my_app

# Lower-overhead alternative using perf
perf trace -p 12345 --duration 10

# Trace library calls instead of syscalls
ltrace -e malloc+free -p 12345

Production checklist

Practical rules for using strace effectively.
  • Always use -f when tracing daemons or multi-process programs; without it you miss child syscalls.
  • Use -o to redirect traces to a file; mixing strace output with program stderr creates confusion.
  • In production, prefer perf trace over strace to avoid the ptrace performance penalty.
  • Use -c first to get a high-level picture, then drill down with -e trace= on the hot categories.
  • Remember strace output contains secrets (passwords in write() calls, tokens in connect() addresses); handle trace files securely.
