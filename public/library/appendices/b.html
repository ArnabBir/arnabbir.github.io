    APPENDIX B / F · Parsing Command-Line Options

    Command-line parsing is input validation

    A utility accepts --count=-1 and converts it into a huge unsigned allocation.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    Option parsing separates grammar from meaning. Recognizing -n is only the first stage; the supplied string still needs range, format, and policy validation. Positional arguments, a literal -- separator, missing operands, and repeated options need documented behavior.

    Contract and implementation boundary

    getopt returns option characters, -1 at the end, and error indications depending on optstring. optind identifies the remaining arguments. For integers use strtol with errno cleared, an end pointer, and explicit bounds before converting to a narrower or unsigned type. GNU getopt_long and argument permutation are not universal POSIX behavior.

    Contract references: getopt.3 · strtol.3. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    atoi cannot distinguish malformed input from a valid zero. Accepting a numeric prefix such as 12junk silently changes the user's request. A command parser should reject unreasonable resource sizes even if the number fits the machine type.

    Worked reasoning trace

    Assumptions: Count policy is decimal 1 through 100 with no suffix.

    1. Starting state

      Input is 12x.

    2. Operation

      strtol parses 12 and leaves end pointing at x.

    3. Expected observation

      Reject the argument despite the numeric prefix fitting in range.

    Tradeoff: Strict parsing avoids ambiguity but accepts fewer convenient informal inputs.

    Original practice problem

    Specify a --count option restricted to 1 through 100. Evaluate empty input, -1, 0, 1, 100, 101, 12x, and an overflowing decimal string. Keep the conversion independent from allocation so every failure can be tested without large resource use.
