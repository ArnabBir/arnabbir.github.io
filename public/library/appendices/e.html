    Read sources by authority and version

    Two accurate-looking references disagree because they describe different standards and kernels.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    Start with the interface contract for observable behavior, then use implementation documentation to explain mechanisms. Linux man-pages distinguish standards, history, notes, and bugs. POSIX Issue 8 describes the 2024 contract. Kernel documentation and glibc manuals answer different layers of a system question.

    Contract and implementation boundary

    Record the exact API, platform, version, and claim under review. For a Linux extension, avoid presenting a Linux-specific implementation detail as a portable guarantee. For a networking protocol, read the relevant RFC state and requirement language rather than inferring behavior from a browser diagram.

    Contract references: standards.7 · feature_test_macros.7 · POSIX.1-2024. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    A reachable URL is not evidence that every sentence derived from it is correct. An old example can remain compilable while relying on obsolete assumptions. A benchmark on one machine is not an API guarantee.

    Worked reasoning trace

    Assumptions: A current source says dup3 is POSIX.1-2024; deployment targets an older standard.

    1. Starting state

      Source availability and deployment availability differ.

    2. Operation

      Record Linux introduction, libc declaration, and standards edition separately.

    3. Expected observation

      Do not infer that every older POSIX system acquired dup3 retroactively.

    Tradeoff: Versioned evidence is more work but prevents timeless claims from drifting.
