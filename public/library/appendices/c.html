    APPENDIX C / F · Casting the NULL Pointer

    Pointer types still matter at variadic boundaries

    A variadic API expects a pointer sentinel but receives an integer zero of the wrong representation.

    ConceptAPI contractWorked tracePracticeSources

    The underlying idea

    A null pointer constant converts appropriately in a context with a known pointer parameter type. Variadic arguments lack that target-type conversion. An integer zero and a null pointer need not have the same size or representation. Teach the call boundary, not a blanket rule to cast every NULL everywhere.

    Contract and implementation boundary

    For an execl-style argument list, terminate with a correctly typed null pointer such as (char *) NULL as required by the interface. In ordinary prototyped C pointer parameters the conversion is already defined. Function pointers and object pointers have distinct portability rules; do not treat arbitrary casts as ABI repair.

    Contract references: stdarg.3 · exec.3 · NULL.3const. Check the documented return convention and platform notes before using an interface.

    Where reasoning goes wrong

    A cast can silence a diagnostic without making the underlying object or calling convention valid. Assuming LP64, ILP32, and all platforms pass variadic values identically makes latent bugs architecture-dependent.

    Worked reasoning trace

    Assumptions: An execl-style variadic list ends after argv entries.

    1. Starting state

      The sentinel position has no declared pointer parameter type.

    2. Operation

      Pass (char *) NULL as the sentinel.

    3. Expected observation

      The call supplies the expected pointer type rather than relying on integer-zero representation.

    Tradeoff: Explicit types at variadic boundaries improve portability; blanket casts can hide other errors.

    Compare a prototyped takes_pointer(char *) call with a variadic sentinel call. Annotate which argument positions have a target type at the call site. Compile declaration probes with strict warnings, but explain why absence of a warning is not a proof of portable ABI correctness.
